# 権限昇格と足場 · Linux 権限昇格決定木

### 低権限 shell を得た後の列挙順序をどう定めるか
**Q1**: www-data / 一般ユーザーのリバース shell に着地したばかりで、やることが多すぎる。先にどこを見て、どんな順序で列挙すれば時間を無駄にしないか?
**A1**: 「低コスト高命中優先」の漏斗に従う。第一梯隊(30 秒以内、ほぼゼロリスク):`id`/`sudo -l`/`uname -a`/`hostname`/`ss -tlnp`。この 4 つが後続のどの幹に進むかを決める。sudo に成果があれば sudo に進み、カーネルが古ければカーネルを予備に残し、ローカルリッスンポートが内部サービスを露出すればサービス面に進む。第二梯隊:SUID/SGID リスト、`getcap -r /`、cron、書き込み可能な機微パス。第三梯隊:ディスク全体の認証情報探索。判定基準は「1 コマンドで結論が出るものを先に実行し、大量のファイルを読んで徐々に掘るものを後回しにする」ことである。
**Q2**: 手動で 1 つずつ打つのが遅すぎる。直接 linpeas を走らせてもよいか?
**A2**: よいが、場面による。外向きがあり/ファイルを配置でき、配置検知を恐れないなら、自動化スクリプト(linpeas/linenum)の一気実行が最速である。しかし数百行の出力で重点が埋もれやすく、大きなスクリプトの配置は EDR/AV の命中リスクがある。安全なやり方:先に手動で第一梯隊を走らせて方向を定め、自動化スクリプトで盲区を補い、赤くマークされた 95%/99% 項目を重点的に見て、黄色のノイズに流されない。
**Q3**: 列挙で大量の「可能なベクトル」が出た。優先順位をどう付けるか?
**A3**: 「確実性 × 隠蔽性 × 安定性」で並べる。確実性:sudo NOPASSWD の GTFOBins バイナリ > 理論上存在するカーネル CVE。安定性:設定系権限昇格(sudo/suid/cron/cap)はほぼ崩れず、カーネル exp は panic し得る。そのため設定系を先に絞り尽くし、カーネル exp を最後の手段にする。
**Q4**: この shell 自体が不安定で、動くとすぐ切れる。まだどう列挙するか?
**A4**: 先に安定化してから列挙する(tty 昇格の条項参照)。不安定な shell で重量級スクリプトを走らせず、先に手動で第一梯隊を走らせ、重要な出力(sudo -l、suid リスト)を保存しておく。切れても情報はある。同時に別の場所に 2 本目のより安定したチャネル(SSH key、web shell、スケジュールタスクの折り返し)をすぐに立てる。
**Q5**: 全列挙を終え、明らかなベクトルがない場合、この経路が「遮断」されたらどこへ方向転換するか?
**A5**: 直交ディメンションに方向転換する:(1) 時間ディメンション。pspy で cron/root プロセスを監視する。静的列挙では見えないスケジュールタスクが現れる。(2) 認証情報横展開のディメンション。「本機の縦方向権限昇格」を諦め、パスワード/鍵を探して横展開か踏み台にする。(3) 権限グループのディメンション。`id` の追加グループ(docker/lxd/disk/adm/shadow)を見直す。グループ権限は最も見落とされやすい権限昇格面である。1 つの面に固執して掘り尽くすより、ディメンションを替える。

### sudo -l に出力があるとき、どう絞り尽くすか
**Q1**: `sudo -l` が、root でパスワード不要であるコマンドを実行できると示す。それをどう root shell に変えるか?
**A1**: 先にこのバイナリが GTFOBins に `sudo` 項目を持つかを見る。大多数の一般的なプログラム(find/vim/less/awk/python/tar/env など)には既成のエスケープ法があり、当てはめるだけでよい。核心の考え方:root で動くこのプログラムに、任意コマンドの実行か shell の spawn、または任意ファイルの読み書きをさせる。判定基準:GTFOBins に該当すればほぼ確実に取れる。
**Q2**: そのバイナリが GTFOBins になく、カスタムスクリプトか見慣れないプログラムの場合はどうするか?
**A2**: 手動で分析する。スクリプトなら `cat` で読む:どの子コマンドを呼ぶか(相対パスなら PATH ハイジャックできる)、`eval`/ユーザー入力の連結があるか、どの制御可能なファイルを読み書きするか。バイナリなら `strings`/`ltrace` でどの外部プログラムやライブラリを呼ぶかを見る。カスタムプログラムの定番の穴:子プロセス呼び出しが絶対パスでない、環境変数を信頼する、予測可能な一時ファイルを書く。
**Q3**: sudo ルールに `env_keep` があるか `env_reset` がない場合、利用できるか?
**A3**: できる。これは高価値シグナルである。`LD_PRELOAD`/`LD_LIBRARY_PATH` が保持されていれば悪意ある so をロードして権限昇格できる。`PYTHONPATH`/`PERL5LIB` が保持されていればモジュールをハイジャックできる。`BASH_ENV` が保持されていて sudo が bash スクリプトを走らせるなら注入できる。env_keep に動的リンク関連の変数が見えれば、ほぼ点数のプレゼントである。
**Q4**: sudo ルールが引数を限定している(例 `sudo systemctl status X` しかできない)場合、引数に阻まれたらどうするか?
**A4**: 引数が許す範囲内の「越境」点を探す。systemctl status は pager(less)を呼び、less 内で `!sh` できる。pager/editor を持つコマンドの多くがこうしてエスケープできる。ルールがワイルドカード `*` を使うなら、追加引数やパス遷移を試す。本当にロックされたら次の A5 に進む。
**Q5**: sudo が何も与えない、またはパスワードが必要で私が持たない場合、この経路が遮断されたらどこへ方向転換するか?
**A5**: sudo 自身の脆弱性のディメンションに方向転換する:`sudo --version` を見る。旧バージョンは Baron Samedit(ヒープオーバーフロー。sudo コマンドを 1 つも実行できる必要がなく、sudo が存在して脆弱なバージョンなら可能)などのローカル権限昇格を受ける。sudo バージョンもきれいなら、sudo 面を完全に諦め、SUID/capabilities/cron/カーネルなどの他の直交面に方向転換する。

### SUID/SGID バイナリの調査と利用
**Q1**: `find / -perm -4000 2>/dev/null` で大量の SUID が出た。どれを見る価値があるか?
**A1**: システム既定のもの(passwd/su/mount/ping/pkexec などの標準セットは「背景ノイズ」。ただし pkexec は PwnKit を別途留意する)をフィルタする。重点は:非標準パスのもの、名前が見覚えないもの、バージョンを調べられるもの。リストを GTFOBins の SUID 項目と照合し、該当すれば直接利用する。見覚えないカスタム SUID プログラムが最も肥沃である。開発者が手抜きで設定したことが多く、コマンド注入かパスの問題がある。
**Q2**: 一般的なプログラム(例 find/nmap 旧版/cp)が SUID ビットを持つ場合、どう使うか?
**A2**: 直接 GTFOBins の SUID セクションを引く。find は `-exec /bin/sh -p \;` できる(`-p` は有効 uid を保持する点に注意)。ファイルを書けるものは /etc/passwd を上書きできる。ファイルを読めるものは shadow を読める。重要な詳細:SUID shell では `-p` で bash/dash の権限降下による euid 喪失を防ぐ。
**Q3**: カスタム SUID バイナリでソースがない。どう穴を探すか?
**A3**: `strings` で何を呼ぶか見る。`ltrace`/`strace` を 1 回走らせて system()/exec 呼び出しとファイルアクセスを見る。定番の命中:絶対パスなしで `system("service ...")` のように子コマンドを呼ぶ → PATH ハイジャック。ユーザー入力をコマンドに連結する → コマンド注入。私が書き込める設定/ログファイルを open する。
**Q4**: 子コマンドを呼ぶが絶対パスを使い、PATH ハイジャックできない。他に手はあるか?
**A4**: 関数ハイジャックに方向転換する。プログラムが動的リンクで、私が LD_PRELOAD を設定できるなら(SUID は通常の LD_PRELOAD を消す点に注意。ただしプログラム自身が setuid 前に環境を読む、`LD_PRELOAD` が消されていない辺角、または `LD_LIBRARY_PATH` が書き込み可能なディレクトリを指し RUNPATH が許す場合)、libc 関数をハイジャックできる。またはそれが読む書き込み可能なファイルでデータ注入する。または書式文字列/バッファオーバーフローのバイナリ脆弱性がないか見る。
**Q5**: SUID 面を全て試して突破できず、遮断されたらどこへ方向転換するか?
**A5**: capabilities 面に方向転換する。`getcap -r / 2>/dev/null`。多くの現代システムは SUID を cap で代替する(cap_setuid/cap_dac_read_search/cap_dac_override は全て権限昇格か任意読み取りができる)。これは SUID リストでは見えない独立ベクトルである。それも駄目なら cron/書き込み可能 service の時間面に方向転換する。

### capabilities 権限昇格
**Q1**: `getcap -r /` であるバイナリが capability を持つと出た。どの cap が直接権限昇格できるか?
**A1**: 高価値 cap:`cap_setuid`(直接 setuid(0)。この cap を持つ python/perl は 1 行で権限昇格)、`cap_dac_read_search`(読み取り権限を迂回して shadow/root ssh key を任意に読む)、`cap_dac_override`(書き込み権限を迂回して /etc/passwd を変更)、`cap_sys_admin`(ほぼ万能でマウント/エスケープ可能)、`cap_sys_ptrace`(root プロセスへの注入)、`cap_sys_module`(カーネルモジュールをロードして直接 ring0)。これらを見たらほぼ権限昇格確定である。
**Q2**: `cap_setuid` を持つのが python の場合、どう実行するか?
**A2**: `python -c 'import os; os.setuid(0); os.system("/bin/sh")'`。cap は setuid(0) を元の権限なしで成功させる。perl/ruby/node も同様で、どのインタープリタが cap を持つかによる。判定基準:そのインタープリタが setuid システムコールを呼べればよい。
**Q3**: cap が `cap_dac_read_search` で、読み取りしかできず実行できない場合、どう換金するか?
**A3**: 任意読み取りを認証情報に転換する。読むのは /etc/shadow で root hash をオフライン爆破、/root/.ssh/id_* で直接 root に SSH、データベース設定/履歴コマンドで認証情報を得て横展開。読み取り権限自体は shell を与えないが、鍵を読めば身元を得たのと同じである。
**Q4**: cap が `cap_dac_override`(書き込み可)の場合、どう使うか?
**A4**: 任意書き込みを権限昇格に転換する:/etc/passwd に UID=0 のアカウントを追加する(既知パスワードの hash を付ける)、root の authorized_keys を書く、root が実行する cron/スクリプトを書く。どれを選ぶかは、どの経路が最も速くトリガーされ、最も安定するかによる。
**Q5**: getcap が何も列挙しない場合、遮断されたらどこへ方向転換するか?
**A5**: cap 面が空なのはよくある。SUID 面(まだなら)かグループ権限面に方向転換する。さらに cap はファイルでなくコンテナ/名前空間層に設定されていることがある点に注意する。コンテナ内なら `capsh --print` でプロセス自身の cap を見る。`cap_sys_admin` などのコンテナ cap はエスケープベクトルであり、ファイル cap のディメンションではなくコンテナエスケープのディメンションに属する。

### カーネル exploit をいつ使うか、どうリスクを制御するか
**Q1**: `uname -a` がカーネルが非常に古いと示す。カーネル exp を使いたい。今撃つべきか?
**A1**: カーネル exp は「最後の手段」であり「第一選択」ではない。panic で対象マシンを落とし、他チーム/本番に影響し、検知される可能性があるからである。決定:先に設定系(sudo/suid/cap/cron/グループ)が全て無路と確認してからカーネルを考える。かつ成熟して安定した exp(PwnKit/DirtyPipe/DirtyCow/OverlayFS のような大量検証済みのもの)を優先し、PoC 品質が低く崩れやすいものを避ける。
**Q2**: カーネルバージョンを使える exp にどう正確にマッピングするか?
**A2**: 3 要素である:カーネルバージョン番号(uname -r)、ディストリビューションとそのパッチレベル(cat /etc/os-release、カーネル build 日付)、アーキテクチャ。ディストリビューションはパッチを backport するので、「バージョン番号が脆弱性範囲内」は「未パッチ」を意味しない。linux-exploit-suggester で初篩し、その結果を「結論」ではなく「候補」として扱い、パッチ状態を 1 つずつ照合する。
**Q3**: 対象マシンにコンパイラがない(no gcc)場合、カーネル exp が C ソースならどうするか?
**A3**: 「他所でコンパイル」に方向転換する。ローカルか攻撃マシンで、一致するカーネルヘッダ/アーキテクチャで静的バイナリにクロスコンパイルして送る。または既存のプリコンパイルバイナリ/コンパイル不要の exp(一部はスクリプトか pipe/ファイル原語を利用)を選ぶ。または同じディストリビューションのマシンを探してコンパイルする。本番対象マシンにコンパイラを入れるのは避ける。
**Q4**: カーネル exp を撃って成功も崩壊もしなかった場合、問題をどう判断するか?
**A4**: 調査する:アーキテクチャ/バージョンが正確に一致するか、特定の config が必要か(user namespaces 有効、ある sysctl)、SMEP/SMAP/KASLR などの緩和がこの exp を無効にしていないか。一部の exp は複数回必要(競合)。緩和が揃って無効と確認したら、無理に試さず記録して他の面に方向転換する。
**Q5**: カーネル exp がマシンを直接崩した/全カーネル exp が遮断された場合、どうするか?
**A5**: 崩れたなら、再起動して回復するのを待てるか評価する(本番対象は慎重に。スコアに影響し得る)。戦略上は直交面に方向転換する:横展開に戻る。本機の root が不要かもしれない。本機の認証情報を得て、設定がより緩いマシンへ横展開するか、ドメイン内経路を直接探す方が、このマシンのカーネルに固執するより効率的である。

### cron スケジュールタスク権限昇格
**Q1**: cron 権限昇格点を探したい。どこを調べ、何を見るか?
**A1**: `cat /etc/crontab`、`ls -la /etc/cron.*`、`/var/spool/cron/*`、各ユーザーの crontab。重点は:root で動くタスク + それが実行するスクリプト/プログラムを私が書き込める、またはそれが呼ぶコマンドが相対パス(PATH ハイジャック)、またはワイルドカードを使う(ワイルドカード注入)。判定基準:root のスケジュール実行 + どの環か 1 つ制御可能 = 権限昇格。
**Q2**: crontab で root があるスクリプトを走らせ、そのスクリプトファイルに私が書き込み権限を持つ場合、どうするか?
**A2**: スクリプトにリバース shell か `cp /bin/bash /tmp/rootbash; chmod +s /tmp/rootbash` を追記し、次回トリガーを待つ。上書きでなく追記にして、元機能を壊して発見されないようにする。トリガー後 `/tmp/rootbash -p` で root を取る。cron 周期に注意し、1 周期辛抱強く待つ。
**Q3**: スクリプト自体は書き込み不可だが、それが呼ぶコマンドが絶対パスを書いていない。PATH をどうハイジャックするか?
**A3**: crontab 先頭の `PATH=` 定義を見る。PATH に私が書き込めるディレクトリが含まれ、システムディレクトリより前なら、そのディレクトリに同名の悪意あるプログラムを置く。PATH が制御できないなら、スクリプト内で `cd` する作業ディレクトリを私が書き込めるかを見る(相対呼び出し)。核心:root がコマンド名を解決する際、私のファイルに先に当たるようにする。
**Q4**: cron があると疑うが crontab ファイルで全て見えない(systemd timer や隠しタスク)場合はどうするか?
**A4**: pspy に方向転換する。root なしでリアルタイムにプロセス作成と cron 実行を監視でき、crontab で読めない systemd timer、スケジュールスクリプト、それらの完全なコマンドラインとパスが見える。これが「見えないスケジュールタスク」発見の重要なツールで、静的列挙の盲区を補う。
**Q5**: cron 面を全て調べ、制御できる環がない場合、遮断されたらどこへ方向転換するか?
**A5**: systemd のディメンションに方向転換する。`systemctl list-timers`、書き込み可能な .service/.timer ユニットファイル、ExecStart が指す書き込み可能なバイナリを確認する。systemd timer は cron の現代の代替で、多くのマシンは cron がなく全て systemd である。それも駄目ならファイル監視で他の自動化トリガー点を探す。

### 書き込み可能なファイルシステムパスと認証情報収集
**Q1**: 明らかな sudo/suid ベクトルがない。認証情報を探りたい。先にどこを探るか?
**A1**: 高命中位置:ユーザーホームディレクトリ(.bash_history、.ssh/、.config、.aws/、.git-credentials)、web アプリ設定(データベース接続文字列、API key。wp-config.php、.env、settings.py)、/var/www、バックアップファイル(.bak/.old/.swp)、ログ。history には平文パスワードが残りやすい(ユーザーが手違いでパスワードをコマンドラインに打つ)。設定ファイルにはほぼ必ず DB/サービス認証情報がある。
**Q2**: 大量のパスワード/hash を見つけたら、どう使うか?
**A2**: 分類して利用する:平文パスワードは先に `su` で他のユーザーと root に試す(パスワード再利用は非常に多い)、SSH を試す、sudo を試す。hash はオフライン爆破に回す(先に種別を判断)。DB 認証情報でデータベースに入ると、より多くの認証情報があるか、それ自体が root で動いて権限昇格できるかもしれない。鍵は直接 SSH。判定基準:先に横展開の再利用(コスト最低)、次に爆破。
**Q3**: ディスク全体のパスワード検索を漏れなく行う手順は?
**A3**: `grep -rniE 'password|passwd|pwd|secret|api[_-]?key|token' /etc /var/www /opt /home 2>/dev/null`。.env/.yml/.ini/.php/.py 設定ファイルの検索、.ssh 秘密鍵の検索、history ファイルの検索を組み合わせる。linpeas には専用の認証情報収集モジュールがあり漏れを補える。メモリとプロセスのコマンドライン(ps にパスワード付き引数があるかもしれない)も忘れない。
**Q4**: 秘密鍵を見つけたが passphrase で開けない、またはパスワード爆破が進まない場合、遮断されたらどうするか?
**A4**: passphrase 付き秘密鍵は ssh2john で形式変換してオフライン爆破できる(弱い passphrase は破れることが多い)。爆破全体が進まないなら、考えを転換する:既存認証情報の解読を追わず、「認証情報不要」の権限昇格面(suid/cron/カーネル)を探すか、既存 shell で他マシンへ横展開する。認証情報収集は横展開の燃料であり、縦方向が行き詰まったとき、それは横展開への鍵になることが多い。
**Q5**: 何も探れず、認証情報面が遮断されたら、どこへ方向転換するか?
**A5**: プロセス/メモリのディメンションに方向転換する:`ps aux` でサービスがパスワードをコマンドライン引数に置いていないか見る。ネットワークのディメンションに方向転換する:ローカルでリッスンするサービス(サービス面の条項参照)に既定/弱いパスワードがあるかもしれない。ファイル監視に方向転換する:pspy でプロセスが周期的に認証情報付きで起動するのを捕まえられるかもしれない。認証情報は常にディスク上にあるとは限らず、実行時にもある。

### ローカルリッスンサービスの権限昇格(127.0.0.1 にしか公開しないサービス)
**Q1**: `ss -tlnp` で 127.0.0.1 だけをリッスンするポートがいくつか見えた(例 3306/6379/その他)。これは何を意味するか?
**A1**: これらは「内部サービス」で、外網からは攻められないがマシン内部から直結でき、かつ root か高権限ユーザーで動き、設定が緩いことが多い(「どうせ本機しか接続できない」ため)。これはひどく過小評価された権限昇格面である。1 つずつ識別する:データベース(mysql/postgres)、キャッシュ(redis)、管理インターフェース、メッセージキュー、自作サービス。
**Q2**: redis がローカルだけをリッスンしている。どう権限昇格するか?
**A2**: 先にパスワードなし/弱いパスワードで接続する。redis が root で動くなら、定番の手法はファイル書き込み原語である。dir と dbfilename を設定して RDB を authorized_keys / cron ディレクトリ / web ルートに書くか、モジュールロードを使う。判定基準:redis にファイル書き込み能力がある + 高権限で動く + 私が書き込みパスを制御できる = 権限昇格。
**Q3**: mysql/postgres が root で動く場合、権限昇格できるか?
**A3**: できる。DB 高権限アカウント(web 設定から得ることが多い)を得たら:mysql は UDF(user defined function)でシステムコマンド実行、ファイル書き込み(FILE 権限 + secure_file_priv が許可)。postgres は COPY ... PROGRAM か言語拡張でコマンド実行。DB プロセスの OS ユーザーが誰かで、実行するコマンドのユーザーが決まる。root なら直接権限昇格である。
**Q4**: ローカルポートが知らない自作サービスだった。どう手を付けるか?
**A4**: 先にプロトコルを把握する:`nc`/curl で接続して banner とレスポンスを見て、通信フォーマットを掴む。自作ローカルサービスの定番の穴:無認証の管理コマンド、コマンド注入、パス遷移、逆シリアル化。開発者が「ローカル=信頼できる」と仮定するため、認証を一切付けていないことが多い。root で任意コマンドを実行できれば権限昇格である。
**Q5**: ローカルサービスを全て試し、強いパスワードか攻められない場合、遮断されたらどこへ方向転換するか?
**A5**: 「これらの認証情報が横展開できるか」に方向転換する。DB に保存されたユーザー/パスワードは他所の認証情報かもしれない。または:そのサービスの設定ファイル/データディレクトリが読めるかもしれず、中に他の認証情報や鍵がある。それも駄目ならサービス面を諦め、suid/cron/cap の設定面に戻る。ローカルサービスは重要だが唯一の面ではなく、通らなければ替える。

### グループ権限の権限昇格(docker/lxd/disk/adm/shadow など)
**Q1**: `id` が私がいくつかの非既定グループにいることを示す。どのグループが権限昇格と等しいか?
**A1**: 危険グループ早見:`docker`(root と等価。ホスト / をマウントできる、特権コンテナを起動できる)、`lxd`/`lxc`(同様にホストディスクをマウント)、`disk`(ブロックデバイスを直接読み書きできる = ファイルシステム全体の読み書きで権限を迂回)、`shadow`(/etc/shadow を読んで全 hash を取れる)、`adm`(ログを読める、認証情報を含むことが多い)、`video`/`kmem`、`sudo`/`wheel`(パスワードが必要だが試す価値がある)。docker/lxd/disk を見たらほぼ root と等しい。
**Q2**: docker グループにいる。どう権限昇格するか?
**A2**: `docker run -v /:/mnt --rm -it <任意イメージ> chroot /mnt sh`。ホストのルートをコンテナにマウントして chroot すれば、あなたがホストの root である。ローカルにイメージがなければ最小イメージか既存イメージでよい。原理:docker デーモンは root で動き、docker グループメンバーはそれに任意のホストパスをマウントさせられる。
**Q3**: disk グループで docker がない場合、どう使うか?
**A3**: disk グループは /dev/sdaX などのブロックデバイスを読み書きできる。`debugfs /dev/sdaX` で任意ファイルを直接読む(shadow、root ssh key を含む)。ファイル権限を迂回する。またはブロックデバイスを直接編集して書き込む。ファイルシステム全体の読み書き権限を持つことに等しく、鍵/hash を読むか passwd を変更できる。
**Q4**: lxd グループだがシステムに既成コンテナイメージがなく、インポートできない場合はどうするか?
**A4**: 「イメージを持ち込む」ことに方向転換する。体積が極小の alpine 系 rootfs をイメージとしてインポートする(オフラインで送れる)。その後 `security.privileged=true` でホスト `/` をマウントしたコンテナを起動し、コンテナ内がホストの root である。イメージを送れないなら、一歩退いてこのグループに他の能力があるか見るか、他の権限昇格面に替える。
**Q5**: グループに危険なものがなく、グループ権限面が遮断されたらどこへ方向転換するか?
**A5**: 標準の suid/cron/cap/カーネル面に方向転換する。グループ権限は「あれば即殺、なければ飛ばす」の素早い確認項目で、`id` で一目で見終わる。それに固執せず、なければ即別の直交ディメンションに方向転換する。

### writable な /etc/passwd または /etc/shadow
**Q1**: /etc/passwd を私が書き込めると分かった。どう直接 root を取るか?
**A1**: passwd に UID=0 GID=0 のアカウントを 1 行追加し、パスワードフィールドに私が知る平文に対応する hash を入れる(openssl passwd か mkpasswd で生成)。その後 `su` でその新アカウントに切替えれば root である。またはより隠蔽的に:ある既存アカウントの 2 番目のフィールドの `x` を私の生成した hash に置換し、既存 root 項目のパスワードを直接変更する。判定基準:passwd が書き込み可能 = 即権限昇格。
**Q2**: /etc/shadow が書き込み可能で passwd でない場合、どう使うか?
**A2**: 既知パスワードの hash を生成し、shadow の root 行の hash フィールドを置換し、`su root` で既知パスワードでログインする。shadow が書き込み可能であることは、任意アカウントのパスワードを設定できることと等価である。
**Q3**: /etc/passwd が読み取り専用で書き込めないが、中のあるアカウントの 2 番目のフィールドが直接 hash(x でない)であるのを読んだ場合はどうするか?
**A3**: 旧式か設定ミスのシステムは hash を passwd に置く(全員可読)。これらの hash を直接オフライン爆破し、破れればそのユーザー/root のパスワードになる。これは「読み取り権限」の換金の一種である。
**Q4**: passwd を書けるが、hash を生成する openssl/mkpasswd ツールがない場合はどうするか?
**A4**: 攻撃マシンでオフラインで hash を生成して貼り付ける。対象マシンにツールは不要。従来の DES/crypt は手計算も可能で、既知の公開サンプル hash `AzL1zWgcbGwU:0:0`(既知平文に対応)を使える。核心は hash をローカルで生成し、対象マシンは書き込まれるだけであること。
**Q5**: passwd/shadow がどちらも書き込み不可(正常な場合)の場合、この線が遮断されたらどこへ方向転換するか?
**A5**: これは元々低確率の設定ミス確認項目で、書き込み不可は正常である。「間接的に書き込む能力を得られるか」に方向転換する。例:ある cap_dac_override バイナリ、ある root cron、ある制御可能な root サービスが passwd を書ける。どれもなければ他の直交面に方向転換する。

### shell の安定化(tty 昇格)と作業面の維持
**Q1**: リバース shell がダム shell で、tab 補完が使えず、Ctrl-C が直接切断し、sudo がエラーを返す。先に何をするか?
**A1**: 権限昇格前に、まず対話型 tty に昇格する。そうしないと多くの操作(sudo の対話パスワード入力、su、vim エスケープ、ssh)ができない。標準フロー:`python3 -c 'import pty;pty.spawn("/bin/bash")'` で半対話を取り、`Ctrl-Z` でローカルに戻って `stty raw -echo; fg`、戻って `export TERM=xterm; stty rows.. cols..` を設定する。全対話 tty を得れば Ctrl-C が切れず、補完と履歴が使える。
**Q2**: 対象マシンに python がない場合、どう tty を昇格するか?
**A2**: 原語を替える:`script -qc /bin/bash /dev/null`、`socat`(あれば最も完全な pty を与える)、perl で pty 経由の `exec "/bin/sh"`、または `expect`。どれもなければ次善として stty を手動調整し、少なくとも sudo の対話を可能にする。判定基準:目標は対話プログラムを載せられる pty を取ることである。
**Q3**: なぜ権限昇格前に必ず shell を安定させる必要があるか?
**A3**: 多くの権限昇格動作は対話に依存するからである。sudo はパスワード入力、su は tty、GTFOBins の vim/less エスケープは端末、カーネル exp は時に対話確認が必要。ダム shell ではこれらが静かに失敗するか「must be run from a terminal」を返し、「この経路は通らない」と誤判断させる。安定化は「ツール問題」が「ベクトル問題」に化けるのを排除する。
**Q4**: shell が非常に不安定で数分で落ち、権限昇格が終わらない場合はどうするか?
**A4**: 即座に冗長チャネルを構築する:現在のユーザーの authorized_keys に SSH key を書いて安定した SSH を取る(できれば)、または cron/systemd のスケジュール折り返しを足す、または web shell を落とす。安定した足場を得てから余裕を持って権限昇格する。いつ切れるか分からない tcp 1 本に全てを賭けない。
**Q5**: rbash / 制限付き shell に落ち、コマンドが全て制限されている。これは遮断か、どう方向転換するか?
**A5**: 制限付き shell エスケープのディメンションに方向転換する:実行を許され、子 shell を spawn できるプログラム(vi/vim の `:!sh`、awk/find/less/man の shell エスケープ、ssh -t の強制コマンド、`bash --noprofile`、`-c` を持てるインタープリタ)を探す。rbash は現在の shell の PATH とリダイレクトだけを制限するので、何かのプログラムで制限のない子プロセスを spawn できればエスケープである。抜けたら正常に列挙と権限昇格を行う。

### コンテナ内 vs 物理マシンの判定とコンテナエスケープ
**Q1**: shell を得て、先にコンテナ内か物理/仮想マシンかをどう判断するか?
**A1**: 判定基準を組み合わせる:`/.dockerenv` ファイルが存在する、`cat /proc/1/cgroup` に docker/lxc/kubepods がある、`ps` で PID 1 が systemd/init でなくアプリケーションである、`hostname` がランダムな 16 進である、`mount` が overlay ファイルシステムを示す、ネットワークが単一の veth だけである。コンテナかの判定が権限昇格の目標を決める:コンテナ内で「コンテナ root への権限昇格」は意味が薄く、本当の目標は「ホストへのエスケープ」である。
**Q2**: コンテナ内で既にコンテナ内 root と確認したら、エスケープ点をどう探すか?
**A2**: 確認する:(1) `--privileged` か(`capsh --print` で大量の cap、特に cap_sys_admin があるか)。(2) docker.sock がマウントされているか(`/var/run/docker.sock` が存在すればホスト docker を指揮できる)。(3) 危険なマウント(ホスト / または /proc がマウントされている)。(4) 危険な cap(sys_admin/sys_module/dac_read_search)。どれか 1 つに該当すればエスケープ経路がある。
**Q3**: コンテナ内に docker.sock がある。どうエスケープするか?
**A3**: sock の存在はコンテナ内からホストの docker API を呼べることを意味する。docker CLI か直接 curl で sock を叩き、ホスト `/` をマウントした新コンテナを起動して chroot すれば、ホストの root である。ホスト上の docker グループ権限と等価である。
**Q4**: 特権コンテナ(privileged)だが docker.sock がない。どうエスケープするか?
**A4**: 特権コンテナはホストデバイスにアクセスできる。定番法:`fdisk -l` でホストディスクデバイスを探し、コンテナ内に mount してホストファイルシステムを直接読み書きする。または cgroup release_agent 手法(cgroup v1)でホストに root でスクリプトを実行させる。または cap_sys_module でカーネルモジュールをロードする。特権 = デバイスと cap が全て開放され、エスケープ経路は多い。
**Q5**: コンテナが何も設定ミスしていない(非特権、sock なし、危険マウントなし、cap がきれいに削減)場合、エスケープが遮断されたらどこへ方向転換するか?
**A5**: 2 つの直交面に方向転換する:(1) カーネル面。コンテナとホストはカーネルを共有するので、カーネル exp 1 つでコンテナからホストの ring0 に直接上がれる可能性があり、コンテナ設定に依存しない。(2) 横展開面。コンテナ内のアプリ認証情報、環境変数、マウントされた secret、到達できる内部サービス(他のコンテナ、k8s API、ホストサービス)を使う。これらで横展開する方が、無理なエスケープより現実的なことが多い。無理なエスケープが通らなければカーネルかネットワークを攻める。

### ワイルドカード注入(wildcard injection)
**Q1**: root cron が私が書き込めるディレクトリで `tar -czf backup.tar.gz *` や `chown -R ... *` のような実行をしているのを見た。利用できるか?
**A1**: できる。これはワイルドカード注入である。`*` は shell にディレクトリ内のファイル名へ展開され、私が「コマンドラインオプションのようなファイル名」を作れれば、それらが引数としてコマンドに渡される。判定基準:root 実行 + コマンドに `*` がある + 私がディレクトリを書き込める。
**Q2**: ファイル名を tar の権限昇格引数にどう変えるか?
**A2**: tar は `--checkpoint` と `--checkpoint-action=exec=...` に対応する。ディレクトリに `--checkpoint=1`、`--checkpoint-action=exec=sh runme.sh` という名前の空ファイルを作り、runme.sh を置く。tar が `*` を展開する際、これらのファイル名をオプションとして解析し、root で runme.sh を実行する。
**Q3**: コマンドが tar でなく rsync/chown/chmod などの場合、注入できるか?
**A3**: そのコマンドに「コマンド実行や権限変更ができる」危険なオプションがあるかを見る。rsync には `-e`/`--rsh`。chown/chmod は `--reference=file` で権限を私の制御するファイルに合わせられる。考え方は統一:そのコマンドのオプションマニュアルを調べ、「引数で副作用をトリガーする」オプションを 1 つ探し、対応するファイル名を作る。
**Q4**: ディレクトリに既に正常ファイルがあり、私が足したオプションファイルが元コマンドを壊してエラーになり発見されないか?
**A4**: 可能性はある。tar の checkpoint 注入は通常、パッケージング成功に影響せず、比較的隠蔽的である。しかし一部の注入は元タスクをエラーにさせる。比較検討する:権限昇格成功後、即座にこれらの偽装ファイルを削除して現場を復元する。または副作用が最小のオプションを選ぶ。レッドチームは撃った後の痕跡消去を重視する。
**Q5**: ディレクトリが書き込み不可、またはコマンドがワイルドカードを使っていない場合、このベクトルが遮断されたらどこへ方向転換するか?
**A5**: ワイルドカード注入は「書き込み可能ディレクトリ + ワイルドカード + root 実行」の 3 つが揃う必要があり、1 つ欠ければ適用不能で、正常である。cron 面の他の利用方式(スクリプト書き込み、PATH ハイジャック)に戻るか、別の直交面に替える。これは機会型ベクトルで、あれば使い、なければ強要しない。

### PwnKit / pkexec と polkit 系の権限昇格
**Q1**: システムに pkexec(SUID)があり、他にベクトルがない。PwnKit を試す価値はあるか?
**A1**: ある。pkexec はほぼ全ての Linux デスクトップ/サーバーに入っており、PwnKit(CVE-2021-4034)の影響面は極めて広い。メモリ破壊だが極めて安定し、ほぼ崩れない。「カーネル exp が冒険すぎ、設定面も無路」のときの黄金の中間選択肢である。先に pkexec バージョンが影響範囲で未パッチかを確認する。
**Q2**: pkexec に PwnKit があり得るかをどう素早く判断するか?
**A2**: polkit/pkexec パッケージのバージョンとパッチ日付を見る。この穴は非常に古く広範囲で、更新を怠るマシンの多くが今も中る。先に検知型 PoC(実際の権限昇格はせず判定だけ)を走らせるか、安定した exp を直接試す。カーネル exp と違い panic しないので、試行錯誤コストが低い。
**Q3**: pkexec はあるがパッチ済みの場合、別の polkit 経路はあるか?
**A3**: polkit エコシステムには他の CVE がある(例 より古い CVE-2021-3560。dbus 競合で認証を迂回してユーザーに管理者を付与)。pkexec が修正済みなら、polkit/accountsservice/dbus の組み合わせの他の既知の穴を見る。判定基準:対象が脆弱なバージョンの policykit デーモンを動かしているか。
**Q4**: exp をコンパイルして走らせたが「無効」と出る。どこが間違っている可能性があるか?
**A4**: PwnKit 系は環境に敏感である:本当に未パッチか、glibc バージョン、一部の堅牢化(ベンダーが pkexec に非公式緩和を当てた)を確認する。急いで死刑にせず、別の実装バージョンに替えて試す(PoC ごとに品質差が大きい)。パッチが揃っていると確認したら記録して他の面に方向転換する。
**Q5**: pkexec がそもそも存在しない、または完全に修正済みの場合、この線が遮断されたらどこへ方向転換するか?
**A5**: 他の「広域で安定したローカル権限昇格」候補に方向転換する:DirtyPipe(CVE-2022-0847。カーネル 5.8+ の区間、読み取り専用ファイルへの任意書き込み、極めて安定)、Baron Samedit(sudo)、OverlayFS 系。これらと pkexec は並ぶ「高安定性権限昇格ライブラリ」で、1 つが修正済みなら次を試し、あなたの安定権限昇格武器庫を構成する。

### DirtyPipe / DirtyCow 系メモリ原語の権限昇格
**Q1**: カーネルバージョンが DirtyPipe(5.8–5.16 のある区間)の範囲に入る。それを使いたいが、どんな能力を与えるか?
**A1**: DirtyPipe は「読み取り専用ファイルへの任意書き込み」原語を与える。それ自体は直接 shell を与えず、本来書き込み不可のファイルを変更できるようにする。換金経路:/etc/passwd を変更(root パスワード除去か UID0 追加)、root が実行する SUID プログラム/スクリプトを上書き、sudoers を変更。判定基準:カーネルが区間内 + 未パッチ。
**Q2**: DirtyPipe を具体的にどう root shell に変えるか?
**A2**: 一般的な 2 つ:(1) /etc/passwd を上書きして root 行のパスワード hash を既知値に変えて su する。(2) 既存の SUID バイナリをハイジャックし、その内容を一時的にあなたの payload に置換し、root で実行後に復元する。どれを選ぶかは現場でどちらが安定し、痕跡を消しやすいかによる。
**Q3**: カーネルがより古く DirtyPipe が適用できないが、DirtyCow(CVE-2016-5195)の範囲に入る場合はどうするか?
**A3**: DirtyCow は copy-on-write の競合で、「読み取り専用のメモリマップファイルへの書き込み」原語を与える。換金は同様(passwd 変更か SUID ハイジャック)。ただし DirtyCow は競合で、一部の変種はマシンを不安定にし、崩すこともある。比較的安定した実装を使う(例 passwd 変更のバージョンは vDSO ハイジャック版より安定)。古いカーネルではそれを優先して考える。
**Q4**: この種のメモリ原語 exp を走らせて権限昇格しない場合、どう調査するか?
**A4**: 確認する:カーネルパッチレベル(ディストリビューションの backport は修復するが uname は変わらない)、堅牢化による原語の無効化、競合系は複数回必要、対象ファイルが本当に攻撃面か(/etc/passwd が別の認証バックエンドを使っていないか)。換金対象を替えて(passwd が駄目なら SUID ハイジャック)再試行する。
**Q5**: 全メモリ原語 exp がパッチで遮断された場合、どこへ方向転換するか?
**A5**: カーネル面が修正済みであることは、このマシンがパッチを勤勉に当てていることを示す。カーネルを続けて攻めるのは収益が低い。戦略を転換する:(1) 設定面を再精査する(パッチ勤勉なマシンはアプリ層設定が逆に緩いことがある)。(2) 横展開。パッチ不勤勉なマシンを探す。(3) 認証情報面。パッチ勤勉 ≠ 設定厳格なので、ディメンションを替える。

### root が実行/読み取りするファイルへの書き込み
**Q1**: 「root が読むか実行するファイル」に書き込み権限がある(passwd/cron でない別のもの)。権限昇格できるかどう判断するか?
**A1**: 重要なのは自分に 2 つ問うこと:(1) root がこのファイルを、いつ、どの方式で使うか。(2) 私が書き込む内容は「実行」されるか、単に「読み取られる」か。実行可能系(スクリプト、source される設定、systemd ExecStart が指すファイル、LD 設定)= 直接権限昇格。データ系のみ(root が読んで決定する)= 間接的にコマンドをトリガーできるかを見る。
**Q2**: root ユーザーの shell 設定ファイル(.bashrc/.profile 系)を私が書き込める場合はどうするか?
**A2**: root が対話 shell にログインするなら(管理者が su/ssh で入ってくる)、その .bashrc に payload を追記し、次回 root ログイン時にトリガーする。ただし root は頻繁にログインしないかもしれず、トリガー時期が不定である。「待ち伏せ型」ベクトルとして可能で、ソーシャル/待機と組み合わせる。/etc/profile.d/ 配下の書き込み可能スクリプトも見る。全ログインに影響する。
**Q3**: root サービスが読む設定ファイル(ある daemon の conf)が書き込み可能な場合はどうするか?
**A3**: その設定が「実行するコマンド/ロードするモジュール/スクリプトパス」を指定できるかを見る。多くの daemon 設定は hook、plugin、exec 命令に対応し、それを私の payload に向けて、サービスリロードをトリガーすれば(私がトリガーできるか再起動を待つ)root で実行される。判定基準:設定項目に「コマンド/パス」型の制御可能なフィールドがあるか。
**Q4**: 書き込んだがなかなかトリガーされない(root がログインしない、サービスが再起動しない)場合はどうするか?
**A4**: トリガーを探す:合法的にサービスを reload できるか(一部は一般ユーザーにシグナルやインターフェースを許す)、サービスをクラッシュさせて systemd に自動再起動させ設定を再読ませるか、システムに定期再起動/ログローテーションがありトリガーするか。全くトリガーできないなら、これは「受動的待ち伏せ」ベクトルであり、「能動トリガー」型の権限昇格面(suid/カーネル)を探す。
**Q5**: 書き込み可能なのが全て純粋なデータファイルで、root が読んでも何も実行しない場合、この線が遮断されたらどこへ方向転換するか?
**A5**: 「データが決定に影響する」考え方に方向転換する。root がそれを読んだ後、内容に基づいて危険な操作をしないか(例 パスリストを読んで chown/実行)。本当に無害なデータなら、このファイルを諦めて他の面に方向転換する。書き込み可能ファイルの価値は root がどう消費するかに完全に依存し、消費方式が無害なら価値はない。

### PATH ハイジャック(SUID スクリプト / 環境継承)
**Q1**: SUID プログラムか root スクリプトが絶対パスを書かずに子コマンドを呼んでいる。PATH ハイジャックしたいが、前提は何か?
**A1**: 前提:(1) そのプログラムが高権限で動く際に「私が制御できる PATH」を使う、または(2) それが fork したプロセスが私の汚染できる環境を継承する。SUID C プログラムについて、絶対パスなしで `system()`/`popen()` が `service`、`id`、`cat` などを呼ぶなら、PATH の先頭を書き込み可能なディレクトリに設定し、同名の悪意あるファイルを置くだけでよい。判定基準:高権限実行 + 相対コマンド + PATH 制御可能。
**Q2**: ハイジャックできるコマンドをどれだけ呼ぶかをどう確認するか?
**A2**: `strings` でコマンド名らしき文字列がないか見る。`ltrace -f` を 1 回走らせて system/execvp が何を呼ぶか、相対か絶対かを見る。`sh -c "service apache ..."` のようなものを見たら、`service` をハイジャック対象に確定する。
**Q3**: 同名の悪意あるファイルを作り、PATH を変更したが効かない場合はどうするか?
**A3**: 調査する:(1) SUID プログラムが自分で PATH をリセットした(安全な書き方)。(2) `system()` は `/bin/sh -c` を使い、一部の sh は安全な既定 PATH を使う。(3) 悪意あるファイルに実行権限がない、または shebang が間違い。プログラムが安全な PATH をハードコードしていれば、PATH ハイジャックのこの線は無駄なので、関数ハイジャックか別の穴に方向転換する。
**Q4**: 対象コマンドが絶対パスを使い、PATH ハイジャックが完全に通らない場合、どこへ方向転換するか?
**A4**: LD 層ハイジャックに方向転換する:プログラムが動的リンクで、LD_LIBRARY_PATH/LD_PRELOAD の処理に抜けがあるなら(sudo env_keep がこれらを保持する場合を含む)、悪意ある so でそれが呼ぶライブラリ関数をハイジャックする。またはデータ面に方向転換する:それが読む書き込み可能なファイル。絶対パスは PATH を遮るが、ライブラリとデータは遮れない。
**Q5**: PATH と LD がどちらも正しく堅牢化され、この SUID が隙がない場合、どこへ方向転換するか?
**A5**: このバイナリは書き方が規範的であることを示すので、固執しない。他の SUID/cap/cron 目標に方向転換するか、バイナリ脆弱性の角度に方向転換する(外部入力を処理するロジックがあれば、オーバーフロー/注入があるかもしれない)。1 つの堅牢化された SUID が全システムの堅牢化を意味しないので、目標を替える。

### LD_PRELOAD / LD_LIBRARY_PATH ハイジャック
**Q1**: LD_PRELOAD が権限昇格に使えるのはどんな条件か?
**A1**: 核心:ある「高権限プロセス」に私の悪意ある so をロードさせること。典型的な場面:(1) `sudo -l` が `env_keep+=LD_PRELOAD` を示す。直接 `sudo LD_PRELOAD=/tmp/e.so <許可コマンド>` で、so のコンストラクタが root で走る。(2) ある root プロセス/スクリプトが私の設定できる環境を継承する。注意:通常の SUID は LD_PRELOAD を消すので、主に sudo の env_keep か、非 SUID の高権限実行経路に依存する。
**Q2**: 悪意ある so をどう書くか?
**A2**: `__attribute__((constructor))` を持つ関数を書き、中で setuid(0)+execve("/bin/sh") して共有ライブラリにコンパイルする。ロード時にコンストラクタが自動実行され、ホストプロセスの権限(root)で shell を起動する。判定基準:so がロードされれば即トリガーで、対象プログラムがその中の関数を能動的に呼ぶ必要はない。
**Q3**: sudo が保持するのが LD_LIBRARY_PATH で LD_PRELOAD でない場合、どう使うか?
**A3**: LD_LIBRARY_PATH でライブラリ検索パスを制御できる。対象プログラムが依存する .so の名前を 1 つ見つけ、私の書き込み可能なディレクトリに同名の悪意ある so を置く(必要なシンボルをエクスポート + コンストラクタで権限昇格)。LD_LIBRARY_PATH をそのディレクトリに向ける。プログラムが私の偽ライブラリをロードすれば命中。LD_PRELOAD より、依存ライブラリ名を探す 1 歩多い。
**Q4**: env_keep がこの 2 つを保持せず、SUID が環境を消し、LD ハイジャックが通らない場合、どこへ方向転換するか?
**A4**: 他の env 型注入に方向転換する:env_keep が PYTHONPATH/PERL5LIB/RUBYLIB を保持 → スクリプトモジュールをハイジャック。BASH_ENV を保持 → sudo が bash スクリプトを走らせる際に注入。sudoers がどの環境変数を許可するか見る。変数ごとに異なるハイジャック面がある。全てなければ env 面を諦める。
**Q5**: 全環境変数注入面が遮断される(env_reset が厳格)場合、どこへ方向転換するか?
**A5**: 環境に依存しない権限昇格に方向転換する:GTFOBins の直接エスケープ(vim/less/コマンド自身の機能)、バイナリ脆弱性、カーネル、cron。env 注入は多くの面の 1 つにすぎず、env_reset が厳格なのは良い設定だが、他の面も厳格とは限らない。直交ディメンションに替える。

### NFS no_root_squash 権限昇格
**Q1**: マシンが NFS 共有をエクスポートしているのを見つけた(`cat /etc/exports` か `showmount`)。権限昇格できるかは何を見て決めるか?
**A1**: export オプションに `no_root_squash` があるかを見る。既定の root_squash はクライアントの root を nobody にマップする。no_root_squash はクライアントの root 身元を保持する。つまり私が制御するマシンで root としてこの共有をマウントし、作成したファイルがサーバー上で本当の root 所有者になる。判定基準:no_root_squash + 私が root を持つマシンからマウントできる。
**Q2**: no_root_squash がある場合、どう権限昇格を実行するか?
**A2**: 私が制御する(root を持つ)マシンでその NFS 共有を mount し、root として共有内に SUID root の shell を置く(`cp /bin/bash .; chmod +s`)。対象マシン(共有がローカルにある)に戻り、この SUID bash を `-p` で実行すれば対象マシンの root を取る。重要:両端が同じファイルを共有し、所有者が root として保持されるのを利用する。
**Q3**: 攻撃マシンが NFS ポートに接続できない(ファイアウォール)が、対象マシン自身が export している場合はどうするか?
**A3**: 対象マシン上に既に低権限 shell があるが、外へ出て NFS を張れないなら、考えを変える:ローカルでループバックマウントできるか、対象マシンが既にマウントした他の no_root_squash 共有を利用するか(逆に、それが他人のものをマウントしている)。ネットワークが完全に隔離されて NFS 特性を使えないなら、この線は適用不能で、別の面に方向転換する。
**Q4**: root_squash(既定の安全)で no_root_squash でない場合、まだ利用できるか?
**A4**: 直接の SUID 埋め込みはできない(root が nobody に圧縮される)。しかし共有内の既存ファイルの権限が緩いか(他人のスクリプトを書き込める)、読める認証情報があるかを見る。root_squash は「root として書く」ことだけを遮り、「共有内容を読む」「一致する uid として書く」は遮らない。価値は下がるがゼロではない。
**Q5**: NFS 面が全く使えない(エクスポートなし/全 squash/ネットワーク不通)場合、どこへ方向転換するか?
**A5**: NFS は特定環境にしかない機会ベクトルで、ないのは正常である。本機の標準面(suid/sudo/cron/cap)に方向転換する。内部ネットワークの多マシン環境なら、他の共有プロトコル(SMB)か横展開に注意を向け、単一の NFS 特性に時間をかけない。

### root になった後、すぐ足場を固定すべきか
**Q1**: root に権限昇格したばかり。最初にすべきは権限昇格後の利用か、先に固定か?
**A1**: 先に固定する。root は shell の切断、追い出し、マシン再起動で失われ得る。低コストの固定:安定した折り返しを 1 つ残す(SSH key を root に、または隠蔽的なスケジュール折り返し)、重要認証情報(shadow、ssh key、DB パスワード)を記録して随時の復旧と横展開に備える。判定基準:root 権限は失われやすいリソースで、取得後 60 秒以内に復旧可能性を構築する。
**Q2**: 固定時に「安定」と「隠蔽/痕跡消去」をどう両立するか?
**A2**: 競技/評価の場面は rootkit 級の永続化は不要だが、単点障害を避ける。折衷:目立たない SSH key 1 つ + root を取り直せる全ての経路(その SUID/cron がまだある)を記録する。権限昇格経路自体がまだあるなら、それが天然の「永続化」であり、必ずしも新しい怪しいファイルを足す必要はない。痕跡消去:権限昇格過程で落とした exp、一時 SUID bash、偽装ファイルを削除する。
**Q3**: root を得た後、権限昇格タスクは終わったか?
**A3**: 本機の縦方向は完了だが、戦役はまだかもしれない。root 後、即座に「root でしかできない収穫」を行う:全 hash を dump する(横展開/爆破用)、全 ssh key と DB 認証情報を読む、このマシンと内部ネットワークの他ホストの信頼関係(known_hosts、マウント、履歴 ssh コマンド)を見る、メモリ認証情報を取る。root は横展開の燃料庫で、「root になった」で止まらない。
**Q4**: root を取ったが shell が非常に不安定で、固定動作が終わる前に切れそうな場合はどうするか?
**A4**: 優先順位で急いで行う:第一優先は安定した折り返し/SSH key を 1 つ書く(命綱)。第二は shadow と重要 key を dump する(情報)。残りは後回し。最も不可逆で、最も命綱な操作を最前に置き、次の秒で切れると仮定する。
**Q5**: 権限昇格が全過程失敗し、root を取れず、このマシンが「遮断」されたら、戦略上どう方向転換するか?
**A5**: 横展開優先の考え方に方向転換する:root は唯一の目標ではなく、現在の低権限アカウントが横展開に必要な全て(認証情報、内部ネットワーク到達性、共有アクセス)を既に握っているかもしれない。内部ネットワークの他マシンを攻める、ドメイン経路を探す、現有権限で機微データにアクセスする。多くの場合、戦役全体の勝敗は別のマシンにあり、このマシンを root まで攻めることではない。早めに損切りし、戦場を替える。

### pspy プロセス監視:静的列挙で見えないものを掘る
**Q1**: 静的列挙(cron ファイル、SUID、cap)を全て掘っても収穫がない。隠れた root 活動を疑う。どう見るか?
**A1**: pspy を使う(root なしで /proc のプロセス作成/終了を監視)。それが捕まえられるもの:cron がトリガーする短命プロセス、systemd timer、デーモンが周期的に呼ぶ外部コマンド、そして最も肥沃なのは、他のユーザー/スクリプトがコマンドラインで平文で渡すパスワード(mysql -p、curl -u、ssh sshpass)。判定基準:静的ファイルは「今何が起きているか」を見せない。pspy が時間ディメンションを補う。
**Q2**: pspy を送れない/外向きがない場合、どう代替するか?
**A2**: 手書きの監視ループ:`while true; do ls -la /proc/*/cwd 2>/dev/null; cat /proc/*/cmdline; done` または `ps` スナップショットの反復 diff。粗いが瞬時プロセスを捕まえられる。核心は「高頻度の /proc ポーリング」であり、必ずしも pspy というバイナリでなくてよい。
**Q3**: pspy が root が周期的にあるスクリプトを走らせるのを捕まえた。次にどう権限昇格に変えるか?
**A3**: このコマンドの各環でどれが書き込み可能かを見る:スクリプト自体、スクリプトが呼ぶ子コマンド(相対パス→PATH)、それが読み書きするディレクトリ(ワイルドカード/ファイル注入)、それが source する設定。「観測した root 挙動」を環ごとに「制御可能点」に分解する。
**Q4**: 他のユーザーのコマンドラインに平文パスワードを捕まえたら、どう使うか?
**A4**: 直接記録し、そのパスワードを試す:そのユーザーへ su する、sudo(そのユーザーがより良い sudo ルールを持つかもしれない)、DB/SSH/他ホストへ再利用する。コマンドラインが漏らすパスワードは純粋な点数のプレゼントで、情報としてだけ見ず、即座に身元を横断する。
**Q5**: 長く監視しても何も捕まらない場合、この経路が空ならどこへ方向転換するか?
**A5**: 「受動待機」でなく「能動トリガー」に方向転換する:一部の root ロジックはイベントでトリガーされる(ログインで motd、メール受信、ファイル到着、サービス再起動)。これらのイベントを起こして root コード経路を活性化するか、時間ディメンションを諦めて、静的な書き込み可能ファイル/グループ権限のディメンションに戻る。

### sudo セッション再利用と sudo バージョン脆弱性
**Q1**: 現在のユーザーに sudo 権限があるがパスワードが必要で、私が持たない。手詰まりか?
**A1**: 先に 2 点を見る。1 つ:そのユーザーが最近 sudo を使ったか(sudo にはタイムスタンプキャッシュがあり、既定では数分間パスワード不要)。そのアクティブな端末/tty をハイジャックできれば、キャッシュに乗って直接 sudo できる。2 つ目:`sudo --version` を見る。旧バージョンはローカル権限昇格 CVE を受ける(Baron Samedit ヒープオーバーフロー、sudoedit の CVE、-u#-1 の CVE-2019-14287)。これらはパスワードを知らなくてよい。
**Q2**: sudo キャッシュに乗れるかをどう判断するか?
**A2**: キャッシュは tty/セッションにバインドされる。そのユーザーが既に認証した shell セッションに入れるなら(tmux/screen 共有、またはそのユーザーがあなたの既に制御するアカウント)、同じセッション内で sudo がパスワード不要になるかもしれない。判定基準:「sudo した直後で、まだタイムアウトしていない」同ユーザーのセッションが乗れるか。
**Q3**: sudo バージョンが脆弱性区間に入るが、パッチ済みか不確かな場合はどうするか?
**A3**: ディストリビューションがパッチを backport してバージョン番号を変えないことがあるので、バージョン番号だけを信じない。低リスクで先に原理的検知を行う(例 Baron Samedit には非破壊の判定法がある)。利用可能と確認してから exp に進む。注意:sudo 系ヒープオーバーフロー exp はクラッシュリスクがあるので、このマシンが崩れた場合の代償を先に心で評価する。
**Q4**: ユーザーがそもそも sudo 権限を持たず、sudo バージョンもきれいな場合、この線が全廃ならどこへ方向転換するか?
**A4**: sudo 面から完全に離れる。SUID/cap/cron/グループ権限などの設定面に方向転換するか、逆にパスワードを釣る:偽の sudo(PATH 前方の同名スクリプト)を置いてユーザーが入力するパスワードを記録し、本人がトリガーするのを待つ。後者は「提権」でなく「釣り」で、本人の対話がある目標に向く。
**Q5**: sudo パスワードを釣りたいが、対象に人が対話しない(純サーバーでログインなし)場合、釣れないがどうするか?
**A5**: ソーシャルベクトルを諦め、純粋な技術面に戻る。人が対話しないマシンでは、権限昇格は設定/カーネル/サービス脆弱性にしか依存できず、パスワードを騙し取るのは期待できない。精力を SUID/cap/カーネル exp/内部サービスの、人に依存しないディメンションに戻す。

### パスワードを探り当てた後:パスワード再利用とアカウント横断
**Q1**: 設定ファイル/history/バックアップで平文パスワードを 1 つ探り当てた。それでどう権限昇格するか?
**A1**: 1 つのアカウントだけに試さない。このパスワードを体系的にスプレーする:su root(root の弱いパスワードかもしれない)、su で本機の shell を持つ各ユーザーへ、sudo(あるユーザーが sudo を設定済みかもしれない)、本機の全サービス(DB/SSH/web バックエンド)。パスワード再利用は Linux 権限昇格の最も高頻度な現実経路の 1 つである。判定基準:1 つのパスワードが複数の身元に値するので、1 つずつ試す。
**Q2**: su で、あるユーザーに成功したが、そのユーザーも root でない。無駄に切替えたか?
**A2**: 無駄ではない。身元を替えれば権限昇格面が 1 セット替わる:新ユーザーは異なる sudo -l、危険グループ、ファイル所有、自分の cron/サービスを持つかもしれない。切替えるたびに第一梯隊の列挙(id/sudo -l)をやり直し、「横断」を「新しい権限昇格面を開く」と捉える。
**Q3**: 探り当てたのが hash で平文でない場合はどうするか?
**A3**: オフライン爆破(john/hashcat + 辞書/ルール)。破れたらパスワード再利用のフローに戻る。破れなければ pass-the-hash ができるか見る(Linux では稀だが、SSH/Kerberos/一部サービスで可能なことがある)、または hash を情報として残し、別の経路に方向転換する。
**Q4**: パスワードがあるアプリ/DB のもので、システムアカウントのものでない場合、まだ役に立つか?
**A4**: ある。先にこの DB/アプリが root か高権限で動くかを見る(そうならサービス権限昇格に進む)。次にこのパスワードがシステムパスワードに再利用されていないかを見る(運用者の一般的な習慣)。アプリパスワードはサービス権限昇格とパスワード再利用への二重の入口である。
**Q5**: 探り当てた全パスワードをスプレーして 1 つも当たらない場合、この線が切れたらどこへ方向転換するか?
**A5**: 「認証情報不要」の純粋な脆弱性面(SUID/cap/cron/カーネル/内部サービス)に戻るか、認証情報収集の範囲を広げる:まだ探っていない場所(他ユーザーのホームディレクトリは権限昇格後しか読めない、メモリ、ブラウザ/メール認証情報、git リポジトリ履歴)。パスワードスプレーが空なのは多くの場合「手元のパスワードが少なすぎる」だけで、「再利用の経路が通らない」のではない。

### systemd サービスと timer の権限昇格
**Q1**: cron 面を掘って収穫がない。現代のシステムは systemd を使う可能性が高い。何を調べるか?
**A1**: systemd の service と timer を調べる:`systemctl list-timers`、/etc/systemd/system と /lib/systemd/system 配下の unit ファイルの権限を見る。探すもの:root で動く unit で、その unit ファイルが書き込み可能、またはその ExecStart が指すスクリプト/バイナリが書き込み可能、または WorkingDirectory/EnvironmentFile が制御可能。判定基準:任意の root unit 連鎖に 1 環でも私が書けるものがあるか。
**Q2**: root service の unit ファイルを私が書ける場合、どう root になるか?
**A2**: ExecStart をあなたの payload に変更し、そのサービスの再起動をトリガーする。ファイルを変えられないが `systemctl edit`(権限あり)できるか、それが指す EnvironmentFile の書き込み可能ファイルを制御できるなら、同様に注入できる。変更後、トリガーを工夫する(サービスが自ら再起動する、または restart 権限がある)。
**Q3**: unit ファイルは書き込み不可だが、ある root service に start/restart を実行できる(sudo か polkit が許可)のを見つけた。どう使うか?
**A3**: この service が起動時に読む制御可能なファイル、走らせる制御可能なスクリプトを見る。または「書き込み可能な ExecStart 対象」と組み合わせる。restart 権限だけあって連鎖が全て書き込み不可なら、実行体がちょうど私の書き込み可能な位置にある service を探す。
**Q4**: 自分の systemd unit を作成できるか?
**A4**: /etc/systemd/system かユーザー級 unit ディレクトリが書き込み可能か、daemon-reload+start できるかを見る。書き込み可能で root で新 unit を起動できるなら、ExecStart=あなたの shell の unit を直接書く。これは既存 service のハイジャックよりすっきりしている。
**Q5**: systemd 面を全て排除した(unit が全て書き込み不可、start 権限なし、新 unit 作成不可)場合、どこへ方向転換するか?
**A5**: 他のトリガーフレームワークに戻る:D-Bus/polkit が認可する操作、logrotate/motd などのスクリプトフレームワーク、または「トリガーされて実行」のディメンションを完全に離れ、SUID/cap/カーネルの「能動実行」ディメンションに戻る。systemd の 1 本の木にぶら下がらない。

### root で動くデータベース/サービスの権限昇格
**Q1**: `ss -tlnp` か ps で本機に MySQL/PostgreSQL/Redis が動き、所有者が root だと分かった。それをどう権限昇格に変えるか?
**A1**: DB が root で動く = 任意ファイル書き込み/コマンド実行の潜在がある。MySQL:接続できれば(パスワード再利用/socket 無認証)、UDF で so を書いてシステムコマンド実行、または INTO OUTFILE で root の authorized_keys/cron を書く。PostgreSQL:COPY ... TO/FROM PROGRAM で直接コマンド実行、または LO ラージオブジェクトでファイルを書く。Redis:未認可なら CONFIG SET で crontab/SSH key/module load を書く。判定基準:認証で接続できる + サービスが高権限で動く。
**Q2**: DB に接続できない(パスワードが必要で私が持たない)場合、この線は切れたか?
**A2**: 先にパスワードを探す:web アプリ設定ファイル、環境変数、history、バックアップにほぼ必ず DB パスワードがある。またはローカルの無認証入口を探す:MySQL の unix socket、Redis の 127.0.0.1 バインドはパスワードなしが多い。DB 権限昇格の「壁」は通常認証で、認証認証情報は本機のファイルに散らばっていることが多い。
**Q3**: Redis が未認可だが 127.0.0.1 にバインドされ、私が既に本機にいる。どう攻めるか?
**A3**: 本機から到達できるなら直接 redis-cli。crontab を書く、~/.ssh/authorized_keys を書く(Redis の所有者ホームディレクトリ/権限が許せば)、または MODULE LOAD で悪意あるモジュールをロードしてコマンド実行する。127 へのバインドは既に本機にいるあなたに障害ではなく、むしろネットワーク露出の発見リスクを減らす。
**Q4**: DB が root で動いていない(例 mysql ユーザー)場合、ファイル書き込み/コマンド実行にまだ意味はあるか?
**A4**: あるが、目標が変わる:このときコマンド実行で得られるのは mysql/postgres ユーザーであり、root ではない。それを「サービスアカウントへの横断」と捉え、そのアカウントから権限昇格面を探し直す(別のグループ、別のファイル権限があるかもしれない)。root で動いていないから価値がないとは思わない。
**Q5**: DB バージョンが古く、DB ソフト自体の RCE 脆弱性を直接攻めたい。できるか?
**A5**: 代替として可能だが、優先度は「正当な機能の乱用」(UDF/COPY PROGRAM の方が安定し、サービスを崩さない)より低い。ソフトの CVE はライブラリ崩壊のリスクがあり、exp があるとも限らない。先に機能乱用を絞り尽くし、DB ソフト exp は最後の手段である。
**Q6**: 本機に root で動くサービスが全くなく、内部サービス面が空ならどこへ方向転換するか?
**A6**: ローカルファイル/権限のディメンション(SUID/cap/cron/グループ)に戻るか、ローカルでリッスンするが非 root のサービスを「横断/情報」の入口として扱う(「権限昇格」の入口でなく)。サービス面が空なのは常態で、死路ではない。

### ptrace で高権限プロセスへ注入
**Q1**: システムに root 所有のプロセスがずっと動いている。現在のユーザーがそれに注入できるか?
**A1**: ptrace 能力と制限を見る。CAP_SYS_PTRACE があるか、または yama の ptrace_scope=0(`cat /proc/sys/kernel/yama/ptrace_scope`)で対象と同 uid なら attach できる。ただし注意:通常ユーザーは既定で root プロセスに ptrace できない(uid が違う)。判定基準:ptrace_scope 値 + cap の有無 + 同 uid か。
**Q2**: ptrace_scope=0 だが対象プロセスが root で私は一般ユーザー。attach が拒否される。まだ見込みはあるか?
**A2**: uid が違うと ptrace_scope=0 でもカーネルの uid 検査を止められない。一般ユーザーが root プロセスに ptrace するのは元々許されない。この経路は、あなたに CAP_SYS_PTRACE があるか、先に対象プロセスと同 uid のアカウントへ横断する必要がある。そのため先に身元を解決し、それから注入を論じる。
**Q3**: 本当に CAP_SYS_PTRACE がある場合、どう root shell に落とすか?
**A3**: root プロセスに attach し、shellcode を注入するか、execve/system を実行させて shell を起動するか、メモリを書き換えてシステムコールを実行させる。ツール化は既成の注入フレームワークを使える。cap_sys_ptrace の本質は「任意プロセスのアドレス空間に入る」ことで、root プロセスを 1 つ宿主に選べばよい。
**Q4**: 注入したいが対象プロセスがいつ終了するか分からず不安定で、リスクが大きい場合はどうするか?
**A4**: 長期間安定した root デーモンを宿主に選ぶ(短命プロセスでなく)、注入方式は「既存実行フローのハイジャック」でなく「新プロセスの派生」を選び、重要サービスを壊す確率を下げる。レッドチームはクラッシュ面を制御する。
**Q5**: ptrace 能力がなく、同 uid にも切替えられず、注入が完全に通らない場合、どこへ方向転換するか?
**A5**: 他の capability(cap_setuid/cap_dac_read_search の方が直接的)に方向転換するか、「プロセス注入」のディメンションを完全に離れ、SUID/sudo/cron に戻る。ptrace 権限昇格はニッチな経路で、通らないのは正常なので、未練を残さない。

### /etc/ld.so.preload と全体的な動的リンクハイジャック
**Q1**: sudo 内の LD_PRELOAD 以外に、「全体に効く」ライブラリハイジャック面はあるか?
**A1**: ある。/etc/ld.so.preload と /etc/ld.so.conf.d/ の書き込み権限を調べる。ld.so.preload に列挙された so はシステム上の全ての動的リンクプログラムにロードされる(root で動くものも含む)。このファイルを書けるなら、悪意ある so を置けば、任意の root プロセス/SUID プログラムの起動時に root でコンストラクタが実行される。判定基準:この 2 箇所のどちらかが書き込み可能。
**Q2**: /etc/ld.so.preload が書き込み可能な場合、悪意ある so をどう書けばシステムを壊さないか?
**A2**: so のコンストラクタ内で判断する:euid==0 のときだけ payload をトリガーし、実行後復元し、各プロセスが狂ったように spawn しない(システムを引きずり倒して目立つ)。定番のやり方:preload のライブラリが geteuid などをハイジャックし、root コンテキストを検知してから動作し、できるだけ 1 回限りにする。ノイズ制御が鍵である。
**Q3**: ld.so.preload が存在せず書き込みも不可だが、ld.so.conf.d が書き込み可能な場合、どう使うか?
**A3**: ld.so.conf.d に、私の制御するディレクトリを指すライブラリ検索パスの 1 行を書き、同名 so を置いて、ある root プログラムがロードするライブラリを上書きする(ldconfig のキャッシュ更新が必要。私がトリガーできるか、root がトリガーするのを待つ)。preload より間接的だが、同じく全体リンクハイジャックである。
**Q4**: これらのファイルが全て root only で書き込み不可の場合、ハイジャックの入口がなく、どこへ方向転換するか?
**A4**: 「局所」リンクハイジャックに縮小する:ある具体的な SUID プログラムが書き込み可能なディレクトリからライブラリをロードするなら(RUNPATH/RPATH が書き込み可能位置を指す、または dlopen が相対パス)、それに対してハイジャックする。全体が駄目なら単点を探す。どちらも駄目ならリンクハイジャックのディメンションを完全に離れる。
**Q5**: 局所にも書き込み可能なライブラリロード点がなく、リンクハイジャック全体が無駄なら、次はどうするか?
**A5**: 直交する実行原語に方向転換する:PATH ハイジャック(ライブラリでなくコマンドをハイジャック)、root が読むファイルへの書き込み(passwd/cron/authorized_keys)、またはカーネル exp。リンクハイジャックは「コード注入」の 1 つにすぎず、注入できなければ「重要なファイルへの直接書き込み」の考え方に替える。

### SUID 無効の謎:nosuid / no_new_privs / 読み取り専用マウント
**Q1**: 完璧な SUID 権限昇格ベクトルを見つけたのに、exp が効かず、euid がずっと変わらない。どういうことか?
**A1**: マウント/カーネル制限を強く疑う。`mount` でそのバイナリの所在パーティションが nosuid かを見る(/tmp、/home は nosuid でマウントされることが多く、SUID ビットが形骸化する)。プロセスが no_new_privs(NNP)状態かも見る。コンテナ/systemd 堅牢化はよくセットする。NNP が効くと、SUID と cap 昇格が全て無効になる。判定基準:mount オプション + /proc/self/status の NoNewPrivs フィールド。
**Q2**: nosuid マウントが原因で、SUID バイナリが /tmp 上で動かないと確認した場合、どうするか?
**A2**: 利用を nosuid でないパーティションに移す。ある SUID プログラムがシステムパーティション(通常 / は nosuid でない)にあるなら、それは権限昇格できる。無効なのは、あなたが nosuid ディレクトリに落とした SUID payload である。そのため:システム内蔵の SUID を利用するか、payload を書き込み可能かつ非 nosuid の場所に落とす。
**Q3**: プロセスが no_new_privs=1 で、SUID/cap が全線無効。これは設定系権限昇格をほぼ塞ぐが、どこへ方向転換するか?
**A3**: NNP は通常コンテナ/サンドボックスに現れる。これはあなたがコンテナ内にいる可能性を示唆する。2 つの線に方向転換する:1 つはコンテナエスケープのディメンション(socket/マウント/特権コンテナ/カーネルエスケープを探す)。2 つ目は権限昇格に依存しない経路(既にマウントされたホストの機微ファイルを直接読む、コンテナ内 root 身元を利用する)。NNP は「戦場を替える」強シグナルである。
**Q4**: 制限付きコンテナ/名前空間内にいるかをどう素早く判断するか?
**A4**: 総合的に見る:/.dockerenv、cgroup 内容、mount 内の overlay、プロセス数が極少、NNP=1、能力セットが削減(capsh --print)。複数のシグナルが重なればほぼ確定。確定後、権限昇格の考え方を全体として「本機 root」から「ホストへのエスケープ」に切り替える。
**Q5**: コンテナでもなく、NNP もないのに、SUID が効かない。他に何の可能性があるか?
**A5**: SELinux/AppArmor が遮っていないか(LSM の条項参照)、そのバイナリ自身が権限を drop したか、fs.suid_dumpable のような変な設定かを確認する。1 つずつ排除しても解がなければ、SUID 面は使えないと判定し、cron/サービス/カーネルのディメンションに方向転換する。

### Docker/containerd socket ファイルの露出
**Q1**: docker グループでないが、/var/run/docker.sock を私が読み書きできるのを見つけた。これは何を意味するか?
**A1**: root と等しい。docker socket にアクセスできれば、Docker API でホスト / をマウントした特権コンテナを起動し、中でホストファイルシステムにやりたい放題できる(authorized_keys を書く、passwd を変える、ホストへ chroot)。判定基準:docker.sock に rw がある(グループメンバー、または socket 権限の設定ミス、または既にコンテナ内で socket がマウントされている)。
**Q2**: socket アクセス権はあるがマシンに docker CLI がない場合、どう API を呼ぶか?
**A2**: curl で直接 unix socket の HTTP API を叩く(--unix-socket)、または HTTP を送れる任意のツールで create/start コンテナのリクエストを構築する。CLI は単なるラッパーで、socket + HTTP だけで十分である。判定基準:生のリクエストを送れればよく、docker バイナリに依存しない。
**Q3**: コンテナ内で docker.sock がマウントされているのを見つけた場合、ホスト上で見つけた場合と違いはあるか?
**A3**: 目標は一致する(ホストの制御)が、これは典型的なコンテナエスケープの形である:コンテナ内からホストの docker socket にアクセス → 特権コンテナを起動してホストルートをマウント → エスケープ。マウントされたのが containerd/crio の socket でも原理は同じで、対応する API に替える。
**Q4**: socket 権限が厳しく取れないが、docker グループにいる場合、同じか?
**A4**: 同じ。docker グループメンバーは socket に権限があり、直接 `docker run -v /:/host --privileged` でホストをマウントする。docker グループ == root は公認の結論である。グループにもおらず、socket 権限もなければ、この線は切れたとみなす。
**Q5**: docker/containerd socket がどちらも到達できず、コンテナランタイムのこの経路が切れた場合、どこへ方向転換するか?
**A5**: 他のエスケープ/権限昇格面に方向転換する:特権コンテナの cap(cap_sys_admin で cgroup release_agent をマウントしてエスケープ)、マウントされたホストディレクトリ、カーネル exp(コンテナはホストカーネルを共有し、カーネルの穴は同様にエスケープできる)。socket はエスケープの 1 種にすぎず、runtime が到達できなければ cap/マウント/カーネルの 3 本足に替える。

### カーネルモジュールロードの権限昇格
**Q1**: 通常の経路が全て塞がり、自分にカーネルモジュールをロードする能力があると分かった(CAP_SYS_MODULE か modprobe 関連を書ける)。どう使うか?
**A1**: kmod をロードできるのはほぼ root と等しい。カーネルモードのコードでカーネル構造を任意に変更できる(現在のプロセスの cred を root に変える)。悪意ある .ko を書き、insmod/modprobe で入れ、init 内で現在のプロセスを権限昇格するか root shell を spawn する。判定基準:capsh が cap_sys_module を示す、または /sbin/modprobe を制御できる(kernel.modprobe sysctl が書き込み可能パスを指す)。
**Q2**: cap_sys_module はあるが、対象マシンにコンパイラ/カーネルヘッダがなく、.ko をコンパイルできない場合はどうするか?
**A2**: 同バージョンのカーネルの別マシン(またはローカルで同バージョン環境を構築)で .ko をクロスコンパイルして送る。.ko はカーネルバージョン/vermagic が一致すればロードできる。対象でコンパイルせず、コンパイルを他所に移すのが通常の操作である(exp コンパイルの条項参照)。
**Q3**: kernel.modprobe という sysctl が指すパスを私が書けるが、cap_sys_module がない場合、権限昇格できるか?
**A3**: できる。カーネルがあるモジュールをロードする必要が生じたとき(例 未知の socket プロトコル族をトリガー)、kernel.modprobe が指すプログラムを root で呼ぶ。それをあなたのスクリプトに向け、モジュール自動ロードをトリガーすれば、スクリプトが root で走る。これは「modprobe パス変更」の定番利用である。
**Q4**: vermagic が一致せず、モジュールがどうしてもロードできない場合、この線は切れたか?
**A4**: 対象の正確なカーネルバージョンと設定を得られれば、理論上 vermagic を合わせて再コンパイルできる。合わせられなければ kmod の経路を諦める。他の cap かカーネル exp に方向転換する(カーネル exp はモジュールロード不要で、カーネル脆弱性を攻める)。vermagic に長く時間をかけない。
**Q5**: cap_sys_module もなく、modprobe パスも制御できず、カーネルモジュール面に入り口がない場合、どこへ方向転換するか?
**A5**: カーネル脆弱性 exp(別の仕組み:合法的なモジュールロードでなくカーネル bug を利用)に方向転換するか、ユーザーモードの設定面に戻る。カーネルモジュールロードは「合法だが危険な機能」で、この機能がなければ「bug を違法に利用する」カーネル exp に進むか、カーネルのディメンションを離れる。

### フレームワークトリガー系スクリプトの権限昇格(logrotate / motd / mail / hooks)
**Q1**: cron と systemd を全て掘った。他に「root が自動でスクリプトを走らせる」フレームワークはあるか?
**A1**: 見落とされやすいものが山ほどある:logrotate(ローテーション時に root で走り、postrotate スクリプトを設定でき、logrotten などの歴史的 CVE がある)、update-motd(SSH ログイン時に root が /etc/update-motd.d/ 配下のスクリプトを走らせる)、/etc/profile.d、mail がトリガーする procmail、git リポジトリの hooks、PAM スクリプト、initramfs hooks。判定基準:「あるイベント発生→root があるディレクトリ下のスクリプトを実行」という仕組みで、そのスクリプトかディレクトリが書き込み可能。
**Q2**: /etc/update-motd.d/ 配下に私が書けるスクリプトがあるが、SSH ログインしてくる人がいなくてトリガーしない場合はどうするか?
**A2**: 自分でログインを作る(このマシンに SSH できれば、低権限ユーザーでログインしても motd が root でトリガーされる)、または実在の人がログインするのを待つ。motd 権限昇格のトリガー条件は「1 回の SSH ログイン」で、通常は自分で満たせる。
**Q3**: logrotate 設定か、それが処理するログディレクトリが書き込み可能な場合、どう権限昇格に変えるか?
**A3**: 2 つある:1 つは logrotate 設定を変更して postrotate を足せれば、ローテーション時に root があなたのコマンドを実行する。2 つ目は logrotate が書き込み可能なログを処理する際の競合/シンボリックリンク問題(logrotten 系)を狙って利用を構築する。判定基準:logrotate が root で実行するその 1 歩に影響できるか。
**Q4**: これらのフレームワークのスクリプト/ディレクトリが全て root only で書き込み不可の場合、トリガー面が空ならどこへ方向転換するか?
**A4**: 「トリガーされて実行」という大きなディメンション(cron+systemd+各フレームワーク)全体が枯渇したことを示す。「能動実行」のディメンションに方向転換する:SUID/sudo/cap で自分が root で走る。root があなたのものを走らせるのを待たない。2 つの大ディメンションは直交するので、片方が空なら果断に片方へ替える。
**Q5**: これらのマイナーなトリガー点を体系的に漏れなくスキャンするには?
**A5**: 「イベント→実行体」のリスト思考で一周スキャンする:起動、ログイン、メール受信、ログローテーション、パッケージ管理(apt/dpkg の pre/post スクリプト)、バックアップタスク、監視プローブ。各イベントに「それは何の身元で走るか、どのファイルを走らせるか、私が書けるか」と問う。これは各ツール名を散発的に覚えるより漏れにくい。

### ローカル exp のコンパイルと配送の決定
**Q1**: あるローカル権限昇格 exp(カーネル/PwnKit/DirtyPipe)を使うと決めた。対象マシンで直接 gcc コンパイルすべきか?
**A1**: できるだけ対象でコンパイルしない。理由:対象にコンパイラ/カーネルヘッダがないことが多く、コンパイル産物の配置がノイズになり、監視をトリガーする可能性もある。ローカルか、同じディストリビューション同カーネルバージョンのマシンで静的バイナリをコンパイルし、きれいな実行ファイルを送るのを優先する。判定基準:対象に gcc があるか(`which gcc/cc`)+ 外向き/配置条件。
**Q2**: 対象のカーネルバージョンが特殊で、ローカルに対応環境がない場合、どうするか?
**A2**: 一致するバージョンのコンテナ/VM(uname で正確に合わせる)を引いてコンパイルするか、exp のプリコンパイル版を探す。カーネル exp は特にバージョン合わせが重要。環境を整えられない場合は、退路として対象ローカルでコンパイルを検討するが、そのノイズと失敗リスクを受け入れる。
**Q3**: コンパイルはできたが対象が外向きできず、exp を送れない場合はどうするか?
**A3**: 既存の shell チャネルで送る:base64 で貼り付けて配置、既存の web アップロード点、SCP/SFTP(認証情報があれば)、payload を制御済みの他サービスに詰める。転送は純粋な工学的問題で、「外向きがない」から exp が使えないと思わない。任意のファイル書き込みチャネルがあれば配送できる。
**Q4**: exp が正しくコンパイルされ、送れたのに、走らせるとセグメンテーション違反/権限昇格しない。exp が無駄か?
**A4**: 先に環境要因を排除してから exp を疑う:カーネルにパッチが backport されているか(バージョン番号が騙す)、KASLR/SMEP/SMAP などの緩和があるか、コンテナ内か(NNP)、対象アーキテクチャが一致するか(x86_64 vs arm)。多くの「exp が動かない」は環境不一致であり、exp 自体の誤りではない。
**Q5**: exp を繰り返し調整しても成功せず、何度かマシンを崩しかけた。続けるべきか?
**A5**: 止める。カーネル exp のクラッシュ代償は高い(ブルースクリーンで足場喪失、露出)。判定基準:同じ exp を 2〜3 回試して不安定なら撤退し、設定系権限昇格(崩れない)か横展開に方向転換する。「このマシンで必ずカーネル権限昇格する」という執着を「より安定した経路か別のマシンに替える」に変える。

### LSM 制約(SELinux/AppArmor/seccomp)下の権限昇格判定
**Q1**: 権限昇格動作がしばしば不可解に拒否される(読めるはずのものが読めない、実行できるはずのものが実行できない)。強制アクセス制御を疑う。先に何を確認するか?
**A1**: LSM 状態を調べる:`getenforce`/`sestatus`(SELinux)、`aa-status` か /sys/kernel/security/apparmor(AppArmor)。SELinux enforcing では、あなたが root でも、SUID が正しくても、ポリシーが操作を遮ることがある。判定基準:enforcing/complain 状態 + 監査ログ(/var/log/audit)の denied レコード。
**Q2**: SELinux enforcing で、それが私の権限昇格を遮ると確認した場合、どう迂回するか?
**A2**: ポリシーが許可する経路を探す:SELinux ドメインが許可する別の操作/位置に替えて同じ目的を達成する(例 A に書けないが B に書ける、そして B でも権限昇格できる)。または緩いドメインを付与されたプロセスを利用する。SELinux 迂回は「ポリシーが許す隙間を通る」ことであり、正面から押し切らない。
**Q3**: AppArmor が私のプロセスに profile を付け、できることを制限する場合、どうするか?
**A3**: profile は実行可能パスにバインドされる。その profile に制約されない実行体に替えて payload を走らせる(例 profile が /usr/bin/foo だけを制限するなら、foo を使わない)。profile 制約から抜けるには、多くの場合「殻」プロセスを替えるだけでよい。
**Q4**: seccomp がシステムコールをフィルタしている(ある exp の syscall が直接 EPERM)場合、どう判断し対応するか?
**A4**: /proc/self/status の Seccomp フィールドを見る。seccomp 制限はコンテナ/サンドボックスに多い。対応:禁止された syscall に依存しない利用経路を選ぶか、先にサンドボックスから抜けてから権限昇格する。seccomp も「あなたが制限環境にいる」強シグナルで、エスケープの考え方に替えることを示唆する。
**Q5**: LSM が設定系権限昇格を全て遮断し、無理に迂回できない場合、どのディメンションに方向転換するか?
**A5**: 2 箇所に方向転換する:1 つはカーネル exp(カーネルモードで cred を変えるか、SELinux enforcing 状態を直接変えられれば、低層から LSM をひっくり返せる)。2 つ目は横展開。これほど厳しいポリシー制約のマシンは、本機の権限昇格の費用対効果が低いので、現有権限で横展開する方がよい。成熟した MAC ポリシーと正面から格闘しない。

### 権限昇格の全ディメンション枯渇:縦方向から横展開への判定と実行
**Q1**: sudo/SUID/cap/cron/サービス/カーネル/グループ権限を全て掘り尽くし、root がどうしても上がらない。手を止めて横展開に転換すべきかをどう判定するか?
**A1**: 「枯渇リスト」を構築する:7 大ディメンションを項目ごとに「調べたが成果なし」とマークする。7 項目全てにバツ、カーネル exp がパッチ/リスクで使えず、認証情報もスプレー空なら、本機の縦方向は枯渇と判定する。このとき続ける限界収益はほぼゼロなので、このマシンを正式に「root を取る対象」でなく「足場/踏み台」と位置づける。判定基準:ディメンションが本当に掘り尽くされたか、ある 1 ディメンションが深掘り不足なのかを先に自己点検する。
**Q2**: 横展開に転換する前、現在の低権限アカウントが横展開に何を提供できるか?
**A2**: 手元のアセットを棚卸しする:内部ネットワーク到達性(権限昇格できないと届かないホスト/セグメントにこのマシンが接続できる)、既に探り当てた認証情報、known_hosts/history が露出する信頼関係、マウントされた共有、このマシンの業務上の役割。低権限 shell は既に内部ネットワークを攻める完璧な踏み台であることが多く、root か否かはトラフィック中継に影響しない。
**Q3**: 具体的な最初の横展開動作は何をするか?
**A3**: このマシンを pivot にする:トンネル/プロキシを立てる(内部ネットワークをあなたのツールチェーンに露出)、既存認証情報で内部ネットワークにスプレーする(SSH/DB/web/SMB)、権限昇格面がより良いマシンを内部ネットワークで探す。戦役目標(ドメインコントローラー/重要データ)はしばしば、あなたが行き詰まったこのマシンにはない。入口を替えるとしばしば視界が開ける。
**Q4**: 「枯渇と思い込んだ」だけで実は漏れていないか?早すぎる諦めをどう避けるか?
**A4**: 横展開に転換する前に 1 回交差検証する:自動列挙(linpeas)を 1 回走らせて手動の盲区を補う、id の追加グループを見直す、pspy に漏れた時間ディメンションのタスクがないか見直す、認証情報収集が全ホームディレクトリ/設定/バックアップをカバーしたか確認する。別の方法で 1 回復査してから枯渇を宣言する。「掘り足りない」を「ない」と誤判断するのを防ぐ。
**Q5**: 横展開も当面局面を開けない場合、この線全体が死んだか?
**A5**: 死んでいない。戦役全体に戻る:別の初期足場、別の入口の方が価値があるかもしれない。レッドチームは多点開花を重視する。1 台の行き詰まりは戦役の行き詰まりではない。このマシンを安定した pivot として維持し、精力を他の攻撃面/他のホストに移し、いつでも戻れる能力を残す。早めに戦場を替えるのは能力であり、降参ではない。
