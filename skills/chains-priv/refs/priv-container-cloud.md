# 権限昇格と足場 · コンテナ/クラウド環境のエスケープと権限昇格の判定

### shell を取得した最初の一歩:自分が本当にコンテナ内にいるのか
**Q1**: Linux 環境に侵入して低権限 shell を取得したばかりのとき、先にカーネル権限昇格に力を注ぐべきか、それとも先にこれがコンテナかどうかを判断すべきか?
**A1**: 先に環境の形態を判断する。方向を誤ると後は全て無駄になる。判定基準は軽いものから順に:`cat /proc/1/cgroup` に docker/kubepods/lxc の文字が現れる、`ls -la /.dockerenv` または `/run/.containerenv` が存在する、`hostname` がランダムな hex である、`mount` で overlay がルートファイルシステムになっている、`cat /proc/1/comm` が systemd/init ではなくアプリケーションプロセスである。どれか 1 つに該当すれば基本的にコンテナである。
**Q2**: cgroup が既に cgroup v2 の統合階層になっており、明らかな文字列が見えない場合はどうするか?
**A2**: 直交するシグナルに切り替える:プロセス数が極めて少ない(`ps aux` に数個しかない)、一般的なシステムサービスがない、`/proc/1/root` の参照先が異常である、`capsh --print` で capability が削られている、`nsenter` が使えない。こうした「環境が非常にきれいで小さい」気配自体がコンテナのフィンガープリントである。
**Q3**: コンテナと判断した後、権限昇格の対象をどう再定義するか?
**A3**: 対象を「root in this box」から 2 層に引き上げる。1 つはコンテナ内の root(エスケープの準備)、もう 1 つはホストマシンの root(本当の足場)である。多くのコンテナは侵入時点で root なので、コンテナ内の権限昇格に時間を浪費せず、直接エスケープ面を調べる。
**Q4**: 自分がコンテナ内にいて既に root だと分かった場合、次に何を調べるか?
**A4**: すぐにエスケープの 4 要素を列挙する:capabilities(`capsh --print`)、マウント(`mount`、`cat /proc/mounts` で hostPath/docker.sock を探す)、デバイス(`ls /dev` で /dev/sda のようなブロックデバイスを探す)、privileged かどうか。この 4 つのどれかが緩んでいればエスケープ経路がある。
**Q5**: ホストマシンのベアメタル(非コンテナ)だと確認できた場合はどうか?
**A5**: その場合は従来の Linux 権限昇格連鎖に進む:SUID→sudo→cron→capability→カーネル。もうエスケープの概念にこだわらず、設定の不備を優先し、カーネル exploit を最後の手段にする。
**Q6**: この経路が完全に行き詰まった場合、標準的なコンテナでもなく権限昇格もできない、どこへ方向転換するか?
**A6**: 縦方向ではなく横展開に方向転換する:現在の権限で本機から到達できる他のサービス、認証情報ファイル(`~/.aws`、`~/.kube/config`、history、env)、内部ネットワークから到達できるホストを列挙する。権限昇格だけが唯一の活路ではなく、高価値の認証情報を 1 つ得る方が、本機の root に固執するより速く足場を築けることが多い。

### コンテナランタイムの種別を特定してエスケープ手法を決める
**Q1**: コンテナ内にいると確認したが、docker/containerd/CRI-O/k8s pod では手法の差が大きく、どう素早く種別を定めるか?
**A1**: プロセスと socket を見る。`/proc/mounts` に `/var/run/secrets/kubernetes.io` がある → これは k8s pod である。`/var/run/docker.sock` にアクセスできる → docker である。環境変数に `KUBERNETES_SERVICE_HOST` がある → k8s である。種別を定めてから SA token を探すべきか docker API を探すべきかが分かる。
**Q2**: k8s pod でありエスケープもしたい場合、優先順位をどう付けるか?
**A2**: k8s の場面では serviceaccount token(`/var/run/secrets/.../token`)と RBAC 権限を優先して調べる。コントロールプレーンの経路はカーネルエスケープより安定し隠蔽性も高いことが多いためである。カーネル/マウントのエスケープは token の権限が不足する場合の代替手段とする。
**Q3**: rootless container(userns の再マッピング)だと分かった場合はどうするか?
**A3**: rootless ではコンテナ内の root は実はホストマシンの通常 uid であり、多くのエスケープが無効になる。判定基準:`cat /proc/self/uid_map` が `0 0 4294967295` でないこと。このとき「コンテナの root=ホストの root」という幻想を捨て、マウントポイント、socket、またはホストマシン側の脆弱性に方向転換する。
**Q4**: ランタイムを判断できず、socket もマウントされていない場合は行き止まりなのか?
**A4**: 違う。capabilities とカーネルのディメンションに方向転換する。マウントの露出が全くなくても、CAP_SYS_ADMIN/CAP_SYS_MODULE があれば、またはホストカーネルに利用可能な CVE があれば、依然としてエスケープできる。先に `capsh --print`、次に `uname -r` で既知のエスケープ CVE と照合する。
**Q5**: 誤ったランタイムの手法に時間を浪費しないようにするには?
**A5**: 10 分間の列挙ウィンドウを設ける:token、mounts、caps、socket、カーネルバージョンの 5 項目を並べて一通り確認し、それから主攻方向を決める。1 つの手法に執着して一本道を突き進まない。

### privileged 特権コンテナの判定と利用
**Q1**: 現在のコンテナが privileged ではないかと疑う場合、どう確認するか?
**A1**: 特権コンテナはほぼ「全 capability + ホストのデバイスが見える」状態である。判定基準:`capsh --print` でほぼ全量の cap が表示される、`ls /dev` に sda/nvme などのホストのブロックデバイスが現れる、`cat /proc/1/status` の CapEff が `0000003fffffffff` のような満値である。該当すれば privileged である。
**Q2**: privileged と確認した後、最も直接的なエスケープ経路は何か?
**A2**: 最もクリーンな 1 つは、ホストのルートディスクを直接マウントすることである。`mkdir /mnt/host && mount /dev/sda1 /mnt/host` を実行し、ホストの cron、authorized_keys、SUID バイナリに書き込むか、直接 chroot する。ブロックデバイスが見える場合、これは cgroup のテクニックより安定する。
**Q3**: ブロックデバイスが見えないが privileged の場合、他に経路はあるか?
**A3**: ある。cgroup release_agent のエスケープを使う(CAP_SYS_ADMIN が必要で、privileged なら当然満たす)。コンテナ内で cgroup コントローラーをマウントし、release_agent にホストで実行するスクリプトを指定して書き込み、プロセス終了をトリガーすればホストの root で実行される。
**Q4**: ディスクパーティション名が分からない(sda1? vda?)。盲目的にマウントすると壊してしまわないか?
**A4**: 先に `cat /proc/partitions` または `lsblk`(あれば)でパーティションを確認し、次に読み取り専用でマウントして(`mount -o ro`)偵察する。ホストのルートと確認してから読み書きする。不明なデバイスに直接書き込まず、対象の破壊を避ける。
**Q5**: privileged のエスケープコマンドを実行したが反応がない/遮断された場合、どこへ方向転換するか?
**A5**: AppArmor/seccomp のディメンションの調査に方向転換する。privileged でもホストが LSM 制限を重ねている可能性がある。`cat /proc/self/attr/current` を見る。LSM に遮断された場合は、docker.sock(マウントされていれば)や SA token などのコントロールプレーン経路に方向転換し、カーネルモードの動作を回避する。

### CAP_SYS_ADMIN など危険な capability の利用選択
**Q1**: 非 privileged だが `capsh --print` に CAP_SYS_ADMIN がある場合、何ができるか?
**A1**: CAP_SYS_ADMIN は「半分の root」であり、最も典型的なのは cgroup release_agent エスケープとマウント操作である。先に cgroup をマウントできるか確認し(v1 の方が利用しやすい)、次に release_agent 連鎖に進む。これはカーネル CVE に依存しない安定したエスケープである。
**Q2**: CAP_SYS_MODULE がある場合はどうか?
**A2**: それは直接のエスケープである。`insmod` で悪意あるカーネルモジュールをロードし、ホストのカーネルモードで任意コードを実行できる。極小の LKM を構築し、init 内でリバースやホストファイルへの書き込みを実行する。前提はホストカーネルのバージョン/ビルド環境が一致することなので、先に `uname -r` で合わせる。
**Q3**: CAP_DAC_READ_SEARCH または CAP_DAC_OVERRIDE はあるが SYS_ADMIN がない場合はどうか?
**A3**: DAC_READ_SEARCH は open_by_handle_at と組み合わせてホストの任意ファイル読み取りができる(shocker 系の手法)。ホストの機微ファイル/認証情報を盗める。DAC_OVERRIDE はファイルの権限ビットを無視して読み書きできる。これらは直接の実行ではないが、認証情報を得て横展開するには十分である。
**Q4**: CAP_NET_ADMIN/CAP_NET_RAW がある場合、権限昇格に役立つか?
**A4**: 本機の権限昇格への寄与は限定的だが、横展開には非常に有用である。スニッフィング、ARP スプーフィング、ルート変更による中間者攻撃ができる。縦方向のエスケープが行き詰まったとき、これが「ホスト/隣接のトラフィックを乗っ取って認証情報を得る」ための入口になる。
**Q5**: cap が多数あるがどの利用も失敗する場合、seccomp に遮断されているかどうかをどう判断するか?
**A5**: capability の許可はシステムコールの許可と同義ではない。seccomp は mount、init_module、open_by_handle_at などの重要な syscall を遮断する。小さなプログラムを書いて対象の syscall を単独で呼び、EPERM/返り値 -1 になるかを確認する。seccomp に遮断されたと確認できたら、制限を受けていない他の cap やマウント経路に方向転換する。

### docker.sock がコンテナにマウントされた場合の利用
**Q1**: `mount` で `/var/run/docker.sock` がコンテナにマウントされているのを見た場合、これは何を意味するか?
**A1**: ほぼホストの root に等しい。docker.sock は Docker デーモンの制御入口であり、これを通じて任意のコンテナを作成できる。先に `curl --unix-socket /var/run/docker.sock http://localhost/version` を試すか、docker クライアントがあれば `docker -H unix://... ps` を実行する。
**Q2**: コンテナ内に docker クライアントがない場合はどうするか?
**A2**: curl で直接 HTTP API を使う。POST /containers/create でホストのルート `/` を /host にマウントし、かつ privileged な新コンテナを作成し、start、exec する。全工程が REST であり、クライアントは不要である。API エンドポイントは安定した公開インターフェースである。
**Q3**: 具体的にどう実行してホストの root を得るか?
**A3**: 新コンテナの HostConfig の Binds に `["/:/host"]` を設定し、起動後にその中で chroot /host を実行すればホストの root 視点になる。cron/authorized_keys/passwd に書き込むか、直接リバースする。核心は docker の正当な能力を使ってホストのディスクを自分にマウントすることである。
**Q4**: docker.sock へのリクエストが 403/権限拒否を返す場合、もう手詰まりなのか?
**A4**: authz プラグインや socket の権限制限がある可能性がある。同種の socket の調査に方向転換する:containerd.sock、crio.sock、podman.sock、または k8s 場面の kubelet。1 つがロックされていても全てがロックされているわけではないので、全ての runtime socket を横に列挙する。
**Q5**: 何もマウントされていないがホストで docker が動いていると分かっている場合、どう方向転換するか?
**A5**: ネットワークのディメンションに方向転換する:Docker のリモート API ポート(2375/2376)が内部ネットワークから到達できるか調べる。暗号化されていない 2375 の露出はリモートからの未認証制御を意味する。これで「ローカルに socket がない」問題を「内部ネットワークのサービスの露出」問題に転換する。

### hostPath / ホストディレクトリマウントの利用
**Q1**: `mount` で何らかのホストディレクトリがコンテナにマウントされている場合(例 /data、/var/log)、価値をどう評価するか?
**A1**: マウントポイントが「挙動を変更できる経路」に触れるかを見る。`/`、`/etc`、`/root`、`/var/spool/cron` がマウントされているなら致命的である。`/var/log` のマウントも、ホストプロセスが読むログ/設定への書き込みを通じて間接的に利用できる。先に `mount | grep -v overlay` でマウント元を全量確認する。
**Q2**: マウントされたのがホストの `/` 全体または `/host` の場合、直接どう使うか?
**A2**: ホストの権限昇格ポイントに直接書き込む:root の authorized_keys、`/etc/cron.d/` へのスケジュールタスク配置、あるホストバイナリへの SUID 付与(chmod u+s)、または `/etc/passwd` を変更して root ユーザーを追加する。最も隠蔽性の高い 1 つを選ぶ。
**Q3**: 業務ディレクトリ 1 つだけがマウントされ、機微な経路ではない場合、まだ見込みはあるか?
**A3**: ある。このディレクトリ内のファイルをホストプロセスがロードするかを調べる:設定、スクリプト、cron が参照するもの、web ルートディレクトリ。「ホストが能動的に読む/実行する」これらのファイルへ注入し、ホストプロセスの手を借りて実行する。マウントポイントが機微でないことは利用不能を意味せず、データの流れを見る必要がある。
**Q4**: マウントが読み取り専用(ro)で書き込めない場合はどうするか?
**A4**: 読み取り専用なら「読む」価値に方向転換する:中にホストの認証情報、鍵、token、設定内のパスワードがないか。ro マウントはしばしば secret を露出する。認証情報を読めたら横展開/コントロールプレーンの権限昇格に方向転換し、書き込みに固執しない。
**Q5**: hostPath が k8s の場面だが、現在の pod に機微な経路がマウントされていない場合、どう方向転換するか?
**A5**: RBAC に方向転換する:SA に pod 作成権限があれば、hostPath `/` をマウントした pod を自分で作成して対象 node にスケジュールする。「この pod にはマウントされていない」を「マウント済みの pod を作成する権限がある」に変える。コントロールプレーンの権限 > 現在の pod 設定である。

### /proc、/sys の露出と core_pattern / release_agent
**Q1**: コンテナ内の `/proc` または `/sys` がホストのもので書き込み可能な場合、どう利用するか?
**A1**: 書き込み可能な `/proc/sys/kernel/core_pattern` は定番である。`|/path/to/evil` と書き、ホストがプロセスクラッシュ時に root でそのプログラムを実行するようにし、故意に core dump をトリガーする。前提は /proc がコンテナの再マウントで遮蔽されていないことである。
**Q2**: core_pattern の経路は crash のトリガーが必要だが、どう安定してトリガーするか?
**A2**: コンテナ内で必ずクラッシュする小さなプログラム(例えば故意のセグメンテーション違反)を実行する。core_pattern のパイプ処理はホストの init 名前空間で実行されるため、handler はホストの root を得る。handler の経路がホストから見えることを確認する(マウントと合わせて)。
**Q3**: `/sys/fs/cgroup` が書き込み可能な場合はどうか?
**A3**: release_agent を使う:notify_on_release + release_agent の組み合わせで、プロセス終了時にホストが指定スクリプトを実行する。CAP_SYS_ADMIN の経路と同源だが、違いはここでは cap ではなく /sys マウントの露出に依存する点である。2 つの判定基準は独立しており、どちらかを満たせばよい。
**Q4**: core_pattern に書き込めない(EACCES)場合、手詰まりなのか?
**A4**: /proc が読み取り専用または再マウントで保護されていることを示す。release_agent(/sys 経由)に方向転換するか、逆に uevent_helper(`/sys/kernel/uevent_helper`)を調べる。これも「カーネルがホスト実行をコールバックする」族であり、保護されていない別の入口に替える。
**Q5**: /proc、/sys が全てコンテナの安全なマウントで遮蔽され、族全体が無効な場合、どこへ方向転換するか?
**A5**: capability + カーネル CVE の組み合わせに方向転換する:/proc/sys の遮蔽が防ぐのは「設定型エスケープ」であり、カーネルのメモリ破壊型 exploit は防げない。`uname -r` を調べ、dirtypipe/dirtycow/OverlayFS などのホストカーネル CVE と照合する。

### カーネル CVE エスケープと runc/containerd CVE の取捨選択
**Q1**: 設定面でエスケープ口が見つからず、カーネル CVE に踏み切る準備をする場合、先に何をするか?
**A1**: 先にカーネルバージョン `uname -r` とディストリビューションを正確に取得し、既知のエスケープ系 CVE(例 DirtyPipe、DirtyCOW、OverlayFS 権限昇格、および runc の CVE-2019-5736 による runc 上書き)と照合する。盲目的に exploit を撃たず、先にバージョンが影響範囲に入ることを確認する。
**Q2**: カーネル exploit には失敗リスク(panic)があるが、撃つべきか?
**A2**: 比較検討する:メモリ破壊型 exploit にはクラッシュの確率があり、レッドチームが隠蔽性を重視するなら設定型エスケープの後に回すべきである。他に経路がなく認可も許す場合、成熟して安定した PoC を選び、先に同一バージョン環境で検証してから対象に投入する。
**Q3**: CVE-2019-5736 のような「runc の上書き」手法の適用条件は何か?
**A3**: コンテナ内で 1 回の `docker exec`/attach を誘導できる必要があり、そのタイミングでホストの runc バイナリを上書きする。判定基準:対象の運用者がコンテナに入って操作する、runc のバージョンが影響範囲内であること。人が対話しない静かなコンテナなら、このタイミングは成立しないので経路を替える。
**Q4**: exploit をコンパイルできない(コンテナ内に gcc がない/ネットワークがない)場合はどうするか?
**A4**: 「外でコンパイル、中で実行」に方向転換する:同一バージョン環境で静的コンパイルしたバイナリを、既存のチャネルで持ち込む。または純スクリプト/コンパイル不要の PoC を選ぶ。コンパイル環境の欠如は exploit を諦める理由にはならず、転送の問題である。
**Q5**: exploit を撃ったが権限昇格せず、クラッシュもしない場合、失敗原因をどう判断するか?
**A5**: 項目ごとに切り分ける:カーネルにパッチがあるか(バージョン番号が範囲内でも backport で修正済みの可能性がある)、seccomp が exploit の使う syscall を遮断したか、KASLR/保護が効いているか。緩和策に遮断されたと確認できたら、設定型またはコントロールプレーン経路に方向転換し、同じ exploit を繰り返し試さない。

### Linux SUID 権限昇格の列挙と判読
**Q1**: ベアメタルの低権限 shell で SUID を調べ始める。コマンドと判読の考え方は何か?
**A1**: `find / -perm -4000 -type f 2>/dev/null` を実行する。1 つずつ照合する:GTFOBins で既知の権限昇格可能なものか(shell エスケープのある find/vim/nmap の旧バージョン/env など)、または自作の SUID バイナリか(注入/パスの問題がある可能性が高い)。システム標準の正常な SUID は無視する。
**Q2**: リストが全て標準のシステムバイナリで、明らかな GTFOBins 項目がない場合はどうするか?
**A2**: 2 つの方向に方向転換する:1 つはバージョンを調べる(ある標準バイナリの旧バージョンには既知の SUID 権限昇格 CVE がある)。もう 1 つは非標準パス下の SUID(/opt、/usr/local、ホームディレクトリ)を重点的に見る。それらは運用者が自ら追加したもので、呼び出す外部コマンド、相対パス、パラメータ注入を監査する。
**Q3**: 自作の SUID プログラムを 1 つ見つけた場合、その利用ポイントをどう探すか?
**A3**: 何を呼び出すかを見る。`strings`/`ltrace` で、system()/popen() で外部コマンドを呼び出し、かつ相対パスや制御可能なパラメータを使うかを確認する → PATH ハイジャックまたはパラメータ注入。制御可能な設定ファイルを読むか、バッファ問題があるかも見る。核心は「root として、私が制御できる何を信頼しているか」である。
**Q4**: SUID プログラムが外部コマンドを呼び出すが絶対パスを使っており、パラメータも制御できず行き詰まった場合、どこへ方向転換するか?
**A4**: capability ファイルに方向転換する(`getcap -r / 2>/dev/null`)。権限昇格ポイントには SUID ビットではなくファイル capability の場合がある(例:あるバイナリが cap_setuid を持つ)。SUID の 1 本が行き止まりでも、capability は並行して独立した 1 本の線である。
**Q5**: SUID も capability もクリーンな場合、「root で動く」入口には他に何があるか?
**A5**: root が所有する実行中のプロセスとサービスに方向転換する:cron、systemd ユニット、root でリッスンするローカルサービス(データベース、メッセージキュー)。権限昇格の本質は「root コンテキストを借りる」ことであり、SUID はその一形態にすぎない。

### sudo の設定不備による権限昇格
**Q1**: `sudo -l` が実行でき、パスワード不要で実行できるコマンドが列挙された場合、どう判読するか?
**A1**: 「shell を派生できる、または任意ファイルを読み書きできるコマンド」を探す。sudo で vi/less/awk/find/env/tcpdump などを実行できる → GTFOBins で直接 root shell にエスケープする。あるスクリプトを実行できる → そのスクリプトを私が変更できるか、制御可能な内容を呼び出すかを確認する。
**Q2**: sudo で実行できるのが具体的なバイナリ 1 つで、パラメータにも制限がある場合、どう迂回するか?
**A2**: ワイルドカード/相対パスで隙を突けるかを見る:ルール内の `*` はしばしば追加パラメータで利用できる。コマンドが設定/プラグイン/プリロードのロードに対応していれば注入できる。sudo のバージョン自体にも注意する(sudoedit、Baron Samedit などのヒープオーバーフロー CVE があった)。`sudo --version` で照合する。
**Q3**: sudo のバージョンが Baron Samedit(CVE-2021-3156)の範囲内だが、パッチ適用済みか不確かな場合はどうするか?
**A3**: 非破壊の検知方法で脆弱性の有無を直接検証し(クラッシュしない判定経路をトリガーする)、確認してから完全な exploit に進む。最初から完全な PoC を撃ってクラッシュリスクを負わない。
**Q4**: `sudo -l` がパスワードを要求するがパスワードがない場合はどうするか?
**A4**: 既知のパスワードが不要な経路に方向転換する:sudo バージョンの CVE(Baron Samedit はパスワード不要)、または sudo の線を完全に諦めて SUID/cron/capability/カーネルに戻る。`sudo -l` がパスワードを要求しても sudo ディメンション全体が無駄なわけではなく、パスワード不要リストの線が無駄なだけである。
**Q5**: env_keep に LD_PRELOAD/LD_LIBRARY_PATH が保持されている場合、どう使うか?
**A5**: それは直接の権限昇格である。悪意ある .so を構築し、呼び出される関数(例 geteuid)をエクスポートする。sudo が許可された任意のコマンドを実行する際、LD_PRELOAD がそれをロードして root で動く。前提は sudoers に env_keep+=LD_PRELOAD があるか Defaults が未クリーンなことで、`sudo -l` の出力で確認できる。

### cron / スケジュールタスクの権限昇格
**Q1**: cron の権限昇格を調べたい場合、先にどこを見るか?
**A1**: `cat /etc/crontab`、`ls -la /etc/cron.*`、`/var/spool/cron/` を確認し、root で動くタスクのうち「私が書き込めるファイル/ディレクトリ/スクリプトを参照している」もの、またはワイルドカードや相対パスを使っているものを重点的に探す。システム標準のタスクは無視する。
**Q2**: root の cron がスクリプトを実行しているが、そのスクリプトを変更できない場合はどうするか?
**A2**: スクリプト内部を見る:あるディレクトリに cd してからワイルドカードを使うか(`tar *`、`chown *` のワイルドカード注入)、私が書き込める設定を source するか、PATH 内で私がハイジャックできるコマンドを呼ぶか。root が書き込み不可でも、連鎖の各環が全て書き込み不可とは限らない。
**Q3**: crontab の内容が見えない(権限不足)が cron があると疑う場合、どう確認するか?
**A3**: 傍路観測に方向転換する:pspy のような無権限のプロセス監視ツールで、周期的に root で起動するプロセスを観察し、cron タスクとそれが呼び出すファイルパスを逆推定する。設定が見えなければ挙動を見る。
**Q4**: cron タスクが全てクリーンで書き込み可能な参照がない場合、どこへ方向転換するか?
**A4**: 他の「周期的な root 実行」の担い手に方向転換する:systemd timer、anacron、およびアプリケーション内蔵のスケジュールロジック。cron はスケジュール権限昇格の一形態にすぎず、timer はしばしば見落とされる。
**Q5**: cron のペイロードを書き込んだがなかなかトリガーされない場合、どう調査するか?
**A5**: 時刻フィールドの解釈が間違っていないか、cron サービスが動いているか(`systemctl status cron`)、ペイロードに構文エラーがあってタスク全体が失敗していないかを確認する。トリガーが本当に制御できないなら、即時性の高い経路(書き込み可能な service を即再起動、SUID)に方向転換し、待つだけにしない。

### 書き込み可能な systemd unit / service による権限昇格
**Q1**: 権限昇格できる書き込み可能なサービスファイルがあると疑う場合、どう特定するか?
**A1**: 権限が緩い unit を探す:`find /etc/systemd/ /lib/systemd/ -writable 2>/dev/null`。さらに root サービスの ExecStart が指すバイナリ/スクリプトを私が書き込めるかを調べる。「root サービスがロードするものを私が変更できる」に該当すればよい。
**Q2**: unit ファイル自体が書き込み可能な場合、どう実行するか?
**A2**: ExecStart をペイロードに変更し、そのサービスの再起動をトリガーする(`systemctl restart`。権限がなければホストの再起動を待つか、再起動できる手段を探す)。要点はリロードをトリガーできるかで、できないと変更しても効かない。
**Q3**: unit は書き込み不可だが ExecStart のスクリプトは書き込み可能な場合はどうか?
**A3**: その方がより直接的である。スクリプト内容を変更するだけで、次回サービス起動時に root で実行される。判定基準は常に「root コンテキストが最終的に実行するファイルを誰が書き込めるか」であり、ExecStart→スクリプト→スクリプト内の参照と層を下って書き込み可能ポイントを探す。
**Q4**: サービスの restart 権限がなく、ホストもすぐには再起動しないため行き詰まった場合はどうするか?
**A4**: 即時トリガーの権限昇格面に方向転換する:SUID、sudo、即トリガーできる socket サービス。service の権限昇格は「いつ再起動するか」に制約される。トリガーが制御できないときは優先度が下がるので、私が能動的にトリガーできる担い手に替える。
**Q5**: 新規 unit は作成できるが既存のものは変更できない場合、役に立つか?
**A5**: 役に立つ。新規 unit を `systemctl link`/enable して start する権限があれば、直接 root で実行するのと等しい。前提は現在のユーザーが systemctl に対して対応する認可を持つこと(しばしば sudo/polkit の設定不備と組み合わさる)なので、先に start できるか試す。

### NFS no_root_squash による権限昇格
**Q1**: 本機または内部ネットワークに NFS エクスポートがあるのを見つけた場合、権限昇格に使えるかをどう判断するか?
**A1**: 重要なのはエクスポートオプションに `no_root_squash` があるかである。`cat /etc/exports`(本機)または `showmount -e <server>`(リモート)で確認する。no_root_squash はクライアントの root が書き込んだファイルがサーバー側でも root 所有のままであることを意味し、SUID を仕込める。
**Q2**: no_root_squash を確認した後、どう権限昇格するか?
**A2**: 私が root を持つマシンでそのエクスポートをマウントし、SUID 付きの shell バイナリを置く(chown root、chmod 4755)。その後、対象マシンでそれを実行すれば root を得られる。核心は NFS を借りて「私の root 所有」を対象に投影することである。
**Q3**: 対象マシンに root がなく、別の場所で SUID を作れない場合はどうするか?
**A3**: 連鎖方式に方向転換する:先に別の手段で、マウント可能なクライアントのどれか 1 台の低コスト root を得る(コンテナ/ローカル仮想マシンでもよい)。その後 NFS を使う。制御可能な root 側が全くない場合、この no_root_squash は使えないので、他の権限昇格面に戻る。
**Q4**: showmount がファイアウォールに遮断され、エクスポートリストが見えない場合は手詰まりなのか?
**A4**: そうとは限らない。直接の検知に方向転換する:mountd/nfs ポートが開いているか、既知のエクスポートパスを盲目的にマウントしてみる。showmount が遮断されたのは列挙が制限されただけで、サービス自体はマウントできる可能性がある。
**Q5**: エクスポートに root_squash(squash あり)が付いている場合、完全に無駄か?
**A5**: 権限昇格の用途は制限されるが、データの価値に方向転換する:通常ファイルの読み書きは依然として可能であり、エクスポート内に他のユーザーが読める認証情報、鍵、バックアップがあれば、同様に横展開に使える。権限昇格の失敗はその NFS が無価値であることを意味しない。

### Kubernetes ServiceAccount token の発見と使い方
**Q1**: k8s pod 内にいると確認した場合、先にどう SA token を得るか?
**A1**: `cat /var/run/secrets/kubernetes.io/serviceaccount/token` を実行する。同じディレクトリに ca.crt と namespace がある。これは pod が標準でマウントする身元である。取得後、これで API server に認証し、何ができるかはバインドされた RBAC に依存する。
**Q2**: token がある場合、この SA の権限境界をどう素早く調べるか?
**A2**: `kubectl auth can-i --list`(token 付き)、または curl で直接 API server の SelfSubjectRulesReview を呼ぶ。create pods、pods/exec、get secrets、create clusterrolebinding のような高リスクの動詞があるかを重点的に見る。
**Q3**: token の権限が非常に小さい(何も can-i not)場合、無駄なのか?
**A3**: 先に捨てない。2 点に方向転換する:1 つは他の namespace/pod により高権限の SA がマウントされているかを列挙する(別の pod を得れば身元を替えられる)。もう 1 つは、この小さな権限に get secrets があるかである。pod を作成できなくても、secret を読めればより強い認証情報を得られる可能性がある。
**Q4**: SA に create pod 権限がある場合、どう node/ホストまで昇格するか?
**A4**: privileged または hostPath `/` をマウントした pod を作成し、nodeName で対象ノードを指定する。入った後、ホストディスクを chroot すれば node の root である。pod 作成権限を持つことはほぼ全 node の root を持つことに等しく、k8s で最も費用対効果の高い権限昇格である。
**Q5**: API server への token リクエストが 401/403 を返す場合、どう調査するか?
**A5**: 401 は token が無効である(期限切れ/削除済み/マウントされたのが投影短期 token で更新が必要)→ ファイルを読み直す。403 は認証されたが RBAC が許可しない → 権限の列挙に戻り、SA を替える。401/403 の区別が「token を替える」か「権限経路を替える」かを決める。
**Q6**: API server にネットワーク到達できない場合はどうか?
**A6**: kubelet(専用の条項を参照)またはローカルエスケープに方向転換する。コントロールプレーンに到達できないとき、pod→node のローカルエスケープ(hostPath/privileged/カーネル)が代替経路になる。到達できない API に時間をかけない。

### k8s RBAC 列挙から権限昇格経路への推論
**Q1**: 中程度の権限の SA を得た場合、やみくもに試すのではなく、どう体系的に権限昇格連鎖を探すか?
**A1**: RBAC をグラフとして辿る。私が create/update できるリソースを列挙し、それぞれに「それは私に、より高い身元またはコード実行をもたらすか」と問う。典型的な高リスクの辺:create pods(任意の SA を選んでマウント)、create rolebinding/clusterrolebinding(自分を admin にバインド)、あるコントローラーの update(その SA を乗っ取る)、escalate/bind 動詞。
**Q2**: create rolebinding はあるが escalate 権限がない場合、自己権限昇格できるか?
**A2**: 制限される。RBAC には権限昇格防止の設計があり、escalate/bind の明示的な付与がない限り、自分の権限を超える role をバインドできない。判定基準:先に、既存の高権限 ClusterRole に bind できる口があるかを見る。escalate チェックに遮断された場合は、create pods+高権限 SA のマウントという迂回経路に方向転換する。
**Q3**: create pod はできるが任意の SA を指定できない場合はどうするか?
**A3**: 「名前空間内の既存の高権限 SA を探す」ことに方向転換し、pod の serviceAccountName をそれに設定する。その ns で pod を作成でき、かつその SA が存在すれば、通常はその身元を借りられる。前提はその SA に対して追加の use 制限がないこと(admission 制限があるか確認する)。
**Q4**: 直接の権限昇格動詞が全てなく、get/list ばかりの場合、どこへ方向転換するか?
**A4**: 情報収集に方向転換する:list secrets/configmaps でハードコードされた認証情報を探す、list pods で他の pod に何がマウントされているか見る、get nodes でバージョンを取得して CVE と照合する。読み取り専用権限の価値は「次の攻撃対象を見つける」ことであり、RBAC の行き止まりを偵察の成果に変える。
**Q5**: 現在が既に頂点(cluster-admin)かどうかをどう判断するか?
**A5**: `can-i '*' '*' --all-namespaces` が yes を返せば頂点である。頂点に達した後は、対象を権限昇格から足場の固定と横展開(etcd の取得、各ノードの取得、クラウド認証情報の取得)に切り替え、もう RBAC にこだわらない。

### kubelet API(10250)の未認可利用
**Q1**: pod から API server に到達できないが、node の 10250 には接続できる場合、どう使うか?
**A1**: kubelet の読み取り専用/読み書き API が anonymous-auth または緩い認可で設定されている場合、直接 pod を列挙して exec できる。先に `curl -sk https://<node>:10250/pods` で、無認証で pod を列挙できるか見る。列挙できればおそらく exec もできる。
**Q2**: pod を列挙できた後、どうコード実行/認証情報を得るか?
**A2**: kubelet の exec API で対象 pod 内のコマンドを実行する(高権限 SA の pod を選ぶ)。その token を読んでから API server を再攻撃するか、機微な pod 内で直接操作する。kubelet を踏み台にして、より強い身元を得るのに等しい。
**Q3**: 10250 が 401/Unauthorized を返す場合はどうするか?
**A3**: Webhook 認可が有効であることを示す。10255(読み取り専用 kubelet、しばしば無認証)に方向転換し、pod リスト/環境変数内の認証情報が漏れるかを見る。またはローカルエスケープに戻る。10250 がロックされても node のパネル全体がロックされているとは限らない。
**Q4**: 10255 も無効で 10250 も認証が必要な場合、この線は全体として無駄か?
**A4**: その通りで、kubelet の線は無駄である。直交するディメンションに方向転換する:この pod のローカルエスケープ(hostPath/privileged/caps/カーネル)、またはクラウド metadata サービスで node のクラウド身元を得る。node の攻撃面は kubelet の 1 ポートだけではない。
**Q5**: kubelet に時間をかける価値があるかをどう判断するか?
**A5**: 先に curl 1 回で /pods のレスポンスを調べて定性する:無認証で列挙できれば高価値で必ず攻める。認証が必要なら、ついでに 10255 を試してから即方向転換し、深入りしない。

### クラウド metadata サービス(169.254.169.254)の利用
**Q1**: クラウド上のホスト/コンテナに侵入した場合、最初に metadata サービスを攻めるべきか?
**A1**: 攻めるべきである。これはクラウド環境の権限昇格の第一の入口である。`curl http://169.254.169.254/latest/meta-data/`(AWS)または各ベンダー対応のパスを叩く。返ればインスタンスロール、一時認証情報を列挙できる。それはしばしば「ホスト権限」から「クラウド身元」へ跳ぶ橋である。
**Q2**: metadata 内の一時認証情報を得た後、どう使うか?
**A2**: AWS では `iam/security-credentials/<role>` から AccessKey/SecretKey/Token を得て、ローカルの aws cli に設定するか直接 API を呼ぶ。このときの権限はそのインスタンスロールの IAM 権限に等しく、次はこのロールが何をできるか列挙する。
**Q3**: 対象が AWS で metadata が 401 を返し、IMDSv2 のように見える場合はどうするか?
**A3**: IMDSv2 は先に PUT で token を得て、その token を付けて GET する必要がある:先に `curl -X PUT .../latest/api/token -H "X-aws-ec2-metadata-token-ttl-seconds: 21600"` を実行し、返った token を header にしてリクエストする。401 は多くの場合 v2 のハンドシェイクを踏んでいないだけで、本当に到達不能なわけではない。
**Q4**: metadata に完全に到達できない場合(iptables/hop-limit やプロキシに遮断)、どこへ方向転換するか?
**A4**: 他のクラウド身元の供給源に方向転換する:ホスト上の `~/.aws/credentials`、環境変数内のクラウド認証情報、k8s の IRSA/workload identity の投影 token、CI/CD が注入する鍵ファイル。metadata はクラウド身元の入口の 1 つにすぎず、認証情報はディスクや環境にも残ることが多い。
**Q5**: これがコンテナの場合、metadata で得られるのは node のロールか pod のロールか?
**A5**: 標準では node のインスタンスロールである(権限がより大きいことが多い)。ただしクラスタが IRSA/Workload Identity で pod に個別の身元を与えている場合は別である。判断:投影された web identity token があるか。node ロールを得る方が pod ロールより価値が高いことが通常なので、優先する。

### クラウド IAM 権限の列挙と権限昇格
**Q1**: クラウド認証情報を 1 組得た場合、それが権限昇格できるか、どこまで横展開できるかをどう判断するか?
**A1**: 先に `aws sts get-caller-identity` で身元を確認し、次に権限を列挙する。盲目的に呼ばず、先に iam:ListAttachedRolePolicies などの自己検査権限があるかを見る。なければ「試行的な呼び出し+エラーメッセージ」で境界を推測する。目標は IAM 権限昇格の原語を見つけることである。
**Q2**: 重点的に探すべき一般的な IAM 権限昇格の原語には何があるか?
**A2**: iam:CreatePolicyVersion(自分のポリシーを変更)、iam:PassRole+関連サービス(高権限ロールを lambda/ec2/glue に渡して代わりに実行させる)、iam:AttachUserPolicy(自分に AdminAccess を付与)、lambda コードの更新、UpdateAssumeRolePolicy(信頼ポリシーを変更して自分が高権限ロールを assume できるようにする)。どれか 1 つに該当すれば垂直方向の権限昇格ができる。
**Q3**: PassRole はあるがどのサービスに渡せるか不確かな場合、どう試すか?
**A3**: pass できる高権限ロールを列挙し、私が create/invoke 権限を持つサービス(lambda/ec2/ecs)を 1 つ見つけて受け皿にする。PassRole は単独では無意味で、「私の代わりに実行してくれ、かつ私が制御できる」サービスと組み合わせて初めて成立する。
**Q4**: 列挙時に AccessDenied が多発し、権限が小さすぎる場合はどこへ方向転換するか?
**A4**: コントロールプレーンではなくデータ面に方向転換する:この小さな権限で S3 バケット、Secrets Manager、SSM Parameter Store、DynamoDB を読めるか。そこにはより高権限の認証情報/パスワードが保存されていることが多い。IAM の権限昇格ができなければ鍵の保管庫を探り、連鎖的に、より強い身元に替える。
**Q5**: 列挙動作が GuardDuty/CloudTrail のアラートをトリガーしないようにするには?
**A5**: レッドチームが隠蔽性を重視する場合、高ノイズの動作を減らす(大規模な List、失敗した呼び出しは AccessDenied レコードを残す)。受動的な情報(metadata、ディスク上の認証情報、既知のサービス)を優先し、最小限の API 呼び出しで権限昇格連鎖を 1 本特定してから正確に実行し、全量の権限ブルートフォースはしない。

### クラウド認証情報漏えい後の横展開と永続化の判断
**Q1**: 長期の AccessKey(非一時)を得た場合、一時認証情報と扱い方に何か違いがあるか?
**A1**: 長期 key は期限がなく、永続化に向くが、監視もより厳しい。先にそれがユーザーのものかロールのものか判断する:ユーザー key(AKIA で始まる)は長期に使える。ロールの一時認証情報(ASIA)は期限が切れるので更新が必要である。定性してから「持続的なアクセスを固める」か「TTL 内に急いで行動する」かを決める。
**Q2**: クラウド上に永続化バックドアを作る場合、費用対効果が高く比較的隠蔽性のある動作は何か?
**A2**: 低ノイズを優先する:既存ユーザーにアクセスキーを 1 つ追加する、目立たない IAM ユーザーを作成する、またはある role の信頼ポリシーを変更して外部アカウントが assume できるようにする。目立つ AdministratorAccess ユーザーの作成は避ける。要点は正常なリソースの命名に紛れ込むことである。
**Q3**: この認証情報が無効化/ローテーションされ、アクセスが突然全て 403 になった場合はどうするか?
**A3**: 収集済みの他の身元に方向転換する:以前に dump した他の key、metadata から再取得できる一時認証情報、他のホスト上の認証情報ファイル。単一点が失効したとき、認証情報の「冗長な供給源」があなたの回復力になる。そのため、初期段階で多点収集しておく。
**Q4**: どのクラウドサービスへ横展開すべきかをどう判断するか?
**A4**: この身元が「読める・変更できる」リソースに沿って進む:S3/Secrets を読める → データと二次認証情報を取る。Lambda/EC2 userdata を変更できる → コード実行。IAM を操作できる → 権限昇格。「対象データ/より高い権限に最も近い」順に並べ、1 つのサービスに固執して猛攻しない。
**Q5**: マルチクラウドまたはハイブリッド(クラウド認証情報+踏み入れたホスト)の場合、どちらを優先するか?
**A5**: 対象の価値密度を見る。クラウドコントロールプレーンで高権限 IAM を得れば、多くのリソースを一掃できることが多いので、通常は優先する。ただし対象データが特定のホスト/内部ネットワークにあるなら、クラウド身元を踏み台にして内部ネットワークへ攻め戻る。両者は互いのてことなり、片方だけに注目しない。

### Windows 権限昇格:トークンとサービス権限
**Q1**: Windows 上で低権限 shell(例 IIS/サービスアカウント)を得た場合、先に何を列挙するか?
**A1**: 先に現在の身元と特権を見る:`whoami /priv`、`whoami /groups`。サービスアカウントはしばしば SeImpersonatePrivilege/SeAssignPrimaryToken を持つ。これは直接 Potato 系のトークン権限昇格(SYSTEM で実行)につながる。この特権があれば権限昇格はほぼ確実である。
**Q2**: SeImpersonatePrivilege がある場合、どう実行するか?
**A2**: Potato ファミリーを使う(RoguePotato/PrintSpoofer/GodPotato など。Windows バージョンと DCOM/Spooler の有無による)。SYSTEM トークンを誘導して impersonate する。どれを選ぶかは対象のバージョンと利用可能なトリガー面で決め、先にどのコンポーネントが使えるか調べる。
**Q3**: whoami /priv でそれらの特権が全て Disabled の場合、まだ使えるか?
**A3**: 使える。Disabled は現在有効化されていないだけであり、権限昇格ツールが自ら有効化する。本当にない(Not listed)ときだけがない。Disabled に惑わされて SeImpersonate の黄金の経路を諦めない。
**Q4**: トークン系の特権が全くない場合、どこへ方向転換するか?
**A4**: 設定面に方向転換する:サービス権限(変更可能なサービス、未引用サービスパス)、AlwaysInstallElevated、スケジュールタスク、書き込み可能な自動起動ディレクトリ、DLL ハイジャック、未パッチのカーネル CVE。トークンの線が行き止まりなら、Windows 権限昇格の他の定番の線に進む。
**Q5**: Windows 権限昇格の全体像を漏れなく素早く把握するには?
**A5**: WinPEAS/PrivescCheck のような列挙スクリプトを実行してベースラインを作り、その後、高価値項目を人手で照合する。自動列挙で面を押さえ、人手の判読で点を定め、手作業で 1 項目ずつ調べて漏れが出るのを防ぐ。

### Windows 未引用サービスパス / 変更可能サービスの権限昇格
**Q1**: Windows サービス系の権限昇格を調べたい場合、先に何を見るか?
**A1**: 3 種類である:未引用サービスパス(Unquoted Service Path かつパスに空白を含む)、サービスのバイナリ/ディレクトリが書き込み可能、サービスの設定が変更可能(binPath を変更可能)。`sc qc <svc>` でパスとアカウントを見て、accesschk を併用して権限を見る。目標は「SYSTEM で動き、かつある環を私が制御できる」サービスを見つけることである。
**Q2**: unquoted path を 1 つ見つけ、中間ディレクトリを私が書き込める場合、どう使うか?
**A2**: 空白の切断点に同名の exe を置く(例 `C:\Program.exe`)。サービス起動時にまずそれが実行され、サービスアカウント(しばしば SYSTEM)で動く。前提は、その上位ディレクトリに書き込み権限があり、サービスの再起動をトリガーできることである。
**Q3**: サービスの binPath は変更できるが再起動できない場合はどうするか?
**A3**: サービスの起動種別を見る:Auto なら再起動を待つか、トリガーできる方法を探す。SERVICE_START 権限があれば直接 `sc start` を実行する。binPath を変更したのにトリガーできないなら、私が即トリガーできる項目(書き込み可能な自動起動、スケジュールタスク)に方向転換する。
**Q4**: accesschk でサービスが全て非常に固くロックされている場合、どこへ方向転換するか?
**A4**: DLL ハイジャックに方向転換する:SYSTEM プロセス/サービスがロードする DLL で、書き込み可能なディレクトリにあるか、検索順序で私が先取りできるものを探す。サービス設定自体はロックされていても、それがロードする DLL のパスはロックされていない可能性がある。
**Q5**: このマシンでサービス権限昇格を深掘りする価値があるかをどう判断するか?
**A5**: 先に自動列挙で「書き込み可能なパスを持つ SYSTEM サービス」と unquoted path を全て列挙する。1 つもなければ素早くトークン/カーネル/認証情報面に方向転換する。サービス権限昇格は設定の抜けに強く依存するので、抜けがなければ無理に探さない。

### Windows AlwaysInstallElevated / スケジュールタスクの権限昇格
**Q1**: AlwaysInstallElevated が使えるかをどう判断するか?
**A1**: 2 つのレジストリキー(HKCU と HKLM の `SOFTWARE\Policies\Microsoft\Windows\Installer\AlwaysInstallElevated`)が両方 1 のときだけ有効になる。該当すれば、悪意ある MSI を SYSTEM でインストールして実行でき、非常に手軽な権限昇格の 1 つである。
**Q2**: 2 つのキーが両方 1 の場合、どう実行するか?
**A2**: ペイロードを実行する MSI を生成し、`msiexec /quiet /i evil.msi` で SYSTEM として実行する。要点は MSI 内のアクションが昇格して実行されることである。生成時に AV を回避するため、検知されにくいペイロード方式を選ぶ。
**Q3**: 1 つのキーだけが 1(もう 1 つが 0 または存在しない)の場合、使えるか?
**A3**: 使えない。2 つが同時に 1 である必要がある。スケジュールタスクに方向転換する:`schtasks /query /fo LIST /v` で、高権限で動き、かつ実行するスクリプト/プログラムを私が書き込めるか、パスをハイジャックできるタスクを探す。これは別の独立した線である。
**Q4**: スケジュールタスクが全てロックされたシステムパスを指す場合、どこへ方向転換するか?
**A4**: 書き込み可能な自動起動位置(スタートアップフォルダ、Run キー)、および認証情報の収集に方向転換する:Windows で unattend.xml、Group Policy Preferences(cpassword)、レジストリ内の自動ログオンパスワード、DPAPI/認証情報マネージャーを調べる。権限昇格が阻まれたら「既存の高権限認証情報を探す」ことに方向転換する。
**Q5**: これらの設定系権限昇格が全て空の場合、最後の切り札は何か?
**A5**: カーネル exploit に方向転換する:`systeminfo` でパッチレベルを取得し、Watson/WES-NG で欠落パッチに対応するローカル権限昇格 CVE を照合する。設定面が全てクリーンな場合、未パッチのカーネル脆弱性が Windows 権限昇格の最終的な切り札である。

### コンテナエスケープ成功後のホスト足場の固定
**Q1**: コンテナからホストの root にエスケープした直後、最初にすべきは権限昇格の強化か横展開か?
**A1**: 先に足場を固定してから拡張する。そうしないと、コンテナが再起動/削除された瞬間に入り口を失う。ホスト(コンテナ内ではなく)に持続的なアクセスを構築する:隠蔽性のある永続化を 1 つ行い、それが消えやすいコンテナに依存しないことを確認する。
**Q2**: ホスト上で永続化する場合、隠蔽性があり安定した選び方は何か?
**A2**: 「正常な運用に紛れ込む」方式を優先する:既存サービスの設定、既存のスケジュールタスク/systemd、SSH 認可。コンテナファイルシステム内に何かを残すのは避ける(コンテナ破棄とともに消える)。ホストの永続ボリューム/ホストのルートに置く。
**Q3**: エスケープに「一時作成した特権コンテナ」を使った場合、終了後に明らかな痕跡を残さないか?
**A3**: 残す。特権コンテナ、異常な pod、docker API 呼び出しは全て記録される。固定後はこれらの一時産物をクリーンアップし(一時コンテナ/pod を削除)、永続化を目立たない担い手に移して、追跡される面を減らす。
**Q4**: ホストが k8s node の場合、固定は単体マシンと何が違うか?
**A4**: node 上のものはクラスタに管理される可能性がある(テイント、自動再作成、GitOps による上書き)。ファイルを直接変更しても元に戻される可能性がある。クラスタ層の永続化(高権限 SA、悪意ある admission webhook、DaemonSet)や、node 上でオーケストレーション管理外の経路に方向転換する。
**Q5**: 固定の動作が EDR アラートをトリガーした場合はどうするか?
**A5**: 即座に手を止めて評価し、最も低ノイズの存続手段(純粋な認証情報アクセス、既存の正当なチャネル)に方向転換し、高リスクの永続化技術を諦める。「盗んだ認証情報で目立たず出入りする」ことに退く方が、永続化のために足場全体を露出するよりましである。

### seccomp / AppArmor / SELinux 制限の識別と対応
**Q1**: エスケープ手法が他所では使えるのにここでは各種 EPERM になる。LSM/seccomp を疑うが、どう確認するか?
**A1**: `cat /proc/self/status | grep Seccomp`(2=filter 有効)、`cat /proc/self/attr/current`(AppArmor profile。unconfined 以外は制限あり)、`getenforce`(SELinux)を調べる。先にどの層が遮断しているか特定して初めて、どの層を迂回すべきか分かる。
**Q2**: seccomp が mount/init_module などを遮断していると確認した場合、どう迂回するか?
**A2**: seccomp は syscall のホワイト/ブラックリストである。迂回できないなら、遮断された syscall に依存しない経路に替える:docker.sock/SA token などのユーザーモードのコントロールプレーンエスケープを使い、遮断されたカーネル syscall には一切触れない。高層の能力で低層の syscall を置き換える。
**Q3**: AppArmor profile がファイルアクセスとマウントを制限している場合、どう対応するか?
**A3**: profile が具体的に何を禁じているかを見る(profile を読めればなお良い)。それは多くの場合、想定されたパスにしか適用されず、カバーされていない入口が存在する。それが管理していない capability、network に方向転換するか、新しい profile をロードできる口、または complain モードを直接探す。
**Q4**: 3 層(seccomp+AppArmor+SELinux)が全て有効で、エスケープ面が非常に固く締められている場合、無理に迂回する価値はあるか?
**A4**: 通常は価値がなく、コストが極めて高い。直交する方向に転換する:本機のエスケープを諦め、認証情報の横展開(token/鍵を読んでコントロールプレーンを攻める)、またはアプリケーション層の脆弱性を利用して、より高権限の隣接サービスに足場を築く。堅固なサンドボックスでは、カーネルを迂回するより戦場を替える方がよい。
**Q5**: ある制限が「設定の既定値」で、そのため抜けがある可能性があるかをどう判断するか?
**A5**: 既定の profile(docker 既定の seccomp/AppArmor)は公開されていて既知なので、何を許可しているか調べられる。カスタム profile だけが現場での試行を要する。先に既定と仮定して公開ホワイトリストと照合し、許可された危険な syscall/cap を探す方が、盲目的に試すより効率的である。

### ユーザー名前空間(userns)が権限昇格判断に与える影響
**Q1**: エスケープ前に先に user namespace を見る必要があるのはなぜか?
**A1**: userns が「コンテナの root が本当の root か」を決めるからである。`cat /proc/self/uid_map` を見る:`0 0 4294967295` なら同一 userns(コンテナ root=ホスト root で、エスケープしやすい)。高 uid にマップされている場合(例 `0 100000 65536`)、コンテナ root はホストではただの一般ユーザーであり、多くのエスケープが無効になる。
**Q2**: 再マッピングされた userns 内にいる場合、どのエスケープがまだ使えるか?
**A2**: マウントの露出(docker.sock、hostPath)やホスト側の脆弱性に依存する経路は依然として有効な可能性がある。それらは「コンテナ root=ホスト root」という前提に依存しないからである。逆に、cgroup release_agent などホストに対する真の CAP_SYS_ADMIN を必要とするものは無効になる。判定基準は「この経路がホストレベルの root を前提とするか」である。
**Q3**: 自分で新しい userns を作成して capability を得ることはできるか?
**A3**: 新しい userns 内では、その ns に対して全 cap を持つが、これらの cap はホストリソースには無効である。エスケープへの寄与は限定的で、主に cap がないとトリガーできないローカルカーネル脆弱性に使う(userns 内で CAP_SYS_ADMIN を得て、脆弱な syscall を攻める)。
**Q4**: userns によって通常のエスケープが全て無効になった場合、どのディメンションに方向転換するか?
**A4**: カーネル CVE(特に歴史上、大量の権限昇格 CVE は非特権 userns 経由でトリガーされてきた)、および認証情報/コントロールプレーン経路に方向転換する。userns が防ぐのは「身元型」エスケープであり、「メモリ破壊型」脆弱性は防げない。
**Q5**: 対象が userns の堅牢化を使っているかを一目で判断するには?
**A5**: uid_map が `0 0 ...` でなく、かつプロセスの CapEff が満値でもホストには無効であれば、堅牢化されている。これを見たら即座に「コンテナ内 root」への期待を下げ、主攻をマウントの露出とカーネル脆弱性に転換する。

### 権限昇格動作が EDR / 監査に遮断されたときの方向転換
**Q1**: 権限昇格の exploit が配置直後に削除/アラートされる場合、静的検知か挙動検知かをどう判断するか?
**A1**: 特徴を変えて試す:同じ exploit を別エンコード/パッキングにしても削除される=挙動検知(動作を見る)。特徴を変えたら配置できる=静的検知。定性が対策を決める。静的検知なら検知回避を施し、挙動検知なら「その挙動をトリガーしない」手法に替える。
**Q2**: 挙動検知(例:注入、トークン操作が EDR に監視される)の場合、どう迂回するか?
**A2**: 「正当な外見」の権限昇格に方向転換する:システム内蔵ツール/正常な管理動作で同じ効果を達成し(living-off-the-land)、高リスクな API 呼び出し/注入を避ける。または設定型の権限昇格(設定ファイルを変更してサービス再起動を借りる)に方向転換する。これはメモリ注入よりはるかに目立たない。
**Q3**: 試すたびにブルーチームにサンプルを渡しており、露出を懸念している場合、試し続けるべきか?
**A3**: 止める。権限昇格は高ノイズの動作であり、繰り返しの失敗は継続的なアラートとなり、封鎖や追跡をトリガーし得る。一歩退いて先に現在の権限を固定し、権限昇格が本当に必須かを評価する。多くの対象は現在の権限+横展開の認証情報で達成でき、本機の root を無理に取る必要はない。
**Q4**: 権限昇格が必須だが環境の監視が厳しい場合、単回の試行の露出をどう下げるか?
**A4**: 先にオフラインの同一バージョン環境で exploit を安定させ、検知回避を済ませ、対象上では成功する 1 回だけ撃つ。対象上で繰り返し試行錯誤するのは避ける。偵察を十分に行い一撃で命中させるのが、EDR に対抗する核心のリズムである。
**Q5**: EDR が強すぎて本機の権限昇格の経路を全体として諦める場合、どこへ方向転換するか?
**A5**: 横展開と認証情報に方向転換する:現在の権限で認証情報(メモリ、設定、チケット)を取得し、監視がより緩い隣接ホストやコントロールプレーンを攻め、別の場所から回り込む。権限昇格はこのマシン上で必ず完了させる必要はなく、戦場を替える方が EDR に正面からぶつかるより割に合うことが多い。

### PATH ハイジャックと相対パス注入
**Q1**: 高権限で動くプログラム/スクリプトが絶対パスなしのコマンドを呼んでいる場合、どう利用するか?
**A1**: これは PATH ハイジャックポイントである。私が制御でき、PATH の前方にあるディレクトリに同名の悪意あるプログラムを置くと、高権限プロセスが呼び出した際に先に私のものに当たる。判定基準は「高権限コンテキスト + 相対コマンド名 + 私がその PATH または作業ディレクトリに影響できる」である。
**Q2**: 対象プロセスの PATH 環境変数を変更できない場合はどうするか?
**A2**: 作業ディレクトリの相対パスに方向転換する:プログラムが `./cmd` を使うか、またはカレントディレクトリに依存し、かつ私が書き込める cwd で実行される場合(cron があるディレクトリに切り替えるケースで多い)、同名ファイルを置くだけでよい。PATH を変更できなくても、相対パス注入ができないわけではない。
**Q3**: こうした「相対コマンドを呼ぶ」高権限プログラムをどう発見するか?
**A3**: 疑わしい SUID/サービスバイナリに strings/ltrace を使い、system()/execvp() が何を呼ぶか見る。pspy で root プロセスが実際に実行するコマンドラインを観察する。パスなしのコマンド名を見たら候補である。
**Q4**: 見つけたが、そのディレクトリにちょうど書き込み権限がなく行き詰まった場合はどうするか?
**A4**: その呼び出し連鎖上の他の書き込み可能な環に方向転換する:設定ファイル、source されるスクリプト、依存するライブラリ。PATH ハイジャックは「制御可能な内容を注入する」一形態にすぎず、データの流れに沿って私が書き込める入力点をどれか 1 つ探す。
**Q5**: 連鎖全体がロックされ、PATH ディメンションが無駄になった場合、どこへ方向転換するか?
**A5**: 並行する権限昇格面に戻る:SUID GTFOBins、sudo、capability、cron、カーネル。PATH ハイジャックは特定のコーディングの抜けに依存するので、通らなければ素早く切り替え、単一点に時間をかけない。

### ファイル capability(getcap)による権限昇格
**Q1**: SUID が全てクリーンなのに、なぜ単独で getcap を実行する必要があるのか?
**A1**: 権限昇格ポイントが SUID ビットではなくファイル capability に隠れている可能性があるからである。`getcap -r / 2>/dev/null` で cap 付きのバイナリを探す。cap_setuid、cap_dac_override、cap_dac_read_search などがプログラムに付いていれば、通常の権限を迂回して権限昇格/任意読み取りを達成できる。
**Q2**: あるバイナリが cap_setuid+ep を持つ場合、どう使うか?
**A2**: このプログラム自体がコード/スクリプトを実行できる場合(例 cap 付きの python/perl/node)、直接それを使って uid を 0 に設定し shell を起動する。判定基準は「危険な cap を持つプログラムの挙動を制御できるか」である。cap 付きのインタープリタはほぼ root に等しい。
**Q3**: cap を持つのが機能単一で挙動を制御できないバイナリの場合はどうか?
**A3**: cap の種別に応じて使い方を替える:cap_dac_read_search→任意ファイル読み取り(shadow/鍵を読む)。cap_net_raw→スニッフィング。cap_dac_override→任意ファイルの変更。直接 shell を起動できなくても、権限昇格に必要な読み書きの原語を得られる。
**Q4**: getcap が全て空で、cap ファイルが全くない場合、どこへ方向転換するか?
**A4**: SUID/sudo/cron/カーネルに方向転換する。capability ファイルの権限昇格は並行する独立した 1 本の線であり、空なら主流の権限昇格面に戻り、唯一の希望にしない。
**Q5**: コンテナ内で getcap により見つかった cap はエスケープと関係があるか?
**A5**: ある。コンテナの場面ではプロセス/ファイルの cap がエスケープできるかに直結する(CAP_SYS_ADMIN の条項を参照)。コンテナ内では getcap と capsh --print を併用し、前者はファイルのディメンション、後者はプロセスのディメンションを見る。両方を調べる必要がある。

### データベース/サービスアカウントからシステム権限昇格へ(UDF、Redis など)
**Q1**: データベース/ミドルウェアの高権限アクセス(例 DB root、Redis 未認可)を得た場合、どうシステム shell に転換するか?
**A1**: 「このサービスはどのシステムアカウントで動き、ファイル書き込みや実行の能力があるか」と問う。MySQL は UDF 権限昇格か、INTO OUTFILE で webshell/cron を書ける。Redis 未認可はファイルを書ける(authorized_keys/cron/webshell を書く)。核心はサービスのファイル書き込み能力をシステム実行ポイントに接続することである。
**Q2**: MySQL で UDF を使う場合、前提条件は何か?
**A2**: FILE 権限が必要で、plugin ディレクトリに書き込め、かつサービスアカウントがそのディレクトリに書き込める必要がある。`SELECT @@plugin_dir`、`@@secure_file_priv` を 1 つずつ検証する。secure_file_priv が空でないと書き込みパスが制限される。これが最も一般的な障壁条件である。
**Q3**: secure_file_priv が書き込みパスを制限し、UDF も OUTFILE も阻まれる場合はどうするか?
**A3**: ファイル書き込みに依存しない経路に方向転換する:データベース内の認証情報/hash を直接 dump して横展開に使う、接続文字列内の他のアカウントパスワード、またはその DB アカウントの他所での再利用。サービス権限昇格が制限されたとき、サービス内の「データ」自体がより速い横展開の燃料になることが多い。
**Q4**: Redis 未認可だが root で動いておらず、書き込みディレクトリが制限されている場合はどうするか?
**A4**: どのユーザーで動いているかを見て、そのユーザーの書き込み可能ポイントに書き込む(そのユーザーの crontab、authorized_keys)。得られるのがサービスアカウントで root でなくても足場になるので、サービスアカウントから本機の権限昇格に進む。一歩で root に到達できないからといって諦めない。
**Q5**: サービスがコンテナ内にあり、ファイル書き込みがコンテナにしか影響しない場合はどうするか?
**A5**: エスケープ判断に方向転換する:先にコンテナ内で足場を築き(サービスアカウント→コンテナ root)、次にコンテナエスケープの 4 要素に進む。サービス権限昇格で得られるのは「コンテナ内の実行」であり、ホストに到達するにはエスケープの 1 歩を重ねる必要がある。2 歩を 1 歩と見なさない。

### 低権限 web shell を安定した対話 shell に昇格してから権限昇格する
**Q1**: 機能が制限された web shell しかない場合(コマンドの出力表示のみ、対話なし)、先に権限昇格か shell の昇格か?
**A1**: 先に昇格する。半端な shell では権限昇格の列挙すら困難である(tty がない、sudo がパスワードを要求する、対話型 exploit が動かない)。先に安定したリバース shell を張り、全 tty に昇格してから(python pty / script / stty)、権限昇格を論じる。道具を整えてから取りかかる。
**Q2**: リバースが毎回失敗し、外部通信が制限されていると疑う場合、どう判断するか?
**A2**: 外向きを 1 つずつ試す:異なるポートの TCP、DNS、ICMP、HTTP プロキシ。どの方向が外へ出られるかを見る。判定基準は「どの外向きチャネルがファイアウォール ACL に遮断されていないか」である。全て不通なら外部通信しない足場方式に方向転換する。
**Q3**: 対象が完全に外部通信できない場合(全方向遮断)、shell の昇格はどう行うか?
**A3**: 正方向/トンネルに方向転換する:対象にポートをリッスンさせて私が接続する(インバウンドが到達できれば)、または既存の web チャネルで HTTP トンネルを作る(対話を HTTP リクエストに封入する)。外部通信が遮断されたら、データチャネルを既に許可されているプロトコルに多重化する。
**Q4**: 全 tty を得た後、権限昇格の列挙順序をどう並べるのが最も効率的か?
**A4**: 先に自動列挙(linpeas/winpeas)を実行して全景を得る。同時に手作業で「低コスト・高収益」の項目を優先して調べる:sudo -l、SUID、書き込み可能な機微ファイル、認証情報ファイル、カーネルバージョン。自動で面を敷き、人手で先端を選び、1 項目ずつの手作業に時間をかけない。
**Q5**: web shell の所在アカウントの権限が低すぎて、列挙すら制限される場合(制限付き shell rbash)はどうするか?
**A5**: 先に制限付き shell を破る:許可されたコマンドの中でエスケープできるもの(vi/awk/shell を指定できるプログラム)を探すか、`bash --noprofile`、SSH の ForceCommand 迂回を使う。rbash の突破は権限昇格の前置ステップであり、制限された環境ではこの一歩が列挙より優先される。

### クラウド関数 / Serverless / CI 環境の権限昇格と横展開
**Q1**: 侵入したのが Serverless/関数コンピューティングまたは CI runner 環境の場合、権限昇格の考え方は通常のホストと何が違うか?
**A1**: この種の環境には「従来のホスト root」の概念がなく、権限昇格の対象は「それがバインドされたクラウド身元/鍵を得る」ことである。最初に環境変数、metadata、注入された認証情報ファイルを読む。関数/パイプラインの実行ロールは権限が小さくないことが多く、それこそが権限昇格の対象である。
**Q2**: CI runner 内で得られる高価値の認証情報には何があるか?
**A2**: パイプラインが注入するデプロイ鍵、クラウド認証情報、アーティファクトリポジトリ/イメージリポジトリの token、コードリポジトリの書き込み権限。CI のデプロイ身元を得ることは、しばしば本番アーティファクト(サプライチェーン)を変更できることに等しい。env とマウントされた secret を優先して列挙する。
**Q3**: CI のリポジトリ書き込み/パイプライン変更の権限を得た場合、どう戦果を拡大するか?
**A3**: パイプラインに悪意あるステップを注入し、そのより高いデプロイ権限を借りて本番環境で実行する。これは「CI 身元を使って本番まで権限昇格する」定番の連鎖である。要点は、パイプライン自体がより高い信頼ドメインで動くことである。認可境界を慎重に評価してから動く。
**Q4**: 関数環境は短いライフサイクルで、足場がすぐに消える場合はどうするか?
**A4**: 関数インスタンス内に駐留するのは期待しない。「今回の実行で得た持続的な認証情報/身元」を使って他所に足場を築くことに重心を置く。消えやすい環境の価値はその身元であり、それ自体ではない。認証情報を採取したら即座に移転する。
**Q5**: 環境変数と metadata が全てクリーンアップ/隔離された場合、どこへ方向転換するか?
**A5**: それがアクセスできる下流サービスに方向転換する:関数はしばしばあるデータベース/キュー/ストレージにアクセスする権限を持つ。そのネットワーク到達性と設定済みの接続文字列に沿って横展開する。実行環境が身元を隔離していても、業務の接続には使える認証情報が残っていることが多い。

### 権限昇格前の戦場評価:いつ縦方向を止めて横展開に転換すべきか
**Q1**: 1 台のマシンで権限昇格が長く行き詰まっている場合、続けて固執すべきかをどう判断するか?
**A1**: タイムボックスを設けて 3 つの問いをする:権限昇格は現在の対象に必須か。現在の権限でタスク(データ取得/横展開)を既に満たせるか。このマシンは対象へ至る唯一の経路か。「非必須/既に十分/バイパスがある」なら手を止めて横展開に転換し、root のための root を目指さない。
**Q2**: 現在の権限が実は既に十分だとどう判断するか?
**A2**: タスクの目標に合わせる:目標が特定のデータ、特定の認証情報、または踏み台であり、現在の権限で既に読める/接続できるなら、root はあれば嬉しいだけである。レッドチームは「目標を達成したか」を見るのであり、「最高権限を得たか」ではない。
**Q3**: 横展開に転換すると決めた場合、現在の低権限から何を採取して横展開に使うか?
**A3**: root が不要なものを採取する:現在のユーザーの history、ssh key、`~/.aws`/`~/.kube`、ブラウザ/設定内のパスワード、内部ネットワークから到達できるサービス、ARP/接続テーブルが露出する隣接ノード。これらは次の 1 台への横展開に十分なことが多く、本機の権限昇格を迂回できる。
**Q4**: 横展開も当面開けない場合、戻って権限昇格を続けるべきか?
**A4**: 先に偵察を補ってから決める。盲目的に振り戻さない。見落としていた面(他のユーザーディレクトリ、スケジュールタスク、内部ネットワークで新たに見つかったサービス)を再列挙する。縦も横も行き詰まったとき、問題は「手法不足」ではなく「情報不足」にあることが多いので、情報補充を優先する。
**Q5**: 権限昇格が本当に優先必須になるのはどのような場合か?
**A5**: 対象データ/動作が明確に root を必要とする場合(shadow の読み取り/メモリ dump、永続化の導入、他ユーザーのチケット取得)、または権限昇格が横展開を開く鍵になる場合(本機のドメインアカウント hash を取ってドメインを攻める)。このとき権限昇格は経路依存であり、投入する価値がある。それ以外は選択肢にすぎない。

### hostPID / hostNetwork / hostIPC 共有名前空間の利用
**Q1**: k8s pod 内で `ps aux` によりホストの全プロセスが見える場合、これは何を意味するか?
**A1**: pod が hostPID(ホスト PID 名前空間の共有)を有効にしていることを示す。これ自体がエスケープ面である:ホストプロセスが見えれば、その `/proc/<pid>/environ`(認証情報を盗む)、`/proc/<pid>/root`(他のコンテナ/ホストのファイルにアクセス)を読める。適切な cap と組み合わせれば、nsenter でホストの名前空間に入ることもできる。
**Q2**: hostPID があり、かつ現在が特権/CAP_SYS_ADMIN を持つ場合、どう直接ホストに入るか?
**A2**: `nsenter --target 1 --mount --uts --ipc --net --pid -- /bin/bash` を実行し、PID 1(ホストの init)の全名前空間に入れば、ホストの root shell になる。hostPID でホストプロセスを特定でき、nsenter が切り込みを完了する。前提は名前空間に入るのに必要な cap を持つことである。
**Q3**: hostPID しかなく、nsenter に必要な cap がない場合、まだ何を絞り出せるか?
**A3**: 「読む」価値に方向転換する:`/proc/*/environ` と `/proc/*/cmdline` を走査してホストプロセス内のパスワード/token/接続文字列を盗み、`/proc/*/root/` を走査して他のコンテナのファイルを探る。入れなくても、共有 PID 名前空間の情報漏えいは認証情報を得て横展開するのに十分である。
**Q4**: hostNetwork(ホストネットワークの共有)の場合は、どう使うか?
**A4**: ホストのネットワーク面に直接立つことになる:ホストの localhost 上で 127.0.0.1 だけをリッスンするサービス(kubelet、etcd、クラウド metadata、ローカルの無認証管理ポート)にアクセスでき、ホストのポートをスニッフィング/バインドすることもできる。「自分はローカルにしか公開していない」と思っているサービスを攻める方向に転換する。
**Q5**: これらの共有名前空間が 1 つも有効でなく、エスケープが行き詰まった場合、どこへ方向転換するか?
**A5**: エスケープの 4 要素の残りに戻る:マウント(hostPath/socket)、capabilities、カーネル CVE。共有名前空間はエスケープ面の 1 つにすぎず、有効でなければ他の 3 面を調べ、この 1 本にとどまらない。

### polkit / pkexec / D-Bus のローカル権限昇格(PwnKit 系)
**Q1**: Linux の通常の権限昇格面が全てクリーンな場合、「システム内蔵の高権限コンポーネント」で調べる価値があるものには何があるか?
**A1**: ローカルの IPC/権限代理コンポーネントを調べる:pkexec(polkit)、D-Bus サービス、および setuid のシステム管理ツール。これらは root で動き、ローカルの低権限呼び出しを受け付ける。歴史上、複数の全滅級ローカル権限昇格を生んでいる(例 pkexec の PwnKit CVE-2021-4034)。存在するだけでバージョン照合の価値がある。
**Q2**: システムに pkexec があり、かつ SUID の場合、PwnKit が使えるかをどう判断するか?
**A2**: PwnKit はロジック/メモリ破壊の脆弱性で、ほぼディストリビューションを選ばない。判定基準は主に polkit のバージョンにパッチが当たっているかである。先に pkexec が SUID か確認し(`ls -l $(which pkexec)`)、次にパッケージバージョンが影響範囲に入ることを確認する。成熟した PoC は安定し、クラッシュリスクも低く、非常に割に合う 1 枚である。
**Q3**: pkexec が削除済みまたはパッチ適用済みの場合、polkit の線には他に何かあるか?
**A3**: polkit の認可ロジックの脆弱性(例 CVE-2021-3560 の D-Bus 競合。素早く切断して root によるユーザー作成をトリガーする)、または低権限で高権限の動作をトリガーできる他の D-Bus サービスの列挙に方向転換する。同じ polkit/D-Bus エコシステム内の入口は pkexec だけではない。
**Q4**: この種の exploit が制限付き/コンテナ環境で効かないことがあるのはなぜか?
**A4**: それらが polkit/D-Bus デーモンの稼働と、現在の名前空間内に root で存在することに依存するからである。コンテナ内にはこれらのサービスがインストールされていないか、動いていないことが多い。先にサービスが動いているか確認し(`ps` で polkitd/dbus-daemon を探す)、動いていなければ直接除外して exploit を無駄にしない。
**Q5**: polkit/pkexec が全て通用しない場合、どの切り札に方向転換するか?
**A5**: カーネル exploit の切り札(uname とローカル権限昇格 CVE の照合)と認証情報の横展開に戻る。システムコンポーネントの権限昇格は「設定/バージョンの抜け」型であり、カーネルのメモリ破壊型、認証情報型とは 3 本の直交する線である。1 本が塞がったら次の 1 本に切り替える。
