# 権限昇格と足場 · 足場を確保した後の最初の内部ネットワーク情報収集

### shell を得たら慌てて権限昇格しない:これがどんな身元・どんな環境か判定する
**Q1**: 侵入して shell を得たばかりで、指がむずむずして直接 sudo -l や権限昇格スクリプトを走らせたくなる。最初の一歩は何か?
**A1**: 先に「三問の自己点検」を行う。一問目は私は誰か(id/whoami、uid、gid、所属グループ)。二問目はこれは何か(コンテナ/仮想マシン/物理マシン/WSL。判定基準:/.dockerenv、/proc/1/cgroup 内の docker/kubepods、hostname がランダム hash か)。三問目は shell が安定しているか(半対話か、落ちるか、タイムアウト kill があるか)。順序を誤ると機会を浪費する。5 秒で回収される webshell で対話型の権限昇格を走らせれば必ず途中で挫折する。
**Q2**: コンテナか実機かをどう素早く判断するか?
**A2**: 判定基準を組み合わせる:ルートに /.dockerenv か /run/.containerenv がある。/proc/1/cgroup に docker/lxc/kubepods が現れる。PID 1 が systemd/init ではなくアプリケーションである。ネットワークカードが eth0+lo だけで 172.17/10.x である。mount に overlay が大量にある。2 項目以上該当すればほぼコンテナと判断できる。
**Q3**: コンテナの場合、情報収集の重心は実機と何が違うか?
**A3**: 重心は「本機の権限昇格」から「エスケープ面」に転換する:ホストディレクトリ(/host、/mnt)がマウントされているか、privileged か(マウントできるか、cap が揃っているか)、docker.sock が見えるか、K8s serviceaccount token があるか。コンテナ内のローカル権限昇格は、特定の cap を奪う場合を除いて、ほとんど意味がない。
**Q4**: 環境が極小コンテナで、id も mount もどのツールもない場合、この経路が遮断されたらどうするか?
**A4**: 「リソースを持ち込む」ディメンションに方向転換する:先に武器の配送を解決し、自前の静的 busybox/nsenter で観測能力を回復する。観測できないことは面がないことと同義ではなく、ツール不足である。先にツールを補ってから判定する。
**Q5**: shell が不安定で収集のたびに切れる場合、どう止血するか?
**A5**: 不安定な shell を安定したチャネルに昇格することを優先する:全 TTY(python pty/script/socat)にするか、より信頼できる C2 beacon を落とす。「チャネルの安定性」を第一ラウンドの前置インフラとして扱い、収集しながら落ち続けるのを我慢しない。

### 権限のディメンションを先に定性する:一般ユーザー / サービスアカウント / 既に root か SYSTEM
**Q1**: id の結果が普通の低権限ユーザーだった。精力をどこに置くか?
**A1**: 目標は「本機の縦方向の権限昇格で root/SYSTEM に到達する」ことであり、権限昇格ベクトルの収集を中心にする:sudo -l、SUID/SGID、書き込み可能な高権限プロセスの設定、カーネルバージョンの既知ローカル権限昇格への露出面、root で実行され現在のユーザーが書き込めるスケジュールタスク。低権限段階で早まって横展開に広げず、先に足を固める。
**Q2**: 着地時点で既に root/SYSTEM なら、権限昇格を飛ばすか?
**A2**: 飛ばす。直接「換金と横展開」に進む:認証情報を取得し(Linux:shadow/ssh key/history/設定の平文。Windows:lsass/SAM/DPAPI/ブラウザ)、永続化を構築し、横展開を始める。最高権限でなお権限昇格にこだわるのはウィンドウの無駄である。
**Q3**: 身元がサービスアカウント(www-data、mysql、あるアプリ専用)の場合、特殊な考え方は何か?
**A3**: サービスアカウントはしばしばある種のリソースに過剰な権限を持つ:DB アカウントは全庫を読める/ファイルを書ける/UDF 権限昇格できるかもしれない。web アカウントは設定内の DB パスワードと API key を読める。バックアップアカウントはディスク全体を読める。判定基準は「このアカウントが誰に仕えるか」であり、職責に沿って与えられた過剰な権限を探す。
**Q4**: Windows サービスアカウントに SeImpersonate/SeAssignPrimaryToken 特権があるのを見つけたらどうするか?
**A4**: 明確なシグナルであり、Potato ファミリー(トークン窃取系のローカル権限昇格)に方向転換して直接 SYSTEM に上げる。そのため whoami /priv は Windows の第一ラウンドで必ず収集し、特権リストがユーザー名より路線を決める。
**Q5**: アカウントが root でもなく、明らかな権限昇格面もなく、sudo -l がパスワードを要求し、使える SUID もなく、死路に見える場合、どこへ方向転換するか?
**A5**: 「横展開でより良い身元に替える」ことに方向転換する:このマシンで縦方向に固執するより、現在の身元で触れられる他のホスト/サービスを偵察し、認証情報を得て、権限昇格面がより大きい別のマシンに足を移す。権限昇格が行き詰まったとき、横展開がしばしば解毒剤になる。

### 地形の把握:ネットワーク位置、ネットワークカード、ルート、このマシンが二枚差しの踏み台か
**Q1**: 足を固めた後、「ネットワークのどの位置にいるか」をどう素早く把握するか?
**A1**: ip a/ipconfig /all、ルートテーブル、ARP キャッシュ、DNS 設定を収集する。核心の判定基準はネットワークカード数とネットワークセグメントである:単一ネットワークカードは普通のノード。複数ネットワークカードで異なるセグメントに属するなら、ネットワーク間境界の踏み台であり、価値が非常に高く、重点保護して利用する。
**Q2**: 2 枚目のネットワークカードが外から届かない内部セグメントを指すのを見つけたら、次に何をするか?
**A2**: 即座にこのマシンを pivot(socks/ポートフォワーディング/VPN over C2)にする計画を立て、後続のツールが隠れたセグメントを貫通できるようにする。第一ラウンドで「新しいセグメントの発見」は本機の掘り進めより優先度が高く、それが戦役全体の縦深を決める。
**Q3**: ARP テーブルとルートテーブルは他に何を教えてくれるか?
**A3**: ARP ネイバーは同一セグメントのアクティブホストを露出する(全網スキャンより隠蔽的)。ルート項目はこのマシンがどう行くか知っているセグメントを露出する(現在通らなくても)ので、横展開の候補リストになる。DNS サーバーのアドレスはしばしばドメインコントローラーか核心 DNS で、高価値の位置特定の手掛かりである。
**Q4**: 内部ネットワークの生存ホストをスキャンしたい。直接 nmap で全セグメント大掃除してもよいか?
**A4**: 慎重に。大範囲の高速スキャンは最も響き、IDS/NDR をトリガーして足場を露出させやすい。先に低ノイズ手段を使う:ARP ネイバー、netstat の既存接続、hosts、known_hosts、履歴コマンドに現れた IP。本当に能動スキャンが必要なときは、狭い範囲、低レート、重要なポートだけを探る。
**Q5**: 能動スキャンがアラートをトリガーし、ブルーチームが連動し、接続が保てなくなりそうな場合、どう転換するか?
**A5**: 「ノイズ低減+情報源の交代」に方向転換する:能動スキャンを止め、純粋な受動情報(本機のログ、設定、キャッシュ、トークン)に切り替え、既に取得した認証情報で「認証式の横展開」(チケットを持って直結し、正常なアクセスのように見せる)を行い、ポートスキャンで対象を発見するのはやめる。ノイズの経路が遮断されたら認証情報の経路を使う。

### カーネル / パッチの定性:既製のローカル権限昇格を使えるか
**Q1**: Linux の低権限ユーザーで、カーネル権限昇格の見込みがあるか知りたい。どこから判断するか?
**A1**: 先に uname -a、/etc/os-release、アーキテクチャを取る。既知のローカル権限昇格(汚れた牛系、pkexec/polkit 系、overlayfs、nftables、カーネル UAF など)の影響範囲と照合する。判定基準は「バージョンが脆弱性ウィンドウに入る+関連コンポーネントが存在する」ことである。盲目的に exp を走らせず、先にバージョンを一致させてカーネル破壊のリスクを減らす。
**Q2**: パッチを当てたか、緩和策を開いたかをどう知るか?
**A2**: Linux はカーネル堅牢化、pkexec/polkit が削除されたか、関連 sysctl(例 unprivileged_userns_clone)が無効かを確認する。Windows は systeminfo のパッチリストを既知 KB と差集合で見る。緩和策が開いていれば既製 exp は失敗する可能性が高いので、ベクトルを替える必要がある。
**Q3**: 使えそうなカーネル exp を見つけた場合、対象でその場でコンパイルして走らせるべきか?
**A3**: できるだけその場でコンパイルしない。対象にコンパイラがないかもしれず、コンパイルしてカーネル破壊で再起動すると足場を失い、痕跡も多い。ローカルで同バージョンの静的バイナリをコンパイルしてから投げるのを優先する。やむを得ずその場でやるなら、対象が本番の核心マシンか(崩れると騒ぎが大きい)を先に評価する。カーネル exp は最後の手段であり、第一選択ではない。
**Q4**: カーネルバージョンが新しすぎる/全パッチ済み/緩和策全開で、カーネル権限昇格が全く見込みがない場合、どこへ方向転換するか?
**A4**: 「設定ミス型の権限昇格」という直交ディメンションに方向転換する:カーネルの経路が封じられたとき、実際の権限昇格の 90% は設定面から来る。sudo ルール、SUID バイナリの GTFOBins 用法、書き込み可能な service/cron、弱いファイル権限、パスワード再利用。exp を捨てて「人が何を設定ミスしたか」を進める。
**Q5**: 設定面もきれいで、堅牢化が行き届いたマシンの場合、さらにどうするか?
**A5**: 「認証情報再利用+横展開」に方向転換する:堅牢化された単機は本機の権限昇格で落とされず、他所で漏れたパスワード/鍵/チケットで横から貫かれることが多い。このマシンを情報源と踏み台として扱い、必ずしもそれ自体で権限昇格しない。

### SUID/SGID/Capabilities 面の列挙と利用判読
**Q1**: Linux のローカル権限昇格面を体系的に探したい。SUID をどう収集し判読するか?
**A1**: find / -perm -4000 -type f 2>/dev/null で SUID を列挙し、-2000 で SGID を列挙する。リストを得たら先にシステム標準品(passwd、sudo など)を除き、非標準/カスタム/バージョン付きのバイナリを重点的に見る。判定基準:GTFOBins のそのプログラムの SUID 用法でファイルを読み書きできるか、shell を起動できるか。
**Q2**: リストが全て標準のシステムバイナリで、カスタムがない場合、手詰まりか?
**A2**: そうとは限らない。標準品も旧バージョンなら利用できることがある(例 ある pkexec/fusermount/その他)。1 つずつバージョンを照合する。さらに capabilities を忘れない:getcap -r / 2>/dev/null で cap_setuid、cap_dac_override などの能力を持つプログラムを探す。これらは見落とされやすい。
**Q3**: カスタム SUID プログラムを 1 つ見つけたが内部動作が分からない。どう分析するか?
**A3**: strings/ltrace/strace で何を呼ぶか見る:相対パスで外部コマンドを呼ぶか(PATH ハイジャック)、system()/popen で連結するか、現在のユーザーが書き込める設定を読むか。判定基準は「それが私の制御できる入力を何か信頼しているか」である。
**Q4**: PATH ハイジャックの考え方は、どんな条件で成立するか?
**A4**: その SUID が相対パス(非絶対パス)で外部コマンドを呼び、かつ PATH をリセットしていないこと。成立すれば書き込み可能なディレクトリに同名の悪意あるプログラムを置き、PATH を前置する。絶対パスを使うか PATH を消しているなら成立しないので、時間を浪費しない。
**Q5**: SUID/cap が全て利用できず、この本地面が遮断されたら、どこへ方向転換するか?
**A5**: 「プロセスとスケジュールタスク面」に方向転換する:ps aux で root プロセスが周期的に書き込み可能なスクリプトを実行していないか、root で動くサービスが書き込み可能な設定を読んでいないかを見る。SUID の静的面の外に、動的実行面がもう一つの大きな権限昇格源である。

### sudo -l の深掘り:パスワード不要かだけでなく
**Q1**: sudo -l が走る(パスワード不要かパスワード既知)。この出力をどう読むか?
**A1**: 許可されたコマンドを 1 つずつ見る:NOPASSWD か、ワイルドカードを持つか、root で GTFOBins エスケープ可能なプログラム(vi/less/awk/find/tar/systemctl など)を実行できるか。判定基準は「この sudo ルールを任意コマンド実行に撬られるか」である。
**Q2**: 無害に見えるカスタムスクリプトの sudo 実行を許可されている場合、どうするか?
**A2**: スクリプト内容を読む:外部コマンドを呼ぶか(PATH/引数注入できる)、私が制御できるファイルを処理するか、root が私の読めるディレクトリに書くか。無害なスクリプトも内部実装で撬られることが多い。スクリプト内容が読めないときは挙動を見る(strace)。
**Q3**: sudo バージョン自体に利用できる点はあるか?
**A3**: sudo --version を記録し、既知の sudo 脆弱性ウィンドウ(例 ある sudoedit/引数解析系)と照合する。sudo -l が何も与えなくても、ある種の脆弱性は迂回できる。バージョンが一致したら対応するベクトルを試す。
**Q4**: ルールに LD_PRELOAD/LD_LIBRARY_PATH 関連の env_keep がある場合、どう読むか?
**A4**: 大きなシグナルである:sudo が LD_PRELOAD を保持し、かつあるプログラムの実行を許可するなら、悪意ある .so で権限昇格できる。Defaults の env_keep リストと secure_path が緩いかを確認する。これは設定ミス型権限昇格の定番ポイントである。
**Q5**: sudo -l がパスワードを要求し私が持たない、または明示的に not allowed の場合、この線が死んだらどこへ方向転換するか?
**A5**: 「このユーザーのパスワードを取る」または「sudo を迂回する」ことに方向転換する:history/設定/ブラウザ/鍵を探してそのユーザーのパスワードを探す(再利用が多い)、または sudo を完全に諦めて SUID/cron/カーネル面に進む。sudo は権限昇格の脚の 1 本であり、唯一ではない。

### スケジュールタスク / cron / サービス:動的実行面の権限昇格
**Q1**: 周期的に高権限で実行され、私が干渉できるものを探したい。どこから見るか?
**A1**: Linux:/etc/crontab、/etc/cron.*、各ユーザーの crontab、systemd timer。Windows:schtasks /query /fo LIST /v、スケジュールタスク内の SYSTEM/管理者で動くタスク。判定基準は「高権限の周期的実行 + 実行対象またはそのパスを私が書き込める」ことである。
**Q2**: root cron があるスクリプトを呼び、私は書き込み権限がないが、スクリプトのディレクトリは書き込める。見込みはあるか?
**A2**: ある。スクリプトが相対パスでコマンドを呼ぶか、cron の PATH に書き込み可能なディレクトリが含まれるか、スクリプトがワイルドカード tar を使うか、書き込み可能な include をロードするか。スクリプト自体の権限だけを見ず、その依存連鎖の各環の権限を見る。
**Q3**: 明らかな cron はないが、隠れたスケジュールタスクを疑う場合、どう発見するか?
**A3**: プロセス監視法を使う:pspy 系ツールは root なしでも周期的な新プロセスを見られ、見えない cron/timer とその完全なコマンドラインを露出する。設定ファイルを探しても見つからないタスクを発見できる。
**Q4**: Windows 上でハイジャックできるサービスを探す場合、何を見るか?
**A4**: サービスのバイナリパスが書き込み可能か(置換できる)、unquoted service path か(空白を含みパスセグメントが書き込み可能)、サービスのレジストリ ImagePath/DACL が弱いか、SYSTEM で動くか。これらは Windows ローカル権限昇格の高頻度ポイントである。
**Q5**: 全てのスケジュールタスク/サービスの権限が固く、動的面が遮断されたら、どこへ方向転換するか?
**A5**: 「認証情報面」に方向転換する:動的実行面が封じられたら、このマシンにキャッシュされた認証情報(メモリ、設定、チケット)を取得し、他人の高権限身元で本機の権限昇格を代替する。実行面と認証情報面は 2 つの直交する権限昇格の経路である。

### Linux 認証情報の収集:設定、履歴、鍵の中の平文と再利用
**Q1**: 一般/サービスアカウントを得て、素早く認証情報を掬いたい。先にどこを探るか?
**A1**: 優先順位:~/.bash_history と各種 history、~/.ssh(秘密鍵/known_hosts/config)、アプリ設定(DB 接続文字列、.env、web 設定、CI 設定)、/var/www 配下のソースコード内のハードコードされたパスワード、バックアップファイル(.bak/.old/.swp)。判定基準は「誰かがパスワードを書き固めている可能性が最も高い場所はどこか」である。
**Q2**: history で誰かが平文パスワードで何かにログインした形跡を見たら、どう使うか?
**A2**: 記録して「パスワードスプレー/再利用」を行う:内部ネットワークのパスワード再利用率は非常に高く、1 つの DB パスワードが、あるユーザーの SSH パスワードやドメインアカウントのパスワードと等しいことがよくある。掬った各パスワードを横展開と権限昇格の鍵として扱い、複数の対象で試す。
**Q3**: SSH 秘密鍵を見つけたら、価値をどう最大化するか?
**A3**: known_hosts と config を見て、その鍵がどのホストを開くか知る(known_hosts が未ハッシュなら直接ホスト名/IP が得られ、横展開の地図になる)。秘密鍵がパスワードなしなら直接使い、パスワードありなら passphrase のオフライン爆破を試す。秘密鍵+known_hosts はしばしば連鎖的な横展開ができる。
**Q4**: 設定ファイルが全て規範的で平文パスワードがなく、認証情報収集が空振りしたら、どこへ方向転換するか?
**A4**: 「メモリと実行時状態」に方向転換する:設定になくても、メモリにはある。データベース/アプリプロセスのメモリ、環境変数(/proc/PID/environ)、プロセスのコマンドライン(ps の -p password)は実行時認証情報を漏らすことが多い。静的に探しても見つからなければ動的を探る。
**Q5**: 認証情報面をさらに広げたい。システム級の場所はあるか?
**A5**: 集中認証の漏えいがあるかを見る:/etc/shadow(読み取り権限があればオフライン爆破)、Kerberos keytab、クラウド認証情報(~/.aws、~/.config/gcloud)、コンテナ/オーケストレーションの secret マウント、git リポジトリ履歴内の鍵。認証情報収集は「個人、アプリ、システム、クラウド」の 4 層をカバーする。

### Windows 認証情報の取得:lsass / SAM / DPAPI / ブラウザ
**Q1**: Windows 上で管理者/SYSTEM を得た。認証情報をどこから、どの順序で取るか?
**A1**: 先に lsass(メモリ内の平文/hash/チケット。mimikatz/comsvcs dump/nanodump)、次に SAM+SYSTEM レジストリ(ローカルアカウント hash)、次に DPAPI(保存された認証情報、ブラウザパスワード)、次に LSA secrets(サービスアカウントパスワード)。判定基準は「メモリ内のアクティブな認証情報からディスク上の認証情報へ層ごとにスキャンする」ことである。
**Q2**: 直接 lsass に触れて EDR に遮られた場合はどうするか?
**A2**: 取得方式を替える:定番 mimikatz の特徴を使わず、システム内蔵の comsvcs.dll MiniDump を使うか、PPL 迂回を使うか、メモリ dump をローカルに持ち帰ってオフライン解析し、対象上で機微操作を走らせる特徴面を減らす。lsass 取得が遮られたのは「手法」が遮られたのであり、「目標」がなくなったのではない。
**Q3**: lsass が全く動かせない(PPL+EDR+RunAsPPL)場合、どこへ方向転換して取るか?
**A3**: オフライン/ディスク上の認証情報に方向転換する:SAM/SYSTEM/SECURITY レジストリ hive(reg save 後にオフライン解析)、DPAPI masterkey+ブラウザ認証情報ライブラリ、スケジュールタスク/サービスに保存された認証情報、GPP cpassword、各種設定ファイルの平文。lsass は多くの認証情報源の 1 つにすぎない。
**Q4**: 取れたのが NTLM hash で平文でない場合、何ができるか?
**A4**: 直接 Pass-the-Hash で横展開するか、オフライン爆破で平文を復元する(平文はより多くのプロトコルにスプレーできる)。平文でないからと捨てない。hash は NTLM 認証ではパスワードと等価である。
**Q5**: Kerberos TGT/TGS チケットを取れたら、どう使うか?
**A5**: Pass-the-Ticket:チケットをインポートしてそのユーザーとして直接サービスにアクセスし、パスワードを迂回する。TGT は任意のサービスチケットを要求でき、単一の TGS より価値が高い。チケットには時効があるので、取ったら早く使う。

### ドメイン参加かの判定:単機戦 vs ドメインペネトレーション、全く異なる 2 つの戦い方
**Q1**: Windows を 1 台落としたら、それがドメイン内かどうかをどう最初に判断するか?
**A1**: systeminfo の Domain フィールド、whoami /fqdn、nltest /dsgetdc、環境変数 USERDNSDOMAIN、ドメイン SRV レコードの解決可否を見る。判定基準:ドメインあり=AD ペネトレーションの戦い方に入る。ワークグループ=単機+ローカル認証情報の横展開の戦い方。この分岐が後続の戦術全体を決める。
**Q2**: ドメイン内と確認したら、第一ラウンドでどのドメイン情報を収集するか?
**A2**: ドメイン名/ドメインコントローラーアドレス、現在のユーザーのドメイン内グループ、ドメイン内のユーザー/コンピュータ/グループリスト、SPN、信頼関係、GPO。ツールは先に低ノイズのネイティブコマンド(net、nltest、setspn、PowerShell AD モジュール)、次に BloodHound コレクターを検討する。
**Q3**: ドメイン内だが現在がローカルアカウント(ドメインアカウントでない)場合、ドメイン偵察はできるか?
**A3**: できる。ドメインコントローラーへネットワーク到達でき、任意の有効なドメイン認証情報が 1 つあればよい。手元にローカルアカウントしかないなら、先にドメインアカウントを 1 つ得る(キャッシュされたドメイン認証情報、ドメインユーザーがログインしたチケットを取る)。ドメイン身元がないとドメイン列挙は制限されるので、先に「ドメインチケットがあるか」を解決する。
**Q4**: ワークグループ/非ドメインマシンと判定したら、考え方をどう変えるか?
**A4**: 単機+ローカル認証情報の再利用に転換する:AD という大網がないので、横展開はローカル管理者 hash の再利用、SMB/RDP パスワードスプレー、共有列挙による。ドメインコントローラーと Kerberos を探しに行かない。それらはワークグループには存在しない。
**Q5**: ドメイン列挙が動くとすぐアラートをトリガーする(ブルーチームが LDAP の異常照会を監視)場合、遮断されたらどう転換するか?
**A5**: 「低ノイズ + 定点」のドメイン偵察に転換する:BloodHound の全量取得を諦め、必要なそのユーザー/その ACL だけを正確に単点照会するか、既存の正常な管理トラフィックに紛れるか、既に取得したチケットに基づく認証式横展開を行い、大範囲列挙をしない。全量列挙が遮断されたら定点情報に進む。

### ドメイン内攻撃面の整理:BloodHound 視点で最短権限昇格経路を探す
**Q1**: ドメイン列挙データが手元に来た。大量のオブジェクトから「ドメイン管理者への最短経路」をどう見つけるか?
**A1**: BloodHound 系のグラフ解析を使う:現在の身元を起点に、高価値目標(ドメイン管理者、DC)への ACL/グループメンバーシップ/セッション経路を探す。判定基準は「どの辺を私が実際に制御できるか」(例 あるオブジェクトに GenericWrite がある、高権限ユーザーが私の取れるマシンにセッションがある)。
**Q2**: BloodHound コレクターがうるさすぎるか EDR に遮られ、全量グラフを取れない場合はどうするか?
**A2**: 手動の定点列挙に転換する:全グラフは不要で、いくつかの重要な問いに答えるだけでよい。誰が DA か、どのマシンに DA セッションがあるか、どのオブジェクトに書き込み権限があるか、Kerberoast できる SPN は何か。ネイティブ LDAP 照会で 1 つずつ答え、局所経路を組み立てればよい。
**Q3**: グラフで自分がドメイン管理者から遠く、直接の辺がない場合、どう進めるか?
**A3**: 「中継の踏み台身元」を探す:グラフに沿って、私が一歩で取れる中程度の権限のアカウント/マシンを探し、取ったらそれを新たな起点として経路を再計算する。ドメインペネトレーションは多ホップであり、一歩で DA を期待しない。身元を取るたびに最短経路を再計算する。
**Q4**: ある経路が「高権限ユーザーがあるマシンにアクティブセッションを持つ」ことに依存するのを見つけたら、どう利用するか?
**A4**: そのマシンを落とし、メモリ内のそのユーザーのチケット/認証情報を取る(Pass-the-Ticket/Hash)。それでその高権限身元を窃取できる。セッション即認証情報であり、セッションのあるマシンは高価値の中継点である。
**Q5**: 全ての経路が、私が取れない堅牢化マシンで行き詰まり、ドメイン内の推進が遮断されたら、どこへ方向転換するか?
**A5**: 「証明書/委任/信頼」などの構造的ベクトルに方向転換する:別の直交攻撃面に替える。ADCS 証明書テンプレートの設定ミス(ESC 系)、Kerberos 制約/非制約委任、ドメイン信頼関係によるクロスドメイン攻撃。ACL 経路が行き止まりのとき、AD の証明書と委任体系が別の通天の経路であることが多い。

### 半対話 shell を全機能対話 TTY に昇格する
**Q1**: リバースした shell で Ctrl-C が使えず、sudo もできず、tab 補完もない。どう昇格するか?
**A1**: 標準の昇格連鎖:python3 -c 'import pty;pty.spawn("/bin/bash")' で pty を起動し、Ctrl-Z でローカルに戻って stty raw -echo して fg、対象に戻って export TERM=xterm、stty rows/cols を設定する。判定基準:昇格後に sudo が走り、対話プログラムが使え、Ctrl-C で接続が切れないこと。
**Q2**: 対象に python がない場合、どう TTY を昇格するか?
**A2**: 等価ツールに替える:script -qc /bin/bash /dev/null、socat の両端 pty、または expect/perl/他のスクリプト言語で pty を起動する。判定基準は「本物の pty を取れるか」で、ツールは一意ではない。
**Q3**: なぜ権限昇格前に必ず TTY を昇格する必要があるのか?昇格しないとどこで詰まるか?
**A3**: 昇格しないと:sudo が no tty を返す、対話型権限昇格(パスワード入力/確認)が失敗する、Ctrl-C がリバース接続全体を直接殺す、多くの対話プログラム(vi/ftp/ssh)が使えない。第一ラウンドの多くの権限昇格動作は対話に依存するので、昇格しないのは自分の手足を自ら縛るのに等しい。
**Q4**: 昇格の過程でうっかり接続を切ってしまい、繰り返し切れる。どう安定させるか?
**A4**: 「先に持続的で安定したチャネルを落としてから昇格する」ことに方向転換する:脆いリバース上で揉むより、この脆い shell で正規の C2 beacon か autossh の逆接続を 1 つ落とし、安定したチャネルを得てから、その中で TTY 昇格と後続の全操作を行う。
**Q5**: 環境制限が極めて厳しい(制限付き shell rbash、常用バイナリがない)場合、昇格が遮断されたらどこへ方向転換するか?
**A5**: 「制限付き shell のエスケープ」という専用ディメンションに方向転換する:rbash のエスケープ点(shell エスケープのあるプログラム、PATH がロックされていない、環境変数を変えられる)を探すか、全く別の足場方式(サービス/スケジュールタスクで非制限の実行コンテキストを取る)に替える。

### 無外向き / オフライン環境での武器配送
**Q1**: 対象が私側に接続できない(無外向き)ので、必要なツールを送り込めない。どうするか?
**A1**: 先に外向き面を正確に判定する(次の条項参照)。本当に無外向きと確認したら「その場の材料+既存チャネル配送」に方向転換する:既存の C2/トンネルでアップロードする、対象に既にあるツール(certutil、curl、wget、bitsadmin、python、powershell ダウンロード)を使う、SMB/内部ネットワーク到達可能な中継機経由で配布する。
**Q2**: 対象にコンパイラもスクリプトインタープリタもない場合、どう能力を持ち込むか?
**A2**: 静的コンパイルバイナリを使う:ローカルでツールを対象アーキテクチャに静的コンパイルし(arch 一致に注意)、既存チャネルで配置する。対象環境のランタイムに依存しない。判定基準は「私のツールが対象のどのランタイムにも依存しない」ことである。
**Q3**: ディスクに置くと即 AV に削除され、ツールが 3 秒も生きられない場合はどうするか?
**A3**: 「ファイルなし/メモリ配送」に方向転換する:ディスクに置かず、直接メモリロードする(reflective load、fileless、payload を既に授信されたプロセスに詰める)。または先に検知回避/特徴除去してから置く。ディスク配置で殺されるのは「ディスク配置」という動作の問題であり、メモリ実行に替えて迂回する。
**Q4**: 内部ネットワークに 1 台外向きできるマシンがあり、対象マシンはできない。どう使うか?
**A4**: 外向きできるマシンを配送の中継にする:ツールをまず中継機に置き、内部ネットワークチャネル(SMB 共有、HTTP、内部 socks)経由で隔離された対象へ配布する。第一ラウンドで「誰が外向きできるか」は重要な地形情報であり、専用にマークしておく。
**Q5**: どのチャネルも立てられない(極度の隔離、純粋な単方向コマンド出力)場合、配送が完全に遮断されたらどこへ方向転換するか?
**A5**: 「純粋な living-off-the-land」に方向転換する:外部ツールの配送を全て諦め、対象内蔵のバイナリだけで情報収集と権限昇格をこなす(システムコマンド、内蔵スクリプトエンジン)。極度の隔離時、内蔵ツールが唯一の武器であり、能力はツールからシステムネイティブコマンドへの習熟に移る。

### 外向き検知:このマシンがどう外と話せるかを把握する
**Q1**: 足場が外向きできるか、どう外向きできるかを知りたい。どう体系的に測るか?
**A1**: プロトコル別に 1 つずつ測る:DNS 持ち出し(ほぼ最もよく通る)、HTTP/HTTPS 直結、プロキシ経由の外向き、ICMP、常用ポート(80/443/53)の外向き。判定基準は「どのプロトコル、どのポート、プロキシ要否で、私が制御する外部アセットに到達できるか」である。1 種類だけ測って結論しない。
**Q2**: 直結は通らないが、内部ネットワークにプロキシサーバーがある場合、どう判断して利用するか?
**A2**: システム/ブラウザ/環境変数内のプロキシ設定(http_proxy、PAC、WPAD、レジストリ ProxyServer)を探す。企業網の外向きはプロキシ強制が多いので、プロキシ設定を得ればそれを借りて出られる。プロキシ情報自体も第一ラウンドで収集すべき情報である。
**Q3**: DNS しか出られない場合、何ができるか?
**A3**: DNS トンネルで C2 とデータ持ち出しを行う:遅いが封じにくい。判定基準は私が制御するドメインの任意のサブドメインを解決できるかである。DNS の外向きは「何も通らないように見える」環境で最後の活路であり、優先して測る。
**Q4**: 全プロトコルの外向きが遮断された(本当の隔離セグメント)場合、C2 を立てられないが、どこへ方向転換するか?
**A4**: 「内部ネットワーク中継の折り返し接続」に方向転換する:外網へ直接接続せず、トラフィックを内部ネットワーク内の別の外向きできるマシン経由で多段中継する(pivot 連鎖)。外向き能力は「借りる」ことができ、必ずしも本機自身のものでなくてよい。
**Q5**: 外向きテスト自体が私を露出させないか?
**A5**: 露出させる。外へ様々なポート/プロトコルを繰り返し打つのは明らかなビーコンで、外向きアラートをトリガーし得る。そのため節制する:先に受動手掛かり(既存設定、既存の外向き接続 netstat)から外向き方式を推測し、能動テストを最小化する。外向き検知をスキャンにしない。

### AV/EDR の識別:動く前に誰が監視しているか知る
**Q1**: マシンに足を下ろしたら、権限昇格/認証情報取得の前にどう防御を把握するか?
**A1**: セキュリティ製品を列挙する:プロセス/サービス内の AV/EDR の特徴(一般的なベンダーのプロセス名)、インストール済みセキュリティソフトのディレクトリ、Windows Defender の状態(Get-MpComputerStatus)、カーネルドライバリスト、EDR の minifilter の有無。判定基準は「次の自分の動作がその銃口に当たらないか」である。
**Q2**: EDR があると確認したら、操作戦略をどう変えるか?
**A2**: 「走れるなら走る」から「各動作の特徴を先に見積もる」に変える:高特徴コマンド(定番 mimikatz、明らかな whoami /all の組み合わせ、大範囲列挙スクリプト)を避け、ネイティブコマンド、メモリ操作、動作の分割による相関低下を優先する。EDR があるとき、遅いことは即ち速いことである。
**Q3**: EDR が純粋なローカル遮断か、クラウド連動の報告かどう判断するか?
**A3**: 外連の EDR クラウドチャネルがあるか、SOC の監視時間帯かを見る。保守的に「必ず報告される」と仮定し、人が復盤する基準で操作する。判定基準は相手を過大評価する方がよく、過小評価は足場を根こそぎ失う。
**Q4**: 私の核心ツールが EDR に直接遮られ、権限昇格動作ができない場合、どこへ方向転換するか?
**A4**: 「手法を替えるのであり目標を替えない」ことに方向転換する:同じ目標(例 lsass 取得)にも複数の技術経路があり、遮られたのはある経路の特徴である。低特徴の実装に替える、ファイルなし方式に替える、先に dump してオフライン解析に替える。または先に EDR を盲目化/迂回してから操作する。
**Q5**: EDR が強すぎてどの機微操作も難しい場合、このマシンを諦めるべきか?
**A5**: 必ずしも諦めない。「純粋な情報/踏み台に降格する」ことに方向転換する:この強防御マシンで危険な動作をせず、低リスクの偵察とネットワーク中継だけに使い、権限昇格と認証情報取得の作業は防御の弱い隣接マシンに移す。抵抗が最も小さいマシンを選んで動く。

### 永続化のタイミング:いつ埋めるか、どの層に埋めるか
**Q1**: 足を固めたばかりで、すぐ永続化すべきか?
**A1**: 層別に見る。先に現在の権限下で目立たない「命綱チャネル」を 1 つ残す(高権限でなくても)。唯一の入口を失うのを防ぐ。ただし重い作業(高権限永続化)は権限昇格が安定してから行う。判定基準:入口が単一なほど早く冗長化すべき。権限が低いほど永続化の価値は限定的である。
**Q2**: 永続化方式をどう選べば見つかりにくいか?
**A2**: 環境に融合するものを選ぶ:システム既存の仕組み(正当なスケジュールタスク風、サービス、スタートアップ項目、SSH authorized_keys、web の正当なパス)を優先して再利用し、独創的で目立つバックドアを避ける。判定基準は「ブルーチームがベースライン比較をしたとき、これが飛び出るか」である。
**Q3**: 高権限永続化(ドメイン級)はいつ行い、何に注意するか?
**A3**: ドメイン管理者などの高権限を得た後、少量の隠蔽的なドメイン級永続化(チケット系、証明書系、特定アカウントの ACL)を行う。ただし節制する。埋めるほど発見確率が上がる。判定基準は「最小の永続化で最大の再進入保障を得る」ことである。
**Q4**: 私が埋めた永続化が消された/足場が失われた場合はどうするか?
**A4**: 「多様な冗長化」の考え方に方向転換する:全ての永続化を同じ仕組み/同じマシンに賭けない。別々のホスト、別々の層(ユーザーモード/サービス/認証情報/証明書)に分散して埋める。1 箇所消されても別の箇所から再進入できる。失うのは単点の冗長不足を示すので、冗長を補う。
**Q5**: 先に権限昇格か、先に永続化か。リソースが限られ 1 つしか選べない場合はどうするか?
**A5**: 入口の安定性で順序を決める:入口が非常に不安定(いつ落ちるか分からない)→ 先に最低限の命綱チャネルを残してから権限昇格する。入口が安定 → 先に権限昇格してより高い権限を得てから、より堅牢な永続化を行う。機械的に二者択一せず、「先に失うと損が最も大きいのはどれか」で並べる。

### データベースアカウントの着地:DB 権限から本機と横展開を撬る
**Q1**: 得たのがデータベースアカウント(DB に接続できるがシステム shell はまだ)の場合、どうシステム層に昇格するか?
**A1**: DB の能力に沿って出口を探す:ファイルを書けるか(webshell を web ディレクトリにエクスポート)、ファイルを読めるか(設定/鍵を読む)、システムコマンドを実行できるか(UDF、xp_cmdshell 系、拡張)。判定基準は「この DB アカウントに、データ境界を越えるどんな能力が付与されているか」である。
**Q2**: DB アカウントが高権限(例 DBA 級)の場合、優先して何をするか?
**A2**: 高権限 DB アカウントはしばしば直接コマンド実行か拡張ロードで、DB サービスアカウント権限(しばしば高いシステム権限)まで権限昇格できる。同時にライブラリ内の認証情報テーブル(アプリユーザー、他のシステムの対向パスワード)を dump する。ライブラリ内のパスワードは横展開の金鉱である。
**Q3**: DB アカウントの権限が非常に低く、特定の数テーブルしか読めない場合、まだ価値はあるか?
**A3**: ある。ライブラリ内の業務データ/パスワード hash/token 自体が目標か横展開の燃料かもしれない。低権限 DB も先に読める認証情報系データを掬い尽くしてから権限昇格を考える。データ即戦果であり、shell だけが戦果ではない。
**Q4**: webshell を書きたいが web ディレクトリの絶対パスが分からない場合、どうするか?
**A4**: DB 側か既存情報からパスを推測する:設定テーブルを読む、エラーが漏らすパスを見る、一般的なパスを試す、DB でシステムファイルを読んで web ルートを逆算する。パス不明のとき、ファイル書き込み系権限昇格は「どこに書くか」で詰まるので、先に位置特定を解決する。
**Q5**: DB にファイル書き込みもコマンド実行もなく、サンドボックス化されている場合、DB 権限昇格の経路が遮断されたらどこへ方向転換するか?
**A5**: 「DB で掬った認証情報で横展開する」ことに方向転換する:本機のシステムを撬れなくても、ライブラリ内のパスワード/鍵を他のシステムに使う(パスワード再利用)と一撃で当たることが多い。DB 着地点の価値は半分がシステム権限昇格、半分がそこに保存された認証情報にある。

### Web ディレクトリ / ソースコード / 設定:足場の足元の情報金鉱
**Q1**: web サービスから侵入した。現在の shell 以外に、足元に何が掘れるか?
**A1**: システム的に web ルートとアプリケーションディレクトリを探る:設定ファイル(DB/キャッシュ/メッセージキュー/サードパーティ API 認証情報)、ソースコード内のハードコードされた鍵、アップロードディレクトリ、バックアップと一時ファイル(.bak/.git/.svn)、ログ(token/session を含むことがある)。判定基準は「開発と運用がこのマシンにどんな秘密を残したか」である。
**Q2**: .git ディレクトリの露出を発見したら、価値をどう最大化するか?
**A2**: 完全な git 履歴を引く:履歴のコミットには「削除された」鍵、パスワード、内部アドレス、他システムの接続情報がよくある。現在のコードがきれいでも履歴がきれいとは限らない。git log/履歴 diff は専用の情報ディメンションである。
**Q3**: 設定が全て環境変数のプレースホルダで、実際の値がない場合はどうするか?
**A3**: 実行時状態に値を取りに行く:設定が参照する環境変数の実際の値は、プロセスの環境(/proc/PID/environ)、オーケストレーション/コンテナの secret、CI/CD 変数、鍵管理サービスにある。プレースホルダは「どんな秘密があるか」を示すので、プレースホルダ名に沿って実行時状態で真の値を探す。
**Q4**: ソースコード内に内部 API/他サービスのアドレスを発見したら、何に使うか?
**A4**: これは横展開の地図である:内部ネットワークにまだどんなサービスがあり、そのアドレスと認証方式が分かる。より弱い内部サービスを攻められるかもしれない。ソースコード内の「内部依存」リストは、ポートスキャンより正確に次の目標を指すことが多い。
**Q5**: web ディレクトリの権限が固く、設定を何も探れない場合、この線が遮断されたらどこへ方向転換するか?
**A5**: 「システム級とユーザー級の収集」に方向転換する:web ディレクトリの外、システムの /etc、ユーザーホームディレクトリ、一時ディレクトリ、メモリ、履歴コマンドにも認証情報があるかもしれない。web ディレクトリは多くの情報源の 1 つにすぎず、1 箇所がきれいなら層を替える。

### 横展開対象の優先順位:大量の到達可能ホスト、どれを先に攻めるか
**Q1**: 内部ネットワーク偵察で十数台の到達可能ホストが見つかった。リソースは限られる。優先順位をどう付けるか?
**A1**: 「価値×到達性×抵抗」で並べる:ドメインコントローラー/ファイルサーバー/DB/運用踏み台が最も価値が高い。私の現有認証情報で直結できるものが到達性が最も高い。防御が弱いものが抵抗が最も小さい。判定基準は「高価値で、既に鍵があり、防御が弱い」交わりを先に攻め、IP 順に盲打ちしない。
**Q2**: あるホストが高価値かをどう素早く判断するか?
**A2**: 役割の手掛かりを見る:ホスト名/DNS(dc、sql、backup、jump などの命名)、開放ポート(ドメインコントローラーの 88/389/445 の組み合わせ、DB ポート)、誰がログインしたか(高権限ユーザーのセッション)、どれだけのマシンが依存するか。役割が IP より価値を決める。
**Q3**: 明らかに高価値だが防御が非常に強いマシンがある。無理に噛むべきか?
**A3**: 通常は噛まない。「迂回」に方向転換する:先にその周辺の弱いマシンを取る、その上にセッションを持つユーザーの認証情報を取る、それが信頼する経路を探して間接的に到達する。高価値で強防御の対象は正面から取られることが少なく、周辺ペネトレーションで「包囲」されることが多い。
**Q4**: どのホストが本当に到達できる(通じる)か不確かな場合、どう低ノイズで確認するか?
**A4**: 認証式検知をスキャンの代わりに使う:既存の認証情報で SMB/WMI/WinRM 接続を試し、通じれば到達可能で、ついでに認証情報の有効性も検証できる。ポートスキャンより隠蔽的である。到達性と認証情報の有効性を 1 回の動作で同時に確認する。
**Q5**: 並べた目標が 1 つも攻められない(認証情報が再利用されず、全部パッチ済み)場合、横展開が行き詰まったらどこへ方向転換するか?
**A5**: 「本機に戻って深掘りしてより良い認証情報に替える」ことに方向転換する:横展開が攻められないのは鍵不足が多く、制御済みマシンに戻ってより多くの認証情報(より高権限なアカウントのチケット、ドメイン認証情報)を取得するか、共有認証情報にアクセスできる層まで権限昇格してから、目標を並べ直す。横展開のボトルネックは対象でなく認証情報にあることが多い。

### Kerberoast / AS-REP Roasting:低権限ドメインアカウントでも撬れるパスワード
**Q1**: 普通のドメインアカウントが 1 つしかない。ドメインコントローラーに触れずに高権限パスワードを直接得る手は何か?
**A1**: Kerberoasting を試す:SPN を持つサービスアカウントの TGS チケットを要求し、オフラインでそのパスワードを爆破する(サービスアカウントは弱いパスワードで高権限のことが多い)。任意の有効なドメインアカウントが開始でき、低ノイズである。判定基準は「ドメイン内に SPN を設定したサービスアカウントがあるか」である。setspn/SPN 照会で先に目標プールを確認する。
**Q2**: チケットを要求できたが爆破できない(パスワードが強い)場合はどうするか?
**A2**: AS-REP Roasting に替える:「事前認証を要求しない」設定のアカウントを探し、先にチケットを持たずに直接オフライン爆破できる hash を取る。両者は補完的な直交手法で、1 つが失敗したらもう 1 つを試す。両方失敗ならパスワードが概ね強いことを示すので、別のベクトルに方向転換する。
**Q3**: 爆破する価値が最も高いサービスアカウントをどう選ぶか?
**A3**: 高権限の SPN アカウント(特権グループ内、DA 級サービスアカウント)を優先して選ぶ。破れば直接高権限になる。判定基準は「このアカウントのパスワードが計算力を費やす価値があるか」である。SPN リストはグループメンバーシップ情報と併せて見て、無差別に爆破しない。
**Q4**: Kerberoast リクエストが検知される(ブルーチームが異常 TGS リクエストを監視)場合はどうするか?
**A4**: 低頻度の定点に方向転換する:全ドメインを一度に roast せず(全量リクエストは強アラート信号)、少数の高価値 SPN のチケットだけを要求する。または既存認証情報の他の横展開経路に替える。手法の頻度を下げ、roast をスキャンにしない。
**Q5**: ドメイン内に roast できるアカウントが全くない(SPN なし、全員事前認証要求)場合、この線が空ならどこへ方向転換するか?
**A5**: 「委任 / ACL / 証明書」の構造的面に方向転換する:Kerberoast はパスワード面であり、失敗したら AD の他の設定ミス面に替える。非制約/制約委任、危険な ACL、ADCS テンプレート。パスワード面の収穫がないことは AD に穴がないことを意味しない。

### ADCS 証明書面:過小評価されたドメイン権限昇格の高速道路
**Q1**: ドメイン内のパスワード面と ACL 面がうまくいかない場合、証明書サービスを見るべきか?
**A1**: 見るべきである。ADCS は常年の、見落とされた権限昇格の高速道路である。先にドメイン内に CA(証明書サービス)があるか判定し、証明書テンプレートの設定を列挙する。判定基準は「低権限ユーザーが認証/権限昇格に使える証明書を申請できるテンプレートがあるか」である。CA があれば、ESC 系の設定ミスを 1 周専門に調べる価値がある。
**Q2**: テンプレートのどの設定ミスを具体的に調べるか?
**A2**: 数種類を見る:テンプレートが申請者による SAN のカスタマイズを許可するか(任意ユーザーへのなりすまし、ESC1 系)、登録権限が広すぎるか、CA が任意の SAN を受け付けるか、乱用可能な EKU があるか、CA サーバー自体の web エンドポイントが relay 可能か。判定基準は「どの箇所で高権限ユーザーになりすます証明書を取れるか」である。
**Q3**: 乱用可能なテンプレートを 1 つ見つけたら、証明書をどうドメイン権限に変えるか?
**A3**: それで対象(例 DA)になりすます証明書を申請し、その証明書で Kerberos 認証(PKINIT)を行って対象のチケット/hash を取る。証明書は持続的で失効しにくい身元証明であり、取れればその身元を得たのと同じである。
**Q4**: CA に明らかなテンプレート設定ミスがなく、ADCS の直接経路が通らない場合、別の角度はあるか?
**A4**: relay/エンドポイントの角度に方向転換する:CA の web enrollment/証明書インターフェースが NTLM relay できるかもしれない(ESC8 系)。強制認証と組み合わせてマシンアカウントを CA へ relay して証明書を取る。テンプレート面がきれいなら、エンドポイント面が別の ADCS 経路である。
**Q5**: ドメインに ADCS が全く配備されておらず、証明書の経路が全く存在しない場合、どこへ方向転換するか?
**A5**: 「委任 + 重要マシンの認証情報」に戻る:ADCS がなければ、力を Kerberos 委任の乱用、ドメインコントローラー/重要サーバー上の高権限チケットの取得、信頼関係に置く。ADCS は多くの通天の経路の 1 つにすぎず、なければ別の経路に進む。

### MS17-010 / SMB 系リモート面:内部ネットワークで重火器を使うべきか
**Q1**: 内部ネットワークをスキャンして 445 が開いた古いマシンが数台見つかった。MS17-010 を一気に撃ちたい。撃つべきか?
**A1**: 先に「値するか+安定か」を判断する。判定基準:対象が本当に脆弱性バージョンウィンドウに入るか、本番の核心マシンか(メモリ破壊系 exp はブルースクリーンのリスク)、より安定した認証式横展開の代替があるか。古くて未パッチのマシンは使えるが、重火器の優先度は「認証情報によるクリーンな横展開」より低くすべきである。
**Q2**: 対象が本当に的中する可能性を先に確認して盲打ちを減らすには?
**A2**: 安全な検知(プロトコルフィンガープリント/脆弱性検知スクリプト、判定のみで利用しない)でバージョンとパッチ状態を確認してから、実弾を撃つか決める。判定基準は「検知を通ってから撃つ」ことで、ブルースクリーンのリスクで賭けない。
**Q3**: 認証式横展開(現有の hash/パスワード)が使えるとき、まだリモート exp を使うか?
**A3**: 認証式横展開を優先する。チケット付き PsExec/WMI/WinRM は安定し、正常な運用トラフィックのように見え、メモリ破壊 exp よりはるかに優れる。重火器は「認証情報がなく、かつこの古いマシンを必ず取らなければならない」ときの代替であり、第一選択ではない。
**Q4**: exp が対象をブルースクリーン/サービス停止させ、かえってブルーチームを驚かせた場合、どう補うか?
**A4**: 即座に同種の重火器を止め、認証式またはより温和な脆弱性の横展開に転換する。露出度を評価して、足場を切り替えるか活動を下げるか決める。ブルースクリーンは強アラートなので、以降は「既に露出」基準で動作を収束する。
**Q5**: 対象が全パッチ済みで、SMB リモート面が全封鎖の場合、この種の経路が遮断されたらどこへ方向転換するか?
**A5**: 「認証情報 + アプリケーション層」に方向転換する:SMB リモート脆弱性面が封じられたら、内部ネットワーク横展開の主力は認証情報再利用とアプリケーション層脆弱性(内部 web、ミドルウェア、DB)に戻る。リモートメモリ破壊脆弱性は横展開のごく一部であり、パッチが揃ったら別の面に進む。

### Zerologon / ドメインコントローラー直撃系:高収益高リスクの判定
**Q1**: ドメインコントローラーを特定した。直撃の脆弱性があると聞く。賭けるべきか?
**A1**: 非常に慎重に。判定基準:ドメインコントローラーが脆弱性バージョンウィンドウに入るか、その exp がドメインコントローラーを破壊するか(あるものはマシンアカウントのパスワードを変更し、処理を誤るとドメインコントローラー障害、本番影響、強アラートになる)。ドメインコントローラー直撃は一度事故になれば全体的な災害なので、先にロールバック/復旧能力を評価する必要がある。
**Q2**: この種の高リスク exp を使うと決める前に、何を準備する必要があるか?
**A2**: 「復旧方案」を準備する:exp が何を変更するか(例 マシンパスワード)を把握し、復旧手順を用意して、ドメインコントローラーを撃って麻痺させ、元に戻せなくなるのを避ける。判定基準は「安全に撃って復元できるか」で、できなければ本番のドメインコントローラーに触れない。
**Q3**: この種の高リスク exp を使わない、より安定したドメインコントローラー取得方法はあるか?
**A3**: ある。認証情報連鎖を優先する:Kerberoast/委任/ACL/証明書/高権限セッションの取得で一歩ずつ DA かドメインコントローラーのマシンアカウントを取り、クリーンに DCSync で hash を引く。これは破壊的 exp よりはるかに安定し、第一選択とすべきである。
**Q4**: 高リスク exp がドメインコントローラーで失敗または遮断された場合、どうするか?
**A4**: 果断にこの線を諦めて構造的権限昇格に方向転換する:失敗した直撃は既にアラートになっている可能性があるので、ACL/委任/証明書などの「正常な操作に見える」経路に戻ってゆっくり DA まで磨く。直撃の失敗はドメインが取れないことを意味せず、この近道が通らなかっただけである。
**Q5**: ドメインコントローラーを取った後、最初にすべきことは何か?
**A5**: DCSync でドメイン内 hash(特に krbtgt)をエクスポートする。krbtgt を得れば黄金チケットで長期の任意身元が実現できる。同時に目立たないドメイン級永続化を構築し、動作を節制して即座に復盤されないようにする。ドメインコントローラー取得は収穫の始まりであり、終わりではない。

### Pass-the-Hash / Pass-the-Ticket:認証情報を得た後の最も適切な使い方
**Q1**: 手元に大量の hash とチケットがある。横展開でどれを使い、どう選ぶか?
**A1**: 認証情報の種別でプロトコルを選ぶ:NTLM hash→PtH(NTLM 認証の SMB/WMI)。TGT/TGS→PtT(Kerberos)。平文→全プロトコルにスプレー可能。判定基準は「対象がどの認証を受け付け、私のこの鍵がどの種別か」である。hash を Kerberos しか認めない場面に無理に使わない。
**Q2**: PtH があるマシンで拒否された(hash は有効だが接続できない)。原因として何が考えられるか?
**A2**: 調査する:対象がローカルアカウントのリモート NTLM を無効にしているか(制限管理モード/LAPS でパスワード変更)、ドメインアカウントが必要なのに私がローカルを使っているか、ファイアウォールが対応ポートを遮っているか。ドメインアカウントの認証情報に替えるか、プロトコルを替える(Kerberos)。拒否はしばしば「認証方式の不一致」であり、hash が無効なのではない。
**Q3**: PtT を PtH より優先すべきはいつか?
**A3**: ドメイン環境では Kerberos の方が「正常」で、NTLM 関連の検知をトリガーしにくく、チケットで複数サービスを要求できる。チケットがあれば PtT を優先する。さらに一部の堅牢化環境は NTLM を無効にしており、Kerberos しか通せない。このとき PtT が唯一の選択肢である。
**Q4**: 手元の認証情報で横展開してもあちこち壁に当たる(再利用されない、隔離される)場合はどうするか?
**A4**: 「認証情報の品質を高める」ことに方向転換する:現在の鍵が駄目なら、より高価値の認証情報を取得しに戻る。ドメイン管理者チケット、マシンアカウント、krbtgt。横展開が通らないのは「鍵のレベル不足」が多く、道がないのではない。鍵を昇格してから攻める。
**Q5**: 認証情報横展開で騒ぎを大きくしないには?
**A5**: 低ノイズのプロトコルと低頻度のリズムを選ぶ:画面いっぱいの PsExec より WMI/WinRM を優先する、同じ hash を全網にスプレーしない(スプレーは強アラート)、既存セッションを再利用して繰り返し新規接続しない。認証情報横展開の隠蔽性は「正常な運用にどれだけ似ているか」に依存するので、節制して使う。

### 内部ネットワークのポートスキャン:どうしてもスキャンするときのノイズ最小化
**Q1**: 受動情報が足りず、本当に内部ネットワークのポートを能動的に探らなければならない。どうスキャンすればアラートを爆発させないか?
**A1**: 3 原則である:狭く(目標セグメント/重要ポートだけ 445/3389/22/80/443/DB ポート。全ポートしない)、遅く(低並列低レート、スキャナのフィンガープリントを避ける)、分散(分けて分時に、一気に全網しない)。判定基準は「トラフィックを散発的な正常アクセスのように見せ、1 回のスキャンに見せない」ことである。
**Q2**: 先にどのホストが生きているか知ってからスキャン先を決めたい。生存検知をどう低ノイズで行うか?
**A2**: スキャンなしの生存情報を優先する:ARP ネイバー、DNS 逆引き、ドメイン内のコンピュータオブジェクトリスト、netstat の既存接続。本当に探るなら、少量の高命中ポート(445/135)を軽く探り、ping 全セグメントをしない。生存判定は「新規トラフィック」より「既存データ」を借りる。
**Q3**: pivot プロキシ経由で内部ネットワークをスキャンする場合、速度と安定性をどう両立するか?
**A3**: プロキシ経由のスキャンは遅くなりパケットロスしやすいので、さらに並列度を下げる。判定基準は「遅くて正確である方が、速くて結果を失いプロキシまで壊すよりよい」である。プロキシ連鎖上のスキャンは直結より保守的にし、そうしないと露出し、かつ信頼できる結果も得られない。
**Q4**: スキャンを始めた直後に NDR アラートをトリガーしたのに気づいたら、どうするか?
**A4**: 即スキャンを止め、認証式発見に転換する:既存の認証情報で接続する(SMB/WinRM)。通じれば到達を確認でき、スキャントラフィックを一切出さない。ポートスキャンが遮断されたとき、「認証情報でノックする」ことが隠蔽的な代替発見手段になる。
**Q5**: 能動トラフィックが全く許されない(極端に機微な環境)場合、ポート情報をどう得るか?
**A5**: 純粋に受動で再構築する:本機の netstat、ARP、hosts、known_hosts、アプリ設定内の対向アドレス、ログ内の接続記録で内部ネットワークのトポロジを組み立てる。極端な環境では、トポロジ情報は全て「制御済みホストが覚えているもの」から来る。

### pivot を立てる:足場を深層セグメントへのトンネルに変える
**Q1**: 内層セグメントにこの足場しか到達できないのを見つけた。自分のツールをどう突入させるか?
**A1**: プロキシトンネルを構築する:socks プロキシ(C2 または ssh -D 経由)でローカルツールを足場マシン経由で内層にアクセスさせる。判定基準は「私のスキャン/横展開ツールが内層 IP に透過的に届くか」である。既存の安定チャネル(C2 内蔵転送/ssh)の再利用を優先し、別に目立つサービスを立てない。
**Q2**: 足場マシンに ssh がなく、大きなツールも送りにくい場合、どうトンネルを立てるか?
**A2**: 軽量/メモリ化の転送を使う:C2 内蔵の socks、小さな静的転送バイナリ、またはシステム内蔵能力でポートフォワーディングする。判定基準は「最小の配置で貫通能力に替える」ことである。ツールは小さく静かであるほどよい。
**Q3**: トンネルは立ったが遅く頻繁に切れる。どう安定させるか?
**A3**: 調査する:単一ホップか多段ホップか(段が多いほど不安定)、帯域/遅延、C2 ハートビート設定。安定性は速度より優先する。並列度を下げ、再接続を強くし、必要なら中間にもう 1 台近い中継を足して連鎖を短縮する。深層作業はトンネルの安定に依存するので、揺れるトンネル上で重要操作をしない。
**Q4**: 足場マシンがいつ消されるか分からず、トンネルが切れたら深層と連絡不能になる。どう防ぐか?
**A4**: 「多段冗長入口」に方向転換する:深層セグメント内にもう 1 つ足場を取って第二入口にする。チャネル全体を 1 台に吊るさない。ある 1 台が消されても、別の経路で深層に入れる。pivot にも冗長が必要である。
**Q5**: 目標セグメントが厳格な ACL で、足場マシンすら内層に届かず、トンネルを立てられない場合、どこへ方向転換するか?
**A5**: 「本当の境界マシンを探す」ことに方向転換する:現在の足場マシンが内層への経路上にないので、先に二枚差し/内層アクセスを認可された踏み台マシンを見つける(ルートを見る、誰が内層と通信しているかを見る)。取ってから pivot する。届かないなら、届くマシンに替えて踏み台にする。

### クラウド上の足場:メタデータサービスとクラウド認証情報が第一優先
**Q1**: 足場が実はクラウド上のインスタンス(ECS/EC2 系)だと分かった。第一ラウンドで先に何を取るか?
**A1**: クラウドメタデータサービス(IMDS、一般的に 169.254.169.254)を優先する:インスタンスにバインドされた一時クラウド認証情報(ロール token)を直接吐き出すことがある。判定基準は「IMDS から STS/ロール認証情報を取れるか」で、取れればそのマシンのクラウド上の権限を得たことになり、価値は本機のシステム権限昇格より高いことが多い。
**Q2**: IMDS でロール認証情報を得た後、何ができるか?
**A2**: それでクラウド API を呼ぶ:権限を列挙し、バケット/オブジェクトを列挙し、他リソースを読み、他のインスタンスへの横展開や、より高いクラウドロールへの権限昇格ができるかを見る。クラウド認証情報は戦場を「このマシン」から「クラウドアカウント全体」に広げる。先にこの認証情報の権限境界を把握する。
**Q3**: IMDS が堅牢化されている(token 要求の v2、または無効)場合、この経路が封じられたらどうするか?
**A3**: 他のクラウド認証情報源に方向転換する:マシン上の ~/.aws / gcloud / az 設定、環境変数の AK/SK、CI 変数、アプリ設定のクラウド鍵、マウントされたクラウド secret。IMDS はクラウド認証情報源の 1 つにすぎず、堅牢化されたらディスク上のものを探る。
**Q4**: これがクラウドか、どのクラウドかをどう素早く定めるか?
**A4**: フィンガープリントを見る:メタデータアドレスの到達性、DMI/BIOS ベンダー情報、カーネル内のクラウドドライバ、ネットワークカード/ホスト名の命名規則、クラウド agent プロセスの有無。クラウドベンダーを判定してから、どのメタデータインターフェースと認証情報ファイルを探すべきか分かる。
**Q5**: クラウドと確認したがクラウド認証情報が何も得られず、クラウド経路が当面空の場合、どこへ方向転換するか?
**A5**: 従来の内部ネットワーク/本機のディメンションに戻る:クラウド環境にも通常のシステム権限昇格、内部ネットワーク横展開、DB、AD(クラウド上にもドメインがあり得る)がある。クラウド認証情報は加速器であり唯一の経路ではない。取れなければ通常の内部ネットワークの戦い方で続ける。

### コンテナ / K8s:Pod 内からクラスタ全体を見渡す
**Q1**: 自分が K8s Pod 内にいると確認した。第一ラウンドでどこを見るか?
**A1**: 先に serviceaccount を見る:/var/run/secrets/kubernetes.io/serviceaccount 内の token と CA。判定基準は「この SA token で API Server に何ができるか」(Pod を列挙/作成できるか、secret を読めるか、namespace を跨げるか)。SA 権限がクラスタ内でどれだけ進めるかを決める。
**Q2**: SA token の権限が悪くない場合、どう制御ノード/クラスタへ昇格するか?
**A2**: 一般的な経路:create Pod 権限があればホストのルートディレクトリをマウント/特権コンテナでノードエスケープを実現する。secret を読めれば他サービス/クラウド認証情報を取る。namespace を跨げれば面を広げる。判定基準は「どの API 権限でホストマシンや高権限 secret を踏めるか」である。
**Q3**: コンテナからホストへエスケープしたい。先に何を判断するか?
**A3**: エスケープ面を判断する:privileged か、どの capabilities があるか、docker.sock やホストディレクトリがマウントされているか、マウントできるか、カーネルに使えるエスケープ脆弱性があるか。判定基準は「ホストのファイルシステムかカーネルに触れる箇所が 1 つでもあるか」である。エスケープリストを項目ごとに確認する。
**Q4**: SA token の権限が非常に狭く、エスケープ面も全封鎖で、K8s の経路が非常に固い場合、どこへ方向転換するか?
**A4**: 「アプリ/ネットワーク層」に方向転換する:コンテナ内で動くアプリ自体、Pod がアクセスできる内部ネットワークサービス(データベース、内部 API、他の Pod)、クラスタネットワーク内の東西トラフィック。逃げられなければ、コンテナが到達できるネットワーク面で横展開する。クラスタが硬くても、アプリが硬いとは限らない。
**Q5**: 高権限 SA(cluster-admin 級など)を得た場合、最初に何をするか?
**A5**: API 面を安定制御して収穫する:全 namespace の secret を列挙する(クラスタ内の全サービス/クラウド/DB 認証情報の集散地)、コントロールプレーンコンポーネントを探す、必要に応じて隠蔽的な永続化(例 毒入り DaemonSet)を構築する。cluster-admin はクラスタ全体に等しく、重点は認証情報の収集と安定した永続化である。

### 蜜罐 / 蜜アカウント / おとりの識別:罠に頭から突っ込まない
**Q1**: 内部ネットワークに「良すぎて非現実的」なマシン(明らかな弱いパスワード、誘惑的なファイルだらけ)が現れた。興奮すべきか警戒すべきか?
**A1**: 警戒する。判定基準:防御の厳重な内部ネットワークに異常に攻めやすい/異常に露出した対象が現れるのは、蜜罐の可能性がある。それが現実の業務と断絶していないかを見る(正常なトラフィックがない、命名が不自然、ファイルがわざとらしく置かれている、アカウントが一度もログインしない)。現実のアセットには生活の痕跡があり、おとりには通常ない。
**Q2**: 蜜アカウント(honey account/honey token)をどう識別するか?
**A2**: 不自然さを見る:高権限な名前のアカウントなのに一度もログインしない、パスワードを一度も変えない、見つけやすい場所(設定内のあからさまな認証情報など)に「故意に」置かれている。この種のアカウントで認証すると、即座にアラートになる可能性が非常に高い。判定基準は「この認証情報は私が使うのを待ってそこに置かれたものか」である。
**Q3**: 蜜罐かどうか疑うが不確かな場合、どう探るか?
**A3**: 低コミットの探りを行う:先に読み取り専用/受動観察だけをする(正常なトラフィック、プロセス、誰と通信するかを見る)。高特徴の動作や毒入れを即座にしない。判定基準は「最小の露出で真偽を確認する」ことで、おとりと確認したら避け、本物なら手を付ける。
**Q4**: 既に蜜罐を踏んだ/監視サンドボックスに誘導された疑いがある場合、どうするか?
**A4**: 「既に露出」モードに転換する:即座に動作を収束し、このマシンからどの手法と入口が露出したかを評価し、独立した予備の足場とチャネルに切り替えて続行する。蜜罐を踏む最大のリスクは、あなたの TTP 一式へ芋づる式に辿られることなので、関連を断つのが最も重要である。
**Q5**: ネットワーク全体が高度に布陣され、どこも罠に見える場合、どう進めるか?
**A5**: 「現実の業務に張り付いて進む」ことに方向転換する:現実の業務トラフィック、現実のユーザー活動があるアセットだけに触れ、正常な業務連鎖に沿って横展開し、「孤立、露出、生活の痕跡がない」おとりを全て避ける。布陣が重いほど、近道を探すのではなく現実のトラフィックを隠れ蓑にすべきである。

### 痕跡とログ:攻めながら「自分は何を残したか」を考える
**Q1**: 第一ラウンドの情報収集が終わった。自分が残した痕跡をどう棚卸しするか?
**A1**: 分類して棚卸しする:配置ファイル(ツール、payload、dump)、ログ(ログイン、コマンド、認証イベント)、新規接続/プロセス/アカウント/タスク、shell 履歴。判定基準は「ブルーチームが今このマシンを見たら、どれが私の残した異常か」である。自分の「汚れデータ」リストを心に持つ。
**Q2**: ログを消すべきか?消すと逆に目立たないか?
**A2**: 比較検討する。ログの全消し/大幅変更自体が強アラート信号である(ログの断絶は非常に目立つ)。判定基準:「事後に消す」より「残さない」を優先する。ディスクに置かない、ネイティブコマンド、正当なパス再利用で痕跡の発生を減らす。本当に消すなら自分の数行を定点削除し、ログ全体を消さない。
**Q3**: shell history に機微コマンドを大量に残してしまった。最も安定した処理は?
**A3**: 優先は最初から書かないこと(history を記録しない設定/ history に残らない実行方式を使う)。既に書いたなら自分の数行を定点で掃除し、タイムスタンプの一貫性に注意する。判定基準は「変更を最小にし、新たな異常(ファイルタイムスタンプの急変など)を作らない」ことである。
**Q4**: ある動作が既にアラートをトリガーし、痕跡が露出したのに気づいたら、どうするか?
**A4**: 「損害制御」に方向転換する:既に露出した痕跡を消すことにこだわらない(間に合わないことが多い)。それが何を露出したか、他の足場に波及しないかを評価し、重要能力をきれいな予備チャネルに移す。露出した痕跡の重点は「関連を断つ」ことであり、「きれいに拭く」ことではない。
**Q5**: 長期駐留で、痕跡を持続的に最小に保つには?
**A5**: 「日常に溶け込む」原則に方向転換する:動作を正常な運用の時間帯と方式に合わせる、正当なアカウントとツールを再利用する、活動頻度を制御する、いかなる「断絶/急変/孤立」の異常も避ける。持続的な隠蔽は、ある回の巧みな掃除ではなく、長期的に正常なユーザーらしく振る舞うことに依存する。

### 全面行き詰まりの振り返り:権限昇格も横展開も動かないときの体系的な方向転換
**Q1**: 権限昇格を全て試し、横展開も動かない。完全に行き詰まった。やみくもにぶつからず、突破口をどう体系的に探すか?
**A1**: 「ディメンション棚卸し」を行う:攻撃面を直交ディメンションに分解して 1 つずつ自己点検する。本機(カーネル/SUID/cron/sudo/サービス)、認証情報(メモリ/ディスク/履歴/ブラウザ/クラウド)、ネットワーク(新セグメント/pivot/外向き)、身元(ドメイン/サービスアカウント/クラウドロール)、アプリ(ソース/設定/DB/内部サービス)。行き詰まりは通常、あるディメンションを全く調べていないことであり、調べたもの全てが本当に穴なしなのではない。
**Q2**: 「本当に穴がない」か「情報が足りない」かをどう判断するか?
**A2**: 「自分の観測の死角はどこか」と自問する:ツール不足で見えないか(ツールを補う)、権限不足で読めないか(先に小さく権限昇格してから見る)、ノイズ懸念で調べるのを怖がっているか(低ノイズ手段に替えて調べる)。大多数の「穴なし」は実は「見尽くしていない」である。先に観測を広げてから「穴なし」と結論する。
**Q3**: 各ディメンションを浅く見ただけで、どれも突破できない場合、次はどうするか?
**A3**: 「広さのスキャン」から「一点の深掘り」に転換する:最も可能性の高い 1 ディメンション(通常は認証情報の再利用か、あるカスタムアプリ)を選んで底まで深掘りする。ソースを全て読む、hash を全て爆破する、呼び出し連鎖を全て追う。行き詰まったとき、深さの方がもう 1 層の広さより結果を出すことが多い。
**Q4**: 動かせる足場が 1 つも権限昇格できない場合、もう撤収すべきか?
**A4**: 先に「足場/入口を替える」に転換してから撤収を論じる:最初の攻撃面に戻って 2 つ目の入口(別の脆弱性、別の境界マシン)を探し、全く新しい起点で現在の死局を迂回する。同じ足場で行き詰まったら、足場を替えるとしばしば豁然と開ける。
**Q5**: 時間/リソースが尽きそうで、取捨選択しなければならない。最後の主攻方向をどう定めるか?
**A5**: 「期待収益/残存抵抗」で並べ、火力を 1 つに集中する:通常は「私が既に半分の鍵を持ち、かつ対象価値が高い」線(例 既に hash を取ったが対象を探すだけ、既にドメイン設定ミスを見つけたが利用するだけ)。終局ではもう広く網を張らず、成功に最も近い単点に賭けて全力突破する。

### 足場の生存維持:入口を対抗の中で長く生かす
**Q1**: 第一ラウンドの収集期間中、この苦労して得た入口を簡単に失わないようにするには?
**A1**: 即座に「冗長チャネル」を構築する:最初の接続だけに依存しない。早めにもう 1 本、独立した仕組み、独立した外向き方式の予備チャネル(別プロトコル、別ポート、別トリガー方式)を落とす。判定基準は「任意の 1 本が切断されても、私がまだ入れる」ことである。単点の入口が最大の脆弱性である。
**Q2**: 主チャネルと予備チャネルをどう設計すれば一網打尽にされないか?
**A2**: 直交させる:別々の配置位置、別々の C2/プロトコル、別々の永続化仕組み、できれば別々のホスト。判定基準は「ブルーチームが 1 本を発見して対処したとき、もう 1 本まで芋づるに露出しない」ことである。同源同特徴の多チャネルは 1 本と等しい。
**Q3**: beacon のハートビートが頻繁すぎてトラフィック解析に掴まるのを心配する。生存と隠蔽をどう両立するか?
**A3**: ハートビート頻度を下げ+ジッタを加え+正常な業務トラフィックの特徴に貼り付ける。判定基準は「チャネルが長く生きるには、口数を減らし、正常なトラフィックらしく話す」ことである。生存性と隠蔽性はここでは統一されており、騒がしいほど短命である。
**Q4**: 足場マシンが対処されそうだ(ブルーチームがその上で動いている)場合、どう戦果を救出するか?
**A4**: 「救出の優先順位」に転換する:まだいるうちに、最初に取得済みの認証情報/情報を回送し、能力を他所の予備足場に移す。名残惜しんで収集を続けない。マシンがなくなりそうなら、先に取得済みの認証情報と別の入口を守る。ものはこのマシンより重要である。
**Q5**: 唯一の足場を既に失い、全チャネルが切れた場合はどうするか?
**A5**: 「収集済みの情報でコールドスタート再進入」に方向転換する:以前に取った認証情報、把握したセグメントトポロジ、発見した他の入口が、再び入る鍵である。第一ラウンドの情報収集の最大の価値の 1 つは、足場を失った後も情報で道を再び辿れることである。そのため情報は早めに持ち出し、そのマシンに全て押し込めない。
