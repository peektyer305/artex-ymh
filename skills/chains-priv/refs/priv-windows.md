# 権限昇格と足場 · Windows 権限昇格決定木

### 低権限 shell に着地した直後、最初にすべきこと
**Q1**: 身元不明の shell を得たばかり。最もすべきでないのは即 winPEAS を投げること。先に何をするか?
**A1**: 先に 60 秒かけて自分を定位する:`whoami`、`whoami /priv`、`whoami /groups`、`hostname`、`systeminfo`。三問に答える:私は誰か、マシンの成色、ドメイン内か。この 3 点なしに自動化を走らせると、無関係な出力に埋もれ、配置ファイルが EDR に掴まるリスクを増やす。
**Q2**: 私が一般ユーザーで、整合性が Medium の場合、次の判定基準は?
**A2**: Medium は、ローカル管理者グループにいても高整合性トークンがないことを意味する。これが「SYSTEM への権限昇格」か「UAC bypass だけでよいか」を決める。`whoami /groups` で Administrators にいるかを見る:グループ内で Medium → UAC bypass。グループ外 → 本当のローカル権限昇格。
**Q3**: `whoami /priv` で最初に何を走査するか?
**A3**: SeImpersonate、SeAssignPrimaryToken、SeBackup、SeRestore、SeDebug、SeTakeOwnership、SeLoadDriver を走査する。どれか 1 つでも Enabled なら、経路はほぼ確定し、目的なくサービスを探すより 10 倍速い。
**Q4**: サービスアカウント(IIS APPPOOL/mssql など)の場合、優先順位をどう変えるか?
**A4**: サービスアカウントはほぼ必ず SeImpersonate を持つので、Potato ファミリーに直行する。これは投入産出比が最も高い線で、遠回りしない。
**Q5**: 偵察のこの経路が行き詰まった。コマンドが制限され、出力が呑まれ、shell が不安定。どこへ方向転換するか?
**A5**: 「足場の安定化」という直交ディメンションに方向転換する:先に shell を安定した折り返しか beacon に昇格するか、より完全な実行チャネルに替える。権限昇格の前提は安定したコマンド実行で、shell が切れたら全て無駄である。
**Q6**: 偵察情報をどう保存して重複労働を避けるか?
**A6**: systeminfo/whoami /all/サービス/ソフト/ネットワークを各 1 部ずつ自分の戦報に保存する(対象のディスクに落とさない)。権限昇格は反復プロセスで、しばしば振り返って照合する。コマンドを繰り返すのは遅く、露出も増やす。

### SeImpersonate を手にしたら、どう SYSTEM になるか
**Q1**: SeImpersonate が Enabled。どの Potato を選ぶか?
**A1**: 先にバージョンとパッチを見る。旧システム/COM が使える → JuicyPotato。新システムで RPC/COM が封じられている → PrintSpoofer(Spooler パイプ)、RoguePotato(リモート OXID)、GodPotato(比較的汎用)。判定基準は「どの前置がこのマシンで成立するか」であり、「どれが最新か」ではない。
**Q2**: PrintSpoofer が spoolss パイプが見つからないと報じる場合はどうするか?
**A2**: Spooler が止められている。固執せず、RoguePotato/GodPotato に切り替える。Spooler に依存しない。SeImpersonate 権限昇格の本質は「SYSTEM プロセスを騙して私の名前付きパイプに接続させる」ことで、実装手段は多く、前置も様々なので、1 つずつ試すコストは低い。
**Q3**: ツールに騙されず、真の成功をどう検証するか?
**A3**: ツールが出力する success を信じない。payload に検証できることをさせる:高権限プロセスを新規起動して折り返す、または SYSTEM しか書けないディレクトリにファイルを作る。SYSTEM トークンを目で見て初めて実とする。
**Q4**: Potato が全て EDR に遮られる(名前付きパイプの挙動が検知される)場合、どうするか?
**A4**: 直交に方向転換する:① 自前のトークン窃取コードでツールの特徴を消す。② 「サービスアカウント自体の権限」に方向転換する。それはあるデータベース/共有/ドメインオブジェクトに特権を持つかもしれず、横展開か直接認証情報を読む方が隠蔽的である。
**Q5**: RoguePotato が外部 135 の中継を必要とするが、マシンの外向きが制限されている場合はどうするか?
**A5**: 本機でポートリダイレクトして OXID 解決をループバックに引き戻すか、全ローカルの GodPotato に替える。外向きが硬い制約なら「全ローカル」変種を優先する。

### ローカル管理者グループだが Medium 整合性のみ(UAC を通す必要がある)
**Q1**: whoami /groups が Administrators にいると示すが、高整合性ではない。どう高権限を取るか?
**A1**: これは「権限昇格」でなく「UAC を越える」ことである。auto-elevate のホワイトリストプログラムを 1 つ選んで UAC bypass する(fodhelper、computerdefaults、sdclt、関連レジストリキーや DLL のハイジャック)。判定基準は現在の UAC レベルで、既定レベルではこれらの迂回の大半が有効。最高レベル(「常に通知」)では大半が無効である。
**Q2**: どの bypass がこのバージョンの Windows でまだ有効かをどう知るか?
**A2**: build 番号で一致させる。UAC bypass はバージョン依存が高く、古い技法は新 build で塞がれる。先に `ver`/build を取り、対応するウィンドウ内の技法を選ぶ。古い技法で新システムに無理にぶつからない。
**Q3**: fodhelper 系を 2 つ試して高権限プロセスが立ち上がらない場合はどうするか?
**A3**: UAC が最高に設定されているか、その auto-elevate 項目が削除された可能性がある。直交に方向転換する:既に管理者なので、直接管理者認証情報で「非対話高権限」経路を使う。SYSTEM 身元でサービス/スケジュールタスクを作る、または PsExec で本機 admin$ に接続し、UAC 対話モデルを迂回する。
**Q4**: 平文の管理者パスワードがあるが Medium のみ。最もきれいな SYSTEM 取得方式は?
**A4**: そのパスワードで、SYSTEM で動くサービスかスケジュールタスクを新規作成/乗っ取る。メモリ注入系より安定し隠蔽的である。正当な認証情報があるときは「正当な仕組み」を優先し、脆弱性を使わない。
**Q5**: 全 UAC bypass が失敗し、このマシンでは高権限が取れない場合、どこへ方向転換するか?
**A5**: 目標を替える。既にローカル admin なので、横展開価値(本機の hash を取る、LSASS を読む、踏み台にする)は既に十分である。「本機で SYSTEM を取る」を格下げし、ドメイン内横展開に方向転換する。別のマシンの方がドメイン権限を取りやすいことが多い。

### サービス系権限昇格:未引用サービスパス
**Q1**: unquoted service path を探したい。利用可能なものをどう素早く特定するか?
**A1**: サービスパスを列挙し、「空白を含み未引用、かつ私がある級の中間ディレクトリに書き込み可能」の 3 条件を探す。3 つが揃わなければ利用できない。空白だけで書き込み権限がないのは偽陽性で、時間を浪費しない。
**Q2**: 候補を 1 つ見つけたら、ハイジャック点に書き込めるかどう確認するか?
**A2**: パスの各空白前のディレクトリに対して書き込み権限を測る(一時ファイルを作って削除)。書ける → 同名 .exe を置いてハイジャック。書けない → この線は無効で、次を見る。
**Q3**: サービスが手動/無効起動で、payload を置いてもトリガーしない場合はどうするか?
**A3**: 私がサービスを再起動できるか(sc start 権限)、システム再起動を待つかを見る。能動的にトリガーできないなら、それを「再起動後に効く」永続化+権限昇格として掛け、同時に能動トリガーできる経路を並行して探す。待つだけにしない。
**Q4**: この種のサービスが全て規則通り引用符を付けており、権限昇格が手を付けられない場合、どこへ方向転換するか?
**A4**: サービスの他の 2 つの直交面に方向転換する:① サービスのバイナリファイル/所在ディレクトリの ACL が書き込み可能か(直接 exe を替える)。② サービスのレジストリキー ImagePath/権限が変更可能か。unquoted はサービス設定ミスの 1 種にすぎない。
**Q5**: サービス変更で本番業務を壊さない(痕跡/アラート)ようにするには?
**A5**: 非重要で、素早く自己回復できるサービスを優先して選ぶ。ハイジャックした exe 内で先に私の payload を起動し、その後元の真のバイナリを呼んでサービス機能を正常に保ち、運用アラートを減らす。

### サービスバイナリ/レジストリが書き込み可能(弱い ACL)
**Q1**: 自動化があるサービスのバイナリが私に変更可能と提示した。どう確認するか?
**A1**: その exe とそのディレクトリの有効権限を調べる(icacls / accesschk の考え方)。私のユーザー/グループが Write か FullControl を持つか確認する。ツールが報じる「書き込み可能」は手で再確認する。ACL 継承にはしばしば落とし穴がある。
**Q2**: 書き込み可能と確認したら、どう変更するのが最も安定か?
**A2**: 直接元ファイルを削除しない(ロック/検証があるかもしれない)。「その場で wrapper に置換する」ことを優先する:先に私の高権限動作を実行し、その後バックアップした元バイナリを起動してサービスを正常に保つ。その後再起動をトリガーするか待つ。
**Q3**: サービスのレジストリキーに書き込み権限があるがファイルにない場合、権限昇格できるか?
**A3**: できる。ImagePath を私の payload に変える、FailureCommand(サービス失敗時に実行)を変える、Parameters を足す。レジストリ側とファイル側は 2 つの独立した攻撃面で、1 つが通らなければもう 1 つを試す。
**Q4**: サービスが私と同級かより低い権限で動く場合、変更しても権限昇格の意味がないが、どうするか?
**A4**: 先にサービスの実行アカウントを確認する。SYSTEM/高権限アカウントで動くサービスだけに権限昇格価値がある。低権限で動くなら飛ばし、LocalSystem サービスを探す。
**Q5**: ディスク全体に弱い ACL のサービスがない場合、どこへ方向転換するか?
**A5**: 「書き込み可能な自動実行点」という大分類に方向転換する:スケジュールタスク、スタートアップ項目、Run キー、DLL 検索パス。サービスは自動高権限実行の担い手の 1 種にすぎない。

### SeBackup / SeRestore 特権を手にしたら
**Q1**: whoami /priv に SeBackupPrivilege がある。それでどう権限昇格するか?
**A1**: SeBackup は DACL を迂回して任意ファイルを読める。定番の使い方:SAM、SYSTEM、SECURITY レジストリ hive(またはシャドウ内)をエクスポートし、オフラインでローカルアカウント hash を抽出する。これは直接 SYSTEM を与えないが、PtH 用のローカル管理者 hash を与える。
**Q2**: SAM/SYSTEM をコピーした。次は?
**A2**: オフラインで secretsdump 系ツールで hash を抽出し、本機/同イメージの他マシンに pass-the-hash する。判定基準:ローカル admin hash は同じバッチのマシンで再利用されることが多く、価値は単機を超える。
**Q3**: ファイルが使用中でコピーできない場合はどうするか?
**A3**: シャドウコピー(VSS)でロックされたファイルを読むか、SeBackup セマンティクスのバックアップ API で読む。普通の copy でロックされた hive に無理にぶつからない。
**Q4**: SeRestore だけがあり SeBackup がない場合、考え方は同じか?
**A4**: 違う。SeRestore は「任意ファイル/レジストリへの書き込み」で、高権限サービスのバイナリを上書きできる、レジストリキーを変更できる、イメージハイジャック関連キーを置換して実行できる。書き込み権限の権限昇格面は読み取りより直接的である。
**Q5**: hive は取れたが hash が破れず、PtH も禁止されている場合、どこへ方向転換するか?
**A5**: DPAPI/ドメイン認証情報面に方向転換する:hive 内の SECURITY には LSA secrets、キャッシュされたドメイン認証情報、サービスアカウントパスワードも含まれる。これらを抽出する方がローカル hash の爆破より横展開価値が高いことが多い。

### SeDebugPrivilege を手にしたら
**Q1**: SeDebugPrivilege がある。直接権限昇格できるか?
**A1**: できる。SeDebug は任意のプロセス(SYSTEM プロセスを含む)を開ける。最も直接的:SYSTEM プロセスに注入する、またはそのトークンをコピーして高権限プロセスを起動する、または直接 lsass を dump する。判定基準は「どの動作が EDR の目に最も軽いか」である。
**Q2**: 直接 lsass を dump するのが目立ちすぎる。別の使い方はあるか?
**A2**: ある。SeDebug で SYSTEM プロセスを 1 つ探し、DuplicateToken 後に CreateProcessWithToken で私のプロセスを起動する。lsass に触れず、挙動がより温和である。トークン窃取はメモリ dump より隠蔽的である。
**Q3**: 注入が EDR に遮られる(リモートスレッド/メモリ書き込みが hook)場合、どうするか?
**A3**: 直交に方向転換する:トークンコピーの経路に替える(対象メモリに書かない)、または SeDebug 以外の私の既存特権に替える。重点監視される注入原語で繰り返しぶつからない。
**Q4**: SeDebug があると確認したが、コードの OpenProcess がまだ拒否される。なぜか?
**A4**: 特権が Disabled 状態の可能性がある。先にトークン内で Enable する必要がある。多くのツールが特権を明示的に有効化せずに呼ぶ。先に AdjustTokenPrivileges で有効化してから操作する。

### カーネル/システム脆弱性の権限昇格(exploit 系)をいつ使うか
**Q1**: 設定系を全て試して無理。カーネル exploit に踏み切るべきか?
**A1**: カーネル exploit は「高収益高リスク」の選択肢である。判定基準:① OS build とパッチ(patchlevel)を正確に一致させられる。② その exploit が安定でブルースクリーンを起こしにくい。③ 業務が潜在的なクラッシュに耐えられる。3 つが揃わなければ慎重に。ブルースクリーンは足場を壊し、運用者を驚かせる。
**Q2**: systeminfo のパッチ情報を使える exploit リストにどう変えるか?
**A2**: インストール済み KB リストを既知の権限昇格 CVE と照合する(Watson/WES-NG の考え方)。「対応パッチが欠けている」少数に絞る。大量の汎用 exploit を盲打ちしない。
**Q3**: MS17-010 系をどう定位するか?
**A3**: それはリモート SMB 面で、通常は横展開用であり、ローカル権限昇格ではない。ローカル権限昇格は CVE 系のカーネル LPE(各年の win32k/ALPC/CLFS 権限昇格など)をより多く見る。選定は先に「ローカル LPE」か「リモート RCE」かを切り分ける。
**Q4**: exploit を走らせて権限昇格も崩壊もしない場合、どう判断するか?
**A4**: おそらくパッチが実は当たっている、または build が一致していない。繰り返し走らせない(クラッシュ確率が上がる)。戻って正確な build/patch を照合し、一致しなければ exploit を替えるか、この線を完全に諦める。
**Q5**: カーネルの経路が全体的に通らない(全パッチ済み)場合、どこへ方向転換するか?
**A5**: 「サードパーティソフトのローカル脆弱性」面に方向転換する:インストール済みの殺毒ソフト/ドライバ/データベース/バックアップソフトにはローカル権限昇格脆弱性がよくある(特に BYOVD の攻撃されやすいドライバ)。システムの全パッチ ≠ サードパーティの全パッチ。

### 認証情報収集:ファイルシステムと設定内の平文
**Q1**: 設定権限昇格が通らない。認証情報を探りたい。先にどこを探るか?
**A1**: 先に「デプロイ/運用の遺物」を探る:unattend.xml、sysprep.inf、Autologon レジストリ、各 web/app 設定(接続文字列)、スクリプト内のハードコードされたパスワード、PowerShell 履歴。これらが最も出荷率が高い。
**Q2**: キーワードをどう定めるか?
**A2**: ディスク全体/重要ディレクトリを grep で password、pwd、pass、cpassword、connectionstring、secret、AccessKey などを検索する。判定基準は「どのパスワードがより高権限のアカウントかドメインアカウントに対応するか」である。
**Q3**: 大量のパスワードを見つけたら、先にどれを使うか?
**A3**: 権限価値で並べる:ドメイン管理者/サービスアカウント > ローカル admin > その他。先に本機で権限昇格できるか検証する(runas/サービス)、できなければ横展開に方向転換する。見つけた順に盲試しない。
**Q4**: GPP 内の cpassword をどう処理するか?
**A4**: SYSVOL の Groups.xml などに含まれる cpassword は、公開された固定 AES 鍵で直接復号できる。これはドメイン内の定番の遺物で、専門に探す価値がある。解けたのはローカル管理者パスワードであることが多く、横展開価値が大きい。
**Q5**: 全て探しても平文パスワードがない場合、どこへ方向転換するか?
**A5**: 暗号化認証情報面に方向転換する:DPAPI blob、ブラウザ/メールクライアント/データベースクライアントが保存する認証情報、Windows 認証情報マネージャー。平文がないことは認証情報がないことを意味せず、復号が必要なだけである。

### DPAPI が保護する認証情報をどう解くか
**Q1**: DPAPI 暗号化された blob をいくつか見つけた。どう解くか?
**A1**: DPAPI のユーザー主キーはユーザーのログオンパスワードに保護される。既にそのユーザーコンテキストで動いていれば、直接 CryptUnprotectData を呼んで解ける。そのユーザーのパスワードか hash を得ていれば、オフラインで masterkey を解いてから blob を解く。
**Q2**: そのユーザーコンテキストでなく、パスワードもない場合、まだ解けるか?
**A2**: 既にローカル SYSTEM/ドメイン管理者なら、DPAPI backup key(ドメイン級)で任意ユーザーの blob を解ける。そのため DPAPI はしばしば「高権限を得た後に他のユーザーの認証情報をさらに収穫する」ツールであり、起点ではない。
**Q3**: 解けて注目すべきものは何か?
**A3**: 保存された RDP 認証情報、スケジュールタスクが保存するアカウントパスワード、ブラウザ cookie/パスワード、Wi-Fi、VPN 認証情報。判定基準は同じく「どれがより高権限やより多くのホストに通じるか」である。
**Q4**: DPAPI が全線で解けない場合、どこへ方向転換するか?
**A4**: LSASS メモリ面に方向転換する。多くの認証情報はメモリ内で平文/再利用可能なチケットであり、DPAPI を解く必要がない。DPAPI と LSASS は 2 つの独立した認証情報源である。

### LSASS 認証情報取得の取捨選択
**Q1**: ローカル管理者/SYSTEM に到達し、lsass を dump したい。直接 mimikatz sekurlsa か?
**A1**: 先に EDR を評価する。lsass アクセスは第一の監視点である。判定基準:対象に EDR があるか、lsass に PPL 保護があるか、一度の高リスク動作に耐えられるか。EDR があれば裸で定番ツールを走らせない。
**Q2**: lsass が PPL(RunAsPPL)を開いて読めない場合、どうするか?
**A2**: BYOVD で署名付きドライバを入れて PPL を外すか、迂回する。lsass に触れない認証情報源(DPAPI、キャッシュ hash、チケットファイル、レジストリ secrets)に方向転換する。PPL に無理に正面からぶつからない。動作が大きい。
**Q3**: 取りたいが目立たないようにするには、どう特徴を減らすか?
**A3**: 既製ツール名/メモリ署名を使わない:システム内蔵の仕組み(例 comsvcs MiniDump 系)で dump ファイルを 1 つ落とし、ローカルに持ち帰ってオフライン解析する。「メモリを読む」と「解析」を分離し、対象マシン上の怪しい挙動を減らす。
**Q4**: dump しても hash だけで平文がない場合、どうするか?
**A4**: 新システムは既定で平文をキャッシュしない(WDigest が無効)。hash があれば PtH/PtT を使うか、Kerberos チケット(PtT)を取る。平文に固執しない。hash/チケットも同様に横展開できる。
**Q5**: lsass が全く触れない(PPL+EDR の二重保険)場合、どこへ方向転換するか?
**A5**: 「ドメイン側で lsass に触れない攻撃」に方向転換する:Kerberoast、AS-REP roast、ADCS 証明書乱用、DCSync(既に高権限なら)。これらはチケット/証明書から認証情報を取り、本機メモリを迂回する。

### スケジュールタスクが書き込み可能で権限昇格する
**Q1**: ハイジャックできるスケジュールタスクを探したい。判定基準は何か?
**A1**: 「高権限アカウントで動く + タスクが呼ぶスクリプト/プログラムを私が書ける、またはタスク定義ファイルを私が書ける」ものを探す。タスクを列挙し、Run As と Action が指すファイルパスを見て、書き込み権限を 1 つずつ測る。
**Q2**: SYSTEM タスクを 1 つ見つけたが、トリガー条件が「毎日未明」で、利用に一夜待つ必要がある場合はどうするか?
**A2**: 私が手動トリガーできるか(schtasks /run 権限)、トリガーを変更できるかを見る。できなければ「定時に効く」権限昇格+永続化として掛け、同時に即時トリガーの経路を並行して探す。戦線全体を待機に縛らない。
**Q3**: タスクが指すディレクトリを私が書けるが、ファイル自体の権限が厳しい場合、利用できるか?
**A3**: DLL 検索/相対パスを見る:タスクが書き込み可能なディレクトリから DLL をロードするか、相対パスでプログラムを呼ぶなら、同名ファイルを置けばハイジャックできる。ディレクトリ書き込み可能はファイル書き込み可能より有用なことが多い。
**Q4**: スケジュールタスクのこの線が全封鎖の場合、どこへ方向転換するか?
**A4**: 他の自動高権限実行点に方向転換する:サービス、Run/RunOnce レジストリキー、スタートアップフォルダ、WMI イベント購読。スケジュールタスクは「定時高権限実行」の 1 実装にすぎない。

### スタートアップ項目 / Run キー / AutoElevate プログラムがハイジャック可能
**Q1**: 起動時自動起動プログラムで権限昇格したい。先に何を見るか?
**A1**: HKLM と各ユーザーの Run/RunOnce、スタートアップフォルダ、高権限で起動する自動起動プログラムを列挙する。判定基準:その自動起動項目がより高権限のアカウントで動き、かつその exe/DLL/所在ディレクトリを私が書ける。
**Q2**: HKLM Run を私が書けるが、項目が現在のユーザー身元で動く場合、役に立つか?
**A2**: それは永続化であって権限昇格ではない。権限昇格には「管理者/SYSTEM か他ユーザー身元で自動起動する」項目を探す必要がある。「永続化」と「権限昇格」の 2 つの目的を分ける。混ぜない。
**Q3**: 管理者ログイン時に動くプログラムを見つけ、それが書き込み可能なディレクトリにある場合、どうするか?
**A3**: ハイジャックバイナリ/DLL を置き、管理者の次回ログインでトリガーする。これは「高権限ユーザーの対話を待つ」型の権限昇格で、収益は高権限ユーザーがそのマシンにログインするかに依存する。誰もログインしなければ価値は限定的である。
**Q4**: 高権限ユーザーがこのマシンにログインしない場合、この線は無効だが、どこへ方向転換するか?
**A4**: 「対話に依存しない」自動実行に方向転換する:SYSTEM サービス/スケジュールタスクは誰もログインしなくても走る。ユーザー対話が必要な技法は、無人のサーバーでは死路である。

### DLL ハイジャック / DLL 検索順序
**Q1**: 高権限プログラムを 1 つ狙って DLL ハイジャックしたい。実行可能性をどう判断するか?
**A1**: そのプログラムがロードするがシステムディレクトリに欠けている、または書き込み可能なディレクトリから先に検索される DLL(検索順序/side-loading)を探す。プロセス監視でロード時の NAME NOT FOUND 記録を見て、配置できる DLL 名とパスを特定する。
**Q2**: 対象 DLL が System32 に既に存在する場合、まだハイジャックできるか?
**A2**: プログラムが相対パスを使うか、その作業ディレクトリが検索順序で前方にあり書き込み可能なら、私の DLL に先に当たる可能性がある。判定基準は「私の書き込み可能なディレクトリが、そのプログラムの実際の検索順序で真の DLL より先か」である。
**Q3**: DLL を置いたがプログラムがクラッシュして私のコードを実行しない場合はどうするか?
**A3**: 私のプロキシ DLL は元の DLL のエクスポート関数を転送する必要がある(proxy/forward)。そうしないとプログラムが関数欠如でクラッシュする。ハイジャックは「私のものを実行しつつ元機能を壊さない」必要がある。
**Q4**: そのプログラムに DLL 署名検証/改ざん防止があり、ハイジャックが失敗する場合、どこへ方向転換するか?
**A4**: 別の高権限プログラムに方向転換するか、非 DLL 面(サービス/タスク/認証情報)に方向転換する。DLL ハイジャックは具体的なプログラムのロード挙動に依存し、1 つが駄目なら目標を替える方が防御を無理に攻めるより割に合う。

### PATH 環境変数のハイジャック
**Q1**: システム PATH に私が書き込めるディレクトリが含まれ、前方に並んでいるのを見つけた。権限昇格できるか?
**A1**: できる。ある高権限サービス/タスク/プログラムがコマンドを呼ぶ際にフルパスを書かない(例 単に `cmd`、あるツール名だけ書く)なら、PATH 内で私の書き込み可能なディレクトリの同名 exe に先に当たる。先に「高権限プロセスが短い名前でコマンドを呼ぶ」ことを確認する。
**Q2**: こうしてトリガーされる高権限呼び出しをどう見つけるか?
**A2**: サービス/スケジュールタスク/ログインスクリプト内で短い名前で呼ばれるプログラム、または一部のプログラムが起動時に検知する補助ツールを見る。トリガーする者がいなければ、書き込み可能な PATH ディレクトリは潜在面であり実手ではない。
**Q3**: この線が成立しない場合、どこへ方向転換するか?
**A3**: 具体的な DLL 検索ハイジャックかサービス/タスク面に方向転換する。PATH ハイジャックは「短い名前での呼び出し」というやや稀な前提に依存し、成立しなければ未練を残さない。

### AlwaysInstallElevated ポリシー
**Q1**: AlwaysInstallElevated を調べたい。何を調べるか?
**A1**: HKLM と HKCU 配下の Installer の AlwaysInstallElevated がどちらも 1 か調べる。2 つがどちらも 1 のときだけ有効で、このとき任意の .msi が SYSTEM でインストールされる。
**Q2**: どちらも 1 と確認したら、どう利用するか?
**A2**: 私の payload を実行する .msi を生成し、msiexec で静かにインストールすれば SYSTEM になる。これは非常にきれいな線で、ポリシー設定ミスで全滅する。
**Q3**: HKCU だけが 1 で HKLM が 0 の場合、使えるか?
**A3**: 使えない。両方が 1 である必要がある。1 つ欠ければ無効なので、msi の構築に時間を浪費せず、他の面に方向転換する。

### インストール済みサードパーティソフトのローカル脆弱性 / BYOVD
**Q1**: システムパッチが全適用されている。まだ権限昇格面はあるか?
**A1**: ある。インストール済みのサードパーティソフトとそのサービス/ドライバのバージョンを列挙する:殺毒ソフト、バックアップ、仮想化、データベース、リモート管理ツールはローカル権限昇格脆弱性を持つことが多い。システム全パッチ ≠ サードパーティ全パッチ。
**Q2**: インストール済みソフトを使える脆弱性にどう変えるか?
**A2**: インストール済みプログラムのバージョンを列挙して既知のローカル権限昇格 CVE と照合する。重点は「SYSTEM で動くサードパーティサービス」と「ロード済みのサードパーティカーネルドライバ」である。
**Q3**: BYOVD を使いたい。判定基準は何か?
**A3**: 既知の攻撃されやすい署名付きドライバを入れる/ロードできる必要がある(先に管理者権限が必要)。そのため BYOVD は「admin→カーネル/EDR 迂回」に使われることが多く、低権限からの起点ではない。連鎖内での位置を把握する。
**Q4**: サードパーティ脆弱性もない場合、どこへ方向転換するか?
**A4**: 認証情報収集と横展開に戻る:本機が動かせなければマシンを替える。内部ネットワークには、設定がより緩いかパッチがより古いホストが必ずあるので、1 台に無理に噛み続けない。

### ドメインマシン:ローカル権限昇格か直接ドメイン権限か
**Q1**: これがドメインメンバーマシンで、ローカル SYSTEM を得た。次にドメイン権限か本機続行か?
**A1**: 本機 SYSTEM は本機の価値を絞り尽くしたので、重心をドメインに移す。SYSTEM 身元のマシンアカウントでドメイン偵察(BloodHound データ)を行い、本機にログインしたドメインユーザーのチケット/hash を取る。本機 SYSTEM はドメインへの踏み台であり、終点ではない。
**Q2**: まだ本機 SYSTEM を取っていないが、ドメインに速い経路があり得る。どう比較検討するか?
**A2**: 並行評価する:ドメイン側に Kerberoast/AS-REP/ADCS ESC/無認証の zerologon/PetitPotam+ADCS 連鎖があれば、本機の権限昇格より速くドメイン管理者に到達できるかもしれない。判定基準は「どの経路の前置を私が既に満たしているか」である。
**Q3**: 本機の権限昇格が全線行き詰まったが、普通のドメインアカウントがある。どこへ方向転換するか?
**A3**: 本機の高権限が不要なドメイン側攻撃に完全に方向転換する:Kerberoast でサービスアカウント hash を取ってオフライン爆破、AS-REP roast で事前認証不要のアカウントを探す、ACL 設定ミスを調べる(BloodHound で制御可能経路を探す)。低権限ドメインアカウント自体が 1 本の鍵である。
**Q4**: ドメイン管理者を得た。まだ戻ってこの本機 SYSTEM をやる必要があるか?
**A4**: 通常は不要。ドメイン管理者があれば PsExec/WMI で任意のドメインメンバーを SYSTEM にできる。逆立ちして無駄なことをしない。ドメイン管理者権限を目標ホスト/DC に使うことこそ重点である。

### 足場から Kerberoast をやる
**Q1**: 普通のドメインアカウントが 1 つしかない。Kerberoast したいが、前提は足りるか?
**A1**: 足りる。任意の認証済みドメインユーザーが SPN アカウントの TGS を要求できる。先に SPN を持つユーザーアカウント(サービスアカウント)を列挙し、そのチケットを要求し、オフライン爆破する。低権限アカウントで開始できる。
**Q2**: roast で大量のチケットが出た。先にどれを破るか?
**A2**: SPN が高権限/ドメイン管理者グループに属する、またはパスワードが弱い可能性のあるもの(古いサービスアカウント)を優先する。判定基準は「破れた後の権限跳躍が最大」である。均等に力を入れない。
**Q3**: チケットが全て強パスワード(AES)で、オフライン爆破できない場合はどうするか?
**A3**: AS-REP roast(事前認証を無効にしたアカウントを探す)に方向転換するか、ACL/証明書面に方向転換する。Kerberoast は「弱いパスワードのサービスアカウントが存在する」ときだけ効率的で、強パスワード環境ではディメンションを替える。
**Q4**: ドメイン内に roast できる SPN アカウントがない場合、どこへ方向転換するか?
**A4**: ADCS 証明書乱用(ESC 系)か委任設定ミス(制約/非制約/RBCD)に方向転換する。これらは弱いパスワードに依存せず、設定ミスによる。

### ADCS 証明書テンプレート乱用(ESC 系)の判断
**Q1**: ドメインに CA がある。ESC 権限昇格面があるか見たい。先に何を見るか?
**A1**: 証明書テンプレートを列挙する(Certify/certipy の考え方)。「低権限で申請可能 + 任意 SAN を指定できる/認証に使える」テンプレート(ESC1 系)、または CA 設定ミス(ESC6/ESC8 など)を探す。判定基準は「私の低権限身元が、高権限ユーザーになりすます証明書を申請できるか」である。
**Q2**: 疑わしいテンプレートを 1 つ見つけたら、利用可能かをどう確認するか?
**A2**: enrollee に subject 提供を許可するか、EKU がクライアント認証を含むか、私の所在グループが enroll 権限に入るかを見る。3 つが揃って ESC1 が使える。1 つ欠けたら他の ESC 番号を見る。
**Q3**: 証明書を申請した後、どう権限に変えるか?
**A3**: 証明書で PKINIT 認証して対象アカウントの TGT を取るか、その NT hash を取る。証明書は「対象身元で認証する」認証情報であり、取れればそのアカウントを得たのと同じである。
**Q4**: CA が全て正しく設定され、ESC 面がない場合、どこへ方向転換するか?
**A4**: 委任乱用、DACL 攻撃経路(BloodHound)、または強制認証+中継(PetitPotam→ADCS ESC8 は web enrollment が必要)に方向転換する。ADCS は多くのドメイン権限昇格面の 1 つにすぎない。

### PrintNightmare / Spooler 系
**Q1**: Spooler 関連の脆弱性でローカル権限昇格したい。判定基準は何か?
**A1**: 先に Print Spooler サービスが動いているか、対応するパッチが未適用かを確認する。PrintNightmare 系はローカルで悪意あるドライバ DLL をロードして SYSTEM で実行できる。サービスが停止しているかパッチが揃っていれば無理である。
**Q2**: ローカルの PrintNightmare 権限昇格をトリガーして反応がない場合はどうするか?
**A2**: おそらくパッチ済みか、Point-and-Print ポリシーが締められている。繰り返しトリガーしない(大量のイベントログを残しやすい)。パッチを照合し、駄目なら他のドライバ/サービス面に方向転換する。
**Q3**: この線が遮断されたら、どこへ方向転換するか?
**A3**: 他の「サービスが SYSTEM で私の制御可能な内容をロードする」面に方向転換するか、認証情報の横展開に方向転換する。単一の CVE が修正されてもマシン全体に穴がないとは限らないが、1 つの CVE に固執して底まで時間をかけない。

### 認証情報再利用:横展開後に戻って権限昇格
**Q1**: 本機が動かせないが、他所で大量のパスワード/hash を得た。それでどう本機を権限昇格するか?
**A1**: 1 つずつ本機で検証する:あるローカル/ドメインアカウントのパスワードが本機の管理者かもしれない。それで本機の高権限へ runas/PtH する。権限昇格は必ずしも脆弱性に依存せず、認証情報の再利用が一撃で当たることが多い。
**Q2**: ある hash が本機の admin かをどう素早く判断するか?
**A2**: 本機に PtH 認証テストを 1 回行う(例 admin$ / SMB 認証にアクセス)。成功すれば本機 admin で、直接 PsExec で SYSTEM を取る。1 つずつ手動 runas しない。
**Q3**: 手元の hash が本機でどれも認められない場合、どこへ方向転換するか?
**A3**: 「本機上の他ユーザーの認証情報を取る」かドメイン側攻撃に方向転換する。本機が外部の hash を認めないなら、本機のメモリ/DPAPI から、本機自身が認識する認証情報を掘る。

### hash しかなく平文がない場合:PtH か解読か
**Q1**: NTLM hash を取ったが平文がない。PtH か爆破か?
**A1**: 先に PtH。NTLM hash は NTLM 認証の横展開/権限昇格に直接使え、平文は不要。対象が Kerberos しか認めない、または平文を非 Windows システムに再利用する必要がある場合だけ爆破する。
**Q2**: 対象環境が NTLM を無効にし、PtH が通らない場合はどうするか?
**A2**: Kerberos に方向転換する:hash で overpass-the-hash して TGT を取り(pass-the-key)、PtT する。hash は PtH だけでなく Kerberos チケットにも替えられる。
**Q3**: 両方制限される(NTLM 無効 + 強 Kerberos ポリシー)場合、どこへ方向転換するか?
**A3**: 平文を解読して正当なログインチャネルを通ることに方向転換するか、認証情報源を替える。認証プロトコルが締められたら、「正常なユーザーのように平文でログインする」に戻るのが最も安定する。

### 制限付き実行環境:AppLocker / WDAC / 制約言語モード
**Q1**: PowerShell が Constrained Language Mode で、権限昇格スクリプトが走らない。どうするか?
**A1**: 先に制限源を確認する(AppLocker/WDAC がトリガーした CLM)。迂回の考え方:非 PowerShell 実行(信頼された LOLBins、コンパイル exe、他のスクリプトエンジン)を通るか、CLM の既知の迂回を探す。ロックされた PS 内で無理に書かない。
**Q2**: exe も AppLocker のホワイトリストに遮られる場合はどうするか?
**A2**: マイクロソフトが既定で許可する書き込み可能なパス(一部のシステムディレクトリのホワイトリスト例外)を通るか、信頼された LOLBin で私のロジックをロードする。判定基準は「どの実行経路がホワイトリストポリシーの隙間にあるか」である。
**Q3**: 実行制限が厳しすぎて、どの payload もディスクに置けない場合、どこへ方向転換するか?
**A3**: 「新規実行体を配置しない」経路に方向転換する:純粋にシステム内蔵ツール(living-off-the-land)で偵察と認証情報収集をこなすか、権限昇格点を「設定ミス」に選ぶ(サービス/タスクを変更し、システム自身の仕組みで実行する)。バイナリ投下をしない。

### 非対話コマンド実行しかない(安定 shell がない)場合の権限昇格
**Q1**: Web/コマンド注入点で 1 コマンドずつしか実行できず、対話 shell がない。どう権限昇格するか?
**A1**: 先に実行を昇格する方法を工夫する:各コマンドが独立で状態がないと、権限昇格は難しい。優先して安定した折り返し(リバース shell)を落とし、対話とコンテキストを得る。安定チャネルがなければ、権限昇格はほぼできない。
**Q2**: 外向きが封じられ、リバース shell を張れない場合はどうするか?
**A2**: 正方向接続に方向転換するか、既に開いたポート/プロトコルのトンネル(DNS、HTTP トンネル、開いているサービスポートの再利用)を通る。実行チャネルが遮断されたら、先に「どう安定して通信するか」を解決してから権限昇格を論じる。
**Q3**: チャネルがどうしても立たず、単コマンドの盲撃ちしかできない場合、どこへ方向転換するか?
**A3**: 権限昇格を「一度で完了できる」動作に変える:単一コマンドで msi/サービス/タスクを書き、システムが高権限で私のペイロードを実行するようにする。「対話が必要な権限昇格」を「投下すれば自動で高権限実行」に転換する。

### EDR/AV が権限昇格動作を遮る場合
**Q1**: 私の権限昇格 exploit/ツールが配置直後に殺される。静的か挙動検知かをどう判断するか?
**A1**: 先に見分ける:配置即削除 = 静的シグネチャ。実行してある段階まで行ってから遮断 = 挙動検知。静的問題はサンプルを変える(再コンパイル/特徴除去/ファイルなし実行)。挙動問題は検知回避でなく技法経路を替える。方向を誤ると無駄骨である。
**Q2**: 静的検知回避後、実行時に挙動で遮られる場合はどうするか?
**A2**: 遮られたのが「動作パターン」(例 lsass 注入、名前付きパイプパターン)であることを示す。同じ目的で挙動が異なる経路に替える:注入の代わりにトークンコピー、メモリ操作の代わりに設定ミス利用。
**Q3**: 繰り返し検知回避を試すと草を打って蛇を驚かせないか?
**A3**: 驚かせる。殺されるたびにアラートが出る。1 台の重点マシンで連続して EDR にぶつからない。判定基準:2〜3 回ぶつかって通らなければ止め、「最も攻撃らしくない」設定系権限昇格に方向転換するか、マシンを替える。
**Q4**: この EDR が硬すぎて、権限昇格動作が全て露出する場合、どこへ方向転換するか?
**A4**: 本機で高リスク動作をしない経路に方向転換する:ドメイン側攻撃(Kerberoast/ADCS は他所から発起)、または直接 EDR の弱いホストへ横展開してから戻る。硬いマシンは迂回して攻める。

### サービスアカウントの外部リソースへの特権(横展開即権限昇格)
**Q1**: データベース/アプリのサービスアカウントで、本機が動かせない。他に価値はあるか?
**A1**: ある。サービスアカウントはしばしばデータベース、ファイル共有、他サーバーに特権を持つ。本機 SYSTEM に固執するより、その既存権限で横展開する:データベースに接続してコマンド実行、それが権限を持つ共有/ホストにアクセスする。アカウント身元自体が権限である。
**Q2**: 例 mssql サービスアカウントなら、どう使うか?
**A2**: そのアカウントはデータベース内で高権限なことが多い。DB で OS コマンドを実行する(関連機能が有効なら)、またはそのドメイン身元で roast/委任する。判定基準は「それが他所で持つ権限が、本機 SYSTEM より価値があるか」である。
**Q3**: サービスアカウントの外部権限も非常に限られている場合、どこへ方向転換するか?
**A3**: 本機のメモリに戻って、それがキャッシュする他の認証情報を取るか、通常のドメイン側攻撃に方向転換する。1 つのアカウントを絞り尽くしたら攻撃面を替え、単一の身元でその場を回らない。

### WSUS / SCCM / 内部ネットワーク配布システムの設定ミス
**Q1**: パッチ/ソフト配布システムで権限昇格できるのではと疑う。先に何を見るか?
**A1**: 本機が内部ネットワーク WSUS を使い、HTTP(HTTPS でない)経由か、または SCCM クライアントがあるかを見る。WSUS over HTTP は中間者攻撃で悪意ある「更新」を配布して SYSTEM で実行できる。SCCM には複数の乱用がある(NAA 認証情報、ポリシー配布)。
**Q2**: WSUS が HTTP だが、私が中間者位置にいない場合、どうするか?
**A2**: 本機から WSUS へのトラフィックを改ざんできる必要がある(本機 hosts/プロキシ書換、またはネットワーク位置)。中間者になれなければこの線は成立しないので、SCCM クライアント側か別の面に方向転換する。
**Q3**: この種の企業配布面が全てないか、堅牢化されている場合、どこへ方向転換するか?
**A3**: 標準のローカル権限昇格と認証情報面に方向転換する。配布システム乱用は「環境固有の高収益」面で、なければ強要せず、本筋に戻る。

### WMI イベント購読 / 他の自動実行永続点を権限昇格に再利用
**Q1**: 通常の自動実行点(サービス/タスク/Run)が全て封じられた。他にどの高権限トリガー面があるか?
**A1**: WMI 永久イベント購読、ログインスクリプト(GPO 配布)、Image File Execution Options(IFEO)ハイジャック、補助機能(sticky keys 系、先に高権限での書き込みが必要)。「高権限で実行され、かつ定義/対象を私が書ける」ものをどれか 1 つ探す。
**Q2**: ある GPO 配布のログインスクリプトのディレクトリを私が書けるか、どう考えるか?
**A2**: SYSVOL 内のログインスクリプトかその参照ファイルを書けるなら、その GPO を適用する全ユーザー/マシンに影響し、権限昇格+横展開を兼ねる。ただし通常は既にある程度のドメイン権限が必要。判定基準は「私の現在の権限でその点まで変更できるか」である。
**Q3**: これらのマイナーな点も全て書き込み不可の場合、どこへ方向転換するか?
**A3**: 本機の設定面がほぼ絞り尽くされたことを示す。認証情報/ドメイン側に方向転換するか、マシンを替える。自動実行点を列挙し尽くして無果なら、同種の点を探し続ける限界収益は既に低い。

### SYSTEM に権限昇格した後の足場の安定化
**Q1**: SYSTEM を得た。得たそばから失わないように、先に何をするか?
**A1**: 先に足場を固定する:現在の脆弱性から独立した折り返し/永続化(高権限サービスかタスク)が 1 本あることを保証し、それから本機の全認証情報(hash/チケット/DPAPI)を取る。見せびらかして横展開する前に、「戻れる」と「鍵を手に持つ」を先に確定する。
**Q2**: 最も安定し目立たない永続化はどれか?
**A2**: 「正常に見える」仕組みを優先する:名前が普通のサービス/スケジュールタスク、または既存の正当な自動起動項目の再利用。高特徴のバックドアを避ける。判定基準は「運用者の定例検査で目立たない」ことである。
**Q3**: すぐログを消すべきか?
**A3**: 慎重に。大規模なログ消去自体が強アラート信号である。重要項目の定点処理か挙動偽装を優先し、全消去しない。きれいに消しすぎる方が、少しノイズを残すより怪しい。
**Q4**: SYSTEM を取ったがこのマシンが孤立機(ドメイン不参加、横展開価値なし)の場合、どこへ方向転換するか?
**A4**: 対象価値を再評価する:エッジマシンにすぎないなら、重心をそれが到達できるセグメント/認証情報に移す。SYSTEM 自体が目標ではなく、それが接続するものこそ目標である。

### 全線権限昇格失敗:情報収集に戻って再スキャン
**Q1**: 設定、カーネル、認証情報、ドメイン側を全て試し、全線行き詰まった。このマシンを諦めるべきか?
**A1**: 先に諦めず、「自分が見落とした」と疑う。権限昇格の失敗は十中八九、情報不足である:別の自動化ツールで交差検証し、サービス/タスク/認証情報を手で再確認し、非既定パスのソフトディレクトリを見る。盲区は「本当に穴がない」より一般的である。
**Q2**: 再スキャンで具体的にどの盲区を補うか?
**A2**: ユーザー profile の奥の設定、非定番のドライブ/ディレクトリ、スケジュールタスクの XML 定義、レジストリ内のマイナーな自動起動キー、停止しているが起動できるサービス、PowerShell/コマンド履歴、メモリ内のプロセスコマンドライン(平文パスワード引数を含む)。
**Q3**: 身元の視点を替えると新しい面が出ないか?
**A3**: 出る。一部の書き込み可能点/認証情報は特定のユーザーにしか見えない。別の制御済みアカウントのコンテキストに切り替えて再スキャンすると、以前見えなかった攻撃面が露出することが多い。権限面は身元に応じて変わる。
**Q4**: 本当に再スキャンしても無果の場合、どう理性的に方向転換するか?
**A4**: 横展開に方向転換し、単機に無限に投入しない。判定基準:このマシンの情報価値(認証情報、接続性)を今回の目標に足るだけ絞り取ったか。足りたらそれを踏み台にして、設定がより緩い隣接機を攻める。レッドチームは最弱の 1 環を探すのであり、最硬の 1 台を攻略しない。
**Q5**: 万一このマシンが必ず取るべき重要標的(例 対象データが本機にある)で、かつ権限昇格できない場合はどうするか?
**A5**: 戦術目標を替える:SYSTEM でなくてもデータを取れるかもしれない。現在の権限で対象ファイル/データベースを直接読めるか?読めれば権限昇格を迂回して直接戦果を取る。権限昇格は手段であり目的ではない。本当の戦利品に目を向ける。

### SeTakeOwnership / SeRestore の組み合わせで高権限ファイルを奪う
**Q1**: SeTakeOwnershipPrivilege がある。それだけで権限昇格できるか?
**A1**: 単独では足りない。それは「任意オブジェクトの所有権を引き継ぐ」ことだけを許す。権限昇格連鎖は:先に高権限サービスの exe/重要ファイルを TakeOwnership し、owner になった後、自分に DACL を変更し(owner は権限変更できる)、私のペイロードを書き込む。それは「ACL 変更+ファイル書き込み」と組み合わせて初めて閉じる。
**Q2**: ある SYSTEM サービスのバイナリを引き継ぎたい。最も安定した目標の選び方は?
**A2**: 非核心で、再起動でき、SYSTEM で起動するサービスのバイナリを選び、引き継いだ後 wrapper に置換する(先に私のものを走らせ、後で元ロジックを呼ぶ)。再起動をトリガーして効かせる。重要システムファイルを引き継がない。壊すとマシン全体が不安定になり運用者を驚かせる。
**Q3**: 引き継いで権限も変えたが、ファイルがプロセスに使用中で書き込めない場合はどうするか?
**A3**: 現在未実行/停止可能なサービスのファイルに変えるか、レジストリ側に変える(ImagePath を私の書き込み可能な場所に向ける)。使用中のロックを避ける。使用中はファイル置換のよくある落とし穴なので、「未ロードの対象」に替えて迂回する。
**Q4**: SeTakeOwnership だけで、対応する書き込み/ACL 変更能力がない場合、この線が切れたらどこへ方向転換するか?
**A4**: 他の明確な単点特権(SeImpersonate/SeBackup/SeRestore/SeDebug)か設定系面に方向転換する。特権権限昇格は「この特権の完全な利用連鎖が閉じるか」を重視する。連鎖が閉じなければ時間をかけず、独立して連鎖を成せる特権に替える。

### セッションハイジャック:ログイン済み高権限ユーザーのトークン/セッションを窃取
**Q1**: 既に本機 SYSTEM で、マシンに他のユーザーがログインしている。その身元へ横展開できるか?
**A1**: できる。SYSTEM は現在のログインセッションを列挙できる(query user / プロセストークン)。他のログイン済みユーザー(ドメイン管理者/運用者かもしれない)のトークンを窃取してプロセスを起動するか、その RDP/対話セッションをハイジャックする。判定基準:私が現在握る身元より価値の高い身元がログイン中か。
**Q2**: 管理者の切断された(disconnected)RDP セッションがある。どう利用するか?
**A2**: SYSTEM 身元でその切断セッションを引き継ぐ/私のセッションに接続する(tscon 系の仕組み)。それでパスワードなしでそのデスクトップコンテキストに入る。これは「SYSTEM でドメイン高権限ユーザー身元に替える」定番の踏み台動作である。
**Q3**: そのトークンを窃取したいが、そのユーザーのプロセスが保護され/EDR に監視されている場合、どうするか?
**A3**: トークンでなく認証情報を取る:そのユーザーがログイン中なら、その認証情報/チケットが lsass か DPAPI にある可能性が高い。hash/チケットを取って横展開し、そのプロセスへの直接操作を避ける。トークン窃取と認証情報窃取は 2 つの経路で、1 つが監視されたらもう 1 つに替える。
**Q4**: マシンに他の高権限ユーザーが全くログインしていない場合、この線は無効だが、どこへ方向転換するか?
**A4**: 「高権限ユーザーのログインを待つ/誘導する」(ログインでトリガーする収集点を埋める)ことに方向転換するか、直接ドメイン側の能動攻撃に方向転換する。セッションハイジャックは「高権限ユーザーがその場にいる」ことに依存する。誰もいなければ期待せず、能動経路に戻る。

### 非ドメイン(workgroup)独立ホストの権限昇格の考え方の違い
**Q1**: このマシンが workgroup 独立機でドメイン不参加。権限昇格の考え方を変える必要があるか?
**A1**: 変える必要がある。ドメインがなければ、Kerberoast/ADCS/DCSync というドメイン側の近道がなく、重心は全て本機に置かれる:設定ミス(サービス/タスク/AlwaysInstallElevated)、単点特権、カーネル/サードパーティ脆弱性、本機認証情報。攻撃面は狭まるが、より集中する。
**Q2**: workgroup マシンの認証情報価値をどう評価するか?
**A2**: ローカルアカウントのパスワードが他の workgroup マシンで再利用されているかを見る。独立機は同じローカル管理者パスワードで一括配備されることが多い(LAPS なしではなおさら)。本機の admin hash を取って同セグメントを PtH スキャンすると、一撃で複数台を取れることが多い。
**Q3**: 本機の権限昇格が行き詰まり、ドメインも借りられない。横展開は何によるか?
**A3**: ローカル認証情報の再利用 + ネットワークサービス脆弱性による。方向転換:本機の SAM/LSASS 内のローカル認証情報を取って隣接機を PtH するか、同じセグメントの開いた利用可能サービス(SMB/RDP/データベース)を探して直接別の 1 台に入る。ドメインなしでは「認証情報再利用+サービス脆弱性」が横展開の主力である。
**Q4**: 対象がこの孤立機 1 台だけで、パスワードも再利用されず、サービスにも穴がない場合、完全に無路か?
**A4**: 最も基本的な判定基準に戻る:情報の盲区を再スキャンし(「全線失敗」の連鎖参照)、権限昇格が本当に必要かを再評価する。戦利品が現在の権限で既に取れるなら、直接データを取って終了する。孤立機は本機面を尽くした後、権限昇格の限界価値とタスク目標を再較正すべきである。
