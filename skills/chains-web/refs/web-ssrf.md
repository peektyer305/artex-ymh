# Web · SSRFの探査と内部ネットワーク攻撃

### 怪しいパラメータを見つけたら、SSRF 入口かを判断する
**Q1**: ページに URL を食べるパラメータがある(画像取得、webhook、リモートファイルインポート、PDF 描画、共有プレビュー)。サーバー側リクエストを発起できるかをどう判断する?
**A1**: まず「外向き通信できるか」の判定基準を確立する。自分が制御する帯外チャネル(HTTP ログ監視 / DNS 記録サーバー)に向け、サーバーが能動的に接続してくるかを見る。判定基準は三層だ。DNS は解析されるが HTTP がない(ドメイン解析だけしたか、出口ファイアウォールが TCP を遮った)、HTTP も到達する(完全な外向き通信 SSRF)、何もない(純粋なフロントエンドロードかパラメータが消費されない)。帯外命中前に結論を下さない。
**Q2**: 帯外で DNS は受けたが HTTP を受けない。廃棄か?
**A2**: 廃棄ではない。DNS-only は往々にして、サーバーが解析後に内部プロキシを経由したか出口壁に遮られたことを意味する。このとき価値は「盲 SSRF で内部ネットワークを打つ」に転じる。対象は内部ネットワークドメインを解析でき、内部ネットワーク IP に TCP を送れるが、エコーが取れないだけだ。時間差(内部ネットワークの生存ホスト vs 不存在ホストのレスポンス遅延)でブール探査する。
**Q3**: DNS すらない場合は?
**A3**: パラメータが本当にサーバーに消費されるかを検査する。file://、gopher://、dict:// などの scheme に替えてエラー情報が変わるかを見る。レスポンス時間、Content-Type、エラースタックを観察する。パラメータがフロントエンドで連結されるだけで、サーバーが決して fetch しないなら、その点を諦める。
**Q4**: 外向き通信を確認した。次の核心の判定基準は?
**A4**: 「内部ネットワークに触れるか」を判定する。それで内部ネットワーク保留セグメントのゲートウェイ、クラウドメタデータアドレス、localhost の高位ポートをリクエストし、レスポンス長/ステータスコード/時間の差異で内部ネットワーク到達可能性を判断する。外向き通信≠内部ネットワーク到達。多くの対象は出口が公衆ネットワークへ通るが内部ネットワークが隔離されている。
**Q5**: この SSRF が完全に WAF に塞がれた。どこへ転じる?
**A5**: 直交次元に転じる。この一つのパラメータに固執しない。同じアプリで SSRF 入口は通常群をなして現れる(アバター URL、リッチテキストのリモート画像、oembed、SSO コールバック、XML 外部エンティティ)。機能点を替えて再測する。往々にして一つはフィルタ未適用だ。それも駄目なら XXE/CRLF 注入など、外向きリクエストを間接的に誘発できる原語を探す。
**Q6**: 判定基準で「TCP を打てる」と「HTTP しかできない」を区別すべきか?
**A6**: すべきだ。http(s) scheme だけをサポートしポートも制限されれば、打てる面が非常に狭い。gopher/dict をサポートすれば任意の TCP payload を構成できる(Redis/MySQL/内部 HTTP API を打つ)。先に scheme ホワイトリストの境界を探る。これが後続の武器化経路を決める。

### クラウド環境で SSRF は優先してメタデータサービスを打つ
**Q1**: SSRF の外向き通信を確認し、対象が公有クラウド上だ。第一に何をすべきか?
**A1**: クラウドメタデータエンドポイントを打つ(各公有クラウドは固定のリンクローカルアドレスでメタデータ HTTP API を晒し、ベンダーごとにアドレスが異なる)。SSRF の収益が最も高い単点だ。一時認証情報、インスタンスロール、ユーザーデータスクリプトを取れる。まずメタデータルートパスをリクエストしてサービス存在を確認し、それから層ごとに列挙する。
**Q2**: メタデータサービスが 401 を返すかトークンを要求する(IMDSv2)?
**A2**: IMDSv2 は先に PUT で token を取り、token 付きで GET し、且つ既定で hop 数を制限する。純 GET 型 SSRF は打てない。このとき SSRF が PUT を送りカスタムヘッダを付けられるかを判断する。多くの SSRF はできないので、同機に到達できる他の内部サービスを探すか、旧版 IMDSv1 がまだ動くインスタンスを探す方向に転じる。
**Q3**: メタデータのリンクローカルアドレスへの文字列ブラックリストをどう迂回する?
**A3**: IP 表記法の変形(十進整数、十六進、8 進、IPv6 マップ)、DNS リバインディング、そのアドレスに解決される自分のドメインを指す、URL パーサ差異(userinfo@、多重スラッシュ、#、? の混乱)。核心の発想は「アプリ層検証の host」と「下層が実際に接続する host」を不一致にすることだ。
**Q4**: 一時認証情報を取った後、どう検証し増幅する?
**A4**: まず認証情報で身元照会 API を呼んで身元と権限境界を確認し、それが触れるストレージ/鍵/コンピュート資源を列挙する。急にデータを動かさず、先にロール権限を把握し、高騒音操作でアラートを誘発しない。
**Q5**: このクラウドが馴染みのないベンダーで、メタデータアドレスが不明だ?
**A5**: クラウドベンダー識別に転じる。レスポンスヘッダ、TLS 証明書、IP 帰属、DNS PTR を見る。クラウドごとにメタデータアドレスとパス構造は異なるが、やり方は同じだ(すべてリンクローカルアドレス+HTTP API)。ベンダー識別後、対応するメタデータパス辞書を当てる。
**Q6**: メタデータが打てず、内部ネットワークも隔離された。SSRF に何の使い道がある?
**A6**: 情報利用に転じる。コンテナ/オーケストレーションプラットフォームの service account token パスを読む(SSRF がファイルを読めるか、kubelet/API server にアクセスできるか)、同一 VPC 内の内部 API ゲートウェイを探る。クラウド上の SSRF の価値はメタデータだけではない。横方向の内部マイクロサービスも同様に価値がある。

### エコーあり SSRF と盲 SSRF の攻め方の分流
**Q1**: エコーありかブラインド攻撃かを先に判断し、武器を選ぶには?
**A1**: 自分が制御し、固定のマーク文字列を返すページをリクエストさせ、アプリのレスポンスにその内容がそのまま返るかを見る。返る=エコーあり(内部ネットワーク HTTP を直接読める)。返らないが帯外にリクエストがある=盲。この分流が後の全構築方式を決める。必ず先に定性する。
**Q2**: エコーあり時、内部ネットワークをどう高効率に探る?
**A2**: SSRF を内部ネットワーク HTTP プロキシとして使う。内部ネットワーク各ホストの一般的なポートパスをリクエストし、直接返りを読む。管理バックグラウンド、監視パネル、レジストリセンター、CI、オブジェクトストレージコンソールのような「無認証内部ネットワークサービス」を優先して探る。エコーあり SSRF の内部ネットワーク Web 攻撃は効率が極めて高い。
**Q3**: 盲 SSRF で内部ネットワーク構造をどう問い出す?
**A3**: 差異化オラクルを使う。レスポンスステータスコード、レスポンスボディ長、レスポンス時間の三つから一つをブールチャネルにする。ポート開放 vs 閉鎖の接続時間差、接続できる vs 拒否のエラー差で、逐ビットで生存ホストと開放ポートを列挙する。遅いが実行可能だ。
**Q4**: ブラインド攻撃で差異が非常に小さく、ノイズが大きく、ブールチャネルが不安定だ?
**A4**: 差異の増幅に転じる。明らかな時間分岐を作る探査を選ぶ(filtered ポートに接続するとタイムアウトまで hang し、refused は即返る)。あるいは帯外戻りのあるプロトコルを打つ(内部ネットワークサービスにこちらのリスナーへ逆接続させる)ことで「盲」を「半盲」に変える。
**Q5**: 完全に盲で、帯外も時間差もなく、ほぼチャネルがない。どこへ転じる?
**A5**: 攻撃面に転じるのであって盲探査を続けない。盲 SSRF の高価値経路は「エコー不要で副作用を起こせる」内部ネットワークサービスを直接打つことだ。内部メッセージキュー/Redis/webhook へ書操作を投げる、内部サービスの一度きり動作(リセット、制御可能なアドレスへのエクスポート)を誘発する。目標を「情報を読む」から「状態を変える」に変える。
**Q6**: ブラインド攻撃で命中した内部ネットワークサービスが具体的に何かをどう判断する?
**A6**: プロトコルフィンガープリントで逆算する。同一ポートに異なる scheme(http vs gopher の裸バイト)を送り、どちらがエラーにならず、どちらが特定の挙動を誘発するかを見る。一般的なポート約束(キャッシュ、データベース、レジストリセンター、検索エンジンの典型ポート)と合わせて推測を絞る。

### gopher/dict で SSRF を任意 TCP 打点に格上げする
**Q1**: SSRF が gopher をサポートすると確認した。内部ネットワークに未認可のキーバリューキャッシュサービスがある。SSRF をどう RCE に変える?
**A1**: gopher は裸の TCP バイトストリームを送れる。発想は、そのサービスのネイティブプロトコルコマンドを gopher URL にエンコードし、サーバーにこちらの代わりに内部ネットワークへこの payload を送らせることだ。キーバリューキャッシュ系では、典型的な武器化はスケジュールタスク書き込み/webshell 書き込み/SSH key 書き込みの三経路で、そのサービスの実行身元と書き込み能力に依存する。
**Q2**: gopher payload を構築するとき最も踏みやすい穴は?
**A2**: 改行と URL エンコードだ。多くのサービスプロトコルは \r\n に敏感で、gopher 内で正確に二重エンコードする必要がある。またアプリ層が URL をさらに一度デコードし、二重エンコードのずれを起こし得る。先にローカルで同じサービスを立てて gopher で通し、その後で真目標に送る。盲構築しない。
**Q3**: 対象が http scheme だけを許可し、gopher が ban された?
**A3**: CRLF 注入経路に転じる。URL の host/path に \r\n を注入できれば、HTTP リクエストに追加行を挟み、行ベースで且つ前導ゴミを許容するサービス(キャッシュ、メールなど)に同様にコマンドを配信できる。あるいは dict/ftp など半制御バイトを送れる他の scheme を探す。
**Q4**: 内部ネットワークデータベース(MySQL/PG など)は認証ハンドシェイクが必要で、gopher の一方向ストリームで行けるか?
**A4**: 難しい。認証ハンドシェイクのあるプロトコルは多ラウンド対話が必要で、一方向 gopher は通常打てない。判定基準は「プロトコルが server-first か、チャレンジレスポンスが必要か」だ。必要な場合は、無認証かプロトコルが寛容な目標(キャッシュ、検索、レジストリセンター)に転じるか、多ラウンドできる SSRF(返りを読んで継続発信)を探す。
**Q5**: payload を送ったがサービスが無反応だ。どう切り分けする?
**A5**: 層ごとに特定する。まず TCP 到達を確認する(帯外か時間差)、次にバイトの完全性を確認する(ローカルで対照)、最後にコマンド意味を確認する(権限/パス)。一気に payload 内容を疑わない。多くはエンコードかポートが通っていないことが原因だ。
**Q6**: この TCP 武器化が全体として失敗した。戦略的にどこへ転じる?
**A6**: SSRF を偵察ツールとして使うことに戻す。RCE できなくても、それは依然内部ネットワーク地図の描画器だ。既に判明した内部ネットワークサービスリストを他の原語(取った認証情報、見つけた他の脆弱性)に渡して打つ。SSRF は「見る」を担い、他が「打つ」を担う。

### SSRF が内部ネットワークに入った後、どう内部ネットワーク地図を描くか
**Q1**: 安定してエコーする SSRF を持つ。内部ネットワークのホストとサービスを把握したい。どこから始める?
**A1**: まず自分がどのネットワークセグメントにいるかを特定する。本機の複数 NIC アドレス、一般的なゲートウェイ、DNS サーバーをリクエストし、メタデータやエラー情報から内部ネットワーク IP セグメントを抜き出す。セグメントを確定してから横にスキャンする。誤ったセグメントで探査を浪費しない。
**Q2**: SSRF 経由のポートスキャンが遅すぎる。どう高速化する?
**A2**: 層に分けてスキャンする。先に「各マシンが高確率で開く少数の高価値ポート」(Web 管理、レジストリセンター、キャッシュ、DB)をスキャンして、素早く生存ホストを丸で囲む。その後生存ホストを深くスキャンする。セグメント全体を全ポート総当たりスキャンすると、遅すぎ且つ騒音が巨大になる。
**Q3**: 開放ポートを大量にスキャンで出した。どれを先に打つ?
**A3**: 「未認可+高権限」で並べる。内部ネットワークサービスの既定未認証の比率は非常に高い。レジストリセンター/設定センター(全量のサービス設定と鍵を読める)、CI/成果物ライブラリ(毒を盛れる)、監視とオーケストレーションパネル(実行できる)、オブジェクトストレージコンソール。低コスト高リターンの未認可面を優先する。
**Q4**: SSRF が GET しかできず、多くの内部ネットワークサービスが POST/特定ヘッダを必要とする。地図が描けない。どうする?
**A4**: scheme 格上げ(gopher で body とヘッダ付きの完全な HTTP を構成)に転じるか、より能力の強い SSRF 入口を探す。どちらも駄目なら、GET で読める情報(バージョン、設定、サービス名)を最大限に搾り、後続の攻撃チェーンに渡す。
**Q5**: 内部ネットワーク DNS が解析できる。IP でなくホスト名でスキャンすべきか?
**A5**: すべきだ。SSRF に内部ネットワークドメインを解析させれば、命名規則(サービス名、環境識別子)を得られることが多く、裸 IP より速く高価値目標を特定できる。一般的な内部サブドメイン辞書も試す。DNS 視点と IP 視点は直交で、両方使う。
**Q6**: 地図を半分描いたところで SSRF 入口が修復/無効化した。地図が未完成だ。どうする?
**A6**: 即座に既存情報を固定し、持続的な足場を探す。途中で SSRF を通じて認証情報か別の到達可能な入口を得ていれば、優先してそれでこの SSRF に依存しないチャネルを確立する。単点 SSRF はいつでも消え得る。早く「一時的到達」を「安定チャネル」に変えるほど良い。

### SSRF で内部ネットワークの未認可 Redis / キャッシュサービスを打つ
**Q1**: 内部ネットワークに未認可のキーバリューキャッシュサービスを探り当てた。SSRF で何ができる?
**A1**: まず可書を確認する(key を一つ読み、テスト key を一つ書く)。可書なら三つの古典的な足場確保経路の一つを進む。判定基準はサービスの実行身元とファイルシステム権限だ。高権限ならシステムのスケジュールタスクディレクトリに書ける、web ディレクトリに書けるなら webshell を落とす、対象マシンが SSH を開いているなら authorized_keys を書く。経路を選ぶ前に、それがどこに書けるかを先に探る。
**Q2**: 三経路のどれが実行可能かをどう素早く判断する?
**A2**: パスの可書性と身元を探る。データ書き込みディレクトリを変えられるか(dir/dbfilename 系設定)、web ルートパスが既知か、SSH がリスンし且つホームディレクトリが可書か。最もリスクの低い一本を優先する(SSH key を書くのは通常システムファイル上書きより安全)。情報不足なら先に読取専用で偵察し、構造を破壊する書き込みをしない。
**Q3**: gopher を打ってもコマンドが効かない。どこが誤っている可能性がある?
**A3**: よくあるのは、プロトコル区切り文字のエンコード、サービスが保護モードを開いて外部の危険コマンドを拒否、あるいはそれがスレーブで読取専用だ。逐一調べる。先に無害な読コマンドを送ってチャネルが通ることを確認し、次に設定照会で権限を確認し、最後に書コマンドを送る。
**Q4**: このキャッシュサービスに実は認証がある/保護モードが開いている。書けない。どうする?
**A4**: 読取利用に転じる。書けなくても、キャッシュには session、内部 token、業務の機密データが眠ることが多い。読めば直接セッションか認証情報を得て横移動できるかもしれない。目標を「足場確保 RCE」から「認証情報窃取」に変える。
**Q5**: サービスがコンテナ内にあり、ファイルを書いてもコンテナから出られない。打つ価値がある?
**A5**: ある。ただし期待を調整する。コンテナ内 RCE も依然内部ネットワークの足場で、さらなる SSRF/スキャン/認証情報収集に使える。深入りする価値はコンテナのネットワーク位置とマウント(ホストディレクトリのマウント、service account token の有無)に依存する。先にコンテナエスケープ面を列挙してから決める。
**Q6**: キャッシュ利用チェーン全体が通らない。この発見を横方向にどう使う?
**A6**: 「内部ネットワークに未認可キャッシュが存在する」ことを情報とし、その組織の内部ネットワークセキュリティ基線が全般に緩いと推測する。平行して同類の未認可サービス(他のキャッシュインスタンス、レジストリセンター、DB)を探す。未認可を一つ見つけると、往々にして一群がある。戦果面を広げ、この一インスタンスに固執しない。

### CRLF 注入と SSRF の組み合わせで scheme 制限を突破する
**Q1**: SSRF は http だけを許可するが、URL 連結箇所に \r\n を注入できるとわかった。これで何ができる?
**A1**: CRLF で、サーバーが発する HTTP リクエストに追加のリクエストヘッダ、さらにはリクエスト全体を注入できる。内部ネットワークサービスを指すリクエストの密輸、Host ヘッダ注入でルーティング迂回、行ベースの内部ネットワークプロトコル(SMTP/キャッシュ)へのコマンド配信に使える。まず注入点がリクエスト行かヘッダかを確認し、何バイト制御できるかを把握する。
**Q2**: CRLF が本当に外向きリクエストに注入されたかをどう判断する?
**A2**: カスタムヘッダを一つ注入し、リクエストを自分のリスナーに当て、そのまま現れるかを見る。帯外で注入ヘッダが見えれば=成立。見えなければ正規化フィルタされたので、エンコードを替える(%0d%0a、%0a、Unicode 変種、二重エンコード)して再試行する。
**Q3**: 壁に当たった。\r\n がフィルタか正規化された。どうする?
**A3**: リクエスト密輸/ヘッダ注入を起こせる他の原語に転じる。HTTP パラメータ汚染、URL パーサ差異(ライブラリごとに @ / # / \ の扱いが違う)、あるいはネイティブに gopher をサポートする入口を探す。CRLF は「外向きバイトを制御する」多くの手段の一つにすぎない。
**Q4**: 注入は成功したがヘッダしか足せず、body を変えられない。POST が必要な内部ネットワークサービスを打てるか?
**A4**: 限定的だ。ヘッダしか制御できないなら、GET+ヘッダで副作用を誘発できるサービスを優先して打つか、注入で内部ネットワークへの完全な第二リクエストを構築する(リクエスト密輸式)。body が必要な目標は gopher 経路に転じる。
**Q5**: 内部ネットワークサービスが不正な前導に寛容でなく、注入したゴミで接続がリセットされる。どうする?
**A5**: 寛容な目標を選ぶ。行ベース、逐行解析、未知の前導を無視するプロトコル(一部のキャッシュ、メールサービス)は厳格な HTTP サービスよりこの手を食べやすい。payload でなく対象ポートを替える。
**Q6**: CRLF のこの道が完全に無果だ。戦略的に転じる?
**A6**: 「アプリ層検証 vs 下層接続の不一致」という母題の他の分岐に戻る。DNS リバインディング、リダイレクト追従(アプリにまずこちらの制御する 301 をリクエストさせ、それから内部ネットワークへジャンプ)、IP エンコード難読化。CRLF は迂回手段の一つで、通らなければ直交する迂回に替える。

### 302 リダイレクトに依存して SSRF の host ホワイトリストを迂回する
**Q1**: SSRF がホワイトリストドメインへのリクエストだけを許すが、リダイレクトを追従すると疑う。どう利用する?
**A1**: ホワイトリストが許し、こちらが制御できるアドレスで、内部ネットワーク/メタデータアドレスへ 30x ジャンプを返す。アプリが初回ジャンプでしか host を検証せず、リダイレクト追従時は検証しないなら、迂回できる。先に追従するか、何ジャンプ追従するかを測る。
**Q2**: 追従し且つ追従後に検証しないことをどう確認する?
**A2**: 第一ジャンプで「自分の別の帯外アドレス」へ戻して追従を確認し、第二ジャンプを内部ネットワークに向けて本当の探査をする。二段に分けて検証する。先に追従挙動を証明し、次に目標到達を証明する。一段で済ませず、失敗の所在を特定しやすくする。
**Q3**: リダイレクトを追従するが、Location の host も検証する。どうする?
**A3**: DNS リバインディングに転じる。ホワイトリスト/検証を通るドメインを「検証時」に正当 IP に解決させ、「実際のリクエスト時」に内部ネットワーク IP に解決させる(TTL ゼロ+二重 A レコード交代)。検証と使用の間の時間窓を攻める。
**Q4**: アプリが同源/同ドメインのリダイレクトしか追従しない。どう破る?
**A4**: プロトコル内ジャンプの境界を試す。相対 Location、ホワイトリストドメインの不正なサブパスへのジャンプ後に二次 SSRF、あるいはオープンリダイレクトとの組み合わせ。ホワイトリストドメイン自身に open redirect があれば、それで正当に内部ネットワークへジャンプする。対象ドメインの open redirect を足がかりにする。
**Q5**: リダイレクトもリバインディングも全て防がれた。host 検証を迂回する他の道は?
**A5**: URL パーサ差異という直交面に転じる。検証に使う解析ライブラリとリクエストを送るライブラリが `http://allowed@internal/`、`http://internal#allowed`、`http://allowed\@internal` などの host 抽出で一致しない。逐一 fuzz して解析の分岐を探す。
**Q6**: 全ての迂回が失敗した。この点は救えないか?
**A6**: 点を替える。同一対象の他の SSRF 入口は検証が弱いかもしれない。あるいは攻撃種別を替える。ホワイトリストが極めて厳格な SSRF は収益が低く、精力を別の攻撃面(デシリアライズ、認証欠陥)に投じるほうが良い。タイムリーな損切りはレッドチームの規律だ。

### DNS リバインディングで「検証時合法、使用時内部ネットワーク」を破る
**Q1**: SSRF が host 検証をし、検証後すぐ同じ URL でリクエストを送る。時間窓がないように見える。DNS リバインディングはまだ打てるか?
**A1**: 鍵は「検証解析」と「リクエスト解析」が同一の DNS クエリかだ。アプリが先に resolve して検証し、下層ライブラリに再び resolve させてリクエストを送るなら、二回のクエリがあり、窓が存在する。極低/ゼロ TTL のドメインで、二回の解析に異なる IP を取らせる。先に二次解析するかを測る。
**Q2**: 二次解析をするかをどう判断する?
**A2**: 毎回異なる結果を返す権威 DNS(正当 IP と内部ネットワーク IP を交代)を使い、複数リクエストのうち内部ネットワーク命中の兆候(レスポンス差異)があるかを観察する。命中すれば二次解析窓の存在を証明する。
**Q3**: アプリが DNS 結果をキャッシュするか一度しか解析しない。リバインディングが無効化した。どうする?
**A3**: 時間窓に依存しない迂回に転じる。直接の IP エンコード難読化(検証に内部ネットワーク IP を公衆ネットワークと誤判定させる)、あるいは DNS をせず文字列ホワイトリストだけの弱い検証を探す。リバインディング失敗は通常、検証がかなり規範的なことを示す。検証ロジック自体の解析脆弱性を攻める方向に変える。
**Q4**: リバインディングの命中窓の確率が低すぎ、不安定だ。成功率をどう上げる?
**A4**: 交代命中率を上げる。TTL を 0 に短縮、リクエスト頻度を上げる、複数 A レコードで OS に二回の接続間で交代させる。あるいはアプリに同一 URL への複数リクエストを誘発させる(一部の機能はリトライする)。リトライ回数が多いほど命中が安定する。
**Q5**: 制御可能な権威 DNS がまったくない。リバインディングをどう素早く組む?
**A5**: 既成のリバインディングサービスを使う(公開の rebinding-as-a-service ツールが交代 A レコードのドメインを提供)。自分のインフラを組めないとき、まず公開ツールで実現可能性を検証し、それから自前構築するかを決める。
**Q6**: この仕組みが完全に通らない。どこへ転じる?
**A6**: 対象の SSRF host 検証が非常に成熟していることを示す。「host 検証を通らない外向き」に転じる。XXE、PDF/画像レンダラ内のリモート資源埋め込み、SVG の外部参照、Markdown のリモート画像。これらは往々にして別のコード経路で、SSRF の検証が掛かっていない。
### XXE を SSRF とファイル読取の二重原語として使う
**Q1**: 対象に XML アップロード/解析入口がある。SSRF として使えるかをどう判断する?
**A1**: 先に外部エンティティが解析されるかを測る。自分の帯外アドレスを指す外部エンティティを定義し、サーバーが接続してくるかを見る。来れば=SSRF として使える(内部ネットワークへ HTTP/他 scheme を発起できる)。同時に file:// でローカルファイルも読めることが多い。一つの入口で二つの原語だ。
**Q2**: パーサがエンティティ内容をエコーしない(盲 XXE)。ファイルをどう読む?
**A2**: OOB 持ち出しを進む。パラメータエンティティ+外部 DTD で、読んだファイル内容を自分のサーバーへ送る URL に連結する。あるいはエラー型 XXE で、ファイル内容を解析エラーメッセージに出す。盲 XXE は帯外チャネルに頼り、直接エコーではない。
**Q3**: 外部エンティティが無効化された(安全パーサ)。どうする?
**A3**: 他の XML 関連面に転じる。パラメータエンティティがまだ開いているか、XInclude をサポートするか、SOAP/SAML など XML を食べる入口(設定が緩いことが多い)を探す。あるいは、エンティティは禁だが DTD のネットワークロードが禁でなければ、この点を純 SSRF として使う。
**Q4**: SSRF できるが http しかサポートせず、ファイルを読めない。逆に SSRF だけにできるか?
**A4**: できる。しかも XXE の SSRF は往々にしてアプリ主 SSRF の防御に制約されない(別の解析経路)。それを「host 検証を迂回した清潔な SSRF 入口」として内部ネットワークとメタデータを打つ。価値はファイル読取より低くない。
**Q5**: 内容に & % < などの文字があり、外部 DTD の構築が失敗する。どう切り分けする?
**A5**: これは XXE の古典的な穴だ。一部の文字がエンティティのネストを壊す。外部 DTD でパラメータエンティティを分離し、データを二次エンティティで包む、あるいは CDATA/エラーチャネルで文字制限を回避する。先にローカルパーサで構築を再現してから目標を打つ。
**Q6**: XXE 全体が通らない(全禁)。この XML 入口にまだ価値があるか?
**A6**: XML 層の他の攻撃に転じる。Billion Laughs(DoS は通常打たない)、SAML 署名迂回(認証 XML なら)、XPath/XSLT 注入。どれも駄目なら、この入口が閉じたと認め、リモート URL を食べる他の機能で SSRF を探す。

### SSRF が内部ネットワーク HTTP サービスに命中した後のフィンガープリントと経路選択
**Q1**: SSRF のエコーで内部ネットワークサービスのホームページを読んだ。それが何か、打つ価値があるかをどう素早く判断する?
**A1**: フィンガープリントを取る。レスポンスヘッダ(Server/X-Powered-By/フレームワーク特徴ヘッダ)、タイトル、favicon ハッシュ、特定パスの存在性、エラーページの傾向。フィンガープリントがどの既知利用を使うかを決める。ホームページだけで推測せず、情報量の高いパスをいくつか探って身元を確認する。
**Q2**: フィンガープリントが管理機能付きの内部プラットフォームを示した。次は?
**A2**: 優先して未認可アクセスを探る。多くの内部ネットワーク管理プラットフォームは既定で無認証か弱いパスワードだ。まずその管理/API パスを直接アクセスしてログインが必要かを測る。無認証なら実行可能な機能(タスクスケジューリング、スクリプト実行、設定変更)へ直行する。
**Q3**: 認証が必要だが SSRF は匿名 GET しか送れない。入れない。どうする?
**A3**: そのプラットフォームの未認可 API エンドポイントを探す(管理プラットフォームには個別に認証・認可を漏らした API がありがち)、あるいは既知の未認可/事前認証の脆弱性を版フィンガープリントで照合する。SSRF で内部ネットワーク Web を打つ突破口は「防備のないある子 API」にあることが多い。
**Q4**: POST + 認証ヘッダが必要で、GET 型 SSRF では全く届かない。どうする?
**A4**: SSRF 能力を格上げする(gopher でヘッダと body 付きの完全な HTTP リクエストを構成)。格上げできないなら、この高価値目標を記録し、より強い入口か認証情報を得てから戻る。能力不足のとき硬く消耗しない。
**Q5**: 読んだレスポンスが文字化け/バイナリだ。フィンガープリントが取れない?
**A5**: 非 HTTP サービスか TLS サービスを HTTP としてリクエストした可能性がある。scheme を替える(https、gopher 経由の生 TCP)、ポートを替えて再試行する。文字化け自体が信号で、このポートが平文 HTTP でないことを示す。バイナリプロトコルサービスとして扱う。
**Q6**: この内部ネットワークサービスに利用価値がないと確認した。今回の偵察をどう無駄にしないか?
**A6**: それでネットワークセグメントの用途を逆算する(データベースセグメント、管理セグメント、業務セグメントか)、後続のスキャン優先順位を調整する。単一サービスが無価値でも、内部ネットワークトポロジ上の位置は情報で、次のどのセグメントをスキャンするかを導く。

### 出口がファイアウォールに制限され、特定の内部ネットワーク目標しか打てないと判断する
**Q1**: SSRF の外向き通信は正常だが、大半の内部ネットワーク IP を打つとタイムアウトし、個別だけが通る。どう理解する?
**A1**: サーバーに出口/東西方向ファイアウォールがあり、特定の内部ネットワーク目標への接続だけを許可していることを示す。これらの「通る少数の目標」は、業務が本当に依存するサービス(許可せざるを得ない)で、価値がむしろ高い。通るホワイトリスト目標を重点研究対象にする。
**Q2**: 許可された内部ネットワーク目標をどう体系的に探す?
**A2**: 時間差で一括探査する。ファイアウォールに drop されたものはタイムアウト、許可されたがサービスが閉じているものは速やかに refused、許可され且つサービスが開いているものは正常応答。三状態の区別で「ファイアウォール許可」のアドレス空間を丸で囲み、深掘りする。
**Q3**: 通る目標が脆弱性のないヘルスチェックポートばかりで、利用価値がない?
**A3**: 発想を変える。ヘルスチェックポートのあるホストは、他のポートも開いていることが多い。ただそのポートは SSRF ホストのファイアウォールに許可されていない。しかし「そのホスト自身」には許可されているかもしれない。そのホストに一点落とせれば、それを足がかりに自分の他のポートを打てる。目標を「直接打つ」から「足がかりを探す」に変える。
**Q4**: このファイアウォールがメタデータアドレスも遮り、クラウド認証情報経路が断たれた。どう転じる?
**A4**: 許可された内部サービス内で認証情報を探す。業務サービスの設定 API、レジストリセンター、ログサービスにはハードコードされた内部認証情報がよくある。ファイアウォールはメタデータを遮るが、業務サービス自身が漏らす鍵は遮れない。
**Q5**: ファイアウォールが IP でなくドメインで許可すると疑う。どう検証し利用する?
**A5**: ホスト名リクエスト vs IP リクエストを比較する。ドメインが通り、同じ IP の直結が通らなければ、SNI/Host で許可している。ならば必ず許可されたドメインを使って攻撃を担わせる(そのドメインをリバインディング、そのドメイン下の利用可能パスを探す)。
**Q6**: 出口制限が厳しすぎ、到達できる高価値目標がほぼない。戦略的に転じる?
**A6**: この SSRF の内部ネットワーク攻撃の ROI が低いと認め、純偵察/帯外検証ツールに降格する。主攻方向をアプリ自身の他の脆弱性(認証、注入、ロジック)か、既に得た足場でのローカル権限昇格と横移動に転じる。

### SSRF が認証情報を得た後、「外部ブラインド攻撃」から「認証情報付き横移動」へ
**Q1**: SSRF(メタデータ/内部ネットワーク設定)でクラウド/内部ネットワーク認証情報を一つ得た。SSRF を使い続けるか、姿勢を替えるか?
**A1**: 替える。SSRF は制限され、一方向で、失われやすいチャネルだ。認証情報を得たなら、それで正常な API チャネルで横移動でき、能力がはるかに大きく安定する。判定基準: 認証情報で SSRF を離れて直接目標にアクセスできるか。できれば転じ、SSRF は予備の偵察として残す。
**Q2**: 認証情報の権限が不明だ。安全に境界を探るには?
**A2**: まず読取専用の身元/権限自己点検(who am I、アクセス可能資源の列挙)をし、段階的に試す。いきなり削除/変更系の高騒音操作をしない。境界を探る原則は低権限の読取専用動作から始めて広げ、どれが拒否されるかを観察する。
**Q3**: 認証情報が一時的で、すぐ失効する。横移動が間に合わない?
**A3**: 優先して二つのことをする。一つはより持続的な認証情報を取る(新しい key を作る、自分にロールを加える、長期 secret を読む)。もう一つはそれに依存しないチャネルを確立する(到達可能なホストに点を落とす)。一時認証情報の第一要務は「持続的な足場に換える」ことだ。
**Q4**: 認証情報の権限が極めて低く、ほぼ何もできない。無駄に取ったか?
**A4**: 必ずしも無駄ではない。低権限認証情報もメタデータを読め、資源リストを列挙でき、一部の内部 API にアクセスできることが多く、これらは横移動の地図だ。それを「内部ネットワーク視野の拡張器」として使い、直接の攻撃ツールではない。それで偵察してより多くの攻撃可能目標を探す方向に転じる。
**Q5**: 認証情報で操作すると即アラート/禁止される。どうする?
**A5**: 行動監視があることを示す。低頻度、リアルな操作に転じる。正常な業務呼び出しパターンを模す、時間をずらす、必要な動作だけをする。継続的に封じられるなら、SSRF チャネルに戻って無認証情報の静かな偵察をし、より隠密な利用経路を再計画する。
**Q6**: 認証情報がまったく使えない(IP 束縛/条件付きアクセスがある)。どう転じる?
**A6**: 認証情報が送信元 IP/条件を制限するなら、信頼される位置から使う必要がある。つまり SSRF のいるサーバー環境に戻って使う(そのマシンに点を落としてローカルで認証情報を使う)。認証情報の価値は「どこから使うか」に依存する。先に信頼できる実行位置を取る方向に転じる。

### SSRF と「フロントエンドクロスドメインプロキシ」という偽 SSRF を区別する
**Q1**: URL を食べる API がこちらの帯外に接続してきたが、実はフロントエンド/CDN プロキシで真の SSRF でないと疑う。どう見分ける?
**A1**: 鍵の判定基準: リクエスト源 IP が対象サーバーの内部ネットワーク出口か。帯外が受けた接続 IP の帰属を見る。対象サーバー IP/そのクラウド出口=真 SSRF。CDN/公開プロキシ/ユーザーブラウザ IP=偽 SSRF(内部ネットワーク価値なし)。「戻りがある」に騙されない。
**Q2**: 源 IP が CDN だ。まだ救える?
**A2**: 部分的には。CDN 回源プロキシなら、CDN 自身の内部ネットワーク管理面/メタデータをリクエストさせられるかもしれない(CDN ノードもサーバー)。しかし多くの場合、対象の内部ネットワークは打てず、価値が限られる。判断して果断に降格する。
**Q3**: 対象の内部ネットワークに触れられるか(公衆ネットワークに出られるだけでないか)をさらに確認するには?
**A3**: 対象の内部ネットワーク保留アドレス/メタデータを直接リクエストさせ、差異のあるレスポンスがあるかを見る。公衆ネットワークに出られる≠内部ネットワークに入れる。この一歩が偽 SSRF と真の内部ネットワーク SSRF の分水嶺で、必ず実測する。
**Q4**: 公衆ネットワークに出られるが内部ネットワークに全く触れられない(全隔離)。この種の SSRF をどう使う?
**A4**: 用途を降格する。帯外確認ツール、匿名リクエストプロキシ(本当の送信元を隠して第三者を打つ)、対象の出口 IP を探る手段として使う。内部ネットワークに触れない SSRF にも周辺価値はあるが、内部ネットワーク攻撃の主線にはせず、別の入口へ転じる。
**Q5**: 色々見分けて、ブラウザ端の fetch(SSRF の幻覚)だとわかった。どう素早く損切りする?
**A5**: リクエストがブラウザ特徴(UA、Origin、CORS プレフライト)を持つか、源 IP が訪問者自身かを調べる。そうなら即座に SSRF として打つのをやめ、クライアント問題(CSRF/オープンリダイレクト方向か)に再分類する。定性をタイムリーに正して浪費を避ける。
**Q6**: 真の SSRF と確認したが、源 IP が馴染みのないホスティングセグメントに落ちる。どう計画する?
**A6**: まずこのセグメントが対象の自前 IDC かレンタルクラウドかを把握する。それでメタデータを打つか(クラウド)、直接内部ネットワークを横スキャンするか(自前 IDC)を決める。源 IP のネットワーク帰属が内部ネットワークの攻め方を決める。先に帰属判定をしてから動く。

### SSRF が内部ネットワークを探り当てたが全サービスが認証必須の行き詰まり
**Q1**: 内部ネットワークは到達でき、サービスもいくつかスキャンできるが、どれも認証が必要で、SSRF は匿名しかできない。詰まった。どう破る?
**A1**: 発想を変えて「認証不要で情報を漏らす」面を探す。サービスのエラーページ、バージョン API、metrics/ヘルスチェックエンドポイント、swagger/api-doc、静的資源ディレクトリ。これらは認証・認可がなく、バージョン、内部パス、さらには設定や token を漏らし得る。
**Q2**: metrics/actuator 系エンドポイントを見つけた。何を搾れる?
**A2**: この種の運用エンドポイントは金鉱だ。環境変数(鍵を含む)、ヒープダンプ(メモリ内の認証情報を含む)、設定、内部サービスアドレス、さらには設定変更/操作誘発の能力を漏らし得る。優先してどの子エンドポイントが晒されているかを列挙し、逐一搾る。
**Q3**: 全サービスの未認可エンドポイントすら塞がれた。本当に見込みがない?
**A3**: 「認証機構そのもの」を攻める。内部ネットワークサービスは同じ認証を再利用することが多い。別の場所(キャッシュの session、設定の API key、別の漏えい点)から認証情報を一つ取れば、複数の内部ネットワークサービスを一括で通せるかもしれない。突破口を「サービス」から「共有認証情報」に移す。
**Q4**: SSRF が認証に使えるものを取ってくれるか?
**A4**: 取れる。SSRF に内部ネットワーク設定サービス、CI 変数、鍵管理 API(未認可なら)、あるいはファイル(file scheme 対応なら)を読ませてアプリ設定を取る。SSRF の高階用法は「内部ネットワーク自身の認証情報を読み出して」から戻って認証することだ。
**Q5**: 内部ネットワークサービスが送信元 IP ベースの信頼(内部ネットワークなら信頼)を使う。SSRF は内部ネットワーク IP と見なされるか?
**A5**: これこそ SSRF で内部ネットワークを打つ核心の見返りだ。SSRF が発するリクエストの源 IP は信頼される内部ネットワーク IP で、多くのサービスは内部ネットワークからの発信を認証免除にする。あるサービスが「外部ネットワークは認証必要、内部ネットワークは認証免除」なら、SSRF は天然にそれを満たす。この種のネットワーク位置ベースの信頼を重点的に探す。
**Q6**: 未認可面もなく、共有認証情報もない。戦略的に転じる?
**A6**: SSRF 主線を退き、本当の内部ネットワーク実行位置を得る方向に転じる(他の脆弱性で shell を取る)。「外部からの一方向探査」を「内部の双方向足場」に格上げする。認証の行き詰まりは往々にして「内部ネットワークの中に入る」ことでしか破れず、「外から突く」ではない。

### SSRF のレスポンス長/ステータスコードでブールブラインドチャネルを作る
**Q1**: 盲 SSRF で帯外はないが、アプリが内部ネットワークレスポンスの違いでわずかに異なるページを出す。これを信頼できるチャネルにどう変える?
**A1**: オラクルを較正する。まず確実に存在しない内部ネットワークアドレスと、確実に存在するもの(ゲートウェイなど)をリクエストし、両者のステータスコード/長さ/時間のベースラインを記録する。両者を最も安定して区別する次元を見つけ、それを「生存/開放」の判定基準にする。先に較正してから列挙する。
**Q2**: 三次元とも揺れ、単回判定が信頼できない。どうする?
**A2**: 複数回サンプルして統計を取る。各探査を N 回走らせ、中央値か多数決で揺れを消す。盲チャネルの信頼性は反復から来るのであって単回ではない。揺れの大きい対象はサンプル数を増やし、遅いが正確にする。
**Q3**: アプリが内外レスポンスにほぼ差異を出さない。チャネルが弱すぎる。どうする?
**A3**: 差異を作る。明らかな分岐を生む探査を使う。filtered ポートに接続するとタイムアウトまで hang する(時間差が巨大)、超長/不正 URL をリクエストして異なるエラーを誘発する。弱チャネルを強チャネルに替え、弱い信号を硬く読まない。
**Q4**: チャネルはあるが極めて遅く、内部ネットワーク全体の列挙に数日かかる。どうする?
**A4**: 目標を絞る。セグメント全体を盲スキャンせず、DNS 名辞書/一般的なホスト名で少数の高価値ホストを先に特定し、その少数の高価値ポートだけを探る。盲 SSRF は「狙い撃ち」であって「網羅的」ではない。範囲を絞るほど実行可能になる。
**Q5**: チャネルが途中でレート制限/封じられた。どうする?
**A5**: 頻度防御を誘発したことを示す。減速、セッション/送信元を替える、時間を分散する。継続的に封じられるなら、盲チャネルのコストが高すぎると認め、エコーありか帯外が使える入口を探す。帯外できる SSRF 一つが盲探査百回に勝る。
**Q6**: 全チャネル手段が不安定だ。この盲 SSRF を諦めるべきか?
**A6**: まず ROI を判定する。対象環境の価値が高いなら、強いチャネルを構築する投入に値する。周辺機能にすぎないなら、直接他の攻撃面に転じる。レッドチームは計算する。盲 SSRF は最も時間のかかる経路の一つで、強いチャネルがないとき優先して別の道を探す。

### SSRF と内部ネットワークサービスの「戻り」を組み合わせて盲を通じさせる
**Q1**: 盲 SSRF で内部ネットワークにサービスがあるのを探り当てた。逆接続させて確認しチャネルを確立したい。発想は?
**A1**: そのサービスの「指定アドレスへ能動的にリクエストを発する」機能(webhook 登録、コールバック URL、リモートへのエクスポート、ミラー同期)を探し、こちらの公衆ネットワークリスナーへ逆接続させる。SSRF がまずサービスに届き、サービスがさらにチャネルを開いてくれる。盲が半盲になる。
**Q2**: 内部ネットワークサービスの逆接続には外向き通信が必要だが、内部ネットワークが外向き通信しない。どうする?
**A2**: 「こちらが制御でき、SSRF ホストが到達できる内部ネットワークアドレス」へ逆接続させる。つまり SSRF ホスト自身か別の到達可能な点を中継にする。どこかの到達可能な位置に足場があれば、内部ネットワークサービスにそれへ接続させ、そこからさらに転送する。多ホップ中継を構築する。
**Q3**: 内部ネットワークサービスの能動的な逆接続機能が見つからない。どうする?
**A3**: 誘発式に転じる。多くのサービスは特定操作後に通知を送る/更新を引く/ライセンスを検証するために設定可能なアドレスへアクセスする。その設定をこちらに向ける(可書なら)、あるいはその更新検査を誘発する。「サービスの正常な外向き挙動」をこちらのチャネルにハイジャックする。
**Q4**: 逆接続は確立したが不安定で、断続的だ。どう強化する?
**A4**: この一時チャネルで優先して一つだけする。より安定した足場を落とす(持続的な shell をリバースする、持続的なバックドア設定を書く)。ハイジャックした外向きチャネルが長期安定すると期待せず、早く自主制御可能なチャネルに変える。
**Q5**: 全逆接続の試みが内部ネットワーク出口壁に塞がれた。完全に外向き通信なしだ。どうする?
**A5**: 持ち出しを諦め、純粋な「状態変更」の攻め方に戻る。SSRF で内部ネットワークサービスに書操作をして、こちらが別の場所から観測できる副作用を起こす(こちらに別の権限で読める共有資源を変える)。共有ストレージを「チャネル」にする。チャネルは必ずしもネットワークでなく、共有状態でもよい。
**Q6**: 共有状態のチャネルすらない。戦略的に転じる?
**A6**: これは高度に隔離された内部ネットワークだと認め、外部 SSRF だけでは深入りが難しい。他の脆弱性で「内部ネットワーク shell を先に一つ取る」経路に転じるか、既に判明した情報を納品する。隔離された内部ネットワークで外部 SSRF に固執しない。

### SSRF で内部ネットワークを打つときの隠密性と騒音制御
**Q1**: SSRF で内部ネットワークをスキャンしたいが、大量探査がアラートを誘発するのが怖い。速度と隠密をどう両立する?
**A1**: まず相手の監視成熟度を評価する(WAF の有無、異常トラフィックアラートの兆候)。高監視環境では先に小範囲で試して反応を観察する。低監視ならスキャンを開放できる。原則: 先に低騒音偵察で「相手が見ているか」を確認してから、スキャンの積極度を決める。
**Q2**: どの SSRF 探査動作の騒音が最も大きく、慎重にすべきか?
**A2**: セグメント全体の全ポート総当たりスキャン、高頻度のリバインディング命中試行、メタデータへの狂った列挙、内部ネットワークサービスの大量エラーログを誘発する不正リクエスト。これらが最もアラートしやすい。少量の高情報量探査で代替できるなら網羅的スキャンをしない。
**Q3**: 既にアラートを誘発した。どう損切りする?
**A3**: 即座に頻度を下げて手を止め、暴露程度を評価する。単なる異常トラフィックアラート(具体的利用まで特定されていない)なら、送信元/セッションを替えて冷却後に低調に続けられる。狙われて遮断されたなら、既に得た足場で隠密な横移動に転じ、騒がしい外部探査を諦める。
**Q4**: 隠密要件下でスキャンが遅すぎ、タスク窓が足りない。どうする?
**A4**: 大を掴んで小を捨てる。最も高リターンな少数目標(メタデータ、レジストリセンター、未認可管理面)だけを探り、全面網羅を諦める。隠密制約下ではレッドチームは「全面調査」でなく「正確な外科手術」をする。
**Q5**: 相手が明らかにこちらを誘導している(レスポンスが順調すぎ、目標が理想的すぎる)。ハニーポットを疑う。どうする?
**A5**: 警戒を高める。ハニーポットの特徴は、異常に開放された高価値サービス、完璧すぎる弱いパスワード、怪しい認証情報。保守的な検証に転じる。低コミットメントの動作で真偽を交差確認し、疑わしいハニーポットに本物のツール/バックドアを投入して TTP を暴露しない。
**Q6**: 隠密と進展が完全に衝突した(積極的でなければ進展なし)。どう意思決定する?
**A6**: 交戦規則と目標価値に戻る。認可が許し目標価値が高ければ、一定の騒音で進展を買うことも受け入れられる。長期潜伏系の目標なら遅くすることを選ぶ。汎用の答えはなく、目標の性質と交戦制約が決めるのであって技術の慣性が決めない。

### SSRF がファイルしか読めない(file scheme)ときの利用方向
**Q1**: SSRF が file:// をサポートするが外向き通信しない。サーバーのローカルファイルしか読めない。どう利用する?
**A1**: 優先して「権限を広げられるか内部ネットワーク視野を与える」ファイルを読む。アプリ設定(データベース/ミドルウェア認証情報)、クラウド認証情報ファイル、SSH key、環境変数ファイル、history ファイル、内部ネットワークサービスアドレス設定。ファイル読取の価値は認証情報とトポロジを読み出すことで、無作為に読むことではない。
**Q2**: アプリがどこにインストールされているかわからず、パスが不明だ。どうする?
**A2**: 先にパスを漏らす汎用ファイルを読む。プロセスとマウント情報(/proc 下)、起動スクリプト、web サーバー設定。これらからアプリのルートパスと設定位置を逆算し、それから狙って読む。先にファイルシステム構造をマッピングしてから深掘りする。
**Q3**: テキストしか読めず、バイナリが読めない/権限が足りない。どうする?
**A3**: 現在の権限で読める設定系テキストに集中する。重要ファイルの権限が足りないなら、「プロセス視点」の情報(そのサービスが自分の設定と環境変数を読める)を読む。環境変数には注入された鍵がよくある。A を読めなければ、同じ目的を達成する B を読む。
**Q4**: 読んだ設定の認証情報が暗号化/外部鍵参照だ。どうする?
**A4**: 参照チェーンを追う。設定がどの鍵サービス/ファイルを指すかを読む。アプリ実行時の環境を読む(復号後の値は環境変数かメモリダンプにありがち)。暗号化設定は本当の鍵が別所にあることを示し、蔓を辿る。
**Q5**: file scheme が禁じられ、http だけで外向き通信しない。ファイル読取がなくなった。どうする?
**A5**: 純粋な内部ネットワーク HTTP SSRF の攻め方に転じる(本トピックの他のチェーン)。あるいは他のファイル読取原語(パストラバーサル、テンプレート注入のファイル読取、ログ API)を探す。ファイル読取とネットワーク SSRF はこの入口の二つの能力で、一つが消えてももう一つを使う。
**Q6**: 大量のファイルを読んでも有用な認証情報がない。空手を避けるには?
**A6**: 読んだ情報を構造化して情報にする。OS バージョン、インストール済みサービス、内部ネットワークで誰と繋がるか、ユーザーは誰か。直接認証情報が取れなくても、これらは後続の権限昇格/横移動の基礎地図だ。ファイル読取が完全に無収穫なことは稀で、鍵は情報を搾れるかだ。

### SSRF に深入りする価値があるか、タイムリーに他攻撃面へ転じるかの判断
**Q1**: 一つの SSRF に長く費やして進展が遅い。続けるか転じるかをどう判断する?
**A1**: ROI を計算する。三点を評価する。到達可能な目標の価値(メタデータ/内部ネットワーク高価値サービスに触れるか)、こちらの能力上限(GET-only か gopher 全能か)、残りの迂回難度(検証がどれほど厳しいか)。三点とも悪ければ転じる。一つ光るものがあればさらに投じる。埋没費用で硬く消耗しない。
**Q2**: この SSRF の「能力上限」をどう素早く探り、判断材料にする?
**A2**: 標準プローブ一式で素早く測る。どの scheme をサポートするか、メソッド/ヘッダ/body を変えられるか、リダイレクトを追従するか、ポートホワイトリストの範囲、内部ネットワーク/メタデータに触れるか。30 分で能力境界を把握し、天井を判断する。打ちながら推測しない。
**Q3**: 能力は非常に強いが、高価値の内部ネットワーク目標が一時的に見つからない。どうする?
**A3**: 能力の強い SSRF は取っておく価値がある。先に別の場所で内部ネットワーク情報(他の漏えい、ドキュメント、DNS)を取り、高価値目標の位置が明確になってから、この強い SSRF で正確に打つ。能力と目標情報を分けて進める。
**Q4**: 能力が弱い(GET-only、検証厳)が、目標価値が極めて高い。どうする?
**A4**: 迂回研究への投入に値する。高価値目標なら、GET-only でも多くの未認可 Web を打てる。厳しい検証にも解析脆弱性を攻める余地がある。費用対効果が高いとき、遅い作業でも細工を尽くす価値がある。
**Q5**: 反復して横跳び(これが詰まればあれ、あれが詰まればこれ)が低効率だ。どうする?
**A5**: 優先キューを定め計時する。各攻撃面にタイムボックスを設け、時間に達して突破しなければ次へ切り、交代はするが無限に戻らない。規律化した時間管理で感情的な横跳びを代替する。各点の状態を記録して戻って続けられるようにする。
**Q6**: 対象全体の SSRF 面を評価し尽くし、ROI が全て低い。戦略的に転じる?
**A6**: 攻撃カテゴリを完全に替える。認証/認可欠陥、注入系、デシリアライズ、ビジネスロジック、既知コンポーネント脆弱性。SSRF は多くの入口の一つにすぎず、必ず通すべき道ではない。レッドチームは全体の攻撃面を見て、ROI の高い道を進む。

### SSRF が内部ネットワークデータベースポートに到達した利用判断
**Q1**: SSRF が内部ネットワークのあるホストに典型的なデータベースポートが開いているのをスキャンした。直接打てるか?
**A1**: プロトコル対話モデルを判定する。認証ハンドシェイク、server-first、多ラウンドが必要なデータベース(多くのリレーショナル)は一方向 SSRF では打ちにくい。まずこの SSRF が多ラウンド読み書きをサポートするか(返りを読んで継続発信できるか)を判断する。できなければ標準 DB ハンドシェイクは打てない。硬く試さない。
**Q2**: ハンドシェイクが必要なデータベースだ。一方向 gopher は本当に無理か?
**A2**: 少数の場合は実行可能だ。一部のデータベースは特定設定で認証を飛ばせる、既知の認証不要利用がある、プロトコルが乱序に寛容だ。しかし一般的な結論は「難しい」。より現実的なのは、「別の場所から DB 認証情報を取って正常に接続する」(設定ファイル、キャッシュの接続文字列)に転じることだ。
**Q3**: どの内部ネットワークデータ/ストレージポートが SSRF の直接攻撃に適する?
**A3**: 認証ハンドシェイクが不要か client-first、行プロトコル、寛容なもの。未認可のキーバリューキャッシュ、一部の文書/検索エンジンの HTTP API、無認証の時系列/ログライブラリ。それらは HTTP か、一方向配信で即効くので、SSRF 能力に合う。優先する。
**Q4**: DB 自体を打てない。SSRF はこの DB ホストに他に使い道がある?
**A4**: ある。同一ホストは管理 Web、バックアップサービス、監視エージェントなどの HTTP 面も開いていることが多い。SSRF が打てる。DB ポートが打てなくてもこのマシンに見込みがないわけではない。その他のポートをスキャンする。
**Q5**: DB 認証情報を取ったが、SSRF ホストのいるネットワークからしか接続できない。どう使う?
**A5**: 完全な DB セッションを発起できる位置が必要だ。SSRF 能力が完全なセッションを担えないなら、先に内部ネットワークに実行可能な点を一つ落とし(他の経路で)、そこから認証情報で DB に接続する。認証情報はある。欠けているのは実行位置だ。
**Q6**: データベースのこの道が完全に通らない。どこへ転じる?
**A6**: データへの他の到達方式に転じる。アプリ層のデータ API(API は包装された DB アクセス)、キャッシュ/検索内のデータコピー、バックアップファイル。要るのはデータであって DB ポートではない。層を替えて同じデータを取る。

### 内部マイクロサービス/API ゲートウェイの SSRF 横展開
**Q1**: SSRF が内部 API ゲートウェイかサービスメッシュ入口に届いた。単一サービスを打つより何が良く、どう利用する?
**A1**: ゲートウェイは「一を突破すれば全体」だ。後ろの一群のマイクロサービスへルーティングし、且つ内部呼び出しは認証免除か固定の内部 token を使うことが多い。それで大量のバックエンド API にアクセスできる。まずゲートウェイのルーティングルール(パス接頭辞がどのサービスをマップするか)を把握し、それを内部ネットワークサービスのディレクトリとして使う。
**Q2**: ゲートウェイの背後にどんなサービスがあるかをどう発見する?
**A2**: ゲートウェイのサービスディスカバリ/ドキュメントエンドポイントを探る(多くのゲートウェイはルートテーブル、ヘルスチェック、集約 swagger を晒す)。あるいは一般的なサービス名辞書でパス接頭辞を探る。ゲートウェイ自身がバックエンドリストを漏らすことが多い。先にその「地図」を読む。
**Q3**: ゲートウェイが内部呼び出しに特定の内部認証ヘッダを要求し、SSRF がヘッダを付けられない。どうする?
**A3**: その内部 token がどこから来るかを探す。ハードコードされた設定、環境変数注入、キャッシュにありがちだ。SSRF のファイル読取/設定読取で内部 token を取り、それを付ける(gopher でヘッダ付きリクエストを構成)。内部サービスメッシュの「信頼 token」は横移動の鍵だ。
**Q4**: サービス間が mTLS で、SSRF は正当なサービスを完全に偽装できない。どうする?
**A4**: mTLS 下では SSRF が信頼サービスに偽装しにくい。グリッド「周辺」の薄弱点を探す。mTLS を検証しない legacy サービス、内部ネットワークに晒されたデバッグ API、ゲートウェイ自身の対外面。mTLS の厳しい場所は迂回し、覆われていない隅を探す。
**Q5**: ゲートウェイがホワイトリストのバックエンドへのルーティングだけを許可し、目標サービスに届かない。どうする?
**A5**: ホワイトリスト内のバックエンドサービスそのものを打つ(それらは相互に信頼する)、その一つを足がかりに目標へ届く。あるいはゲートウェイのルート迂回(パス難読化、header 注入でルーティング目標を変える)を探す。ゲートウェイのホワイトリストも host ホワイトリストと同じく解析迂回がありがちだ。
**Q6**: サービスメッシュ全体の防御が厳密で、SSRF が横に動けない。どこへ転じる?
**A6**: これは成熟したゼロトラスト内部ネットワークだ。外部 SSRF の収益は限られ、「正当なサービス身元を一つ取る」方向に転じる。つまりバックエンドサービスインスタンスそのものを攻め落とす(その脆弱性、その認証情報)、その正当な身元でグリッドに溶け込む。ゼロトラスト内部ネットワークは「内部の一員になる」ことであり「外から突く」ではない。

### SSRF で CI/CD と成果物リポジトリを打ってサプライチェーン横移動する
**Q1**: SSRF が内部ネットワークに CI サーバーか成果物リポジトリをスキャンした。なぜ優先して打ち、どう打つ?
**A1**: それがサプライチェーンのハブだからだ。制御すればビルド成果物を汚染し、デプロイ認証情報を取れ、大量の下流に触れられる。先に未認可を探る。CI/成果物サービスの既定設定は管理 API か匿名読取を晒しがちだ。まず匿名でビルド設定、認証情報変数、成果物を読めるかを測る。
**Q2**: CI から匿名でどんな高価値情報を読める?
**A2**: ビルドログ(鍵を印刷しがち)、環境変数/secret(設定が漏れていれば)、デプロイスクリプト(目標ホストと認証情報を含む)、接続するコードリポジトリのアドレス。CI は鍵の集散地で、ログと変数を読むだけで複数組の認証情報を直接得られることが多い。
**Q3**: 匿名読取しかできず、ビルドを誘発できない(SSRF は GET のみ)。どう増幅する?
**A3**: 読んだ認証情報を別の場所で使う(デプロイ認証情報で本番へ、リポジトリ認証情報で成果物へ毒を盛る)。SSRF は CI 内の鍵を読む役割を担い、本当の横移動はその鍵で別チャネルで完了する。読取+外部利用の組み合わせ。
**Q4**: CI が認証必須で何も読めない。どうする?
**A4**: その未認可の子機能(webhook 受信端、ビルド状態 API、プラグイン API が認証・認可を漏らしがち)を探すか、その CI 版の既知の事前認証脆弱性をフィンガープリント照合する。CI 系ソフトウェアは歴史的に脆弱性が多く、版フィンガープリントが突破口だ。
**Q5**: CI を打つリスクが高い(発見されやすく、影響大)。打つべきか?
**A5**: 認可と騒音を天秤にかける。ビルドへの毒盛りは高影響・高危険の操作で、明確な認可が必要だ。偵察段階なら、まず読むだけで書かず、情報と認証情報だけを取り、「毒盛り」という破壊的動作は必要且つ認可が確認できたときに残す。
**Q6**: CI が打てない。サプライチェーン方向に他に入口は?
**A6**: 他のサプライチェーンノードに転じる。コードリポジトリ(SSRF が内部 git サービスに届く)、パッケージ管理のプライベートレジストリ、デプロイオーケストレーションプラットフォーム、鍵管理サービス。サプライチェーンは一本のチェーンで、CI はその一環だ。どの環でも横移動できる。環を替えて打つ。

### SSRF とテンプレート注入/デシリアライズの組み合わせ技
**Q1**: 単独の SSRF の収益が頭打ちだ。他の脆弱性と組み合わせて増幅するには?
**A1**: 「SSRF がネットワーク到達性を提供 + 別の脆弱性がコード実行を提供」の組み合わせを探す。SSRF がデシリアライズ/テンプレート注入/既知 RCE のある内部ネットワークサービスに届くとき、SSRF は「届く」前提で、その脆弱性は「打ち抜く」手段だ。内部ネットワークサービスで誰に既知 RCE があるかを評価する。
**Q2**: 内部ネットワークサービスに既知のデシリアライズ点があるが、POST の複雑な body が必要で、SSRF が届けられない。どうする?
**A2**: SSRF の配信能力を格上げする(gopher でシリアライズ payload を含む完全な POST を構成)。デシリアライズ gadget 自体がバイトストリームで、gopher は天然に送れる。鍵はアプリ層の検証迂回とバイトの正確な構築を正しく行うこと。先にローカルで対照する。
**Q3**: 組み合わせチェーンが長すぎる(SSRF→迂回→gopher→デシリアライズ→gadget)。どの環が最も断たれやすい?
**A3**: 環ごとに検証し、チェーン全体を盲送しない。先に SSRF がそのサービスに届くことを証明し、次に完全な POST を送れることを証明し、次にデシリアライズが誘発されることを証明し、最後に gadget が効くことを証明する。各環を独立検証し、断点が一目でわかる。一気に全チェーンを投げてどこが誤ったか推測しない。
**Q4**: 内部ネットワークサービスに既成の RCE 脆弱性がない。どうする?
**A4**: 「設定類」の増幅を探す。SSRF で内部ネットワークサービスの設定を変える(悪意ある資源に向ける、危険機能を開く)、それにこちらの制御するものをロードさせて二次 SSRF/RCE を作る。直接 RCE がなければ設定変更で RCE 条件を製造する。
**Q5**: 組み合わせチェーンがテスト環境で通るが、真目標では断たれる。どうする?
**A5**: 差異を調べる。真目標のバージョン/設定/防御はテスト環境と異なる。逐項比較する(サービス版、WAF の有無、パスの一致)。組み合わせチェーンは環境差異に敏感で、真目標とローカルが同じと仮定せず、各環のフィンガープリントを再較正する。
**Q6**: 全組み合わせを試して通らない。どこへ転じる?
**A6**: 分解して使う。SSRF 単独の偵察/認証情報読取の価値は残っている。別の脆弱性は別の入口で単独に打つ。組み合わせが成らなくても収益ゼロではない。各原語の独立価値を搾り切り、別の攻撃面で新たな組み合わせを探す。

### SSRF の IP/URL エンコード難読化迂回の体系的試行
**Q1**: SSRF が対象に文字列/IP 検証をする。乱れ打ちでなく体系的に迂回を試したい。どう整理する?
**A1**: 「検証がどの層で迂回されるか」で分類して逐一試す。IP 表記法層(十進/十六/八進/IPv6 マップ/ゼロ省略)、DNS 層(リバインディング/内部ネットワークを指すドメイン)、URL 解析層(userinfo@、#、多スラッシュ、バックスラッシュ、空白文字)、大文字小文字とエンコード層(URL エンコード/二重エンコード/Unicode)。四類それぞれ代表 payload を試し、ランダムにしない。
**Q2**: 検証がブラックリストか解析脆弱性かをどう知って、類を選ぶ?
**A2**: 境界を探る。正当なドメインが通り、内部ネットワーク IP 直書きが遮られれば=内部ネットワークへの検査がある。内部ネットワーク IP の各種エンコードでどれが通るかを試す。通れば=文字列ブラックリスト。どれも通らないが `a@internal` 型が通れば=解析分岐。先に検証種別を分類してから狙って打つ。
**Q3**: 単一エンコードが全て遮られる。組み合わせエンコードを試すべきか?
**A3**: 試すべきだ。検証とリクエストの二回のデコード間にずれがあり得る。二重エンコード、エンコード+リダイレクト、エンコード+リバインディングの重ね合わせがしばしば貫通する。体系的に「二つずつの組み合わせ」を行うが、重複を避けるため記録する。
**Q4**: 全部試して一つも通らない。検証が強すぎるのか見落としかをどう判断する?
**A4**: 既知のパーサ差異テストセット(公開の SSRF bypass 早見表)と照合し、全て網羅したかを逐条確認する。権威あるテストセットも通らないなら、検証が成熟しているとほぼ判定でき、非迂回経路(リダイレクト、XXE などの別コード経路)に転じる。
**Q5**: 迂回が全滅だ。どの直交次元に転じる?
**A5**: 「この検証関数を通らない外向き」に転じる。同アプリの他の SSRF 入口(検証が再利用されていないかもしれない)、リダイレクトで検証には正当な初回ジャンプだけを見せる、XXE/レンダラなどの独立した解析経路。迂回できないなら迂回を避ける。それを通らない道に替える。
**Q6**: 検証はあるが、リクエストライブラリ自身がさらに正規化し、こちらの構築が「戻された」。どうする?
**A6**: 観察を分離する。帯外でサーバーが実際に接続する host が何かを調べる(正規化で変わっているかもしれない)。「こちらが送る→検証が見る→実際に接続する」の三状態の変化を把握し、実際の接続の一歩に合わせて構築する。検証に対して盲目的に調整しない。

### SSRF で内部ネットワークを打つとき TCP 到達だがサービス無応答を区別する
**Q1**: SSRF がある内部ネットワークポートを探り、接続はするがサービスが長く返さない。ポートが開いてサービスが詰まっているのか、中間機器に hang されたのかをどう判断する?
**A1**: 挙動を対比する。真に開放されたサービスは通常何かを返すか、プロトコルに従って待つ。ファイアウォールの tarpit/パケット破棄はタイムアウトまで hang する。異なる scheme と即応答する既知のプローブ(HTTP ポートに正当な HTTP を送るなど)で区別する。hang を一律に「開放」としない。
**Q2**: こちらの payload がプロトコルに合わず、サービスが応答しないのではと疑う。どうする?
**A2**: プロトコルマッチを替える。HTTP らしきポートには規範的な HTTP を送る。バイナリサービスには gopher でそのプロトコルのマジックバイトを送る。サービスの無応答は「こちらの言語が違う」ことが多い。最もマッチしそうなプロトコルを先に試してから、本当に無応答かを判断する。
**Q3**: ポートが開いていると確認したが、期待通り返さない。何が考えられる?
**A3**: server-first プロトコル(先にこちらの流儀に従って話すのを待つ)、TLS が必要(平文リクエストが捨てられる)、認証が必要、の可能性がある。逐一排除する。TLS を加える(https scheme)、プロトコルを替える、先にハンドシェイクかを見る。返りの異常自体がフィンガープリントの手掛かりだ。
**Q4**: SSRF のタイムアウトが長すぎ、大量の hang がスキャン効率を殺す。どうする?
**A4**: SSRF パラメータでタイムアウトを制御できないなら、「即失敗」の探査を優先する(即 refused か即応答するポートを先にスキャン)、hang しやすい目標は優先度を下げて最後に処理かスキップ。応答速度で目標を等級分けする。
**Q5**: このポートが完全に状態不明だ。こだわる価値がある?
**A5**: 内部ネットワークでの重要性を見る。高価値ポートなら手段を替えて確認する価値がある(帯外、他入口の交差検証)。普通のポートなら「状態不明」とマークして飛ばす。単一の曖昧な目標に全体の推進を止めさせない。
**Q6**: 大量のポートがこの曖昧な hang 状態を呈する。何を示し、どう転じる?
**A6**: 相手に統一の東西方向防御(既定 drop+tarpit)がある可能性が高い。戦略を転じる。全ポートの盲スキャンを諦め、業務が本当に依存する少数の許可ポートだけを正確に打つ(前述の「出口制限」チェーンの発想)。曖昧状態が遍地=防御が働いている。正確な打撃に変える。

### SSRF で前置プロキシ/WAF を迂回して直接バックエンドを打つ
**Q1**: 対象の前に WAF/リバースプロキシがあるが、SSRF で内部ネットワーク側からバックエンドオリジンサーバーに届く。これに何の価値がある?
**A1**: 巨大な価値がある。内部ネットワーク側のバックエンドは往々にして内部からのリクエストを信頼し、WAF フィルタを通らず、認証免除すらある。SSRF でバックエンドの内部ネットワーク IP からリクエストを送れば、全ての境界防御を迂回してオリジンサーバーへ直結し、以前 WAF に遮られた攻撃が直接効くかもしれない。
**Q2**: 届いたのが真のオリジンサーバーか別のプロキシ層かをどう確認する?
**A2**: レスポンスを対比する。オリジンサーバーは通常、より多くの内部ヘッダ、より詳細なエラー、WAF 特徴がない。普段 WAF に遮られる payload を送り、この道から通れば境界を迂回したことを示す。「WAF が遮るか」を試験紙にしてオリジンサーバー到達を判断する。
**Q3**: オリジンサーバーも Host/内部 token を検証する。どうする?
**A3**: SSRF のヘッダ制御能力(gopher/CRLF)で、要求される Host と内部信頼ヘッダを補う。これらの内部ヘッダ値は設定/他漏えいから取れることが多い。オリジンサーバーの「内部信頼」はまさに SSRF が偽装できるものだ。
**Q4**: バックエンドが双方向検証をし、真のフロントエンドプロキシ転送でないと見抜く。どうする?
**A4**: フロントエンドプロキシ転送時にのみある特徴(特定ヘッダ、client cert)を探す。補えないなら目標を替える。同一バックエンドに検証の緩い他の内部入口があるかもしれない。あるいは信頼されるフロントエンドコンポーネント自身の脆弱性に戻る。
**Q5**: この WAF 迂回でバックエンドを打つ道が通らない。どこへ転じる?
**A5**: SSRF を他の高価値面(内部ネットワーク横移動、メタデータ)に使う。WAF 迂回は SSRF の多くの用途の一つにすぎない。あるいは WAF 迂回の他手段(エンコード/チャンク/プロトコル層迂回)に替え、SSRF に依存しない。
**Q6**: オリジンサーバーを打つとき、WAF 迂回で逆にバックエンドログに捕まりやすくならないか?
**A6**: バックエンドログは内部ネットワーク源 IP(つまり SSRF ホスト)を記録し、遡及はそのアプリを指す。注意: WAF を迂回してもログを迂回しない。低頻度、必要な動作を主とし、残す痕跡がどのマシンを指すかを理解して、後続を計画する。

### SSRF がコンテナオーケストレーションプラットフォーム(kubelet/API server)に触れる
**Q1**: SSRF が内部ネットワークにコンテナオーケストレーションコンポーネントらしきポートに届いた。なぜ高価値で、先に何をする?
**A1**: オーケストレーションプラットフォームはクラスタの総制御で、取れば大量のコンテナとノードを制御できる。まずフィンガープリントでどのコンポーネントかを確認する(API server、kubelet、etcd、それぞれ典型ポート)。次に未認可を探る。歴史的にこれらのコンポーネントには匿名/未認可アクセスの設定がよくある。先にコンポーネント種別と認証要否を確認する。
**Q2**: kubelet 系ノードエージェントが未認可だと探り当てた。何ができる?
**A2**: ノードエージェントの未認可は往々にして pod の列挙、pod 内のコマンド実行、ログ読取を許す。クラスタの任意コンテナで RCE するのと同等だ。先に pod を列挙して高価値コンテナ(機密マウント/特権付き)を探し、その中で実行する。SSRF からクラスタ RCE への直路だ。
**Q3**: API server が token を要求し、SSRF の匿名では入れない。どうする?
**A3**: token の源を探す。コンテナ内の service account token ファイル(SSRF がファイルを読めるなら)、設定の kubeconfig、CI のクラスタ認証情報。どれか一つの service account token を取れば、それで API server を打てる。token はクラスタの通行証だ。蔓を辿る。
**Q4**: etcd 系ストレージが未認可で到達可能だ。どう利用する?
**A4**: オーケストレーションストレージにはクラスタの全状態と secret(しばしば平文か弱暗号)がある。未認可で etcd を読めば全ての secret(各 service account token を含む)を直接エクスポートでき、クラスタの鍵束を取るのと同じだ。優先度が極めて高く、読めば全クラスタを薙ぎ払える。
**Q5**: 全オーケストレーションコンポーネントが認証必須で、token も取れない。どうする?
**A5**: 単一コンテナに転じる。まず業務コンテナを一つ攻め落とす(そのアプリの脆弱性)、コンテナ内部から自分自身の service account token を取り、内部から API server を打つ。総制御に入れないなら先に一つのコンテナに入り、内から外へ。
**Q6**: オーケストレーションプラットフォームの防御が厳密で、全体が打てない。どこへ転じる?
**A6**: ノード/ホスト層に戻る。オーケストレーションが打てなくても、下層のノードホストに他の露出面(SSH、ノード管理エージェント、クラウドメタデータ)があるかもしれない。あるいはデータ面(コンテナが動かす業務サービス自体)へ転じる。総制御の外に、データ面とノード面は直交する二つの道だ。

### SSRF で内部ネットワークサービスディスカバリ/レジストリセンターを読み、一括で情報を取る
**Q1**: SSRF が内部ネットワークのサービスレジストリ/設定センターに届いた。なぜ情報の金鉱で、どう搾る?
**A1**: レジストリセンターは全内部ネットワークサービスのアドレス、ポート、ヘルス状態、さらには設定と認証情報を保存する。一度読めば内部ネットワークサービス全体の地図を取得でき、盲スキャンを省ける。先に未認可読取を探る(この種のミドルウェアは既定で匿名可読であることが多い)、全量のサービスリストを引く。
**Q2**: サービスリストを取った後、利用優先順位をどう付ける?
**A2**: 前述の各チェーンの高価値原則で篩う。管理系、データ系、CI 系、オーケストレーション系サービスの登録項目を探し、それらが晒すメタデータ(バージョン、環境タグ)と組み合わせて柔らかい柿を特定する。レジストリセンターは「スキャン」を「ディレクトリ検索」に変え、直接ディレクトリで注文する。
**Q3**: レジストリセンターはさらに設定も保存する。認証情報を読めるか?
**A3**: しばしば読める。設定センターにはデータベース接続文字列、API key、内部 token が平文か弱暗号で保存されがちだ。優先して設定項目を読むのであってサービスリストだけではない。リストはトポロジを、設定は鍵を与え、鍵の価値がより高い。
**Q4**: レジストリセンターが認証必須で読めない。どうする?
**A4**: その読取専用/ヘルスエンドポイント(単独で露出し認証免除がち)に転じるか、その既知の未認可脆弱性を版フィンガープリントで照合する。あるいは従来の SSRF ポートスキャンに戻って自分で地図を描く。レジストリセンターは近道であって唯一の道ではない。塞がれたら元の道を進む。
**Q5**: レジストリセンターを読める。書けるか。書くと何ができる?
**A5**: 書けるなら、悪意あるサービスインスタンスを登録/ルートを改ざんし、トラフィックをこちらの制御可能なエンドポイントへハイジャックできる(内部呼び出しの仲介者、内部 token の釣り)。ただし書は高影響操作で、認可が必要且つ慎重に。先に読取だけを情報にし、書操作は必要と確認したときに残す。
**Q6**: レジストリセンターという近道が消えた。情報収集をどこへ転じる?
**A6**: 他の「内部ネットワークの自己記述」源に転じる。内部 DNS(ゾーン転送/辞書列挙でホスト名)、監視システム(トポロジとホストリスト)、内部 wiki/文書サービス、CMDB。内部ネットワークには「自分の姿を記録した」システムが数種あり、別の一つを調べる。

### SSRF 突破後、安定した内部ネットワークチャネル確立の取捨
**Q1**: SSRF で内部ネットワークに間欠的に届けるが、毎回それに頼るのは脆い。いつ安定チャネル構築に転じるべきか?
**A1**: SSRF でどれか一つ「実行可能な位置」(未認可 RCE、ログインできる認証情報)を得たら、重心を「SSRF の反復利用」から「内部ネットワークに安定した足場を一つ落とす」ことに移すべきだ。SSRF は足がかりであり、長期の住処ではない。判定基準: 能動的に実行できる点を得たか。
**Q2**: 内部ネットワークが外向き通信せず、リバースチャネル構築が難しい。どうする?
**A2**: 多段中継を進む。SSRF が到達でき且つ点を落とせる周辺ホストに中継を建て、内部ネットワーク奥のホストはそれへ接続し、それが外へ接続する(あるいはそれが SSRF ホストの到達できるホスト)。外向き通信できないなら「外向き通信できるマシン」を出口にし、チェーンで転送する。
**Q3**: 不安定な SSRF チャネル一つしかなく、安定足場すらまだない。まず何をする?
**A3**: 限られた窓で「一撃で鍵を取る」動作を優先する。認証情報を含む設定を読む、メタデータ token を一度取る、未認可 RCE を打って持続的なバックドアを落とす。貴重な窓を低価値の全量スキャンに使わず、それに依存しないアセットに換える一撃に集中する。
**Q4**: 中継を建てたが、内部ネットワーク監視が異常接続を発見した。どうする?
**A4**: チャネルの特徴を下げる。業務の既存の正当な外向きポート/プロトコルを再利用する(正常トラフィックに偽装)、時間をずらす、並行を制御する。あるいは長接続を低頻度ポーリング式に変える。チャネルは「正常な業務に見える」ようにし、目立つポートと高頻度接続を使わない。
**Q5**: 安定チャネルがどうしても建てられない(全隔離+厳監視)。どうする?
**A5**: 「非同期作戦」を受け入れる。SSRF を使えるたびに原子的な推進だけをする(情報を少し取る/変更を少し落とす)、長いタスクを複数回の短い窓に分割して完成させる。安定チャネルがないとき、一連の離散動作で戦果を蓄積するのであって、持続接続に依存しない。
**Q6**: いつ深入りを諦め、既存成果を納品すべきか?
**A6**: 継続投入の限界収益がリスク(暴露、破壊)を下回るとき。影響を証明できる重要アセット(認証情報、高価値システムへ到達できる証拠)を既に得ていれば、タイムリーに証拠を固定して納品し、一台多く取るためにチェーン全体の暴露を冒さない。レッドチームの目標はリスクの証明であって、全滅させることではない。

### SSRF でメール/内部通知系サービスを打って配信する
**Q1**: SSRF が内部ネットワークの SMTP か内部通知サービスに届いた。ゴミを送る以外に何ができる?
**A1**: 価値は「内部の信頼される身元で配信する」ことにある。内部ネットワークから発されるメール/通知は下流システムと社員に信頼されがちで、内部フィッシング、アラート偽造で操作誘導、メールに依存する自動化フロー誘発に使える。まず開放中継か、認証不要かを判定する。
**Q2**: この種の行プロトコルサービスに SSRF でどう配信する?
**A2**: gopher/CRLF で複数行のコマンドを構築する(行ベースのプロトコルは一方向配信に友好的)。先にチャネルが通ることを確認する(無害なコマンドを一つ送ってレスポンスか副作用を見る)、それから完全なセッションを構築する。行プロトコルは SSRF 一方向配信の理想的な目標だ。
**Q3**: サービスが認証必須で、開放中継が閉じられた。どうする?
**A3**: 配信でなく読取に転じる。内部メール/通知システムのキュー、ログ、設定には機密内容と認証情報があるかもしれない。配信が駄目なら情報源にする。あるいは他の行プロトコルの内部サービス(メッセージキュー、ログ受信器)に転じる。
**Q4**: それで内部フィッシングをしたいが、受信者とコンテキストが不明だ。どうする?
**A4**: 先に偵察する。前で得た内部ネットワーク情報(連絡先サービス、ディレクトリサービス、CI 通知設定)で、誰がこのシステムからのメッセージを信頼するか、正常なメッセージがどんな形かを把握する。フィッシングの成功率はリアルさに依存する。先に正常状態を把握する。
**Q5**: この配信経路が防がれた。どこへ転じる?
**A5**: 他の「信頼される内部誘発」面に転じる。内部 webhook、自動化オーケストレーションのコールバック、チャットボット API。「内部システム間で互いに信頼するメッセージチャネル」は全てこの発想の直交代替だ。別の信頼チャネルに替える。
**Q6**: この種の配信動作で過度の影響を避けるには?
**A6**: 検証的配信(送れることを証明、自分か認可されたテストアカウントに送る)に厳しく限定し、本当に社員へ一斉送信しない。レッドチームは能力境界を証明するのであって、本当の業務妨害とパニックを起こさない。配信系操作は特に自制する。

### SSRF をクラウドなし、純粋な伝統内部ネットワークで調整する
**Q1**: 対象がクラウド上でない(自前 IDC)。メタデータが打てない。SSRF の内部ネットワーク攻撃の重心をどう調整する?
**A1**: メタデータという近道が消え、重心を「内部ネットワークサービスの普遍調査+未認可面」に転じる。伝統内部ネットワークは往々にしてセキュリティ基線がより緩く、内部サービスが認証を設けない比率が高い。精力を全て生存ホストと未認可の高価値サービスのスキャンに投じる。リターン率は同様に高い。
**Q2**: 伝統内部ネットワークで優先してどんな目標を探す?
**A2**: ドメイン関連インフラ(ディレクトリ/認証サービス)、ファイル共有、運用足がかり/踏み台、バックアップシステム、旧くてパッチ未適用の内部 Web。伝統内部ネットワークの「スイートスポット」は歴史的に残された無人保守のサービスとドメインインフラだ。
**Q3**: SSRF がドメイン環境らしきサービスに届いた。直接ドメイン攻撃へ進められるか?
**A3**: SSRF の一方向能力は限られ、ドメイン攻撃ツールチェーン(多くが対話型プロトコルを要する)を直接走らせるのは難しい。より現実的なのは、SSRF で内部ネットワークの足場かドメイン認証情報を一つ取り、足場から標準のドメイン攻撃手法(Kerberos 系攻撃、ADCS 乱用など)を進めること。SSRF は「門に入る」を担い、ドメインを打つのは足場が担う。
**Q4**: 伝統内部ネットワークの多くのサービスが旧プロトコル(非 HTTP)で、SSRF が届かない。どうする?
**A4**: gopher で行プロトコルの旧サービスを打つか、SSRF は一部のバイナリ旧プロトコルに無力だと認め、打てる HTTP/行プロトコル面に集中する。旧プロトコルサービスは「内部ネットワークの足場を得た後」にネイティブツールで打つために残す。分担は、SSRF がネットワークサービスを打ち、足場が旧プロトコルを打つ。
**Q5**: 自前内部ネットワークにメタデータもなく、明らかな未認可面もない。詰まった。どうする?
**A5**: 情報漏えいの深掘りに転じる。伝統内部ネットワークの設定、共有ディレクトリ、内部文書、コードリポジトリには認証情報が散在しがちだ。SSRF のファイル読取/HTTP 読取能力でこれらの「人が残した鍵」をスキャンする。伝統環境の突破口は「サービス脆弱性」でなく「人の不注意」に多い。
**Q6**: 純内部ネットワーク SSRF の全体 ROI 評価が低い。どこへ転じる?
**A6**: アプリ自身の他の脆弱性で直接 shell を取る(外部一方向 SSRF より強い)、あるいはフィッシング/認証情報スプレーなど内部ネットワークに入る他の初期アクセス手段に転じる。SSRF は内部ネットワークに入る一種の方式にすぎず、自前環境で必ずしも最適ではない。ROI で初期アクセス経路を替える。

### SSRF で内部ネットワークオブジェクトストレージと内部鍵サービスを打つ
**Q1**: SSRF が内部ネットワークのオブジェクトストレージコンソールか鍵管理サービスに届いた。なぜ優先し、搾り取れるかをどう判断する?
**A1**: この二種は「データと認証情報の総倉庫」で、一旦未認可で読めれば一網打尽に等しい。先に未認可を探る。多くの内部ネットワーク自前のオブジェクトストレージと鍵サービスは内部ネットワークソースを認証免除か弱認証にする。SSRF でその管理/API ルートパスをリクエストし、バケット/鍵が直接列挙できるかを見る。
**Q2**: オブジェクトストレージが匿名でバケットを列挙できる。まず何を見る?
**A2**: 「設定/バックアップ/ログ/認証情報」系の命名のバケットとオブジェクトを探す。バックアップには全データベースエクスポートがよくあり、設定バケットには接続文字列、ログバケットには印刷された鍵がある。オブジェクト名とサイズで高価値ファイルを素早く特定し、逐一ダウンロードしない。
**Q3**: 鍵サービスが認証必須で、SSRF の匿名では読めない。どうする?
**A3**: その token の源を探す(アプリがどんな身元で鍵サービスにアクセスするか)。その身元の認証情報は設定/環境変数/オーケストレーション secret にある。鍵サービスへアクセスする身元を取ってから、それを付けて読む。鍵サービスの入場券はそれを呼ぶアプリ側に散らばっている。
**Q4**: オブジェクトストレージがソースベースのアクセスポリシーを使い、SSRF の内部ネットワーク IP がちょうど信頼される。どう利用する?
**A4**: これこそ SSRF の見返りだ。信頼される内部ネットワーク/サービス身元でリクエストを発する。ストレージポリシーがある内部ネットワークセグメントかサービスロールを信頼し、SSRF ホストがちょうどその中にあれば、本来対外でないオブジェクトを読める。「ネットワーク位置/ロールに基づく信頼」のバケットを重点的に探す。
**Q5**: ストレージと鍵サービスが厳格な認証で、搾り取れない。どうする?
**A5**: その「周辺」に転じる。アクセスログサービス(誰が何を保存したか記録)、CDN/キャッシュのオブジェクトコピー、アプリ側キャッシュの認証情報。主倉庫に入れないなら、データと認証情報のコピーとキャッシュを探す。あるいは呼び出し側アプリから身元を取る方向に戻る。
**Q6**: 大量のデータを読んだが、どれが「影響を証明できる」重要データかわからない。どう取捨する?
**A6**: 証明価値で並べる。平文認証情報を含む設定一つ、顧客/業務の機密データサンプル一つ、横移動できる鍵一つ、で十分にリスクを証明できる。最小限の必要なサンプルだけを証拠に取り、大量ダウンロード(高騒音・高危険)をしない。レッドチームは「取れることを証明」するのであって「全部持ち去る」のではない。

### SSRF で内部ネットワークを打つ全体の振り返り:いつこの道が通らないと判定するか
**Q1**: 一つの対象で SSRF 関連の道を全て通った。この主線を全体として諦めるかをどう体系的に判断する?
**A1**: 四つの問いで自己点検する。入口能力(天井に達したか)、到達性(内部ネットワーク/メタデータが完全に隔離されたか)、迂回(検証が解なしに成熟したか)、収益(達成済みの目標がリスク証明に十分か)。四つとも否ならこの道は通らないと判定し、他の攻撃面に転じる。恋々としない。
**Q2**: 「本当に通らない」と「手法を尽くしていない」をどう区別する?
**A2**: 標準リストと照合して網羅度を検証する。scheme を全て試したか、四類のエンコード迂回を全て試したか、リダイレクト/リバインディング/XXE の独立経路を全て試したか、エコーあり/盲/帯外の三チャネルを全て評価したか。リストを全網羅してなお無果なら初めて本当に通らない。そうでなければ尽くしていない。
**Q3**: 「暫定的に通らない」と判定したが、目標価値が高い。どう処理する?
**A3**: 放棄でなく棚上げする。現在の SSRF の能力と既に判明した情報を記録し、他の攻撃面で新しいもの(認証情報、別の入口、新版情報)を得たら戻って再利用する。高価値目標の SSRF は「待機する予備武器」として残す価値がある。
**Q4**: 他の攻撃面に転じた後、SSRF の試していない角度を思い出した。この戻りをどう管理する?
**A4**: タイムボックス付きの待機キューで全ての攻撃点(「戻って補試」の項目含む)を管理する。規律を持って戻る(記録、制限時間、検証)、感情的に乱れ飛ばない。戻るたびに新しい情報か新しい手段を携える。そうでなければ戻らない。
**Q5**: チーム/エージェントに明確な「転向信号」が必要だ。何を使う?
**A5**: 定量化可能なトリガーを使う。単点投入がタイムボックスを超え且つ新進展なし、連続 N 回の迂回試行が全失敗、ROI 評価が他の選択可能な面より低い。トリガーが発火したら転向する。転向の意思決定をルール化し、主観的な先延ばしと埋没費用の罠を避ける。
**Q6**: 最終的に SSRF 主線を諦めるとき、既存成果をどう無駄にしないか?
**A6**: SSRF 段階の産出を全てアセット化する。内部ネットワーク地図、サービスリストと版フィンガープリント、取った認証情報、確認した到達経路。これらは後続の全攻撃面の共有情報基盤だ。SSRF が打ち抜けなくても、それが描いた内部ネットワーク視野は engagement 全体に長く有用だ。
