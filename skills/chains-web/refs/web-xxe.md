# Web · XXE の識別と帯外持ち出し

### XML 解析入口の特定:どこに XXE があり得るか
**Q1**: 対象 X の多数の API を前に、どのポイントがサーバー側で XML を解析し、XXE を投げる価値があるかをどう素早く判断するか？
**A1**: まずデータ形式でスキャンする。リクエストボディが `<...>` 構造、Content-Type に `xml/soap/svg` を含むものはすべて候補である。次に機能から隠れた入口を推測する。ファイルインポート（docx/xlsx/svg/rss）、SSO（SAML）、請求書 / 決済（SOAP）、設定アップロード、Webhook コールバック、バックグラウンドのデータ同期である。判定基準：サーバーが「あなたが与えた構造化データを読む」限り、XML パーサーが存在する可能性がある。
**Q2**: ある API が現在 JSON を受け取っている場合、裏側が XML を処理できるかをどう知るか？
**A2**: 多くのフレームワークは Content-Type に応じて body パーサーを分派する。`application/json` を `application/xml` に変え、body を等価な XML に置き換えて一度送る。JSON エラーではなくフィールドを認識するか XML 関連のエラーを返すようになれば、バックエンドに XML パーサーがぶら下がっており、入口が成立する。
**Q3**: 「ここで実際にエンティティが解析された」ことを最小コストでどう確認するか？
**A3**: 良性の外部エンティティプローブを送り、エンティティの値を自分が制御する帯外アドレス（DNS/HTTP）に向ける。コールバックを受信すれば、パーサーが動作していることと外部エンティティが処理されていることを同時に証明できる。このステップはファイルを読まず、機密データに触れない、最もクリーンな生存プローブである。
**Q4**: 多数の候補をひとつずつテストするのは遅すぎる。どう優先順位を付けるか？
**A4**: 優先順位 = 外向き通信の可能性 × パーサーの緩さ。ファイルアップロード系（svg/office）は古いライブラリが使われ、デフォルト設定が緩いことが多い。内部ネットワークのサービス間 SOAP は外向き通信の確率が高い。対外ゲートウェイは往々にして強化されている。まず「内部の匂い」が濃い API を攻める。
**Q5**: すべての候補にプローブを送っても一切コールバックがない場合、この識別の道は塞がれている。どうするか？
**A5**: 直交する次元へ転換する。「自分が入口だと思った場所」だけを見ない。**レスポンス**を見る。一部の API は自ら XML/RSS/SAML を生成し、レスポンス側または保存後の二次解析があるかもしれない。**間接トリガー**を見る。アップロード後の非同期処理、エクスポート、レポート生成である。コールバックがない ≠ 解析されていない、であり、単に外向き通信がないだけかもしれない。error-based 検証に切り替えるべきで、諦めるべきではない。
**Q6**: 結局、解析されていないのか、解析されたが外向き通信がないのか、どう区別するか？
**A6**: 故意の構文エラーを対照として使う。不正なエンティティ参照を送り、パーサー特有のエラー（行番号・列番号、libxml/Xerces の文字列）が返れば、解析は動いており、問題は外向き通信の制限にある。error-based または DNS のみの手法を使う。まったく反応がない場合は、パーサーに入っていない可能性があるため、入口を変える。

### 表示のある XXE の検証とアップグレード
**Q1**: プローブで外部エンティティが使えることを確認し、ファイルを読めるかをすぐ検証したい場合、まず何を読むか？
**A1**: クロスプラットフォームで、必ず存在し、内容が安定した低感度のファイルを読んで原理を検証し、表示されるフィールドに埋め込む。まず「file:// + 表示」のチェーンが通ることを証明し、それから機密ファイルを論じる。最初から高価値のファイルを読まず、内容の特殊文字で失敗と誤判定しないようにする。
**Q2**: エンティティは表示できるが、ソースコード / 設定を読むとレスポンスが空または切り詰められるのはなぜか？
**A2**: たいていは内容に `<`、`&`、`%` があるか、閉じられていない構造が XML ドキュメント構造を壊して解析が中断したためである。方向転換：PHP の場面では `php://filter/convert.base64-encode` で全体をエンコードする、CDATA で包む、またはパラメータエンティティ + 外部 DTD のブラインド帯外に切り替えて、内容の汚染を避ける。
**Q3**: 対象が PHP でなく、base64 filter が使えず、内容に特殊文字もある場合はどうするか？
**A3**: OOB のブラインド帯外へ転換する。ファイル内容をパラメータエンティティに詰め、自分のサーバーを指す URL に連結してリクエストを送り、データを URL 経由で戻す。「内容がローカルレスポンスに入らない」問題を根本から迂回する。これは表示の次元から帯外の次元への切り替えである。
**Q4**: 表示フィールドに長さ制限があり、長いファイルが読み切れない場合は？
**A4**: 分割して読む。substring 系の技巧（パーサーが対応していれば）、またはオフセットで複数回読んで連結する。あるいは帯外に切り替え、自分のサーバー側で完全なストリームを受信し、表示の長さ制約を受けない。
**Q5**: ファイルを読める場合、ついでに SSRF/RCE へアップグレードできるか？
**A5**: ファイルを読めることはエンティティが解析可能なことを示す。`file://` を `http://内部ネットワークアドレス` に変えれば SSRF になる。PHP で expect が有効なら `expect://` でコマンド実行を試せる。Java は `jar:`/`netdoc:` で面を広げる。判定基準は、まずプロトコル wrapper が対応されているかを確認することである。
**Q6**: ファイル読み取りが突然すべて「エンティティ未定義」を返すか遮断される場合、封じられたのか？
**A6**: WAF をトリガーしたか、DOCTYPE が禁止された可能性がある。まずエンコード変形で WAF かどうかを探る。パーサー層で DOCTYPE が禁止されているなら、XInclude またはパラメータエンティティの路線に切り替え、元のペイロードで無理に突かない。

### ブラインド型 XXE：生存確認は優先して DNS を使う
**Q1**: レスポンスにエンティティの表示が一切なく、ブラインド XXE を疑う場合、最初の一歩で何を検証するか？
**A1**: まず「パーサーが能動的に外向き接続するか」だけを検証する。DNS 帯外で最も軽いプローブを使う。外部エンティティに自分が制御する一意なサブドメインを解析させる。DNS はほぼすべての外向き通信制限を貫通し、対象が TCP を張れる必要がない。DNS クエリを受信する = ブラインド XXE が成立する。
**Q2**: なぜ先に DNS で、直接 HTTP 帯外ではないのか？
**A2**: HTTP は対象が TCP で外向き通信でき、http プロトコルに対応している必要がある。DNS は敷居が低く、純粋な内部ネットワーク、egress が厳格な環境でもまず「存在性」の証拠を得られる。DNS が通り HTTP が通らないなら、外向き通信が制限されていることを直接示し、データの帯外持ち出しは DNS に頼る必要がある。
**Q3**: DNS が通った場合、どう「生存」から「データを持ち出す」へ上げるか？
**A3**: 外部 DTD を使う。パラメータエンティティでファイル内容を読み、`xxx.ファイル内容.あなたのドメイン` のサブドメインに連結して解析を発起し、内容を DNS クエリに入れて戻す。DNS ラベルの長さ制限と文字集合に注意し、先に base64/hex 化する必要がある。
**Q4**: 一意なサブドメインはすべて受信できるが、データ部分が常に空の場合は？
**A4**: パラメータエンティティは内部サブセット内でのネスト参照が制限されており、file 読み取りは**外部** DTD に置いて初めて有効になる。方向転換：データのパラメータエンティティと帯外のパラメータエンティティをすべて外部 DTD ファイルに移し、内部には外部 DTD を参照するパラメータエンティティを1つだけ残す。
**Q5**: DNS すら受信できず、ブラインドも通らず、完全に塞がれている場合はどうするか？
**A5**: error-based のローカル持ち出しへ転換する。パーサーがエンティティ処理時に例外を投げるよう構築し、ファイル内容をエラーメッセージに連結して、データをエラー表示とともに返す。完全に外向き通信に依存しない。これは「帯外の次元」から「ローカルエラーの次元」へ切り戻す重要な方向転換である。
**Q6**: 対象パーサーがエラーを一切表示せず、error-based も塞がれている場合は？
**A6**: 時間 / 挙動ベースの差異ブラインド（条件エンティティで異なる遅延や異なるレスポンスコードをトリガーする）へ転換するか、SSRF の次元へ退く。ファイルが読めなくても、内部ネットワークのサービスやクラウドメタデータを攻められれば同様に価値がある。

### JSON エンドポイントから XML 解析への強制切り替え
**Q1**: 対象が標準の REST/JSON API で、表面上 XML が見えない場合、まだ望みはあるか？
**A1**: ある。多くのバックエンドフレームワークは同じルートに JSON と XML のデシリアライザを同時に登録しており、Content-Type だけで振り分ける。header を `application/xml` に変え、JSON オブジェクトを等価な XML 要素構造に翻訳して送って試す。
**Q2**: Content-Type を変えたが直接 415/400 が返る場合、非対応なのか？
**A2**: 必ずしもそうではない。一部のフレームワークは正確な MIME（`text/xml` vs `application/xml`）を要求するか、XML バージョン宣言の明示を要求する。バリアントをひとつずつ試す。ルートがアノテーションで消費種別を限定している可能性もあり、その場合は複数形式を明示的に受け入れる API（コンテンツネゴシエーションの汎用 API など）に切り替える。
**Q3**: XML として解析されるようになったが、フィールド名が合わない場合はどうするか？
**A3**: まず形式が正しく、フィールドが任意の XML を送ってエラーを観察する。エラーは期待されるルート要素 / 名前空間 / フィールド名を漏らすことが多く、それに基づいて構造を合わせ、それから DOCTYPE を埋め込む。
**Q4**: 強制切り替えは成功したが、DOCTYPE を注入すると「DTD が許可されない」と返る場合は？
**A4**: このデシリアライザが DTD を禁止していることを示す。XInclude へ転換する。DOCTYPE が不要で、要素内で `xi:include` が許可されていればファイルを読める。あるいは、そのアプリケーションの実際に XML を処理する他の古い API へ戻す。
**Q5**: すべての形式バリアントが失敗し、この強制切り替えの道が死んだ場合はどうするか？
**A5**: 次元を変える。アプリケーション内で「ネイティブに XML を使う」機能（ファイルインポート、SSO、SOAP）を探し、現代フレームワークに保護された JSON API に固執しない。ネイティブ XML 機能の解析設定は往々にしてより緩い。

### 表示がない場合の error-based によるデータ持ち出し
**Q1**: 解析が動いていることを確認したが、完全に外向き通信がなく、表示もない場合、どうデータを取り出すか？
**A1**: error-based を使う。外部 DTD でパラメータエンティティを定義してファイル内容を読み、それを不正なシステムエンティティのパス（`file:///nonexistent/内容` を指すなど）に連結する。パーサーが「ファイルが見つからない」例外を投げるとき、内容を含むパスをエラーメッセージに打ち込んで表示する。
**Q2**: しかし対象が自分の外部サーバーの DTD を読み込めない場合（外向き通信なし）、この手法も外部 DTD が必要なのか？
**A2**: そこが矛盾点である。「ローカル DTD の再利用」へ転換する。多くのシステムは DTD ファイルを同梱している（ディストリビューション / フレームワークとともにインストールされる）。その内部で定義済みのパラメータエンティティを使い、内部サブセットの再定義を通じて error-based をトリガーし、全工程で外向き通信をしない。判定基準は、まず対象システム上に再利用可能なローカル DTD がどれだけ存在するかを探ることである。
**Q3**: 対象上で再利用可能なローカル DTD をどう見つけるか？
**A3**: 対象の技術スタックに基づいて一般的なパスを推測する（異なる Linux ディストリビューション、Java / フレームワーク同梱のドキュメント型定義ファイル）。file:// でひとつずつ読み込みを試し、パスエラーを返さず読み込みに成功したものが再利用可能なローカル DTD である。
**Q4**: エラー情報がアプリケーションで一律「サーバーエラー」に包まれ、内容を取得できない場合は？
**A4**: アプリケーションが詳細な例外を飲み込んだのである。方向転換：debug API / ログの漏えいがないか見るか、DNS のみのブラインド帯外へ戻る（前に外向き通信が制限されていると判断しても、DNS の外向きは単独で許可されていることが多く、純粋な DNS をもう一度試す価値がある）。
**Q5**: error-based でデータを出せるが、毎回1行 / 1区間しか取れない場合は？
**A5**: 正常である。エラーチャネルの容量が小さいだけである。substring で分割して複数回取り、または先に base64 で内容を圧縮して特殊文字の干渉を減らし、それから区間ごとに連結する。
**Q6**: error チャネルも完全に塞がれ、この道が完全に断たれた場合、どこへ転換するか？
**A6**: 「ファイルを読む」目標を諦め、SSRF 利用の次元へ転換する。同じ XXE で内部ネットワークの HTTP サービス、クラウド IMDS を攻め、資格情報を取得する / 未認可 API を攻める。ファイルが読めないことは XXE に価値がないことを意味しない。

### 外向き通信の制限：DNS のみでのデータ持ち出し案
**Q1**: 対象が DNS の外向きのみ許可し、HTTP がすべて塞がれている場合、ファイルを持ち出せるか？
**A1**: できる。DNS トンネル式の持ち出しを使う。パラメータエンティティでファイルを読む → base32/hex エンコード（DNS は大文字小文字を区別せず、base32 がより安定）→ DNS ラベルの長さ（≤63 バイト）に合うよう分割 → 各区間をサブドメインとして解析を発起し、自前の権威 DNS でクエリログを収集して再構築する。
**Q2**: ファイルに改行や特殊文字があり、そのままドメインに入れると壊れる場合、どう処理するか？
**A2**: まず必ずエンコードする。base32/hex は合法的な DNS 文字のみを生成する。base64（`+/=` を含み大文字小文字を区別するため、DNS が情報を失う）を避ける。エンコードは DTD 内でネストしたパラメータエンティティで行う。
**Q3**: 内容が長すぎ、DNS ドメインの総長（253 バイト）でも収まらない場合は？
**A3**: 分割 + 連番：各区間にオフセット / 連番のプレフィックスを付けて複数回クエリし、サーバー側で連番に従って再構築する。または先にファイルの重要な断片（ある設定の資格情報フィールドなど）だけを持ち出し、ファイル全体にしない。
**Q4**: 権威 DNS がなく、VPS が1台しかない場合は？
**A4**: VPS 上で簡易な権威 DNS サービスを動かすか、既製の OOB プラットフォームでサブドメインのクエリを受信する。NS レコードを VPS に向ければ、すべての `*.あなたのドメイン` のクエリがそこに届き、パケットキャプチャでデータが得られる。
**Q5**: DNS クエリすら受信できず、DNS のみの手法も通らない場合はどうするか？
**A5**: ローカル error-based（データがエラー表示とともに返る、外向き通信ゼロ）へ転換するか、ブラインドのブール / 時間ブラインドでビット単位に抽出する。外向き通信が完全にゼロのとき、唯一の道はデータを「ネットワークから出す」のではなく「レスポンスまたはエラーから出す」ことである。
**Q6**: DNS は出るが上流 DNS のキャッシュ / 重複排除で、一度しか受信できない場合は？
**A6**: 毎回のクエリに一意なランダムプレフィックスを付けてキャッシュ重複排除を避け、各区間が実際に送信されることを保証する。並列度も制御する。速すぎるとパーサーにまとめられたり帯域制限されたりする可能性がある。

### データ持ち出しが WAF に遮断される場合：XML エンコード変形による迂回
**Q1**: ペイロードを送った直後に WAF に遮断される場合（403 / 遮断ページが返る）、XML キーワードマッチングが疑われるとき、まず何を試すか？
**A1**: まず低コストのエンコード変形を行う。XML body 全体を UTF-16 に変換する（対応する BOM と宣言を付ける）。多くの WAF は `DOCTYPE`/`ENTITY` を UTF-8/ASCII でしかマッチしないため、エンコードを変えればルールが外れるがパーサーはそのまま読む。
**Q2**: UTF-16 が駄目な場合、他にどのようなエンコードの角度があるか？
**A2**: UTF-7（古いパーサー）を試す、宣言内で他の charset を指定する。あるいは改行 / タブ / コメントで `<!DOCTYPE`、`SYSTEM` などのキーワード内部を語分割してルールを迂回する。または機密のプロトコル名（file/http）を大文字小文字で難読化する、URL エンコードする（対応している wrapper 上で）。
**Q3**: リクエストボディが WAF に深く検査され、変形がすべて識別される場合はどうするか？
**A3**: トランスポート層の難読化へ転換する。リクエストボディを gzip/deflate で圧縮する（`Content-Encoding: gzip` を付ける）。バックエンドが先に解凍してから検知するが WAF が解凍しないなら、迂回できる。判定基準は、対象アプリケーションが圧縮リクエストボディに対応しているかである。
**Q4**: WAF が `SYSTEM` の外部エンティティキーワードを専門に遮断する場合は？
**A4**: `SYSTEM` の代わりに `PUBLIC` 宣言を使う（意味的に等価で URL を運べる）。またはパラメータエンティティを外部 DTD で定義し、リクエストボディには機密語を含まない参照を1つだけ残し、機密部分を WAF が見られない外部 DTD へ移す。
**Q5**: 各種の迂回がすべて遮断された場合、この塞がれた道をどう転換するか？
**A5**: 入口の次元を変える。同じアプリケーションの異なる API が同じ WAF ルールを適用しているとは限らない（ファイルアップロード、内部ネットワークのコールバック、旧バージョンの API はしばしば盲点である）。XXE を重点防御された API から防御の薄い API へ移す。
**Q6**: WAF ではなくパーサー自体が外部エンティティを禁止した疑いがある場合、どう確認してから決めるか？
**A6**: 純粋な内部エンティティ（外向き接続なし）のペイロードを送る。正常に解析されれば、パーサーは生きており、外部エンティティ / DTD だけが禁止されているので、XInclude またはローカル DTD の error-based へ転換する。内部エンティティも遮断されるなら、それが WAF / 前置防御であり、エンコード迂回の次元を続ける。

### DOCTYPE が無効化された場合：XInclude への方向転換
**Q1**: `<!DOCTYPE>` を注入すると直接「DTD が許可されない」と返り、従来の XXE が死んだ場合、他に道はあるか？
**A1**: ある。XInclude へ転換する。DOCTYPE/DTD に依存せず、対象 XML 内で自分が制御できる要素が XInclude 名前空間の宣言を許可していれば、`<xi:include href="file:///..."/>` でファイルを読める。前提は、アプリケーションが自分の入力を既存の XML ドキュメントに挿入してから解析することである。
**Q2**: XInclude 処理が有効かをどう判断するか？
**A2**: 良性ファイルを include するプローブを送り、レスポンスにファイル内容が挿入されるかを見るか、自分のサーバーのリソースを include してコールバックがあるかを見る。多くの場面で XInclude は明示的な有効化が必要で、成功しないのが普通であり、実測が必要である。
**Q3**: XInclude でテキストファイルを読むと解析エラーになる場合は？
**A3**: 含まれる内容が XML として解析されたためである。`parse="text"` 属性を付けて純テキストとして包含し、ファイル内容の `<`/`&` が構造を壊すのを避ける。
**Q4**: アプリケーションが自分が提出した完全な XML だけを解析する場合（ドキュメント全体を与えられる）、XInclude は依然として最適か？
**A4**: そうではない。ドキュメント全体を提供でき、DOCTYPE も全体的に禁止されていなければ、従来の外部エンティティ / パラメータエンティティの方が強い（帯外も error-based もできる）。XInclude は「断片しか注入できず DTD も禁止されている」ときの的を絞った転換であり、考えなしに使わない。
**Q5**: XInclude も禁止または無効で、塞がれ続ける場合はどうするか？
**A5**: error-based のローカル DTD 再利用（DOCTYPE 注入を必要としない前提で、パーサーに他のエンティティ処理面があるかを見る）へ転換するか、直接 SSRF / プロトコル利用の次元へ転換する。同時に、このパーサーを続ける価値があるかを再評価し、入口を変えるべきかもしれない。

### SVG アップロードがトリガーする XXE
**Q1**: 対象にアバター / 画像アップロードがあり SVG を受け入れる場合、どうそれを XXE に変えるか？
**A1**: SVG は本質的に XML である。DOCTYPE + 外部エンティティを埋め込んだ SVG をアップロードし、エンティティの値を SVG のテキストノードに表示する。サーバーが XML ライブラリで解析するか、サムネイル / トランスコード（一部のグラフィックライブラリなど）を行うなら、エンティティが解析される。まず帯外プローブ付きの SVG をアップロードしてコールバックがあるかを見る。
**Q2**: アップロードは成功したが解析の兆候が一切ない場合、そもそもサーバー側で解析されていないのか？
**A2**: 単にバイナリとして保存された可能性がある。判定基準：サーバーに「処理」動作があるかを見る。サムネイル生成、PNG 変換、サイズ / メタデータの読み取りである。後処理がなければ解析されない。方向転換してトランスコード / プレビューのあるアップロードポイントを探す。
**Q3**: SVG が PNG に変換され、表示がなくなった場合、どう持ち出すか？
**A3**: トランスコードはテキストを捨て、表示の道が断たれる。帯外に切り替える。エンティティの値の表示を求めず、解析過程で自分のサーバーへのリクエスト（DNS/HTTP）がトリガーされればよい。データは error-based またはパラメータエンティティで持ち出し、最終画像に依存しない。
**Q4**: アップロード検証が本物の画像だけを認める場合（マジックバイト / サイズを検査）は？
**A4**: SVG はテキストでマジックバイトの問題はないが、検証がビットマップ形式を強制するなら、他の XML 媒体へ転換する。同様に EPS/PDF 内に XML を埋め込む、office ドキュメント（OOXML の項を参照）を試す、または純粋な XML API に切り替える。
**Q5**: SVG は解析されたが外部エンティティが禁止されている場合、この塞がれた道はどうするか？
**A5**: ドキュメント内の error-based（ローカル DTD）へ転換するか、SVG が対応する他の外部参照（`<image href>` による SSRF など）を利用する。ファイルが読めなくても、SVG 内の外部リンク要素で内部ネットワークの偵察ができる。
**Q6**: SSRF にアップグレードして内部ネットワークを攻めたい場合、SVG 内でどう進めるか？
**A6**: 外部エンティティまたは `<image>`/`<use>` の href を内部ネットワークのアドレスに向け、トランスコードサービスに代わりに内部ネットワークへリクエストさせ、レスポンスの差異 / エラーを観察してブラインド SSRF を行う。

### OOXML/Office ドキュメント型 XXE
**Q1**: 対象が docx/xlsx/pptx のインポートに対応している場合、どう XXE を埋め込むか？
**A1**: OOXML は zip パッケージ内に複数の XML パーツを含む。正常なドキュメントを展開し、サーバーに解析されるパーツ（document.xml / sharedStrings.xml など）の先頭に DOCTYPE + 外部エンティティを挿入し、再パッケージしてアップロードする。サーバーが XML ライブラリでそのパーツを読むときにトリガーされる。
**Q2**: どの XML パーツを変えれば最も解析されやすいか？
**A2**: サーバーが「必ず読む」コアパーツを選ぶ。ドキュメント本文、共有文字列テーブル、ワークブックのリレーションシップテーブルである。冷門のパーツはスキップされる可能性がある。まず複数のパーツに異なる一意な帯外プローブを置き、どれがコールバックするかを見て、実際に解析されるパーツを特定する。
**Q3**: 再パッケージ後にドキュメントが破損と判定され、解析されない場合は？
**A3**: たいていは zip 構造または `[Content_Types].xml` が壊れたためである。最小限の変更だけを行い、ディレクトリ構造と圧縮方式を保つ。元のドキュメントを増分修正し、再構築しない。検証が通ってからエンティティを埋め込む。
**Q4**: 内容は解析されたが表示がない場合は？
**A4**: ドキュメントインポートは通常パーツ内容を表示せず、天然のブラインド場面である。直接外部 DTD のパラメータエンティティ帯外または error-based を使い、表示を期待しない。
**Q5**: サーバーが強化された現代の OOXML ライブラリを使い、DTD が禁止されている場合は？
**A5**: そのアプリケーションが XML を処理する他のより古いコンポーネント（旧版のインポート、サードパーティの変換サービス）へ転換するか、ドキュメント種別を変える（旧式のバイナリ / RTF 変換チェーンなど）。企業のドキュメント処理には複数のパーサーがあることが多く、防御は不均一である。
**Q6**: どの層が解析しているか（フロントエンドのプレビュー vs バックエンドの取り込み）を確定したい場合、どうするか？
**A6**: 一意な識別子付きの帯外プローブ + トリガー時期の観察を使う。アップロード即コールバック = 同期フロントエンド / 受信層の解析。遅延コールバック = バックグラウンドの非同期処理。これに基づいて防御境界と以降のペイロード投入位置を判断する。

### SOAP/WSDL エンドポイントの XXE
**Q1**: SOAP サービスを発見した場合、XXE はどこから着手するか？
**A1**: SOAP メッセージ自体が XML である。SOAP Envelope の前に DOCTYPE + 外部エンティティを挿入し、エンティティ参照をある文字列パラメータに入れる。SOAP エンドポイントはしばしば内部サービス間の通信で、外向き通信の確率もパーサーの緩さも高めであり、良質な標的である。
**Q2**: DOCTYPE を付けると SOAP が schema 検証失敗を返す場合は？
**A2**: 厳格な schema は余計な構造を拒否する。エンティティ参照を schema が許可する文字列フィールドの値に正確に入れ、全体構造を合法に保つ。DOCTYPE は XML 宣言の後、Envelope の前に置き、Envelope 構造を壊さない。
**Q3**: 正しい SOAP 構造が分からない場合、どう構築するか？
**A3**: まず WSDL（よくある `?wsdl` サフィックス）を取得して合法的なリクエストテンプレートを生成するか、通常の呼び出しを1回パケットキャプチャし、その上に最小限のエンティティを埋め込み、構造のエラー確率を下げる。
**Q4**: SOAP ゲートウェイが XXE 防御を行い、外部エンティティが禁止されている場合は？
**A4**: 方向転換：SOAP の後ろには複数の内部サービスが直列につながっていることが多く、前置ゲートウェイが禁止していても下流のパーサーが禁止しているとは限らない。パラメータエンティティ / XInclude を試すか、XXE をそのサービスが露出する他の非 SOAP API に移す。XXE を SSRF に転換して内部ネットワークのサービス一覧を攻める手もある。
**Q5**: すべての SOAP バリアントが遮断された場合、この道はどこへ転換するか？
**A5**: プロトコル / 入口の次元へ転換する。SOAP サービスには REST、メッセージキュー、管理 API が伴うことが多く、面を変えて攻撃する。または確認済みの SOAP XML 解析で SSRF により内部ネットワークを探り、ファイルが読めなくても内部ネットワークのトポロジを描ける。
**Q6**: SOAP XXE を借りて内部ネットワークを攻めたい場合、優先して何を探るか？
**A6**: 外部エンティティを内部ネットワークの一般的な管理ポート / サービスディスカバリアドレスに向け、レスポンス / エラーの差異で稼働を判断する。SOAP サービスがあるセグメントには通常他のマイクロサービスやミドルウェアがあり、横展開の良い起点である。

### SAML レスポンス / アサーション内の XXE
**Q1**: 対象が SAML SSO を使う場合、XXE の機会はあるか？
**A1**: ある。SP は IdP が送る SAML Response（XML）を解析する。SP に提出する SAML メッセージを構築 / 改ざんできるなら（特に自前の IdP または中間者の場面）、そこに DOCTYPE + 外部エンティティを埋め込み、SP の解析時にトリガーする。
**Q2**: SAML には署名検証があり、改変すれば無効にならないか？
**A2**: XXE は**署名検証の前**の解析段階でトリガーされることが多い。多くの実装は先に XML 全体を解析してから署名を検証する。だから署名が失敗しても、エンティティは既に処理され帯外に出ている可能性がある。判定基準：帯外プローブが「署名無効」を返す前にコールバックするかを見る。
**Q3**: SAML メッセージが base64+deflate でエンコードされている場合、どう埋め込むか？
**A3**: デコード → DOCTYPE / エンティティを埋め込む → 元のエンコード（deflate+base64）で再パッケージして再提出する。SP が期待するトランスポートバインディング（Redirect/POST）に対応するエンコード方式を保つことに注意する。
**Q4**: 表示がない場合（SSO が成功 / 失敗しか返さない）、どう持ち出すか？
**A4**: 天然のブラインド場面である。帯外 DTD または error-based を使う。SAML 処理チェーンのエラーは時に詳細な例外を返すか、読み取り可能なログに記録するため、優先して error-based を試す。
**Q5**: SP が強化された SAML ライブラリを使い、DTD が完全に無効化されている場合は？
**A5**: 現代の SAML ライブラリは多くがデフォルトで DTD / 外部エンティティを禁止する。方向転換：IdP 側または SAML メタデータエンドポイント（metadata も XML で、より緩いパーサーを使う可能性がある）を攻めるか、XXE を諦めて SAML のロジック脆弱性（署名迂回、アサーション改ざん）を攻める。脆弱性の種別の次元を変える。

### XXE を SSRF にアップグレードして内部ネットワークを攻める
**Q1**: XXE を確認したがファイル読み取りの価値が限定的な場合、どう SSRF に転換してより大きな戦果を得るか？
**A1**: 外部エンティティを `file://` から `http://内部ネットワークアドレス:ポート/` に変える。パーサーが代わりに内部ネットワークへのリクエストを発起する。まず内部ネットワークの稼働ホストと一般的なサービスポートをスキャンし、レスポンスの差異またはエラーでブラインド判断する。
**Q2**: ブラインド XXE で SSRF のレスポンス内容が見えない場合、どう内部ネットワークサービスの稼働を判断するか？
**A2**: 差異信号を使う。接続 vs 拒否でエラーが異なる、レスポンスの所要時間が異なる。または内部ネットワークサービスのレスポンスを error-based / パラメータエンティティで再び帯外に持ち出す。稼働偵察は差異に頼り、内容の読み取りは二次持ち出しに頼る。
**Q3**: パーサーが限られたプロトコルしか対応せず、http も非対応の場合は？
**A3**: 言語スタックを見る。Java は http/https/ftp/jar/netdoc に対応することが多い。PHP は http/ftp/php/expect などに対応する。file プローブは成功するが http が失敗するなら、http handler が制限されているため、そのスタックが対応する他のプロトコルで SSRF を行うか、ファイル読み取りの次元へ戻る。
**Q4**: 内部ネットワークにサービスはあるがすべて POST / 複雑なプロトコルを要求し、XXE は GET しか送れない場合は？
**A4**: XXE の SSRF は多くが GET / 単純なリクエストに制限される。gopher（スタックが対応していれば）で任意の TCP ペイロードを構築して Redis / 内部ネットワークのミドルウェアを攻める。gopher 非対応なら「GET だけで利用できる」対象（未認可のパネル、クラウドメタデータ）に集中する。
**Q5**: 内部ネットワークの外向き通信が厳格に隔離され、SSRF も発信できない場合は、この道も断たれるのか？
**A5**: ローカルの次元へ戻る。地道に file:// で設定 / 資格情報 / ソースコードを読んで情報利用するか、`/proc` 系の情報を読んで環境判断を補助する。SSRF が通らないとき、ファイル読み取り自体の情報価値を無駄にしない。
**Q6**: SSRF で内部ネットワークの HTTP サービスを攻めた場合、次の戦果をどう拡大するか？
**A6**: 優先してクラウドメタデータ（一時資格情報の取得）、サービスディスカバリ / レジストリ（ネットワーク全体のトポロジと鍵の取得）、内部の未認可管理 API を攻める。XXE-SSRF で1つの Web 脆弱性を内部ネットワークへ入る扉に変える。

### XXE でクラウド環境の IMDS を攻めて一時資格情報を取得する
**Q1**: 対象がクラウド上にあると判断した場合、XXE-SSRF はまずどこを攻めるか？
**A1**: インスタンスメタデータサービス（IMDS、リンクローカルアドレス）を攻める。XXE でサーバーにメタデータパスへリクエストさせ、ロールの一時資格情報の取得を試みる。取得できればクラウド上の横展開可能な鍵を手にしたに等しく、優先度が最も高い。
**Q2**: ブラインド XXE でメタデータのレスポンスボディを取得できない場合はどうするか？
**A2**: メタデータは http GET が返すテキストで、帯外に適した素材である。パラメータエンティティでレスポンスを帯外 URL に連結するか、error-based で表示する。まずメタデータアドレスに接続できることを確認し、それから資格情報の内容を持ち出す方法を考える。
**Q3**: 対象が IMDSv2（PUT で token を取得することを要求）を使う場合は？
**A3**: XXE は通常 GET しかできず、v2 の token を取得できないため、直接資格情報を読むと失敗する。方向転換：環境内の他の SSRF ポイント、または PUT / header を送れるプリミティブを探す。あるいはインスタンス上の他の機密面（マウントされた鍵ファイル、環境変数ファイル）を読む。
**Q4**: メタデータアドレスがネットワークポリシーで遮断され、接続できない場合は？
**A4**: 他のクラウド内部エンドポイントへ転換する。サービスディスカバリ、内部 API ゲートウェイ、K8s 場面の kubelet / API server アドレスなどである。クラウド内部ネットワークの横展開面は多く、メタデータが唯一の入口ではない。
**Q5**: すべてのクラウド内部アドレスが到達不能で、この道が断たれた場合、どこへ転換するか？
**A5**: ファイル読み取りへ落とす。クラウドホスト上には平文の資格情報ファイル、CLI 設定、デプロイ鍵がよくある。XXE の file:// でこれらの足場となる資格情報を直接読み、同様にクラウドアクセス権を取得できる。

### プロトコル wrapper の選択：言語スタックに応じて攻撃面を決める
**Q1**: XXE が成立した後、どうバックエンド言語に基づいて最も強力な wrapper を選ぶか？
**A1**: まず言語スタックをフィンガープリントする（エラーの特徴、header、挙動）。PHP → `php://filter`（ソースコード読み取り）、`expect://`（RCE、有効なら）、`data://` を試す。Java → `file`/`http`/`ftp`/`jar:`/`netdoc:`。.NET → 制限が多く主に file/http。スタックが対応し、害が最も大きいものを選ぶ。
**Q2**: ある wrapper がパーサーに対応しているかをどう素早く確認するか？
**A2**: 各 wrapper で良性のプローブ（既知のファイルを読むか自分へコールバックする）を送り、成功 / コールバックするものが対応している。最小のプローブでひとつずつ篩にかけ、非対応のプロトコルに時間を費やさない。
**Q3**: PHP の場面でソースコードを読みたいが、直接読むとすべて空になる場合は？
**A3**: ソースコードは `<?php` などの特殊文字を含み XML を壊す。`php://filter/convert.base64-encode/resource=対象` でソースコードを base64 化してから取り、デコードすれば平文のソースコードが得られる。
**Q4**: Java でアップロードされた zip 内のファイルを読むか、解析をトリガーしたい場合は？
**A4**: `jar:` プロトコルでアップロードパッケージ内のエントリを参照する。`netdoc:` は file の代替としてファイルを読める（一部のフィルタが file だけを遮断する場合に有効）。これも file が的を絞ってフィルタリングされたときの転換である。
**Q5**: RCE したいが `expect://` が有効でなく、wrapper の道が通らない場合はどうするか？
**A5**: XXE の直接 RCE はそもそも稀であり、無理に求めない。方向転換：file:// で読んだ資格情報 / ソースコードから二次利用を探す（ソースコード内でデシリアライズポイントや鍵を発見するなど）。XXE を直接 RCE の手段ではなく情報収集の踏み台として扱う。

### パラメータエンティティのネスト構築のデバッグの落とし穴
**Q1**: ブラインド帯外の外部 DTD を書き終えたがトリガーされない場合、どう系統的に切り分けるか？
**A1**: 3つの区間に分けて検証する。①内部サブセットが外部 DTD を参照できるか（まず外部 DTD に純粋なコールバックだけをさせ、読み込みを確認する）。②外部 DTD 内でファイルを読むパラメータエンティティが有効か（既知のファイルを読んで持ち出す）。③帯外 URL の連結が成功するか。区間ごとに特定し、一度に全セットを使わない。
**Q2**: パラメータエンティティ内に `%` を直接含められないとエラーが出る場合は？
**A2**: XML 仕様はパラメータエンティティの値内で `%` を直接参照することを禁止しており、文字エンティティ `&#x25;` でエスケープし、二次解析のときに初めて `%` に展開させる必要がある。これがネストしたパラメータエンティティで最もよくある落とし穴である。
**Q3**: 外部 DTD はローカルでは読み込めるが、対象上では読み込まれない場合は？
**A3**: 対象が外向き通信できない可能性がある（自分の DTD を読み込めない）。ローカル DTD の再利用または error-based へ転換する。または DTD の Content-Type / 到達可能性の問題（自分のサーバーの返すコード、ファイアウォール）かを確認する。
**Q4**: データは持ち出せたが内容が文字化け / 切り詰められる場合は？
**A4**: エンコードしていないか、URL の特殊文字を含むことが原因である。まず base64/hex エンコードしてから URL に連結する。長すぎるなら分割する。パラメータエンティティ内でエンコードを完了し、受信側でデコードする。
**Q5**: 各種のネストがすべて通らず、時間を費やし尽くした場合はどうするか？
**A5**: より単純な持ち出しプリミティブに変える。対象に実際に表示または error チャネルがあるなら、複雑なパラメータエンティティのネストに固執しない。error-based へ転換すれば、しばしば1つのペイロードでデータが出るため、多層パラメータエンティティのデバッグより速い。

### ストアド型 / 二次解析の XXE
**Q1**: 提出時にトリガーされないが、データが保存されてバックグラウンドで再解析される疑いがある場合、どう検証するか？
**A1**: 一意な識別子付きの帯外プローブを提出し、考えられる二次処理の経路（バックグラウンドタスク、エクスポート、管理者の閲覧、レポート）をトリガーする。遅延してコールバックを受信したら、ストアド型 / 二次解析であり、トリガーポイントは提出の瞬間ではない。
**Q2**: 二次解析がいつ発生するか分からない場合、どうトリガー時期を捉えるか？
**A2**: 各提出に一意なサブドメインを使い、送信時刻を記録する。コールバックを継続監視し、コールバックのタイムスタンプから送信時刻を引いたものがトリガー遅延となり、定期タスクか人為的トリガー（管理者が開くなど）かを推測できる。
**Q3**: トリガーが管理者の操作に依存し、制御できない場合は？
**A3**: これが二段階脆弱性の忍耐コストである。方向転換：自分で二次解析をトリガーできる機能（セルフエクスポート / プレビュー）を探すか、提出後にその保存データを読み取る別の API を能動的に呼び出して自己トリガーする。
**Q4**: ストアド型で表示もなく安定した帯外もない場合、どうデータを取得するか？
**A4**: error-based と組み合わせる。二次解析が処理時にエラーを出し、エラーを自分が読める場所（ログ表示、タスク状態、エラー詳細 API）に書き込ませる。ストアド型の場面ではデータの出口は「処理結果」にあり、「提出レスポンス」にないことが多い。
**Q5**: 二次解析が完全に隔離されたバックグラウンドで、DNS すら出ない場合、断たれたらどうするか？
**A5**: そのバックグラウンドの他の外向き通信 / 表示ができる機能へ転換するか、持ち出しを諦めて内部ネットワークの SSRF に変える（バックグラウンドマシンは往々にしてより深い内部ネットワークにあり、SSRF の価値がより高い）。不利な隔離環境を「より深い内部ネットワークへ入れる」信号として扱い、行き止まりとしない。

### パーサーのフィンガープリントと的を絞ったペイロード
**Q1**: ペイロードの汎用的な書き方が効かず、パーサーに合わせてカスタマイズしたい場合、まずどうフィンガープリントするか？
**A1**: エラーの特徴文字列（libxml2、Xerces、Expat、System.Xml、lxml など）を見る、デフォルト挙動（外部エンティティをデフォルトで解析するか、パラメータエンティティをデフォルトで展開するか）を見る。パーサーによって DTD / パラメータエンティティ / XInclude の対応は大きく異なるため、的を絞って手法を選ぶ。
**Q2**: libxml（PHP/Python でよく使われる）と分かった場合、どのような利用可能な特性があるか？
**A2**: 旧バージョンはデフォルトで外部エンティティを読み込む。`php://filter`（PHP バインド時）に対応する。パラメータエンティティの外部 DTD への対応が良く、ブラインド帯外と error-based に適する。新バージョンはデフォルトで外部エンティティを無効にするため、重心を XInclude または設定の抜け穴探しへ移す。
**Q3**: 現代の強化されたパーサー（デフォルトで全禁止）の場合、まだ望みはあるか？
**A3**: 確率は低いが設定の抜け穴を見る。開発者が特定の特性を明示的に有効化していたり、サードパーティの変換コンポーネントを使っていたりする可能性がある。フルセットのプローブ（内部エンティティ / 外部エンティティ / パラメータエンティティ / XInclude / プロトコル）を送って能力境界をひとつずつ測り、全禁止と決めつけない。
**Q4**: フィンガープリントが定まらず、エラーが隠されている場合はどうするか？
**A4**: 挙動の差異から逆算する。特定のパーサーだけが受け入れる構文プローブ（あるパーサー特有のエンティティ処理など）を送り、受け入れ / 拒否に基づいてどのパーサーかを逆算し、それからカスタムペイロードを使う。
**Q5**: パーサーがデフォルトで一切を禁止していると確認した場合、この道はどこへ転換するか？
**A5**: アプリケーション内の他の解析コンポーネント（同一システムに複数のパーサーが共存する）へ転換するか、脆弱性の種別を変える。一枚岩のパーサーに無限に投入せず、タイムリーに次元を変える。

### Billion Laughs / DoS の取捨選択
**Q1**: エンティティを注入できることを発見した場合、ついでにエンティティ拡張 DoS（Billion Laughs）を試すべきか？
**A1**: 通常、実際のレッドチームで DoS を能動的に打つのは**避けるべき**である。対象をダウンさせ、自分を露呈させ、以降の利用を壊すからである。「脆弱性の存在確認」がリソース消費の差異でしか判断できず、かつ認可が許す場合にのみ、慎重に小規模で検証する。
**Q2**: ではエンティティ拡張に非破壊の用途はあるか？
**A2**: ある。**小さい倍数**のエンティティ拡張で時間差判断を行う。軽微な解析所要時間の増加をブラインドの傍路信号として使い、エンティティが実際に展開されたことを証明し、サービスを実際にはダウンさせない。規模の制御が鍵である。
**Q3**: それをブラインドに使いたいが、制御不能を恐れる場合は？
**A3**: 拡張の層数と総量を厳格に制限し、まず最小規模でレスポンス遅延を測り、段階的に微調整し、遅延が顕著になったら即座に止める。判定基準は「差異を観測できる」ことで十分であり、決して最大化を追求しない。
**Q4**: 対象がエンティティ拡張に制限をかけて（entity expansion limit）エラーを返す場合は？
**A4**: パーサーに防御があることを示し、この DoS / 遅延の傍路は狭まる。正規のデータ持ち出し（帯外 / error-based）またはブールブラインドへ転換し、制限されたエンティティ拡張にこだわらない。
**Q5**: 認可範囲が一切の DoS を明確に禁止している場合、この道にまったく触れられない場合はどうするか？
**A5**: DoS の次元を直接諦め、エンティティ能力をすべてデータ持ち出しと SSRF に投入する。それこそが XXE の主戦場であり、DoS は端の高リスクにすぎない。

### RSS/Feed/Sitemap などの隠れた XML 入口
**Q1**: 通常の API がすべて強化されている場合、他に見落とされやすい XML 入口はあるか？
**A1**: RSS/Atom フィードのインポート、OPML、sitemap.xml の提出、ポッドキャスト / カレンダー（iCal は時に XML と組み合わされる）、XML-RPC API、旧式の API である。これらは「端の機能」で、長年誰も強化せず、パーサー設定が古い。
**Q2**: これらの隠れた入口をどう見つけるか？
**A2**: 過去のルートを辿る、フロントエンド JS 内の XML 関連呼び出しを見る、一般的な古い API パス（xmlrpc、rss インポート、feed 購読）を試す、「URL から購読をインポート」のような機能（さらに SSRF を内包する）の有無を見る。
**Q3**: 「URL から RSS をインポート」のような機能をどう利用するか？
**A3**: 二重の価値がある。まず SSRF で自分が与えた URL を取得し（内部ネットワークを探れる）、取得した内容がさらに XML 解析される（XXE ができる）。自分のサーバーに置いた悪意のある feed（DOCTYPE 外部エンティティを含む）を取得させ、一石二鳥である。
**Q4**: 古い API を発見したが、同様に外部エンティティが禁止されている場合は？
**A4**: 古い API はむしろ禁止されていない可能性が高い。本当に禁止されているなら、パラメータエンティティ / XInclude を試す。またはその内包する SSRF（インポート URL）で内部ネットワークへ転換する。XXE 部分が制限されていてもである。
**Q5**: これらの端の入口がすべて通らない場合はどうするか？
**A5**: メインの流れに戻って再評価する。おそらくそのアプリケーションは全体として XXE に免疫があり、他の脆弱性種別へ転換する。ただし先に「全禁止」なのか「入口を間違えた」のかを確認する。端の機能は深く隠れており、まだ発見されていない解析ポイントがあるかもしれない。

### 帯外データの切り詰めとエンコードのラッピング
**Q1**: 帯外で受信したデータが常に一部欠けるか、ある文字で切れる場合、どう特定するか？
**A1**: 通常は内容内の特殊文字（`&`/`#`/改行/`?`）が URL または DNS 内で区切り文字 / 終端文字として切り詰められるためである。根治策は、持ち出す前に内容全体に base64/hex エンコードを施し、合法文字だけを残し、受信側でデコードして復元することである。
**Q2**: base64 内の `+` `/` `=` が URL/DNS 内でまた問題になる場合は？
**A2**: URL では URL-safe な base64 または追加の URL エンコードを使う。DNS では base32/hex を使う（base64 は大文字小文字を区別し、非法文字を含むため DNS が失う）。チャネルに応じてエンコードを選ぶのが鍵である。
**Q3**: データが長すぎ、1回の帯外に収まらない場合は？
**A3**: 分割する。substring でオフセットに従って区間を切り、各区間に連番プレフィックスを付けて複数回持ち出し、受信側で順に再構築する。または先に最も重要な断片（ある資格情報フィールド）だけを持ち出し、ファイル全体にしない。
**Q4**: 分割して並列に送ったら、受信側の順序が乱れる場合は？
**A4**: 各区間に連番 / オフセットの識別子を強制的に付け、受信側は到着順ではなく識別子で並べ直す。並列速度を制御し、パーサーによるまとめやパケット損失を避ける。
**Q5**: エンコードも分割も行ったがやはり収集しきれず、チャネル自体が不安定な場合は？
**A5**: チャネルの次元を変える。DNS が不安定なら HTTP に変える（逆も同様）。または帯外から全体的に error-based のローカル表示へ切り替える（ネットワークを経由せず、天然に切り詰めがない、ただ毎回の量が小さい）。安定性を単回の容量より優先する。

### jar:// によるアップロードパッケージの読み取りと内部ネットワーク利用（Java）
**Q1**: 対象が Java でファイル / パッケージのアップロードがある場合、`jar:` プロトコルをどう使えるか？
**A1**: `jar:file:///アップロードしたパッケージ!/内部エントリ` で自分がアップロードした圧縮パッケージ内のファイルを読める。またはリモートの `jar:http://...` と組み合わせてサーバーに自分のパッケージをダウンロード・解析させる。読み取り、SSRF、および一部の場面での処理チェーン利用に使える。
**Q2**: jar プロトコルが対応されているかをどう先に確認するか？
**A2**: `jar:` が既知の到達可能なリソースを参照するプローブ（確認できるエントリを読むかコールバックする）を送り、成功すれば対応している。Java スタックはしばしばデフォルトで対応するが、SecurityManager / 設定で制限されていると失敗する。
**Q3**: jar:http で自分のパッケージをダウンロードさせたいが、対象が外向き通信できない場合は？
**A3**: 外向き通信ができないならリモート jar を取得できない。ローカルの `jar:file:` で既に対象にアップロードしたパッケージを参照する。アップロード先のパスすら制御できないなら、通常の file:// 読み取りまたは SSRF の次元へ戻る。
**Q4**: jar プロトコルが禁止されたが file はまだ使える場合は？
**A4**: jar handler だけが的を絞って禁止されたことを示す。`netdoc:`（file の別の Java 参照）または直接 file:// に転換し、禁止された単一プロトコルに固執しない。
**Q5**: これで深く進みたいが、jar 利用が制限された後、どこへ転換するか？
**A5**: SSRF で内部ネットワークを攻める + file で資格情報 / ソースコードを読む、へ転換する。Java アプリケーションが読む設定にはデータベース / ミドルウェアの資格情報がよくあり、横展開の直接的な燃料で、jar に固執するより実用的である。

### XXE でソースコード / 設定を読んだ後の横展開の意思決定
**Q1**: XXE でアプリケーションのソースコードと設定を読んだ場合、次のステップでどう最大の価値を搾り出すか？
**A1**: 「直接横展開できるもの」で並べて探す。データベース / キャッシュ / メッセージキューの資格情報、クラウドアクセスキー、内部サービスアドレスと token、暗号化鍵 / JWT の秘密鍵、他のホストの SSH / デプロイ鍵である。まず即座に接続できる資格情報を取る。
**Q2**: 設定内の資格情報が接続するのは内部ネットワークのアドレスで、外から接続できない場合は？
**A2**: 正常である。資格情報は有効だがサービスが内部ネットワークにある。方向転換：同じ XXE の SSRF 能力で対象の内部からこれらのサービスに接続するか、資格情報を既に内部ネットワークに立足した後の横展開の燃料として残す。情報とチャネルを対応させて使う。
**Q3**: ソースコード内に他の脆弱性の手掛かり（デシリアライズポイント、ハードコードされたバックドア、パス）が見えた場合は？
**A3**: このとき XXE は偵察ツールである。ソースコードを地図として扱う。より強い脆弱性（デシリアライズ RCE、認証バイパス）を特定して主攻とし、XXE は情報収集の踏み台としての使命を果たす。
**Q4**: JWT/session の鍵を読めたら何ができるか？
**A4**: 鍵で任意のユーザー / 管理者の token を偽造して直接権限昇格ログインし、ファイル読み取り脆弱性を完全なアカウント乗っ取りへアップグレードする。これは XXE の情報を直接権限に転換する高価値の経路である。
**Q5**: しばらく読んでも無用な設定ばかりで、利用可能な資格情報がなく、行き詰まった場合はどうするか？
**A5**: 読み取り対象の次元を変える。`/proc/self/environ`（環境変数に鍵が隠れていることが多い）、履歴ファイル、他の既知パスの機密ファイルを読む。またはファイル読み取りから SSRF / 内部ネットワーク偵察へ完全に転換する。1つのディレクトリで無用なファイルを繰り返し読まない。

### Windows 対象：UNC パスによる NetNTLM の持ち出し
**Q1**: XXE の対象が Windows と判断した場合、ファイル読み取り以外に何を搾り出せるか？
**A1**: 外部エンティティ / 参照を自分が制御する UNC パス（`\\あなたのホスト\share`）に向ける。Windows は解析時にマシン / サービスアカウントで SMB 認証を行い、リスニング側で NetNTLM のチャレンジレスポンスをキャプチャし、オフラインクラックまたはリレーできる。
**Q2**: XXE に UNC アクセスを発起させるにはどうするか？
**A2**: エンティティの SYSTEM 値またはあるファイル参照を UNC パスとして書き、パーサーにそのパスへのアクセスをトリガーさせる。前提は、パーサー / 実行スタックが UNC をファイルパスとして処理し SMB を発起することである。まず自分の SMB リスナーに接続できるかをプローブで確認する。
**Q3**: SMB 認証を受信できない場合、通っていないのか？
**A3**: 外向き 445 が封じられている可能性がある（よくある）。方向転換：他の外向きポートのキャプチャ方法を試すか、HTTP/DNS 帯外に戻って通常のデータ持ち出しを行う。445 の封鎖は内部ネットワークの常態であり、SMB だけに賭けない。
**Q4**: NetNTLM を受信したが解けない場合は？
**A4**: リレーへ転換する。キャプチャした認証を内部ネットワークの他の未強化 SMB/LDAP サービス（署名が強制されていない場合）へリアルタイムにリレーして直接権限を取得する。オフラインのブルートフォースではない。解けないなら利用方法を変える。
**Q5**: 対象が Linux で、UNC の手法がまったく使えない場合はどうするか？
**A5**: SMB の次元を直接諦め、file:// 読み取り + SSRF の主線に戻る。UNC/NetNTLM は Windows 専用の傍路であり、プラットフォームが合わなければ投入しない。

### gopher プロトコルのスマグリングによる SSRF の増幅
**Q1**: XXE-SSRF が単純な GET しか送れず、複雑なプロトコルを必要とする内部ネットワークのサービス（Redis / ミドルウェア）を攻めたい場合、どうするか？
**A1**: バックエンドスタックが gopher に対応していれば（一部の PHP/curl バインド場面）、`gopher://` で任意の TCP バイトストリームを構築し、Redis / プロトコルコマンドを URL にエンコードし、SSRF で任意のペイロードを送り、読み取り専用の偵察を書き込み / コマンドへアップグレードする。
**Q2**: gopher が使えるかをどう判断するか？
**A2**: `gopher://あなたのホスト:ポート/` のプローブを送り、リスニング側でそのままのバイトを受信するかを見る。受信すれば対応している。Java ネイティブは一般に gopher 非対応で、PHP は curl 経由なら対応することがある。
**Q3**: gopher 非対応で、複雑な内部ネットワークサービスを攻められない場合は？
**A3**: 「GET だけで利用できる」対象へ転換する。未認可の HTTP パネル、クラウドメタデータ、単純な REST 内部 API である。火力を SSRF 能力範囲内の標的に集中し、任意プロトコルを無理に求めない。
**Q4**: gopher は送れるがペイロードが XML/URL エンコードで壊れる場合は？
**A4**: gopher ペイロードは大量の特殊文字を含み、XML エンティティと URL の2層で正しくエンコードする必要がある（改行、`%`、バイナリ）。層ごとにエスケープし、まず単純なコマンドでエンコードチェーンを検証してから複雑なペイロードを使う。
**Q5**: 内部ネットワークのサービスを突破したら、どう戦果を拡大するか？
**A5**: Redis 系はファイル書き込み / モジュール読み込み / スケジュールタスク書き込みで RCE へ転換できる。書き込み可能な内部ネットワークサービスを見つけたら、XXE-SSRF から正式に内部ネットワークの立足と横展開の段階へ移り、XXE は誘導の使命を果たす。

### ブール / 時間ブラインドによるビット単位の抽出（究極の受け皿）
**Q1**: 完全に表示なし、帯外なし、error チャネルなしで、レスポンスの「成功 / 失敗」または遅延の差異しかない場合、データを読めるか？
**A1**: できるが、遅い。条件ブラインドを使う。エンティティを構築し、「あるファイルのあるバイトが条件を満たすとき」に観測可能な差異（異なるレスポンス、エラー、遅延）を引き起こし、バイトごとに二分探索で抽出する。これはすべての通常の持ち出しが断たれた後の最後の受け皿である。
**Q2**: XML / エンティティで「条件による差異のトリガー」をどう構築するか？
**A2**: パラメータエンティティ / error-based の条件経路を利用する。内容が判断を満たすときエラー / 遅延する分岐を通り、満たさないとき正常な分岐を通る。判定基準は、区別できる2つの状態を安定して観測できるかである。
**Q3**: 差異信号が不安定な場合（ネットワークの揺れで遅延の誤判定が起きる）は？
**A3**: 複数回サンプリングして中央値を取る、条件分岐の遅延差を大きくする、遅延ではなくブールの差異（レスポンスコード / 内容）を優先する。安定性が足りないなら遅延を使わず、より確実な信号に変える。
**Q4**: これが遅すぎ、数 KB のデータを抜き出すのに果てしない時間がかかる場合はどうするか？
**A4**: ファイル全体ではなく、最も重要な断片（資格情報 / 鍵の正確なフィールド）だけを抜き出す。または本当にすべての帯外が断たれているかを再評価する。もう一度 DNS（無視されてまだ開いていることが多い）、error-based を試す。ブラインドは最後の手段であり、使わずに済むなら使わない。
**Q5**: ブラインドでも抜き出せない場合（ブールの差異すらない）、完全に行き止まりならどうするか？
**A5**: この XXE は現在の環境でデータを効果的に持ち出せないと認め、その他の価値へ転換する。SSRF、DoS（認可時のみ）、または直接攻撃面を変える。タイムリーに損切りし、結論を蓄積し、死んだチャネルで時間を使い尽くさない。

### Content-Type と charset の正確な一致の落とし穴
**Q1**: XML 解析があると確信しているが、リクエストが XML として処理されない場合、どこで詰まっている可能性があるか？
**A1**: しばしば Content-Type の正確さで詰まる。全バリアントを試す。`application/xml`、`text/xml`、`application/soap+xml`、`;charset=` 付きと無し、およびアプリケーション独自の vendor 種別（`application/vnd.xxx+xml`）。フレームワークのコンテンツネゴシエーションは往々にしてある1つの正確な文字列しか認めない。
**Q2**: charset 宣言と XML 宣言内の encoding が一致しないとどうなるか？
**A2**: パーサーが誤ったエンコードで読み、ペイロード内の重要な文字がずれ、DOCTYPE が無効になる可能性がある。HTTP ヘッダの charset、XML 宣言の encoding、実際のバイトエンコードの3つを一致させる。UTF-16 で WAF を迂回したいときは、さらに3箇所を揃える必要があり、さもないと解析が直接壊れる。
**Q3**: ある Content-Type で解析に入れるがエンコードエラーが出る場合は？
**A3**: 入口は正しいがエンコードが揃っていないだけである。標準の UTF-8 に戻してまずロジックを通し、XXE が成立することを確認してから、他のエンコードで迂回することを検討する。「入口の検証」と「迂回の実験」を混ぜて切り分けない。
**Q4**: すべての Content-Type バリアントが解析に入らない場合、この切り分けの線は断たれるのか？
**A4**: 方向転換：おそらくその API は本当に XML を処理しない。ヘッダフィールドで無限に試さない。機能層に戻ってネイティブな XML 入口を探す。または method（GET vs POST）、ルートアノテーションの制限が原因かを確認し、正しいメソッド / パスに変えて再試行する。
**Q5**: ゲートウェイが Content-Type のホワイトリストで非常見の種別を直接遮断する疑いがある場合は？
**A5**: 既知の合法で一般的な種別（text/xml など）でまずゲートウェイを通過できることを確認し、それから対象パーサーが受け入れる種別へ段階的に近づける。ゲートウェイとパーサーの「受け入れ集合」を別々に把握し、その交差だけが利用可能な入口である。

### DTD 非対応時に外部一般エンティティを利用する
**Q1**: 対象がパラメータエンティティを禁止したが、通常の外部一般エンティティはまだ使える場合、どうデータを読むか？
**A1**: 最も基本的な形に戻る。`<!ENTITY x SYSTEM "file:///...">` をドキュメント本文で直接参照 `&x;` する。表示があれば直接データが出る。これはパラメータエンティティが制限されたが外部一般エンティティは制限されていないときの降格路線である。
**Q2**: 一般エンティティで複数行のファイルを読むと表示が1行目だけ / エラーになる場合は？
**A2**: 一般エンティティはファイル内容をドキュメント内容として連結し、特殊文字に当たると即壊れる。base64（PHP filter）に転換するか、単行の単純なファイルを読んでまず原理を検証し、複雑なファイルは帯外 / error-based で扱う。
**Q3**: 外部一般エンティティはローカルファイルを読めるが、帯外に使えない場合は？
**A3**: その通り。一般エンティティのブラインド帯外能力は弱い（パラメータエンティティのように SYSTEM URL に連結できない）。表示がないなら error-based へ転換するか、パラメータエンティティを有効化する方法を考える（一部のパーサーは外部 DTD コンテキストでのみパラメータエンティティのネストを許可する）。
**Q4**: 一般外部エンティティも禁止され、内部エンティティだけが残る場合は？
**A4**: 内部エンティティは外部リソースを読めず、ほぼエンティティ拡張系（DoS）しかできない。このとき XXE のデータ持ち出し能力はほぼゼロになり、XInclude（エンティティ機構から独立）へ転換するか、脆弱性の次元を変える。
**Q5**: どの種別のエンティティが禁止されているかを判断し、どう素早く境界を探るか？
**A5**: 4種類のプローブを分けて測る。内部エンティティ、外部一般エンティティ、外部パラメータエンティティ、XInclude である。どれがコールバック / 有効ならそれを使う。一度にパーサーの能力境界を把握してから戦略を決め、ひとつずつブラインドで試してリクエストを無駄にしない。

### data URL / PHP ラッパーによるソースコード読み取り
**Q1**: 対象が PHP で、`<?php` を含むソースコードを読みたいが、通常の file:// がすべて特殊文字で壊れる場合、どうするか？
**A1**: `php://filter/read=convert.base64-encode/resource=対象パス` を使い、ソースコードを読み取り段階で base64 化する。産物は安全な文字だけを含み、XML 構造を壊さず、デコードすれば平文のソースコードが得られる。これは PHP 場面でソースコードを読む標準的な転換である。
**Q2**: filter チェーンでさらに多くの変換を重ねて他の干渉に対処できるか？
**A2**: できる。filter はチェーン式に対応する（先に zlib、それから base64 など）。ただし先に最も単純な base64 単層で通す。層数が多いほどどこかの段階で失敗しやすく、切り分けコストが高いため、必要に応じて増やす。
**Q3**: 読みたいのがソースコードではなくコマンド実行の場合、PHP に望みはあるか？
**A3**: `expect://` 拡張が有効ならコマンドを実行できるが、デフォルトではインストールされないことが多い。まずプローブで expect が使えるかを測る。使えないなら XXE の直接 RCE を期待せず、filter でソースコードを読んで二次脆弱性を探す。
**Q4**: `php://filter` も無効化されている場合（allow_url 関連の設定がオフ）は？
**A4**: 通常の file:// + CDATA または帯外読み取りへ転換する。またはコード以外の機密ファイル（設定 / ログ）を読んで `<?php` の干渉を避ける。ラッパーが禁止されたならネイティブプロトコルの路線へ戻る。
**Q5**: PHP と確認したが filter も file も何も読めず、断たれた場合はどうするか？
**A5**: 外部エンティティが全体として禁止されている可能性がある（ラッパーだけでなく）。内部エンティティのプローブを送ってパーサーがまだ生きているかを確認する。生きていれば XInclude へ転換し、全禁止なら攻撃面を変える。「PHP なら必ず filter できる」と決めつけない。

### 帯外コールバックの送信元を判断して実際のトリガーを確認する
**Q1**: 帯外コールバックを受信したが、対象サーバーが送ったもので、WAF / サンドボックスの先読みによる誤検知ではないとどう確定するか？
**A1**: 鍵は関連性である。各ペイロードに一意なサブドメイン / 一意なパスを使い、送信からコールバックまでの送信元 IP、User-Agent、時刻を記録する。送信元 IP が対象の出口と一致し、UA がサーバー側 XML ライブラリらしければ、実際のトリガーとみなす。スキャナーのクラウドセグメント / ブラウザ UA からのものは中間機器の先読みの可能性がある。
**Q2**: コールバックの送信元 IP が対象とまったく異なる場合、誤検知か？
**A2**: 必ずしも誤検知ではない。対象の外向き通信が NAT / プロキシ / クラウドゲートウェイを経由し、出口 IP がフロントエンドと異なる可能性がある。UA、タイミング、ペイロードを送った後だけにコールバックするかを組み合わせて総合判断し、IP だけで一票否決しない。
**Q3**: セキュリティ機器が能動的にペイロードを「起爆」して偽陽性を作る場合、どう排除するか？
**A3**: 実際に解析して初めてトリガーされる多段依存のペイロード（外部 DTD を読み込んでからコールバックする2段階リクエストなど）を使う。単純な先読み機器は一般に多段 DTD を追わないため、偽陽性の一部を排除できる。
**Q4**: 実際のトリガーと確認したがデータを取得できない場合（コールバックだけで内容を伴わない）は？
**A4**: それは生存の証明は成立したが、データの持ち出しが未成立である。方向転換してデータをコールバックの URL / サブドメイン（パラメータエンティティ）に連結するか error-based にし、「存在の証明」から「データの取得」へ進める。
**Q5**: 偽陽性らしきものを繰り返し受信し、真偽を判断できず時間を無駄にする場合はどうするか？
**A5**: より確実な検証の次元に変える。直接 error-based（データがエラー表示から返り、送信元に曖昧さがない）を使うか、既知の内容のファイルを読んで検証する。期待する内容を読み戻せれば鉄証であり、コールバックの送信元にこだわるより速く確定できる。

### 内部ネットワーク SSRF 後に XXE でレスポンス内容を二次持ち出しする
**Q1**: XXE-SSRF で内部ネットワークのサービスを攻めたが、ブラインドで、サービスのレスポンス内容を取得できない場合、どう読み戻すか？
**A1**: 内部ネットワークのレスポンスを「ファイル内容」として扱う。一部の場面ではエンティティでまず内部ネットワークの URL へリクエストしてレスポンスを取得し、パラメータエンティティ / error-based でそのレスポンスを帯外チャネルに連結して戻す。前提は、パーサーが http レスポンスを参照可能なエンティティ内容として許すことである。
**Q2**: 内部ネットワークサービスが返すのが HTML/JSON で、大量の特殊文字を含み XML を壊す場合は？
**A2**: ファイル読み取りと同じ理屈で、先にエンコード（base64）してから持ち出すか、error-based で分割する。内部ネットワークのレスポンスの特殊文字干渉はファイルより深刻で、エンコードはほぼ必須である。
**Q3**: パーサーが http レスポンスをエンティティ参照として許さない場合（file のみ対応）は？
**A3**: その SSRF は稼働のブラインド判断しかできず、内容を読み戻せない。方向転換：レスポンス差異 / 遅延でブールブラインドを行い内部ネットワークサービスの挙動を推測するか、「稼働それ自体が価値」の対象（これで内部ネットワークのトポロジを描く、未認可面を探すなど）に集中する。
**Q4**: 内部ネットワークのレスポンスが大きすぎ、持ち出しに収まらない場合は？
**A4**: 重要な部分だけを取る。substring でレスポンス内の資格情報 / token フィールドを抽出し、ページ全体にしない。または複数回に分割する。内部ネットワークのレスポンスは欲しいのがごく一部であることが多く、全体を持ち出さない。
**Q5**: 二次持ち出しのチェーンが脆くて失敗しがちな場合、この道はどこへ転換するか？
**A5**: 一歩引いて XXE で対象マシン上のその内部ネットワークサービスのクライアント設定 / 資格情報（往々にしてローカルファイルに落ちている）を読み、「リアルタイムにレスポンスを読む」複雑なチェーンを迂回し、静的な資格情報を直接取得して接続する方が安定する。

### タイムボックス管理：XXE をいつ諦めて攻撃面へ転換するか
**Q1**: ある XXE の疑いのあるポイントにかなりの時間を投入しても進展がない場合、続けるべきかをどう理性的に判断するか？
**A1**: 能力境界のリストで照合する。内部エンティティ / 外部一般エンティティ / 外部パラメータエンティティ / XInclude / 各プロトコル / 表示 / DNS / HTTP / error チャネルを逐項検証したか。これらの直交する次元がすべて「禁止 / 不通」と実測されたなら、続けても限界利益は極めて低く、攻撃面へ転換すべきである。
**Q2**: 「方法を間違えた」と「対象が本当に免疫」をどう区別するか？
**A2**: 内部エンティティのプローブを見る。内部エンティティすら解析されないなら、パーサーがそもそも有効化されていないか完全に無効化されており、ほぼ免疫で、諦められる。内部は解析されるが外部だけ制限されているなら、面はあるが難しいだけで、XInclude / ローカル DTD をもう一度試す価値がある。
**Q3**: まだ試していない冷門のバリアントがいくつか残っている場合、列挙を続けるべきか？
**A3**: 収益で並べ、残りの「低コスト高リターン」のバリアント（入口変更、error-based など）だけを試し、「高コスト低確率」の深いデバッグは諦める。レッドチームは全体の前進速度を重視し、単一点の完璧さではない。
**Q4**: 上層 / プロセスがこのポイントで必ず結果を出すことを要求する場合はどうするか？
**A4**: 「実測した能力境界マトリクス」を結論として納品する。系統的に検証済みで、この面が有効に防御されていることを証明すること自体が価値ある結論である。方向転換して、既に読んだあらゆる情報（致命でなくても）を記録し、以降の利用に供する。
**Q5**: XXE を諦めると決めた後、精力を優先してどこへ転換するか？
**A5**: 現在の情報と最も接続しやすい攻撃面へ転換する。同じアプリケーションの他の入力ポイント（インジェクション / デシリアライズ / アップロード）、既に得た情報が指すサービス、または認証 / 認可のロジック脆弱性である。XXE 段階の偵察成果を次の攻撃次元へシームレスに供給し、ゼロからやり直さない。

### .NET 対象の XXE の境界と方向転換
**Q1**: フィンガープリントでバックエンドが .NET と判定した場合、XXE の手法は Java/PHP と何が異なるか？
**A1**: .NET パーサーはバージョンによる挙動差が大きい。旧版の `XmlDocument`/`XmlTextReader` はデフォルトで DTD と外部エンティティを解析する可能性があるが、新版および `XmlReader` はデフォルトでオフである。プロトコル対応も狭い（主に file/http、php filter なし、jar は限定的）。まずプローブで DTD と外部エンティティがデフォルトで有効かを測ってから投入を決める。
**Q2**: .NET の場面で特殊文字を含むファイルを読む場合（php filter なし）、どう処理するか？
**A2**: base64 ラッパーがないため、CDATA で包む、パラメータエンティティのブラインド帯外、または error-based へ転換する。ソースコードを読む類のニーズは .NET 上では PHP より面倒で、ローカルの平文表示を追求せず帯外を優先する。
**Q3**: デフォルトで強化された .NET パーサーに当たり、DTD が直接禁止されている場合は？
**A3**: 現代の .NET はデフォルトで `DtdProcessing=Prohibit` である。XInclude（有効なら）へ転換するか、開発者が明示的に `DtdProcessing=Parse` に変えた古い API を探す。どちらもなければその対象の XXE 面はほぼ閉じており、攻撃面へ転換する。
**Q4**: .NET 上で SSRF にアップグレードして内部ネットワークを攻めるのは可能か？
**A4**: 可能である。外部エンティティを http の内部ネットワークアドレスに変えればよい。.NET の http handler は通常ある。ただしプロトコルの豊富さは低く、複雑なプロトコルスマグリング（gopher）はほぼ見込みがないため、http GET 系の内部ネットワーク対象に集中する。
**Q5**: .NET の XXE の各道がデフォルト防御で塞がれ、断たれた場合、どこへ転換するか？
**A5**: .NET エコシステムでより一般的な高リスク面へ転換する。デシリアライズ（BinaryFormatter/Json.NET の TypeNameHandling）、ViewState、アップロードである。XXE が強化された現代の .NET 上で収益が限定的なとき、未練を残さず、フィンガープリント情報をより肥沃な攻撃種別へ導く。
