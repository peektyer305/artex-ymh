# Web · JWT/OAuth/SSOなどの認証機構攻撃

### JWTを入手したら、まずどの次元から攻めるか決める
**Q1**: JWTらしき3セグメント構成のbase64url文字列をキャプチャしたとき、やみくもに書き換える前に、まず何を判断すべきか。
**A1**: まず最初の2セグメントをbase64urlデコードしてheaderとpayloadを確認する。重点はheaderの`alg`、`kid`、`jku`、`x5u`、`typ`と、payloadの`iss`/`aud`/`exp`/`sub`/`role`系フィールド。攻撃面はほぼすべてheaderの署名検証ルーティングに集中している。まず「このトークンがどのアルゴリズムを使い、鍵がどこから来るのか」というモデルを確立してから、攻め方を決める。
**Q2**: headerがHS256で、payloadに明確な権限フィールドがある場合、最初の直感は何か。
**A2**: HS256は対称鍵による署名であり、攻撃の核心は「そのsecretを入手できるか/ブルートフォースできるか」に変わる。まず弱い鍵を仮定し、payloadを改ざんしてroleを変更したうえで、辞書によるオフラインのブルートフォースで署名を解く。同時に保険を残す:サーバー側にalg混同(RS→HS)の可能性がないか確認する。
**Q3**: RS256/ES256のような非対称の場合はどうか。
**A3**: 非対称では秘密鍵がないため、直接署名を書き換える手は通じない。方向転換:alg混同(RS256をHS256へダウングレードし、公開鍵をHMAC secretとして使う)、`kid`インジェクション、`jku`/`x5u`で自陣のJWKSを指す、`none`アルゴリズム。攻撃面は「鍵のブルートフォース」から「署名検証に使う鍵の出所の乗っ取り」へ移る。
**Q4**: トークンを改ざんして、実際に受理されたかどうかを素早く判断するにはどうするか。
**A4**: 「署名検証が通った場合にのみ現れる差異のあるレスポンス」を探す:権限外アクセスのAPIで200か401か、レスポンスボディにユーザー名が含まれるか、あるいはバックエンドのログ/挙動を一度トリガーするか。最小限の変更(たとえば重要でないフィールドを1つだけ変えて再署名する)で、まず「署名検証が実際に行われているか」を検証してから、権限改ざんに進む。
**Q5**: headerの攻め方がすべて失敗し、署名がびくともしない場合、どこへ方向転換するか。
**A5**: 「署名の偽造」という路線から離れ、トークンの【ロジック/ライフサイクル】を攻める:expが実際に検証されるか(期限切れトークンをまだ使えるか)、同一トークンをセッション/ユーザーをまたいでリプレイできるか、ログアウト後に無効化されるか、aud/issが検証されるか(別のサービスが署名したトークンを流用できるか)。署名の安全性≠ロジックの安全性であり、多くのターゲットは後者にある。
**Q6**: さらに深く掘りたい場合、情報漏えいの次元はあるか。
**A6**: payload自体は平文であり、内部ユーザーIDの形式、テナントID、内部ネットワークのサービス名、権限モデルの列挙値を漏えいする可能性がある。偽造できなくても、これらは横展開と権限外アクセスのための情報になる。JWTを「サーバー側が自ら晒す構造説明書」として読む。

### alg=noneとアルゴリズムダウングレードの試行順序
**Q1**: algの改ざんを試す場合、`none`から試すべきか、それともRS→HS混同から試すべきか。
**A1**: コストと依存がゼロなので、まず`none`系列から試す。header `{"alg":"none"}`を構成し、payloadを対象の権限に変更し、署名セグメントは空にする(末尾のドットを残す必要がある実装もある)。同時に変種を用意する:`None`、`NONE`、`nOnE`で大文字小文字のブラックリストを迂回する。
**Q2**: noneが拒否されたとき、「ライブラリがそもそも対応していない」のか「明示的に遮断された」のかをどう判断するか。
**A2**: エラーメッセージの違いを見る。「unsupported alg」系ならライブラリ層で無効化されている。「signature required」なら、署名フィールドを期待していることを示す。前者はRS→HSへ方向転換し、後者は空署名の各種エンコード変種と、「noneを設定スイッチとして許可する」歴史的な脆弱性バージョンがあるかを試す。
**Q3**: RS→HS混同に進む前提は何か。
**A3**: 前提はサーバー側のRSA公開鍵を入手できること。公開鍵は`/.well-known/jwks.json`、OAuth discoveryエンドポイント、TLS証明書、フロントエンドのJS、ドキュメントによくある。公開鍵PEMを入手し、それをHMACのsecret文字列として扱い、HS256で改ざん後のpayloadに署名する。
**Q4**: 公開鍵の形式の細部で、どのような落とし穴に陥りやすいか。
**A4**: HMAC keyのバイトは、サーバー側が公開鍵を読み込むときに使う文字列と【バイト単位で一致】していなければならない。PEMの改行、末尾改行の有無、SPKIかPKCS1かを含む。複数のPEM変種を用意してそれぞれ署名して試すこと。1種類だけ試して失敗と断定してはならない。
**Q5**: 混同もうまくいかない場合、このライブラリはアルゴリズム族を根本的に区別しているのか。
**A5**: 現代のライブラリの多くは`alg`に鍵の種別を強く紐づけており、混同が効かないのは正常。`kid`/`jku`のような「鍵の出所の乗っ取り」へ方向転換するか、あるいは対称のシナリオへ戻る。HSを実際に使うのか確認し、終始RSで署名検証が厳格なら、労力をトークンのロジック/OAuthフロー層へ移す。
**Q6**: アルゴリズム層で時間を浪費しすぎないようにするにはどうするか。
**A6**: アルゴリズム層にタイムボックスを設ける(たとえば15分でnone/ダウングレード/kid/jkuの4点セットを実行)。4点セットがすべて不発なら、OAuthフローか権限外アクセスのロジックへ思い切って方向転換し、署名に固執しない。レッドチームでは方向転換の規律が単点の深掘りより重要。

### kidパラメータのインジェクション攻撃面の判定
**Q1**: headerに`kid`フィールドがある場合、何を疑うべきか。
**A1**: `kid`は鍵識別子であり、サーバー側はそれを使って鍵を照会する。照会の実装がSQL、ファイルパス、コマンドの文字列連結なら、インジェクションが成立する。まずkidの値の形態を判断する:ファイル名(`keys/1.pem`)のような形か、データベースのid(数字/uuid)のような形か、それともURLのような形か。
**Q2**: パスだと疑う場合、どう活用するか。
**A2**: ディレクトリトラバーサルを試し、【内容が既知のファイル】を指すようにして、署名keyを制御可能にする。定番は`/dev/null`を指す方法(keyが空になり、空のsecretで署名する)や、静的な予測可能ファイルを指す方法。核心は「鍵の値」を既知のものに変え、合法的な署名を偽造すること。
**Q3**: SQLに連結されていると疑う場合はどうか。
**A3**: SQLインジェクションを試し、照会が自分が指定した鍵の値を返すようにする(UNIONで制御可能な文字列をkeyとして返す)。その文字列で署名する。判定基準:インジェクションのペイロードが署名検証の結果を変えるか、データベースのエラーを引き起こす。
**Q4**: kidインジェクションはどう命令実行につなげるか。
**A4**: バックエンドがkidをシステムコマンドに連結する場合(稀だが存在する)、コマンドインジェクションを試せる。ただし優先度は低く、まずパス/SQLの2つの本線を尽くす。
**Q5**: kidの各種インジェクションがすべて効かない場合、原因は何が考えられ、どこへ方向転換するか。
**A5**: kidがホワイトリストによる表引きのみで、連結を行っていない可能性がある。`jku`/`x5u`へ方向転換する。同じ「鍵の出所を制御する」だが、ローカルの表引きではなくURL経由になる。headerにこれらのフィールドがない場合は、alg混同かトークンのロジック層へ戻る。
**Q6**: kidを深掘りする価値があることを事前に知らせるシグナルはあるか。
**A6**: kidを変更した後のレスポンス時間/エラー種別の変化(存在しないファイルを指して500が出る、引用符を注入してSQLエラーが出るなど)は強いシグナルで、サーバー側が本当にそれを使って動的照会を行っていることを示す。続ける価値がある。kidを変更しても反応がない場合は、ほぼ表引きなので、深入りしない。

### jku / x5uで自陣のJWKSを指す実装
**Q1**: headerに`jku`(JWK Set URL)が現れる場合、これはどのような攻め方を意味するか。
**A1**: サーバー側は`jku`が指定するURLから公開鍵を取得して署名検証する。URLを制御できるなら、自分のサーバーに自分で生成した鍵ペアを置き、秘密鍵でトークンに署名し、`jku`を自分のJWKSに向ける。サーバー側は自分の公開鍵で署名検証するため必ず通る。核心は「自分で鍵を持ち込み、自ら身元を証明する」こと。
**Q2**: jkuを直接自分のドメインに変えると、通常どのような遮断に遭遇するか。
**A2**: サーバー側には多くの場合hostのホワイトリストがある(自ドメインのみ許可)。迂回するにはSSRF/URL解析迂回の一連を使う:`@`混同(`https://trusted.com@evil.com`)、サブドメイン(`trusted.com.evil.com`)、オープンリダイレクト(ホワイトリストのドメイン上で自分のJWKSへ転送するAPIを探す)、DNS/解決の曖昧さ。
**Q3**: 自分のJWKS内のkidはどう設定するか。
**A3**: 自分のJWKS内のkeyの`kid`をトークンheaderの`kid`と一致させる。サーバー側が自分のkeyを選択するためにはこれが必要。JWKには自分の公開鍵(n/e)を入れ、トークンは対応する秘密鍵で署名する。細部の整合が成否を分ける。
**Q4**: サーバー側が外向き通信をまったく行わず、自分のURLを取得できない場合はどうするか。
**A4**: これは遮断されているシナリオ。`x5u`(証明書URL、同様だがX.509経由)へ移るか、ローカルの鍵の出所(kid)へ戻る。「外部の鍵の出所」がすべて外向き通信不可で失敗するなら、鍵の乗っ取りから完全に離れ、OAuth redirect_uriかトークンのロジックを攻める。
**Q5**: ホワイトリスト迂回をすべて試しても通らない場合、続ける価値はあるか。
**A5**: SSRF迂回に上限を設ける。ホワイトリストが厳密な完全一致でオープンリダイレクトがないなら、jkuの線はほぼ行き止まり。方向転換する直交次元:自ドメインのJWKSを信頼しているなら、その自ドメイン配下の制御可能なパスに汚染/アップロードできないか(ファイルアップロード+jkuで自ドメイン配下の自分がアップロードしたファイルを指す)。「外部URL」の問題を「自ドメイン配下の制御可能なコンテンツ」の問題に変える。
**Q6**: jku偽造を攻略した後、どう戦果を最大化するか。
**A6**: adminまで権限昇格して止まらない。制御可能な署名で権限モデルを列挙し(role/scopeの値を一つずつ試す)、サービス間呼び出しのトークンを偽造する(同じ鍵体系が内部マイクロサービスをカバーしている場合)。単点のトークン偽造を信頼ドメイン全体への通行証へ拡大する。

### HS256の弱い鍵ブルートフォースの取捨
**Q1**: HS256と確定した場合、ブルートフォースに投入すべきか。判定基準は何か。
**A1**: まず低コストで汎用の弱いパスワード辞書を素早く回す(よくあるsecret、`secret`、会社名、既定値、漏えいしたフレームワークのサンプルkey)。数分回して出なければ評価する:鍵が高エントロピーのランダム文字列なら、ブルートフォースの期待リターンは極めて低く、本線にすべきではない。
**Q2**: どのやり方でブルートフォースするのが効率的か。
**A2**: サーバー側に触れずオフラインでブルートフォースする。完全なJWTをhashcat(HS256対応モード)かjohnに与える。辞書を優先し、ルールを次に、純粋なマスクを最後にする。辞書のソース:汎用の弱い鍵テーブル、対象関連語(ドメイン名/製品名/年の組み合わせ)、過去に漏えいしたsecretのライブラリ。
**Q3**: 辞書が尽きた場合、マスクの総当たりに進むべきか。
**A3**: 鍵の形態の手がかりを見る。漏えいしたサンプル/ドキュメントがkeyの長さや文字集合を示唆するなら(32桁hexなど)、的を絞ったマスクは試す価値がある。手がかりがまったくない場合、やみくもなマスクは無駄なので止める。
**Q4**: ブルートフォースの線が行き止まりと判定されたら、どこへ方向転換するか。
**A4**: 「鍵の推測」ではなく「鍵の取得」へ転換する。secretはソースコード/設定/環境変数/git履歴/フロントエンドのバンドルファイルにハードコードされていることが多い。任意ファイル読み取り、ソースコードの漏えい、`.env`、バックアップファイルに触れられれば、secretを直接読み出すほうがブルートフォースよりはるかに確実。認証の問題を情報漏えいの問題に変える。
**Q5**: 万一secretがKMSから動的に取得され、まったく保存されない場合はどうか。
**A5**: その場合はHS鍵の線を完全に放棄し、トークンのロジック層とOAuthフロー層へ移る。同時に振り返る:強固な鍵管理は往々にしてチームのセキュリティ意識が高いことを意味するため、重心を暗号学的攻撃ではなく業務ロジックの権限外アクセスへ移すべき。
**Q6**: 弱いsecretをブルートフォースで当てた後、自分のトークンを変える以外に何ができるか。
**A6**: 任意のトークンに署名できることは「身元発行権」を持つことに等しい。任意のユーザーを偽造し、service accountを偽造し、異常なフィールドを持つトークンを構成してバックエンドの解析ロジックを探る(超長exp、role配列の注入、複数テナントidなど)。1つのsecretは認証チェーン全体のマスターキーであり、使い尽くす。

### tokenが期限切れ/リプレイを検証しないロジック脆弱性
**Q1**: 署名を攻められない場合、トークンのライフサイクルに脆弱性がないか体系的に検証するにはどうするか。
**A1**: 項目ごとに確認する:1) 期限切れ(exp経過)の旧トークンをリプレイし、まだ受理されるかを見る。2) ログアウト後に元のトークンが無効化されるか。3) パスワード変更後に旧トークンが無効化されるか。4) 同一トークンを複数デバイス/複数IPから並行使用できるか。各項目が独立したターゲット。
**Q2**: 期限切れトークンがまだ使えると判明した場合、何を意味し、どう拡大するか。
**A2**: サーバー側がexpを検証していない、またはクロック/検証ロジックに欠陥があることを示す。拡大方向:そうであれば、あらゆる漏えい(ログ、Referer、キャッシュ、過去のトラフィック)に含まれる旧トークンが長期間有効になり、価値が跳ね上がる。他の漏えい点と組み合わせて過去のトークンを収集する。
**Q3**: ログアウト後もトークンが有効な場合、レッドチームにとっての価値はどこにあるか。
**A3**: ステートレスJWTによくある問題(サーバー側がブラックリストを保持しない)。価値:トークンを一度入手すれば(被害者がログアウト済みでも)、永続アクセスは相手の「ログアウト」に影響されない。これは「ステートレスJWT」か「ステートフルセッション」かを判断するプローブでもある。
**Q4**: ステートレスか、サーバー側にセッションテーブルがあるかをどう区別するか。
**A4**: payloadのうち署名保護外のものを改ざんするのは現実的ではないが、観察はできる:サーバー再起動後にトークンがまだ有効か(有効→ステートレス)、ログアウトが即時に無効化されるか(即時→ステートフルのブラックリスト)。これに基づき以降の攻め方を選ぶ。
**Q5**: これらのロジックテストがすべて問題なし(すべて正しく無効化される)の場合、どこへ方向転換するか。
**A5**: ライフサイクル管理が健全であることを示す。【偽造/リプレイ】ではなく、トークンの【取得経路】へ方向転換する:XSSでトークンを盗む、トークンの保存場所(localStorage vs HttpOnly cookie)、CSRF、そしてOAuthフロー内のトークン漏えい点(redirect、Referer、ログ)。攻撃は「資格情報の偽造」から「資格情報の窃取」へ転換する。
**Q6**: 見落とされやすい項目はあるか。
**A6**: `nbf`(not before)とクロックオフセット、そしてrefresh tokenのローテーション/再利用検知。多くの実装はaccess tokenだけに注目し、refresh tokenは無限に再利用できたりローテーションされなかったりする。これは永続化の価値の高い資産で、しばしばテスト漏れになる。

### OAuth redirect_uriのオープンリダイレクト/token窃取
**Q1**: OAuth認可フローに入る際、最初に注目するパラメータは何か。
**A1**: `redirect_uri`。これは認可コード/tokenの返送先を決める。まずその検証の厳格度を測る:制御可能なドメインに変えられるか、パスを変えられるか、パラメータを追加できるか、部分一致か完全一致か。これはOAuthで最も頻出する入口。
**Q2**: ドメインの完全な置換が拒否された場合、他にどのような迂回方法があるか。
**A2**: 層を分けて試す:同一ドメイン内のオープンリダイレクト(redirect_uriはホワイトリストのドメインのまま、そのドメインにコードを自分へ転送する踏み台APIがある)、パストラバーサル、`?`/`#`/`@`/バックスラッシュの追加、サブドメインのワイルドカードが過度に緩い、大文字小文字とエンコードの変種、そして`localhost`/プライベートアドレスがホワイトリストにあるか。
**Q3**: 結局何を盗みたいのか、codeかtokenか。
**A3**: response_typeを見る。`code`フローでは認可コードを盗む(さらにtokenへ交換できる必要がある、またはPKCE欠如と組み合わせる)。`token`(インプリシットフロー)はfragment内のaccess tokenを直接盗む。インプリシットフローの漏えいはより直接的で、利用可能なインプリシットフローがないか優先的に見る。
**Q4**: codeを盗んだがtokenへ交換できない場合、どこで詰まり、どう打開するか。
**A4**: 通常はclient_secretの欠如かPKCEの存在。打開策:PKCEが本当に必須かを確認する(code_challengeを外しても通るか)、client_secretがフロントエンド/ドキュメントに漏えいしていないか、codeを再利用できるか/別のclientで使用できるか。PKCEが厳格でsecretが秘匿されているなら、code窃取のリターンは限定的なので、インプリシットフローか別のパラメータへ移る。
**Q5**: redirect_uriが全面厳格で、リダイレクトの次元全体が遮断された場合、どこへ方向転換するか。
**A5**: OAuthの他の制御可能なパラメータとロジックへ移る:`state`欠如→CSRF/ログイン混同、`scope`の権限昇格、認可コードの紐づけが緩い→code injection/置換攻撃、そしてaccount linkingフローの身元混同。redirectはOAuthの唯一の弱点ではない。
**Q6**: 他人のaccess tokenを入手した後、影響範囲をどう評価するか。
**A6**: トークンでresource serverとuserinfoエンドポイントを攻め、実際のscope、アクセスできるAPI、アプリケーションをまたいで再利用できるか(同一IdPで複数clientが共有)を列挙する。それが「単一アプリケーションの資格情報」か「身元プラットフォーム全体の通行証」かを評価し、戦果の報告レベルを決める。

### OAuth state欠如によるログインCSRF / アカウント乗っ取り
**Q1**: OAuthリクエストで`state`パラメータが欠如している、または検証されない場合、何ができるか。
**A1**: stateはCSRF対策の紐づけ値。欠如は「自分のアカウントを被害者のセッションに紐づける」または「被害者のサードパーティアカウントを自分のアカウントに紐づける」機会を得られることを意味し、ログインCSRFやアカウント乗っ取りを形成する。まず「誰のcodeが、誰のセッションに落ちるのか」を明確に考える。
**Q2**: 具体的にどうアカウント乗っ取りを構成するか。
**A2**: 定番のaccount linkingシナリオ:被害者に【自分の】認可codeを含むコールバックリンクをクリックさせ、被害者が現在ログイン中のアカウントを自分が制御するサードパーティ身元にリンクさせる。その後、そのサードパーティ身元でログインする=被害者アカウントにログインする。判定基準:紐づけ操作がstateを検証せず、二重確認もしない。
**Q3**: 逆に、pre-account-takeoverはどう進めるか。
**A3**: 対象が「まずメールで登録し、その後同じメールでOAuthログインすると自動マージされる」ことを許可する場合、先に被害者のメールでプレースホルダー登録し、被害者が後でOAuthで初回ログインすると、自分がパスワードを知るアカウントにマージされる。核心は「メールが身元の主キーでありながら検証が欠如している」こと。
**Q4**: stateは実際に存在するが検証されていないと疑う場合、どう確認するか。
**A4**: stateの値を変更/削除/固定値へ置換し、フローが通常どおり完了するかを見る。通常どおりなら検証されていない。さらにstateがセッションと強く紐づいているかを確認する(別セッションのstateで通るか)。
**Q5**: stateの検証が厳格で、ログインCSRFの線が断たれた場合、どこへ方向転換するか。
**A5**: 身元混同の他の面へ移る:IdPが返すメール/subが検証されないまま信頼されているか(未検証メールも検証済みとして扱う)、複数IdPで同じメールが異なるprovider間で混用されないか、`nonce`欠如によるid_tokenリプレイ。「CSRFの紐づけ」から「身元クレームの信頼度」へ移る。
**Q6**: この種のロジック脆弱性を、実ユーザーに誤って影響を与えずに低リスクで検証するにはどうするか。
**A6**: 自分が制御する2つのアカウント(攻撃者アカウント+模擬被害者アカウント)を自分のブラウザ/2つのセッション間で再現し、実ユーザーには一切触れない。レッドチームのレポートはPoCが制御可能で再現可能であることを自ら証明できる必要があり、運任せにしてはならない。

### OIDC id_tokenの検証ブラインドスポット
**Q1**: OIDCのid_token(JWT)を入手した場合、通常のJWTとの攻撃上の違いはどこにあるか。
**A1**: id_tokenにはOIDC特有のclaimが増える:`iss`、`aud`、`nonce`、`azp`、`at_hash`。攻撃面はJWT汎用の一連に加え、「これらのclaimをクライアントが真剣に検証しているか」が増える。多くのクライアントは署名のみ検証し、iss/aud/nonceを検証しない。
**Q2**: iss/audが検証されないと何ができるか。
**A2**: クライアントが`aud`を検証しない場合、同一IdPが【別のclient】へ発行したid_tokenを対象のclientへ直接渡し、身元を偽る(token混同/audience confusion)。`iss`を検証しない場合、自分で構築したIdPが署名したtokenさえ使える。
**Q3**: nonceの欠如または不検証の結果は何か。
**A3**: id_tokenをリプレイできる。一度傍受したid_tokenを繰り返し送信してログインを完了できる。判定基準:同一id_tokenを2回送信しても両方成功する、またはnonceを変えても結果に影響しない。
**Q4**: クライアントがid_tokenをaccess tokenとして使っていると疑う場合、何が問題か。
**A4**: 混用はid_tokenの緩い検証が認可判断に使われることを意味し、上述のすべてのclaim検証欠陥の影響を増幅する。テスト:id_tokenで保護されたAPIを直接呼び出せるか。
**Q5**: すべてのclaimが厳格に検証され、OIDC層に穴がない場合、どこへ方向転換するか。
**A5**: IdPとclientの間の【フロー】へ移る:認可コードフローのcodeの紐づけ、PKCE、そしてIdP自体の設定(dynamic client registrationが開いているか、redirect_uriのホワイトリスト)。SAML/その他併存するSSOプロトコルへ移ることもできる。同じ対象には複数プロトコルが併存することが多く、1つが厳格でもすべて厳格とは限らない。
**Q6**: 複数プロトコルのSSOに対して、どう突破口を選ぶか。
**A6**: 実装が最も「手書き」で、成熟したライブラリの利用が最も少ないものを選ぶ。SAMLのXML解析、自社開発のトークン交換、旧式のCASプロトコルは、標準のOIDCライブラリより脆いことが多い。偵察段階で対象が対応するすべてのログイン方式を列挙し、最も素朴なものを狙う。

### SAMLアサーションと署名ラッピング攻撃(XSW)
**Q1**: 対象がSAML SSOを使う場合、何を優先してテストするか。
**A1**: 署名検証の頑健性を優先してテストする。特にXML Signature Wrapping(XSW)。SAMLアサーションはXMLであり、署名が保護するノードとアプリケーションが実際に読み取るノードが同じとは限らない。この食い違いがXSWの根源。まず合法的なSAMLResponseをキャプチャしてベースラインとする。
**Q2**: XSWの核心操作は何か。
**A2**: XMLに自分が偽造したアサーションを挿入し(NameID/attributeを対象ユーザーに変更)、元の署名済みアサーションも残す。ノードの位置/id参照を調整し、署名検証には元のものを検証させ、アプリケーションには自分が偽造したものを読み取らせる。複数のXSW変種(古典的レイアウトがいくつかある)を一つずつ試す。
**Q3**: アプリケーションがどのノードを読むのか、どう知るか。
**A3**: レスポンスを観察する:偽造アサーションのNameIDを異なる値に変え、最終的に誰としてログインするかを見る。誰が有効になるかで、アプリケーションがどのノードを読んだかが分かる。このフィードバックで「署名検証ノード」と「データ読み取りノード」の食い違い箇所を特定する。
**Q4**: 対象が署名をまったく検証しない、または署名を除去できることを素早く見つけるにはどうするか。
**A4**: まず最も手間がかからないものを試す:`<Signature>`要素を直接削除する、またはアサーションを書き換えて再署名せずに送信する。それでもログインできるなら、署名がまったく検証されていない(XSWより深刻で単純)。常にまず「署名検証があるか」を試してから、複雑なXSWに進む。
**Q5**: ライブラリが新しく、XSWの全変種が失敗し、署名検証が厳格な場合、どこへ方向転換するか。
**A5**: SAMLの署名以外の面へ移る:アサーションのリプレイ(`NotOnOrAfter`/`OneTimeUse`の検証がない)、`Recipient`/`Audience`の不検証(別の宛先へ発行されたアサーションを流用する)、IdP-initiatedフローの受け入れ、そしてXXE(SAMLはXMLであり、パーサーが外部エンティティを取り込む可能性がある)。SAMLメッセージ自体がXXEの天然の媒体。
**Q6**: SAMLで見落とされがちな高価値ポイントは他に何があるか。
**A6**: NameID/属性内のインジェクションと身元混同:commentの切り詰め(`admin<!---->@evil.com`がadminとして解析される)、大文字小文字/正規化の差異によるユーザー照合の食い違い。そしてIdPメタデータを置換できれば、信頼の根を直接変更できる。これらのロジック面は暗号学的な面よりリターンが高いことが多い。

### session cookieとJWTが併存する場合の選択
**Q1**: 対象がsession cookieとJWTを同時に使う場合、どちらを攻めるべきか。
**A1**: まず「どちらが権威か」を把握する。cookieが主でJWTが補助のシステムもあれば(またはその逆)、両方を並行して検証するもの、ダウングレード経路があるものもある。「どの資格情報が実際に認可を決めるか」と「片方だけを持って他方の検証を迂回できるか」を見つける。
**Q2**: この関係をどう探るか。
**A2**: 変数を制御する:cookieのみでJWTなし、JWTのみでcookieなし、矛盾する両方(cookieがユーザーA、JWTがユーザーB)を送り、各APIの挙動を観察する。矛盾状態が「どちらが決定権を持つか」と信頼の混乱の有無を最もよく露呈する。
**Q3**: あるAPIはcookieのみを認識し、あるAPIはJWTのみを認識すると判明した場合、どう活用するか。
**A3**: この不一致は権限外アクセスの温床。ある高権限APIが弱いほうの資格情報を誤って信頼しているなら、弱い資格情報を狙って偽造すればよい。「2つの認証の境界の隙間」を攻撃面として扱う。
**Q4**: 両方が厳格で隙間がない場合、どこへ方向転換するか。
**A4**: 取得の次元へ移る:cookieはXSS/CSRF/固定/SameSite設定を攻める。JWTは保存場所と漏えいを攻める。CSRFへも移る。JWTをcookieに入れて自動送信するならCSRFの可能性があり、headerに入れるなら本質的にCSRFに耐性がある。これに基づき経路を選ぶ。
**Q5**: session cookie自体でテストすべき定番ポイントは何か。
**A5**: session fixation(ログイン前後でsession idが変わるか)、予測可能性、HttpOnly/Secure/SameSiteの欠如、サブドメインをまたぐ作用範囲が広すぎる、そしてサーバー側のsessionデシリアライズ(一部フレームワークはsessionにシリアライズされたオブジェクトを保存→デシリアライズRCE)。
**Q6**: sessionにシリアライズされたオブジェクトがあると判明した場合、この線をどう昇格させるか。
**A6**: 即座に「認証バイパス」から「RCEの試行」へ昇格させる:シリアライズ形式を判断し(言語/フレームワークの特徴)、対応するgadgetチェーンを探す。認証攻撃は時にコード実行への入口であり、権限外アクセスの層で止まってはならない。

### cookie属性と作用域設定の攻撃
**Q1**: 対象のauth cookieを入手した場合、どの属性を項目ごとに検査すべきか。
**A1**: `HttpOnly`(欠如→XSSで盗める)、`Secure`(欠如→平文で傍受できる)、`SameSite`(None/欠如→CSRF)、`Domain`(広すぎ→サブドメインから読み書きできる)、`Path`、そして`__Host-`/`__Secure-`プレフィックスが偽造利用されるか。各欠如はそれぞれ盗み/偽造/リプレイの経路に対応する。
**Q2**: Domainが親ドメイン(`.example.com`など)に設定されている場合、何を攻められるか。
**A2**: 任意のサブドメインがそのcookieを読み書きできる。1つのサブドメインを制御できるなら(サブドメイン乗っ取り、ユーザーコンテンツのサブドメイン、テスト用サブドメイン)、auth cookieを読み取るか注入でき、サブドメインをまたぐセッション攻撃を形成する。判定基準:まずサブドメインを列挙し、制御可能/乗っ取り可能なものを探す。
**Q3**: SameSite=Laxのとき、CSRFにまだ可能性はあるか。
**A3**: 条件付きで可能性がある。LaxはトップレベルナビゲーションのGETでは依然cookieを送信するため、機密操作がGETを受け付ける、またはメソッドオーバーライド(`_method`)があるなら、CSRFは依然成立する。さらにLaxの短い猶予ウィンドウ、サブドメイン/同一サイトのリクエストが制限されないこともある。Laxを見てCSRFを諦めてはならない。
**Q4**: cookie属性がすべて完璧に設定されている場合、どこへ方向転換するか。
**A4**: cookieの解析/インジェクションの面へ移る:cookie名の衝突(同名で複数値、フロントエンドとバックエンドで取得値が不一致)、cookie tossing(サブドメインが同名cookieを書き、メインドメインのものを押しのける)、そして`__Host-`プレフィックスの迂回。「属性の防御」から「cookie解析の曖昧さ」へ移る。
**Q5**: cookie tossingの具体的な脅威モデルは何か。
**A5**: 制御可能なサブドメインからauth/csrf関連の同名cookieを書き、ブラウザがそれを一括送信する。サーバー側が「誤ったもの」を取得すると、自分に固定/汚染される可能性がある。CSRF token固定やセッション固定を攻めるのによく使う。前提は制御可能なサブドメインがあること。
**Q6**: 制御可能なサブドメインがない場合、これらは難しくなる。最後の退路は何か。
**A6**: 最も直接的なものへ戻る:cookieがURL/ログ/Refererで漏えいしないか、予測可能か、ログイン後に変更されないか。そしてcookieから完全に離れ、JWT/OAuth/SAMLの3本の本線へ移る。認証攻撃は複数プロトコルを並行して進め、1つが塞がれたら別のものへ切り替える。

### JWTの保存場所が決める窃取経路
**Q1**: 対象のJWTを盗みたい場合、まず何を明らかにする必要があるか。
**A1**: まずトークンがどこに保存されているかを特定する:HttpOnly cookie(JSでは盗めず、CSRF/ネットワーク経由)、localStorage/sessionStorage(XSSで直接読める)、メモリ/JS変数、それともURL/fragment。保存場所がどの盗み方を使うかを直接決めるため、道具を間違えてはならない。
**Q2**: localStorageに保存されていると判明した場合、攻撃チェーンをどうつなぐか。
**A2**: その場合、トークン窃取の前提は「XSSできるか」に変わる。XSSがあれば1行のJSでトークンを読み取って外部へ持ち出す。XSSがなければDOM sink、サードパーティスクリプト、依存関係の汚染などの間接的なJS実行経路を探す。認証の問題をXSSの問題に変える。
**Q3**: HttpOnly cookieでJSから盗めない場合、どうするか。
**A3**: JSの読み取りに依存しない経路へ移る:CSRF(cookieを伴ってリクエストを自動送信し、被害者の代わりに操作する)、ネットワーク層での傍受(HTTPSなし/混合コンテンツ)、またはサーバー側にcookieを反射させる(一部のdebug/エラーページがリクエストヘッダーを表示する)。HttpOnlyは読み取りを防ぐが、利用は防がない。
**Q4**: tokenがURLやfragmentに現れる場合のリスクポイントは何か。
**A4**: URL内のtokenはブラウザ履歴、サーバーログ、Refererヘッダー(外部へ遷移した際に漏えい)、そして共有/ブックマークに入る。被害者のブラウザにtokenを伴わせて自分のドメインへ遷移させるポイント(外部リンク、オープンリダイレクト)を探し、Refererからtokenを受け取る。
**Q5**: tokenがよく保護され、XSSも漏えい点もない場合、どこへ方向転換するか。
**A5**: 窃取ではなく偽造へ移る(署名/ロジック攻撃へ戻る)、または下流へ移る:tokenがバックエンドに渡った後、バックエンドはどうマイクロサービスへ渡すのか。サービス間でtokenを平文送信するか、ログに記録するか、SSRFで内部のtoken付きリクエストを読めるか。窃取の戦場はブラウザからサーバー側内部へ前進する。
**Q6**: tokenを盗んだ後、どう制御を延長するか。
**A6**: 即座にrefresh tokenを探す。access tokenは短命で、refresh tokenこそが永続化の鍵。refreshも一緒に盗めるか、refreshがローテーションされるか、無限に更新できるかを確認する。永続アクセスはrefreshに依存し、使い捨てのaccessには依存しない。

### 権限外アクセス:token内の権限フィールドの改ざんプローブ
**Q1**: tokenに`role`/`scope`/`is_admin`/`tenant_id`のようなフィールドがある場合、どう体系的に権限外アクセスを探るか。
**A1**: 署名を変えられなくても、まず「権限モデルを読み解く」:これらのフィールドの取り得る値を列挙する(異なる権限の複数アカウントのtokenを比較して得る)。低権限tokenを入手した後、目標はサーバー側に自分を高権限として扱わせること。方法は2つ:偽造(署名を破る必要がある)か、サーバー側が「tokenのフィールドに完全には依存しない」ロジックの隙間を探す。
**Q2**: サーバー側がtokenのフィールドを完全には信頼しない可能性があるが、これをどう活用するか。
**A2**: 多くのシステムはtokenにroleを持つが、実際の認証・認可ではデータベースや別のheaderを照会する。テスト:リクエスト内の`X-User-Id`/`X-Role`などの補助ヘッダーを変更する、URL内のリソースidを他人のものに変える(IDOR)。権限フィールドと実際の認証・認可のどちらが効くかを見る。隙間はしばしばここにある。
**Q3**: マルチテナントのtenant_idフィールドをどう攻めるか。
**A3**: 偽造できる、またはサーバー側の分離が厳格でないなら、tenant_idを変えてテナントをまたぐアクセスを実現する。署名で固められていても、IDORをテストする:URL/body内のリソースidがtokenのtenantにのみ拘束されるか、別テナントのidに変えると越境するか。マルチテナントの分離はtoken層ではなくアプリケーション層で誤ることが多い。
**Q4**: 比較テストに2つのアカウントが必要だが、2つ目のアカウントを入手できない場合はどうするか。
**A4**: 2つ目を自ら登録する方法を考える(異なる権限レベル)。登録できないなら、同一アカウントの異なる状態(昇格の前後)を使うか、token構造から権限フィールドの形式を逆算して推測値を構成する。比較テストは権限外アクセス発見の最も効率的な手段であり、アカウント入手に投資する価値がある。
**Q5**: tokenのフィールドを変えられず、IDORもすべてサーバー側で検証される場合、どこへ方向転換するか。
**A5**: 横展開の「機能レベルの権限外アクセス」へ移る:データidの権限外アクセスではなく、高権限の【API/動作】(admin APIパス、内部エンドポイント)を呼び出せるか。そして「権限昇格チェーン」へ移る:一般ユーザーが自分のroleを変更するAPIに触れられるか(たとえばプロフィール更新にroleフィールドを混入するmass assignment)。
**Q6**: mass assignmentの線をどう素早く試すか。
**A6**: 任意の「ユーザー情報更新」系リクエストbodyに、`role`/`is_admin`/`permissions`などのフィールドを追加し、サーバー側がそのまま受け取るかを見る。これはトークンの署名制限を迂回してバックエンドの権限レコードを直接変更する定番の近道で、コストが極めて低いため優先して試す。

### JWT headerインジェクションとtyp混同
**Q1**: alg以外に、headerで何を試せるか。
**A1**: `typ`(一部の実装は`JWT`と`at+jwt`などを区別し、混同によりトークンが誤った文脈で受理される可能性がある)、`cty`、そしてカスタムheaderフィールド。さらに`crit`パラメータ。サーバー側がcritical headerを正しく処理しない場合、本来強制されるべき検証を無視する可能性がある。異常値を一つずつ入れて観察する。
**Q2**: typ混同の実際のシナリオは何か。
**A2**: 1つのシステム内でaccess tokenとrefresh token、またはid_tokenとaccess tokenがすべてJWTだがtypが異なる可能性がある。サーバー側がtypを検証しないなら、refresh tokenをaccess tokenとして使う、またはその逆ができ、トークンの用途分離を突破できる。
**Q3**: この用途分離の欠如をどう発見するか。
**A3**: 交差して与える:A用途のトークンをB用途のエンドポイントへ送る。受理されたら分離が機能していない。これは純粋なロジックテストで、暗号学を破る必要はなく、早期に全マトリクスを一巡するべき。
**Q4**: headerに未知のフィールドを入れると、通常どのような反応があるか。
**A4**: 多くのライブラリは未知のheaderを無視し、成果はない。ただし解析例外/異なるエラーコードを引き起こすなら、headerを処理していることを示し、解析の差異を辿る価値がある。判定基準は依然「レスポンスが変わるか」。
**Q5**: header層でまったく成果がない場合、どこへ方向転換するか。
**A5**: payloadの解析の頑健性へ移る:claimの重複(同名の`role`が2つある場合、どちらを取るか)、claimの種別混同(`role`が文字列を期待するのに配列/オブジェクトを与える)、超大/超長の値、Unicode正規化。JSON解析の曖昧さは、署名が正当なトークンを誤って解釈させる可能性がある。
**Q6**: これらの解析攻撃は、どうすれば価値があるといえるか。
**A6**: 対象に【複数のコンポーネントが同一トークンをそれぞれ解析する】構造があるときに価値が最大になる:署名検証のライブラリと業務フィールドを読み取るコードが異なるJSONパーサーを使う場合、claimの重複で「署名検証は安全な値を見て、業務は悪意のある値を読む」状態を作れる。ゲートウェイ+バックエンドの二重解析アーキテクチャがあるかを偵察し、この線の深浅を決める。

### 認可コード/PKCEフローの実装欠陥
**Q1**: 対象が認可コード+PKCEを使う場合、まだどのポイントを攻められるか。
**A1**: PKCEは万能ではない。テスト:1) `code_challenge`を外しても通るか(PKCEが必須でない)、2) `code_challenge_method`を`plain`へダウングレードできるか、3) code_verifierが実際にchallengeと紐づけて検証されるか、4) 認可コードが使い捨てか、短い有効期限があるか。実装を1項目ずつ突く。
**Q2**: PKCEが必須でないことは何を意味するか。
**A2**: PKCEなしの認可コード窃取へ後退できることを意味する(redirect_uriの欠陥と組み合わせてcodeを盗めばtokenへ交換できる)。これは「PKCEがあるから安全」という前提を直接崩す。価値の高い発見であり、優先して検証する。
**Q3**: methodをplainへダウングレードできると何の役に立つか。
**A3**: plainモードではchallengeはverifierの平文そのもの。challengeがフロー中に漏えいすると(URL/ログ)、verifierの漏えいに等しく、PKCEは形骸化する。サーバー側が`plain`を受け付けるかテストする。
**Q4**: 認可コードをリプレイできる/別のclientで使用できる場合、どう攻めるか。
**A4**: 認可コードは本来使い捨てで、単一のclientとredirect_uriに紐づくべき。テスト:同一codeで2回tokenを交換する、client Aのcodeをclient Bでtoken交換する。いずれかが成功すれば深刻なcode injectionの面。
**Q5**: PKCEとcodeの検証がすべて厳格な場合、どこへ方向転換するか。
**A5**: tokenエンドポイント自体へ移る:clientの認証方式(client_secretが弱い/漏えい/空にできるか)、`grant_type`をより緩いものへ切り替えられるか(password grant / client_credentialsの権限外アクセスを許可するなど)、refresh_token grantの悪用。「認可段階」から「トークン交換段階」へ移る。
**Q6**: grant_typeの切り替えの線を具体的にどう探るか。
**A6**: tokenリクエストで`grant_type`を変更して各種の値を試し、想定外に有効な認可モードがないかを見る(`password`でユーザー名とパスワードから直接tokenを交換しフロントエンドのフローを迂回する、`client_credentials`でサービス級tokenを取得するなど)。設定の見落としは余分なgrant typeを残すことが多く、見落とされた裏口になる。

### refreshローテーションなしの永続化利用
**Q1**: refresh tokenを入手した場合、その永続化の価値をどう評価するか。
**A1**: 3点をテストする:1) それでaccess tokenを交換した後、旧refreshが無効になるか(ローテーションか)、2) 同一refreshを連続で何回使えるか、3) refreshの有効期間の長さと無限に更新できるか。ローテーションなし+長い有効期間=永続的な裏口級の資産。
**Q2**: refreshがローテーションされないと判明した場合、レッドチームはどう使うか。
**A2**: refreshを一度盗めば、長期間(数週間から数か月)自己でaccessを更新できる。被害者がパスワードを変更/ログアウトしてもrefreshを失効させない限り制御は続く。これはaccess tokenより1桁上の戦果であり、重点的に保全し報告する。
**Q3**: refreshはローテーションされるが、「再利用」を検知するか。
**A3**: 安全な実装は旧refreshの再利用を検知するとチェーン全体を失効させる(reuse detection)。テスト:新しいrefreshを交換した後で旧refreshを使い、チェーン全体の失効が起きれば検知があることを示す。その場合、自分が持つ窃取refreshは、本来の持ち主も使うと露呈/失効する。これに基づき利用のタイミングを決める。
**Q4**: 利用が発見される確率をどう下げるか。
**A4**: reuse detectionがあるなら、実ユーザーと同じチェーンを並行して使うのを避ける。ローテーションがないなら、目立たず長期利用できる。レッドチームはrefreshの仕組みに応じて「電撃的な利用」か「潜伏的な利用」を選ぶ。
**Q5**: refreshの仕組みが厳格(ローテーション+検知+短期)で、永続化の線が弱い場合、どこへ方向転換するか。
**A5**: 他の永続化手段へ移る:長期API keyの申請/偽造、OAuthのoffline_accessによる長期認可、新しいOAuth clientの作成、またはアカウント層に裏口を残す(予備メール/MFAデバイス)。資格情報の永続化はrefreshだけが経路ではない。
**Q6**: refresh関連攻撃で最も漏れやすいポイントは何か。
**A6**: refresh tokenとaccess tokenの作用域が一致するか。一部の実装はrefreshで元のscopeより大きいtokenへ交換できる(scopeの権限昇格)。これは純粋なロジックの権限外アクセスで、しばしばテスト漏れになる。token交換時にわざと大きいscopeを要求して試す。

### JWT暗号化(JWE)とネストされたtokenの攻撃面
**Q1**: tokenが3セグメントではなく5セグメント(JWE)の場合、攻め方はどう変わるか。
**A1**: 5セグメントはJWE(暗号化)で、JWS(署名)ではない。headerの`alg`(鍵管理)と`enc`(コンテンツ暗号化)が重点。攻撃面:鍵管理アルゴリズムのダウングレード、`alg:dir`/RSA関連の定番padding oracle(Bleichenbacher系)、そして`zip`ヘッダー経由のzip bomb。
**Q2**: JWEにはどの定番の暗号学的攻撃があるか。
**A2**: RSA1_5(PKCS#1 v1.5)で鍵カプセル化する場合、Bleichenbacher padding oracleが存在する可能性があり、CEKを段階的に解ける。判定基準:サーバー側から「復号成功/paddingエラー」の区別可能なレスポンス(oracle)を得られるか。oracleがあれば攻められる。
**Q3**: 区別可能なoracleがない、または現代的なアルゴリズムを使う場合はどうか。
**A3**: その場合、暗号学的攻撃の線はほぼ塞がる。JWEの実装の落とし穴へ移る:`alg:none`系の無保護変種を受け付けるか、アルゴリズム混同があるか(signing keyをencryption keyとして使う)、そしてネストされたJWT(JWE内にJWSを包む)の検証が両層で行われるか。
**Q4**: ネストされたtokenに多い見落としは何か。
**A4**: 外層を復号した後、内層のJWSの署名が再検証されない可能性がある(暗号化すれば十分と思われている)。テスト:内層の署名が無効だが外層の暗号化は正しいトークンを構成し、受理されるかを見る。暗号化≠認証であり、これはよくある混同。
**Q5**: JWEの線が硬すぎる(現代的アルゴリズム+厳格な実装)場合、どこへ方向転換するか。
**A5**: 思い切って暗号学層から離れる。JWEは通常、チームのセキュリティ成熟度が高いことを意味する。リソースを業務ロジックの権限外アクセス、OAuthフロー、SSO統合の接合部へ投じるほうが、暗号化に固執するよりはるかにリターンが高い。
**Q6**: JWEに対する心構えの判断は何か。
**A6**: JWEの存在を「ここは暗号学的攻撃の費用対効果が低い」というシグナルとして受け止め、ダウングレード/ネスト検証の2つの低コストポイントを素早く一巡し、外れたら撤退する。レッドチームは「防御強度のシグナル」を読んで労力を配分できる必要がある。

### サービス間token受け渡しとSSRFの連動
**Q1**: フロントエンドのtokenがバックエンドに届いた後、バックエンドはそれをどう内部サービス呼び出しに使うか。ここで何を攻められるか。
**A1**: マイクロサービスアーキテクチャでは、ゲートウェイが外部tokenを検証した後、内部サービスへ身元を渡すことが多い(元のtokenを転送する、内部service tokenに交換する、または`X-Authenticated-User`のような内部ヘッダーを付与する)。内部へ到達できれば、これらの内部信頼ヘッダーはしばしば【署名がなく、偽造可能】。
**Q2**: どう内部へ到達し、内部信頼ヘッダーを活用するか。
**A2**: SSRFと組み合わせる:サーバー側にリクエストを代行させるポイントを探し、内部サービスを直接攻めて偽造した`X-User`/`X-Role`ヘッダーを付与する。内部サービスは通常、ゲートウェイから来たヘッダーを盲信する。SSRF+内部認証の欠如=権限外アクセスへの直行。
**Q3**: 外部リクエストに内部ヘッダーを直接入れるとどうなるか。
**A3**: ゲートウェイがクライアント由来の内部ヘッダーを除去するかをテストする。多くのゲートウェイは剥がし忘れており、外部から`X-Authenticated-User: admin`を直接送ると内部で信頼される。これはゼロコストで高リターンなので、早い段階で試すべき。
**Q4**: ゲートウェイが内部ヘッダーを正しく剥がし、SSRFもない場合、どこへ方向転換するか。
**A4**: 境界へ戻る:内部の信頼が外部から得られないなら、外部token自体の突破(前述の各項目)に集中するか、SSRF/RCEで内部ネットワークへ侵入してから内部の信頼面へ戻る。内部認証の欠陥は「侵入後」の権限昇格の踏み台であり、先に足場が必要。
**Q5**: 内部service tokenを入手した後、どう戦果を拡大するか。
**A5**: 内部のservice-to-service tokenは通常権限が大きく、検証が緩い。それで他の内部APIを横展開で呼び出し、サービス一覧を列挙し、それが信頼する下流へアクセスする。1つの内部tokenはサービスメッシュ全体の通行証になり得て、価値が極めて高い。
**Q6**: この線の偵察段階で何を収集すべきか。
**A6**: アーキテクチャ情報を収集する:レスポンスヘッダー内のゲートウェイの特徴、内部サービス名/パスの漏えい(エラーメッセージ、swagger、js設定)、tokenの各層での形態変化。信頼のトポロジーを理解してこそ、「どのホップの認証が最も弱いか」を特定できる。

### MFAとSSOの迂回の接合部
**Q1**: 対象にMFAがある場合、認証攻撃にまだ可能性はあるか。どこから隙間を探すか。
**A1**: ある。MFAはしばしば「ログイン」の一歩だけを保護し、token/sessionが一度発行されればMFAを迂回できる。「MFA後のtoken発行の漏えい/偽造点」、または「MFAのステップを飛ばして認証済み状態へ直行する」フローの欠陥を探す。MFAが保護するのは入口であり、入口より後の資格情報ではない。
**Q2**: MFAステップを飛ばすことを具体的にどう試すか。
**A2**: ログインの複数ステップフローを観察する:パスワード入力後にMFAページへ入る際、すでに部分的/完全な資格情報が発行されているか。MFA後のAPIを直接リクエストして検証を飛ばせるか。MFA検証はフロントエンドで強制か、バックエンドで強制か。バックエンドで強制でなければ直接飛ばせる。
**Q3**: SSOのシナリオでMFAにはどの特殊な迂回方法があるか。
**A3**: SSOではMFAをIdPが担うことが多く、SPはIdPのアサーションを信頼する。あるログイン経路(予備IdP、レガシープロトコル、IdP-initiated)がMFAをトリガーしないなら、迂回できる。すべてのログイン入口を列挙し、MFAを強制しないものを探す。
**Q4**: remember-me / trusted-deviceの仕組みをどう攻めるか。
**A4**: この種の仕組みは、以降のMFAを飛ばすために長期の資格情報を発行する。その資格情報が予測可能、窃取可能、紐づけが緩い(デバイス/IPを変えても有効)なら、MFA免除の裏口になる。その紐づけの強度と偽造可能性を重点的にテストする。
**Q5**: MFAの各ステップがバックエンドで強制され、SSOの全経路でMFAが統一され、trusted-deviceの紐づけが厳格な場合、どこへ方向転換するか。
**A5**: アカウント復旧フローへ移る:パスワードリセット、MFAリセット/復旧コードはしばしばMFAの弱い脇口。そしてセッション層へ移る。MFAを迂回できないなら、MFA後のsession/tokenを直接盗む(XSS/CSRF/ネットワーク)。防衛の最弱点はしばしば「ログイン」ではなく「復旧」にある。
**Q6**: アカウント復旧の線がなぜ優先に値するか。
**A6**: 復旧フローはユーザーが資格情報を失ったときにも身元を確認できる必要があり、本質的に「検証強度を下げる」という矛盾の中にある:復旧コードをブルートフォースできる、リセットリンクが予測可能/期限切れにならない、リセットが既存セッションを失効させない、カスタマーサポートのソーシャルエンジニアリング面。それはすべてのフロントエンド認証強度を迂回するメタ入口。

### 認証APIの列挙とレート制限の迂回
**Q1**: 認証APIをブルートフォース/列挙したい場合、まず何を判断するか。
**A1**: まずレート制限/ロックの有無と、「ユーザー名列挙」が可能か(ログイン/登録/パスワード再発行のレスポンス差異でユーザーの存在を区別できるか)を判断する。有効なユーザーを列挙することが、以降のすべてのブルートフォースの前提。レスポンス時間、エラーメッセージ、HTTPコードはすべて列挙のシグナル。
**Q2**: レート制限がある場合どう迂回するか。
**A2**: よくある迂回方法:送信元IPのローテーション(`X-Forwarded-For`/`X-Real-IP`が信頼される場合)、分散リクエスト、間隔を延ばして時間窓を避ける、レート制限のない予備エンドポイントへ切り替える(モバイルAPI、旧バージョンAPI)、そしてパスワードスプレー(各ユーザーに少数の高頻度の弱いパスワードのみを試し、単一アカウントのロックを避ける)。
**Q3**: アカウントロック方針の下で、実ユーザーをロックしてしまうのをどう避けるか。
**A3**: brute forceではなくスプレーを使う:横展開で1つのパスワードを全ユーザーに試し、縦には単一アカウントの試行回数をロックしきい値未満に抑える。効率的で、ロックのアラートも発火しない。レッドチームは自制し、対象ユーザーをすべてロックして対応を誘発してはならない。
**Q4**: XFF系ヘッダーが信頼されず、レート制限が厳格な場合、どこへ方向転換するか。
**A4**: オンラインのブルートフォースから離れる。オフラインでブルートフォース可能な資産を探す:漏えいしたhash、オフラインで破れるJWT HS署名、キャッシュされた資格情報。または認証ロジックの迂回へ移る(前述の各項目)。1つのロジックの穴は千万回のブルートフォースに勝る。オンラインのブルートフォースは最後の手段とすべき。
**Q5**: OTP/認証コードAPIにはどの専用の迂回方法があるか。
**A5**: OTPでよくある:レート制限なしでブルートフォースできる(6桁=100万規模、レート制限がなければ破れる)、OTPがリクエストごとに変わらない/再利用できる、レスポンスにOTPが漏えいする、そして「OTP検証」と「ログイン完了」の2ステップが分離されていて飛ばせる。OTPエンドポイントが独立してレート制限されているかテストする。メインのログインはレート制限があるのにOTP検証にないケースはよくある。
**Q6**: 列挙で有効ユーザーと弱いパスワードを得た後、どう最大化するか。
**A6**: 資格情報の再利用(credential stuffingの発想):一か所で得たユーザー/パスワードの組み合わせを、対象の他のシステム、VPN、メール、クラウドコンソールで再利用する。認証攻撃の戦果は、単点のログイン自体ではなく、資格情報の横展開での再利用価値にあることが多い。

### ロジック迂回:パラメータ改ざんによる認証不要化
**Q1**: 暗号学とフローのほかに、より「単純」だが有効な認証バイパスはあるか。
**A1**: ある。しかもこれらの低コスト高リターンのポイントを優先的に一巡すべき:ログインレスポンスの`{"success":false}`をtrueに変えるとフロントエンドに信頼されるか、`isAuthenticated`系のフロントエンド状態をJSで改ざんできるか、そして「ログイン記憶」cookieが単なるbase64か(`user=guest`を`user=admin`に変える)。素朴な手法はしばしば一撃で致命傷になる。
**Q2**: フロントエンドがレスポンスを信頼するシナリオをどう判断するか。
**A2**: 認証・認可がフロントエンドで行われるかバックエンドで行われるかを見る。ログインレスポンスを傍受して失敗を成功に変えると内部ページへ入れて、内部APIが検証しないなら、認証・認可がフロントエンドに誤って置かれている。この種の「ファットフロントエンド」アプリケーションは影響が集中する領域。判定基準:レスポンスを変えた後、内部データAPIが実際にデータを返すか。
**Q3**: cookie/tokenが平文で編集可能な構造の場合、どう攻めるか。
**A3**: 「資格情報」が単なるbase64/JSON/平文のキー値(署名なし)なら、フィールドを直接変えて権限昇格する。まずデコードして構造を見る。多くの自社開発remember-me、自社開発sessionは署名のない編集可能な文字列。これは最も速い勝利で、偵察段階ですべてのcookieを一度デコードすべき。
**Q4**: 強制ブラウジング(forced browsing)を認証バイパスでどう使うか。
**A4**: ログインせずに保護されたURLへ直接リクエストし、「リンクが見えない」ことだけで保護されているか(security by obscurity)をテストする。adminパネルへ未認可で直行できるか、APIをトークンなしで呼び出せるかもテストする。UIを迂回してバックエンドAPIへ直接向かうのが核心の発想。
**Q5**: これらの素朴な手法がすべてバックエンドの厳格な検証で防がれる場合、何を意味し、どこへ方向転換するか。
**A5**: バックエンドの認証・認可が集中しており健全で、素朴な手法は無効であることを示す。技術的深さが必要な面へ移る:JWT暗号学、OAuthフロー、権限外アクセスのIDOR。素朴な手法は「無料の偵察」であり、素早く一巡したら移り、こだわらない。
**Q6**: これらの散発的な試行を、漏れのない検査にどう整理するか。
**A6**: 認証バイパスのchecklistを作る(フロントエンド信頼/平文の資格情報/強制ブラウジング/既定パスワード/デバッグ用裏口/バックアップAPI)。新しい対象に接するたび、まず機械的に一巡する。レッドチームの安定した成果はchecklistに、ひらめきは深掘りに依存する。両者を組み合わせ、まず広く、次に深く。

### JWTの時間クレームとクロックオフセットの利用
**Q1**: payloadに`exp`/`iat`/`nbf`がある場合、「期限切れでも使える」以外に何を試せるか。
**A1**: 時間セマンティクスの境界を試す:署名が変わらない前提ではこれらを変えられないが、サーバー側のそれらへの処理は観察できる。発行権を得られれば(secretを破れば)、超長expの永久トークンを発行する、またはnbfを未来に設定して時限の資格情報を作れる。発行権がない場合は、サーバー側の検証の緩さを重点的にテストする。
**Q2**: iatには見落とされた使い方があるか。
**A2**: 一部のシステムは`iat`を「パスワード変更後に、ある時点より前のtokenをすべて失効させる」ために使う。iatを検証しない、またはiatを迂回できるなら、パスワード変更/強制ログアウトの仕組みは形骸化し、窃取した旧トークンが長く残る。テスト:パスワード変更後、iatがより前のトークンがまだ有効か。
**Q3**: クロックオフセット(leeway)はどう悪用されるか。
**A3**: ライブラリはしばしば数十秒から数分のクロック許容差を許可する。通常は影響が小さいが、許容差の設定が非常識(数時間/数日)なら、期限切れトークンの利用可能窓が大幅に延び、窃取トークンの利用価値が上がる。exp経過後、どれだけ経ってトークンが実際に失効するかを確認する。
**Q4**: 発行権を得た後、時間クレームでどう永続化を最大化するか。
**A4**: expが極端に遠く、最高権限を包含し、あらゆるフロントエンドの制約を迂回するトークンを発行する。これはrefreshを盗むより徹底した永続化。secretが変わらない限り、トークンは永久に有効。必ず優先してsecretのローテーション仕組みを確認する。
**Q5**: サーバー側の時間検証がすべて厳格で、発行権も得られない場合、この線の価値はなくなるのか。どこへ方向転換するか。
**A5**: 時間の次元の価値は確かに下がる。トークンの空間の次元へ移る:同一トークンの作用域(どのサービス/APIが受け付けるか)、環境をまたぐ再利用(テスト環境のトークンを本番で使えるか、その逆)。時間が固められたら空間の境界を攻める。
**Q6**: テスト/本番のtoken混用をどう調査するか。
**A6**: 異なる環境のトークンを収集し、iss/aud/kidを比較する。鍵やIdPを共用する場合、防御の弱いテスト環境が発行したトークンが本番で受理される可能性がある。防御の弱い環境から発行権を得て、硬い対象を攻める。環境をまたぐ信頼は見落とされがちな横展開の経路。

### 自社開発/改造した認証プロトコルの識別と突破
**Q1**: 対象のtoken/認証が明らかに標準のJWT/OAuthではなく自社開発の場合、どう手を付けるか。
**A1**: 自社開発=成熟したライブラリの裏付けがない=坑がある可能性が高く、優先度を【上げる】べき。まず構造を逆解析する:複数の資格情報サンプルをキャプチャして比較し、どの部分がランダムか(署名/乱数)、どの部分がエンコードされたデータか(ユーザーid/時間/権限)、どんなエンコードを使うか(base64/hex/カスタム)を特定する。
**Q2**: その完全性保護の仕組みをどう特定するか。
**A2**: 資格情報の異なる部分をバイト単位で変更してテストし、どの変更が拒否されるか(完全性保護あり)、どの変更が受理されるか(保護なし/制御可能)を見る。これに基づき「改ざん可能領域」と「固定領域」を描き出す。無保護領域内の権限フィールドは直接変える。
**Q3**: 自社開発の署名/チェックサムを使っていると判明した場合、どう攻めるか。
**A3**: アルゴリズムを分析する:単純なCRC/MD5か(自ら計算して再署名できる)、それとも鍵付きHMACか(鍵を破る必要がある)。鍵なしのチェックサムなら、任意に改ざんして再計算すればよい。自社開発の暗号化なら、ECBモードの特徴(同じ平文ブロックが同じ暗号文ブロックになる)、制御可能なIV、padding oracleを探す。
**Q4**: アルゴリズムを逆解析できず、サンプルも足りず、行き詰まった場合はどうするか。
**A4**: ソースコード/実装詳細の取得へ移る:自社開発認証のロジックはフロントエンドのJS、逆コンパイルしたモバイルApp、漏えいしたソースコード、ドキュメントに隠れていることが多い。実装を読むほうがブラックボックスの逆解析よりはるかに速い。暗号分析の問題を情報漏えい/逆解析の問題に変える。
**Q5**: 実装すら入手できず、ブラックボックスでも攻められない場合、最終的にどこへ方向転換するか。
**A5**: 認証以外の全体フローへ移る:自社開発認証のシステムは、他の部分も自社開発で脆弱なことが多い(自社開発のsession、自社開発の権限、自社開発の暗号化)。同じ開発チームの他の弱点を横展開で探す。1つのチームのセキュリティ水準は相対的に一貫している。
**Q6**: 自社開発認証に対する正しい心構えは何か。
**A6**: 自社開発認証はレッドチームにとって障害ではなく機会。標準プロトコルは全世界で監査されるが、自社開発は内部の数人しか審査しない。逆解析への投資は、標準プロトコルに固執するより費用対効果が高いことが多い。「非標準」を見たら後退ではなく興奮すべき。ただし逆解析にタイムボックスを設け、底なし沼を避ける。

### 認証tokenのキャッシュ/ログ/CDNでの漏えい
**Q1**: tokenを直接攻めるのが難しすぎる場合、「どこでtokenが漏れるか」から入ることはできるか。
**A1**: できる。しかもこれは過小評価されている次元。tokenの漏えい点を体系的に調査する:URLにtokenを含めばCDNキャッシュ/ログ/ブラウザ履歴/Refererに入る。エラーページ/デバッグページがリクエストヘッダーを表示する。監視/APMが完全なリクエストを記録する。サードパーティJS(分析、広告)がtokenを読める。「tokenを盗む」を「漏れ点を探す」に変える。
**Q2**: CDN/キャッシュ汚染とtoken漏えいをどう連動させるか。
**A2**: 認証付きレスポンスが誤ってキャッシュされる場合(cache設定の見落とし)、次のユーザーが前のユーザーのtoken/プライベートデータを含むキャッシュレスポンスを取得する可能性がある。テスト:token付きでリソースをリクエストし、レスポンスが公開キャッシュされるか(`Cache-Control`/`Age`ヘッダー)、別の身元/トークンなしで再リクエストして他人のデータを取得するか(web cache deception)。
**Q3**: web cache deceptionを具体的にどう構成するか。
**A3**: 「静的リソースに見える」パス(`/account/info.css`など)をリクエストし、CDNに拡張子でキャッシュさせるが、バックエンドは動的なアカウントデータを返す。キャッシュされれば、被害者がそのパスへアクセスした後にそのプライベートデータがキャッシュされ、自分が同じパスへアクセスすれば取得できる。前提はキャッシュがサフィックス単位で、バックエンドがサフィックスを検証しないこと。
**Q4**: 対象のキャッシュ設定が正しく、tokenをURLに入れない場合、どこへ方向転換するか。
**A4**: 下流のログ/サードパーティへ移る:SIEM/ログプラットフォームへアクセスできるなら(弱いパスワード/未認可のKibanaなど)過去のtokenを検索できる。統合されたサードパーティサービス(webhook、分析)がtokenを含むデータを受け取る可能性がある。漏えいの戦場は対象本体から、そのデータが流れるサードパーティへ移る。
**Q5**: 漏えいしたtokenがまだ使えるかをどう判断するか。
**A5**: 前述の「ライフサイクル」と組み合わせて判断する:まずexpを見て、次に実際にリプレイしてテストする。ログ内の過去tokenは、システムがステートレスで失効させない場合、まだ有効な可能性がある。漏えい+長い有効期間=既製の資格情報であり、あらゆる偽造の試みより優先する。
**Q6**: この線をどう規模化して収集するか。
**A6**: 偵察の発想で広く網を張る:gitの漏えい、公開キャッシュ/アーカイブ、JS source map、公開されたCIログ、Postmanコレクション、APIドキュメントのホスティングプラットフォームを検索する。認証攻撃は常に「攻める」とは限らず、多くの場合「拾う」。既製のtoken/secretは至るところにあり、先に拾ってから攻める。

### 同一オリジンポリシーとCORS設定ミスによる資格情報の漏えい
**Q1**: 対象のAPIがtokenを使い、フロントエンドとバックエンドが分離されている場合、CORS設定で何を注目するか。
**A1**: `Access-Control-Allow-Origin`が任意のOriginを反射するか、そして`Access-Control-Allow-Credentials: true`かを注目する。両方が同時に成立するなら、任意のサイトが被害者の資格情報を伴ってクロスドメインでレスポンスを読み取れる。自分が悪意のあるページを作れば、被害者に代わってそのデータ/tokenを読み取れる。
**Q2**: CORSが利用可能なことをどう素早く検証するか。
**A2**: カスタムの`Origin: https://evil.com`を付けてリクエストを送り、レスポンスのACAOが自分のOriginをそのまま反射し、credentials付きかを確認する。反射=利用可能。さらにnull origin、サブドメインのワイルドカード、正規表現の誤り(`example.com.evil.com`がマッチする)などの緩い変種も見る。
**Q3**: ACACがfalseだがACAOが反射する場合、まだ可能性はあるか。
**A3**: credentialsがない場合、認証が必要なレスポンスは読めないが、公開/cookie不要のデータは読め、価値は下がる。tokenがcookieではなくbody/localStorageにある場合、CORS+credentialsのモデルは当てはまらず、XSSでの読み取りへ移る。資格情報の保持方式を判断してから攻め方を決める。
**Q4**: CORS設定が厳格(ホワイトリストが正確)で、この線が断たれた場合、どこへ方向転換するか。
**A4**: postMessageへ移る:ウィンドウ間通信がoriginを検証しない場合、乗っ取りまたはインジェクションできる。そしてCSRFへ移る(CORSは読み取りを防ぐが書き込みは防がない。CSRF tokenがなければクロスドメインの書き込み操作は依然可能)。同一オリジン関連の攻撃面はCORSだけではない。
**Q5**: postMessage関連でどう認証を攻めるか。
**A5**: OAuth/SSOはよくpostMessageでポップアップとメインウィンドウ間でtoken/codeを渡す。受信側が`event.origin`を検証しないなら、悪意のあるページが埋め込んで受け渡し中のtokenを窃取できる。送信側のtargetOriginが`*`なら、tokenを任意の埋め込み元が傍受できる。SSOのポップアップフローにおけるpostMessageの使い方を監査する。
**Q6**: この種のクライアント側の認証漏えいをどう特定するか。
**A6**: フロントエンドのJSを読み、`postMessage`、`addEventListener('message'`、`document.domain`、CORSリクエスト設定を検索する。クライアント側の認証ロジックはすべてJSに露出しており、静的監査はブラックボックスの試行より効率的。フロントエンド分離アーキテクチャでは、JSが攻撃の地図。

### 複数ステップログインのステートマシンとレスポンス改ざん
**Q1**: ログインが複数ステップの場合(アカウント→パスワード→MFA→デバイス確認)、この種の複数ステップフローにはどのような構造的弱点があるか。
**A1**: 複数ステップフローは1つの「中間状態の資格情報」(一時token/session)で各ステップをつなぐ。弱点は、中間状態が過度に信頼されるか、ステップを飛ばせるか、あるステップで別の身元を注入できるか。核心の問い:第Nステップで使う身元と第1ステップが固く紐づいているか。
**Q2**: 「response manipulation」を複数ステップログインでどう使うか。
**A2**: あるステップのレスポンスを傍受し(MFA検証の返りなど)、`verified:false`をtrueに変える、またはステータスコードを変え、バックエンドがそれに基づき進むかを見る。中間状態の進行がフロントエンドが返す結果に依存するなら、改ざんして迂回できる。判定基準:レスポンスを変えた後、次の認証済みステップへ進むか。
**Q3**: ステップ間で身元が固く紐づかない場合、どう利用されるか。
**A3**: 定番:第1ステップで被害者のアカウントを送って中間tokenを得て、第3ステップ(MFA/最終確認)で【自分の】MFA/確認を使う。バックエンドが中間tokenのみを認識し、身元の一貫性を再確認しない場合、被害者としてログインできる可能性がある。各ステップが同一subjectを再確認するかテストする。
**Q4**: これらの複数ステップ迂回がすべてバックエンドの厳格なステートマシンで防がれる場合、どこへ方向転換するか。
**A4**: 横展開のログイン入口の多様性へ移る:同一アカウントに複数のログイン経路があるか(パスワード/OAuth/マジックリンク/API)。ある経路のステートマシンはそれほど厳格でない可能性がある。そして「ログイン後」へ移る。ログインを迂回できないなら、ログイン後の資格情報を盗む。
**Q5**: マジックリンク(magic link)/パスワードレスログインにはどの専用の弱点があるか。
**A5**: リンクtokenのエントロピー(予測可能ならブルートフォースできる)、使い捨てか、期限切れになるか、リクエストを開始したデバイス/セッションに紐づくか、そして任意のメールでリクエストして別経路から取得できるか。パスワードレスログインは安全をリンクの配送とtokenの強度に全面的に賭けており、この2点を重点的にテストする。
**Q6**: 複数ステップフローのどのステップに重点を置くべきかをどう判断するか。
**A6**: 各ステップ間に「プローブ」を設ける:どのステップが権限のある資格情報を実際に発行するかを観察する。攻撃は「権限資格情報が実際に発行されるステップ」とその前後の接合部に集中すべきで、重要でない前置ステップで労力を浪費してはならない。重要な遷移点を特定することが効率の核心。

### 権限モデル:scopeとaudienceの不整合
**Q1**: tokenに`scope`がある場合、scope関連の権限外アクセスをどう探すか。
**A1**: まずシステムの全scope値を列挙する(ドキュメント/discovery/異なるtokenの比較)。次に3種の不整合をテストする:1) tokenリクエスト時に過剰なscopeを要求して認められるか、2) サーバー側が実際にscopeに従ってAPIを制限するか(scopeがあってもenforceされない)、3) 低scopeのtokenで高scopeのAPIを呼び出せるか。
**Q2**: scopeがenforceされないことをどう確認するか。
**A2**: あるscopeが明らかに欠けたtokenで、そのscopeを必要とするAPIを呼び出す。成功したら、scopeは飾りで、認証・認可が実装されていないことを示す。これは「OAuthはあるが実際の認可がない」というよくある問題で、純粋なロジックテストで発見できる。
**Q3**: audienceの不整合をどう利用するか。
**A3**: 1つのIdPが複数のサービス(audience)にtokenを署名する。サービスBが`aud`を検証しないなら、サービスAのtokenでBへアクセスできる。テスト:サービスをまたいでtokenを与える。これは企業の複数システムがSSOを共用するときに極めて一般的で、複数のシステムを横展開でつなげられる。
**Q4**: scopeとaudがどちらも厳格に検証される場合、どこへ方向転換するか。
**A4**: scopeの下のリソースレベルの権限外アクセスへ移る:scopeが正しくても、具体的なリソースidの帰属検証(IDOR)が欠けている可能性がある。scopeは「注文を読めるか」を管理するが、「【他人の】注文を読めるか」は別の層の検証で、しばしば漏れる。粗粒度のscopeから細粒度のオブジェクト認証・認可へ移る。
**Q5**: consent(認可同意)の段階で何を攻められるか。
**A5**: consentを迂回できるか(scope付きで直接リクエストして同意ページを飛ばす)、scope upgradeの際に再同意を求めないか、「認可済みアプリケーション」が静かに再利用されるかをテストする。そして悪意のあるclientがユーザーを誘導して過剰なscopeを認めさせる(フィッシング型OAuth、「OAuth phishing」類似)。
**Q6**: OAuthフィッシングの線をレッドチームでどう価値づけるか。
**A6**: 対象がサードパーティによるOAuth clientの登録を許可し、consentの文言が曖昧なら、一見正規のclientを登録して従業員に認可を誘導し、そのtoken/メール/データへの長期的なofflineアクセスを得られる。これはソーシャルエンジニアリングと技術を組み合わせた高価値の永続化入口で、企業SSO環境では特に致命的。

### tokenイントロスペクション(introspection)と失効エンドポイントの悪用
**Q1**: 対象がOAuth token introspectionまたはrevocationエンドポイントを露出している場合、何を攻められるか。
**A1**: introspection(`/introspect`)はtokenの有効性とメタデータを返し、revocation(`/revoke`)はtokenを失効できる。まずこの2つのエンドポイントの認証要件を見る:client資格情報が必要か、誰でも照会できるか。認証なしのintrospectionはtoken状態の漏えいと列挙の面。
**Q2**: 認証なしのintrospectionで何ができるか。
**A2**: 盗んだ/推測したtokenが有効かを検証するのに使える(オフラインoracle)。さらにtokenのscope/sub/expを列挙し、以降の偽造と権限外アクセスの判断を支援する。それを「サーバー側が無料で提供するtoken検証器」として扱い、他の攻撃を加速する。
**Q3**: revocationエンドポイントの認証が不足している場合、どのような害があるか。
**A3**: 任意のtokenを失効できるなら、拒否サービス/強制ログアウトの手段になる(管理者をオフラインに追いやって混乱を起こす)。あるいはレッドチーム後期に痕跡の消去/対応側の遮断に使う。判定基準:他人のtokenをrevokeへ送って成功するか。
**Q4**: この2つのエンドポイントがどちらも厳格なclient認証を要求する場合、どこへ方向転換するか。
**A4**: discoveryエンドポイント(`/.well-known/openid-configuration`)へ移る。これはしばしば認証なしで、全エンドポイント、対応アルゴリズム、jwks_uri、grant typesを漏えいする。偵察の価値の高い情報源で、前述のすべての攻撃の入口設定を逆算できる。エンドポイント自体を攻められないなら、それを情報として使う。
**Q5**: discovery内で攻撃を導くために最も注目すべきフィールドは何か。
**A5**: `jwks_uri`(公開鍵を取得してRS→HSを行う/kidを見る)、`token_endpoint_auth_methods`(`none`を許可するか)、`grant_types_supported`(余分なpassword/implicitがないか)、`response_types_supported`(インプリシットフローがないか)、`scopes_supported`(権限昇格の対象を列挙する)。1つのdiscoveryは攻撃計画書。
**Q6**: discoveryすら露出しない場合、どう情報を補うか。
**A6**: 能動的な列挙へ移る:一般的なエンドポイントのパスを推測する、フロントエンドのJSから設定定数を抜き出す、モバイルAppのハードコードされたエンドポイントをキャプチャする。情報の欠如は経路が存在しないことを意味せず、より能動的に掘る必要があるだけ。放棄ではなく、情報収集の他のチャネルへ移る。

### 認証脆弱性からアカウント乗っ取りへの昇格の仕上げ
**Q1**: すでに某ユーザーのtokenを偽造/窃取できる場合、どう「アクセス」を「乗っ取り」へ昇格させるか。
**A1**: アクセスは一時的で、乗っ取りは永続的。仕上げの動作:メール/電話番号の紐づけ変更、パスワードリセット、自分のMFAデバイスの追加、長期API keyの生成、予備管理者の作成。目標は、元の脆弱性が修正され、元のtokenが失効しても、アカウントの制御権を保持し続けること。
**Q2**: メールの紐づけ変更で「現在のパスワードが必要」とよく遭遇する場合、どうするか。
**A2**: 再認証が不要な紐づけ変更の経路を探す:一部の「情報更新」APIはメール変更にパスワードを要求しない、OAuthの紐づけは要求しない、またはメールの紐づけ変更で旧メールへ確認を送らない(旧メールから気づけない)。各紐づけ変更経路の再認証強度をテストし、最も緩いものを選ぶ。
**Q3**: 実ユーザーに気づかれずに乗っ取るにはどうするか。
**A3**: レッドチームは隠蔽性を評価する:パスワード変更/セッションの強制ログアウトはユーザーに即座に気づかれる。より隠蔽的なのは、予備の資格情報を追加すること(API key、副次メール、app-specific password、OAuth認可)。ユーザーの既存ログインには触れない。潜伏は強奪に優る。
**Q4**: 乗っ取り動作が通知/アラートを発火した場合、どうするか。
**A4**: これは「遮断された」シグナル。隠蔽的な永続化へ移る:通知のない仕組みを利用する(前述のrefreshローテーションなし、長期token、session不失效)。そして目標をすでに達成したか評価する(重要なデータを取れたら撤収)。永続化のために露呈するのは避ける。レッドチームは戦果と露呈を天秤にかける。
**Q5**: 単一アカウントの乗っ取り後、どうより多くのアカウント/システムへ横展開するか。
**A5**: 乗っ取ったアカウントから掘る:その連絡先/共有/チーム権限、保存されている他のシステムの資格情報、SSO身元としてログインできるすべての下流アプリケーション。1つのアカウントはSSOエコシステム内で組織全体へ通じるノード。その信頼の波及範囲を列挙する。
**Q6**: 仕上げ段階でレポートに最も記録すべきものは何か。
**A6**: 完全に再現可能な攻撃チェーン(各ステップのPoC)、影響範囲(どれだけ/どのレベルのアカウントを乗っ取れるか)、そして最小の修正点(どの検証の欠如が根本原因か)。レッドチームの価値は「侵入できた」ではなく「防御側が正確に対処できる」こと。明確な根本原因の特定が、成果物の品質の分水嶺。

### JWT headerが公開鍵(jwk)を持ち込む偽造
**Q1**: headerに`jwk`(完全な公開鍵オブジェクト)が直接埋め込まれている場合、これはjkuと本質的にどう違い、どう攻めるか。
**A1**: `jku`は外部リンクURLで、`jwk`は公開鍵をheaderへ直接入れるもの。サーバー側が誤って【header内に持ち込まれたこのkeyを信頼して署名検証する】なら、自分で鍵ペアを生成し、自分の公開鍵を`jwk`に入れ、自分の秘密鍵で署名する。サーバー側は自分が渡した鍵で自分が渡した錠を検証するため必ず通る。これは外向き通信も外部リソースも不要な自己身元証明。
**Q2**: サーバー側がheader内のjwkを受け入れるかをどう判断するか。
**A2**: 自己署名のトークンを構成し(自分のjwk+自分の秘密鍵で署名)、権限フィールドを1つ変えて直接送る。受理されたら致命的な署名検証ロジックの欠陥。判定基準は前述と同じ:権限外アクセスのAPIが401から200になる。これはすべての「鍵の出所の乗っ取り」で最も直接的なもので、jkuより優先して試すべき(headerがjwkに対応していれば)。
**Q3**: サーバー側が持ち込まれたjwkを受け入れない場合、他に緩い箇所がある可能性はあるか。
**A3**: 一部の実装は「headerにjwkがあればjwkを使い、なければローカルを照会する」。通常フローでローカルkeyを使っていても、jwk分岐を無効化していなければ嵌る。混合もテストする:元のkidを残しつつ自分のjwkを加え、優先順位を見る。解析優先順位の曖昧さはこの種の脆弱性の温床。
**Q4**: jwkが正しく無視/無効化される場合、どの同族の次元へ方向転換するか。
**A4**: jku/x5u(外部リンクの鍵)、kid(ローカルの鍵の出所)へ移る。これらはすべて「署名検証に使うkeyの出所を制御する」もので、jwkが行き止まりなら残りの3つを試す。すべて行き止まりなら、署名検証のkeyがハードコードされていることを示し、トークンのロジック層かHS鍵のブルートフォースへ移る。
**Q5**: jwk偽造を攻略した後の戦果は、jku偽造とどう違うか。
**A5**: 本質は同じ(発行権を得る)が、jwkはより隠蔽的で安定している(自分のサーバーの稼働に依存しない)。それで任意の身元を一括偽造し、異常なclaimへのバックエンドの処理を探る。戦果最大化の発想はjkuと同じ:権限を列挙し、信頼ドメイン内のすべてのサービスをつなげる。
**Q6**: このチェーンで事前に最も収集すべき情報は何か。
**A6**: 対象のJWTライブラリとバージョンを収集する(レスポンスヘッダー、エラーメッセージ、挙動のフィンガープリント)。`jwk`/`jku`/`none`の類の欠陥は特定のライブラリの特定バージョンと強く関連する。ライブラリを特定できれば既知の署名検証欠陥を調べられ、ブラックボックスの試行を狙い撃ちに変えられる。

### リバースプロキシ/ゲートウェイのパス正規化による認証バイパス
**Q1**: 対象がゲートウェイ層で認証を行う場合(保護されたパスはtokenが必要)、ゲートウェイを迂回してバックエンドへ直行できると疑うなら、まず何を考えるか。
**A1**: 「ゲートウェイとバックエンドが同一URLを同じように理解するか」を考える。認証はゲートウェイでパス照合される。ゲートウェイとバックエンドでパスの正規化(大文字小文字、`;`、`//`、`..`、`%2e`、末尾スラッシュ、`.json`サフィックス)の処理が異なるなら、「ゲートウェイは公開と見なし、バックエンドは保護対象と解析する」パスを構成し、認証を迂回して機密APIへ到達できる。
**Q2**: 具体的にどの変形を試すか。
**A2**: 既知の保護されたパス`/admin`に対して試す:`/Admin`、`/admin/`、`/./admin`、`/%61dmin`、`/admin;foo`、`/admin/..;/admin`、`/public/../admin`、`.json`/`.css`サフィックスの付加など。ゲートウェイを通過し(トークンを要求されない)、かつバックエンドでは保護対象リソースとして実行されるものを観察する。
**Q3**: これはHTTPリクエストスマグリング(request smuggling)とどう組み合わせるか。
**A3**: フロントエンドプロキシとバックエンドでリクエスト境界の解析が一致しない場合(CL/TEの相違)、隠れたリクエストを密輸してバックエンドの保護APIへ直行し、ゲートウェイの認証層を完全に迂回できる。判定基準:密輸したリクエストがバックエンドのレスポンスを得られるか。これは前置認証を迂回する重武器で、ゲートウェイとバックエンドが異種の場合に適する。
**Q4**: パス変形と密輸をすべて試しても迂回できない場合、どこへ方向転換するか。
**A4**: ゲートウェイとバックエンドの解析が一致する、またはバックエンドに独立した認証・認可があることを示す。「token自体の突破」か「内部信頼ヘッダーの偽造」(前述のサービス間の項目)へ戻る。境界の迂回に失敗したら、資格情報の突破へ戻る。正規化で無限に列挙せず、タイムボックスを設ける。
**Q5**: 「認証がゲートウェイにあるのかバックエンドにあるのか」を先にどう判断するか。
**A5**: 比較する:バックエンドのポートへ直接アクセスする(到達可能なら)場合とゲートウェイ経由の場合、異常なHost/パスを付けて認証が効かなくなるかを見る。一部のパスがトークンなしでもデータを取れるなら、認証は純粋にゲートウェイ層で、迂回可能。認証境界の位置を明らかにすることが、このチェーンの前提偵察。
**Q6**: 迂回後、本物の機密機能を取得したのであって、まやかしではないことをどう確認するか。
**A6**: 「認証・認可の後でしかできない書き込み操作/データ読み取り」で、実際に権限外アクセスが成功したことを検証する。空のページを取得しただけではだめ。誤検知を避けるため、「認証ルートを迂回した」と「機密ロジックを実際に実行した」を区別する。レッドチームのレポートは防御側の再現の疑義に耐える必要がある。

### パスワードリセットフローとHostヘッダー/tokenの欠陥
**Q1**: パスワードリセットでアカウントを乗っ取りたい場合、このフローのどの段階を先に審査するか。
**A1**: 4段階を審査する:1) リセットtokenの生成(予測可能か、連番か、タイムスタンプ派生か)、2) tokenの紐づけ(ユーザーに紐づくか/使い捨てか/期限切れになるか)、3) リセットリンクの構成(リクエスト内のHostヘッダーでURLを連結するか)、4) リセットが既存セッションを失効させるか。各段階が独立した乗っ取りの入口。
**Q2**: Hostヘッダー汚染を具体的にどう利用するか。
**A2**: サーバー側がリクエストの`Host`/`X-Forwarded-Host`でリセットリンクのドメインを連結するなら、被害者のためにリセットをリクエストしつつ、Hostを自分のドメインに変える。被害者が受け取るメール内のリンクは自分のドメインを指し、クリックするとリセットtokenが自分に届く。判定基準:メール内のリンクのドメインが、自分が制御するヘッダーに影響されるか。
**Q3**: tokenが予測可能なことをどう判断し、利用するか。
**A3**: 複数のリセットtokenを連続でリクエストして規則を観察する:連番か、タイムスタンプか、弱い乱数か(uid+時間ベース)。予測可能なら、被害者のためのtokenを直接生成/推算してリセットを完了する。複数サンプルを比較してエントロピー不足を探すのが鍵。
**Q4**: tokenが強力な乱数で、Hostを制御できず、紐づけが厳格で、この線が遮断された場合、どこへ方向転換するか。
**A4**: リセットフローのロジック面へ移る:リセットリクエストのレスポンスがtokenを漏えいするか(一部のAPIはtokenを直接返す)、リセットAPIが権限外アクセスでuidを指定できるか、リセット後に旧セッションが失効しないなら他の脆弱性と組み合わせる、そして「旧トークン不要で任意のアカウントのパスワードを直接変えられる」IDOR。ロジック欠陥は暗号学的強度を迂回することが多い。
**Q5**: 他人のパスワードを実際に変えずに、低リスクで検証するにはどうするか。
**A5**: 自分が制御する2つのアカウントで実演する:Bアカウントの有効なリセットtokenを取得できることを証明すればよい。実際に新しいパスワードを送信して実ユーザーを締め出す必要はない。PoCは「tokenを制御できる/対象を権限外アクセスで指定できる」段階までで定性に十分。自制はレッドチームの職業的資質。
**Q6**: リセット乗っ取りと前述のOAuth/JWT攻撃をどう連携させるか。
**A6**: パスワードリセットは「あらゆるログイン状態の強度を迂回する」メタ入口。MFA、SSO、JWTがどれだけ強くても、パスワードをリセットできれば乗っ取れる。すべての認証プロトコル層が硬い場合、リセットフローを最後の弱点として優先的に深掘りする。それはしばしば防御の盲点。

### 静的資格情報(API key / Bearer)の識別と悪用
**Q1**: 対象がセッション型tokenではなく静的API key/長期Bearerを使う場合、攻撃の発想はどう変わるか。
**A1**: 静的資格情報はローテーションされず、長期間有効で、しばしばハードコードされる。攻撃の重心は「偽造/迂回」から「探し出す+権限境界の判断」へ変わる。まずそれが静的であることを確認し(形式が固定、expがない、複数回のリクエストで変わらない)、次にその漏えい点と権限範囲を主に攻める。
**Q2**: 静的keyは最もどこで漏えいするか。
**A2**: フロントエンドJS/モバイルAppのハードコード、git履歴と公開リポジトリ、CI/CD設定とログ、Postman/APIドキュメント、エラーメッセージの表示、そしてクライアントとサーバー側の通信の傍受可能な箇所。静的資格情報の核心リスクは「至るところに複製されることで至るところに漏えいする」ことで、広く網を張って収集する。
**Q3**: keyを拾った後、その権限と帰属をどう判断するか。
**A3**: それで低リスクの読み取り専用APIを呼び出して境界を探る(userinfo、アカウント情報)。どのユーザー/サービスを表すか、どの権限があるか、scope制限があるかを見る。いきなり高危険APIを呼び出して自分を露呈しない。まず「この鍵がどの扉を開けられるか」を把握してから動く。
**Q4**: keyの権限が小さく/読み取り専用の場合、この線は無駄になるのか。どこへ方向転換するか。
**A4**: 無駄ではない。「小を以て大を成す」へ移る:小権限のkeyも次のステップに使う内部情報を漏えいする可能性がある、権限昇格APIが存在する可能性がある、同じ漏えい源にさらに高権限のkeyがある可能性がある。そしてkeyの予測可能性へ移る。keyの生成に規則があれば、他のユーザーのkeyを列挙できる。
**Q5**: keyが強力な乱数で、権限が厳格で、漏えい箇所がなく、認証層が硬い場合、最終的にどこへ方向転換するか。
**A5**: 業務ロジックと他の認証の仕組みへ戻る。静的資格情報の設計が良好なことは通常、API側が成熟していることを意味する。労力をWeb UI側のセッション認証、OAuthフロー、権限外アクセスのIDORへ移す。複数入口の体系では、1つの入口が硬くてもすべて硬いとは限らない。
**Q6**: 静的資格情報の攻撃で、レッドチームが最も警戒すべき運用リスクは何か。
**A6**: 静的keyは一度使われると異常検知を発火する可能性がある(新しいIP/新しいUAの呼び出し)。しかもセッショントークンのように「もともと至るところで動く」ものではない。拾ったkeyを使う際は、その通常の呼び出しパターンを評価し、できるだけ本来の用途に寄せ、資格情報の乱用プロファイルで行動を露呈しないようにする。隠蔽性を優先する。
