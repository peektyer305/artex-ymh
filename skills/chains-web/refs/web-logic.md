# Web · ビジネスロジックと権限外アクセス脆弱性

### 資源 ID 付きのリクエストを捕まえたら、まず水平権限外アクセス(IDOR)かを判定する
**Q1**: トラフィックに `GET /api/order?id=1024` のようなリクエストを見た。直感は IDOR だが、どう始める?
**A1**: 急に数字を変えない。第一歩は、この ID が「誰の資源を表すか」を確認することだ。自分のアカウントの注文か、グローバルオブジェクトか。判定基準: 現在の身元でそれを読み、返りボディに「帰属フィールド」(userId/tenantId/owner)があるかを見る。返りボディに帰属の束縛がまったくなければ、サーバーが ID だけでデータを取り、帰属を検証しない可能性が高く、IDOR 確率が極めて高い。
**Q2**: id を 1023 に変えると他者の注文が返った。実証か?
**A2**: 「これは本来公開データ」と「こちらもたまたま権限がある」の二つの誤検知を排除する必要がある。正しいのは二アカウント対照だ。アカウント A で A の資源 ID を取り、アカウント B のセッションでその ID にアクセスする。B が A の非公開データを読めれば=真の権限外アクセス。単一アカウントで数字を変えて成功したように見えても、公開資源にアクセスしただけかもしれない。
**Q3**: 権限外アクセスは読取だけか。書けるか?
**A3**: 同じ資源の書込操作(PUT/DELETE/PATCH)も B のセッションで打つ。多くのシステムは読 API は認証・認可を漏らすが書 API は検証し、逆もある。読み書きを別々に検証し、「読めるなら書ける」と決めつけない。
**Q4**: ID が連番だ。一括でデータを引いて危害面を証明したい。
**A4**: まず小範囲で列挙(±10)して規則を確認し、それから量を走らせるかを評価する。量を走らせる前に考える。認可範囲が許すか、不正検知を誘発しないか。危害証明は少数サンプル + 列挙可能の説明で十分で、本当に全量ダンプする必要はない。
**Q5**: 数字を変えたら 403 が返った。この道は死んだか?
**A5**: 死んでいない。直交次元に転じる。403 はこの一つのパラメータ位置だけを遮った可能性がある。パラメータ受け渡しチャネルを替える。id を query から body、header、cookie、JSON ネスト、配列形 `id[]=1023` に移す。HTTP メソッドを替える。`id=1023.json`/パス型 `/order/1023` を試す。サーバーは複数入口の認証・認可が不一致なのが常態だ。
**Q6**: 全部 403 で、確かにこのオブジェクトが固定された。
**A6**: オブジェクト種別を替える。一つのシステムの IDOR は往々にして孤例ではない。注文が固定でも、請求書、住所、メッセージ、添付、エクスポート API も固定とは限らない。横方向に「ID 付きの読み書き API」を全てスキャンし、認証・認可が最も薄弱な入口を探す。一点に固執しない。

### 一般アカウントで管理者機能に触りたい(垂直権限外アクセス)
**Q1**: 低権限アカウントを持つ。垂直権限外アクセスを検証したい。どこから始める?
**A1**: まず「管理面がどんな形か」をマッピングする。低権限アカウントのフロントエンド JS、ルートテーブル、メニュー API 返りをキャプチャする。多くのフロントエンドは管理者のルート/ボタンも配信し、CSS で隠すか `if(isAdmin)` で描画しないだけだ。JS から `/admin/*`、`/manage/*` のエンドポイントリストを掘り出す。これが垂直権限外アクセスの標的リストだ。
**Q2**: `/admin/userList` を掘り出した。低権限 token で直接リクエストすると 403 が返る。
**A2**: 403 は「この一つの API に検証がある」ことしか示さない。垂直権限外アクセスの核心は「検証漏れの兄弟 API」を探すことだ。同じ機能に複数の実装がしばしばある。旧版 `/api/v1/admin/xxx`、内部 `/internal/`、エクスポート `/export`、モバイル `/m/`。逐一試す。認証・認可が不完全な API が欠け口だ。
**Q3**: どの API を打つ価値があるか、より巧い判定基準はないか?
**A3**: 認証・認可が「ゲートウェイで統一」か「各 API で個別」かを見る。統一ゲートウェイ認証・認可なら垂直権限外アクセスは難しい。一部の API の返り構造のスタイルが著しく異なる(異なるフレームワーク/異なるチーム)なら、後から合流したもので、認証・認可が最も漏れやすい。スタイルの急変 = 認証・認可の断層の信号だ。
**Q4**: 管理 API をリクエストするとデータが返ったが、空リストだけだ。権限外アクセスか?
**A4**: 空リストは「認証・認可は通ったがデータがこちらの身元でフィルタされた」かもしれない。本当に権限外アクセスを証明する動作を構築する必要がある。「状態を変える」管理操作を呼ぶ(あるユーザーを遮断する、ある設定を変える)、それが効くかを見る。管理の書込操作を実行できて初めて硬い証拠だ。
**Q5**: API に検証があるが、`role` フィールドだけがこちらの制御可能な場所から来る?
**A5**: 認証・認可の根拠がクライアント制御可能かを検査する。role/isAdmin が JWT payload、cookie、リクエストヘッダから来て、サーバーが再検証しないなら、これらのフィールドを直接改ざんして試す。この種の「クライアント宣言の身元を信頼する」ことは垂直権限外アクセスの高頻度点だ。
**Q6**: 全管理 API が厳格に検証し、垂直権限外アクセスが通らない。
**A6**: 「権限昇格経路」へ転じるのであって「直接アクセス」ではない。低権限アカウントを高権限に変えるロジックを探す。ユーザーグループ編集 API が自分にロールを付与できるか、招待/承認フローが自己承認できるか、登録時の role パラメータが注入できるか。「管理機能へのアクセス」から「自身の権限属性の改ざん」という直交次元に転じる。

### 権限外アクセスが成立しそうだが、「これは誤判定だ」をどう排除するか
**Q1**: パラメータを変えて他者のデータらしきものを取ったが、本当の脆弱性か不明だ。どう自己証明する?
**A1**: 清潔な三方対照実験を立てる。アカウント A(被害者)、アカウント B(攻撃者)、匿名セッション。A で一意マーク付きの非公開資源を作る(備考にランダム文字列を書くなど)、その ID を記録する。その後 B と匿名でそれぞれアクセスする。「本来 A の秘密文字列を見るべきでない身元が見た」ときのみ成立する。一意マーク法が公開データの誤検知を一撃で排除する。
**Q2**: B が見られるが、B もたまたま認可されている(同チームなど)のでは?
**A2**: A、B に業務上の関連がないことを保証する。異なるテナント、異なるチーム、互いに友達でない。関係型システムでは「同グループ可視」は設計であって脆弱性ではない。隔離性はアカウント作成時に制御しておく。
**Q3**: 200 が返るが body が暗号化/エンコードで、本当のデータか読めない。
**A3**: ステータスコードだけを見ない。「権限外アクセスリクエスト」と「正常リクエスト」のレスポンス長、フィールド構造、時間差を比較する。長さが正当なレスポンスと一致し且つ固定のエラーページでなければ、本当のデータである確率が高い。さらに前で埋めた一意マークで検証する。レスポンス差分はステータスコードより信頼できる。
**Q4**: 時々読めて時々読めない。結果が不安定だ。
**A4**: 不安定は往々にしてロードバランサの後ろの複数インスタンスで認証・認可設定が不一致か、キャッシュがある。session を固定し、ノードを固定し(粘着があれば)、ランダムパラメータでキャッシュを迂回して再テストする。まず環境ノイズを排除してから結論を下す。
**Q5**: 再現できなくなった。さっきのは偶然か?
**A5**: 各歩の完全なリクエスト(header/cookie/タイミング含む)を記録する。再現失敗は、ある動的 token かステップ順を漏らしたことが多い。成功したときの生パケットを保存し、バイト単位でリプレイする。記憶で再構成しない。再現可能性は脆弱性成立の最低条件だ。

### 決済/注文の金額が改ざん可能なビジネスロジック
**Q1**: 注文フローで金額、数量パラメータがクライアント送信される。価格改ざんを疑う。どう体系的に測る?
**A1**: まずこの取引の「金額がどこから来て、どこで確定するか」を描く。理想的なシステムは、サーバーが商品 ID で価格を引き、クライアントは商品と数量だけを送る。危険信号はクライアントが直接 price/amount/total を送ることだ。決済確認の一歩でキャプチャし、価格系フィールドを逐一小さく変える(0、負数、小数、超長を含む)。
**Q2**: price を変えてもサーバーが二次的に価格を検証し、効かない。
**A2**: 「価格計算チェーンの他の制御可能変数」に転じる。数量、クーポン、ポイント相殺、送料、通貨、税率、満額割引の閾値。総額 = f(複数変数)で、サーバーは単価だけを検証して割引率や数量を信頼しているかもしれない。割引/数量という間接因子を攻め、最終総額ではない。
**Q3**: 数量を負数にするとどうなる?
**A3**: 負数は古典的なロジック脆弱性だ。`総額 = 単価 × 数量` で、負数は総額を負にし、アカウントに「返金」すらさせ得る。同様に超巨大数量で整数オーバーフローして負に回り込むのを測る。境界値(0、負、極大、オーバーフロー点)はビジネスロジックの主戦場だ。
**Q4**: 金額が全て固定だが、決済が第三者ゲートウェイへのジャンプだ。
**A4**: 「注文金額」と「決済金額」の一致性検証を攻める。古典的欠陥: 注文では 100 元を記録するが、決済ゲートウェイへ送る金額やコールバック内の金額を変えられ、システムがコールバック結果だけを信じて注文原価を再検証しない。決済コールバック/非同期通知の金額、注文番号、署名が厳格に束縛検証されるかを測る。
**Q5**: コールバックに署名があり、変えられない。
**A5**: 状態機械次元に転じる。「未決済なのに決済済み状態を得られるか」。決済成功コールバックを並行呼び出しする、旧の成功コールバックを新注文にリプレイする、「待決済」状態で直接「発送/開通」API を呼んで決済を飛ばす。決済を迂回するほうが金額偽造より一般的だ。
**Q6**: これらが全て防御済みで、金額ロジックが堅い。
**A6**: 「報酬の搾取/資金増殖」の直交面に替える。返金フロー(返金額 > 実払、重複返金)、残高/ポイント互換の丸め誤差、通貨交換の四捨五入アービトラージ。資金システムの脆弱性は「買う」側でなく「返す/換える」側に多い。

### クーポン/ポイント/報酬の搾取系のロジック
**Q1**: 対象が EC/マーケティングシステムだ。報酬の搾取点を探したい。発想は?
**A1**: 「発行」と「検収」の両端の不均衡を探す。空から価値を生む動作を全て列挙する。クーポン受取、チェックイン、招待リベート、初回割引、タスク報酬。逐一問う。反復誘発できるか?自分を自分で招待できるか?報酬発行に冪等/重複排除があるか?まず「重複受取可能」を攻める。
**Q2**: クーポン受取 API に一人一枚の制限がある。
**A2**: 制限が「どの次元でロックされるか」を測る。userId でロックするなら、デバイス/新規アカウントを替えて迂回できるか。携帯番号でロックするなら、異なる接頭辞、空白付与、大文字小文字、別名メールで一意性を迂回できるか。フロントエンドの disable ボタンに依存するなら、直接 API をリプレイする。制限次元と一意性判定が報酬の搾取の急所だ。
**Q3**: バックエンドに冪等があり、単一アカウントで二枚目を受け取れない。
**A3**: 並行次元に転じる。競合だ。冪等検査と実際の発行の間に時間窓があることが多い。同じリクエストを並行で N 部送り、「未受取と確認後」に一斉に書き込み、受取制限を突破するかもしれない。並行/単パケット複数リクエストでこの TOCTOU 窓を打つ。
**Q4**: クーポンの重ね掛けルールを悪用できるか?
**A4**: ルールの組み合わせを測る。満額割引クーポン + 割引クーポン + 送料無料が想定外に重ねられるか、クーポンが除外商品に使えるか、先に注文してクーポンを使い後で商品を変える、返金時にクーポンが原路返還されて再利用できるか。業務ルールの組み合わせ爆発の箇所に漏れたロジックが最も多い。
**Q5**: クーポンシステムが厳しく、搾り取れない。
**A5**: 直交目標に替える。販促/招待キャッシュバックの資金ループ。A が B を招き、B が A を招いて互いに稼ぐ、登録キャッシュバック > 新規獲得コストで正の収益ループを作る。マーケティングシステムの金の漏れは「人を引く」グラフ構造にあり、単枚のクーポンではない。

### 競合条件(Race Condition)の判定と利用
**Q1**: ある操作に競合があると疑うが、確かでない。まず打つ価値があるかをどう判断する?
**A1**: 「検査-then-使用」且つ有限資源/カウンタが関わる操作を探す。出金、在庫引当、受取制限、投票、残高減算。判定基準: その操作が「値を読む→判断→書き戻す」であり、二歩が非原子か。この種の TOCTOU は競合の温床だ。逆に純冪等/無状態の操作は打たない。
**Q2**: この窓を実際にどう打つ?
**A2**: 複数の同じリクエストを並行送信し、「検査通過済みだが未書き戻し」の瞬間に同時に落とす。ツールでは単一接続複数リクエスト(HTTP/2 単パケット)か複数スレッドで同時送信する。鍵は到達時間差を圧縮することで、同時に近いほど命中窓が大きい。
**Q3**: 数十並行打っても効果がない。
**A3**: 時間窓が極めて狭いかもしれない。戦略は、まず大量並行で命中確率を上げる。それでも当たらないなら、「臨界区間を引き延ばす」工夫をする。サーバー処理遅延を作る(大 payload、遅いクエリ誘発)、ネットワークジッタを利用する。あるいはこの点がそもそも原子的(DB 行ロック/一意制約)かもしれないので、点を替える。
**Q4**: この API に DB 一意制約があり、原子性が非常に強いと確認した。
**A4**: 「クロス API 競合」に転じる。単一 API は原子でも、二つの異なる API が同一資源を操作するときグローバルロックがない。「出金」と「振込」がそれぞれ原子でも、並行で走らせれば残高が二度使われるかもしれない。同一状態を共有しつつ各自独立にロックする API ペアを探す。
**Q5**: 競合は確かに存在するが一、二回しか多重受取できず、危害が小さい。
**A5**: 深掘りする価値があるかを評価する。競合の価値は「増幅できるか」にある。クーポン 1 回の多重受取は危害が低いが、命中したのが出金/残高なら、小窓でも数十回反復すれば実質の資金損失だ。標的価値で投入を決め、低価値競合は果断に諦めて他のロジック面に転じる。

### パスワードリセットのロジック脆弱性
**Q1**: アカウント乗っ取りを打ちたい。「パスワードを忘れた」フローに注目した。まず何を見る?
**A1**: リセットトークンの「生成-配信-検証」の三段を分解する。まず token がどこから来るかを問う。メール/SMS に送られる(不可視)か API 返りボディにある(可視)か?次に token 強度を問う。ランダム長文字列か、予測可能なタイムスタンプ/連番/短い数字検証コードか。予測可能か可視の token は直接乗っ取れる。
**Q2**: token が 6 桁の数字検証コードで、携帯に送られ、見えない。
**A2**: ブルートフォース可能性に転じる。6 桁数字は百万空間にすぎない。サーバーに試行回数制限、検証コード有効期限、ロック機構があるかを見る。制限が欠けるか、IP を替える/session を消してカウントをリセットできれば、ブルートフォースする。判定基準は「誤り試行後のシステム挙動が収束するか」だ。
**Q3**: 回数制限があり、5 回でロックされる。
**A3**: 「制限の作用域」迂回を探す。制限は検証コードに紐づくかアカウントに紐づくか?新しい検証コードを再申請して試行カウントをリセットできるか(申請無限 + コードごとに数回 = 変則無限)?並行検証でカウンタ競合を迂回できるか?制限の束縛次元が迂回できるかを決める。
**Q4**: 発想を変え、検証コードを推測せずロジック迂回できないか?
**A4**: 検証ロジックの欠陥を測る。レスポンスに token が漏れないか、正誤の差異(タイミング/長さ)が漏れないか。リセットリクエストの「誰に送るか」を改ざんできるか。携帯/メールフィールドを被害者に変えて token は自分のものを使う。HTTP host ヘッダがリセットリンクのドメインに影響するか(host 注入で token を盗む)。
**Q5**: トークンフローが厳しく、ブルートフォースもロジックも通らない。
**A5**: リセットの「次の一歩」に転じる。新パスワード設定の一歩が独立して権限外アクセスできるか。あるシステムは token 検証は厳しいが、「新パスワード送信」API が userId だけを認めて token を認めない、token が使い切りでなく失効せずリプレイできる。攻撃面を「token を取る」から「token を使う API 自体」へ移す。
**Q6**: それも駄目で、リセットチェーン全体が堅い。
**A6**: 乗っ取り経路を完全に替える。携帯/メールの紐づけ変更フロー、OAuth 紐づけハイジャック、session 関連脆弱性、登録時のアカウント先取り(被害者メールで登録してアカウント統合されるか)。アカウント乗っ取りは複数の道があり、リセットはその一つだ。

### 多段フローのステップ飛ばし/状態機械迂回
**Q1**: 対象に多段ウィザード(実名認証、口座開設、決済など)がある。ステップ飛ばしを疑う。どう測る?
**A1**: まず正常フローを一度完全に通し、各ステップの API とそれが設定する「状態フラグ」を記録する。核心の問いは、第 N ステップに入るときサーバーが「第 N-1 ステップ完了」を検証するかだ。測り方: 最後のステップの API を直接リクエストし、前の全ステップを飛ばして通過するかを見る。
**Q2**: 最後のステップに直接ジャンプすると「先に前のステップを完了してください」と返る。
**A2**: 状態検証があるということだが、検証根拠がどこにあるかを見る。状態がクライアントにある(cookie/隠しフィールド/step パラメータ)なら、step を直接完了状態に変える。サーバー session にあるなら、並行か乱順呼び出しで状態機械を想定外の組み合わせにする。状態の保存位置が攻め方を決める。
**Q3**: 状態がサーバーにあり、変えられない。
**A3**: 「部分完了」の中間状態の脆弱性を探す。ステップ 1、2 を完了して中間認証情報を取り、ステップ 3 で前に確認済みのデータを改ざんする(実名時に身分証を変える、口座開設後に紐づけカードを変える)。システムは「前に検証済み」を信頼して改ざんされた値を再検証しない。既にロックされたが編集可能なフィールドを攻める。
**Q4**: ある重要な検証ステップ(決済、審査)を飛ばせるかを検証したい。
**A4**: 状態機械の「分岐」を探す。正常経路は審査が必要だが、「下書き直接公開」「インポートで審査飛ばし」「管理者代行操作」という支路があり、権限検証が緩い。終状態に到達する全ての経路を列挙し、防御が最も弱い経路を打つ。
**Q5**: 全ての経路が厳格に直列検証する。
**A5**: タイミング/ロールバック次元に転じる。フロー完了後に「ロールバックして再変更」でき、終状態データと検証済みデータを分離できるか。提出済み注文をさらに変更できるか。二つのフローインスタンスを並行させ、A フローの検証済み状態を B フローが再利用できるか。「ステップ飛ばし」から「状態の乱れ/再利用」という直交面に転じる。

### JWT/token 関連の権限外アクセス
**Q1**: キャプチャすると認証が JWT だ。token 自体から権限外アクセスを探したい。まず何を見る?
**A1**: JWT を解いて三部を見る。header の alg、payload の身元宣言(sub/role/uid/tenant)。第一のテスト点: alg を none に変えられるか(署名除去)、payload の role/uid を変えてサーバーが再検証するか。サーバーが payload を信頼し且つ検証に欠陥があれば、直接身元を変えて乗っ取る。
**Q2**: alg:none を試して拒否され、署名は HS256 だ。
**A2**: アルゴリズム混乱を測る。サーバーが RS256 と HS256 を同時にサポートするなら、公開鍵を HMAC 鍵として使うかもしれない。公開の RSA 公開鍵を HS256 の secret として再署名し、サーバーが公開鍵で HMAC を検証すれば通る。前提は公開鍵を取れること(証明書/jwks エンドポイント)。RS/HS 混乱の古典的な攻め方だ。
**Q3**: アルゴリズム混乱も駄目だ。純粋な対称鍵かもしれない。
**A3**: 弱鍵ブルートフォースに転じる。HS256 の secret が弱いパスワード(secret/辞書語)なら、オフラインで署名をブルートフォースできる。JWT 解読辞書を回す。secret を割れば任意の身元を偽造できる。判定基準は鍵のエントロピーで、一般的なフレームワーク既定鍵、サンプル鍵を重点的に試す。
**Q4**: 鍵が割れず、非常に強い。
**A4**: token のライフサイクルとスコープに転じる。token が期限切れ後も使えるか、ログアウト後に失効するか、A サービスの token を B サービスに使えるか(受信者 aud を検証しない)、低権限 token をリフレッシュ後に高権限 scope を注入できるか。token の「どこで使うか」は「偽造できるか」より緩いことが多い。
**Q5**: 全て厳しく、JWT のこの道が封じられた。
**A5**: 認証以外の権限外アクセス面に替える。JWT が堅くても業務 API の認証・認可が堅いとは限らない。token は「誰か」だけを証明し、「何にアクセスできるか」を保証しない。正当な token を持って前の全ての IDOR/垂直権限外アクセスを打つ。認証強 ≠ 認可強。火力を「身元偽造」から「正当身元下の権限外アクセス」へ移す。

### 権限外アクセス探査が WAF/不正検知遮断を誘発した
**Q1**: 権限外アクセスを一括テスト中に突然遮断され、リクエストが検証コードを返す/IP を封じる。どうする?
**A1**: まず「頻度」か「内容」かを分ける。速度を落として数発送る。正常に戻れば=頻度不正検知。同じく遮断されれば=内容特徴が命中。頻度問題なら遅くする、IP プールを替える、ランダム遅延を加える。内容問題だけ payload を変える必要がある。一発で特徴を猛打しない。
**Q2**: 頻度不正検知で、速くするとすぐ封じられる。
**A2**: 権限外アクセスの検証はそもそも高頻度を必要としない。一つの IDOR を証明するのは二、三の対照リクエストだけだ。「量を走らせて全量ダンプ」を諦め、「正確なサンプリング + ロジックで列挙可能を説明」に替える。リズムを人間の操作レベルに落とせば不正検知はほぼ誘発しない。低頻度正確は不正検知迂回の最適解だ。
**Q3**: 内容特徴で、あるパラメータ値を送ると即遮断される。
**A3**: これは純粋なロジック権限外アクセスより SQLi/XSS 特徴が WAF に遮られた可能性が高い(ロジック権限外アクセスは正当な数字を変えるので通常特徴がない)。本当に内容で遮られるなら、パラメータに攻撃特徴を注入した可能性がある。純粋な業務値(正当な形式の ID)に戻って権限外アクセスを測り、注入系 payload を分離して別処理する。
**Q4**: IP を封じられ、テスト全体が停止した。
**A4**: インフラ次元に転じる。出口 IP を替える(住宅プロキシ/複数クラウドノード)、UA/フィンガープリントを替える、アカウントごとに別出口を束縛する。同時に評価する。不正検知がこれほど敏感なら、対象に成熟した防御があり、権限外アクセス面もゲートウェイに統一集約されている可能性がある。主攻方向を防御の薄弱なサブシステム/旧 API に移すことを考える。
**Q5**: IP を替えてもすぐ関連付けて遮断される。
**A5**: 不正検知が行動プロファイリングをしている(デバイスフィンガープリント/操作シーケンス)。「本物の正当トラフィックに紛れ込む」に転じる。正常業務操作の合間にテストリクエストを挿入し、人間のリズムを模す。あるいは攻撃面を不正検知を通らない内部/API 直結入口に替える。外層不正検知が解けないとき、不正検知層を迂回する入口を探すほうが硬直な不正検知対抗より賢明だ。

### 権限外アクセスが「無エコー」で、打てたかわからない
**Q1**: 権限外アクセスの書込操作を呼んだ。200 が返るが効果が見えない。成否をどう確認する?
**A1**: 帯外検証か二次読取チャネルを確立する。書込操作(他者のプロフィール変更、他者データ削除)後、被害者アカウントに戻るか別の読 API でそのデータが本当に変わったかを調べる。書込 API の返りコードだけを信じない。それは「成功を返しても無言でフィルタされた」かもしれない。状態変化の観測可能な結果を基準にする。
**Q2**: 被害者アカウントがなく、結果を検証できない。
**A2**: 自己観測可能な資源を使う。権限外アクセス操作を「こちらが読めるオブジェクト」に作用させる。あるいは帯外(OOB)。操作が通知/メール/webhook を誘発するなら、制御可能な受信端を置いて戻りを観察する。直接エコーがないとき帯外チャネルが判定の利器だ。
**Q3**: 操作が「バックグラウンドタスクを誘発」し、完全にブラックボックスだ。
**A3**: 時間/副作用の傍証を使う。操作後にレスポンス時間の変化、後続 API が返すカウンタ/タイムスタンプの変動、新しい資源 ID の生成を観察する。ロジック脆弱性の判定は「システム状態の観測可能な擾乱」に頼ることが多く、直接エコーではない。
**Q4**: 傍証が何もなく、純粋に無言だ。
**A4**: 盲テストの発想に転じる。盲 SQLi に似て、「操作が効けばシステム挙動 A、さもなくば B」の差分実験を構築する。権限外削除後に同名資源を再作成して衝突するかを見る。二値化した観測可能な差異で操作が足場確保されたかを逆算する。
**Q5**: 盲テストでも差分が立たず、この点は観測できない。
**A5**: 果断にエコーのある権限外アクセス面に転じる。ブラックボックスで観測できない点は費用対効果が極めて低く、時間を即検証できる読型 IDOR、結果が見える操作に投じる。観測不能 ≈ 証明不能。レッドチームが要るのは証明可能な戦果で、転じるのが即ち損切りだ。

### マルチテナントシステムのテナント隔離権限外アクセス
**Q1**: 対象が SaaS マルチテナントだ。テナントを一つ登録した。テナント横断の権限外アクセスをどう探す?
**A1**: 核心は「テナント識別子」と、それが強制束縛されるかを見つけることだ。キャプチャしてリクエスト内の tenantId/orgId/workspace パラメータがどこにあるか、クライアント制御可能かを調べる。測り方: こちらの tenantId を別テナントの値に変え、相手の資源にアクセスできるかを見る。テナント ID が列挙可能/推測可能で、サーバーがそれだけでデータを取るなら、隔離が破れた。
**Q2**: リクエストに明示的なテナントパラメータがなく、token 内蔵だ。
**A2**: テナントが身元に束縛され、直接パラメータ変更が無効だ。相手の資源 ID(注文/ファイル/ユーザー ID)で直接アクセスし、サーバーが ID でデータを取るとき「その資源が現テナントに属するか」を検証するかを測る。多くのシステムの認証・認可は「ログインした」までで、「資源のテナント帰属」の層を漏らす。
**Q3**: 資源 ID が UUID で列挙できず、他者の ID を取れない。
**A3**: ID 漏えいチャネルを探す。招待リンク、共有機能、エクスポートファイル、ログ、エラー情報、検索 API、自動補完。マルチテナントシステムは「協業/共有」機能でテナント横断 ID を漏らしがちだ。あるいは自分のテナントを二つ登録して相互対照し、先に隔離機構の欠陥存在を証明し、危害面はロジックで論証する。
**Q4**: データ面の隔離がかなり良い。
**A4**: 制御面に転じる。テナントのメンバー管理、ロール設定、課金、サブドメイン/カスタムドメインの束縛。自分を別テナントに加入できるか、他者のドメインを束縛できるか、相手テナントの設定を権限外で変えられるか。制御面の隔離はデータ面より雑なことが多い。
**Q5**: 完全隔離で、テナント境界が非常に堅い。
**A5**: 共有インフラ層に転じる。マルチテナントはキャッシュ、メッセージキュー、ファイルストレージバケット、検索インデックスを共有しがちだ。キャッシュキーにテナント次元が含まれるか(キャッシュ取り違え)、アップロードファイルの保存パスがテナント横断アクセスできるか、グローバル検索が他テナントデータを漏らすかを測る。隔離の脆弱性は「見落とされた共有の土台」に隠れがちだ。

### 「権限外アクセスで単一を読む」から「アカウント乗っ取り」への格上げ
**Q1**: 任意ユーザー情報を読める IDOR があるが、読むだけだ。どうアカウント乗っ取りへ格上げする?
**A1**: この IDOR が漏らす「乗っ取り素材」を棚卸しする。メール/携帯(リセット用)、秘密の質問、API key、session token、紐づいた第三者情報。token 系の認証情報を読めれば直接使う。IDOR の価値は、それが漏らすフィールドが別の乗っ取りチェーンに接続できるかにある。
**Q2**: 基本プロフィールしか読めず、認証情報がない。
**A2**: 漏れたプロフィールをパスワードリセット/身元検証フローに与える。メール+誕生日+携帯末尾がわかれば、「アカウント復旧」の検証条件を満たせるかもしれない。IDOR が与える情報 + 薄い二次検証 = 組み合わせて乗っ取り。単独脆弱性が不十分なら、連結できる第二の環を探す。
**Q3**: 直接の書込型権限外アクセスで認証情報を変えられるか?
**A3**: 読型 IDOR から対応する書型を探る。同じ userId パラメータで、プロフィール更新 API を試す。他者のメール/携帯をこちらのものへ権限外で変えられるか、その後正常なリセットフローで乗っ取る。読み書き IDOR は対で現れがちで、ID を読めたら「紐づけ連絡先の変更」を重点的に試す。
**Q4**: 書 API に追加検証がある(メール変更に検証コード)。
**A4**: session/token 層の乗っ取りに転じる。他者の session を権限外でリセットできるか、そのアクティブ token を読んで再利用できるか、OAuth 紐づけをハイジャックできるか。「認証情報変更に二次検証が必要」の迂回は、既存のセッション認証情報を直接盗み使うことだ。
**Q5**: 認証情報層も乗っ取れない。
**A5**: 一歩引いて戦果を再評価する。大量のユーザー PII を権限外で読めるだけでも、それ自体が高危険なデータ漏えい脆弱性だ。無理に乗っ取りへ格上げしない。レッドチームの目標は影響の証明可能な最大値で、一括 PII 漏えい + ロジック説明で納品できる。「乗っ取り」への執念で時間を無駄にしない。

### フロントエンドに隠された機能/API(クライアント認証・認可の信頼)
**Q1**: 画面の機能が少ないが、バックエンドにそれ以上の能力があると疑う。どう掘る?
**A1**: フロントエンドを地図として見るのであって壁ではない。全 JS(特にバンドルされた main.js/chunk)をダウンロードし、API パス、ルート定義、権限判定ロジックを抽出する。フロントエンドはリクエストを減らすため、完全な API リストとロール列挙をハードコードしがちだ。これが隠し機能の宝の地図だ。
**Q2**: JS が圧縮難読化され、読めない。
**A2**: ツールで文字列を抽出する。正規表現で `/api/`、`http`、パスパターン、role キーワードを拾う。ロジックを読む必要はなく、エンドポイントとパラメータ名を掬い出せばよい。難読化はロジックを塞ぐが文字列定数は塞げない。エンドポイントを拾ったら直接バックエンドへリクエストを送って測る。
**Q3**: 大量の API を掘った。どれを先に打つ?
**A3**: 優先順位: 名前に admin/internal/debug/export/delete/config を含むもの、パラメータに id/user/all を含むもの、フロントエンドに `if(role===...)` で門番された機能に対応する API。フロントエンドが条件文で隠す機能 = バックエンドが二次認証・認可をしていない可能性が高い。門番が最も厳しいフロントエンド機能ほどバックエンドは最も緩いことが多い。
**Q4**: フロントエンドで disable されたボタンを見つけた。対応 API を直接呼ぶと通った。
**A4**: クライアント認証・認可の信頼を実証した。即座にこのパターンを全ての「フロントエンド制限」動作に横展開する。禁じられた、隠された、グレーアウトのボタンを全て測る。一点が通れば、このシステム全体がフロントエンド認証・認可に依存していることを示し、一括で収穫する。
**Q5**: API がフロントエンドの送る署名/token を要求し、単独呼び出しがエラーになる。
**A5**: フロントエンドの正当なコンテキストを再利用する。ブラウザのログイン済みセッションで、コンソールからフロントエンドの API ラッパー関数を直接呼ぶ(それが自分で計算した署名を付ける)、ゼロからリクエストを構築しない。フロントエンドに署名させ、「API が複雑なフロントエンド計算を必要とする」壁を迂回する。

### GraphQL API の権限外アクセスと情報漏えい
**Q1**: 対象が GraphQL を使うとわかった。REST の権限外アクセス測定と何が違い、まず何をする?
**A1**: まず introspection クエリを試し、完全な schema を取る。全種別、フィールド、クエリ、変更。これは API 全景図を直接得るのと同じだ。introspection が開いていれば、mutation リストを全部掘り出す。そこに REST 画面では見えない管理/内部操作が隠れている。schema は GraphQL 権限外アクセスの起点だ。
**Q2**: introspection が無効化された。
**A2**: フィールドブルートフォース/ドキュメント推測に転じる。GraphQL エラー情報は「did you mean X」と示しがちで、フィールド名辞書で存在するフィールドを探せる。あるいはフロントエンド JS の query 文から schema を逆算する。introspection が閉じても schema が秘密になるわけではない。一般的なクライアント(Apollo)の永続化クエリ漏えいも試す。
**Q3**: GraphQL でどう権限外アクセスを打つ?
**A3**: GraphQL の認証・認可はしばしばフィールド級で、漏れやすい。測るのは、一つのクエリに他者のオブジェクトをネストしてアクセスできるか(node(id:) か関連フィールドで未認可データへジャンプ)、mutation がオブジェクト帰属を検証するか。ネストクエリは「入口は認証・認可するが深層フィールドは認証・認可しない」欠陥を迂回できる。
**Q4**: 単一クエリの認証・認可は全てされている。
**A4**: GraphQL 特有の攻撃面に転じる。別名一括(alias で一つのリクエストに数百変種を送り、レート制限を迂回して検証コードブルートフォース/列挙)、クエリのネストが深すぎる DoS、一括クエリ(batching)で毎リクエスト制限を迂回。GraphQL の「一リクエスト多操作」特性は制限迂回の利器だ。
**Q5**: 全て防がれ、GraphQL 層がかなり堅い。
**A5**: GraphQL の後ろの resolver ロジックに転じる。GraphQL は入口にすぎず、後ろの resolver は直接 SQL を連結したり内部サービスを呼んだりすることが多い。注入(GraphQL パラメータが SQL へ)、SSRF(あるフィールドが内部リクエストを誘発)、resolver の下層 IDOR への透過を測る。攻撃面を「GraphQL プロトコル層」から「それが呼ぶバックエンドロジック」へ沈める。

### 検証コード/二次検証(SMS、図形、OTP)の迂回
**Q1**: 重要な操作に検証コード/OTP が必要だ。迂回したい。まず何を判断する?
**A1**: まず検証コードがフロー内で「必須か任意か」を特定する。キャプチャして見る。検証コードフィールドを付けないか空値を付けて直接送信し、サーバーが通過するか。大量のシステムはフロントエンドが強制、バックエンドは選択検証だ。判定基準: 検証コードパラメータを除去/空にしたときのサーバー反応。最も楽な第一テストだ。
**Q2**: バックエンドが確かに検証し、空値は通らない。
**A2**: 検証の一般的な欠陥を測る。検証コードが使い切りか(使用後も失効せずリプレイ可能)、有効期限が無限か、操作/アカウントに紐づくか(A の検証コードを B の操作に使えるか)、レスポンスに検証コードか「正誤」の傍証が漏れないか。ロジック欠陥はブルートフォースより清潔だ。
**Q3**: 4-6 桁の SMS/図形コードだ。ブルートフォースしたい。
**A3**: ブルートフォース可能性の三要素を判定する。コード空間(4 桁数字=万級でブルートフォース可能)、試行回数制限、検証コードの交換頻度。ロックがないかカウントをリフレッシュできるなら、直接ブルートフォースする。図形コードはさらに OCR 自動認識か既知の固定/弱いコードを試す。空間小 + 無制限 = ブルートフォース可能。
**Q4**: 回数制限があり検証コードが強い。
**A4**: 「検証コード非リフレッシュ」の競合か状態の脆弱性に転じる。同じ検証コードがサーバーで未クリアの間に並行送信する、申請後に使用せず直接次のステップへ進む(あるシステムは申請即通過扱い)。「送信の迂回」も測る。送信後の検証 API を直接呼ぶ。検証コードの状態管理を攻め、その値ではない。
**Q5**: 検証コード機構が全体としてかなり堅い。
**A5**: 検証コードが「保護する動作に迂回路がないか」に転じる。検証コードはログインを守るが、「ログイン保持」token/OAuth ログイン/API key ログインは検証コード不要かもしれない。検証コードが守るのはこの一つの入口で、同じ目的に達する検証コード不要のチャネルを探すほうが、正面から検証コードを破るより高効率だ。

### OAuth/SSO シングルサインオンのロジック欠陥
**Q1**: 対象が第三者 OAuth/SSO ログインを使う。ここからアカウント乗っ取りを打ちたい。どの点に注目する?
**A1**: OAuth の古典的な欠陥はいくつかのパラメータに集中する。redirect_uri(こちらの制御するドメインに変えて code/token を盗めるか)、state(欠如なら CSRF でアカウント紐づけ)、「email でアカウントを関連付ける」信頼問題。まず完全な OAuth フローをキャプチャし、これらのパラメータが改ざん可能かをマークする。redirect_uri 検証の緩さは激戦区だ。
**Q2**: redirect_uri にホワイトリスト検証がある。
**A2**: ホワイトリストの緩いマッチングを測る。ドメイン接頭辞だけを検証するか(`evil.com/whitelisted`)、サブパスのオープンリダイレクトを許すか、path traversal があるか、`whitelisted.evil.com` が通るか。ホワイトリストは不厳格な文字列マッチを使いがちで、マッチングロジックの縫い目を探す。同ドメインの open redirect 中継で code を盗むのも測る。
**Q3**: redirect_uri がかなり固定された。
**A3**: email の信頼チェーンに転じる。システムが OAuth の返す email で既存アカウントをマッチし、メールが検証済みかを検証しないなら、第三者で被害者の email を使うアカウントを登録し(メール未検証)、それで OAuth ログインすれば対象アカウントを乗っ取れる。「OAuth 身元からローカルアカウントへのマッピング」の信頼を攻める。
**Q4**: state/CSRF 防御もあり、email も検証状態を検証する。
**A4**: token/code の再利用に転じる。認可コードが使い切りか、クライアント間で使えるか、インプリシットフローの token が URL/referer/ログに漏れないか、紐づけフロー(第三者アカウントをローカルに紐づけ)が CSRF にハイジャックされて「攻撃者の第三者アカウントを被害者のローカルアカウントに紐づける」ことができるか。紐づけ方向の CSRF は見落とされがちだ。
**Q5**: OAuth フロー全体がかなり厳格だ。
**A5**: OAuth 以外のログイン方式の併存問題に転じる。システムはしばしば OAuth とパスワードログインを同時にサポートする。OAuth 登録のアカウントにリセット可能な空パスワードがあるか?OAuth アカウントに「パスワードを忘れた」を走らせてパスワードを設定し、OAuth 乗っ取りを迂回できるか?複数ログイン方式のアカウントは往々にして方式切り替え箇所に縫い目がある。

### API バージョン/ドキュメント漏えいがもたらす権限外アクセス入口
**Q1**: 新版 API を測っている。防御がかなり良いが、旧 API があると疑う。どう探す?
**A1**: バージョン痕跡を能動的に探査する。`/api/v3/` を v1/v2/v0/beta/internal に変える、`/api/` を `/api2/`、`/legacy/` に変える。旧版 API は長年放置され、認証・認可が旧基準だ。同時に swagger/openapi/graphql schema/`.well-known` などの自己記述ドキュメントを探し、全量 API を直接得る。旧 API は新防御を迂回するバックドアだ。
**Q2**: swagger ドキュメントを見つけた。どう高効率に利用する?
**A2**: ドキュメントから「高危険 + 認証・認可漏れの可能性」の API を篩う。一括エクスポート、管理操作、内部サービス、debug/test エンドポイント。ドキュメントはパラメータと認証要否を表記する。認証不要か認証が弱いと表記されたものを直接打つ。ドキュメントは攻撃面を明示標価で与えてくれる。
**Q3**: swagger が認証必須で見られない。
**A3**: 他のドキュメント漏えいチャネルに転じる。フロントエンド JS の API 呼び出し、モバイル App の逆コンパイルで出る API リスト、Postman 公開コレクション、コードホスティングプラットフォームでその組織が漏らしたコード/ドキュメント、Web アーカイブの旧 API。ドキュメントは一箇所で不通でも他に漏えい面がある。
**Q4**: 旧 API を見つけたが、それも認証が必要だ。
**A4**: 旧 API の価値は「認証・認可の実装が古い」ことにある。廃止された弱い認証・認可を使っていないか(旧版署名アルゴリズム、予測可能な token、basic auth の弱いパスワード)、新システムがもはや信頼しないものを信頼していないか(内部ネットワーク header、debug パラメータ)。旧 API + 旧認証・認可 = 縫い目。
**Q5**: 旧 API が全部オフライン/厳格認証・認可だ。
**A5**: バージョン間の「データ一致性/移行」脆弱性に転じる。新旧バージョンがデータベースを共有し、旧 API の書込データが新 API の検証ルールを迂回できるかもしれない。移行期の互換層が旧形式を信頼する。バージョン入口が全て封じられたら、新 API の業務ロジックそのものに注意を戻す。バージョン探査は補助手段にすぎない。

### ファイルアップロード/ダウンロードのロジック権限外アクセス(webshell 向けでない)
**Q1**: ファイルアップロード/ダウンロード機能がある。webshell を追わず、権限外アクセスを探したい。何を見る?
**A1**: ダウンロード側を先に測る。ダウンロード URL のファイル ID/パスが変えられるか、他者のファイルをダウンロードできるか(ファイル型 IDOR)、パストラバーサルでサーバーファイルを読めるか。アップロード側を測る。アップロード後に返る保存パスが予測可能か、他者のファイルパスが列挙できるか。ファイルの「保存パス + アクセス制御」が権限外アクセスの核心だ。
**Q2**: ダウンロードに token が必要で、ファイル ID が UUID だ。
**A2**: token と ID の束縛検証に転じる。ダウンロード token が「有効」だけを検証して「この token がこのファイルに対応する」を検証しないか。つまり自分のファイルの正当な token で他者のファイル ID をダウンロードする。token と資源の非束縛はよくある欠陥だ。UUID 漏えいチャネル(共有リンク、リスト API)も探す。
**Q3**: 束縛がかなり厳しい。
**A3**: 「アップロードが誘発する権限外アクセスの結果」に転じる。アップロードで他者のファイルを上書きできるか(同名/同パス上書き)、アップロードしたファイルが他者のアクセスできる公共空間に入らないか、アバター/添付のアップロードが任意の保存パスを指定できるか(パストラバーサル書き込み)で重要ファイルを上書きする。書側の権限外アクセスは読側より危害が大きい。
**Q4**: アップロードが他ユーザーに影響できるかを測りたい。
**A4**: 「アップロード内容が誰に消費されるか」を測る。アップロードしたファイルが管理者バックグラウンドでプレビューされるか(XSS/SSRF を管理者へ)、インポート解析されるか(XXE/エクスポート CSV への数式注入)、設定/テンプレートとして他ユーザーにロードされるか。アップロードは「制御可能な内容を他者のコンテキストへ送り込む」チャネルだ。
**Q5**: アップロード/ダウンロードがよく隔離されている。
**A5**: ファイル処理の資源/ロジック面に転じる。アップロードサイズ/数量制限を迂回して割当を打つか、アップロード後に無限ダウンロードでトラフィックを水増しするか、画像処理が SSRF できるか(リモート URL 取得)、ファイル名がパス/コマンドに入るか。アクセス制御が縫い目なしなら、攻撃面を「ファイルが処理される過程」という直交次元に移す。

### 一括/エクスポート API の権限外アクセスとデータ増幅
**Q1**: 単条データは権限外アクセス防御されているが、一括クエリ/エクスポート API がある。単独で打つ価値がある?
**A1**: 非常に価値がある。一括 API は「防御の不一致」の高頻度地帯だ。単条クエリは帰属を検証するが、一括クエリ(ID 配列、範囲、all=true を渡す)はアプリ層でだけフィルタするか全くフィルタしないかもしれない。測る: 他者 ID を含む配列を渡す、空のフィルタ条件を渡す、超大ページングを渡す、範囲外データが返るかを見る。
**Q2**: 一括 API が他者 ID を渡すとフィルタされる。
**A2**: フィルタが徹底か測る。「自分の ID + 他者 ID」の混合配列を渡し、一部だけがフィルタされるかを見る。ネスト/エンコード変形の ID でフィルタを迂回する。範囲クエリ(startId-endId)で明示列挙の代わりにする。フィルタロジックは「混合入力」「異常形式」に疎漏が多い。
**Q3**: エクスポート API が自分のデータだけを導く。
**A3**: エクスポートのフィルタ条件が注入できるかを測る。filter/query/sort パラメータが注入されて WHERE 条件を無効にできるか(ロジック注入か SQL 注入)、エクスポートテンプレート/フィールド選択が権限外フィールドを指定できるか。エクスポート API の背後は制御可能なクエリ構築であることが多く、注入 + 権限外アクセスの複合点だ。
**Q4**: エクスポートが安全だが、既にある小さい権限外アクセスを増幅したい。
**A4**: 一括 API で単点の権限外アクセスを増幅する。単条を権限外で読める IDOR があるなら、一括版 API で一度に全量を引けるかを見る。「一度に一つ」を「一度に一庫」に変える。一括 API は権限外アクセス危害の増幅器だ。
**Q5**: 使える一括入口がなく、一括面が通らない。
**A5**: 「ページング/検索」という隠れた一括面に転じる。検索 API がワイルドカード/空キーワードで全庫を返すか、ページング limit を超大に設定できるか、集計統計 API が隠れたデータの存在を漏らすか(カウント漏えい)。明示的なエクスポートが無門でも、検索とページングが変則的な一括漏えいチャネルであることが多い。

### 登録フローのアカウント先取りと身元衝突
**Q1**: 登録段階からロジック脆弱性を探したい。どんな角度がある?
**A1**: 核心は unique 判定の堅牢性を問うことだ。測る: 被害者の email/携帯で登録すると、システムは拒否か、上書きか、統合か?大文字小文字/空白/Unicode 同形/別名(user+x@)で一意性を迂回し、「見た目は同じで実は異なる」アカウントを登録して混乱させられるか。登録の身元一意性はアカウント安全の地盤だ。
**Q2**: メール一意性の検証がかなり厳しい。
**A2**: 「事前登録先取り」に転じる。被害者が OAuth/SSO で初ログインする前に、その email で手動でローカルアカウントを登録してパスワードを設定する。被害者が後で OAuth ログインしたときこちらのアカウントに統合されれば、乗っ取り。「アカウント作成の先後順序」による所有権帰属を攻める。
**Q3**: 登録時に権限外で属性を設定できるかを測りたい。
**A3**: 登録リクエストをキャプチャし、追加フィールドを注入してみる。role=admin、isVerified=true、tenantId=他者、balance=999、referrer でリベートを稼ぐ。バックエンドが mass-assignment でリクエストボディをそのままユーザーオブジェクトにマッピングするなら、登録即権限昇格。多フィールド伝送はゼロコストの探りだ。
**Q4**: 登録フィールドが厳格なホワイトリストだ。
**A4**: 登録後の「初期状態」脆弱性に転じる。新規アカウントが既定である権限を継承するか、招待登録が招待者の権限を継承するか、トライアル/無料アカウントと有料アカウントが改ざん可能なフラグ一つだけの違いか。「アカウント初期化」時の権限付与ロジックを攻める。
**Q5**: 登録全体がかなり綺麗だ。
**A5**: 登録の「資源消費/列挙」副作用に転じる。登録 API が既存ユーザーの列挙に使えるか(エラー差異が「そのメールは登録済み」を漏らす)、検証 SMS/メール爆撃に乱用できるか、一括登録で資源を水増しできるか。登録が直接権限外アクセスできないとき、少なくともユーザー列挙と乱用の入口になり、後続攻撃に情報を供給する。

### 携帯/メールの紐づけ変更と身元連絡先のハイジャック
**Q1**: システムが携帯/メールの紐づけ変更を許す。ここでアカウント乗っ取りを疑う。どう測る?
**A1**: 紐づけ変更フローの検証要件を分解する。安全な紐づけ変更は「旧連絡先の検証 + 新連絡先の検証」が必要だ。測る: 紐づけ変更が新だけを検証し旧を検証しないか(誰がログインしても自分のものへ変えられる)、紐づけ変更リクエストの対象ユーザー ID が他者へ権限外で変えられるか。旧検証の欠如 + 制御可能な対象 = 乗っ取り。
**Q2**: 紐づけ変更に新携帯の検証コード検証が必要だ。
**A2**: 検証コードは「新携帯」に紐づくか「紐づけ変更動作」に紐づくか?測る: まず自分の携帯に検証コードを送って検証を通し、最終送信時に「新携帯番号」パラメータを被害者の気づかない番号に変える、userId を被害者に変える。検証と最終書込のデータが一致検証されるかが紐づけ変更の脆弱性の鍵だ。
**Q3**: パラメータ束縛が厳しく、対象を変えられない。
**A3**: 競合/タイミングに転じる。紐づけ変更の「検証」と「発効」の二歩の間に、並行挿入して検証済みの旧番号と書込の新番号を分離できるか。「紐づけ変更発起」後長く完了しない間に、アカウント状態が利用可能な中間状態にないか。紐づけ変更の状態機械の原子性を攻める。
**Q4**: 逆に紐づけ変更で拒否サービスや先取りをしたい。
**A4**: 紐づけ変更が他者が使っている連絡先を「先取り」できるかを測る。自分のアカウントの携帯を被害者の携帯に変え、成功し且つシステムが「一携帯一アカウント」なら、被害者の紐づけを蹴り出し、そのログイン/リセットを妨げるかもしれない。紐づけ変更の「旧紐づけ解放」ロジックは武器化できる。
**Q5**: 紐づけ変更機構が堅く、乗っ取りが通らない。
**A5**: 紐づけ変更が誘発する下流影響に転じる。紐づけ変更後に旧 session が不適切に失効しないか(旧 session が有効なら、こちらの紐づけ変更で被害者がオンラインのまま)、紐づけ変更通知が旧連絡先に送られるか(送られなければ被害者は無感覚)。乗っ取れなくても、紐づけ変更の「通知とセッション処理の欠陥」も報告可能なセキュリティ問題だ。目標を乗っ取りから監査欠陥に転じる。

### 権限キャッシュ/レスポンスキャッシュによる権限外アクセス(キャッシュポイズニング/取り違え)
**Q1**: 対象に CDN/キャッシュ層がある。キャッシュが権限外アクセスを引き起こすと疑う。どう切り込む?
**A1**: 核心は「ユーザー非公開のレスポンスがキャッシュされて他者に配られないか」を問うことだ。測る: 認証付きの非公開ページのレスポンスヘッダで Cache-Control が誤ってキャッシュを許していないか(public/無 no-store)。非公開データが CDN にキャッシュされると、異なるユーザーが同じキャッシュに命中 = データ取り違え。まずレスポンスキャッシュヘッダを見る。
**Q2**: 他者の非公開レスポンスをキャッシュさせるには?
**A2**: キャッシュキーの分析。キャッシュは URL(+一部 header)をキーとするがレスポンスにユーザー非公開データを含む。静的にした URL(`/profile.css?x=1` など)に動的非公開内容を返させるか、キャッシュキーに含まれない header 差異を利用(cache poisoning)すれば毒を盛れる。「キャッシュキー」と「レスポンス内容が依存する変数」の不一致を探す。
**Q3**: キャッシュキーがユーザー識別子を含み、取り違えられない。
**A3**: Web Cache Deception(キャッシュ欺瞞)に転じる。`/account/profile/nonexistent.jpg` にアクセスすると、サーバーがアカウントページを返す一方 CDN が `.jpg` 拡張子でキャッシュする。次の訪問者がその URL を読むと被害者のデータを読める。「URL 拡張子がキャッシュ可否を決める」と「パスが実際に動的内容を返す」の錯配を攻める。
**Q4**: キャッシュ欺瞞も防がれた。
**A4**: キャッシュポイズニングで他の影響を打つ。キーに含まれない header でキャッシュを汚染し、XSS/リダイレクトを注入して、その URL を訪問する全ユーザーを被害に遭わせる。目標を「権限外アクセスでデータを読む」から「キャッシュ増幅のクライアント攻撃」に転じる。同じキャッシュ欠陥で異なる影響面を打てる。
**Q5**: キャッシュ層の設定がかなり厳格だ。
**A5**: アプリ内キャッシュに転じる。多くの権限外アクセスの取り違えは CDN でなくアプリ層キャッシュ(Redis/ローカルキャッシュ)のキーにユーザー次元が漏れている。A のリクエスト後 B のリクエストが A のキャッシュに命中する。測り方: A、B が素早く交互に同じ API をリクエストし、B が偶発的に A のデータを取るかを見る。キャッシュ攻撃面をエッジ CDN からバックエンドキャッシュ層に移す。

### 数値境界と符号乱用(負数、オーバーフロー、精度)
**Q1**: 数量/金額/枠に関わる業務に直面した。体系的に境界を測りたい。必測値は?
**A1**: 境界辞書一式を作り逐一流す。0、負数、極大値(int32/int64 超)、小数(整数フィールドに浮動小数点を送る)、超長数字、科学表記、null/空。各数値パラメータを一巡する。ロジック脆弱性は「プログラマが考慮しなかった入力域」に高度に集中する。これはロジックテストの規定動作だ。
**Q2**: 負数が最も問題を起こしやすい場面は?
**A2**: 「数量 × 単価」「残高 ± 変動」「割当の減算」の箇所。負数量→負総額→返金/加算、負振込→相手を逆に引き自分に加算、負チャージ。乗算と減算が制御可能な数値を含む点を探し、負号は梃子だ。
**Q3**: 負数が遮られた(> 0 を検証)。
**A3**: 整数オーバーフローに転じる。型上限に近い極大値を送り、`a + b` か `a × b` をオーバーフローさせて負か小さい値に回り込ませ、`> 0` 検証を迂回する。検証がオーバーフロー前に、使用がオーバーフロー後に行われるとき利用できる。「極大数量」で後続計算の異常も試す。
**Q4**: 浮動小数点精度を利用したい。
**A4**: 金融/ポイントシステムが浮動小数で金を保存するなら、丸めアービトラージを測る。0.5 分の丸めを生む小額取引を反復して利益を蓄積する、超多桁小数で切り捨て偏差を作る。精度問題は「高頻度小額 + 丸め方向固定」で実質利益に増幅できる。
**Q5**: 数値検証が非常に完備している。
**A5**: 「数値の意味」へ転じるのであって「数値そのもの」ではない。同じ操作の重複送信(数量 1 だが N 回リプレイ = 変則超量)、API 間累加で単一 API 上限を迂回、異なる単位/通貨パラメータで換算脆弱性を作る。単値境界が塞がれたら、「複数回/多次元の累積」という直交面に転じる。

### 一つの IDOR を見つけた後、システム全体の権限外アクセスパターンをどう判断するか
**Q1**: 一つの API で IDOR を確認した。それをシステム全体への判断にどう広げる?
**A1**: 一つの IDOR は「認証・認可アーキテクチャの欠陥」の信号であり、孤立したバグではない。直ちに「このシステムはオブジェクト級の認証・認可が全体に欠けている」と仮定し、体系的に検証する。オブジェクト ID 付きの全 API を列挙し逐一測る。判定基準は脆弱性の「根本原因」だ。根本原因が「ID でデータを取って帰属を検証しない」なら、同じアーキテクチャの全 API が被害を受け得る。
**Q2**: 当たる API と当たらない API がある。規則は?
**A2**: 被害を受ける API の共通点を分析する。同一開発チーム/同一フレームワーク/同一時期/同一データアクセス層を辿る API は一緒に当たるか一緒に当たらないか。「認証・認可の断層線」を探す。多くは新旧モジュールの境、マイクロサービスの境界、統一認証・認可ミドルウェアを迂回したルートにある。規則は個別の運試しより高効率だ。
**Q3**: 個別手動でなく、どう素早く大面積検証する?
**A3**: 二アカウント対照法を自動化する。アカウント A の正当なトラフィックを全て録画し、アカウント B のセッションでこのリクエスト群をリプレイする。B のリプレイで A のデータを取れた API が即権限外アクセス。この「セッション置換リプレイ」でサイト全体の IDOR を一度に掃き出せる。
**Q4**: こう測ると特定の前置状態が必要な API を漏らさないか?
**A4**: 漏らす。状態依存のある API(先にオブジェクト作成が必要)はリプレイが失敗する。補足手法として、この種の API では A、B が各自オブジェクトを作り、その後相手のオブジェクト ID を交差アクセスする。「リプレイ失敗」を「脆弱性なし」と誤判定せず、「真に安全」と「単に状態不満」を区別する。
**Q5**: 大面積テストでぽつぽつ数点しか当たらない。
**A5**: システムに統一認証・認可があるが個別の漏れがあることを示す。「最近の変更/最も周辺」の API に転じる。新規機能、グレー API、内部/運用 API、第三者連携コールバック。統一認証・認可体系の脆弱性は「管轄に入りきれなかった」周辺に常にある。火力を主フローからシステムの端材に移す。

### 権限外アクセステストが詰まったときの直交方向転換の総則
**Q1**: 一つの対象で思いつく権限外アクセスを全て試して失敗した。次の一歩をどう決める?
**A1**: まず「一つの次元で反復していないか」を振り返る。権限外アクセスには複数の直交軸がある。身元次元(水平/垂直)、オブジェクト次元(異なる資源種別)、操作次元(読/書/削)、入口次元(異なる API/版/プロトコル)、状態次元(異なるフロー段階)。どの軸が未網羅かを検査し、試した軸に力を加えない。
**Q2**: どの軸も試した気がする。
**A2**: 「信頼境界」の視点に替える。システムはどこで「信頼の仮定」をするか?フロントエンドを信頼、内部ネットワーク header を信頼、第三者コールバックを信頼、検証済みの旧データを信頼、同一テナントを信頼。各信頼の仮定を攻撃点として再検討する。ロジック脆弱性の本質は「誤った信頼」であり、信頼を探すほうがパラメータを探すより本質的だ。
**Q3**: それでも突破できない。
**A3**: 情報駆動に転じる。対象が使うフレームワーク/コンポーネント/SaaS 製品の既知のロジック欠陥と既定設定問題を検索する。多くの業務システムは成熟製品を基にしており、その固有の権限外アクセスパターン(既定権限、サンプル設定、既知 CVE)は自分で盲試するより速く命中する。「盲測」から「既知面への狙い撃ち」へ。
**Q4**: 情報にも合致がない。
**A4**: 攻撃カテゴリを完全に替える。ビジネスロジック/権限外アクセスは Web 攻撃面の一支にすぎない。この線が枯渇したら、横方向に注入系(SQLi/SSTI/コマンドインジェクション)、サーバーリクエスト系(SSRF/XXE)、認証系、インフラ系(コンポーネント脆弱性/設定誤り)へ転じる。レッドチームは一カテゴリに固執せず、タイムリーにカテゴリを切り替えるのが核心規律だ。
**Q5**: Web 面全体がかなり堅い。
**A5**: 攻撃面そのものに転じる。アセットマッピングをやり直して新入口を探す。サブドメイン、隣接サイト、API ゲートウェイ外の直結サービス、モバイル/ミニプログラム専有 API、サプライチェーン(第三者 JS/依存)。既知の攻撃面が全て堅いとき、攻撃面を広げるほうが単点深掘りより価値がある。「新しい扉を探す」方向に転じ、旧い壁を叩き続けない。

### 承認/ワークフローの自己承認とフロー権限外アクセス
**Q1**: 対象に承認フロー(経費精算/公開/権限申請)がある。ロジック脆弱性を探したい。切り口は?
**A1**: まず「申請者」と「承認者」のロール分離を整理する。核心の測点: 申請者が自分の承認者になれるか(自己承認)、承認 API を権限外で呼んで自分の申請を承認できるか、申請書の「承認者」フィールドを制御可能なアカウントに改ざんできるか。ロール分離の無効化がワークフロー第一の脆弱性だ。
**Q2**: 承認者がシステム規則で自動指定され、変えられない。
**A2**: 承認 API の認証・認可を測る。申請者の身元で直接「承認」API(approve action)を呼び、ログインだけを検証して「あなたが指定承認者か」を検証しないかを見る。ワークフローは往々にして権限を UI 層に置く。承認者にだけ承認ボタンを表示するが、API は誰でも呼べる。画面でなく API を攻める。
**Q3**: 承認 API が承認者の身元を検証する。
**A3**: 「承認後改ざん」に転じる。申請通過後、申請内容を変更して「承認済みのもの」と「実際に実行するもの」を不一致にできるか(承認したのは A の 100 円精算、実行時に 10000 に変える)。承認が固定するフィールドが本当に固定か。承認と実行の間のデータ一致性を攻める。
**Q4**: 承認を迂回して直接終状態へ行きたい。
**A4**: 「承認不要の支路」を探す。緊急チャネル、管理者代行送信、一括インポート、API 直結が承認を飛ばさないか。申請金額/レベルが「承認不要の閾値」下にちょうど落ちるようにし、大申請を複数の小額免除申請に分割する。承認誘発条件の境界を攻める。
**Q5**: 承認フローが厳密で、支路がない。
**A5**: 承認の「撤回/再開」ロジックに転じる。承認済みを撤回して再変更し、自動で旧承認を引き継げるか、却下された申請をこっそり変えて前の部分承認を再利用できるか、多段承認で前段通過後に後段が改ざんされたデータで承認できるか。「承認を迂回する」から「承認状態の可逆性とデータ分離」という直交面に転じる。

### 時間/有効期限に関わるビジネスロジック脆弱性
**Q1**: 対象が有効期限(クーポン、会員、token、期間限定活動)に関わる。時間次元の脆弱性を探したい。発想は?
**A1**: 「時間を誰が判定するか」を探す。クライアントが時間パラメータを送れる(注文時間、活動タイムスタンプ)か、クライアント時計に依存するなら、直接変える。サーバー判定なら境界を測る。ちょうど失効する瞬間、タイムゾーン差異、有効期限計算の閏/月末誤り。時間の信頼源と境界が切り口だ。
**Q2**: 時間はサーバー判定だ。
**A2**: 「先取り/延後」に転じる。期間限定活動を開始前に直結 API で先行参加できるか(フロントエンドは未開放だが API は用意済み)、終了後に未失効の旧認証情報で補助参加できるか、予約/秒殺が時間窓を迂回できるか。「活動状態」と「API 可用性」の時間差を攻める。
**Q3**: 有効期限で資源の延命をしたい。
**A3**: 有効期限が想定外に延長できるかを測る。オブジェクト操作がその失効時間をリフレッシュできるか(アクセスごとに延長→永久有効)、トライアル期間をリセット/紐づけ変更で再誘発できるか、期間限定権限の取消後に token が即時失効するか。「失効」という動作が信頼して実行されるかを攻める。
**Q4**: 有効期限機構がかなり厳しい。
**A4**: 競合と時間窓に転じる。失効検査と使用の間の窓で並行使用する(失効間際のクーポン一枚を失効の瞬間に並行検収で複数回使う)。時間境界の原子性欠陥。サーバー時間が間接的に影響できるかも測る。
**Q5**: 時間ロジック全体がかなり堅い。
**A5**: 「時間関連の情報漏えい/列挙」に転じる。レスポンス時間差で資源の有無を判断する(タイミング側チャネル)、token 生成が予測可能なタイムスタンプをシードに使うか(予測可能なら偽造)、有効期限計算がサーバー時間を漏らして他攻撃に使えるか。時間が直接利用できないとき、側チャネルの情報源として使う。

### 検索/フィルタ/ソートパラメータが引き起こす権限外アクセスと注入
**Q1**: 対象に強力な検索/フィルタ機能がある。ここからどんな問題を見つけられる?
**A1**: 検索 API の危険は「ユーザー制御のクエリ条件が直接バックエンドクエリを構築する」ことだ。まず権限外アクセスを測る。filter パラメータを空に/改ざんして既定の「本人のみ」フィルタを無効にできるか、検索で本来見るべきでないオブジェクトにマッチできるか(権限フィルタがアプリ層でなくクエリ層にある)。検索はオブジェクト級の認証・認可を迂回しがちだ。
**Q2**: 検索結果に権限フィルタがされた。
**A2**: フィルタが「クエリ前」か「結果後」かを測る。クエリが全量を引いてアプリ層でフィルタ表示するなら、ページング/カウント不一致(総数が隠しレコード数を漏らす)、ソートパラメータで隠しレコードのフィールド値がソート位置で漏れる、集計統計が無権限データを含む。後フィルタモードは「存在性」と「集計値」を漏らす。
**Q3**: 検索パラメータの注入を測りたい。
**A3**: 検索は注入の高頻度口だ。キーワードが SQL に入る(SQLi)、NoSQL クエリに入る(NoSQL 注入、オブジェクト `{"$ne":null}` を送るなど)、Elasticsearch/Lucene クエリに入る(クエリ構文注入で権限外検索)、ORM の制御可能なフィールド名/ソートフィールド(sort=secret_column でフィールド漏えい)。各パラメータがどのクエリエンジンに入るかを逐一測る。
**Q4**: sort/フィールド選択パラメータが制御可能だ。
**A4**: 制御可能な「列名/フィールド名」を重点的に打つ。sort、fields、orderBy、groupBy パラメータが直接クエリに連結されるなら、権限外フィールドを指定してソートで漏らす、存在しないフィールドを参照してエラーを誘発しテーブル構造を漏らす。フィールド名注入は値注入より WAF を迂回しやすい(典型的な攻撃特徴を持たない)。
**Q5**: 検索 API の防御がかなり厳しい。
**A5**: 検索の「資源消費と連想」面に転じる。ワイルドカード/正規表現検索が ReDoS か遅いクエリ DoS を誘発する、自動補完/連想 API が他者のデータ断片を漏らす、検索履歴/ホットワードが他のユーザー入力を漏らす。検索が直接権限外アクセスや注入できないとき、その連想と性能特徴は依然利用可能な直交面だ。

### 「正当な機能の乱用」角度からロジック脆弱性を探す
**Q1**: システム防御がかなり良く明らかなバグがないが、「機能乱用」角度から問題を探したい。どう考える?
**A1**: 発想を替える。「プログラムの誤り」でなく「設計が想定外の目的に使われる」ことを探す。全ての正常機能を列挙し、それぞれに問う。設計意図をはるかに超える使い方をしたらどうなるか?共有機能→無限共有で有料を迂回、エクスポート→反復エクスポートでトラフィックを打つ、通知→爆撃、トライアル→無限延長。乱用はバグでなく設計欠陥だ。
**Q2**: 具体的に機能を「武器化」するには?
**A2**: 機能の「外部副作用」を梃子にする。第三者にメッセージ/リクエストを送る機能(招待、通知、webhook、パスワードリセットの送信)はどれも爆撃か SSRF 中継に乱用できる。相手の資源を消費する機能は DoS にできる。機能の副作用を攻撃目標に向ける。
**Q3**: 「A 機能で B 機能の禁止された効果を達成」を探したい。
**A3**: 機能間の「権限不一致」を探す。直接プロフィール変更は審査が必要だが、「インポート/同期/バックアップ復元」機能で変えると審査不要。直接権限昇格は禁止だが、「ロール複製/アカウントクローン/テンプレート適用」で間接昇格。一つの操作に複数の実装経路があり権限検証が不揃いなら、弱い経路で強い効果を達成する。
**Q4**: 機能がどれもおとなしく、明らかな乱用面がない。
**A4**: 「組み合わせ乱用」に転じる。単機能は正常でも、A 機能の出力を B 機能に与えると想定外の結果を生む。公開共有機能でリンクを生成し、別の機能でそのリンクの権限を昇格させる。ロジック脆弱性は「機能の編成」の隙間にあり、単機能内ではないことが多い。
**Q5**: 組み合わせても見つからない。
**A5**: 「業務ルールの経済学的脆弱性」に転じる。システムの価値フロー(金、ポイント、割当、信用)を分析し、「正のフィードバックループ」や「アービトラージ経路」がないか探す。ある組み合わせ操作の産出 > 投入。この種の脆弱性はどの技術ルールにも違反しないが業務を損なう。技術面が縫い目なしなら、業務経済モデルの不均衡点を探す。

### マイクロサービス/内部 API の信頼境界権限外アクセス
**Q1**: 対象がマイクロサービスアーキテクチャだ。サービス間の信頼が利用できると疑う。どう探す?
**A1**: 「内部向けの信頼フラグ」を探す。サービス間呼び出しは往々にして内部ネットワーク IP、特定 header(X-Internal、X-User-Id、X-Forwarded-For)、共有鍵で相互信頼し、且つそれが外部から偽造不能と仮定する。測る: 外部リクエストからこれらの内部 header を注入し、エッジサービスが透過するか、内部サービスが盲信するか。内部身元の偽造がマイクロサービス権限外アクセスの核心だ。
**Q2**: ゲートウェイが外部から来る内部 header を剥がす。
**A2**: ゲートウェイを迂回する直結入口を探す。内部サービスに露出したポート、管理 API、ヘルスチェック/デバッグエンドポイントがあるか、SSRF で内部からリクエストを発起する(偽造 header 付き)。ゲートウェイの剥がしは「ゲートウェイを通るトラフィック」だけを守る。通らない経路を探す。SSRF + 内部信頼は絶妙な組み合わせだ。
**Q3**: X-Forwarded-For などの header で送信元を偽造したい。
**A3**: システムが XFF/送信元 IP で認証・認可判断をするかを測る(内部ネットワーク IP は認証不要、特定 IP は管理権)。XFF/X-Real-IP を内部ネットワークアドレスかホワイトリスト IP に偽造する。多くのシステムは「内部ネットワークなら信頼できる」とし、header 内の IP はクライアント制御可能だ。IP 信頼はよくある誤りだ。
**Q4**: header 偽造が全てフィルタされた。
**A4**: サービス間認証の認証情報に転じる。サービス間が固定 token/mTLS/JWT で相互認証するなら、その認証情報が漏れていないか(設定ファイル、ログ、フロントエンド、コードライブラリ)、予測可能か、期限切れでもローテーションされないか。サービス間認証情報を取れば「内部身元」の通行証を得るのと同じだ。
**Q5**: サービス間認証がかなり厳しい。
**A5**: サービスメッシュの「データ面 vs 制御面」とメッセージキューに転じる。サービス間が MQ/イベントバスで通信するとき、偽造メッセージを直接投げて下流操作を誘発できるか(入口認証・認可を迂回)、受信すべきでないイベントストリームを購読してデータを漏らすか。同期呼び出しの信頼境界が堅いとき、非同期メッセージチャネルという見落とされがちな直交面に転じる。

### 権限外アクセスから機密操作へ:データ権限外アクセスからシステム影響への格上げ
**Q1**: 安定した権限外アクセスの読み書き能力を持つ。どう評価し「システム級」影響へ格上げする?
**A1**: 権限外アクセスが届く「高価値操作」を棚卸しする。コマンド実行系機能を権限外で誘発できるか(インポートスクリプト、タスク実行、設定更新)、システム設定を変えられるか(SMTP、コールバック URL、連携鍵)、他ユーザーの高権限動作を操作できるか。「データ CRUD」から「コード実行/設定制御」への機能を探す。ロジック脆弱性は入場券で、システム影響が終局だ。
**Q2**: 権限外アクセスで設定を変えられる。どう RCE か深入りに変える?
**A2**: 「設定即コード」の点を探す。制御可能なテンプレート(SSTI)、制御可能なコールバック/webhook URL(SSRF→内部ネットワーク)、制御可能なファイルパス(危険位置への書込)、制御可能なスクリプト/数式フィールド、連携設定の接続文字列(データベース/LDAP の向き先変更)。設定項目は往々にして入力検証を迂回して直接下層へ通るチャネルだ。
**Q3**: 権限外アクセスで webhook/URL を設定できる。内部ネットワークに入りたい。
**A3**: 制御可能な URL で SSRF を行う。内部ネットワークサービス、クラウドメタデータエンドポイント(一時認証情報取得)、内部管理 API に向ける。権限外アクセスで設定した外向きリクエスト機能は、アプリ層からインフラ層へ飛び込む橋だ。判定基準は、この URL が本当にサーバーにリクエストされるか、内部ネットワークレスポンスか戻りを受信できるかだ。
**Q4**: システムが設定系操作を厳格に検証し、格上げできない。
**A4**: 縦でなく横に転じる。権限外アクセス能力でより多くの/より高い権限のアカウントを乗っ取る(管理者アカウントのデータを探す、その紐づけを変える)、管理者身元でシステム操作権を得る。「縦の権限昇格」が阻まれたら、先に「横で高権限ユーザーへ」進み、それから縦へ。往々にしてよりスムーズだ。
**Q5**: 高権限アカウントに触れず、システム影響が頭打ちだ。
**A5**: 目標と損切りを再較正する。権限外アクセスがデータ層に留まるなら、既存戦果の重大性(大規模 PII/資金/業務データ)が納品基準に達しているかを評価する。レッドチームの価値は「証明可能な最大影響」で、「必ず shell を取る」ではない。データ層の影響が十分なら証拠を固定して納品。不十分なら、完全に別の初期入口に転じて縦深経路を再探索する。

### セッション管理の欠陥:固定、並行と失効の不備
**Q1**: セッション自体からアカウント安全問題を探したい。まずどの点を見る?
**A1**: ログイン前後の session 識別子の変化をキャプチャする。核心の測点: ログイン後に session id が再生成されるか(不変 = セッション固定リスク、攻撃者が sid を予め設定して被害者のログイン後にセッションを共有)、session が IP/UA に紐づくか、ログアウト後に旧 session がサーバーで失効するか(フロントエンドの cookie 削除だけでは不十分)。セッションの「生成-束縛-破棄」の三段にそれぞれ穴がある。
**Q2**: ログイン後に session が確かに変わり、固定攻撃が成立しない。
**A2**: 並行セッションと失効方針に転じる。パスワード変更/紐づけ変更後に他デバイスの旧 session が蹴られるか、同一アカウントで無限に多端末オンラインできるか、遮断/降格されたユーザーのアクティブ session が即時効くか。多くのシステムは「権限を変えたが旧セッションがそのまま動く」で、これは権限昇格取消無効化の脆弱性だ。
**Q3**: 漏れた session token を利用したい。
**A3**: XSS/ログ/referer/前の IDOR で他者の session token を取ったら、直接 cookie に注入して再利用すれば乗っ取り。前提は session がデバイスフィンガープリントに紐づかないこと。token のスコープを測る。HttpOnly か(XSS 読取を防ぐ)、Secure か、SameSite 設定は。セッション認証情報の保護属性が盗用可否を決める。
**Q4**: session がデバイス/IP に紐づき、盗用後に拒否される。
**A4**: 紐づけの厳格度を測る。IP 紐づけが正確に IP か /24 セグメントだけか(同一セグメントなら迂回可能)、UA 紐づけが偽造複製できるか、フィンガープリントが被害者環境から抽出してリプレイできるか。紐づけは往々にして緩く、被害者の環境特徴を複製すれば迂回できる。
**Q5**: セッション機構が全体としてかなり堅い。
**A5**: 「ログイン保持」/長期認証情報に転じる。remember-me token、API key、リフレッシュ token の強度と失効方針は主 session より緩いことが多い。予測可能、長期有効、ログアウトで失効しない、漏れても失効できない。短セッションが堅いとき、長期認証情報がより柔らかい代替の乗っ取り経路だ。

### CSRF と状態変更操作の権限外アクセス誘発
**Q1**: 被害者に「受動的に」権限外アクセス操作を実行させられるか(CSRF)を測りたい。まず何を判断する?
**A1**: 「状態を変え且つ cookie だけで認証・認可する」操作を探す。パスワード変更、紐づけ変更、振込、管理者追加、設定変更。判定基準: そのリクエストが予測不能な CSRF token/カスタム header を必要とするか、それともブラウザが自動で付ける cookie だけで実行できるか。cookie だけ = CSRF 可能。先に高価値の状態変更操作を選ぶ。
**Q2**: リクエストに CSRF token が付く。直接偽造できない。
**A2**: token の堅牢性を測る。token が本当に検証されるか(削除/空にすると通過するか)、ユーザーに紐づくか(自分の token で被害者を打つと通過するか)、予測可能/グローバル固定か、GET リクエストも受けて迂回できるか。多くの「token あり」システムは検証が形骸だ。
**Q3**: token 検証がかなり厳しい。
**A3**: SameSite とメソッド迂回に転じる。cookie の SameSite が Lax なら、GET 型クロスサイトリクエストは依然 cookie を付ける。GET で誘発できる状態変更を探す。None なら完全にクロスサイト可能。Content-Type 迂回(text/plain で JSON を送ってプレフライトを迂回)、サブドメイン信頼(制御可能なサブドメインから同站リクエストを送る)も測る。
**Q4**: CSRF と組み合わせて権限外アクセスを打ちたいのであって単なる CSRF ではない。
**A4**: CSRF + ロジック脆弱性の組み合わせ。CSRF で被害者(特に管理者)に「その権限で実行する」操作を誘発させる。管理者にリンクをクリックさせ、自動で自分を管理者に追加させる、自分が制御可能なパラメータを含む操作を誘発させる。CSRF は「被害者の権限を借りる」投下手段で、権限外アクセスと組み合わせれば効果倍増だ。
**Q5**: 現代ブラウザは既定 SameSite=Lax で、CSRF 面がかなり狭い。
**A5**: CSRF の近親に転じる。フロントエンドが SPA で token を localStorage に置くなら、CSRF は天然に無効化するので、XSS で token を盗む方向に替える。あるいは clickjacking(X-Frame-Options がなければ、iframe で機密操作をクリック誘発)。古典的な CSRF が SameSite で塞がれたら、「被害者に操作を誘導する」発想を XSS か UI リダイレクトハイジャックという直交手段に転じる。
