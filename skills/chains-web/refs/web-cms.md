# Web · CMS汎用の攻め方:識別→既知の脆弱性→管理画面 getshell

### Web 対象を手に入れたら、まず脆弱性スキャンに急ぐべきか
**Q1**: 目の前に http://対象X がある。直接スキャンするか、先に別のことをするか?
**A1**: 急に脆弱性スキャンをしない。脆弱性スキャンは「ハンマーを持って釘を探す」ことで、効率が低く騒がしい。手始めの最優先は**フィンガープリント識別**だ。まず「これは何か」(CMS/フレームワーク/ミドルウェア/言語)を把握してから「何を打つか」を決める。判定基準: CMS ブランド+メジャーバージョンを確定すれば、後続の各歩(EXP 探し、管理画面探し、アップロード点探し)が有限集合に収束し、意思決定コストが急減する。
**Q2**: CMS ブランドをどう素早く判定する?
**A2**: 多次元で交差し、単一特徴を妄信しない。見るべきは、① 特徴パス(/wp-admin、/administrator、/admin.php、?s=モジュール などの傾向)② 静的資源フィンガープリント(favicon hash、特定の js/css パス、meta generator)③ レスポンスヘッダ(X-Powered-By、Set-Cookie 名)④ robots.txt/sitemap/著作権表記にあるパスの習慣。
**Q3**: 複数の特徴が互いに矛盾する場合は?
**A3**: 二次開発/スキン変更/リバースプロキシの可能性がある。最も偽造しにくい証拠を優先する。favicon hash、固有資源パスは著作権表記より信頼できる。矛盾自体が情報で、スキン変更は往々にしてフロントエンドだけを変えバックエンドは変えておらず、管理画面のパスと既定の脆弱性が残っているかもしれない。
**Q4**: フィンガープリントがまったく出ない(全て魔改造)場合は?
**A4**: 直交次元に転じる。「ブランド識別」から「挙動特徴の識別」へ。エラーページ(404/500 のエラースタック)のフレームワーク痕跡、パラメータ傾向、Cookie 構造から下層フレームワークを推測し、上層 CMS にこだわらない。それも駄目なら「入力点で汎用脆弱性クラスを探す」純ブラックボックスモードに入り、ブランドに依存しない。
**Q5**: ブランド確認後の次の意思決定は?
**A5**: 即座に**正確なバージョン**を求める。ブランド+バージョンで初めて既知の脆弱性と一対一に対応できる。バージョン不明では既知の脆弱性は確率ゲームにすぎない。

### CMS ブランドを確定したら、どうマイナーバージョンまで正確にするか
**Q1**: ある CMS だとわかったが、脆弱性はマイナーバージョンに強く依存する。バージョンをどう定める?
**A1**: バージョンはブランドより価値が高い。経路は、① バージョン宣言ファイル(CHANGELOG、README、version 定数、composer.json/package.json)② 資源のバージョン化パスか ?ver= パラメータ ③ バージョン間の固有ファイルの存在性探査(A あり B なし → ある区間に落ちる)。
**Q2**: バージョンファイルが削除/deny された?
**A2**: 「差異フィンガープリント」に転じる。各バージョンで変化する静的資源(js/css/画像の内容 hash)で比較ライブラリを作り、レスポンスボディの hash が一致すればバージョンを定める。受動的で、機密ファイルの可読に依存しない。
**Q3**: 区間までしか定まらず、具体点に定まらない?
**A3**: 十分なら先に進む。全区間にまたがって存在する脆弱性は直接打つ。小区間にしかないものは「あれば儲け、なければ退く」順で無害な PoC で探る。
**Q4**: バージョンがかなり新しく、パッチ済みに見える?
**A4**: 既知の脆弱性を諦めない。多くのサイトは「バージョンは新しいがパッチが追いついていない」か「核心だけパッチしてプラグインは未対応」だ。方向転換として、① このバージョンの **1day**(公開されたばかりで、大半のサイトが未修正)を調べる② 火力を CMS 核心から**第三者プラグイン/テーマ/拡張**へ移す。バージョンが独立し更新が遅れ、既知の脆弱性の激戦区だ。
**Q5**: バージョンが全く確認できず、時間も限られる。どこへ進む?
**A5**: 「バージョン駆動」を諦め、「入力点駆動」に転じる。バージョンに関係なく、制御可能な全入力(検索/ログイン/登録/パスワードリセット/アップロード/API)を列挙し、汎用脆弱性クラスごとにブラックボックスでテストする。バージョンは効率化の先験であり、必須ではない。

### ブランド+バージョンが揃ったら、どう体系的に既知の脆弱性を探すか
**Q1**: ブランドとバージョンが確定した。実行可能な攻撃リストにどう変える?
**A1**: 「バージョン→脆弱性」マッピングを作り、**収益/コスト/隠密性**で並べる。優先順位: 未認可 RCE > 未認可任意ファイル読み書き > 未認可 SQLi(管理画面へ誘導できる)> 認証後 RCE > 高権限が必要な脆弱性。前置条件が少ないほど一撃で当たりやすい。
**Q2**: 脆弱性が多数ある。どれを先に打つ?
**A2**: 先に**前置条件が最少で最も隠密**なものを打つ。ログインが必要な RCE より、まず未認可で設定ファイルを読む脆弱性がないかを見る。データベースのパスワード/鍵を読めば戦局が直接変わるかもしれない。同時に騒音を評価し、低騒音の情報漏えいで先に環境を把握してから必殺技を定める。
**Q3**: 公開 EXP を直接コピーして打つのは信用できるか?
**A3**: 信用できない。必ず原理を読んで理解する。公開 EXP はしばしば重要な payload を削られていたり、他環境のパスを固定していたり、バックドアを含んだりする。誘発チェーンを理解してから自分で payload を構築し、EXP は参考に留める。さもないと、通らないときに「穴がない」のか「EXP が壊れている」のか区別できない。
**Q4**: 既知の脆弱性を打っても反応がない。穴がないのか環境問題か?
**A4**: 変数を分離する。まず**無害な探査**で脆弱性の存在を確認する(時間ブラインド注入、DNSlog で SSRF/コマンド実行の外向き通信を確認)、それから利用する。「脆弱性が存在しない」と「存在するが利用条件が不満(open_basedir、disable_functions、無エコー)」を区別する。後者なら手法を替え、脆弱性を替えない。
**Q5**: 全既知の脆弱性を試して全て無効なら?
**A5**: 直交次元に転じる。① 「CMS 本体」から**実行環境**(ミドルウェア/インタプリタ/バックエンドコンポーネントの既知脆弱性)へ ② 「既知の脆弱性」から**設定欠陥**(ディレクトリトラバーサル、バックアップ、ソース漏えい、既定の認証情報、未認可 API)へ ③ 「汎用脆弱性」から**ビジネスロジック**(権限外アクセス、フロー迂回、検証コード欠陥)へ。実際のサイトは CVE でなく設定とロジックで死ぬことが多い。

### 未認可攻撃面を優先:ログイン画面の前にまず何を見るか
**Q1**: 管理画面のログインページを見たら、ログインに取りかかるべきか?
**A1**: 先にログイン画面に飛び込まない。認証の前に**未認可で到達可能な攻撃面**がしばしばある。インストールページの再実行、未認可 API、静的資源ディレクトリ、デバッグ API、閉じ忘れた setup/install。パスワード不要で触れるものはどれもブルートフォースログインより先に見る。
**Q2**: 未認可面をどう列挙する?
**A2**: ① インストール/初期化パスがまだ開いているか(再実行できれば=直接制御)② デバッグ/開発 API(debug/test/phpinfo/actuator 類)③ 未認可のデータ/管理 API(REST/GraphQL の権限外アクセス)④ ディレクトリリストが開いているパス ⑤ swagger/ドキュメントが晒す API リスト。
**Q3**: 未認可 API らしきものを見つけたが 403/401 を返す?
**A3**: 諦めず、**認可バイパス**を試す。HTTP メソッドを替える、パスの大文字小文字/末尾スラッシュを替える、パストラバーサル(..;/、%2e)、偽造送信元ヘッダ(X-Forwarded-For/X-Original-URL)、Accept/Content-Type を替える。403 は「前置プロキシが遮ったがバックエンドは遮っていない」ことが多い。
**Q4**: 未認可面が全部塞がれた。どこへ転じる?
**A4**: 認証境界に戻るが情報を持って戻る。未認可列挙で集めたユーザー名、API 命名習慣、エラー情報を、**認証攻撃**の最適化に使う(狙った弱いパスワード、パスワードリセットロジック、SQLi によるログイン迂回)。未認可偵察の産物を認証攻撃に与える。

### 管理画面ログインページを見つけたら:ブルートフォースか迂回かの取捨
**Q1**: 管理バックグラウンドのログインを特定した。第一動作はブルートフォースか?
**A1**: ブルートフォースは下策であり第一選択ではない。順に試す。① 既定/弱い認証情報(少数の高頻度組み合わせ、ロックを誘発しない)② ログインロジックの脆弱性(SQLi 迂回、認証欠陥、パスワードリセット乗っ取り)③ 万能パスワード。どれも駄目ならブルートフォース。ブルートフォースは騒音が大きく、ロックしやすく、不正検知を誘発しやすく、暴露コストが最も高い。
**Q2**: ブルートフォースできるかどう判断する?
**A2**: 先に**防御機構**を探る。検証コード、失敗ロック、頻度制限、IP 遮断。3-5 回故意に失敗してレスポンスの変化を観察する。ロックが存在すれば、闇雲なブルートフォースは実際のアカウントをロックして悪化させる。
**Q3**: 検証コード/ロックがあり、ブルートフォースはほぼ封じられた。どこへ転じる?
**A3**: 直交に転じる。① **認証ロジック**を攻めるのであってパスワードではない。SQLi ログイン迂回、JWT/session 偽造、「ログイン保持」token の予測、パスワードリセットフローの欠陥。② **他の認証入口**を攻める。API ログイン、モバイル API、SSO コールバックは、フロントエンドの検証コードとロックがないことが多い。③ 未認可で到達可能な管理機能があれば、直接**認証後の脆弱性**を打つ。
**Q4**: ユーザー名すらわからない。ブルートフォース空間をどう縮める?
**A4**: まずユーザー列挙を行う。ログイン/パスワードリセットの**レスポンス差異**(ユーザー不存在 vs パスワード誤りのエラー/時間)、登録時の重複名プロンプト、記事/コメントの著者、API が返すユーザーオブジェクト。実際のユーザー名を列挙すれば、ブルートフォースは「ユーザー名×パスワード」から「パスワードのみ」に次元が下がり、成功率が桁違いに上がる。
**Q5**: フロントエンド/低権限アカウントを一つ取った。管理画面をこじ開けられるか?
**A5**: **パスワード再利用**と**権限外アクセス**を試す。同じパスワードを管理画面/他のシステムで試す。低権限アカウントで高権限機能にアクセスする(role を変える、直接管理 API をリクエスト)。多くの CMS はフロントエンドとバックエンドでユーザーテーブルを共有しており、フロントエンドの弱いパスワードが突破口になり得る。

### 管理画面に入ったら、どう getshell するか(汎用手法の優先順位)
**Q1**: 管理バックグラウンドに入った。最速でコード実行を得るには?
**A1**: 成功率順に試す。① **テンプレート/テーマ編集**(テンプレートファイルへ直接スクリプトを書く)② **プラグイン/拡張アップロード**(webshell 入りプラグインをインストール)③ **ファイルアップロード点**(アバター/添付/メディアライブラリ+解析迂回)④ **設定項目のファイル書き込み**(ある設定はスクリプトに落とされる:サイト設定、擬似静的、キャッシュ)⑤ **データベース操作**(SQL 実行箇所で into outfile か設定変更)。
**Q2**: 管理画面の機能が多い。どう「ファイルを書ける/実行できる」点を特定する?
**A2**: 3 種を注視する。コード/テンプレート/ルールを入力させる場所(テンプレートエンジン、擬似静的、カスタムタグ)、**ファイルをアップロードする**場所、**編集してサーバーへ保存する**場所(オンライン編集、インポート/エクスポート、バックアップ復元)。それらは天然の書き込みプリミティブだ。
**Q3**: テンプレート編集箇所の入力がエスケープ/サンドボックス化された?
**A3**: **SSTI** サンドボックスエスケープを試す(先にエンジンを判別して狙って打つ)。本当にサンドボックスが死んでいるなら「アップロード+解析」チェーンに転じる。実行不能拡張子のファイルをアップロードし、解析脆弱性か .htaccess/設定でスクリプトとして実行させる。
**Q4**: getshell したが権限が非常に低い(www-data)。直ちに権限昇格すべきか?
**A4**: 急に権限昇格しない。先に「根を張り+面を広げる」。安定して隠密な webshell/メモリ馬を一つ落とし、現在の権限で取れるものを全て取る(データベース、設定、鍵、内部ネットワーク到達性)。権限昇格は後続の独立段階だ。当面の目標は足場を安定させ、次のホップの情報を収集すること。
**Q5**: 管理画面にファイル書き込み点が一つもない(純展示型管理画面)場合は?
**A5**: 「**認証後の他の脆弱性**」に転じる。管理画面から到達できる SQLi(→ファイル書き込み/設定読取)、管理画面パラメータが誘発するデシリアライズ/ファイルインクルード、管理画面 SSRF(内部ネットワークを打つ)。getshell は必ずしも「アップロード」ではない。認証後 SQLi とデータベースのファイル書き込み権限でも成立する。それも駄目なら、管理画面で読んだ**機密情報**(データベース設定、鍵、他システム認証情報)で横展開し、このマシンを迂回して後方を直接打つ。

### アップロード/ファイル書き込みが WAF に遮断されたら
**Q1**: webshell アップロードが WAF に遮断された。この点を諦めるか?
**A1**: 諦めない。まず**どの層が遮断するか**を特定する。ファイル名/拡張子?Content-Type?ファイル内容(eval/system の特徴コード)?リクエスト構造?変数を制御して逐項テストする。純粋に正当なファイルを送って通れば内容/名前を遮断している。不正リクエストを送って遮断されれば構造を遮断している。
**Q2**: 内容の特徴コードを遮断している?
**A2**: **検知回避/変形**に転じる。webshell を暗号化/エンコード、キーワード分割、マイナーな実行関数、動的連結、コールバック/可変関数。まず「無害なプローブ」(タイムスタンプを書くだけの最小スクリプト)を送って通ることを確認し、段階的にペイロードを載せ、二分で遮断されるキーワードを特定する。
**Q3**: ファイル名/拡張子を遮断している?
**A3**: **解析迂回+拡張子迂回**に転じる。大文字小文字、二重書き、マイナーな実行可能拡張子、複数拡張子、ミドルウェア解析特性との組み合わせ。あるいは発想を変え、正当な拡張子(画像/文書)にコードを含めて送り、ファイルインクルード/解析で読み込ませる。
**Q4**: リクエスト構造/パラメータを遮断している?
**A4**: **HTTP 層の難読化**に転じる。multipart 境界の不正、Content-Type の変造、パラメータ汚染、チャンク転送、大文字小文字と空白の攪乱。多くの WAF はサーバーと解析差異がある(parser differential)。
**Q5**: アップロード経路が WAF に完全に塞がれた。全体をどこへ転じる?
**A5**: アップロードを迂回する。① **非アップロードのファイル書き込みプリミティブ**に替える(SQLi のファイル書き込み、ログインクルード、設定書き込み)② **メモリ馬/無ファイル足場確保**に替える(デシリアライズでメモリ馬を打ち、ディスクに落とさずファイル系ルールを迂回)③ **対象を替える**(WAF は通常 Web だけを守るので、同一ネットワークセグメントのカバーされていないサービス/ポートへ転じる)。
**Q6**: 前がクラウド WAF だと疑う。それ自体を迂回できるか?
**A6**: **真のオリジンサーバー IP を追跡**する。履歴 DNS、サブドメイン、同一証明書アセット、メールヘッダ、SSRF 戻り、オリジンサーバー直結の誤設定。真の IP を見つけてオリジンサーバーへ直接アクセスすれば、クラウド WAF は形骸化する。これは CDN/WAF に遮られたときの古典的な直交方向転換だ。

### 対象が CDN/WAF の後ろにいる:先に誰を打つか
**Q1**: 対象が CDN に解決され、直結では打てない。どう進める?
**A1**: まず CDN を迂回する必要があるかを分ける。加速だけで防御をしないなら、脆弱性はそのまま打てる。セキュリティ CDN/クラウド WAF なら、優先的に**オリジンサーバーの真の IP を探す**。世界各地の DNS 履歴、サブドメイン(多くが CDN を張らない)、SSL 証明書フィンガープリントで同一証明書アセットを検索、対象の能動的な外向き通信点(メール/SSRF/webhook)、C セグメントの連想。
**Q2**: 候補 IP をいくつか見つけた。オリジンサーバーをどう確認する?
**A2**: Host ヘッダを候補 IP に束縛して直接リクエストし、返りが本サイトと一致するか(同 title/同特定資源)を比較する。一致すればオリジンサーバーだ。hosts に書き込み、後続の全攻撃はオリジンサーバー経由で防御を迂回する。
**Q3**: オリジンサーバーがどうしても見つからず、CDN を硬く突破するしかない?
**A3**: **低特徴攻撃**に転じる。ルールを誘発しない脆弱性クラス(ロジック、権限外アクセス、情報漏えいは往々にして WAF ルールに覆われない)を使い、高特徴の SQLi/RCE payload を避けるか、payload を変形してルールを迂回する。
**Q4**: CDN がさらに頻度制限/IP 遮断をする?
**A4**: **減速+分散**に転じる。頻度を閾値以下に下げる、出口 IP を交代する(プロキシプール)、ブルートフォース/列挙を低頻度の正確操作に替え、「一発で命中する」脆弱性を優先し、大量リクエストが必要なブラインド注入/ブルートフォースを避ける。

### 対象に IP を封じられた / 不正検知を誘発した。どう続けるか
**Q1**: 打っているうちに IP が封じられた(全タイムアウト/ban)。まだ救えるか?
**A1**: まず**遮断の粒度**を確認する。単一 IP 遮断?C セグメント遮断?session/フィンガープリント遮断?きれいな出口 IP を一つ替えて試す。通れば IP 遮断、通らなければより細かいフィンガープリント(UA/Cookie/TLS フィンガープリント/行動)が封じられている。
**Q2**: IP 封と確認した。どう替える?
**A2**: 出口を交代する。プロキシプール、クラウドホスト、住宅プロキシ(より実ユーザーに似て、一括封じにくい)。偵察段階では犠牲にできる IP を使い、正確利用段階ではきれいな IP を使う。良い IP を高騒音操作に浪費しない。
**Q3**: IP を替えてもすぐ封じられる。封じられているのは行動か?
**A3**: **行動特徴を下げる**に転じる。リズムを遅くし、間隔をランダム化し、正常なブラウザフィンガープリントとアクセス順序を模し、スキャナ特徴を外す(既定 UA、特定 header、固定パス順序)。機械の行動を人間の行動に偽装する。
**Q4**: 不正検知が強すぎ、正面のコストが高すぎる。全体をどこへ転じる?
**A4**: 攻撃面を転じるのであって入口に固執しない。① **アセットを替える**(他のドメイン/サブドメイン/隣接サイト/C セグメント、防御強度は不均衡で最弱環を探す)② **チャネルを替える**(晒された他のポートへ:データベース/キャッシュ/管理プロトコル/VPN/メール、Web 不正検知がないことが多い)③ **経路を替える**(認可範囲内のサプライチェーン/第三者/ソーシャルエンジニアリング)。

### ソース漏えい / .git / バックアップファイル:ホワイトボックス化の機会
**Q1**: ブラックボックスが辛い。ソースを手に入れてホワイトボックス化する方法は?
**A1**: 体系的に**ソース漏えい**を探す。.git/.svn/.hg 漏えい、バックアップファイル(.bak/.zip/.tar.gz/.sql/日付付き名前)、エディタの一時ファイル(.swp/~)、IDE 設定(.idea/.vscode)、vendor 漏えい、パッケージがソース付きで本番に上がる。ソースを手に入れればブラックボックスがホワイトボックスになり、掘り効率が天地の差になる。
**Q2**: .git がアクセス可能だとわかった。どう利用する?
**A2**: git 漏えい復元ツールで完全な .git を取得してリポジトリを再構築し、全ソース+履歴を取る。**コミット履歴が特に価値がある**。開発者は履歴のコミットでパスワード/鍵/内部ネットワークアドレスを誤ってコミットし、後で「削除」しても履歴に残る。
**Q3**: ソースを手に入れたらまず何を見る?
**A3**: ① 設定ファイル(データベース/Redis/鍵/第三者認証情報、戦局を直接変え得る)② 認証とアップロード関連コード(迂回と getshell 点を探す)③ 危険関数(eval/system/デシリアライズ/ファイル操作)から入口を逆に特定する ④ ハードコードされた鍵(JWT/session/暗号化 token の偽造)。
**Q4**: バックアップファイル名が推測できず、ブルートフォースも成果なし?
**A4**: **規則推測+他の漏えい源**に転じる。命名習慣(ドメイン/プロジェクト名/日付形式)で辞書を作る。エラーページ/ログの漏らすパスを調べる。JS 内の API とパスを調べる。それも駄目ならソース経路を諦めてブラックボックスに戻る。ソースは加速器であり必須ではない。

### 既知の脆弱性を全部打っても無効:0day/ロジックの分水嶺
**Q1**: この CMS の全公開脆弱性を検証して確かにない。この入口を諦めるべきか?
**A1**: まず「本当にないか、探しきれていないか」を問う。盲点は、① 第三者プラグイン/テーマ(独立した脆弱性ライブラリ、極めて見落としやすい)② 二次開発のカスタム機能(どの CVE ライブラリにもないが明らかな脆弱性があり得る)③ このバージョンの最新 1day/パッチ diff。実際のサイトの穴は「CMS+顧客が改変した部分」の接ぎ目に多い。
**Q2**: 二次開発部分に穴があると疑う。ブラックボックスでどう掘る?
**A2**: 「入力点駆動」に戻る。全カスタム機能の入力を列挙し、各脆弱性クラスを体系的にテストする。二次開発コードは通常セキュリティ監査を通っておらず、最も肥沃な狩場だ。ソースを既に取っていれば接ぎ目コードを直接ホワイトボックス監査する。
**Q3**: 公式最新版のパッチが非常に新しい。1day を探したい?
**A3**: **パッチ diff** に転じる。修正前後のコード差異を比較して脆弱性点を特定し、PoC を逆算する。対象が「バージョンは新しいが最新パッチを追っていない」か「仮想パッチはあるがソース未修正」なら、diff で出た穴は依然打てる。
**Q4**: ロジック脆弱性をどう探すか。技術的脆弱性とどこが違う?
**A4**: ロジックの穴は「関数が危険か」でなく「**フローを乱せるか**」を見る。権限外アクセス、状態ジャンプ(支払い/審査/検証を飛ばす)、条件競合、パラメータ改ざん(価格/ロール/負数を変える)、パスワードリセット/紐づけ乗っ取り。これらは WAF が遮れず、スキャナが掃き出せない。エージェントが詰まったとき最も転じるべき直交次元だ。
**Q5**: この CMS が鉄壁だ。戦術的にどう損切りする?
**A5**: 対象を移すのであって固執しない。強化済みの本サイトより、管理が疎かな隣接サイト/サブドメイン/テスト環境/旧システムの方が価値がある。単点が妥当な時間を超えて進展しなければ横方向にアセットを替え、その点を「低優先度、新情報があれば戻る」とマークする。

### getshell 後:webshell の存続とバックドア戦略
**Q1**: アップロードした webshell をそのまま足場にできるか?
**A1**: まず**存続性と隠密性**を評価する。特徴の明らかな shell はいつでも駆除/HIDS アラートの対象で、接続した時点で暴露する。戦略は、① 検知回避 shell か**メモリ馬**を使う(ディスクに落ちず、ファイル検査で見つからない)② shell を正常ファイルの片隅に隠し、独立した不審ファイルにしない ③ アクセスパスワードを付け、同業者/スキャナの乗っ取りを避ける。
**Q2**: 足場環境に EDR/HIDS があるかをどう判断する?
**A2**: 足場確保前に低調に偵察する。プロセス列挙でセキュリティエージェントを探す、/etc やレジストリの防御ソフト痕跡を見る、高危険コマンドが遮断/遅延されるかを観察する。EDR があれば「無ファイル+低頻度コマンド」モードに切り替え、連続の高危険システムコールをしない。
**Q3**: webshell 接続後にコマンド実行が遮断/無エコーだ?
**A3**: 問題を分離する。**コマンドが遮断された**のか**エコーが切られた**のかを確認する。無エコーなら**帯外**(DNS/HTTP 外向き通信)でコマンドが本当に実行されたかを確認する。コマンド遮断なら**検知回避実行**(エンコードコマンド、実行コンポーネントを替える、外部コマンドを呼ばず言語ビルトイン能力を使う)に転じる。
**Q4**: 長期駐留したい。webshell 以外に何がある?
**A4**: 複数の直交バックドアを層にして配置する。メモリ馬(隠密)、スケジュールタスク/サービス(持続的だが発見されやすい)、正当機能の隠し管理入口。原則は、種別を違えて互いにバックアップし、一つが除去されても他が残る。単点バックドアが除去されて全足場を失わない。
**Q5**: 足場が発見されて除去され、再進入できない。どうする?
**A5**: getshell 前に集めた情報に戻って直交進入する。以前に読んだデータベース/他システムの認証情報、内部ネットワーク到達サービス、鍵。同じ既に暴露した web 入口に依存しない。それは今監視されている。アセット、認証情報、チャネルを替えて足場を再確立する。

### ディレクトリ/パス列挙:どうスキャンすれば高効率で騒がないか
**Q1**: ディレクトリスキャンをしたい。直接大辞書で全量ブルートフォースするか?
**A1**: しない。全量の大辞書は遅く騒がしく、遮断を誘発しやすい。戦略は、まず**狙い撃ちの辞書**を使う。CMS が確認済みならその CMS 専用パス辞書を使い、命中率が汎用辞書よりはるかに高い。先に正確、後に汎化。
**Q2**: 何をスキャンするのが最も価値がある?
**A2**: 優先順位: 管理画面入口 > バックアップ/ソースファイル > 設定/機密ファイル > 未認可 API > アップロードディレクトリ > デバッグページ。目的は「戦局を変えられるもの」を探すことで、ディレクトリを全て列挙することではない。
**Q3**: 200/302 が大量に返り真偽が判別できない?
**A3**: まず**ベースライン**を測る。必ず存在しないランダムパスをリクエストし、正常な「404/存在」がどう見えるかを見る。存在しないパスも 200 を返す(偽 404)なら、ステータスコードでなく**レスポンス長/内容類似度**でフィルタする。
**Q4**: スキャンが WAF/頻度制限に遮られた?
**A4**: **騒音低減の精査**に転じる。並行度を下げる、情報に基づいて高価値パスを少数手動検証する、機械の全量ブルートフォースをしない。あるいは直交する偵察源に替える。JS ファイル、sitemap、robots、ページリンク、履歴アーカイブから受動的にパスを抽出し、スキャントラフィックを一切発しない。
**Q5**: 管理画面入口がどうしてもスキャンで出ない?
**A5**: **受動的情報**に転じる。ログイン後のジャンプをキャプチャする、フロントエンド JS にハードコードされた管理画面ルートを見る、この CMS の既定管理画面パスの変種を調べる、リダイレクトの Location ヘッダを見る。管理画面は改名されがちだが、フロントエンドコードかジャンプロジックが実パスを漏らす。

### favicon / 資源フィンガープリントで同類アセットを逆引きする
**Q1**: 対象を一つ手にしている。素早く戦果を広げて同類システムを探すには?
**A1**: **favicon hash / 特徴資源フィンガープリント**で全ネットワークマッピングして逆引きする。同一システムは往々にして同一の favicon と静的資源を共有するため、これで同組織/同ベンダーの他のアセットを逆引きできる。一つの穴が同型のシステム一群を一括で打てるかもしれない。
**Q2**: なぜ同類アセットを探すか?
**A2**: ① 同型システムは同じ既知の脆弱性を再利用でき、本サイトが打ちにくいとき隣の同型が未強化かもしれない ② 防御の弱い同型を先に取ってから、横展開で主目標へ戻る ③ EXP を検証する。同型の一つで payload の有効性を確認してから主目標に使い、主目標の暴露リスクを下げる。
**Q3**: フィンガープリント検索で大量に出る。本当に関連するものをどう選ぶ?
**A3**: **帰属関連**で選ぶ。同一証明書、同一 IP セグメント、同一登録情報、同一サブドメイン命名規則のものが同一組織アセットだ。同型でも別組織のものは傍証で、EXP 検証に使い、直接の戦果に数えない。
**Q4**: フィンガープリントマッピングが成果なし(資源が改変/固有 favicon なし)?
**A4**: 他の関連次元に転じる。同一 SSL 証明書、同一 ICP/whois、同一 IP 逆引き、サブドメイン列挙、ページ内の第三者統計 ID(同一 ID が同一組織の複数サイトに紐づくことが多い)。アセットマッピングは多次元の交差で、favicon の一本の木に吊るされない。

### インストール / 再インストールページがまだ開いている:直接乗っ取り
**Q1**: CMS のインストール/setup ページがまだアクセスできるとスキャンで出た。何を意味する?
**A1**: 高価値だ。インストールフローが未ロックなら、**再インストールで乗っ取り**できる可能性がある。インストールウィザードを再度通し、データベースを制御可能なデータベースに向けるか、管理者パスワードを再設定し、最高の管理画面権限を直接得て、全認証を迂回する。これは「未認可→完全制御」の近道だ。
**Q2**: インストールページはあるが「インストール済み」でロックされている?
**A2**: **ロック解除条件**を探す。多くの CMS は lock ファイルでインストール済みを示す。lock 判定を削除/迂回できれば(パス制御可能、ロジック欠陥)再インストールできる。あるいはインストールフロー内に**未認可の子ステップ**(あるステップの API が単独で呼べる)がないかを見て、局所的に利用する。
**Q3**: 再インストールは既存データを破壊する。レッドチームがすべきか?
**A3**: 慎重に。認可されたレッドチームは本番データの破壊を避けるべきだ。優先して「**非破壊的利用**」を選ぶ。インストールフロー内で情報を漏らす/ファイルを書く子 API だけを呼び、本当にデータベースを上書きしない。再インストールが必須なら、影響と認可境界を先に評価する。
**Q4**: インストールページが削除され、この道がなくなった。どこへ転じる?
**A4**: 同類の「初期化状態」脆弱性に転じる。設定ウィザード、データベース接続テスト API(SSRF/ファイル書き込みがありがち)、インポート/復元機能。これらはインストールページと同源で、「初期設定を信頼する」ロジックであり、認証・認可が欠けがちだ。

### データベース/設定ファイルを読んだ後:認証情報をどう使うか
**Q1**: 任意ファイル読取で設定ファイルのデータベースパスワードを手に入れた。次は?
**A1**: この一つのデータベースだけを見ない。設定ファイルは**認証情報の金鉱**だ。データベースのパスワード、Redis/MQ のパスワード、オブジェクトストレージの鍵、第三者 API key、暗号化ソルト/JWT 鍵、SMTP。各認証情報が何をこじ開けられるかを逐一評価し、「直接 RCE/横展開できる」順に利用を並べる。
**Q2**: データベースのパスワードを取ったが、データベースのポートが対外でない?
**A2**: **既存の足場経由で接続**する。既に getshell していれば、web マシンからローカルにデータベースへ接続する(通常内部ネットワークで疎通)。shell がないならまず別の手段で内部ネットワークに入ってから接続する。データベースのパスワードの価値は「内部ネットワークに入れたとき」に実現する。記録して待つ。
**Q3**: データベースに接続できた。どう getshell へ格上げする?
**A3**: **データベース→ファイルシステム**を試す。web ディレクトリへファイルを書く(FILE 権限+可書ディレクトリ+物理パスが必要)、UDF/ストアドプロシージャでコマンド実行、CMS 管理者パスワードを変えて管理画面に入り、管理画面経由で getshell。抵抗が最小の一本を選ぶ。
**Q4**: 取れたのがパスワード hash で平文でない?
**A4**: **解読か hash 再利用**に転じる。オフライン解読(辞書/ルール/レインボーテーブル)、あるいは特定のプロトコルで直接 pass-the-hash。解けなければ hash を情報として保存し、他の手掛かり(パスワード再利用規則)と合わせて範囲を絞る。
**Q5**: 設定の認証情報を全部試しても使えない。どこへ転じる?
**A5**: **鍵類の利用**へ転じるのであってパスワード類ではない。設定内の JWT/暗号鍵で**正当な認証情報を偽造**できる(管理者 token/session を自己署名)。この道は「アカウントとパスワード」の層全体を迂回し、見落とされがちだが極めて致命的だ。

### SQL インジェクションを取った:注入から getshell への経路選択
**Q1**: SQLi を確認した。直接データをダンプするか?
**A1**: データダンプは最低の収益にすぎない。先に格上げ経路を計画する。① **管理者認証情報**を読む→管理画面へ→管理画面で getshell ② FILE 権限があれば→**webshell を web ディレクトリへ書く** ③ **設定ファイル/鍵**を読む→横展開か認証情報偽造 ④ DBMS 特性→**直接コマンド実行**。対象環境に応じて抵抗最小の格上げチェーンを選ぶ。
**Q2**: into outfile で shell を書けるかをどう判断する?
**A2**: 3 つの前提。データベースアカウントに FILE 権限がある、対象ディレクトリが可書、web ディレクトリの物理パスを知っている。物理パスが欠けたらまずエラー/phpinfo/設定漏えいから探す。FILE 権限が欠けたらファイル書き込みを諦め、「認証情報を読んで管理画面へ」の経路に転じる。
**Q3**: 注入がブラインドで、データが取れない。どうする?
**A3**: ブラインド注入は遅いが自動化できる。まず**最高価値の少量データ**(管理者アカウントのパスワード hash、一つの鍵)だけをブラインド取得し、全テーブルをダンプしない。管理画面の認証情報を取れば注入の遅い道を離れ、管理画面で速い道を進む。
**Q4**: 注入点が WAF に遮られた?
**A4**: **SQLi の WAF 迂回**に転じる。コメント/大文字小文字/エンコード/等価関数/インラインコメント難読化、パラメータ汚染、注入位置の変更。あるいは**注入手法を替える**。エラー注入が遮られたら時間ブラインドへ、ユニオンが遮られたらブールブラインドへ。それも駄目なら**別の注入点**に替える。一つのサイトには注入が複数あることが多く、防御の弱い方へ替える。
**Q5**: データベースが外向き通信せずファイル書き込みもできない制限環境だ。注入に何の価値がある?
**A5**: 「注入=読取能力」という本質に戻る。**認証情報と設定**を読んで横展開し、**業務データ**を読んでロジック突破口を探し、**他テーブル**を読んで他システムの情報を得る。読取能力そのものが情報入口で、必ずしもこのマシンで getshell する必要はない。

### 無エコー場面:ブラインド注入 / 無エコー RCE の確認と利用
**Q1**: 疑わしい RCE の点を打つが、エコーがまったくない。通ったかをどう確認する?
**A1**: 無エコーは未実行と等しくない。**帯外確認(OOB)**を使う。対象に能動的に外向き通信させ、こちらの制御する DNS/HTTP へアクセスさせる(例 nslookup/curl をこちらの一意サブドメインへ実行)。リクエストを受信すれば=コマンドが確かに実行された。これは「脆弱性が存在しない」と「存在するが無エコー」を分ける鍵の判定基準だ。
**Q2**: DNS/HTTP すら受信できない。対象が外向き通信しない?
**A2**: 先に降格確認する。**時間遅延**(sleep を実行し、レスポンスが遅くなるかを見る)でコード実行を確認する。外向き通信しなくても測れる。実行能力を確認したら、データ持ち出し問題を解決する。
**Q3**: 実行を確認したがエコーが取れない。結果をどう持ち出す?
**A3**: **ブラインド打撃の持ち出し**に転じる。コマンド結果を DNS クエリ/HTTP リクエストのドメインかパスにエンコードして持ち出す。あるいは結果を web 可読ファイルに書いてから読む。無エコー利用の核心は「別のデータ出口を見つける」ことで、元経路のエコーを死に等しいまで待たない。
**Q4**: 対象が完全に外向き通信せず、可読の落地点もない。ほぼ全盲?
**A4**: **メモリ馬/逆接続**に転じる。利用点で直接メモリ馬を注入し、以降はそれで対話し、「元利用点の無エコー」を迂回する。あるいは対象にこちらのポートへ反接させる(対象が外向き通信できるポートが必要)。全盲では「自分の対話チャネルを一つ確立する」ほうが原点のエコー修復より現実的だ。
**Q5**: 逆接続も外向き通信制限で完全に塞がれた。徹底的に盲だ。どうする?
**A5**: このマシンが「唖の端末」だと認め、戦略を転じる。盲の能力で**最小の必要動作**だけをする。安定した webshell を既知の可読パスに書く、他チャネルで到達できる駐留点を落とす。「盲実行」を「半盲のファイル読み書きチャネル」に変え、それに基づいて段階的に拡張する。

### ファイルインクルード(LFI/RFI):ファイル読取から getshell へ
**Q1**: ファイルインクルード点を見つけた。まず何をする?
**A1**: まず**種別と範囲**を確認する。リモートを含められるか(RFI)それともローカルのみ(LFI)?パス制限/拡張子強制はあるか?RFI ならリモートスクリプトを直接含めて getshell でき、最も楽だ。LFI なら「含められ且つ制御可能な内容を含む」ローカルファイルを探す。
**Q2**: LFI だけだ。どうコード実行に格上げする?
**A2**: **制御可能な内容のローカルファイル**を探して含める。アップロードした画像馬、web/ミドルウェアの**ログ**(UA/リクエストに payload を書き込んでからログを含める)、session ファイル、一時ファイル、/proc 関連。核心は「先に悪意ある内容をローカルのどこかのファイルに落とし、それから含める」ことだ。
**Q3**: 拡張子強制(自動で .php などを付ける)かパス制限がある?
**A3**: **切断/プロトコル迂回**を試す。パストラバーサルでの位置特定、ラッパープロトコル(php://filter でソース読取、data://、php://input は設定次第)、エンコード迂回。shell を読めなくても少なくとも**ソースを読んでホワイトボックス化**し、設定ファイルを読んで認証情報を得られる。
**Q4**: 何も含められず、利用条件が全て不満だ。どこへ転じる?
**A4**: LFI を**任意ファイル読取**として使う。設定を読んでデータベース/鍵の認証情報を横展開し、ソースを読んでホワイトボックス監査で別の穴を探す。ファイルインクルードが getshell できなくても、その「読」能力は高価値な情報入口であり、無駄にしない。

### デシリアライズ入口:識別と利用
**Q1**: どこかにデシリアライズがあると疑う。入口をどう確認する?
**A1**: 「**信頼できない入力をデシリアライズに与える**」箇所を探す。Cookie/パラメータ内のシリアライズ特徴(PHP の O:/a:、Java の rO0AB/ac ed 00 05、.NET の特徴、Python の pickle)、明らかな base64 シリアライズ文字列。言語とシリアライズ形式の識別が gadget 選択の前提だ。
**Q2**: デシリアライズと確認したが、既成の利用チェーンがない?
**A2**: **gadget チェーン**を探す。対象がどのライブラリ/コンポーネントをロードしているかに依存する。まず依存を把握し(エラー、ソース、フィンガープリント)、対応する公開 gadget を選ぶ。同じシリアライズ点でも、gadget チェーンを替えることが「通せるか」を決める鍵変数だ。
**Q3**: gadget を打っても反応がない。チェーンがないのか遮断されたのか?
**A3**: まず**探査型 gadget**(DNS/遅延だけを誘発し、直接 RCE しない)でチェーンが到達可能かを確認する。到達可能だが RCE にならないのは gadget と環境の不一致で、チェーンを替える。完全に無反応なら入口が本当にデシリアライズしていない可能性があり、入口の検証に戻る。
**Q4**: デシリアライズはあるが、全既知チェーンが防御/バージョン不一致で通らない?
**A4**: 方向転換として、① デシリアライズで**非 RCE の危害**(SSRF、ファイル読み書き、DoS)をしても戦局を進められる ② **メモリ馬**の利用方式に転じてファイル検知を迂回する ③ この点を諦め、直交する脆弱性クラスに転じる。デシリアライズ gadget は環境に強く依存し、通らないのは正常だ。単点で予算を尽くさない。

### SSTI:テンプレート注入を識別しサンドボックスをエスケープする
**Q1**: 入力がページにエコーされる。SSTI を疑う。どう確認する?
**A1**: **数式プローブ**を使う。`{{7*7}}` / `${7*7}` / `#{7*7}` のような各エンジン構文を入力し、49 がエコーされればテンプレートがサーバー側で評価している=SSTI。どの構文が効くかがテンプレートエンジン種別を直接晒す。
**Q2**: SSTI を確認したらどう RCE へ格上げする?
**A2**: エンジンに応じて**エスケープチェーン**を選ぶ。エンジンごとにテンプレートコンテキストオブジェクトから実行可能なコマンドへ登る経路が異なる(ビルトインオブジェクト→リフレクション/イントロスペクション→コマンド実行プリミティブ)。先にエンジンを定め、そのエンジンの成熟したエスケープ payload を適用する。
**Q3**: エンジンにサンドボックスがあり、通常のエスケープが遮られた?
**A3**: **サンドボックス迂回**に転じる。アクセス経路を替える(別の属性チェーンでブラックリストを迂回)、文字列連結でキーワードフィルタを迂回、エンコード迂回。サンドボックスは通常ブラックリストで、塞がっていない間接経路が常にある。オブジェクトチェーンを逐一試す。
**Q4**: サンドボックスが厳しく、RCE がどうしても出ない。どこへ転じる?
**A4**: 利用を降格する。SSTI は RCE しなくても、**サーバー変数/設定/鍵を読める**(設定オブジェクトへのアクセス)、SSRF、ファイル読取ができることが多い。鍵を取れば認証情報の偽造に使える。「RCE 失敗」を「情報漏えい成功」に変えれば戦局は依然進む。

### SSRF:サーバーに内部ネットワークを打たせる
**Q1**: SSRF(サーバーにリクエストを発起させる)を見つけた。価値はどれほど?
**A1**: SSRF は「内部ネットワークの入場券」だ。価値はサーバーの身元で**外部から届かないもの**にアクセスすることにある。内部ネットワークサービス、クラウドメタデータ API、本機ループバックの管理ポート。まず対象が外向き通信できるか、どの内部ネットワークセグメントにアクセスできるかを探る。
**Q2**: SSRF でまず何を打つ?
**A2**: 優先順位: ① クラウド環境ならまず**メタデータ API**を打つ(一時認証情報/AK-SK を取れれば、直接クラウド権限へ格上げ)② 本機ループバックの**未認可管理サービス**(127.0.0.1 に束縛され且つ認証・認可なしがち)③ 内部ネットワーク他ホストの未認可サービス(キャッシュ/データベース/管理プロトコル)。
**Q3**: SSRF にプロトコル/ドメインホワイトリスト制限がある?
**A3**: **迂回**に転じる。IP 表記法を替える(十進/十六進/省略)、DNS rebinding、URL 解析差異、ジャンプ追従、プロトコルを替える(gopher は任意 TCP を構成して内部ネットワークサービスを打てる)。gopher は SSRF を「GET のみ」から「プロトコル級対話」へ格上げできる。
**Q4**: SSRF がリクエストを送るだけでレスポンスが返らない(盲 SSRF)?
**A4**: **盲打+帯外**に転じる。DNS で到達可能性を確認し、「一つのリクエストだけで副作用を起こす」目標(未認可 Redis/内部ネットワーク API へデータを書き込んで RCE を誘発)を使えば、エコーなしでも利用できる。盲 SSRF は「レスポンスを読む」でなく「副作用のある目標を打つ」ことを頼る。
**Q5**: 内部ネットワークが完全隔離され、SSRF が出られず何も打てない。どこへ転じる?
**A5**: SSRF を**内部ネットワーク探査器**として使う。利用できなくても、そのレスポンス差異/時間で**内部ネットワークのポートと生存を探査**し、内部ネットワークトポロジを描いて情報にする。探査結果は、後で本当の足場を得た後の攻め先を導く。

### XXE:XML 外部エンティティの利用の取捨
**Q1**: 対象が XML を解析する。XXE を疑う。まず何を測る?
**A1**: まず**エンティティ解析が有効か**を測る。外部エンティティを参照するプローブを注入し、こちらのサーバーへリクエストさせる(OOB)。リクエストを受信すれば=XXE 成立且つ外向き通信可能。この一歩が脆弱性と外向き通信能力を同時に確認する。
**Q2**: XXE を確認した。何ができる?
**A2**: 主に 3 種。① **任意ファイル読取**(設定/ソース/認証情報を読む)② **SSRF**(サーバー身元で内部ネットワークを打つ、SSRF チェーンと同様)③ 一部環境での RCE(特殊拡張依存)。ファイル読取と SSRF が最も安定した収益で、優先する。
**Q3**: エコーがあれば直接読む。無エコーなら?
**A3**: **OOB 持ち出し XXE**に転じる。外部 DTD で読んだファイル内容をこちらのサーバーへのリクエストに連結して持ち出す。無エコー XXE は帯外チャネルでデータを取る。ブラインド注入と同じ発想だ。
**Q4**: 対象が外部エンティティを無効化 / 防御がある。XXE が打てない。どこへ転じる?
**A4**: 他の XML 関連問題(XInclude、SOAP/SAML 処理欠陥)に転じるか、直交する脆弱性クラスに転じる。同時に、「サーバーがユーザー提供の構造化データを解析する」箇所は XML に限らず各種パーサがあり、同源の攻撃面なので、横方向に同類の入口を探す。

### フロントエンド登録 / 権限外アクセス:一般ユーザーから管理画面をこじ開ける
**Q1**: 管理画面が打てないが、フロントエンドで一般ユーザー登録ができる。有用か?
**A1**: 極めて有用だ。「認証後身元」を得れば**認証後攻撃面**が開く。一般ユーザーがアクセスできる API はゲストよりはるかに多く、その中に権限外アクセスとアップロードがしばしばある。まず登録して入り、認証後の機能を全て列挙する。
**Q2**: 一般ユーザーをどう管理者に格上げする?
**A2**: **垂直権限外アクセス**を試す。直接管理 API をリクエストする(フロントエンドに表示されない≠バックエンド到達不能)、登録/プロフィール変更時に role/権限フィールドを改ざんする(mass assignment)、user id を変えて他者/高権限データにアクセスする。多くのシステムはフロントエンドで権限制御し、バックエンドで検証しない。
**Q3**: 権限外アクセスが全てバックエンド検証で遮られた?
**A3**: **水平権限外アクセス+機能乱用**に転じる。横方向に他の同級ユーザーのデータにアクセスして突破口を探すか、一般ユーザーが使える機能(アップロード/インポート/共有)で注入やファイル書き込みを探す。権限がこじ開けられないなら「許可された機能」内で技術的脆弱性を探す。
**Q4**: 登録が閉鎖 / 審査が必要?
**A4**: **既存アカウントの取得**に転じる。弱いパスワードで一般ユーザーを一つブルートフォースする、パスワードリセットで乗っ取る、登録ロジック迂回(登録 API を直接呼んでフロントエンド制限を飛ばす)、情報漏えいから認証情報を一つ得る。目的は「任意の認証身元を一つ手に入れる」ことで、入手源は問わない。
**Q5**: どうしてもアカウントを取れない。どこへ転じる?
**A5**: **未認可面とゲスト到達可能な脆弱性**に戻るか、他のアセットに転じる。認証後攻撃面は非常に肥沃だが、前提は身元があること。身元が取れないときこの道で詰まらず、まず別の場所で入口を探す。認証情報/内部ネットワーク足場を得れば、逆にここを解決できるかもしれない。

### 検証コード / token / SMS:ロジック迂回の考え方
**Q1**: ある機能(ログイン/パスワードリセット)が検証コードに塞がれた。どう破る?
**A1**: 先に「検証コードを認識する」ことを考えず、まず「**検証コードが本当に検証されるか**」を測る。検証コードパラメータを送らない、空を送る、旧値を再利用する、並行リクエスト、を見てバックエンドが本当に検証するかを見る。大量の検証コードは「フロントエンドの見せかけ/バックエンド未検証/一度生成で再利用可能」で、ロジックの破れ目は画像認識よりはるかに有用だ。
**Q2**: 検証コードは確かに検証されるが、ブルートフォースしたい?
**A2**: **検証の欠陥**を探す。検証コードに回数/期限制限があるか(無制限ならブルートフォース可能)、session に紐づくか、誤り後にリフレッシュされるか(リフレッシュされなければ同一検証コードに対してパスワードをブルートフォースできる)。短い検証コード+非リフレッシュ+無ロック=直接ブルートフォース可能。
**Q3**: SMS/メール検証コード(パスワードリセット)をどう迂回する?
**A3**: コードを推測せず**検証ロジック**を攻める。検証コードがブルートフォース可能か(4-6 桁で無ロック)、レスポンスに正解コードが漏れないか、検証とリセットが**独立した二段階**か(リセット API を直接呼んで検証を飛ばす)、他者の携帯/メールを権限外で変える、token 予測可能。
**Q4**: token(パスワードリセットリンク内)をどう打つ?
**A4**: token の**予測可能性/権限外**を見る。タイムスタンプ/連番/弱乱数に基づいて推算できるか、ユーザーに紐づくか(紐づかなければ自分の token で他者を変更できる)、期限切れか。弱い token 生成はパスワードリセット乗っ取りの高頻度点だ。
**Q5**: 全迂回が失敗し、検証コード/token ロジックが堅い。どこへ転じる?
**A5**: 直交に転じる。**検証コード保護のない入口**に替える(API/モバイル API は検証コードがないことが多い)、攻撃対象を替える(この保護された機能を打たず、別を打つ)。検証コードは特定機能だけを守る。迂回できないなら迂回を避ける。カバーされていない箇所を探す。

### ミドルウェア / コンテナの脆弱性:CMS 本体の外の入口
**Q1**: CMS 本体がかなり綺麗だ。他にどこから入れる?
**A1**: 目を上げて **CMS の下の実行スタック**を見る。Web ミドルウェア(Nginx/Apache/IIS/Tomcat)、アプリコンテナ、言語インタプリタ、リバースプロキシ/ロードバランサ、管理パネル。これらは CMS と独立にパッチされ、長年放置されがちで、見落とされた入口だ。
**Q2**: ミドルウェアの脆弱性をどう発見する?
**A2**: ミドルウェアとバージョンをフィンガープリントし(レスポンスヘッダ、エラーページ、既定ページ)、既知の脆弱性に対応付ける。解析脆弱性、ディレクトリトラバーサル、認証バイパス、既知 RCE、危険な既定設定(一部の管理 API が既定で開放など)。ミドルウェアのバージョンは CMS より露出しやすく、パッチ漏れしやすい。
**Q3**: 対象がコンテナ/クラウド上で動く。追加の攻撃面はある?
**A3**: ある。コンテナオーケストレーション/管理 API(未認可のオーケストレーション API、コンテナ管理ポート)、コンテナエスケープ、クラウドメタデータ API(クラウド認証情報取得)。getshell でコンテナに入った後、**ホストへエスケープできるか、他のコンテナへ横展開できるか**、クラウド AK/SK を取れるかを重点評価する。
**Q4**: ミドルウェアも全最新版で穴がない。どこへ転じる?
**A4**: **設定層**へ転じるのであってバージョン層ではない。ミドルウェアの誤設定(ディレクトリリスト、危険な HTTP メソッドの開放、alias/rewrite 設定の不備によるパストラバーサルや未認可)。バージョンが新しくても設定を誤れば打てる。設定欠陥はバージョンを食わない。

### 隣接サイト / C セグメント / サブドメイン:横展開でどれを先に打つか
**Q1**: 主目標が非常に堅い。周辺から突破したい。隣接サイトと C セグメントのどちらを先に打つ?
**A1**: まず関係を分ける。**隣接サイト**(同一サーバーの他のサイト)は一度取れば直接目標マシンにいるので価値が最高。**サブドメイン**(同組織の他の業務)は横展開価値が高い。**C セグメント**(同一ネットワークセグメントの他ホスト)は関係が緩く、帰属と認可の確認が必要。優先は 隣接サイト>サブドメイン>C セグメント。
**Q2**: 隣接サイトは主目標にどう役立つ?
**A2**: 同一サーバーの隣接サイトで getshell すれば=主目標のいるマシンの権限を直接得て、本サイトの強化を全て迂回する。だから本サイトが攻めにくいとき、同一 IP 上で防御の弱い隣接サイトを「脇戸」として使い、取れば即本サイトの宿主を取るのと同じだ。
**Q3**: サブドメインを落としたら主目標にどう戻る?
**A3**: サブドメインは**情報と認証情報の源**だ。同組織はしばしばアカウント体系、内部ネットワークアクセス、SSO、データベース、パスワード再利用を共有する。サブドメインで得た認証情報/内部ネットワーク足場で、主目標の内部ネットワーク側か認証側へ戻り、その正面防御を迂回する。
**Q4**: 周辺アセットもかなり堅い。この横展開の道が通らない。どこへ転じる?
**A4**: **認可境界内の他の次元**に転じる。サプライチェーン(対象が使う第三者システム/オープンソースコンポーネント)、ソーシャルエンジニアリング/フィッシング(認可範囲)、晒された非 Web サービス。同時に**認可範囲**がアセット選択を制限していないか再確認する。認可外の C セグメントホストを打って越境しない。

### JWT / session / 鍵:認証情報を偽造して認証を迂回する
**Q1**: システムが JWT/token で認証する。偽造できるか?
**A1**: まず token 構造と署名機構を分析する。JWT のよくある破れ目: ① alg=none で署名迂回 ② 弱い鍵を**オフラインで HMAC 鍵をブルートフォース**して自己署名 ③ アルゴリズム混乱(RS256→HS256 で公開鍵を鍵に使う)④ 署名未検証。いずれかが成立すれば任意のユーザー(管理者含む)を偽造できる。
**Q2**: 署名鍵を取った(ソース/設定漏えいから)。どう使う?
**A2**: 直接**任意の身元を自己署名**する。admin ユーザー/権限昇格 claim の token を構築し、ログイン体系全体を一歩で迂回する。これが設定/ソースの鍵がパスワードより致命的な理由だ。それは「正当な身元を偽造する」能力を与える。
**Q3**: 伝統的な session(サーバー保存)で JWT ではない。まだ偽造できるか?
**A3**: session の生成/検証を見る。session id が予測可能か、IP/UA に紐づくか、固定/注入可能か。session データがクライアント側にシリアライズされる(署名付き)なら、JWT と同じ発想で鍵を探して偽造する。サーバー保存の session なら**セッション固定/窃取**の発想に転じる。
**Q4**: token 機構がかなり厳しい。偽造できない。どこへ転じる?
**A4**: **本当の token を取得**するのであって偽造ではない。XSS で token を盗む、中間者、ログ/referer の token 漏えい、他の API が token をエコーする。偽造が通らないなら「借りる」ことを工夫する。それも駄目ならアカウントとパスワードの次元か他の入口へ戻る。

### API / GraphQL:構造化 API の攻撃面
**Q1**: フロントエンドが SPA、バックエンドが API。従来の CMS の攻め方と何が違う?
**A1**: 攻撃面が「ページ」から「API」へ移る。まず**全量の API 収集**を行う。フロントエンド JS のルートと API 定義をキャプチャ、swagger/openapi ドキュメント、GraphQL の introspection。API リストが完全なほどテストできるものが多い。多くの API はフロントエンドが使わないがバックエンドは到達可能だ。
**Q2**: API で重点的に何をテストする?
**A2**: ① **権限外アクセス**(id を変える/認可ヘッダを削って他者や管理データにアクセス。API は権限外アクセスの激戦区)② 一括パラメータ改ざん(mass assignment で role を変える)③ 未認可 API(一部の API が認証・認可を漏らす)④ 注入(API パラメータにも SQLi/NoSQLi/コマンドインジェクションがある)。
**Q3**: GraphQL なら、どう打つ?
**A3**: まず **introspection** を開いて全 schema を取る(全種別とクエリを晒す)。そして探す。未認可クエリ、権限外アクセス、ネストクエリ DoS、一括クエリでレート制限迂回、mutation 内の危険な操作。introspection が閉じられたらフロントエンドから既に使われている query をキャプチャして schema を逆算する。
**Q4**: API の認証・認可が厳格で、権限外アクセスも塞がれた。どこへ転じる?
**A4**: **API の技術的脆弱性**へ転じるのであってロジックではない。パラメータ注入、ファイルアップロード API、SSRF 型 API(URL パラメータを受ける)、デシリアライズ(API が構造化データを受ける)。ロジックが打てなければ「各入力パラメータが潜在的な注入点」というブラックボックスの基本に戻る。

### パスワード再利用と認証情報の横展開:一つの鍵で複数の錠を開ける
**Q1**: 認証情報を一つ取った(どこかのアカウントとパスワード)。現在のシステム以外に何ができる?
**A1**: 即座に**横展開で再利用**する。人も組織もパスワードを普遍的に再利用する。同じパスワードを管理画面、他のサブシステム、データベース/SSH/メール/VPN で試す。認証情報の本当の価値は往々にしてその発生源のシステムでなく、横展開で開けられる他のシステムにある。
**Q2**: 取れたのが一括のユーザー認証情報(DB ダンプ)だ。どう高効率に利用する?
**A2**: **認証情報スプレー**を行う。パスワード規則を抽出する(会社名+年、季節などの一般的な構成)、他のシステムのユーザーに一括で試す。「少数の高頻度パスワード × 多ユーザー」を使い、「多パスワード × 単ユーザー」ではない。ロックを避けつつ命中を最大化する。
**Q3**: 平文がなく hash だけだ。再利用にまだ見込みは?
**A3**: ある。① オフライン解読で平文にして再利用 ② 一部プロトコルは直接 **pass-the-hash** ③ hash 自体を「同じか否か」の判定に使う(同じ hash=同じパスワード、再利用関係を晒す)。解けない hash も情報であり、捨てない。
**Q4**: 認証情報の再利用が全て失敗した。どこへ転じる?
**A4**: **認証情報以外の信頼関係**に転じる。鍵/token/証明書(パスワードを推測せず身元を偽造)、確立済みのセッション、マシン間のパスワード不要の信頼(内部ネットワークでは一般的)。パスワード再利用は横展開の一つの道であり、唯一ではない。信頼関係はパスワードより価値が高い。

### getshell 後の制限:disable_functions / open_basedir 迂回
**Q1**: webshell を取ったが、コマンド実行関数が全て禁じられた(disable_functions)。どうする?
**A1**: shell が無駄だと思わない。disable_functions 迂回には複数の直交路がある。① **禁じられていない実行関数**を探す(禁止リストは往々にして不完全)② 言語/拡張特性を利用する(LD_PRELOAD と誘発可能な外部呼び出しの併用、特定拡張の脆弱性)③ **メモリ馬**でプロセス内実行し、禁じられたコマンド関数に依存しない。
**Q2**: open_basedir が web ディレクトリのみに制限した?
**A2**: **トラバーサル/迂回**を試す。open_basedir 制約を受けない関数の特性、シンボリックリンク、既知の迂回技で対象ディレクトリへアクセスする。迂回できなければ**許容範囲内**で利用する。web ディレクトリの設定/認証情報は依然読めるので、横展開に使う。
**Q3**: コマンド実行が迂回できず、shell はファイル読み書きだけになった。まだ進められるか?
**A3**: 進められる。「読み書き」だけで多くのことをできる。設定/鍵/認証情報を読んで横展開、解析可能か他プロセスがロードする位置へファイルを書く、設定ファイルを変えてアプリ挙動に影響させる。「制限された shell」を「コマンドライン」でなく「ファイル読み書きプリミティブ」として使う。
**Q4**: 各種迂回が失敗し、このマシンは完全に制限された。どこへ転じる?
**A4**: **現在の限られた能力でより良い足場に換える**。読んだ認証情報で内部ネットワークの制限のない他のマシンに接続する、同一マシンの別サービス(権限設定が異なる)を探す。このマシンが制限されたと認め、それを「足がかり/情報点」とし、戦場をそれが届く次へ移す。

### 低権限 shell 後:権限昇格段階でどの方向を探すか
**Q1**: getshell が低権限ユーザー(www-data/apache)だ。root/system へ権限昇格したい。まず何を見る?
**A1**: まず**体系的な情報収集**をしてから動く。権限昇格は「EXP を暗記する」でなく「設定誤りを探す」ことだ。収集: システムバージョン/パッチ、実行中の高権限サービス、可書の高権限ファイル、スケジュールタスク、sudo 権限、認証情報の残存。自動列挙スクリプトで先に全景を描いてから選ぶ。
**Q2**: 収集が終わった。権限昇格経路をどう並べる?
**A2**: **低リスク高確実**を優先する。設定誤り(可書のサービスファイル/スケジュールタスク、sudo 設定の不備、SUID 乱用)> 平文認証情報の再利用(root パスワード/鍵を直接使う)> カーネル EXP(最後の選択、クラッシュしやすく騒音が大きい)。設定誤りはカーネル権限昇格よりはるかに安定する。
**Q3**: Windows ホストの権限昇格は何を見るのが違う?
**A3**: **サービスとトークン**を見る。引用符なしのサービスパス、変更可能なサービス、AlwaysInstallElevated、トークン権限(SeImpersonate 類→Potato 系の権限昇格)、認証情報(レジストリ/ファイル/メモリのパスワードと hash)。ドメイン環境のマシンではドメイン層の権限昇格経路も評価する。
**Q4**: 通常の権限昇格を全部試して昇格できない。どこへ転じる?
**A4**: **縦の代わりに横**に転じる。本機では昇格できないが、現在の権限で読める認証情報/アクセスできる内部ネットワークサービスが、**別のマシンでは直接高権限**かもしれない。レッドチームの目標は重要権限を取ることで、必ずしもこのマシンで垂直権限昇格する必要はない。横に進んでより柔らかい高権限目標へ到達しても同じく目標達成だ。
**Q5**: ドメイン環境だ。単機の権限昇格の意味はまだ大きいか?
**A5**: 目標次第だ。目標がドメインコントローラなら、単機の root/system は本機の認証情報を取る手段にすぎず、重点を**ドメイン内攻撃チェーン**(Kerberoast、ADCS 証明書攻撃、委任乱用、zerologon 類)へ転じる。本機の権限昇格は「ドメインを打てる認証情報/マシン身元の取得」に奉仕し、終点ではない。

### 検知回避の足場確保と痕跡:隠密性と推進速度の取捨
**Q1**: 各歩で検知回避と痕跡除去をすべきか。遅くならないか?
**A1**: 段階で天秤をかける。**偵察段階**はやや騒がしくてもよい(トラフィックは避けにくい)。しかし**足場確保と駐留段階**は隠密でなければならない。ここが EDR/HIDS に最も捕まりやすい。原則は、高価値動作(シェル確保、権限昇格、横展開)は必ず低特徴、低価値の探査は騒音を許容できる。
**Q2**: どの程度隠密にすべきかをどう判断する?
**A2**: **環境の防御強度**と**タスク目標**を見る。EDR/状況認識のある環境では、一度のアラートが全盤暴露につながり得るので、極限まで隠密にすべき。純粋に突破して flag を取る場面は適度に積極的でよい。先に少量のコストで防御を探査し(セキュリティエージェントの有無、コマンドが記録されるか)、それで戦略を定める。
**Q3**: 既に一度アラートを誘発した。どう損切りする?
**A3**: 直ちに**暴露程度**を評価する。アラートが既に応答されたか(IP 封/シェル除去/パスワード変更)。応答されたら現在の入口は廃棄し、**予備の直交バックドア/認証情報**に切り替えて低調に回復する。監視されている入口で動作を続けない。多点駐留の価値がこの瞬間に現れる。
**Q4**: ログを消すべきか。消したらより不審にならないか?
**A4**: 天秤をかける。**認可されたレッドチームは通常業務/システムログを消さない**(取証を壊し、異常が気づかれやすい)。より安定なのは「**痕跡を少なく残す**」ことで「事後に消す」ことではない。無ファイルの手法を使う、監査される高危険操作を避ける、源から痕跡を減らす。これは「ログが消された」というより目立つ信号を残すより良い。
**Q5**: 隠密要件が高すぎ、推進がほぼ停滞した。どうする?
**A5**: **目標と認可**を再較正する。タスクが本当に証明したいことは何か。「getshell できる/ある権限を取れる」の証明だけで済むなら、取れれば止め、各歩深入りしてリスクを増やさない。隠密と推進が衝突したら、「この行動の最小成功判定」に戻り、達成すれば収め、無限に戦果を広げない。

### 全局が詰まった:どう次元を替えて優先順位を並べ直すか
**Q1**: 一つの対象を長く打って進展がない。「もう少し粘る」か「方向を替える」かどう判断する?
**A1**: **損切り判定基準**を設ける。同一攻撃面/同一脆弱性クラスで複数回連続して実質的進展がない(成功しないだけでなく「新しい情報が出ない」)なら方向転換すべきだ。判定基準は時間でなく「情報増分」だ。各試行がまだ未知を縮めている限り続ける。原地で空回りし始めたら次元を替える。
**Q2**: どの直交次元に転じるか。体系的な方法は?
**A2**: **攻撃面マトリクス**で次元ごとに巡る。識別層(フィンガープリント/バージョン手段を替える)→脆弱性層(既知の脆弱性/設定欠陥/ロジック脆弱性/0day)→入口層(Web/他のサービスポート/認証入口)→アセット層(本サイト/サブドメイン/隣接サイト/C セグメント/サプライチェーン)。まだ真剣に試していない次元に転じる。詰まるのは一つの次元で固執しているからだ。
**Q3**: 「頻繁に乱し、どれも浅く試すだけ」の反対の極端をどう避ける?
**A3**: 一枚の**試行記録**を維持する。各攻撃面に「何を試したか、結論、未試行の経路が残るか」をマークする。方向転換前にまず現在の面が「尽くすべきを尽くした」ことを確認し、転換後は随時、残価値のある点へ戻れる。記録があって初めて固執もせず闇雲に替えもせずに済む。
**Q4**: 全次元を一巡しても入れない。本当に打てないのか?
**A4**: 戻って**前提を疑う**。対象範囲が正しいか(漏れたアセット/サブドメインはないか)、情報が十分新しくないか(公開されたばかりの 1day はないか)、情報の盲点はないか(ある漏えい源を未確認)。詰まりは「穴がない」でなく「情報が不全」であることが多い。情報を補う(マッピングをやり直す、収集をやり直す)ほうが硬く打つより有効なことが多い。
**Q5**: 対象が現在確かに隙がないと確認した。どう締める?
**A5**: **時間次元と受動次元**に転じる。対象を「新情報待ち」とマークし、受動監視(新脆弱性の公開、アセット変化、認証情報が他チャネルに出現)を掛け、精力をより産出のある対象へ移す。レッドチームは資源配分のゲームで、一時的に打てない硬い対象は無限投入に値しない。情報を記録し、機会を見て再戦する。
