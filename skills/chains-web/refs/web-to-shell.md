# Web · webの脆弱性からシステムシェルへの足場確保

### SQL インジェクション：「データベースを照会できる」から「シェルを取得できる」へ
**Q1**: SQLi を確認済みでデータを読み取れるが、目標がシステムシェルであってデータベースのダンプではない場合、まず何を判断するか？
**A1**: まず3つのことを確定する。データベース種別（MySQL/MSSQL/Oracle/PG）、現在の DB ユーザー権限（`current_user`/`is_srvrolemember('sysadmin')`）、DB と Web が同一マシンかどうか。シェルへの足場確保の経路はこの3点に強く依存する。ペイロードを積む前に、まず3つの枠を埋める。

**Q2**: 対象が MySQL で root の場合、どう足場を確保するか？
**A2**: 優先して `secure_file_priv` を確認する。空であれば `INTO OUTFILE` で web ディレクトリに webshell を書き込む（前提：絶対パスが分かること + ディレクトリが書き込み可能 + スタッククエリまたは union の書き込み位置があること）。web の絶対パスが取れない場合はエラー / `@@datadir` / 設定の漏えい / phpinfo から推測する。`secure_file_priv` に制限がある場合は UDF による権限昇格に切り替える（`lib_mysqludf_sys` を plugin ディレクトリに書き込み、システムコマンドを実行する）。

**Q3**: MSSQL で高権限の場合はどうか？
**A3**: 直接 `xp_cmdshell` に向かう（無効なら `sp_configure` で有効にする）。削除・無効化されている場合は `sp_OACreate` コンポーネント、CLR アセンブリ、Ole Automation の3つの代替手段を使う。本質は「ストアドプロシージャ→システムコマンド実行」の橋を探すことである。

**Q4**: web の物理パスが取れず、`INTO OUTFILE` の書き込み先がない場合、どうするか？
**A4**: この経路は一旦棚上げし、直交する次元へ転換する。webshell を書かず、「DB 内で直接コマンドを実行する」（UDF/xp_cmdshell/CLR）方法に切り替える。これは web ディレクトリに依存しない。DB 権限もコマンド実行に足りない場合は、もう一段下がって SQLi を**情報源**として扱い、設定を読み、パスワードを読み、hash をダンプして、横展開で別の入口を攻める。

**Q5**: 低権限の DB アカウントしかなく、ファイル書き込みもコマンド実行もできない場合、インジェクションの線は死んでいるのか？
**A5**: 死んでいるとは言えない。低権限インジェクションの価値は、`information_schema` を読み機密テーブルを探すこと、アプリケーション設定を読むこと（接続文字列に高権限アカウントが含まれることが多い）、バックエンドの管理者 hash をダンプして管理画面へのログインをブルートフォースし、さらに管理画面の機能ポイントから getshell すること、へ転換される。**方向転換**：「インジェクションから直接足場確保」から「インジェクション→資格情報→より肥沃な攻撃面への切り替え」へ転換する。

**Q6**: 「同一マシンかどうか」の判断がなぜ重要なのか？
**A6**: UDF/xp_cmdshell で取得した shell がどのマシンに落ちるかを決めるからである。DB と Web が分離している場合、DB コマンド実行が与えるのは DB サーバーの立足点であり、内部ネットワークのコアにより近い可能性がある。対象に応じて横展開の経路を再計画すればよい。

### ファイルアップロード：検証を迂回して解析可能な webshell を取得する
**Q1**: アップロード機能を見つけて webshell を送りたい場合、最初の一歩で何を把握するか？
**A1**: 検証がどの層にあるかを把握する。フロントエンド JS（パケット改変で迂回）、Content-Type、拡張子のブラックリスト/ホワイトリスト、ファイルヘッダの magic、内容スキャン（WAF/アンチウイルスがペイロードを走査）。さらに、書き込み先のパスがアクセス可能か、対応するスクリプトを解析可能かも把握する。検証層を把握せずに闇雲に試すのは壁に突き当たるようなものだ。

**Q2**: 拡張子がホワイトリストで画像のみ許可されている場合、どう突破するか？
**A2**: 2つの主線がある。1つは**アップロードと解析の分離**で、画像に偽装した馬を LFI / インクルード / サムネイル処理と組み合わせてトリガーする。もう1つは**解析の脆弱性や代替拡張子**（`.php3/.phtml/.pht`、大文字小文字、二重書き、末尾の特殊文字、`::$DATA`、パスの切り詰め）を探すことである。解析の脆弱性はミドルウェアに強く結びつくため、まずミドルウェアの種別を探る。

**Q3**: ホワイトリストが厳格で解析の脆弱性もないが、アップロード先ディレクトリを制御できる場合は？
**A3**: `.htaccess`/`web.config` 攻撃に切り替える。設定ファイルをアップロードして、ある「無害な拡張子」をスクリプトとして解析させ、その拡張子の馬を送る。Nginx で htaccess がない場合は、解析の脆弱性 / 画像に偽装した馬 + インクルードチェーンに戻る。

**Q4**: アップロードできたが 404 になるか、ソースコードが返って解析されない場合、どう転換するか？
**A4**: 書き込み先が web のアクセス可能なパスにないか、そのディレクトリが静的/実行禁止に設定されていることを示す。**方向転換**：設定の漏えい / エラーから実際の書き込み先を突き止めるか、解析可能なディレクトリへ送り先を変える。アップロード先パスを完全に制御できない場合は webshell を諦め、アップロードポイントを**別の媒体**へ転換する。バックエンドの処理コンポーネントの脆弱性（画像ライブラリの RCE、XXE、ZIP 展開時のパストラバーサルによるファイル書き込み）をトリガーする。

**Q5**: 内容が WAF にスキャンされ、ワンライナー馬が送った直後に削除される場合は？
**A5**: 検知回避の次元へ転換する。ワンライナーを分割 / エンコード / 変形し、機密のリテラルを含まない動的呼び出し、暗号化馬、極小 loader による二段階読み込みを用いる。スキャンが厳しい場合は優先して**メモリ馬**を落とし、ファイルがスキャンされる窓を減らす。

**Q6**: サイト全体のアップロードポイントがすべて塞がれた場合、方向は終わりか？
**A6**: 直交する面へ転換する。「アップロードで getshell」から「アップロードを探針として使う」へ。それは物理パス、ミドルウェアのバージョン、バックエンドの処理チェーンを露呈することが多く、これらの情報は SQLi によるファイル書き込み、LFI インクルード、既知コンポーネントの nday に供給される。アップロードポイントはシェルを与えなくても高価値の情報源である。

### SSTI：テンプレートインジェクションからコマンド実行へ前進する
**Q1**: ページが入力をテンプレートとしてレンダリングしている（`{{7*7}}` が 49 を表示する）場合、次の一歩は？
**A1**: まず**エンジンをフィンガープリント**する。プローブ群（`${7*7}`、`{{7*'7'}}`、`#{}`、`<%= %>`）で Jinja2/Twig/Freemarker/Velocity/Thymeleaf を区別する。エンジンが異なれば利用チェーンはまったく異なるため、フィンガープリントを誤れば後がすべて狂う。

**Q2**: Python の Jinja2 と確認した場合、どう RCE に至るか？
**A2**: オブジェクトチェーンを辿る。組み込みオブジェクトから `__class__`→`__mro__`→`__subclasses__()` を経て `os`/`subprocess`/`Popen` を呼べるクラスを探すか、`cycler/joiner/namespace` の `__init__.__globals__` 経由で `os` を取得する。核心は「サンドボックスのオブジェクトからコマンドを実行できる入口へ辿り着く」ことである。

**Q3**: サンドボックスが `__`、`class`、`os` をすべてフィルタリングしている場合は？
**A3**: 迂回へ転換する。`attr()` フィルタで属性を取得、`request.args` の連結、`~` による文字列連結、`|join`、hex/unicode でのキーワードエンコード、辞書アクセスによるドット回避。等価な手段で禁止された属性取得 / グローバル取得のチェーンを再構築する。

**Q4**: Java 系（Freemarker/Velocity）の場合は？
**A4**: Freemarker は `Execute`/`ObjectConstructor`/`JythonRuntime` を経由し、Velocity は `ClassTool`/リフレクションで Runtime を呼ぶ。判定基準は、コマンドを実行できるユーティリティクラスを new できるかどうかである。制限されている場合はホワイトリストの静的メソッドの中にあるリフレクションの入口を探す。

**Q5**: 実行できるが**表示されない**場合はどうするか？
**A5**: ブラインド確認へ転換する。DNSlog/HTTP の帯外でコマンドが実際に実行されたことを検証し、次にコマンドで結果を読み取り可能なファイルに書き込む / サーバーへ送り返す / 別のレスポンス位置に埋め込む。確認後は直接リバースシェルに進み、ページへの表示にこだわらない。

**Q6**: エンジンを識別できず、すべての算術プローブが表示されない場合、SSTI なのか？
**A6**: おそらく**誤検知**である。**方向転換**：再評価する。XSS（クライアント側）、通常のリフレクション、あるいはバックエンドがエスケープしている可能性がある。時間を費やさず、そのパラメータに対して通常のインジェクションテスト（SQLi/コマンドインジェクション。OGNL/SpEL 式インジェクションは別扱い）に戻り、別の種類の脆弱性仮説に切り替える。

### デシリアライズ：利用チェーンを識別して RCE へ足場を確保する
**Q1**: パケットキャプチャで `rO0AB`（Java）または `O:` で始まる（PHP）シリアライズの特徴を確認した場合、どう着手するか？
**A1**: まず言語と形式を確定し、次に**依存関係に利用可能な gadget があるか**を確定する。Java では CommonsCollections/Beanutils/Fastjson/Jackson が classpath にあるかを確認し、PHP では制御可能なマジックメソッド（`__wakeup/__destruct/__toString`）の有無を確認する。デシリアライズの急所は入口ではなく gadget である。

**Q2**: Java のデシリアライズでどう素早くチェーンを探すか？
**A2**: ysoserial の各チェーンをひとつずつ打って差異を観察する。DNSlog プローブ（URLDNS/JRMP）を併用して、まず「デシリアライズが実際に発生し、外向き通信がある」ことを確認してから、コマンド付きチェーンに進む。チェーンが多い場合は対象の依存バージョンに基づいて収束させ、全量のブラインド攻撃でアラートを誘発しないようにする。

**Q3**: PHP で既存の POP チェーンがない場合は？
**A3**: 手動監査へ転換する。入口のマジックメソッドを探し、「制御可能な属性→機密 sink（`system/file_put_contents/call_user_func`）」の呼び出しチェーンを連結する。sink が欠けている場合はファイル書き込み / インクルードの sink を探して間接的に達成する。

**Q4**: デシリアライズポイントを確認したが、すべての既知 gadget が通らない（外向き通信なし/表示なし/エラー）場合は？
**A4**: 層ごとに切り分ける。まず DNSlog で**そもそもトリガーされていないか**を確認する（magic bytes がフィルタリングされているか、Hessian/独自 readObject のようなホワイトリスト方式のデシリアライズが使われている可能性がある）。トリガーされたが外向き通信がない場合はローカル gadget に転換する（ファイルへの足場確保 / 馬の書き込み / スケジュールタスクの書き込み）。それでも駄目なら**方向転換**する。SerialKiller/lookahead で防御されている可能性があるため、別の入口またはコンポーネントの nday を攻める。

**Q5**: Fastjson/Jackson のような JSON デシリアライズはどう区別して扱うか？
**A5**: これらは `@type`/ポリモーフィズムによって任意クラスの読み込みをトリガーし、利用ポイントは悪意のあるクラスを指定して getter/setter に動作を実行させられるかどうかである（JNDI インジェクション→リモート読み込み）。判定基準は、バージョンが影響を受ける範囲内か、autoType/ブラックリストの迂回があるかどうかである。

**Q6**: JNDI で高バージョンの JDK がリモート codebase の読み込みを塞いでいる場合は？
**A6**: ローカル factory / EL インジェクションなど、リモート class のダウンロードに依存しない迂回へ転換するか、対象の classpath にある既存の利用可能なファクトリクラス（接続プール / テンプレートクラスの bean プロパティ gadget）を探す。核心は「リモートで class を読み込む」から「ローカルの既存クラスで実行を組み立てる」へ転換することである。

### コマンドインジェクション：フィルタリングを迂回してコマンドを送り込む
**Q1**: あるパラメータがシステムコマンドに連結されている疑いがある場合（ping、画像処理、エクスポート）、どう確認するか？
**A1**: 区切り文字で探る（`;`、`|`、`&&`、バッククォート、`$()`、改行 `%0a`）。遅延（`sleep`/`timeout`）または DNSlog を併用して実行されたかどうかを判断し、表示に依存しない。インジェクション位置を確認してから迂回を論じる。

**Q2**: 空白がフィルタリングされている場合はどうするか？
**A2**: `${IFS}`、`$IFS$9`、`<`、`{cmd,arg}`、Tab で空白を置き換える。キーワードがフィルタリングされている場合は変数連結、ワイルドカード、バックスラッシュによる語分割、base64 デコード実行を使う。考え方は「意味を保ち、字面を変える」ことである。

**Q3**: 実行できるが**表示されない**場合は？
**A3**: 帯外を使う。DNSlog でコマンド結果を帯外に持ち出す（サブドメインに埋め込む）、curl/wget で送り返す、web の読み取り可能なファイルに書き込んでからアクセスする。表示されないことは利用不可能を意味しない。

**Q4**: 入力がコマンドに入っているように見えるが一向にトリガーされない場合、どう死活を判断するか？
**A4**: **フィルタリングによる遮断**か、**そもそも shell に入っていない**か（パラメータ化された execve 配列や安全な API が使われている可能性がある）を区別する。前者なら迂回方法を変え、後者ならこのパラメータに見込みはない。**方向転換**：別のパラメータ / API を再調査するか、その機能が裏で呼び出しているコンポーネント自体の脆弱性を攻める（nday のあるコマンドラインツールを呼び出している）。

**Q5**: WAF がトランスポート層でコマンドの特徴を遮断する場合は？
**A5**: エンコードとチャンク化へ転換する。URL の二重エンコード、パラメータ汚染、チャンク転送、Unicode、コメントによるキーワード分割。それでも遮断される場合は**次元を変える**。同じアプリケーションで防御の弱い入口（内部 API、古い API、非常規の method）を探す。

**Q6**: 実行できることを確認した場合、どう安定した shell を確保するか？
**A6**: まず外向き通信の方向を探る。外向き通信が可能なら直接リバースし tty をアップグレードする。外向き通信ができない場合はまず webshell を落とすか、バンド方向でポートを bind し、一回限りのコマンド実行を持続可能な対話制御へアップグレードする。

### LFI/ファイルインクルード：「ファイルを読める」から「コードを実行できる」へ
**Q1**: LFI（任意のファイルを読める）を確認した場合、どう RCE へアップグレードするか？
**A1**: 目標は「インクルードされる内容に自分のコードを入れる」ことである。汚染可能な書き込み先を洗い出す。アクセスログ（UA/URL インジェクション）、SSH/mail ログ、session ファイル、一時ファイル、アップロードファイル、`/proc/self/environ`。判定基準は「どのファイルに制御可能な内容を書き込め、かつインクルードできるか」である。

**Q2**: ログ汚染は具体的にどう行うか？
**A2**: UA に PHP コードを埋め込んで access.log に書き込み、ログのパスをインクルードして実行をトリガーする。前提は、ログの絶対パスが分かり、インクルードできること（open_basedir に遮られないこと）である。パスが不確定ならまず LFI で設定を読んでパスを推測する。

**Q3**: PHP 環境で wrapper が使える場合は？
**A3**: `php://filter` でまずソースコードを読んで監査し、`data://`/`php://input`/`expect://` で直接実行し（設定に依存）、`phar://` をデシリアライズと組み合わせる。wrapper が使えるかどうかは `allow_url_include`/PHP バージョンに強く依存する。

**Q4**: `allow_url_include=Off`、ログ権限なし、session を制御できない場合、汚染の手掛かりはないのか？
**A4**: **方向転換**：PHP の一時ファイルの競合インクルード（phpinfo との併用または upload tmp の競合）を使うか、`php://filter` のチェーン変換（filter chain）で実行可能な内容を直接構築する。外部の書き込み可能なファイルに依存しない現代的な LFI2RCE である。それでも駄目なら LFI を純粋な読み取りとして扱い、ソースコード / 鍵を読んで別の面を攻める。

**Q5**: `open_basedir` の制限で対象を読めない場合は？
**A5**: 迂回へ転換する。`glob://`、シンボリックリンク、`chdir`+`ini_set` の組み合わせ、既知の basedir bypass。迂回できない場合は許可されたディレクトリ範囲内で利用可能なファイル（アプリケーションログ / キャッシュ / session）を探す。

**Q6**: リモートインクルード（RFI）で自分のサーバーのファイルをインクルードできる場合は？
**A6**: それはより直接的で、自分の VPS 上の馬をインクルードさせる。ただし現代では `allow_url_include` は Off が多く、RFI は稀である。成立する場合は外向き通信の方向と URL が WAF に遮断されることに注意し、IP、非常規のポート、data プロトコルで回避できる。

### RCE を手にしたのに**表示されない**場合：まず実行を確認し、次に制御を取る
**Q1**: RCE の疑いで打ったが、ページに何も出力されない場合、成功したかどうかを判断するか？
**A1**: 目視に頼らない。3つのサイドチャネルを使う。DNSlog、HTTP のコールバック（curl で自分のサーバーを打つ）、時間ブラインド（`sleep 5` で遅延を見る）。どれかがヒットすればコード実行が証明される。

**Q2**: DNSlog は届くが HTTP は届かない場合、何を意味するか？
**A2**: **実行でき、DNS は外向きに通るが、HTTP/TCP の外向き通信が制限されている**ことを意味する（典型的な内部ネットワークで DNS のみ許可）。重要な情報：リバースシェルもおそらく通らないため、DNS トンネルまたは純粋な webshell による滞在を使うべきで、通常のリバースを試す時間を無駄にしない。

**Q3**: 3つのプローブがすべて無反応の場合、外れたのか、実行されたが完全に隔離されているのか？
**A3**: 時間ブラインドで再確認する。`sleep` が安定してレスポンスを延長するなら実行は成功したが**完全に外向き通信がない**。時間ブラインドでも差異がないならおそらく外れている。この分岐が、以降を「表示 / 足場確保の方法を考える」にするか「ペイロード / 脆弱性を変える」にするかを決める。

**Q4**: 実行を確認したが完全に外向き通信がない場合、どうコマンド結果を取得するか？
**A4**: 「その場での表示」へ転換する。コマンド出力を web のアクセス可能なファイルに書き込んでから読む、データベース / ログに書き込んでから照会する、次のレスポンスのフィールドに埋め込む。表示のない RCE を「コマンド→足場確保→読み取り」の2段階表示に作り変える。

**Q5**: web ディレクトリすら書き込み不可で、読み取り可能な戻り先がない場合は？
**A5**: **方向転換**：表示の取得を諦め、「持続的なチャネルを確立する」コマンドを直接ブラインドで発行する。メモリ馬を書き込み、スケジュールタスク / サービスを追加し、バックドアアカウントを作成し、独立したチャネルでコールバックするかトリガーを待つ。現在のリクエストレスポンスの制限を迂回する。

**Q6**: ブラインド攻撃でシステムをクラッシュさせたり、アラートを誘発したりしないようにするには？
**A6**: ブラインド状態のコマンドは冪等で非破壊的にし、まず環境を探り（whoami / 権限 / アンチウイルスのプロセス）、その後に行動する。各コマンドで失敗時のリトライとアラート面を考慮し、大量の高リスクコマンドを一気に流して対応チームを呼び込まない。

### webshell を取得した後：まず状況を判断し、慌てて探り回らない
**Q1**: webshell に接続できた場合、最初に何をするか？
**A1**: 状況の4つの問い。自分は誰か（whoami/権限）、自分はどこにいるか（内部ネットワークの IP/ホスト名/ドメイン内か）、外向き通信ができるか（DNS/HTTP/TCP をそれぞれテスト）、周囲に何があるか（アンチウイルス EDR のプロセス、ポート、他のサイト）。この4つの問いが以降の各ステップを決める。

**Q2**: 外向き通信のテストをなぜプロトコル別に行うのか？
**A2**: リバースシェル、ツールのダウンロード、トンネルはすべて外向き通信の方向に依存するが、内部ネットワークではプロトコルのホワイトリストがよく使われる（DNS のみ、あるいは特定のプロキシ 80/443 のみ）。各プロトコルの疎通をテストすることで、どのコールバック / トンネルを使うかが直接決まり、試行錯誤の繰り返しで露呈するのを避けられる。

**Q3**: EDR / アンチウイルスを発見した場合、行動をどう調整するか？
**A3**: ノイズ低減を優先する。ファイルをあまり落とさない、コマンドが高リスクの特徴を避ける、公開ツール（特徴が強い）を慎重に使う。情報収集はシステム標準の living-off-the-land コマンドを使い、ツールはできるだけメモリ上で読み込む。まず EDR の型番を把握してから検知回避が必要かを決める。

**Q4**: 現在 www-data の低権限で webshell の機能が制限されている場合、どうするか？
**A4**: ごく正常である。webshell の段階ではまず**情報と踏み台**として扱う。設定を読んでデータベース / 他のシステムの資格情報を取得する、ホームディレクトリ / history を探る、内部ネットワークの疎通を見る。権限昇格は次の独立した段階であり、web の権限で root が必要なことを無理に行わない。

**Q5**: webshell が時々切断されて不安定な場合、どうするか？
**A5**: 「ワンライナー webshell」からより安定した制御チャネルへ速やかにアップグレードする。tty shell をリバースするか、安定した C2 beacon を落とし、重要な操作を安定したチャネルに置く。webshell は緊急時の予備入口として残し、すべての卵をひとつの籠に盛らない。

### リバースシェルがファイアウォールに遮断される場合：方向を変え、プロトコルを変え、姿勢を変える
**Q1**: コマンド実行はできたが、リバースシェルが接続してこない場合、まず何を疑うか？
**A1**: まず**外向き通信が遮断された**のか**ペイロードが実行されていない**のかを切り分ける。最も簡単な外向き通信プローブ（curl/dns で自分を打つ）で外向き通信の方向を確認する。実行できることを確認した後、問題の多くは外向きポリシーにある。対象が外向きのポート / プロトコル制限を行っている。

**Q2**: 高ポートが通らない場合、どう調整するか？
**A2**: 対象が通常許可している外向きポート（443/80/53）に変えて試し、これらのポートのリスナーへリバース接続する。多くの環境では web でよく使う外向きポートのみ許可しているため、C2 をこれらのポートに偽装すれば大部分の外向き ACL を通過できる。

**Q3**: すべての TCP 外向き通信が遮断され、DNS のみ通る場合は？
**A3**: **方向転換**して DNS トンネルを使う。DNS で C2 トラフィックを運ぶ。遅いが DNS のみ許可の環境を抜けられる。あるいは ICMP トンネルを使う（ICMP が許可されている場合）。核心は唯一許可されているプロトコルを媒体として見つけることである。

**Q4**: 外向き通信がすべて封鎖されている場合（純粋な隔離セグメント）はどうするか？
**A4**: リバースの方針を破棄し、**バンド方向へ転換する**。対象上でポートを bind して自分の接続を待つ（前提として入方向に到達可能な経路があること。前置の踏み台 / ポート転送でそのポートに触れること）。入方向も到達不能なら、純粋な webshell / 足場確保と滞在に戻り、「ポーリングでタスクを取得する」方式の低頻度 beacon に頼る。

**Q5**: リバースはできたが機能不全の shell の場合（tab なし、Ctrl-C なし、対話なし）は？
**A5**: tty をアップグレードする。`python -c 'pty.spawn'`/`script`/`socat` で疑似端末を割り当て、`stty raw` で端末サイズを同期する。対話式 shell は以降の権限昇格と内部ネットワーク操作に極めて重要であり、機能不全の shell で妥協しない。

**Q6**: リバースコマンドが一向に反応せず、ペイロードがアンチウイルスに遮断された疑いがある場合は？
**A6**: ペイロードの形態を変える。shell の種別を変え（bash/python/perl/php/powershell から対象にあるものを選ぶ）、エンコード難読化、メモリ上で実行してファイルを落とさない。それでも駄目なら**チャネルの仮説**を変える。リバースせず、既存の web チャネルでコマンドを配信し、帯外で送り返す。新しい接続を必要とする方式を迂回する。

### Linux の低権限 shell での権限昇格：系統立てて経路を選ぶ
**Q1**: Linux の低権限 shell を取得した場合、権限昇格はどこから手を付け、闇雲な試行を避けるか？
**A1**: まず列挙する（LinPEAS または手動）。カーネルバージョン、SUID/SGID、sudo 権限、cron、書き込み可能な機密ファイル、サービスとポート、ケーパビリティ、環境変数。権限昇格は「自分が触れる高権限の入口を探す」ことであり、列挙でまず入口の一覧を網羅する。

**Q2**: `sudo -l` でパスワードなしで実行できるコマンドが表示された場合、どう使うか？
**A2**: GTFOBins を調べる。ほぼすべての一般的なバイナリに「正規の機能から shell へ逃げる」姿勢がある（`!` によるエスケープ、`-exec`、ファイル書き込みによる上書きなど）。sudo で実行できるコマンドは最もクリーンな権限昇格経路であり、優先して使う。

**Q3**: sudo はないが SUID バイナリが多数ある場合は？
**A3**: ひとつずつ GTFOBins の SUID の項と照合する。非標準の SUID プログラムは逆アセンブルする / 外部コマンドを呼んでいるか（PATH ハイジャック）、既知の CVE があるかを確認する。判定基準は「この root 所有のプログラムに、root として任意のコードを実行させる隙間があるか」である。

**Q4**: sudo/SUID/cron を列挙し終えても見込みがなく行き詰まった場合、どこへ転換するか？
**A4**: **直交する次元へ転換する**。「資格情報の再利用」に切り替える。設定 / history / メモリの中のパスワードを探り、`su` で高権限ユーザーになるか他のマシンへ再利用する。それでも駄目なら**カーネル権限昇格**を見る（ディストリビューションのカーネルバージョンと照合して local root exploit を探す。ただしクラッシュリスクに注意し、本番では慎重に使う）。さらにコンテナ / クラウドメタデータも見られる（コンテナ内なら、本機の権限昇格ではなくエスケープを選ぶ）。

**Q5**: カーネルバージョンが古いが、クラッシュを恐れて直接 exploit を実行できない場合は？
**A5**: まず同じバージョンの環境で exploit の安定性を検証してから実行する。本番では非破壊の権限昇格（設定 / 資格情報 / サービスの設定ミス）を優先し、カーネル exploit は最後の手段とし、できるだけ実績のある安定した実装を選び、影響範囲を制御する。

**Q6**: すべて試しても www-data のままの場合、権限昇格は望みがないのか？
**A6**: 目標を再評価する。おそらく **root は不要**である。現在の権限で読めるデータベースの資格情報 / 鍵は、より価値の高いマシンへ直接横展開できるかもしれない。**方向転換**：「垂直の権限昇格」から「水平の移動」へ転換し、現在の権限を踏み台にして内部ネットワークを攻める。往々にして本機の root に固執するより割に合う。

### Windows の低権限 shell での権限昇格：サービスアカウントから SYSTEM へ
**Q1**: Windows の低権限（IIS/ネットワークサービス）を取得した場合、権限昇格はまず何を見るか？
**A1**: まず `whoami /priv` でトークン権限を見る、`whoami /groups`、システムのパッチレベル（`systeminfo`）、サービスとパス、書き込み可能なディレクトリ。Windows の権限昇格は「このトークンにどの特権があるか + システムにどのパッチが欠けているか」に強く依存する。

**Q2**: `whoami /priv` に `SeImpersonate`/`SeAssignPrimaryToken` がある場合は？
**A2**: 直接 Potato シリーズ（ポテト系）のトークン窃取で SYSTEM へ向かう。サービスアカウントはほぼ必ずこの特権を持つため、これは IIS/MSSQL の足場確保後で最も定番の権限昇格である。判定基準はこの2つの特権があるかどうかである。

**Q3**: 利用可能な特権がない場合、どの経路を取るか？
**A3**: サービスの設定ミスを調べる。引用符なしのサービスパス（unquoted service path）、弱いサービス権限（バイナリ変更可能 / 設定変更可能）、書き込み可能な自動実行プログラム、DLL ハイジャック、AlwaysInstallElevated。PowerUp/winPEAS でこれらの設定エラーをスキャンする。

**Q4**: 設定に問題がなく、パッチもすべて当たっていて行き詰まった場合、どこへ転換するか？
**A4**: **方向転換**して資格情報と横展開へ向かう。レジストリ / 設定 / Unattend / GPP の中のパスワードを探る、mimikatz を実行して現在のセッションの資格情報を取得する、ドメイン内かを確認する（ドメイン内なら権限昇格の問題がドメイン資格情報の取得による横展開に転換される可能性がある）。本機で昇格できないなら取得した資格情報でドメイン内 / 他のマシンへ移動する。

**Q5**: 資格情報を取得したいが EDR が lsass を監視している場合は？
**A5**: 回避手法へ転換する。非常規の方法で lsass にアクセスする、システム標準のツールで dump する、あるいは先に EDR を迂回 / 無力化してから取得する。取得できないなら次善策として**平文 / 可逆の資格情報**（設定ファイル、スケジュールタスク、ブラウザの保存、チケット）を探す。必ずしも lsass に触れる必要はない。

**Q6**: パッチが欠けているがどのカーネル exp を使うべきか不確定な場合は？
**A6**: Watson/WES-NG で `systeminfo` の出力を照合して利用可能な exp を正確に特定し、多数の EXE を闇雲に投げない（検知されやすく、クラッシュしやすい）。選定後は優先してメモリ上で読み込み、単発で検証し、ノイズを制御する。

### 既知コンポーネントの nday：フィンガープリントを先行させ、0day として無理に攻略しない
**Q1**: ある web アプリケーション / ミドルウェアに対して、どう効率的に getshell ポイントを見つけるか？
**A1**: まず**フィンガープリントを識別する**。ミドルウェア（Weblogic/Tomcat/JBoss/WebSphere）、フレームワーク（Struts2/Spring/ThinkPHP/Shiro）、CMS とバージョン。web-to-shell の8割は既知の nday を攻めるものであり、フィンガープリント + バージョンが exp を選ぶ鍵である。最初から手動で 0day を掘らない。

**Q2**: フィンガープリントは判明したがバージョンが曖昧な場合、どう具体的に利用可能な exp を特定するか？
**A2**: 差異フィンガープリントでバージョンを収束させる（特定の静的ファイルの hash、エラーの特徴、デフォルトパス）。バージョンを nday の影響範囲に絞り込む。バージョンが正確に絞れれば、exp の命中率と安定性ははるかに高くなる。

**Q3**: 対応する nday の PoC がある場合、直接打つ前に何に注意するか？
**A3**: まず無害な検証（探査型ペイロード / DNSlog）で脆弱性が実際に存在し、パッチが当たっていないことを確認してから、getshell ペイロードに進む。多くの対象は「バージョン的に脆弱そうでも実はホットパッチ / WAF の仮想パッチが当たっている」ため、先に検証して露呈を防ぐ。

**Q4**: PoC の検証は通ったが getshell ペイロードが入らない（遮断される / 無効）場合は？
**A4**: 層ごとに切り分ける。WAF が特徴を遮断しているのか（エンコード / 変形 / ペイロードのバリアント変更へ転換）、環境が条件を満たしていないのか（特定のコンポーネントが classpath に必要など）。**方向転換**：同じ脆弱性に複数の利用姿勢（ファイル書き込み / メモリ馬 / JNDI / リバース）がよくあり、現在阻まれている方式を迂回する別の足場確保方法に切り替える。

**Q5**: 対象コンポーネントに確かに脆弱性があるが、仮想パッチ / WAF で全面的に防御されている場合、どうするか？
**A5**: **攻撃面を変える**。1つのアプリケーションに複数のコンポーネントがあることが多く、他のポート / サブアプリケーション / 古い API をスキャンする。あるいはその nday の最新の迂回バリアントを探す。重点防御された点を無理に攻略するのは費用対効果が低いため、防御の薄い箇所へ転換する。

**Q6**: 対応する nday がまったく見つからない場合、見込みはないのか？
**A6**: 2つの方向へ転換する。1つは設定系の問題（デフォルトパスワード、未認可、コンソールの露出）である。コンポーネントに脆弱性がなくても設定ミスがあれば同様に getshell できる。もう1つは既知の種類の脆弱性として手動テストする（その種のフレームワークの一般的なインジェクション / デシリアライズのパターン）ことである。nday が見つからないことは設定の脆弱性がないことを意味しない。

### フロントに脆弱性がない場合：認証を迂回して管理画面に入り、機能ポイントから getshell する
**Q1**: フロントを一通りスキャンしても直接利用できる脆弱性がない場合、どう続けるか？
**A1**: 視線を管理画面へ移す。管理画面の機能ポイント（テンプレート編集、プラグインアップロード、データベースバックアップ、スケジュールタスク、SQL 照会ボックス）は、往々にして設計上の getshell 入口である。問題は「どう管理画面に入るか」に変わる。

**Q2**: 管理画面のログイン口で、まず何を試すか？
**A2**: 弱いパスワード / デフォルトパスワード（admin 系）、ブルートフォース（ロックアウトポリシーに注意）、および認証バイパス系（SQLi の万能パスワード、ロジック迂回、JWT 偽造、権限外アクセス）。まず低コストで弱いパスワードを試し、同時に認証ロジックの欠陥を探す。

**Q3**: 管理画面に入れたが機能ポイントがどれも「きれい」に見え、明確なアップロードがない場合は？
**A3**: 細かく見る。テンプレート / テーマ編集（PHP を書く）、ログ / 設定の書き込み、データベースバックアップの拡張子変更による webshell の足場確保、インポート / エクスポート、スケジュールタスクのコマンド、任意ファイルダウンロードによるソースコード読み取りとさらなる脆弱性探索。管理画面の getshell は「一見正常な」管理機能に隠れていることが多い。

**Q4**: 管理画面の弱いパスワードがブルートフォースできず、認証も迂回できず行き詰まった場合、どうするか？
**A4**: **方向転換**：入口を変えて管理画面の資格情報を取得する。SQLi で管理者の hash を dump してクラックする、ソースコードの漏えいにあるデフォルトアカウントを探す、フィッシング / 資格情報の再利用、session/token の漏えいを探す。管理画面に入る道はブルートフォースだけではない。別の場所から鍵を盗んで入る。

**Q5**: 管理画面に入れたが現在のアカウントの権限が低く、getshell 機能に届かない場合は？
**A5**: 管理画面内で**権限外アクセス / 水平の権限昇格**により管理者へ昇格するか、低権限アカウントでも触れる書き込みポイントを探す。管理画面内部にも同様に権限境界の問題が存在する。「管理画面に入れれば最高権限」と決めつけない。

**Q6**: 管理画面の機能に確かに getshell ポイントがない（純粋な表示型）場合は？
**A6**: その管理画面の価値は情報と資格情報の面へ転換される。読み取った設定、接続文字列、API key、内部アドレスを、インフラ（データベース / ミドルウェア / 内部ネットワークのサービス）への直接攻撃に供給する。管理画面は getshell できなくても情報の金鉱になり得る。

### WAF による全工程の遮断：WAF を識別し、ルールを特定し、正確に迂回する
**Q1**: ペイロードを送った直後に遮断される場合（遮断ページ / 403 が返る）、闇雲に改変せずどう系統的に対応するか？
**A1**: まず WAF が遮断したのかアプリケーション自体が拒否したのかを確認する。段階的なペイロードで**遮断をトリガーする具体的な特徴文字 / キーワード**を特定する（二分法で削除・変更する）。何を遮断しているかを知ってこそ的を絞って迂回でき、ランダムな変形で運試しをしない。

**Q2**: あるキーワード（`union`/`select`/`script` など）が遮断されていると特定した場合は？
**A2**: 等価な変形を使う。大文字小文字、インラインコメントによる語分割、エンコード（URL / 十六進 / unicode / 二重エンコード）、同義語置換、空白文字置換。目標は意味を保ち、WAF の字面マッチングを壊すことである。

**Q3**: 長さ / 頻度 / 挙動に基づく遮断の場合（単一キーワードではない）は？
**A3**: 戦略層へ転換する。速度を落として頻度による封鎖を避ける、チャンク転送でペイロードを分割する、パラメータ汚染（HPP）で WAF とバックエンドの解析を不一致にする、HTTP メソッド / Content-Type を変えて WAF に異なる解析経路を通らせる。

**Q4**: 各種の迂回をすべて試しても遮断される場合、どこへ転換するか？
**A4**: **方向転換**してこの一箇所に固執せず攻撃面を変える。WAF がカバーしていない入口を探す。オリジンサーバーの IP へ直接接続（CDN / クラウド WAF を迂回）、内部 / 古い API、非常規のサブドメイン、API エンドポイント。WAF は通常主要な面しか守っておらず、周辺の入口はむき出しであることが多い。

**Q5**: クラウド WAF（CDN 前置）の疑いがある場合、どう迂回するか？
**A5**: 実際のオリジンサーバーの IP を探す（履歴 DNS、証明書、サブドメイン、SSRF プローブ）。オリジンへ直接接続して前置の防御を迂回する。オリジンに独立した防御がない場合、CDN WAF を迂回すれば防御の大半を取り除いたに等しい。

**Q6**: 迂回に成功したが非常に脆い場合（効いたり効かなかったりする）は？
**A6**: ルールの端をかすめて通っていることを示しており、いつ封鎖されても、対応を誘発してもおかしくない。**方向転換**して安定性を優先する。一度でも実行機会を得たら、再び WAF を迂回する必要のない持続的なチャネル（メモリ馬 / 帯外チャネル）を即座に落とし、WAF を繰り返し突破して繰り返しリスクを取らない。

### メモリ馬 vs ファイル上の webshell：滞在方式の取捨選択
**Q1**: RCE を手にした場合、ファイルの webshell を落とすべきか、メモリ馬を打つべきか？
**A1**: 2点を見る。対抗の強度（強力な EDR / ファイル監視がある → メモリ馬）と安定性の要件（再起動後の存続が必要 → ファイルに落とすか永続化を加える）。メモリ馬は隠密性が高い（ファイルを落とさず、ディスクスキャンで検出されない）が、プロセス / アプリケーションの再起動で無効になる。優劣ではなく取捨選択である。

**Q2**: メモリ馬を打つと決めた場合、前提条件は何か？
**A2**: 対象のランタイムに Handler（Java の Servlet/Filter/Listener/Interceptor 型、またはミドルウェア層）を注入できる必要がある。前提は、一度のコード実行と、実行フレームワークの理解があることである。判定基準は「そのリクエスト処理チェーンに自分のフックを掛けられるか」である。

**Q3**: メモリ馬を注入した後、自分は見つけられ、他者には見つけにくくするには？
**A3**: 隠れたトリガー条件（特定の header / パラメータ / パスのときだけ応答する）を使い、目立つルートへの登録を避ける。同時に再訪できるよう注入方式を記録する。隠密性は「自分の合図にだけ応答する」ことから生まれる。

**Q4**: アプリケーションの再起動でメモリ馬が失われた場合、どうするか？
**A4**: これはメモリ馬の固有の代償である。**方向転換**して冗長な滞在へ向かう。メモリ馬 + 控えめなファイル上のバックドア + システム層の永続化（スケジュールタスク / サービス / スタートアップ項目）の3層で、どれかが存続していれば再訪できる。滞在を単一の揮発しやすい点に賭けない。

**Q5**: webshell を落としたが、ファイルスキャン / トラフィックの特徴で検知されるのを懸念する場合は？
**A5**: ファイルとトラフィックの両面で特徴を下げる。ファイルは暗号化馬 / 異常な構造で静的スキャンを避け、トラフィックは暗号化通信で特徴検知を避ける。さらに webshell を通常の業務ファイルに隠し、目立たないパスに置く。ファイル馬の対抗はファイル + トラフィックの二本立てである。

**Q6**: 対象の対抗が強く、どちらも検知されやすい場合、どう衡量するか？
**A6**: 「打ってすぐ離脱 + 最小限の滞在」を優先する。重要な成果（資格情報 / 横展開の立足点）を取得したら速やかに拠点を移し、高対抗の単一点に長期滞在することで露呈するのを減らす。滞在は最小限かつ最も隠密な1つの緊急入口だけを残す。

### Redis の未認可アクセス：キャッシュサービスからシステムシェルへ
**Q1**: 未認可の Redis（直接接続できる）を見つけた場合、どうシェルの足場確保に結びつけるか？
**A1**: Redis がファイルを書き込める特性が鍵である。まず `config set` で dir/dbfilename を変更できるかを確認し、内容を機密の位置に書き込む。判定基準は、設定を変更できる権限があるか + 対象ディレクトリが書き込み可能かつ解析可能 / 読み込み可能かである。

**Q2**: web サービスが同一マシンにある場合、どう Redis で webshell を落とすか？
**A2**: `config set dir` で web ディレクトリを指し、`dbfilename` をスクリプト名に設定し、馬を含む key を書き込んで save し、webshell を足場確保する。前提は、web の絶対パスが分かること、Redis プロセスに書き込み権限があること、ディレクトリが解析可能であること。

**Q3**: web と同一マシンでない / web のパスが取れない場合、他にどのような姿勢があるか？
**A3**: SSH 公開鍵の書き込み（authorized_keys を書く。redis ユーザーのホームディレクトリが書き込み可能で SSH が有効であることが必要）または cron の書き込み（Linux のスケジュールタスクでリバース。crontab ディレクトリが書き込み可能で、ディストリビューションと互換であることが必要）へ転換する。3つの道（webshell / SSH key / cron）から、対象の条件を満たすものを1つ選ぶ。

**Q4**: 3つの書き込みがすべて阻まれる場合（権限が低い、ディレクトリが書き込み不可、監視されている）は？
**A4**: **方向転換**してレプリケーションによる RCE（悪意のあるマスターで .so モジュールを読み込みコマンドを実行する）へ向かう。これは特定のファイルへの書き込みに依存しない。それでも駄目なら Redis を**データ / 情報源**として扱う。中には session、token、業務データ、他のシステムの資格情報がよく保存されており、横展開へ転換する。

**Q5**: Redis にパスワードがあるが弱い / SSRF で内部ネットワークの Redis を攻められる場合は？
**A5**: 弱いパスワードはまずブルートフォースで認証を取得する。SSRF の場面では gopher プロトコルで Redis のプロトコルパケットを構築し、内部ネットワークの未認可 Redis を攻める。SSRF を Redis のファイル書き込み RCE へ転換する。判定基準は SSRF が任意の TCP ペイロードを送れるかである。

**Q6**: 新版の Redis で protected-mode が有効 / config が無効化され、書き込み経路が通らない場合は？
**A6**: レプリケーションによるモジュール読み込みは往々にして依然として可能である（前提が異なる）。すべて防御されている場合は情報利用に戻る。「ファイル書き込み」の単一経路に時間を費やさない。Redis のシェル確保には複数の直交する道があり、前提に基づいてひとつずつ選別する。

### SSRF：「サーバーにリクエストを送らせられる」から内部ネットワークのシェルへ
**Q1**: SSRF（対象に自分の代わりにリクエストを送らせられる）を確認した場合、シェルまであとどれくらいか、まず何をするか？
**A1**: SSRF 自体はシェルではなく**内部ネットワークの入口**である。まず能力の境界を探る。どのプロトコルを打てるか（http/https/gopher/dict/file）、レスポンスを読めるか（表示ありの SSRF かブラインド SSRF か）、どの内部ネットワークのアドレス / ポートに到達できるか。能力が以降に何を打てるかを決める。

**Q2**: gopher を打て、内部ネットワークに到達できる場合、どうアップグレードするか？
**A2**: gopher は任意の TCP ペイロードを構築でき、SSRF を「内部ネットワークの任意サービスのクライアント」に変えることに等しい。未認可の Redis へのファイル書き込み、内部ネットワークの MySQL 攻撃、内部ネットワークアプリケーションへの POST 利用の送信を行う。判定基準は、対象の内部ネットワークにこのような「パケットを送れば RCE できる」サービスがあるかである。

**Q3**: GET しか送れず gopher がなく、能力が制限されている場合は？
**A3**: 「GET ベースの内部ネットワーク入口を打つ」へ転換する。内部ネットワークの未認可の管理 API、クラウドメタデータ（一時資格情報の取得）、他の web アプリケーションの GET 型 RCE / 表示のある脆弱性。GET のみの SSRF の価値は、1つの URL で利用できる対象を打つことにある。

**Q4**: ブラインド SSRF（レスポンスの表示なし）の場合、どう命中したかを判断するか？
**A4**: 帯外と挙動の差異に頼る。DNSlog で外向きに通ることを確認し、レスポンス時間の差でポートの開閉を判断する（SSRF ポートスキャン）。ブラインド SSRF でも内部ネットワークの偵察 + 表示を必要としない利用（Redis のファイル書き込みなど）は可能で、データを取り戻せないだけである。

**Q5**: SSRF に各種のプロトコル / アドレスのフィルタリングがある場合（特定のドメイン / IP のみ許可）は？
**A5**: 迂回へ転換する。DNS rebinding、IP の変形（十進 / 八進 / IPv6 / 短縮ドメイン）、`@`/`#` による難読化、リダイレクト（ホワイトリストの URL を 302 で内部ネットワークへ飛ばす）、解析の不一致。目標は、フィルタには正当な対象に見せつつ、実際のリクエストを内部ネットワークへ届けることである。

**Q6**: SSRF で内部ネットワークを一通り探っても直接 RCE できるサービスがない場合、行き詰まってどこへ転換するか？
**A6**: **方向転換**：SSRF を偵察ツールとして使う。内部ネットワークの稼働ホストと開放ポートを探り、内部ネットワークの地図を描く。取得した資産情報を以降に供給する（既に他の立足点があれば横展開に使う）、またはクラウドメタデータによる資格情報取得という内部ネットワークのサービス脆弱性に依存しない道に集中する。

### ソースコード / 設定の漏えい：ホワイトボックス化した監査で足場確保ポイントを探す
**Q1**: `.git`/`.svn`/バックアップパッケージ/`.DS_Store` などのソースコード漏えいを発見した場合、その価値をどう活用するか？
**A1**: ブラックボックスをホワイトボックスに変える機会である。まずソースコードを完全に dump し、次に2種類のものを監査する。**ハードコードされた鍵 / パスワード / 接続文字列**（直接使う）と**コード内の脆弱性**（アップロード検証ロジック、インジェクションポイント、デシリアライズ、認証・認可の欠陥）である。ソースコードが手にあれば、脆弱性探索の効率は倍になる。

**Q2**: ソースコードを dump した後、優先してどこを見るか？
**A2**: まず機密の定数（password/secret/key/token/appid）、設定ファイル、データベース接続を検索する。次に認証・認可とアップロード / ファイル操作に関連するコードを見て、利用可能なロジックを探す。まず手軽に取れる資格情報を摘み、それからロジック監査を行う。

**Q3**: フレームワークが使う暗号化 key / 署名鍵（session/JWT/シリアライズの key など）を取得した場合、何を意味するか？
**A3**: 直接 RCE または認証バイパスにつながる可能性がある。漏えいした key で署名を偽造する、正規の暗号化されたシリアライズデータを構築する（フレームワークのデシリアライズと組み合わせる）、管理者トークンを偽造する。ハードコードされた鍵は web-to-shell の近道であることが多い。

**Q4**: ソースコードがコンパイル済み / 難読化されている、または一部しか dump できず監査できない場合はどうするか？
**A4**: **方向転換**：部分的なソースコードでも、技術スタック、ルート、隠れた API、バージョンを特定でき、これらを使って的を絞ったブラックボックステストを行える。難読化コードでは優先して設定 / 鍵のようなロジックを読解しなくてもよい産物だけを探す。難読化コードの通読に没頭せず、すぐに使えるものを掴む。

**Q5**: `.git` の漏えいがあるが、dump ツールで履歴を完全に取得できない場合は？
**A5**: ツールを変える / 手動でオブジェクトのハッシュに従って取得し、**過去のコミットで削除された鍵**を重点的に探す（開発者は鍵をコミット後に削除することが多いが、履歴には残っている）。git の履歴は資格情報漏えいの多発地帯であり、現在のバージョンだけを見ない。

**Q6**: 監査で見つけた脆弱性も漏えいした資格情報も使えない場合（環境が既に強化されている）は？
**A6**: 漏えいした情報には依然として横展開の価値がある。内部ドメイン名、API アドレス、従業員の命名規則、他のシステムの入口である。**方向転換**して、それを内部ネットワーク / 横展開の地図と辞書の情報源として扱い、現在のアプリケーションの getshell だけに固執しない。

### コンテナ内の shell：まず「自分がコンテナ内にいるか」を判断し、それからエスケープを決める
**Q1**: shell を取得した後、どう自分がコンテナ内にいるかを判断するか？
**A1**: 特徴を調べる。`/.dockerenv`、cgroup 内の docker/kubepods の文字列、プロセス番号 1 が init ではなくアプリケーションであること、ランダムな hash のようなホスト名、最小限のファイルシステム。コンテナ内にいるかの判断が、以降を「本機の権限昇格」にするか「コンテナエスケープ」にするかを決める。

**Q2**: コンテナ内にいると確認した場合、エスケープ前にまず何を見るか？
**A2**: コンテナの設定面を見る。特権コンテナ（privileged）か、どのホストディレクトリがマウントされているか（`/`、docker.sock、ホストデバイス）、ケーパビリティ（`SYS_ADMIN` など）、docker/k8s API にアクセスできるか。エスケープの機会はほぼすべてこれらの設定ミスから生まれる。

**Q3**: docker.sock のマウント、または特権コンテナを発見した場合、どうエスケープするか？
**A3**: docker.sock → docker API を直接呼び出し、ホストのルートディレクトリをマウントした新しいコンテナを起動してホストのファイルを取得 / 実行する。特権コンテナ → cgroup の release_agent、ホストデバイスのマウントなどの定番のエスケープを通じる。判定基準は「この設定ミスがホストに触れる取っ手を与えているか」である。

**Q4**: コンテナ設定がクリーン（非特権、危険なマウントなし、ケーパビリティ最小）でエスケープできず、行き詰まった場合どうするか？
**A4**: **方向転換**：エスケープが唯一の目標ではない。コンテナ内にはサービスアカウントの token（k8s の serviceaccount）、環境変数内の資格情報、アクセス可能な内部ネットワークのサービスがよくある。これらで**横展開 / k8s API 攻撃**を行えば、現在のホストへのエスケープより価値が高いかもしれない。

**Q5**: k8s の pod 内で、serviceaccount token で何ができるか？
**A5**: token で kube-apiserver を攻める。権限が足りれば特権 pod の作成、secret の読み取り、対象ノードへのスケジュールができ、クラスターレベルの横展開、さらにはエスケープに等しい。判定基準はこの SA の RBAC 権限がどの程度かであり、まず権限を列挙してから行動する。

**Q6**: ホストへエスケープしたが、ホストもクラスタの worker の1つにすぎない場合、どう続けるか？
**A6**: 対象次第である。worker 上には他の pod の secret、kubelet の資格情報、ノードの内部ネットワーク位置がある可能性がある。**方向転換**してホストを新しい踏み台としてクラスタ内の横展開を行い、経路を「単機エスケープ」から「クラスタペネトレーション」へアップグレードする。

### 複数の脆弱性が併存する場合：どれを優先して攻めるか（攻撃面の優先順位付け）
**Q1**: 1つの対象から同時に複数の疑わしい脆弱性（SQLi 1つ、アップロード1つ、古いコンポーネント1つ）がスキャンで見つかった場合、どれを優先して攻めるか？
**A1**: 「シェルまでの距離 × 成功確率 × ノイズ / リスク」で並べる。既知の安定した nday は通常最短経路として優先する。直接 getshell できるもの（アップロード / RCE）は、データを読むだけのもの（SQLi）より優先する。欲張って並列に乱打せず、最短かつ最も安定した1つを選んで先に足場を確保する。

**Q2**: 「シェルまでの距離」をどう素早く見積もるか？
**A2**: 直接のコマンド実行 / ファイル書き込み = 距離最短。インジェクション / LFI は二次のアップグレードが必要 = 中程度。情報漏えい = 最遠（さらに1ホップ接続が必要）。同時に前提条件の充足度を評価する（追加情報や権限が必要か）。距離が近く前提がすべて満たされるものを先に攻める。

**Q3**: 最良の選択肢を数回攻めて成功しない場合、いつ切り替えるべきか、固執せずに？
**A3**: **損切りの線**を設ける。同じ道筋でいくつかの主流の姿勢を試し、かつ自分の姿勢の問題ではなくハードな遮断（パッチ / 強力な WAF / 環境の不備）と特定できたら、次の候補へ切り替える。埋没費用を避け、ある道が「構造的に阻まれている」と検証できたら転換する。

**Q4**: すべての候補の脆弱性が攻められない場合、どこへ転換するか？
**A4**: **方向転換**して偵察と攻撃面の拡大へ戻る。ポート / サブドメイン / 関連サイトを再スキャンし、新しい入口、より細かいフィンガープリント、見落とされた API を探す。たいていは攻撃面が十分に展開されていないのであり、「本当に脆弱性がない」わけではない。web-to-shell が行き詰まったら、情報収集に戻ることで新たな局面を開けることが多い。

**Q5**: ノイズが大きい（アラートを誘発しやすい）が成功率が高い脆弱性がある場合、攻めるか？
**A5**: 行動目標と対抗強度を見る。隠密性 / 長期滞在を追求するなら先に低ノイズの道を試す。純粋にフラグ / 素早い攻略ならノイズを受け入れられる。高ノイズの脆弱性を必ず攻めるなら、「攻めて入ったら即座にノイズ低減 / 移動する」後手を先に用意し、攻めた後にむき出しで留まらない。

**Q6**: 1つ突破した後、他の脆弱性は管理する必要があるか？
**A6**: 価値を保持する。他の脆弱性は**予備入口**（主チャネルが封鎖されたときの再訪先）になり得るし、異なる権限 / 異なるマシンへ通じる可能性もある。足場確保に成功したら、未使用の脆弱性を冗長として記録し、shell を取得したからといって残りの入口を捨てない。

### XXE：それが結局シェルに通じるかを判断する
**Q1**: XXE（XML 外部エンティティインジェクション）を確認した場合、それは直接 getshell できるか、まず何を判断するか？
**A1**: XXE の直接 RCE は条件が厳しいため、まず期待値を正しく置く。パーサーが何をサポートするかを判断する。`file://` でのファイル読み取り、http での内部ネットワーク探索（SSRF）、`php://filter` での PHP ソースコード読み取り、`expect://`（PHP の特定拡張が必要で稀）である。多くの XXE の現実的な価値はファイル読み取り + SSRF であり、直接のシェルではない。

**Q2**: 表示のある XXE の場合、最大化の利用は何か？
**A2**: 機密ファイル（設定 / 鍵 / ソースコード）を読み、読み取った資格情報 / 鍵を別の攻撃チェーンにつなぐ（シリアライズの key を取得してデシリアライズ RCE を攻めるなど）。表示のある XXE = 強力な任意ファイル読み取りであり、価値は「シェルに通じるものを読み出す」ことにある。

**Q3**: ブラインド XXE（表示なし）の場合はどうするか？
**A3**: OOB（帯外）へ転換する。外部 DTD で読み取ったデータを自分のサーバーへ帯外で持ち出す（error-based またはパラメータエンティティによる持ち出し）。ブラインド XXE でもファイルは読めるが、帯外チャネルで取り戻す必要があり、構築がやや複雑である。

**Q4**: パーサーが外部エンティティを無効化している / 各種プロトコルがすべて通らない場合、XXE の線は通らないのか？
**A4**: **方向転換**：XXE を格下げして SSRF として使い（内部ネットワークへのリクエストをまだ送れるなら）内部ネットワークのサービスを攻める。SSRF も封じられているなら、このポイントは無効とし、その API の他の脆弱性仮説（インジェクション / デシリアライズ。XML API のバックエンドにはデシリアライズがよくある）へ戻る。

**Q5**: XXE でファイルを読めるが、何を読めば最もシェルに近いか？
**A5**: 優先して読むもの。アプリケーション設定（DB / 他のシステムの資格情報）、フレームワークの鍵（signing / 暗号化 key）、ソースコード（アップロード / インジェクションポイントを監査で見つける）、SSH / クラウドの資格情報である。目標を明確にする。「さらに RCE または横展開へ進める」ファイルを読み、目的なくシステムファイルを読まない。

**Q6**: XXE で読み取った資格情報 / 鍵を、どうシェルへ接続するか？
**A6**: 振り分ける。DB の資格情報 → データベースに接続してインジェクションの足場確保の流れへ進む。フレームワークの鍵 → 署名偽造 / デシリアライズ RCE の構築。SSH / クラウドの資格情報 → 直接ログイン / クラウド API の呼び出し。XXE の締めくくりは「読み取ったものを、実際に getshell できるチェーンへ供給する」ことである。

### 暗号化系の脆弱性（フレームワークの固定鍵など）：まず key を取得し、それから利用を論じる
**Q1**: 対象フレームワークに「固定 / 漏えいした鍵による制御可能な暗号化データ」の問題（一部のフレームワークの cookie 暗号化、シリアライズ署名など）があると疑う場合、どう着手するか？
**A1**: まずフレームワークと暗号化の特徴（cookie の形式、フィールド構造）を確認し、次に**key がどこから来るか**を判断する。デフォルトのハードコードされた key、ソースコード漏えい内の key、ブルートフォース可能な弱い key である。チェーン全体の敷居は key にあり、key がなければ以降は論じられない。

**Q2**: デフォルト / 弱い key が使われているとどう判断するか？
**A2**: 既知のデフォルト key の辞書で検証する（正しく復号できるか / サーバーに受け入れられるデータを構築できるか）。表示の特徴（復号成功 vs 失敗のレスポンス差異）があればブラインドで検証できる。key が一致すれば利用可能が証明される。

**Q3**: key を取得した場合、どう RCE へ至るか？
**A3**: key で正規の暗号化ペイロードを構築し、サーバーが**デシリアライズ**するデータに埋め込み、利用可能な gadget と組み合わせて RCE をトリガーする。判定基準は、正規の暗号文を構築できる + バックエンドがデシリアライズする + classpath に gadget がある、の3つが揃って初めて通る、である。

**Q4**: key は一致したが利用可能な gadget がない場合（依存関係にチェーンがない）は？
**A4**: **方向転換**：key には依然として価値がある。認証 cookie / token を偽造して身元を偽装し、管理者へ権限外アクセスでログインする。デシリアライズが通らないなら、「正規の暗号化データで身元を偽装する」という gadget を必要としない利用面へ退く。

**Q5**: key の辞書がすべて一致せず、ソースコード漏えいもない場合、行き詰まってどうするか？
**A5**: **方向転換**して key のブルートフォースに時間を費やさない。このアプリケーションの別の攻撃面へ切り替える。固定 key 系の脆弱性は「あれば即座に決まり、なければ固執しない」種類であり、key が取れなければ基本的に脆弱性を変えるべきである。

**Q6**: 攻めて入ったが、新バージョンで修正済み / ランダム key に変更されていると分かった場合、どう素早く判定するか？
**A6**: 構築したペイロードが受け入れられるかを見る。ランダム key では偽造データは一律復号失敗 / 拒否される。ランダム key と確認したら、即座にこの道は通らないと判定して方向転換し、同じペイロードを繰り返し再試行しない。

### 認証バイパス / 権限外アクセス：匿名または低権限から直接 getshell 機能へ到達する
**Q1**: ある機能は getshell できるが管理者が必要で、正面から管理者の資格情報を取得できない場合、どう迂回するか？
**A1**: 認証と認可の隙間を探す。未認可の直接アクセス（管理 API に認証・認可がない）、水平 / 垂直の権限外アクセス（id/role を変更して権限外アクセス）、JWT 偽造（弱い署名 / none アルゴリズム / 漏えいした key）、ロジック迂回（多段フローのステップ飛ばし）。目標は「管理者でログインせずに、その getshell 機能を呼び出せる」ことである。

**Q2**: JWT に問題があると疑う場合、まず何をテストするか？
**A2**: 順にテストする。`alg:none`、弱い鍵のブルートフォース（HS256 の弱い secret）、アルゴリズム混乱（RS256→HS256 で公開鍵を鍵として使う）、kid インジェクション。どれかが成立すれば任意のユーザー / 管理者の token を偽造し、高権限機能へ直接到達できる。

**Q3**: ある管理 API が認証・認可なしで直接呼び出せることを発見した場合、どうシェルへ利用するか？
**A3**: この未認可の API が何をできるかを見る。ファイル書き込み、コマンド実行、設定変更、管理者の作成をトリガーできるか。未認可アクセス + 危険な機能 = 直接 getshell、またはまず管理者を作成してログインし通常の getshell 機能を進む。

**Q4**: すべての認証 / 権限外アクセスの試みが失敗した場合（認証・認可が厳しい）、行き詰まってどこへ転換するか？
**A4**: **方向転換**：「認証の迂回」から「本物の資格情報の取得」へ転換する。SQLi での dump、ソースコード漏えい、資格情報の再利用、フィッシング、session の漏えいである。錠を迂回できなければ鍵を盗みに行く。2つの道（認証・認可の迂回 vs 資格情報の取得）は直交しており、一方が塞がったらもう一方へ切り替える。

**Q5**: ある一般ユーザーの身元を取得したが、getshell 機能に届かない場合は？
**A5**: **垂直の権限外アクセス**で管理者へ昇格する。リクエスト内のロールを変更する、管理エンドポイントへ権限外アクセスする、権限検証がフロントエンドのみにある欠陥を利用する。多くのシステムの認証・認可は UI だけを遮りバックエンドの API を遮っていないため、バックエンドのエンドポイントを直接攻めて試す。

**Q6**: ロジックが複雑で迂回できない場合、この機能ポイントを諦めるべきか？
**A6**: 必ずしも機能ポイントを諦めるのではなく、そこへ到達する経路を変える。同じバックエンドロジックを呼び出せる第2の入口（異なる API、旧バージョンのエンドポイント、内部 API）があるかもしれない。**方向転換**して「同じ getshell 能力へ通じる、防御されていないもう1つの扉」を探す。

### PHP webshell でコマンド実行が制限される場合：disable_functions / open_basedir の迂回
**Q1**: webshell に接続できたが `system/exec` がすべて `disable_functions` で禁止されている場合、まずどう突破口を判断するか？
**A1**: まず環境を列挙する。`phpinfo`/`ini_get` でどの関数が禁止されているか、PHP バージョン、SAPI（fpm/cgi/apache module）、`putenv/mail/imap` などのマイナーな利用可能関数の有無を確認する。迂回手法は PHP バージョンと残存する利用可能関数に強く結びつくため、まず「何が残っているか」を明確に列挙する。

**Q2**: いくつかの関数がまだ禁止されていない場合、どう迂回の道を選ぶか？
**A2**: 残存する関数に応じてチェーンを選ぶ。`LD_PRELOAD`（`putenv` + `mail`/`error_log` のような新プロセスをトリガーできることが必要）、`imap_open`（コマンドインジェクション）、`FFI`（PHP7.4+ で直接 libc を呼ぶ）、`proc_open` の漏れ。判定基準は「どのチェーンが依存する関数が、ちょうど禁止されていないか」である。

**Q3**: 関数がきれいに禁止され、利用可能なものが1つも残っていない場合は？
**A3**: **方向転換**して PHP の低レイヤーの脆弱性による迂回を利用する。特定バージョンの bug（fpm/opcache 関連など）、または `pwnkit` の考え方でファイル書き込みからトリガーする。どれも駄目なら一歩引く。コマンド実行が唯一の目標ではない。webshell 自体がファイルの読み書きができるため、それを**ファイル読み書き + 横展開の情報収集**に使い、「システムコマンドの取得」を「データと資格情報の取得」へ格下げする。

**Q4**: `open_basedir` の制限で対象ファイルを読めない場合は？
**A4**: 定番の迂回へ転換する。`ini_set`/`chdir` の組み合わせ、`glob://`、シンボリックリンク、`realpath` キャッシュなど。PHP 層で迂回できないなら、既に得たコマンド実行（いずれかの disable 迂回が成功していれば）で直接システム層から読む。2つの制限を分けて個別に攻略する。

**Q5**: ようやく迂回してコマンドを実行できたが非常に不安定な場合（偶発的な成功）は？
**A5**: 迂回が競合 / 特定のタイミングに依存していることを示す。**方向転換**：一度でも安定した実行窓があれば、その迂回に依存しないチャネルを即座に落とす。新しい実行可能な入口を書く、スケジュールタスクを追加する、または正常な shell をリバースする。毎回脆い迂回チェーンを辿り直さない。

**Q6**: すべての迂回が失敗した場合、この webshell に価値はないのか？
**A6**: そうではない。制限された webshell でも内部ネットワークの情報源かつファイルのチャネルである。設定を読む、ソースコードをダウンロードしてローカルで監査する、他のサイトを探る。**方向転換**してそれを「ファイルレベルの立足点」として他の攻撃チェーンへ供給する。コマンド実行の制限 ≠ 立足点の無効、である。

### 単機の shell から内部ネットワークの踏み台へ：外向き通信チャネルとプロキシトンネルの意思決定
**Q1**: 境界マシンの shell を取得し、内部ネットワークへ攻める場合、最初の一歩で何を構築するか？
**A1**: まず外向き通信能力を確定する（前の段階で DNS/HTTP/TCP の各プロトコルをテスト済み）。それに基づいてトンネルの形態を選ぶ。原則は、対象が既に許可しているチャネルでプロキシトラフィックを運ぶことである。TCP が出るならバンド / リバースの socks、HTTP しか出ないなら HTTP トンネル、DNS しか出ないなら DNS トンネル。トンネルの選定 = 外向き通信能力の関数である。

**Q2**: 外向き通信ができる場合、直接リバースプロキシ（対象が自分に接続）かバンド（自分が対象に接続）か？
**A2**: 入方向の到達可能性を見る。対象が自分へ能動的に接続できる（外向き通信がある）→ リバース socks が最も手軽。自分が対象のあるポートへ直接触れる（境界にマッピングがある / 同一セグメント）→ バンド。公衆ネットワークから内部ネットワークを攻める場面の多くでは**リバース**を使う。内部ネットワークのマシンが能動的に出る方が、受動的に接続されるより許可されやすいからである。

**Q3**: トンネルを構築した後、どう内部ネットワーク横展開の次のホップを計画するか？
**A3**: socks を通じて内部ネットワークのスキャン / ツールのトラフィックを流し込み、まず内部ネットワークの偵察（稼働、ポート、ドメイン内か）を行い、それから対象を選ぶ。踏み台マシンの価値は「外部ツールを内部ネットワークに接続する」ことであり、先に地図を描いてから動き、トンネル越しにブラインド攻撃しない。

**Q4**: トンネルが頻繁に切れる / 遅延が高くて使えない場合は？
**A4**: 帯域制限 / 検知によるものか、リンク自体が悪いのかを切り分ける。**方向転換**：搬送プロトコルを変える（TCP が不安定なら HTTP/HTTPS over 443 に変える）、多段の踏み台で分散する、またはトンネルへの依存を下げる。重い作業（ブルートフォース、大規模スキャン）を踏み台マシンのローカルで実行し、結果だけを返し、トンネルの負荷を減らす。

**Q5**: 内部ネットワークにセグメント分けがあり、踏み台マシンもごく一部のセグメントにしか触れない場合は？
**A5**: **多段トンネル**を構築する。セグメントを跨ぐ2台目のマシンを制圧して2段目の踏み台とし、一段ずつプロキシチェーンを奥へ延ばす。web-to-shell で取得した最初のマシンは多くの場合外周にすぎず、横展開はチェーン状の踏み台で層ごとに深く進む。

**Q6**: 外向き通信が完全に封鎖されている場合（隔離セグメント）、トンネルは論外か？
**A6**: **方向転換**して非リアルタイムのチャネルへ向かう。web アプリケーション自体を relay として使う（コマンド / 結果を通常の業務リクエストに隠す）、または共有ストレージ / データベース / 内部サービスで間接的に通信する。完全隔離の環境ではリアルタイムの対話 shell を諦め、「非同期の配信 + 非同期の取得」という作業モードに変える。

### 任意ファイル読み取り / ダウンロード：シェルへ通じる重要なファイルを的を絞って読む
**Q1**: 任意ファイル読み取り / ダウンロードの脆弱性（制御可能なパスパラメータ）を取得した場合、どうそれをシェルへ通じる一歩に変えるか？
**A1**: それ自体はシェルを与えないが、シェルへ通じるものを読み出せる。**読み取りリスト**を（優先順位に従って）策定する。アプリケーション設定（DB / 他のシステムの資格情報）、フレームワークの鍵、ソースコード、SSH / クラウドの資格情報、`/etc/passwd`+プロセス情報（環境の探索）。「さらに前進させてくれる」ファイルを目標を明確にして読む。

**Q2**: 対象の絶対パスが分からない場合、どう設定とソースコードを読むか？
**A2**: まずパスを特定できるファイルを読む。ミドルウェア設定（webroot の取得）、`/proc/self/cwd`、`/proc/self/cmdline`、起動スクリプト。アプリケーションの絶対パスを段階的に割り出し、それからその設定 / ソースコードを読む。パスが未知のときは、まず「メタ情報を読んで位置を特定」し、次に「対象ファイルを読む」。

**Q3**: パストラバーサルのフィルタリングがある場合（`../` が遮断または正規化される）は？
**A3**: 迂回へ転換する。エンコード（`%2e` / 二重エンコード / unicode）、`....//`、絶対パス、null バイト（古い環境）、プロトコル wrapper。判定基準は、フィルタリングがブラックリストかホワイトリストかである。ブラックリストにはほぼ常に迂回できる等価な変形がある。

**Q4**: 設定内の資格情報 / 鍵を読めた場合、どうシェルの足場確保へ接続するか？
**A4**: 振り分ける。DB の資格情報 → データベースに接続してインジェクション / UDF で足場確保。フレームワークの鍵 → 署名偽造またはデシリアライズ RCE の構築。SSH / クラウドの資格情報 → 直接ログインまたはクラウド API の呼び出し。任意ファイル読み取りの締めくくりは常に「読み取ったものを、実際に getshell できるチェーンへ接続する」ことである。

**Q5**: 特定の種別 / ディレクトリしか読めず、機密ファイルに届かない場合、行き詰まってどこへ転換するか？
**A5**: **方向転換**：読める範囲内で価値を絞り出す（アプリケーション自身のログ / キャッシュに session/token/平文があるかもしれない）、またはそれを**情報面**として他の脆弱性を補助する（ソースコードの断片を取得してアップロード / インジェクションポイントを監査する）。読み取り範囲が制限されている場合は、「資格情報を直接読む」から「他の脆弱性と組み合わせられる断片を読む」へ転換する。

**Q6**: ファイルは読めるが、対象は実は書き込み / 実行を望んでいる場合、読み取りが行き止まりになったらどうするか？
**A6**: 任意読み取りの上限を正しく認識する。それは「読む」だけである。**方向転換**して、読み取った情報で**書き込みまたは実行**の脆弱性を探す / 構築する（アップロードロジックを読んで迂回を探す、鍵を読んでデシリアライズを攻める）。純粋な読み取りの脆弱性が直接 getshell することを期待しない。その役割は「偵察兵」であり「突撃兵」ではない。

### ストアド XSS/CSRF：管理者セッションを乗っ取って管理画面に入り、さらに getshell する
**Q1**: フロントも管理画面も直接の脆弱性がないが、管理者に届くストアド XSS がある場合、どうシェルまで計画するか？
**A1**: XSS を「管理者の手を借りる」ものとして扱う。経路：XSS がトリガーされたとき、管理者の身元で**管理画面の getshell 機能を呼び出す**（アップロード / テンプレート編集 / コマンド機能）、または cookie/token を盗んで自分で管理画面にログインする。判定基準は、管理画面に、そこまで手間をかける価値のある getshell できる機能ポイントがあるかである。

**Q2**: cookie を盗むのと、XSS で管理者の操作を直接代行するのとでは、どちらが良いか？
**A2**: HttpOnly がある場合 cookie は盗めないため、XSS が管理者のブラウザ内で直接リクエストを送って getshell 動作を完了させる（fetch で管理画面のアップロード API を呼ぶなど）。HttpOnly がなく強力なバインディングもないなら、token を盗んで自分でログインする方が柔軟である。防御を見て姿勢を決める。

**Q3**: CSRF token / SameSite の防御があり、XSS が送るリクエストが拒否される場合は？
**A3**: XSS と CSRF 防御は共存しながら迂回できる。XSS は同一オリジンのコンテキストで、先にページ / API を読んで CSRF token を取得し、それを付けてリクエストを送れる。SameSite も同一オリジンのため遮断しない。判定基準は、XSS が対象と同一オリジンで実行されるかである。そうなら CSRF token はほぼ無意味である。

**Q4**: 管理者による XSS のトリガーを待てない / 打点に誰もアクセスしない場合、行き詰まってどうするか？
**A4**: **方向転換**：XSS は「被害者が引っかかる」ことに依存し、不確実性が高い。より能動的な道（認証バイパス、インジェクションでの資格情報取得）があれば優先する。どうしても XSS を使うなら、トリガーを誘導する方法を考える（ペイロードを管理者が必ず見る位置、チケット / コメント / ログの管理画面などに置く）。受動的なトリガーへの依存を下げる。

**Q5**: 管理画面に入れても getshell 機能がない場合、このチェーンに価値はあるか？
**A5**: 費用対効果を再評価する。管理画面がただのデータで getshell ポイントがないなら、大きな労力をかけて管理者を釣るのは割に合わない。**方向転換**して管理者権限をより価値のあるものの取得（資格情報、他のシステムの入口）に使うか、攻撃面を変える。「管理画面に入る」こと自体のために管理画面に入らない。

**Q6**: 純粋な CSRF（XSS なし）で getshell まで押し進められるか？
**A6**: できるが、より制限される。CSRF は事前に構築したリクエストをブラインドで送るだけである（レスポンスを読めない）。管理画面のある getshell 操作が「1つの固定リクエストで完結する」（固定内容のアップロード、ある機能の有効化など）なら、CSRF でブラインドトリガーできる。レスポンスの読み取り / 多段の対話が必要なら CSRF では足りず、XSS または他の道へ戻る必要がある。

### web の立足点から設定内の資格情報で他のシステムへ横展開する
**Q1**: web で shell を取得し、設定内に多数のデータベース / ミドルウェア / 他のシステムの資格情報を見つけた場合、横展開をどう優先順位付けするか？
**A1**: まず資格情報を分類して並べる。直接接続できるサービス（DB / Redis / ミドルウェア管理コンソール）、再利用できるアカウント（同じパスワードで他のマシンにログイン）、高価値の資格情報（ドメインアカウント、クラウド key、運用の踏み台）。「直接利用可能 × コアへの通じやすさ」で並べ、一撃で決まるものを先に攻める。

**Q2**: データベースの資格情報を取得した場合、データを読む以外にどう権限を拡大するか？
**A2**: 接続して DB 権限を見る。高権限 DB なら UDF/xp_cmdshell で**別の DB サーバー**上に直接 shell を落とせる（web と DB が分離している場合、これが2台目のマシンになる）。DB の資格情報は単なるデータではなく、「別のマシンの shell への入場券」かもしれない。

**Q3**: 資格情報の再利用（同じパスワード）を、ロックアウトさせずにどう系統的に試すか？
**A3**: まず小規模で検証する（その組のパスワードを数台 / 数サービスで試す）。再利用が成立することを確認してから範囲を広げる。アカウントロックとログインアラートに注意し、速度と並列度を制御する。資格情報のスプレーは「先にパターンを検証し、それから慎重に展開する」もので、いきなり全セグメントへブルートフォースして防御を誘発しない。

**Q4**: 資格情報がすべてアプリケーション専用で、他のどのシステムにもログインできない場合、横展開が行き詰まるか？
**A4**: **方向転換**：「資格情報による横展開」から「ネットワークの横展開」へ転換する。現在の立足点を踏み台にして内部ネットワークをスキャンし、未認可のサービス、他の脆弱性のある web、攻撃可能なミドルウェアを探す。この道で資格情報が通らないなら脆弱性の道を行く。2つの横展開の次元は直交して相補的である。

**Q5**: 取得したのがクラウドプラットフォームの AK/SK またはメタデータの資格情報の場合、どう使うか？
**A5**: これは本機の root よりはるかに価値が高いかもしれない。クラウド API を呼び権限を見る。他のインスタンスの列挙 / 進入、OSS / ストレージバケットの読み取り、セキュリティグループの変更、より多くの資格情報の取得ができるか。**方向転換**してクラウドのコントロールプレーンで横展開する。高権限のクラウド key 1組が環境全体の鍵に等しい可能性がある。

**Q6**: 横展開で2台目のマシンを制圧した後、「1台制圧するたびに手掛かりを失う」ことをどう避けるか？
**A6**: 各立足点で「状況判断 + 資格情報 / 設定の調査」を繰り返し、新しい資格情報を資格情報ライブラリに集約して循環利用する（資格情報 → 新しいマシン → 新しい資格情報）。web-to-shell 以降の内部ネットワークへの前進の本質は「資格情報の雪だるま」であり、資格情報と資産のローリングリストを構築して手掛かりを途切れさせない。

### shell 取得後の安定性と永続化：立足点を守る
**Q1**: ようやく web-to-shell に成功した場合、一度の切断 / 再起動で台無しにならないようにするには？
**A1**: まず現在の立足点の脆弱性を評価する。webshell が消されるか、プロセスが再起動するか、接続が安定しているか。それに基づいて永続化の強度を決める。原則：**先に固定化し、それから深く進む**。揮発しやすい入口が1つしかないうちに深い領域へ突っ込まない。

**Q2**: 永続化を何層構築し、どう分散させるか？
**A2**: 冗長に層を分ける。アプリケーション層（webshell / メモリ馬）、システム層（スケジュールタスク / サービス / スタートアップ項目 / バックドアアカウント）、資格情報層（再利用可能な資格情報の取得自体が最も安定した「永続化」である）。層ごとにトリガー方法と存続条件を異ならせ、一網打尽にされないようにする。

**Q3**: 永続化をどう置けば発見されにくく / 消されにくいか？
**A3**: 隠密性は「正常に紛れる」ことから生まれる。通常の業務ファイル / 一般的なシステムの場所に隠し、目立たない名前を使い、トリガー条件を隠す（合図のときだけ応答する）。同時に各バックドアの位置とトリガー方法を記録する。自分は見つけられ、防御側には見つけにくくする。

**Q4**: 永続化の動作自体が EDR / アラートをトリガーするのを懸念する場合はどうするか？
**A4**: 高対抗の環境では**戦略を転換する**。システム層の永続化を少なく、あるいは残さず、「資格情報 + 隠れたメモリ滞在 + いつでも再進入できる入口」に頼る。永続化のノイズは時に価値より大きく、衡量のうえ「軽い永続化 + 素早い再進入」を選び、重いバックドアを落とさないこともできる。

**Q5**: 立足点が突然失われた場合（webshell が削除された / 接続が切れた）、どう素早く復旧するか？
**A5**: 用意しておいた冗長な入口から再進入する。これこそ多層永続化の意味である。すべて失った場合は、**方向転換**して以前取得した資格情報で再ログイン / 再利用するか、最初の入口の脆弱性を再び攻める。だから初期段階では必ず「攻めながら資格情報と予備入口を蓄える」ことである。

**Q6**: 長期滞在と、打ってすぐ撤退、どちらにするかどう判断するか？
**A6**: 対象と対抗を見る。長期制御 / 継続的な横展開が必要なら永続化を重視し、純粋に素早く成果を取るなら取得したら即撤退して露呈を減らす。デフォルトでは「重要な成果を取得したら、より隠密な立足点へ速やかに移る」ことを優先し、初期の web 立足点に長期間目立って留まらない。

### いつ「nday を攻める」から手動の 0day 探索へ転換するか
**Q1**: 既知の nday をすべて試しても攻められない場合（パッチ適用済み / 防御が万全）、0day を掘り続けるべきか、対象を変えるべきか？
**A1**: まず投資対効果を計算する。手動の 0day 探索はコストが高く、期間が長い。判定基準は「この対象がどうしても必要か + ソースコード / ホワイトボックスの条件があるか」である。ソースコードの漏えいがある、またはプログラムをダウンロードして監査できるときに、脆弱性探索の費用対効果が十分になる。純粋なブラックボックスで無理に掘る優先度は非常に低くすべきである。

**Q2**: 掘ると決めた場合、どの種類の脆弱性から着手するのが最も効率的か？
**A2**: その技術スタックで「最も getshell につながりやすい」種類を選んで集中的に監査する。アップロードロジック、デシリアライズポイント、コマンド連結、テンプレート / 式のレンダリング、ファイル操作である。「sink を探して制御可能な入力を逆算する」監査の考え方で臨み、全コードを通読しない。目標は RCE 系の脆弱性であり、任意の脆弱性ではない。

**Q3**: ブラックボックスでソースコードがないがロジックの脆弱性を疑う場合、どう低コストで掘るか？
**A3**: ロジックと設定系（コードを読む必要がない）に集中する。権限外アクセス、認証バイパス、未認可 API、パラメータ改ざんである。このような「ブラックボックスでテスト可能」な脆弱性は、メモリ / インジェクション系の 0day よりはるかに掘りやすい。**まずブラックボックスで検証できるものを掘り、それからホワイトボックスが必要なものを検討する**。

**Q4**: しばらく掘っても進展がない場合、いつ損切りして方向転換するか？
**A4**: 時間 / 試行回数の上限を設ける。上限に達したら**方向転換**して偵察と攻撃面の拡大へ戻る。たいていは攻撃面が十分に展開されていないのであり（サブドメイン / 関連サイト / 他のポート / 他の入口の見落とし）、「この点に本当に掘るべき 0day が待っている」わけではない。web-to-shell が行き詰まったとき、攻撃面の拡大の期待利益は通常、掘り続けることより高い。

**Q5**: 0day の疑いを掘り当てたが利用が不安定 / 条件が厳しい場合、磨き上げる価値はあるか？
**A5**: それが唯一の経路かを見る。他により安定した入口の候補があれば、脆い 0day を磨かない。確かに唯一の突破口なら、まず同じ環境で安定するまで再現してから対象に臨み、一回限りの不安定な利用で相手を警戒させない。

**Q6**: 0day の探索と攻撃面の展開の労力をどう配分するか？
**A6**: デフォルトは**先に広さ、後から深さ**である。まず資産 / 入口を網羅し、すべての nday と設定の脆弱性を一通り篩にかけ、「広さを本当に掘り尽くした」ことを確認してから、深い脆弱性探索に投入する。大多数の web-to-shell は広さ不足で死ぬのであり、深さ不足ではない。

### 式インジェクション（OGNL/SpEL/EL）：テンプレート SSTI と区別した足場確保
**Q1**: テンプレート SSTI ではなく式インジェクション（Java の OGNL/SpEL/EL など）を疑う場合、どう区別し確認するか？
**A1**: コンテキストを見る。式インジェクションは、ページテンプレートのレンダリングではなく、フレームワークのパラメータバインディング、検索 / フィルタ式、ルールエンジン、エラーメッセージによく現れる。対応するエンジンのプローブ（SpEL `#{}`/`T()`、OGNL `%{}`/`@`、EL `${}`）で確認する。エンジンを正しく判定してこそ利用チェーンが正しくなる。

**Q2**: SpEL と確認した場合、どう RCE へ至るか？
**A2**: SpEL では `T(java.lang.Runtime).getRuntime().exec(...)` または `new ProcessBuilder` が使える。核心は `T()` で任意のクラスを参照し静的メソッドを呼ぶことである。判定基準は、式が「評価可能なコンテキスト」で完全に解析されるかである。

**Q3**: OGNL（一部の MVC フレームワークのパラメータによく見られる）の場合は？
**A3**: OGNL は `@java.lang.Runtime@getRuntime().exec()` または context 経由の呼び出しを使う。多くのフレームワークが OGNL のサンドボックス / ブラックリスト（`#` アクセスの禁止、特定クラスの禁止）を加えていることに注意する。判定基準は、フレームワークの式セキュリティ管理を迂回して Runtime にアクセスできるかである。

**Q4**: サンドボックス / ブラックリスト（重要なクラスまたは構文が禁止）があり、式が通らない場合は？
**A4**: 迂回へ転換する。リフレクションによる間接呼び出し（Class.forName で禁止されたクラスを取得する）、コンテキスト変数の変更で制限を解除する（一部のバージョンでは先にサンドボックスを無効化できる）、エンコード / 連結でキーワードを迂回する。**サンドボックスが新バージョンの厳格な実装なら**、**方向転換**する。そのフレームワークのこのバージョンの式インジェクションはほぼ塞がれている可能性があるため、他の脆弱性または他のコンポーネントを攻める。

**Q5**: 式は評価できるが**表示されない**場合（結果が表示されない）は？
**A5**: 表示のない RCE と同じように扱う。まず DNSlog / 遅延で実行を確認し、次に式でコマンド結果をファイルへ書き込む / 帯外で送り返す。式インジェクションが表示のない RCE に至った後、足場確保の手法は通常の RCE と同じであり、式の層で表示にこだわる必要はない。

**Q6**: プローブは反応するが完全な利用チェーンの構築が常に失敗する場合、どう特定するか？
**A6**: 「式が完全に評価されていない」（一部しか解析されない / 切り詰められる / エスケープされる可能性）のか「評価されたがサンドボックスに実行を遮られた」のかを切り分ける。前者は注入位置 / 閉じ方を調整し、後者は迂回または脆弱性の変更へ転換する。**まず評価の深さを確認し、それからペイロードを直すか方向を変えるかを決める**。

### クラウド上の web-to-shell：shell 取得後にクラウドメタデータとクラウド資格情報を攻める
**Q1**: web で攻め込んだのがクラウドホスト（ECS/EC2 系）の場合、shell 取得後、本機の権限昇格以外に何を見るべきか？
**A1**: 真っ先にクラウドメタデータサービス（内部ネットワークの 169.254.x 系アドレス）を探る。インスタンスにバインドされた**一時的なクラウド資格情報**を取得できることが多い。クラウド上では root が不要なことが多く、高権限のクラウド資格情報1組の価値は本機の root をはるかに上回る。まずクラウドの身元を見て、それから本機の権限昇格を論じる。

**Q2**: インスタンスの一時資格情報を取得した場合、どう価値を判断するか？
**A2**: この組の資格情報の権限を列挙する（どのクラウド API を呼べるか）。ストレージバケットの読み取り、他のインスタンスの列挙 / 進入、セキュリティグループの変更、より多くのマシンへのアクセス取得ができれば、横展開、さらには環境の乗っ取りに等しい。判定基準はバインドされたロールの権限範囲である。まず RBAC を把握してから行動を計画する。

**Q3**: SSRF しかない（まだ shell がない）が対象がクラウド上にある場合、直接メタデータに到達できるか？
**A3**: できる。SSRF でクラウドメタデータを攻めるのは定番の組み合わせで、サーバーに代わりにメタデータ API へリクエストさせて資格情報を取得し、getshell を飛ばして直接クラウドの制御権を取る。判定基準は、メタデータサービスが防御しているか（IMDSv2 が特定の header/token を要求するなど）である。

**Q4**: メタデータサービスが強化されている場合（IMDSv2 / token 必須 / アクセス禁止）、この道が断たれたらどうするか？
**A4**: **方向転換**：本機に戻り、クラウド資格情報の他の取得元を探る。設定ファイル内の AK/SK、CI/CD の資格情報、運用スクリプト、環境変数、クラウド CLI のキャッシュ資格情報である。メタデータが封じられていてもクラウド資格情報が存在しないわけではない。ファイルシステム内を探す。それでもなければ通常の本機権限昇格 / 内部ネットワーク横展開へ戻る。

**Q5**: クラウド資格情報を取得したが権限が小さい場合（あるバケットの読み取りのみ）、どう拡大するか？
**A5**: クラウド上の**権限昇格**を探す。assume できる高権限ロール、遷移可能な信頼関係、変更可能なポリシー、他のインスタンス上のより高権限の資格情報である。クラウド環境の横展開はしばしば「低権限資格情報 → 設定ミスを通じて高権限ロールへ連鎖」であり、内部ネットワークの資格情報の雪だるまのようにクラウド IAM の中で転がす。

**Q6**: 従来のホストではなくコンテナ / Serverless の場合、メタデータの手法は依然として適用できるか？
**A6**: 適用できるし、より重要である。コンテナ / 関数は往々にしてバインドされたクラウド身元で動作し、メタデータ / 環境変数内の資格情報が主な戦利品である。**方向転換**してクラウド身元の次元へ向かう。この種の環境では「shell を取る」意義は限定的で、「クラウド資格情報を取る + クラウドのコントロールプレーンを攻める」ことが主線である。

### 資産と入口の発見：web-to-shell の起点における攻撃面の展開
**Q1**: 対象がドメイン1つ / サイト1つしか与えられず、まだ脆弱性を見つけていない場合、最初の一歩で何をするか？
**A1**: 目の前の1ページを急いで攻める前に、まず攻撃面を展開する。系統的に収集する。サブドメイン、関連サイト / C セグメント、ポートサービス、ディレクトリと隠し API、フィンガープリントとバージョン、過去の資産である。web-to-shell の成否の8割は攻撃面を十分に広く展開できるかで決まり、入口が多いほど突破口も多い。

**Q2**: メインサイトがきれいに見える場合（防御が万全）、どう柔らかい標的を探すか？
**A2**: 周辺資産へ転換する。古いサブドメイン、テスト / ステージング環境、バックアップサイト、管理画面、サードパーティコンポーネント、忘れられた API である。コアサイトの強化はファミリー全体の強化を意味しない。周辺資産は長年放置されており、web-to-shell で最も肥沃な入口である。

**Q3**: ディレクトリ / API スキャンで何を検出できれば価値があるか？
**A3**: いくつかの高価値な発見に注目する。アップロードポイント、管理画面ログイン、API ドキュメント / デバッグ API、バックアップファイル、ソースコード漏えい、`.git`、設定ファイル、既知コンポーネントのパスである。スキャンはディレクトリを列挙するためではなく、「シェルまたは資格情報へ通じる」入口を探すためであり、その目標に沿って結果を篩い分ける。

**Q4**: 一通りスキャンしても有用なものが出ず、起点で行き詰まった場合どうするか？
**A4**: **方向転換**して発見の次元を変える。「ディレクトリのブルートフォース」から「フィンガープリント駆動」へ（コンポーネントを識別してから、そのコンポーネントの既知パス / 脆弱性を的を絞って調べる）、「メインドメイン」から「関連資産」へ（証明書、パッシブ DNS、favicon hash で同組織の他のサイトを探す）、「HTTP」から「他のポートサービス」へ。起点で行き詰まるのは往々にして発見手段が単一だからであり、直交する発見方法に切り替える。

**Q5**: 資産が多すぎて攻めきれない場合、どう優先順位を付けるか？
**A5**: 「getshell までの距離」で篩い分ける。アップロード / 管理画面 / 既知の脆弱なコンポーネント / 漏えいのある資産を優先し、純粋な静的表示サイトは後回しにする。均等に力を注がず、「一撃で shell を落とせる可能性が最も高い」少数の入口に精力を集中する。広さを網羅したら、即座に深さの優先順位付けを行う。

**Q6**: 攻撃面は広く展開したが、各入口を浅く試しただけで突破できない場合は？
**A6**: よくあるアンチパターンである。**方向転換**：広さを展開し終えたら深さへ転換する。最も有望な入口を2〜3個選んで深く打ち抜く（1つのアップロードポイントですべての迂回姿勢を試し尽くす、1つのコンポーネントですべての nday と設定の脆弱性を篩い尽くす）。100個の入口をそれぞれ1回ずつ試すのではない。web-to-shell は最終的に「正しい入口を十分に深く打つ」ことで成る。

### ダム shell を完全対話式 tty へアップグレードする：以降の権限昇格を解錠する前提
**Q1**: リバースで shell が返ってきたが、補完がなく、Ctrl-C で直接切断され、`sudo`/`su` が "must be run from a terminal" とエラーを返す。なぜ先にアップグレードする必要があるのか？
**A1**: それは疑似端末のないダム shell で、多くの権限昇格動作（対話式 sudo、ssh、passwd、フルスクリーンプログラム、内部ネットワークツール）が本物の tty を要求する。tty のアップグレードは綺麗好きではなく、以降の操作を解錠する前提条件である。先にアップグレードしてから作業し、端末の欠如による大量の失敗と手戻りを省く。

**Q2**: 標準のアップグレードチェーンは何か？
**A2**: 定番のチェーン：`python -c 'import pty;pty.spawn("/bin/bash")'` で pty を起動 → ローカルで `Ctrl-Z` で中断 → `stty raw -echo; fg` で raw モードに戻す → 対象で `export TERM=xterm` し `stty rows/cols` でウィンドウサイズを揃える。python がなければ `script /dev/null`、`socat` の両端 pty、または `expect` で端末を割り当てる。

**Q3**: 対象が非常に軽量で、python/script/socat がすべてない場合は？
**A3**: **方向転換**：静的コンパイルされた socat/busybox をアップロードして pty を取得する。または現在のチャネルのアップグレードにこだわらず、「対話不要」の方法で重要な動作を完了する（`sudo -S` で stdin からパスワードを渡す、authorized_keys を書いてから直接 `ssh` で入れば自然と本物の tty を得られる）。本物の tty を得る最もクリーンな方法は往々にして「何とか ssh で入る」ことであり、現在のダム shell を無理にアップグレードしない。

**Q4**: アップグレード中に shell がフリーズ / 端末が乱れる / 切断された場合どうするか？
**A4**: 多くは stty パラメータまたは fg の順序の誤りが原因である。まずローカルで `reset` して端末を復旧する。重要な教訓：tty のアップグレードには切断のリスクがあり、操作前に必ず**冗長チャネル**（別の shell または再トリガーできるコールバック）を確保する。入口が1つしかないときにこのような危険な操作をせず、一気に進めて連絡を絶ち、台無しにしない。

**Q5**: 完全対話へアップグレードした後、安定するためにあと何をするか？
**A5**: ウィンドウサイズを揃え（さもないと vim/top が乱れる）、TERM を設定し、job control が使えることを確認する。その後、この苦労して得た安定した shell を即座に「立足点の固定化」（永続化 / 資格情報の取得）に使い、揮発しやすい初期チャネルで素のまま走り続けない。

**Q6**: なぜダム shell でずっと間に合わせないのか？
**A6**: ダム shell は重要な局面でつまずく。対話式の権限昇格が動かない、パスワード入力が表示されない、内部ネットワークの対話ツールが落ちる。かえって全体のペースを遅くする。初期段階で1分かけて tty をアップグレードすることは、以降の各ステップへの投資である。対抗環境でアップグレードのノイズが大きすぎるなら、**方向転換**して直接 ssh / C2 beacon でネイティブな対話を取得し、ダム shell での苦労を飛ばす。
