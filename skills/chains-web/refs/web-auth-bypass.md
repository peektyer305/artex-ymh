# Web · 認証とセッションバイパスの考え方

### ログイン画面を前にまずやること:認証メカニズムの把握であり、急なブルートフォースではない
**Q1**: 対象 X を開くとログイン画面しかなく、手元に認証情報が一切ない。最初の一歩は何か?
**A1**: すぐに辞書ブルートフォースをかけない。まず「認証メカニズムのフィンガープリント」を行う。ログインリクエストがフォーム POST か JSON API か OAuth/SAML リダイレクトかを確認する。返りで自前署名の cookie か JWT か不透明な session id が送られているかを見る。成功フローを一度(仮アカウントでも)キャプチャして、何ステップあるか、フロントエンドの暗号化/署名があるかを確認する。判定基準は、「サーバーが結局何を根拠にあなたを誰と認定するのか」を明確にすることであり、バイパスポイントは常にこの信頼チェーンの最も弱い環にある。
**Q2**: パケットキャプチャすると、パスワードがフロントエンドで JS 暗号化されてから送信されており、ブルートフォースの payload すら組み立てられない。
**A2**: 暗号文の層で正面から戦わない。暗号化関数を JS から取り出してローカルで再現する(通常は CryptoJS/RSA 公開鍵で、公開鍵はフロントエンドにある)。それをブルートフォース前のプリプロセッサにする。あるいはもっと楽な方法として、ブラウザのコンソールで暗号化関数を hook し、こちらが与える平文辞書に対して逐一暗号文を吐かせる。フロントエンド暗号化は受動的な盗聴しか防げず、能動的な攻撃者は防げない。
**Q3**: ログイン成功と失敗で返る HTTP ステータスコードが同じだが、レスポンスボディ/リダイレクトがわずかに違うのを観測した。
**A3**: これが「オラクル」(oracle)だ。差異を定量化する。バイト長、レスポンス時間、Set-Cookie の有無、Location リダイレクト先。安定して「正しいか誤りか」を区別できる信号はどれも、ユーザー名列挙やその後のブールブラインド注入の判定基準に使える。
**Q4**: この画面がそもそも主戦場ではない可能性はないか?
**A4**: その警戒を持つべきだ。ログイン画面が鉄壁でも、同一ドメイン下の登録、パスワードリセット、API ドキュメント(swagger)、旧版モバイル向け API こそが弱点であることが多い。まず認証関連エンドポイントの横展開(/api、/oauth、/reset、/register、/graphql)を一通り行ってから、主攻方向を決める。
**Q5**: 通常のブルートフォース、SQLi、弱いパスワードをすべて試したが、このログイン地点はびくともせず、完全に詰まった。
**A5**: 「直接認証をバイパスする」という次元から退き、直交する次元に転じる。一つは「ログインしなくてもアクセスできる資源」へ転じる。未認可 API、ディレクトリ走査で出るバックアップ/設定を探し、認証情報が平文で眠っているかもしれない。もう一つは「外部入力を信頼する段階」へ転じる。パスワードリセット、メール検証、第三者ログインのコールバックは、往々にしてログイン自体より緩い。認証の壁が高いとき、壁を越えるより脇戸を探すほうがよい。

### 既定/弱いパスワードを試したいが、ロックを誘発しそうで怖い
**Q1**: 対象がオープンソースのシステムかデバイスの管理画面に見える。まず既定の認証情報を試したいが、アカウントがロックされるか不安だ。
**A1**: まずシステムの正体を判定する(favicon hash、ページの著作権表記、特有のパス、エラー傾向)。公式の既定認証情報リストに絞り込む。これは闇雲なブルートフォースより成功率が桁違いに高い動作だ。同時に「犠牲アカウント」でロック方針を探る。何回か連続で誤入力して、ロック/検証コード/遅延が出るかを見て、閾値を掴んでからペースを決める。
**Q2**: 既定のパスワードは変更済みだが、システム種別は間違いなく確認できた。
**A2**: そのシステムの過去の CVE に方向転換する。多くの製品には認証バイパス、ハードコードされたバックドア、未認可 API の公開脆弱性がある。バージョンフィンガープリントを既知の脆弱性に突き合わせるほうが、パスワードを推測し続けるより効率的だ。製品が既知+バージョン確定=優先的に脆弱性データベースを調べる。
**Q3**: バージョンが新しすぎて、使える N-day がない。
**A3**: 弱いパスワードに戻るが戦略を変える。「アカウントブルートフォース」ではなく「パスワードスプレー」を使う。高頻度の弱いパスワードを一つ固定し(季節+年、会社名+123 のような構成規則)、多数のユーザー名に対してそれぞれ一度ずつ試す。これで単一アカウントのロックを自然に回避できる。
**Q4**: 有効なユーザー名リストがなく、スプレーのとっかかりがない。
**A4**: まずユーザー名の入手源という直交問題を解決する。企業メール形式(名.姓@ドメイン)から導出する、LinkedIn/GitHub/文書メタデータから人名を収集する、ログイン/リセット API の列挙差異から逆算する。ユーザー名はスプレーの弾薬であり、弾薬不足なら先に偵察次元で補給する。
**Q5**: サイト全体が厳格なロック+検証コードで統一されており、スプレーも通らない。
**A5**: 「カウンターそのものをバイパスする」方向へ転じる。ロックは往々にしてユーザー名単位か IP 単位で数えられる。IP プールを替える(X-Forwarded-For が信頼されることがある)、大文字小文字変更や空白付与で「別ユーザー名」を作る、ロックにカウントされない予備のログインエンドポイント(モバイル API、Basic 認証 API)を探す。カウンターには境界があり、境界の外は通り道だ。

### ログイン地点に SQL インジェクションによるバイパスを疑う
**Q1**: ログイン箇所に特殊文字を入れると例外や挙動変化が起きる。SQLi で認証をバイパスできるのではと疑う。
**A1**: まず注入が認証クエリ内で起きているかを判定する。ユーザー名/パスワード欄で典型的な論理恒真の閉じとコメントを試し、直接ログイン成功するか、エラーが変わるかを観察する。鍵となる判定基準は「パスワード検証をバイパスできたか、単なるエラーか」であり、前者だけが認証バイパスで、後者は単なる通常の注入だ。
**Q2**: 注入はできるがログインロジックが「hash を取り出して比較」する方式で、恒真では入れない。
**A2**: 発想を変える。UNION やサブクエリで「自分が制御できるパスワードの偽レコード」を一行作り、返る hash が自分の知る平文の hash と一致するようにする。あるいは注入で既知アカウントの行を返すようにする。目的は WHERE を恒真にすることではなく、返る認証情報の内容を自分の知るものにすることだ。
**Q3**: WAF が一般的な注入キーワードをすべて遮断する。
**A3**: 注入次元をまだ捨てず、WAF バイパスを試す。大文字小文字の混在、インラインコメント、エンコード、等価関数、超長 payload。ただし損切りを設ける。WAF バイパスのコストが高すぎるなら「ここは注入できる可能性がある」という情報だけ記録して他へ転じ、後で戻る。
**Q4**: ブラインド注入で、エコーがないことを確認した。
**A4**: ブール/時間ベースのブラインド注入を使うが、認証地点でのブラインド注入は目標を正確に絞る。DB 全体をゆっくりダンプするのではなく、管理者アカウントの認証情報フィールドを優先的に取得するか、直接バイパスを組み立てる。ブラインド注入は遅いため、認証場面では「targeted extraction」であり全量ではない。
**Q5**: データベース層は完全に注入できない(パラメータ化が徹底されている)。SQLi は死んだ。
**A5**: 直交する次元に転じる。認証バイパスは SQLi だけではない。NoSQL インジェクションへ転じる(バックエンドがドキュメント DB なら、オペレータ注入でパスワード検証を恒真にできる)、認証ロジックの脆弱性へ転じる(返り値の改変、ステップ飛ばし)、トークン層へ転じる(JWT/session 偽造)。データベースが注入できなくても、認証ロジックに穴がないとは限らない。

### JWT を入手したら、まず構造を分解してから攻め方を決める
**Q1**: ログイン後にサーバーが JWT を発行する。トークン層で仕掛けたい。最初の一歩は?
**A1**: header と payload を base64 デコードし、3 点を読む。alg は何か(none/HS*/RS*)、payload に身元/ロール/権限フィールドがあるか(role、isAdmin、uid)、kid/jku/x5u のような鍵を指すヘッダがあるか。この 3 点が後の攻撃面を決める。JWT は「答えを内包するトークン」であり、まずどんな情報を晒しているかを見る。
**Q2**: header の alg が HS256 で、payload に role フィールドがある。
**A2**: 2 系統を並行する。一つは alg=none/空署名を試し、サーバーが無署名トークンを受け入れるかを見る。もう一つは署名検証が必須なら、HS256 の鍵が弱いパスワードだと賭けてオフラインで鍵をブルートフォースし、解ければ任意の role のトークンを自由に署名できる。
**Q3**: alg=none は拒否され、鍵もブルートフォースで解けない。
**A3**: RS256(非対称)かを見る。もしそうなら「アルゴリズム混乱」を試す。alg を HS256 に変え、サーバーが公開する RSA 公開鍵を HMAC 鍵として署名する。バックエンドが同じ verify 関数でアルゴリズムを固定していなければ、公開鍵で対称検証してしまいバイパスされる。公開鍵は公開されている。そこが致命的な点だ。
**Q4**: header に kid か jku がある。
**A4**: これは鍵注入面だ。kid が SQL/ファイルパスに連結されるなら、注入やパストラバーサルで自分が制御する鍵を指すようにできる。jku/x5u は鍵 URL を指すので、自分が管理するサーバーに変えて自分の鍵ペアを配布し、自分の公開鍵で自分の署名を検証させる。核心は「サーバーに私が与えた鍵で私が偽造したトークンを検証させる」ことだ。
**Q5**: トークン偽造の試みはすべて厳格に拒否され、署名検証に隙がない。
**A5**: 「トークン偽造」から「トークンの窃取/再利用」という直交次元へ転じる。XSS でトークンを盗む、ログ/URL/referer に漏れたトークンを探す、トークンが長期に失効しないかをリプレイする、トークンが localStorage に書かれて読み取り経路が残っていないかを見る。いくら署名が厳しくても、漏れれば同じように使える。

### セッション cookie が JWT ではない場合、予測可能性と固定を判断する
**Q1**: サーバーが不透明な session id(読めない文字列)を発行し、JWT ではない。どう攻める?
**A1**: まず「予測可能」か「偽造可能」かを判定する。複数の session id サンプルを集め、順次増加か、タイムスタンプ符号化か、弱い乱数かを確認する(エントロピー評価ツールでまとめて回す)。構造に導出可能な規則が潜んでいれば、他者のセッションを予測できる。不透明は安全と等しくない。
**Q2**: session id は高エントロピーの乱数に見え、予測の余地がない。
**A2**: 「セッション固定」(session fixation)に転じる。ログイン前後で session id が変わるかを見る。ログイン後に再発行されなければ、未認証の session id を先に取得して何とか被害者に植え付け、彼がログインすればこの id が認証済みセッションに昇格し、こちらが再利用できる。
**Q3**: ログイン時に id が再発行され、固定も成立しない。
**A3**: セッションライフサイクルの欠陥に転じる。ログアウト後に旧 id が本当に失効するか、パスワード変更後に他のセッションが蹴り出されるか、トークン有効期限が実質無限でないか。「本来失効すべきなのに有効なまま」という窓を探し、既に漏れた旧トークンと組み合わせてリプレイする。
**Q4**: 偽造 cookie を被害者に植えたいが、注入点がない。
**A4**: cookie 属性を確認する。HttpOnly 欠如なら XSS で読み書きでき、Secure 欠如なら平文チャネルで注入でき、SameSite が緩ければクロスサイトでの持ち運びが容易になる。属性の欠陥が、どの投下手段(XSS/中間者/CSRF)でそれを操れるかを決める。
**Q5**: cookie が高エントロピー、属性が揃い、ライフサイクルが厳格で、セッション層は完全に打てない。
**A5**: 直交次元に転じる。セッションを打つのではなく「セッションの背後にある認可」を打つ。多くのシステムはセッションは安全でも API の認証・認可が緩い。リクエスト内の uid/オブジェクト id を直接変えて水平方向の権限外アクセス(IDOR)を行うか、フロントエンドで隠しているだけでバックエンドがロールを検証しない管理 API を呼ぶ。他者のセッションを奪えなければ、自分のセッションで権限外アクセスする。

### パスワードリセットフローは往々にしてログインより緩い
**Q1**: ログインが攻めきれないので、「パスワードを忘れた」に注目した。まず何を見る?
**A1**: リセットフローを最初から最後まで通し、各ステップを記録する。何を入力するか(メール/携帯/ユーザー名)、サーバーが何を送るか(メールリンク/SMS OTP)、リセット認証情報がどんな形か(トークンは URL 内?予測可能?)、リセット API が身元を二重に検証するか。リセットフローの目的は「旧パスワードを知らずに新パスワードを設定する」ことであり、本来パスワードを迂回する正規経路だ。ロジックが緩めば即座に災厄になる。
**Q2**: リセットリンクにトークンが付く。予測可能か偽造可能かを判断したい。
**A2**: 複数のリセットトークンを申請して比較する。タイムスタンプ/連番/ユーザー id に基づく弱い構成か、MD5(メール)のようなオフライン計算可能な値か。公開情報からトークンを導出できれば、任意のユーザーのパスワードをリセットできる。
**Q3**: トークンが強乱数で、導出できない。
**A3**: 「トークン投下の段階」の信頼の脆弱性へ転じる。リセットメールのリンクドメインは Host ヘッダから取られるか?もしそうなら、リクエスト時に Host を自分が制御するドメインに変えれば、被害者が受け取るリンクはこちらのサーバーを指し、彼がクリックした時点でトークンを取得できる。Host ヘッダ注入はリセットリンクの古典的な弱点だ。
**Q4**: リンクのドメインが書き込み固定で、Host ヘッダが効かない。
**A4**: リセット API そのもののロジックへ転じる。新パスワード送信時、リクエストに改ざん可能なユーザー識別子(userid/email)が含まれ、バックエンドがそれだけを信じてトークンと当該ユーザーの一致を検証しないか。自分の正当なトークンと被害者の id を組み合わせて送信し、彼のパスワードを権限外で変更できるかを試す。
**Q5**: リセットフローの各段階が厳格で、リセット経路も塞がれた。
**A5**: 2FA/OTP という直交次元に方向転換するか、「アカウント乗っ取りの他の入口」へ転じる。メール変更フロー、第三者ログイン連携時のアカウント統合ロジック、登録時のメール先取り。パスワードリセットはアカウント乗っ取りの一経路にすぎない。「アカウントの帰属を変え得るすべての操作」へ視野を広げる。

### OTP / 二段階認証のバイパス判断
**Q1**: パスワードは合っているが OTP/SMS 検証コードで詰まった。バイパスをどう探す?
**A1**: まず OTP の弱点面を分類する。検証コードがブルートフォース可能か(桁数少+無制限)、応答が正誤を区別できるか、検証リクエストと「2FA 通過済みか」という状態が分離されているか。判定基準は、2FA は本質的に「2 番目の扉」であり、力ずくで鍵を開けるか、この扉を通らない迂回路を見つけるかだ。
**Q2**: OTP が 6 桁の数字だが、明確なレート制限が見えない。
**A2**: まずブルートフォースを試すが、隠れたレート制限を探る(あるシステムは N 回後に無言で失効させるか新コードに切り替える)。同時に OTP の再利用/固定を試す。同じコードが複数回使えるか、新しいセッションで旧コードがまだ有効か、コードが具体的な操作に紐づいているか。
**Q3**: レート制限があり、ブルートフォースが封じられた。
**A3**: 「状態分離」の脆弱性へ転じる。OTP を検証する API が通ると「検証済み」マークを発行する(cookie フィールド/返りトークン/特定ステップへの遷移)。OTP を飛ばしてその先の保護されたエンドポイントを直接リクエストし、バックエンドがこのマークだけを信じて OTP 通過を再確認しないかを試す。多段フローは「ステップジャンプ」で転ぶのが一番多い。
**Q4**: バックエンドが各ステップを検証し、飛ばせない。
**A4**: レスポンス改ざんに転じる。OTP 検証の返りパケットを遮断し、{"success":false} を true に、ステータスコード 400 を 200 に変え、フロントエンドがこれに従って通過するかを見る。「フロントエンドが返り値で次の手を決める」ファットクライアントに特に効く。
**Q5**: サーバーが権威を持って検証し、レスポンス改ざんも無効、2FA が鉄壁だ。
**A5**: 直交次元へ転じる。2FA をバイパスするより「アカウントに 2FA がそもそも不要になる」か「2FA のない入口から入る」ことを目指す。API/モバイル/旧 API が 2FA を免除していないか、予備の復旧コードフローがより弱くないか、第三者 SSO ログインがローカルの 2FA を迂回しないかを確認する。2 番目の扉が施錠されたら、この扉を設けていない部屋を探す。

### OAuth ログインの redirect_uri と state の面
**Q1**: 対象が OAuth/第三者ログインを使う。このフローで乗っ取り点を探したい。まずどこを見る?
**A1**: 認可リクエストのパラメータ、特に redirect_uri と state を見る。redirect_uri は認可コード/トークンをどこへ返すかを決める。検証が緩ければ(サブドメイン、パス、オープンリダイレクトを許容)、認証情報をこちらのアドレスに劫持できる。state は CSRF 対策で、欠如または未検証ならログイン CSRF を仕掛けられる。まずこの 2 つのパラメータの検証厳格度を把握する。
**Q2**: redirect_uri をまったく別のドメインに変えたら拒否された。
**A2**: 急に諦めず、緩いマッチングの境界を試す。同一登録ドメイン下のオープンリダイレクトエンドポイント、path の追記、@ 記号の構成、サブドメインのワイルドカード、末尾スラッシュ/パラメータの差異。検証は往々にして前方一致か包含一致しか行わない。「見た目は正当だが実際はこちらに返す」URL を組み立てる。
**Q3**: redirect_uri が厳格に固定され、完全一致だ。
**A3**: 認可コード/トークンの他の漏えい経路へ転じる。コードが Referer に出て第三者に漏れるか、クライアント間で再利用できるか(A アプリのコードで B アプリのトークンを交換)、インプリシットフローのトークンが URL フラグメントに残り後続ページに読まれるか。
**Q4**: state パラメータも単独で打つ価値があるか?
**A4**: ある。state が欠如かサーバー未検証なら「ログイン CSRF」を仕掛けられる。被害者にこちらの認可コードで連携を完了させ、彼のセッションをこちらのアカウントにログインさせるか、こちらの第三者身元を彼のアカウントに紐づけ、後でこちらの第三者ログインで彼のアカウントに直接入る。「身元の紐づけ関係を乱す」方向だ。
**Q5**: OAuth の各パラメータ検証が規範的で、このチェーンを突破できない。
**A5**: 直交次元へ転じる。OAuth の背後にある「アカウント統合/紐づけロジック」を攻める。同一メールが第三者で検証済みなのに対しローカル未検証の場合の統合方法、被害者のメールで先にローカルアカウントを登録し、彼が第三者ログインで統合してくるのを待つ手。全体としてローカル認証面に戻すこともできる。OAuth プロトコル自体は成熟しており、穴は実装側のアカウントマッピングロジックに多い。

### SAML / SSO アサーションの署名処理
**Q1**: 企業対象が SAML SSO を使う。アサーション層で身元を偽造したい。切り口は?
**A1**: SAMLResponse のサンプルを一つ入手し、3 点を見る。アサーションが署名されているか、署名の対象範囲(レスポンス全体か assertion のみか)、パーサに XML 署名ラッピング(XSW)の余地があるか。SAML の急所は「署名検証の XML ノード」と「実際に身元を取り出す XML ノード」をずらせるかにある。
**Q2**: アサーションに署名があり、直接 NameID を変えると署名が壊れる。
**A2**: XML 署名ラッピング(XSW)を試す。元の署名済みノードを残して検証を通し、同時に自分が偽造した未署名のアサーションを挿入して業務ロジックに取り出させる。「どのノードを検証するか」と「どのノードを使うか」の不一致を利用する。SAML の最も古典的なバイパスパターンだ。
**Q3**: パーサが XSW 対策をしている。
**A3**: XML 層の他の古い問題へ転じる。XXE(SAML は XML で、パーサが安全でなければファイル読取/SSRF できる)、コメント切断(NameID に XML コメントを入れてパーサが読む値を変える)、署名除去(実装によっては署名欠如時にそのまま通す)。
**Q4**: アサーション全体を偽造して自分で署名したい。
**A4**: それには IdP の秘密鍵が必要で、情報収集の次元で探す。メタデータエンドポイント、設定漏えい、証明書が弱い鍵か公開テスト鍵を使っていないか。秘密鍵が取れなければ偽造署名は空論だ。「鍵探し」か「署名バイパス」に力を注ぎ、「署名を力ずくで計算」しない。
**Q5**: SAML 実装が堅牢で、署名も解析も隙がない。
**A5**: 直交次元へ転じる。SSO の信頼チェーンの末端を攻める。SP と IdP のセッション確立後、SP のローカルセッション管理に前述の一般的な脆弱性がないか。あるいはこの SSO の保護外にあるアプリ入口へ転じる(残存するローカルログイン、サービスアカウント、API トークン)。プロトコルは堅固でも、接続しているアプリ群には必ず落伍者がいる。

### 認証が多段フローなら「ステップジャンプ」を探す
**Q1**: 認証が一段でなく「アカウント入力→パスワード入力→デバイス選択→ホーム」という多段だ。どう利用する?
**A1**: 各ステップのリクエストとそれが運ぶ「進捗認証情報」(隠しフィールド、step パラメータ、一時トークン、cookie 内の state)を記録する。多段フローの脆弱性はほぼすべて「進捗を偽造できるか、後段のステップを直接リクエストして前段の検証を飛ばせるか」にある。まずこの状態機械を描く。
**Q2**: 最終ステップを直接リクエストしたら、最初のステップに戻された。
**A2**: 進捗検証があるということだ。進捗認証情報がどこから来るかを見る。もし最初のステップ(アカウント入力、まだパスワード未検証)で発行されるなら、それを使って後続ステップをリクエストすればパスワードを飛ばせる。「早期に発行される認証情報」を探す。
**Q3**: 進捗認証情報はパスワード検証後に発行される。
**A3**: パラメータ改ざんへ転じる。多段には step=2、stage=verify のようなパラメータがよくあり、直接完了状態に変えてみる。あるいは「2FA が要るか」というブール判定パラメータを true から false に変える。フロントエンド主導のフローは特に脆い。
**Q4**: サーバーが権威を持って状態を保持し、パラメータを変えられない。
**A4**: 競合へ転じる。二つのステップの間に「検査と使用」の時間窓があるとき、並行リクエストで状態機械を想定外の組み合わせに持ち込める(同時送信で検証を飛ばすなど)。多段認証+並行性は見落とされがちな隅だ。
**Q5**: 状態機械が厳密で、競合窓もなく、ステップ飛ばしは完全に失敗した。
**A5**: 直交次元へ転じる。フローが通らないなら、フローが依存する「データ」を攻める。各ステップが信頼するユーザー識別子を権限外で置換できないか(こちらの進捗認証情報に被害者の id を組み合わせる)。「フローをバイパスする」ことを「正当なフロー内で他者の身元に置換する」ことへ変える。

### フロントエンドとバックエンドの認証・認可の不一致
**Q1**: 低権限アカウントでログインできた。権限昇格したい。まず何を疑う?
**A1**: まず「フロントエンドで隠すだけで、バックエンドは検証しない」ことを疑う。フロントエンドはロールに応じてメニュー/ボタンを隠すが、対応する API がサーバー側の権限検査をしていないかもしれない。高権限機能のリクエストサンプルを一つ入手し(JS からエンドポイントを掘る、ドキュメントから掘る)、低権限セッションで直接打って、バックエンドが認めるかを見る。
**Q2**: 高権限 API がどんな形かわからない。
**A2**: フロントエンド JS から静的解析で掘る。すべてのルート、API パス、ロール判定で囲まれた呼び出しがコード内にある。JS に出現するが現在のロールでは呼べないエンドポイントを列挙し、こちらのセッションで逐一試す。フロントエンドコードはバックエンド API の地図だ。
**Q3**: 高権限 API を直接呼ぶと 403 が返る。
**A3**: パラメータ級の権限外アクセスへ転じる。API 自体は開いているが、リクエスト内のフィールドで「誰に/何に操作できるか」を区別している。uid、objectId、role、tenantId などのフィールドを変え(水平権限外アクセス IDOR/垂直権限外アクセス)、他者のデータを操作できるか、より高いロールとして振る舞えるかを見る。
**Q4**: 重要な操作には、こちらが持たない token/署名フィールドがさらに必要な。
**A4**: このフィールドが別の場所から取得できるか、予測可能か、どこかの低権限 API の返りで漏れていないかを見る。多くの「追加検証フィールド」は、実は別のレスポンスで平文で渡されている。
**Q5**: バックエンドの認証・認可がどこも厳しく、権限昇格が完全に詰まった。
**A5**: 直交次元へ転じる。横方向に「同じ権限でもより信頼される入口」を探す。内部/管理サブシステム、運用 API、メッセージキュー/コールバックのような内網信頼が既定のチャネル。あるいはより高い権限の認証情報を取る方向へ戻る(管理者のセッション/パスワードを打つ)。現在のアプリの認証・認可が厳しいなら、攻撃面を替えるのであって同じ壁にぶつかり続けない。

### 登録フローの Mass Assignment による権限昇格
**Q1**: システムが登録を開放している。登録時に自分を管理者にしたい。考え方は?
**A1**: 登録リクエストの JSON/フォームをキャプチャし、どんなフィールドを送っているかを見る。核心の推測は、バックエンドがオブジェクト全体をそのまま DB に束縛していないか(mass assignment)だ。リクエストに role、isAdmin、isVerified、accountType のようなフィールドを追加し、本来ユーザーが制御すべきでない属性を権限外で設定できるかを試す。
**Q2**: バックエンドモデルにどんな制御可能フィールドがあるかわからない。
**A2**: 別の場所からフィールド名を推測する。ユーザー情報 API の返り JSON、API ドキュメント、フロントエンドフォームの隠し項目、エラー情報。返りボディに出るフィールド名は、往々にして注入を試せる属性名そのものだ。
**Q3**: isAdmin を足しても効かない。フィールド名が違うのかもしれない。
**A3**: 命名のバリエーション(is_admin、admin、userType=1、level=99)とネスト構造(role:{name:"admin"})を試す。ORM の束縛粒度と命名規則が正しいキーを決めるので、何組か組み合わせる。
**Q4**: 登録 API が機密フィールドをフィルタリングしている。
**A4**: 他の「オブジェクト更新を受け付ける」エンドポイントへ転じる。プロフィール変更、設定、バッチインポート API は往々にして登録ほどフィルタリングが厳しくない。同じ mass assignment 脆弱性が更新 API では塞がれていないことが多い。
**Q5**: すべての書き込み API がフィールドのホワイトリストをしており、権限昇格フィールドが通らない。
**A5**: 直交次元へ転じる。「自分の権限を上げる」ことから「検証の閾値を下げる」ことへ転じる。登録時にメール検証を飛ばして直接有効化できるか、特権メールドメインを先取りできるか(@内部ドメインをバックエンドが社員と見なすなど)、既定で高権限を付与する境界ロジックを誘発できるか。書き込みがホワイトリストで塞がれたら、ロジックで権限を付与する脇道を探す。

### cookie 内のロール/身元フィールドの改ざん
**Q1**: cookie が純ランダムでなく、一部読める(base64 にユーザー名や role がある)。どうする?
**A1**: 解ける部分をすべてデコードし、身元/権限フィールドと完全性保護の方式を識別する(平文?署名付き?暗号化?)。判定基準は「フィールドを変えたとき、サーバーが気づく手段があるか」だ。まず cookie が改ざん防止に何を頼っているかを確定する。
**Q2**: cookie が「データ+署名」の構造だ。
**A2**: 署名を攻める。HMAC で鍵が弱ければオフラインでブルートフォースできる。署名アルゴリズムがデータから導ける場合(あるフレームワークの既知署名形式)、署名欠如時に通すダウングレードがサーバーにある場合。鍵を割るか署名をバイパスすれば任意に role を変えられる。
**Q3**: cookie 全体が暗号化され、中身が読めない。
**A3**: 暗号の攻撃面へ転じる。ECB モードならブロック並べ替えができ、CBC ならビット反転(padding oracle)で望む平文に変えられる。暗号化に完全性保護がなければ、暗号文の改ざんで有利な平文に変わるかもしれない。暗号化は改ざん防止と等しくない。
**Q4**: 暗号化に完全性保護が付く(AEAD)ので動かせない。
**A4**: 「正当に高権限 cookie を取得する」方向へ転じる。偽造ではなく。高権限ロールを登録/誘導できるか、システムに role の高い cookie を発行させられるか(前述の mass assignment など)。変えられないなら、システムが正当に「良いもの」を発行するよう仕向ける。
**Q5**: cookie が暗号から署名ロジックまで厳格で、改ざん経路がすべて死んだ。
**A5**: 直交次元へ転じる。「自分の身元認証情報を変える」ことを諦め、「自分の正当な認証情報で権限外アクセスする」方向へ転じる。cookie 内の身元は変えられなくても、API のデータオブジェクトへの認証・認可がされていないかもしれない(IDOR)。身元は本物だが、アクセスする対象は他者のものであり得る。

### ロジック脆弱性:レスポンス値がログイン成否を決める
**Q1**: これはファットクライアント/SPA で、ログイン成否をフロントエンドがバックエンド返り値で決めていると疑う。どう検証する?
**A1**: 誤ったパスワードでログインし、レスポンスパケットを遮断する。返り構造に authenticated、success、role、code のようなフィールドがないか観察する。仮説:フロントエンドはこれらの値だけを見て通過するかもしれない。判定基準は、false を true に、一般ユーザーを admin に変えて再送し、フロントエンドがログイン成功と誤認するかだ。
**Q2**: 返り値を変えるとフロントエンドは確かに入れたが、操作すると未認可と出る。
**A2**: これは「フロントエンドの偽ログイン」で、バックエンドは認めていない。この進入はたいていフロントエンドが描画する静的コンテンツしか見えず、価値は限られる。ただし無駄にしない。入った画面は実際の API エンドポイントとデータ構造を晒すので、これを偵察成果として、本当のバックエンド認証・認可を打つ。
**Q3**: フロントエンドに入った後、確かにいくつか実際のデータ API が呼べた。
**A3**: ならばバックエンドの一部の API が認証・認可をしていない(フロントエンドのログイン門が形骸化)。直ちにこれらの API を洗い出し、未認証リクエストで直接打ち、どれが本当にデータ取得/操作できるかを確認する。偽ログインの価値は、裸のバックエンドを探し当ててくれる点にある。
**Q4**: バックエンド API は本物の token を要求し、偽ログインでは取得できない。
**A4**: 「返り値改ざん」を他の段階へ転じる。2FA 検証、権限判定、決済/承認のような、同じくバックエンド返りのブール値に依存するフロー。どこに「フロントエンドがバックエンド返りで通過を決める」箇所があれば、そこにこの手を再利用する。
**Q5**: サイト全体が権威あるバックエンド検証で、レスポンス改ざんがまったく効かない。
**A5**: 直交次元へ転じる。これは厚いバックエンドのアプリだと認め、「フロントエンドを騙す」ことから「本当の認証情報取得と注入の脆弱性」(SQLi、SSTI、デシリアライズ、トークン偽造)へ注意を移す。レスポンス改ざんはクライアントを信頼するアーキテクチャにしか効かない。厚いバックエンドなら攻め方一式を替える。

### GraphQL エンドポイントの認証バイパス
**Q1**: 対象に GraphQL エンドポイントがある。認証面で何を掘れる?
**A1**: まず introspection で schema を把握する(開いていれば)。重点は、どの query/mutation が認証・認可ディレクティブで保護されていないか、ユーザー/認証情報を直接晒すフィールドがないか、REST 層の認証・認可を迂回する「バックドア」操作がないか。GraphQL は REST で隠していた能力を平らに晒すことが多い。
**Q2**: introspection が閉じられていて、schema が見えない。
**A2**: フィールドブルートフォース/推測に転じる。一般的な命名辞書で query 名を推測し、エラー情報("did you mean...")からフィールドを逆算し、フロントエンド JS の GraphQL ドキュメントから実際のクエリを掘る。schema が隠されても API が消えたわけではない。
**Q3**: 機密 mutation を見つけたが認証が必要だ。
**A3**: 認証・認可の不一致を試す。同じ schema 内で、@auth ディレクティブがあるフィールドと漏れているフィールドがある。バッチクエリ(aliases)で最初の一つしか検証しないか、ネストしたクエリが認可済みの親オブジェクトを借りて未認可の子フィールドを取得できるか。GraphQL の認証・認可の漏れは「粒度の不揃い」に多い。
**Q4**: ログインをブルートフォースしたいが、GraphQL でどう攻撃を増幅する?
**A4**: エイリアス(aliases)で単一リクエストに数百〜数千回の login 呼び出しを詰め、1 つの HTTP リクエストで大量のブルートフォースを行い、リクエスト数ベースのレート制限を自然に迂回する。GraphQL 特有のブルートフォース増幅だ。
**Q5**: 認証・認可が整い、レート制限も操作数で計算され、GraphQL では突破できない。
**A5**: 直交次元へ転じる。GraphQL の背後は同じデータ層だ。それが持ち込み得る注入(パラメータが SQL/NoSQL に連結される)、IDOR(node(id:)で id から任意オブジェクトを直接取得)、バッチクエリによる DoS で他の攻撃を補助する。プロトコルを迂回できなければ、それが晒すデータアクセスロジックを打つ。

### Basic/Digest と API Key のような「単純認証」
**Q1**: 対象の API が HTTP Basic か API Key で認証する。どう攻める?
**A1**: まず認証情報が漏れる可能性のある場所を特定する。Basic/API Key は「静的共有秘密」で、最大の弱点は漏えいであって解読ではない。フロントエンド JS、モバイルの逆コンパイル、Git 履歴、公開コードリポジトリ、Swagger の例、Wayback アーカイブを漁る。判定基準は「この静的秘密がどこかで平文で書き込まれていないか」だ。
**Q2**: 漏えいが見つからず、Basic 認証をブルートフォースしたい。
**A2**: Basic は base64(user:pass)なので、オフラインで辞書を組み立ててブルートフォースできるが、まずレート制限とロックを探る。また Basic は機械対機械で使われがちで、アカウントは service/admin のような固定名かもしれないので、弱いパスワードのスプレーと組み合わせる。
**Q3**: API Key が割れず、漏れもない。
**A3**: 「Key の認可境界」へ転じる。低権限の API Key が高権限エンドポイントを呼べるか(バックエンドが key の有効性だけを検証し権限を検証しない)、key が環境をまたいで再利用できるか(テスト key が本番を打てる)、key が URL 内にあってログ/referer に記録されないか。key が有効でも境界が緩ければ権限外アクセスできる。
**Q4**: API が各 key に厳格な権限束縛をしている。
**A4**: 「より高権限の key を取得する」方向へ転じる。管理パネル、CI/CD 設定、コンテナ環境変数、内部サービス間呼び出しで流れる key。多くの高権限 key は設定やログに眠っており、解読不要だ。
**Q5**: 静的な認証情報がどこも厳しく、取得も解読もできない。
**A5**: 直交次元へ転じる。認証情報そのものを諦め、プロトコル/トランスポート層へ転じる。Basic が平文 HTTP なら中間者で傍受できる。SSRF があれば内網視点から、内網のみを信頼する認証不要 API にアクセスできる。静的秘密が取れないなら、何とか「信頼される位置」に立つことを目指す。

### セッションログアウト/失効ロジックの欠陥
**Q1**: 失効したかログアウトされた疑いのある token を手に入れた。まだ使えるか?
**A1**: まず「失効が本当に失効か」を検証する価値がある。多くのシステムはログアウトでクライアントの cookie を消すだけで、サーバーの session は破棄しない。あるいはパスワード変更後も旧 token が有効だ。この token で保護リクエストをリプレイし、まだ通るかを見る。判定基準は、サーバーが本当に token の失効状態を保持しているかだ。
**Q2**: token が確かにまだ使えるが、権限範囲が不明だ。
**A2**: この token がアクセスできるエンドポイントの境界を段階的に探り、対応するロールと有効期限を確認する。「本来失効すべきなのに生きている」高権限 token は黄金だ。優先的にアクセスを固定する(早急にそれでより持続的な足場を取る)。
**Q3**: token が JWT で、サーバーがそもそも能動的に失効させられない。
**A3**: これはステートレス JWT の固有の弱点だ。一度発行すれば、失効まで無効化できない。失効時間が非常に長く設定されていれば、漏れた token はどれも長期有効な鍵になる。「漏れた JWT を一つでも取得する」ことに攻撃の重点を置く。取れれば即長期利用できる。
**Q4**: token の有効期限が非常に短く、窓が狭すぎる。
**A4**: リフレッシュトークン(refresh token)に転じる。ライフサイクルが長く、更新の鍵だ。refresh token が漏れている、予測可能、交換ロジックに欠陥がある(ローテーション不徹底、再利用可能)なら、新しいアクセストークンを継続的に交換できる。短い窓では refresh token こそ本当の目標だ。
**Q5**: セッション失効、失効、リフレッシュのロジックがどれも厳格だ。
**A5**: 直交次元へ転じる。「セッションの持続性」を打たず、「セッション再取得の容易さ」へ転じる。「ログインを保持」の長期 cookie があるか、前述の乗っ取りフローで随時再ログインできるか、ログイン不要の API 認証情報があるか。セッションが厳格なら、何度でも入り直せる安定したチャネルを探す。

### 検証コード/人機チャレンジが自動化を阻む
**Q1**: ブルートフォース/列挙の経路が検証コードで塞がれた。どう続ける?
**A1**: まず検証コードが「本当に効いているか」を判定する。検証コードがフロントエンドで描画されるだけで、バックエンドが検証しないか、検証が迂回可能なことがある(空値、前回通過値の再利用、固定の万能コード)。まず送信時に captcha フィールドを空/でたらめにして、バックエンドが認めるかを見る。判定基準は、この人機チャレンジが単なる見せかけではないかだ。
**Q2**: バックエンドが確かに検証コードを検証する。
**A2**: 「検証コードの再利用」を試す。一度通過した captcha token が複数リクエストで再利用できるか、ページを更新してもコードが変わらないか。コードが単一リクエストに紐づかなければ、通過済みコードを一つ取って連打すればレート制限を迂回できる。
**Q3**: コードが毎回変わり、単一リクエストに紐づく。
**A3**: 発火条件へ転じる。検証コードは失敗 N 回後にのみ出現するか?もしそうなら、ペースを閾値以下に落として「低頻度スプレー」を行い、検証コードを一切発火させない。検証コードを迂回するより「それを起こさない」ほうが良いことがある。
**Q4**: 検証コードを直接認識したい。
**A4**: 単純な図形/数字コードは OCR かコード代行サービスで通せるが、費用対効果を評価する。弱いパスワードがあるか不明なログイン地点のために認識パイプラインを組むのは割に合わないかもしれない。損切りを設け、まず背後に本当に割れるものがあるかを確認してから投入する。
**Q5**: 検証コードが強く、レート制限も厳しく、自動化経路がすべて塞がった。
**A5**: 直交次元へ転じる。「大量に推測する」ことを諦め、「正確な単点」へ転じる。OSINT で得た本物の認証情報/漏えい DB で一度だけの認証情報スタッフィング(credential stuffing、量が少なく防御を発火させない)、あるいは検証コード保護のない API(API、モバイル、リセットフロー)へ転じる。人機チャレンジが防ぐのは大量の自動化であり、正確な少数の試行は防げない。

### 認証情報スタッフィング:漏えいしたアカウントとパスワードを手にしている
**Q1**: 公開漏えいデータから「メール:パスワード」を入手した。この対象にどう使うのが最も効率的か?
**A1**: ブルートフォースではなく認証情報スタッフィング(credential stuffing)を行う。実在するアカウントとパスワードの組み合わせで一対一に試す。成功率が桁違いに高く、単一アカウントロックも発火しない。まず小ロット・低速で試し、対象が漏えい認証情報を再利用しているかを検証する。判定基準は命中率で、一度でも命中すればユーザーがここでパスワードを再利用している証拠だ。
**Q2**: 直接本番ログイン地点を打つと風控を発火させそうで怖い。
**A2**: まず風控の形を探る。デバイスフィンガープリント、IP 評判、行動分析のどれも遮断し得る。少量サンプル、分散 IP、正常なリズムを模して境界を探るか、風控が弱い入口(旧版 API、モバイル、提携先 API)を優先的に打つ。
**Q3**: 命中したがアカウントが 2FA を開いている。
**A3**: パスワードが正しく+2FA が塞ぐなら、前述の 2FA バイパス次元へ転じる。迂回できなくても、この認証情報には価値がある。パスワードが正しいことを証明しており、同じパスワードを再利用する他のシステムで使える(対象の他のアセットへ横展開)。
**Q4**: 漏えい DB のパスワードがすべて期限切れ/命中率ゼロだ。
**A4**: 「パスワード変種の推測」へ転じる。ユーザーのパスワード変更には規則がある(旧パスワード+連番/年)。漏えい旧パスワードから変種の小辞書を作り、targeted なスプレーを行う。人はパスワードを記憶する慣性があり、それは利用できる。
**Q5**: 認証情報スタッフィングがまったく当たらず、風控に IP を封じられた。
**A5**: 直交次元へ転じる。「ユーザーのパスワードを推測する」ことから「パスワード機構そのものを迂回する」ことへ。SQLi/ロジックバイパス/トークン偽造という正しいパスワードに依存しない経路に戻る。あるいは「フィッシング/ソーシャルエンジニアリング」でリアルタイムの認証情報を取得する(認可の範囲内で)。認証情報スタッフィングは確率のゲームなので、当たらなければ確定的な技術バイパスへ替える。

### 競合条件で認証/認可を打つ
**Q1**: 通常の認証攻撃を一通り試した。競合条件が使えないか見たい。どの点が試す価値がある?
**A1**: 「検査と使用の間に時間窓がある」操作を探す。レート制限のカウント、特典/枠の一度きりの検証、アカウント有効化、2FA の試行回数、トークンの一度きり使用。高並行で複数リクエストを同時に送り、状態判定が更新前に複数回通らないかを見る。判定基準は「同一資源の検証が原子的か」だ。
**Q2**: OTP/ブルートフォースのレート制限に競合があると疑う。
**A2**: レート制限のカウンタが増える前に並行で一括リクエストを送る(単パケット複数リクエスト/並列接続)。カウンタが反応する前に多く試せて、レート制限を変則的に突破できる。レート制限が原子的増加でなければ、超過発行の窓がある。
**Q3**: 並行で効果が出ない。窓が狭すぎるのかもしれない。
**A3**: 同期送信の技術でリクエストを同一瞬間に押し込む(HTTP/2 単一接続複数ストリーム、または先にヘッダを送り最後の 1 バイトを残して同時に解放)。同一時間窓に落ちるリクエスト数を最大化する。競合の成功率は同期精度に極めて敏感だ。
**Q4**: 競合は確かに存在するが安定して再現できない。
**A4**: サンプル量を増やし複数ラウンド試し、成功率を記録するのであって毎回の成功を求めない。認証バイパスでは、たまの一度の成功(高権限アカウントの重複作成、検証の一度の多重通過)で足場ができるかもしれない。不安定な競合にも価値はある。
**Q5**: 対象の各所の検証が原子的/ロック済みで、競合の窓がない。
**A5**: 直交次元へ転じる。競合は「時間」次元の攻撃だ。打てなければ「ロジック/注入/トークン」という「内容」次元に戻る。あるいは競合の考え方を純粋な認証でなくビジネスロジックに水平展開する(認証後の一度きり操作など)。戦場を替えるのであって技術を替えるのではない。

### CSRF で認証済み状態の操作を奪う
**Q1**: アカウントに入れないが、ログイン済みの被害者に代わって操作を実行させたい。切り口は?
**A1**: 「アカウントの帰属/認証情報を変える」状態変更リクエストを探す。メール変更、パスワード変更、第三者連携、信頼デバイス追加。CSRF 対策(token/SameSite/カスタムヘッダ)があるかを判断する。なければ、被害者に誘発させれば代わりに重要属性を変えられ、間接的に乗っ取れる。判定基準は「この高危険操作をクロスサイトで発火できるか」だ。
**Q2**: 重要な操作に CSRF token が付く。
**A2**: token が本当に検証されるかを見る。省略できる、空にできる、他者の token を使える、ユーザーに紐づかないか。多くの CSRF token は形だけで、バックエンドが帰属を厳格に検証していない。
**Q3**: token 検証は厳格だが、ログイン自体に保護がない。
**A3**: 「ログイン CSRF」へ転じる。被害者にこちらのアカウントへログインさせる(こちらの認証情報で発火)。彼が「こちらのアカウント」で入力した機密情報(カード番号、アップロード文書)がこちらに落ちる。方向を逆にする。彼のセッションを取るのではなく、彼をこちらのセッションに入れる。
**Q4**: 他の脆弱性と組み合わせて CSRF を増幅したい。
**A4**: CSRF+それ自体:CSRF で被害者のメールを変え、パスワードリセットで完全乗っ取りを完成する。または CSRF で保存型 XSS の書き込みを発火する。単独の CSRF は価値が限られるが、連鎖させれば乗っ取りチェーンになる。
**Q5**: SameSite が厳格で、すべての状態操作が CSRF 対策済みだ。
**A5**: 直交次元へ転じる。「クロスサイト誘導」から「同サイト実行」へ転じる。対象に XSS があれば、同一オリジンのスクリプトが token を読め、認証情報付きで直接リクエストを送れるため、CSRF 対策を完全に迂回できる。CSRF が打てないとき、一つの XSS がすべての CSRF 対策を無効化する。

### パスワードポリシーとアカウント有効化のロジックの穴
**Q1**: 登録/パスワード変更フローで、mass assignment 以外にどんなロジックの穴を見る価値がある?
**A1**: 「状態遷移」の完全性を見る。登録後アカウントは有効化待ちか直接使えるか、有効化 token をどう検証するか、パスワード変更で旧パスワードを検証するか、パスワードポリシーを迂回できるか(空パスワード、極端に短い、ユーザー名と同一)。判定基準は、「本来必須の検証を飛ばせる」経路があるかだ。
**Q2**: アカウントはメール有効化が必要で、有効化メールが届かない。
**A2**: 有効化が本当に必須かを見る。未有効化アカウントで直接ログインして塞がれるか、有効化 token が予測可能/自作可能か、自助有効化できる API があるか。あるシステムの有効化は形だけで、ログインは有効化状態を強制検証しない。
**Q3**: パスワード変更 API が旧パスワードを要求し、こちらは持っていない。
**A3**: 旧パスワード検証を迂回できるかを見る。フィールドを空にすると「スキップ」扱いにならないか、旧パスワードフィールドがバックエンドでそもそも読まれていないか、リセットフローで旧パスワード検証を迂回して直接新パスワードを設定できないか。「旧パスワード必須」はフロントエンドの要求にすぎないことが多い。
**Q4**: 一括登録/乱用したいが、メールの一意性制限がある。
**A4**: メール正規化の脆弱性へ転じる。大文字小文字、プラスエイリアス(user+x@)、ドット、Unicode 同形文字が「別メール」として登録されつつ同じ実メールに配信されるか、逆に一意性を迂回して特権メールを先取りできるか。正規化の不一致=身元境界の曖昧化だ。
**Q5**: すべての状態遷移が厳格に検証され、ロジックの穴が掘れない。
**A5**: 直交次元へ転じる。「登録/パスワード変更ロジック」から「それが依存する下層の能力」へ。メール送信箇所の宛先が制御可能なら SSRF/フィッシング、テンプレート箇所が注入可能なら SSTI。ロジックが隙なく噛み合っているとき、それが呼ぶ危険な機能に注目する。

### ある API が「そもそも認証不要か」の判断
**Q1**: 攻撃面を整理していて、まったく認証・認可のない API を素早く見つけたい。方法は?
**A1**: 認証が必要とわかっている機能のリクエストを一つ取り、認証情報(cookie/token/header)を全部外して送り、返りを見る。各エンドポイント種別にこの「認証情報除去リプレイ」を体系的に行う。判定基準は単純で、認証を外してもデータ取得/操作できるものは未認可 API だ。この種の穴は報酬が最も高く、最初にスキャンすべきだ。
**Q2**: 大半の API は認証情報除去で 401 を返すが、少数はデータを返した。
**A2**: 直ちにその少数を深掘りする。開発で取り残された内部 API、デバッグエンドポイント、「フロントエンドが直接呼ばないので誰も認証・認可を付けなかった」バックグラウンド API かもしれない。それがアクセスできるデータ面を辿って拡大し、ユーザーリスト/認証情報/設定を取得できることが多い。
**Q3**: 認証必須 API はよく遮断されるが、隠しエンドポイントがあると疑う。
**A3**: エンドポイント発見へ転じる。JS/モバイル/ドキュメント/履歴アーカイブから未公開パスを掘る。異なるバージョン接頭辞(/v1 /v2 /internal /admin)、異なる HTTP メソッド(GET が塞がれば POST/PUT)、末尾迂回(.json、パスの大文字小文字、スラッシュの二重書き)を試す。隠れたものこそ認証・認可がないことが多い。
**Q4**: ある API は既知パスに認証・認可するが、メソッド/大文字小文字を変えると迂回できた。
**A4**: これは認証・認可ミドルウェアのパスマッチング欠陥だ。マッチングルールと実際のルート解析が一致しない(大文字小文字、エンコード、末尾スラッシュ、HTTP メソッドのホワイトリスト)。これらの変種を体系的に fuzz し、「認証・認可層と業務層が同一 URL を別様に理解する」隙間を狙う。
**Q5**: サイト全体の API 認証・認可が隙なく、漏れたエンドポイントがない。
**A5**: 直交次元へ転じる。「未認可アクセス」が通らないと認め、「正当な認証情報の取得」か「権限外アクセス」へ戻る。最低権限の正当なアカウントで API ごとに境界を探る(IDOR/垂直権限外アクセス)。裸の API がないなら、本物の身元で権限外アクセスするのであって、無身元の入口を探すのではない。

### トークン漏えいの受動的収集(ログインを打たずに鍵を拾う)
**Q1**: ログインを猛攻するより、まず「拾える token がないか」を見たい。どこで拾う?
**A1**: 漏えい面を体系的に収集する。フロントエンド JS にハードコードされた key/token、Git リポジトリ履歴、CI ログ、エラーページのスタック情報、Wayback/公開キャッシュ、公開 S3/ストレージバケット、モバイル APK の逆コンパイル。判定基準は「長期認証情報が外部から読める場所に書かれている箇所がどこか一つでもあるか」だ。鍵を拾うのは常に錠前をこじるより速い。
**Q2**: JS に token/key らしきものを見つけたが、権限があるか不明だ。
**A2**: まず種別と範囲を判定する。フロントエンドの公開 key(一部 SDK の公開可能 key)か、本来晒してはならないサーバー秘密鍵か。それで対応サービスの API を呼んで境界を探り、何を読める/書けるかを確認する。「設計上公開されているもの」と「誤って晒されたもの」を区別する。
**Q3**: 見つけた token が失効済み/無効に見える。
**A3**: 傍証価値へ転じる。失効していても、token 形式、発行元、フィールド構造、鍵 id(kid)などを晒しており、偽造/認証体系の理解のための情報になる。失効済みサンプルもトークン機構を分析する素材だ。
**Q4**: 漏えい収集を自動化したいがノイズが大きすぎる。
**A4**: 高シグナルの情報源に絞る。フロントエンドのメイン JS bundle、設定系ファイル(.env、config.js)、鍵が保存されがちな既知パスを優先する。一般的な token 形(JWT の三段構成、一般的な key 接頭辞)にマッチする正規表現を設ける。正確さは広く撒くより有効だ。
**Q5**: すべての漏えい面を漁ったが、使える認証情報が一つも拾えない。
**A5**: 直交次元へ転じる。受動的収集が空振りなら、能動的な技術バイパス(前述の SQLi/トークン偽造/ロジック脆弱性)へ転じる。あるいはアセット範囲を広げる。同一組織の他のサブドメイン/システムが、横展開で再利用できる認証情報を漏らしているかもしれない。この対象が綺麗でも、兄弟システムも綺麗とは限らない。

### マルチテナントシステムでのテナント越境
**Q1**: 対象がマルチテナント SaaS で、A テナントのアカウントを持つ。B テナントへ越えたい。切り口は?
**A1**: まずテナント隔離が何で実現されているかを把握する。リクエスト内の tenantId/orgId フィールド、サブドメイン、トークン内のテナント claim。判定基準は、「サーバーがデータ照会時に、テナント境界をこちらの制御可能な入力から取るか、改ざん不能なセッションコンテキストから取るか」だ。前者なら越境の口になる。
**Q2**: リクエストに明らかな tenantId パラメータがある。
**A2**: 直接 B テナントの id に変えて再送し、B のデータを読めるかを見る。成功すれば水平権限外アクセスでテナント越境だ。tenantId が URL、body、header の複数箇所に出るなら、一箇所だけ変えればよいかに注意する(バックエンドが信頼すべきでない箇所を信頼しているかもしれない)。
**Q3**: tenantId がトークンから取られ、変えられない。
**A3**: オブジェクト id の越境へ転じる。テナント claim が固定でも、objectId で資源を直接照会する際に「そのオブジェクトが自分のテナントに属するか」を検証していなければ、objectId を B テナントの資源 id に変えても越境できる(IDOR によるテナント越境)。隔離は「リスト API」ではされて「詳細 API」で漏れがちだ。
**Q4**: 他テナントの資源 id を列挙したい。
**A4**: id が予測可能か(連番/短い乱数)、公開箇所(共有リンク、メール、エクスポートファイル)から実際の id を集める。予測可能なオブジェクト id があれば、テナント越境は「できるか」から「一括収穫」になる。
**Q5**: テナント隔離が各層で厳格に検証され、越境できない。
**A5**: 直交次元へ転じる。「データ越境」から「制御面越境」へ。共有の管理 API、テナント横断の検索/レポート、プラットフォーム級の super-admin 機能、テナント間で共有されるキャッシュ/キュー。あるいはテナント自身のユーザーを攻める(このテナント内で権限昇格)。テナントの壁が堅いとき、壁の共通の扉を探すか、自分の敷地内での権限昇格に戻る。

### 認証の背後にある第三者/内部サービスの信頼
**Q1**: アプリが認証を内部/第三者サービスに委任している。この信頼を利用したい。どう見る?
**A1**: 信頼チェーンを描く。フロントエンド→ゲートウェイ→認証サービス→業務サービス。「あるホップが前のホップは既に認証済みと仮定して自分は検証しない」箇所を探す。判定基準は、業務サービスが特定の header(X-User-Id、X-Authenticated-User など)を直接信頼し、その header を外部から注入できるかだ。
**Q2**: 業務サービスが身元 header を信頼していると疑う。
**A2**: 外部リクエストに直接この種の header(X-User-Id、X-Forwarded-User、X-Auth-Request-User などの一般的な形)を付けて試す。ゲートウェイが本来剥がす/上書きすべきなのにしていなければ、業務層がこちらの偽装身元を真に受ける。ゲートウェイ認証・認可アーキテクチャの古典的な亀裂だ。
**Q3**: ゲートウェイがこれらの header を剥がし、注入が無効だ。
**A3**: 「ゲートウェイを迂回してバックエンドへ直結」に転じる。業務サービスにゲートウェイを経由しない直接到達アドレス(内部ポート、デバッグポート、迂回ドメイン)はないか。バックエンドへ直結すれば、ゲートウェイの剥がしも認証・認可も飛ばされ、偽装 header が再び効く。表門を通らない道を探す。
**Q4**: バックエンドへ直結できない。
**A4**: SSRF を借りる。アプリ内に SSRF があれば、「信頼されるサーバーの視点」からこれらの内部認証不要/内網信頼 API をリクエストでき、信頼境界の内側に立つのと同等だ。SSRF は外部攻撃者を内網の信頼区域へ運ぶ橋だ。
**Q5**: 信頼チェーンの各ホップが独立検証し、迂回路も SSRF もない。
**A5**: 直交次元へ転じる。アーキテクチャ層の信頼バイパスが通らないなら、アプリ層の通常の認証/認可脆弱性(トークン、ロジック、注入)へ戻る。あるいはチェーン内で最も弱いサービスそのものへ転じる(ある内部サービスに独立した N-day があるかもしれない)。信頼チェーンが厳密なら、それを構成する薄弱なノードを打つ。

### パスワードリセットの答え/秘密の質問のような弱い二次検証
**Q1**: リセットフローが「秘密の質問」や個人情報で二次検証する。どう打つ?
**A1**: まずこれらの検証項目の「取得可能性」を評価する。秘密の質問(母の旧姓、出生地、ペットの名前)、身分証/社員番号の断片などは、大半が OSINT で調べられるか列挙可能な弱い秘密だ。判定基準は、「本人しか知らない」この情報が、実は公開で調べられるか、答えの空間が小さいかだ。
**Q2**: 秘密の質問の答えがわからない。
**A2**: 2 系統に分ける。一つは OSINT(ソーシャルプラットフォーム、公開資料がこれらの答えを直接漏らすことが多い)。もう一つは列挙。秘密の質問は答えの空間が極小(是非、有限の選択肢、一般的な姓)で、直接ブルートフォースでき、この種の検証は往々にしてレート制限がない。
**Q3**: 秘密の質問に試行回数制限がある。
**A3**: 検証フローのロジックバイパスへ転じる。答え検証の返り値を改ざんできるか、このステップを飛ばして新パスワード設定へ直接行けるか、複数の検証因子のうち最も弱い一つだけを満たせばよいか。弱い二次検証には不徹底なフロー実装が付き物だ。
**Q4**: 複数項目を同時に検証する必要がある。
**A4**: 「または」ロジックの脆弱性を探す。本来「全て満たす」べきなのに「いずれか一つでよい」と実装されているか、ある項目の検証が空のとき通過扱いされるか。多因子の実装では、組み合わせロジックが最も間違えやすい。
**Q5**: 二次検証が厳格で、情報も調べられない。
**A5**: 直交次元へ転じる。「検証の質問に答える」ことを諦め、前述の token 予測、Host ヘッダ注入、権限外でのパスワード変更という回答に依存しないリセット脆弱性へ転じる。あるいは完全にレーンを替えてログイン/トークン層へ。知識ベースの検証は技術的なバイパスを防げない。

### パスワードレス/魔法のリンク/OTP のみのログインの攻め方
**Q1**: 対象が「魔法のリンク」か純 OTP のパスワードレスログインで、打つパスワードがない。どうする?
**A1**: 攻撃面を再配置する。パスワードレスは「秘密」をパスワードから「リンク/検証コードの配信と検証」へ移している。判定基準は、その一度きりの認証情報(magic link token / OTP)が予測可能か、傍受可能か、リプレイ可能か、列挙可能かだ。秘密が担体を替えれば、弱点も場所を替える。
**Q2**: 魔法のリンクの token がランダムに見える。
**A2**: 配信と紐づけへ転じる。リンクドメインが Host ヘッダから取られるか(劫持可能)、token が発起デバイス/セッションに紐づくか(紐づかなければこちらが発起し、被害者がクリックした後こちらが使う)、token が一度きりか(リプレイ可能なら窓が広い)。パスワードレスシステムの急所は token の紐づけ関係に多い。
**Q3**: OTP のみのログインで、検証コードは 6 桁だ。
**A3**: OTP ブルートフォース/レート制限探査の次元へ戻る。パスワードレスでは OTP が唯一の門であり、レート制限が不十分なら直接ブルートフォースでログインでき、リスク等級は「パスワード+OTP」より格段に高い。厳格な試行制限があるかを優先検証する。
**Q4**: token/OTP の生成と検証がどちらも厳格だ。
**A4**: 「アカウント識別子」の段階へ転じる。パスワードレスログインは通常メール/携帯だけで認証情報を発行する。システムに認証情報をこちらの制御するアドレスへ発行させられれば(紐づけメール/携帯を変える、正規化で二つの識別子をこちらに向ける)、検証全体を迂回できる。配信内容でなく配信対象を攻める。
**Q5**: 生成、検証から配信の紐づけまで隙がない。
**A5**: 直交次元へ転じる。パスワードレスログインでセッションが確立した後のセッション管理/認可は通常の面なので、session/IDOR/権限外アクセスへ戻る。あるいはそれが依存するメール/SMS チャネルそのものを攻める(メールボックスを乗っ取ればすべてのパスワードレスアカウントを乗っ取れる)。表門がパスワードレスで厳重なら、「認証情報を受け取るメールボックス」を打つ。

### 認証を深掘り続けるか攻撃面を替えるかの判断(メタ意思決定)
**Q1**: 認証バイパスに長く費やした。続けるか方向転換するか、このメタ意思決定をどう行う?
**A1**: 費用対効果を評価する。まだ試していない直交次元(注入/ロジック/トークン/セッション/リセット/OAuth/権限外アクセス)を列挙し、それぞれのシグナル強度を推定する(既に異常の兆候があるか)。判定基準は、「兆候はあるが試し切っていない方向」がまだあるかだ。すべての次元を試してシグナルがなければ、続けるのは埋没費用だ。
**Q2**: 認証点はかなり堅そうだが、他の機能をまだ触っていない。
**A2**: 直ちに「認証が唯一の入口ではない」という認識に転じる。多くの対象の本当の突破口は業務機能(ファイルアップロード、エクスポート、SSRF、注入)であり、ログインではない。まず現在の最低権限アクセスでアプリの機能面全体を一巡してから、認証を続ける価値があるか判断する。
**Q3**: 方向転換したら認証の穴を逃しそうで不安だ。
**A3**: 「記録して棚上げ」戦略を使う。認証点で観測したすべての異常、疑わしい点、作りかけの payload をリスト化し「再訪待ち」とマークして、安心して方向転換する。構造化した棚上げは放棄ではなく、後で新情報(漏れた鍵など)が得られたら正確に戻れる。
**Q4**: 方向転換後、別の場所で低権限の足場を得た。
**A4**: 新しい足場で認証を逆に助ける。内網視点からは認証サービスの設定/ログ/鍵が見え、DB の hash が読め、ゲートウェイを迂回して直結できる。外部から攻めきれない認証も、内部の低権限点から見返せば開いていることが多い。足場は認証を見直す新しいレンズだ。
**Q5**: すべての次元を試し尽くし、対象全体が打てず、完全に詰まった。
**A5**: 最後の直交方向転換を行う。範囲を広げる(同一組織の他のアセット/サブドメイン、横展開でより弱い兄弟システムを探す)、時間次元へ転じる(新しい N-day を待つ、アセット/情報収集をやり直す)、人の次元へ転じる(認可範囲内のソーシャルエンジニアリング/フィッシング)。単一対象の技術面を尽くした後は、「アセットの広さ、時間、人」という 3 つのより大きな直交軸で戦場を開き直す。

### WebSocket ハンドシェイク時の認証の弱点
**Q1**: 対象アプリが WebSocket を多用する。そのリアルタイムチャネルの認証に穴がないか見たい。まず何を見る?
**A1**: WebSocket ハンドシェイク(HTTP Upgrade)の段階をキャプチャする。認証情報はハンドシェイクとともに運ばれるか(cookie/token)、接続後にアプリ層メッセージで認証・認可するか。判定基準は、チャネル確立と身元検証が分離されているかだ。先に接続して後から認証・認可するなら、接続から認証・認可までの間のメッセージが保護されないかもしれない。
**Q2**: ハンドシェイク時に cookie で認証する。
**A2**: WebSocket ハンドシェイクは既定で同一オリジンポリシーと CSRF token の制約を受けない(古典的な CSWSH、クロスサイト WebSocket 劫持)ことに注意する。サーバーが cookie だけを頼りに Origin を検証しなければ、任意のサイトから被害者の cookie 付きでハンドシェイクを発火し、被害者として通信するチャネルを確立できる。まず Origin が検証されるかをテストする。
**Q3**: サーバーが Origin を検証している。
**A3**: 接続内メッセージの認可粒度へ転じる。接続後の各メッセージ(チャネル購読、メソッド呼び出し)で権限を再検証するか。多くの実装は「接続=全解放」で、他者のチャネルを権限外で購読したり管理メソッドを呼んだりできる。攻撃面をハンドシェイクからメッセージ級の認証・認可へ移す。
**Q4**: メッセージ級も検証している。
**A4**: WS 場面での token の扱いに転じる。ブラウザの WS はカスタム header を付けられないため、token は URL クエリ文字列に入りがちで、ログ、referer、プロキシキャッシュに漏れる。これらの漏えい点を探して token を取得し再利用する。
**Q5**: WS チャネルがハンドシェイクからメッセージまで厳格だ。
**A5**: 直交次元へ転じる。それを支える HTTP 認証面へ戻るか、WS の背後にあるメッセージ処理ロジック(メッセージ内容の注入、デシリアライズ)を攻める。リアルタイムチャネルの認証が厳格なら、それが運ぶデータそのものを打つ。

### 認証レスポンスのキャッシュによるセッション取り違え
**Q1**: 対象の前に CDN/キャッシュ層がある。認証関連レスポンスが誤ってキャッシュされていないか判断したい。
**A1**: 個人化/認証情報を含むレスポンス(ユーザー名付きページ、Set-Cookie、非公開 API 返り)にキャッシュの痕跡がないかを見る。レスポンスヘッダの Cache-Control、Age、X-Cache ヒットマーク。判定基準は、「本来非公開でユーザーごとに異なるレスポンス」が公開キャッシュに保存されていないかだ。保存されていれば、あるユーザーのセッション/データがキャッシュされて他者へ配られるかもしれない。
**Q2**: Set-Cookie 付きレスポンスがキャッシュされているのを見つけた。
**A2**: セッション取り違えにつながり得る。A のログイン時の Set-Cookie がキャッシュされ、B が同じ URL をリクエストすると A のセッション cookie を得る。このキャッシュヒットを構築/待つことで、他者の認証済みセッションを「拾える」。まずキャッシュキーとヒット条件を安定して再現する。
**Q3**: 受動的にヒットを待つのでなく能動的に毒を盛りたい。
**A3**: Web キャッシュポイズニングへ転じる。キャッシュキーに入らないがレスポンスに影響する入力(ある header)を探し、公開キャッシュエントリを汚染し、後続の全ユーザーにこちらの構築した内容(注入スクリプトで token を盗むなど)を渡す。「キャッシュを拾う」から「キャッシュへ毒を盛る」へ格上げする。
**Q4**: キャッシュキーの設計が厳格で、毒を盛れない。
**A4**: キャッシュデセプション(cache deception)へ転じる。被害者に「静的資源に見える」URL(.css/.js 接尾辞付き)だが実際は彼の非公開データを返す URL へアクセスさせ、キャッシュに彼の非公開レスポンスを静的ファイルとして保存させ、こちらが同じ URL を読む。キャッシュを騙して本来保存すべきでない非公開ページを保存させる方向だ。
**Q5**: キャッシュ層が認証内容を適切に処理し、毒盛り/欺瞞の余地がない。
**A5**: 直交次元へ転じる。キャッシュ層が綺麗なら源站の認証/セッション脆弱性そのものへ戻る。キャッシュ問題は「インフラ設定」次元なので、打てなければ「アプリロジック」次元へ戻る。

### デシリアライズ型セッショントークンの攻め方
**Q1**: session cookie をデコードすると、ある言語のシリアライズオブジェクト(Java/PHP/.NET/Python 構造)に見える。何を意味する?
**A1**: サーバーがこちらの制御可能なデータをデシリアライズしている可能性があり、これは認証バイパス面であると同時に RCE 面だ。まず形式を確認する(Java の rO0/aced 始まり、PHP の a:/O: 構造、.NET の ViewState など)。判定基準は、このトークンがデシリアライズされてオブジェクトになってから使われるかだ。もしそうなら、改ざんは「身元」と「コード実行」を同時に脅かす。
**Q2**: シリアライズオブジェクトだと確認した。まず認証バイパスをしたい。
**A2**: オブジェクト内の身元/ロールフィールドを変えて再シリアライズする(完全性保護がなければ)。多くのフレームワークはユーザー情報を cookie にシリアライズするのに署名しないため、直接 role=admin に変えられる。まず最も軽い改ざんを試し、身元を変えて権限を取れるなら取る。
**Q3**: シリアライズデータに署名/MAC が付く(あるフレームワークの署名 cookie)。
**A3**: MAC 鍵を攻める。フレームワーク既定鍵、弱い鍵、漏れた鍵(設定/ソース漏えい)。鍵を得れば身元の偽造も悪意あるシリアライズ payload の構築もできる。署名トークンの強度はその鍵の秘匿性に完全に依存する。
**Q4**: デシリアライズできるなら、認証バイパスの他に何をすべきか?
**A4**: デシリアライズ RCE へ格上げする。対応言語の gadget チェーンで payload を構築し、デシリアライズ過程にコマンド実行を誘発させる。認証バイパスはアプリ内身元を取るだけだが、RCE はサーバーを直接取る。同じ穴でも後者の価値がはるかに高く、優先的に試す価値がある。
**Q5**: オブジェクトに完全性保護があり、鍵が取れず、改ざんも gadget も打てない。
**A5**: 直交次元へ転じる。鍵が死節なら、「鍵を取得する」情報収集次元(ソース/設定漏えい)へ転じるか、このトークンに依存しない他の認証脆弱性へ戻る。デシリアライズの扉が施錠されたら、扉の鍵(鍵)は別の次元で探すために他に隠されている。

### 送信元 IP / 転送ヘッダに基づく信頼のバイパス
**Q1**: ある API/管理画面が「内網は認証不要、外網は認証必要」に見える。送信元 IP で信頼を判断していると疑う。どう打つ?
**A1**: それが信頼する「送信元」が TCP の実 IP か、偽装可能な header かを判断する。判定基準は、アプリが X-Forwarded-For、X-Real-IP、X-Client-IP などの転送ヘッダを読んで「内網か/信頼できる送信元か」を判定するかだ。これらのヘッダを読んで検証しなければ、内網 IP に偽装して騙せる。
**Q2**: X-Forwarded-For: 内網セグメントを付けたが効かない。
**A2**: ヘッダの各種変種と多値構成を試す(XFF はカンマ区切りリストで、アプリが最初か最後かを取る)、他の等価ヘッダ、大文字小文字の差異を試す。フレームワーク/プロキシごとに「どのヘッダ、どの部分を取るか」の理解が異なり、その差異を総当たりして信頼される一つを探す。
**Q3**: アプリが信頼プロキシの設定した実 IP を取っており、偽装ヘッダが無効だ。
**A3**: 「信頼される位置から発火する」方向へ転じる。SSRF があれば、内部サーバーにこちらの代わりに内網のみを信頼する API へリクエストさせ、信頼できる送信元を自然に帯びる。SSRF は「こちらは外網にいる」ことを「リクエストは内網から来る」ことに変える。IP 信頼を迂回できなければ、内網の口を借りてこちらの代わりに話させる。
**Q4**: SSRF がなく、内網にも入れない。
**A4**: 「外に晒された本来内網向けの API」を探す。運用/デバッグ/監視エンドポイントは IP ホワイトリストを設定しつつも外部から偶然アクセスできる、あるいはホワイトリストに穴がある(ある中間ノードが未適用)ことがある。ホワイトリストが覆い切れていない一角を探す。
**Q5**: IP 信頼が厳格で、SSRF もなく、ホワイトリストに穴もない。
**A5**: 直交次元へ転じる。ネットワーク位置に基づく信頼が打てなければ、認証情報に基づく認証面(トークン/パスワード/ロジック)へ戻る。位置信頼は「あなたはどこにいるか」の次元であり、尽くしたら「あなたは誰か」の次元へ戻る。

### トークン比較のタイミング側チャネルと短い乱数
**Q1**: ある API key / token / リセットコードがある。検証方式や長さに弱点があるか評価したい。
**A1**: まずエントロピーと長さを評価する。token は何桁か、文字セットはどれだけ大きいか、予測可能な接頭辞(タイムスタンプ/連番セグメント)があるか。判定基準は、その有効空間がブルートフォース可能なほど小さいか、構造が導出可能な部分を漏らしているかだ。短いか半構造化のトークンは、妥当な時間内に総当たりか推算できる。
**Q2**: token が十分長くランダムで、ブルートフォースが現実的でない。
**A2**: 比較方式のタイミング側チャネルへ転じる。サーバーがバイト単位の短絡比較を使う場合(== でなく定数時間比較)、正しい接頭辞が長いほどレスポンスが遅い。理論上は正しい値をバイト単位で測れる。判定基準は、レスポンス時間が接頭辞の正しさに応じて安定して変わるかだ。
**Q3**: ネットワークジッタが大きすぎて、タイミング信号がノイズに沈む。
**A3**: S/N 比を上げる。大量反復で中央値を取る、近くから発火する、HTTP/2 で接続オーバーヘッドを減らす。ただし現実的に評価する。リモートタイミング攻撃は極めて難しく、ジッタが信号を常に覆うなら、この経路は通らないと断じ、「理論上は存在するが実行不能」と記録して粘らない。
**Q4**: タイミングで打てない。このトークンを別の角度から見る余地は?
**A4**: トークン生成の乱数源を見る。弱い PRNG(時間/pid ベースのシード)を使うか、複数サンプルを請求してシードを逆算し後続トークンを予測できるか。弱い乱数は「高エントロピー」を見かけにすぎなくする。生成側から予測できれば、比較側からブルートフォースする必要がない。
**Q5**: トークンが長く、乱数が強く、比較が定数時間で、側チャネルが皆無だ。
**A5**: 直交次元へ転じる。トークンそのものが暗号的に隙がなければ、トークンの「値」でなくトークンの「流通」を打つ。それがどこで転送/保存/ログ記録されて漏れるか(前述のトークン漏えい収集)。計算も計測もできない秘密は、どこかで平文で書き残されている可能性が常にある。
