# Web · デシリアライズ脆弱性の判定とチェーン構築

### ある入参がデシリアライズ入口かどうかの識別
**Q1**: 対象 X の制御可能なパラメータに、読めないバイナリ/base64 が入っている。デシリアライズ入口か暗号化データかをどう判断する?
**A1**: まずエンコード除去とマジックナンバー比較を行う。これが判定の第一原理の動作だ。base64 デコード後の先頭数バイトを見る。`AC ED 00 05`(base64 接頭辞 `rO0`)は Java ネイティブシリアライズストリーム。`{` 始まりは JSON(fastjson/jackson の可能性)。PHP の `O:数字:"クラス名"` は PHP シリアライズ。`\x80\x04`/`\x80\x03` は Python pickle。`04 08` 付近は Ruby Marshal。判定基準は構造規則であってランダムエントロピーではない。暗号化データは通常高エントロピーで固定ヘッダがない。
**Q2**: 解いてみると gzip 圧縮の後に base64 された複数層で、剥いてもまだ乱数だ。どうする?
**A2**: 多重エンコードは常態で、「外から内」へ層ごとに剥く。base64→gzip/zlib→さらに base64 かもしれない。各層の特徴バイトを自動探査するループを書く。クラス名/マジックナンバーが出たら止める。底まで剥いても純粋な高エントロピーバイナリで長さが 16 の倍数なら、対称暗号(Shiro の rememberMe など)に傾き、このとき入口は「復号後」であり現層ではない。
**Q3**: 判定基準がどれも満たさず、自研のバイナリ形式に見える。どうする?
**A3**: 副チャネルの判定基準に転じる。1 バイト変えてサーバーのエラーを見る。デシリアライズ点は異常に `ObjectInputStream`、`unserialize()`、`pickle.loads`、`readObject` のスタックフレームやクラス名を漏らすことが多く、形式を盲推測するより速い。
**Q4**: この道が死んだら(パラメータのどのバイトを変えても安定して 400 でスタック情報なし)は?
**A4**: 直交次元に転じる。このパラメータに固執せず、サイト全体のトラフィックマッピングに戻る。デシリアライズ点は Cookie、rememberMe、ViewState、RPC ポート(Java RMI 1099/T3 7001/Hessian)、メッセージキューのデシリアライズによくあり、入口面を替えるほうが単一パラメータに固執するより効率的だ。
**Q5**: 「デシリアライズされる」のであって単に保存されるのではないことをどう素早く確認する?
**A5**: 構造は正当だがフィールドが異常な payload(Java で正当なストリームだがクラスが存在しないなど)を送り、`ClassNotFoundException` のような意味エラーが返れば、サーバーが確かにオブジェクト再構築をしている。判定成立だ。

### 言語/フレームワークスタックを確認して正しい武器庫を選ぶ
**Q1**: デシリアライズ点と確認した。先に言語判定に力を割くべきか?
**A1**: 必ず先に判定する。gadget ライブラリは強く言語に束縛され、言語を誤ればゼロだ。マジックナンバーの他に、レスポンスヘッダ `X-Powered-By`、`Server`、Set-Cookie 名(`JSESSIONID`=Java、`PHPSESSID`=PHP、`ASP.NET_SessionId`=.NET)、エラーページの傾向、URL 拡張子(`.jsp/.do/.action` vs `.php` vs `.aspx`)を傍証にする。
**Q2**: Java と確認した。さらにフレームワークを細分する必要があるか?
**A2**: ある。Java でも「ネイティブシリアライズ / fastjson / jackson / Shiro / WebLogic T3 / Dubbo Hessian」で攻め方がまったく違う。デシリアライズストリーム自体を見る。`rO0`=ネイティブ。JSON+`@type`=fastjson。JSON+`$type`=Json.NET(実は .NET)。Cookie 名 `rememberMe`=Shiro。
**Q3**: PHP と判定したが、ネイティブの unserialize か phar か不明だ。
**A3**: 明示的なデシリアライズパラメータがあるかを見る。制御可能な unserialize 入口がなく、ファイル操作系関数(file_exists/fopen/getimagesize)があれば、phar デシリアライズ次元に転じる。`phar://` で誘発する。
**Q4**: 言語判定基準が互いに矛盾する(ヘッダは nginx だがストリームは Java)。どうする?
**A4**: 「データストリームのマジックナンバー」を最高優先の判定基準にする。HTTP ヘッダはリバースプロキシ/CDN に改ざんされ得る。nginx は前置にすぎず、バックエンドは依然 Java アプリサーバーの可能性がある。
**Q5**: 言語がまったく判定できず、ブラックボックスでフィンガープリントがない?
**A5**: DNSLog のブラインド攻撃に転じる。各言語に対して「DNS リクエストだけを誘発し gadget に依存しない」探査を一つ送る(Java の URLDNS、PHP の SoapClient/phar 経由 DNS、Python の os 誘発)。どれが戻るかで言語を確定し、探査でフィンガープリントを逆算する。

### Java ネイティブシリアライズ確認後の無エコーブラインド領域
**Q1**: Java ネイティブデシリアライズと確認したが、打ってもページに変化がない。利用できるかをどう確認する?
**A1**: まず第三者ライブラリに依存しない URLDNS チェーンで「ストリームがデシリアライズされ且つ外向き通信できる」ことを検証する。JDK 同梱クラスのみを使い、DNS 解析を一度誘発する。DNSLog を受信すれば、入口が生き、制御可能、且つ対象が外向き通信することを証明する。gadget 変数を入れない最も清潔な判定プローブだ。
**Q2**: URLDNS は DNS を受信したが、CommonsCollections コマンド実行チェーンに替えると反応がない?
**A2**: 「入口は通るが gadget 依存が欠ける」ことを示す。URLDNS 成功はデシリアライズ自体の動作だけを証明し、classpath に CC/Spring などの利用可能チェーンがあることを意味しない。依存の探査に転じる。ysoserial の各チェーンを逐一ブラインド送信するか、先に classpath を探る(依存探査チェーンを見よ)。
**Q3**: DNSLog がずっと戻らない。穴がないのか外向き通信しないのか?
**A3**: 二つの可能性を分けて判定する。まず DNSLog プラットフォーム自体が使えることを自測する。次に対象が内部ネットワーク隔離かを判定する。帯内の判定基準に替える。ある gadget がクラス欠如で異なる異常を投げるなら、レスポンス差異(エラー種別/レスポンス時間)をブール判定基準にし、外向き通信に依存しない。
**Q4**: 完全に外向き通信せず、エコーもなく、エラー差異もない。ブラインド領域が深すぎる。どうする?
**A4**: 時間側チャネルに転じる。計測可能な遅延を作るチェーン(大オブジェクト/再帰/sleep 類の挙動を誘発)を構築し、レスポンス時間を 1bit 判定基準にして実行を確認する。実行を確認したらメモリ馬/逆接続に転じて実エコーにする。
**Q5**: 時間側チャネルも不安定だ?
**A5**: 直交する入口に替える。同一対象に複数のデシリアライズ面(RMI/JMX/T3 ポート、他の HTTP パラメータ)があるかもしれない。現在の盲点を諦め、エコーの可能性のある面を打つ。

### ysoserial 全チェーンブラインド送信の選択戦略
**Q1**: ysoserial をブラインド送信したい。数十のチェーンをどんな順で打てば高効率か?
**A1**: 「依存の普及度 × 無害探査優先」で並べる。先に URLDNS/JRMPClient で通路を検証し、最も一般的な依存チェーンを打つ。CommonsCollections 系(1-7、異なる CC 版を覆う)、CommonsBeanutils、Spring 系。各チェーンは先に DNS/遅延で無害検証し、どれが誘発するかを確認してから、そのチェーンでコマンド実行に替える。一発目から RCE を打って防御を驚かせない。
**Q2**: CC1 は通らないが CC6 は通る。何を示す?
**A2**: 対象の JDK が高いか CC 版が新しいことを示す。CC1 が依存する `AnnotationInvocationHandler` は高版 JDK で改造されて無効になる。CC6 は `TiedMapEntry` でその制限を迂回し、JDK 版を選ばない。CC6/CC5 が命中するのは通常「高版 JDK + commons-collections 3.1+」環境を指し、以降は全てそれを使う。
**Q3**: 全 CC チェーンが通らないが、デシリアライズはあると確認済みだ。
**A3**: 非 CC 依存に転じる。CommonsBeanutils(Shiro/他フレームワークと共に classpath に入りがち)、C3P0、Rome、Hibernate、Groovy、Clojure。逐一探る。命中面は往々にして業務依存で決まり、汎用ライブラリではない。
**Q4**: ysoserial 生成のストリームを打つと `invalid stream header` か filter 遮断が出る?
**A4**: 前者は多くがエンコード層の不整合だ(gzip/base64 すべきなのにしていない)。外層ラッパーを揃えてから送る。後者は JEP290/カスタム ObjectInputFilter の遮断で、「filter 迂回」次元に転じる(関連チェーンを見よ)。
**Q5**: 全チェーンが失敗した。Java ネイティブのこの道を諦めるべきか?
**A5**: 先にツールと JDK を自己点検する。ysoserial は対象に近い JDK でコンパイルして生成する必要がある(高版 JDK 生成のストリームは対象が認めないクラスを持ち得る)。低版 JDK に替えて再生成して試す。それでも通らなければ、このポートの他のプロトコル脆弱性(T3/IIOP 専用の攻め方)に転じるか、入口を替える。

### classpath 依存の盲探——どの gadget があるか不明
**Q1**: ブラインド送信が時間を食う。先に classpath にどんなライブラリがあるかを探ってから正確にチェーンを選べないか?
**A1**: できる。発想は「クラスの存在有無で観測可能な差異を作る」ことだ。成功が特定の gadget クラスの存在に依存するデシリアライズストリームを構築する。クラスが存在→A 挙動、不存在→`ClassNotFoundException`。エラー/遅延/DNS の差異でクラスごとに探査し、依存フィンガープリントを組み立ててから正確に打つ。
**Q2**: エラーが統一異常ページに飲まれ、ClassNotFoundException が見えない?
**A2**: DNS 差異プローブに転じる。「対象クラスが存在するときだけ DNS 誘発の分岐に進む」構築を設計する。DNS を受信=クラス存在、受信なし=不存在。帯内判定基準を帯外判定基準に替える。
**Q3**: 外向き通信も封じられ、帯外も帯内も差異信号がない?
**A3**: 時間判定基準に転じる。「クラス存在」経路を「不存在」経路より計測可能な分だけ遅くする。複数回サンプルして中央値を取りジッタに抗う。
**Q4**: 探査コストが高すぎ、ライブラリが多すぎて探し切れない。どうする?
**A4**: 戦略を変える。総当たりせず、先に対象技術スタックの高頻度依存を仮定する(Shiro なら CommonsBeanutils が必携、Spring アプリは spring-core の確率が高い)。3-5 個の高価値仮定を狙って検証し、命中すれば使う。完全なマッピングを求めない。
**Q5**: 探し終わって既知の利用可能 gadget がまったくない?
**A5**: 「gadget なしでも打てる」直交次元に転じる。URLDNS で SSRF、大オブジェクト構築で DoS、あるいはデシリアライズ自体のファイル/属性副作用を利用する。または JNDI 注入系の脆弱性( JNDI lookup 面があれば)に替え、ローカル gadget への依存を迂回する。

### JEP290 / ObjectInputFilter に遮られた
**Q1**: 高版 JDK の対象で、ストリームを送ると `filter status: REJECTED` で塞がれる。まだ見込みはあるか?
**A1**: ある。ただし filter がブラックリストかホワイトリストかを見る必要がある。先に種別を判定する。異なる gadget の最上位クラスを替えて探り、個別のクラスだけが拒否され他が通るならブラックリストで、リストにない等価チェーンを探す。ほぼ全ての非ホワイトリストクラスが拒否されるならホワイトリストで、難度がはるかに高い。
**Q2**: ブラックリストだ。迂回チェーンをどう探す?
**A2**: 「最上位入口クラス」が異なり効果が等価な gadget に替える。多くの filter は `InvokerTransformer`/`TemplatesImpl` のような有名クラス名だけを遮断する。CommonsBeanutils、Rome、あるいは異なる誘発経路のチェーンに替えれば、最上位クラス名が違うので迂回できる。
**Q3**: ホワイトリストで、ほぼ打てない?
**A3**: 「プロトコル層/アプリ層が自ら持つホワイトリスト内の利用可能クラス」に転じる。あるミドルウェアのホワイトリストには業務に必須だが乱用可能なクラス(特定 RPC の解析クラスなど)が残っている。あるいは二次デシリアライズを進む。外層はホワイトリストが許すコンテナクラスを使い、内層で再びデシリアライズを誘発して外層 filter を迂回する。
**Q4**: 二次デシリアライズをどう足場確保する?
**A4**: ホワイトリストが許し、且つその内部が何かのバイト配列に対して再びデシリアライズを呼ぶクラス(ある Hessian/カスタム readObject のネストなど)を探す。外層は filter を通り、内層のデシリアライズは同じ filter の制約を受けないかもしれない。filter 迂回の古典的な直交面だ。
**Q5**: すべて駄目で、filter が厳格な全局ホワイトリストだ?
**A5**: このデシリアライズ点を諦め、対象の他の攻撃面に転じる。厳格なホワイトリスト filter は強い防御であり、レッドチームは時間をより柔らかい入口(他のサービス、ロジック脆弱性)に投じ、無理に攻めない。

### PHP unserialize + POP チェーン構築
**Q1**: PHP 対象に制御可能な `unserialize` があるが、使えるクラスがわからない。POP チェーンをどう組み始める?
**A1**: まず使えるクラスとマジックメソッドを把握する。デシリアライズが自動誘発できるのは `__wakeup`、`__destruct`。後続は `__toString`(オブジェクトが文字列として扱われる)、`__get/__set`、`__call` が連鎖する。判定基準は、ある「デシリアライズ即実行」のマジックメソッドから出発し、危険な sink(system/eval/file_put_contents/call_user_func)へ進める属性呼び出し経路を見つけることだ。
**Q2**: ソースはあるがクラスが多すぎる。チェーンの頭と尾をどう素早く特定する?
**A2**: 双方向に検索する。チェーンの尾: 危険関数(system/exec/eval/include/file_put_contents/unserialize)を grep して誰が呼ぶかを逆検索する。チェーンの頭: `__destruct`/`__wakeup` を grep する。中間は `__toString`/`__call` などで頭と尾を繋ぐ。ツール化は phpggc で一般的なフレームワーク(Laravel/Symfony/ThinkPHP など)の既成 POP チェーンを直接生成できる。
**Q3**: ソースがなく、純粋なブラックボックス PHP デシリアライズだ?
**A3**: 既知フレームワークチェーンのブラインド攻撃に転じる。フィンガープリントでフレームワーク版を判定し、phpggc の対応版チェーンをブラインド送信する。判定基準はレスポンス差異だ。ブラックボックスでの自前 POP 構築はほぼ不可能で、公開チェーンライブラリに依存する。
**Q4**: `__wakeup` が利用を塞ぐ(検証/属性リセット)。どうする?
**A4**: 古典的な迂回。シリアライズ文字列のオブジェクト属性個数の表記が実際の個数より**大きい**とき、旧版 PHP(<5.6.25/<7.0.10)は `__wakeup` を飛ばす。`O:4:"Xxxx":N` の N を実属性数より大きく変えれば迂回できる。高版ではこの穴は修正済みで、次の条に転じる。
**Q5**: 高版で __wakeup を迂回できない、あるいは使える __destruct がない?
**A5**: phar 次元に転じるか、`__destruct` 以外の誘発点を探す。あるいは文字列エスケープ/属性注入を利用する(文字エスケープチェーンを見よ)。全て無路なら、このパラメータが他にできること(SQLi/ファイルインクルード)に転じ、デシリアライズに閉じない。

### PHP phar デシリアライズ(明示的な unserialize なし)
**Q1**: PHP 対象に制御可能な unserialize がないが、ファイル操作関数がある。デシリアライズを打てるか?
**A1**: 打てる。phar を進む。`phar://` 擬似プロトコルはファイル系関数(file_exists/is_dir/fopen/getimagesize/file_get_contents など)に処理されるとき、phar ファイル meta-data 内のオブジェクトを自動デシリアライズし、POP チェーンを誘発する。判定基準は、対象に「ファイルパス制御可能 + 任意内容のファイルをアップロード/書き込みできる」かだ。
**Q2**: 悪意ある phar をどう対象に送り込む?
**A2**: ファイルアップロード点が一つ必要だ(拡張子が制限されていても)。phar は任意の拡張子に偽装できる(.jpg/.gif に変える)。誘発はファイル拡張子でなく `phar://` プロトコル解析に依存するからだ。アップロード後、ファイル関数で `phar://path/to/file.jpg` として参照する。
**Q3**: アップロードに画像形式検証(getimagesize 検査)がある?
**A3**: phar 構築時にファイル先頭に正当な画像マジックナンバー(GIF89a など)を置き、「画像+phar」のポリモーフィックファイルにする。getimagesize は先頭を正当な画像と認め、phar パーサは後方の phar 構造を読める。
**Q4**: PHP 8+ 対象だ。phar はまだ効くか?
**A4**: PHP 8 は phar デシリアライズの誘発を厳しくした(一部関数は meta-data を自動デシリアライズしなくなった)。判定基準が厳しくなる。依然誘発する関数を優先的に探す。全て塞がれたら他のデシリアライズ面に転じるか phar を諦める。
**Q5**: ファイル関数が制御可能なパスを受け取る箇所がなく、phar の誘発点がまったくない?
**A5**: 直交面に転じる。明示的な unserialize を探す、SSRF 内で phar を使えるか、あるいは攻撃チェーン全体を替える(アップロード自体が直接 webshell を落とせるなら phar を迂回する必要なし)。

### PHP 文字エスケープ(デシリアライズ文字列注入)
**Q1**: 対象が unserialize 前にデータに文字列置換をする(フィルタ後長さが変わる)。利用できるか?
**A1**: できる。これはデシリアライズ文字エスケープだ。置換で文字列が「伸びる/縮む」と、シリアライズ形式の長さ表記が乱れ、攻撃者が後続オブジェクト属性を制御可能に「食う」か「注入」できる。判定基準は、「デシリアライズ前の str_replace などでバイト数が変わる」かだ。
**Q2**: 伸長エスケープ(フィルタ後文字が増える)をどう利用する?
**A2**: 1 バイト増えるごとに、1 バイト分「押し出して」制御可能な注入ができる。置換され得る文字を十分に使い、増えた空間を偽造した属性/オブジェクトのシリアライズ断片で埋め、本来制御すべきでない属性値を注入する。
**Q3**: 短縮エスケープ(フィルタ後文字が減る)は?
**A3**: 短縮は後方の正当なデータをある文字列属性に「吸い込む」。注入したい属性のシリアライズ断片を吞まれる領域の後に置き、長さのずれでこちらの断片が独立属性として解析されるよう構築する。
**Q4**: オフセットが計算できず、構築がいつもデシリアライズ失敗する?
**A4**: ローカル再現に転じる。対象のフィルタロジックをローカル PHP で再現し、`unserialize` が期待オブジェクトを返すまでバイト単位でオフセットを調整する。デシリアライズ形式は長さに極めて敏感で、ローカルで精確に揃え、対象で盲試しない。
**Q5**: 対象のフィルタが長さを変えない(等長置換)?
**A5**: 等長置換はエスケープを生まず、この道は通らない。標準の POP チェーン/phar に転じるか、このフィルタを通らない他のデシリアライズ入口を探す。

### Python pickle の判定と利用
**Q1**: `\x80\x04`/base64 内が pickle に見える。どう確認し利用する?
**A1**: pickle は極めて利用しやすい。`__reduce__` が直接 `(os.system, ('cmd',))` を返して任意実行を実現でき、ほぼ gadget チェーンを必要としない。まず対象が確かに `pickle.loads` で制御可能入力を読む(json でなく)ことを確認し、`__reduce__` 付きクラスで無害探査(DNS/遅延)をする。
**Q2**: どう無害に検証してから RCE に上げる?
**A2**: 先に `__reduce__` が DNS か遅延だけを誘発する呼び出しを返すようにし、実行を確認してからコマンドに替える。pickle は強すぎ、直接 RCE を打つとリスクが大きい。先に生存を探る。
**Q3**: 対象が `pickle` を使うが制限がある(カスタム `find_class` ホワイトリスト/RestrictedUnpickler)?
**A3**: ホワイトリスト内で乱用可能なクラスに転じる。特定モジュールのみ許可なら、そのモジュール内で間接的に実行/ファイル操作を誘発できる呼び出し可能オブジェクトを探す。あるいはホワイトリスト内で二次的にコードをロードできるクラス(eval/import できるオブジェクトを許可しているなど)を探す。
**Q4**: そもそも pickle でなく、PyYAML/jsonpickle だ?
**A4**: 判定基準と攻め方を替える。PyYAML の `yaml.load`(safe_load でない)は `!!python/object/apply:os.system` で実行できる。jsonpickle は `py/object` のデシリアライズで任意クラスをインスタンス化できる。データ形式の特徴を見て武器を切り替える。
**Q5**: 全て安全なデシリアライズ(json/safe_load)で、コード実行面がない?
**A5**: 直交に転じる。安全なデシリアライズにも型混同/DoS/キー上書きのロジック脆弱性があり得るが、RCE は望めない。デシリアライズ RCE の発想を諦め、対象の他の攻撃面に戻る。

### .NET デシリアライズの判定
**Q1**: .NET 対象だ。デシリアライズ面の有無と種別をどう判断する?
**A1**: .NET デシリアライズは数種あり、判定基準が異なる。`BinaryFormatter`(バイナリ、`AAEAAAD` base64 特徴)、`Json.NET` の `$type` 付き(TypeNameHandling 不適切)、`ViewState`(ASP.NET の `__VIEWSTATE` パラメータ)、`LosFormatter`、`NetDataContractSerializer`。まずデータ形式とパラメータ名で種別を特定する。
**Q2**: Json.NET と特定し、レスポンスに `$type` がある。どう利用する?
**A2**: サーバーの `TypeNameHandling` が None でなければ、`$type` で任意型を指定して gadget を誘発できる(`ObjectDataProvider` で任意メソッド呼び出しなど)。ysoserial.net で対応 formatter の payload を生成する。判定基準は `$type` を注入でき且つ解析されるかだ。
**Q3**: ViewState だが machineKey が必要?
**A3**: machineKey 次元に転じる。ViewState デシリアライズ利用には有効な `validationKey/decryptionKey` が必要だ(`enableViewStateMac=false` でない限り)。key の源は、設定ファイル漏えい、既知の既定/弱い key、他の脆弱性で web.config を読む。key を取ったら ysoserial.net の ViewState プラグインで生成する。
**Q4**: machineKey が取れず、ViewState が打てない?
**A4**: `enableViewStateMac` が無効か(旧アプリ/特定設定)を判断する。無効なら key 不要。そうでなければ他の .NET デシリアライズ面に転じるか ViewState を諦め、key のブルートフォースに時間を割かない(現代の key 強度ではブルートフォースは非現実的)。
**Q5**: ysoserial.net の各 formatter チェーンが通らない?
**A5**: 直交に転じる。.NET の gadget は実行時に利用可能なアセンブリに依存する。formatter/gadget の組み合わせを替えて逐一試す(TypeConfuseDelegate、ObjectDataProvider、WindowsIdentity など)。それでも通らなければ攻撃面を替える。

### Node.js デシリアライズ
**Q1**: Node 対象で、デシリアライズがあると疑う。どう判定する?
**A1**: Node のよくある危険ライブラリは、`node-serialize`(`unserialize`)、`funcster`、`serialize-to-js`。特徴はシリアライズデータに `_$$ND_FUNC$$_` か関数文字列が含まれること。利用点は `node-serialize` がシリアライズされた即時実行関数(IIFE)を実行することだ。
**Q2**: payload をどう構築する?
**A2**: オブジェクトのある属性に `"_$$ND_FUNC$$_function(){...}()"` を置く。デシリアライズ時にその関数が eval され、末尾の `()` で即時実行される。中で `require('child_process').exec` で逆接続する。先に無害な DNS/遅延検証をする。
**Q3**: 対象が安全な JSON.parse を使い、関数デシリアライズがない?
**A3**: JSON.parse 自体はコードを実行せず、この面はない。プロトタイプ汚染(prototype pollution)に転じる。対象がデシリアライズ後のオブジェクトを再帰的に merge するなら、`__proto__` 注入が間接 RCE につながるかもしれない。Node デシリアライズの直交する高価値面だ。
**Q4**: プロトタイプ汚染は確認したが、汚染から RCE への gadget が見つからない?
**A4**: テンプレートエンジン/子プロセス spawn の汚染可能なオプション(EJS/Pug のコンパイルオプション、child_process の shell 引数)を探す。これらの「設定属性」を汚染して初めて RCE に格上げできる。判定基準は、アプリが後続で汚染されたプロトタイプ属性を読むかだ。
**Q5**: すべて成立しない?
**A5**: 通常に戻る。Node アプリの SSRF/コマンドインジェクション/パストラバーサルがデシリアライズより得手しやすいことが多く、ここに閉じない。

### fastjson autoType の判定とバージョン探査
**Q1**: Java JSON 入口に `@type` が付く。fastjson を疑う。まず何をする?
**A1**: 先に fastjson かと大まかなバージョンを判定する。バージョンごとに autoType スイッチと迂回手法が天地の差だからだ。DNS プローブを使う。`@type` を DNS を誘発するクラス(JdbcRowSetImpl/JNDI 類か探査クラス)に向けて送り、戻るかを見ると同時に、異常エコーでバージョン区間を逆算する。
**Q2**: DNS が戻った。何を示す?
**A2**: autoType が少なくともそのクラスを許可しており、利用面があることを示す。続けて JNDI RCE に格上げできるかを確認する。`@type` を `JdbcRowSetImpl` に向け、`dataSourceName` をこちらの RMI/LDAP に設定する。JNDI 注入が fastjson から RCE への主経路だ。
**Q3**: 対象の fastjson 版が高く、autoType が既定で閉じ、一般的なクラスが ban されている?
**A3**: 迂回次元に転じる。バージョンごとに異なる bypass(`Class` キャッシュ利用、異常クラス、`java.lang.` 接頭辞混乱、`L;` ラップ、二重書きなどの歴史的迂回)がある。判定基準はバージョン番号だ。先にバージョンを精確に特定してから対応する公開 bypass を選び、闇雲に試さない。
**Q4**: JNDI を打つと、対象の JDK 高版がリモート class をロードしない?
**A4**: JNDI 高版迂回次元に転じる(JNDI チェーンを見よ)。ローカル factory、EL、Groovy、Tomcat/Spring BeanFactory など、リモート codebase に依存しない利用。
**Q5**: 全て遮られ、fastjson の確認も打つこともできない?
**A5**: jackson(`@class`/`enableDefaultTyping`)の判定に替えるか、fastjson2(形式と迂回がまた違う)かを確認する。それでも無果なら他の攻撃面に転じる。

### Shiro rememberMe デシリアライズ
**Q1**: `rememberMe` Cookie を見た。Shiro デシリアライズ面かをどう判断する?
**A1**: 特徴は極めて明瞭だ。ログイン関連リクエストの Set-Cookie に `rememberMe=deleteMe` が含まれるか、Cookie に `rememberMe` という長い base64 がある。Shiro はシリアライズオブジェクトを AES-CBC で暗号化して Cookie に入れ、デシリアライズ前にまず復号する。判定チェーン: rememberMe の存在を確認 → AES key が必要 → 初めてデシリアライズを誘発できる。
**Q2**: AES key をどう取る?
**A2**: まず既知の既定/漏えい key 集合をブルートフォースする(歴史的版のハードコード既定 key が広く流布、各種漏えい key 辞書)。判定基準: 候補 key で payload を暗号化し、返りに `rememberMe=deleteMe` が**含まれない**(復号成功で異常を投げない)なら key が命中。gadget なしの純粋な key 探査だ。
**Q3**: key ブルートフォースが全て外れた。どうする?
**A3**: key 漏えいチャネルに転じる。設定ファイル、ソース漏えい、他の脆弱性でファイルを読む。Shiro key がランダム生成の強 key なら、オフラインブルートフォースは非現実的で、漏えいで取るしかない。ブルートフォースに固執しない。
**Q4**: key は取れたが、デシリアライズ gadget が通らない?
**A4**: 初期の Shiro(1.2.4-)は CommonsCollections を使えるが、Shiro の既定依存は CommonsBeanutils なので、CB チェーンを優先する。判定基準: Shiro 環境はほぼ必ず commons-beanutils を持ち、ShiroAttack 系ツールで CB チェーンを回すと命中率が最も高い。
**Q5**: key が合い、CB チェーンも通らない。高版 Shiro か?
**A5**: 高版(1.4.2+)は既定で AES-GCM に変わり、旧 CBC padding 迂回が無効になり、filter もあるかもしれない。方向転換として、暗号化モードを確認する(GCM は別構築が必要)、あるいはこのアプリの他の攻撃面に替える。Shiro key 漏えいは他の設定漏えいを伴うことが多く、蔓を辿って別を探す。

### JNDI 注入の高版迂回
**Q1**: デシリアライズ/fastjson/log4j 系脆弱性で JNDI lookup を制御できるが、対象の JDK 高版がリモート codebase をロードしない。どうする?
**A1**: 高版 JDK(8u191+/11+)は既定で `com.sun.jndi.ldap.object.trustURLCodebase=false` となり、リモート URL から factory class をロードしない。「ローカル gadget」利用に転じる。LDAP/RMI に、ローカル classpath に既に存在し乱用可能な factory への参照を返させ、リモートロードに依存しない。
**Q2**: ローカル factory は具体的に何を探す?
**A2**: 古典は `org.apache.naming.factory.BeanFactory`(Tomcat 同梱)と `javax.el.ELProcessor` の組み合わせで、EL 式でコマンド実行する。あるいは Groovy/Spring 環境の対応 bean。判定基準は、対象 classpath に Tomcat/Spring/Groovy のような乱用可能 factory を含む依存があるかだ。
**Q3**: 対象が Tomcat でもなく EL/Groovy もない?
**A3**: デシリアライズ型 JNDI に転じる。LDAP に `javaSerializedData` 属性付きのエントリを返させ、クライアントがそれをデシリアライズする。これは「ローカル gadget チェーン」(CC/CB など)に戻る。JNDI をデシリアライズ誘発器として使い、codebase 制限を迂回するのと同等だ。
**Q4**: デシリアライズ JNDI も filter に遮られた?
**A4**: RMI 経路を試す(RMI と LDAP の JEP 制限の時系列は異なり、一部版では RMI が依然迂回可能)。あるいはローカル factory + デシリアライズの二重試行を組み合わせる。プロトコルを逐一替えるのがここでの直交動作だ。
**Q5**: 全ての高版防御が機能し、JNDI が完全に打てない?
**A5**: JNDI RCE 経路を諦め、同じ脆弱性で低危険利用(SSRF で内部ネットワーク探査、DNS で外向き通信マッピング)に戻すか、攻撃面を替える。JNDI は現代 JDK で大幅に収斂したと認め、無理に攻めない。

### 無エコー・無外向き通信——デシリアライズでメモリ馬を打つ
**Q1**: デシリアライズ RCE ができると確認したが、エコーも外向き通信もない。コマンドは実行したが結果が見えない。実制御をどう取る?
**A1**: メモリ馬(無ファイル webshell)に転じる。Java コードを実行できるなら、逆接続せず、現在の JVM に悪意ある Servlet/Filter/Listener/Interceptor を動的登録し、以降は通常の HTTP リクエストに特定 header/パラメータを付ければコマンドを誘発してエコーできる。判定基準は、対象が Web ミドルウェア(Tomcat/Spring/WebLogic)で、そのコンテキストを取得できるかだ。
**Q2**: デシリアライズで短いコードしか実行できない。完全なメモリ馬をどう入れる?
**A2**: gadget で loader を一段実行する。リフレクションで現在のスレッドの `StandardContext`/Spring の `WebApplicationContext` を取得し、Filter/Controller を動的登録する。コードが長いなら先に defineClass の bytes をデシリアライズで書き込むか、分割する。核心は「最小の実行権限でコンテナコンテキストを取得する」ことだ。
**Q3**: コンテナコンテキストが取れない(非標準 Web コンテナ)?
**A3**: Agent 型メモリ馬に転じる。Java Instrumentation/JVMTI で、`Runtime` で agent をロードするか、`ClassLoader` で直接 defineClass して注入する。あるいは退いて、可書ディレクトリがあれば最も素朴な「ファイル webshell 書き込み」を使う。
**Q4**: メモリ馬すら注入失敗(高版セキュリティマネージャ/RASP 遮断)?
**A4**: RASP 迂回か目標の降格に転じる。まず実行能力で RASP を無効化/盲目化する(できれば)、あるいは RASP が hook しない実行プリミティブに替える。RASP が強すぎるなら、直交して、現在の実行能力で内部ネットワーク偵察(環境変数/設定/認証情報を読む)を横展開し、このマシンの安定シェルを硬く取らない。
**Q5**: 何もかも遮られ、コマンド実行で実質動作すらできない?
**A5**: 最低価値の利用に戻る。脆弱性の存在確認自体を拠点情報とし、同一ネットワークセグメントのより柔らかい他対象を打つ。硬い対象に無限投入しない。

### ブラックボックス fuzz テストでデシリアライズ点を特定する
**Q1**: 大規模サイトのブラックボックスで、デシリアライズがどこにあるかわからない。どう高効率に探す?
**A1**: まず高確率の位置を列挙する。全ての base64/十六進形のパラメータ、Cookie、隠しフォームフィールド、RPC/カスタムプロトコルのポート、メッセージキュー。それぞれに「汎用探査 payload」(各言語の DNS 誘発 payload)を一括送り、DNSLog でどの位置が戻るかを受信する。一括帯外探査がブラックボックス特定の主武器だ。
**Q2**: DNSLog が戻ったが、どのパラメータが誘発したかわからない?
**A2**: 一意サブドメインで各 payload をマークする(`param1.xxx.dnslog`)。戻ったサブドメインが直接、発生源のパラメータを指す。ブラックボックス一括テストの必須技で、一度に打ってからどのドメインが戻るかを見る。
**Q3**: 対象が外向き通信せず、DNSLog が全無?
**A3**: 帯内差異 fuzz に転じる。疑わしいデシリアライズパラメータに「正当なヘッダ + 破損したボディ」を送り、レスポンスにデシリアライズ特徴の異常(クラス名/スタック)が出るかを見る。帯外信号でなくレスポンス差異で特定する。
**Q4**: レスポンスが統一エラーページに飲まれ、差異がない?
**A4**: 時間差異 fuzz に転じる。一部のデシリアライズは特定の構造処理で異常に時間がかかる。レスポンス時間のクラスタリングで「挙動が異なる」パラメータを見つける。
**Q5**: 全て信号なしで、fuzz が産出しない?
**A5**: 情報駆動に転じる。フィンガープリント/バージョン/オープンソースコードから、このフレームワークの既知デシリアライズ CVE の正確な入口パスを特定し、定点で打つ。盲 fuzz を続けない。ブラックボックス fuzz が無果なら、既知脆弱性の正確な再現のほうが割が合う。

### gadget クラスがロードされたが実行エラー——依存衝突のデバッグ
**Q1**: gadget の最上位クラスが対象に受け入れられた(ClassNotFound が出ない)が、実行時に別の異常を投げて RCE にならない。問題はどこか?
**A1**: 高い確率で、チェーン中間のあるクラスの**バージョン**がローカルと一致せず、フィールド/メソッドシグネチャが合わない。判定基準: 異常が `NoSuchMethodError`/`NoSuchFieldException`/`InvalidClassException(serialVersionUID mismatch)` であって ClassNotFound でない。クラスはあるがバージョンがずれていることを示す。
**Q2**: `InvalidClassException: serialVersionUID mismatch` を具体的にどう解く?
**A2**: 対象のそのクラスのバージョンが、payload 生成に使ったバージョンと異なり、serialVersionUID 不一致で拒否された。対策: 対象の正確な依存バージョンを探り(エラーがバージョンを漏らすことが多い、フロントエンド資源/エラーページから推測)、同じバージョンのライブラリで gadget を再生成する。
**Q3**: 正確なバージョンが探れない?
**A3**: 多バージョン爆撃に転じる。一般的なバージョン群で同じチェーンをそれぞれ生成して一括送り、命中すれば成立。デシリアライズはバージョンに敏感で、バージョン総当たりが正確な探査より速いことがある。
**Q4**: バージョンを替えても中間クラスのメソッド不存在が出る?
**A4**: そのチェーンが対象環境で不完全なことを示す。バージョンに鈍感な等価チェーンに替える(異なる gadget はバージョン許容度が異なる)。あるいは誘発経路を替えて欠落した中間クラスを迂回する。
**Q5**: 全バージョン、全チェーンが実行段階で詰まる?
**A5**: 「クラスロードだけで完全な実行を要しない」利用に転じる。TemplatesImpl は自身のバイトコード実行を内包し、第三者チェーンの完全性に依存しない。あるいは URLDNS に戻って SSRF/DoS。この RCE チェーンがこの環境では通らないと認め、直交に転じる。

### デシリアライズ点は確認したが入力が完全に制御できない
**Q1**: コードに readObject があるが、入力が部分的な検証/ラップを通っているようで、バイトストリームを完全制御できるか不明だ。どう判定する?
**A1**: 汚点境界テストを行う。入力の異なる区間を変え、どの変更がデシリアライズ結果に影響し、どれが検証に遮られるかを観察する。判定基準は「最初のバイトをこちらのオブジェクトヘッダにできるか」だ。前に固定ラップ(長さヘッダ/署名)があれば、まずラップ形式を満たす必要がある。
**Q2**: 前に署名/HMAC があり、バイトを変えると拒否される?
**A2**: これは「署名付きデシリアライズ」で、署名鍵なしでは正当なストリームを構築できない。鍵の取得に転じる(設定漏えい/弱い鍵/他の脆弱性でファイルを読む)、あるいは署名を検証しない迂回入口がないか探す。署名は硬い門で、硬くぶつからない。
**Q3**: 長さ接頭辞だけで署名ではない?
**A3**: ならば容易だ。形式に合わせて長さ接頭辞を補えば制御できる。構築時にローカル再現で接頭辞形式を揃えてから送る。
**Q4**: 入力が固定型にデシリアライズされ、`@type`/クラスを替えられない?
**A4**: クラスが固定だがフィールドが制御可能なら、「その固定クラス自身のフィールドが危険な挙動を引き出せるか」(フィールドが URL/ファイルパスで SSRF/ファイル読取を誘発)に転じる。クラスを替えられないとき、許可されたクラス内で副作用を探す。
**Q5**: 完全に制御できず、純粋なサーバー内部データだ?
**A5**: 攻撃面ではない。時間を無駄にしない。本当に外部から制御できる入力点に転じる。「制御可能性」の判定は死点での時間浪費を避ける鍵だ。

### 二次/ネストデシリアライズ(Hessian/Kryo/カスタム)
**Q1**: Hessian/Kryo など非ネイティブの Java シリアライズに遭遇した。ysoserial のネイティブチェーンが使えない。どうする?
**A1**: プロトコル専用の gadget に替える。Hessian には独自の gadget 生態がある(デシリアライズ時に呼ぶ map/comparator を利用した誘発チェーン、Rome、SpringPartiallyComparableAdvisorHolder など)。判定基準: 先に Hessian であることを確認し(特徴バイト)、Hessian 専用チェーンを選び、ネイティブチェーンを当てない。
**Q2**: Hessian 専用チェーンも filter に遮られた?
**A2**: 二次デシリアライズの発想に転じる。Hessian デシリアライズに「内層ネイティブデシリアライズ」を一度誘発させる(あるクラスが readResolve 内で ObjectInputStream を呼ぶ)。Hessian ホワイトリストクラスを外殻にし、内層でネイティブ gadget を打って外層制限を迂回する。
**Q3**: Kryo/Protostuff 系は?
**A3**: これらは既定ではネイティブほど汎用に利用できない。判定基準は、対象が「任意クラス登録/ポリモーフィズム」を開いているかだ。ポリモーフィズムが閉じていれば、デシリアライズ RCE 面は小さく、ロジック脆弱性に転じる。
**Q4**: ミドルウェアが Dubbo/RMI でこれらのシリアライズを担う?
**A4**: RPC 層の攻め方に転じる。Dubbo は複数のシリアライズ(Hessian2 既定)をサポートし、直接そのデシリアライズポートを打ち、Dubbo 専用チェーンを使う。判定基準はポートのプロトコルフィンガープリントだ。
**Q5**: 全ての非ネイティブシリアライズに使えるチェーンがない?
**A5**: この RPC/ミドルウェア自身の既知 CVE(認証バイパス、他の RCE)に転じるか、攻撃面を替える。非ネイティブシリアライズの RCE は敷居が高く、全てが通るわけではない。タイムリーに転じる。

### デシリアライズで webshell を書き込む経路の意思決定
**Q1**: デシリアライズでファイルを書ける。webshell を落としたいが、どのパスに書くかわからない。どう定める?
**A1**: まず web ルートディレクトリを確定する。判定基準の源は、エラーページが漏らす絶対パス、既定インストールパス(ミドルウェア/OS 組み合わせで推測)、他の脆弱性で読んだ設定。web からアクセス可能且つスクリプトを実行できるディレクトリに書いて初めて意味があり、盲書きは無用だ。
**Q2**: web ルートパスが取れない?
**A2**: 「パスに依存しない」利用に転じる。メモリ馬(ディスクに落とさない)、逆接続、あるいは既知の固定で解析可能なディレクトリに書く(あるミドルウェアには予測可能なアップロード/一時ディレクトリがある)。ファイル webshell はパス依存が最も強い方式で、パスが取れなければ無パス方式に替える。
**Q3**: パスは知っているがディレクトリが可書でない?
**A3**: 他の可書ディレクトリに転じる。一時ディレクトリ、ログディレクトリ、アップロードディレクトリ。ログディレクトリが可書且つログがスクリプトとして解析されるなら(稀な設定)、ログインクルードと組み合わせる。そうでなければメモリ馬に戻る。
**Q4**: 書いたがスクリプトが解析されない(静的ディレクトリ/権限)?
**A4**: そのディレクトリがスクリプトハンドラのマッピング内にないことを示す。スクリプトを実行できると確認済みのディレクトリ(通常アプリの主ディレクトリ)に替える。判定基準: 先に探査ファイルを書いてブラウザでアクセスし、解析されるかを確認する。
**Q5**: 全ての可書ディレクトリがスクリプトを解析しない?
**A5**: webshell を諦め、メモリ馬か直接コマンド実行で横展開する。webshell の足場確保は手段の一つであって目的ではない。実行能力を得たら環境に応じて最も楽な永続化を選ぶ。

### 「疑似 XXE/SSRF」からデシリアライズへの誤判定
**Q1**: デシリアライズだと思って長く打っても反応がない。脆弱性種別を誤判定していないかどう調べる?
**A1**: 判定の源に戻ってマジックナンバーと言語を再検証する。XML データも見誤りやすい。`<` 始まりは XML(XXE/XStream)で、ネイティブシリアライズではない。XStream は「XML をデシリアライズする」が、攻め方(XML gadget を使う)がまったく違う。種別誤判定は時間浪費の最も一般的な原因だ。
**Q2**: XStream(XML デシリアライズ)と確認した?
**A2**: XStream 専用チェーンに転じる。任意クラスのインスタンス化 + 動的プロキシで EventHandler/コマンド実行チェーンを誘発する。判定基準は XML に任意型タグを注入できるかだ。Java ネイティブチェーンとは共用できない。
**Q3**: XML だが XStream でなく、通常の解析だ?
**A3**: XXE 次元に転じる。外部エンティティでファイル読取/SSRF/帯外。デシリアライズ面ではない。タイムリーに脆弱性種別のメンタルモデルを切り替える。
**Q4**: データが JSON だが、ずっとネイティブバイナリとして打っていた?
**A4**: 止まって再判定する。JSON デシリアライズ(fastjson/jackson/Json.NET)とバイナリネイティブシリアライズは武器がまったく異なる。1 分かけてマジックナンバー/形式判定をやり直すほうが、1 時間ブラインド攻撃するより勝る。
**Q5**: 種別が何度判定しても定まらない?
**A5**: 最も愚直だが信頼できる方法に転じる。各種別の専用の無害プローブを一つずつ送る(異なるマジックナンバー/形式)。どのプローブがサーバー挙動の変化を起こすかがその種別だ。対象に種別を自ら語らせる。

### デシリアライズが SSRF/内部ネットワークマッピングを誘発する(RCE なしの価値)
**Q1**: デシリアライズで RCE が出ないが、URLDNS/ネットワークリクエストを誘発できる。これに何の価値がある?
**A1**: SSRF 次元に転じて価値を搾り取る。URLDNS 類のチェーンがサーバーに制御可能な DNS/HTTP リクエストを発起させ、内部ネットワークの生存ホスト探査、クラウドメタデータ(169.254.169.254)、内部ネットワーク未認可サービスの攻撃に使える。RCE にならなくてもこの穴に価値があることを意味する。
**Q2**: DNS しか誘発できず、完全な HTTP を送れない?
**A2**: DNS-only でも内部ネットワークホスト名解析の探査、データ持ち出し(情報をサブドメインにエンコード)ができる。判定基準: 解析されるドメインを制御できるか。できれば帯外データ持ち出しができる。
**Q3**: HTTP を送れる。どう格上げする?
**A3**: 内部ネットワークサービス利用チェーンに転じる。SSRF で内部ネットワーク Redis/未認可 RPC/管理 API を打ち、SSRF から二次的に RCE へ格上げできるかもしれない。デシリアライズ SSRF は内部ネットワークの足がかりで、探査に留まらない。
**Q4**: 内部ネットワークが完全隔離され、SSRF も価値ある目標に届かない?
**A4**: データ持ち出し/クラウドメタデータに転じる。本機の metadata にしか届かなくても、クラウド認証情報を取って横展開できるかもしれない。SSRF をローカル/メタデータエンドポイントに向け、遠方の内部ネットワークではない。
**Q5**: 外向き通信すら完全に封じられた?
**A5**: この穴を「脆弱性存在の情報」に降格し、記録して他面に転じる。全てのデシリアライズ点が現金化できるわけではない。認めて転じる。

### log4j 類の「式/lookup 注入」とデシリアライズの区別
**Q1**: デシリアライズを探しているが、ある入力が式として解析される(`${...}` など)のを見つけた。これはデシリアライズか?
**A1**: デシリアライズではないが、同じく高危険で、混同しない。`${jndi:...}`/SpEL/OGNL/EL は式インジェクションで、JNDI/直接実行を誘発する。機構は異なるが、デシリアライズと JNDI 利用の後端を共有することが多い。判定基準: 入力内の `${}`/`#{}`/`%{}` が評価されれば式インジェクションだ。
**Q2**: 式インジェクションが JNDI を誘発できると確認した?
**A2**: 前述の JNDI 利用チェーンを再利用する(リモート codebase かローカル factory、JDK 版次第)。式インジェクションは「誘発器」、JNDI 利用は「ペイロード」で、後半は fastjson JNDI と完全に同じだ。
**Q3**: 式が WAF に `jndi`/`${}` キーワードを遮られた?
**A3**: 式層の難読化に転じる。各種 lookup ネスト/大文字小文字/環境変数連結でキーワードを迂回するか、非 JNDI の式利用に替える(直接 SpEL/OGNL 実行、JNDI を経由しない)。迂回は式構文層で行う。
**Q4**: JDK 高版で JNDI が打てない?
**A4**: SpEL/OGNL なら、そもそも JNDI に依存する必要がなく、式で直接 `Runtime.exec` を呼んで実行し、JDK の JNDI 制限を迂回する。式インジェクションが log4j-jndi より柔軟なのはここだ。
**Q5**: 式がサンドボックスに制限された(読取のみ評価)?
**A5**: データ漏えいに転じる。式で環境変数/システム属性/設定(認証情報を含み得る)を読む。RCE できなくても。あるいは本当のデシリアライズ面に戻る。

### WAF がシリアライズストリームを遮断する迂回
**Q1**: Java シリアライズ payload が WAF に特徴(rO0/クラス名)で遮られた。どう迂回する?
**A1**: シリアライズストリームには特徴を乱せる複数の等価エンコードがある。先に試すのは、不要な base64 を外して raw にする、gzip と base64 の層順を変える、Java シリアライズプロトコルの同一オブジェクトに対する複数の正当な表現(TC_ マーク変種)を利用する。目的は静的特徴マッチを無効にしつつストリームを正当に保つことだ。
**Q2**: WAF がクラス名文字列(平文クラス名)を遮る?
**A2**: Java シリアライズストリームではクラス名は既定で平文だ。「平文クラス名の露出を減らす」チェーンに転じるか、シリアライズプロトコルの reference 機構/文字列 block 分割で連続するクラス名特徴を断つ。一部ツールはストリーム難読化をサポートする。
**Q3**: WAF が Content-Type/パラメータ位置を遮る?
**A3**: 配信方式に転じる。リクエストメソッドを替える、パラメータ位置を替える(body↔cookie↔header)、チャンク転送、charset 難読化。同じ payload でも位置を替えれば通ることがある。配信層の直交動作だ。
**Q4**: ストリーム難読化後に対象のデシリアライズも失敗した?
**A4**: 難読化がストリームの正当性を壊したことを示す。戻す。デシリアライズは形式に極めて敏感で、難読化はストリームが解析可能なことを保たねばならない。難読化後のストリームが依然 readObject できることをローカルで検証してから送り、対象で無造作に変更しない。
**Q5**: WAF が強すぎ、どのシリアライズ特徴も遮る?
**A5**: 攻撃面に転じる。この WAF を通らない入口(内部ネットワーク RPC ポート、他のサブシステム)を打つか、非シリアライズ脆弱性に替える。強い WAF の硬直迂回は費用対効果が低い。

### Ruby デシリアライズ(Marshal/YAML)
**Q1**: Ruby/Rails 対象で、デシリアライズを疑う。判定基準は?
**A1**: 特徴: Marshal データは `\x04\x08` 始まり(base64 後 `BAg`)。Rails の cookie/session は Marshal かもしれない。YAML(`yaml.load`)もオブジェクトをデシリアライズできる。判定基準はデータヘッダ + フレームワーク(Rails/Sinatra)だ。
**Q2**: Marshal で制御可能だ。どう利用する?
**A2**: 公開されている Ruby universal gadget チェーン(`Gem::Requirement`/`Gem::DependencyList` などを経由)で RCE を実現する。判定基準は、対象の Ruby/Rails 版に対応するチェーンが使えるかだ。
**Q3**: Rails cookie で署名がある(secret_key_base)?
**A3**: Shiro と同様、`secret_key_base` がないと偽造できない。secret の取得に転じる(設定漏えい/ソース/他の脆弱性)。署名が有効なとき、key なしでは偽造不可で、硬くぶつからない。
**Q4**: YAML.load だ?
**A4**: YAML 特有の利用に転じる。`!ruby/object:` タグで任意クラスをインスタンス化してチェーンを誘発する。対象が `safe_load` を使うならオブジェクトデシリアライズがなく、他面に転じる。
**Q5**: 全て安全なデシリアライズ/署名に塞がれた?
**A5**: Rails の他の古典面(mass assignment、動的 render、SQLi)に転じる。Ruby デシリアライズが通らないとき、フレームワーク層に他に道があることが多い。

### デシリアライズが本当に「sink に到達した」かの判定
**Q1**: payload を送ると異常エコーがあるが、「危険な sink までデシリアライズされた」のか「解析エラーだけ」か不明だ。どう区別する?
**A1**: 異常が発生する深さを見る。異常スタックが `readObject`/`resolveClass` の早期なら、入口層の拒否(filter/クラス不存在)で、sink に届いていない。異常が gadget チェーン中間クラスのメソッド内(InvokerTransformer/TemplatesImpl 関連)なら、チェーン実行段階まで深入りしており、sink に近い。スタックの深さが判定基準だ。
**Q2**: スタックが見えず、ブール式の成功/失敗しかない?
**A2**: 「段階的検証」チェーンを使う。先にチェーンの半分までで DNS を誘発する構築を送り、次に最後までで DNS を誘発する構築を送る。どの段の DNS が戻るかで、チェーンがどこまで進んだかがわかる。ブラックボックスの sink 判定を観測可能な段階に分解する。
**Q3**: 中間段は戻るが最終段は戻らない。チェーン末尾で詰まる?
**A3**: チェーン末尾クラスが対象に欠けるかバージョン不一致だ。等価なチェーン末尾(異なる最終 sink クラス)に替えるか、チェーン全体を替える。「どの段で詰まるか」を特定してから狙って替え、チェーン全体を盲替えしない。
**Q4**: 第一段すら戻らない?
**A4**: 入口が呑み込んでいないことを示す。制御可能性/エンコード層/filter の検査に戻り、チェーン調整を続けない。詰まりが入口かチェーン内かを判定することが、どちらの方向を直すかを決める。
**Q5**: 段階的検証もできない(外向き通信なし、差異なし)?
**A5**: 時間による段階分けに転じる。異なるチェーン段に異なる遅延を持たせる。それも駄目なら他の入口に転じ、ブラインド領域で無闇に調整しない。

### デシリアライズとメモリ馬を組み合わせた後の横展開意思決定
**Q1**: デシリアライズでメモリ馬/コマンド実行を得た。次は何をすべきか。直接横展開する?
**A1**: 先に本機の情報収集をしてから決める。急に乱スキャンして IDS を驚かせない。優先して読むのは、アプリ設定(DB/Redis/ミドルウェア認証情報)、環境変数、クラウドメタデータ、`~/.ssh`、history、内部ネットワーク hosts。デシリアライズの落点は往々にしてアプリサーバーで、設定内の認証情報が最速の横展開燃料だ。
**Q2**: DB/Redis 認証情報を取った。どう使う?
**A2**: 再利用を判断する。アプリの認証情報は内部ネットワークで複数箇所再利用されがちだ。それで内部ネットワーク DB/Redis に接続し、Redis 未認可/マスタースレーブ複製でもう一点落とす。認証情報再利用は内部ネットワーク横展開の第一の梃子だ。
**Q3**: 権限が低権限の web ユーザーで、横展開が制限される?
**A3**: 先に本機の権限昇格(SUID/カーネル/サービス設定/スケジュールタスク)で高権限を取り、それから横展開する。あるいは昇格せずに採集した認証情報で他マシンへ横展開する(横展開は本機 root を必ずしも必要としない)。二つの道を並行評価してどちらが近いかを見る。
**Q4**: 内部ネットワークが厳格にセグメント化され、このマシンが他に届かない?
**A4**: このマシンを足がかり/トンネル(ポートフォワード/socks プロキシ)にし、後続ツールがそれ経由で内部ネットワークへ届くようにする。セグメント化されたネットワークでは、落点の価値は「目標」でなく「チャネル」だ。
**Q5**: このマシンが純 DMZ の行き止まりで、何にも届かない?
**A5**: このマシンから採れた認証情報/情報で他の外部入口を打つ(漏れたアカウントで VPN/メール/他の公網向けシステム)、別の方向から内部ネットワークに入る。この点が行き止まりだと認め、次元を替えて進入する。

### デシリアライズ探査が対象をクラッシュ/アラートさせた後の対処
**Q1**: gadget をブラインド送信していると対象アプリが崩れたようだ/大量の 500 が出る。続けるか止めるか?
**A1**: 即座に減速して評価する。デシリアライズブラインド攻撃(特に誤ったストリーム)は OOM/スレッド蓄積を誘発しやすく、アプリを落とすと暴露しつつ自分の道も断つ。判定基準: 対象プロセスがクラッシュしたら、現在の session/token も失効し得るので、手を止めて回復を観察する。
**Q2**: 再び打ち崩すのをどう避ける?
**A2**: 正確な攻め方に転じる。まず URLDNS/分段探査でブラインド送信を最小化し、チェーンを確定してから有効な payload を一発だけ送る。「広く撒くゴミストリーム」を減らし、隠密且つ対象の可用性を傷つけない。
**Q3**: 既に WAF/IDS アラートを誘発し、IP が封じられるかもしれない?
**A3**: 出口/リズムを転換する。頻度を下げる、プロキシ出口を替える、時間窓を空ける。デシリアライズ利用は高頻度を必要とせず、遅く正確なほうが速く騒がしいより優る。
**Q4**: 対象が回復後に防御を加えた(前は打てたのに今は打てない)?
**A4**: 緊急応答を誘発したことを示す。ブルーチームのブラインド領域に転じる。入口を替える、時間帯を替える、より隠密な利用(逆接続の代わりにメモリ馬)を使う。防御側がこの面を監視していると仮定し、直交面に進む。
**Q5**: 対象が完全にオフラインになり、回復不能だ?
**A5**: この面は当面廃棄し、他の目標/他面に転じ、既知の脆弱性を記録して機会を待つ。レッドチームは長期アクセスを保全し、一点のために目標を殺さない。

### シリアライズデータがデータベース/キャッシュ内で二段階デシリアライズされる
**Q1**: 制御する入力が即時デシリアライズされず、先に DB/キャッシュに保存される。二段階デシリアライズを疑う。どう確認する?
**A1**: 「読取経路」を探す。データは保存され、別の機能がそれを読むときに初めてデシリアライズされる。判定基準: 送信後、「そのデータを読む」他の API(バックグラウンド表示、スケジュールタスク、キャッシュ読取)を誘発し、そのときに誘発するかを観察する。二段階利用は「注入点」と「誘発点」を分けて探す必要がある。
**Q2**: どの機能がそれを読むかわからない?
**A2**: 帯外プローブで「地雷を埋める」。URLDNS payload を保存し、各機能を広くクリックする/スケジュールタスクを待ち、DNSLog がどの瞬間に戻るかで誘発機能を特定する。時間と機能に自ら誘発点を晒させる。
**Q3**: 保存時にエスケープ/エンコードされ、デシリアライズ前に形式が壊れた?
**A3**: 保存層がバイトを変えるか(エンコード変換、エスケープ)を検査する。DB 文字セットがバイト変化を起こすなら、保存エンコードに逆算して構築する。文字エスケープに似て、ローカルで保存チェーンを模して揃える。
**Q4**: 誘発点が非同期/遅延(スケジュールタスク)で、検証が遅い?
**A4**: 忍耐の帯外検証に転じる。地雷を埋めた後 DNSLog を長期監視し、阻塞せず別を進める。二段階デシリアライズの誘発には遅延がつきもので、帯外チャネルで非同期に収穫する。
**Q5**: 読取/デシリアライズ誘発点が一つも見つからない?
**A5**: 保存されたのがデシリアライズされないデータだけかもしれない。その保存データの他の利用(保存型 XSS/SQL 二段階注入)に転じるか、面を替える。「保存すれば必ずデシリアライズされる」と仮定しない。

### 異常エコーでバージョンと依存をフィンガープリントする
**Q1**: 対象のデシリアライズが異常を投げ、部分的なスタックをエコーする。これをどう情報に変える?
**A1**: 異常スタックは無料の依存マッピングだ。スタック内のパッケージ名/クラス名がフレームワーク(spring/shiro/dubbo)を晒し、異常情報がライブラリ版を持ち得る。`serialVersionUID` 不一致エラーは対象クラスの UID を直接与える。体系的に収集し、正確な gadget 選定根拠を組み立てる。
**Q2**: 異常種別だけエコーしスタックを出さない?
**A2**: 「プローブクラス」で能動的に異常を引く。既知の特定ライブラリ/版にしか存在しないクラスを送り、存在有無が異なる異常を返す。異常種別の差異で依存を逆算する。エコーされる各 bit をフィンガープリントに搾り切る。
**Q3**: serialVersionUID mismatch エラーをどう直接使う?
**A3**: 対象クラスの UID を得たら、ローカルで同じ UID で gadget を再生成する(か対応版のライブラリを探す)。mismatch を消す。これは「エラー」を直接「突破」に変える最短経路だ。
**Q4**: 異常が全て 500 空ページに飲まれる?
**A4**: エコー情報経路が断たれたので、帯外(DNS)か時間側チャネルで依存探査する。無エコーでは異常に頼らず、探査チャネルを替える。
**Q5**: レスポンスステータスコードすら差異がない?
**A5**: 純時間探査か入口を替える。対象が完全に情報を漏らさないときブラインド攻撃コストは極めて高く、エコーのある他面を優先する。

### デシリアライズ点はあるが DoS しかできず RCE できない場合の取捨
**Q1**: デシリアライズが制御可能と確認したが、反復してもクラッシュ/資源枯渇しか起きず実行を得られない。投入産出をどう天秤にかける?
**A1**: まず「欠けているのが gadget か制御可能性か」を判定する。classpath に利用可能チェーンが全くない(純粋環境)なら、RCE 面が本質的に存在しない可能性があり、チェーン調整を続けるのは埋没費用だ。判定基準: 依存探査で既知チェーンなし + filter 厳格 → RCE 確率極低。
**Q2**: RCE 面なしと確認した。DoS に利用価値はある?
**A2**: レッドチーム目標では DoS は通常主線にしない(可用性を傷つけ、暴露する)。目標が可用性リスクの検証そのものでない限り、脆弱性を記録し、アクセス権を取れる面に転じる。
**Q3**: 何か gadget を見逃していないか?
**A3**: 「非標準のの gadget 源」に転じる。対象の自研クラスに利用可能な readObject/リフレクションロジックが潜むかもしれない。ソースがあれば、業務クラスのデシリアライズ副作用を監査し、公共 gadget ライブラリだけを見ない。自研チェーンは見落とされがちだ。
**Q4**: ソースがなく、業務クラスを監査できない?
**A4**: 他の攻撃面に転じる。無源、無公共チェーン、filter ありのデシリアライズ点は、ブラックボックスでの RCE が極めて難しく、時間をより柔らかい目標に振り向ける。
**Q5**: しかしこれが唯一の入口で、諦めがたい?
**A5**: ならばそれを SSRF/情報点として最大化利用する(内部ネットワーク探査、データ持ち出し)、対象の依存変更を継続的に注視する(新規コンポーネント投入が利用可能チェーンを持ち込み得る)。現在の状態で RCE に固執しない。

### jackson enableDefaultTyping の判定
**Q1**: JSON 入口に fastjson の `@type` はないが jackson の兆候がある。多態デシリアライズリスクの有無をどう判定する?
**A1**: jackson の危険なスイッチは `enableDefaultTyping()` か `@JsonTypeInfo` で、有効にすると JSON に `["クラス名", {...}]` の配列ラップ形式か `@class` で型を指定できる。判定基準: 型マーカーを注入してインスタンス化されるかを試す(DNS プローブ)。
**Q2**: 型を注入できると確認した。どう打つ?
**A2**: jackson の既知 gadget(JNDI クラス `com.sun.rowset.JdbcRowSetImpl`、C3P0/各種リモートロード可能な bean)で JNDI/RCE を誘発する。fastjson と発想は通じ、gadget クラスリストがやや異なる。
**Q3**: jackson 版が高く、ブラックリストが更新済み?
**A3**: ブラックリスト外の新しい gadget クラスに転じる(jackson の CVE 系列は利用可能クラスを増やし続けている)。版に対応する公開利用クラスを逐一試す。判定基準は版区間だ。
**Q4**: JNDI 後端が高版 JDK に制限された?
**A4**: 前と同じ。ローカル factory/デシリアライズ型 JNDI に転じて codebase 制限を迂回する。jackson→JNDI→ローカル gadget が汎用の降格経路だ。
**Q5**: 全て遮られたか、非既定 typing だ?
**A5**: default typing が有効でなければ、jackson デシリアライズ面はほぼ存在しない。他面に転じる。全ての jackson が利用可能と仮定しない。多数の既定設定は安全だ。

### WebLogic/ミドルウェアの T3-IIOP プロトコルデシリアライズ
**Q1**: Java アプリサーバーの管理ポート(T3/IIOP など)をスキャンで見つけた。プロトコル層デシリアライズを疑う。どう始める?
**A1**: この種のミドルウェアプロトコルはハンドシェイク後にクライアントデータをデシリアライズし、HTTP から独立した攻撃面だ。まずプロトコル探査でポートとバージョンを確認し、対応する既知のプロトコルデシリアライズ CVE を選んで payload を選ぶ。判定基準はポートフィンガープリント + バージョンだ。
**Q2**: 打つとパッチ済み(known CVE が修正済み)だ?
**A2**: 同一プロトコルの他の gadget/迂回変種に転じる。ミドルウェアのデシリアライズパッチはしばしば「ブラックリスト追加」で、歴史的に変種で繰り返し迂回されてきた。版に応じてパッチ後の迂回変種を探す。
**Q3**: HTTP は打てないがプロトコルポートは接続できる?
**A3**: これこそ価値だ。プロトコルポートは防御が疎かになりがち(WAF は HTTP しか見ない)。火力を HTTP から裸のプロトコルポートに移すのが、Web 層防御を迂回する直交次元だ。
**Q4**: プロトコルポートがファイアウォールで送信元 IP を制限している?
**A4**: 方向転換として、既に内部ネットワークに一点あれば、内部ネットワークからそのポートを打つ(管理ポートは往々にして内部ネットワークのみ開放)。外部から打てないミドルウェアポートも、内部ネットワークの足場を得れば往々にして開いている。
**Q5**: 管理ポートに全く届かない?
**A5**: HTTP 面に戻ってこのミドルウェアの他の穴(パストラバーサル、SSRF で管理ポートを逆打ち)を探すか、目標を替える。ミドルウェアプロトコル RCE は威力が大きいが到達可能性が必要で、到達できなければ割に合わない。

### 最終の最後の手段——デシリアライズの主線全体が死んだときの全局方向転換
**Q1**: このデシリアライズ点を判定、依存、gadget、迂回まで全て試して通らない。どう体系的に諦めと転換を決める?
**A1**: 「詰まり点の分類」で転換方向を決める。感情的な諦めではない。分類: 入口が制御不能 / 使える gadget なし / filter が厳しすぎる / 外向き通信なし・エコーなし / バージョン不一致。各分類が異なる直交出口に対応する。まずどの層で詰まっているかを明確にする。
**Q2**: 「使える gadget なし」で詰まる?
**A2**: 他の脆弱性種別(SQLi/SSTI/ファイルアップロード/ロジック)に転じる。これらは classpath gadget に依存せず、得手する確率が高いかもしれない。デシリアライズが唯一の RCE 経路ではない。
**Q3**: 「外向き通信なし・エコーなし」で詰まる?
**A3**: 帯内利用(メモリ馬/エコー構築)に転じるか、SSRF/情報点に降格する。詰まりは「チャネル」であって「脆弱性」ではない。チャネル次元で工夫する。
**Q4**: 「filter/WAF が厳しすぎる」で詰まる?
**A4**: 攻撃面移転に転じる。この防御を通らない入口(内部ネットワークポート、他のサブドメイン、API 版差異)を探す。防御は外層で、迂回できなければ扉を替える。
**Q5**: 全ての面が行き止まりで、対象全体が鉄壁に見える?
**A5**: 人/サプライチェーン/情報面に転じる。設定漏えい、第三者コンポーネント、社員認証情報、関連アセット。技術の正面が打てないとき、レッドチームの価値は次元を替えることにある(アセットマッピングで影のアセットを探す、サプライチェーンの弱点)。最硬の正面に無限投入せず、現在の進展を記録して戦略転換する。
