# Web · SQLインジェクション:判定→利用→読み書き→権限昇格

### あるパラメータが制御可能かもしれない。まず注入できるかを判定する
**Q1**: パラメータ付きの API を入手し、値が SQL に連結されそうだが、本当の注入点か不明だ。いきなり sqlmap を投げて草を驚かさず、第一歩はどう判定する?
**A1**: まず最小擾乱の差異判定を行い、すぐにデータを出そうとしない。数字型は `id=1 and 1=1` / `and 1=2`、あるいは算術等価 `id=2-1` を試す。文字型は単引用符で閉じた後、`'` と `''`、`'||''` / `' '` を対にする。判定基準は「ページ/返りコード/長さに再現可能な真偽の分岐が出るか」であり「エラーが出た」ではない。エラーは構文が変わったことしか示さず、真偽の分岐こそが式が WHERE に入ったことを示す。先に手動でロジックが通ることを確認し、それからツールを検討する。
**Q2**: 単引用符を足すとページが直接 500 を返すが、`and 1=1`/`and 1=2` に差異がない。これは注入か?
**A2**: 必ずしもそうではない。引用符が誘発したのが WAF/フレームワーク異常であって SQL 層ではない可能性がある。「構文がデータベースに解析された」と「文字が前置ロジックに遮られた」を区別する必要がある。等価式で引用符を迂回して試す。数字型は演算、文字型は緩い閉じか末尾のコメント `-- `。どの等価 payload にも差異がなければ、制御可能な注入点ではない確率が高い。
**Q3**: 真偽の分岐はあるが、特に不安定で、同じ payload が時に真になり時に偽になる?
**A3**: キャッシュ、ロードバランサの複数バックエンド、あるいは結果自体のランダム性(時間/ランダムソート付きなど)を疑う。他変数を固定する。同じ session/cookie に固定する、無関係の一意パラメータを加えてキャッシュを破る、連続複数回で最頻値を取る。複数バックエンドでデータが不一致なら注入は依然成立し得るが、「同一バックエンド」を基準に反復検証する。
**Q4**: 手動判定のこの道がまったく差異を出さず、エラーも出ない。どの直交次元に替える?
**A4**: 「非ブールの観測可能なチャネル」に転じる。時間ブラインド注入プローブ(`sleep`/重負荷サブクエリ)でレスポンス時延が制御可能かを見る。あるいは帯外(OOB)に転じる。DNS/HTTP 持ち出しで対象が解析を発起できるかを見る。それも駄目なら注入点面を替える。同一リクエストの他パラメータ、Header(UA/Referer/X-Forwarded-For)、Cookie、JSON body フィールド、二次注入の書込点。単一パラメータに固執しない。
**Q5**: 時間ブラインド注入の遅延も明らかでない。もう見込みがないのか?
**A5**: 対象が危険関数を制限しているか接続タイムアウトがあるかもしれない。敷居を下げる。短い sleep を複数回統計して平均値をベースラインと比較し、ネットワークジッタを排除する。重計算型の遅延(大範囲のデカルト積)に替えて sleep ブラックリストを迂回する。それでも動かなければ、この点は無エコーブラインド注入の価値がないと判定し、パラメータ/API の変更に戻る。

### 注入できると確認したら、まずどのデータベースでどの注入種別かを把握する
**Q1**: 注入成立を確認したが、バックエンドが MySQL/MSSQL/Oracle/PG/SQLite か、ユニオン/エラー/ブール/時間のどれが使えるかまだ不明だ。どう並べる?
**A1**: まずデータベースのフィンガープリントを探ってから利用形態を定める。フィンガープリントは方言差異の関数を使う。文字列連結(`+` vs `||` vs `concat`)、バージョン関数(`version()`/`@@version`/`banner`)、コメントスタイル、`limit` vs `top` vs `rownum`。種別判定は情報量の高い順に試す。ユニオンでエコーできるか > エラーでエコーできるか > ブール > 時間。情報量が最も多く且つ安定するものを打つ。
**Q2**: ユニオン注入の列数をどう素早く定める?`order by` を半分まで試して WAF に遮られた?
**A2**: `order by N` の二分で列数を探すのが最も省パケットだ。遮られたら `union select null,null...` に替え、エラーが出なくなるまで null を逐列足す。これでも列数を定められる。それも駄目ならエラー型で直接列数情報を吐かせる。鍵は「最少リクエストで列数とエコー位を確定する」ことで、線形に 1234 とゆっくり足さない。
**Q3**: 列数は合っているがページがデータを表示せず、一行目だけか全く表示しない?
**A3**: エコー位が可視域にないか、元クエリが `limit 1` かもしれない。元クエリを無結果にしてエコーをこちらの行に譲る。前半を `and 1=2` にするか id を存在しない値にし、こちらのデータを union で先頭行に出す。エコー位の特定は識別可能な定数(特定の数字列など)を逐列入れ、どの列がページに表示されるかを見る。
**Q4**: データ型が一致せず、union 時に列型変換エラーが出る?
**A4**: エコー位はデータ型に敏感だ(特に PG/Oracle の強型)。全部まず `null` を入れて構造通過を保証し、対象エコー列だけを個別に文字列/数字に替えてその列の受容型を探る。`cast`/`convert` で明示的に型変換する。逐列試し、一度に全部替えない。
**Q5**: ユニオンとエラーが両方フィルタされ、ブール/時間だけが残り、効率が低すぎる。どうする?
**A5**: ブラインド注入を受け入れるがスループットを最適化する。順次列挙でなく二分で文字ごとに変える。取れるものは先に「構造」(データベース名/テーブル名/重要列名)を取り、その後定点で値を取る。全データベースをブラインドダンプしない。同時に OOB 持ち出しを並行評価する。対象が外向き通信できるなら、DNS 持ち出しは時間ブラインド注入より数桁速い。これは直交する高速化の次元だ。

### WAF があり、payload を送ると即遮断される
**Q1**: 注入点は本物だが、`union`/`select`/`'` などを含むと即 WAF に遮られる(403/リダイレクト/検証コード)。まずどの層が遮断するかを判定する?
**A1**: 先に遮断の階層を特定してから迂回を語る。遮断されるのが「キーワード」か「意味」かを見る。`union` 単独で遮断されればキーワードブラックリスト。`un/**/ion` が通れば単純なパターンマッチ。遮断レスポンスの特徴(固定ページ/固定ヘッダ/クラウド WAF banner)を観察して、クラウド WAF かアプリ同梱かを判断する。闇雲に tamper を当てず、先に敵を知る。
**Q2**: キーワード/正規表現ブラックリストと確認した。通常の迂回をどう配置する?
**A2**: 「字面を変え意味を変えない」ことを層ごとに試す。大文字小文字混在、インラインコメント `/**/`、等価関数置換(`concat`↔`concat_ws`、空白↔`/**/`↔`%0a`↔`+`)、エンコード(URL 二重エンコード、十六進、`char()`)。一度に一つの次元だけ変え、どの token がルールを誘発するかを特定して狙って迂回する。tamper スクリプトを一括で当てない。
**Q3**: 単パケットは通るが、連続数十パケットでレート制限/IP 封になる?
**A3**: これは頻度/行動検知で、payload 問題ではない。減速+分散。ランダム遅延を加える、出口 IP/プロキシプールを交代する、長接続を再利用してハンドシェイク特徴を減らす、ブラインド注入の文字数を最少に絞る。アカウント級の不正検知なら session を替える。戦略を「内容を迂回する」から「騒音を下げる」へ移す。
**Q4**: 各種変形が通らず、WAF が強すぎる。この注入は廃棄か?
**A4**: 直交次元に替えるのであってこの一つのパラメータに固執しない。その一、注入位置を替える。WAF は query だけを重点視することが多いので、body/JSON/multipart/Header/Cookie を試す。あるいは HTTP パラメータ汚染(同名パラメータ複数)でバックエンドに未フィルタの方を取らせる。その二、プロトコル/エンコード入口を替える。チャンク転送 `Transfer-Encoding: chunked`、`Content-Type` 変形、charset 差異(GBK のワイドバイトがエスケープ引用符を食うなど)。その三、完全に穴を替える。この点は記録し、別の脆弱性面を探す。
**Q5**: ワイドバイトがあると疑うが確信がない。どう素早く検証する?
**A5**: バックエンドフィルタが `'` を `\'` にエスケープするとき、文字セットが GBK 類なら `%df%27` が `%df%5c` を一つの正当な漢字にしてバックスラッシュを「食い」、`'` が逃げる。判定基準: `%df'` を注入して構文エラーか真偽の分岐が出ればワイドバイトが成立。成立しなければその次元を排除し、エンコード/位置の迂回に戻る。
**Q6**: クラウド WAF が強固に遮る。WAF を迂回して直接源站を打てるか?
**A6**: 独立した直交試行としてあり得る。源站の実 IP を探す(履歴 DNS、証明書 SAN、サブドメイン、SSRF 戻り、メールヘッダ)。源站が WAF だけを信じるアクセス制御をしていなければ、源站へ直結すればクラウド洗浄を完全に迂回できる。これは「ルールを迂回する」でなく「防御アーキテクチャを迂回する」ことで、一撃で致命になりがちだ。

### ブラインド注入が遅すぎる。チャネルを格上げしたい
**Q1**: ブール/時間ブラインド注入しかなく、数万文字で朝までかかる。もっと速いチャネルは?
**A1**: 優先して帯外(OOB)を評価する。対象が外向き通信できるかを判定する。DBMS が自発的に DNS/HTTP を発起する payload を構築する(MSSQL の UNC/`xp_dirtree`、Oracle の `utl_http`/`dbms_ldap`、MySQL は `load_file` と UNC の特定条件下併用)。自分が制御する DNS 権威ログで subdomain の持ち出しデータを受ける。一度のリクエストで一段を持ち出せ、逐文字のブラインド注入よりはるかに速い。
**Q2**: 対象が外向き通信しない。OOB は行き止まりだ。まだ高速化できるか?
**A2**: ブラインド注入に戻るが問題規模を圧縮する。まず「メタデータと位置情報」(どのデータベース、どのテーブルが認証情報テーブルか、対象列名)だけをブラインドし、少数の高価値行を正確に取る。全データベースドラッグを諦める。二分、ビット単位、一括並行リクエストで文字ごとのコストを最低に圧縮する。目標を「データをドラッグする」から「次へ進める最小集合をドラッグする」に変える。
**Q3**: OOB は通ったが短い断片しか出ない。長いデータが切られる?
**A3**: DNS ラベルには長さ制限がある(単一ラベル 63、全体 253)。分片で持ち出す。データを切ってエンコードし、複数のサブドメインに分けて送る、あるいは十六進/base32 エンコード後に連結する。異なる接頭辞で分片順をマークし、権威ログ側で再構成する。これは工学問題であり、チャネルの失敗ではない。
**Q4**: 時間ブラインド注入も OOB も不安定で、レスポンス/戻りが時々ある。
**A4**: 冗長と検証を導入する。各判定を N 回反復して多数を取る。OOB はリクエスト nonce を加えて対応ビットを関連付ける。時間ブラインド注入はネットワークジッタに応じて適応閾値を設定する。根本原因が対象側の非同期/接続プールによる時系列の乱れなら、時系列に依存しない観測可能量(エラーコードの分岐、行数の分岐)に替える。

### データを取れた。次はファイル読取/書込をしたい
**Q1**: 任意クエリができるが、欲しいのは足場確保能力で、サーバーファイルを読むか webshell を書くことだ。まずこの権限があるかを判定する?
**A1**: まず「ファイル権限」という直交能力を探る。注入=読み書きできると仮定しない。MySQL は `load_file` できるか、`secure_file_priv` が空か、アカウントに FILE 権限があるか。MSSQL は `xp_cmdshell`/`OPENROWSET`/`BULK` があるか。PG は高権限で `COPY`/大オブジェクト/`pg_read_file` が使えるか。判定基準は「既知の存在するシステムファイルを一つ読めるか」で、読めてから書く話をする。権限探査が失敗したらこの線で時間を浪費しない。
**Q2**: MySQL で `into outfile` で webshell を書きたいが書けない?
**A2**: 詰まり点を逐一排除する。`secure_file_priv` が非空且つ非対象ディレクトリ→任意パスに書けず、許すディレクトリにしか書けない。web ルートの絶対パスが不明→まずパスを取る手段を考える(エラー漏えい、設定ファイル読取、phpinfo、ログ)。ディレクトリが可書でない/所有者が違う→可書ディレクトリに替える。`--secure-file-priv=NULL` で完全無効→この道は完全に塞がった。各歩に独立した判定基準があり、「書けない」とひと括りにしない。
**Q3**: Web の絶対パスが取れず、outfile の手掛かりがない?
**A3**: 「パス取得」の子問題に転じる。手段は、エラーを誘発して物理パスをエコーさせる、フレームワーク/ミドルウェアの設定ファイルを読む(既知の既定パス)、プロセス/環境情報を読む、サーバー既定サイトパスリストを読んで逐一試す。あるいはファイル書込を諦め、「ファイルを読んで認証情報/ソースを取る」というより敷居の低い線に替える。DB 設定、鍵、ソースを読めれば横展開に十分なことが多い。
**Q4**: ファイル書込権限が全くなく、読取も `secure_file_priv` で制限された。足場確保のこの道が断たれた。どう転じる?
**A4**: 「ファイルシステム」でなく「データそのもので権限昇格する」方向へ転じる。データベースを読めるなら高価値データへ直行する。バックグラウンド管理者の hash(解読後にログインして機能点で getshell)、他システムの再利用認証情報、API key/鍵、session、暗号鍵。データベース注入の価値は getshell でなく「データベースに別所への鍵が眠っている」ことにしばしばある。目標を足場確保から認証情報収穫に変える。
**Q5**: MSSQL で `xp_cmdshell` を開きたいが閉じられている?
**A5**: 現在のアカウントが sa か `sysadmin` を持つなら、`sp_configure` で `xp_cmdshell` を再び開ける(`show advanced options` が必要)。権限が足りず開けないなら、他の実行面に転じる。`OLE Automation`、CLR アセンブリ、`OPENROWSET` でローカル実行、プロキシジョブ(SQL Agent)。どれも駄目ならファイル読取/認証情報収集の線に戻る。権限不足のときはコンポーネントを硬く開かず、先に身元レベルを確認する。

### 注入から直接コマンド実行/getshell を取りたい
**Q1**: SQLi から直接 RCE に行きたい。どのデータベース/設定にネイティブな実行経路があるか、まず実現可能性を判定する?
**A1**: データベースごとに可能性を列挙してから検証する。MSSQL は `xp_cmdshell`/CLR/OLE が最も直接的。PG は高権限で `COPY TO/FROM PROGRAM`、あるいは悪意ある拡張/大オブジェクトで UDF を落とす。MySQL は UDF(`lib_mysqludf_sys`)がプラグインディレクトリへ書けて且つ高権限である必要があり敷居が高い。より現実的なのは `into outfile` で webshell を書くこと。Oracle は `java`/`dbms_scheduler`/`utl` 系。まず「現在のアカウント権限レベル」と「対象コンポーネントが有効か」を判定し、低権限アカウントに UDF を空想しない。
**Q2**: MySQL で UDF 権限昇格して実行したいが、条件がいつも満たされない?
**A2**: UDF は依存が苛烈だ。root 級 DB アカウント、プラグインディレクトリを特定して書ける、`.so`/`.dll` のアーキテクチャ一致が必要。どれかが満たされなければ UDF を諦め、`into outfile` で webshell を落とす(敷居がはるかに低い)。UDF は「Web 層に書ける場所がなく、純粋な DB チャネルしかない」ときだけ無理に攻める価値がある道だ。判定基準: 先にアカウントが root@localhost 級かを確認し、そうでなければ UDF で消耗しない。
**Q3**: getshell は成功したが落ちたのは低権限 web ユーザーで、システム権限からまだ遠い?
**A3**: これは予期通りだ。SQLi の足場確保は通常 www-data/apache/mssql サービスアカウントを与える。「本機の権限昇格」の直交段階に切り替える。Linux は SUID/sudo/カーネル/スケジュールタスク/能力ビット、Windows はサービス権限/未引用符パス/トークン/`SeImpersonate`(サービスアカウントが持ちがちで、Potato 系で権限昇格できる)。SQLi 段階はここでローカル権限昇格の知識線にバトンを渡す。
**Q4**: 各 RCE 経路が権限/コンポーネントで塞がれ、注入はデータを読むだけで実行できない?
**A4**: 「注入はデータ層で止まる」と受け入れ、価値を最大化してから次元を替える。読んだ認証情報/ソースで別の入口を探す。ソースのハードコード鍵、他サービスのパスワード、内部 API のロジック脆弱性。あるいは DB アカウントで他の同認証情報サービスに接続する(認証情報再利用の横展開)。RCE が唯一の勝利条件ではない。「次ホップへ通じるものを読む」ことも同様に戦局を進める。
**Q5**: データベースがホスティング/クラウド RDS で、本機のファイルシステムもコマンド実行もない?
**A5**: クラウドホスティング DB は天然に OS 実行面がない。xp_cmdshell/outfile を探すのをやめる。「データ + クラウド身元」次元に替える。高価値データをドラッグする、データベース内のクラウド AK/SK や接続文字列を探す、その DB インスタンスに束縛されたクラウドロールが利用できるかを評価する(アプリ側 SSRF でインスタンスメタデータを取るなど)。戦場をホストからクラウド制御面に移す。

### 二段階/保存型注入に遭遇し、単点探査が反応しない
**Q1**: パラメータに直接注入しても、その場でまったく反応しない。しかしデータが保存されて別所で誘発されると疑う。二段階注入をどう判定する?
**A1**: 二段階注入の入力点と誘発点は分離している。発想は、「書込型」機能(登録、プロフィール変更、コメント、インポート)に引用符/サブクエリ付き payload を埋め、「そのデータを消費する」機能(バックグラウンドリスト、レポート、連結クエリ箇所)で誘発するかを観察することだ。判定基準は「書込時は静か、読取表示時にエラーか挙動異常が出る」こと。入力点と潜在的誘発点の両方を同時に注視する。
**Q2**: 二段階を疑うが、保存データがどの機能で再び SQL に連結されるかわからない?
**A2**: 一意に追跡可能なマーク + 広く撒く。一意文字列付き payload を埋め、そのデータを表示/処理する全ページを巡回して誘発点を探す。あるいは payload に OOB 特性を持たせる(誘発即戻り)。そうすればどこで誘発されても信号を受信でき、ページごとに探す手間が省ける。
**Q3**: 誘発点は見つかったが、payload が書込時にエスケープされ、保存時点で安全になっている?
**A3**: 二段階の鍵の前提は「保存時にエスケープ、取出し時に再エスケープせず直接連結」だ。保存時に徹底的にエスケープされればこの道は通らない。発想を変える。「保存時にエスケープされない」チャネル(直接 `insert` する一括インポート、内部ソースを信頼する API)を探すか、取出し後に二次連結して原文を復元する場面を探す。
**Q4**: 二段階が無果で、通常の注入面に戻ってもパラメータ化に塞がれる?
**A4**: パラメータ化が覆いにくい構文位置に転じる。`ORDER BY`/`GROUP BY` の後の列名、`LIMIT`、テーブル名/列名の識別子、`IN()` リスト構築、動的連結のソート方向。これらの位置はバインド変数を使えないことが多く、パラメータ化コードの天然の欠け口だ。これは「値注入」と直交する「識別子注入」の次元だ。

### データをドラッグしたら hash で、解読で詰まる
**Q1**: 大量のユーザー hash を取った。パスワードを復元してバックグラウンドにログインし戦果を広げたい。第一歩は何か?
**A1**: まず hash 種別と加塩の有無を識別する。辞書を走らせるのを急がない。長さ/文字セット/形式接頭辞で MD5/SHA*/bcrypt/カスタム連結塩を判定する。判定基準が戦略を決める。無塩の弱い hash は先にオンラインレインボー/漏えいライブラリで秒で割れる。bcrypt/argon2 の強い hash は無理にブルートフォースせず、別の道に転じる。先に分類し、それから計算力を投じるかを決める。
**Q2**: 加塩か強い hash で、ブルートフォースの費用対効果が低すぎる。まだ割るか?
**A2**: 「高価値の単一アカウント」(最高管理者)だけに狙った解読を投じ、狙い撃ちの辞書(対象関連語+ルール)を使い、全量ブルートフォースしない。同時に直交する道に転じる。そのアプリにロジック迂回(パスワードリセット、session 偽造、権限外アクセスで直接バックグラウンドへ)、あるいは DB 内の既存 session/token/ログイン保持 cookie で身元を冒用する。パスワードを迂回するほうがパスワードを割るより速い。
**Q3**: 平文パスワードを一括解読した。価値をどう最大化する?
**A3**: 即座に「認証情報再利用」の横展開をする。同じパスワードを他システム(SSH/RDP/VPN/メール/他 Web バックグラウンド/DB)で試す。人はサイト全体で同じパスワードを使いがちだ。ユーザー名:パスワード をスプレー辞書に整理し、内部ネットワーク/外部アセットに低速でパスワードスプレーする。SQLi がドラッグした認証情報の本当の価値はクロスシステム再利用にある。
**Q4**: パスワードが全く割れず再利用もできない。このデータは無駄か?
**A4**: 無駄ではない。用途の次元を替える。データ自体が、ソーシャルエンジニアリングと情報収集(メール/携帯/組織構成)、管理者アカウント名を見つけて後続のブルートフォース対象にする、システム間の関連識別に使える。同時に、見落とした非パスワード類の高価値データがないか振り返る。API 鍵、内部 URL、暗号鍵、設定。戦果は hash 一種ではない。

### バックグラウンド管理者を打ちたいが、一般ユーザーデータしか取れない
**Q1**: 注入で取れたのは一般ユーザーテーブルで、管理者がいない。欲しいのは高権限入口だ。どう続ける?
**A1**: まずデータ視野を広げてから決める。全データベース全テーブルを列挙し、管理/バックグラウンド/運用関連テーブル(命名に admin/manager/sys/backend を含みがち)を探す。判定基準: 現在の業務データベースだけを見ない。注入アカウントは複数データベースできることが多い。まず「どこに高権限アカウントが眠るか」を把握してから定点で取る。
**Q2**: 全データベースをひっくり返しても独立した管理者テーブルがない。バックグラウンドアカウントはどこに?
**A2**: バックグラウンドは独立システム/独立データベース/独立インスタンスかもしれず、現在の注入では届かない。方向転換として、取った一般認証情報で権限外アクセス(水平/垂直権限外アクセスで直接管理機能へ)、バックグラウンドログイン入口を別途打つ、一般ユーザーの中に高ロールを付与されたアカウントがないか(RBAC テーブルの role フィールド)を見る。管理者は「ユーザーテーブル」でなく「ロール関連テーブル」にいるかもしれない。
**Q3**: 管理者らしきアカウントを見つけたが hash しかなく割れない。直接変えられるか?
**A3**: 注入が書けるなら(スタッククエリ/書込機能あり)、UPDATE 改ざんを評価する。管理者 hash をこちらの知るパスワードの hash に変える、一般アカウント登録後に UPDATE で権限を上げる。リスクが高い(変更は監査され得る/業務に影響)ので、読経路が通らず且つ痕跡を受け入れられる場合のみ使う。優先は読取手段、データベース書き込みは重い手段だ。
**Q4**: 読取専用注入で、割れず、権限外アクセスもない。管理者取得のこの道が完全に塞がった?
**A4**: 「身元偽造」の直交次元に転じる。session 署名鍵/JWT secret/暗号 key(設定かデータベース内にありがち)を取れば、管理者 token を自分で署名して直接バックグラウンドに入れ、アカウントとパスワードを完全に迂回できる。あるいは「ログイン保持」トークン生成ロジックの欠陥を利用して偽造する。「アカウントを割る」から「認証情報を偽造する」へ。往々にしてより清潔だ。

### スタッククエリが使えるかが、攻め方の上限を決める
**Q1**: UPDATE/データベース書き込み/コンポーネント開設を実行したい。これらは複数文が必要だ。対象がスタッククエリ(`;` 区切り)をサポートするかを先に判定する?
**A1**: スタック対応はデータベース+ドライバに依存する。MSSQL/PG は通常サポート。MySQL の古典 `mysqli_query`/PDO は既定で複数文をサポートしない(明示的に開く場合を除く)。まず無害なプローブで検証する。`;select sleep(N)` か `;` の後に観測可能な副作用を一つ続け、実行されるかを見る。判定基準は「第二の文が効果を生んだか」であって「エラーが出なかった」ではない。スタックが使えれば書き込み操作/DDL/コンポーネント開設が全て解錠される。
**Q2**: スタック探査が反応しない。サポートしないのか `;` がフィルタされたのか?
**A2**: 「ドライバ非対応」と「WAF がセミコロンを遮る」を区別する。エンコード/位置を替えて `;` を試す(URL エンコード、改行、コメント包み)ことで第二文を実行できるかを見る。どの形式でも副作用がなければ、基本的にドライバ層が複数文をサポートしていないので、認める。このとき書き込み操作は単文でできること(`into outfile`、サブクエリ副作用)だけに頼り、`;update` を期待しない。
**Q3**: スタックが使える。書き込み操作前にどんなリスクを先に評価すべきか?
**A3**: データベース書き込みは高影響操作で、まず可逆性と監視を評価する。データ変更は業務異常を誘発し得る、DBA に発見され得る、ロールバックできない。原則: 読経路で目標を達成できるなら書かない。書くなら優先して「新規の制御可能な行を追加」し「既存行の改ざん」をしない。原値を記録してロールバック可能にし、トリガー/監査のあるテーブルを避ける。レッドチームは痕跡を制御できるべきだ。
**Q4**: スタックをサポートせず、且つ書/実行が必須だ。他に道は?
**A4**: 「単文副作用」次元に転じる。単文で成立する操作もある。MySQL の `into outfile`/`into dumpfile` はスタック不要でファイルを書ける。サブクエリ内で副作用のある関数を呼ぶ、エラー注入内に操作を埋め込む。あるいは OOB/ファイル足場確保で複数文の要求を迂回する。本当に駄目なら純読取に戻り、SQLi を「実行器」でなく「情報源」と位置付ける。

### JSON/API/ORM 場面で、旧式の注入の手応えが失われる
**Q1**: 対象が現代 API(JSON body、GraphQL、ORM バックエンド)だ。単引用符を送っても反応がない。注入がないのか?
**A1**: 旧式の手応えで結論を下さない。現代スタックの注入面は変わった。ORM は多くがパラメータ化するが、連結は動的ソート、フィールド選択、ネイティブクエリ、`LIKE` 連結、`IN` リスト、ORM の `raw`/`whereRaw` 用法に現れがちだ。まず body のどのフィールドが最もネイティブ SQL に入り得るか(ソートフィールド、フィルタ、search)を判定し、全フィールドでなくこれらのフィールドに注入テストする。判定基準は依然真偽/時間/OOB の分岐だ。
**Q2**: JSON のフィールドが文字列で、注入 payload の引用符が JSON 構造を壊す?
**A2**: JSON 値内ではエスケープ `\"` を使うか、引用符を含まない数字型/関数型 payload を使う。二層の解析に注意する。JSON 解析の一層、SQL 解析の一層で、payload は両層に同時に正当でなければならない。数字型注入は JSON 内で最も楽だ(引用符の悩みがない)。
**Q3**: GraphQL API だ。注入点はどこに隠れる?
**A3**: GraphQL の resolver の下層が SQL を連結するなら、注入点は query/mutation のパラメータ変数にある。argument を逐一測る。特にフィルタ、ソート、ページング、検索系パラメータ。GraphQL 構文に惑わされず、下層は依然あのデータベースで、判定方法は変わらない。
**Q4**: 現代 ORM が確かに全てパラメータ化し、通常の注入面が本当にない。どこへ転じる?
**A4**: ORM 自身の注入面と非 SQL データ層に転じる。ORM 層の欠陥: オペレータ注入(`{eq: x}` を `{gt: ""}` 系のクエリロジック操作に変える)、NoSQL 注入(バックエンドが Mongo などなら `$ne`/`$gt`/`$where` 注入)、一括代入。あるいは他脆弱性クラスに転じる。認証/権限外アクセス/SSRF/デシリアライズ。SQLi が打てなければ、このスタックがよく防いでいると認め、穴の面を替える。

### ソート/フィールド名などの識別子位置の注入
**Q1**: 値は全てパラメータ化されたが、`sort=column` のソートパラメータが直接 `ORDER BY` に連結されそうだ。これをどう利用する?
**A1**: `ORDER BY` の後は識別子位置で、バインド変数を使えず、パラメータ化コードの古典的な欠け口だ。まず検証する。`sort=1`/`sort=2` を送ってソート結果が変われば、列番号を制御できる。不正な列名を送ってエラーが出れば、連結されるのは列名だ。利用上、`ORDER BY` の後にサブクエリ/`CASE WHEN` を続けてブールブラインド注入できる(`order by (case when 条件 then col_a else col_b end)`)、ソート結果の差異でデータを読む。
**Q2**: `ORDER BY` 箇所では union が使えず(位置が違う)、ブラインド注入は遅すぎる?
**A2**: `ORDER BY` 位置は元々 union しにくい。バックエンドが MySQL/PG なら、この位置でエラー型サブクエリのエコーを試すか、`CASE WHEN` のブールブラインド注入。高速化したければ時間/OOB プローブを CASE 分岐に入れる。これは「低帯域」注入点だと受け入れ、重要な位置情報を取るだけに使い、全データベースをドラッグしない。
**Q3**: アプリが sort パラメータにホワイトリストをした(既定の列名のみ受け付け)。この点は廃棄か?
**A3**: ホワイトリスト識別子は正しい防御で、この点は確かに廃棄だ。同一リクエストの他に連結され得る位置に転じる。ソート方向 `asc/desc` の後、`LIMIT`/`OFFSET`(あるデータベースではここにもサブクエリを入れられる)、グループフィールド、値型パラメータ面に戻る。一つの API に複数の連結点があり、一つがホワイトリストでも全部ではない。
**Q4**: アプリ全体の全識別子位置がホワイトリストだ。識別子注入の次元が閉じた?
**A4**: 開発者がこの種に意識的であることを示す。値注入面に戻って手法を格上げする(二段階、WAF 迂回)、あるいは全く異なる脆弱性クラスに替える。同時に記録する。防御が成熟したアプリは単点が難しく、重心を「ロジック脆弱性/設定誤り/サプライチェーン」というコード監査が覆いにくい面に移すべきだ。

### 注入は成立するが完全に無エコー・無エラー・明らかな時延なし
**Q1**: ロジック上注入は成立する(payload を変えると安定した真偽の分岐がある)が、ページはいつも同じで、エラーもなく、sleep も明らかでない。情報をどう絞り出す?
**A1**: 実はブールチャネル(真偽の分岐)を手にしている。ただ観測可能量がページ文字にないだけだ。条件で変わる計測可能なものを探す。HTTP ステータスコード、レスポンスボディ長(一バイト差でも)、リダイレクト有無、Set-Cookie 有無、レスポンス時間の統計差異、さらにある機能の副作用(「操作成功/失敗」など)。これらを 1/0 として逐ビット盲注入する。判定基準: 安定して二値化できる量を一つ見つければ続けられる。
**Q2**: 長さ/ステータスコードすら一定で、真偽の分岐がごく隠れた箇所にしか現れない?
**A2**: 分岐信号を増幅する。真/偽分岐に大きな差異を作らせる。真のときクエリを非常に遅くするか大量データを返させ、偽のとき速くする。あるいは真のとき観測可能なエラーを誘発し、偽のとき正常にする。既存の差異を受動的に探すのでなく、「観測可能な結果」を能動的に設計する。
**Q3**: 時間ブラインド注入がネットワークジッタに沈み、統計が出ない?
**A3**: S/N 比を上げる。sleep 倍率を上げてベースラインとの距離を広げる、各ビットを複数回サンプルして中央値を取る、外れ値を除く、相対比較(同じリクエストを二度送って真偽分岐を別々に測る)を使う。対象が sleep 時間を制限するなら、重計算遅延で代替する。工学上は必ず信号を絞り出せる。注入自体が成立しない場合を除く。
**Q4**: 全盲注入チャネルが塞がれた(無エコー・無時延・無 OOB)。この注入はまだ有用か?
**A4**: 「ブラインド状態の書/操作」次元に転じる。データを読めなくても、盲で操作を実行できるなら(スタック UPDATE/コンポーネント開設/ファイル書込)、依然進む。結果を見る必要はなく、副作用を発生させるだけでよい(盲で管理者パスワードを変える、盲で webshell を書いて後で直接アクセス)。「読取指向」から「操作指向」への転換が無エコー場面の鍵の転身だ。

### 権限が低すぎ、欲しいデータベース/テーブルを読めない
**Q1**: 注入アカウントの権限が非常に低く、`information_schema` は見えるが多くのデータベース/テーブルが access denied だ。どうする?
**A1**: まずアカウントが何に触れるかを正確に測ってから計画する。現在のアカウント権限(`current_user`、権限ビュー)、読めるデータベースを調べる。判定基準が出たら「読める高価値目標」に集中し、denied のテーブルに硬くぶつからない。低権限アカウントも同データベース業務データ内の認証情報を読めることが多い。
**Q2**: 現在のアカウント権限が厳しく制限され、高権限 DB アカウントへ権限昇格したい?
**A2**: DB 内の権限昇格経路を探す。設定ファイル/接続文字列を読んでより高権限アカウントのパスワードを取る、データベース自身の脆弱性(既知 CVE、既定アカウント)を利用する、ファイルを書けるなら webshell を落として OS 層から DB root 設定を読む。あるいは同インスタンスの他データベースに眠る高権限認証情報を横方向に探す。DB アカウントの権限昇格は「より高権限アカウントのパスワードを読む」ことに頼ることが多く、SQL 特権の格上げではない。
**Q3**: 読取専用の単データベースアカウントで、権限昇格のパスワードすら読めない?
**A3**: DB 権限が頭打ちだと認め、OS/アプリ次元に転じる。webshell を足場確保できれば(低権限でも)、ファイルシステムから DB 主設定を読んで root 接続文字列を取る。あるいは既存の低権限データでアプリ層/横展開の突破口を探す。DB 権限が唯一の進捗バーではない。
**Q4**: 権限昇格も足場確保も完全にできず、この一データベースしか読めない。戦術的にどう位置付ける?
**A4**: それを「情報ノード」として使い切る。読める全データをエクスポートして認証情報収穫と情報集約を行い、横展開とソーシャルエンジニアリングに与える。同時にこのアセットを「低価値・既に搾り切った」とマークし、主攻方向を他のアセットに移す。レッドチームは損切りを会得し、枯れた井戸で時間を消費しない。

### webshell を取った後、データベースへ戻ってさらに操作したい
**Q1**: 注入で webshell を落とし、本機実行を得た。データベースを振り返って利用するのに何の増分がある?
**A1**: webshell を手にすれば、DB 利用方式が格上げされる。DB 設定ファイルを直接読んで高権限接続文字列を取り、ローカルクライアントで全権でデータベースに接続し、注入の諸制限(WAF、盲注入、権限)から脱する。このときすべきは「制限付き注入から直結の高権限セッションへの転換」で、効率が天地の差になる。
**Q2**: 設定の DB アカウントが高権限だ。接続後に横展開で何をする?
**A2**: 高権限 DB セッションは、全データベースエクスポート、他データベースの認証情報読取、MSSQL/PG なら直接 OS コマンド実行で本機権限昇格、DB リンク(linked server/dblink)で他 DB インスタンスへ横展開できる。DB は内部ネットワークの信頼ハブであることが多く、一つの高権限 DB アカウントが複数台を繋げるかもしれない。
**Q3**: DB と web が別マシンで、設定のデータベースが内部ネットワークの別の一台にある?
**A3**: 良いことだ。これは横展開の手掛かりだ。webshell を足がかり/プロキシにして内部ネットワークのその DB に接続する。その DB の実行面(xp_cmdshell など)を評価して足場を DB サーバーへ拡張する。注入→webshell→DB 設定→内部ネットワーク DB ホストは、古典的な縦深チェーンだ。
**Q4**: DB 設定が暗号化か接続文字列がファイルにない。直結のこの道が断たれた?
**A4**: 他の認証情報源に転じる。プロセスメモリの dump、アプリ実行時の環境変数、フレームワークの鍵ライブラリ、履歴コマンド記録、他のサービス設定。あるいは注入チャネルに戻って使い続ける(制限付きだが使える)。直結が唯一の手段ではない。認証情報は複数箇所から掬える。

### 注入か別の脆弱性が働いているか判断がつかない
**Q1**: ある payload がページを異常にするが、SQL 注入か SSTI/コマンドインジェクション/XPath/LDAP 注入か不明だ。どう区別する?
**A1**: 各注入種別の特徴プローブを分けて打ち、誰が応答するかを見る。SQL は `'`/算術/`sleep`。SSTI は `{{7*7}}`/`${7*7}` が 49 を出すか。コマンドインジェクションは `;id`/`|whoami`/時延。LDAP は `*)(` 類。全ての異常を SQLi とせず、先に「脆弱性種別の鑑別」を行う。方向を誤ると大量の時間を浪費する。
**Q2**: 複数のプローブが反応する。同一入口に複数種の注入があるのか?
**A2**: あり得る。あるいはある種の副作用を誤判定している。「利用価値」で主攻を並べる。コマンドインジェクション/SSTI は通常直接 RCE に至り、SQLi のデータ読取より価値が高い。優先して実証する。SQLi は予備にする。最も直接 shell を取れる種を主線にする。
**Q3**: SQLi でなく別だと確認した。前の SQLi の発想は無駄か?
**A3**: 無駄ではない。判定手法は汎用だ(真偽の分岐、時間、OOB は種別をまたいで適用できる)。対応する種別の利用チェーンへ素早く切り替えればよい。レッドチームの注入判定フレームワークは共有で、種別を正しく識別したら武器データベースを替えるだけだ。
**Q4**: 各注入種のプローブが軽微に反応するがどれも利用できない。統一防御に遮られたようだ?
**A4**: 前に統一の WAF/入力フィルタがあり、全ての特殊文字を処理しているかもしれない。「特殊文字に依存しない」脆弱性面に転じる。ロジック脆弱性、権限外アクセス、認証欠陥、SSRF、ファイルアップロード、既知コンポーネント CVE。全ての「注入類」が文字フィルタに統一遮断されたとき、戦場は注入メタ文字を要しない脆弱性次元に移すべきだ。

### sqlmap が走らないが、点は本物だと思う
**Q1**: 手動判断ではこの点が注入らしいが、sqlmap を一括で走らせても出ない。まず何を疑う?
**A1**: まず「コンテキストを正しく与えていない」を疑うのであって「注入がない」ではない。sqlmap は既定で cookie/header/token(CSRF/使い捨て token)を正しく付けず、注入位置を識別せず、WAF 向け tamper を調えず、level/risk が低すぎて payload を漏らす。判定基準: 手動検証が成立した payload を手動で再送して点が本当にあることを確認し、それから sqlmap を狙って設定する(パラメータ指定、tamper 追加、level/risk 引き上げ、認証供与)。
**Q2**: 設定が全て合っても sqlmap が空手だ。ツール能力の限界か?
**A2**: そうだ。sqlmap は二段階注入、非標準エコー、複雑な WAF、多段状態が必要な注入には無力であることが多い。これらこそ手動の領分だ。ツールを盲信しない。手動検証が成立した点は手動で底まで掘る。sqlmap が走らない≠穴がない。
**Q3**: 手動で真偽の分岐は取れるがデータ取得が極端に遅い。sqlmap に盲注入ドラッグを引き継がせたい?
**A3**: 手動で見つけた正確な注入構文(閉じ方、コメント、迂回技)を sqlmap のカスタム注入マーク `*`、`--prefix/--suffix`、`--technique` で正確に指定し、sqlmap に「高速逐文字盲注入」という得意の力仕事だけをさせる。ツールは体力、人は判断を担う。
**Q4**: sqlmap と手動をどう調節しても安定データを引けない。点は偽かもしれない?
**A4**: 原点に戻って注入が本当に成立するかを再検証する(判定チェーンを見よ)。キャッシュ/ランダム/複数バックエンドによる偽分岐を排除する。再検証で分岐が再現できないとわかったら、この点を果断に諦め、他のパラメータ/API に転じる。誤判定を認めてタイムリーに転じるほうが、偽点で一晩消費するより勝る。

### データベース版/構造が要るが information_schema が禁じられた
**Q1**: データベーステーブル構造を列挙したいが、`information_schema` が制限かキーワードフィルタされた。どう迂回する?
**A1**: 代替メタデータ源を探す。MySQL は `mysql.innodb_table_stats`、`sys` データベース。MSSQL は `sysobjects`/`syscolumns`/`sys.tables`。Oracle は `all_tables`/`all_tab_columns`。PG は `pg_catalog.pg_tables`/`pg_class`。`information_schema` はその一種のビューにすぎず、各データベースに複数のシステムカタログが照会できる。
**Q2**: システムテーブルキーワード(`information_schema`、`sysobjects` など)が WAF に遮られる?
**A2**: キーワードに通常の迂回(コメント分割、大文字小文字、エンコード)を施すか、遮られない文字列を含まない代替カタログ名を使う。全メタデータテーブル名が遮られるなら、「構造を推測する」に退く。一般的なテーブル名/列名辞書で存在性をブラインド探索(`select 1 from users` のエラー有無で存在判定)、半盲で構造を再構築する。
**Q3**: 構造列挙がどうしても開かない。列挙せず直接値を取れるか?
**A3**: 取れる。多くの場合、完全な構造は不要だ。業務の常識で高価値テーブル列名を直接推測する(users/admin、username/password/email)ことで命中率が高い。目標指向。要るのは認証情報であって完全な schema ではない。列挙を飛ばして急所を直取する。
**Q4**: システムテーブル全禁、盲推測も当たらない。構造情報が完全に取れない?
**A4**: エラー/エコー漏えい次元に転じる。多くのフレームワークのエラーは SQL 断片、テーブル列名、パスを吐く。故意にエラーを誘発して構造断片を集める。あるいはフロントエンド/JS/API レスポンスのフィールド名からデータベース列名を逆算する(命名はしばしば一致)。構造情報はアプリ層の傍路から取得でき、全てを SQL メタデータに頼る必要はない。

### 対象にハニーポット/おとり注入点の疑いがある
**Q1**: この注入点は「順調すぎる」。即データが出て、権限が異様に高く、構造が専用に設えたようだ。ハニーポットを警戒すべきか?
**A1**: 疑いを持ち続ける。ハニーポット/おとりの特徴: 異常に容易な高権限、データが「完璧に魅力的」すぎる、レスポンスに怪しいマークがある、挙動が現実の業務ロジックに合わない。判定基準は「現実のシステムの複雑さと合わない」こと。動作を遅くし、先に低擾乱で偵察する。重手法(ファイル書込、コンポーネント開設)を急いで TTP を暴露しない。
**Q2**: ハニーポットを疑うが確信がない。どう低リスクで検証する?
**A2**: 破壊的操作でなく無害なプローブで探る。任意の payload に「協力的」かを見る(本物のシステムには本物のエラーと制限がある)、ドラッグしたデータが交差検証に耐えるか(他の情報源と突き合うか)、時系列/挙動が本物のバックエンドらしいか。ハニーポットは往々にして「過度に協力的」だ。
**Q3**: おとり環境とほぼ確認した。既に踏み込んでしまった。どうする?
**A3**: 即座に騒音を下げ、暴露面を評価する。高特徴の操作を止め、挙動が記録されたと仮定する。自分が使ったフィンガープリント可能な payload/ツール/出口を点検する。本当のレッドチーム交戦なら、インフラの変更(出口 IP、ツール特徴)を検討し、同じ TTP を真目標で再利用して関連付けられないようにする。
**Q4**: 真偽が分からず、進めないわけにもいかない。どうバランスを取る?
**A4**: 「多点交差検証」戦略に転じる。宝をこの一つの怪しい点に賭けず、他の独立入口から同時に傍証する。複数の直交情報源が互いに裏付ければ、本物の確率が高い。この点だけが異常に寛大で、他の面が全て堅いなら、それは餌である可能性が高い。単点の手応えでなく全体の一貫性で真偽を判断する。

### データ量が巨大だ。ドラッグ戦略をどう取捨するか
**Q1**: ドラッグできると確認したが、テーブルが百万行あり、盲注入で全ドラッグは非現実的だ。ドラッグ戦略をどう定める?
**A1**: 目標駆動で、全量をしない。まず「今回何が要るか」を明確にする。認証情報?特定人物のデータ?鍵?これに基づき正確な WHERE で必要な行列だけを取る(`where role='admin'`、`where username='X'`)。判定基準: 各リクエストは明確な目標に奉仕すべきで、機械的な dump ではない。盲注入場面ではリクエスト数を最小に絞る必要が特に高い。
**Q2**: ユニオンエコーが一度に多く取れる。単一リクエストの情報密度をどう上げる?
**A2**: 集約で多行多列を一つのエコー位に押し込む。`group_concat`(MySQL)/`string_agg`(PG)/`for xml`(MSSQL)で整列を一つの文字列にして一度に持ち出す。長さ切り捨て(`group_concat_max_len`)に注意し、必要なら分割する。ユニオン注入は「卸売」であって「小売」ではない。
**Q3**: ドラッグ中にレート制限/不正検知を誘発し、半分で切られた?
**A3**: 「速ドラッグ」から「安定ドラッグ」へ転じる。減速、分割、出口交代、中断点からの再開(取ったオフセットを記録して次回続ける)。あるいは単一リクエストの産出を上げて(集約)総リクエスト数を減らす。不正検知は速度問題で、工学手段で迂回する。能力問題ではない。
**Q4**: データが大きすぎ盲注入が遅すぎ、時間が足りない。どう損切りする?
**A4**: 「最小実行可能な戦果」の発想に転じる。全テーブルを諦め、次段階に入れる最小の認証情報集合(管理者アカウント数個で足りる)だけを正確に取り、取れたら横展開を進める。ドラッグは後でより良いチャネル(直結/webshell)を得てから補う。大量のドラッグに行動全体のリズムを殺させない。

### 注入がログイン画面にあり、直接認証を迂回したい
**Q1**: ログイン画面がユーザー名/パスワードをクエリに連結している疑いがある。ドラッグ以外に、直接注入でログインを迂回できるか?
**A1**: まず認証迂回を試す。ドラッグより速い。古典: ユーザー名箇所に `admin'-- ` でパスワード検証をコメントアウトする、`' or 1=1-- ` でクエリを恒真にして先頭ユーザーを返す。判定基準: 「検証 SQL」を恒真にできるか、目標アカウントだけにマッチできるか。まず「一行を調べて比較する」か「アプリ層でさらにパスワードを検証する」かを確認する。前者なら迂回で直接入れる。
**Q2**: `or 1=1` で入ったのは最初のユーザー(管理者でないかも)。admin に正確に入りたい?
**A2**: ユーザー名箇所に `admin'-- ` を指定して admin 行だけにマッチさせ、後続のパスワード条件をコメントアウトし、直接 admin 身元で入る。あるいは `' or username='admin'-- `。「どの行にマッチするか」を制御し、恒真でランダムな先頭行を取らない。
**Q3**: アプリが「先にユーザーを調べ、コードでパスワード hash を比較」する。注入でパスワード比較を迂回できない?
**A3**: クエリが返す行に hash フィールドが含まれコードで比較されるなら、union で一行偽造できる。クエリに username=admin、password=こちらの知る平文の hash という構成行を返させ、アプリの比較が通ればログインできる。注入を「条件迂回」から「返却データの偽造」へ格上げする。
**Q4**: ログイン画面がパラメータ化/プリコンパイルされ、認証迂回もドラッグも動かない。どこへ転じる?
**A4**: 認証体系の他の面に転じる。パスワードリセットロジック、検証コード/SMS 迂回、権限外アクセスでログイン後 API を直接アクセス、既定の弱いパスワードのスプレー、JWT/session 欠陥。ログイン SQL がパラメータ化されても認証フロー全体に隙がないわけではない。別の環を打つ。

### エラー注入だが、エラー情報が切り捨て/長さ制限される
**Q1**: エラー注入でエコーできるが、毎回ごく短い断片しか吐かない。データが取り切れない?
**A1**: エラーエコーには長さ上限があることが多い(MySQL エラーは約 30~60 文字可視など)。`substring`/`mid` でオフセット分割して逐段取り、連結して復元する。判定基準: 単回で見える長さを確定したら、その歩幅でスライド窓を動かして完全なデータを取る。これは分片の工学であり、障害ではない。
**Q2**: 分片が遅すぎる。より大きなエコーのチャネルに替えたい?
**A2**: union(単回エコー長がエラーよりはるかに大きい)か OOB(ほぼ長さの心配なし)への格上げを評価する。エラー注入は情報密度が低く、union/OOB に替えられるなら替える。エラー型は通常「他が全て駄目なときの最後の手段」で、より良いチャネルがあれば優先して捨てる。
**Q3**: エラー関数(`extractvalue`/`updatexml`/`floor` など)がフィルタされた?
**A3**: 同データベースの他のエラー誘発法に替える。MySQL には複数のエラー原語(幾何関数、型変換、重複キー)、MSSQL は型変換エラー(`convert`)、PG は `cast` エラー。一つのエラー関数が禁じられれば別の一つに替える。エラー注入の誘発方式は各データベースに複数の予備がある。
**Q4**: 全エラーがアプリに統一捕捉され汎用エラーページになり、エラー注入チャネル全体が失效した?
**A4**: 盲注入か OOB に転じる。アプリが詳細エラーを閉じるのは一般的な強化で、このときエラー型は行き止まりだ。ブール/時間盲注入に戻るか、帯外持ち出し。エラーエコーが消えても、情報は「挙動差異」と「持ち出し」から取れる。飲み込まれたエラーに固執しない。

### ファイルを書きたいが、どのディレクトリに書けるかわからない
**Q1**: FILE 書込権限があるが、どのディレクトリが可書且つ Web からアクセスできるか(shell を落とすため)わからない。どう定める?
**A1**: 二つの条件の交わりを求める。可書(DB プロセスアカウントに書権あり)+ 実行可能アクセス(Web ルートにあり且つスクリプトを解析できる)。まず Web ルートの絶対パスを確定する(エラー/設定/既定パス)、その下のよくある可書サブディレクトリ(アップロード/キャッシュ/一時)を選ぶ。判定基準: 無害な探査ファイルを書いて URL でアクセスでき且つ解析されるか。
**Q2**: Web ルートが可書でなく、あるアップロード/一時ディレクトリだけ可書だが Web ルートにない?
**A2**: 天秤をかける。可書ディレクトリが URL でアクセスできずスクリプトエンジンに解析もされないなら、webshell を落とす意味がない。このとき「ファイルを書いて別のことをする」に転じる。スケジュールタスク/スタートアップ/設定ファイルを書く(DB プロセス権限が届けば)、他プロセスが読んで実行する位置に書く。ファイル書込の価値は webshell だけではない。
**Q3**: ディレクトリは可書だがスクリプトエンジンが解析しない(静的ディレクトリに設定されている)?
**A3**: 解析される位置に替えるか、ファイル種別を替える(ミドルウェア解析特性/設定ファイル上書きでディレクトリを解析可能にする)。あるいは webshell を諦め、そのディレクトリに書いたファイルをデータ持ち出し/汚染用途に変える。解析権限は硬い制約で、迂回できなければ目標か用途を替える。
**Q4**: 様々なディレクトリをいじっても使える shell にできず、ファイル書込線が死んだ?
**A4**: 「ファイルを読んで認証情報を集める」と「データ層の権限昇格」に戻る。ファイル書込の敷居(パス+可書+解析可能の三条件)は元々苛烈で、ファイル読取の敷居ははるかに低い。FILE 権限があるなら、ソース/設定/鍵を読んで認証情報を横展開するほうが、無理に shell を落とすより割が合うことが多い。目標の優先順位を調整する。

### 注入の影響面を判断する:単データベースかインスタンス全体か
**Q1**: 注入を一つ取った。その「輻射範囲」を知りたい。現在の業務データベースだけか、DB インスタンス全体か内部ネットワークの他データベースまでか?
**A1**: アカウントのデータベース間到達可能性を探る。現在のアカウントが可視/可読の全データベース、複数データベース権限の有無、他インスタンスへ通じる DB リンク(MSSQL linked server、PG dblink、Oracle db link)の有無を調べる。判定基準がこの点を「局所戦果」か「内部ネットワークハブ」かを決める。現在のデータベースだけを見ず、先に影響面を量る。
**Q2**: linked server / dblink が他の DB インスタンスを指すのを見つけた。どう利用する?
**A2**: リンク経由でクロスインスタンスクエリ、さらには RCE を実行する(MSSQL linked server は `openquery` でリモート実行できることが多く、対端が高権限に設定されていれば、対端で xp_cmdshell をチェーンで開ける)。これは DB 層横展開の黄金経路だ。一つの注入が DB リンクを経由して複数の DB サーバーを繋げる。
**Q3**: リンクはあるが対端の権限が低い/実行できない。チェーン横展開が途中で断たれる?
**A3**: 対端が低権限でも、対端データを読んで認証情報を集められる。あるいは対端が第三台を指すリンクを持つか(複数ホップ)を列挙する。DB リンクネットワークは網状であることが多く、一本のチェーンが断たれても傍チェーンがあるかを見る。DB リンクのトポロジを内部ネットワーク地図として描く。
**Q4**: 孤立した単データベースで、リンクも複数データベース権限もない。輻射面が非常に小さい。どうする?
**A4**: それが葉ノードだと受け入れ、本データベースの価値(認証情報、鍵)を搾り切ってから OS 層と他アセットの横展開に転じる。同時にその DB ホスト自体が内部ネットワークの一台として持つ価値(そのネットワーク位置、到達可能性)を記録し、視点を「DB ロジック」から「このホストの内部ネットワークトポロジ上の位置」へ移す。

### PostgreSQL 特有の権限昇格からコマンド実行へ
**Q1**: バックエンドが PostgreSQL で、現在のアカウント権限が低くない。注入から OS コマンド実行へ、どのネイティブ経路がある?
**A1**: バージョンと権限で経路を選ぶ。高版のスーパーユーザーは `COPY ... FROM PROGRAM 'コマンド'` で直接システムコマンドを実行して結果を読み戻せる(スタックか COPY を実行できるコンテキストが必要)。あるいは悪意ある C 拡張/UDF を作る、大オブジェクトでファイルを書いてデータベース外スクリプトを落とす。判定基準: 先に superuser か `pg_execute_server_program` 系ロールのメンバーかを確認する。
**Q2**: superuser でなく、`COPY FROM PROGRAM` の権限が足りない?
**A2**: PG 内の権限昇格を探す。あるバージョンには superuser へ昇格できる既知の問題がある。あるいは `SECURITY DEFINER` 関数の誤設定、可書の高権限関数、`pg_shadow`/設定を読んでより高いアカウントを取る。どれも駄目ならファイル読取(`pg_read_file` があれば)、純データ収穫に退く。
**Q3**: スタッククエリが使えず、`COPY FROM PROGRAM` が複数文で使えない?
**A3**: 単文で使える実行/読取原語を探すか、注入を COPY を実行できるコンテキストに入れる工夫をする。確かに単 SELECT しかできないなら、PG のコマンド実行は多くが通らない。`pg_read_file`/`lo_*` のファイル読取か純データ線に転じる。複数文制限が PG RCE の本質的な制約だと認める。
**Q4**: PG の RCE 経路が全てバージョン/権限/スタック制限で塞がれた?
**A4**: データと横展開に転じる。PG はデータウェアハウス/バックエンドサービスにいることが多く、データベースに大量の業務認証情報、接続文字列、他システム token があるかもしれない。データを読み尽くして認証情報再利用の横展開をするほうが、PG RCE に固執するより速く効く。DBMS 選型に囚われず、目標はより多くのアセットの取得であって特定技法ではない。

### MSSQL が sa か高権限を取った後の縦深
**Q1**: MSSQL 注入で現在 sa/sysadmin だ。xp_cmdshell 以外にどう最大化する?
**A1**: 高権限 MSSQL は内部ネットワークの利器だ。全能力を列挙してから選ぶ。xp_cmdshell でコマンド実行、`xp_dirtree`/UNC で NTLM 持ち出しを誘発して中継/解読、linked server の横展開、OS ファイル読取、レジストリ操作、サービスアカウントコンテキストの取得。判定基準: 先に SQL Server サービスアカウントの身元を確認する(ドメインサービスアカウントであることが多く、価値が極めて高い)。
**Q2**: xp_dirtree/UNC で SQL Server にこちらの制御する SMB へ接続させたい。目的は?
**A2**: SQL Server サービスアカウントにこちらの SMB へ認証させ、その NetNTLM hash を捕捉してオフライン解読か NTLM 中継で他サービスへ使う。サービスアカウントがドメインアカウントなら、この一歩で戦果を「一つの DB」から「一つのドメイン身元」へ拡張できるかもしれない。DB→ドメインの古典的な足がかりだ。
**Q3**: SQL Server サービスアカウントが低権限のローカルアカウントで、取っても横展開できない?
**A3**: ならば本機の権限昇格を進む。SQL Server サービスアカウントは通常 `SeImpersonatePrivilege` を持ち、Potato 系(Potato)技術でローカル権限昇格して SYSTEM にできる。「ドメイン横展開」から「本機権限昇格」に転じ、この一台をまず取る。サービスアカウントの身元がどちらの道を進むかを決める。先に探る。
**Q4**: sa 権限だが対象が厳格な外向き通信/コンポーネント制限をしており、高権限が発揮できない?
**A4**: 外向き通信と危険コンポーネントに依存しない能力に転じる。純粋なローカルファイル読み書き(機密設定を読む)、linked server(内部ネットワーク横展開は公網外向き通信不要)、データ収穫。高権限の価値は RCE だけではない。内部ネットワークの信頼関係(linked server、サービスアカウント)がより隠密な縦深経路であることが多い。

### 注入がパラメータ化に遮られたが、動的連結の欠け口があると疑う
**Q1**: 主要パラメータはパラメータ化されたが、大きなアプリがどこも厳密なはずがない。漏れた連結点をどう体系的に探す?
**A1**: 「パラメータ化が覆いにくい位置」リストを絨毯式に巡る。ソート/グループフィールド、`LIKE` パターン、`IN` リスト、動的テーブル名列名、一括/インポート機能、レポートのカスタムクエリ、検索の高度フィルタ、新規/端材機能(旧コードはパラメータ化が良く、新機能は連結しがち)。判定基準: どの機能が「ユーザーにクエリ構造をカスタマイズさせる」か、そこに連結があり得る。
**Q2**: 機能が多すぎる。ブラインドテストせず優先順位をどう付ける?
**A2**: 「構造可変」と「新規/端材」機能を優先測る。ユーザーにソート選択、フィールド選択、フィルタ条件組み合わせ、エクスポート、検索をさせるものは連結確率が高い。明らかに単純 CRUD の成熟 API を避ける。ソースがあれば `raw`/文字列 SQL 連結のパターンを直接検索する。資源を高確率箇所に投じる。
**Q3**: 連結点を一つ見つけたがフィルタが厳しく、単点突破が難しい?
**A3**: 一つの欠け口で固執せず、先に横方向に同類でより緩い点がないか網羅的に調査する(同一開発者が書いた複数の動的クエリ機能は防御水準がまちまち)。防御が最も弱いものを突破口にする。多点比較し、柔らかい柿を選ぶ。
**Q4**: アプリ全体が確かにパラメータ化され、連結の漏れが見つからない。SQLi 次元が頭打ち?
**A4**: 現実を尊重し、他の脆弱性クラスに転じる。パラメータ化が徹底したアプリでは、SQLi の費用対効果が極めて低い。精力をロジック脆弱性、権限外アクセス、SSRF、ファイルアップロード、コンポーネント CVE、認証欠陥に移す。「このスタックは SQLi をよく防いでいる」と識別してタイムリーに転じるのは、熟練レッドチームの判断力であり、失敗ではない。

### DB 内の暗号化フィールドを取ったが、値が全て暗号文だ
**Q1**: ドラッグした高価値フィールド(ある認証情報/プライバシー)が暗号文で、平文でも標準 hash でもない。どうする?
**A1**: まず「可逆暗号」か「一方向 hash」かを判定する。可逆暗号ならどこかに鍵があり、鍵を取れば復号できる。目標を鍵探しに変える。判定基準: 暗号文の長さがブロックサイズの整数倍か(AES/DES 疑い)、IV があるか、base64 包みか。可逆なら key を探し、暗号のブルートフォースを試みない。
**Q2**: 可逆暗号と判断した。鍵はどこにあり得る?
**A2**: 鍵はしばしば、アプリ設定ファイル、コードのハードコード、同データベースの別テーブル、環境変数、鍵管理サービスにある。既に webshell/ファイル読があれば、アプリ設定とソースで暗号 key を探す。SQLi で暗号文をドラッグ + ファイル読で鍵を取る = 平文、二つの能力の組み合わせで完成する。
**Q3**: 鍵が取れず、暗号文が解けない。このデータは廃棄か?
**A3**: 必ずしも復号が必要ではない。ある場面では暗号文を直接「リプレイ」利用できる(暗号化 session/ログイン保持 token など、復号不要でそのまま使う)。その暗号文が「内容理解が必要」か「持っているだけで通行できる」認証情報かを判断する。後者なら復号せず直接使う。
**Q4**: 復号できずリプレイもできない。暗号データは完全に無用か?
**A4**: 他フィールドと他能力に転じる。同テーブル/同データベースには未暗号の高価値データが見落とされていることが多い(パスワードだけ暗号でメール携帯は平文、ソーシャルエンジニアリング/ブルートフォースに使える)。あるいはそのアプリの暗号実装に既知の弱点(弱い鍵導出、固定 IV、ECB モード漏えい)があり、単独で監査する価値がある。暗号データの傍路は実装欠陥にあり、力ずくの解読ではない。

### 注入速度が毎リクエスト 1 ビットに制限され、一括並行したい
**Q1**: 盲注入は毎リクエスト 1 ビット/文字しか確認できず、直列が遅すぎる。不正検知を誘発せずどう並行高速化する?
**A1**: 独立判定を並行化する。各文字位の各二分は相互に独立なリクエストで、並行送信できる。並行プールで複数ビットを同時に打つ。ただし「並行高速化」と「不正検知閾値」の間で均衡点を探す。まず小並行で対象のレート制限線を探り、封禁を誘発しない最大並行で走る。判定基準: エラー率/遮断率が上がれば並行を下げる。
**Q2**: 並行すると即レート制限、直列は遅すぎる。二律背反?
**A2**: チャネルを替えて総リクエスト数を減らすのが根治だ。単一リクエストで多く取る(集約/ビット演算で一度に複数ビット)、union/OOB へ格上げ。並行は「多くのリクエスト」を速く送るだけで、「リクエスト総数」を減らすのが本質的な高速化だ。高帯域チャネルに替えられるなら並行に固執しない。
**Q3**: 対象のレスポンスが遅く、並行しても全体が遅い?
**A3**: 毎リクエストのコストを最適化する。payload を簡潔に、接続を再利用、必要なデータだけ取る(先に特定、次に値の取得)。同時に価値があるかを評価する。対象が遅くデータ量も大きいなら「十分なら止める」を検討し、重要認証情報を取れたら次段階に転じ、ドラッグし切ることを求めない。
**Q4**: 各種高速化が限界で、時間予算が足りない。どう意思決定する?
**A4**: 「ドラッグ速度を上げる」でなく「データ需要を下げる」に転じる。再検討する。本当にこれほど多くのデータが要るか?通常は高権限アカウント数個か鍵一つで次へ進める。大量ドラッグの目標を「最小突破集合」に削れば、現速度でも時間内に取れる。戦術目標の縮小が最も有効な高速化だ。

### 同一注入点で、破壊的検証へ格上げすべきかの判定
**Q1**: 注入できると確認した。次に重手法(ファイル書込、コンポーネント開設、スタック DML)でさらに検証/利用すべきか?暴露と破壊のリスクがある。
**A1**: 「情報増分 vs 暴露/破壊の代価」で意思決定する。まず低リスク手段(読取専用クエリ、盲注入値の取得)で目標を達成できるかを尽くす。読取専用で進めず、且つ重手法が重要な増分をもたらすときだけ格上げする。判定基準: 各格上げの前に「この一歩が現在唯一の経路で、収益が暴露に値するか」を問う。検証のための検証をしない。
**Q2**: 顧客の認可範囲/交戦規則(ROE)で「書き込み操作」の可否が不明だ?
**A2**: 既定で保守的になる。レッドチームは認可境界内で行動すべきだ。データ変更/shell 足場確保が許されるか不明なら、読取での証拠取得を優先し、破壊的動作は明確な認可か必要なときまで残す。越界の「戦果」は功績でなくリスクだ。ROE が不明なら最小影響で行動する。
**Q3**: 読取専用で危害証明に十分だ。まだ getshell が必要か?
**A4**: 行動目標を見る。目的が「高危険 SQLi の存在証明」なら、機密データをドラッグした証拠で十分で、getshell でリスクを増やさない。目的が「これを足がかりに内部ネットワークへ深入り」なら、足場確保が必要だ。手段は目標に従い、技の見せびらかしのために不要な高危険操作をしない。
**Q4**: 重手法が必須と判断した。暴露と破壊をどう最小化する?
**A4**: 最小化の原則。操作前に原状を記録してロールバック可能にする、監査/トリガーのあるオブジェクトを避ける、改ざんでなく制御可能な追加を使う、足場物は打ち終えたら即清掃、並行と騒音を制御する。「必要な破壊」を「可逆、低騒音、清掃可能」にする。これが熟練レッドチームとスクリプトキディの分水嶺だ。
