# Web · ファイルアップロード迂回の意思決定

### アップロード点を見つけたら:まず「エコー契約」を把握してから動く
**Q1**: ファイルアップロード機能を見つけた。サーバーがどう処理するかまだ不明だ。第一歩は何をすべきか?
**A1**: 急に webshell を打たない。まず「最も良性」の正当なファイル(1x1 の gif/png など)を送り、3 点を観察する。レスポンスに【保存パス/ファイル名/URL】のエコーがあるか、ファイル名が【リネーム/ランダム接頭辞付与/タイムスタンプ付与】されるか、アップロードしたファイルに直接アクセスできるか。この 3 点が後続の全戦略を決める。パスが不明なら shell にアクセスできず、ファイル名が完全にランダム化されれば別の足場確保方式に頼る必要がある。
**Q2**: エコーにパスがまったくなく、アクセスも 404 だ。「足場確保してアクセス可能」という前提をどう確立する?
**A2**: 間接手掛かりを探す。画像系アップロードにはサムネイル/アバター表示がよくあるので、ページの img src を見てディレクトリ規則を逆算する。ダウンロード/エクスポート機能が実パスを晒すかもしれない。エラー情報(故意に超大か不正なファイルを送る)が絶対パスを漏らしがちだ。本当にパスがなければ、「アップロード+別の脆弱性の組み合わせ」の発想(アップロードとローカルファイルインクルード LFI の併用など)に転じる。
**Q3**: サーバーがファイルを純ランダム hash にリネームし且つ無エコーだ。単独のアップロードでは打てない。どこへ転じる?
**A3**: この道(直接 RCE)を先に棚上げする。【アップロードを原語とする】他の利用に転じる。①既知パスの設定/静的ファイルをアップロードで上書きする(条件競合かパストラバーサル)②XXE/SSRF 系のファイル解析脆弱性(悪意ある svg/xlsx/xml を送る)③保存型 XSS(html/svg をアップロード)。アップロードで足場確保できること自体が資産で、RCE が唯一の目標ではない。
**Q4**: このアップロード点が深掘りに値するかをどう素早く判断する?
**A4**: 判定基準: 足場確保パスを制御できるか + ファイル名拡張子を制御できるか + サーバーがファイル内容を解析するか。三つとも否なら価値が低く、優先して他の攻撃面に転じる。一つでもあれば見込みがあり、続ける。
**Q5**: 先に拡張子を試すか、内容を試すか?
**A5**: まず一度「ベースライン探査」をする。正常な拡張子+webshell 内容を送り、次に悪い拡張子+正常内容を送り、それぞれどこで遮断されるかを見る。これでフィルタが【フロントエンド/拡張子のブラックリスト/ホワイトリスト/内容検知/サーバー解析】のどの層にあるかを特定し、盲目的な総当たりを避ける。

### フロントエンド JS 検証:本質的にの紙でできた壁。ブラウザ内で戦って時間を無駄にしない
**Q1**: ファイル選択時にページが「jpg/png のみ対応」と出す。これはどの層の検証で、どう対処する?
**A1**: 極めて高い確率でフロントエンド JS 検証だ。判定基準: 遮断が【アップロードクリックの瞬間、ネットワークリクエストがまだ発されない】で起きる。この種の検証はプロキシに無意味だ。直接 Burp を開き、まず正当なファイルを送ってリクエストを発出させ、repeater で filename と content を変えるか、直接 JS を無効化/検証関数を削除する。
**Q2**: 遮断が本当にフロントエンドだけかをどう確認する?
**A2**: キャプチャして見る。遮断されたとき Burp に【対応する POST リクエストがまったくない】なら、純粋なフロントエンド。リクエストが発出され、サーバーが拒否を返したなら、サーバー側検証で、フロントエンド迂回は無効だ。
**Q3**: フロントエンド迂回後にサーバーも遮った。何を示す?
**A3**: 複数層の検証が存在し、フロントエンドは第一関門にすぎない。このとき注意を全てサーバーに移し、フロントエンドはもう気にしない。層ごとに分解を始める。拡張子?content-type?ファイルヘッダ?内容特徴?

### 拡張子ブラックリスト:等価な実行可能拡張子を逐一試す
**Q1**: サーバーが .php を拒否した。ブラックリストと判断した。どう迂回する?
**A1**: ブラックリストは「悪い拡張子を列挙するが列挙しきれない」ことを意味する。同エンジンの等価な実行可能拡張子を体系的に試す。PHP 系は php3/php4/php5/phtml/pht/phps/php7。ASP 系は asp/aspx/asa/asax/cer/cdx。JSP 系は jsp/jspx/jspf。逐一試し、足場確保でき且つ解析されるものを使う。
**Q2**: 全等価拡張子が遮られた。ブラックリストがかなり完全だ。次は?
**A2**: 【拡張子そのもの】でなく【解析層の欺瞞】に転じる。①大文字小文字の混在(.pHp、サーバーの拡張子比較が大小区別で解析は非区別なら)②拡張子に特殊文字を付ける(.php 空白、.php.、.php::$DATA[Windows]、.php/[一部環境])③二重書き(.pphphp、一度だけ置換する場合)。
**Q3**: これらの小細工も全廃だ。拡張子のこの道は死んだか?
**A3**: ほぼ死んだ。直交次元に転じる。【ミドルウェア解析脆弱性】(Nginx/Apache の設定欠陥で画像をスクリプトとして走らせる)か【内容型攻撃】(スクリプトの足場確保を追わず、ファイル解析を打つ)。拡張子でさらに磨かない。
**Q4**: ある迂回拡張子が本当にスクリプトとして実行されるか、足場確保されただけかをどう知る?
**A4**: 足場確保≠実行。足場確保後にアクセスし、返るのが【ソーステキストかそのままの内容】なら未解析。【実行結果/空白/期待出力】なら解析された。明らかな出力のあるプローブ(固定文字列を印刷)で判定し、純 webshell で盲接続しない。

### ホワイトリスト拡張子:戦場を「拡張子」から「解析」へ移す
**Q1**: サーバーが jpg/png/gif だけを許可し、ホワイトリストが非常に硬い。拡張子を迂回できない。どうする?
**A1**: ホワイトリスト下では拡張子そのものに固執しない。核心の発想を「【正当な拡張子のファイル】をスクリプトとして実行させる」ことに変える。三つの主路。①ミドルウェア解析脆弱性 ②サーバーがファイル名を include/解析ロジックに連結する(LFI と併用)③ファイル内容そのものが解析を誘発する(アップロードするのが include される設定/テンプレート)。
**Q2**: ホワイトリストが「最後のドットの拡張子を取る」可能性がある。複数拡張子で騙せるか?
**A2**: 試す価値がある。shell.jpg.php(拡張子検査が .jpg を見るよう騙す?通常駄目、最後のドットを取る)、shell.php.jpg(逆に、ミドルウェアを .php 解析に騙す。これは Apache の複数拡張子を右から左へ認識可能な拡張子を探す特性に依存)。判定基準は、サーバーの【拡張子を取るアルゴリズム】とミドルウェアの【拡張子を解析するアルゴリズム】が一致しないかを把握すること。不一致なら縫い目がある。
**Q3**: ミドルウェア解析脆弱性も存在しない(パッチ全適用)、ホワイトリストが鉄壁だ。どこへ転じる?
**A3**: 「アップロード即 RCE」を諦める。【アップロード+二次脆弱性】チェーンに転じる。正当な画像をアップロードするが内容に phar/シリアライズ payload を含め、phar://デシリアライズと併用する。あるいは svg/xml をアップロードして XXE を打つ。あるいはアップロードしたものを他のコンポーネントが消費するファイル(アバターがバックグラウンド管理ページに描画 → 保存型 XSS で管理者を打つ)。アップロードは入口にすぎず、利用点は他所にある。

### Content-Type 検証:MIME ヘッダを変えるのが最も安い一撃
**Q1**: アップロードが拒否され、Content-Type を検査していると疑う。どう迂回する?
**A1**: これは最も迂回しやすい層だ。Burp で multipart 内の `Content-Type: application/x-php` を `image/jpeg` か `image/png` に変え、内容と拡張子は動かさない。Content-Type はクライアント制御可能なフィールドで、サーバーがそれを信じるのは設計欠陥だ。
**Q2**: MIME を変えても拒否される。検証が MIME だけでない。本当の遮断点をどう特定する?
**A2**: 変数を制御する。悪い内容を固定して MIME だけ変える(遮断→純 MIME 問題ではない)、良い MIME を固定して拡張子だけ変える(変化→拡張子を検査)、拡張子を固定してファイルヘッダを変える(変化→magic bytes を検査)。次元ごとに隔離し、本当の検証次元を固定してから狙って打つ。

### ファイルヘッダ/magic bytes 検知:shell に画像の帽子を被せる
**Q1**: サーバーがファイルヘッダを読んで型を判定する(getimagesize 類)と疑う。どう通過する?
**A1**: ファイルの先頭に正当な画像の magic bytes を付ける。GIF は `GIF89a`、JPG は `FFD8FFE0`、PNG は `89504E47`。後ろにスクリプトコードを続ける。getimagesize/file コマンドに画像と誤判定させ、スクリプトエンジンはその中のコードを実行する(条件: そのファイルが最終的にスクリプトとして解析されること)。
**Q2**: getimagesize は通過したがまだ実行されない。問題はどこ?
**A2**: 二つのことを分ける。画像検証通過(内容層)とスクリプトとして実行される(解析層)は独立だ。画像の帽子は前者しか解決しない。後者は拡張子/解析脆弱性の併用が必要だ。解析の関門が越えられないなら、「ホワイトリスト/ミドルウェア解析」の支線に戻る。サーバーが画像を二次描画して付加データを洗い流すなら、下の「二次描画対抗」の専節に転じる。

### 00 切断:旧環境の一度きりの鍵
**Q1**: どんな条件で %00/0x00 切断を検討する?
**A1**: 前提は苛烈だ。PHP < 5.3.4 か特定の C 関数がパスを処理、且つ【パス/ファイル名が制御可能でファイルシステム呼び出しに入る】。場面は `upload/shell.php%00.jpg` で、システムが 00 で切断し、実際には shell.php と書かれる。判定基準: 対象が旧環境。現代環境ではほぼ無効だ。
**Q2**: 現代環境で 00 切断が見込みない。等価の「切断類」の発想はまだある?
**A2**: 他のパス処理欠陥に転じる。パストラバーサル(../ で足場確保ディレクトリを制御)、Windows の ::$DATA と末尾ドット/空白の除去、ファイル名の改行/特殊文字による解析曖昧。本質は全て「ファイル名が制御可能 + システムのファイル名正規化が不一致」だ。

### ミドルウェア解析脆弱性:サーバー設定に shell を実行させる
**Q1**: ホワイトリストが鉄壁だが、目標が Nginx/Apache/IIS だ。ミドルウェアをどう使う?
**A1**: 目標は【Web サーバーが非スクリプトファイルをスクリプトインタプリタに渡す】設定欠陥を利用することだ。Nginx の古典は `shell.jpg/x.php`(パス情報 + cgi.fix_pathinfo=1 で jpg を php として走らせる)。Apache は右から左へ複数拡張子を解析する `shell.php.jpg`。IIS6 には `x.asp;.jpg` のセミコロン切断と `x.asp/` のディレクトリ解析。先にミドルウェア種別と版を探り、対応技法を選ぶ。
**Q2**: 対象にこの種の解析欠陥があるかを盲試でなくどう確認する?
**A2**: 先にミドルウェア+版+PHP 実行方式(fpm/cgi/module)を精確にフィンガープリントする。cgi.fix_pathinfo 関連欠陥は特定設定でのみ成立する。無害なプローブファイルを送って対応パスでアクセスし、解析が誘発されるかを見る。明らかに不適なアーキテクチャで時間を消費しない。
**Q3**: ミドルウェアが最新版で、設定が安全だ。この道が完全に断たれた。どこへ転じる?
**A3**: アプリ層のロジックに戻る。【アプリが自分でアップロードファイルパスを include/require/テンプレート描画に連結する】箇所(LFI/テンプレート注入)、あるいは【アップロードファイルが他の機能に二次処理される】チェーンを探す。ミドルウェアが機会を与えなければアプリに与えさせる。

### .htaccess/web.config:解析規則を書き換える元武器
**Q1**: アップロードできるが拡張子が全て制限された。サーバーが「どう解析するか」自体を変えられるか?
**A1**: .htaccess(Apache)か web.config(IIS)のアップロードが許され且つディレクトリで効くなら、これは次元を下げる打撃だ。.htaccess をアップロードして .jpg を php として解析させる(AddType/SetHandler)、その後画像webshellを送る。前提は AllowOverride が有効、アップロードディレクトリに .htaccess を置けること。
**Q2**: .htaccess を送ったが効かない。原因は何で、どう調べる?
**A2**: 原因は通常、AllowOverride None、アップロードディレクトリが解析範囲外、ファイルがリネームされた、のどれかだ。調べる: .htaccess が原名で足場確保されたか(リネームされたら廃棄)、ディレクトリが Apache に管轄されているか。IIS 環境なら web.config の同様の経路に替える。
**Q3**: カスタム設定ファイルのアップロードが許されない。この手が使えない。代替は?
**A3**: 「既存の解析規則を利用する」ことに転じるのであって「新しい規則を追加する」ではない。つまりミドルウェアの既存の解析脆弱性、あるいはアプリ層の include ロジック。元武器が使えなければ通常のアップロード迂回マトリクスに戻り、詰まらせない。

### 条件競合:「足場確保から削除まで」の時間窓を打つ
**Q1**: アップロード後にファイルが即検知され削除される(先に足場確保してから検証)。まだ機会はある?
**A1**: ある。条件競合だ。ファイルが「ディスク書き込み」から「削除」までの間に微小な時間窓がある。高並行で同時に【shell を狂ったようにアップロード】と【その shell URL を狂ったようにアクセス】をする。あるアクセスが未削除の瞬間に命中し且つより持続的な足場確保を誘発すれば(shell 自身がさらに新ファイルを他所に書くなど)、勝ちだ。
**Q2**: 競合がずっと取れない。窓が小さすぎる。成功率をどう上げる?
**A2**: 並行を上げ+payload を「自己固化」させる。アップロードするスクリプト内容の第一の仕事が新しい webshell を別ディレクトリに書くこと(削除範囲から脱する)。こうすれば一度実行されれば永久に足場確保できる。同時に多スレッドでアクセスし、単機で足りなければ分散する。
**Q3**: サーバーが「検証通過してから足場確保」(メモリ内で検証)に変えた。競合窓が消えた。どこへ転じる?
**A3**: 競合のこの道は死んだ。内容/拡張子の迂回に戻って「検証を通過させる」か、他の攻撃面に転じる。条件競合は「先に足場確保して後で検証」アーキテクチャにしか効かない。アーキテクチャを識別してから使うかを決める。

### 二次描画対抗:圧縮の生存区にコードを隠す
**Q1**: 画像が GD ライブラリに再描画され、通常の画像webshellが全て洗い流される。コードをどう生き残らせる?
**A1**: 描画=デコードして再エンコードであり、一部のバイト区はこの過程で変わらないことを理解する必要がある。やり方: まず正常な画像をアップロードし、描画後の出力をダウンロードして、比較して【描画前後で変わらないバイトブロック】を見つけ、payload をその生存区に埋めてから再アップロードする。こうすれば二次描画後もコードが残る。
**Q2**: 生存区を探すのが面倒すぎる。もっと楽な判断は?
**A2**: 先に価値があるかを判断する。その画像が表示だけで、スクリプトとして解析されないなら、画像webshellを作っても RCE の意味がない。保存型 XSS か XXE に転じるほうが良い。そのときだけ「足場確保ファイルが解析実行できる」なら、二次描画対抗に終値がある。先に解析可能性を確認してから投入する。
**Q3**: 描画ライブラリが GD でなく Imagick だ。対抗戦略は変わる?
**A3**: 変わる。Imagick は攻撃面がより大きく、優先してその解析脆弱性(MVG/MSL/svg がコマンド実行、SSRF を誘発)を打つのであって、生存区の画像webshellを苦労して作らない。ライブラリが強いほど、「ライブラリを打つ」べきで「ライブラリを迂回する」べきではない。

### 圧縮パッケージのアップロード:解凍足場確保とトラバーサル
**Q1**: アップロードするのが zip/tar で、サーバーが自動解凍する。これにどんな機会がある?
**A1**: 二種。①【解凍パストラバーサル】(Zip Slip): 圧縮パッケージ内のファイル名に `../../` を含め、解凍時に目標ディレクトリから脱出し、任意の位置のファイルを上書きする(web ルートのスクリプト書き込み、crontab/authorized_keys の上書きなど)。②圧縮パッケージ内に実行可能拡張子のファイルを隠し、解凍でアップロード時の拡張子検査を迂回する(検査するのは .zip、解凍して出るのは .php)。
**Q2**: Zip Slip でファイルを書くが、どこに書けば RCE かわからない。どう目標を定める?
**A2**: 優先して上書きするのは、web ディレクトリのスクリプト(直接 RCE)、スケジュールタスクファイル、SSH authorized_keys、アプリ設定/自動ロードファイル。判定基準は「どのファイルがシステムかアプリに能動的に実行/ロードされるか」だ。web ルートパスが不明なら、先にエラー/情報漏えいで絶対パスを特定する。
**Q3**: 解凍に安全検証がある(../ と絶対パスを拒否)。トラバーサルが塞がれた。解凍をまだ利用できる?
**A3**: 【シンボリックリンク】(tar が symlink を保持: 先に /etc/passwd を指すソフトリンクをパッケージに入れ、読み取りを誘発)、あるいは【解凍爆弾/資源枯渇】で DoS を試す、あるいは「パッケージ内に悪い拡張子を隠す」という独立した支線に戻る。トラバーサルが塞がれても解凍機能に他の縫い目がないわけではない。

### SVG アップロード:XSS と XXE の二つの開口
**Q1**: svg のアップロードが許される。これは「無用な画像」か?
**A1**: むしろ逆だ。svg は XML で、天然に二つの開口を持つ。①埋め込み `<script>` → 保存型 XSS(svg がブラウザに直接描画されるとき)②svg は外部エンティティをサポート → XXE(ファイル読取/SSRF/内部ネットワーク探査)、特にバックエンドが XML パーサでそれを処理するとき。svg を普通の画像として素通りさせない。
**Q2**: svg 内の script が実行されない(img src として参照される)。XSS が空振りだ。どこへ転じる?
**A2**: img 参照は確かにスクリプトを実行しない。XXE に転じる。DOCTYPE 外部エンティティ付きの svg を構築し、バックエンド解析(サムネイル生成/寸法抽出)時に外部接続するかファイル内容をエコーするかを見る。OOB(自分の DNS/HTTP を打つ)で盲 XXE を確認する。
**Q3**: バックエンドパーサが外部エンティティを無効化した。XXE も消えた。svg に何が残る?
**A3**: 描画チェーンの下流に転じる。svg が png に変換されるなら(Imagick/rsvg)、変換器の解析脆弱性を打つ。svg が保存されて【本当にスクリプトを実行するページ】で include されるなら、スクリプト実行の発想に戻る。svg が死んでも「それが後で誰に消費されるか」を辿って続ける。

### アップロード+LFI の組み合わせ:足場確保できても実行できなければ、それを include する人を探す
**Q1**: ファイルはアップロードできるがサーバーが解析しない(純静的ディレクトリ)。同時にサイトに LFI がある。どう繋ぐ?
**A1**: 古典的な組み合わせ。アップロードするのは【内容がスクリプト、拡張子は任意】のファイル(.jpg 画像webshellでもよい)、それから LFI でそれを include する。LFI の include はファイル内容を実行し、拡張子を問わない。これで「アップロードディレクトリが解析されない」制限を迂回する。
**Q2**: LFI にパス制限がある(特定ディレクトリしか含められない)。アップロードディレクトリを含められない?
**A2**: PHP 擬似プロトコルとラッパーに転じる。`php://filter` でソースを読んで位置特定、`data://`/`php://input` で直接実行(allow_url_include なら)、phar:// とアップロードした画像webshellの組み合わせでデシリアライズを誘発。アップロードファイルを含められなければプロトコルに助けさせる。
**Q3**: サイトに LFI がない。この組み合わせが成立しない。代替の include 点は?
**A3**: 他の「ファイル内容をロードする」機能を探す。テンプレートエンジンがユーザーファイルを描画(→SSTI)、デシリアライズがアップロードファイルを消費、ログインクルード(先にアップロードでログを汚染してからログを含める)。核心は「誰がこちらの足場確保したバイトをコード/データとして消費するか」だ。

### Phar デシリアライズ:画像は偽装、phar が弾頭
**Q1**: アップロードが画像だけを受け、スクリプトを実行できない。しかしコードに phar:// が到達可能なファイル操作がある。どう打つ?
**A1**: phar デシリアライズを使う。phar ファイルを構築し、その meta-data を悪意あるシリアライズオブジェクトにして、phar 全体を jpg に偽装する(画像ヘッダを付けて検証を騙す)。その後、あるファイル関数(file_exists/fopen/getimagesize など)に `phar://アップロードパス` で誘発させると、デシリアライズが POP チェーンを実行する。
**Q2**: アップロードは通るが phar:// を誘発できる sink が見つからない。チェーンが断たれた。どうする?
**A2**: コード監査の視点に戻って sink を探す。ファイルパスを受け且つパス部分が制御可能な関数は全て候補だ。対象がブラックボックスでソースがないなら、機能から推測する(ファイルプレビュー、画像処理、添付検証)どこがアップロードファイルを二次読取するか。sink が見つからなければこのチェーンは成立しない。他へ転じる。
**Q3**: PHP 版が既に既定で phar メタデータを解析しない(8.0+)。phar チェーンが廃れた。どこへ転じる?
**A3**: 他のデシリアライズ入口(フレームワークの unserialize 点、session デシリアライズ)に転じるか、デシリアライズを諦めて通常の RCE 迂回マトリクスに戻る。phar には版の窓があり、失効したら弾薬を替える。

### パストラバーサルで足場確保位置を制御する
**Q1**: アップロードディレクトリが固定で解析されないが、filename フィールドが制御できそうだ。足場確保ディレクトリを変えられるか?
**A1**: パストラバーサルを試す。filename に `../../` を入れてファイルを web 解析可能なディレクトリかシステムの機密位置に書く。判定基準: サーバーが filename に正規化/basename 処理をしているか。していなければ隔離ディレクトリから脱出でき、不可解析を可解析に変えられる。
**Q2**: 直接 ../ がフィルタされた。トラバーサルが遮られた。変形をどう試す?
**A2**: エンコードと変種を試す。`..%2f`、`..%252f`(二重エンコード)、`....//`(一度 ../ をフィルタした後に残る)、Windows の `..\`、絶対パス注入。本質はフィルタロジックとファイルシステム正規化の不一致を探すことだ。
**Q3**: filename がサーバーに basename+リネームを強制された。トラバーサルが完全に無効だ。どこへ転じる?
**A3**: 足場確保位置が制御不能なら「shell を解析ディレクトリへ移す」ことを諦める。ミドルウェア解析、LFI include、あるいは現在のディレクトリを可解析にする(.htaccess)に戻る。パスが制御できないとき、「解析規則」を変えるほうが「ファイル位置」を変えるより現実的だ。

### ファイル名注入:足場確保パスがコマンド/SQL に入る
**Q1**: スクリプトとして実行する以外に、ファイル名そのものをどう利用できる?
**A1**: サーバーが filename を【shell コマンド】(convert/ffmpeg を呼んで処理など)か【SQL 文】か【ログ】に連結するなら、filename が注入点だ。filename にコマンド区切り文字 `;$(...)` か SQL 構文か XSS payload を含めるように構築し、ファイル実行を追わず、「ファイル名が消費されるときの誘発」を追う。
**Q2**: filename がコマンド実行に流れたかをどう判断する?
**A2**: filename に OOB プローブを含めて送る(`` `curl こちらのサーバー` `` か `$(nslookup こちらのドメイン)`)、外部接続が返るかを見る。盲注入の発想で、帯外チャネルで確認し、エコーに依存しない。
**Q3**: filename が特殊文字を厳格にフィルタされ、注入できない。似た面はまだある?
**A3**: 他の制御可能なメタデータに転じる。画像 EXIF/文書メタ情報がバックグラウンドに抽出されて表示されるかもしれない(→保存型 XSS/注入)、アップロード時の他のフォームフィールド。「ユーザー制御可能且つサーバーに二次処理される」フィールドは全て候補で、filename だけではない。

### 大文字小文字と拡張子正規化の不一致
**Q1**: 拡張子ブラックリストがかなり完全に見える。「大文字小文字/正規化」級の縫い目はない?
**A1**: 試す。①純大文字小文字 `.PHP/.pHp`(サーバーが小文字比較で、ファイルシステム/解析が大小非区別なら迂回できる、特に Windows)②拡張子に末尾ドット/空白 `.php.` `.php `(Windows が自動除去して .php に足場確保)③`.php::$DATA`(NTFS データストリーム、足場確保時に ::$DATA が除去)。これらは「検査時の文字列」と「足場確保後の実名」の不一致を利用する。
**Q2**: これらの技は Linux ではほぼ無効だ。プラットフォームが違う。どうする?
**A2**: 先に目標 OS を確認する。Windows 特性(末尾ドット、空白、::$DATA、大小非区別)は Linux でほぼ無効化する。判定基準は OS のフィンガープリントだ。Linux 環境なら精力を拡張子等価名、ミドルウェア解析、内容層に転じ、Windows 専有技で消耗しない。

### 二重拡張名と解析アルゴリズムの博弈
**Q1**: サーバーが「最後のドット以降の拡張子」を取ってホワイトリストする。二重拡張子で騙せるか?
**A1**: 鍵は【アップロード検証の拡張子取得アルゴリズム】と【ミドルウェアの解析拡張子取得アルゴリズム】を不一致にすることだ。アップロード検証が最後の一段を取る(.jpg を見て放行)、一方 Apache が右から左へ最初の認識可能な拡張子を見つける(.php に当たれば解析)なら、`shell.php.jpg` が検証通過と解析を同時に満たす。これは二つのアルゴリズムが喧嘩する産物だ。
**Q2**: ミドルウェアも最後の拡張子を取る(喧嘩しない)。二重拡張子が無用だ。どこへ転じる?
**A2**: 区切り文字を導入して第三者に曖昧を作る。`.php%00.jpg`(切断類)、`.php;.jpg`(IIS セミコロン)、`.php#.jpg`。あるいはミドルウェア規則自体に誤りを起こさせる(解析脆弱性)に戻る。アルゴリズムが一致するなら「文字層の曖昧」を作ってどちらかに誤判定させる。

### 空バイト/特殊文字でファイル名解析を汚染する
**Q1**: ファイル名に見えない/特殊な文字で解析曖昧を作りたい。どんな方向がある?
**A1**: 方向: null バイト(切断)、改行/キャリッジリターン(multipart ヘッダ解析を汚染し、追加フィールドを分裂させ得る)、セミコロン(IIS)、スラッシュ(ディレクトリを作る)、Unicode 同形/正規化(overlong UTF-8、全角ドット)。どれも「パーサと検証器が同じバイト列を別様に理解する」ことに賭ける。
**Q2**: この種の文字は多くが WAF/フレームワークに正規化された。汚染が無効化した。まだ試すか?
**A2**: 現代フレームワークは多くが正規化済みで、収益は逓減する。判定基準: まずプローブを一つ二つ送って洗浄されるかを見る。洗浄されるなら総当たりしない。ロジック層の欠陥(アルゴリズム不一致、二次処理)に転じるほうが文字級の汚染より投入価値がある。

### multipart プロトコル層の不正で WAF を迂回する
**Q1**: WAF がアップロードリクエストを遮るが、multipart の解析が不完全だと疑う。どう迂回する?
**A1**: WAF とバックエンドの multipart 解析差異を攻める。①filename に引用符/エンコード変種、複数の filename パラメータ、大文字小文字の `Content-Disposition` ②Content-Type 後に余分なパラメータか改行を加える ③boundary で工夫する(超長、特殊文字、大文字小文字)。目標は WAF が悪意フィールドを解析できずバックエンドが解析できるようにすることだ。
**Q2**: 具体的にどの変形から先に試すか。優先順位は?
**A2**: 「WAF は稀だがバックエンドは寛容」なものを優先する。filename の二重書き/エンコード、charset 難読化、multipart にゴミフィールドを入れて WAF の状態機械を乱す。判定基準は「WAF は A を見て、バックエンドは B を見る」解析の亀裂を見つけること。レスポンス差異(遮断/非遮断、足場確保/非足場確保)で有効な変形を二分して特定する。
**Q3**: WAF の解析がかなり堅牢で、プロトコル層が迂回できない。どこへ転じる?
**A3**: 「プロトコル層の欺瞞」でなく「内容層の検知回避」に転じる。WAF が遮るのは payload 特徴(`eval/system` など)かもしれない。ならば webshell 内容を難読化する(可変関数、エンコード、無エコー)ことで特徴マッチを無効にする。プロトコルが迂回できなければ特徴を迂回する。

### webshell 内容の検知回避:静的駆除を通過する
**Q1**: ファイルは無事足場確保され解析されたが、ワンライナートロイの木馬の内容が駆除/WAF に遮られた。どうする?
**A1**: これは内容対抗層だ。`eval($_POST)` のような高特徴の書き方を捨て、①関数名の動的連結/コールバック(call_user_func、可変関数)②payload をエンコード(base64/排他的論理和/gzip)して実行時に解く ③非標準のの実行関数を利用(バッククォート、assert 代替、pcntl、preg_replace /e 旧版)④明らかなキーワードのないワンライナー。目標は静的特徴を消すことだ。
**Q2**: 検知回避 shell は接続できるがトラフィックが検知される(行動層)。どうさらに進める?
**A2**: トラフィック層の対抗に転じる。暗号化トラフィック型webshell(冰蝎/哥斯拉類の発想。AES 暗号化通信)、C2 を正常パラメータに隠す、対話頻度を下げる。静的を過ぎてもトラフィックの関門が残る。層ごとに過ぎる。
**Q3**: 環境の駆除が極めて厳しく、足場確保即削除で、内容の検知回避も耐えられない。どこへ転じる?
**A3**: 「足場確保しない」利用に転じる。メモリ馬(デシリアライズ/式注入でメモリ内の悪意ある filter/servlet/ミドルウェアを登録し、ディスクに書かない)。駆除がディスクを見るならメモリを打つ。これは「アップロードで足場確保」から完全に転じる直交次元だ。

### メモリ馬:ディスク足場確保のこの道が殺し尽くされたとき
**Q1**: 全足場確保ファイルが即削除/即駆除される。アップロード足場確保のこの道が完全に死んだ。実行をどう維持する?
**A1**: メモリ馬に転じる。前提は既に一度のコード実行能力があること(アップロードが誘発した一時 RCE、デシリアライズ、式注入のいずれでも)。この実行でメモリに駐留する悪意コンポーネントを動的登録する(Java の Filter/Servlet/Listener、PHP の常駐プロセス/拡張、.NET の module)。以降は特定リクエストで誘発し、ディスクにファイルがない。
**Q2**: 一時 RCE はあるが再起動で消える。メモリ馬も失われる。どう天秤にかける?
**A2**: メモリ馬は永続性と引き換えにする。「再起動で生き残る」ことを犠牲に「ディスク無痕跡」を得る。判定基準は目標を見る。高対抗環境(EDR がディスクを殺す)ならメモリ馬を優先。長期駐留が必要なら監視のブラインド領域(非 web ディレクトリ、システムファイル偽装)に足場確保するかスケジュールタスクを加える。対抗強度で選ぶ。
**Q3**: 一度のコード実行すら得ておらず、アップロード足場確保しかない。メモリ馬の前提が成立しない?
**A3**: その通り。メモリ馬には先に RCE 入口が要る。アップロードしかないなら、「アップロードを RCE にする」全支線(解析/include/デシリアライズ)に戻る。メモリ馬は「実行済み後の駐留手段」であり、実行を得る手段ではない。本末を転倒させない。

### クラウドストレージ/OSS 直接アップロード:攻撃面が丸ごと変わる
**Q1**: アップロードが直接オブジェクトストレージ(S3/OSS)の事前署名 URL で進む。従来の webshell の発想が全く使えない。どうする?
**A1**: 攻撃面が変わった。オブジェクトストレージバケットは通常スクリプトを実行しない。RCE を考えない。①事前署名 URL/policy パラメータが改ざんできるか(key を変えて他者ファイルを上書き、content-type を変える、想定外パスへアップロード)②バケットが CDN オリジン取得を実行環境へ設定しているか ③SSRF でアップロードコールバックを経由して内部ネットワークを打つ ④保存型 XSS(バケットがホストする html/svg が同源でロードされる)。
**Q2**: 事前署名ポリシーが厳しく、バケットがよく隔離されている。直接アップロードそのものに縫い目がない。どこへ転じる?
**A2**: アップロードの「前後のロジック」に転じる。事前署名 URL を申請する API が権限外アクセスできるか(他者に代わって生成、key を列挙)、アップロード完了コールバックが偽造できるか(直接コールバックを呼んでシステムに送信完了と思わせる、コールバックパラメータを注入)、メタデータがバックエンドに消費される箇所。クラウドアップロードの縫い目は「ファイルそのもの」でなく「業務ロジック」にありがちだ。

### アップロード+SSRF:サーバーにファイルを取らせる
**Q1**: アップロード機能が「URL からファイルをインポート」をサポートする。何を意味する?
**A1**: 天然の SSRF だ。サーバーがこちらの与える URL をリクエストする。利用: ①内部ネットワークを探る(内部ネットワークアドレスを与えてレスポンス差異を見る)②クラウドメタデータを打つ(169.254.169.254 で一時認証情報を取る)③プロトコル密輸(file:// gopher:// でファイルを読むか内部ネットワークサービスを打つ)。アップロード機能が SSRF 入口になる。
**Q2**: URL にプロトコル/ドメインホワイトリストがあり、SSRF が制限された。どう迂回する?
**A2**: SSRF の通常の迂回に転じる。DNS rebinding、302 で内部ネットワークへジャンプ、IP エンコード変種(十進/八進/短縮アドレス)、@ 難読化、信頼ドメイン下のオープンリダイレクト。目標はホワイトリストが検証する URL と実際にリクエストする URL を不一致にすることだ。
**Q3**: SSRF が迂回できないが、インポート機能がリモート内容を保存して解析する。他にどう使う?
**A3**: 内容層に戻る。リモートに悪意ある svg/xml(XXE)、画像(処理ライブラリの脆弱性誘発)、超大ファイル(DoS)を返させる。SSRF が打てなければ「それを取り戻した後どう処理するか」を利用する。

### 文書系アップロード:office/pdf のマクロと解析
**Q1**: 対象が docx/xlsx/pdf のようなオフィス文書だけを受け付ける。どう打つ?
**A1**: これらは複合/構造化ファイルで、攻撃面は「解析と後続の消費」にある。①docx/xlsx は本質的に zip+xml → 外部エンティティを入れて XXE を打つ、Zip Slip ②文書が変換/プレビューされるなら(LibreOffice/wkhtmltopdf)→ 変換器を打つ(wkhtmltopdf の file:// SSRF/LFI、マクロ実行)③人にダウンロードされて開かれるなら → マクロフィッシング(ソーシャルエンジニアリング向け)。
**Q2**: 文書が保存されるだけで解析されず、人にも開かれない。静かに寝ている。価値は?
**A2**: 価値が低く、他のアップロード点か攻撃面に転じる。文書系の殺傷力は全て「解析される/開かれる」という二次動作にある。純保存は誘発条件がないのと同じだ。判定基準: この文書が後で誰に、どんな方式で消費されるかを追う。
**Q3**: 文書がサーバーで PDF プレビューに変換される。変換器が打点の重心だ。まず何を試す?
**A3**: 先に変換器種別を探る(レスポンス特徴/メタデータ)、それから狙って打つ。LibreOffice のマクロ/数式、wkhtmltopdf/Chrome-headless の SSRF+ローカルファイル読取(html に file:// か iframe 内部ネットワーク)、ImageMagick の委任コマンド注入。変換チェーンは文書アップロードで最も肥沃な面だ。

### アバター/資源がバックグラウンドに描画される:管理者を打つ保存型 XSS
**Q1**: アップロードした画像/資料がバックグラウンド管理画面に表示される。一般ユーザー視点では RCE がない。どう格上げする?
**A1**: 保存型 XSS で管理者を打つ。svg/html をアップロードできるか、ファイル名/EXIF に XSS payload を含められるか、且つバックグラウンド管理ページがそのまま描画するなら、管理者が開いた時点で被害に遭う。cookie/CSRF token を盗む、代わりに操作する、管理バックグラウンド機能を借りてさらに RCE。低権限アップロードが高権限を打つ横展開に変わる。
**Q2**: バックグラウンドが表示内容をエスケープし、XSS が発火しない。代替は?
**A2**: 他の「バックグラウンドに消費される」注入に転じる。ファイル名/メタデータがバックグラウンドの SQL に入る、バックグラウンドがコマンドを呼んでファイルを処理する(コマンド注入)、バックグラウンドのファイルプレビューが SSRF/XXE を誘発する。エスケープが防ぐのは XSS で、他の sink は防げない。sink を替えて続ける。
**Q3**: ファイルがバックグラウンドに見られるか全く不明だ。ブラインド領域をどう処理する?
**A3**: ブラインド攻撃プローブを埋める。OOB 戻りのある payload をアップロードする(svg に外部リンクを加える、EXIF に XSS beacon を置く)、管理者の誘発時の外部接続コールバックを待つ。帯外チャネルで「見えない消費者」を探り、戻りがあればこのチェーンが生きていることを示す。

### 無エコーブラインド伝送:OOB と差異でフィードバックを確立する
**Q1**: アップロード後完全に無エコー、アクセス不能、足場確保されたか不明だ。ブラックホールに打つようだ。成否をどう判断する?
**A1**: 帯外フィードバックを確立する。payload に自前の戻りを持たせる(webshell 内容の第一行が curl/dns でこちらのサーバーへ、svg/xml は外部エンティティで外部接続、ファイル名注入は OOB プローブ)。戻りがあれば=解析/消費された。無エコーは無フィードバックと等しくない。OOB でフィードバックを作る。
**Q2**: OOB すら戻らない。本当に打てていないのか、外向き通信が制限されたのか?
**A2**: 二者を区別する。DNS 外部接続(HTTP より出やすい)に替えて外向き通信が制限されたかを測る。DNS も戻らなければ、純内部ネットワークで無外向き通信かもしれない。OAST の多プロトコル試行に転じるか、「時間/レスポンス差異」という外向き通信不要のブラインド判定基準に替える(sleep を誘発してレスポンスが遅くなるかを見るなど)。
**Q3**: 対象が完全に外向き通信せず、差異も測れない。ブラインド伝送が全く無フィードバックだ。どこへ転じる?
**A3**: この点のブラインド攻撃を諦め、エコーのある攻撃面に転じて情報を蓄積するか、先に外向き通信を解決する(プロキシ/トンネルを探す)してから戻る。無フィードバックの点は費用対効果が極めて低い。固執せず、記録して移る。

### ファイル上書き:新規 shell でなく既知の重要ファイルを書き換える
**Q1**: 新規の実行可能ファイルを増やせないが、アップロードして目標パスを制御できる。他に勝ち方がある?
**A1**: ある。既存の重要ファイルを上書きする。目標: 設定ファイル(悪意ある設定/デバッグ開放に変える)、自動ロード/インクルードのファイル、静的資源(フロントエンドサプライチェーンを打つ)、依存/テンプレートファイル、認証関連ファイルの上書き。新規ではなく、システムが既に実行/信頼するファイルを改ざんする。
**Q2**: 「上書きに値し且つ上書きできる」ファイルをどう見つける?
**A2**: 判定基準は二つ。そのファイルがシステム/アプリに能動的にロード/実行される(誘発価値がある)+ アップロードがそのパスに書ける(到達可能)。フレームワークの自動ロードファイル、スケジュールタスク、可書のテンプレートキャッシュを優先する。先に情報漏えい/エラーで実パスを特定し、可書性を評価する。
**Q3**: 目標ファイルの権限が読取専用で、上書きが失敗する。どこへ転じる?
**A3**: 他の可書且つ価値のある位置(一時ディレクトリ、キャッシュディレクトリ、ログ)に転じるか、「新規+解析させる」主線に戻る。上書きは権限制約を受ける。書けなければ目標か手法を替え、特定のファイルに固執しない。

### アップロードサイズ/種別制限が引き出す境界攻撃
**Q1**: アップロードに厳格なサイズ/数量制限がある。それを迂回する以外に、制限そのものを攻撃点にできる?
**A1**: できる。①超大ファイル/大量ファイルで資源枯渇 DoS を試す ②サイズ検証がフロントエンドか迂回可能なら、バックエンドにフォールバックがなく想定外のファイルを送ってストレージを破壊する ③分割アップロード/中断点からの再開 API にロジック脆弱性がありがちだ(分割番号の範囲外、マージ時のパストラバーサル、総サイズ未検証)。制限機構そのものの実装に欠陥があり得る。
**Q2**: 分割アップロード API で重点的に何を見る?
**A2**: マージロジックを見る。分割ファイル名/パスが制御可能か(トラバーサル)、分割機構で最終ファイルへの拡張子/内容検査を迂回できるか(検査がマージ前か後か)、同名分割の並行アップロードの競合。分割は「一つのアップロード」を多段に分解し、各段の受け渡しに縫い目があり得る。

### 複数のアップロード点:横方向に比較して最も弱いものを探す
**Q1**: サイトに複数のアップロード機能がある(アバター、添付、インポート、リッチテキストの画像貼付)。どれを打つかどう選ぶ?
**A1**: 一つだけを見ない。横方向に比較する。異なるアップロード点は往々にして異なるコード/異なる人が書き、検証強度が不揃いだ。リッチテキストエディタの画像貼付、バックグラウンドインポート、旧機能モジュールは検証が最も緩いことが多い。まず各点に素早くベースライン探査をし、「検証が最も弱い + 足場確保が最も解析されやすい」ものを選んで打つ。
**Q2**: 主アップロード点は鉄壁だが、別に隠れたアップロード API が未防備だ。この種の点をどう発見する?
**A2**: 能動的に掘る。サイト全体のトラフィックをキャプチャして全ての multipart リクエストを見る、ディレクトリブルートフォースで upload/import/api API を探す、JS を掘って隠れたアップロードエンドポイントを探す、エディタ/プラグイン同梱のアップロードルートを見る。防御は往々にして「目立つ」点にだけ付けられ、隠れた点が突破口だ。
**Q3**: 全アップロード点が同じく厳格(統一ゲートウェイ検証)で、強弱を分けられない。どこへ転じる?
**A3**: 統一検証層があるなら、その層の汎用迂回(プロトコル不正、解析差異)を打つ。一箇所迂回すれば全箇所通る。あるいはアップロード攻撃面から完全に離れる。統一防御は「一つを迂回=全部を迂回」を意味する。集中してその層の亀裂を探す。

### 全線行き詰まり:一歩引いてアップロード点の本当の価値を再評価する
**Q1**: 拡張子、内容、解析、競合、組み合わせを全て試した。このアップロード点がどうしても打てない。続けるべきか?
**A1**: 止まって再評価する。レッドチームは時間コストを制御すべきだ。判定基準: この点が唯一の経路か?唯一でなければ、試した次元を記録し、他の攻撃面(他の機能、他のホスト、他のプロトコル)に転じる。単点への固執は新人病で、熟練者は「機会費用」を評価する。
**Q2**: 「アップロード次元を確かに尽くした」ことをどう体系的に確認してから撤く?
**A2**: マトリクスリストを一巡する。フロントエンド/MIME/拡張子のブラックリスト/ホワイトリスト/ファイルヘッダ/二次描画/ミドルウェア解析/htaccess/競合/トラバーサル/二重拡張子/プロトコル不正/内容検知回避/組み合わせ利用(LFI/phar/XXE/SSRF)/クラウド直接アップロード/文書解析/保存型 XSS。各次元にチェックを付ける。全てチェック且つ縫い目なしで初めて尽くした。撤収できる。
**Q3**: 撤収した後、この偵察をどう無駄にしないか?
**A3**: アップロード過程で蓄積した情報(絶対パス、OS/ミドルウェア版、バックエンドフレームワーク、外向き通信状況、内部 API)は他の攻撃面にも同様に有用だ。それらを全体の意思決定に与え、この「失敗点」を他経路の布石にする。レッドチームに無駄に打った点はなく、あるのは活かしていない情報だけだ。
