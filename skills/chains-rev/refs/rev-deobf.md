# リバースエンジニアリング PWN · 難読化解除とアンチデバッグ対策

### 未知のバイナリを手にしたとき、最初の一太刀はどこに入れるか
**Q1**: 出所不明の ELF/PE を手にして、パッカーがあるのか、難読化されているのか分からない。時間を無駄にしないためにまず何をする?
**A1**: まず「トリアージ」の三連を行う:`file` でアーキテクチャ/ビット数/static かどうか/strip かどうかを見る。`checksec` で保護(NX/PIE/Canary/RELRO)を見る。`strings`/`rabin2 -z` で可読文字列を走査する。この 3 ステップが以降のすべてのルートを決める。どんな状況でもコストゼロで先に行う。判定基準:strip+高エントロピー+平文文字列なし → 高確率でパックまたは難読化。平文文字列が多数(printf フォーマット文字列、エラー、アルゴリズムのマジックナンバー)→ 直接静的解析を開始する。
**Q2**: strings に可読文字列がほとんどなく、"usage" すらない。何を示すか?
**A2**: 全体の .text が暗号化されている(パッカー/SMC)か、文字列が実行時に復号されるかのどちらか。急いで IDA を使わず、まずセクションのエントロピー値(`ent`/IDA のセグメントエントロピー)を見る。エントロピー>7.2 の大きなブロック = パック/暗号化データ。
**Q3**: では「標準パッカー」か「独自/難読化」かをどう素早く判断する?両者は投入が天と地ほど違う。
**A3**: 入口点を見る。標準パッカー(UPX など)の入口は小さな stub 内にあり、セクション名に特徴がある(UPX0/UPX1)。独自難読化の入口は通常のコードだがジャンクコード/平坦化で満ちている。前者は瞬時にアンパックでき、後者は長期戦になる。
**Q4**: file が static かつ strip と示し、IDA では sub_xxxx ばかりでシンボルがない場合、どう素早く意味を復元する?
**A4**: FLIRT/署名(IDA lumina、同バージョン libc の bindiff)で libc 関数を復元する。static バイナリではまず __libc_start_main を識別して本当の main を見つけ、それから I/O 関数(read/write/printf)から相互参照を逆に調べてコアロジックを特定する。
**Q5**: トリアージを終えてもまだどこから着手していいか分からず、情報量に溺れている。どこへ方向転換する?
**A5**: 「動的優先」の直交する次元へ方向転換する。直接動かして `ltrace`/`strace` でシステムコールとライブラリ呼び出しの系列を見る。挙動が、どのファイルを読むか、どのポートに接続するか、何を比較するかを教えてくれる。静的で行き詰まったとき、挙動の観測はしばしば一言で意図を暴く。
**Q6**: 判定基準を再利用できる一言にまとめると?
**A6**: エントロピー/シンボル/平文文字列の 3 つの信号 → 「アンパック vs 難読化解除 vs 直接逆に見る vs 動的観測」の 4 つの主ルートを決める。必ず先に 5 分トリアージしてから投入する。

### パッカーを判定しアンパック戦略を選ぶ
**Q1**: エントロピー値が高く、セクション名が怪しい。パッカーを疑う。どう確認してパッカーの種別を定める?
**A1**: DIE(Detect It Easy)/PEiD 系でパッカーを調べる。インポートテーブルが LoadLibrary/GetProcAddress だけ残っていないか(パッカー特有の IAT)、セクションが書き込み可・実行可になっていないか(自己解凍セクション)を見る。種別確定がアンパック法選択の前提である。
**Q2**: UPX などの標準パッカーと確認し、直接 `upx -d` するとエラーになる場合はどうする?
**A2**: エラーは通常、パッカーがマジックマーカー/セクション名を改変された(自動アンパック対策)ことが原因。修復方法:セクション名/UPX バージョンヘッダのフィールドを標準値に戻してから `-d` する。またはアンパッカーを諦めて「メモリダンプ」の汎用法へ進む。
**Q3**: 見たことのない独自パッカー。汎用的なアンパックの考え方は?
**A3**: ESP 定律 / メモリブレークポイント法を使う。パッカーは解凍し終わると必ず OEP に jmp する。解凍ループが書き込む対象セクションの実行点にブレークを張り(ハードウェア実行ブレークポイント)、ブレークしたところが OEP。そこからメモリを dump し IAT を修復する(Scylla/importrec)。
**Q4**: dump は取れて動くが、IDA 内の IAT がすべて間違ったアドレスになる。どう修復する?
**A4**: ImpRec/Scylla を使ってプロセス実行状態でインポートテーブルを再構築する。IAT の先頭を特定し、ツールに呼び出し対象を解析させ、修復後に書き戻す。IAT を修復しないと静的解析は一歩も進めない。
**Q5**: パッカーにアンチデバッグがあり、デバッガを付けるとすぐ終了/偽分岐に進む。アンパックが塞がれた。どこへ方向転換する?
**A5**: 「デバッガなしアンパック」の直交する次元へ方向転換する。frida/DBI(Pin/QBDI)で ptrace の痕跡なしにメモリ割り当てと mprotect を hook する(実行権限が変わる瞬間が復号完了点)。またはエミュレータ(unicorn/qiling)で本物のデバッグ環境から離れて OEP まで実行する。
**Q6**: エミュレーションすら環境検知で失敗する場合は?
**A6**: 最後の手段は力ずくで向き合う。各アンチデバッグポイントを特定して 1 つずつ patch し(アンチデバッグ対策チェーン参照)、アンパックを通常の動的解析問題に格下げする。

### デコンパイルがジャンクコードだらけで読み進められない
**Q1**: IDA の F5 が失敗、または逆アセンブルが乱れ、無意味な push/pop/jmp+1 だらけ。ジャンクコードと判断してよいか?
**A1**: 典型的なジャンクコードの特徴:命令の中間にジャンプする(あるバイトオフセットへ jmp して逆アセンブルをずらす)、恒真/恒偽ジャンプ(xor eax,eax; jz)、無効プレフィックス。確認後は「ごみ」を NOP 化して正常な CFG に戻すことが目標である。
**Q2**: 手作業で 1 つずつ patch するのは遅すぎる。量が多い場合はどうする?
**A2**: スクリプト(IDApython/idc)で pattern 一致による一括 patch を書く。よくあるジャンクコードテンプレート(`EB FF C0 48` のような中間ジャンプのバイト列)を識別し、一括で NOP を埋めて `MakeCode` で再解析する。
**Q3**: ジャンクコードが恒真ジャンプで本物のコードを包んでいる。盲目的に NOP するとロジックを壊すか?
**A3**: 壊す。そこで「不透明述語」(opaque predicate、値は恒定的だが形式が複雑)と実条件ジャンプを区別する必要がある。判定基準:その述語が外部入力に依存するかどうか。依存せず静的に評価できる = 不透明述語であり、安全に簡約できる。
**Q4**: 逆アセンブラがデータをコードとして/コードをデータとして読み続け、行ったり来たりする。どう安定させる?
**A4**: 誤った領域を手動で `Undefine` し、正しい命令境界で `MakeCode` し、混入した定数データを `MakeData` する。CFG が一度揃えば、後続の pattern で一括除去できる。
**Q5**: ジャンクコードを除去しても F5 が失敗し、ここで完全に行き詰まった。方向転換先は?
**A5**: 「動的 trace で実経路を復元する」次元へ方向転換する。DBI で実際に実行された命令アドレスの系列(execution trace)を記録し、実際に走った基本ブロックだけを解析して、静的に未実行のジャンクコードの妨害をすべて迂回する。動的実行は自然にデッドコードを濾過する。
**Q6**: 経験を再利用できる一言は?
**A6**: ジャンクコードの本質は「逆アセンブラの線形/再帰降下を騙す」ことで、対策は常に「実実行フローを基準にする」こと。静的に簡約できるなら簡約し、できなければ trace で直接真の経路を取る。

### 制御フロー平坦化(OLLVM CFF)の復元方法
**Q1**: 関数が大きな while(switch(state)) ディスパッチャに押し潰され、すべての基本ブロックが dispatcher 配下にある。どう実制御フローを復元する?
**A1**: まず構造を識別する。主ディスパッチ変数(state var)、ディスパッチャブロック、実ブロック、前処理ブロック。目標は「各実ブロック実行後に state が何に代入されるか」を復元すること → 元の後続関係を再構築する。
**Q2**: state の遷移値が実行時に計算され、静的に次のブロックが見えない。どうする?
**A2**: シンボリック実行(angr/miasm)かテイント追跡を使う。各実ブロックについて state 変数をシンボル量に設定し、ブロック終了時の state の値を求解する → そのブロックの実後続を得て、CFG に組み戻す。
**Q3**: シンボリック実行が経路爆発/タイムアウトし、復元できない。次善策は?
**A3**: 混合法を使う。具体値 + シンボル(concolic)。dispatcher 分岐を具体入力で駆動実行し、実際に通った state 系列を記録して増分的に復元する。完全性を追求せず、対象ロジック関連の経路だけを網羅する。
**Q4**: 平坦化の外にさらに偽制御フロー(bogus control flow)と不透明述語が重なっている。buff を重ねられたがどう解体する?
**A4**: 層ごとに除去する。まず不透明述語を潰し(恒定的な分岐を簡約)、それから平坦化を解体する。順序が逆だと偽述語に state 解析を誤誘導される。既存の deflat スクリプト(angr/miasm ベース)を先に 1 回走らせてから手作業で仕上げる。
**Q5**: 自動 deflat ツールがこの魔改造 OLLVM に完全に無効で、塞がれた。どの直交する次元へ方向転換する?
**A5**: 「完全な CFG 復元」を諦めて「目標指向の動的観測」へ方向転換する。実際は関数全体を復元する必要はなく、「入力 X のとき、それがどの buffer に何の変換をしたか」を知るだけでよい。hook/trace で dispatcher の入口/出口にブレークポイントを張り、(入力→出力) のペアを記録し、難読化関数をブラックボックスとしてモデル化する。さらには求解したい制約を直接シンボリック実行する。
**Q6**: いつ復元を止めてブラックボックスにすべきか?
**A6**: 判定基準:自分の目標が「条件を満たす入力(検証/シリアル番号など)を求めること」であって「全ロジックを理解すること」でないとき、ブラックボックス+制約求解(angr find/avoid)は逐ブロック復元より通常 1 桁速い。

### 文字列/定数が暗号化され、静的に重要情報が見えない
**Q1**: 重要文字列(パス、鍵、プロンプト)が実行時に復号され、静的に文字化けしている。どう取得する?
**A1**: まず復号関数を特定する。その暗号文データを相互参照し、誰が読むかを見る → 高確率で decrypt(buf, len, key) ループ。見つけたら 2 つの道がある:静的解析でアルゴリズムを再現するか、動的に 1 回走らせて平文を直接読むか。
**Q2**: 復号アルゴリズムが単純(単バイト xor/加減算)なら、静的解析で再現する価値はあるか?
**A2**: ある。スクリプトを書いて全暗号文文字列を一括で解いてコメントとして書き戻すと、IDA 内が即座に可読になり、後続の解析への利益が極めて高い。IDApython でこの decrypt を参照する全呼び出し点を走査してパラメータを抽出する。
**Q3**: アルゴリズムが複雑、または key が実行時生成で、静的解析での再現コストが高い。どうする?
**A3**: 動的へ方向転換する。decrypt 関数の戻り地点でブレーク/hook し、メモリから全平文文字列を直接 dump する。または main まで走らせてからプロセスメモリ内の可読文字列を一度に検索する(この時点で全て復号済み)。
**Q4**: 「使うときだけ復号し、使い終わると即座に消去する」ので、メモリから全量を掴めない。どうする?
**A4**: 復号関数本体を hook して毎回の出力を記録する(frida の Interceptor.attach で onLeave に返却バッファを読む)。事後スキャンではなく、遅延復号は事後 dump には効くが hook には無効である。
**Q5**: 復号関数自体が平坦化/アンチデバッグで保護されており、hook できない。塞がれた。方向転換先は?
**A5**: 「実行せず、直接計算する」へ方向転換する。復号ロジックを抜き出し(暗号文データセクション + アルゴリズム)、unicorn 内でこの小さな関数だけをエミュレーションして、暗号文を与えて平文を得る。元プログラムのアンチデバッグとプロテクトの殻を完全に迂回する。
**Q6**: 一言の経験は?
**A6**: 文字列復号は常に「アルゴリズム再現 vs 実行時出力を掴む vs 抜き出して単独エミュレーション」の三択であり、アルゴリズムの複雑さとプロテクト強度に応じて段階的に選ぶ。

### ptrace 系アンチデバッグの特定と迂回
**Q1**: プログラムがデバッガに入れるとすぐ終了/挙動が異常になる。ptrace アンチデバッグを疑う。まず何を調べる?
**A1**: Linux ではまず 2 箇所を調べる。`ptrace(PTRACE_TRACEME)`(自分を自分で trace し、他者に trace させない)と `/proc/self/status` の TracerPid フィールドの読み取り(非 0 ならデバッグ中)。strace を走らせればこれらの呼び出しが見える。
**Q2**: PTRACE_TRACEME の自己保護だと確認した。どう迂回する?
**A2**: 三択。(a) LD_PRELOAD で偽 ptrace を常に 0 を返すようにする。(b) デバッガ内で ptrace 呼び出し後にブレークして戻り値を 0 に変える。(c) その呼び出しを静的に patch する(xor eax,eax か NOP に変える)。
**Q3**: /proc/self/status を読んで TracerPid を判定しており、LD_PRELOAD の ptrace では無意味。どうする?
**A3**: 標的を変える。open/read を hook して status の読み取りを遮断し TracerPid を 0 に改ざんする。またはデバッガ内で読み込んだ buffer 内の TracerPid 値を変える。または比較ロジックを patch する。アンチデバッグ検知点は「多源」なので、点ごとに破る。
**Q4**: 検知点が多すぎて散らばり、1 つずつ探すのは骨が折れる。系統的な方法はあるか?
**A4**: ある。DBI/frida で既知のアンチデバッグ API(ptrace/getppid/sysctl/isDebuggerPresent など)を全量 hook して一度に中和する。またはアンチアンチデバッグプラグイン(gef/pwndbg の関連設定、ScyllaHide/linux 版)で一般的な検知を一括処理する。
**Q5**: 標準 API を使わず、自分で syscall するかシグナル/例外で検知しており、プラグインが無効。塞がれた。どこへ方向転換する?
**A5**: 「ptrace のない観測手段」へ方向転換する。ptrace 検知の前提は誰かが ptrace していることなので、非 ptrace の DBI(Pin/QBDI/frida gum)かエミュレーション実行(qiling/unicorn)を使い、根本から TracerPid を発火させない。検知できないものを検知する。
**Q6**: 再利用の一言は?
**A6**: アンチデバッグは「観測されている痕跡を検知する」もので、アンチアンチデバッグの直交する昇格は「その痕跡を残さない観測方式に替える」ことであって、同じ次元で逐点に絡み合うことではない。

### 時間差アンチデバッグ(rdtsc / 時間検知)
**Q1**: シングルステップやブレーク後、プログラムが異常分岐に進む。時間検知(2 点間の所要時間を測ってシングルステップ/ブレークで遅くなったかを判定)を疑う。どう確認する?
**A1**: `rdtsc`/`clock_gettime`/`GetTickCount` の呼び出しを探す。特に「2 回時刻を取って差分 + 閾値と比較」のパターン。ブレークポイント/シングルステップは時間差を急増させ、見破られる。
**Q2**: 確認した。どう破る?
**A2**: 時間差を常に小さく保つ。時間源関数を hook し、各呼び出しの戻り値がごく小さな固定量だけ増えるようにする。またはその差分比較を patch する(jg/ja を反転または NOP)。目標は「とても速く動いている」と思わせることである。
**Q3**: rdtsc は生の命令でライブラリ関数を hook できない。どうする?
**A3**: 2 つの道。CPU/VMM 層で遮断する(一部デバッガは rdtsc ブレークポイント/置換をサポート)、または静的 patch で rdtsc 後の減算/比較を恒成立に変える。またはエミュレータで rdtsc の意味論を受動カウンタに置き換える。
**Q4**: 時間検知点が多く重要経路上に分散し、逐一 patch すると通常ロジックに影響する。どう安定させる?
**A4**: 時間源を patch せず「判定」を patch する。統一して「時間差 > 閾値なら悪い分岐」の比較を識別し、判定ジャンプだけを反転/除去して、時刻読み取りは残すことで時間に依存する他の通常ロジックを壊さない。
**Q5**: 時間差を後続の計算に混ぜている(単純なジャンプではなく、復号 key に関与する)ので、判定の patch も無意味。塞がれた。方向転換先は?
**A5**: 「全速・ブレークなし実行 + 事後解析」へ方向転換する。遅いと露呈するなら、シングルステップせず、ソフトウェアブレークポイントを張らず、ハードウェアブレークポイントか純粋な trace(DBI 記録)で全速実行する。または受動エミュレータ内で時間を恒久化し、「遅い」という信号を根本から除去する。
**Q6**: 一言は?
**A6**: 時間アンチデバッグが狙うのは「お前は遅くなった」ことで、対策は「遅くなっていないと思わせるか、そもそも遅くしないか」。patch 判定 / 恒久時間源 / 全速 trace の 3 段階で進む。

### ソフト/ハードウェアブレークポイント検知(0xCC スキャン、DR レジスタ)
**Q1**: ソフトウェアブレークポイントを張るとプログラムがクラッシュ/ジャンプする。自身のコード内の 0xCC を走査していると疑う。どう確認する?
**A1**: プログラムが自分の .text セクションに対して CRC/チェックサムを行うか、0xCC をバイト単位で比較するループを探す。ソフトウェアブレークポイントは対象バイトを 0xCC に変えるので、チェックサムが変わる。
**Q2**: 自己チェックサム(code checksum)と確認した。どう迂回する?
**A2**: ソフトウェアブレークポイントを使わず、ハードウェアブレークポイントを使う(メモリバイトを変更せず、チェックサムに見つからない)。または先にチェックサム計算を終わらせて、その結果を恒成立に patch する。またはチェックサム関数を hook して固定の正しい値を返す。
**Q3**: さらにハードウェアブレークポイントも検知する(DR0-DR7 デバッグレジスタを読む)ので、ハードブレークも見つかる。どうする?
**A3**: ハードウェアブレークポイント検知は通常 GetThreadContext/例外処理内の DR レジスタ読み取りによる。対策:そのコンテキスト取得呼び出しを hook して、DR フィールドをゼロにして返す。またはメモリブレークポイント(ページ保護)/ DBI ブレークポイントを使い、DR を占有しない。
**Q4**: ソフト/ハードブレークとも検知され、メモリブレークポイントは遅すぎる。三面を囲まれた。どうする?
**A4**: 「実ブレークポイントを一切張らない」観測へ退く。純粋な trace(実行フローを記録して事後に見る)かエミュレーション実行。ブレークポイント検知の前提はブレークポイントがあることなので、なければ検知できない。
**Q5**: エミュレーション環境まで識別できる(アンチ仮想マシンチェーン参照)ので、塞がれてしまった。どの直交する次元へ方向転換する?
**A5**: 「静的 + 少量の精密な動的」の混合へ方向転換する。静的解析でロジックを 80% まで理解し、必須検証の 1-2 点だけを最も隠密な手段(メモリ書き込み監視/条件を極端に絞ったハードブレーク)でその 1 つの値を取る。動的介入面を最小化して検知を逃れる。
**Q6**: 再利用の要点は?
**A6**: ブレークポイント検知の破り方は「メモリを変えず、DR を占有しない観測方式に替える」こと。多重検知が重なるときは、動的介入の「表面積」を減らすほうが力ずくで当たるより効果的である。

### アンチアンチデバッグ:動的 patch か静的 patch か
**Q1**: アンチデバッグポイントを多数見つけた。デバッガ内で動的に変えるべきか、バイナリを直接 patch して永続的に除去すべきか?
**A1**: 用途で見る。一度きりの解析なら動的 patch(デバッガスクリプト/条件ブレークで自動的に戻り値を変える)が速く、元ファイルを壊さない。繰り返し実行、exploit を書く、改変済みサンプルを配布するなら静的 patch でディスクへ書き出す。
**Q2**: アンチデバッグを 1 つ静的 patch したらプログラムが直接クラッシュした。なぜ?
**A2**: 高確率で自己チェックサム(コード/ファイル checksum)が改変を検知した。チェックサムも一緒に patch するか、ディスクへ書き出さない動的方式に変えるか、patch 後にチェックサム値を再計算して修正する。
**Q3**: 動的 patch の最も省力な方法は?
**A3**: デバッガの起動スクリプトで各アンチデバッグ呼び出し点に「ヒットしたら戻り値/フラグを変えて自動継続」の条件ブレークを張る。一度設定すれば全行程が自動化され、手動介入が不要になる。
**Q4**: アンチデバッグポイントが複数の動的ロードモジュール/遅延復号コードに分散し、起動時にはまだ存在しない。patch できない。どうする?
**A4**: 「コード準備完了の瞬間」に掛ける。mprotect/dlopen/復号関数を hook し、対象コードが実行可能にマップ/復号された瞬間に patch する。タイミングを合わせて初めて有効になる。
**Q5**: これを patch すればあれが現れ、もぐら叩きのように終わらない。引きずられる。方向転換先は?
**A5**: 「環境レベルでの中和」の直交する次元へ方向転換する。逐点 patch より、実行基盤ごと替える。LD_PRELOAD で一連の検知関数を一括偽造するか、qiling/frida で受動実行環境を提供して一括遮断する。「逐点戦」を「一度きりの環境戦」に変える。
**Q6**: 意思決定の一言は?
**A6**: 少数の静的点 → ディスクへ書き出す patch。多かつ動的生成 → タイミングを合わせた hook。終わらない → 環境レベルの一括中和へ次元を上げる。

### 暗号アルゴリズム識別(標準 vs 魔改造)
**Q1**: 明らかに暗号学のループをリバースエンジニアリングで見つけた。どんなアルゴリズムかを素早く認識するには?
**A1**: 「指紋定数」を認識する。AES の S-box/T-table、SHA の初期 H 定数、MD5 の正弦テーブル、TEA の 0x9E3779B9(黄金比 delta)、CRC の多項式テーブル。findcrypt/signsrch 系プラグインで一掃すれば分かる。
**Q2**: 定数は揃っているがフローが改変されている(魔改造 AES)。標準ライブラリでは解けない。どうする?
**A2**: 魔改造点は通常、S-box の変更、ラウンド数の変更、鍵スケジュールの変更、XOR オフセットの追加。標準と逐項比較して変更箇所を特定し、魔改造版に合わせて復号を自分で書き直す。「AES に見えるから標準 AES で解く」と信じない。
**Q3**: 特徴定数が 1 つもなく、まったく認識できない。自前暗号か?
**A3**: 自前かテーブル差し替えの可能性がある。識別に固執せず、「未知の可逆変換」として扱う。可逆かどうか(対応する復号経路があるか)、既知平文・暗号文ペアで構造を求解できるか、あるいは暗号化関数を抜き出してエミュレーションしブラックボックスとして使えるかを確認する。
**Q4**: 「暗号文から平文を求める」だけでよく、アルゴリズム認識が不要。最速経路は?
**A4**: 暗号化が可逆で復号関数がプログラム内にあるなら、それを直接呼び出す(unicorn/qiling でその関数を単独実行するか、LD_PRELOAD でプログラムに解かせる)。アルゴリズム識別は手段であって目的ではない。
**Q5**: アルゴリズムは認識できたが key を取得できない(ハードウェア/サーバー側生成)。鍵で死んでいる。塞がれた。どこへ方向転換する?
**A5**: 「鍵の出所側」へ方向転換する。key がローカルにないなら、それを生む場所まで追う。ネットワークパケット取得(通信プロトコルのリバースエンジニアリング)、鍵導出関数(KDF)の逆算、または鍵が暗号化関数に入る瞬間に hook してメモリから平文 key を直接読む。暗号そのものではなく key の「出生地」を攻める。
**Q6**: 再利用は?
**A6**: 暗号リバースエンジニアリングの優先順位:標準定数の認識 → 魔改造差分を探す → key を求めるか中間状態を hook → 関数を抜き出してブラックボックス化。それが純粋な標準実装だと常に仮定しない。

### 仮想マシンベースの難読化(VM プロテクト)への着手
**Q1**: 重要ロジックが独自バイトコード + インタプリタ(VMProtect/自前 VM 系)に変換され、読めるネイティブ命令がない。どう着手する?
**A1**: まず全部を復元しようとしない。目標を 3 段階に分ける。VM ディスパッチャ(opcode を取得 → handler へジャンプするループ)の特定、handler 集合の列挙、VM コンテキスト(仮想レジスタ/スタックがどのメモリにあるか)の理解。これが devirtualize の土台である。
**Q2**: handler が数十から百個ある。各 handler が何をするかをどう効率的に把握する?
**A2**: 各 handler をシンボリック実行/小サンプル trace で「opcode → 意味(等価なネイティブ操作)」のマッピングテーブルを作る。多くの handler は単純な算術/メモリアクセスなので、逐個注釈すれば VM ISA が出てくる。
**Q3**: 手作業で handler テーブルを作るのは遅すぎる。より速い道は?
**A3**: trace 駆動へ方向転換する。既知の入力を与え、VM が実際に実行した opcode 系列(bytecode trace)を記録し、実際に走ったバイトコード経路だけを復元する。ISA 一式ではなく。目標指向は完全 devirt よりずっと速い。
**Q4**: VM を復元する気はなく、自分の入力にどんな検証をしたかだけを知りたい。どうする?
**A4**: ブラックボックスモデル化する。VM 保護の関数全体を f(input)→output と見なし、DBI で VM の入口/出口にブレークポイントを張って大量の (入力, 出力) ペアを採取するか、f を直接シンボリック実行してソルバーに条件を満たす入力を探させる。VM を理解しなくても目標を解ける。
**Q5**: VM にさらにアンチデバッグが入れ子で、毎回 opcode エンコードも変わる(ポリモーフィズム)。徹底的に把握できない。塞がれた。方向転換先は?
**A5**: 「より高次の抽象層での観測」へ方向転換する。必要な答えは往々にして VM の外にある。VM は計算し終わると必ず外部世界と対話する(比較結果、ファイル読み書き、ネットワーク送信、システム API 呼び出し)。VM の「境界 API」で hook し、入出力と最終 syscall を観察して、VM 内部にはまったく触れずに迂回する。ポリモーフィック難読化はその対外挙動を守れない。
**Q6**: 一言の戦略は?
**A6**: VM プロテクトには、復元できるなら復元せず、「目標指向 trace」と「境界ブラックボックス」を優先する。完全 devirt は逐命令の理解が必須なときだけ行い、コストが極めて高い。

### 自己書き換えコード(SMC)による静的歪み
**Q1**: IDA 内のコードが無意味に見える/チェックサムが通らない。実行時に書き換えられる(SMC)と疑う。どう確認する?
**A1**: 特徴:プログラムが自分のコードセクションに書き込み操作をする、mprotect/VirtualProtect を呼んで .text を書き込み可にする、「一段を復号 → ジャンプして実行」のパターンがある。静的に見えるのは「書き換え前」の虚像である。
**Q2**: SMC と確認した。静的解析の正しい姿勢は?
**A2**: 静的バイトを信じない。「書き換え完了・実行前」の瞬間に実コードを dump する。mprotect が実行権限を戻すところで hook してブレークするか、そのセクションが実行されるまで走らせてメモリから再逆アセンブルする(IDA の debugger 内で reanalyze)。
**Q3**: 「一段を使い、一段を書き換え、走りながら変わる」ので、統一的な「復号完了点」がない。どうする?
**A3**: セクションごとに追う。書き換え領域へジャンプする前に現行バージョンを dump するか、全行程 trace で実際に実行された命令フロー(execution trace)を記録し、実実行系列を静的ビューの代わりにする。
**Q4**: SMC がアンチデバッグと連動している(デバッグを検知すると真のコードを復号しない)。どう破る?
**A4**: まずアンチデバッグを解決して復号を正常に発生させる(アンチアンチデバッグチェーン参照)、それから復号後のコードを掴む。順序:アンチアンチデバッグ → 真の復号を発火 → 真のコードを dump。
**Q5**: 復号ロジックが対象環境だけにある入力(ハードウェア/時刻/ネットワーク)に依存し、ローカルでは永遠に真のコードを解けない。塞がれた。どこへ方向転換する?
**A5**: 「環境を補うか完成品を掴む」へ方向転換する。対象環境内で走らせて復号後コードを dump してローカルに持ち帰るか、依存入力を偽造する(qiling 内でハードウェア/時刻/ネットワークの返却を mock する)ことで復号を受動環境で完遂させる。ロジックを攻められないなら環境を補う。
**Q6**: 再利用は?
**A6**: SMC の鉄則:「メモリ内で今から実行されるバイトを基準にし、ディスク/初期静的ビューを信じない」。核心動作は正しいタイミングで実コードを dump することである。

### 静的優先か動的優先かの決定
**Q1**: 中程度の複雑さの対象。静的を先に読むべきか、動的を先に走らせるべきか。どう決める?
**A1**: 3 つの要素を見る。アンチデバッグの有無(あれば → 静的を先にし、動的の地雷を避ける)、難読化強度(強ければ → 動的で真の経路を取る)、目標が「全部の理解」か「ある値/入力を求める」か(値を求める → 動的/シンボリック実行のほうが速い)。絶対はなく、トリアージ後に信号で選ぶ。
**Q2**: 静的を選んだが、難読化が重くて読めない。動的に切り替えるべきか?
**A2**: 切り替えるべき。静的が「制御フローが読めない/ジャンクコード・平坦化に溺れる」で行き詰まったとき、動的 trace は実実行経路を直接くれる、静的な自然な補完である。静的で合理的な時間を超えて粘らない。
**Q3**: 逆に、動的に走らせても対象分岐を発火できない(特定の入力でないと進まない)。どうする?
**A3**: 静的に戻って「この分岐に入る条件」を探すか、シンボリック実行で発火入力を逆算する(angr で入口から対象アドレスを find)。動的で発火できない経路は、静的/シンボリック実行が補う。
**Q4**: 両方を行き来して足踏みしている感じで、時間が流れている。どう損切りする?
**A4**: 単回の目標を明確にする。各ラウンドで具体質問を 1 つだけ答える(「この buffer はどこから来たか」「この比較のもう一方のオペランドは何か」)。最も省力な手段で答え終えたら離れ、「全部理解したい」という貪欲による空転を避ける。
**Q5**: 静的も動的も行き詰まり、全体が塞がれた。どの第三の次元へ方向転換する?
**A5**: 「シンボル/制約求解」の直交する次元へ方向転換する。実際に必要なのが「ある制約を満たす入力」だけなら、angr/concolic がリバースエンジニアリング問題を方程式を解く問題に変え、しばしばロジックの完全理解を飛ばして直接答えを出す。第三の脚は往々にして無視される。
**Q6**: 意思決定の口訣は?
**A6**: アンチデバッグがある/ディスクへ書き出す必要 → 静的から着手。難読化が重い/真の経路が要る → 動的。入力を求解する → シンボリック実行。三者は陣営ではなく、現在のサブ目標に応じて交代するツールである。

### PWN:脆弱性種別の確定
**Q1**: 対話のあるサービス型バイナリを手にした。まず脆弱性種別をどう特定する?
**A1**: 全入力点(read/scanf/recv/gets)をリバースエンジニアリングして境界を見る。定長 buffer に超長を受け取る = スタックオーバーフロー。printf(user) = フォーマット文字列。malloc/free のペアロジック異常 = ヒープ脆弱性。配列インデックスが入力由来で未検証 = OOB。まず脆弱性を分類してからエクスプロイトを論じる。
**Q2**: 複数の入力点が怪しい。どれを先に攻める?
**A2**: 「制御可能度 × 破壊力」で並べる。戻りアドレス/関数ポインタを直接上書きできるスタックオーバーフローを優先。次に任意読み書きできるフォーマット文字列/ヒープ。OOB はどこまで読み書きできるかを見る。利益が最も直接的なものを先に攻める。
**Q3**: スタックオーバーフローに見えるが Canary があり、オーバーフローが即座に遮断される。どうする?
**A3**: まず canary をリーク/迂回できるか考える(対応チェーン参照)か、canary を通らないプリミティブ(フォーマット文字列の任意書き込み、ヒープ脆弱性)へ方向転換する。脆弱性種別が確定しても経路は唯一ではない。利用面を変える。
**Q4**: 静的に目立つ脆弱性が見えず、プログラムもクラッシュしない。ロジックがより隠蔽されていると疑う。どう探す?
**A4**: fuzzing(AFL++/libfuzzer スタブ)で異常入力を与えてクラッシュ点を探すか、入力処理関数をシンボリック実行して範囲外/異常を探す。人目では見えない境界脆弱性は、fuzz がしばしば一発で当てる。
**Q5**: fuzz もクラッシュせず、静的にも穴がない。この対象は脆弱性がないように見える。塞がれた。どこへ方向転換する?
**A5**: 「非メモリ破壊」の次元へ方向転換する。問題を読み直す。論理脆弱性(権限迂回、整数オーバーフローによるロジック乱れ、競合/UAF のタイミング、コマンド連結インジェクション)であって古典的なスタック・ヒープオーバーフローでない可能性がある。視点を「メモリ破損」から「ロジックとステートマシン欠陥」へ切り替える。
**Q6**: 一言は?
**A6**: 脆弱性の特定 = 入力点の列挙 × 各境界と信用前提の検査。古典的なメモリの穴が見つからなければ、論理/競合/整数欠陥へ次元を上げる。

### 保護機構がエクスプロイト手法を決める
**Q1**: checksec で NX/PIE/Canary/RELRO が並ぶ。これでどう利用路線を定める?
**A1**: 逐項を制約に翻訳する。NX → スタック上で shellcode を実行できず、ROP/ret2libc が必要。PIE → アドレスがランダムで、まずベースアドレスをリークする必要。Canary → スタックオーバーフローはまず canary をリーク/迂回する必要。Full RELRO → GOT を書き換えられず、別の書き込み対象を探す必要。保護表がそのまま路線図である。
**Q2**: 全開(NX+PIE+Canary+Full RELRO)で、手が出ないように見える。まずどれを攻める?
**A2**: まず「情報リーク」を解決し、あるアドレス(スタック/libc/PIE ベースアドレス)を取得する。leak がなければ他はすべて空論。メモリを回帰できる原語(フォーマット文字列、OOB read、未初期化出力)を探す。
**Q3**: PIE なし(プログラムベースアドレス固定)だが他の保護はある。これはどんな利点をもたらす?
**A3**: プログラム自身のコード/GOT/BSS アドレスが固定なので、ROP gadget の供給源、書き込み対象、データを置く安定領域として直接使える。PIE なしは大きな突破口であり、固定アドレス資源を優先して利用する。
**Q4**: Partial RELRO で GOT が書き込み可。どう使う?
**A4**: GOT hijack を使う。任意書き込みがあれば、今から呼ばれる関数の GOT 項目を system/one_gadget に向ける。Partial RELRO は GOT 上書きの古典的前提なので、優先して考える。
**Q5**: 保護が全開で、leak 原語も見つからず、徹底的に行き詰まった。どの直交する次元へ方向転換する?
**A5**: 「リーク需要自体を迂回する利用手法」へ方向転換する。ret2csu/ret2dlresolve(libc leak 不要で直接シンボルを解決)、既知の固定領域へのスタック移行、partial overwrite(アドレスの下位バイトだけを変えてランダム化上位を迂回)など。leak がないとき、partial overwrite と dlresolve は古典的な突破口である。
**Q6**: 再利用は?
**A6**: checksec の各項目を 1 つの「禁止ルール」と捉え、利用とは「全ルールの下で 1 つの合法経路を見つける」こと。全開時はまず leak を奪い、奪えなければ免 leak 手法(dlresolve/partial overwrite)を使う。

### アドレスリークで ASLR/PIE を破る
**Q1**: PIE/ASLR があり、アドレスが 1 つ必要。どこで leak を探す?
**A1**: 一般的な leak 源:フォーマット文字列脆弱性(%p でスタック上の残留 libc/スタック/PIE アドレスを直接打つ)、範囲外読み取りの回帰、UAF で解放済みブロック内のポインタを読む、未初期化変数の出力。まずどの入力が「メモリを回帰できる」かを走査する。
**Q2**: フォーマット文字列で leak できるが、打ち出されたアドレスがどのベースアドレスか分からない。どう対応付ける?
**A2**: オフセット法を使う。同一次実行内で、ある %p 値から対応する既知シンボルのオフセットを引く = ベースアドレス。どの種別のアドレスかは範囲で判断する(スタックアドレスは高位、libc は mmap 領域、PIE はプログラムベースアドレス近傍)。複数回走らせて、どのビットがランダムでどのビットが固定かを観察して分類する。
**Q3**: leak されたのが libc 内の関数アドレス。libc ベースアドレスを計算し、さらに system を取るには?
**A3**: libc ベースアドレス = leak 値 − そのシンボルのこの版 libc 内オフセット。前提は libc バージョンを知ること(libc 識別チェーン参照)。さらに各シンボルの相対オフセットを足して system/bin_sh を求める。
**Q4**: 1 回の対話で 1 回しか leak できず、その後プログラムが終了する。足りない場合はどうする?
**A4**: 「ループ/複数回対話できる」構造(メニューループ)を探し、leak と後続利用を別ラウンドに置く。または 1 回の leak でできるだけ多くの %p を一気に打つ。ループがなければプログラムを終了させないようにする(戻りアドレスを部分上書きして main に戻してやり直す)。
**Q5**: leak 原語がまったくなく、ASLR が硬い壁。どこへ方向転換する?
**A5**: 「免 leak の ASLR 突破」へ方向転換する。partial overwrite(アドレスの下位 1-2 バイトだけを上書きし、上位のランダムは不変のまま下位のランダム部分をブルートフォース、確率は許容できる)、ret2dlresolve(libc アドレス不要)、またはブルートフォース(fork 型サービスは ASLR が不変で、力ずくで推測できる)。fork server は ASLR の自然な弱点である。
**Q6**: 重要な判定基準は?
**A6**: fork サーバーは ASLR が毎回同じ → ブルートフォース/partial 可能。非 fork かつ leak なし → dlresolve か partial overwrite。leak あり → まずアドレスを分類してからベースアドレスを計算する。

### ROP gadget が足りない
**Q1**: ROP を組もうとしたが、ROPgadget で探した断片では欲しい原語が揃わない(例えば pop rdx がない)。どうする?
**A1**: まず探索面を広げる。static バイナリ/libc 全体を探し、主プログラムだけにしない。マッチを緩める(pop rdx; ret がなければ、副作用が許容できる pop rdx; pop rcx; ret などを探す)。gadget は libc 内にふんだんにあることが多い。
**Q2**: 対象が NX+静的コンパイルで、gadget はプログラム自身からしか取れず、確かに重要断片が欠けている。どうする?
**A2**: 組み合わせ gadget を使う。直接のがなければ ret2csu のような「汎用レジスタローダ」(__libc_csu_init 内の pop rbx/rbp/r12/r13/r14/r15 + call 系列)で複数のパラメータレジスタを制御する。csu は gadget 砂漠のオアシスである。
**Q3**: system("/bin/sh") を直接やりたいが "/bin/sh" 文字列が見つからず、書き込みもできない。どうする?
**A3**: 目標を変える。read/gets で書き込み可セクション(bss)に "/bin/sh" を書き込んでそのアドレスを参照する。または ret2libc で libc 内の既存 "/bin/sh" を使う。または execve syscall に切り替えて自分でパラメータを配置する。文字列がなければ自分で作る。
**Q4**: gadget は足りるがスタック空間が ROP チェーン全体を収められない。どうする?
**A4**: スタック移行(stack pivot)を使う。leave;ret / xchg rsp 系 gadget で rsp を大量に書き込める制御領域(bss)へ移し、そこで完全なチェーンを展開する。空間不足なら引っ越す。
**Q5**: あらゆる組み合わせでも使えるチェーンが組めず、ROP の道が塞がれた。どの直交する次元へ方向転換する?
**A5**: 「非 ROP の制御フロー乗っ取り」へ方向転換する。ret2dlresolve(ローダに system を解決させる)、GOT/hook 上書き、__malloc_hook/__free_hook(旧 libc)、IO_FILE 偽造(FSOP)による関数ポインタ呼び出し、SROP(sigreturn で全レジスタを一度に設定)。ROP 砂漠では SROP/dlresolve が古典的な次元替えである。
**Q6**: 一言は?
**A6**: gadget 不足の解法のはしご:供給源を広げる → ret2csu で組み合わせ → スタック移行で空間を替える → SROP/dlresolve/IO などの非 ROP 原語に替える。

### ヒープエクスプロイト手法の選択
**Q1**: ヒープ脆弱性(UAF/overflow/double free)と確認した。数々の手法(tcache/fastbin/unlink/...)を前にどう選ぶ?
**A1**: まず 3 つを見る。glibc バージョン(tcache/安全検査の有無を決める)、自分の原語(chunk header を overflow できるか?UAF 読み書きできるか?double free できるか?)、目標(任意書き込み?leak?)。手法は「原語×バージョン」の関数であって、套路を暗記するものではない。
**Q2**: 新版 glibc(tcache + safe-linking 付き)で、古典的な fastbin attack が無効。どうする?
**A2**: tcache を優先する。tcache poisoning(next を対象に向ける)のほうが簡単。safe-linking は先に heap ベースアドレスをリークして XOR マスクを計算する必要がある。まず heap leak をしてから poison する。バージョンが safe-linking の対処要否を決める。
**Q3**: double free しかできない。何ができる?
**A3**: tcache double free(旧バージョンでは key 検査なしで直接環になる)→ 任意アドレスへの割り当て。新版では tcache key 検知があるため先に迂回する(オフセット free / key 変更)。double free の価値 = 任意アドレス割り当て 1 回との交換。
**Q4**: libc leak が必要。ヒープ内でどうやる?
**A4**: 1 つの chunk を unsorted bin に入れる(サイズが十分大きく tcache に入らない)、その fd/bk が main_arena(libc 内)を指す。UAF/OOB でそれを読む = libc leak。unsorted bin はヒープ内で libc をリークする古典的な水源である。
**Q5**: 手法をすべて試し、対象への割り当てまで行ったが、glibc の各種 check(size 不一致、bin 整合性)に阻まれる。塞がれた。どこへ方向転換する?
**A5**: 「これらの check に守られていない対象」を攻める方向へ転換する。tcache(検査が最少)、__free_hook/__malloc_hook(旧 libc、関数ポインタへの書き込み一撃)、FSOP/IO_FILE 利用(任意書き込みを偽造 _IO_FILE に向けて vtable 呼び出しを発火)など。bin 整合性 check が道を塞ぐとき、hook/IO の「ポインタ 1 箇所を書けば getshell」の対象に切り替える。
**Q6**: 再利用の要点は?
**A6**: ヒープエクスプロイトはまず「glibc バージョン + 手元の原語」を確定し、それで tcache/unsorted/fastbin を選ぶ。安全検査に阻まれたら check がより弱い対象(tcache/hook/IO)へ方向転換する。

### libc バージョン識別
**Q1**: リモート問題が libc を与えない。関数アドレスをいくつかリークした。libc バージョンをどう定める?
**A1**: リーク値の下位 12 ビット(ページ内オフセット、ASLR 不変)を libc データベース(libc.rip / libc-database)でマッチする。2-3 個の シンボル名+leak 下位ビット を入力すると、データベースが具体的なバージョンを逆引きする。下位 12 ビットは libc の「指紋」である。
**Q2**: アドレスを 1 つしかリークできず、複数の候補 libc がマッチした。どう絞る?
**A2**: 別の関数をもう 1 つリークして 2 つ目の制約を得る。または既知の相対オフセット差(2 シンボル間の間隔はバージョンごとに異なる)で除外する。1 つで足りなければもう 1 つ取って相互検証する。
**Q3**: バージョンにマッチした。確実な system/bin_sh オフセットをどう得る?
**A3**: 対応バージョンの libc.so をダウンロードし、それで base と各シンボルオフセットを計算する。ローカルで同じ libc で通してからリモートへ。必ず「リモートと同種の libc」でローカル再現する。オフセットが少しでもずれると crash する。
**Q4**: データベースにこの libc が見つからない(魔改造/ディストリビューション特供)。どうする?
**A4**: 「その場調達」へ方向転換する。多くの利用は正確なバージョンを必要としない。ret2dlresolve(libc オフセット不要)、より多くのアドレスをリークして線形関係から逆算、または問題環境側からその libc を取得する方法を考える(別の API でファイルを読めることがある)。
**Q5**: libc がまったく取れず、dlresolve も適用不可。塞がれた。どこへ方向転換する?
**A5**: 「libc 非依存の利用」へ方向転換する。プログラム自身の gadget だけで ROP、直接 syscall(execve)、SROP。libc を利用チェーンから完全に排除し、バージョン依存を消す。
**Q6**: 一言は?
**A6**: libc 識別は「leak の下位 12 ビットでデータベース検索」に頼る。見つからなければ免 libc(dlresolve/純 syscall/SROP)路線でバージョン依存を迂回する。

### seccomp サンドボックス迂回(execve 禁止で ORW のみ)
**Q1**: getshell 後に execve が禁止されている(seccomp)と分かった。まずどうルールを把握する?
**A1**: seccomp-tools dump で 1 回走らせて、どの syscall を allow/deny しているかを見る。典型は execve/execveat を禁止し open/read/write だけを許可 → 意図は shell を弾くのではなく ORW で flag を読ませること。まずホワイトリストを見てから戦略を定める。
**Q2**: ORW のみと確認した。利用チェーンをどう変える?
**A2**: 目標を「getshell」から「open(flag)+read でメモリへ+write で stdout へ」に変える。ROP/shellcode でこの 3 つの syscall のパラメータを順に配置して呼び出す。手法は不変で、syscall を orw 三点セットに替える。
**Q3**: open も禁止され、openat かそれ以下しかない。どうする?
**A3**: 等価 syscall を使う。openat で open を代替、sendfile/pread で read+write を代替、さらには mmap でファイルをマップして直接読む。ホワイトリスト内の「ファイル内容を外に出せる」あらゆる組み合わせが使え、open/read/write 三点セットに固執しない。
**Q4**: ファイルを読む syscall までほぼ禁止され、ORW が通らない。どこへ方向転換する?
**A4**: 「ファイル読み取り以外の外部漏出」へ方向転換する。write/socket が許可なら、サイドチャネル(クラッシュするかどうか/遅延で flag を 1 バイトずつリーク)や、許可 syscall でのブルートフォース式比較を使える。ORW が死んだらサイドチャネルで 1 バイトずつブルートフォースする。
**Q5**: seccomp が「特定アーキテクチャの syscall 禁止」型(例えば x86_64 だけ禁止で x32 ABI は非禁止)。これは脆弱性か?
**A5**: 脆弱性であり、古典的な迂回点である。フィルタが arch を検査していないか x32 ABI(syscall 番号 +0x40000000)を見落としているなら、別 ABI で禁止された execve を呼べる。seccomp ルールが arch-complete かどうかを検査するのが標準的な突破口である。
**Q6**: 再利用は?
**A6**: seccomp 迂回のはしご:ルールを dump → ORW 三点セット → 等価 syscall に替える → サイドチャネルで 1 バイトずつ → arch/ABI のフィルタ欠陥を探して別 ABI で禁止呼び出しを呼ぶ。

### ローカルで通ってリモートで通らない
**Q1**: exploit がローカルでは安定して getshell するが、リモートではクラッシュ/無応答。まず何を疑う?
**A1**: 第一容疑者は libc 不一致(リモートはローカルのものではない)。次に環境変数/スタックアラインメントの差、tty 差によるバッファ挙動の違い、アドレス空間レイアウトの差。まず libc 一致を確定する。
**Q2**: libc 差かどうかをどう検証する?
**A2**: リモートでリークしたアドレスからバージョンを逆引きし(libc 識別チェーン)、ローカルで使ったものと比較する。違えばリモートと同種の libc に替えて全オフセットを再計算する。オフセットが 1 つでもずれるとチェーン全体が崩れる。
**Q3**: libc が一致しても通らない。次に何を調べる?
**A3**: スタックアラインメント。一部 libc の system/movaps は 16 バイトアラインメントを要求し、リモートで movaps に落ちる。対策:戻りチェーンの前に ret を 1 つ入れてアラインメントを取る。これは「ローカルで通りリモートで崩れる」高頻度原因である。
**Q4**: 対話タイミングの問題(リモート recv が全部受信できない、送信が速すぎる)をどう切り分ける?
**A4**: pwntools の recvuntil/sendlineafter を厳密なアンカーで同期させ、sleep で時間を賭けない。各ステップが期待する応答を確実に受けてから次を送る。リモート遅延は大きいので、タイミングは固定待ちではなくアンカーに頼る。
**Q5**: 既知の差をすべて排除しても通らない。徹底的に行き詰まった。どこへ方向転換する?
**A5**: 「環境感度を下げる」利用再構築へ方向転換する。よりロバストな手法に替える。免 libc(dlresolve/syscall)でバージョン依存を減らす、one_gadget を手組み execve に替える、leak の冗長性を増やす。exploit を「精密に環境依存」から「環境非依存」へ再構築するのが、リモートで通らない根本解である。
**Q6**: 一言は?
**A6**: ローカルで通りリモートで通らない、の切り分け順序:libc バージョン → スタックアラインメント → 対話タイミング → 環境感度。治本は利用を環境非依存に再構築することである。

### one_gadget の制約が満たせない
**Q1**: one_gadget で一撃を狙いたいが、そこまで走らせても getshell しない。なぜ?
**A1**: one_gadget には前置制約がある([rsp+0x30]==NULL や特定レジスタが 0 など)。現在のコンテキストが制約を満たさないと getshell せず crash する。まず one_gadget で各候補の constraints を見る。
**Q2**: one_gadget が複数ある。どう満たせるものを選ぶ?
**A2**: 発火点でデバッガを使い現在のレジスタ/スタック状態を見て、各 gadget の制約と照合して、ちょうど満たすものを選ぶ。発火経路が異なると満たす gadget も異なり、呼び出し点を変えると制約が良くなることがある。
**Q3**: 全 one_gadget の制約が満たせない。どうする?
**A3**: 「制約を満たす現場を作る」方法を考える。制約が特定レジスタ 0/特定スタック位 NULL を要求するなら、先に ROP でそのレジスタ/スタックを整えてから one_gadget へジャンプする。制約が満たせないなら先に満たしに行く。
**Q4**: 制約の配置が面倒、または空間が足りない。one_gadget を諦めてどこへ方向転換する?
**A4**: 「素直な ret2system」へ方向転換する。自分で pop rdi = "/bin/sh"; ret; system。gadget は数個増えるが隠れ制約がなく安定。one_gadget は近道であって唯一の道ではない。制約が満たしにくいなら安定した system 三段へ進む。
**Q5**: 対象が system/execve を禁止(seccomp)。one_gadget も system も無意味。どの直交する次元へ方向転換する?
**A5**: ORW/syscall チェーンへ方向転換する(seccomp チェーン参照)。shell を起動できないなら、目標を直接 syscall で flag を読むことに変え、one_gadget のような「shell 起動原語」は全体として意味を失う。syscall のパラメータ配置へ替える。
**Q6**: 再利用は?
**A6**: one_gadget 失敗はまず制約を見る → 候補を替える → 能動的に制約を満たす配置 → ret2system へ戻る → exec 禁止なら完全に ORW へ転換。近道が通らなければ安定路を進む。

### IO_FILE / FSOP 利用への方向転換
**Q1**: ヒープエクスプロイトで任意書き込みまで来たが、__malloc_hook/__free_hook が新 libc で消えた。どうする?
**A1**: IO_FILE 利用へ方向転換する。新 glibc は hook を除去し、主流は _IO_FILE 構造 + vtable の偽造へ移った。目標は exit/fflush/fread などで vtable 関数ポインタ呼び出しが発火するときに、自分のアドレスへ乗っ取ること。hook が消えたら FSOP が後を継ぐ。
**Q2**: FSOP の核心攻撃面は何か?
**A2**: _IO_list_all チェーン上の FILE 構造 + その vtable。fake FILE を偽造し、その vtable を制御可能メモリに向け、IO flush 時に _IO_overflow などの仮想関数呼び出しを自分の対象(system かチェーン)へ発火させる。ポインタ 1 箇所の任意書き込みで IO 呼び出し全体をこじ開ける。
**Q3**: 新 libc に vtable check(_IO_vtable_check が vtable を合法区間に制限)があり、偽造 vtable がクラッシュする。どうする?
**A3**: 合法区間内の「利用可能 vtable」を使う。_IO_str_jumps / _IO_wstr 系のうち間接的に制御可能関数ポインタを呼べる項目(House of 系の apple/emma などの発想)で vtable 区間検査を迂回する。check は区間だけを制限し具体は制限しないので、区間内で借りられるものを選ぶ。
**Q4**: IO flush を発火するタイミングすらない(プログラムが正常終了しない/fflush しない)。どうする?
**A4**: 能動的に発火する。多くの利用は exit → __run_exit_handlers → fflush が FILE チェーンを走査する乗っ取りに頼る。または stdout 構造を上書きして次の printf/puts で発火する。必ず通る IO/exit 経路を 1 つ見つけて引き金にする。
**Q5**: IO 利用が全体として複雑すぎ、check も多すぎて、できない。どこへ戻る?
**A5**: 戻って「もっと単純な原語を見落としていないか」を評価する。GOT を直接書き換えられるか(Full RELRO でなければ)、スタック移行 ROP できるか、__exit_funcs 内の関数ポインタを書き換えられるか(pointer guard があるため要処理)。IO は高度な手段なので、先にもっと省力な道がないか確認してから乗り出す。
**Q6**: 一言は?
**A6**: 新 libc で hook なし → FSOP へ転換。vtable check に当たる → 合法区間内で借りられる jumps を使う。発火タイミング欠如 → exit/stdout を乗っ取る。複雑で詰まったら先にもっと単純な原語を探す。

### フォーマット文字列のオフセット特定
**Q1**: printf(user) のフォーマット文字列脆弱性を確認した。第一歩として「自分の入力が第何引数位置か」をどう定める?
**A1**: `AAAA%p%p%p...` または `%1$p%2$p...` を送り、どの %N$p が 0x41414141('AAAA')を打ち返すかを見る。その N が制御可能入力のオフセットである。これが全フォーマット文字列利用の座標原点である。
**Q2**: オフセットを見つけた。まずどう leak を取る?
**A2**: %N$p で異なる位置を打つ。スタック上には libc 戻りアドレス、__libc_start_main、canary、スタックアドレスがよく残る。位置を順に走査し、libc/スタック/PIE/canary を分類し、必要なアドレスをまず全部リークする。
**Q3**: 任意書き込み(%n)したいが、フォーマットは 1 回しかできない。どう計画する?
**A3**: 1 回でリークと書き込みを同時にやるのは非現実的で、通常はプログラムのループで複数回 printf に入る。1 回だけなら、その 1 回を最重要の一撃(戻りアドレス下位の変更/1 つの GOT 項目の変更)に使う。複数回なら初回リーク、以降書き込み。
**Q4**: %n で大きな値を書くと大量の文字出力が必要になり、遅すぎる/切り詰められる。どうする?
**A4**: バイト分割で書く。%hhn(1 バイト)/%hn(2 バイト)で対象値をバイト単位に分割し、各回は必要な下位数だけを出力し、$ で異なるバイトアドレスを指定する。大きな数は複数の小さな書き込みに分ける。
**Q5**: 対象環境が %n を禁止(FORTIFY / _FORTIFY_SOURCE が %n を遮断)。書けない。どこへ方向転換する?
**A5**: 「読み取り専用利用 + 書き込み原語の代替」へ方向転換する。フォーマット文字列は依然として全力で leak(%p/%s の任意読み取り)でき、「書き込み」の仕事は別の脆弱性(スタックオーバーフロー/ヒープ)に任せる。またはリークした情報を別の利用チェーンに供給する。%n 禁止なら強力な任意読み取り器に退化し、書き込みは別の場所に頼る。
**Q6**: 再利用は?
**A6**: フォーマット文字列:まずオフセット(%N$p で AAAA を打つ)→ スタックを走査して leak → %hhn でバイト分割任意書き込み → %n 禁止なら純粋な任意読み取り器として他の脆弱性と組み合わせる。

### hook/frida インスツルメントで重要関数を特定する
**Q1**: 大きなバイナリで「自分の入力を処理する関数」が見つからない。静的相互参照が多すぎる。動的にどう素早く特定する?
**A1**: ユニークな magic 値(例 "ZZZZ1234")を入力し、frida/DBI で一般的な処理関数(strcmp/memcmp/read コールバック)を hook するか全量 trace し、誰のパラメータに自分の magic が現れるかを見る。データフローが重要関数へ導いてくれる。
**Q2**: どの関数を hook すればよいか分からない。全 hook はできない。どう範囲を絞る?
**A2**: まず境界(read/recv が入力を受ける瞬間)を hook し、そこから呼び出しスタックを下へ trace する。または frida-trace で一連の候補関数に一括でブレークポイントを張り、ヒットを見る。「入力入口」から流れに沿って下るのが最も省力である。
**Q3**: 重要比較が独自関数で strcmp ではないので、標準ライブラリの hook がヒットしない。どうする?
**A3**: 戦略を変える。メモリブレークポイント/書き込み監視。自分の入力はある buffer に落ちるので、誰がその buffer を読むかを監視する。または全命令を trace して「自分の入力アドレスを参照した」命令を探す。独自関数を名前で hook できないときは、関数名ではなくデータアドレスを監視する。
**Q4**: 対象にアンチ frida/アンチ hook 検知(gum の痕跡/inline hook の trampoline を検知)があり、インスツルメントするとクラッシュする。どうする?
**A4**: より隠密な DBI(QBDI/Pin、対象メモリを inline patch しない)や ptrace 級のハードウェアブレークポイント観測に替える。または先にアンチ hook 検知を解決する(アンチ hook チェーン参照)。frida 検知への対策は frida の痕跡を残さないインスツルメントに替えることである。
**Q5**: 各種インスツルメントがすべて検知/塞がれ、動的特定の道が死んだ。どこへ方向転換する?
**A5**: 「静的データフロー + シンボリック実行」へ方向転換する。入力 buffer のアドレスから、どの関数に渡されたかを静的に追う(テイント解析)か、angr で入力シンボル化から explore し、ソルバーに処理ロジックまで連れて行かせる。動的が封じられたら静的テイント/シンボルで補う。
**Q6**: 一言は?
**A6**: 重要関数の特定:magic 値 + 境界 hook で流れに沿って下るのが最速。独自比較はデータアドレスを監視。アンチ hook なら隠密 DBI に替えるか静的テイント/シンボリック実行へ転換。

### アンチ hook / 整合性自己チェックサム検知
**Q1**: 対象関数を inline hook したら、プログラムが検知してクラッシュ/偽ロジックに進む。どう見つけたのか?
**A1**: inline hook は関数先頭のバイトを jmp に変える。対象の一般的な検知:重要関数の先頭数バイトをチェックサムする、関数アドレスが期待モジュールを指すか検査する。それは「コードが改変された」痕跡を調べている。先に検知しているのがバイト整合性かアドレス出所かを確認する。
**Q2**: 「関数先頭バイトのチェックサム」と確認した。どう迂回する?
**A2**: バイトを変えない hook に替える。ハードウェアブレークポイント(メモリ不変)、または DBI(QBDI/Pin はコピー上でインスツルメントし、元メモリを動かさない)。コードバイトを元のままにしてチェックサムを通す。バイト変更が検知されるならバイトを変えない観測を使う。
**Q3**: 検知しているのが「呼び出しが不正モジュール/frida-agent の存在から来る」こと。どうする?
**A3**: 注入痕跡を隠す。frida のデフォルト特徴(ポート/モジュール名/スレッド名)を変えるか、独立 agent モジュールを持たない方式(対象の既存メモリへ注入)を使う。注入源を検知するなら注入の識別可能な特徴を消す。
**Q4**: 周期的に全コードセクションの CRC 自己チェックサムをし、あらゆる patch が見つかる。どうする?
**A4**: 2 つの道。チェックサム関数自体を特定して中和する(常に正しいと返す)。ただしこれも patch なので自己チェックサムの入れ子になる恐れがある。または完全に patch せず、エミュレーション実行/ハードウェアブレークポイントで純粋な観測をする。チェックサムが入れ子のときは「ゼロ改変観測」を優先する。
**Q5**: アンチ hook + 自己チェックサム + アンチデバッグの三点セットが連動し、どこも壁。全体が封じられた。どの直交する次元へ方向転換する?
**A5**: 「完全オフラインの静的/エミュレーション」次元へ方向転換する。対象を unicorn/qiling の全エミュレーション環境に移し、自分が CPU とメモリビュー全体を制御する。その「観測されていることを検知する」手段(チェックサム/アンチデバッグ/アンチ hook)はすべて、自分が全知全能の宿主である前では無効になる。なぜなら自分はその体内でインスツルメントするのではなく、体外でその世界を演じているからである。
**Q6**: 戦略の一言は?
**A6**: すべての「反観測」技術は「観測者が被観測者のプロセス/マシン内に痕跡を残す」ことを前提とする。全エミュレーションへ昇格する(自分がその CPU になる)ことが釜の下の薪を抜く通解であり、代償はエミュレーション環境構築のコストである。

### アンチ仮想マシン / アンチサンドボックス検知
**Q1**: サンプルが自分の解析仮想マシン内で何もせず直接終了する。アンチ VM を疑う。まず何を調べる?
**A1**: 一般的な VM 指紋検知を調べる。CPUID の hypervisor ビット、レジストリ/デバイス内の VMware/VBox 文字列、MAC プレフィックス、特定ドライバ/プロセス名、ディスクサイズ/メモリ過小、rdtsc タイミング異常。strace/API monitor で何を読んだかを見て環境を判定する。
**Q2**: CPUID/レジストリ指紋を調べていると確認した。どう実機だと思わせる?
**A2**: 逐項偽装する。CPUID の hypervisor 検知分岐を patch、VM 特徴レジストリキー/デバイス名を変更、MAC を変更、ディスクメモリを増やす。または「VM 検知したら終了」の判定ジャンプを直接 patch して一刀両断にする。
**Q3**: 検知点が多すぎて逐個偽装したくない。最も省力な方法は?
**A3**: 環境を偽装せず「結論」を偽装する。全検知が集約する「VM かどうか」の真偽判定/最終ジャンプを特定し、その 1 点だけを patch して常に「実機」と判定させる。総バルブを掴むほうが各蛇口をひねるより省力である。
**Q4**: 検知しているのが「サンドボックス挙動の特徴」(ユーザー対話なし、マウス不動、実行時間が短すぎるなど)。どうする?
**A4**: 人間の痕跡を補う。マウス移動/クリックをシミュレートし、マシンに履歴ファイル/ブラウジング履歴を持たせ、実行時間を延ばして検知窓を通す(patch で sleep を消すか時間を早送りする)。挙動型検知には挙動を補い、指紋ではない。
**Q5**: アンチ VM 検知手段が未知で、偽装が不完全で、サンプルが実ロジックを発火しない。塞がれた。どこへ方向転換する?
**A5**: 「物理マシン/ベアメタル解析」または「全エミュレーション」へ方向転換する。物理マシン(復元カード/スナップショット付き)で走らせて VM 指紋を消すか、逆に qiling/unicorn 全エミュレーションで CPUID/レジストリ/時刻の各戻り値を自分が掌握し、見せたいものを何でも見せる。偽装がきれいでないなら、戻り値を完全掌握できる基盤に替える。
**Q6**: 一言は?
**A6**: アンチ VM の破り方:指紋偽装 / 総判定 patch / 挙動痕跡補完 の三択。どれも駄目なら物理マシンか全エミュレーションという「環境戻り値を完全制御できる」基盤へ。

### 間接ジャンプ / dispatcher 復元(非平坦化)
**Q1**: 逆アセンブルに jmp rax / call [rax] の間接ジャンプが大量にあり、IDA が対象を追えず、CFG が断片化する。どうする?
**A1**: 間接ジャンプ対象は実行時に計算される。まずレジスタの出所を見る。ジャンプテーブル(switch)、関数ポインタ配列、仮想関数呼び出しのどれか。静的に解けるもの(ジャンプテーブルベース+インデックス範囲)は手作業/スクリプトで CFG を補完する。
**Q2**: ジャンプテーブル(jump table)だが IDA が境界を認識していない。どう補う?
**A2**: テーブルベース(間接ジャンプ前の lea/mov)とインデックス上限(前の cmp/jae 境界検査)を探し、これでテーブル項目数を計算し、手動で offset 配列と定義して IDA に各 case への参照を張らせる。CFG が繋がる。
**Q3**: C++ 仮想関数呼び出しで、具体実装を追えない。どうする?
**A3**: オブジェクトの vtable を探す。オブジェクト構築箇所(vtable ポインタ代入)を特定する。vtable 内が各仮想関数のアドレスである。または call [rax] で動的にブレークして rax がどの具体関数を指すかを見る。仮想呼び出しは vtable で型を復元する。
**Q4**: 間接対象が実行時データ(ファイル/ネットワークから読み込んだアドレス)に依存し、純静的では解けない。どうする?
**A4**: 動的へ方向転換する。間接ジャンプ箇所でブレークして毎回の実際のジャンプ対象を記録し(trace indirect branches)、実行時に観測した辺関係を静的 CFG に書き戻す。静的に解けない間接辺は、trace で実値を観測して補う。
**Q5**: 間接ジャンプが難読化が意図的に作ったもの(毎回対象が複雑な演算経由)で、静的も動的も復元しにくい。塞がれた。どこへ方向転換する?
**A5**: 「目標指向、全 CFG を求めない」へ方向転換する。関心があるのは大抵ある具体的経路だけ。concolic で欲しい入力に沿って具体実行し、実際に通った間接ジャンプ系列だけを記録して「今回の実行の実制御フロー」を得る。全図は復元しない。
**Q6**: 再利用は?
**A6**: 間接ジャンプ:まず分類(ジャンプテーブル/関数ポインタ/仮想呼び出し)し静的に補えるなら補う → 実行時データ依存なら trace で実対象を観測 → 難読化が意図的なら concolic で対象経路だけを取る。

### 難読化解除ツール選択:シンボリック実行 vs 手作業 vs コンパイラ最適化
**Q1**: 難読化コードの一段。angr シンボリック実行、手作業解析、コンパイラ/オプティマイザ簡約のどれを使う?どう決める?
**A1**: 規模と目標で見る。小さい断片+入力を求める → シンボリック実行が最速。構造的難読化(平坦化/ジャンクコード)に成熟スクリプトがある → deobf ツール(miasm/binary lifter + 最適化 pass)を使う。ロジックを完全に食べ尽くす必要があり量が少ない → 手作業。大砲で蚊を撃たず、手で大量コードを掘らない。
**Q2**: angr を使ったが経路爆発/メモリ爆発した。どう救う?
**A2**: 探索を制限する。find/avoid を精密に指定、全シンボルでなく concolic(具体入力で誘導)、複雑ライブラリ関数を hook して SimProcedure に替える、シンボル変数範囲を縮小。シンボリック実行は爆発を制御しなければ無駄なので、まず枝刈りをする。
**Q3**: 難読化が「式の膨張」(MBA、a+b を大量のビット演算に書く)。ツールをどう選ぶ?
**A3**: 専用 MBA 簡約器(SMT ベースの式簡約、arybo/msynth 系)か IR 最適化(コードを IR に lift して constant folding/算術簡約を走らせる)を使う。MBA は数学恒等式の膨張なので、力ずくで読まず代数的に簡約する。
**Q4**: 既存ツールがこの魔改造難読化に適応せず、ツール改修コストが高い。どうする?
**A4**: 「trace + 差分」へ格下げする。コードを復元せず、大量の入力を与えて入出力ペアを採取し、プログラム合成/回帰フィッティングで等価関数を推測する。または重要変数をテイント追跡して関心部分だけを理解する。ツールが適応しなければブラックボックス挙動モデル化へ退く。
**Q5**: 全自動化が奏功せず、手作業は大きすぎて、プロジェクトが引きずられる。どの直交する次元へ方向転換する?
**A5**: 「問題規模の再定義」へ方向転換する。一歩下がって「自分は何が要るのか」を問う。往々にして関数全体の難読化解除は不要で、ある検証結果/ある key/ある経路だけが要る。大きな問題を「この具体サブ問題だけを解く」に切り、最小手段(単点 hook で 1 つの値を読む)で取得して、全体の難読化解除を迂回する。
**Q6**: 一言は?
**A6**: ツール選択 = 規模×目標:小さな求解はシンボリック実行、構造的難読化は deobf pass、MBA は代数簡約。どれも駄目なら問題を単点ブラックボックスまで縮小する。

### 通信系バイナリ:プロトコル / 暗号化トラフィックのリバースエンジニアリング
**Q1**: 対象がクライアントで、サーバーとの私有プロトコルをリバースエンジニアリングしたい。どこから着手する?
**A1**: まずパケットを取得して形態を見る(平文?TLV?暗号化?)。平文なら、取得パケットとコード内のパッキング関数を直接照合する。暗号化なら、「暗号化前/復号後」の平文接点を重点的に探す。ネットワーク関数(send/recv)の 1 つ上層が往々にして平文である。取得パケットで形態を定め、コードで構造を定める。
**Q2**: トラフィックが TLS 暗号化で、取得パケットがすべて暗号文。平文をどう取る?
**A2**: TLS 層をバイパスする。SSL_write/SSL_read(平文が TLS ライブラリに入る瞬間)を hook するか、SSLKEYLOGFILE/frida hook でセッション鍵を取得して Wireshark に復号させる。TLS を逆に見ず、TLS ライブラリに入る前に平文を遮断する。
**Q3**: アプリケーション層の暗号化を自前実装している(TLS 内にもう 1 層私有暗号)。SSL hook の出力もまだ暗号文。どうする?
**A3**: もう 1 層上を探す。アプリケーション層の encrypt/decrypt 関数(通常は業務ロジックに隣接)を特定し、その平文側を hook する。「暗号タマネギ」を層ごとに剥き、各層で「暗号化関数の平文側」に点を設ける。
**Q4**: 証明書固定(certificate pinning)があり、中間者がパケットを取得できない。どうする?
**A4**: pinning を迂回する。証明書を検証する関数を hook して常に通す(frida の一般的な unpinning スクリプト)か、SSL_read/write を直接 hook してパケット取得なしで平文を直接読む。pinning が防ぐのは MITM であり、アプリケーション層平文の hook はその影響を受けない。
**Q5**: 暗号化関数が重度に難読化/VM 保護内にあり、hook もできず逆にも見られない。塞がれた。どこへ方向転換する?
**A5**: 「関数を抜き出して oracle にする」へ方向転換する。暗号化/復号関数をその初期化ごと、unicorn/qiling で単独実行し、平文を食わせれば暗号文を吐き、暗号文を食わせれば平文を吐く。アルゴリズムを完全に理解しなくても任意のパケットを作成/復号できる。難読化は単独で呼び出せる可逆関数を守れない。
**Q6**: 一言は?
**A6**: プロトコルのリバースエンジニアリング:パケット取得で形態を定める → 「暗号化関数の平文側」で層ごとに hook → pinning なら unpin か平文側を直接読む → 逆に見られないなら暗号化・復号関数を抜き出して oracle として呼ぶ。

### 大型バイナリで重要ロジックを素早く特定する
**Q1**: 数十 MB の大きなプログラムで、具体機能を 1 つだけ関心がある。迷わずに素早く特定するには?
**A1**: 「アンカー文字列/挙動」から逆に調べる。その機能関連のエラー文字列、メニュー文字、ログ、API 呼び出し(ファイル関連なら open、ネットワーク関連なら connect を調べる)を相互参照して関連コードへ直接たどる。main から順に読まず、対象特徴から逆に調べる。
**Q2**: 使える文字列アンカーがない(暗号化/プロンプトなし)。入口をどう探す?
**A2**: 挙動差分から。その機能をやる/やらないの 2 回を走らせ、trace 差分(coverage diff、lighthouse/drcov など)で「その機能をやるときだけ実行される」コードブロックを強調し、関連関数を直接囲い込む。差分カバレッジはアンカーなし特定の神器である。
**Q3**: 1 つの関数を特定したが、それが数百のサブ関数を呼ぶ。どれが深掘りに値するかどう判断する?
**A3**: 「対象データ/システムコールへの近さ」で並べる。自分が関心を持つ buffer を直接操作する、対象 syscall を直接発起するサブ関数を優先。純粋なユーティリティ関数(メモリコピー/ログ)は先にスキップ。呼び出し数ではなくデータフローに沿って深掘りする。
**Q4**: 相互参照/差分をやっても膨大な呼び出し関係が整理できない。どうする?
**A4**: 可視化 + 動的コールグラフを使う。proximity view / call graph で対象関数の上流下流に集中する。または frida-trace で実行時に実呼び出し系列を録画し、実際にどう一歩ずつ対象へ進むかを見る。静的グラフが大きすぎるなら実行時の実経路で切り詰める。
**Q5**: 対象機能の発火条件が厳しい(特定入力/状態でないと進まない)ので、動的にそのセクションへ到達できない。塞がれた。どこへ方向転換する?
**A5**: 「シンボリック実行の逆方向到達性」へ方向転換する。対象コードアドレスを find にし、angr で入口から「どんな入力ならここに来られるか」を逆算して、発火条件の特定と経路の発見を同時にやる。または対象ブロックから CFG に沿って手作業で前駆条件を逆にたどる。到達できないならソルバーに到達方法を計算させる。
**Q6**: 一言は?
**A6**: 大型バイナリの特定:アンカー文字列で逆に調べる → アンカーなしならカバレッジ差分 → データフローでサブ関数を篩う → 発火しないならシンボリック実行で到達条件を逆算。

### 「深掘り続行か、対象/手法を替えるか」の損切り意思決定
**Q1**: 1 点(ある関数/ある脆弱性/ある迂回)に長く投入しても進展がない。損切りすべきかどう判断する?
**A1**: 「進展信号」チェックポイントを設ける。ある程度時間を投入するごとに「さっきより具体的に何を知ったか」を問う。数ラウンド連続で「また 1 つの推測を排除した」だけで前向きな情報の増分がなければ、損切り信号である。足踏み感 = 替えるべき。
**Q2**: 替えるなら、まず手法を替える(同対象)か対象を替える(同タスク)か?
**A2**: 「同対象で直交する手法に替える」(静的で詰まったら動的、動的で詰まったらシンボリック実行)を優先し、コストが低く経験が再利用できる。手法をすべて試したら初めて対象/攻撃面の変更を考える。まず横に次元を替え、それから縦に対象を替える。
**Q3**: 「あちこち替えてどれも浅く」というもう一方の極端をどう避ける?
**A3**: 各手法に「最小検証目標」(明確な 1 つの判定可能問題)とタイムボックスを定める。箱内で答えられなければ替える、答えられたら深掘りを続ける。境界のある粘りは、無思考な硬直でも一触れ即退散でもない。
**Q4**: 次元をいくつか替えても全滅で、方向が根本から間違っているのではと疑う。どう校正する?
**A4**: 「題意/情報」に戻って読み直す。対象が与えた全手がかり(ファイル名、プロンプト、開放 API、プロテクト設定)を再確認する。行き詰まりの多くは明示された方向を 1 つ見落としたことが原因。疑い切ったとき、答えはよく読めていない題面にある。
**Q5**: 方向は間違っていないと確認できたが、既知の手法がすべて塞がれた。最後にどこへ方向転換する?
**A5**: 「対象粒度を下げる + 原語の組み合わせ」へ方向転換する。「一撃で取る」を「まず半完成の能力を 1 つ取る」(1 回の任意読み取り、1 つの leak、1 つの不完全な書き込み)に分解し、複数の弱原語を組み合わせて強利用を作る。すべて塞がれたとき、弱原語の接合がしばしば唯一の出口である。レッドチームの仕事は破片を溶接してチェーンにすることである。
**Q6**: 損切りの口訣は?
**A6**: 「前向きな情報の増分」を進展判定基準とする。まず横に直交手法を替え(タイムボックス付き)→ 再び題面を読み直して方向を校正 → 最後に大目標を弱原語の組み合わせに分解。進まなければ転じ、転じるときは境界を持つ。
