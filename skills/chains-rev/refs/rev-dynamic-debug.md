# リバースエンジニアリング PWN · 動的デバッグとブレークポイント戦略

### バイナリに着手するとき:まず静的か先に動的か
**Q1**: 未知の ELF/PE を手にし、時間が限られている。先に IDA で静的に通読すべきか、直接デバッガに投げ込んで走らせるべきか?
**A1**: まず 30 秒の「安価な偵察」を行う:`file` でアーキテクチャ/strip かどうか/PIE かどうかを見る。`checksec` で NX/Canary/RELRO/PIE を見る。`strings` で重要文字列を掴む。これが後続の全ブレークポイント戦略を決める。シンボルがあれば名前でブレークできる。strip なら文字列/インポートテーブルで特定する。急いでアセンブリを通読しない。
**Q2**: 偵察を終えた。先に動的か先に静的か?
**A2**: 判定基準は「入力から危険点までの経路の長さ」。プログラムの対話が単純(入力を 1 回読んで処理)なら、直接動的に 1 回走らせて I/O 挙動を観察するのが最速。制御フローが複雑(ステートマシン、多層メニュー)なら、まず静的に重要関数の呼び出しグラフを描き、仮説を持って動的検証し、デバッガ内で手当たり次第に試さない。
**Q3**: 動的に 1 回走らせるとき、何を見るべきか?
**A3**: ブレークポイントを張らず、まず `ltrace`/`strace` か procmon で、どのライブラリ関数/システムコールを呼ぶかを見る。read/recv がどこで入力を読むか、malloc/free があるか(ヒープ問題の示唆)、open で設定ファイルを開くか。挙動の輪郭はアセンブリを逐行読むより情報密度がはるかに高い。
**Q4**: 動的も静的も触ったがコアロジックが整理できない。どうする?
**A4**: 「データ駆動」へ方向転換する。制御フローを追わず、データを追う。入力バッファに watchpoint/ハードウェア読み書きブレークポイントを張り、プログラム自身に「誰が私の入力を触ったか」を語らせる。アクセス点に沿って処理関数を逆算するほうが、main から下へ trace するより効率的である。
**Q5**: この静的+動的の常套路が完全に行き詰まった(難読化が激しい、アンチデバッグが遮断する)?
**A5**: 直交する方向転換。「コードの理解」を諦め、「ブラックボックス差分」に変える。異なる入力で走らせ、出力/covered basic block(QEMU/DynamoRIO/Pin のインスツルメントでカバレッジ記録)を diff し、どの分岐がどの類の入力で発火するかを観察して、リバースエンジニアリング問題を fuzzing+カバレッジフィードバック問題に格下げする。

### ブレークポイントをどこに張るか:入口点か重要関数か
**Q1**: プログラムが大きすぎて全行程シングルステップできない。ブレークポイントはどこに張るのが最も省力か?
**A1**: 入口ブレークポイントを盲目的に張って果てしなくシングルステップしない。優先は「データ境界」:入力関数の戻り箇所(read/recv/scanf の後)、出力関数の呼び出し箇所(printf/send の前)、そして怪しい危険関数(strcpy/memcpy/sprintf/system)。これらが情報濃度の最高点である。
**Q2**: シンボルがあれば名前で張れるが、strip された場合、これらの点をどう特定する?
**A2**: PLT/IAT に頼る。ライブラリ関数呼び出しは strip でもインポートテーブルに残る。gdb では `b read`、`b system` で直接 libc シンボルにブレークする。Windows は `bp kernel32!ReadFile`。プログラム自身の関数が strip されていれば、文字列相互参照を使う:重要プロンプト文字列のアドレスを探し、search/xref でそれを参照するコードを特定してからブレークする。
**Q3**: 「入力を処理するコア関数」にブレークしたいが、どれか分からない?
**A3**: 「逆算法」を使う。出力/判定点(「Wrong」/「Correct」を出力するところ)でブレークし、ブレークしたら呼び出しスタック(`bt`)を見る。スタックフレームを上へたどると判定ロジックの呼び出しチェーンがあり、コア検証関数は通常スタックの中上層にある。
**Q4**: ライブラリ関数にブレークしたがヒットが頻繁すぎる(malloc が数千回呼ばれる)?
**A4**: 条件ブレークを使う。gdb の `b malloc if $rdi > 0x400`(size でフィルタ)か、特定の呼び出し元戻りアドレスにブレークする。頻繁ヒットは選点が低層すぎることを示す。1 層上へ業務関数に上げる。
**Q5**: 重要関数がどうしても見つからず、ブレークポイントがすべて空振り。どうする?
**A5**: 「メモリ変更追跡」の直交する次元へ方向転換する。「誰が処理するか」を見つけられないなら、「何が変えられたか」を監視する。対象グローバル変数/flag バッファにハードウェア書き込みブレークポイントを張るか、rr で録画して逆方向実行(reverse-continue)で結果から原因を逆に調べる。

### アンチデバッグが発火した:プログラムがデバッガを検知して終了する
**Q1**: デバッガに入れるとプログラムが自殺/挙動が異常になる。アンチデバッグと判定した。まず検知点をどう特定する?
**A1**: まずカテゴリで分ける。Linux で最も多いのは `ptrace(PTRACE_TRACEME)` なので、`catch syscall ptrace` か `b ptrace` で、ブレーク後に戻り値を直接 0 に変える。Windows で最も多いのは `IsDebuggerPresent`/`CheckRemoteDebuggerPresent`/PEB.BeingDebugged なので、これらの API にブレークするか PEB フラグビットを直接 patch する。
**Q2**: 1 つの検知を patch したら別の場所でクラッシュした。多重検知のように見える?
**A2**: 多層アンチデバッグは常態である。1 つずつ手で直さず、直接汎用迂回を使う。Linux は `LD_PRELOAD` で ptrace を 0 を返すように hook。Windows は ScyllaHide/TitanHide プラグインで PEB/時間差/例外などの一連の検知をワンクリックで隠す。精力をロジックに残し、アンチデバッグ消耗戦に陥らない。
**Q3**: 時間ベースのアンチデバッグを疑う(シングルステップで遅いと終了する)?
**A3**: `rdtsc`/`QueryPerformanceCounter`/`GetTickCount` の呼び出しを探す。それは 2 点間の所要時間を測り、ブレーク/シングルステップで差分が急増して検知を発火する。対策:被測区間内でシングルステップせず、ハードウェアブレークで直接区間末尾へジャンプする。または時間比較分岐を patch する。
**Q4**: 検知点が int3 で自身のコードを走査する(ソフトウェアブレークポイントを検知)場合はどうする?
**A4**: これがソフトウェアブレークポイント(0xCC)が自己チェックサムで見つかる場面である。ハードウェアブレークポイント(gdb の `hbreak`、x64dbg のハードウェアブレーク)に替える。メモリバイトを変更しないので、CRC 自己チェックサムを逃れる。
**Q5**: 静的 patch/hook がすべて、より隠蔽された検知に見破られた。アンチデバッグが頑固すぎる?
**A5**: 直交する方向転換。プロセス内デバッグから完全に離れる。「外部観測」に替える。QEMU/Unicorn で重要断片をエミュレーション実行する(アンチデバッグの多くは本物の OS 挙動に依存し、エミュレータ内では無効になる)。またはハードウェア支援の Intel PT/eBPF ベースの追跡で、CPU/カーネル層から実行軌跡を取得し、そのプロセスに入らない。

### PIE が有効:毎回アドレスが変わり、ブレークポイントアドレスが計算できない
**Q1**: プログラムが PIE で、IDA で見えるのはオフセットアドレス。gdb で `b 0x1234` がヒットしない。どうする?
**A1**: PIE 下の静的アドレスは 0 相対のオフセットで、実行時はロードベースアドレスが付く。ハードコードしない。まず `starti` で入口に止まり、`vmmap`/`info proc mappings` でイメージベースアドレスを取得し、`b *(base+offset)` する。またはシンボル名/関数名でブレークして、gdb にリロケーションを処理させる。
**Q2**: 毎回デバッグでベースアドレスを手計算するのは面倒?
**A2**: pwndbg/gef では直接 `b *$rebase(0x1234)` で自動加算する。exp を書くときは gdbscript で `$rebase` を使う。実行時ベースアドレスをリークして exploit にするには、アドレスリーク原語(フォーマット文字列/範囲外読み取り)が要り、既知のコード/データアドレスを漏らしてその静的オフセットを引く。
**Q3**: ブレークポイントは正しく張れたが、exploit 内の libc/PIE base 計算がいつも間違う?
**A3**: 「リークしたのがどのアドレスか」を照合する。リーク値はそれ自身の対応モジュール内静的オフセットを引く必要があり、別のシンボルのオフセットを引いてはいけない。`vmmap` でセグメント先頭を確認し、`リークアドレス - そのシンボルの静的オフセット = base` を、さらに base 下位 3 ビットが 0(ページアラインメント)かを照合する。整っていなければ対象を取り違えて計算している。
**Q4**: ローカルでは計算できるが、リモート環境のベースアドレス規則が違う?
**A4**: リモートの ASLR エントロピー/ロード順序は異なるかもしれないが、「モジュール内オフセットは固定」の不変は変わらない。exploit が全行程「リーク base + オフセット」を使い、絶対アドレスを一切ハードコードしないことを保証する。libc バージョン不一致も全オフセットを狂わせる。先にリモート libc バージョンを確認する(後続の libc 識別項目参照)。
**Q5**: リークが一切取れず、PIE base が計算できない。道が死んだ?
**A5**: 直交する方向転換。絶対アドレス需要を迂回する。PIE base 非依存の技術を使う:partial overwrite(アドレス下位バイトだけを変更、ページ内オフセットは固定で ASLR 影響なし)、ret2csu/ret2dlresolve(libc アドレス不要)、既知制御領域への stack pivot。「精密なアドレスが必要」を「ページ内相対だけでよい」に変える。

### クラッシュ点の特定:プログラムが crash したがどの行で落ちたか分からない
**Q1**: 異常入力を食わせてプログラムがセグメンテーションフォルトした。クラッシュ命令をどう素早く特定する?
**A1**: デバッガ内で直接 crash まで走らせる。gdb が障害命令で止まるので、`info registers` で rip/pc と障害アドレスを見る。rip がすでに 0x41414141 のような制御可能値なら、おめでとう。制御フローは乗っ取られており、直接オフセット計算段階に入る。
**Q2**: rip が制御不能で、ある mov/アクセス命令で落ちた。性質をどう判定する?
**A2**: crash 種別を見る。不正アドレス読み取り(SEGV on read)はポインタ汚染/UAF が大半。不正アドレス書き込みはバッファオーバーフローの書き越え。不正アドレス実行は制御フローは乗っ取られたがアドレス計算を誤った。`bt` を併用してスタックが既に踏み荒らされていないかを見る(bt が正常フレームを出さない = スタックオーバーフローの典型特徴)。
**Q3**: 「どのバイトがクラッシュを引き起こしたか」をより精確に知りたい?
**A3**: sanitizer を使う。ASAN で再コンパイル(ソースあり)か QASAN/Valgrind(ソースなし)。範囲外読み書きの精確なアドレス、サイズ、割り当て/解放スタックを直接報告する。生 gdb で段階的に特定するより 1 桁速い。
**Q4**: crash が偶発で、毎回落ちない?
**A4**: 偶発クラッシュはヒープレイアウト/未初期化データ/競合が原因であることが多い。`rr` で 1 回のクラッシュ実行を録画し、逆方向デバッグで安定再現する。またはヒープ環境を固定(ASLR 無効、tcache 状態ゼロ)してクラッシュを決定的にする。
**Q5**: 落ちはするが完全に制御できず、利用可能性が見えない。この crash 路は無駄か?
**A5**: 必ずしも無駄ではないが、まず「より良い原語」を探す方向へ転換する。制御不能な crash は現在の入力点の原語が弱いことを示す。他の入力面(他のメニュー項目、他のフィールド)を監査するか、バグ種別を変える:このオーバーフローが制御不能なら、より強い制御を与える UAF/double free/整数オーバーフローがないかを見る。1 つの弱原語に固執しない。

### オーバーフローオフセットを求める:戻りアドレスを上書きできるがオフセット量が分からない
**Q1**: スタックオーバーフローで rip を制御できる。入力から戻りアドレスまでの精確なオフセットをどう素早く求める?
**A1**: cyclic pattern を使う。pwntools の `cyclic(200)` で非重複系列を生成して流し込み、crash 後に rip/pc の値を `cyclic_find(value)` に渡して直接オフセットを計算する。手作業で A の個数を二分探索しない。
**Q2**: 64 ビット下で rip 値が切り詰められた(canary/アドレスが出力不能で半分しか上書きされない)?
**A2**: 64 ビットアドレスは高位がよく 0 で、crash 時 rip は pattern の先頭数バイトしか取れないことがある。`cyclic_find` では実際に得たバイト数でマッチする。または rsp が指す pattern(`x/gx $rsp`)を見て逆算する。スタック上の pattern はレジスタ内より完全である。
**Q3**: オフセットは求まったが、上書き後も期待する戻りアドレスに到達しない?
**A3**: 途中に canary があるか検査する。オフセット箇所がちょうど canary 位置なら、上書きすると戻り乗っ取りではなく __stack_chk_fail が発火する。gdb で `b __stack_chk_fail` を検証し、ヒットすれば先に canary をリーク/迂回する必要があり、オフセットは canary の後の戻りアドレスまで計算する。
**Q4**: バッファに長さ検査/文字フィルタがあり、pattern が満杯に流し込めない?
**A4**: 戦略を変える。一回限りのオーバーフローに頼らない。ループ書き込み(バイト単位)や複数回書ける場面がないか見る。悪い文字(\x00\n など)があれば cyclic が切り詰められるので、`cyclic(n, alphabet=...)` で悪い文字集合を避ける。
**Q5**: 何度調べても安定したオフセットが出ず、スタックレイアウトがいつも変わる?
**A5**: 直交する方向転換。固定オフセットの発想を捨てる。スタックレイアウトが環境変数/argv 長で浮動するとき、相対特定に変える:スタックアドレスを 1 つリークして相対オフセットで書くか、stack pivot でスタックを完全掌握できるヒープ/bss 領域へ移し、不安定なスタックオフセットへの依存を消す。

### ヒープ問題の着手:どの点でブレークしてヒープレイアウトを観察するか
**Q1**: ヒープ利用問題と判定した(大量の malloc/free)。動的デバッグの第一歩はどこでブレークする?
**A1**: 裸の malloc/free ではなく、ヒープ操作原語のラッパー関数でブレークする。業務コードには通常 add/delete/edit/show のメニューが 1 層包んでいる。各メニュー処理関数の入口でブレークし、各操作後に pwndbg の `heap`/`bins`/`vis_heap_chunks` で chunk レイアウトの変化を見て、「操作→ヒープ状態」のマッピングを構築する。
**Q2**: 特定の chunk のライフサイクルを監視したい?
**A2**: そのアドレスを取った後、ハードウェア書き込みブレークポイント(`watch *addr` / `hbreak`)を張る。それへのあらゆる書き込み(free 後の fd ポインタ書き込みを含む)で止まり、UAF/double free の発火点を掴む切り札である。
**Q3**: free 後の chunk がどの bin(tcache/fastbin/unsorted)に入ったかをどう確認する?
**A3**: free 前後で各 1 回 `bins` を取って比較する。size がどの範囲に落ちるかで行き先が決まる。tcache(デフォルト <0x410 かつ対応 tcache が未満杯)、fastbin、unsorted。これが利用手法を直接決める:tcache poisoning か fastbin dup か unsorted bin leak か。
**Q4**: libc をリークする必要がある。ブレークポイントをどう連携する?
**A4**: unsorted bin 内の chunk の fd/bk は main_arena(libc 内)を指す。chunk を 1 つ unsorted bin に入れ、クリアせずに show すると、リーク値から main_arena 関連オフセットを引けば libc base になる。show の読み取り箇所でブレークして、リークされたのが確かに arena ポインタかを検証する。
**Q5**: ヒープ手法がローカルで通るが、libc バージョンを替えると利用が無効になる?
**A5**: glibc バージョンは強相関(tcache key/安全リンク safe-linking/ポインタ暗号化は 2.32 から導入)。まず対象 libc バージョンを精確に識別し、対応バージョン下で再デバッグする。手法が新版緩和(safe-linking で fd 暗号化など)に阻まれたら、直交する方向転換:裸 fd 上書きに依存しない手法(そのバージョンに適応した House of 系変種、largebin attack、tcache stashing など)に替える。

### 比較関数でブレークする:平文を見る/検証を迂回する
**Q1**: プログラムが入力検証(パスワード/シリアル番号/flag 照合)をする。正しい値を動的に取りたい。どこでブレークする?
**A1**: 比較原語でブレークする。`b strcmp`/`b memcmp`/`b strncmp` で、ヒット時に 2 つのパラメータ(rdi/rsi が指すメモリ)を見る。片方は自分の入力、もう片方は期待値であることが多く、直接 `x/s` で読み出す。これが最も省力な「動的答案取得」である。
**Q2**: 標準ライブラリ比較を使わず、自前ループでバイト単位に比較している?
**A2**: そのループを探す。特徴は、インデックスが増加し、バイト単位で入力とある定数/配列を比較し、不一致でジャンプする。ループ本体の比較命令でブレークし、シングルステップで各ラウンドが自分のバイトと誰を比較するかを見て、「誰」をバイト単位で書き留めれば対象文字列になる。
**Q3**: 検証は入力を変換してから比較する(ハッシュ/暗号化/XOR)。比較点でブレークすると暗号文しか見えない?
**A3**: ブレークポイントを「変換が起きる前」に前倒しするか、変換の逆を掴む。対称変換(XOR、単純加算)なら定数とアルゴリズムを読んで逆算する。ハッシュなら逆算できず、変換関数でアルゴリズム解析するか、(空間が小さければ)ブルートフォースする。重要:比較点で見えるのは変換後の値であり、ここでハッシュを逆算しようと時間を浪費しない。
**Q4**: バイト単位比較だが「全体検証後に正誤判定」で、1 バイトずつ試せない?
**A4**: 「全合致でないと通らない」全体比較なら、動的に期待値を直接読めばよい(上の A1/A2)。「文字ごとの即時フィードバック」(1 文字合えば 1 経路進む)なら、サイドチャネルを使える:タイミング/カバレッジフィードバックで文字単位にブルートフォースするか、angr で各文字を制約求解する。
**Q5**: 検証ロジックが VM 保護/難読化され、ブレークポイントで平文比較が見えない?
**A5**: 直交する方向転換。「比較を読む」を諦め、「シンボリック実行で求解」に変える。angr/Triton で「出力=正しい」を制約に設定し、ソルバーに入力を逆算させ、難読化比較ロジックの人手理解を迂回する。またはブラックボックス fuzz+カバレッジで、ツールに検証を通す入力を探させる。

### その場 patch:検証/アンチデバッグをスキップして直接通す
**Q1**: 検証分岐が道を塞いでいる。命令を直接変えて常に通すようにしたい。どう操作するのが最も安定か?
**A1**: その条件ジャンプ(je/jne/jz)を特定し、動的に `set $eflags` で一時的にフラグを反転して「変えたら通る」を検証する。確認後に永続化方式を決める。デバッグ期の EIP/eflags 変更は一時的で、長期にはバイトを patch する(je→jmp かジャンプを nop、または test 結果を変える)。まず一時検証してから永続化し、最初から乱さない。
**Q2**: patch 後、別の場所でプログラムがクラッシュした。整合性自己チェックサムがあるように見える?
**A2**: コードセクションが CRC/hash 自己チェックサムされると、バイト変更が見つかる。対策:デバッグ期の動的 patch(ディスクへ書き出さず、自己チェックサムは元バイトを読むが実行時に自分が変える)、ハードウェアブレーク+レジスタ変更で迂回、または自己チェックサム関数自体を「常に完全」を返すように先に patch する。
**Q3**: patch したいが、どのジャンプを変えればよいか分からない?
**A3**: 推測しない。2 つの分岐の目標に各々ブレークポイントを張り、正常入力で 1 回走らせてどちらにヒットするか、誤入力で 1 回走らせてどちらにヒットするかを見て、「通過」に対応する分岐を確定し、どのジャンプをどう進めるべきかを逆算する。アセンブリを読んで推測せず、挙動で区別する。
**Q4**: patch はデバッグ推進のためだが、最終 exploit はリモート攻撃で、リモートはバイトを変えられない?
**A4**: 重要注意。patch はローカルの理解/デバッグ手段にすぎず、リモートにはバイナリ改変権がない。リモートは正規入力で自分で対象分岐へ進ませるか、メモリ書き込み原語で実行時にリモートプロセスメモリを変える必要がある。「ローカル patch が通った」を「問題を解いた」と取り違えない。
**Q5**: 保護が強すぎ、あらゆる patch が自己チェックサム/アンチ改ざんに破られる?
**A5**: 直交する方向転換。コードを変えず、データ/環境を変える。検証が読む「データ」を条件を満たすようにし、「コード」を変えない:条件を満たす入力を構成する、依存する外部データ源を hook する、LD_PRELOAD で呼び出すライブラリ関数を置換する(自分のバイトではなく挙動を変える)。コードセクションへの整合性検査を避ける。

### マルチスレッド/子プロセス:ブレークポイントは止まったがスレッドを間違えた
**Q1**: 対象が fork で子プロセスを出してリクエスト処理する。自分が張ったブレークポイントは親プロセスにあり、子プロセスロジックを追えない。どうする?
**A1**: gdb はデフォルトで親プロセスに従う。`set follow-fork-mode child` で子プロセスに従うか、`set detach-on-fork off` で親子を同時に保持する。ネットワークサービス型 PWN(接続ごとに fork)はまず follow モードを正しく設定しないと、ブレークポイントが accept ループの親プロセスで永遠に空転する。
**Q2**: マルチスレッドプログラムで、ブレークポイントがヒットすると全スレッドが乱れ、変数値が合ったり間違ったりする?
**A2**: まずスケジューリングモードを確認する。`set scheduler-locking on` でシングルステップ時に現在スレッドだけを走らせ、別スレッドがシングルステップの隙に共有状態を変えるのを防ぐ。競合解析のときは切る。`info threads`/`thread N` でどのスレッドを見ているか明確にする。
**Q3**: 「自分のこの接続を処理する子プロセス/スレッド」にブレークしたいが、並行が多い?
**A3**: 条件で絞る。ブレークポイントに自分の接続特徴(ある fd、あるリクエスト id、ある送信元ポートに対応する buffer 内容)でマッチする条件を付ける。またはサービスを単一プロセス/単一スレッドで走らせる(多くのサービスに -d/debug/単 worker パラメータがある)ことでデバッグ環境を簡素化し、ロジックが通ってから並行に戻す。
**Q4**: fork 後、子プロセスがすぐ exec で新プログラムになり、ブレークポイントが全部消えた?
**A4**: exec はイメージを置換し、旧ブレークポイントが無効になる。`catch exec` で exec 後に止まり、新イメージにブレークを張り直す。または `set follow-exec-mode new` を使う。setuid 権限昇格チェーンなら、exec 前後の権限/環境変化点に注目する。
**Q5**: 並行デバッグがどうしても整理できず、競合が再現しにくい?
**A5**: 直交する方向転換。「オンラインデバッグ」から「オフライン録画再生」へ。rr はマルチスレッド/子プロセス実行の記録後の決定的再生をサポートし、再現不能な並行バグを繰り返し研究できる固定軌跡に変える。または strace -f で親子プロセスのシステムコールを全量記録し、オフラインで対話系列を解析する。

### リモートデバッグ:対象が別マシン/別アーキテクチャにある
**Q1**: 対象が ARM/MIPS ルーターや別マシンで動いており、ローカルで直接 gdb できない。どうデバッグする?
**A1**: gdbserver でリモートデバッグする。対象側で `gdbserver :port ./prog`(または attach は `--attach pid`)、ローカルで対応アーキテクチャの gdb-multiarch を `target remote ip:port` で接続する。まず対象アーキテクチャを確認(`file` 出力)し、対のクロス gdb を使わないとシンボル/レジスタが全滅する。
**Q2**: 対象が組み込み機器で、gdbserver を入れられない/権限がない?
**A2**: QEMU ユーザーモードエミュレーションに替える。`qemu-arm -g port ./prog` で直接 gdbstub を起動し、ローカルでリモート接続する。実機不要、gdbserver 不要、さらに実ハードウェア依存の一部アンチデバッグを迂回できる。システム級なら `qemu-system-*` 全システムエミュレーション+gdb でカーネルに接続する。
**Q3**: リモートに接続できたが、ブレークポイント挙動が変で、アドレスが合わない?
**A3**: 両端のバイナリが完全に一致するか(同一ファイル、同じロードベースアドレス)を検査する。ライブラリパスが違うと libc シンボル/オフセットがずれる。ローカルで `set sysroot`/`set solib-search-path` を対象のライブラリコピーに向け、gdb が解決するシンボルと対象実行時を一致させる。
**Q4**: リモートデバッグのネットワーク遅延が大きく、シングルステップが極端に遅い?
**A4**: シングルステップを減らし、ブレークポイント直行を多用する。条件ブレークを張って重要点へ一気にジャンプし、往復を減らす。または QEMU ローカルエミュレーションで実機リモートを代替し、ネットワーク往復を消す。timing 敏感なアンチデバッグは低速リモート下でより誤発火しやすいので、エミュレーションできるならする。
**Q5**: 対象機器が完全に閉じていて、gdbserver/QEMU も入れられない?
**A5**: 直交する方向転換。動的デバッグから純静的+断片エミュレーション実行へ。Ghidra/IDA でコアアルゴリズムを静的に逆に見て、Unicorn で関心のある関数断片を単独エミュレーション実行する(レジスタ/メモリ初期値を与えて出力を取る)。実機全体を走らせる必要なし。「システム全体のデバッグ」を「1 関数のエミュレーション」に格下げする。

### strip でシンボルなし:ブレークポイントを張る糸口がない
**Q1**: バイナリが strip され、関数名がない。ブレークポイントを張りたいが関数アドレスが分からない。どう破る?
**A1**: ライブラリ関数は影響を受けない。PLT/動的シンボルはまだあるので、`b malloc`/`b system` がそのままブレークできる。自身の関数は 3 つの手で:文字列相互参照(プロンプト文字列を探す→xref)、インポート関数呼び出し点(printf/read でブレークして呼び出しスタックを見る)、入口 main の特定(_start 内で __libc_start_main に渡される第一パラメータが main)。
**Q2**: 後続のブレークポイントを張りやすくするためにシンボルを一括復元したい?
**A2**: 署名マッチを使う。IDA の FLIRT/Lumina、Ghidra の Function ID で、静的リンクされた libc 関数(memcpy/strlen など)を認識して自動命名できる。libc バージョンを認識した後、対応シンボルをロードすると、大量のライブラリ関数名が戻り、ブレークポイントを直接名前で張れる。
**Q3**: 静的リンクかつ strip で、PLT すらなく、ライブラリ関数も名前がない?
**A3**: 静的リンクのライブラリ関数は署名(FLIRT)で認識するか、挙動特徴で見分ける(memcpy の rep movs ループ、malloc の arena 操作など)。どうしても認識できなければ挙動でブレークする:read/write は最終的に syscall を通るので、`catch syscall read/write` でシステムコール層から遮断し、シンボルに一切依存しない。
**Q4**: 「入力を処理するその関数」だけにブレークしたい。シンボルが全くない?
**A4**: syscall 層で受ける。`catch syscall read`(または recvfrom)がヒットしたら `finish` で呼び出し元へ戻る。そこが入力を読む業務関数なので、アドレスを書き留めてブレークする。システムコールを「アンカーポイント」として業務関数を逆算する。strip も阻めない。
**Q5**: 関数が多すぎ、文字列も難読化され、常規の特定が全滅?
**A5**: 直交する方向転換。カバレッジ誘導特定。Pin/DynamoRIO/QEMU で異なる入力下の実行アドレス集合を記録し、「特定の入力だけが発火するコードブロック」を diff して、それがその入力を処理する重要関数である。実行時挙動の差分を静的シンボル特定の代わりにする。

### watchpoint:ある変数/メモリがいつ改変されるか知りたい
**Q1**: あるグローバル変数/フラグビットがわけもなく変わった。改変者を掴みたい。どうする?
**A1**: ハードウェア書き込みブレークポイント。gdb の `watch *0xADDR`(または `watch varname`)。メモリが書かれたら止まり、`bt` が改変者の呼び出しスタックを直接示す。これが「誰が私のデータを汚染したか」を特定する最も直接的な手段で、逐関数ブレークよりはるかに効率的である。
**Q2**: `watch` を張ったが「software watchpoint」と出て極端に遅い?
**A2**: ソフトウェア watchpoint はシングルステップ検査で遅く、使えない。ハードウェア watchpoint を確保する。多くのプラットフォームで gdb が自動選択するが、なければハードウェアデバッグレジスタ数を超えていないか(x86 は 4 個の DR のみ)、アドレスがアラインされていないかを検査する。ARM/組み込みは対象がハードウェアブレークポイントをサポートするか確認する。
**Q3**: 1 バイトでなく、まとまったバッファ全体の読み書きを監視したい?
**A3**: ハードウェアブレークポイントには長さ制限(通常 1/2/4/8 バイト)がある。大領域を監視するときは「番兵バイト」(領域の先頭/末尾または重要フィールド)を watch する。または `rwatch`(読み取り)/`awatch`(読み書き)を必要に応じて使う。全セクションを監視するならページ級保護(mprotect で書き込み不可にし、書き込みで SIGSEGV を発火してスタックを見る)がより柔軟である。
**Q4**: watch のヒットが多すぎ、変数が合法に何度も書かれ、「異常」なその回を見つけられない?
**A4**: 条件を付ける。`watch var if var == 0xdeadbeef`(特定値に書かれたときだけ止まる)、または `if $rip == 特定セクション` で特定コード領域の書き込みだけを関心対象にする。異常値/異常書き込み者をフィルタ条件にし、大量の正常書き込みをスキップする。
**Q5**: watchpoint のハードウェア資源が足りない/対象がサポートしない。監視できない?
**A5**: 直交する方向転換。ページ保護か録画再生で代替する。mprotect/VirtualProtect で対象ページを書き込み不可にし、SEGV handler で書き込み者を捕獲する(大範囲を監視できる)。または rr で録画してメモリアドレスに逆方向 watch を掛ける(reverse execution で最後の書き込みを調べる)。ハードウェアデバッグレジスタを消費しない。

### ROP チェーンの検証:組めたのに通らない
**Q1**: ROP チェーンを書いたがローカルで通らない。デバッガでどの gadget に問題があるかどう特定する?
**A1**: 最初の gadget へ ret する直前の戻り箇所(スタックオーバーフローの戻り点)でブレークし、その後シングルステップ `si` で ROP チェーンを歩く。各 ret ごとに自分の期待アドレスと照合し、何番目のジャンプでずれたかを見る。rsp がチェーンの次項を指すか、rdi/rsi などのレジスタが正しく設定されたかを照合する。
**Q2**: チェーンが途中のある gadget でクラッシュした?
**A2**: 落ちた命令を見る。よくある落とし穴:gadget 内に欲しい pop 以外に副作用命令がある(余分な値を pop してスタックがずれる)、または gadget アドレスの計算ミス(PIE/libc base を足し忘れ)。その gadget の逆アセンブルを照合し、スタック上に用意したパディング項目数と、実際に pop する数が一致するか確認する。
**Q3**: スタックアラインメント問題(system 呼び出しで movaps がクラッシュ)?
**A3**: 64 ビット下で system/libc 関数を呼ぶ前に rsp は 16 バイトアラインメントが要り、そうでないと movaps が SIGSEGV を発火する。system に入る前に `p $rsp & 0xf` を調べ、非 0 ならチェーンに ret gadget を 1 つ足してアラインメント補正する。これはローカルで通り、リモート/特定環境で通らない古典原因である。
**Q4**: シングルステップ検証では合っているが、連続実行(continue)するとクラッシュする?
**A4**: 問題は「ブレークポイントなしの実実行環境」にあることを示す。バッファ/悪い文字でチェーンが転送中に切り詰め/改変された可能性がある。悪い文字(\x00\x0a など)がチェーンのアドレスに現れないか、読み込み関数が期待する長さでチェーン全体を受信したかを検査する。
**Q5**: チェーンのロジックは全合致なのに通らない。繰り返し検証しても解がない?
**A5**: 直交する方向転換。長いチェーンへの依存を下げる利用技術に替える。ROP チェーンは長いほど脆い。より短く安定した経路に替える:ret2libc で 1 回 system を呼ぶ、ret2dlresolve(leak 不要)、SROP(1 回の sigreturn で全レジスタを一度に設定)、one_gadget へ乗っ取る(制約 1 つ満たせば getshell)。「短チェーン/単点」で脆い長チェーンを代替する。

### one_gadget:制約が満たせず打てない
**Q1**: libc base がある。one_gadget で一歩 getshell したいが、跳んでも shell が起きない。どう調べる?
**A1**: one_gadget の各候補には制約が付く(`[rsp+0x40]==NULL` や rdx/rsi が 0 など)。`one_gadget libc.so` で全候補と制約を列挙し、gadget へジャンプする瞬間にブレークして、現在のレジスタ/スタックがどの候補の制約を満たすかを逐個検査し、満たすものを使う。
**Q2**: 全 one_gadget の制約が現在満たされない?
**A2**: 諦めず、まずどれだけ足りないかを見る。あるレジスタが 0 であることだけ足りないなら、gadget へジャンプする前に 1 つの gadget でゼロにできないか。または乗っ取り点を替える。発火点が異なれば(malloc hook/free hook/exit handler/戻りアドレス)、gadget 到達時のレジスタコンテキストが異なり、点を替えると制約が満たされることがある。
**Q3**: 高バージョン glibc で __malloc_hook/__free_hook がなくなり、乗っ取り点が減った?
**A3**: 2.34+ はこれらの hook を削除した。新乗っ取り点へ方向転換する:__exit_funcs(exit 時のデストラクタチェーン、pointer guard が付くため要リーク/迂回)、_IO_FILE 構造の vtable(FSOP/House of 系)、tls_dtor_list。one_gadget へ跳ぶ担体は変わったが、発想は同じ。「自分が変えられ+プログラムが呼ぶ関数ポインタ」を 1 つ探す。
**Q4**: 制約は満たしたが execve("/bin/sh") が立ち上げた shell がすぐ終了する?
**A4**: しばしば stdin/stdout 環境問題(リモートは特に)。exp の `p.interactive()` 前にストリームを閉じていないか確認する。execve の第三パラメータ(envp)が不正だと異常になり得るので、rdx がよりきれいな gadget に替えるか、ret2system で明示的にパラメータを制御する。
**Q5**: one_gadget の道が完全に通らない(制約が死活満たせない、バージョンに hook なし)?
**A5**: 直交する方向転換。「一歩で完了」を諦め、制御可能な複数ステップに戻る。ROP で明示的にパラメータを設定して execve/system を呼ぶ(rdi/rsi/rdx を自分で制御すれば one_gadget の制約に縛られない)。または orw(open-read-write)で flag ファイルを直接読む(execve 禁止のサンドボックス場面に適用)。制約に勝てなければ自分でコンテキストを作る。

### libc バージョン識別:オフセットが全部間違う根源
**Q1**: libc 内のアドレスをリークして base を計算したいが、リモートがどの libc バージョンか分からず、オフセットが定まらない。どうする?
**A1**: リーク値の下位 12 ビット(ページ内オフセット、ASLR 不変)を libc-database/blukat.me でマッチする。既知シンボル 1-2 個(puts/read の GOT 値など)の下位 3 ビットをリークすると、データベースが候補 libc を逆引きするので、対応 .so をダウンロードして全オフセットを取得する。
**Q2**: 候補 libc が複数出た?
**A2**: シンボルをもう 1 つリークして範囲を絞る。2 シンボルの下位ビットの組み合わせでほぼ一意にバージョンが定まる。または問題環境の手がかり(Ubuntu バージョンは特定 glibc に対応)を見る。候補を得たら、ローカルでその libc で 1 回打って、通ればそれが正解である。
**Q3**: 問題が直接 libc.so.6 ファイルをくれる。それでもバージョンを識別する必要があるか?
**A3**: くれるならそれでオフセットを直接計算するが、「くれるものがリモートで実際に使うものか」を確認する。`strings libc.so.6 | grep "GNU C Library"` でバージョン番号を見て、loader(`ld.so`)を対にして正しいバージョンでローカルテストする(`patchelf --set-interpreter`/LD_PRELOAD)。ローカル loader と問題 libc の不一致による偽失敗を避ける。
**Q4**: バージョンは合っているのにヒープ手法がやはり無効?
**A4**: 小バージョンの差も致命的。tcache(2.26+)、safe-linking(2.32+)、hook 削除(2.34+)、House of の各種緩和は特定バージョンに張り付く。小バージョン番号まで精確にし、そのバージョンの緩和状態で手法を選ぶ。大バージョンだけで判断しない。
**Q5**: マッチする libc が死活見つからない/魔改造 libc?
**A5**: 直交する方向転換。libc オフセット非依存の利用。ret2dlresolve(libc アドレス不要、動的リンカを濫用して system を自己解決)、または純 ROP でプログラム自身の .text 内 gadget で orw を完成して flag を読む。魔改造/未知 libc では、攻撃面をプログラム自身と loader の、自分が確定情報を持つ部分へ縮小する。

### シングルステップが遅すぎる:大ループ/初期化が時間を食う
**Q1**: 重要ロジックの前に数百万回回るループや大初期化があり、シングルステップでは一生かかる。どう素早く越える?
**A1**: シングルステップしない。ループ後の最初の命令にブレークして直接 `continue` で越える。または現行関数を `finish` で戻りへジャンプ、`until` でループを抜ける、`advance アドレス` で指定位置へ一歩で進む。シングルステップは最後の数命令だけに使う。
**Q2**: ループ内部に自分が関心を持つある反復(第 N 回目で問題が出る)がある?
**A2**: 条件ブレークでその回に固定する。`b ループ体 if $rcx==N` か、処理データ内容でマッチ(`if *($rdi)==対象値`)。デバッガにループを数えさせ、関心のある反復で直接止まる。
**Q3**: ループが何回回ったか/何回ヒットしたかを止まらずに統計したい?
**A3**: `ignore ブレーク番号 回数` で前 N 回をスキップする。または dprintf/コマンドリストでヒット時に出力して止まらない(`commands`+`continue`)。ブレークポイントをログとして使い、逐回手動でなく一括観察する。
**Q4**: 初期化段階に大量の malloc/暗号化・復号があり、デバッグ全体を遅くする?
**A4**: 関心のない段階をスキップする。ブレークポイントを直接業務入口(main 内の入力読み取り後など)に張り、`starti` 後 1 回の `continue` で直行し、初期化を全速で走らせる。本当に観察したい窓内だけを精細にデバッグする。
**Q5**: ループ内にアンチデバッグのタイマーがあり、遅いと発火する。早送りも駄目?
**A5**: 直交する方向転換。エミュレーション実行でスキップする。Unicorn/Qiling でこのループを全速エミュレーションして結果状態を取り、その状態を実機デバッグの後続に戻す。またはタイマー検査を直接 patch する。「エミュレーションで結果を計算」を「実機でループを走らせる」代わりにし、速くかつタイミングアンチデバッグを避ける。

### 自己書き換えコード/パッカー:ブレークポイントを張ってもコードがまだ解けていない
**Q1**: 静的に見えるコードはジャンクコード/暗号化で、実行時に復号される。ブレークポイントを静的アドレスに張ると乱れる。どうする?
**A1**: まず自己復号させてからブレークする。復号ループの後、復号後コードを実際に実行する前にブレークする(通常、復号完了後に解いた領域へジャンプするので、その jmp/call 目標でブレーク)。または書き込まれるコードページにハードウェア書き込みブレークポイントを張り、書き込み完了で止まる。この時点のメモリが実命令である。
**Q2**: パッカー付きプログラムで、元の入口点(OEP)にブレークしたい?
**A2**: OEP を探す古典法:ESP 定律(パッカーは解凍完了時にスタックを均衡させ、入口 pushad 後に esp にハードウェアブレークを張り、pop で戻るときが OEP 近傍)。またはコードセクションを実行不可にし、パッカーが解いたコードへ跳ぶと例外で止まる。OEP 到達後に dump+IAT 修復でアンパック済みサンプルを得る。
**Q3**: コードが実行しながら自分を変える(SMC)ので、ブレークポイントバイトが復号に上書きされる?
**A3**: ソフトウェアブレークポイント(0xCC)は自己書き換えに上書きされるか、検証を妨害する。ハードウェア実行ブレークポイント(メモリ不変)に替え、「コードが安定した後」のアドレスに張る。セクション全体が繰り返し自己書き換えするなら、その領域への書き込み動作に書き込みブレークポイントを張り、毎回何に変わるかを追う。
**Q4**: 復号が実行時鍵/環境に依存し、静的にはアンパックできない?
**A4**: 純動的 dump する。コード復号完了の瞬間まで走らせ、メモリからこのセクションを直接 dump(gdb の `dump memory`)して静的解析に回す。完全なアンパックを追求せず、関心のあるそのセクションの平文命令だけを取得すればよい。
**Q5**: パッカーが強すぎ(仮想化保護/多層)、アンパック/動的も困難?
**A5**: 直交する方向転換。アンパックせず、I/O 意味論だけを観察する。VMP/Themida 系仮想化パッカーはリバースエンジニアリングコストが極めて高いので、ブラックボックスにする:それが呼ぶ重要 API(ネットワーク/ファイル/暗号化・復号)を hook して入出力を見るか、最終的に落ちるシステムコールを trace し、「それが対外的に何をしたか」から機能を逆算し、「内部でどうするか」を迂回する。

### フォーマット文字列:制御可能な fmt パラメータ位置を特定する
**Q1**: フォーマット文字列脆弱性(printf が直接ユーザー入力を食う)を疑う。動的にどう確認しパラメータオフセットを特定する?
**A1**: まず確認する。`%p %p %p` を入力し、原様回帰なら普通の文字列、スタック上の値(アドレス/文字化け)を出力すれば脆弱性確定。その後 `AAAA%p.%p.%p...` または `%1$p %2$p ...` を入力し、どの %p が 0x41414141 を打つか数える。その番号が入力のパラメータオフセットである。
**Q2**: 任意書き込み(%n)が対象アドレスにヒットできるか検証したい?
**A2**: printf 内部でブレークし、fmt を組んだ後 %n 処理までシングルステップし、書こうとするアドレス(pwndbg が表示)を調べ、自分の対象アドレスと等しく、書き込み値が出力済み文字数と等しいか確認する。pwntools の `fmtstr_payload` で生成してから動的に再照合するのが最も安定である。
**Q3**: スタック上に自分の入力オフセットが見つからない(入力が別バッファにある)?
**A3**: 入力がスタックにないとき、%n の書き込み対象は「スタック上の既存ポインタチェーン」に頼る。スタック上の、スタックを指すポインタを 1 つ探し、それでまず位置を特定し、多段 %n で間接書き込みする。または発想を変える:多くの fmt 利用は入力がスタックにある必要はなく、GOT/戻りアドレスの書き換えは既存スタックポインタの 1 つが使えればよい。
**Q4**: %n が無効(FORTIFY の %n 検査)または出力が長さ制限される?
**A4**: `_FORTIFY_SOURCE` は書き込み可メモリ内の %n を禁止する。読み取り専用原語に替える:純リーク(%p/%s で canary/libc/スタックアドレスをリーク)を別の書き込み原語と組み合わせる。または長さ制限だけなら、`%hn`/`%hhn` で分割して小額ずつ書く、バイト単位で対象に書く、一回の大数書き込みを迂回する。
**Q5**: fmt の道が利用しきれない(検査が厳しすぎ/オフセットが制御不能)?
**A5**: 直交する方向転換。fmt を純粋な情報リークエンジンに格下げし、他の脆弱性と組み合わせる。任意書き込みができなくても、fmt の canary/libc base/PIE base リーク能力は極めて強く、そのリークをスタックオーバーフロー/ヒープ脆弱性に供給して利用を完成させる。1 つの脆弱性が通じないなら情報源として使い、別の原語と組み合わせる。

### canary:スタックオーバーフローが canary に阻まれる
**Q1**: スタックオーバーフローは発火できるが、戻ると __stack_chk_fail が canary クラッシュを報告する。どう進める?
**A1**: まず gdb でスタック上の canary 位置と値(pwndbg の `canary`)を特定し、自分のオーバーフローがそれを跨ぐ必要があるかを見る。canary を上書きせず目的を達成できるなら(ある局所ポインタだけを変えるなど)最良。そうでなければ先に canary 値をリークし、オーバーフロー時に元値を埋め戻す必要がある。
**Q2**: canary をどうリークする?
**A2**: 情報リーク原語を探す:フォーマット文字列 %p でスタックを出力(canary の特徴は最下位バイト 00、残りはランダム)、範囲外読み取り、または「バイト単位で書いて切り詰めない」入力関数(read が 00 を足さない)とバイト単位ブルートフォースを組み合わせる(毎回 1 バイト多く書き、クラッシュしなければそのバイトが合致。ASLR なしまたは fork で canary が不変なサービスに適する)。
**Q3**: fork サービスで canary をバイト単位にブルートフォースしたい?
**A3**: fork された子プロセスは親プロセスの canary を継承する(再ランダム化しない)ので、バイト単位にブルートフォースできる。各位置で 0~255 を試し、子プロセスがクラッシュしたら次へ、クラッシュしなければヒット。8 バイトで最大 8*256 回。前提はクラッシュが親プロセスの継続 fork に影響しないこと。サービスが fork モデルと確認してからこの手を使う。
**Q4**: canary をリークしたが埋め戻してもやはりクラッシュする?
**A4**: 一部バイトしかリーク/上書きしていないか、canary 位置の計算ミスを検査する。canary から戻りアドレスまでの間には保存された rbp もあり、レイアウトは精確でなければならない。gdb で実際のスタックフレームを照合する:入力→buf→canary→rbp→retaddr、逐項オフセットを照合する。
**Q5**: リーク原語が一切なく、fork モデルでもない。canary を迂回できない?
**A5**: 直交する方向転換。canary に守られた「戻りアドレス」の道を迂回する。canary は関数の戻りだけを守り、以下は守らない:GOT/関数ポインタ(これらを変えても canary 検査を通らない)、局所構造体内のポインタ(canary より前で、上書きできる)、ヒープ上の対象。スタック canary を発火させない書き込み対象に変えるか、canary のない入力点/関数に替える。

### 環境不一致:ローカルで通ってリモートで通らない
**Q1**: exp がローカルで安定して getshell するが、リモートで同じ入力をすると失敗する。どこから調べる?
**A1**: 「最も可能性が高い」順に切り分けする。①libc バージョンが違う(オフセット全滅)②スタック上の初期環境が違う(argv/envp/環境変数の数がスタックレイアウトを変える→スタックアドレス/アラインメントに影響)③バッファ/対話タイミング(リモート recv が分割パケット、ローカルは一括受信)。まず libc バージョンという第一容疑者を確定する。
**Q2**: 対話タイミング/送受信の問題を疑う?
**A2**: ローカルで `p = remote` を自分のサービスに向けて、リモート挙動を再現する。各 `recvuntil` が本当に期待区切りを受けたか(リモートにはローカルが想定するプロンプト文字列がないかもしれない)を検査する。`p.recvrepeat`/精確な `recvuntil` で脆い固定長 recv を代替し、分割パケット差を消す。
**Q3**: スタックアドレス/アラインメントの差を疑う?
**A3**: リモートの envp/argv がローカルと違うとスタックが平行移動し、ハードコードしたスタックアドレスが無効になるか、16 バイトアラインメント状態が変わる(system の movaps クラッシュ)。exp ではスタックアドレスをハードコードせず(リーク+相対)、ROP チェーンに ret gadget を 1 つ予約してアラインメントを受ける。
**Q4**: リモートに近い環境でローカル再現したい?
**A4**: 問題の Dockerfile/libc/ld で一致環境を構築する:`patchelf --set-interpreter ./ld --set-rpath . ./prog` でローカルに問題の loader+libc で走らせるか、直接同バージョンコンテナ内でデバッグする。環境を揃えてからデバッグし、本機システム libc で偽テストしない。
**Q5**: 各種の切り分けをすべて揃えてもリモートが失敗する。なすすべがない?
**A5**: 直交する方向転換。精確な再現を追求するより exploit のロバスト性を高める。リモートには見えない変数(ASLR エントロピー、並行、タイムアウト)がある。より揺らぎに強い技術に替える:ヒープスプレー/広域 nop sled で誤差を許容、複数回試行スクリプト(リモート ASLR は低エントロピーのブルートフォース、fork がアドレスを保持するなら再接続)、「精確が必要」なステップを「確率ヒット」戦略に置換する。

### seccomp サンドボックス:getshell が起動しない
**Q1**: 実行フローは取れたが execve("/bin/sh") が無反応。seccomp を疑う。どう確認する?
**A1**: 静的/動的にフィルタを調べる。`seccomp-tools dump ./prog` で禁止 syscall を直接列挙する。execve/execveat が ban なら、shell を起動するこの道は行き止まりなので、何を許可したか(通常 open/read/write が残る→ orw で flag を読む)を見る。まずホワイトリストを得てから利用方向を定める。
**Q2**: execve 禁止、open/read/write 許可を確認した?
**A2**: orw へ方向転換する。ROP で `open("flag",0)` → `read(fd,buf,n)` → `write(1,buf,n)` を構成し、flag ファイルを直接読んで出力する。shell は不要。デバッガで各 syscall のレジスタパラメータが正しく、fd 戻り値が期待どおりかを検証する。
**Q3**: open まで禁止され、openat/他の変種しか許可されない?
**A3**: ホワイトリスト内の等価 syscall を見る。openat で open を代替、readv/preadv で read を代替、sendfile でファイルを直接 fd 1 へ送る(1 手で flag を出す、buf 不要)。seccomp は具体番号だけを ban することが多く、機能等価の別 syscall 番号で迂回する。
**Q4**: フィルタがさらにアーキテクチャを制限(x32 禁止/特定レジスタ禁止)?
**A4**: あるフィルタは arch を検査して x32 syscall の混用を防ぐ。古い套路は x86-32 互換モードに切り替えて別 syscall テーブルを使うことだが、フィルタが既に arch==x86_64 を検証していれば塞がる。ホワイトリスト内に戻って可能な組み合わせを探し、専用に塞がれた道へ力ずくで突かない。
**Q5**: ホワイトリストが極めて狭く、orw も組めない?
**A5**: 直交する方向転換。flag ファイルを読まず、別の情報出口か権限昇格面へ。ネットワーク syscall(socket/connect/sendto)が許可されていれば flag を帯外送信する。これが権限昇格チェーンの 1 環なら、目標はファイルを読むことではなくある状態を変えることかもしれない。問題を読み直す:サンドボックスがこれほど厳しいなら、想定解は execve/orw を経ない論理脆弱性かサイドチャネルの可能性が高い。

### catch syscall:システムコール層から挙動をアンカーする
**Q1**: このプログラムが何をしているか全く分からず、シンボルもない。システムコール層からその挙動を素早く掴むにはどうする?
**A1**: `catch syscall` で全システムコールにブレークする(または `catch syscall open read write connect` と指定)。各ヒットでレジスタ内の syscall 番号とパラメータを見る。これは「プログラムが OS に対して何をしたか」の最底層の真実で、どんなユーザー空間コードを追うより信頼でき、アンチデバッグも本物の syscall を偽造しにくい。
**Q2**: 特定の類(ファイル/ネットワーク)に集中したい?
**A2**: 関連 syscall だけを catch する。ファイル系 open/openat/read/write/unlink、ネットワーク系 socket/connect/bind/sendto/recvfrom、プロセス系 execve/fork/ptrace。疑う機能で選び、無関係な syscall に溺れない。ptrace は特に catch すべきである。それはアンチデバッグの印である。
**Q3**: syscall ヒット後、どの業務コードが発起したか知りたい?
**A3**: ヒット時に `bt` でスタックを見るか、`finish` で呼び出し点へ戻る。そこがその操作を発起した関数である。syscall をアンカーに、`finish` で業務層へ浮上し、重要関数アドレスを逆算してから精細にブレークする。
**Q4**: プログラムが直接 syscall 命令を使い(libc ラッパーを通らない)、`b read` がブレークできない?
**A4**: 静的コンパイルか手書き syscall は libc シンボルを迂回し、`b read` は当然ブレークできないが、`catch syscall read` はそのままブレークする。それはカーネル境界を遮断するので、どうやってカーネルに入るかは問わない。これが catch syscall の関数ブレークポイントに対する核心優位である。
**Q5**: syscall 層でも糸口がない(ロジックがすべてユーザー空間計算で、ほぼ syscall しない)?
**A5**: 直交する方向転換。純計算型プログラム(crackme/アルゴリズム問題)は syscall しないので、ユーザー空間に戻ってカバレッジ/テイント解析を使う。Pin/Triton でテイント追跡し、入力バイトがどう演算を経て判定に影響するかを追うか、angr でシンボリック実行して求解する。syscall アンカーは I/O 密集プログラム向きで、純アルゴリズムはデータフロー解析ツールに変える。

### 動的に鍵を取る:暗号化・復号関数の平文/鍵を掴む
**Q1**: プログラムがデータを暗号化して送信/保存する。平文か鍵を取るにはどこでブレークする?
**A1**: 暗号化関数の入力側(平文が入る前)と鍵ロード箇所でブレークする。標準ライブラリ(OpenSSL EVP_*、CryptEncrypt)ならこれらの API に直接ブレークし、第一パラメータ領域が平文/鍵であることが多い。自前実装ならデータフローを見て、「ネットワーク送信/ファイル書き込み前の最後の変換」でブレークする。その前のメモリが平文である。
**Q2**: 対称鍵を掴みたい?
**A2**: 鍵はハードコード(静的に高エントロピー定数/S-box 特徴を検索してアルゴリズムを識別)か、実行時に導出される。暗号化コア関数の入口でブレークする。鍵は通常パラメータとして渡されるか、ある構造体に setup された直後である。鍵を保持するメモリに読み取りブレークポイントを張り、初期化時に誰が書いたかを見る。
**Q3**: 受信した暗号文を復号するだけでよい(アルゴリズム詳細は不要)?
**A3**: プログラム自身の復号関数を再利用する。デバッガでそれを制御し、自分の暗号文をその復号入力バッファに入れ、復号関数を手動呼び出し(gdb の `call`)して、プログラムに自分で解かせる。自分でアルゴリズムを再実装するよりはるかに速い。
**Q4**: 鍵が毎回のセッションでネゴシエーションされる(TLS/DH)?
**A4**: 長期鍵ではなくネゴシエーション後のセッション鍵を掴む。対称暗号が有効になった瞬間(鍵ネゴシエーション完了後)にブレークし、メモリからセッション鍵を dump する。または暗号化関数を hook して平文をバイパス記録する。鍵交換の数学を逆に見ず、落ちたセッション鍵を直接掴む。
**Q5**: 暗号化・復号がプロテクト/難読化領域にあり、ブレークポイントが入れない?
**A5**: 直交する方向転換。アルゴリズムに触れず、端から端へのバイパスをする。データが「暗号化に入る前」と「復号から出た後」のきれいな境界にブレークポイントを張る(通常は業務層バッファ)。または LD_PRELOAD で呼び出す暗号ライブラリ関数を hook して入出力パラメータを記録する。「アルゴリズムを逆に見る」問題を「平文境界でデータを掴む」に変える。

### ブレークポイントが止まらない:ヒットしない切り分け
**Q1**: ブレークポイントを張って `continue` したら直接走り切った/クラッシュした。ブレークポイントがまったくヒットしない。まず何を調べる?
**A1**: まずブレークポイントが本当に実行されるアドレスに張られたか確認する。`info breakpoints` で resolved かを見る(pending はモジュール未ロード)。PIE/共有ライブラリ未ロード時はアドレスが間違い。`starti` で最早期に止まり、対象モジュールロード後(`catch load`)にブレークするか、シンボル名で gdb に遅延バインディングさせる。
**Q2**: ブレークポイントは張られたと表示され、アドレスも合っているのにヒットしない?
**A2**: そのコードがそもそも実行されていない(別の分岐を進んだ)可能性。制御フローが本当にここに来るか、より前の必経点でブレークして検証する。またはプロセスが fork していて、自分がブレークしたのはこのセクションを走らないプロセス(follow-fork 参照)。アンチデバッグが早期 detach した可能性もある。
**Q3**: ライブラリ関数にブレークしたが、プログラムが静的リンク/インラインで、シンボル名が間違った場所を指す?
**A3**: インライン/LTO は「関数」を消すか複数コピーを作る。`info line`/逆アセンブルで、自分がブレークしたアドレスが本当にそのロジックかを照合する。静的リンク時 `b read` は libc 内部にブレークし業務呼び出し点でないことがある。具体アドレスか syscall 層にブレークし直す。
**Q4**: ハードウェアブレークポイントを張っても反応しない?
**A4**: ハードウェアデバッグレジスタが対象自身に占有されている(アンチデバッグが DR レジスタに書き込み、自分のブレークを消す)か、数上限を超えている(x86 は 4 個のみ)。DR レジスタ状態を検査し、同時に使うハードウェアブレークポイントを減らすか、ソフトウェアブレークに替えて相互検証する。
**Q5**: 各種ブレークポイントがどれもヒットせず、系統的に妨害されているように見える?
**A5**: 直交する方向転換。観測機構を替える。プロセス内ブレークポイントがアンチデバッグに無力化されたら、プロセス外/カーネル層観測を使う:ftrace/eBPF/uprobe でカーネルプローブを掛ける、Intel PT で全量制御フロー軌跡を記録する、QEMU エミュレーション実行でインスツルメントする。「そのプロセス内でブレーク」から「その外で軌跡を録る」へ転じる。

### 逆方向デバッグ:結果は分かるが原因が分からない
**Q1**: プログラムの最後の変数が悪い値だが、それを悪くした過程は既に走り終え、再実行も再現しにくい。どう逆に調べる?
**A1**: タイムトラベルデバッグを使う。`rr record ./prog` で 1 回録画し、`rr replay` で悪い値が現れるところまで走り、そのメモリを `watch` してから `reverse-continue`。最後に「それを書いた」場所まで逆方向実行し、汚染源を直接特定する。順方向デバッグは繰り返し再実行して推測するが、逆方向デバッグは一歩で届く。
**Q2**: rr 録画時のプログラム挙動が裸実行と違う(rr 下では再現しない)?
**A2**: rr はマルチスレッドを直列化し、競合を隠すことがある。バグが本物の並行に依存するなら、rr は逆に再現できない。このとき非決定的録画に替えるか、1 回のクラッシュ core dump を直接掴んで事後解析する。バグが並行依存かを判断して rr の使用を決める。
**Q3**: 「この関数ポインタが誰に不正値へ変えられたか」を逆に調べたい?
**A3**: replay でそのポインタを `rwatch`/`watch` し、`reverse-continue` で最後の書き込み点に止まり、`bt` で改変の呼び出しスタックを得る。UAF/型混同/オーバーフローで関数ポインタを変える「犯人が遠くにいる」バグは、逆方向 watch が最速の特定法である。
**Q4**: rr が対象アーキテクチャ(ARM/組み込み)をサポートしない?
**A4**: rr は主に x86 をサポートする。対象が ARM/MIPS なら、QEMU 全システムエミュレーションの record/replay、または gdb 自前の `record`(process record、遅いが逆方向可)、または密ログ(dprintf で各ステップ状態を出力)でオフラインにタイムラインを再構築する。
**Q5**: 逆方向デバッグでも根本原因が特定できない(状態汚染がプロセス/モジュールを跨いで散りすぎ)?
**A5**: 直交する方向転換。テイント解析でデータの出所を追う。逆方向実行は「誰が最後に書いたか」を得意とするが、汚染が複数ホップを跨ぐとき、Triton/Pin のテイント追跡で「悪い値がどの入力バイトから流れてきたか」をマークし、データ伝播チェーンの角度から根本原因を探す。時間次元ではない。

### デバッガ選び:gdb 系かそれ以外か
**Q1**: 新タスクに着手する。どのデバッグツール群を使う?判定基準は?
**A1**: プラットフォーム+対象で定める。Linux ELF/PWN → gdb+pwndbg/gef(ヒープ可視化、ROP、ワンクリック leak)。Windows → x64dbg(ユーザーモード)/WinDbg(カーネル&複雑)。クロスアーキテクチャ/組み込み → gdb-multiarch+gdbserver/QEMU。マクロ解析は IDA/Ghidra 静的を併用。1 本のハンマーで全釘を打たない。
**Q2**: gdb 素のままは使いにくい。pwndbg/gef/peda はどれを選ぶ?
**A2**: PWN 場面では pwndbg が最も充実(heap/bins/vis、telescope、自動 leak)、gef は UI が親切でプラグインが多く、peda はやや古い。1 つ入れて使いこなせばよく、全部入れない(コマンド衝突)。核心は、ヒープ可視化、レジスタ/スタックコンテキスト自動表示、pattern/rop 補助の存在である。
**Q3**: Windows カーネルドライバ/ブルースクリーン級の対象に出会った?
**A3**: x64dbg はユーザーモードで、カーネルには WinDbg + 二重マシンデバッグ(VM+シリアル/ネットワーク)かローカルカーネルデバッグが要る。ドライバ、rootkit、カーネル権限昇格脆弱性は必ず WinDbg 系で、ユーザーモードデバッガに期待しない。
**Q4**: 対象に強いアンチデバッグがあり、主流デバッガは入るとすぐ見破られる?
**A4**: より隠密な組み合わせに替える:x64dbg+ScyllaHide、gdb に LD_PRELOAD のアンチアンチデバッグ、または直接エミュレータ(QEMU/Qiling)/DBI フレームワーク(Frida/Pin)を使う。これらは伝統的な ptrace/デバッグポートで付着せず、アンチデバッグ検知面が異なる。
**Q5**: 対話式デバッガがすべて対象環境に拒まれる(GUI なし、権限なし、検知が厳しい)?
**A5**: 直交する方向転換。DBI/インスツルメントで対話デバッグを代替する。Frida のスクリプト hook(GUI 不要、本番プロセスに注入可)、Pin/DynamoRIO インスツルメント記録、または純静的+Unicorn エミュレーション。「人がデバッガ前でシングルステップ」から「スクリプト自動インスツルメント採取」へ転じ、無人/制限環境に適応する。

### テイント/カバレッジ:入力が多すぎてどのバイトが重要か分からない
**Q1**: 大きな入力(数百バイト)で、数バイトだけが判定に影響する。重要バイトをどう素早く見つける?
**A1**: テイント解析を使う。Triton/libdft/Pin で入力をテイント源としてマークし、1 回走らせて、どのバイトのテイントが判定分岐の比較オペランドへ伝播したかを見る。その数バイトが重要バイトである。バイト単位の diff 試行より精確である。
**Q2**: テイントツールがない。土方流でどう見つける?
**A2**: カバレッジ差分:バイト単位(またはブロック単位)で入力を変異し、毎回の基本ブロックカバレッジを記録する(QEMU/DynamoRIO の bbtrace)。カバレッジが変わるバイトが制御フローに影響する重要バイトである。手動版は「1 バイト変えて挙動が変わるか見る」。
**Q3**: 重要バイトを見つけた後、その正しい値を解きたい?
**A3**: 制約求解に任せる。angr/Triton で重要バイトにシンボル変数を建て、「通過分岐への到達」を目標に設定し、ソルバーに満たす値を解かせる。または空間が小さければその数バイトを直接ブルートフォースする。変換ロジックを人力で逆に見ない。
**Q4**: テイント伝播が中断(データがある不透明変換/ルックアップテーブルを通った)?
**A4**: テーブル駆動/ビット演算はよくテイント解析を「濁らせる」(過剰汚染かテイント喪失)。変換点の前後で各 1 回データを dump して人手で橋渡しするか、その変換だけを Unicorn で単独エミュレーションして入出力マッピングを確立し、全体解析に組み戻す。
**Q5**: テイント+カバレッジ+シンボリック実行がすべてこの対象で無効(経路爆発/難読化)?
**A5**: 直交する方向転換。ブラックボックス fuzzing+人手へ退く。自動化ツールが全滅するほど難読化されたら、カバレッジ誘導 fuzz(AFL++ qemu モード)で運試しに通過入力を探し、同時に最も重要なその小さな判定ロジックだけを人手で逆に見る。「完全理解」を諦め、「通る入力を見つける」ことを追求する。

### 実行中プロセスへの付着:attach のタイミングと落とし穴
**Q1**: 対象が既に走っている(デーモン/発火済み状態)。attach すべきか再起動デバッグすべきか?
**A1**: 状態が再構築しにくい(確立済み接続、ロード済み実行時データ)なら attach する(`gdb -p PID`)。初期化から見るなら再起動デバッグ。attach はプロセスを一時停止するので、worker を間違えて attach しない(マルチプロセスサービスは先に `pstree`/`ps` で自分のリクエストを処理する PID を見つける)。
**Q2**: attach 時に ptrace 権限不足と出る?
**A2**: `ptrace_scope` 制限(Yama)。root があれば `echo 0 > /proc/sys/kernel/yama/ptrace_scope`。root なしなら自分が起動した子プロセスだけをデバッグできる(親子関係は免除)。attach でなく起動デバッグに変えるか、CAP_SYS_PTRACE のある方式を使う。
**Q3**: attach はできたが、プロセスが無関係な待ちに止まっている(accept/read でブロック)?
**A3**: 正常。それは入力を待っている。まずブレークポイントを張ってから `continue` し、その後外部から仕事を発火する(リクエスト/入力を与える)ことで、自分のブレークポイントまで走らせる。attach 後のブロック点でやたらとシングルステップしない。
**Q4**: attach は対象に検知されるか?
**A4**: 検知される。attach も ptrace で、プログラムが tracer を検知すれば(/proc/self/status の TracerPid を読む、または既に TRACEME で占有)見つかる。隠密にするならアンチアンチデバッグで TracerPid を隠すか、ptrace 非ベースの観測(eBPF/uprobe)に替える。
**Q5**: 対象が短命プロセス(fork-exec で一瞬で消える)で、attach が間に合わない?
**A5**: 直交する方向転換。attach せず、「起動即一時停止」か外部記録に変える。`LD_PRELOAD` で注入し main 前に `raise(SIGSTOP)` して attach を待つか、gdbserver で最初から引き継ぐ。短命プロセスの一括解析なら strace -f/eBPF で全行程記録し、リアルタイム attach でなく事後解析する。

### メモリ検索:値は分かるがアドレスが分からない
**Q1**: ある値(パスワード平文、HP、あるフラグ)がメモリにあるがアドレスが分からない。どう特定する?
**A1**: メモリ検索する。gdb pwndbg の `search 値`(文字列/バイト/dword 対応)、または `find` コマンドで全メモリを走査する。ゲーム改造ツールの発想(Cheat Engine)で未知初期値には「変化/不変化」の漸進検索をする。アドレスを特定したら watch を張って誰が読み書きするかを見る。
**Q2**: 検索すると大量のマッチアドレスが出る?
**A2**: 絞る。プログラム状態を変えてその値を変化させ、新しい値で再検索して交差を取る(漸進フィルタ)。またはメモリ領域で篩う(`vmmap` 後、heap/bss/stack 内のマッチだけを検索し、無関係なマッピングを除外)。複数回フィルタして一意にする。
**Q3**: 値がエンコード/暗号化されて保存され、平文では検索できない?
**A3**: 平文で検索できない = 保存されているのは変換後形式である。逆に、その値を処理する関数でブレークし、ロード/デコードの瞬間のメモリ内原始形式を見て、その保存フォーマットを書き留めてから再検索する。またはデコード後のきれいなコピーで直接特定する。
**Q4**: スカラー値でなくポインタ/構造体を特定したい?
**A4**: 既知アドレスを指すポインタを検索する(誰が対象を参照するかを探す)。`search -p 既知アドレス` でスタック/ヒープ内のそれを指すポインタを探し、層ごとに上ってルートオブジェクトまでたどる。これはオブジェクト関係図を再構築し、構造体ベースアドレスを特定する常用手法である。
**Q5**: メモリ検索が完全に不発(値が動的計算でメモリに落ちない、またはレジスタ/暗号化ヒープ内)?
**A5**: 直交する方向転換。「データを検索」から「コードを追う」へ。値がメモリに安定して落ちないとき、それを使う演算点(比較/表示/ネットワーク送信)でブレークし、使用現場のレジスタから直接掴む。静的なメモリを大海で検索しない。それを使う者に沿って進む。

### 条件ブレークポイント式:複雑なヒット条件の書き方
**Q1**: 「特定のオブジェクト/特定のリクエスト」で関数に入るときだけ止めたい。条件ブレークポイント式をどう設計する?
**A1**: パラメータ内容を条件にする。`b handler if $rdi->id == N`(構造体フィールド)、`if strcmp((char*)$rdi, "target")==0`(文字列、gdb は strcmp を呼べる)、`if $rsi==特定fd`。条件を、自分が関心を持つその 1 回の呼び出しに精確にマッチさせ、何百何千回もの無関係ヒットをスキップする。
**Q2**: 条件内で多段ポインタ参照/構造体フィールド読み取りが必要?
**A2**: シンボルがあれば直接 `p->field->sub`。strip ならオフセットで `*(long*)($rdi+0x18)==value`。まず 1 回のヒット内で手動 `x` で構造レイアウトを確認してオフセットを確定し、そのオフセットを条件に書く。条件ブレークが遅い = 式が重すぎるので、簡約する。
**Q3**: 条件ブレークでプログラムが使えないほど遅くなった(毎ヒット評価される)?
**A3**: ソフトウェア条件ブレークは毎ヒット gdb に戻って評価し、高頻度点では遅くなる。改法:ハードウェアブレーク+条件、条件を下げる(よりヒットの少ない上層関数に条件を付ける)、dprintf で記録だけして止まらない+事後 grep。高頻度経路では重い条件を慎む。
**Q4**: 「最初の条件成立後に一連の動作を自動で行いたい」?
**A4**: `commands` でブレークポイントにコマンドリストを付ける(ヒット時にレジスタ/メモリを dump、値を変え、そして continue)。対話デバッグを自動化する。gdb スクリプトと組み合わせて「N 回ヒットして初めて本当に止まる」などの複雑ロジックを実現できる。
**Q5**: 条件ロジックが複雑すぎて gdb 式で書けない?
**A5**: 直交する方向転換。スクリプト化 DBI で式を代替する。Frida/gdb-python で完全なプログラミング言語でヒット判定を書く(任意の複雑ロジック、呼び出し間状態、正規表現マッチ)。gdb の単行条件式よりはるかに強力である。条件が複雑ならプログラマブル hook へ昇格する。

### exploit 原語の検証:書けたか、読めたか
**Q1**: 任意書き込み原語があると思う。デバッガで本当に対象アドレスに書けるか確認したい。どう検証する?
**A1**: 書き込み発火の前でブレークし、実際のストア命令(mov [dst], val)までシングルステップし、`p $dstアドレス` が対象と等しく、`p 値` が期待と等しいことを確認し、実行後に `x` で対象アドレスを照合して書き込み成功を確認する。「論理的に書ける」が本当に書けると仮定しない。アラインメント、範囲外検査、型切り詰めで書けない/書き間違えることがある。
**Q2**: 原語が「任意読み取り」で、読み取り範囲と内容を確認したい?
**A2**: 読み取り点でブレークし、読み取り元アドレスと長さが本当に自分が制御できるか、clamp されたか(長さ検査は切り詰める)を調べる。読み出した内容が自分のリーク対象(canary/ポインタ)を含むか。多くの「任意読み取り」は実際には隠れ境界があり、動的検証で一発で分かる。
**Q3**: 書き込み原語が制限値しか書けない(0 を書けない、小数しか書けない、バイトアラインメント制限)?
**A3**: 制限を把握してから利用を計画する。動的試行で、どの値を、何バイト、どのアドレス粒度で書けるかを調べる。00 切り詰めならバイト単位/部分上書き、加算しかできないなら相対変更。原語の「能力境界」を精確に測り、利用案はこの境界に沿って設計する。
**Q4**: 原語が 1 回しか使えない(発火後プロセス状態が破壊される)?
**A4**: 単回原語は一撃致命に使う。優先して「より強い能力に連鎖できる」対象(長さフィールドを 1 つ変えて範囲外を得る、ポインタを 1 つ変えて任意読み書きを得る)に書く。デバッグでこの 1 回の書き込みが次のステップへ接続できるか確認し、書き込み対象の優先度を計画する。
**Q5**: 繰り返し検証してこの原語が弱すぎる(制限が多すぎ、制御不能)と分かった?
**A5**: 直交する方向転換。より強い原語を探すか原語を組み合わせる。1 つの弱書き込み+1 つの弱読み取りはよく任意読み書きに組み合わせられる(読み取りでアドレスをリーク→書き込みでポインタを変える→再び読み書き)。または脆弱性点を変えて再探索:他の入力面を監査してもっときれいな範囲外/UAF がないかを見る。残虐な原語の上に完全な利用チェーンを無理に組み上げない。

### インライン/最適化:ソース行ブレークポイントのずれ
**Q1**: ソースにデバッグ情報があるが、ある行でブレークすると別の場所に止まるか全く止まらない。なぜ?
**A1**: コンパイラ最適化(-O2)はインライン化、並べ替え、コード削除を行い、ソース行と機械命令が一対一対応しなくなる。`disassemble /s` でソース行に対応する実命令を見て、ソース行でなく命令アドレスでブレークする。または未最適化(-O0)再コンパイル版でロジックをデバッグし、結論を持って最適化版に戻って検証する。
**Q2**: 最適化後、変数が `p var` で "optimized out" と表示される?
**A2**: 変数がレジスタに置かれたか削除された。現在どのレジスタにあるかを調べ(`info scope`/逆アセンブルでどのレジスタが担うかを見る)、レジスタ値を直接見る。または変数が必ずメモリに居座る点(アドレスを取られる、関数を跨いで渡される)で観察する。"optimized out" を見て取得できないと信じない。
**Q3**: インライン化された関数の入口でブレークしたいが、独立アドレスがない?
**A3**: インライン後、その「関数」は呼び出し元の体内に散在する。呼び出し元内でインライン展開されたその命令セクションを(ソース行か特徴で識別して)探してブレークする。複数箇所インラインなら、各呼び出し点に 1 コピーずつあるので、全部ブレークするか自分が関心を持つその呼び出し点を選ぶ。
**Q4**: 最適化が自分のブレーク位置と隣接コードを合併し、シングルステップが行ったり来たり乱れる?
**A4**: 命令並べ替え/ソフトウェアパイプラインはシングルステップのソース行を行き来させ、これは正常な最適化産物である。行番号に惑わされず、逆アセンブル級のデータフロー(どのレジスタが何を持つか)を追って実行を理解する。ソース行順ではない。
**Q5**: 最適化+LTO で関数構造が完全に変わり、ソース級デバッグが完全に無効?
**A5**: 直交する方向転換。ソース級を捨て、純粋なアセンブリ級動的解析に戻る。ソースなしバイナリとして扱う:データ境界(入力/出力/syscall)でブレークし、レジスタとメモリの実値を見て、ソース駆動でなく挙動駆動で進める。重度最適化下のソースは参考にすぎず、実行時真実を基準とする。

### hook 点を掴む:どの関数ポインタを変えるのが最も得か
**Q1**: 任意書き込みがある。「プログラムが必ず呼ぶ」関数ポインタを乗っ取って制御フローを取りたい。どれを選ぶ?
**A1**: 判定基準は「書き込み可 + 必ず呼ばれる + 呼び出しタイミングが制御可能」。古典候補:GOT 項目(RELRO 未開なら書き込み可、変えると次回そのライブラリ関数呼び出しで乗っ取り)、__free_hook/__malloc_hook(旧 glibc)、exit handler、_IO_FILE vtable、C++ vtable。デバッガで対象ポインタが書き込み可(vmmap で権限を見る)かつ自分がその呼び出しを発火できることを確認する。
**Q2**: Full RELRO が有効で、GOT が読み取り専用で変えられない?
**A2**: GOT が書き込み不可なら対象を変える。ヒープ上の関数ポインタ(vtable、コールバック構造)、書き込み可データセクションの関数ポインタ、または GOT を通らない間接呼び出し点。Full RELRO は GOT だけをロックし、プログラム自身の書き込み可関数ポインタはそのまま変えられる。
**Q3**: 高バージョン glibc が malloc/free hook を削除した?
**A3**: 2.34+ はこれらの hook がないので、FSOP(偽造 _IO_FILE チェーン、vtable を乗っ取り、プログラムの exit/fflush で発火)、__exit_funcs(pointer guard 暗号化の処理が要る、先に fs:0x30 の guard をリークするか暗号化を経ない経路を使う)、またはプログラム自身のコールバック機構へ転換する。
**Q4**: ポインタを変えたが呼び出し時にクラッシュ(パラメータが合わない/コンテキストが満たさない)?
**A4**: 乗っ取り点が呼び出し時のレジスタコンテキストを決める。直接 system へ跳ぶには rdi が "/bin/sh" を指す必要がある。コンテキストの rdi が欲しいものでないなら、コンテキストにマッチする one_gadget へ跳ぶか、先に gadget でレジスタを調整してから目標へ進む。デバッグで乗っ取り瞬間のレジスタを照合する。
**Q5**: すべての常規 hook 点が書き込み不可/到達不可?
**A5**: 直交する方向転換。ポインタを乗っ取らず、「データ意思決定」を乗っ取る。長さ/サイズ/インデックスフィールドを 1 つ変えてより強い範囲外能力を得るか、データを指すポインタを 1 つ変えて任意読み書きを実現する(直接制御フローでなく)。データ面の能力で迂回して制御フロー乗っ取りを構成し、ある関数ポインタに固執しない。

### TLS/早期アンチデバッグ:main の前で問題が出る
**Q1**: プログラムが main の前(初期化段階)でデバッガ検知/復号する。main でブレークするのはもう遅すぎる。どうする?
**A1**: もっと早くブレークする。TLS callback(Windows、PE の TLS ディレクトリ内のコールバックは入口前に実行)、.init_array/constructor(Linux、main 前のコンストラクタ)はよくある早期検知/復号点。x64dbg は「TLS callback」ブレークポイントを設定、gdb は `starti` で最初の命令から始める。デフォルトで main に止めない。
**Q2**: .init_array にアンチデバッグがあると疑う?
**A2**: `info functions`/.init_array セクション内の関数ポインタを見て、逐個その入口でブレークする。これらは main 前に走り、アンチデバッグ/自己復号がここに隠れがちである。`starti` 後に `b *(init_array項)` で逐個通す。
**Q3**: Windows の TLS callback 内で PEB.BeingDebugged を検知する?
**A3**: TLS callback はプロセス主スレッド入口前、さらには自分の attach 完了前に走る。「起動即一時停止」デバッグ(x64dbg が直接プロセスを起動するとシステムブレークポイントで止まり、TLS より早い)+ ScyllaHide で PEB を事前に隠す。または TLS コールバックアドレスにブレークしてその実行前に確実に止める。
**Q4**: 早期検知がある方式で後続の復号鍵を変えた(デバッグ検知すると誤って解く)?
**A4**: これは「アンチデバッグと復号の結合」で、検知後もプログラムはクラッシュせず、誤ったコードを解いて走り続ける。非常に隠蔽されている。早期検知点で必ず迂回し(デバッグされていないと思わせる)、クラッシュしてから反応しては遅い。検知分岐でブレークし、「未デバッグ」経路を強制する。
**Q5**: 早期アンチデバッグが頑固すぎ、プロセスが起動すると即座に汚染される?
**A5**: 直交する方向転換。早期コードを静的に除去するかエミュレーション実行する。静的 patch で TLS callback/init 内の検知を除去(直接 return に変える)するか、Qiling/Unicorn で init 段階をエミュレーション実行する(エミュレータ内では PEB/ptrace 検知が自然に無効)。復号後の状態を得てから実機デバッグの後続に切り替える。

### GOT/PLT 観察:遅延バインディングと乗っ取り検証
**Q1**: あるライブラリ関数の呼び出しが PLT/GOT をどう経るか、そして乗っ取れるかを理解したい。どう動的に見る?
**A1**: その関数の初回呼び出しでブレークし、PLT stub にシングルステップで入り、GOT へのジャンプを観察する。初回呼び出しの GOT は PLT+6(解決へ戻る)を指し、_dl_runtime_resolve が解決した後 GOT が本物の libc アドレスで満たされ、以後は直接ジャンプする。この遅延バインディング過程を見て初めて GOT を変えるタイミングと効果が分かる。
**Q2**: ある GOT 項目が自分の書き込み原語で乗っ取れるか確認したい?
**A2**: `vmmap` で GOT セクションの権限を見る(Partial RELRO では .got.plt 書き込み可、Full RELRO では読み取り専用)。書き込み可なら書き込み原語でその項目を対象アドレスに変え、次回プログラムが対応関数を呼ぶと自分の対象を実行する。変える前に `x` で元値を記録し、変えた後照合する。
**Q3**: _dl_runtime_resolve を利用して ret2dlresolve をやりたい?
**A3**: この手は libc のリーク不要で、Elf_Sym/Elf_Rel 構造を偽造してリゾルバに system を解決させる。動的検証:PLT[0] が _dl_runtime_resolve を呼ぶところでブレークし、自分が構成した reloc offset と偽造構造が正しく読み取られるか検査する。構造レイアウトは間違えやすく、動的にフィールド単位で照合する必要がある。
**Q4**: Full RELRO が ret2dlresolve/GOT 書き換えをすべて無効にした?
**A4**: Full RELRO では GOT が読み取り専用かつ起動時に全部解決済みで、この 2 手はほぼ無駄。GOT 非依存の経路へ方向転換する:直接 ret2libc(leak 要)、スタック上 ROP、またはプログラム自身の関数ポインタ/vtable。RELRO は GOT だけを守り、他は守らない。
**Q5**: PLT/GOT の利用次元がすべて緩和に封じられた?
**A5**: 直交する方向転換。「リンカ機構」の次元を離れる。データ構造乗っ取り(_IO_FILE/FSOP、ヒープ内の関数ポインタ)、純スタック ROP/SROP へ移る。GOT/PLT は制御フロー乗っ取りの 1 つの担体にすぎず、緩和がそれを封じたら別の担体に替える。利用目標(制御フロー取得/flag 読み取り)は不変である。
