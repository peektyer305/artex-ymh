# リバースエンジニアリング PWN · リバースエンジニアリングの静的切り口と対象関数の位置特定

### 未知のバイナリを手にした最初の 1 分間の進め方
**Q1**: 見覚えのない ELF/PE を手に、まだ逆アセンブラを開いていない。第一歩として何を意思決定する?
**A1**: まず「コストゼロの情報収集」をしてからリバースエンジニアリングを論じる。順序:`file`(アーキテクチャ/ビット数/stripped か/静的リンクか動的リンクか)→ `checksec`(RELRO/Canary/NX/PIE)→ `strings -a` で粗く走査(URL、パス、フォーマット文字列、エラー情報、コンパイラ banner)→ `nm`/`readelf -s` でシンボルが残っているかを見る。判定基準:これら数コマンドが 30 秒で後続の姿勢を決める。動的リンク+シンボルあり = 直接 main へ突撃。静的+stripped = まずシンボル復元が必要。
**Q2**: `file` が statically linked, stripped と示し、シンボルが一気に消えた。慌てる?
**A2**: 慌てない。これは異常ではなく常態。静的+stripped は libc もコンパイルされているので、後で gadget を探す際は逆に資源が潤沢。stripped は関数名がないだけで、関数がないわけではない。「入口と定数から逆算する」へ方向転換し、「名前で探す」をやめる。
**Q3**: strings の出力が山ほどある。その中から価値ある手がかりをどう抽出する?
**A3**: 優先度で並べる:`/bin/sh`、`system`、`flag`、`%s/%d/%n` のようなフォーマット文字列、`Segmentation fault`、メニューテキスト("1. Add / 2. Delete")、GCC/Clang バージョン文字列、libc パス。メニューテキストは特に貴重で、直接コマンドディスパッチ関数に対応する。相互参照 1 回でコアロジックに落ちる。
**Q4**: このステップで役立つ文字列が 1 つもない(暗号化/パッカー)場合はどうする?
**A4**: この「静的文字列走査」の道が塞がれたので、直交する次元へ方向転換する。**エントロピー検知とパッカー識別**。`detect-it-easy`/`entropy` でセクションのエントロピー値を見る。高エントロピー(>7.5)+ 怪しいセクション名(UPX0/UPX1)= パッカーなので、まずアンパックしてからこのフローへ戻る。エントロピーが正常なのに文字列がないなら、実行時復号の可能性が高く、動的に復号後にメモリを dump する。
**Q5**: 「純粋な静的読解」か「静的位置特定+動的検証」か、どちらを進むかどう判断する?
**A5**: 判定基準はロジックの複雑さとデバッグ可能性。バイナリがローカルで走る(対話メニューがある)なら → 静的は位置特定だけにして、時間を動的デバッグの実証に費やす。純アルゴリズム検証/出力のない crackme なら → 静的で力ずくに読む方が費用対効果が高い。最初からデコンパイル擬似コードに固執しない。
**Q6**: 情報収集を終えた。主攻方向を一言でどう定める?
**A6**: 組み合わせ判定基準:NX 有効 + system/backdoor あり → ret2text/ret2libc。NX 有効 + 既存 gadget 源なし → 制御可能ポインタでフローを変えるか ROP。Canary 有効 → まず canary をリークする原語を探す。PIE 有効 → まずアドレスリークを探す。「防御マトリクス」を「どの原語が欠けているか」に翻訳し、その欠けを持って関数を位置特定する。

### シンボル除去(stripped)バイナリで本当の main を特定する
**Q1**: 逆アセンブラが `_start` に落ち、ライブラリ初期化コードばかり。main はどこ?
**A1**: 標準 libc 起動チェーンを進む。`_start` は main のアドレスをパラメータとして `__libc_start_main` に渡す(x86-64 では通常 `mov rdi, offset main` の直後に `call __libc_start_main`)。`__libc_start_main` の呼び出し点を特定し、その第一パラメータ(rdi)が main である。これが stripped で main を探す第一鉄則である。
**Q2**: 静的リンクが `__libc_start_main` も strip し、認識できない。どうする?
**A2**: 「構造パターンマッチ」へ方向転換する。`_start` の構造は同一コンパイラ下で高度に固定される:rbp をクリア、argc/argv を取得、3 つの関数ポインタ(main/init/fini)を渡す。シンボルがなくても、`_start` 内で最初にパラメータとして渡されるコードセクションアドレスが main である。そのアドレスへ跳べばよい。
**Q3**: 跳んでみると巨大な関数で、main かどうか不確定。どうする?
**A3**: 挙動特徴で確認する。main は通常、直後に setvbuf/alarm/初期化を呼び、その後 while(1) メニューループか一回きりのロジックに入る。stdin/stdout への setbuf、scanf/read への呼び出し、分岐の多い switch が見えれば、ほぼ確定である。
**Q4**: この libc 起動規約が無効(独自 runtime / libc なし)の場合はどうする?
**A4**: 直交する次元へ換える。**「ユーザー入力関数」から逆算する**。プログラムは必ず入力を読むので、read/recv/scanf/fgets を相互参照し、誰がそれらを呼ぶか、それらに最も近い大関数が業務核心である。main 探しを迂回して直接「処理ロジック」を探す。
**Q5**: Go/Rust のような非標準入口の場合、業務をどう特定する?
**A5**: runtime を識別して言語特性に沿って進む。Go:`main.main` を探す(stripped でも pclntab が関数名を復元できることが多く、`go_parser`/Ghidra スクリプトを使う)。Rust:シンボルに mangled な `crate::module::func` があり、demangle して業務モジュール名を見る。runtime スケジューラで時間を浪費しない。
**Q6**: どれも特定できず、時間が流れている。どう受ける?
**A6**: 受けの戦略。**入口エントロピー最高/xref 最密の関数が被疑核心**。逆アセンブラの関数リストを参照数、サイズで並べ、人は往々にして一目で 2-3 個の候補を特定できる。逐個 5 分速読で排除する。「精確に main を探す」ことを追求せず、「脆弱性のある関数を探す」ことを追求する。

### 文字列/定数から相互参照で重要ロジックを特定する
**Q1**: 怪しい文字列(エラーテキストや flag パスなど)を見つけた。それでコードをどう特定する?
**A1**: 核心手法は xref(相互参照)。逆アセンブラでその文字列を選び、「誰が私を参照しているか」を調べる(IDA の x / Ghidra の References)。それを参照する関数が往々にして関連業務ロジックである。文字列は stripped バイナリで最も信頼できる「命名アンカーポイント」である。
**Q2**: 1 つの文字列が複数箇所から参照される。どう篩う?
**A2**: 意味論で対にする。"Wrong password" 系文字列は、どの分岐の else で出力されるかを見る。その分岐の if 条件が検証ロジックである。"Correct/Success" の出現箇所は成功経路に対応する。成功/失敗分岐に沿って判定式を逆算するほうが、関数全体を通読するよりはるかに速い。
**Q3**: 重要定数が文字列でなくマジックナンバー(magic number)の場合はどうする?
**A3**: 同様に即値を検索する。怪しい十六進マジックナンバー(0xdeadbeef、チェックサム初期値、鍵定数)を逆アセンブラで即値参照を全域検索する。特に暗号アルゴリズム定数(AES S-box、SHA 初期値、CRC 多項式)は検索一発でアルゴリズム種別を標示できる。
**Q4**: 文字列がデータセクションで連結/動的構成され、静的には完全な文字列を検索できない。どうする?
**A4**: この道が塞がれたので、**動的文字列ブレークポイント**へ方向転換する。strcpy/sprintf/memcpy または文字列比較関数(strcmp/strncmp)でブレークし、1 回走らせて、構成された文字列がレジスタ/スタック内に現れるので、その後静的に注釈を付ける。
**Q5**: バイナリが重要文字列を意図的に XOR/エンコードしており、xref のアンカーポイントがない。どうする?
**A5**: 次元を変えて「デコード関数」を探す。.data/.rodata 内の高エントロピーバイトブロックを観察し、それを参照しループ+XOR/加算を持つ小関数を探す。それが実行時デコーダである。デコードロジックをスクリプト(idapython/Ghidra script)でオフラインに走らせて平文を復元すれば、アンカーポイントが戻る。
**Q6**: 使える文字列アンカーポイントが完全にない(純計算問題)場合の受けは?
**A6**: 制御フロー形状の特定へ方向転換する。「分岐が最も深く、ループが最も緊密で、大量のビット演算がある」関数を探す。それが通常は検証/暗号化の核心である。関数複雑度(cyclomatic complexity)で並べ、最も複雑なものへ直接突撃する。

### インポートテーブル/PLT から危険関数の呼び出し点を特定する
**Q1**: 動的リンクの問題で、すべての危険操作を素早く探したい。どこから切り込む?
**A1**: PLT/インポートテーブルから切り込む。プログラムがどの libc 関数を呼ぶか列挙し、危険なもののリストを作る:gets/strcpy/strcat/sprintf(オーバーフロー)、scanf("%s")、read(長さパラメータを見る)、system/execve(コマンド実行)、printf 系(フォーマット文字列)、malloc/free/realloc(ヒープ)。各々に xref を張り、つるをたどって呼び出し点へ。
**Q2**: 危険関数の呼び出し点が複数ある。どう「脆弱性のあるその 1 つ」を特定する?
**A2**: パラメータの制御可能性と境界を見る。read(fd, buf, n) の n が buf 実サイズより大きいか。strcpy のソースがユーザー入力か。printf の第一パラメータが直接ユーザー文字列か(フォーマット文字列脆弱性)。静的には「バッファサイズ vs コピー長」の差を監視し、差 > 0 かつ制御可能なら入口である。
**Q3**: プログラムが system を直接呼ばないが、コマンド実行を疑う。どう探す?
**A3**: 間接原語を探す。execve/execl/popen/`__libc_system` を検索するか、"/bin/sh"、"sh"、"/bin/cat" 定数を検索する。静的リンク問題では system がインライン化/改名されることがあるので、内部で使う `do_system` 特徴を検索するか、"/bin/sh" バイト列の libc セクション内位置を直接検索する(ret2libc 用に残す)。
**Q4**: インポートテーブルが難読化(dlsym/GOT 手動充填で動的解決)され、呼び出し点を見つけられない。どうする?
**A4**: この静的道が塞がれたので、**動的 GOT/PLT 観測**へ方向転換する。dlopen/dlsym でブレークするか、実行後に GOT テーブルを dump して実際にどの関数へ解決されたかを見る。ltrace で実行時にどのライブラリ関数が呼ばれたかを直接見て、逆に確認する。
**Q5**: 対象が自前プロトコル/標準危険関数なし。どうする?
**A5**: 視点を変えて「自前の危険ラッパー」を探す。多くのプログラムは read+parse を 1 つの関数に包み、危険はその中に隠れる。大量に呼ばれる中小関数を探し、内部にスタックバッファ+ループ書き込みがあるかを見る。自前 memcpy こそが真犯人である。
**Q6**: 複数の候補で優先度をどう付けて時間を無駄にしない?
**A6**: 判定基準:制御可能長のスタック書き込み > フォーマット文字列 > ヒープ操作 > 論理脆弱性。スタックオーバーフローは特定が速く、利用が安定するので優先検証。スタックの道がすべて塞がれたらヒープと論理へ転じる。

### checksec 結果が重点特定を逆に導く
**Q1**: checksec が出た。この防御フラグで直接「何の関数を探すか」を教えてもらうには?
**A1**: 防御を「必要な原語」に翻訳し、それから指向的に探す。No Canary + NX + No PIE = スタックオーバーフロー点を探して直接 ret2text/ROP(特定重点:スタックバッファ書き込み)。Canary on = まず情報リークが必要(特定重点:スタック内容を出力できる/範囲外読み取りの関数)。防御が「どの鍵が欠けているか」を決めるので、その鍵を作る関数を探しに行く。
**Q2**: PIE が有効で、アドレスをリークする必要があると分かったが、どの種の関数を探す?
**A2**: 「未初期化/範囲外メモリを出力する」点を探す:printf %s でスタック残留を出力、read 後にクリアせず puts、配列範囲外読み取り。.text/libc ポインタを回帰できるあらゆる場所が候補である。特定戦略は「出力関数(puts/write/printf)+そのパラメータ出所」を中心に xref する。
**Q3**: Full RELRO で GOT を変えられない。特定の発想をどう調整する?
**A3**: GOT overwrite を捨て、別の書き込み可制御点へ方向転換する:スタック上の戻りアドレス(ROP)、関数ポインタ/仮想テーブル、`__malloc_hook`(旧 libc)、`exit` 関連構造、`_IO_FILE` 構造(FSOP)。特定重点を「GOT」から「プログラム自身の関数ポインタと FILE 構造」へ移す。
**Q4**: 全防御が引き上げ(Canary+PIE+Full RELRO+NX)で、手が出ないように見える。どうする?
**A4**: これは「防御の壁」であり、解がないわけではない。**論理と原語チェーンの次元**へ方向転換する:まず任意読み取り(すべてをリーク)+任意書き込み(すべてを変える)を 1 つずつ探し、利用を「2 つの原語」に分解して各々特定する。万能オーバーフローを 1 つ探さない。全防御問題はほぼすべて UAF/OOB の組み合わせ原語に頼るので、静的特定の重点を「オーバーフロー点」から「ライフサイクル誤り(free 後も使う)」へ転じる。
**Q5**: seccomp サンドボックスの有無を静的にどう判断し、何を探すかがどう変わる?
**A5**: prctl/seccomp/`__NR_` 関連呼び出しと BPF フィルタ構造を検索する。サンドボックスがあれば、`system`/`execve` が禁止される可能性があり、特定目標を「getshell 関数」から「orw(open/read/write)チェーン」に必要な gadget とファイル読み取りロジックへ変える。先にサンドボックスを確認してから利用形態を定め、無駄な労力を避ける。
**Q6**: checksec が静的リンク問題で正確かどうか分からない。どうする?
**A6**: 静的リンクでは checksec の「libc gadget の有無」判断は適用外なので、自ら評価する:`ROPgadget --binary` で直接 gadget 数を数える。静的問題は gadget が極めて潤沢なので、特定重点は「制御可能なオーバーフロー点」の 1 変数に戻る。gadget は欠けない。

### デコンパイル擬似コードが乱れる/読めないときの推進判断
**Q1**: Ghidra/IDA のデコンパイル擬似コードがぐちゃぐちゃ(型ミス、変数だらけ)。読み続けるか手を変えるか?
**A1**: まず乱文を無理に読まず、「2 分修型」をしてから判断する:関数署名を修復、重要変数に種別を付ける(undefined を int/char[] に)、既知変数をリネーム。多くの「乱れ」は型推論の失敗で、型を直せば擬似コードが大きく明瞭になる。直しても乱れるなら、ツールの変更を考える。
**Q2**: デコンパイラがスタック構造を誤認識(バッファサイズが違う)し、オーバーフロー判断に影響する。どうする?
**A2**: 擬似コードのスタックレイアウトを信じず、アセンブリに戻って実 offset を見る。`sub rsp, N` でスタックフレームサイズを確定し、read/gets の書き込み対象 [rbp-X] を見て、N-X で実オーバーフロー距離を計算する。擬似コードの local_XX 命名は信頼できず、アセンブリの offset が ground truth である。
**Q3**: 1 つの関数が数千行にデコンパイルされ、とても読み切れない。どうする?
**A3**: 通読せず、「目標誘導読解」をする。特定原語だけを関心があるので、そのデータフローだけを追う:ユーザー入力変数から出発し、どの関数に使われるかを順に追い(テイント追跡の発想)、無関係な分岐は直接畳んでスキップする。デコンパイラの「変数の全使用点ハイライト」機能でデータフローを特定する。
**Q4**: IDA と Ghidra の両デコンパイラを替えても結果が読めない。どうする?
**A4**: 静的読解の道が塞がれたので、**動的実証**へ方向転換する。ロジックを推測せず、直接走らせる:gdb で関数入口にブレークし、既知の入力を与え、シングルステップでそれが入力に何をするか、スタックがどう変わるかを見る。動的 1 回の実行は静的 30 分の読解に勝る。これが静的で行き詰まったときの最重要の直交する方向転換である。
**Q5**: 擬似コードに SIMD/コンパイラ最適化由来の怪しい命令が大量にあり読めない?
**A5**: それは多分ベクトル化されたループ(memcpy/チェックサム/暗号化)。逐命令で読まず、その「全体意味」を識別する:何を入力し、何を出力し、長さはいくつか、をブラックボックスとして扱う。または最適化視点を下げる。動的入出力ペアでその機能をフィットさせ、各 pxor を理解しなくてよい。
**Q6**: デコンパイラ自体が関数を解析漏れ(関数として認識していない)している疑いがある。どうする?
**A6**: 関数境界を手動で補正する。逆アセンブラでそのバイトを "Create Function"(IDA:P キー / Ghidra:F)。間接ジャンプ、ジャンクコードによる認識中断でよくある。修復してから再デコンパイルする。ジャンクコードで継続的に失敗するなら、「反逆アセンブル」処理フローへ転じる。

### パッカー/難読化:識別とアンパックの意思決定
**Q1**: バイナリのセクションエントロピーが高く、関数が数個しかなく、文字列が全くない。パッカーを疑う。どう確認し処理する?
**A1**: まずパッカー種別を確認する:`detect-it-easy`/PEiD/セクション名特徴(UPX0/UPX1、.vmp、.themida)。既知パッカー(UPX)は公式 `upx -d` でワンクリックアンパックを優先。アンパックできないか未知パッカーなら、「動的アンパック」へ:元の入口点(OEP)が復号実行される瞬間にメモリを dump する。
**Q2**: UPX がマジックナンバーを変えられ、`upx -d` がエラーになる。どうする?
**A2**: マジックナンバーを手動修復するか汎用アンパックへ進む。UPX 構造は固定なので、改ざんされた "UPX!" マーカーを戻せば救えることが多い。駄目なら ESP 定律で動的アンパック:パッカーは解凍完了時に OEP へ向かう大ジャンプがあり、スタック均衡点でブレークし、OEP 到達後に Scylla/dump ツールでダンプ+インポートテーブル再構築する。
**Q3**: VMP/Themida のような仮想化パッカーに出会い、アンパックできない。どうする?
**A3**: 力ずくでアンパックせず、戦略を転換する。**アンパックせず、重要点だけをインスツルメントする**。仮想化パッカーが守るのは特定の関数で、プログラムの大部分のロジックはまだネイティブ実行される。自分が関心を持つ入出力境界(照合関数、IO)を特定し、そこでブレークして動的観測し、VM handler のリバースエンジニアリングを迂回する。
**Q4**: 実行時自己復号(標準パッカーではない)の場合、実コードをどう特定する?
**A4**: 復号ループ(XOR/ビット演算 + コードセクションへの書き戻し)を探し、その後でブレークする。またはページ保護追跡:コードセクションを実行不可にし、初回実行で発火したら、その瞬間のメモリを dump する。動的への方向転換がここでの必然の選択である。
**Q5**: ジャンクコード(junk/opaque predicate)で逆アセンブルがずれる。どうする?
**A5**: ジャンクコードパターン(`jz+jnz` が同一アドレスへ、`call $+5;add [esp]` がごみバイトを飛ばすなど)を識別し、スクリプトで nop に patch するかジャンプを修正してから再解析する。IDA は idapython で一括 patch できる。処理後に制御フローが正常に戻ってから特定を続ける。
**Q6**: ジャンクコードが多すぎて手動 patch が現実的でない。どうする?
**A6**: 自動化難読化解除の次元へ方向転換する:D810/Ghidra の難読化解除プラグイン、またはシンボリック実行/テイント解析ツール(angr/Triton)で平坦化解除(control flow flattening)を行う。駄目なら静的を捨て、動的 trace(Pin/DynamoRIO)で実実行経路を記録し、通った命令だけを解析する。

### スタックオーバーフロー候補関数の識別と静的監査
**Q1**: スタックオーバーフローを探したい。静的でどう素早く候補関数を囲い込む?
**A1**: 「固定サイズスタックバッファ + 非制御書き込み」の組み合わせを探す。信号:関数内で `char buf[N]`(アセンブリでは sub rsp を見る)に gets/scanf("%s")/strcpy/read(fd,buf,>N) が対応。重点は read の長さパラメータと buf 宣言サイズの差:read(0, buf, 0x100) なのに buf が 0x40 しかないと、オーバーフロー確定である。
**Q2**: read の長さが即値でなく変数。制御可能かどう判断する?
**A2**: その長さ変数の出所を逆に調べる。それが別のユーザー入力(先に長さを読んでからデータを読むプロトコル)由来で、上界検証がないなら、制御可能なオーバーフローである。sizeof(buf) 由来か min() でクランプされていれば安全。データフローで長さパラメータを遡るのが重要である。
**Q3**: オーバーフロー点を見つけた。戻りアドレスまで届くかをどう静的に見積もる?
**A3**: 距離を計算する:スタックフレーム `sub rsp, N`、buf は [rbp-X]、戻りアドレスは [rbp+8]。オーバーフロー量は ≥ X+8(+canary 長 8 があれば)必要。静的でまず padding 長を計算し、動的で cyclic pattern で較正する。静的は見積もり、動的は精確値を与える。
**Q4**: 明らかに大バッファだが Canary 保護があり、直接オーバーフローするとクラッシュする。どうする?
**A4**: 戻りアドレスを変えるオーバーフローが canary に壁で塞がれたので、**先に canary をリークする**次元へ方向転換する。範囲外読み取りまたは部分上書き後に出力する点(先に read してクリアせず printf、または %s で canary の後まで読む)を特定して canary 値をリークし、同じ入力に正しい canary を付けて戻りアドレスを上書きする。特定重点を「オーバーフロー点」から「リーク点+オーバーフロー点」の対へ拡張する。
**Q5**: スタックバッファ書き込みに長さ検証があり安全に見える。まだ望みはあるか?
**A5**: 境界条件を監査して off-by-one/off-by-few を探す。検証が `<=` を `<` でなく使う、ループが `i<=n`、null 終端で 1 バイト多く書く。これらは saved rbp の最下位バイト、さらには canary/戻りアドレスの下位バイトまで上書きできる。静的には比較演算子とループ境界を監視する。1 バイトも入口になり得る。
**Q6**: スタック関数がすべてきれいで、オーバーフローがない。どうする?
**A6**: スタックオーバーフローの次元が枯渇したので、直交する方向転換:フォーマット文字列(printf ユーザー制御)、ヒープ(malloc/free 使用誤り)、グローバル/BSS バッファオーバーフロー(canary 保護なし)、配列インデックス範囲外(負インデックスか超界書き込み)。スタックがきれいでも穴がないわけではない。書き込み原語の種別を変えて続ける。

### フォーマット文字列脆弱性の静的特定
**Q1**: フォーマット文字列脆弱性を疑う。静的でどう精確に特定する?
**A1**: printf/fprintf/sprintf/snprintf/syslog などに xref し、逐個「フォーマット文字列パラメータがユーザー制御か、固定フォーマットがないか」を見る。判定基準:`printf(user_buf)` であって `printf("%s", user_buf)` ではないこと。第一パラメータが直接ユーザーデータなら脆弱性である。
**Q2**: 大量の printf 呼び出しの中から安全と不安全をどう素早く区別する?
**A2**: 第一パラメータ(rdi)の出所を見る。.rodata 内の定数文字列アドレスなら = 安全。スタック上/ヒープ上のユーザーバッファなら = 危険。逆アセンブリで一目で分かる `lea rdi, [rodata_str]`(安全)vs `mov rdi, [rbp-buf]`(危険)。
**Q3**: フォーマット文字列脆弱性を特定した。静的でさらに何を確定すれば利用を加速できる?
**A3**: オフセットと能力を確定する。静的にユーザー入力文字列がスタック上で printf のパラメータ取得起点からどれだけ離れているか(第何 %p で自分の入力が回帰されるか)、そして %n 書き込みと組み合わせられるか(NX は %n に影響しない)を計算する。静的は「パラメータオフセット候補範囲」を出し、動的は `AAAA.%p.%p...` で精確に特定する。
**Q4**: フォーマット文字列が sprintf で別バッファへ、直接出力されない。それでも使えるか?
**A4**: 使えるが性質が変わる。これは「フォーマット文字列による二次オーバーフロー」(%100d で対象バッファを押し広げる)の可能性。特定重点は対象バッファサイズとフォーマット文字列展開長の関係へ転じ、スタックオーバーフローの引き金として扱う。
**Q5**: プログラムが %n をフィルタ(FORTIFY が %n を無効化)した。どうする?
**A5**: %n 書き込みの道が塞がれたので、**フォーマット文字列の読み取り専用用途**へ方向転換する:%p/%s で情報リーク(canary、libc、スタックアドレス、PIE ベースアドレス)をし、フォーマット文字列を「リーク原語」に格下げして、別の書き込み原語と組み合わせる。特定需要は「フォーマット文字列自体が書けるか」から「対にできる書き込み点がどこか」へ変わる。
**Q6**: プログラム全体にユーザー制御のフォーマット文字列が一切ない。どうする?
**A6**: フォーマット文字列の次元が存在しないので、絡まずに、オーバーフロー/ヒープ/論理の次元へ戻る。套路のために無理にフォーマット文字列を探さず、この道が通らないと認めることが時間節約の意思決定である。

### ヒープ問題:malloc/free ラッパーとライフサイクル誤りの識別
**Q1**: メニューが add/edit/delete/show のようなので、ヒープ問題と判断した。静的でまず何をする?
**A1**: まず「データ構造と管理配列」を逆に見る。グローバルのポインタ配列(chunk ポインタを格納)、size 配列、in-use 状態を記録するフラグを特定する。add(malloc+ポインタ格納)、delete(free)、edit(書き込み)、show(出力)の 4 操作の関数を各々特定し、オブジェクトのライフサイクルを描く。
**Q2**: UAF(use-after-free)をどう静的に発見する?
**A2**: free 後にポインタがクリアされるかを監視する。delete 関数を特定し、`free(ptr)` 後に `ptr=NULL` がない(グローバル配列の対応項目がクリアされない)のに、edit/show がそのインデックスにまだアクセスできるなら → UAF。判定基準は「free されたが管理配列にポインタが残り、再利用できる」ことである。
**Q3**: double free や範囲外をどう静的に発見する?
**A3**: delete に検証があるかを見る:free 前にそのインデックスが既に free されているか(フラグ)、インデックスが範囲外か(index が < 上限か、負数を許すか)。検証欠如が double free / 配列範囲外ポインタ書き込みである。同時に add の size がユーザー制御で上限なし(ヒープオーバーフロー)かも見る。
**Q4**: 静的に chunk レイアウトとヒープ挙動がはっきりせず、読み進められない。どうする?
**A4**: ヒープロジックは静的推論が難しいので、**動的ヒープ可視化**へ方向転換する。pwndbg/gef の `heap`/`bins` コマンドで、実際に add/free を数回して bin 内で chunk がどう流れ、fd/bk ポインタがどう変わるかを見る。ヒープ問題はほぼ必ず動的検証が必須で、静的は操作関数の特定とロジックの穴探しだけを担う。
**Q5**: UAF を確認したが、何を変えられるか分からない(libc バージョンが手法を決める)。どう特定する?
**A5**: まず libc バージョンを定める(動的リンクなら libc ファイルを見る、静的ならコンパイル特徴/tcache 構造を見る)。バージョンが利用を決める:tcache あり(2.26+)なら tcache poisoning で fd を変える。旧版なら fastbin dup / unsorted bin leak。特定重点は「そのバージョンでどの hook/構造が書き込み可か」(__free_hook/__malloc_hook/IO_FILE/tcache struct)へ転じる。
**Q6**: 保護が強すぎ(check が揃い、key 検証あり)で、常規ヒープ手法がすべて塞がれた。どうする?
**A6**: house-of-XXX 系高級原語か FSOP へ方向転換する。hook が削除され(高バージョン glibc)、tcache に検証があるとき、特定目標は `_IO_2_1_stdout_`/stderr の FILE 構造、`__exit_funcs`、tls-storage へ転じる。「hook を変えて getshell」の道が死んだと認め、ファイルストリーム/終了フローを攻めるのが現代ヒープ問題の主な方向転換である。

### バックドア/予約 win 関数の特定
**Q1**: 問題がバックドア関数(直接 getshell/flag を与える)を残した疑いがある。どう素早く探す?
**A1**: 3 本を並行する:"/bin/sh"、"cat flag"、"flag.txt" 文字列を検索して xref。関数を列挙して win/backdoor/getshell/system_call を含む名前がないか(stripped でも漏れることがある)。system/execve/open("flag") を呼ぶ全関数を走査。ヒットしたら候補目標である。
**Q2**: 疑わしい win 関数を 1 つ見つけた。それが目標であり、どう入るかどう確認する?
**A2**: その呼び出し状況を見る。xref が一切ない(「孤児関数」で、プログラムの正常フローが決して呼ばない)なら、それはほぼ確実に ret2 用のバックドアである。そのアドレスを書き留め、利用時に戻りアドレスを直接その入口に変える(または push rbp を飛ばす gadget でスタックを整える)。
**Q3**: win 関数が特定パラメータを要する(system が rdi=/bin/sh を要するなど)。対応物をどう特定する?
**A3**: 制御できるレジスタ手段を静的に棚卸しする:`pop rdi; ret` gadget を探す、既存の "/bin/sh" アドレスを探す、またはバックドア関数内部が既にパラメータを備えていないかを見る(一部バックドアは自前 lea rdi,'/bin/sh' を持つ)。特定需要は「関数探し」から「関数+パラメータ gadget 集め」へ拡張する。
**Q4**: バックドア関数に検証がある(あるグローバル変数がマジックナンバーに等しいと getshell)。直接跳ぶだけでは無意味。どうする?
**A4**: これは壁ではなく道標なので、**まず前置条件を満たす**方向へ転換する。そのマジックナンバー比較を特定し、別の書き込み原語(オーバーフローでグローバルを変える、フォーマット文字列で書く)でそのグローバル変数を要求値に変えてからバックドアを発火できるかを見る。「一歩 ret2win」を「条件変更 + 発火」の 2 ステップに分解する。
**Q5**: プログラム全体にバックドア関数がない。どうする?
**A5**: もう探さず、これが「自力更生」型問題と認め、標準利用チェーンへ方向転換する:ret2libc(libc をリークして system を呼ぶ)、ret2syscall(libc なしで int 0x80/syscall gadget + execve)、ROP orw。特定重点を「既存バックドア」から「リーク原語 + gadget チェーン」へ転じる。
**Q6**: 疑わしいバックドアを複数見つけ、どれを選ぶか分からない。どうする?
**A6**: 「制約が最少」で選ぶ。パラメータなしで直接実行できるもの(内部に /bin/sh を備える)、前置条件検証のないもの、スタックアラインメントの落とし穴がないものを優先。複数候補なら利用ステップが最少のものを選び、デバッグ変数を減らす。

### 非 x86 アーキテクチャ(ARM/MIPS)の静的特定調整
**Q1**: `file` が ARM/MIPS/aarch64 と示す。x86 のリバースエンジニアリングとどの特定差に注意すべき?
**A1**: 呼び出し規約と gadget の形が変わる。ARM:パラメータは r0-r3 を通り、戻りアドレスは lr にある(スタック上ではない、プッシュされない限り)。MIPS:パラメータは a0-a3、分岐遅延スロット(delay slot)がある。ジャンプ後も次の 1 命令が実行される。オーバーフロー点を特定する際、「戻りアドレスがいつスタックに落ちるか」を理解する必要がある。通常は関数が lr をプッシュする prologue の後である。
**Q2**: ARM でオーバーフローして戻りアドレスを変えても、スタックを変えても無意味なことがある。なぜ?
**A2**: リーフ関数(leaf function)は lr をプッシュせず、戻りは直接 lr レジスタを使うから。特定時に対象関数がリーフかどうかを判断する:非リーフだけが `push {..., lr}` して、スタック上に上書き可能な戻りアドレスがある。lr をプッシュする関数をオーバーフロー対象に選ぶ。
**Q3**: MIPS の遅延スロットで gadget/フロー計算が狂う。どうする?
**A3**: 「ジャンプ命令の次の 1 命令は必ず実行される」という鉄則を覚えて制御フローを読む。ROP を組むとき、各 gadget の遅延スロット副作用を考慮し、遅延スロットが無害か利用できる gadget を選ぶ。静的読解ではジャンプと次の 1 命令を一体として見る。
**Q4**: ツールがこれらのアーキテクチャのデコンパイルサポートが弱く、読めない。どうする?
**A4**: **クロスアーキテクチャ動的エミュレーション**へ方向転換する。qemu-user + gdb-multiarch でプログラムを動的にデバッグするか、unicorn/angr で関心のある関数をエミュレーション実行する。静的に読めないとき、エミュレーションで 1 回走らせてレジスタ変化を見るのが最速の直交する方向転換である。
**Q5**: ARM の Thumb/ARM 混在モードで逆アセンブルが乱れる。どうする?
**A5**: モードを手動指定する。アドレス最下位ビットが 1 なら Thumb で、逆アセンブラは間違えやすい。命令の文字化けを発見したら、そのセクションの Thumb/ARM モードを切り替え(IDA の alt+g で T フラグを変える)てから再逆アセンブルする。モードが合えばロジックが明瞭になる。
**Q6**: これらのアーキテクチャで既存 gadget/バックドアが欠けている。どうする?
**A6**: syscall 直呼びと mprotect へ方向転換する。組み込み問題は libc system がないことが多く、特定重点は「svc/syscall gadget で execve ができるか」、または mprotect で制御可能メモリを実行可能にして shellcode に跳ぶかへ転じる。gadget が乏しいとき shellcode 路線はこれらのプラットフォームで逆に実行可能である(NX が未開のことが多い)。

### 独自暗号/検証アルゴリズムの識別とその入口特定
**Q1**: crackme 系で、入力が一通り計算された後に照合される。そのアルゴリズム関数をどう特定する?
**A1**: 「最終照合点」から逆算する。プログラムが成功/失敗を判定する分岐(strcmp/memcmp/またはバイト単位 cmp+jne ループ)を探す。それが比較する 2 つのオペランド:片方は自分の入力の変換結果、もう片方は対象定数。照合点の上流のデータ変換チェーンが暗号アルゴリズムである。
**Q2**: 標準アルゴリズムか自前かをどう判断する?
**A2**: 特徴定数を検索する。標準アルゴリズムには指紋がある:AES(S-box 0x63...)、MD5/SHA(初期化定数)、TEA/XTEA(0x9e3779b9 delta)、base64(文字テーブル)、CRC(多項式)。指紋が見つかれば = 標準アルゴリズムで、既存実装で直接逆算する。見つからなければ = 自前で、手作業のリバースエンジニアリングが必要。
**Q3**: 標準アルゴリズムと確認したが魔改造(定数/ラウンド数変更)された。どうする?
**A3**: 「標準骨格 + 局所変更」を識別する。標準実装と照合して、変更された delta/S-box/ラウンド数を特定し、その差分部分だけを逆に見る。ゼロから逆に見ず、標準アルゴリズムの肩に立ってパラメータを変えるのが最速である。
**Q4**: 純粋な自前でロジックが複雑、手作業で逆に見られない。どうする?
**A4**: 静的で力ずくに逆に見るのが塞がれたので、**シンボリック実行/制約求解**へ方向転換する。angr/z3 で「入力→照合対象」を制約として建て、ソルバーに入力を逆算させ、アルゴリズム内部を理解しない。これが検証系リバースエンジニアリングで行き詰まったときの第一の直交する方向転換である。
**Q5**: アルゴリズムは可逆だが鍵/初期値が必要。静的でどう探す?
**A5**: 鍵の出所を特定する:ハードコード定数(.rodata を直接読む)、環境/ファイルから読み込む、または別のコードが生成する。生成されるなら生成関数を特定し、ハードコードなら直接写す。鍵は往々にしてアルゴリズム関数近くの即値かデータ参照内にある。
**Q6**: アルゴリズムが一方向(hash)で、根本的に不可逆。どうする?
**A6**: 攻撃面を変える。一方向 hash は逆算できないので、方向転換する:ブルートフォース(入力空間が小さければ)、プログラムに照合用の平文残留がないか探す、または「部分検証」(先頭数バイトしか検証しない、セグメントブルートフォース可能)かを見る。数学的に不可逆と認め、工学的に実行可能なブルートフォース/リーク経路へ転じる。

### 入力処理入口とテイント源の特定
**Q1**: 系統的に脆弱性を探したい。まず「汚いデータがどこから入るか」を知る必要がある。全入力源をどう特定する?
**A1**: テイント源リストを作って xref する:read/recv/fgets/scanf/gets(標準入力/ネットワーク)、fread/mmap(ファイル)、getenv(環境変数)、argv(コマンドライン)、recvfrom(UDP)。各入力関数の呼び出し点がテイント源であり、ここから下へデータフローを追う。
**Q2**: 入力が入った後、多層の関数を経て渡される。どう見失わない?
**A2**: テイント伝播追跡をする。デコンパイラでそのバッファ変数の全使用点をハイライトし、どの関数に渡されるか(パラメータとして)、どこへコピーされるか(strcpy/memcpy の目標もテイントになる)を見る。テイントデータが危険 sink(オーバーフロー/フォーマット文字列/コマンド実行)に到達するまで追えば、完全な脆弱性経路が見つかる。
**Q3**: データフローがある関数境界で切れた(細かく見ていない関数に渡した)。どうする?
**A3**: その関数に入って、テイントに何をしたかを確認する:検証フィルタ(テイントが浄化された)、原様使用(テイント継続)、インデックス/長さとして使用(整数脆弱性の可能性)。中間関数が安全だとデフォルトで仮定しない。テイント追跡は関数呼び出しを貫通しなければならない。
**Q4**: 入力源が多すぎ、データフローが発散し、人手で追えない。どうする?
**A4**: 自動化テイント解析ツールへ方向転換する。人手テイント追跡が埋没したら、静的テイント解析(ソースには CodeQL、バイナリ層のテイントプラグイン)か動的テイント(Triton/libdft)で source→sink 経路を自動マークし、ツールに枝刈りさせる。
**Q5**: 入力がまず構造体/グローバルに格納され、非同期に使われる。静的に繋がらない。どうする?
**A5**: 格納位置をハブにする。テイントがグローバル buf に格納されたら、その「グローバル buf」を xref し、それを読む全箇所を探し、「書き込み点」と「読み取り点」を 2 組に分けて列挙してから対にする。関数/非同期を跨ぐ場面では、変数名でなく格納位置をアンカーにする。
**Q6**: テイントが sink に到達したが途中に長さ検証があり、利用できないように見える。どうする?
**A6**: 検証を迂回できるか監査してから諦める。検証に使う長さも制御可能か、整数オーバーフローで検証が無効になるか(負数迂回、回り込み)、TOCTOU(検証後にデータが変わる)かを見る。検証の存在は安全を意味しない。まず検証自体を攻める。確かに迂回できないなら別のテイント経路へ転じる。

### 整数オーバーフロー/型変換脆弱性の静的監査
**Q1**: 整数問題によるメモリ破壊を疑う。静的で何を監視する?
**A1**: 「ユーザー制御の整数がメモリ操作のサイズ/インデックスに関与する」箇所を監視する。信号:malloc(n*size)、read(fd,buf,len)、memcpy(dst,src,len)、arr[idx] で、n/len/idx がユーザー入力由来。オーバーフロー/回り込み/符号問題で実値が期待を超えるかを監査する。
**Q2**: 具体的にどの整数パターンが脆弱性になりやすい?
**A2**: 3 類。①符号あり/符号なし混用。負数を size として size_t を期待する関数に渡すと巨大値になる。②乗算オーバーフロー。n*size が回り込んで小さくなり、malloc が小さすぎて後で範囲外書き込み。③切り詰め。int を short/char に代入して上位ビットを捨て、検証を無効にする。逆アセンブリでは movsx(符号拡張)vs movzx(ゼロ拡張)に注意する。
**Q3**: 符号問題が利用可能かをどう静的に確認する?
**A3**: 検証と使用が異なる符号性を使っていないか追う。古典:`if((int)len > MAX) reject;` の後に `memcpy(dst, src, (size_t)len)`。負の len が検証を通った後、超大コピーに変わる。この「検証は符号あり、使用は符号なし」の不一致点を特定する。
**Q4**: 整数脆弱性経路が存在するように見えるが発火条件が極端に厳しく、入力が計算できない。どうする?
**A4**: 手計算でなく制約求解へ方向転換する。整数回り込みの臨界入力を z3 でモデル化して求解するか、境界値(0、-1、0x7fffffff、0x80000000、0xffffffff の鬼値)を直接動的にブルートフォースする。純手計算にこだわらない。
**Q5**: 目立つ整数脆弱性が見つからないが、プログラムに大量の算術がある。どうする?
**A5**: 全算術を絨毯監査せず、「結果がメモリ操作に流れる」算術だけを監査し、残りは無視する。sink(malloc/memcpy/インデックス)を終点に、逆方向にそれに供給する数個の算術式だけを見る。範囲を大幅に縮小する。
**Q6**: 整数次元に確かに穴がない。どうする?
**A6**: 手を引いて、スタック/ヒープ/論理の次元へ戻る。整数脆弱性は「補助増幅器」で、往々にして他の脆弱性の発火条件であって独立入口ではない。なければ無理に作らず、本線に戻って続ける。

### 論理脆弱性(非メモリ破壊)の特定発想
**Q1**: メモリ系脆弱性がすべて塞がれた。問題は論理脆弱性かもしれない。どう切り込んで特定する?
**A1**: 「権限/状態判定点」から手を付ける。プログラム内の「何かをできるかどうか」を決める分岐を探す:身分検証、残高/回数検査、ステートマシン遷移、番号/token 照合。論理脆弱性はこれらの判定の疏忽に隠れる。バッファ内ではない。
**Q2**: 具体的にどの論理欠陥パターンを探す?
**A2**: 一般的なもの:①ステートマシン検証欠如。ある操作が前置状態を検査せず実行できる(未ログインでパスワード変更)。②競合/回数迂回。検査と使用の間で状態が変わる。③負数/境界。振込が負額を許可して逆に加算。④重複利用。一回きりの証憑が無効フラグを立てない。これら「検査欠如または検査後に状態が変わる」箇所を特定する。
**Q3**: 論理脆弱性の「検査欠如」をどう静的に判断する?
**A3**: 同類操作の検査一貫性を比較する。add がインデックス範囲外を検査し edit が検査しないなら、edit が缺口である。操作 A が認証を要求し、並行の操作 B が要求し忘れているなら、その不一致箇所が脆弱性である。横断比較は論理疏忽を発見する利器である。
**Q4**: 静的に見ると論理が複雑すぎ、状態が多すぎて推理しきれない。どうする?
**A4**: **動的状態探査**へ方向転換する。頭の中でステートマシンを走らせず、直接対話する:乱順操作(先に削除してから使用、ステップを飛ばす)、境界値(0、負数、超大)、重複送信を試し、プログラムが非期待応答をするか観察する。論理脆弱性は往々にして「手動で非標準のな操作列を試す」ことで発見され、動的が静的より効率的である。
**Q5**: 論理脆弱性がメモリ/フローを変えられる。それを getshell にどう昇格する?
**A5**: それが何の原語を与えるかを見る。論理の穴は往々にして「配列の範囲外読み書き」「任意インデックスのポインタ書き込み」「重要グローバル変数の変更」を与える。それを原語として、メモリ利用チェーン(GOT/戻りアドレス/関数ポインタ変更)に接続する。特定重点は「この論理の穴がどの重要構造を読み書きできるか」へ転じる。
**Q6**: 長く検討しても論理問題に見えない。どうする?
**A6**: 早めに損切りする。論理脆弱性は発散し尽くしにくい。横断比較と乱順試行の両方で異常がなければ、メモリ次元に戻って再監査する(以前にある sink を見落とした可能性)。論理次元で無限に発散せず、タイムボックスを設ける。

### C++ バイナリ:仮想テーブルとオブジェクト特定
**Q1**: デコンパイルが this ポインタ、間接呼び出しだらけ。C++ と判断した。静的でどう整理する?
**A1**: まず「オブジェクト-仮想テーブル」モデルを確立する。C++ オブジェクトのメモリレイアウト:先頭 8 バイトは vptr(仮想テーブルを指す)であることが多い。コンストラクタ(オブジェクトに vptr を埋める箇所)を特定し、仮想テーブル配列から各仮想関数アドレスを読み、`call [rax+offset]` の間接呼び出しを具体仮想関数に解決する。
**Q2**: 間接呼び出し `call [reg+N]` がどこへ跳ぶか分からない。実関数をどう特定する?
**A2**: 静的で仮想テーブルを解く:N は仮想関数の仮想テーブル内オフセットで、そのオブジェクトの仮想テーブルベース(コンストラクタで vptr に代入されるアドレス)を探す。仮想テーブルベース+N のポインタが対象関数である。逆アセンブラは自動で vtable を解決できることがあり、手動ならコンストラクタを追う。
**Q3**: C++ 問題の脆弱性はよくどこにあり、どう特定する?
**A3**: 重点は:①type confusion。オブジェクトを誤った型で使い、vptr 解釈が間違う。②オブジェクトの UAF。delete 後に vptr が懸空し、占位して仮想テーブルを偽造できれば制御フローを握る。③コンテナ範囲外(vector/string の範囲外)。delete 後のオブジェクトがまだ仮想関数を呼ばれるかを特定する(UAF+vtable 乗っ取りが C++ pwn の本線)。
**Q4**: 仮想テーブル呼び出しチェーンが深く、オブジェクト関係が乱れ、静的で追えない。どうする?
**A4**: 動的ブレークポイントで実 vptr を見る方向へ転換する。間接 call でブレークし、実行時に reg が指すオブジェクト、その vptr が指す実仮想テーブルを見て、1 回の実行でオブジェクト種別を明らかにする。C++ の多態は静的で解きにくいとき動的が最も直接的である。
**Q5**: 仮想テーブルを乗っ取りたいが、偽造仮想テーブルをどこに書くか分からない。どうする?
**A5**: 制御可能メモリ + 制御可能 vptr の 2 要素を特定する。完全な偽オブジェクトを書き込めるヒープブロック(add 時に内容制御可能)と、旧 vptr を使う経路(UAF)を発火できる点を探す。偽造仮想テーブルの vptr を制御可能メモリに向け、そのメモリに偽関数ポインタを配置する。特定需要は「制御可能書き込み領域」と「仮想呼び出し発火点」である。
**Q6**: シンボルが strip され name mangling もなく、クラスを認識できない。どうする?
**A6**: RTTI と挙動識別に頼る。RTTI があれば、`type_info` にクラス名文字列が残ることが多い。RTTI がなければ挙動でオブジェクトに命名する(コンストラクタがどのフィールドを初期化したか、仮想テーブルに何個の関数があるか)。元クラス名の復元を追求せず、異なるオブジェクト種別を区別できれば前進できる。

### タイムボックス:静的で行き詰まったときいつ戦略を転換すべきか
**Q1**: ある関数の静的リバースエンジニアリングに長く費やしても突破がない。続けるべきかどう判断する?
**A1**: 硬いタイムボックスを設ける(単一関数の静的読解が 15-20 分を超えて進展がなければ強制転換)。レッドチーム/CTF の敵は時間である。判定基準:この時間内に「脆弱性位置への理解」が前進していなければ、それは合図。読む時間が足りないのではなく、方法が間違っているので、次元を変えるべき。
**Q2**: どの方向へ転換すべき?どう選ぶ?
**A2**: 「直交性」で次の手を選ぶ。静的で読めない → 動的デバッグ。動的で走らない → シンボリック実行。論理が推理できない → ブラックボックスで入力を乱試行。オーバーフローが見つからない → 脆弱性種別を変える(ヒープ/フォーマット文字列/論理)。常に現在の失敗方法と次元が異なる手へ転じ、同一方法をもっと強くはやらない。
**Q3**: 「あちこち横跳びして、どの道も浅くしか進まない」をどう避ける?
**A3**: 仮説-検証の記帳を使う。方向を転換する前に「私は脆弱性が X 種別と賭け、検証には Y を見る」と書き、各仮説に明確な反証条件を与える。反証されたら線を引いて仮説を替える。感覚で乱跳びしない。探索を記録付きの仮説排除に変える。
**Q4**: 複数の道をすべて試して詰まり、本当に手がかりがない。どうする?
**A4**: 最上流に戻って情報を再収集する。往々にして最初に見落とした手がかりがある:strings を再実行して見落としたパス/関数名を探す、第二のバイナリ/設定ファイルがないか、問題説明/添付の示唆を見る、libc バージョンの既知利用テンプレートと比較する。行き詰まったとき「情報層へ退く」ほうが「コード層を深掘りする」より突破口になりやすい。
**Q5**: 自分のツール/環境問題で行き詰まった疑いがある。どうする?
**A5**: ツールを相互検証する。別のデコンパイラ(IDA↔Ghidra↔Binja)で別ツールの方が認識が良いか、データベース/署名を更新、逆アセンブルモード(アーキテクチャ/Thumb/バイト順)が誤設定でないか確認する。「読めない」がツールの解析ミスであって、ロジックが本当に難しいとは限らない。
**Q6**: 時間が本当に足りない。有限時間で成果をどう最大化する?
**A6**: 「広さ優先トリアージ」へ方向転換する。一題を深掘りするより、各候補点を素早く通して「利用可能性の高低」を判定し、最も穴が出そうな 1-2 箇所(制御可能なスタック書き込み > 明らかな UAF > フォーマット文字列)に火力を集中する。資源が逼迫したとき、利用ステップが最少で最も安定した経路を選び、派手だが不確実なものを捨てる。

### 静的で gadget と制御可能レジスタ落点を特定する
**Q1**: ROP を組もうとしている。静的段階で ROPgadget を走らせる以外に何を特定すべき?
**A1**: 「オーバーフロー点でどのレジスタ/スタックが既に自分が制御できるか」を特定する。ROP は gadget があるだけでは足りず、発火時のスタックレイアウトを知る必要がある:戻りアドレスの直後のスタック空間は自分の入力の継続か?ret 時にどのレジスタが既に制御可能データを指しているか?静的で「制御落点」を計算して初めて gadget チェーンを計画できる。
**Q2**: gadget が山ほどある。本当に必要な数個をどう選ぶ?
**A2**: 目標から逆算して必要な gadget を求める。execve を呼ぶには `pop rdi/rsi/rdx; ret` と syscall gadget が要る。ret2libc には `pop rdi; ret` + system + "/bin/sh" が要る。まず利用形態を定め、その形態リストで gadget 集合を精確に検索する。全 gadget を通読しない。
**Q3**: 重要 gadget が欠ける(例えば `pop rdx` がない)。どうする?
**A3**: 代替技法へ方向転換する。pop rdx が欠けるとき:`mov rdx, ...; ...; ret` の間接設定を探す、libc 内の magic gadget を使う、`__libc_csu_init` の汎用 gadget で一度に複数レジスタを制御する(旧 libc)。駄目なら SROP に替える(sigreturn で全レジスタを一度に設定、必要なのは syscall gadget 1 個 + 制御可能スタックだけ)。
**Q4**: gadget が足りず、スタック空間も長いチェーンを置けない。どうする?
**A4**: この道が塞がれたので、**スタック移行(stack pivot)**へ方向転換する。`leave; ret`/`pop rsp` 系 gadget でスタックポインタを制御可能な大バッファ(ヒープ/bss)へ移し、完全な ROP チェーンを置く十分な空間を得る。空間不足はよくある壁で、pivot は標準の直交解である。
**Q5**: スタック移行の目標が実行可能かをどう静的に確認する?
**A5**: 「アドレス既知かつ内容制御可能」なメモリを特定する:bss 上のグローバルバッファ(No PIE ならアドレス固定)、またはアドレスをリーク済みのヒープブロック。そこに ROP チェーンが収まり、実行時に到達できるか確認する。静的で足場を選び、動的で pivot 後の rsp が正しく落ちるか検証する。
**Q6**: 使える gadget が完全にない(極小バイナリ)。どうする?
**A6**: 利用パラダイムを変える。gadget 砂漠のとき:ret2dlresolve(libc リーク不要で任意関数を呼ぶ)、ret2csu、または NX 未開なら直接 shellcode。特定重点を「gadget 探し」から「より多くのコードを導入できる原語を 1 つ探す(dlresolve 偽造構造の書き込み可領域など)」へ転じる。

### seccomp サンドボックスを特定し利用形態を調整する
**Q1**: shell を取ったのに execve が禁止された。サンドボックスを疑う。静的でどう確認する?
**A1**: 静的で prctl(PR_SET_SECCOMP)、seccomp_init、BPF フィルタルール配列を検索する。sandbox インストール関数を特定し、その BPF ルールを読んでどのシステムコール番号が禁止か(execve=59、execveat など)を見る。または seccomp-tools dump で動的にルールを得る方が速い。
**Q2**: サンドボックスがあると確認した。利用目標をどう変える?
**A2**: getshell から orw(open/read/write flag)へ変える。特定需要は、open("flag")→read→write(1) の syscall チェーンに必要な gadget(pop rdi/rsi/rdx + syscall)の構成に変わる。サンドボックスは「shell が要る」を「ファイルを読んで外部へ」に格下げするので、事前に確認して、shell を通してから無意味と気づくのを避ける。
**Q3**: サンドボックスが open まで禁止。どうする?
**A3**: 代替 syscall へ方向転換する。open 禁止なら openat。read 禁止なら pread/readv。write 禁止なら writev/sendfile/puts。サンドボックスのホワイトリスト内で放行された等価 syscall を特定し、それらで等価なファイル読み取りフローを組む。
**Q4**: サンドボックスがごく少数の syscall だけ許可(例:read/write/exit のみ)。どうする?
**A4**: 極限サンドボックスは side-channel/無 open 読み取りへ方向転換する。既に開いた fd を使う、stat/access の戻り差でバイパスリークする、または flag が既にプログラムにメモリへ読まれた残留を直接 write する。標準 orw が塞がれたと認め、「open せずに flag 内容を取る」発想へ転じる。
**Q5**: サンドボックスが seccomp の arch 検証や ptrace を使う。どうする?
**A5**: 検証機構を特定して迂回する。フィルタが arch で判断するなら、x86 互換モードへ切り替え(CS セグメントを変えて int 0x80 で 32 ビット syscall 番号を使い、64 ビットフィルタを迂回)を試す。ptrace で親プロセスを監視するなら、監視ロジック自体を攻めることを考える。
**Q6**: サンドボックスの位置/ルールがどうしても特定できない。どうする?
**A6**: 純粋な静的検索をせず、直接動的に。疑わしいインストール点の前後で seccomp-tools でルールを掴むか、strace でどの syscall が EPERM/KILL されたかを見る。動的一発は静的で BPF バイトコードを読むよりはるかに速い。

### 複数バイナリ/共有ライブラリ連動の特定
**Q1**: 問題が主プログラム + 複数の .so/別バイナリを与えた。先にどれを解析し、どう分担する?
**A1**: まずコンポーネント関係図を作る。主プログラムは入口とロジック核心なので、先に逆に見る。.so は呼ばれるライブラリ(自前暗号/検証は自前 .so 内によくある)。loader/サーバー多プロセスなら、誰が誰を呼ぶか、データがどうコンポーネント間を渡るかを整理する。判定基準:脆弱性点は往々にして「主プログラムが自前 .so 関数を呼ぶ」境界にある。
**Q2**: 主プログラムが .so 内の関数を呼んだ。ファイルを跨いでどう追う?
**A2**: 主プログラム内でそのインポートシンボルへの呼び出しを特定し、関数名を書き留め、対応 .so 内でシンボルで実装を探す。2 つのファイルを同じ逆アセンブリプロジェクトにロード(または別々に開いて)照合する。データフローがファイルを跨ぐとき、.so 関数を「サブルーチン」としてテイント追跡を続ける。
**Q3**: 自前 .so が重要だが、主プログラムが間接(dlopen/dlsym)ロードし、静的に対応付けられない。どうする?
**A3**: dlsym の文字列パラメータを特定して実関数名を得て、.so 内で探す。関数名も実行時に組み立てられるなら、動的に: dlsym の戻り箇所で解決されたアドレスを見て、.so のどの関数に落ちるか逆算する。
**Q4**: 複数コンポーネント間がネットワーク/IPC 通信で、静的ではフロー全体が繋がらない。どうする?
**A4**: **動的全チェーン取得**へ方向転換する。strace/ltrace でシステムコールとライブラリ呼び出しを追う、tcpdump/socket でコンポーネント間トラフィックを掴む、gdb で各プロセスに attach する。分散ロジックは静的で組みにくく、動的に実対話データを観測するのが最も直接的である。
**Q5**: バージョン関連:問題付属の libc/.so がローカルと違う。利用にどう影響する?
**A5**: 一律に問題付属を基準にする。付属 libc でオフセットを計算し(patchelf で主プログラムの interpreter と rpath を問題 libc に向ける、または LD_PRELOAD/pwntools の libc パラメータを使う)、ローカル環境は必ず対象環境を再現する。そうしないとオフセットが全滅する。
**Q6**: コンポーネントが多すぎてどれを逆に見るべきか分からない。どうする?
**A6**: 「テイントデータを処理するコンポーネント」を優先する。どのコンポーネントがユーザー/ネットワーク入力を直接受けて解析するか。そこが攻撃面の核心である。純設定/ログコンポーネントは先にスキップ。資源をデータ入口コンポーネントに集中し、平均的に力を使わない。

### メニュー駆動プログラム:コマンドディスパッチと各機能実装の特定
**Q1**: プログラムがループメニュー(数字入力で機能選択)。各機能の実装関数をどう素早く特定する?
**A1**: ディスパッチ中枢を探す。メニュー出力後には必ず選択肢読み取り(scanf/read で整数 1 個)+分岐ディスパッチがある。if/else if で選択肢番号を比較する列か、switch(ジャンプテーブル jmp [table+idx*8] にコンパイル)、関数ポインタ配列のいずれか。このディスパッチ点を特定すれば、各 case/テーブル項目が 1 つの機能関数に直結する。
**Q2**: ジャンプテーブル(jump table)にコンパイルされた。選択肢番号を関数に対応付けるには?
**A2**: ジャンプテーブルを解く。逆アセンブラは通常 `jmp ds:table[rax*8]` を既に認識している。table 配列まで追って各項目アドレスを読み、インデックス順に「選択肢1→funcA、選択肢2→funcB」。合わないときは手動:table ベース + 選択肢番号*8 のポインタが目標である。
**Q3**: 隠し選択肢(メニューにないがコードが処理する)をどう発見する?
**A3**: メニューテキストだけを見ず、ディスパッチがカバーする選択肢範囲を見る。メニューが 1-5 しか表示しないのに分岐が 6/7 やあるマジックナンバーを処理するなら、それが隠し機能(往々にしてバックドア/デバッグ機能)である。「表示される選択肢集合」と「コードが実際に受け付ける選択肢集合」を比較し、差集合が隠し入口である。
**Q4**: 選択肢番号の読み取りに scanf("%d") を使い、非数字入力で異常がある。どう特定する?
**A4**: これは手がかりであって干渉ではない。**入力解析の異常経路**へ方向転換する。scanf はマッチ失敗時に入力を消費せず、変数が旧値を保持するため、無限ループや未初期化選択肢番号の使用につながる。scanf の戻り値が検査されるかを特定し、未検査箇所が論理脆弱性の入口であることが多い。
**Q5**: ディスパッチロジックが O2 最適化で対応関係が見えない。どうする?
**A5**: 動的テーブル作成へ方向転換する。gdb でディスパッチ点にブレークし、順に 1、2、3...を入力して、毎回どのアドレスへジャンプするかを記録し、「選択肢→関数」マッピングを直接作る。最適化後の制御フローを静的に無理に解かない。
**Q6**: 機能関数が多すぎ、どれを先に逆に見るか分からない。どうする?
**A6**: 攻撃価値順に逆に見る。優先は add/create(割り当て+書き込み、ヒープオーバーフロー/size 制御可能)、edit(書き込み、範囲外)、delete(free、UAF/double free)、show(読み取り、リーク)。config/help/exit 系は先にスキップ。資源を「読め書け解放でき」る機能に投入する。

### グローバル/BSS データ構造と重要変数の特定
**Q1**: ロジックが多数のグローバル変数(フラグ、カウンタ、ポインタ配列)に依存する。それらをどう系統的に特定する?
**A1**: .bss/.data の参照から逆算する。怪しいグローバルアドレスに xref し、誰が書くか、誰が読むかを見て、読み書きパターンで命名する:add が書き、delete が消すのは「オブジェクトポインタ配列」。検証時にしか読まないのは「権限フラグ」。操作ごとに自増するのは「カウンタ」。匿名グローバルを意味を持つ構造に復元する。
**Q2**: いくつかのグローバルが並び、同じ構造体のフィールドと疑う。どう確認する?
**A2**: アクセスのベース+オフセットパターンを見る。コードが常に `base + 0/8/16` の形で隣接アドレスを組でアクセスするなら、それらは 1 つの構造体のフィールドである。逆アセンブラで構造体(struct)を定義し、`base+8` を `obj->size` のように表示させると、後続の読解が倍効率になる。
**Q3**: 重要グローバル(「認証済みか」フラグなど)を見つけた。それが利用にどう役立つ?
**A3**: 論理迂回の標的である。ある範囲外書き込み/フォーマット文字列がこのフラグに届けば、正常フローを通らず直接「認証済み/管理者」になれる。その精確なアドレス(No PIE 固定、PIE はベース加算)を特定し、既存の書き込み原語が届くか評価する。
**Q4**: グローバルバッファが bss にあり canary 保護がない。これは何を意味する?
**A4**: **bss オーバーフロー**という比較的省力な道へ方向転換する。bss/data 上のグローバル配列オーバーフローはスタック canary に守られず、隣接グローバル(ポインタ配列、関数ポインタ、フラグ)を上書きできる。隣接レイアウトを特定する:オーバーフローするグローバルの直後に何の重要変数が続くか、それが上書き目標である。
**Q5**: グローバルポインタ配列のインデックス検証欠如を、どう任意アドレス読み書きに変える?
**A5**: インデックス演算 `array[idx]` を特定し、idx が負または超界で検査がなければ、`array + idx*8` が任意アドレスを指せる。array ベースをアンカーに、目標(GOT/戻りアドレス/別グローバル)までの必要な idx を計算して、任意読み書き原語に変える。
**Q6**: グローバルが多すぎ、xref が雑すぎて整理できない。どうする?
**A6**: 「判定に関与する」「メモリ操作に関与する」グローバルへ縮小する。if 条件に読まれるもの(論理標的)、ポインタ/インデックス/長さとして使われるもの(メモリ標的)だけを関心対象にする。純出力/純定数のグローバルは無視する。用途で枝刈りし、各グローバルにすべて檔案を作らない。

### プログラムの自己チェックサム/アンチデバッグロジックを特定し迂回する
**Q1**: プログラムがデバッガに入れると挙動が異常/終了する。アンチデバッグを疑う。どう特定する?
**A1**: 一般的なアンチデバッグ原語を検索する:ptrace(PTRACE_TRACEME)(デバッグされると 2 回目の ptrace が失敗)、/proc/self/status を読んで TracerPid を調べる、INT3(0xCC)検知、rdtsc 時間差、getppid で親プロセスを判断。これらの呼び出しを xref し、検知点と「検知したら悪さをする」分岐を特定する。
**Q2**: ptrace アンチデバッグを特定した。どう迂回する?
**A2**: 三択:検知分岐を patch する(ジャンプを無条件で正常路へ)、実行時に戻り値を変える(gdb で ptrace 返却後に rax を期待値に)、LD_PRELOAD で ptrace を乗っ取って常に成功を返す。静的 patch が最も一労永逸である。
**Q3**: プログラムにコード自己チェックサム(自身が改変されるとクラッシュ)があり、patch するとクラッシュする。どうする?
**A3**: これは自己チェックサム(checksum)が働いているので、**先に検証関数を特定して一緒に処理する**方向へ転換する。自身の .text を読んで hash を計算し比較するループを探し、それも patch するか、比較を恒成立にする。またはファイルを変更しない動的法(メモリブレークポイント/レジスタ値変更)に変えて、ファイル検証の発火を避ける。
**Q4**: アンチデバッグが多すぎ、1 つずつ patch するのが遅い。どうする?
**A4**: 個別排除でなく迂回へ方向転換する。アンチデバッグ対抗プラグイン(gdb の ida 風アンチアンチデバッグスクリプト、ScyllaHide、qemu ユーザーモードで走らせて一部検知を迂回)、または直接 strace でデバッガに入らず静的観測、unicorn で対象関数だけをエミュレーションして、アンチデバッグ環境全体を避ける。
**Q5**: アンチデバッグが「検知したら静かにロジックを変える」(クラッシュせず誤分岐に進む)。どうする?
**A5**: 「静かな分岐」を警戒する。それは故意に偽ロジックへ逆に見るよう誤導している可能性がある。検知点を特定したら、「検知が真」「検知が偽」の 2 分岐の差を重点確認する。本物のロジックは「未デバッグ」分岐内にある。誤った分岐を逆に見て時間を浪費しない。
**Q6**: アンチデバッグかプログラム自体の正常ロジックか区別できない。どうする?
**A6**: 対照実行する。同じ入力で、デバッガに入れず直接走らせた場合(出力を記録)と、デバッガに入れて走らせた場合を比べ、挙動の不一致箇所がアンチデバッグの発火点である。一発で特定できる。「デバッガ内か否か」を差分変数として二分する。

### 重要比較点(strcmp/memcmp)を識別しその弱点を利用する
**Q1**: プログラムが自分の入力とある秘密を比較する。比較点を特定し、うまく搾り取れるかを見たい。どうする?
**A1**: 比較関数を特定する:strcmp/strncmp/memcmp/または手書きバイト単位ループ。見つけたらまず比較方式を見る:「最初の相違で戻る」か(時間サイドチャネルでバイト単位ブルートフォース可)、「先頭 N バイトだけ比較」か(部分一致で通過)、比較対象が平文定数か(直接読み出す)。
**Q2**: 比較対象がハードコードされた平文定数。直接読める?
**A2**: 読める。memcmp(user, "secret", n) の "secret" は .rodata にあり、直接 strings/逆アセンブルで読み出せば答え級の情報である(ここでの方法:比較基準の平文は静的に読み取れる)。定数参照を特定すれば正しい入力が得られ、計算すら要らない。
**Q3**: 比較が短絡(バイト単位で比べ、間違えば止まる)。どうブルートフォース可能に変える?
**A3**: 時間サイドチャネルを利用する。バイト単位 strcmp は正しいバイトが多いほど所要時間が長いので、バイト単位に逐位ブルートフォースできる(各位 256 回試して最長のものを取る)。「早期リターン」実装と確認した後、タイミングブルートフォース戦略へ方向転換し、256^n を 256*n に下げる。
**Q4**: 比較する秘密が実行時に動的生成(定数でない)で、読めない。どうする?
**A4**: 静的に読めないなら、**比較点で動的に平文を掴む**方向へ転換する。strcmp/memcmp の入口でブレークすると、プログラムがそこまで走った時点で、その「秘密」パラメータが既にレジスタ/メモリに現れているので、直接読み出す。比較点での動的ブレークが実行時秘密を取る最速法である。
**Q5**: 比較が自前で、標準関数を呼ばない。どう識別する?
**A5**: 「ループ + 逐要素 cmp + 不一致なら break/エラーフラグ設定」のパターンを探す。自前比較は通常小さなループで、ある配列とユーザー入力をバイト単位に xor か sub して非ゼロを判定する。このループ形状を識別すれば比較ロジックを特定でき、定数を読むか動的に掴むかを決める。
**Q6**: 比較通過後も多層検証があり、1 層通すだけでは足りない。どうする?
**A6**: 検証チェーンリストを作って層ごとに特定する。多段検証(フォーマット→長さ→内容→署名)は順に各層を特定し、各層で迂回か基準読み取りを探す。一歩で通ることを期待しない。「通過」を複数のサブ条件の合接と捉え、個別に撃破する。

### コンパイラ/最適化レベルを識別してリバースエンジニアリング戦略を調整する
**Q1**: 同じロジックでもコンパイル産物が天と地ほど違って読める。まずコンパイル特徴をどう判断してから戦略を定める?
**A1**: banner とコード形態から判断する。`strings` 内の "GCC: (...) x.y.z"/clang バージョンがコンパイラを与える。関数 prologue、スタック保護形態、レジスタ割り当てスタイルが最適化レベルを与える。O0 は変数がすべてスタックにあり、直白的。O2/O3 は大量のインライン化、レジスタ受け渡し、ループベクトル化。まず「自分が O0 か O2 に対面しているか」を認識すれば、読解期待が合う。
**Q2**: O0 と O2 でそれぞれ読解姿勢をどう調整すべき?
**A2**: O0:擬似コードを信じ、変数がソースに対応し、逐行読める。スタックオーバーフローオフセットも計算しやすい(変数がすべてスタック)。O2:ソースとの逐行対応を期待せず、関数が呼び出し元へインラインされ、局所量がレジスタを流れる。代わりに「データフローと全体意味」を見る。スタックオフセットは最適化で直感と違うことがある。
**Q3**: LTO(リンク時最適化)や PGO と分かった。関数境界がぼやけた。どうする?
**A3**: 関数がモジュールを跨いでインライン再編されたと認め、「あるソース関数」を探さない。機能ブロック(入力処理ブロック、検証ブロック)を単位に理解し、関数を単位にしない。文字列/定数アンカーで機能ブロックを特定し、それがどの元関数に属すかは無視する。
**Q4**: 最適化レベルを誤判断し、O0 の発想で O2 コードを読んで詰まった。どうする?
**A4**: これは「期待ミスマッチの壁」なので、**再較正 + 動的**へ方向転換する。最適化が急進的と認めたら、擬似コードを減らして動的を増やす:直接 gdb でシングルステップしてレジスタを見る。最適化コードの実意味論は実行時に最も明瞭である。O0 の忍耐で最適化後のベクトル化ループを逐行読まない。
**Q5**: コンパイラ特徴はさらにどんな利用関連情報を推測させてくれる?
**A5**: 防御デフォルト値と libc 挙動を推測させる。新版コンパイラはデフォルトで PIE/Full RELRO/FORTIFY(_chk 版関数)を有効にする。旧版はないことがある。__printf_chk/__memcpy_chk が見えれば FORTIFY 有効で、フォーマット文字列 %n が禁止され、バッファにサイズ検査がある可能性が高い。どの套路が無効かを事前に知る。
**Q6**: コンパイラ banner が完全にない(strip された)。どうする?
**A6**: 命令スタイルの指紋に頼る。prologue/末尾モード、スタックアラインメント方式、PLT stub 形態、例外処理テーブル(GCC の .eh_frame vs MSVC の SEH)で GCC/Clang/MSVC/組み込みツールチェーンを区別できる。精確なバージョンを認識できなくても、ツールチェーン族を認識すれば戦略誘導に十分である。

### 配列インデックス範囲外(OOB)読み書き点の特定
**Q1**: 配列範囲外(オーバーフローでなく悪いインデックス)を疑う。静的でどう特定する?
**A1**: `array[idx]` で idx がユーザー入力由来の箇所を探し、インデックス検証を監視する。信号:`base + idx*elemsize` のメモリアクセスに制御可能な idx が対応。検証を監査:idx < 上限を検査するか?idx >= 0 を検査するか(符号あり負インデックスは重灾区)?どちらかが欠ければ OOB である。
**Q2**: 上界検査はあるがまだ範囲外を疑う。脆弱性はどこ?
**A2**: 検査の符号性と境界記号を調べる。`if(idx > N)` が符号あり比較なら、負 idx が検査を通って配列前方メモリへ(低アドレスへ範囲外)。`>` vs `>=` は 1 要素違う。比較命令が signed(jg/jl)か unsigned(ja/jb)かを特定する。負インデックスは符号あり検査に特効である。
**Q3**: OOB 読み取りと OOB 書き込みは価値が違う。これが何をできるかどう判断する?
**A3**: OOB 読み取り → 情報リーク原語(隣接のポインタ/canary/libc アドレスを読んで回帰)。OOB 書き込み → 改ざん原語(隣接グローバル/関数ポインタ/戻りアドレスを変える)。特定後すぐ評価:範囲外が触れられる隣接メモリに何の高価値対象があるか。それが leak か control 原語かを決める。
**Q4**: インデックス範囲外だが歩幅(elemsize)固定で、変えたい対象に届かない。どうする?
**A4**: 到達性を換算し、届かなければ別の原語へ転じる。base + idx*8 の粒度と範囲が対象アドレスに届かないなら、idx の取値範囲(型制限)がどれだけカバーするか評価する。届かなければこの原語は有限と認め、別の書き込み点を探す。届かない対象に固執しない。
**Q5**: 範囲外アクセスがポインタ配列(array[idx] がポインタでさらに参照)へのアクセス。これは何を意味する?
**A5**: これは「範囲外 + 参照」の二重威力で、しばしば任意アドレス読み書きへ昇格できる。悪い idx で偽造/隣接ポインタを 1 つ選ばせ、プログラムがそれに読み書きする。そのポインタ内容も同時に制御できれば、任意読み書きである。「先に悪い idx でスロットを選び、そのスロット内容を書く」配合操作の有無を特定する。
**Q6**: 静的で範囲外がどこまで届くか計算できない。諦めるべきか?
**A6**: 純粋な静的計算をせず、動的検証へ転じる。範囲外 idx を 1 つ与えて実際に走らせ、gdb でどのアドレスにアクセスしたか、クラッシュしたか、何を読み/変えたかを見る。範囲外の到達性は動的一測で分かり、静的にメモリレイアウトを推算するより速く正確である。

### 情報リーク(leak)原語の専門的な特定
**Q1**: PIE/Canary があり、まず leak を 1 つ取る必要がある。静的でリーク点をどう専門的に探す?
**A1**: 「メモリ内容を自分に送り返す」全出口を探す:puts/write/printf/send とそのパラメータ出所。パラメータが「未初期化/範囲外/free 後」のメモリを指す出力はすべて候補 leak である。出力関数をアンカーに xref し、逐個その出力データがアドレス性の内容を含むかを見る。
**Q2**: ある出力点が価値あるアドレス(libc/PIE/canary/heap)をリークできるかどう判断する?
**A2**: リークされるメモリに「何が常在するか」を見る。スタック残留には libc 戻りアドレス、__libc_start_main 関連がよくある。未クリアヒープブロックには fd/bk ポインタが残る(heap/libc を漏らす)。canary はスタックバッファに隣接する。出力のメモリ位置を特定し、その位置の典型的残留物と照合して、どの類のアドレスがリークできるか判断する。
**Q3**: リークできる点を見つけたが puts が \x00 で切り詰め、アドレスリークが不完全。どうする?
**A3**: 無切り詰め出力かオフセットリークへ方向転換する。puts は空バイトで止まるので、write(長さ付き、空バイトを見ない)のリーク点を使う。またはアドレス下位がよく 00 という特性を利用し、上位有効バイトだけを残すよう上書きして puts に欲しいバイト列を出力させる。puts の代替となる write 型出力があるか特定する。
**Q4**: プログラム全体にメモリを直接出力する点が見つからない。leak が手が出ない。どうする?
**A4**: この道が塞がれたので、**間接/サイドチャネルリーク**次元へ方向転換する。直接回帰がなければ:エラーメッセージの差(アドレス違いで報錯が変わる)、クラッシュ有無の真偽リーク、時間差、または partial overwrite でブルートフォース(PIE/libc の半バイトを 1/16 確率で当てる)。直接 leak がないと認め、ブルートフォースかバイパスへ転じる。
**Q5**: leak アドレスを 1 つ得た。それがどの種のアドレスか、ベースアドレスを計算できるかをどう静的に確認する?
**A5**: アドレス特徴と既知オフセットを見る。libc アドレスは通常ある固定高位、ヒープアドレスは別のセグメント、スタックアドレスはまた別。リーク値から「そのシンボルのファイル内オフセット」を引いてベースアドレスを得る(libc leak - リーク関数の libc 内オフセット = libc base)。特定需要:リークされたのがどの既知シンボルかを確認してこそベースを逆算できる。
**Q6**: leak 値が毎回違い、安定オフセットが計算できない。どうする?
**A6**: 「ASLR の正常なランダム」か「別のものを漏らした」かを区別する。同種アドレスは毎回走らせて下位 12 ビット(ページ内オフセット)が固定、上位がランダムのはず。下位も乱れるなら、リークしているのは安定シンボルでなくごみである。リーク点が本当に自分の思う変数を出力しているか再確認し、メモリ位置を誤特定した可能性がある。

### 未初期化変数/スタック残留データの利用特定
**Q1**: 「未初期化の変数を使った」脆弱性を疑う。静的でどう特定する?
**A1**: 「バッファ/変数を宣言 → 未書き込みで読む/出力」の経路を探す。典型:局所 char buf[N] が未クリアで、ある分岐下で read に満杯に書かれないまま puts/使用される。または malloc(クリアしない)後に直接読む。これら「読みが書きの前」の変数を特定する。残留は前回の呼び出しがスタック/ヒープに残したデータである。
**Q2**: 未初期化をどう利用可能な leak か control に変える?
**A2**: スタック残留は前の関数が残した戻りアドレス/canary/ポインタを含むことが多いので、未初期化読み+出力 = 無料の leak。ヒープ残留(tcache 再利用ブロック)は fd ポインタを含むので、heap/libc を漏らす。この未初期化データが出力されるかポインタとして使われるかを特定し、それが leak か control 原語かを決める。
**Q3**: 「前回の呼び出しが残したのがちょうど自分の欲しいもの」かをどう静的に確認する?
**A3**: 呼び出し系列を解析して残留内容を決める。スタック残留は「前にどの関数がこのスタックを使ったか」で決まる。先に libc アドレスをそのスタック位置に置く関数を呼び、次にこの未初期化読みの関数を呼べば、残留が libc アドレスである。特定需要:残留内容を「プリセット」できる前駆呼び出しを探し、呼び出し順序を構成する。
**Q4**: 未初期化経路はあるが残留内容が制御不能/ごみ。どうする?
**A4**: 残留を能動的に配置する(heap/stack feng shui)方向へ転換する。先に特定サイズのブロックを割り当て-解放する、または先に特定関数を呼ぶことで、欲しいデータをそのメモリに「餌として」置き、未初期化読みを発火する。制御できなければ先にレイアウトし、レイアウトできなければ諦めて別の原語へ転じる。
**Q5**: この脆弱性が動的再現で時々効いたり効かなかったりする。どうする?
**A5**: 残留は実行履歴に依存するので、前置状態を固定しなければならない。毎回発火前の操作系列を完全に一致させる(同じメニュー操作順序)ことで、ランダム性を消す。「どの前置操作がそのメモリ残留に影響するか」を特定し、それらを利用スクリプトの前置ステップとして固定する。
**Q6**: 未初期化点が見つからず、問題の leak に別の出所もない。どうする?
**A6**: 広義の「読みが書きの前」走査に戻る。局所変数だけでなく、構造体の部分初期化(数フィールドだけ埋めて残り残留)、配列の部分充填、realloc が拡張した新領域も見る。これらはすべて残留 leak 源である。本当になければ別の leak 手段へ徹底的に転じる。

### 署名で静的リンクバイナリ内のライブラリ関数シンボルを復元する
**Q1**: 静的リンク+stripped で、sub_XXXX だらけ。libc と業務コードの区別がつかない。どうする?
**A1**: 関数署名識別(FLIRT/Ghidra FidDB)を使う。静的リンクは libc をコンパイルしており、これらのライブラリ関数には固定バイトパターンがある。対象 libc バージョンにマッチする署名庫を走らせれば、printf/malloc/strcpy などが自動で名前復元される。残った署名未ヒットのものこそ本当の業務コードで、攻撃面が一瞬で収束する。
**Q2**: 署名を走らせてもまだ大きな塊が未識別。業務コードをどう区別する?
**A2**: 消去法で特定する。署名ヒットはライブラリ関数なので無視。残った未命名関数のうち、(識別済みの)read/malloc/printf を呼び、メニュー/検証ロジックを含むものが業務核心である。「誰が既知の入出力関数を呼ぶか」でさらに特定する。
**Q3**: 手元にマッチするバージョンの署名庫がない。識別率がとても低い。どうする?
**A3**: 署名生成か別のマッチ源へ方向転換する。libc バージョンを確定できれば、対応バージョンの libc.a を sig ツール(IDA の sigmake、Ghidra スクリプト)で署名を自分で生成してから適用する。または同バージョンの符号化済み参照バイナリを探して diff(BinDiff)でシンボルを移す。
**Q4**: 署名が一部の業務関数をライブラリ関数と誤識別し、誤導した。どうする?
**A4**: 誤報を警戒し、挙動で再照合する。「strcpy と識別された」関数の xref がメニューロジックを指すなら、誤マッチである。重要関数は署名名を盲信せず、実装を一瞥して確認する。署名は加速器であって真理ではない。
**Q5**: libc バージョンすら不確定で、署名がまったく合わない。どうする?
**A5**: 指紋でバージョンを逆算してから戻る方向へ転換する。libc 内の特徴文字列("GNU C Library ... release version 2.XX")、または識別済み少数関数のバイトを既知バージョンデータベース(libc-database)と照合してバージョンを確定し、バージョンを得てから対応署名を適用する。まず「どの libc か」という前置を解決する。
**Q6**: 署名復元が現問題にあまり役立たない(業務が全自前)。どうする?
**A6**: それは攻撃面がそもそも自前コードにあることを示し、署名の価値は既に回収済み(ライブラリのノイズを排除してくれた)。シンボル復元への投入を止め、精力をすべて署名未ヒットの自前関数の脆弱性監査へ転じる。

### angr/シンボリック実行をいつ使うべきか、いつ使わないか
**Q1**: 複雑な検証を逆に見て、angr シンボリック実行を使うか迷う。どう意思決定する?
**A1**: 判定基準は「経路複雑度 vs 状態空間」。angr に適する:目標が明確(あるアドレス到達/あるアドレス回避)、経路分岐が爆発しない、大量のシステム対話がない純計算検証(crackme、シリアル番号検証)。この場合ソルバーに入力を探させるほうが手作業で逆に見るよりずっと速い。
**Q2**: angr が「爆発」(経路爆発/走りきれない)するのはどんな状況?
**A2**: ループ回数が多く入力に依存、hash/暗号がある(制約ソルバーは一方向関数を解けない)、大量のメモリ/システムコール対話、状態空間の指数膨張。強いハッシュ、長いループ、複雑なヒープ対話が見えたらシンボリック実行の力ずくの解を期待しない。
**Q3**: angr を使うと決めたが、長く走っても結果が出ない。どうする?
**A3**: 死なずに枝刈りする。find/avoid で対象アドレスと避ける失敗分岐を精確に指定、複雑だが無関係な関数(printf、複雑計算)を hook して具体値で代替、入口からでなく中間状態(blank_state)から始めて重要セクションだけをシンボル化する。ソルバーに本当に自分が関心を持つ小さなセクションだけを計算させる。
**Q4**: angr の道が確かに走れない。どうする?
**A4**: 人手/動的次元に戻る。シンボリック実行は万能ではない。爆発したら認める:動的ブルートフォース(入力空間が小さいとき)、手作業でアルゴリズムを逆に見る、または z3 で抽出した核心制約だけをモデル化する(全プログラムシンボリック実行より軽い)。「angr の結果を待つ」上で無限に耗やさない。
**Q5**: シンボリック実行と動的をどう組み合わせればより効率的か?
**A5**: 混合(concolic)。具体入力で重要分岐の前まで走らせ(動的/unicorn)、その状態からシンボリック実行に切り替えて最後のセクションだけを解く。または angr の unicorn エンジンで具体実行部分を加速する。「どの小さなセクションがシンボル化に値するか」を特定し、残りは具体値にするのが、大プログラム対策の正解である。
**Q6**: シンボリック実行が解いた入力がローカルで再現しない。どうする?
**A6**: モデルと実環境の差を検査する。angr の libc 関数、システムコール、stdin バッファのモデルが実機と異なる可能性。find/avoid アドレスが正しいか(PIE ベース)、入力注入方式(stdin vs argv)が一致するかを確認する。差を特定してから再解するか、実制約を動的に検証し直す。

### ネットワークサービス/デーモン型 pwn の特定差
**Q1**: 対象がネットワークサービス(ポートをリッスンする pwn)。ローカル問題と特定がどう違う?
**A1**: 入口が main から「接続処理関数」へ移る。まず socket/bind/listen/accept チェーンを特定し、accept 後に各接続を処理するその関数こそ本当の業務入口かつ攻撃面である。main のサーバー構築コードに脆弱性を探さない。脆弱性はネットワークデータを受信した後の解析にある。
**Q2**: サービスが fork モデル(接続ごとに fork で子プロセス)。利用にどう影響?
**A2**: fork 子プロセスは親と同一アドレス空間レイアウトを共有する(ASLR は fork 時に再ランダム化しない)。これは好材料:同一接続/複数接続で canary/アドレスをバイト単位にブルートフォースできる(毎回のクラッシュは子プロセスだけが崩れ、親プロセスのアドレスは不変)。fork モデルと特定すれば「canary/PIE のブルートフォース」の安定経路を解除できる。
**Q3**: ネットワークデータの解析入口をどう特定する?
**A3**: recv/read(接続 fd)から xref し、データフローを追う:buf に受信した後、どの parse 関数が処理するか。プロトコル解析には「長さフィールドを読む→長さに応じて body を読む」パターンがよくあり、その長さフィールドが制御可能で無界か(ネットワーク pwn の第一の穴は長さプレフィックスオーバーフロー)を重点監査する。
**Q4**: サービス型対象がローカルで起動できず、動的デバッグできない。どうする?
**A4**: ローカル再現環境の構築へ方向転換する。socat/自前 wrapper でサービスの stdin/stdout を socket に橋渡ししてローカルで走らせるか、gdb で accept 後の子プロセスに attach する(set follow-fork-mode child)。構築できなければ純静的特定 + リモートブラインド攻撃検証を先にする。これがネットワーク問題の必須の方向転換である。
**Q5**: マルチスレッドサービス(非 fork、共有ヒープ)の特定にどんな追加注意が要る?
**A5**: スレッド間競合と共有ヒープ汚染に注意する。マルチスレッド共有ヒープは、1 つの接続のヒープ操作が別に影響し、race condition や接続跨ぎの UAF があり得る。グローバル/共有の接続オブジェクト配列があるか、ロックが全アクセスを覆うか(競合窓が攻撃面)を特定する。
**Q6**: オーバーフローを特定したがリモートに canary があり、fork 時アドレスは変わるか?ブルートフォースすべきか?
**A6**: まず fork vs exec を確認する。純 fork(execve しない)→ アドレス不変で、canary/PIE のバイト単位ブルートフォースが可能なので、ブルートフォースする。fork+execve(再ロード)→ 毎回アドレスが再ランダム化され、ブルートフォース不可なので、真の leak を探さなければならない。サービスの再起動モデルを特定して、ブルートフォースか leak かを決める。これは方向性の意思決定である。

### Windows PE の入口と API 特定差
**Q1**: 対象が ELF でなく Windows PE。静的特定の入口に何の違いがある?
**A1**: 入口チェーンが違う:PE の AddressOfEntryPoint は CRT 起動コード(__scrt_common_main)を指し、それがさらに mainCRTStartup→main/WinMain を呼ぶ。GUI プログラムは WinMain、コンソールは main を探す。特定手法は ELF の main 探しに似るが、libc のではなく MSVC の CRT 起動モードを認識する。
**Q2**: PE に PLT がない。どの危険 API を呼んだかどう特定する?
**A2**: IAT(インポートアドレステーブル)を見る。PE のインポートは IAT にあり、kernel32/ntdll/user32 からインポートする API を列挙する。危険リスト:strcpy/sprintf/memcpy(CRT)、CreateProcess/WinExec/system(実行)、VirtualAlloc/VirtualProtect(RWX、shellcode)、CreateFile/ReadFile(IO)。IAT 項目に xref して呼び出し点を探す。
**Q3**: API が動的解決(GetProcAddress/LoadLibrary)で、IAT に見えない。どうする?
**A3**: GetProcAddress の文字列パラメータを特定して、どの API が解決されたか知る。悪意/パッカー付き PE はこれでインポートを隠すことが多い。LoadLibrary("xxx.dll")+GetProcAddress("API名") の対を探すと、その文字列が実呼び出しを暴露する。文字列も難読化されていれば動的に GetProcAddress の戻り箇所で掴む。
**Q4**: PE の防御(GS/DEP/ASLR/CFG)と Linux の対応関係、影響は?
**A4**: マッピング:GS≈Canary、DEP≈NX、ASLR は類似、SafeSEH/SEHOP は SEH 保護、CFG(Control Flow Guard)は間接呼び出し対象を制約する。特定時にまず PE ヘッダ/ロード設定ディレクトリでどれが有効か確認する。CFG 有効なら間接呼び出しの乗っ取りが制限されるので、ROP/SEH または CFG に守られない戻りアドレスへ方向転換する。
**Q5**: SEH 関連の利用/例外処理に出会った。どう特定する?
**A5**: 例外処理登録を特定する。32 ビットはスタック上の SEH チェーン(fs:[0])を見て、オーバーフローで SEH レコードを上書きして例外ハンドラを乗っ取れる(SafeSEH 無効時)。64 ビットはテーブルベースの SEH(.pdata/例外ディレクトリ)で、スタック上にないので、発想を別へ転じる。まずビット数と SEH 種別を確認してから戦略を定める。
**Q6**: 手元の Linux ツールチェーンが PE サポートが弱く、デバッグが難しい。どうする?
**A6**: Windows ネイティブツール/環境へ方向転換する。IDA/Ghidra はどちらも PE を静的に見られるが、動的デバッグは x64dbg/WinDbg + 本物の Windows か wine へ転じる。純 Linux 環境で詰まったら、PE 動的解析は必ず Windows 側へ戻る。gdb で PE を力ずくにデバッグしない。

### クラッシュ点から脆弱性のある関数を逆に特定する
**Q1**: 手当たり次第に異常入力を食わせてプログラムが落ちた。このクラッシュで脆弱性がどこかを逆算したい。どうする?
**A1**: クラッシュを「無料の脆弱性道標」として使う。クラッシュ時の pc/rip とスタックを見る:rip が不正アドレスに落ちる(特に入力バイトで埋まった値、0x4141...など)→ 制御フローは乗っ取られており、どの関数の戻り/間接呼び出しがそれを持ち去ったかを遡れば、そこがオーバーフロー/乗っ取り点である。クラッシュアドレスが特定範囲を直接縮小する。
**Q2**: クラッシュが rip を満杯に(全入力バイト)している。何を示し、次は?
**A2**: 戻りアドレスが制御可能であること、すなわちスタックオーバーフロー確定を示す。次は cyclic pattern でオフセットを精確に特定する(rip の値を pattern に逆引きして padding 長を得る)。クラッシュから直接「オフセット計算」段階にジャンプし、静的にオーバーフロー点を監査する手間を省く。
**Q3**: クラッシュが rip でなくあるメモリアクセス(不正アドレス読み/書き)にある。どう解釈する?
**A3**: それはデータポインタが汚染されたのであって戻りアドレスではない。クラッシュ命令が `mov [reg], ...`(不正書き)か `mov ..., [reg]`(不正読み)か、reg の値に入力バイトが含まれるかを見る。reg がどう来たかを遡る → 汚染されたポインタ/インデックス(OOB か UAF の懸空ポインタ)を特定し、脆弱性種別も判明する。
**Q4**: coredump があるがソース/シンボルがない。どう最大化して利用する?
**A4**: core を gdb + バイナリにロードし、完全な現場を見る:レジスタ、スタック遡及(bt)、クラッシュ点近傍メモリ。stripped でも、スタックに残る戻りアドレスチェーンが呼び出し経路を再構築でき、最後の正常フレームと最初の破壊フレームの間を特定する。脆弱性はその関数内にある。
**Q5**: 「差分クラッシュ」でどの入力バイトが発火したかにどう絞る?
**A5**: 入力を二分する。正常入力は落ちず、ある異常入力は落ちる。二分法で徐々に迫る:入力のどのセグメントを変えるとクラッシュするか、そのセグメントが対応する解析ロジックに影響する。毎回のクラッシュの rip/エラーアドレス変化と合わせて、その入力フィールドを処理する具体関数を特定する。曖昧な「プログラムが落ちた」を「第 N バイトがどの関数に入ったか」に変える。
**Q6**: クラッシュがどうしても再現できない/不安定。どうする?
**A6**: クラッシュの道は信号が弱すぎるので、**能動的な静的監査 + 有向 fuzz**へ方向転換する。待ち伏せしない:危険 sink から静的で能動的に穴を探すか、カバレッジ誘導 fuzzer(AFL++/libFuzzer)で系統的にクラッシュを発生させ、発火経路を自動記録する。散発的な手動クラッシュが信頼できないとき、系統的な fuzz が直交する昇格である。
