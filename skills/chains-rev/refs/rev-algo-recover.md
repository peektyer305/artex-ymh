# リバースエンジニアリング PWN · アルゴリズム/暗号化復元の考え方

### バイナリを手にした最初の一歩:まずエントロピーを測り、ローディングを見て、急いでデコンパイルしない
**Q1**: 手元に未知の ELF/PE があり、平文ロジックなのかパック/暗号化なのか分からない。最初にどう意思決定するか?
**A1**: 急いでデコンパイラに投げ込まない。まずコストゼロの偵察を行う:`file`/`strings`/`binwalk`、それから全体と `.text` をそれぞれエントロピー測定する。エントロピーが 8 に近く入口セクションが極小 = パックまたは自己解凍。エントロピーが中程度で可読文字列が大量にある = 平文ロジックで、そのまま静的解析へ。判定基準は「エントロピー勾配」:パッカーの特徴は「小さな解凍スタブ + 高エントロピーの大きな blob」。
**Q2**: エントロピーが非常に高いのに `strings` で多くのライブラリ関数名が見える。矛盾している?
**A2**: データセクション/リソースだけが暗号化されていて、コードセクションにはパッカーがかかっていないことを示す。この種の対象はアルゴリズムロジックが平文コード内にあり、暗号化されているのは定数テーブル(S-box、鍵、flag の暗号文)だけであることが多い。コードのデコンパイルを優先し、高エントロピーの blob は「復号待ちデータ」としてマークして、アンパックに時間を浪費しない。
**Q3**: パッカーがかかっていると確認した。自分でアンパックするか、そのまま力ずくで読むか?
**A3**: まず既知のパッカーを調べる(UPX/themida/vmprotect の特徴セクション名、`upx -d` で試しアンパック)。既知のパッカーに既存ツールがあるなら手作業しない。判定基準:アンパックに費やす時間は総予算の 20% を超えるべきではない。
**Q4**: アンパックの道が塞がれた(アンチデバッグ + 変形パッカーで、きれいな dump が取れない)場合はどうする?
**A4**: 直交する次元へ方向転換:アンパックせず、実行時に取得する。パッカーは最終的に平文コードをメモリに展開して実行するため、OEP ブレークポイント / メモリブレークポイントで解凍完了の瞬間に dump するか、直接主要 API(暗号化・復号/比較関数)を hook して平文の中間値を取得し、静的解析でアルゴリズムを復元する袋小路を迂回する。
**Q5**: 動的解析もアンチデバッグで完全に止められた?
**A5**: もう一段方向転換する:痕跡を残さない動的手法に切り替える。QEMU/Unicorn で全システムまたは関数レベルのエミュレーション実行をするか、DBI(Frida/Pin)で ring3 層を hook して、デバッガ向けの検知を回避する。アンチデバッグは通常 `ptrace`/デバッグポートを検知するが、エミュレーション実行はこれらを発火させない。

### 暗号アルゴリズムの識別:まず「マジックナンバー定数」を認め、次に構造を認める
**Q1**: 暗号化と思われるループをリバースエンジニアリングで見つけた。それがどの標準アルゴリズムかを素早く判断するには?
**A1**: まずマジックナンバー定数を走査する。`0x67452301`/`0xefcdab89` が見えれば MD5/SHA1 の初期化ベクトル、`0x6a09e667` は SHA256、`0x9e3779b9` は TEA/XXTEA の delta、AES には固定の S-box/T-box がある。findcrypt/yara ルールで一気に判定する。定数はアルゴリズムの身分証明書である。
**Q2**: 目立つ定数はないが、構造がブロック暗号に似ている?
**A2**: ラウンド構造を見る。16 ラウンド + 各ラウンドで左右半ブロック交換 = Feistel(DES/TEA 系)。10/12/14 ラウンド + バイト置換+行シフト+列混合 = AES。大量のモジュロ加算、巡回シフト、XOR の混合が見えれば = ARX 構造(ChaCha/Salsa/RC5)。ラウンド数を数えることと半ブロック交換を見ることが最速の判定基準である。
**Q3**: 定数が改変されている(魔改造アルゴリズム)場合はどうする?
**A3**: 変わらない骨格に注目する。魔改造は通常 S-box、初期化ベクトル、ラウンド数、delta だけを変更し、全体のデータフローは変わらない。まず標準アルゴリズムの枠組みで注釈を付け、それから変更点を逐点 diff する。判定基準は「構造の保存」:定数を変えるのは容易だが、データフロー構造を変えるのはコストが大きく、攻撃者は普通そこまでしない。
**Q4**: アルゴリズム識別の道が完全に行き詰まった(純粋な自前難読化アルゴリズムで、どの標準にも対応しない)場合はどうする?
**A4**: 「識別」を諦めて「ブラックボックスモデル化」へ方向転換する。それが何のアルゴリズムかは気にせず、暗号化関数をブラックボックスとして扱う。key を固定して平文を変えながら暗号文の関係を観察し、雪崩効果、ストリーム暗号かどうか(バイトごとに独立か)、交換可能かどうかをテストする。「暗号文の i バイト目が平文の i バイト目だけに依存する」と分かれば = バイトごとのマッピングであり、直接マッピングテーブルを作ってブルートフォースすれば、アルゴリズムを理解する必要はまったくない。
**Q5**: ブラックボックスで拡散があると分かった(1 バイト変えると全体が変わる)?
**A5**: 代数/シンボル解析へ方向転換する。angr/シンボリック実行で暗号化関数を記号化するか、可逆アルゴリズムなら直接逆関数を探す。拡散はあるが可逆な自前アルゴリズムは、シンボリック実行が自動で逆関数を求められることが多い。

### CTF リバースエンジニアリング:check 関数を見つけるのが本当の出発点
**Q1**: crackme で flag を入力して正誤を判定する。デコンパイルは数千行ある。どこから切り込む?
**A1**: `main` を頭から読まない。リバースエンジニアリングではアンカーポイントを探す。"Correct"/"Wrong"/"成功" などの文字列を相互参照するか、`puts`/`printf` が成功メッセージを出力する位置を探し、判定分岐まで逆方向にたどる。判定分岐の上流が check ロジックである。判定基準:「結果」から逆算するほうが「入口」から順に追うより 1 桁速い。
**Q2**: 文字列が暗号化されていて、"Correct" を検索できない?
**A2**: アンカーポイントを替える。`strcmp`/`memcmp`/独自比較関数を探すか、プログラムの終了コードの分岐(`exit(0)` vs `exit(1)`)を探す。比較関数の 2 つのパラメータは、一方がユーザー入力を変換した値、もう一方が対象値であり、対象値が解く鍵であることが多い。
**Q3**: check を見つけたが、それが大量の制約の塊(各桁が相互に関係する)だった?
**A3**: 手計算しない。これは典型的な SMT の場面である。z3/angr で各制約を方程式に翻訳して、ソルバーに解かせる。判定基準:制約が「決定的な可逆演算 + 最終的な等価比較」なら → 必ずシンボリックに解ける。
**Q4**: angr のシンボリック実行で状態爆発 / 実行しきれない場合はどうする?
**A4**: 「負荷軽減」戦略へ方向転換する。① `hook` で高コストなライブラリ関数(printf、sleep など)をスキップする。② 純粋な check 関数だけを手作業で抽出して z3 に単独で与え、angr にプログラム全体を走らせない。③ 制約に境界を付けて(flag の可視文字 0x20-0x7e)枝刈りする。それでも駄目なら、動的 patch のブルートフォースへ方向転換する。
**Q5**: シンボリック実行の道が完全に塞がれた(check にハッシュ/不可逆演算がある)?
**A5**: 次元を変える。不可逆なら求解できず、ブルートフォースかバイパスしかない。バイトごとに独立してハッシュしてから比較するなら、バイト単位でブルートフォース(1 バイトあたり 256 回)する。全体ハッシュが不可逆なら、情報リーク(長さ、部分平文のヒント)がないか探すか、実装の脆弱性攻撃へ方向転換する(「アルゴリズムを諦めて実装攻撃へ」参照)。

### 静的と動的の併用:静的で行き詰まったら動的で確認する
**Q1**: 静的解析である変換関数を見たが、ロジックが複雑で何を計算しているのか分からない。どうする?
**A1**: 静的解析に固執しない。動的検証に移る。ブレークポイントを張り、既知の入力を与え、レジスタ/メモリを直接読んで入出力の対応関係を見る。関数が理解できないとき、「既知の値を与えて結果を観察する」ほうがアセンブリを 1 命令ずつ読むよりずっと速い。判定基準:純粋な変換関数で重要なのは I/O マッピングであり、過程ではない。
**Q2**: 関数にグローバル状態/副作用があり、単一のブレークポイントでは全体が見えない?
**A2**: trace を使う。Frida/DBI で関数の毎回の呼び出しの入出力パラメータを記録するか、`ltrace`/独自 hook で出力する。複数回の呼び出しの I/O 系列はステートマシンの挙動(ストリーム暗号の keystream の進行など)を露呈させる。
**Q3**: 対象がアンチデバッグ付きで、ブレークポイントを張るとすぐ終了する?
**A3**: 対抗へ方向転換する。まずアンチデバッグのポイント(`ptrace(PTRACE_TRACEME)`、`/proc/self/status` での TracerPid 読み取り、時間差検知)を特定し、patch するかプラグイン(ScyllaHide 系)で隠す。判定基準:アンチデバッグは「一度きりの検査」であることが多く、検査ポイントの戻り値を patch するのが最も手軽である。
**Q4**: アンチデバッグが多すぎて patch しきれない(複数箇所 + 自己チェックサム)?
**A4**: 実行環境を変える。Unicorn/QEMU で対象関数をエミュレーション実行し、必要なメモリセグメントとレジスタだけを初期化して、そのアルゴリズム部分を単独で動かす。エミュレータは本物のデバッガではないため ptrace 検知を発火させず、中間状態も任意に読み取れる。
**Q5**: 関数が外部環境に依存しすぎていて、単独でエミュレーションするために抽出できない?
**A5**: さらに方向転換する。全システムエミュレーション(プロセス全体を QEMU user mode で動かす)+ エミュレーション層での hook を使う。完全な環境がありつつ痕跡を残さず観測できるため、関数を抽出できないときの最終手段となる。

### PWN:まず保護を確認してから攻撃面を決める
**Q1**: PWN 問題のバイナリを手にした。最初の意思決定は何か?
**A1**: `checksec` で保護を確認する。NX/Canary/PIE/RELRO の 4 点セット。保護の組み合わせが直接攻め方を決める。NX なし → shellcode。NX あり PIE なし → ret2libc/ROP の固定アドレス。全開 → リーク + 精緻な ROP が必要。判定基準:保護が攻撃の「予算」を決める。まず計算してから手を付ける。
**Q2**: 保護が全開。突破口をどこに探す?
**A2**: 脆弱性プリミティブを探す。「アドレス」を探さない。まず制御可能なポイントを特定する。スタックオーバーフロー?ヒープの UAF/overflow?フォーマット文字列?フォーマット文字列は全開時の万能薬で、同時にリーク(PIE/Canary 迂回)と任意書き込みができる。判定基準:全開時は「情報リーク + 任意書き込み」の二重プリミティブを持つ脆弱性を優先して探す。
**Q3**: オーバーフローが 1 つだけで、リーク手段がなく、PIE が有効でベースアドレスが分からない?
**A3**: 部分上書きを探す。PIE では下位 12 ビットが固定なので、戻りアドレスの下位バイトだけを上書きして局所ジャンプ(one gadget / 重要分岐)ができる。またはプログラム自身の puts/write で一度リークしてから 2 回目に進む。判定基準:リークがないときは「ページ内オフセットは不変」という不変量を使う。
**Q4**: ROP チェーンに必要な gadget が揃わない場合はどうする?
**A4**: libc へ方向転換する。プログラム自身の gadget は少ないが、libc には何でも揃っている。libc のアドレスを 1 つリークしてベースアドレスを計算したら、libc の gadget、`system`、one_gadget を使う。判定基準:静的 gadget が足りなければ「libc 全集を導入する」。
**Q5**: サンドボックス(seccomp)が execve を禁止し、ret2libc で shell を取る道が塞がれた?
**A5**: syscall の次元へ方向転換する。seccomp は通常一部の呼び出しだけを禁止する。`open/read/write` の ORW チェーンで直接 flag ファイルを読むか、許可された `mmap`+shellcode、`openat` を使う。まず seccomp-tools でルールを dump し、どの番号が許可されているかを見て、許可された呼び出しに沿って攻撃チェーンを再構築する。

### ヒープエクスプロイト:まず glibc のバージョンを判定してから攻め方を選ぶ
**Q1**: ヒープ問題で、どのヒープエクスプロイト手法を使うか決める前に何を確認すべきか?
**A1**: まず glibc のバージョンを確認する。バージョンがどの手法を使えるかを決める。tcache は 2.26 で導入、2.29+ には double free を防ぐ tcache key、2.32+ には safe-linking(ポインタ暗号化)がある。判定基準:ヒープ手法には「バージョン窓」があり、バージョンを間違えると必ず失敗する。まず `strings libc | grep GLIBC` するか、問題が与える libc を見る。
**Q2**: 対象の glibc が非常に新しく、古い手法(unsorted bin attack、fastbin dup)がすべて禁止されている?
**A2**: 新版の汎用手法へ方向転換する。house of 系(botcake、apple2 など)、tcache stashing、そして `__free_hook`/`__malloc_hook` が削除された後は IO_FILE(FSOP、`_IO_2_1_stdout_` house of 系)を攻める。判定基準:新 glibc では hook がなくなり、攻撃面は IO_FILE と largebin に移る。
**Q3**: safe-linking のせいで偽造した fd ポインタが合わない?
**A3**: まずヒープアドレスをリークして暗号化 key(`pos >> 12`)を計算し、それから対象アドレスを `ptr ^ (pos>>12)` で暗号化して書き込む必要がある。判定基準:safe-linking は迂回できないのではなく「chunk があるページのアドレスを先に知る必要がある」ので、まずヒープアドレスのリークを行う。
**Q4**: リークプリミティブがまったくなく、ヒープアドレスも libc も分からない?
**A4**: 「リークなし」の攻め方へ方向転換する。partial overwrite(下位バイトの部分上書き)を使うか、ヒープレイアウトの決定性(largebin/unsorted bin に残る main_arena ポインタによる相対書き込み)を使う。判定基準:リークがないときは「残留ポインタ + 部分上書き」で最初のリークを作り出す。
**Q5**: 問題が割り当て回数/サイズを制限していて、手法を展開できない?
**A5**: 発想を変える。chunk overlapping / off-by-one(null byte)で重なりを作り、1 つの穴を複数のプリミティブに増幅して、割り当て回数制限を突破する。サイズが制限されているなら unsorted bin の切り出しで必要なサイズを構成する。

### VM リバースエンジニアリング:まず命令セットを復元してからバイトコードを翻訳する
**Q1**: バイトを取り出して実行する巨大な switch/ループをリバースエンジニアリングで見つけ、VM 保護と判断した。どう着手する?
**A1**: VM の構造を確認する。①バイトコード配列(操作データ)②dispatcher(フェッチ-デコード-実行ループ)③仮想レジスタ/スタック(VM コンテキスト)を見つける。1 命令ずつ読まず、まず handler テーブルを「この opcode は何をするか」へ逐個リバースエンジニアリングし、VM 命令セットのドキュメントを作る。判定基準:VM リバースエンジニアリングの本質は「逆アセンブラを書くこと」であり、先に ISA を構築してからロジックを論じる。
**Q2**: handler が数十個あり、リバースエンジニアリングが非常に遅い?
**A2**: 高頻度の opcode を優先してリバースエンジニアリングする。まずバイトコード実行を trace して、どの handler が呼ばれるか統計し、中核の算術/比較/ジャンプを先にリバースエンジニアリングし、使用頻度の低いものは進めながら補う。判定基準:ロジックの 80% は 20% の opcode が担う。
**Q3**: 各 handler に追加の難読化(ジャンクコード、間接ジャンプ)が施されている?
**A3**: 動的へ方向転換する。静的に難読化された handler を読むより、各 opcode 実行前後の VM コンテキストの変化(レジスタ/スタック)を trace し、挙動から意味を逆算する。判定基準:難読化されているのは形式であり、I/O 挙動は欺けない。
**Q4**: VM が VM を入れ子にしている(多層仮想マシン)ので、リバースエンジニアリングできない?
**A4**: 次元を変える。VM を復元せず、直接データフローを trace する。入力を与え、VM 内部がユーザー入力に対して実際にどのような算術操作をしたかを記録し、VM をブラックボックスとして「入力→出力」の等価演算を抽出し、その等価演算をシンボリックに求解する。多層 VM は定数因子を増幅するだけで、等価演算は多くの場合とても単純である。
**Q5**: trace さえもアンチデバッグ/自己書き換えで動かない?
**A5**: さらに Unicorn エミュレーションへ方向転換する。dispatcher + バイトコードメモリだけをエミュレーションし、VM を純粋なエミュレーション環境で動かし、インスツルメントして各 opcode を記録する。エミュレーション層は完全に制御可能で、自己書き換えとアンチデバッグを迂回できる。

### 難読化対策:難読化の種別を識別してから対症的に難読化解除する
**Q1**: デコンパイル結果が無意味なジャンプ、恒真判定、ごみ計算ばかり。どう系統的に難読化解除する?
**A1**: まず難読化の種別を分類する。制御フロー平坦化(1 つの主ディスパッチブロック + 大量の状態)、偽制御フロー(不透明述語)、命令置換(単純な演算を複雑な等価式に置換)、ジャンクコード。種別ごとに対応するツールが異なる。平坦化は deflat/シンボリック実行で CFG を復元し、不透明述語はテイント/求解で恒真を証明してから削除する。判定基準:先に分類し、ごちゃ混ぜのまま力ずくで読まない。
**Q2**: 制御フロー平坦化でロジックがステートマシンに分解され、元のフローが読めない?
**A2**: 真の後続を復元する。状態ディスパッチ変数を識別し、シンボリック実行で各真ブロック実行後の次の状態値を確定し、元の CFG を再構築する。ツールチェーン(D-810、miasm、angr スクリプトなど)で自動化できる。判定基準:平坦化は CFG の辺を隠しているだけであり、状態変数の値が真の辺を決める。それを求解すれば復元できる。
**Q3**: 不透明述語が多すぎて、自動ツールが誤削除や削除漏れを起こす?
**A3**: 局所的な動的検証へ方向転換する。疑わしい分岐に対し、動的に複数組の入力で常に片側だけ通るかを観察し、恒定的なら偽分岐である。判定基準:不確かな静的判断は動的サンプルで反証するのが最も信頼できる。
**Q4**: 難読化が商用プロテクト(VMP/Themida の変形など)で、自動難読化解除がすべて無効?
**A4**: 「難読化解除」を諦めて「復元の迂回」へ方向転換する。対象アルゴリズムが具体的な入力に対して実際に計算した軌跡だけを trace し(ユーザー入力の動的テイント追跡)、軌跡から意味を抽出して、難読化された完全なコードは復元しない。判定基準:難読化解除は「全部を復元する」ことで、問題を解くには「重要なデータフローを復元する」だけでよく、後者のコストは 1 桁低い。
**Q5**: 動的軌跡さえ自己書き換え/ポリモーフィズムに妨害されて見えない?
**A5**: さらに次元を下げる。注目点を「ユーザー入力バイト」の伝播に絞り、シンボル/テイントでこの数バイトが関与する演算だけを追い、無関係な難読化コードはすべて無視する。ポリモーフィック難読化が変えるのは無関係なコードであり、テイントスライスがそれらをフィルタリングできる。

### 暗号の誤用:アルゴリズムを力ずくで破る前に実装の弱点を探す
**Q1**: 対象が標準の強アルゴリズム(AES/RSA)を使っており、力ずくで破るのは不可能。まだ望みはあるか?
**A1**: ある。アルゴリズムを破らず「使い方」を破る。チェックリストを列挙する。ECB モードか?IV が固定/予測可能か?nonce の再利用か?弱い鍵/鍵のハードコードか?padding oracle か?判定基準:実戦では暗号はほぼすべて「誤用」で死ぬのであって「アルゴリズム自体」ではない。まず使い方を監査する。
**Q2**: AES-ECB だと分かった?
**A2**: ECB に拡散がないことを利用する。同じ平文ブロック→同じ暗号文ブロック。バイト単位のブルートフォース(バイトごとに位置合わせしてリークする ECB byte-at-a-time)ができ、または繰り返しブロックを識別して構造を推測できる。判定基準:ECB は平文パターンをリークし、それ自体が脆弱性である。
**Q3**: CBC で、サーバーが padding の正誤を教えてくれる?
**A3**: padding oracle を使う。パディング検証の差分フィードバックを利用して、バイト単位で復号/暗号文を偽造する。鍵はまったく不要。判定基準:あらゆる「暗号文操作 + 有効かどうかの観測可能なフィードバック」が oracle になり得る。
**Q4**: アルゴリズムの使い方に問題が見当たらず、標準 AES の正しいモードで、この道が塞がれた?
**A4**: 鍵の出所攻撃へ方向転換する。鍵はどう作られたか。ハードコードか?弱い PRNG(rand() のシード未設定、時間シード)から導出か?予測可能なデータからの KDF か?アルゴリズムがどんなに強くても、鍵が予測可能ならすべてが無に帰す。攻撃面を「暗号文」から「鍵生成」へ移す。
**Q5**: RSA で、明らかな小さな指数/共通モジュラスなどの古典的弱点がない?
**A5**: パラメータ解析へ方向転換する。n は分解可能か(ビット数が小さい、Fermat 近似素数、factordb などの既知因子データベース)。e と φ の関係はどうか。秘密鍵の一部ビットが既知か。padding が生のパディングなし(準同型操作が可能)か。判定基準:RSA の攻撃面は「パラメータ選択」にあり、既知攻撃の前提条件を逐一照合する。

### 自前ハッシュ/チェックサムの復元:衝突と原像の選択
**Q1**: 入力が自前 hash で処理された後に定数と比較される。hash は不可逆。どうする?
**A1**: まず「原像」が必要か「衝突」が必要かを判断する。正確な入力を復元しなければならないなら → 原像を探す。チェックサムを通すだけでよいなら → 任意の衝突を探せばよく、後者のほうがはるかに容易なことがある。判定基準:まず「本当に実入力が必要なのか」を問う。多くのチェックサムは衝突だけでよい。
**Q2**: hash の出力空間が小さい(たとえば 32 ビットだけ残す)?
**A2**: 直接ブルートフォースする/レインボーテーブルを作る。出力空間が 2^32 以内なら、GPU/マルチスレッドでのブルートフォースが可能。判定基準:自前 hash は手間を省くために出力を切り詰めることが多く、切り詰めはすなわち弱体化。まず出力ビット幅を見る。
**Q3**: バイト単位の独立ハッシュ(各文字を個別に hash してから連結する)?
**A3**: 分割統治する。バイト単位で独立なら 256 空間のマッピングなので、位置ごとにテーブルを作って逆引きすれば即座に解ける。判定基準:独立性 = 分解可能。必ず先に雪崩効果をテストしてバイト間の結合の有無を見る。
**Q4**: hash が強い拡散を持ち、出力が広く、原像が必須で、ブルートフォースの見込みがない。この道は死んだ?
**A4**: 構造攻撃へ方向転換する。自前 hash には代数的な弱点がよくある。線形/アフィン構造(純粋な XOR シフト)なら → 線形方程式系を立ててガウス消去で解く。周期/不動点があれば → それを利用する。判定基準:不可逆 ≠ 構造なし。自前アルゴリズムの作者が暗号学的強度に到達していることはまれなので、線形成分を探す。
**Q5**: 構造攻撃さえ手が出ない(ロジックが非線形で出力も広い)?
**A5**: 制約の出所を変える。問題の文脈に戻ってバイパスを探す。長さのリークがあるか、部分平文が既知か(フォーマットのプレフィックス)、複数の関連暗号文で差分が取れるか。hash 求解問題を「既知制約付きの探索」に変換し、制約でブルートフォース空間を大幅に枝刈りする。

### 鍵/定数の抽出:まず動的に dump してから静的に位置特定する
**Q1**: アルゴリズムロジックは分かったが、鍵/暗号文は実行時に復号されるため、静的に見ると文字化けしている。どう取得する?
**A1**: 動的に dump する。鍵が使われる瞬間(暗号化関数に渡される前など)にブレークポイントを張り、メモリを直接読んで平文の鍵を取得する。判定基準:どんなに強い定数暗号化でも、使用時点では必ず平文になる。「使用点」で待ち伏せする。
**Q2**: 鍵がメモリのどのアドレスにあるか分からない?
**A2**: 逆方向に位置特定する。まず暗号化関数を探し(アルゴリズム識別による)、その key パラメータが鍵を指す。または鍵らしきメモリ領域にメモリアクセスブレークポイントを張り、それを読むものが暗号化ロジックである。判定基準:「アルゴリズムが key を使う」ことから key の位置を逆算する。
**Q3**: 鍵が使い終わると即座に消去される(anti-dump)ので、ブレークポイントが遅れると消える?
**A3**: 事前に hook する。鍵を復号する関数の戻り地点、または鍵がメモリに書き込まれる瞬間にブレークする。メモリ書き込みブレークポイントで「鍵が出現した直後」を捉え、「鍵が使われた後」ではない。判定基準:消去されるのは使用後なので、生成時を捉える。
**Q4**: 全行程でアンチデバッグ + 消去があり、動的 dump の道が塞がれた?
**A4**: エミュレーション実行へ方向転換する。Unicorn で「鍵復号関数」を単独で動かし、入力側でその静的暗号文定数を読み、出力側が平文の鍵になる。全行程デバッガなし、消去の妨害なし。判定基準:鍵復号は純粋関数なので、抽出してエミュレーションするのが最もきれいである。
**Q5**: 鍵がハードウェア/環境(マシンコード、時刻、外部入力)に依存し、オフラインで再現できない?
**A5**: 対象を変える。鍵を抽出せず、「鍵使用後の結果」を抽出する。環境依存の鍵が取得できないなら、対象環境内で hook して最終的な復号産物(平文データ)を取得し、鍵そのものを迂回する。判定基準:必要なのがデータであって鍵でないときは、直接データを掴む。

### ホワイトボックス暗号:鍵ではなくルックアップテーブルを攻める
**Q1**: ホワイトボックス AES(鍵がルックアップテーブルに溶け込み、メモリに生の鍵がまったくない)に出会った。どうする?
**A1**: 鍵を探さない。それは T-box に符号化されている。実装攻撃へ方向転換する。優先して DCA(差分計算解析)を試す。サイドチャネルのようにルックアップテーブルのアクセス軌跡を採取し、統計解析で鍵を復元する。テーブル構造の理解は不要。判定基準:ホワイトボックスの鍵はテーブル内に隠れているが、「計算過程は依然として情報をリークする」。
**Q2**: DCA が通じなかった?
**A2**: DFA(差分故障解析)へ方向転換する。最後の数ラウンドで故障を注入し(中間値を patch)、正しい/誤った暗号文のペアで差分を取って鍵を特定する。判定基準:ホワイトボックス実装は故障注入を防ぎにくく、DFA は古典的なホワイトボックス解読手段である。
**Q3**: サイドチャネルをやりたくない。このホワイトボックスを oracle として直接使えるか?
**A3**: 使える。実務的な路線として、目的が単に「この鍵で特定データを暗号化・復号する」ことなら、鍵を抽出する必要はまったくなく、このホワイトボックス関数をブラックボックスの暗号化・復号マシンとして直接呼び出す/エミュレーションすればよい。判定基準:多くの場合、鍵は必要なく、その機能だけが必要である。
**Q4**: ホワイトボックスにさらに外部符号化(入出力が追加で難読化)が重なっていて、DCA/DFA がすべて無効?
**A4**: 構造解析で符号化を剥がす方向へ転換する。まず入出力の符号化変換(通常はバイト単位の全単射)をリバースエンジニアリングし、剥がしてから内側の標準ホワイトボックスに DCA を施す。判定基準:外部符号化は「包装層」なので、まず包装を外してから核心を攻める。
**Q5**: 解析コストが高すぎ、時間が足りず、上記をすべて諦める場合はどうする?
**A5**: 「機能再利用」に格下げする。ホワイトボックスモジュール全体をその文脈ごと自分の環境に移し、暗号化・復号のブラックボックスとして呼び出し、復元を完全に諦めて、工学的な手段で解析時間と交換する。これは行き詰まったときの最終的な方向転換である。

### サイドチャネル思考:ソフトウェア層でも使える
**Q1**: パスワード検証関数が文字単位で比較し、間違うと早期リターンする(短絡比較)。利用できるか?
**A1**: 利用できる。これは時間サイドチャネルである。正しいプレフィックスが長いほど、関数の実行時間が長くなる。応答時間の差で文字単位にパスワードをブルートフォースする。判定基準:あらゆる「早期リターン + 測定可能な所要時間/回数」の比較は情報を漏らす。
**Q2**: 時間差が小さすぎて測定できない?
**A2**: 信号を増幅する。ローカル環境で命令カウント(インスツルメントして実行命令数を統計)、キャッシュヒット、または patch で毎回の比較を遅くして差を増幅する。判定基準:サイドチャネルが通らないのは往々にして S/N 比の問題なので、増幅するか、より安定した観測量(命令数は壁時計時間より安定)に替える。
**Q3**: 対象がリモートサービスで、ネットワーク遅延しかない?
**A3**: 複数回サンプリング + 統計で、大量に反復して分位数を取ってネットワークの揺らぎをフィルタリングするか、時間以外のサイドチャネル(エラーコードの差、応答パケット長、メモリ/リソース消費の差)を探す。判定基準:リモートの時間チャネルはノイズが大きいので、「決定的」なバイパス(状態コード/長さ)を優先して探す。
**Q4**: 比較が定数時間実装(memcmp_const)で、時間サイドチャネルが塞がれた?
**A4**: 他のサイドチャネル次元へ方向転換する。定数時間は時間しか防いでおらず、消費電力/キャッシュ/故障は防いでいないかもしれない。ソフトウェアの場面では DFA(故障注入で中間値を patch)へ、または上流攻撃(パスワードがどう生成されたか、別のリーク点がないか)へ転換する。判定基準:1 つのサイドチャネルが塞がれたら、直交する物理/論理サイドチャネルに替える。
**Q5**: すべてのサイドチャネルが封じられた?
**A5**: メインチャネルに戻る。サイドチャネルは「直接の脆弱性がないときの迂回」であり、対象のサイドチャネル対策が完璧なら、論理脆弱性を探すべき時である。認証フローそのものを再監査し(論理迂回、型混同、ステートマシン欠陥)、サイドチャネルに固執しない。

### アルゴリズムを諦めて実装攻撃へ
**Q1**: アルゴリズム自体の復元コストが極めて高い(強難読化 + 強アルゴリズム)ので、費用対効果が非常に悪い。続けるべきか?
**A1**: 立ち止まって再評価する。レッドチームの目的は「効果の達成」であって「完璧なリバースエンジニアリング」ではない。自分に問う:必要なのはアルゴリズムの理解か、それともある結果を得ることか。後者なら実装攻撃へ方向転換し、論理脆弱性、迂回点、再利用可能な機能モジュールを探す。判定基準:リバースエンジニアリングのコスト > 対象の価値になったら、即座に方向転換する。
**Q2**: 実装層の迂回点をどう探す?
**A2**: 境界を監査する。認証/検証前後の状態、エラー処理分岐、未初期化パス、整数オーバーフローによる制御フロー変更、TOCTOU。強アルゴリズムはしばしば弱い呼び出しロジックに囲まれており、脆弱性は「アルゴリズムの外側のグルーコード」にある。判定基準:アルゴリズムが強いほど、作者は周辺の工学的品質を軽視しがちである。
**Q3**: 実装もかなり厳密で、目立つ論理的な穴がない?
**A3**: 再利用へ方向転換する。対象の暗号化・復号/検証モジュールをコンポーネントとして直接呼び出し(その関数を動的ロードするか、全体を動かして入力を与える)、代わりに働かせる。理解は不要。判定基準:呼び出せるなら復元しない。
**Q4**: モジュールの依存が重すぎて単独で呼び出せず、再利用も塞がれた?
**A4**: データフローの最小スライスへ方向転換する。「自分が関心を持つ数バイトの入力」だけを動的テイント追跡し、それらが経由する等価演算(往々にしてアルゴリズム全体よりはるかに単純)を抽出し、この小さなスライスを求解する。判定基準:全体が解けないこと ≠ 関心のある部分問題が解けないこと。
**Q5**: スライスさえ解析妨害で取得できない?
**A5**: 最後はインテリジェンス/サプライチェーンの次元へ方向転換する。このアルゴリズム/protection は第三者の商用/オープンソースライブラリではないか。バージョンを検索し、公開解析を探し、同種の過去の writeup や既知の弱点を探す。誰かがとっくに解読しているものを真空状態で力ずくにリバースエンジニアリングしない。判定基準:行き詰まったらまず「既知の車輪ではないか」を確認する。

### 差分解析:入力を構成して出力を観察する
**Q1**: 暗号化関数がブラックボックスだが任意に呼び出せる。その性質を素早く把握したい。どんな入力を送る?
**A1**: 系統的な差分テストを行う。①全ゼロ平文 → 暗号文のベースラインを見る。②単一ビット反転 → 雪崩範囲(どの暗号文ビットが変わるか)を見る。③同じ平文を 2 回 → 決定性の有無(ランダム IV/nonce の有無)を見る。④平文を増分 → 線形/カウンタ構造の有無を見る。判定基準:少数の注意深く構成した入力でアルゴリズム族の属性を測れる。
**Q2**: 単一バイトの変更が暗号文の局所にしか影響しないと分かった?
**A2**: ブロック境界を特定する。拡散範囲がブロックサイズと構造を明かす。局所的な影響 = 弱拡散 = ブロック単位の攻撃/マッピングテーブル作成が可能。判定基準:雪崩範囲が攻撃の粒度を直接教える。
**Q3**: 同じ平文でも毎回暗号文が異なると分かった?
**A3**: 乱数源を探す。IV/nonce/salt がある。それが暗号文と一緒に与えられるか(制御可能か)、再利用されるか(nonce 再利用は致命的弱点)、予測可能かを検査する。判定基準:ランダム化は安全と同義ではない。重点は乱数源の品質検査である。
**Q4**: 差分がすべてランダムで、利用できる規則性がまったくない。この道は塞がれた?
**A4**: 強アルゴリズムの正しい実装であることを示す。鍵/実装攻撃へ方向転換する(前述のチェーン参照)。ブラックボックス差分が強アルゴリズムに効かないのは正常なので、テストを続けず、鍵の出所、モードの誤用、サイドチャネルなど直交する面へ移る。判定基準:ブラックボックス差分は「弱アルゴリズム」を篩い分けるもので、篩い出せなければ戦場を変える。
**Q5**: 任意に呼び出せない(有限の既知平文・暗号文ペアしかない)?
**A5**: 既知平文攻撃の枠組みへ方向転換する。有限の平文・暗号文ペアのもとで、疑われるアルゴリズム族に対応する既知攻撃(線形/差分解読の既知前提、ストリーム暗号の keystream 復元)を適用する。判定基準:サンプルが制限されているときは「能動的な探査」から「既存サンプルの受動的解析」へ移る。

### ビット演算のリバースエンジニアリング:段階的に逆を求める
**Q1**: 入力に一連のビット演算変換(XOR、シフト、加減算、乗算)が施されている。逆を求めるにはどこから始める?
**A1**: 逆順に段階的に逆を求める。各可逆操作には逆がある。xor は自己逆、加↔減、左シフト↔右シフト(ビット落ちに注意)、定数乗算↔そのモジュロ逆数の乗算。最後のステップから前に向かって 1 つずつ打ち消す。判定基準:可逆ビット演算チェーン = 後ろから前に逆関数を適用することで、機械的に解ける。
**Q2**: 不可逆操作に出会った(右シフトで下位ビットが落ちる、定数との AND で情報が落ちるなど)?
**A2**: そのビットの分岐をブルートフォースする。失われた情報量は小さい(数ビット)ので、すべての可能性を列挙して検証する。判定基準:局所的に不可逆なときは小範囲のブルートフォースで失われたビットを補い、チェーン全体を諦めない。
**Q3**: 乗算はあるが定数と法が互いに素でなく、モジュロ逆数がない?
**A3**: 逆を求めるのではなく求解へ方向転換する。合同方程式を立て、拡張ユークリッド/CRT を使うか、解のないビットを列挙する。判定基準:モジュロ逆数がないこと ≠ 解がないこと。数論方程式の視点へ移る。
**Q4**: 演算チェーンにルックアップテーブルと状態が織り交ざり、純粋なビット演算ではなく、段階的な逆計算が途切れた?
**A4**: シンボリック実行へ方向転換する。変換全体を z3/angr に与え、ソルバーに混合演算を処理させ、手作業の分解をしない。判定基準:手作業の逆計算が途切れたら SMT に任せる。SMT は演算の複雑さを気にせず、充足可能性だけを気にする。
**Q5**: シンボリック実行も非線形性(ハッシュ、乗算の爆発)でタイムアウトする?
**A5**: 分割へ方向転換する。長いチェーンを数セグメントに切り、可逆なセグメントは手作業で逆を求め、不可逆/非線形な短いセグメントだけをブルートフォースか SMT に任せ、セグメントごとに撃破する。判定基準:チェーン全体が難しいなら「可逆セグメント/難解セグメント」の継ぎ目を探して分割統治する。

### ステートマシン/プロトコルのリバースエンジニアリング
**Q1**: 対象が独自プロトコル/シリアライズ形式で、そのエンコード/デコードを復元したい。どう着手する?
**A1**: まずサンプルを集めて比較する。複数組の「入力-出力」を集めるか複数本のパケットをキャプチャし、フィールドを位置合わせする。固定ヘッダ(マジックナンバー)、長さフィールド、種別タグ(TLV)、チェックサム末尾を探す。判定基準:プロトコルのリバースエンジニアリングはまず複数サンプルの diff でフィールド境界を特定し、それから単一フィールドのエンコードを逆に見る。
**Q2**: フィールドが圧縮/暗号化されているように見える?
**A2**: 層ごとに剥がす。まず圧縮の有無(エントロピー、gzip/zlib のマジックナンバー `78 9c`)、暗号化の有無(エントロピーがほぼ満杯)を判断する。まず解凍し、次に復号し、それから解析する。判定基準:プロトコルスタックは階層化されているので、リバースエンジニアリングも層ごとに剥がす。
**Q3**: 長さまたはチェックサムフィールドはあるがアルゴリズムが不明?
**A3**: チェックサム関数を逆に見る。送信前にチェックサムを計算するコードを探すか、複数サンプルから逆算する(1 バイト変えてチェックサムの変化を見る → CRC/加算和/XOR か)。判定基準:チェックサムフィールドは「制御可能な入力→観測可能な出力」の小さなブラックボックスなので、数組の差分で識別できる。
**Q4**: プロトコルにハンドシェイク/暗号ネゴシエーション(自前の TLS 類似)があり、静的解析でネゴシエーションロジックを逆に見るには複雑すぎて塞がれた?
**A4**: 平文層の hook へ方向転換する。暗号ネゴシエーションを逆に見ず、暗号化・復号関数の平文側(SSL_read/write 系の対応点)を hook して、送受信される平文を直接取得する。判定基準:暗号化プロトコルはアプリケーション層に必ず平文の出入口があり、そこを hook すればネゴシエーション全体のリバースエンジニアリングを迂回できる。
**Q5**: 平文の hook 点さえ特定できない(完全自前スタック)?
**A5**: データフロー追跡へ方向転換する。socket の recv バッファから順方向にテイント追跡し、データがどの関数の変換を経由するかを見る。変換の終点(業務ロジックに入るところ)が平文である。判定基準:データはネットワークから業務に至るまで必ず復号される。テイントに沿って「業務が消費し始める」点までたどる。

### 主要アルゴリズムの位置特定:相互参照とデータアンカーポイント
**Q1**: 大きなプログラムで「特定のファイル/フィールドを処理する」アルゴリズムがどこにあるか探す。どう素早く位置特定する?
**A1**: データアンカーポイントで相互参照を行う。既知のマジックナンバー、文字列、定数、ファイル拡張子をバイナリ内で検索し、誰がそれを参照しているかを見る。参照点の周囲が関連アルゴリズムである。判定基準:コードはデータを中心に組織されるので、既知データが最速のナビゲーションアンカーである。
**Q2**: 関心のあるデータが実行時に生成されるため、静的に検索できない?
**A2**: 動的メモリ検索を行う。プログラムを動かしてからメモリ内でそのデータの特徴を検索し、メモリアクセスブレークポイントを張る。それに触れるものが関連箇所である。判定基準:静的に検索できなければ動的に「データを見張る」。
**Q3**: 特定の API 関連ロジック(ネットワーク/ファイル/暗号化呼び出しなど)を位置特定したい?
**A3**: インポートテーブル + API ブレークポイントを使う。`send`/`CreateFile`/`CryptEncrypt` などにブレークポイントを張り、スタックをたどって呼び出し元へ戻る。判定基準:システム API は天然のアンカーポイントであり、API から業務ロジックを逆算する。
**Q4**: 対象が静的リンク + シンボル除去で、API 境界さえ曖昧で、位置特定が塞がれた?
**A4**: FLIRT/署名識別へ方向転換する。ライブラリ関数の署名(IDA FLIRT、rizin sig)でまず標準ライブラリ関数を認識してシンボルを復元し、自前コードの範囲を絞る。判定基準:静的リンクの大部分はライブラリコードなので、まず署名で「背景を差し引いて」から業務を探す。
**Q5**: 署名でも認識しきれない(魔改造 libc / 非一般的なライブラリ)?
**A5**: 挙動クラスタリングへ方向転換する。動的に全行程の呼び出しを trace し、呼び出し頻度とデータフローで関数をグループ化し、「対象データを処理するクラスタ」を特定する。判定基準:関数名を認識できなければ「それが関心データに対して何をしたか」で特定する。

### ツールチェーン選択:静的デコンパイラの取捨選択
**Q1**: 1 つの対象で IDA / Ghidra / Binja のデコンパイル結果が異なる。どれを信じる?
**A1**: 相互検証し、1 つだけを信じない。デコンパイルは損失のある再構築で、エンジンごとに種別復元や最適化復元の強弱が異なる。重要関数は 2 つのエンジンで照合し、食い違いはアセンブリに戻って判定する。判定基準:デコンパイル結果は「参考翻訳」であり真実ではない。アセンブリこそが ground truth である。
**Q2**: デコンパイルされた種別/構造体がすべて間違い(`int` と offset の山)?
**A2**: 構造体を手作業で復元する。アクセスオフセットのパターンに基づいて struct を再構築し、変数に種別を付けると、デコンパイルは大幅に改善する。判定基準:構造体の復元は C++/複雑ロジックのリバースエンジニアリングの土台であり、序盤の投入に値する。
**Q3**: 最適化が激しすぎて(インライン化、ベクトル化、末尾呼び出し)、デコンパイルが原型をとどめていない?
**A3**: 精度を下げてアセンブリを見る + ブロック単位で理解する。高度に最適化されたコードでは「擬似 C を読む」ことを諦め、アセンブリを直接読んで基本ブロック単位で理解するか、動的にデータフローを trace する。判定基準:O2/O3 では擬似 C は信用できず、アセンブリか動的へ移る。
**Q4**: アーキテクチャが特殊(MIPS/RISC-V/マイコン/DSP)で、主流デコンパイラのサポートが弱く塞がれた?
**A4**: 動的/エミュレーションへ方向転換する。静的サポートが弱いなら QEMU エミュレーションで動かして trace するか、そのアーキテクチャをサポートするツール(Ghidra はアーキテクチャが最も豊富、または Unicorn スクリプトを書く)を使う。判定基準:特殊なアーキテクチャは静的が弱いので動的実行で補う。実行はアーキテクチャの人気を見ない。
**Q5**: エミュレータさえそのアーキテクチャ/周辺機器をサポートしない?
**A5**: ハードウェア/ファームウェアの視点へ方向転換する。実ハードウェアでデバッグする(JTAG/SWD)か、周辺機器のモデル化を行う(MMIO レジスタの挙動をスタブ化する)ことで、ファームウェアをエミュレータ内で動かす。判定基準:純ソフトウェアでエミュレーションできないなら実ハードウェアを導入するか周辺機器モデルを補い、純粋な静的解析で組み込み機器に固執しない。

### 時間予算と方向転換の意思決定
**Q1**: 1 つの問題/対象をリバースエンジニアリングする際、「方向転換すべき時」をどう判断し、無思考に力ずくで読まないか?
**A1**: タイムボックス + マイルストーンを設ける。各ルートに硬直的な時間上限(単一パスの 30-45 分で進展がなければ停止など)を与え、「進展」を検証可能な中間成果(鍵の取得/アルゴリズムの識別/check の一度の成功)と定義する。判定基準:マイルストーンの前進がないこと = 方向転換の合図。「もう少し見れば分かる」と自己欺瞞しない。
**Q2**: もうすぐ突破できそうだが、すでに時間超過している。続けるか転換するか?
**A2**: 「決定性」を見る。残りが機械的作業(やり方が分かっていて、時間がかかるだけ)なら続ける。まだ「推測段階」(この道が正しいか不確定)なら転換する。判定基準:「実行コスト」と「探索の不確実性」を区別し、前者は続行可、後者は転換が必要。
**Q3**: 手元に複数の可能なルートがある。どれを先に攻める?
**A3**: 「情報利得/コスト」で並べ替える。まず安価で仮説を反証/実証できる探査(checksec、findcrypt、文字列、一度の動的 trace)を行い、小コストで不可能な分岐を切り捨ててから深掘りする。判定基準:判断を素早く変えられる行動を先に行う。
**Q4**: 思いつくルートをすべて試しても塞がれ、完全に行き詰まったらどうする?
**A4**: 抽象層を変える。アルゴリズム層で行き詰まったら → 実装/ロジック層へ上げる。静的で行き詰まったら → 動的/エミュレーションへ。ソフトウェアで行き詰まったら → インテリジェンス層へ(これは既知のプロテクト/既知の問題タイプではないか)。判定基準:行き詰まりの本質はしばしば「層の選択ミス」であり、戦術を変えるより系統的に層を変えるほうが有効である。
**Q5**: 層を変えても成果がなく、方向が根本から間違っているのか?
**A5**: 対象の定義に戻って問い直す。本当に必要な成果物は何か。まったく異なる達成経路(解読ではなく迂回、復元ではなく再利用、コアアルゴリズムではなくバイパス情報)はないか。判定基準:長時間の行き詰まりは往々にして「問題を解き間違えている」ことで、要求自体に戻って再分解すると、直交する近道がよくある。

### フォーマット文字列:リークと書き込みのリズム
**Q1**: フォーマット文字列の脆弱性があると確認した。まず何をする?
**A1**: まず偵察に使い、直接攻撃しない。`%p` 列でスタックを dump し、スタック上の canary、libc アドレス、PIE アドレス、そして自分が制御できる入力のパラメータオフセットを特定する。判定基準:fmt は「先に偵察してから攻撃する」プリミティブであり、1 回のリークで PIE/Canary/libc の 3 つの未知量を同時に解決できる。
**Q2**: 制御可能なオフセットを見つけた。どう安定的に任意書き込みする?
**A2**: `%n` 系を使う。`%hhn` は 1 バイト、`%hn` は 2 バイトの書き込みで、正確な幅制御と組み合わせて値を書き込む。対象アドレスをバイト単位で分けて書き、一度に超大値を書いて固まらないようにする。判定基準:大きな値の書き込みはバイト分割 + `%hhn` で初めて実際に可能になる。
**Q3**: 対象が FORTIFY を有効にしていて(`%n` 禁止)、書き込みの道が塞がれた?
**A3**: 純粋なリーク利用へ方向転換する。`%n` が使えないときも、fmt は依然として超強力な任意読み取りである。これで flag/重要データをメモリから直接読み出すか、十分な情報をリークして他の脆弱性(スタックオーバーフローなど)と組み合わせてエクスプロイトを完成させる。判定基準:書き込みは禁止されても読み取りは残る。多くの対象は任意読み取りだけでデータを取得できる。
**Q4**: 発火機会が 1 回だけで、リークと書き込みを 2 回に分けられない?
**A4**: 単発の構成にする。1 つの payload でリークと書き込みを同時に行うか、リークに依存しない対象(GOT を PLT 内の既知アドレスに変更、return の部分上書き)を攻める。判定基準:一回限りの場面では「事前リーク不要」の攻撃対象を優先して選ぶ。
**Q5**: 入力で `%`/`$` がフィルタリングされ、fmt がまったく使えない?
**A5**: 脆弱性を変える。fmt が封じられたら他のプリミティブ(オーバーフロー、論理的な穴)に戻る。判定基準:あるプリミティブが入力フィルタリングで塞がれたとき、プログラムの他の入力点を再列挙し、フィルタリングされた点で無理に合わせようとしない。

### 整数と型:オーバーフローが制御フローを変える
**Q1**: 目立つメモリ破壊の脆弱性はないが、コードにサイズ/長さの計算が大量にある。何を疑うべきか?
**A1**: 整数の問題を疑う。重点は、符号あり↔符号なしの比較、`size` 計算内の乗算/加算オーバーフロー、負の長さによる境界検査の迂回、切り詰め(int→short)。判定基準:整数の脆弱性は「ロジックは正しいが境界が間違い」であり、size を計算してから割り当て/コピーに使う経路を専ら監視する。
**Q2**: size のオーバーフローを 1 か所見つけた。どうエクスプロイトに変える?
**A2**: データフローに沿ってそれがどこへ流れるかを見る。malloc へ流れる → 小さい割り当てに大きな書き込み(ヒープオーバーフロー)。memcpy の長さへ流れる → 範囲外の読み書き。配列インデックスへ流れる → 任意の読み書き。判定基準:整数バグそのものは危険ではなく、「オーバーフロー後の値がメモリ操作のサイズ/オフセットとして使われる」ことが危険である。
**Q3**: オーバーフローは起きたが、後続の二次検査に阻まれた?
**A3**: TOCTOU / 検査迂回を探す。検査に使う値と使用する値が同一か、検査後に変更されるか、マルチスレッド下で競合できるか。判定基準:検査と使用の間の窓は、整数エクスプロイトの一般的な突破口である。
**Q4**: 長く解析しても利用可能な整数経路がない。塞がれた?
**A4**: 別のプリミティブカテゴリへ方向転換する。整数の脆弱性は利用が難しいことが一般的(制約が多い)。メモリ破壊(UAF/オーバーフロー)、論理脆弱性、型混同を再走査する。判定基準:ある種別の脆弱性が通じなければ脆弱性カテゴリを変え、単一のバグ種別に固執しない。
**Q5**: 対象がスクリプト/マネージド言語(GC あり、生ポインタなし)で、整数オーバーフローの発想が無効?
**A5**: 意味論的な脆弱性へ切り替える。マネージド環境では、逆シリアライズ、プロトタイプチェーン汚染、型混同、サンドボックスエスケープ、組み込み関数の誤用を攻める。判定基準:ランタイムが変われば脆弱性モデルも変わり、メモリ系の発想は言語意味論系の脆弱性に席を譲る。

### アンチデバッグ/アンチ仮想マシン対策の層別分解
**Q1**: 対象がデバッガに入れるとすぐ終了/挙動が異常になる。どう系統的にアンチデバッグを分解する?
**A1**: まず検知手段を分類する。①API 系(IsDebuggerPresent、ptrace、NtQueryInformationProcess)②時間系(rdtsc/GetTickCount の差分)③自己チェックサム(ブレークポイント 0xCC の検知、コード hash の検証)④環境系(VM 特徴の検知、シングルステップトラップ)。判定基準:アンチデバッグは階層的であり、まずどの層を使っているかを列挙し、それから層ごとに対処する。
**Q2**: API 系の検知を最も速く処理するには?
**A2**: 戻り値を hook/patch する。検知関数が常に「デバッグされていない」と返すようにする。デバッガスクリプトか Frida で一括 hook する。判定基準:API 系検知は「システムに状態を問う」ものなので、答えを改ざんすればよく、コストが最低なので先に行う。
**Q3**: 自己チェックサムがある(自分が張ったソフトウェアブレークポイントを検知する)?
**A3**: ハードウェアブレークポイント/メモリブレークポイントへ方向転換する。ソフトウェアブレークポイントはバイトを変えるため hash 検証に見つかるが、ハードウェアブレークポイント(DR レジスタ)はコードバイトを変えないので、コードの自己チェックサムを迂回する。判定基準:自己チェックサムが防ぐのは「コードの変更」であり、コードを変えないブレークポイント方式に替える。
**Q4**: アンチデバッグが頑固すぎて(多層 + 検知コードの動的生成)、patch しきれない。塞がれた?
**A4**: エミュレーション実行へ方向転換し、本物のデバッガから完全に離れる。Unicorn/QEMU には本物のデバッガプロセスや ptrace がなく、rdtsc も偽造できる。関心のある関数を抽出してエミュレーション環境で動かす。判定基準:アンチデバッグは「本物のデバッグ環境」を狙うので、釜の下の薪を抜くようにエミュレーション環境へ移る。
**Q5**: 検知しているのが VM/サンドボックスそのもの(仮想マシンでの実行を拒否する)?
**A5**: 実機/偽装へ方向転換する。ベアメタル/裸のマシンで解析するか、VM 特徴を偽装する(MAC、CPUID、レジストリ/デバイス特徴の変更、hypervisor ビットの隠蔽)。判定基準:アンチ VM とアンチデバッグは直交する 2 種類であり、分けて対処し、混同しない。

### 乱数は予測可能:暗号文ではなく PRNG を攻める
**Q1**: 対象の鍵/token/nonce が乱数で生成されている。予測可能かどうかをどう判断する?
**A1**: まず乱数源の種別を見分ける。`rand()`/`Math.random()`/`mt19937` のような非暗号学的 PRNG か、`/dev/urandom`/CSPRNG か。非暗号学的 PRNG は状態を復元できれば全出力を予測できる。判定基準:まず使われているのが CSPRNG かどうかを見る。そうでなければ乱数チェーン全体を攻められる。
**Q2**: mt19937 / LCG だと確認した。どう予測する?
**A2**: 連続出力を集めて内部状態を復元する。mt19937 は 624 個の連続 32 ビット出力を得れば状態を逆算して後続を予測できる。LCG は数組の出力で合同式を解けばよい。判定基準:非暗号学的 PRNG の出力が十分に揃えば状態が確定し、後続はすべて計算できる。
**Q3**: シードが弱いシード(タイムスタンプ/PID)?
**A3**: シードを直接ブルートフォースする。`srand(time(0))` 系なら、シード空間は極小(おおよその時刻 ± 数秒)なので、シードを列挙して乱数列全体を再現する。判定基準:弱いシードは状態復元より手軽であり、まずシードのエントロピーを見る。
**Q4**: 乱数が CSPRNG を使っており、予測の道が塞がれた?
**A4**: 乱数の「生成」ではなく「使い方」へ方向転換する。同じ nonce/IV を再利用していないか(致命的)。乱数が切り詰め/モジュロで偏りを導入していないか。乱数値が出力と一緒にリークして関連付けられないか。判定基準:CSPRNG 自体は予測できないが、「乱数の使い方」にはよく脆弱性がある。攻撃面を生成器から用法へ移す。
**Q5**: 生成も使用も問題がない?
**A5**: 乱数攻撃を諦めて、他の面(鍵の出所、実装の脆弱性、論理迂回)へ転換する。判定基準:乱数性は暗号システムの中で最も攻めにくい環であり、強いと確認したら早めに撤退し、CSPRNG で時間を浪費しない。

### クラッシュからエクスプロイトへ:まず crash を分類する
**Q1**: fuzz か手動テストでクラッシュが発火した。利用価値があるかどうかをどう判断する?
**A1**: まず crash を分類する。どこで落ちたかを見る。PC が制御されている(直接の制御フロー乗っ取り、高価値)、書き込みアドレスが制御可能(任意書き込み)、読み取りアドレスが制御可能(情報リーク/DoS)、それとも純粋なヌルポインタ参照(ほぼ DoS のみ)。判定基準:crash の利用可能性は「何が制御可能か + どの程度制御可能か」で決まる。まず分類してから投入を決める。
**Q2**: PC またはあるレジスタが入力バイトに制御された?
**A2**: 高価値なので、即座に深掘りする。制御幅(何バイト)、オフセット(入力のどの部分)、制約(使えないバイト)を確認する。判定基準:制御フロー乗っ取りはエクスプロイトのピラミッド頂点であり、優先して確実なものにする。
**Q3**: 制御可能な書き込みだけで、PC まで制御できない?
**A3**: 「書き込みプリミティブ→制御フロー」への変換を探す。GOT/vtable/戻りアドレス/関数ポインタ/ヒープメタデータに書き込む。任意書き込みは「実行フローを変えられるメモリ」に届いて初めて役に立つ。判定基準:制御可能な書き込みの価値 = どの重要構造に書き込めるか。
**Q4**: crash が制御不能に見える(無関係なアドレスで落ちる、安定して再現できない)ので塞がれた?
**A4**: 現象ではなく根本原因解析へ方向転換する。ASAN/valgrind で本当の範囲外/UAF の発生源を特定する。そこは往々にしてクラッシュ点より制御可能である。または入力を変えてバグをより制御可能な文脈で発火させる。判定基準:クラッシュ点 ≠ 脆弱性点。根本原因まで遡ると制御可能なバージョンがよく見つかる。
**Q5**: 純粋な DoS 系で、メモリ破壊がなく、利用の見込みがないと確認した?
**A5**: 別の入力面/脆弱性種別へ方向転換する。この crash に利用価値がないことを素直に認め、攻撃面の列挙に戻って新しい入口を探す。判定基準:利用不可能な crash を早めに見切り、繰り返し検討するより時間を節約する。

### 暗号化トラフィック/ストレージ:復号の瞬間を探す
**Q1**: 対象がデータを暗号化してからディスクへ書き出す/ネットワーク送信する。平文が欲しいが、静的解析でアルゴリズムを逆に見るのは遅すぎる。近道はあるか?
**A1**: ある。アルゴリズムを逆に見ず、「復号の瞬間」を遮断する。プログラムは使うために必ず自分で復号するので、復号関数を呼び出した後、平文を消費する前に hook して平文を直接取得する。判定基準:「暗号化ストレージ/転送」のデータは、プログラム実行時に必ず平文に戻る。復元点で待ち構えるのが最も省力である。
**Q2**: 復号関数がどこにあるか分からない?
**A2**: データから逆算する。ストレージバッファ/受信バッファにメモリブレークポイントを張り、それを読むもの → その先が復号である。または既知の暗号文定数にアクセスブレークポイントを張る。判定基準:暗号文はアンカーであり、「誰が暗号文を消費するか」をたどって復号ロジックを見つける。
**Q3**: 大量のサンプルをバッチで、再現可能に復号したい?
**A3**: 復号関数を抽出してオフラインツールにする。鍵 + アルゴリズムを特定した後、Unicorn でその関数をエミュレーションするか Python/C で書き直して、バッチで動かす。判定基準:一度きりの hook はサンプリング向きで、バッチ処理には復号ロジックを独立ツールに固める価値がある。
**Q4**: 復号がサーバー/鍵ネゴシエーションに依存し、オフライン再現が塞がれた?
**A4**: オンラインの仲介者(MITM)へ方向転換する。オフラインで解けないなら、対象の実行環境内で MITM として、平文 API を hook するか、ローカルプロキシでネゴシエーション後のセッション鍵を取得してから復号する。判定基準:鍵がサーバー側にあるときはオフラインを諦め、「動いている対象環境で平文/セッション鍵を取る」へ移る。
**Q5**: 環境も取得できない(暗号文 1 つとバイナリしかない)?
**A5**: 力ずくのリバースエンジニアリングか弱点探しに戻る。このときは素直にアルゴリズムを復元してハードコードされた鍵を抽出するか、アルゴリズム/鍵管理の弱点(弱い KDF、ハードコード、予測可能な導出)を監査するしかない。判定基準:「平文をうまく取る」道がすべて断たれたとき、初めてコスト最高の完全復元へ戻る。

### 多段階復号チェーン:層が層を包む
**Q1**: 第 1 層を解いたら中身がまだ暗号文/新たなバイナリだった。多段階をどう整理する?
**A1**: 玉ねぎを剥くように扱い、「段階リスト」を作る。各層で入力、使用アルゴリズム/鍵、出力を記録する。1 つの層で迷子にならず、自分が第何層にいて、あと何層あるかを常に把握する。判定基準:多段階復号の最大の落とし穴は「層間での迷子」であり、リストで全体ビューを維持する。
**Q2**: 各層で異なるアルゴリズムを使い、層ごとの手作業が遅すぎる?
**A2**: できる限り自動で連結する。layer N の出力を直接 layer N+1 に渡すスクリプトを書いて pipeline を形成し、1 層のパラメータを変えたら全チェーンを再実行する。判定基準:多段階は必ず pipeline 化する。手作業のデータ運搬は必ず間違え、遅い。
**Q3**: ある層の鍵が前の層の出力に依存する(チェーン派生)?
**A3**: 順序を厳格に保ち、中間状態を記録する。鍵がチェーン派生のときは段階を飛ばせず、各層の出力を保存して下層の派生に備える。判定基準:チェーン依存のもとでは、全中間産物の保存が遡及とデバッグの前提である。
**Q4**: 中間のある層で詰まって解けず、チェーン全体が切れたらどうする?
**A4**: 動的にその層をスキップする方向へ転換する。プログラム自身は解けるので、詰まった層の次の層まで走らせ、その層の復号出力を直接 dump して、手作業で解けない中間層をスキップする。判定基準:静的に解けない中間層は「対象に自分で解かせて、自分は下流で結果を取る」ことで迂回し、各層をすべて手作業で復元する必要はない。
**Q5**: 対象にアンチ dump / 各層の解き終わり即消去があり、動的スキップも塞がれた?
**A5**: チェーン全体のエミュレーションへ方向転換する。Unicorn で多段階 loader を全体としてエミュレーション実行し、エミュレーション内のメモリで任意の層を自由に dump する。アンチ dump の影響を受けない。判定基準:アンチ dump が防ぐのは本物のプロセスメモリであり、エミュレーション環境のメモリは完全に自分が掌握する。

### 「比較点」の位置特定で攻撃対象値を確定する
**Q1**: crackme でも検証でも、最終的にどこかの比較に帰着する。「決定的な比較」を正しく見つけるにはどうする?
**A1**: 判定結果から唯一の比較まで遡る。「成功/失敗」という真偽値がどう計算されたかを追跡し、それを生む比較命令(cmp/test/独自 equal)まで逆にたどる。判定基準:すべての変換は最後の比較のためにあり、それを特定すれば対象値も特定できる。
**Q2**: 比較を見つけた。片方は自分の入力変換、もう片方は対象。対象はどこから来たか?
**A2**: 対象の出所を分類する。①ハードコード定数(直接読む)②実行時計算(動的ブレークポイントで値を読む)③別経路の入力から派生。判定基準:まず対象値が静的か動的かを確定し、定数を読むかブレークポイントを張るかを決める。
**Q3**: 対象値が動的に計算される。直接読めればリバースエンジニアリング全体を迂回したことになる?
**A3**: そう。比較が「自分の変換(input) == target」で、target が input と無関係なら、target を直接動的に読み、自分の側の変換だけを逆に見ればよく、target の計算理解を省ける。判定基準:比較の両辺が独立のとき、「入力を含む側」だけを逆に見ればよい。
**Q4**: 比較の両辺がともに入力に依存する(交差検証)ので、独立した対象が読み出せない。塞がれた?
**A4**: 全体の制約求解へ方向転換する。両辺が入力を含む = 入力に関する方程式の組なので、z3/angr に解かせ、辺ごとに値を読まない。判定基準:比較の両辺が結合しているなら「答えを読む」ことを諦め、連立方程式の求解へ格上げする。
**Q5**: 比較が両辺とも不可逆ハッシュ(hash(input)==hash(const))?
**A5**: ブルートフォース/衝突、または上流攻撃へ方向転換する。ハッシュ比較は求解できないので、入力を段階的にブルートフォースするか、hash 入力空間の制約(フォーマット、長さ)を探してブルートフォースを縮小するか、いっそ比較を patch して検証をスキップする(目的が「入力の求解」ではなく「通過させる」だけの場合)。判定基準:ハッシュ比較は「入力が要る」か「通過が要る」かを区別し、後者なら分岐を直接 patch する。

### patch 迂回 vs 実求解の取捨選択
**Q1**: 目的が単に「プログラムに検証通過と思わせる」こと(実パスワードは不要)なら、リバースエンジニアリングすべきか patch すべきか?
**A1**: patch を優先して評価する。目的が挙動(機能のアンロック、検証のスキップ)なら、判定分岐を直接 patch する(ジャンプを変える、戻り値を変える)のが最速で、アルゴリズムの理解は不要。判定基準:「過程ではなく結果が要る」とき、patch が最短経路である。まず「本当にその実値が要るのか」を自問する。
**Q2**: patch をどう最小化する?
**A2**: 単一のスイッチ点を探す。通常は `jz→jnz`/`je→jmp` の 1 命令、または check 関数を直接 `return 1` にするだけで足りる。判定基準:最小 patch = 変更が最少で、判定に最も近いその 1 バイト/ジャンプ。
**Q3**: ローカル検証を patch したが、プログラムに自己チェックサムがある(コード変更を検知する)?
**A3**: メモリ patch / 実行時 hook へ方向転換する。ディスクファイルを変えず、実行時に自己チェックサムの後でメモリを変えるか、検証関数の戻りを hook する。判定基準:静的 patch が自己チェックサムを発火させるときは、「自己チェックサムの後に実行されるメモリ」を変える。
**Q4**: 検証がサーバー側にあり、クライアントの patch はまったく無意味。塞がれた?
**A4**: 実求解へ方向転換する。サーバー側検証は patch できず、実値を取得するか正当なリクエストを偽造しなければならない。このとき初めて素直にアルゴリズムを逆に見て、実パスワードを求めるか署名を偽造する。判定基準:サーバー権威の検証下では patch が無効となり、「迂回」から「真の解」への転換を迫られる。
**Q5**: サーバー側検証でアルゴリズムも強く、真の解も難しい?
**A5**: プロトコル/論理迂回へ方向転換する。検証アルゴリズムの解読ではなく、認証ロジックそのもの(リプレイ、セッション固定、権限外アクセス、パラメータ改ざん)を攻める。判定基準:強アルゴリズムのサーバーでは、攻撃面は「認証フローの論理脆弱性」にあり、暗号そのものにはない。

### shellcode 作成と制限環境
**Q1**: 実行制御権を得て shellcode を投入する。書く前に何を確認する?
**A1**: まず制約を確認する。アーキテクチャ(x86/x64/ARM)、悪い文字(どのバイトが切り詰め/フィルタリングされるか、`\x00`\`\x0a` など)、空間サイズ(バッファの大きさ)、実行環境(NX の有無、mprotect の可否)。判定基準:shellcode は「枷をはめた踊り」であり、まず枷を測ってから書く。
**Q2**: 空間が小さすぎて完全な shellcode が収まらない?
**A2**: stager を使う。まず「より多くのデータを実行可能メモリに読み込んでジャンプする」小さなブートストラップを置き、本体は 2 段階で転送する。判定基準:空間不足なら段階的に投げ込み、無理に詰め込まない。
**Q3**: 悪い文字があり、shellcode にちょうど含まれている?
**A3**: エンコーダ + 自己デコードを使う。encoder(xor エンコードなど)で悪い文字を避け、自己デコードヘッダを付けて実行時に復元する。判定基準:悪い文字はエンコードで迂回するが、デコードヘッダ自体に悪い文字が含まれないことを保証する。
**Q4**: NX が有効で、shellcode をどこに置いても実行不可。塞がれた?
**A4**: コード注入ではなく ROP へ方向転換する。NX 下ではデータを実行できないので、ROP チェーンで既存の実行可能コードを再利用するか、まず ROP で `mprotect`/`VirtualProtect` を呼んで shellcode 領域を実行可能にしてからジャンプする。判定基準:NX が封じるのは「データの実行」であり、ROP でコードを再利用するか、先にメモリ権限を変える。
**Q5**: ROP に必要なスタック移行/gadget まで制限されている(空間/悪い文字の二重の枷)?
**A5**: SROP / ret2csu / ret2dlresolve へ方向転換する。これらの技法はごく少数の gadget で複雑な呼び出しを完遂でき、gadget の乏しい制限環境に適する。判定基準:通常の ROP が制限されるとき、「低 gadget 需要」の高度技法へ移る。

### kernel/ドライバのリバースエンジニアリング特有の考慮
**Q1**: 対象がユーザー空間のプログラムでなくカーネルモジュール/ドライバ。リバースエンジニアリングの発想をどう調整する?
**A1**: まずカーネルの視点を確立する。ioctl/syscall 入口(ユーザー空間がどう対話するか)、特権操作(メモリマッピング、任意読み書きプリミティブ)、そしてそれがどのユーザー空間由来データを信用しているかに注目する。判定基準:カーネル脆弱性の価値は権限昇格にあり、攻撃面は「カーネルがユーザー空間入力を信用する境界」である。まず対話入口を探す。
**Q2**: 利用可能なカーネルプリミティブをどう特定する?
**A2**: 「ユーザー制御可能 → カーネルメモリ操作」を探す。ioctl handler 内の未検証ポインタ/長さ、double fetch、参照カウントの誤り(UAF)。判定基準:カーネルエクスプロイトはまず「任意読み取り + 任意書き込み + リーク」プリミティブを揃え、パラメータ検証の欠落箇所を監視する。
**Q3**: プリミティブがある。どう権限昇格する?
**A3**: 定番経路を使う。cred 構造を書き換えて権限昇格する、関数ポインタを上書きしてカーネル制御フローを乗っ取る、またはページテーブルを書き換える。判定基準:任意書き込みを得た後の目標は、「権限を決めるカーネル構造」を書き換えることである。
**Q4**: カーネルに SMEP/SMAP/KASLR/CFI の全緩和策があり、権限昇格が塞がれた?
**A4**: 個別に方向転換する。KASLR → カーネルアドレスのリークを探す。SMEP → ユーザー空間コードにジャンプせず、カーネル内 ROP を使う。SMAP → ユーザー空間データを参照せず、データもカーネルに置く。CFI → data-only 攻撃を探す(制御フローを乗っ取らずデータだけを変える、cred の直接変更など)。判定基準:各緩和策には対応する直交した迂回法があり、data-only は CFI 時代の汎用的な方向転換である。
**Q5**: 緩和策が完璧すぎて、メモリエクスプロイトが極めて難しい。塞がれた?
**A5**: 論理脆弱性へ方向転換する。カーネル内の論理的な穴(権限検査の欠落、競合状態、型混同)はメモリ緩和策の影響を受けない。判定基準:メモリエクスプロイトが緩和策で積み上がって塞がれたとき、論理脆弱性はすべてのメモリ緩和策を迂回する直交経路である。

### シンボリック実行の経路爆発管理
**Q1**: シンボリック実行でロジックを解くと決めた。最初から経路爆発を避けるにはどうする?
**A1**: まず範囲を絞る。プログラム全体にシンボリック実行せず、対象関数の「入力の進入」から「比較の発生」までの小さな区間だけを走らせる。hook で無関係なライブラリ呼び出し、IO、ループ外部を具体化する。判定基準:シンボリック実行の第一原則は「シンボル範囲の最小化」であり、範囲が小さいほど解ける。
**Q2**: ループが状態の指数的増加を招く?
**A2**: ループを処理する。ループ展開回数を制限する、ループ本体を制約に要約する、または固定回数ループの境界を具体化する。判定基準:ループは経路爆発の主因なので、ループに界を設けるか抽象化することを優先する。
**Q3**: 高コストな関数(ハッシュ、暗号ライブラリ)がソルバーを遅くする?
**A3**: SimProcedure / 具体値へ hook する。具体化できるものはシンボル化せず、既知入力のハッシュを直接計算して与える。判定基準:シンボリック実行では「具体化できるものは一律具体化」し、本当に未知のシンボル変数だけを残す。
**Q4**: 状態がやはり爆発し、ソルバーが走りきれない。塞がれた?
**A4**: 混合具体シンボル(concolic)へ、または戦略を変える。具体入力で誘導する(driller 式)、有向探索に変える(対象アドレスに向けて枝刈りし、無関係な分岐を捨てる)、または手作業解析 + 局所 z3 に戻る。判定基準:純粋なシンボリック実行が爆発するとき、concolic か有向探索に転じて具体情報で枝刈りする。
**Q5**: concolic さえ駄目(制約が本質的に難しい、ハッシュ/大規模ブルートフォースを含む)?
**A5**: シンボリック実行が不適切であると認め、ブルートフォース/サイドチャネル/論理迂回へ方向転換する。判定基準:シンボリック実行は「可逆制約の求解」を得意とし、本質的に不可逆(ハッシュ、強い非線形性)ならパラダイムを変えるべきで、ソルバー上で無限に待たない。

### データ重視:「どの数バイトが結果を実際に決めるか」を見つける
**Q1**: 入力が長いが、どの部分が実際に検証に関与するか分からない。解析面をどう絞る?
**A1**: 入力の感度テストを行う。バイト単位/セグメント単位で入力を変え、出力/判定が変化するかを見る。結果に影響しないバイトは無視でき、影響するものが重要である。判定基準:まず差分で「活性バイト」を探し、解析を実際にロジックへ関与する数バイトに集中させる。
**Q2**: 中央の一区間だけが結果に影響すると分かった?
**A2**: その区間に集中する。この区間を処理するコード経路だけを逆に見て(これらのバイトからテイントで順方向に追う)、残りは無視する。判定基準:活性バイト + テイント伝播 = 逆に見るべきコード部分集合を正確に特定する。
**Q3**: ある重要バイトがどの演算に流れたか知りたい?
**A3**: 順方向テイント追跡を行う。そのバイトをマークし、それが関与する各命令を記録する。得られたテイントスライスが「理解すべき最小ロジック」である。判定基準:テイントスライスは自然に無関係なコードを除去し、大規模/難読化プログラムへの対策の切り札である。
**Q4**: テイント追跡が暗黙フロー / 難読化の伝播で切れるか爆発する。塞がれた?
**A4**: ブラックボックス差分モデル化へ方向転換する。テイントが信頼できないとき、純粋な I/O 差分に戻る。この数バイトを大量に変えて出力を観察し、「入力バイト→出力」の関係モデルを統計的に構築し、内部追跡に依存しない。判定基準:テイント(ホワイトボックス)が切れたらブラックボックス差分に退き、内部追跡を外部観測で代替する。
**Q5**: ブラックボックス差分でも規則性が見えない(強い拡散)?
**A5**: 重要バイトが強アルゴリズムに巻き込まれたことを示す。前述の「アルゴリズム識別/実装攻撃/鍵攻撃」チェーンへ方向転換する。判定基準:バイト単位の差分に規則性がない = 暗号学的強度領域に入った。解析面縮小の段階を離れ、暗号攻撃のパラダイムへ移る。

### リバースエンジニアリングの仕上げ:復元結果の検証
**Q1**: アルゴリズムを復元した/flag を解いた/exp を書いたと自認している。納品前にそれが本当に正しいかどう確認する?
**A1**: 端から端まで検証し、「正しそう」を信じない。アルゴリズムを復元したなら、それで既知平文を再暗号化して元の暗号文と比較する。flag を解いたなら対象を完全に 1 回実行して検証する。exp を書いたならクリーンな環境で複数回再現する。判定基準:レッドチームの納品物は「再現可能な検証」が必須で、リバースエンジニアリングの結論は端から端までの検証を経なければ完了したとは言えない。
**Q2**: ローカルでは合うが、対象環境は必ずしも同じではない?
**A2**: 対象に近い環境で検証する。同じ libc バージョン、同じアーキテクチャ、同じ入力制約の下でテストする。判定基準:環境差(libc、アラインメント、バイト順)が「ローカルで成功しリモートで失敗する」最大の原因であり、検証は環境を合わせる。
**Q3**: exp が成功したり失敗したりで、安定性が足りない?
**A3**: 非決定的要因を調べる。ASLR/ヒープレイアウトのランダム性、race の窓、残留状態。リトライ、同期、ヒープ・ファングシュイを加えて安定性を高める。判定基準:不安定な exp = 未納品。乱数源を突き止めて飼い慣らす。
**Q4**: 検証の結果、実際は間違っていた(以前の判断が誤りだった)と分かった。どうする?
**A4**: 誤った仮説を遡って特定する。検証失敗点から、どの段階の仮説が間違っていたか(アルゴリズムの認識ミス?バイト順?鍵の不一致?オフセットの誤り?)を逆に調べ、最初からやり直さない。判定基準:検証失敗は貴重な信号であり、誤った仮説を精確に特定するほうが、最初から逆に見るよりはるかに効率的である。
**Q5**: 検証を繰り返しても繰り返し間違い、ある段階がいつまでも合わず、完全に行き詰まった?
**A5**: 「対象に自ら証明させる」へ方向転換する。自分で導出せず、対象を直接動的に走らせ、重要ポイントでその実中間値を dump し、自分の復元と段階的に照合する。最初の不一致点が自分の誤り箇所である。判定基準:自分で計算が合わないとき、対象の実実行を「正解」として逐点校正するのが、仕上げ段階の究極の方向転換である。
