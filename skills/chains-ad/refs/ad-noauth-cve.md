# ADドメイン内 · Zerologon/認証不要脆弱性の適用とリスク

### ドメインコントローラを把握したら、真っ先に Zerologon を仕掛けるか
**Q1**: フィンガープリントで対象 X がドメインコントローラと確認(88/389/445/135 が開放)。ドメイン認証情報は一切ない。直接 Zerologon を投入すべきか?
**A1**: まず発火を急がない。Zerologon(CVE-2020-1472)は核弾頭級の脆弱性だが、代償は DC マシンアカウントのパスワードを AD 内で空にすることで、処理を誤れば DC がドメイン離脱し、複製が中断し、生産事故になる。まず三つを問う。対象が 2020-08 以降のパッチを既に当てている可能性はないか。これが唯一のドメインコントローラか(単一点 = 不可逆リスク最大)。より軽い認証不要経路(LLMNR 毒入れ、AS-REP roasting)で低権限認証情報を先に取れないか。判定基準:低リスク手段で足場を取れるなら DC マシンアカウントのパスワードに触れない。
**Q2**: 「打つ価値があるか」の中核トレードオフは?
**A2**: 収益はゼロ認証情報から Domain Admin へ直行。コストは高中断リスク + 強アラート特徴(Netlogon の大量失敗認証)。認可が明確で中断を許す場面は打てる。生産/隠密要求の高い場面は、relay 系の認証不要チェーン(どんなアカウントパスワードも変更しない)を優先する。
**Q3**: この判断が詰まり、情報不足で意思決定できない場合は?
**A3**: 受動情報収集の直交次元へ転換する。まず匿名列挙(null session、LDAP 匿名バインド、RID cycling)でドメイン内の DC 数、おおよそのパッチ水位、ADCS の有無を把握してから再判断する。リスク意思決定を情報で置き換える。

### Zerologon の適用性の前提判断
**Q1**: 利用をトリガーせずに Zerologon が打てるかをどう判断する?
**A1**: パスワードを変更しない検知スクリプトを使う(例: zerologon の tester モード)。認証段階の ClientChallenge ループだけを行い、全ゼロ challenge で通過できるかを統計し、最終的な空化リクエストを送らない。判定基準:検知通過 = 高確率で未パッチ。失敗 = 修正済みまたは強化済み。
**Q2**: 検知が「打てそう」と示したら必ず成功するか?
**A2**: 必ずしもそうではない。EDR やドメインコントローラの強化(強制 Netlogon セキュアチャネル署名/カプセル化、enforcement mode)が実際の利用を失敗させる。検知通過は認証迂回が成立することだけを表し、空化動作はまだ遮られうる。
**Q3**: 検知自体が痕跡を残すか?
**A3**: 残す。検知だけであっても、失敗認証ログ(Event 4742/5805、Netlogon エラー)が蓄積する。対象に SOC があれば、検知ループの回数が多いほど危険。試行ラウンド数をできるだけ減らす。
**Q4**: 検知が遮られた(パッチ適用済み)場合は?
**A4**: 即座に Zerologon を諦め、Netlogon 非依存の直交経路へ転換する。強制認証 + NTLM relay(PetitPotam/PrinterBug → ADCS ESC8 または LDAP)、または noPac(CVE-2021-42278/42287)。これらの脆弱性のパッチラインは Zerologon と異なり、どれか未修正であることが多い。

### Zerologon 実行を決める前の「ロールバック計画」
**Q1**: 本番投入しようとしている。実行前に最も考えるべきことは?
**A1**: 復元計画。利用は DC$ マシンアカウントの AD 内パスワードを空にするが、ローカル SAM/LSA 内の旧パスワードは残る。これで AD とローカルが不一致になり、DC は他の DC と正常に複製できず、リスクが極めて高い。権限取得後、第一にマシンアカウントのパスワードを元の値へ復元しなければならない。
**Q2**: 元のパスワードを知らない。どう復元する?
**A2**: 空化後すぐ DCSync で DC$ マシンアカウントの履歴 hash をエクスポートするか、レジストリ/secretsdump でローカルにキャッシュされた元のマシンアカウント平文/hash を取得し、restore スクリプト(NetrServerPasswordSet2 経由)で AD 内のパスワードを一致値へ書き戻す。判定基準:復元後、DC が正常に外部認証でき、複製が回復する。
**Q3**: 復元窓はどれほど切迫しているか?
**A3**: 速ければ速いほどよい。空化状態では、正常なマシンアカウントの使用のたびにパスワードローテーションや複製衝突を誘発しうる。長引くほど DC のドメイン離脱とデータ不一致の確率が上がる。理想は「空化—DCSync—即復元」を一気呵成にスクリプト化すること。
**Q4**: 復元に失敗した(スクリプトエラー/DC が既に異常)場合は?
**A4**: 最悪のケースであり、緊急損切りの次元へ転換する。取得済みの認証情報(krbtgt、DA hash)を保持し、その DC へのさらなる操作を停止し、人手介入による復旧の要否を評価する。同時に取得済み認証情報で別の健全な DC から永続化を確立し、破壊された DC に依存しない。

### Zerologon 成功後の権限の換金方法
**Q1**: 空化成功、DC マシンアカウント身元で認証できる。次は?
**A1**: 空パスワードの DC$ マシンアカウントで DCSync する(secretsdump でそのマシンアカウントを指定)。krbtgt と全ドメインユーザー hash、特に Domain Admin をエクスポートする。判定基準:krbtgt hash を取得 = ドメイン全体のゴールデンチケット能力を掌握。
**Q2**: なぜマシンアカウントで DCSync できるのか?
**A2**: ドメインコントローラ自身のマシンアカウントはデフォルトでディレクトリ複製権限(DS-Replication-Get-Changes)を持つ。これは DCSync に必要なもの。したがって DC$ を空化 = 複製権の取得と同等。
**Q3**: hash を取得後、まず何をし、すぐパスワードを復元するか?
**A3**: まず krbtgt と少なくともひとつの DA の認証情報を確保し、その後即 DC$ パスワードを復元する。順序は逆にできない。復元後は空パスワード経路を失うため、復元前に認証情報窃取を完了しなければならない。
**Q4**: DCSync が拒否された(権限異常)場合は?
**A4**: 別の換金へ転換する。DC$ の空認証情報で直接 SMB/WMI で DC 本機へログオンして SAM/LSASS をエクスポートする(secretsdump ローカルモード)、または DC サービスに対するシルバーチケットを確立する。単一の DCSync 経路に死闘しない。

### 単一 DC vs 複数 DC 下で Zerologon を打つ場合の取捨
**Q1**: 環境に複数の DC がある。どの台に打つ?
**A1**: FSMO 主控でない、唯一の複製ハブでないメンバー DC を優先し、重要ロールを崩壊させる影響を下げる。判定基準:打った後に短時間異常になっても、ドメイン全体には健全な DC が支えとして残る。
**Q2**: 単一 DC のみの場合は?
**A2**: 単一 DC はリスク最高。一度復元に失敗すればドメイン全体が麻痺し、健全なコピーが支えない。このとき Zerologon を諦め、アカウントを破壊しない relay/noPac 経路へ切り替えるかを再評価すべき。遠回りでも単一点で賭けない。
**Q3**: 複数 DC 時に一台を空化すると他 DC に影響するか?
**A3**: 複製を通じて不一致が伝播する。したがって復元動作は同じく切迫し、復元後のパスワードがローカル DC だけでなく全域で複製一致することを確認する。
**Q4**: この経路(生産への影響が怖くて打てない)が全体として否決されたら、どこへ転換する?
**A4**: ゼロ破壊の認証不要権限昇格次元へ転換する。ADCS 証明書チェーン(ESC1/ESC8)、noPac、shadow credentials。これらは既存のアカウントパスワードを変更せず DA を取れ、ロールバック面がはるかに小さい。

### パッチ適用済みで Zerologon が遮られた後の第一転換先
**Q1**: DC が Zerologon 修正済みと確認。認証不要でドメインを取る道は断たれたか?
**A1**: 断たれていない。Zerologon は認証不要ドメイン内権限昇格のひとつに過ぎない。即座に他の認証不要/低認証チェーンを洗い出す。強制認証 + relay(PetitPotam、PrinterBug、DFSCoerce)、noPac、Certifried(CVE-2022-26923)、AS-REP roasting。判定基準:これらの脆弱性のパッチラインは互いに独立で、漏れがよくある。
**Q2**: どれを先に試す?
**A2**: 環境特徴による。ADCS(証明書サービス)があれば ESC8/ESC1 を優先。ドメイン内 SMB 署名が非強制なら LDAP/SMB への relay を優先。マシンアカウント割当量 >0 なら noPac を優先。環境フィンガープリントで順序を決め、盲目的にしない。
**Q3**: これらに共通の前提は?
**A3**: ネットワーク到達可能性 + 少なくとも一度の認証トリガー。多数の relay チェーンは、強制認証させられる対象(DC または高権限マシン)と、署名が非強制の受信端を必要とする。
**Q4**: これらも全部遮られた(全部パッチ済み、署名全面強制)場合は?
**A4**: 脆弱性次元ではなく認証情報次元へ転換する。低強度パスワードスプレー(ドメインパスワードポリシーに合わせてロック回避)、Kerberoast/AS-REP roast オフライン解読、LLMNR/NBNS 毒入れで net-NTLM を取得。「穴を開ける」から「認証情報を騙す」へ切り替える。

### PetitPotam 強制認証 + ADCS ESC8 relay
**Q1**: Zerologon が通らないが、ドメイン内に ADCS があり Web 登録エンドポイント(certsrv)が開いている。どう計画する?
**A1**: 古典的 ESC8 チェーン。PetitPotam(MS-EFSRPC)で DC に自分の制御下ホストへ NTLM 認証を強制し、この DC$ の認証を ADCS の HTTP 登録エンドポイントへ relay し、DC 身元の証明書を申請し、その証明書で PKINIT 認証して TGT/hash を交換する。判定基準:DC$ 証明書を取得 = DC 身元を取得。
**Q2**: なぜ LDAP ではなく HTTP エンドポイントへ relay するか?
**A2**: HTTP の ADCS Web 登録はデフォルトでチャネルバインディング(EPA)を検証せず、署名も強制しないことが多いため、relay の天然の弱点である。LDAP 側は現代の DC が署名/バインディングを強制することが多く、relay が失敗しやすい。
**Q3**: 強制認証をトリガーできない場合は?
**A3**: トリガーを変える。PetitPotam の複数の EFSRPC メソッドを輪番で、PrinterBug(MS-RPRN)、DFSCoerce(MS-DFSNM)、ShadowCoerce。ひとつの coerce がパッチされても、別プロトコルの coerce へ。これらは異なる RPC 面を打つ。
**Q4**: DC 証明書を取得したが PKINIT のチケット交換が失敗する?
**A4**: KB5014754(証明書マッピング強化)がパッチされている可能性。証明書を Schannel で LDAP へ使い(PassTheCert)、直接 AD 属性を変更する(自分に RBCD や DCSync 権限を追加)方向へ転換し、PKINIT のチケット交換段を迂回する。
**Q5**: ADCS に Web エンドポイントがそもそもない?
**A5**: ESC1/ESC2/ESC3 などテンプレート設定ベースの証明書権限昇格(低権限ドメインアカウントが必要)、または非証明書経路の noPac/relay-to-LDAP へ転換する。ESC8 は ADCS ファミリーのひとつに過ぎない。

### NTLM relay の前提:署名とバインディングの判定基準
**Q1**: NTLM relay をしたい。実行可能性を素早く判断するには?
**A1**: まず対象端の SMB 署名が強制かを探る(RunFinger/nmap smb2-security-mode)。SMB への relay は対象が署名非強制である必要がある。LDAP への relay は DC が LDAP 署名/チャネルバインディングを強制していない必要がある。判定基準:受信端が検証を強制しない = relay に見込みがある。
**Q2**: DC のデフォルト LDAP 署名は強制か?
**A2**: 現代の強化済み DC は LDAPS チャネルバインディングを強制する傾向があり、relay-to-LDAP(S) が失敗する。このとき HTTP(ADCS ESC8)または SMB(非署名のメンバー機)へ relay する方が信頼できる。
**Q3**: relay するのがマシンアカウントかユーザーアカウントかで違いがあるか?
**A3**: ある。マシンアカウントの LDAP への relay は RBCD の設定によく使われる(自身のオブジェクトに書き込み権限を持つ)。ユーザーアカウントの relay は横展開や読み取りにより多く使われる。coerce された身元に応じて relay の落とし先を選ぶ。
**Q4**: 全域で署名が強制され、relay が行き止まりの場合?
**A4**: relay 非依存の認証不要権限昇格へ転換する。noPac(純 Kerberos で NTLM を通らない)、Zerologon(未パッチなら)、または証明書テンプレート系 ESC。relay は NTLM の弱検証に依存し、署名が全面強制なら Kerberos 面の脆弱性へ切り替える。

### noPac(CVE-2021-42278/42287)の判断
**Q1**: 一般ドメインアカウントを持ち、素早く DA へ行きたい。noPac は選択肢になるか?
**A1**: 二つの前提を見る。ドメイン内マシンアカウント割当量 ms-DS-MachineAccountQuota > 0(デフォルト 10 で、一般ユーザーにマシンアカウント作成を許可)、かつ DC が 42278 と 42287 を同時に修正していない。満たせば、マシンアカウントを作成し、その sAMAccountName を DC になりすまして変更し、サービスチケットをリクエストして DC 身元の S4U2self チケットを取得する。判定基準:DC 身元でチケットを発行できれば成功。
**Q2**: マシンアカウント割当量が 0 の場合は?
**A2**: noPac のアカウント作成段が通らない。既存の制御可能マシンアカウント(既にホストを取っていれば、そのマシンアカウントを使う)へ転換するか、アカウント作成不要の経路(relay、Kerberoast)へ切り替える。割当量はハードな敷居である。
**Q3**: noPac の隠密性は?
**A3**: Zerologon より隠密。既存アカウントを破壊しないが、新マシンアカウントを作成して改名するため、4741/4781 イベントを残す。使い終わったら作成したマシンアカウントを削除して痕跡を減らす。
**Q4**: 改名衝突/チケットリクエスト失敗?
**A4**: よくある落とし穴は、新しいマシンアカウント名と本物の DC 名の衝突処理の誤り。なりすまし名に $ を付けないことを確認し、改名後にチケットをリクエストすることを確認する。それでも失敗するなら Certifried(26923)へ転換する。同じくマシンアカウント身元偽造だが、証明書面を通る。

### Certifried(CVE-2022-26923)と shadow credentials
**Q1**: 低権限アカウント + ADCS があり、noPac はパッチ済み。他にマシンアカウント偽造経路は?
**A1**: Certifried。マシンアカウントの自身の dNSHostName への書き込み権限を利用し、それを DC と同じに変更して、マシンテンプレートに基づく証明書を申請して DC 身元を取得する。または shadow credentials。対象オブジェクトに msDS-KeyCredentialLink を書き、自分の鍵で PKINIT 認証する。判定基準:対象身元で TGT を交換できるか。
**Q2**: shadow credentials には何の権限が必要か?
**A2**: 対象オブジェクトの msDS-KeyCredentialLink への書き込み権限(GenericWrite/GenericAll)が必要。relay や ACL 悪用と組み合わせて先に書き込み権限を取ることが多い。またドメイン内で PKINIT をサポートしている必要がある(ADCS/DC 証明書)。
**Q3**: 対象ドメイン機能レベルが 2016 未満で shadow creds が使えない?
**A3**: msDS-KeyCredentialLink は Key Trust に依存し、低機能レベルでは非対応の可能性。伝統的 RBCD(msDS-AllowedToActOnBehalfOfOtherIdentity を書く)+ S4U 委任乗っ取りへ転換し、証明書に依存しない。
**Q4**: この系統(26923/shadow creds/RBCD)はすべて前置書き込み権限が必要。書き込み権限を取れない場合は?
**A4**: その書き込み権限自体を取得する次元へ転換する。高権限マシンアカウントを LDAP へ relay して付与する、ACL 経路分析(BloodHound で誰が対象を書けるか探す)、または先に書けるホストを横展開で取る。認証不要脆弱性はしばしば「最初の書き込み権限を取る」手段であって終点ではない。

### ゼロ認証情報の足場:認証不要列挙の始め方
**Q1**: 内網に入ったばかりで認証情報がひとつもなく、どの脆弱性を打つかも分からない。まず何をする?
**A1**: 認証不要列挙で道を作る。SMB null session、LDAP 匿名バインド列挙、RID cycling でユーザー名を推測、ドメイン信頼/DC リスト/パスワードポリシーを列挙。判定基準:まず目標地図(どれが DC か、ADCS の有無、アカウント命名規則、ロック閾値)を作り、それからどの脆弱性の鍵を使うかを決める。
**Q2**: null session が全部無効化された?
**A2**: ブロードキャスト層の毒入れへ転換する。LLMNR/NBT-NS/mDNS 毒入れ(Responder)で net-NTLMv2 を取得するか、IPv6 DHCP 中間者(mitm6)で WPAD を乗っ取る。対向のサービス開放に依存せず、ネットワーク内の自発トラフィックに依存する。
**Q3**: ユーザー名リストを取得したら次は?
**A3**: パスワードなしでも遊べる。AS-REP roasting で事前認証不要のアカウントを探す(直接ブルートフォース可能な hash を取得)、パスワードスプレーで弱いパスワードを試す(ロックを避けるため速度を厳格に制御)。
**Q4**: 列挙で何も取れず、ネットワークが非常にクリーンな場合は?
**A4**: 物理/トラフィックの直交面へ転換する。ネットワーク内の平文プロトコルを取得、プリンタ/IoT の弱いパスワードの機器を踏み台にする、共有の匿名可読ディレクトリを探して設定内の認証情報を探す。認証不要は脆弱性とは限らず、設定の怠慢かもしれない。

### LLMNR/NBNS 毒入れで net-NTLM を取得後の分岐
**Q1**: Responder が net-NTLMv2 hash を取得した。次は relay かブルートフォースか?
**A1**: 意思決定は hash の主体と対象による。一般ユーザー hash で弱いパスワード傾向があればオフライン解読。リアルタイムで未署名対象へ relay できるなら、relay の方が速く解読不要。判定基準:relay は同時にオンラインで受信端の弱検証が必要。そうでなければ解読へ。
**Q2**: 取得したのがマシンアカウント hash($ で終わる)。ブルートフォースできるか?
**A2**: 基本的に期待しない。マシンアカウントのパスワードはランダム長文字列で解けない。マシンアカウント hash の正しい使い方は relay(LDAP へ RBCD 設定、ADCS へ証明書申請)。
**Q3**: net-NTLMv2 を直接 pass-the-hash できるか?
**A3**: できない。net-NTLMv2 はチャレンジ応答であり NTLM hash ではない。PtH できず、relay かブルートフォースのみ。二種の hash を混同して時間を無駄にしない。
**Q4**: relay 対象が全強制署名で、hash も解けない場合は?
**A4**: 毒入れ面を拡大する方向へ転換する。mitm6 で DHCPv6/WPAD を乗っ取り、より多くの認証を自分に経由させるか、高権限アカウントに自分の UNC パスへアクセスさせる(文書/メール水飲み場)。「より高価値な hash」を取得できる入口へ変える。

### relay の落とし先選択:LDAP / SMB / HTTP-ADCS
**Q1**: 一路の強制認証を relay する。落とし先をどう最適に選ぶ?
**A1**: 収益順に並べる。ADCS-HTTP へ relay して証明書を取る(収益最高、検証最弱) > LDAP へ relay して RBCD 設定/DCSync 権付与(LDAP 署名非強制が必要) > SMB へ relay して横展開実行(対象が非署名が必要)。判定基準:「検証が最弱かつ収益最高」の落とし先を選ぶ。
**Q2**: coerce されたのが DC$ マシンアカウント。LDAP がよいか ADCS がよいか?
**A2**: DC$ は権限が高い。ADCS へ relay すれば直接 DC 証明書を取得 = ドメイン取得。LDAP へ relay すれば任意オブジェクトへ RBCD を設定できる。ADCS が到達可能なら ADCS を優先。チェーンが短い。
**Q3**: SMB へ落として直接 LSASS を取れるか?
**A3**: 取れるが、対象が非署名で、relay 身元が対象ローカルで管理者である必要がある。マシンアカウントは他マシンに対して通常ローカル管理者でないため、relay-to-SMB 実行は制限されやすい。ユーザー管理者認証情報の relay により適する。
**Q4**: 全高価値落とし先が到達不能/遮断された場合は?
**A4**: 落とし先を降格して組み合わせる。LDAP への relay は読み取り専用でも全域情報を dump でき、次の手への道を作る。または MSSQL/他の統合認証サービスへ relay する。「一段階でドメインへ」が取れないなら「情報と足場」を先に取る。

### RBCD(リソースベース制約付き委任)の乗っ取り判断
**Q1**: relay または書き込み権で、あるホストオブジェクトへの書き込み権を取得した。乗っ取りたい。RBCD を使うか?
**A1**: 使う。対象ホストオブジェクトの msDS-AllowedToActOnBehalfOfOtherIdentity に、自分が制御するマシンアカウント SID を書き込み、その後そのマシンアカウントで S4U2self+S4U2proxy を行い、任意ユーザー(例: administrator)の対象サービスへのチケットを偽造する。判定基準:管理者として対象 CIFS/HOST へアクセスするチケットを発行できれば乗っ取り。
**Q2**: 「自分の制御するマシンアカウント」が必要。どこから得る?
**A2**: マシンアカウント割当量 >0 なら自建する。そうでなければ取得済みホストのマシンアカウント hash を使う。これが RBCD の必須前提。
**Q3**: 割当量が 0 で現成のマシンアカウントもない?
**A3**: shadow credentials 経路へ転換する(msDS-KeyCredentialLink を書いて直接対象身元で PKINIT)。追加のマシンアカウントが不要で、対象への書き込み権だけでよい。同じく「書き込み権あり → 乗っ取り」の別の脚である。
**Q4**: RBCD を設定したが S4U のチケット交換が失敗する?
**A4**: よくある落とし穴:対象アカウントが機微/委任不可とマークされている(Protected Users、"account is sensitive")ため S4U2self が転送可能チケットを返さない。保護されていない別の対象サービスへ切り替えるか、証明書/PtH 経路で委任制限を迂回する。

### 「これは本当にドメインコントローラか」を判断して誤った対象を打たない
**Q1**: DC 専用脆弱性を打ちたい。対象 X が本当に DC であって一般メンバー機でないことをどう確認する?
**A1**: 多シグナルを交差させる。88(Kerberos)+389/636(LDAP)+445+SRV レコード(_ldap._tcp.dc._msdcs)+ netbios ドメインロールを同時に満たすか。判定基準:445 だけでは誤判定する。Kerberos+LDAP+DNS SRV の三つが揃って初めて DC。
**Q2**: メンバー機へ誤って打つとどうなる?
**A2**: Zerologon で一般メンバー機のマシンアカウントを空化しても DCSync 価値がない(メンバー機に複製権なし)。痕跡を無駄に残し、そのマシンを崩壊させる恐れもある。noPac/DCSync 系は必ず DC を狙う。
**Q3**: 環境内の DC が NAT/多ネットワークセグメントの背後に隠れて識別しにくい?
**A3**: LDAP/DNS から configuration パーティションの DC リスト(nTDSDSA オブジェクト)、SYSVOL 参照を読み、権威ある DC リストを取得する。ポート推測に頼らない。
**Q4**: どのマシンが DC か全く確認できない?
**A4**: 受動へ転換する。ドメイン内ホストが自ら露出するのを待つ。Kerberos トラフィックを取得して TGT リクエストがどの IP へ送られるかを見る。それが DC である。能動検知をトラフィックで代替する。

### Kerberos 面 vs NTLM 面の脆弱性の経路選択
**Q1**: 対象ドメインが NTLM を大幅に無効化/制限している。認証不要でまだ打てるか?
**A1**: Kerberos 面へ切り替える。noPac、Certifried、Kerberoast、AS-REP roast、委任悪用はすべて Kerberos ベースで、NTLM 無効化の影響を受けない。判定基準:環境が NTLM を無効化すると relay/PtH 系が全滅し、Kerberos 系はまだ生きている。
**Q2**: 逆に Kerberos 強化が厳しい(AES-only、Protected Users が広範)場合は?
**A2**: NTLM relay 面(NTLM がまだ開いていれば)または証明書面へ戻る。二大認証プロトコルの強化はしばしば非同期で、どちらかの面が弱い。
**Q3**: どちらの面が弱いかを素早く判断するには?
**A3**: ポリシーの痕跡を見る。大量の Protected Users/AES-only = Kerberos 強化が強い。SMB/LDAP 署名が非強制 = NTLM 面が弱い。偵察の結論で攻撃面を選ぶ。両面に硬く当たらない。
**Q4**: 両面とも非常に硬い場合は?
**A4**: 設定/人の次元へ転換する。誤った ACL(BloodHound で shortest path を探す)、GPO 悪用、サービスアカウントの弱いパスワード、散在する平文認証情報。強化の厳しいドメインは、しばしばプロトコル脆弱性ではなく設定の怠慢で敗れる。

### WebDAV が HTTP relay をトリガーする場面
**Q1**: ADCS-HTTP へ relay したいが、coerce が出すのが SMB(445)認証。HTTP に変換できるか?
**A1**: 対象マシンが WebClient(WebDAV)サービスを有効化していれば、SMB ではなく HTTP 認証を発起させ、HTTP エンドポイントへ relay できる。判定基準:対象が WebDAV を開いている(PROPFIND で検知、または 445 以外の兆候を見る)。
**Q2**: 対象に WebClient を起動させるには?
**A2**: WebClient はしばしば要求に応じて起動する。searchConnector/library ファイルを使うか、対象に WebDAV UNC パスへアクセスさせてロードをトリガーし、その後 coerce する。
**Q3**: 対象がそもそも WebClient を未インストール/無効化している?
**A3**: 本来 HTTP を使う coerce へ転換するか、SMB relay のみ可能と受け入れて ADCS-HTTP を諦め、LDAP へ relay する。トリガーできない経路で時間を費やさない。
**Q4**: WebDAV relay も成立せず全体が詰まった?
**A4**: coerce プロトコル選択の直交次元へ戻る。coerce されるホストを変える(WebClient が開いているマシンを探す)、またはより高権限の coerce 対象へ変えて relay 収益を上げる。

### Zerologon のアラート特徴と EDR 対抗
**Q1**: 対象に SOC/EDR がある。Zerologon を打ちたい。リスク点は?
**A1**: 最も響くアラートは、短時間に大量の Netlogon 認証失敗(平均約 256 回の試行で全ゼロ成功に当たる)で、4776/5805 の嵐と異常検知を誘発する。判定基準:高失敗率認証は明確な IOC である。
**Q2**: 試行回数を減らせるか?
**A2**: 試行回数は確率で決まり圧縮しにくい。できるのは監視が低い時間帯を選び、並行数を制御すること。ただし本質的に Zerologon は隠密性が悪く、SOC が成熟していれば費用対効果が低い。
**Q3**: 空化+復元の過程には他にどんな痕跡がある?
**A3**: マシンアカウントパスワード変更イベント(4742)、DCSync のディレクトリ複製イベント(4662 with replication GUID)。これらは高忠実度の検知点で、成熟したブルーチームは監視する。
**Q4**: 「うるさすぎて打てない」と判断した後は?
**A4**: 隠密な Kerberos 面の経路へ転換する。noPac/証明書/委任悪用が生むログは正常業務に近く、信頼度が低い。隠密優先なら、低アラート脆弱性で Zerologon を置き換える。

### DC を打った後:永続化方式の選択
**Q1**: 認証不要脆弱性からドメインコントローラ級の権限を取得した。永続化をどう確立する?
**A1**: 階層化する。短期は DA 認証情報/DC$ で直接操作。中期は krbtgt を取ってゴールデンチケットを作る(オフラインで任意チケットを発行)。長期は DCShadow、ADCS バックドア証明書(CA 秘密鍵を盗んで任意ユーザーの長期証明書を発行)を検討。判定基準:ゴールデンチケットは krbtgt の非ローテーションに依存し、CA バックドアの方が持続的。
**Q2**: ゴールデンチケットと CA 秘密鍵バックドア、どちらが隠密か?
**A2**: CA 秘密鍵バックドアの方が隠密かつローテーション耐性が高い。krbtgt を二度変更しても、盗んだ CA 秘密鍵でまだ正当な証明書を発行して認証できる。ゴールデンチケットは krbtgt を二度ローテーションすると失効する。
**Q3**: krbtgt 自体に触れるべきか?
**A3**: hash を取ってゴールデンチケットに使うのはよいが、krbtgt をリセットしない(全域 Kerberos を中断し、巨大な動きで、防御側の削除動作であり、攻撃側がトリガーすべきではない)。
**Q4**: 永続化が消された(krbtgt ローテーション済み、証明書失効)場合は?
**A4**: 多点冗長へ転換する。非 DC アセットに事前配置した足場、予備の低調サービスアカウント、ACL バックドア(目立たないアカウントに DCSync 権を付与)。単一永続化が抜かれても冗長で復帰する。

### 認証不要脆弱性による DC サービス中断の緊急対応
**Q1**: Zerologon/coerce の過程で DC が異常になった(複製エラー、認証の揺れ)。深刻度をどう判断する?
**A1**: まず可逆かを判断する。マシンアカウントパスワード不一致(復元可能)か、サービス崩壊/ブルースクリーン(不可逆)か。判定基準:パスワード整合を再建できれば制御可能。LSASS/サービス崩壊は事故を起こしている。
**Q2**: パスワード不一致による複製中断だと判明した?
**A2**: 即復元を実行する(AD 内の DC$ パスワードをローカルと一致するよう書き戻す)。複製は通常自己回復する。これが実行前に復元スクリプトを準備しなければならない理由である。
**Q3**: 既に不可逆崩壊した場合は?
**A3**: これ以上の破壊を一切止め、影響面を評価し、取得済み認証情報を保持し、他の健全な DC で目標を続行する。「もう一度打って修復」を試みない。事故を拡大する。
**Q4**: 認可範囲は自分に続行を許すか?
**A4**: コンプライアンス判断の次元へ転換する。計画外中断を起こしたなら、レッドチーム規約に従い速やかに顧客連絡先へ通報/一時停止する。これ自体がプロのレッドチーム判断の一部であり、純技術的な転換ではない。

### RODC(読み取り専用ドメインコントローラ)場面の特殊判断
**Q1**: 把握した DC が RODC(読み取り専用ドメインコントローラ)だ。認証不要脆弱性はまだ適用されるか?
**A1**: 大きく異なる。RODC は全パスワードを保持せず(許可されたアカウントだけをキャッシュ)、複製は単方向で、DCSync で完全なドメイン機密を取れない。判定基準:RODC と確認したら、書き込み可能 DC を打つような一括は期待しない。
**Q2**: RODC をどう識別する?
**A2**: そのマシンアカウントが Enterprise/Domain Controllers 特殊グループにいるかを見て、msDS-Reveal 関連属性、krbtgt が RODC 専用の krbtgt_<id> かを読む。
**Q3**: RODC を打ち落として何が取れる?
**A3**: キャッシュされたアカウント認証情報を取れる(パスワード複製ポリシーの許可リストを見る)。ローカルサイトのユーザー/マシンを含むことが多い。横展開の踏み台にはなるが、全域とは等しくない。
**Q4**: RODC の価値が限定的。どこへ転換する?
**A4**: 書き込み可能 DC へ転換する。RODC がキャッシュした認証情報で横展開するか、RODC の管理者委任チェーンから書き込み可能 DC へ通じる道を探す。RODC は本物の DC へ至る中継であり終点ではない。

### マシンアカウント割当量:noPac/RBCD の見えない門
**Q1**: noPac や RBCD を使う計画だ。重要な前提を先にどう確認する?
**A1**: ms-DS-MachineAccountQuota を照会する(LDAP でドメインルート属性を読む)。デフォルト 10 だがセキュリティベースラインで 0 に変更されることが多い。判定基準:>0 かつ一般アカウントあり = 自建マシンアカウント可。=0 = この脚は断たれ、現成のマシンアカウントを別途探す。
**Q2**: 割当量 >0 だがアカウント作成が拒否される?
**A2**: 追加の ACL 制限があるか、単一ユーザー上限に達した可能性。別のドメインアカウント身元で作成するか、OU 単位で禁止されていないかを確認する。
**Q3**: 割当量 =0 で、どうしてもマシンアカウント身元が必要な場合は?
**A3**: 既存マシンアカウントの認証情報を取得する方向へ転換する。マシンアカウントを relay する、ホストを取ってそのマシンアカウント hash をエクスポートする、または coerce 後に relay する。「新規作成」の制限を迂回する。
**Q4**: マシンアカウント身元をどうしても取れない場合は?
**A4**: 純ユーザー身元の経路へ転換する。証明書 ESC1(ユーザーテンプレートが SAN を指定可能)、Kerberoast、ACL 悪用。マシンアカウント依存のチェーンを全部諦める。

### 認証不要だがネットワーク不可達:セグメント分断の転換
**Q1**: 脆弱性は完全に適用可能(未パッチ)だが、DC への 445/135/389 がファイアウォール/セグメント分断で遮られた。どうする?
**A1**: 認証不要脆弱性の前提はネットワーク到達可能性。まずどの層で遮断されたかを確認する。ACL、VLAN 隔離、ホストファイアウォール。判定基準:「DC へ行ける」中間ホストを探して踏み台にする。
**Q2**: DC へ直結できる踏み台をどう探す?
**A2**: 制御済みホストからそのルート/隣接を見て、どのセグメントが DC の重要ポートへ行けるかを走査する。業務サーバー、管理踏み台機は通常 DC への経路を持つ。
**Q3**: 踏み台を取得後、どう打つ?
**A3**: 踏み台上にポート転送/SOCKS プロキシを張り、認証不要脆弱性ツールのトラフィックをプロキシ経由で DC へ送る。自分を「打てる位置」へ移すのに相当する。
**Q4**: どのホストも DC へ行けない(厳格な分断)場合は?
**A4**: DC を直接打つのでなく認証情報窃取へ転換する。業務区で認証情報を取り、管理者を釣り、スクリプト内のサービスアカウントパスワードを探し、DC へ「合法的にログオン」できる認証情報を取得して、認証情報で分断を越える(認証トラフィックが許される場合)。脆弱性で壁を穿つのではなく。

### 認証不要権限昇格の優先順位総合(収益/リスク/隠密)
**Q1**: 複数の認証不要経路の可能性を同時に持つ。優先順位をどう付ける?
**A1**: 三次元で採点する。成功の確実性、破壊リスク、アラート強度。一般的な順序:証明書チェーン(ESC8/ESC1、ゼロ破壊、隠密) > noPac/shadow creds(ゼロ破壊、中程度の痕跡) > relay-to-LDAP/SMB > Zerologon(高破壊高アラート、最後に検討)。判定基準:同等収益なら破壊最小・最も静かなものを選ぶ。
**Q2**: 時間が逼迫し、中断を許す競技/演習場面では変わるか?
**A2**: 変わる。中断を許し速さを求める場合、Zerologon/EternalBlue 系の「一撃必殺」が逆に前へ来る。リスクで速度を買う。優先順位は目標(隠密 vs 速度)で動的に変わる。
**Q3**: どれが成功するか分からない場合の順序付けは?
**A3**: まず低コスト検知(証明書テンプレート列挙、割当量照会、署名検知、Zerologon tester)を行い、検知結果で「成功しそうなもの」を前に並べる。主観的な好みで並べない。
**Q4**: 前列のものが全部失敗した?
**A4**: 予定した順序で逐条降格して試し、失敗するたびに環境認識を更新する(なぜ失敗したか → 強化点はどこか)。最終的に全認証不要脆弱性が封じられたら、認証情報/設定/人の三大直交面へ転換する。「脆弱性面を使い切ったら面を変える」規律を保つ。

### MS17-010 の DC 上での取捨
**Q1**: 旧ドメインコントローラが MS17-010 未パッチの疑い。直接 EternalBlue で system を取る方が楽ではないか?
**A1**: AD 層の複雑なチェーンを省けるが、EternalBlue は DC にブルースクリーンリスクがあり、メモリ破壊型で安定性が悪い。判定基準:認可が中断を許し、対象が古い DC で他の道が全て困難な場合のみ使う。そうでなければ無損傷の AD 論理脆弱性を優先する。
**Q2**: system 取得後、Zerologon と効果は同じか?
**A2**: DC 上で SYSTEM を取得すれば、ローカルで NTDS.dit をエクスポート/DCSync 権と同等で、ドメイン掌握に似た効果。ただし取得方法がより「暴力的」で、サービスを崩しやすい。
**Q3**: 半分まで打って対象がブルースクリーンした?
**A3**: メモリ破壊エクスプロイトの崩壊は通常ソフト復旧できない。記録して損切りする。これが現代のレッドチームが重要アセットに論理脆弱性を優先し、メモリ脆弱性を優先しない理由でもある。
**Q4**: パッチが実は当たっていて EternalBlue が通らない?
**A4**: AD 論理面(Zerologon/noPac/証明書)へ転換する。これらは SMB メモリ脆弱性に依存せず、パッチラインが独立し、ブルースクリーンリスクもない。旧脆弱性が通らなければ主流の認証不要チェーンへ戻る。

### net-NTLM から着地までのタイミングの罠
**Q1**: relay には「リアルタイムでオンラインの認証」が必要だが、自分が取得した認証は一回きり。relay の瞬間にリンクが準備できていることをどう保証する?
**A1**: まず relay サーバーを立て、落とし先を指定してから、coerce/毒入れをトリガーする。認証を「到着したら即転送」させる。判定基準:先に銃を構えてから誘導する。順序が逆なら認証が無駄になる。
**Q2**: coerce は一度しかトリガーできない。その relay が失敗した?
**A2**: 多数の coerce は再トリガーできる(RPC 呼び出しを再送)。失敗したら落とし先を修正して再攻撃する。ただしアラートを避けるため頻度を制御する。
**Q3**: relay は成功したが落とし先操作(RBCD 追加/証明書申請)がタイムアウトする?
**A3**: relay 後の動作チェーンを短縮する。実行する LDAP 変更/証明書リクエストを事前準備し、relay が確立したら一度で完了する。セッション内で臨場判断して時間を無駄にしない。
**Q4**: 繰り返し relay が最後の一歩で失敗する?
**A4**: 落とし先か身元を変える(前述の relay 落とし先判断)、または非 relay の Kerberos 経路へ完全に切り替える。同じチェーンを繰り返し失敗したら、タイミングに死闘せず跳び出す。

### DCSync 権限の最小化バックドア
**Q1**: ドメインを取った。ゴールデンチケットを使わず低調なバックドアを残したい。どうする?
**A1**: 目立たない一般アカウントに DS-Replication-Get-Changes/-All の二つの ACE を単独で付与する(グループメンバーを変更せず、DA を追加しない)。判定基準:このアカウントは以後いつでも全域 hash を DCSync できるが、どの高権限グループにもいない。極めて隠密。
**Q2**: これは DA グループ追加よりどこが隠密か?
**A2**: ブルーチームは特権グループメンバーの変化を監査することが多いが、オブジェクト単位の ACL を監査することは少ない。孤立した複製 ACE は定期検査で見つかりにくい。
**Q3**: ACL 監査で見つかるか?
**A3**: 成熟したブルーチームは BloodHound/ACL 巡回で見つける。より冷門な等価権(特定オブジェクトへの GenericAll など)を選んで痕跡を分散できる。固定パターンだけを使わない。
**Q4**: バックドア ACE が消された?
**A4**: 多機構冗長へ転換する。CA バックドア証明書、非 DC 足場を同時に残す。単一の ACL バックドアが抜かれても、直交する永続化機構で復帰する。

### 認証不要脆弱性が全失敗した後の認証情報スプレー転換
**Q1**: 全認証不要/低認証脆弱性が遮られた。認証情報層に戻るしかない。最も安定して始めるには?
**A1**: まずドメインパスワードポリシー(ロック閾値、観察窓)を読み、スプレーを設計する。一〜二個の高頻度弱いパスワードで全ユーザーに各一回試し、ロック閾値を厳格に下回る。判定基準:遅くてもロックしない(ロック = 露見 + 目標喪失)。
**Q2**: どのパスワードでスプレーする?
**A2**: 季節/会社名/デフォルトパスワード規則 + AS-REP/Kerberoast で解けたパスワードパターンを組み合わせる。汎用大辞書ではなく環境関連語を使う。
**Q3**: 低権限アカウントをひとつスプレーできた。どう拡大する?
**A3**: 任意のドメインアカウントができれば、前述の「低権限前提が必要」な認証不要脆弱性の多くが再び使える(ESC1、Kerberoast、noPac)。ひとつの弱いパスワードが脆弱性チェーン全体を再び開ける。
**Q4**: スプレーも全失敗(ポリシー厳格、弱いパスワードなし)?
**A4**: 人と設定の最後の直交面へ転換する。フィッシングで初期セッションを取る、共有/コードリポジトリ/バックアップの平文認証情報を探す、誤設定サービスを探す。プロトコルもパスワードも硬いとき、突破口は人と運用の怠慢にある。

### AS-REP roasting:認証不要で解読可能 hash を取得
**Q1**: ユーザー名リストはあるがパスワードがない。認証を発起せずにオフライン解読可能な hash を取得したい。どうする?
**A1**: AS-REP roasting。KDC へこれらのユーザーの AS-REP をリクエストする。アカウントが「Kerberos 事前認証不要」(DONT_REQ_PREAUTH)を設定していれば、KDC はそのパスワードで暗号化したチケットブロックを直接返し、オフライン解読できる。判定基準:パスワードが一切不要で、ユーザー名と 88 番ポートへの到達可能性だけで発起できる。
**Q2**: どのアカウントが事前認証を無効化しているかをどう知る?
**A2**: 既に低権限アカウントがあれば LDAP で userAccountControl ビットを照会できる。完全に無認証情報ならユーザー名リストで AS-REP を盲試し、暗号化ブロックが返るのが対象。判定基準:チケットが返る = roast 可能。
**Q3**: roast で hash を取ったが解けない?
**A3**: パスワードが強いことを示す。算力に死闘せず、解読優先度を弱いパスワードの疑い(サービスアカウント、古いアカウント)に置くか、環境語表で定向解読する。解けないならインテリジェンス(アカウントが存在する)として別経路へ進む。
**Q4**: roast できるアカウントがひとつもない?
**A4**: Kerberoast(任意のドメインアカウントが既に必要。SPN サービスアカウントを狙う)または LLMNR 毒入れへ転換する。AS-REP roast は「認証不要」版、Kerberoast は「低認証」版。前者が当たらなければ、まず最初の認証情報を取って後者へ進む。

### mitm6:IPv6/WPAD 乗っ取りで認証を強制
**Q1**: ブロードキャスト毒入れで取れず、ネットワークが比較的クリーン。もっと能動的な認証不要の乗っ取りは?
**A1**: mitm6。多数の Windows はデフォルトで IPv6 を優先し、自動的に DHCPv6 リクエストを送るが、IPv6 ネットワークがないことが多い。DHCPv6 サーバーになりすまして自分を被害者の DNS に設定し、WPAD 乗っ取りと組み合わせて HTTP/SMB 認証を自分へ強制し、net-NTLM を取るか直接 relay する。判定基準:内網で IPv6 が有効(デフォルトでは有効が大半)かつ合法な DHCPv6 がない = 乗っ取り可能。
**Q2**: 認証を乗っ取った後、どこへ relay するのが最も価値がある?
**A2**: LDAP へ relay して被害マシンオブジェクトに RBCD を設定するか、高権限ユーザー認証を relay する。mitm6 は管理者がワークステーションで認証するのを釣れることが多く、価値が高い。
**Q3**: 影響面が大きすぎないか(全網 DNS が乗っ取られる)?
**A3**: 大きい。mitm6 は動きが大きく、正常な名前解決に影響しうる。「うるさい」技術である。認可/隠密要求が高い場合は対象を限定するか短時間だけ使う。長時間開けない。
**Q4**: 対象が IPv6 または WPAD を無効化している?
**A4**: 二層ブロードキャスト毒入れ(LLMNR/NBNS/mDNS)へ戻るか、誘導型 coerce(文書水飲み場、UNC パス)へ転換する。IPv6 面が封じられたら伝統的な名前解決毒入れ面へ戻る。

### ADCS ESC1:ユーザー制御 SAN テンプレートによる権限昇格
**Q1**: 低権限ドメインアカウント + ADCS があるが、coerce/ESC8 条件がない。証明書面にまだ見込みは?
**A1**: 証明書テンプレートを列挙して ESC1 を探す。テンプレートが申請者の SAN カスタマイズを許可(ENROLLEE_SUPPLIES_SUBJECT)し、低権限ユーザーに申請権を付与し、EKU にクライアント認証を含むもの。ヒットすれば、低権限アカウントで SAN を Domain Admin にした証明書を申請し、PKINIT で DA として認証する。判定基準:「任意の SAN を書ける申請可能テンプレート」を見つける = 直接の権限昇格。
**Q2**: 脆弱テンプレートを効率よく見つけるには?
**A2**: 証明書列挙ツール(Certify/certipy find)で全テンプレートの申請権限、SAN フラグ、EKU を列挙し、ESC1〜ESC8 を自動で注記する。手で探さない。
**Q3**: テンプレートはあるが自分のアカウントに申請権がない?
**A3**: 申請権を持つ別の身元(スプレー/roast で取った別アカウント)へ切り替えるか、ESC2/ESC3(他の誤設定)が使えるかを見る。同じ CA 上には複数のテンプレート誤設定がよくある。
**Q4**: 全テンプレートが厳格に設定され、ESCx がない?
**A4**: 証明書面の外へ転換する。noPac、relay、委任悪用。ADCS 設定がクリーンなら、権限昇格の口は Kerberos または ACL 面にあり、証明書面で繰り返し列挙して時間を無駄にしない。

### DC を取った後:ドメイン機密のエクスポート方式選択
**Q1**: 既に DC 上で SYSTEM を持つか DCSync 権を持つ。全域 hash をエクスポートするのにどの方式を使う?
**A1**: 三択。リモート DCSync(secretsdump が複製プロトコルを使い、ファイルを落とさず、最もクリーン) > ボリュームシャドウコピーで NTDS.dit + SYSTEM hive をオフライン解析(DC 上での操作が必要、動き中程度) > ntdsutil/vssadmin スナップショット(システムイベントを残す)。判定基準:リモート DCSync できるなら DC へファイルを落とさない。
**Q2**: なぜ DCSync を優先する?
**A2**: DC へのログオン不要、ディスクファイルを落とさず、ボリュームシャドウ/スナップショット系イベントをトリガーせず、ディレクトリ複製ログ(4662)だけを生み、痕跡が最小で任意の到達可能ホストから発起できる。
**Q3**: DCSync が EDR/トラフィック検知に睨まれた?
**A3**: 「一度取ったら去る」へ転換する。全庫ではなく高価値対象(krbtgt + 少数の DA)だけを同期し、複製イベント量を減らす。または保守窓で行う。全域を一度に引いて大規模複製アラートを誘発しない。
**Q4**: 複製プロトコルが制限され DCSync が通らない?
**A4**: ローカル取得へ転換する。DC 上で LSASS をエクスポート(アクティブセッション認証情報を取得)するか、ボリュームシャドウで直接 NTDS.dit をコピーする。リモート複製面が封じられたらホストローカルのメモリ/ファイル面へ退く。

### coerce トリガーファミリー:ひとつパッチされても別へ
**Q1**: 自分の relay チェーンが強制認証に依存しているが、常用の coerce がパッチされた。チェーン全体を諦めるか?
**A1**: 諦めない。強制認証は脆弱性ファミリーであり、異なる RPC インターフェースを打つ。PrinterBug(MS-RPRN/spooler)、PetitPotam(MS-EFSRPC)、DFSCoerce(MS-DFSNM)、ShadowCoerce(MS-FSRVP)、他 RPC coerce。判定基準:パッチは通常ひとつのインターフェースだけを塞ぐ。別インターフェースの coerce がトリガーできる確率が高い。
**Q2**: 使えるものを素早く見つけるには?
**A2**: 総合 coerce ツール(coercer など)で RPC メソッドを個別に検知し、どれが対象を逆接続させられるかを見る。一括試行してヒットしたら使う。
**Q3**: 対象が spooler を無効化(一般的な強化)していて PrinterBug が通らない?
**A3**: 直接 EFSRPC/DFSNM 面へ切り替える。これらは印刷サービスに依存しない。spooler 無効化は最も一般的な強化で、そこで時間を使わず、デフォルトで次のプロトコルへ換える。
**Q4**: 全 coerce インターフェースがパッチ/無効化された?
**A4**: 「誘導型」認証(強制ではない)へ転換する。UNC パス水飲み場、悪意文書が外向き SMB をトリガー、ユーザー/サービスに自分の共有へアクセスさせる。強制 coerce が全部封じられたら、ソーシャルエンジニアリング/水飲み場で認証を「自発的に」届けさせる。

### クロスドメイン/フォレスト信頼下の認証不要脆弱性の適用境界
**Q1**: 子ドメインを取った。認証不要脆弱性で親ドメイン/他ドメインへ攻めたい。同じ脆弱性はまだ有効か?
**A1**: 「脆弱性の作用範囲」を区別する必要がある。Zerologon/noPac は単一ドメインの DC に作用する。対象ドメイン自身の DC に打たなければならず、子ドメイン DA を取っても親ドメイン DA と自動的に等しくならない。判定基準:まず対象 DC がどのドメインに属するかを確認する。脆弱性はそのドメインにのみ効く。
**Q2**: 子ドメイン DA を取った。親ドメインへの最も省力な道は脆弱性か信頼悪用か?
**A2**: 再び脆弱性を打つより信頼悪用を優先する。子ドメインから親ドメインへは SID History 注入(クロスドメインゴールデン/ダイヤモンドチケットで Enterprise Admin を打つ)、またはフォレスト内信頼の krbtgt を使える。信頼関係自体が設計内の横展開面であり、脆弱性を繰り返すよりクリーン。
**Q3**: 信頼が単方向または外部信頼で、SID filtering が有効な場合は?
**A3**: SID filtering が SID History 注入を遮る。このとき対象ドメイン DC への認証不要脆弱性の直接攻撃へ戻る(その DC が到達可能かつ未パッチなら)。クロスドメイン問題を「別ドメインに対する単一ドメイン打法のやり直し」へ降格する。
**Q4**: 対象ドメイン DC がネットワーク不可達で、信頼もフィルタされる?
**A4**: 認証情報再利用と横展開へ転換する。両ドメイン共用のサービスアカウント/管理者を探す、子ドメイン内で親ドメインリソースへログオンできる認証情報を探す。信頼面も脆弱性面も塞がれたら、「クロスドメインで再利用される人と認証情報」で通す。
