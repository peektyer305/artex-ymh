# ADドメイン内 · ドメインコントローラ直行 vs 横展開での認証情報収集の方向転換判断

### マシンへ上陸した直後、まず身元かネットワークか
**Q1**: ある足場から Windows に入り、シェルを取った。まず何をすべきか?
**A1**: 第一動作は常に `whoami /all` + `net config workstation` + `nltest /dsgetdc:`。判定基準:このマシンはドメインメンバーか。自分はローカルユーザーかドメインユーザーか。どのドメインか、DC は誰か。この三つの答えが後続の全経路分岐を直接決める。ドメインメンバーでなければ急いで AD を攻めない。ドメインメンバーだがローカルシェルなら、まずローカル権限昇格で SYSTEM を取ってから lsass/sam に触れる。
**Q2**: `whoami /all` が自分を低権限ドメインユーザーと示したら?
**A2**: 黄金の起点である。低権限ドメインユーザーでも LDAP を読み取り専用でドメイン全体(ユーザー/グループ/GPO/委任/ACL)を列挙でき、これが BloodHound の敷居である。このとき急いで本機を権限昇格せず、まずドメインプロファイルを採取する。一度の LDAP 照会で明確な横展開経路が見えることがある。
**Q3**: ローカルユーザーで、マシンがそもそもドメインにない場合は?
**A3**: 即座に「このマシンにドメインの痕跡があるか」へ転換する。`cmdkey /list`、DPAPI 保管庫、ブラウザ保存の SMB/RDP 認証情報、`.rdp` ファイル、`runas /savecred` 記録、hosts に手書きのドメイン内名前を調べる。孤島マシンは保守踏み台であることが多く、認証情報マネージャにドメインへ通じる扉が眠っている。
**Q4**: ドメインプロファイルも本機認証情報も空で、マシンが完全に孤立している場合は?
**A4**: 直交次元へ転換する。このマシンのネットワーク位置自体がアセットである。arp/route/netstat で到達できる他のネットワークセグメントを探す。DMZ↔内網の二枚網卡踏み台かもしれない。このとき価値は「私にドメインをくれる」ことではなく、「ドメインをくれるものへ私を届けてくれる」ことにある。

### DC 直行前の最初の冷静な判断
**Q1**: ドメイン内の足場がある。すぐ zerologon/PrintNightmare で DC を打つべきか?
**A1**: まず冷静になる。判定基準:DC のパッチ状態が未知、ブルーチームが全トラフィックを監視しているか、行動窓がどの程度か。zerologon は DC マシンアカウントのパスワードをゼロクリアし、復元しなければドメイン全体を崩壊させ、業務側は一時間以内に必ずアラートする。目標が「ドメイン管理者取得の証明」でない限り、最初の評価は「認証情報を収集して無音で上位へ」に傾けるべき。
**Q2**: では、いつ DC 直行が合理的か?
**A2**: 三条件が同時に成立するとき。(1)フィンガープリントが DC が明らかに未パッチを示す(SMB バージョン、SPN に旧特徴、`nmap --script smb2-security-mode` が古いバージョンを出す)。(2)時間が逼迫し、速攻が必要。(3)復元計画がある(zerologon 後に restore machine password ができる)。ひとつでも欠ければ認証情報収集経路へ転換する。
**Q3**: 最初から認証情報収集の遅攻を選んだが、内網の権限が厳格で認証情報が取れず、後で DC を打ち直しても間に合うか?
**A3**: 通常は間に合うが、「今回の偵察が既に DC のアラートを生んだか」を評価する。LDAP 読み取りのみで、4625/4771 を一度もトリガーしていなければ、後でブルートフォース系経路へ切り替えてもコストは大きくない。逆に、最初から zerologon を打って崩壊させたなら、後で低調に認証情報経路へ進むのはほぼ不可能である。不可逆動作は最後に回す。
**Q4**: DC を全く打てず、認証情報も収集できない場合は?
**A4**: 「信頼関係」という直交次元へ転換する。外部/フォレスト信頼、子ドメイン、Azure AD Connect 同期の有無を見る。主ドメインが打てなくても、子ドメインや対等な提携フォレストが薄弱環であることが多い。横から入って信頼を借りて主ドメインへ刺し戻す方が、DC を硬攻めするより楽である。

### ドメインユーザー認証情報の有無が全体の戦法を決める
**Q1**: 私は「無認証情報段階」と「有認証情報段階」のどちらの列挙をすべきか。これは完全に別の二系統の動作である。
**A1**: 判定基準は極めて明快。`ldapsearch` を匿名で、または手持ちアカウントでドメインオブジェクトを読めるか。読める = 有認証情報段階。読めない = 無認証情報段階。混ぜてやらない。混ぜると、有認証情報段階の動作で無認証情報段階のアラートを誘発する。
**Q2**: 無認証情報段階では何をすべきか?
**A2**: 三つ。(1)無認証 SMB でユーザー名候補を列挙する(RID cycling、NULL session。旧ドメインでは偶に通る)。(2)一般的な姓名辞書で AS-REP roasting を打つ(パスワード不要で、事前認証なしアカウントのハッシュを取得できる)。(3)Kerberos ユーザー列挙を打つ(異なるエラーコードでアカウントの有無を区別)。目的は全て「無」を「有」に変えること。
**Q3**: 有認証情報段階で最も優先すべきことは?
**A3**: ただひとつ。完全な BloodHound 採取。ユーザー/グループ/ACL/GPO/委任/セッションを全取得する。認証情報を持つと意思決定空間が一気に爆発するため、全景図を取らずに打つのは闇雲である。BloodHound が出ると shortest path to Domain Admins が最短経路を直接教えてくれることが多い。
**Q4**: 認証情報はあるがアカウントが制限され、LDAP すら十分に読めない場合は?
**A4**: 「認証情報の昇格」次元へ転換する。このアカウントで何ができるか。SMB 列挙共有(LDAP が制限されても SMB が読めることが多い)、任意マシンへの WinRM/RDP ログオン(一台でも入れれば局面が開ける)、MSSQL サービスアカウント接続(AD を照会できず DB にしか接続できないアカウントもある)を試す。認証情報の「権限面」は多次元であり、LDAP が詰まっても全て詰まったわけではない。

### AS-REP roasting を先に走る価値はあるか
**Q1**: ユーザー名リスト(あるいは推測だけ)を取得した。すぐ AS-REP を打つべきか?
**A1**: 判定基準は二つ。(1)ユーザー名候補があるか(OSINT から推測した姓名形式でも)。(2)自分から KDC へのネットワーク経路が通るか。両方通れば走るべき。AS-REP roasting は有効なパスワードを全く必要とせず、失敗しても KDC ログに 4768 が数件増えるだけで、リスクが極めて低い。
**Q2**: 出たハッシュが解読できない場合は?
**A2**: 固執しない。AS-REP は RC4 ハッシュを使い、弱いパスワードのユーザーは数秒から数時間で解けるが、強パスワードはほぼ不可能。解けないのはこのアカウント群のパスワードが弱くないということで、辞書を増やすのではなく次の次元へ転換する。
**Q3**: 次の次元は何か?
**A3**: 二つの直交方向がある。(a)パスワードスプレー。同じ季節+年+会社名のパスワードで全アカウントをスプレーし、「事前認証を無効化したアカウント」ではなく「パスワードポリシーが甘いアカウント」を狙う。(b)Kerberoasting。任意の有効なドメインアカウントが既にあれば、全 SPN アカウントに TGS をリクエストできる。サービスアカウントのパスワードは通常、人間系アカウントよりはるかに弱い。
**Q4**: ユーザー名がひとつも推測できない場合は?
**A4**: 「ユーザー名収集」という前置次元へ転換する。kerbrute で一般的な姓名辞書を試す(Kerberos 事前認証エラーコードでアカウントの有無を区別できる)、OWA/Exchange フロントのタイミング差でメールプレフィックスを列挙、または会社公式サイト/GitHub/求人情報から社員の英語名形式を収集する。ユーザー名は目標ではなく弾薬である。

### Kerberoasting をすぐ打つべきか
**Q1**: 既に低権限ドメインユーザーで、BloodHound が数十の SPN アカウントを示す。すぐ一括 Kerberoast すべきか?
**A1**: 打つべきだが、選ぶ。原則:高特権グループメンバーの SPN アカウントの TGS を優先する(BloodHound が直接示す)、RC4 暗号の TGS を優先する(4769 内 encryption type 0x17 は解きやすい)、「最近パスワードを変更した」アカウントを避ける(pwdLastSet が新しすぎるものは解けず無駄)。
**Q2**: 全 SPN が AES 暗号(0x11/0x12)の場合は?
**A2**: AES TGS も解けるが、速度は RC4 より一〜二桁遅い。判定基準:走る価値があるかは対象アカウントの価値次第。SPN が Domain Admin なら遅くてもやる。普通のサービスアカウントなら次元を変える。
**Q3**: 長く打っても全部解けない場合は?
**A3**: 現実を受け入れ、辞書を増やさない。二方向へ転換する。(a)サービスアカウントが動く具体的なマシンを探し、そのマシンで平文/DPAPI を取る(サービスは LogonType 5 の対話式で動くことが多く、メモリに平文がある)。(b)BloodHound でこれらのサービスアカウントの ACL 権限を見る。パスワードが解けなくても、あるオブジェクトに GenericWrite/WriteDACL を持つことがある。パスワードを解くより権限を直接 abuse する方が速い。
**Q4**: ブルーチームが AES Only + FAST(Kerberos Armoring)を有効化した場合は?
**A4**: Kerberoasting はほぼ無効。完全に直交する次元へ転換する。認証情報収集(mimikatz/DPAPI)、委任悪用、ADCS 証明書経路、GPO 権限悪用。完全に対抗された経路で時間を消費しない。

### DC バージョンのフィンガープリントが古すぎる。直接扉を壊すか?
**Q1**: nmap が DC に SMB1 が開き、システムバージョン 2008 R2 と示す。直接 MS17-010 で一発か?
**A1**: 止まる。まず三つの反問に答える。(1)このマシンは本当に DC か、それとも名前に DC を含むがただのファイルサーバーか。(2)EternalBlue で DC が崩壊した場合、復元策はあるか。(3)ブルーチームに EDR はあるか。古いシステムは EDR がないことを意味しない。全て通過してから動く。古いシステム+現代 EDR はむしろブルーチームの常套の「ハニーポット化」打法である。
**Q2**: DC と確認し、EDR もない。打つべきか?
**A2**: EternalBlue で DC を打つと極めて高確率でブルースクリーンする。打つなら現代の変種(メモリ注入。DoublePulsar のような古い手法ではない)を使うか、一歩引く。SMB1 が開いているなら、まず zerologon(CVE-2020-1472)または PrintNightmare(CVE-2021-34527)を見る。この二つはクラッシュせず、より隠密で、より徹底的である。
**Q3**: 全部試したが失敗、または不適用の場合は?
**A3**: 「DC 自体」ではなく「DC 周辺」を打つ方向へ転換する。DC 上で動く他サービス(WSUS、CA、Exchange、SCCM)は DC または DC 隣接マシンにあることが多く、そのいずれかを取ればドメイン取得と同等であることが多い。ADCS は特に見る価値がある。ひとつの誤設定テンプレートが万能通行証に等しい。
**Q4**: DC 周辺も全部硬い。まだできることは?
**A4**: 「人」という直交次元へ転換する。ドメイン管理者アカウントはどのマシンにログオンするか。そのマシンで待つ。DC の正門で死闘しない。BloodHound の session データ、イベントログの 4624 からドメイン管理者の足場を逆算し、ドメイン管理者が日常使う運用踏み台をひとつ取ればドメイン管理者を取るのと同じ。

### ADCS の有無が証明書経路を選ぶかどうかを決める
**Q1**: このドメインに ADCS があるか、ESC 脆弱性があるかを素早く判断するには?
**A1**: 三つ。(1)LDAP で `objectClass=pKIEnrollmentService` または `certificationAuthority` を照会。オブジェクトがあれば CA がある。(2)certipy/Certify で一括 `find` し、全テンプレート+ESC 種別マークを直接列挙する。(3)Web Enrollment(HTTP ポート 80/443 の /certsrv)の有無を見る。あれば ESC8 relay が直接使える。
**Q2**: ESC1(SAN 制御可)を発見したが、現在のアカウント権限ではテンプレートを申請できない場合は?
**A2**: 「自分に欠けているのは何か」を判断する。テンプレート ACL が enroll を許可しないのか、申請許可グループに入っていないのか。対応する二経路:(a)BloodHound で「そのテンプレートを enroll できる」グループへ abuse できる道を探し、連鎖的に申請できる権限へ昇格する。(b)別の ESC 種別へ転換する。ESC1-ESC13 は場面が異なり、CA があれば高い確率で少なくともひとつは該当する。
**Q3**: 全 ESC が成立しない場合は?
**A3**: ADCS を諦めず、「CA サーバー自体」へ転換する。CA も通常 Windows サーバーで、CA 秘密鍵ファイルはディスク上にある。CA サーバーのローカル管理者を取得できれば、CA 秘密鍵をエクスポートして任意の証明書を自己署名できる(ESC の外の究極の手)。したがって経路は「テンプレート設定を打つ」から「CA サーバーを打つ」に変わる。
**Q4**: ADCS がまったくない場合は?
**A4**: 証明書経路を工具箱から直接線で消し、考え続けない。Kerberos 委任、ACL 悪用、GPO abuse の三大伝統 AD 権限昇格面のいずれかへ転換する。ADCS は「あれば香る、なければ去る」の選択経路であり、強要しない。

### ローカル管理者を取ったがドメイン管理者ではない。DCSync か横展開か
**Q1**: マシンのローカル SYSTEM を取ったが、現在のログオンチケットにドメイン管理者アカウントがない。どこへ進む?
**A1**: まず分類する。ローカル SYSTEM は三つできる。(a)本機 lsass を dump して本機上の他者の認証情報を取る。(b)本機 SAM/LSA/DPAPI を dump してローカルパスワードと保存されたドメイン認証情報を取る。(c)本機マシンアカウントで一部のドメイン内操作を行う(例: 自分の GPP を復号、Kerberos チケットをリクエスト)。最も速く結果が出るものからやる。
**Q2**: lsass に低権限ドメインユーザーの TGT ひとつだけで、ドメイン管理者の痕跡がない?
**A2**: このマシンに「高特権アカウントが訪問した」証拠があるかを判断する。イベントログ 4624 の LogonType 2/10 のユーザーリスト、C:\Users\ のユーザーディレクトリ、スケジュールタスクの RunAs ユーザー。ドメイン管理者が過去にログオンしたが現在オフラインなら、マシンを「罠」にして戻りを待つ(再起動後に運用担当がログオンする)。
**Q3**: 高権限ユーザーの痕跡がまったくない。横展開を続けるべきか?
**A3**: 判定基準:BloodHound 上でこのマシンから Domain Admins への最短経路は何ホップか。一ホップ直結なら横展開。三ホップ以上は費用対効果が非常に低く、次元を変えるべき。
**Q4**: 次元をどこへ変える?
**A4**: 「このマシンのマシンアカウント」が何ができるかへ転換する。マシンアカウント(MACHINENAME$)は AD 内で身元を持ち、LDAP を照会でき、委任を設定でき、RBCD abuse できる。例えば Resource-Based Constrained Delegation の古典チェーンは「マシン A を制御し、自分に目標マシン B への RBCD を設定し、その後任意ユーザーとして B へアクセスする」。この経路は「横展開ログオン」と完全に直交する。

### SYSVOL に Group Policy Preferences の残骸を発見
**Q1**: SYSVOL の Policies ディレクトリに Groups.xml、Services.xml があり、cpassword フィールドがある。掘る価値は?
**A1**: ある。ただし残骸の囮かを素早く判断する。cpassword は Microsoft の固定 AES 鍵で暗号化され、どんなツールでも秒で解ける。判定基準:解けたパスワードが「運用担当が本当に使いそうなパスワード」(可読性、会社特徴、実業務/時間帯の語を含む)か、それとも汎用辞書の上位十位に入るサンプルパスワードか。後者は八割がたブルーチームが意図的に残したもの。
**Q2**: 解けたのがドメインアカウントのパスワードだ。何に使う?
**A2**: まずこのアカウントがまだ有効かを測る。`ldapsearch` を一度バインドし、読めれば生きている。その後すぐ BloodHound で、このアカウントのグループ、ログオンできるマシン、ACL 特権を調べる。GPP 漏えいアカウントは通常、古い運用アカウントで、権限が予想を超えることが多い。
**Q3**: GPP は全部 cpassword だが、人が読めるパスワードが全く解けない、またはアカウントが既に無効の場合は?
**A3**: SYSVOL の他手がかりへ転換する。SYSVOL はドメイン内の認証済みユーザー全員が読める。GPP だけではない。ログオンスクリプト(.bat/.ps1/.vbs)を探す。ハードコード平文パスワード、UNC パス、内網サーバー名がよくある。MDT/SCCM 関連の設定ファイルを探す。unattend.xml のような初期化パスワードがあるかもしれない。
**Q4**: SYSVOL に利用可能な情報がまったくない場合は?
**A4**: 「NETLOGON 共有 + 他デフォルト共有」へ転換する。またはより徹底的に、LDAP の「フィールド漏えい」へ転換する。ユーザーオブジェクトの description、info、comment フィールドは、運用担当がパスワードのヒント、場合によっては平文を書くことがある。一度の `Get-ADUser -Filter * -Properties description` で宝を掘れることが多い。

### EDR が mimikatz の lsass 取得を遮る
**Q1**: 既にローカル SYSTEM だ。lsass を取ろうと mimikatz を一実行すると即殺される。どうする?
**A1**: 「取る」と「解析」の二動作を分離する。EDR が遮るのは「lsass メモリを読むプロセス + mimikatz 特徴」である。二段階に分ける。まずできるだけ正常な手段(comsvcs.dll の MiniDump、タスクマネージャ dump、silent process exit など)で lsass メモリをファイルに dump し、そのファイルを外へ出してローカルで pypykatz 解析する。EDR は「メモリ注入」より「ファイル着地」に寛容なことが多い。
**Q2**: lsass メモリの dump 自体も遮られる(例: PPL、RunAsPPL が有効)場合は?
**A2**: PPL が遮るのは「ユーザーモードから保護プロセスのメモリを読む」こと。回避法:(a)署名ドライバ(例: RTCore64、mimidrv)をロードしてカーネルから PPL フラグを切る。(b)shtinkering 系の手で先に lsass を silent dump してから取る。(c)lsass を完全に避け、SAM/SECURITY レジストリ hive(HKLM\SAM、HKLM\SECURITY)を取る。ローカルアカウントハッシュと LSA secrets が入っている。
**Q3**: SAM と LSA secrets も現代 EDR に監視されている場合は?
**A3**: DPAPI という完全に直交する経路へ転換する。DPAPI は Windows の認証情報の金庫で、ブラウザ保存パスワード、RDP 保存パスワード、Wi-Fi パスワードが全部入っている。現在のユーザーの masterkey で自分の vault を解け、SYSTEM は全ユーザーのものを解ける。EDR は DPAPI 関連の正常 API 呼び出しにほぼ無反応である。
**Q4**: DPAPI も空、lsass も取れない場合は?
**A4**: 「このマシンは絞り尽くした」と認め、別マシンまたは別次元へ転換する。ずっと突かない。選択肢:(a)EDR カバレッジが薄いマシン(テスト機、老朽サーバー。BloodHound で lastLogon が明らかに古いもの)へ横展開する。(b)coercion(PetitPotam/PrinterBug)へ転換し、他マシンに能動認証させて、認証情報を他人から引き寄せる。

### Kerberos 委任列挙:どの委任を先に見るか
**Q1**: BloodHound が非制約/制約/RBCD の三種の委任オブジェクトを示す。どんな優先順位で見る?
**A1**: 威力と到達可能性を一緒に並べる。非制約(TrustedForDelegation) > RBCD(msDS-AllowedToActOnBehalfOfOtherIdentity 書き込み可) > 制約(msDS-AllowedToDelegateTo)。非制約は目標が一度ログオンすれば TGT を取れる。RBCD は目標マシンの `msDS-AllowedToActOnBehalfOfOtherIdentity` を書ければ S4U 一式が通る。制約は最も制限され、protocol transition かユーザー対話の協力が要る。
**Q2**: 非制約委任を持つマシンを見つけたが、誰もログオンしない場合は?
**A2**: coercion で他人にログオンを強制する。PetitPotam で対象マシン A に自分の制御下マシンへ SMB 認証を強制し、非制約委任と組み合わせて TGT を回収する。判定基準:対象マシンに WebClient サービスがあるか(WebClient は HTTP 認証の LDAP への relay を許可し、組み合わせがより快適)、Print Spooler サービスが動いているか。
**Q3**: RBCD を打ちたいが、現在のアカウントが対象マシンオブジェクトに GenericWrite/GenericAll を持たない?
**A3**: 「対象マシンに書き込み権限を持つアカウントを先に取得する」へ転換する。BloodHound で outbound object control のエッジを逆に調べる。通常数ホップで到達できる。または別の手:ドメイン内マシン X を制御していれば、X のマシンアカウントはデフォルトで自分の属性に書き込み権限を持つ(一部設定下)。自分自身に RBCD を設定してローカル権限昇格できる。
**Q4**: 利用可能な委任設定がまったくない場合は?
**A4**: ACL 悪用次元へ転換する。委任の本質は AD 内の特殊な ACL の組み合わせであり、委任がなくても書き込み可能 ACL がないわけではない。BloodHound で GenericAll/GenericWrite/WriteDacl/AddMember のエッジを調べる。一般ユーザーが高権限グループや高権限ユーザーに意図しない書き込み権限を持つことがよくあり、これらは委任と完全に直交する。

### サーバーにドメイン管理者のログオン痕跡がある
**Q1**: あるサーバーで、イベント 4624 にドメイン管理者アカウントの最近のログオンを見た。即座にこのマシンへ横展開すべきか、それとも列挙を続けるべきか?
**A1**: 即座に全注意をこのマシンへ向ける。冷まさない。判定基準:LogonType は何か。2/10 は対話式/RDP を意味し、メモリにほぼ確実に平文/TGT がある。3 はネットワークログオンで、ハッシュ残留だけの可能性。5 はサービスログオンで、マシンアカウントかサービスアカウントであり本人ではない。前者二つが最優先。
**Q2**: このマシンへどう入る?
**A2**: BloodHound でこのマシンへの最短経路を辿る。直接ログオンできるアカウントがあれば(WinRM/RDP/SMB admin)即ログオン。できないなら、このマシンで動くサービス(MSSQL/IIS/他)を見て、サービス側から本機 SYSTEM へ権限昇格する方が速い可能性がある。
**Q3**: 入ったが lsass にドメイン管理者の認証情報がなく、ログオンイベントだけの場合は?
**A3**: ドメイン管理者が既にログオフしてメモリを消した可能性。判定基準:LogonType 10 の RDP 切断には二種ある。「ログオフ」は綺麗に消すが、「切断のみ」はメモリに残る。ドメイン管理者が「切断のみ」で退出したなら TGT が lsass に残る。全部消えていれば、罠を仕掛けて次回ログオンを待つ。このマシンの日常サービスを改変してログオンをトリガーするか、マシンに小さな故障を故意に起こして運用担当にログオンして調べさせる。
**Q4**: ドメイン管理者が二度とこのマシンにログオンしない(例: 一回限りの排障)場合は?
**A4**: 「このマシンからドメイン管理者を取る」ではなく「このマシンを踏み台にする」へ転換する。このマシンは必ず内網の特定位置(DC へ到達、重要業務システムへ到達)にある。終点ではなく横展開ハブとして扱う。BloodHound に戻り、このマシンからどこへ行けるかを見る。

### MSSQL サービスアカウントで Kerberoast か xp_cmdshell か
**Q1**: BloodHound で大量の MSSQL SPN アカウントを見つけた。パスワード解読かデータベース入口か?
**A1**: 二線並行だが、優先度は現在手元にあるもので決まる。ドメインアカウントがあれば、先に TGS をリクエストしてバックグラウンドで解読を掛ける(どうせバックグラウンドで回る)。同時にフロントで MSSQL へ接続する。MSSQL はデフォルトで全ドメインユーザーの接続を許可するため、ログオンできても全 DB を照会できるとは限らないが、インスタンスの存在は確認できる。
**Q2**: MSSQL に接続したが sysadmin 権限がなく、xp_cmdshell が使えない?
**A2**: MSSQL リンクサーバー(linked server)へ進む。ひとつのインスタンスが他インスタンスへの信頼を設定していることが多く、連鎖していくと sysadmin コンテキストに落ちることがある。PowerUpSQL の `Get-SQLServerLinkCrawl` で一括する。判定基準:一路連鎖していく各ホップの `SRV_LOGIN` が誰かを見る。最後は sa に落ちることがある。
**Q3**: xp_cmdshell を取得した。どの身元で実行する?
**A3**: MSSQL サービスアカウント身元。この身元は LocalService/NetworkService/ドメインアカウントでありうる。判定基準:`SELECT SYSTEM_USER, SUSER_NAME()` と `xp_cmdshell 'whoami /all'` で一目瞭然。ドメインアカウントなら、直接 lsass を dump すればドメインアカウントの完全な認証情報がひとつ手に入る。
**Q4**: MSSQL サービスが NetworkService で、マシン上に他の認証情報がない場合は?
**A4**: 「マシンアカウント身元」という直交経路へ転換する。NetworkService はネットワーク上でマシンアカウント身元として現れるため、マシンアカウントができる全てをできる。任意 SPN の TGS をリクエスト、RBCD 設定、他 SMB への認証など。NetworkService を「低権限の行き止まり」と見なさない。実はマシンアカウントの化身である。

### ドメイン信頼の発見:跨ぐか本ドメインを先に固めるか
**Q1**: `nltest /domain_trusts` または BloodHound で複数のドメイン信頼を発見した。跨ぐべきか、本ドメインでドメイン管理者を先に取るべきか?
**A1**: まず本ドメインを固める。理由:信頼を跨ぐ攻撃は本ドメインの高権限認証情報(例: krbtgt が要る golden across trust、SIDHistory 注入が要る)を必要とすることが多い。本ドメインのドメイン管理者なしでは跨げない。ただし「信頼偵察」を並行して行い、外ドメインの DC、アカウント、名前空間を把握して後続に備える。
**Q2**: 本ドメインがずっと取れないが、外ドメインが弱そうだ。逆操作すべきか?
**A2**: できる。判定基準:外ドメインと本ドメインの信頼方向は何か。双方向、または外ドメインが本ドメインを信頼するなら、本ドメインアカウントは外ドメイン情報を照会できる。逆も同じ。外ドメインに弱点があるなら(例: 未パッチ)、外ドメインから打ち、外ドメインのドメイン管理者を取ってから信頼を借りて本ドメインへ刺し戻す。
**Q3**: SID Filtering が有効で、信頼を跨ぐ golden ticket が使いにくい場合は?
**A3**: 現代の Windows フォレスト信頼はデフォルトで SID Filtering を有効にし、SIDHistory の古い手は無効。TGT delegation across trust(フォレスト信頼が tgtDelegation を有効な場合)または PAM Trust(shadow admin)のような新経路へ転換する。または最も簡単に、外ドメインでも認証情報をひとそろい取得し、信頼による権限昇格に依存せず、二ドメインを独立に打つ。
**Q4**: 信頼が実はアクセス隔離の囮の場合は?
**A4**: 「信頼以外の接続方法」へ転換する。二ドメイン間には VPN、専用線、共有の中間業務システム(例: 共有 Exchange/ファイルサーバー)がよくある。これらの非 AD の横展開面は信頼自体よりはるかに脆いことが多い。ドメイン信頼を唯一のドメイン間ブリッジと見なさない。

### LAPS の展開有無が横展開戦略に影響する
**Q1**: ドメインに LAPS があるか、それが自分にどう影響するかをどう判断する?
**A1**: LDAP で `ms-Mcs-AdmPwd` 属性(古典 LAPS)または `msLAPS-Password` 属性(Windows LAPS)を照会する。オブジェクトがあれば LAPS がある。影響:ローカル管理者パスワードがマシンごとに異なり、pth/平文が一台から他台へ伝染する伝統的横展開経路が断たれる。
**Q2**: LAPS がある場合、どうすべきか?
**A2**: 鍵は「誰が ms-Mcs-AdmPwd を読めるか」。この属性は ACL 保護され、デフォルトでドメイン管理者、Helpdesk グループ、マシン所属 OU の admin だけが読める。BloodHound の `ReadLAPSPassword` エッジを探し、読めるアカウントを取得すれば、一台ずつ平文ローカル管理者パスワードを読める。逆に伝統的 pth より精確である。
**Q3**: 誰も読めず、読めるアカウントへ権限昇格もできない場合は?
**A3**: LAPS が守るのは「ローカル管理者パスワード」であり、「ドメインアカウントがローカルログオンして残した認証情報」を守っていない。転換:横展開を pth に頼らず、「マシンに入ってからマシン上のドメインアカウントキャッシュを取る」に頼る。イベントログ 4624 が誰がこのマシンに来たかを示し、MSCache に彼らのドメインアカウント hash がある。
**Q4**: マシンの EDR が厳しく MSCache を取れない場合は?
**A4**: 完全に非 pth の横展開へ転換する。Kerberos を使う。ドメインアカウントのパスワードかハッシュがひとつあれば、任意マシンの CIFS TGS をリクエストし、直接 Kerberos 身元で接続する。NTLM を経由せず、ローカル管理者パスワードも不要。LAPS は NTLM 伝染だけを遮り、Kerberos は遮れない。

### SMB 445 がなく WinRM 5985 がある。横展開ツールをどう切り替える
**Q1**: 対象マシンの 445 が閉じ、5985 が開いている。psexec/smbexec が使えない場合は?
**A1**: 直接 Evil-WinRM またはネイティブの `Enter-PSSession` に切り替える。判定基準:自分のアカウントが WinRM 認証を通せるか。WinRM はデフォルトで Remote Management Users グループと管理者グループのアカウントだけに接続を許可する。一般ドメインユーザーはデフォルトで接続できない。権限のないアカウントで時間を無駄にしない。
**Q2**: アカウントは接続できるが、EDR が WinRM 側のコマンド実行を遮る?
**A2**: WinRM 認証段階は EDR をトリガーしない。トリガーするのは実行段階である。WinRM を「コマンド」ではなく「データ」の転送に使う。例えば WinRM でファイルをコピーする、WinRM でレジストリを変更して別経路をトリガーする。または AMSI bypass のような手段で PowerShell 層の検知を迂回する。
**Q3**: WinRM も開いていない場合は?
**A3**: 順に試す。RDP(3389。遅いが大部分のコマンドライン検知を回避)、WMI(135+動的高位ポート。wmiexec 方式)、DCOM(MMC20.Application、ShellWindows。冷門だが使える)、SCM リモートサービス作成(445 が完全には無効でない、または RPC over HTTP が要る)。
**Q4**: 全リモート実行経路がファイアウォールで遮られた場合は?
**A4**: 「対象マシンに能動的に出て来てもらう」へ転換する。読める共有に悪意ある LNK/Word/HTA/URL ファイルを置き、運用担当/ユーザーが開くのを待つ。または GPO を乱用する。GPO 書き込み権限があれば、対象マシンへ「起動時実行」タスクを配り、再起動を待つ。逆接続は入站ファイアウォールを完全に迂回する。

### NTLM relay 前の実行可能性判断
**Q1**: NTLM relay をやるつもりだ。まず何を判断すべきか?
**A1**: 三つのスイッチ。(1)対象サービスが signing を強制するか。SMB signing 強制なら SMB への relay は無効。LDAP signing 強制なら LDAP への relay は無効。LDAPS に channel binding(EPA)があれば LDAPS への relay も無効。(2)自分が制御するマシンに対象マシンがアクセスできるか(逆 SMB/HTTP 認証)。(3)認証をトリガーできる coercion 手段があるか。
**Q2**: signing 状態を素早く調べるコマンドは?
**A2**: `crackmapexec smb <target> --gen-relay-list` で signing not required のマシンを直接ふるい出す。これが最速の地図である。この地図と BloodHound を組み合わせれば、「どのマシンへ relay するのが最も価値があるか」が一目で分かる。
**Q3**: signing が全部有効で、SMB/LDAP への relay がどちらも成立しない場合は?
**A3**: ADCS Web Enrollment(ESC8)への relay へ転換する。ADCS の /certsrv は HTTP を使い、デフォルトで channel binding をしない。マシンアカウント認証を relay して証明書を申請すれば、そのマシンの完全な代理認証情報を取得できる。これが現在最も鮮度の高い relay 経路である。
**Q4**: ADCS もない、または ADCS も強化済みの場合は?
**A4**: 「ハッシュを取って解読」という全く別の経路へ転換する。NetNTLMv2 を取得後 relay せず、直接オフライン解読する。パスワードが弱ければ数分で出る。または SMB relay 内の Kerberos relay の新手法(例: LOCAL マシンの CIFS SPN を打つ)へ転換する。これらは signing を迂回する新研究方向である。

### NetNTLMv2 hash を取得後:解読 vs relay
**Q1**: responder/mitm6 が大量の NetNTLMv2 を取得した。hashcat に投げて解くか、その場で relay するか?
**A1**: 一原則がある。relay できるなら relay し、relay できないときだけ解く。理由:relay は対象システム上で直接実行を得られ、パスワード解読が不要。解読が成功しても平文を得るだけで、さらに一手かけて使う必要がある。判定基準:対象環境の signing 状態(前項参照)。
**Q2**: 解読すると決めた。どの hash を先に解く?
**A2**: アカウント価値の高いもの(ドメイン管理者、高権限グループメンバー)を先に解く。マシンアカウント hash は解かない(NetNTLMv2 のマシンアカウント hash はランダム長パスワードで解けない)。判定基準:hash 内の username フィールドでアカウント名が分かる。
**Q3**: 一晩解いても出ない、または環境が NTLM を全面禁止して Kerberos のみの場合は?
**A3**: Kerberos への類似攻撃へ転換する。AS-REP roasting、Kerberoasting、Kerberos relay。これらは NTLM relay と完全に平行な経路で、考え方は同じだが下位プロトコルが異なる。NTLM が取れなければ Kerberos を取る。
**Q4**: 環境に騙せる名前解決がまったくない(mitm6/LLMNR/NBNS 全無効)場合は?
**A4**: 「能動トリガー」へ転換する。coercion(PetitPotam/PrinterBug/DFSCoerce)で対象マシンに能動認証させ、受動スニッフィングに依存しない。coercion は能動的な hash 取得で、ブルーチームのミスを必要としない。

### GPO 変更権限:直接 abuse か後手を残すか
**Q1**: BloodHound が、自分が制御するアカウントがとある GPO に GenericWrite/WriteDacl を持つと示した。即 abuse すべきか?
**A1**: GPO の「作用範囲」を判断する。どの OU にリンクされ、何台のマシン/ユーザーに影響するか。Domain Controllers OU にリンクされた GPO を変更すれば、全 DC でコードを実行できる。これが最も強力な abuse。ある業務 OU にリンクされた GPO は影響面が小さく、後手として残せる。
**Q2**: GPO を具体的にどう abuse する?
**A2**: 三つの典型。(a)Immediate Scheduled Task を追加して対象マシンへ配り即実行。(b)Restricted Groups を変更して自分をローカル管理者グループへ加入。(c)Startup Script を展開。SharpGPOAbuse または pyGPOAbuse で一括する。判定基準:対象マシンの GPO 更新頻度(デフォルト 90 分+乱数 30 分)。
**Q3**: GPO 変更後、ブルーチームが即ロールバックする場合は?
**A3**: GPO 変更監視があることを示す。より隠密な経路へ転換する。既存 GPO を変更せず、無害に見える新しい GPO を作成して目立たない OU にリンクする。または窓期にだけ一時的に GPO を変更して一度だけ実行し、即座に戻す。監査ログが誤操作に見えるようにする。
**Q4**: GPO abuse が検知システムに完全に監視されている場合は?
**A4**: GPO 以外のドメイン制御機構へ転換する。GPO と論理的に等価なもの:ログオンスクリプト(SYSVOL 内の .bat/.ps1)、SCCM 展開、WSUS の悪意パッチ配布。これらの「配布機構」は GPO と直交し、監視盲点がそこにあることが多い。

### ドメイン管理者が失陥機にオンラインログオンしている
**Q1**: マシンを取ったら、ドメイン管理者アカウントが現在オンラインだ。token impersonate か退場を待つか?
**A1**: 即 impersonate する。待たない。判定基準:現在のユーザーセッションがいつ消えるかは完全に制御不能で、次の瞬間ログオフするかもしれない。`incognito` または SharpImpersonation で彼がいる間に token を借りて作業するか、直接 lsass から TGT/平文を抜いてその場で DCSync する。
**Q2**: 彼の token を借りて最も効率的に何をする?
**A2**: 一回の動作で解決する。即 DCSync で krbtgt ハッシュを取る。krbtgt があれば任意のゴールデンチケットを署名でき、以後このドメイン管理者アカウントに依存せず、彼がパスワードを変えても影響しない。欲張って余計なことをせず、一回の動作、素早く入って素早く出る。
**Q3**: DCSync をしたいが、現在のネットワークから DC への RPC 経路が通らない場合は?
**A3**: 「その場で換金」へ転換する。DCSync が通らないなら、一歩引いて impersonate 後の身元で任意の SMB/WMI 操作を行い、その場で自分を Domain Admins グループに加入、または新しい GPO バックドアを設定、または自分の制御下アカウントを Enterprise Admins に加入する。ネットワーク問題が短時間で直るとは期待しない。
**Q4**: ドメイン管理者がその場でログオフした場合は?
**A4**: 「呼び戻す」機会へ転換する。このマシンを故障したように装い、彼/別の運用担当に再ログオンさせる。またはさっき impersonate 時に取ったが使い切っていない情報(キャッシュ NTLM、DPAPI masterkey、ブラウザ cookie)へ転換する。これらは彼のログオン時に残した残余財産である。

### BloodHound データ量が爆発してふるい分けられない
**Q1**: BloodHound が一万オブジェクトを採取し、shortest path 図が読めない場合は?
**A1**: 図を見ず、Cypher クエリを使う。核心問題は三類。(a)`MATCH p=shortestPath((n:User {owned:true})-[*1..]->(m:Group {name:"DOMAIN ADMINS@X"})) RETURN p` でドメイン管理者への経路を探す。(b)`MATCH (n)-[r:GenericAll|GenericWrite|WriteDacl]->(m) WHERE m.highvalue RETURN n,r,m` で高価値対象への書き込み可能 ACL を探す。(c)委任、LAPS を読めるアカウントを探す。この三類クエリで九割の意思決定をカバーする。
**Q2**: 全アカウントに owned マークがない(始めたばかり)。shortest path が使えない場合は?
**A2**: 起点をマークする。自分が現在持つアカウントを手動で owned とマークし(BloodHound で右クリック)、最短経路を調べる。または逆に、Domain Admins から出発し、「外部アカウントが最も abuse しやすい一ホップ」を探し、逆方向に自分が先に誰を取るべきかを特定する。
**Q3**: 経路がすべて「あるマシンへの対話ログオンが必要」だが、そのマシンに入れない場合は?
**A3**: BloodHound の HasSession エッジへ転換する。この対象アカウントがまだ他にどのマシンで session を持つかを見る。同じアカウントが同時に複数ログオンしていることが多く、自分が入れるマシンが一台はある。
**Q4**: BloodHound の採取自体がエラー(タイムアウト、権限不足、切断)する場合は?
**A4**: 分割採取するか、軽量代替へ転換する。ldapdomaindump、adalanche、SharpHound の異なる collection method は軽重がある(DCOnly は DC だけ照会し、他マシンを驚かさない)。または手動 LDAP 照会へ戻り、必要な数オブジェクトだけを照会する。「ツールが動かない」を「インテリジェンスがない」にしない。

### BloodHound 権限がない。手動でどう探るか
**Q1**: BloodHound 採取器が全部遮られ、自分のアカウントも大量オブジェクトを匿名 LDAP 照会できない場合は?
**A1**: 最小露出の手動照会を使う。核心の数本の LDAP filter:`(&(objectCategory=user)(adminCount=1))` で特権ユーザーを探す(adminCount は AdminSDHolder の痕跡)、`(&(objectCategory=computer)(userAccountControl:1.2.840.113556.1.4.803:=524288))` で非制約委任マシンを探す、`(&(objectCategory=user)(servicePrincipalName=*))` で SPN アカウントを探す。毎回一類だけ照会し、一括で引かない。
**Q2**: これらの照会すら権限超過になる場合は?
**A2**: DNS 側面列挙へ転換する。ドメイン内 DNS は匿名照会できることが多い。`nslookup -type=srv _ldap._tcp.dc._msdcs.<domain>` で全 DC が直接出る。DNS でサブネット内のマシン名を逆引きする方が LDAP より緩いことが多い。
**Q3**: DNS もロックされている場合は?
**A3**: SMB 層の列挙へ転換する。`net view /domain`、`net group /domain "Domain Admins"` などの net コマンドは SAMR/LSARPC を使い、権限モデルが LDAP と異なる。LDAP が与えない場合も net が与えることがある。`net user <name> /domain` でユーザー情報をひとつずつ照会する。
**Q4**: 全公式列挙経路がロックされている場合は?
**A4**: 「共有とファイルからインテリジェンスを読む」へ転換する。SYSVOL のポリシーファイル、共有上の残骸 Excel/txt が内網構造を説明し、SCCM/WSUS のログファイルもある。プロトコル照会が動かないとき、静的ファイルにすべてが書かれていることが多い。

### 平文を取得したが pth が使えない:AES Only 環境
**Q1**: ドメインアカウントの平文パスワードを取得した。pth しようとしたら NTLM がドメインポリシーで全面禁止された。どうする?
**A1**: 判定基準をまず明確にする。「KDC が RC4 を受け付けない」のか「ドメイン全体で NTLM 禁止」か。前者は Kerberos チケット暗号だけに影響し、pth over NTLM はまだ使える。後者(NtlmMinClientSec/NtlmMinServerSec 高、NTLM auditing = block)は NTLM を完全に禁止し、Kerberos を使う必要がある。
**Q2**: では平文を使える Kerberos チケットにどう変える?
**A2**: 平文で直接 `getTGT.py`(impacket)で TGT をリクエストする。impacket は暗号アルゴリズム指定に対応する。KDC が AES のみ受け付けるなら、リクエスト時に AES key を使う(平文から PBKDF2 で導出、または直接 AES ハッシュを取って pass-the-key)。
**Q3**: NTLM hash だけで平文がない。AES Only 環境では?
**A3**: pth ではなく pass-the-key へ転換する。pass-the-key は AES256/AES128 key で TGT をリクエストし、pth と意味論が似ているが下位プロトコルは Kerberos。AES key が欠ければ取り方を考える(平文/AES key を取れるマシンで先に取る)。または最も直接的に、解けるならオフライン解読で平文を出して A2 経路へ進む。
**Q4**: 使える Kerberos 経路が完全にない場合は?
**A4**: 横展開認証情報を要らない経路へ転換する。ACL abuse、GPO abuse、委任 abuse は一度の認証(単に LDAP 照会+属性書き込み)で完了し、pth/pass-the-key に依存しない。または ADCS の証明書身元へ転換する。証明書は独自の PKINIT 認証であり、NTLM/伝統 pth と無関係。

### 外部フォレスト信頼のクロスフォレスト打法
**Q1**: 本ドメインのドメイン管理者を取った。forest trust を跨いで親フォレスト/兄弟フォレストへ行きたい。どうする?
**A1**: 判定基準はまず信頼種別と方向。Trust type = Forest かつ双方向ならクロスフォレスト経路がある。single-domain trust は打法が異なる。古典打法:forest trust が SID Filtering を有効にしていない(旧環境)なら、SIDHistory 注入で子ドメインユーザーを親フォレストの Enterprise Admin に装う。SID Filtering 有効(現代デフォルト)ならこの手は無効。
**Q2**: SID Filtering が有効の場合は?
**A2**: TGT delegation across trust へ転換する。一部設定下で forest trust は TGT 転送を許可し、非制約委任と組み合わせてクロスフォレストユーザーの TGT を取れる。またはより実際的に、二つのフォレストが共用するアカウントを探す(運用担当の同じ一団が両フォレストにアカウントを持つ。パスワードスプレーが一発で当たることが多い)。
**Q3**: クロスフォレスト技術経路がまったくない場合は?
**A3**: 「業務側の共有」へ転換する。二つのフォレスト間には共有の Exchange、SharePoint、ファイルサーバー、Jenkins などのアプリシステムがよくある。これらのアプリシステムに両側の認証情報/設定が保存されており、それを取ればフォレストを跨げる。AD 信頼自体に依存しない。
**Q4**: 対象フォレストはそもそも跨ぐ必要がなく、自分が判断を誤った場合は?
**A4**: 冷静に対象定義を評価する。レッドチームの目標は「ドメイン管理者を取る」か「具体的な業務データを取る」か。後者なら、業務データは本フォレストにあるかもしれず、クロスフォレストは時間の無駄。対象定義に戻り、「跨ぐべきか」自体がひとつの意思決定点である。

### ドメイン管理者になったが krbtgt がまだ手元にない
**Q1**: ドメイン管理者になった。即 krbtgt を打ってゴールデンチケットを作るべきか?
**A1**: すべき。理由:ドメイン管理者アカウントはパスワード変更/無効化される。krbtgt ハッシュは永続化の究極の後手である。DCSync で krbtgt を取るのは一度の操作、数秒、リスク極小。原則:ドメイン管理者を取ったら最初に krbtgt DCSync + ハッシュ保存を予備として行う。
**Q2**: krbtgt 以外に何のアカウントハッシュを取る?
**A2**: この類を取る。(a)全域ユーザー hash(オフライン解読可)。(b)重要サービスアカウント hash。(c)DC 本機マシンアカウント(マシン身元永続化用)。(d)trust account hash(信頼を跨ぐ永続化用)。一度の DCSync でフルセットを取る。漏れを残さない。
**Q3**: krbtgt を取った後、即ゴールデンチケットを打って使うか?
**A3**: 即打たない。ゴールデンチケットは現代のログ分析環境では検知されうる(4769 内 TGS の TicketLifetime がポリシー上限を超えると異常)。原則:krbtgt は「緊急時の後手」で、日常の横展開は別アカウントを使う。ゴールデンチケットは別アカウントが全部失効したときだけ使う。
**Q4**: krbtgt を打った後、ブルーチームがどう応答し、自分はどうする?
**A4**: ブルーチームの応答は「krbtgt パスワードを二度変更する」(履歴チケット互換のため二度)。自分の対応:同じく後手を別次元に残す。委任バックドア、GPO バックドア、Skeleton Key、SIDHistory 注入、ADCS 証明書。永続化は一つの卵一つの籠に頼らない。

### DC を打てないが共有の読み書きは自由
**Q1**: DC を打てず、Kerberos 層も厳格に強化されている。しかし内網の大量の共有が Everyone 書き込み可だと発見した。どう使う?
**A1**: これは低コスト高レバレッジである。判定基準:どの共有がユーザー/サービスに定期的にアクセスされるか。これが、自分が置いた悪意ファイルが「消費」されるかを決める。共有上のファイルの最近の変更時刻とアクセス頻度を見て、アクティブなものを選ぶ。
**Q2**: 具体的にどんな悪意ファイルを置く?
**A2**: 投下先を選ぶ。(a)LNK ファイルで UNC パスを指し、SMB 認証をトリガーして relay と組み合わせてハッシュを回収。(b)悪意 Office/PDF。ユーザーが開く必要がある。(c)SCF ファイルは歴史的に認証をトリガーできる(新システムは修正済みだが旧ドメインでは偶に当たる)。(d)共有上に既にある正当スクリプト(例: ある部門の日常 .bat)を置き換え、次回実行が自分のものになる。
**Q3**: Everyone 書き込み可だが誰も開かず、誰も実行しない場合は?
**A3**: 「コード実行できる」囮ではなく「認証をトリガーできる」囮へ転換する。UNC パス類ファイル(LNK/URL/desktop.ini/library-ms)はファイルが一覧されるだけで認証をトリガーし、クリック不要。アクティブ共有のルートに置けば、ディレクトリに入っただけで中招する。
**Q4**: 共有上で機微操作が起きず、ブルーチームも開かない場合は?
**A4**: 「能動トリガー」へ転換する。自分が制御できるユーザーアカウント(低権限でも)を探し、そのアカウント下で一度アクセスをシミュレートして、彼自身を被害者にする。または共有内容自体へ転換する。誰も開かなくても、共有上のファイルに設定ファイル、ログ、バックアップファイルがあり、直接読むだけでインテリジェンスになる。実行は不要。

### ドメインコントローラが隔離セグメントにあり、直結が通らない
**Q1**: 内網をスキャンして DC が隔離サブネットにあるのを発見。自分のセグメントから行けない。どうする?
**A1**: 判定基準をまず明確にする。ネットワーク層隔離(ルート不通/ファイアウォール遮断)か、プロトコル層隔離(ポート不通)か。対応する二経路。ネットワーク層:二枚網卡踏み台機(例: 運用端末が両セグメントに通じる)を探す。プロトコル層:DC セグメントのどのポートが自分のセグメントに開いているか(RPC/LDAP/HTTPS など)を見る。
**Q2**: 二枚網卡マシンを見つけたが、入る権限がない場合は?
**A2**: このマシンを次の横展開対象にする方向へ転換する。これは「必ず取るべき」重要ノードである。ドメイン管理者の痕跡がなくても、そのネットワーク位置自体が全努力に値する。BloodHound + 二枚網卡対象 = 明確な攻略方向。
**Q3**: 二枚網卡マシンがまったくない場合は?
**A3**: アプリ層のセグメント越えへ転換する。DC セグメントに web アプリ、Exchange、SharePoint などがあり、自分のセグメントからアクセス許可されていることがある。これらのアプリで穴を開ける。または認証プロトコル自体を利用してセグメントを越える。DC セグメントのサービスが自分のセグメントへ LDAP/HTTP 照会するなら、その出てくる経路で打ち返す。
**Q4**: 隔離が徹底的で、どんなセグメント越え経路もない場合は?
**A4**: 「DC セグメントに直接打てない」と認め、「DC セグメントの管理者を打つ」へ転換する。管理者の運用端末こそ弱点である。彼らはオフィスセグメントから RDP/SSH で DC セグメントへジャンプする。運用端末を取る = DC セグメントへ入るトークン/RDP 接続/RDP 保存認証情報を取得。踏み台は常に直接壁を穿つより容易である。

### サービスアカウントのパスワードはあるがマシンにログオンできない
**Q1**: サービスアカウントのパスワードを解読したが、RDP/WinRM が全部拒否。何をすべきか?
**A1**: サービスアカウントはしばしば「対話ログオン不可」に制限される(Deny logon locally / Deny logon through RDP)。しかしアカウントが無用なわけではない。判定基準:このアカウントが LDAP でどんな権限を持つか、どんな SPN を持つか、どんなサービスに接続できるか。
**Q2**: 具体的に何ができる?
**A2**: 最低四つ。(a)それで LDAP 照会を実行。元のアカウントより権限が大きいことがある。(b)任意 SPN の TGS をリクエスト(Kerberoast 収集)。(c)委任設定があれば、その委任身元を借りて他アカウントの TGT を得る。(d)あるオブジェクトに ACL があれば、マシンにログオンせず直接 ACL を abuse する。
**Q3**: 全部だめで、このアカウントが純粋に低権限サービスアカウントの場合は?
**A3**: 「このアカウントがどのマシンで動くか」へ転換する。サービスアカウントの背後には必ずプロセスがある。そのプロセスがあるマシンのメモリに、その認証情報がある。逆にそのマシンを探す。そのマシン上の他の認証情報(他サービス、他ログオンユーザー)こそ宝である。アカウント自体は道標で、マシンが鉱脈である。
**Q4**: 対応するマシンも見つからない場合は?
**A4**: パスワード再利用検知へ転換する。サービスアカウントのパスワードはしばしば他アカウントと再利用される(運用担当が手を抜く)。この平文で全他アカウント(個人アカウント、他サービスアカウントを含む)をスプレーする。パスワード再利用は弱い環境で最良のレバレッジである。

### Print Spooler / WebClient coercion のどちらを選ぶ
**Q1**: 対象マシンに認証を coerce したい。PetitPotam、PrinterBug、DFSCoerce のどれを先に試す?
**A1**: 判定基準は「対象マシンでどのサービスが動いているか」。Print Spooler サービスが開いていれば PrinterBug。EFSRPC エンドポイントが開いていれば PetitPotam。DFS があれば DFSCoerce。rpcdump/impacket で一括してエンドポイントを列挙する。
**Q2**: 全部トリガーできる。どのマシンへ coerce する?
**A2**: 「誰に認証させるか」ではなく「自分が制御するどの relay 点へ認証させるか」である。判定基準は自分の relay の下家が何ができるか(relay 意思決定チェーン参照)。対象 DC を認証させ、自分の ADCS Web への relay に回せば、ESC8 で直接 DC 証明書を取得し、一段階で決着する。
**Q3**: 対象マシンがこれらの coercion エンドポイントを全部無効化している場合は?
**A3**: WebClient サービスの HTTP coercion へ転換する。WebClient は WebDAV を許可する。対象が開いていれば(Office を入れたマシンによくある)、HTTP 認証を強制でき、LDAP への relay は SMB relay より優れることもある(HTTP に signing 概念がない)。
**Q4**: 全 coercion が塞がれた場合は?
**A4**: 受動的 poisoning へ転換する。共有上に罠ファイル(LNK/URL が認証をトリガー)を置くか、mitm6 で IPv6 DNS 詐称により WPAD リクエストを奪う。これらは coercion トリガーを要らず、内網 IPv6 がデフォルト有効であるという天然の欠陥である。

### 撤退時に何を消し、何を残すか
**Q1**: 目標達成。何を消し、何を残す?
**A1**: 二層に分ける。攻撃痕跡は消す、永続化は残す。攻撃痕跡は一時アップロードしたツール、変更した設定(想定外のもの)。永続化は仕込んだ後手(最低三本:krbtgt 在手、隠れて特権グループへ加えたドメイン管理者アカウント、GPO/Startup Script バックドア、ADCS 証明書身元)。判定基準:ブルーチームが復盤したとき、自分が静かに戻れるか。
**Q2**: 具体的に何を消す?
**A2**: ツールファイルを消す、イベントログの明らかな異常項目(4624/4672/4688 の自分のプロセス)を消す、Kerberos チケットキャッシュを消す(klist purge で TGT を残さない)、一時作成アカウントを消す(永続化用でない限り)。過剰に消さない。大量のイベントログ消去自体が異常で、逆に露見する。
**Q3**: ブルーチームがオンラインになり、緊急対応を始めたら?
**A3**: 即「戦果拡大」から「永続化確保 + 撤退」へ切り替える。判定基準:ブルーチームの応答速度が、自分がどれだけ動けるかを決める。ノイズの大きい動作(ポートスキャン、ブルートフォース、大規模ログオン)を全部停止し、最も隠密な経路一本だけ残す(例: ADCS 証明書身元。NTLM を経ず pth を経ず、ログがほぼ残らない)。ブルーチームの清掃方法を観察する。
**Q4**: ブルーチームが既に krbtgt を変更、アカウントを無効化、IP を封鎖し始めたら?
**A4**: 「このラウンドは終了」と認めるのが最も重要な意思決定のひとつ。復盤へ転換する。どの永続化が撤去され、どれが生きているか、次回同じ経路で攻撃面を再利用できるか。未練を残さない。レッドチームの真の勝利は「ずっと居座る」ことではなく、「毎回目標達成、復盤コスト最小、次回再挑戦できる」ことにある。

### ドメイン内 DNS で重要アセットを逆引きする
**Q1**: ドメインに入った後、LDAP 以外に低ノイズで高価値マシンを探れる経路は?
**A1**: DNS。DC は通常 DNS を兼ね、ドメインユーザーはデフォルトで SRV レコードと大量の A レコードを照会できる。判定基準:`_ldap._tcp.dc._msdcs.<domain>` で全 DC を直接列挙、`_kerberos._tcp.<domain>` で KDC、`_gc._tcp.<domain>` でグローバルカタログ。さらに各種 sql/exchange/autodiscover の SRV レコードが重要業務の場所を直接示す。
**Q2**: SRV にない重要マシン(SCCM、Jenkins、踏み台機など)をどう探す?
**A2**: DNS ドメイン名辞書列挙へ転換する。一般的な運用命名(mgmt/jump/bastion/sccm/wsus/jenkins/backup/ca01/dc01)と会社プレフィックスを組み合わせて A レコードを照会する。DNS 照会自体はほぼ怪しいログを残さない(正常なアプリ照会と区別不能)。最も静かな列挙方式である。
**Q3**: ドメイン内で DNS scavenging が有効、または一般ユーザーの照会を制限している場合は?
**A3**: 逆引きへ転換する。zone transfer はよく無効化されるが、逆引き zone は開いていることが多い。`dnsrecon -r <subnet>` でセグメント全体を逆引きし、全アクティブマシンの名前を取得できる。また逆引き照会は日常トラフィックにより似ている。
**Q4**: DNS が全面ロックされている場合は?
**A4**: mDNS/LLMNR/NBNS の受動スニッフィングへ転換する。これらのプロトコルは内網でデフォルト有効で、応答トラフィックが自然にマシン名とユーザーセッション情報を漏らす。またこれらのプロトコルは同時に poisoning 攻撃面でもある。受動スニッフィングができないなら能動 poison もできる。一石二鳥である。

### DHCP/mitm6 IPv6 攻撃面の判断
**Q1**: 内網で mitm6 を起動すべきか。この動作のノイズはどの程度?
**A1**: 判定基準:対象ネットワークで IPv6 が有効か。現代の Windows はデフォルトで IPv6 を優先し、内網の九割のドメイン環境は「IPv6 未設定」でも IPv6 リクエストに応答する。リスク:mitm6 は能動詐称であり、一度 IDS が DHCPv6 大量応答を検知すれば即アラート。窓期は短く、収益が一致しなければならない。
**Q2**: いつ起動する価値がある?
**A2**: 二つの前置条件。(1)組み合わせる relay 先がある(例: LDAP または ADCS ESC8)。(2)ドメイン内マシンの IPv6 リクエストを受信できるネットワークセグメントにいる。mitm6 は単独で走っても無意味。必ず ntlmrelayx と組み合わせて、取得したマシン認証を AD/ADCS へ relay する。
**Q3**: ブルーチームがクライアント IPv6 を無効化、または IPv6 RA Guard を展開した場合は?
**A3**: IPv4 側の等価経路へ転換する。LLMNR/NBNS poisoning(responder)。原理は似ており、名前解決リクエストを奪って NTLM 認証を回収する。IPv4 poisoning の取得率は通常 IPv6 より低いが、より汎用的である。
**Q4**: 全名前解決層攻撃が検知/無効化された場合は?
**A4**: 「poisoning 不要の認証取得」へ転換する。coercion(前述の PetitPotam の項)、共有罠、誤設定の SPN サービス。名前解決詐称は opportunistic で、coercion は deterministic で後者がより信頼できる。

### 「ドメイン管理者を本当に取る必要があるか」を判断する
**Q1**: 長く打ってもドメイン管理者に届かない。突き続けるか、目標を再評価するか?
**A1**: 立ち止まって問う。レッドチームの実際の目標は何か。ドメイン管理者は「手段」であって「目的」ではない。目標が財務システムのデータ、ソースコードリポジトリ、顧客データベースなら、それらのシステムのローカル管理者/アプリ管理者がドメイン管理者より直接的であることが多い。
**Q2**: 「局所権限」で足りるかをどう判断する?
**A2**: 対象データ/システムのアクセス経路を列挙する。(a)どの身元が必要か。(b)その身元を何人持つか。(c)自分からその人までどれくらいか。BloodHound は対象オブジェクトで逆方向に最短経路を調べられる。終点を Domain Admins に設定しなくてもよい。
**Q3**: 目標が「ドメイン管理者取得の証明」(競技/演習)の場合は?
**A3**: その場合ドメイン管理者経路を進む必要があるが、やはり「どの経路が最短でノイズ最小か」を評価する。BloodHound の shortest path は意外な短連鎖を示すことが多い。三ホップ以内の到達は DC パッチ面を死闘するよりはるかに現実的である。
**Q4**: 目標定義自体が曖昧(顧客が明確に言っていない)の場合は?
**A4**: 計測可能なマイルストーンへ転換する。初日の目標は「任意の高特権アカウントまたは一台の高価値マシン」で、ドメイン管理者を追求しない。段階的な成果があれば顧客と摺り合わせ、曖昧な目標を明確な目標に変える。目標不明のまま全賭けを「必須ドメイン管理者」に置かない。

### 長時間停滞:やり直すべきかを判断する
**Q1**: ある経路に合理時間(数時間/一日)以上突いている。どう意思決定する?
**A1**: ハードな時間閾値を設け、超えたら強制的に経路を変える。判定基準は「もうすぐ成功」ではなく、「過去 N 時間に実質的進展があったか」。認証情報をひとつ多く取ったか、マシンに一台多く入ったか、オブジェクトをひとつ多く列挙したか。全部「ゼロ進展」なら必ず経路を変えるシグナルである。
**Q2**: どの経路へ変える?闇雲に変えない保証は?
**A2**: 「未探索次元」リストを作り、各大類にチェックを付ける。認証情報収集(メモリ/DPAPI/ブラウザ/共有ファイル)、Kerberos 攻撃面(AS-REP/Kerberoast/委任)、ADCS、ACL abuse、GPO abuse、coercion+relay、信頼、パスワードスプレー、ソーシャルエンジニアリング/物理層。今日完全に未試行の類をひとつ選んで入る。
**Q3**: 全大類を触ったが全部進展なしの場合は?
**A3**: 「偵察をやり直す」へ転換する。問題は打法ではなくインテリジェンスかもしれない。BloodHound データが古い?ネットワークが新セグメントを拡張した?新しくオンラインになったマシンをスキャン漏れした?インテリジェンスを再採取すると、見落としていた目標を発見することが多い。
**Q4**: 偵察もやり直したが突破できない場合は?
**A4**: 「自分に hard stop を与える」ときである。レッドチームの最も重要な能力のひとつは「この経路は通じないと認める」こと。チームメイトに助けを求めて視点を変えるか、状態を記録して後手を残して撤退し、次回新しいツール/新しい研究で再挑戦する。突き続けて消費する時間が最も高価なコストである。
