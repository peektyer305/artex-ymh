# ADドメイン内 · ADCS ESC 証明書攻撃の経路選択

### ドメイン内の足場を取得したら、まずドメインに ADCS が存在するかを判断する
**Q1**: ドメイン内の一般ユーザーコンテキストでシェルを取得したばかりで、証明書経路での権限昇格を狙いたい。最初に何を確認すべきか?
**A1**: 急いでエクスプロイトを実行しない。まずドメインに企業 CA が展開されているかを確認する。判定基準:LDAP の `CN=Enrollment Services,CN=Public Key Services,CN=Services,CN=Configuration,<domain>` 配下にオブジェクトがあるかどうか。あれば企業 CA が存在する。各 CA の `dNSHostName`(CA ホスト)と公開済みテンプレートを記録する。このコンテナがなければ企業レベルの ADCS は存在しないため、証明書による権限昇格はほぼ不可能であり、別の次元に直接切り替える。
**Q2**: LDAP が匿名または制限されていて十分に照会できない場合は?
**A2**: 現在のドメイン認証情報で Certipy の `find` を実行する。`find -vulnerable -stdout` は CA、テンプレート、ACL、EKU、flag を一度に引き出し、ESC1-16 を注記する。Python 環境がなければ Windows 上で `certutil -config - -ping` と `certutil -template` でテンプレートを調べる。
**Q3**: CA がオンラインで到達可能かだけを確認したい場合は?
**A3**: `certutil -config "CAホスト\CA名" -ping` を使うか、CA ホストの RPC(135/445)と証明書 Web エンドポイント(certsrv、certfnsh.asp)を直接テストする。CA がオフラインなら署名発行の経路はすべて断たれ、ESC7 の管理権限か ESC8 relay の前提のみが残る。
**Q4**: Certipy の出力を「次にどの ESC を打つか」へ変換するには?
**A4**: vulnerable セクションの ESC 番号を見て、「前提条件が既に満たされている、エクスプロイト複雑度が低い」順に並べる。ESC1/ESC4 は通常最も直接的であり、ESC8 はマシン認証をトリガーできる必要があり、ESC6 は CA の EDITF flag を見る。
**Q5**: この経路が遮断された。ドメインに ADCS がまったくない、または CA がすべてオフラインの場合は?
**A5**: 直交する次元へ転換する。古典的な AD 権限昇格面に戻る。Kerberoast/AS-REP roast、ACL 悪用、Zerologon/PetitPotam+NTLM relay、GPO 悪用、委任(制約付き/非制約/RBCD)。証明書は数ある経路のひとつに過ぎず、CA がなければ固執しない。
**Q6**: スキャンの動きが大きく EDR に検知されるのが心配か?
**A6**: Certipy の LDAP 照会自体は非常に静かである(通常のディレクトリ読み取りに過ぎない)。本当に音がするのは後続の enroll である。まず `find` による偵察とオフライン分析だけを行い、唯一の利用ポイントを確定してから一度に実行し、無駄な証明書申請ログを減らす。

### あるテンプレートが ESC1 かどうかを判断する(制御可能な SAN + クライアント認証 EKU)
**Q1**: Certipy があるテンプレートを ESC1 の疑いと注記した。本当に攻撃できるかをどう確認する?
**A1**: 三つの条件が同時に成立する場合のみ ESC1 である。テンプレート EKU に Client Authentication(または Smart Card Logon / PKINIT / Any Purpose)が含まれる、テンプレートに `CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT`(申請者が SAN を自己記入可能)が設定されている、かつ現在の身元がテンプレートに Enroll 権限を持ち、CA がそのリクエストに Manager Approval も承認署名も要求しない。
**Q2**: 確認できた。どう攻める?
**A2**: `certipy req -u me@dom -p pass -ca CA名 -template テンプレート -upn administrator@dom`(または `-sid` で対象 SID を指定)。pfx を取得したら `certipy auth -pfx admin.pfx` で PKINIT により TGT を交換するか、直接 NT hash を取得する。
**Q3**: 申請時に SAN が拒否された、または証明書に記入した UPN が含まれていない?
**A3**: そのテンプレートが実際には enrollee-supplies-subject を開いていないか、CA が強制 SAN マッピングパッチを適用していることを示す。`-sid` による SID マッピングに切り替えるか、ESC6(CA 全体の EDITF_ATTRIBUTESUBJECTALTNAME2)に進むべきかを確認する。テンプレート単位ではない。
**Q4**: 対象アカウントに domain admin を記入したが、auth で返ってきたチケットに権限がない?
**A4**: 記入した UPN/SID が実在し、特権アカウントであるかを確認する。PKINIT 後にドメインが証明書の強マッピングを強制している場合(2022 パッチ以降)、弱マッピングは失敗する。`-sid` で対象オブジェクトの objectSid を指定して強マッピングを行う必要がある。
**Q5**: このテンプレートが攻撃できない(承認/承認署名が必要)場合は?
**A5**: 転換する。同じ CA 配下の他の enroll 可能なテンプレートを探す。またはそのテンプレートが ESC2/ESC3 にも同時に該当するかを見る。または ESC4 へ転換する(テンプレートへの書き込み権限があるなら、設定を直接変更して ESC1 にする)。
**Q6**: 全域に enrollee-supplies-subject テンプレートがひとつもない場合は?
**A6**: SAN 注入のこの支流を諦め、ESC3(申請代理/Enrollment Agent)、ESC6(CA レベルの SAN)、ESC7(CA 管理)、ESC8(relay)へ転換する。これらはテンプレートの自己記入 SAN に依存しない。

### ESC2 と ESC3 のどちらへ進むかを区別する
**Q1**: あるテンプレートの EKU が Any Purpose または空で、別のテンプレートが Certificate Request Agent である。それぞれどう使う?
**A1**: EKU が Any Purpose(2.5.29.37.0)または EKU がまったくない = ESC2。証明書を任意の用途に使え、クライアント認証を含む。ESC1 と同様に直接認証できる(SAN を制御できるか代理を行えることが前提)。Certificate Request Agent EKU = ESC3。それ自体は直接ログオンできないが、「登録代理」として他者の代わりに証明書を申請できる。
**Q2**: ESC3 は具体的にどう二段階で進める?
**A2**: 第一段階として Enrollment Agent EKU を持つテンプレートで自分の代理証明書を申請する。第二段階として `certipy req ... -template 某クライアント認証テンプレート -on-behalf-of 'DOM\administrator' -pfx 代理.pfx` で、管理者の代わりにログオン可能な証明書を申請する。
**Q3**: on-behalf-of が拒否された?
**A3**: 対象テンプレートが Application Policy 制限を設定していて特定の登録代理のみを受け付けるか、CA が Enrollment Agent が代理できるアカウント/テンプレート範囲を制限している可能性がある。対象テンプレートを変えるか、CA の enrollment agent restrictions を調べる。
**Q4**: ESC2 のテンプレートで証明書を取得したがログオンに失敗する?
**A4**: Any Purpose は認証できるが、SAN が制御できなければ自分自身を表すだけである。SAN も同時に制御できるなら(ESC1 に退化する)、または ESC2 証明書を代理証明書として使う(Any Purpose は Certificate Request Agent 用途も包含する)ことで on-behalf-of を行う。
**Q5**: 両方とも承認/権限で塞がれた場合は?
**A5**: 転換する。ESC1(より直接的)を優先し、次に ESC4(テンプレート ACL の変更)、ESC7/ESC8 を見る。ESC2/ESC3 は、すでに何らかのテンプレート enroll 権限を持つ場合の補助経路として適しており、第一選択ではない。

### テンプレート自体が書き込み可能な場合に ESC4 へ進む
**Q1**: Certipy が自分はあるテンプレートに WriteDacl/WriteProperty/GenericAll を持つと言った。これをどう換金する?
**A1**: これは ESC4 であり、テンプレート設定を変更できる。方針として、安全なテンプレートを一時的に ESC1 に変更し(enrollee-supplies-subject flag を追加、クライアント認証 EKU を設定、承認と承認署名要件を外し、自分に enroll 権限を付与)、管理者証明書を申請し、その後元に戻して痕跡を消す。
**Q2**: どのツールで変更する?
**A2**: `certipy template -template テンプレート -write-default-configuration`(Certipy の新版はテンプレートを攻撃されやすい状態へワンクリックで変更し、復元用に元設定を保存できる)。または手動で LDAP 経由で `msPKI-Certificate-Name-Flag`、`pKIExtendedKeyUsage`、`msPKI-Enrollment-Flag` を変更する。
**Q3**: 変更後すぐ enroll したがテンプレート未反映と出た?
**A3**: CA にはテンプレートキャッシュがあり、設定反映に時間がかかる。しばらく待つか CA の再読み込みをトリガーする。AD 上のテンプレートオブジェクトを変更したこと、および CA がそのテンプレートを公開済みであることも確認する。
**Q4**: WriteDacl のみで直接の WriteProperty がない場合は?
**A4**: まず WriteDacl で自分に WriteProperty/GenericAll を追加し、その後に設定を変更する。ESC4 の本質は「テンプレートオブジェクトへの書き込み権限」であり、WriteDacl は万能の最初の一歩である。
**Q5**: テンプレート変更という動作が危険すぎて痕跡を残したくない、またはアラートが怖い場合は?
**A5**: ESC7 へ転換する(CA 管理権限も持つなら、自分の保留リクエストを直接承認する方がよりクリーンである)。または既存の ESC1 テンプレートを直接探す。変更が必須なら、元の `msPKI-*` 値を必ず記録し、証明書取得後に即座に復元する。テンプレートを長期間脆弱な状態に放置しない。

### CA 全体で SAN 拡張が開かれている場合に ESC6 へ進む
**Q1**: enrollee-supplies-subject テンプレートはないが、CA 層に穴があると疑っている。ESC6 をどう判断する?
**A1**: CA のポリシーフラグに `EDITF_ATTRIBUTESUBJECTALTNAME2` が含まれるかを調べる。`certutil -config "CA\name" -getreg policy\EditFlags` にそのビットが含まれるか、Certipy find が "User Specified SAN: Enabled" と注記するか。開かれていれば、任意のテンプレート申請時に SAN 属性で任意の UPN を注入できることを意味する。
**Q2**: どう利用する?
**A2**: enroll 可能なクライアント認証テンプレートのいずれかを使い、申請時に `-upn administrator@dom` を付ける。CA が全体で SAN を受け入れるため、テンプレートが自己記入 SAN を開いていなくても証明書に書き込まれる。
**Q3**: 2022 年 5 月のパッチ(KB5014754)後も ESC6 は有効か?
**A3**: パッチ後、CA はデフォルトで強マッピングし弱 SAN を無視するため、ESC6 はしばしば無効になる。無効の場合、CA の `StrongCertificateBindingEnforcement` レジストリ値が互換モード(1 または 0)に下げられていないかを確認する。2 のままならこの支流はほぼ使えない。
**Q4**: ESC6 が無効になったらどこへ転換する?
**A4**: ESC1(テンプレートレベルの自己記入 SAN)、ESC7(CA 管理)、ESC8/ESC11(relay)へ転換する。ESC6 はパッチ適用済みの現代のドメインでは成功率が下がるため、主経路にしない。
**Q5**: EDITF を変更して ESC6 を成立させるには何の権限が必要か?
**A5**: それは既に ESC7 の範疇であり、CA の ManageCA 権限で `certutil -setreg` または Certipy により EDITF flag を開く必要がある。ManageCA を持つなら ESC7 でリクエストを承認する方が直接的であり、ESC6 を先に開く必要はない。

### CA の ManageCA/ManageCertificates 権限を取得した場合に ESC7 へ進む
**Q1**: あるアカウントが CA に対して ManageCA または Manage Certificates 権限を持つことを発見した(そのアカウントを取得できる)。どう換金する?
**A1**: ESC7。二つの手がある。ひとつは ManageCA で CA の EDITF_ATTRIBUTESUBJECTALTNAME2 を開いて ESC6 を作り、任意の SAN 付き証明書を申請する。もうひとつは保留になるリクエストを提出し、Manage Certificates(Issue 権限)で自分の保留リクエストを手動承認する。
**Q2**: ManageCA のみで Manage Certificates がない場合は?
**A2**: ManageCA で自分に officer(証明書管理者)ロールを追加でき、それにより Issue 能力を得る。Certipy の `ca -add-officer` がそれを行う。Issue 権限を取得してから自分のリクエストを承認する。
**Q3**: 保留リクエストを承認する具体的なフローは?
**A3**: `certipy req` で提出して request id と状態 pending を取得し、`certipy ca -issue-request <id>` を実行し、最後に `certipy req -retrieve <id>` で証明書を取り出す。
**Q4**: ManageCA でデフォルトでは公開されていない脆弱テンプレートを有効化できるか?
**A4**: できる。ManageCA は CA に新テンプレートを公開させることができる(`ca -enable-template`)。AD に存在するが未公開の SubCA や脆弱テンプレートがあるなら、有効化後に enroll できる。これは ESC7 の強力な変種である。
**Q5**: 権限操作が監査/ロールバックされた場合は?
**A5**: 転換する。ESC7 の各動作(officer 追加、EDITF 変更、テンプレート公開)は CA ログに記録される。環境の監視が厳しいなら、一回限りの relay(ESC8/ESC11)や純粋なテンプレートレベルの ESC1 に切り替え、CA 設定に触れるのを減らす。officer ロールは使い終わったら remove を忘れない。
**Q6**: ManageCA を持つアカウントをどうしても取得できない場合は?
**A6**: その場合 ESC7 の前提が成立しない。enroll 可能な脆弱テンプレートを探すか、ESC8 でマシンアカウント認証を CA の HTTP エンドポイントへ relay する(事前の CA 管理権限は不要)。

### CA の Web 登録エンドポイントが relay 可能な場合に ESC8 へ進む
**Q1**: CA が certsrv の HTTP/HTTPS 登録エンドポイントを開いている。どう利用する?
**A1**: ESC8。あるマシンアカウントの NTLM 認証を CA の `/certsrv/certfnsh.asp` へ relay し、そのマシンの代わりに証明書を申請する。古典的な組み合わせは、PetitPotam/PrinterBug で DC マシンアカウントに自分へ認証させ、ntlmrelayx がその認証を CA Web エンドポイントへ転送して DC のマシン証明書を申請する、というもの。
**Q2**: relay にはどのテンプレートを使う?
**A2**: デフォルトで Machine/DomainController テンプレート(マシン認証)を使う。`ntlmrelayx -t http://CA/certsrv/certfnsh.asp -smb2support --adcs --template DomainController`。DC 証明書を取得後、PKINIT で DC の TGT を取得し、さらに DCSync へ進む。
**Q3**: エンドポイントが HTTPS で EPA/Channel Binding を要求する場合は?
**A3**: CA が Extended Protection for Authentication を強制している場合、HTTP relay は channel binding に遮断される。HTTP(80)エンドポイントが開いていればそれに切り替えるか、ESC11(ICPR RPC relay。RPC を使うため HTTP の EPA を回避する)へ転換する。
**Q4**: 強制認証(coerce)にパッチが当たった場合は?
**A4**: PetitPotam(EfsRpc)はしばしばパッチされる。PrinterBug(MS-RPRN)、DFSCoerce(MS-DFSNM)、ShadowCoerce、または Coercer ツールで複数の手法を輪番で試す。RPC coerce 面のひとつは必ず塞がれずに残っている。どうしても無理なら、認証をトリガーできる他の動作(WebDAV、ログオンスクリプト)を使う。
**Q5**: relay 先の CA Web エンドポイントがそもそも開いていない場合は?
**A5**: ESC11 へ転換する。CA の ICertPassage RPC インターフェース(ICPR)が RPC 暗号化/署名を強制していないなら、HTTP ではなく RPC へ relay できる。または relay 支流を諦め、テンプレートレベルの ESC1-4 に戻る。
**Q6**: relay 先のアカウントが特権マシンではない場合は?
**A6**: coerce 時に高価値ホスト(DC、CA 自体、Exchange)に自分へ認証させるよう指定する。無作為な一台ではない。relay の価値は、強制認証させたそのマシンの権限に依存する。DC マシンアカウントを選べば DCSync に直結する。

### 誰を coerce し、どこへ relay するかを判断する
**Q1**: relay を狙いたいが、どのマシンに自分へ認証させるべきか分からない。どう選ぶ?
**A1**: 対象選定の原則は、coerce されるマシンの権限が高いほど良い(DC マシンアカウントは DCSync でき、CA マシンアカウントは署名発行でき、Exchange マシンアカウントは多くのドメインで高い ACL を持つ)。relay の落とし先は何が欲しいかで決まる。ADCS に落として証明書を交換するか(ESC8/11)、LDAP に落として RBCD/shadow credentials を行うか、SMB に落としてローカル管理者を取るか。
**Q2**: 一度の coerce で複数の relay 先へ同時に供給できるか?
**A2**: ntlmrelayx は複数先をサポートするが、同じ認証は一度しか消費されない。実戦では、どのチェーンが欲しいかを明確にし、狙いを定めて coerce する方が安定する。認証が誤った先に食われるのを避ける。
**Q3**: DC が自分自身へ DC relay(loopback)するのは遮断されるか?
**A3**: 現代のパッチは NTLM の reflection/loopback に防御を持つため、DC relay が自身へ戻るのは大半が失敗する。relay は「別の」サービス(CA、別の DC、LDAP)へ行うのが確実である。これが ESC8 が CA を relay の落とし先に選ぶ理由でもある。
**Q4**: coerce は成功したが relay がすぐ切断される?
**A4**: SMB 署名(relay 先 SMB は署名非強制が必須)と LDAP 署名/channel binding(relay 先 LDAP は非強制が必須)を確認する。ADCS HTTP relay は SMB 署名の影響を受けない。これが ADCS が第一の落とし先になりやすい理由である。
**Q5**: すべての relay 面(SMB 署名あり、LDAP 強制、ADCS EPA あり)が塞がれた場合は?
**A5**: NTLM relay の次元全体から離れる。Kerberos 側(RBCD には対象マシンアカウントの msDS-AllowedToActOnBehalfOf を変更できることが必要、または shadow credentials で msDS-KeyCredentialLink を変更)、または純粋な認証情報側(Kerberoast、平文パスワードの再利用)へ進む。

### 証明書取得後に PKINIT が失敗する場合のトラブルシューティング
**Q1**: 対象身元の pfx を申請したが、`certipy auth` で TGT を交換しようとすると KDC_ERR またはマッピング失敗が出る。どうする?
**A1**: 高い確率で 2022 年の強証明書マッピングパッチが原因である。ドメインが強制モードへ移行すると、KDC は証明書に SID 拡張(szOID 1.3.6.1.4.1.311.25.2)が含まれることを要求する。解決策は、申請時に `-sid <対象objectSid>` で Certipy に SID を証明書へ埋め込ませること。
**Q2**: 対象テンプレートが SID の埋め込みを許可しない場合は?
**A2**: ESC1 の自己記入 SAN を進む場合、`-sid` は SAN の URL 拡張への書き込みに依存する。CA が拒否するなら、ESC6/ESC7 で CA 側の許可が必要か、許可されたマッピング方式を打つ必要がある。または Kerberos PKINIT ではなく Schannel/LDAP 認証にフォールバックする。
**Q3**: PKINIT が完全に通らないが、正当な証明書は持っている場合は?
**A3**: Schannel へ転換する。`certipy auth -pfx x.pfx -ldap-shell` で LDAP over TLS の証明書認証を行い、LDAP シェルを取得した後に shadow credentials、RBCD、マシン追加などを行う。Kerberos PKINIT を経由しない。
**Q4**: 証明書から直接 NT hash を取得したい場合は?
**A4**: PKINIT で TGT を取得後、U2U + PAC 内の NTLM_SUPPLEMENTAL_CREDENTIAL からそのアカウントの NT hash を解ける(Certipy auth が自動で行う)。前提は、アカウントが NT hash を持ち、KDC がその構造を返すこと。純粋な管理対象サービスアカウントは hash を取得できず、チケットしか使えない場合がある。
**Q5**: 証明書は有効だが対象アカウントが無効化/パスワード変更された場合は?
**A5**: 証明書認証は現在のパスワードに依存しないが、アカウントの有効状態には依存する。対象が無効なら PKINIT は失敗する。別の有効な特権対象に切り替える。これが、無効化されがちな履歴アカウントより、アクティブな管理者やマシンアカウントを優先する理由である。

### 証明書の有効期間が長い場合、永続化認証情報として使う
**Q1**: 管理者証明書を取得した。即時に使う以外に、どう価値を絞り出せるか?
**A1**: 証明書は「オフライン認証情報」であり、有効期間は 1〜2 年以上に及ぶことが多く、パスワード変更の影響も受けない。これを永続化として使う。たとえ相手が侵入を発見して全パスワードを変更しても、この証明書を失効させない限り、いつでも PKINIT で戻れる。pfx を安全にオフライン保存する。
**Q2**: 長期的に自分の証明書を目立たず発行するには?
**A2**: 一般ユーザーテンプレートで自分(現在のアカウント)にクライアント認証証明書を申請する。これは多くのドメインで通常操作であり、ほぼアラートが発生しない。パスワードを失っても認証できるようになり、控えめなユーザーレベルの永続化(THEFT 類)となる。
**Q3**: 証明書が失効されるのが心配か?
**A3**: 失効には管理者が CA 上で revoke し、CRL 更新を待つ必要がある。多くのブルーチームは個別証明書を監視も失効もしない。リスクは一括失効や CA 再構築にある。安全のため、複数の永続化(shadow credentials、チケット、パスワード)を同時に保持し、ひとつの籠に卵を盛らない。
**Q4**: 証明書を偽造してゴールデン証明書を作れるか?
**A4**: CA ホスト自体を侵害していれば、CA 秘密鍵をエクスポートし(`certipy ca -backup` または mimikatz)、それで任意身元・任意 EKU の証明書をオフライン署名できる = Golden Certificate。CA オンラインを経由せず、発行ログもない。これは ADCS 攻撃チェーンの頂点の永続化である。
**Q5**: CA 秘密鍵が HSM/TPM 保護されていてエクスポートできない場合は?
**A5**: 転換する。秘密鍵をエクスポートできないならゴールデン証明書は作れない。次善策としてオンライン署名の長期証明書を使うか、侵害後に CA 上で設定を変更して将来の発行を許可するか、DPAPI/DCSync など他のドメイン永続化の次元へ転換する。

### マシンアカウントの shadow credentials(ESC 以外の証明書隣接経路)
**Q1**: ある対象アカウントに msDS-KeyCredentialLink の書き込み権限(GenericWrite/GenericAll)を持つ。証明書とどんな関係がある?
**A1**: これは Shadow Credentials(Whisker/pyWhisker)である。対象の KeyCredentialLink に KeyCredential(公開鍵)をひと組書き込み、対応する秘密鍵で PKINIT 認証してその対象になる。本質は証明書/鍵認証であり、ADCS が KDC 証明書を展開している(PKINIT 利用可能)ことに依存するが、脆弱テンプレートは不要。
**Q2**: いつ RBCD よりこれを優先するか?
**A2**: 「このアカウントになる」ことだけが必要で、「その身元として特定サービスへアクセスする」ことが不要な場合、shadow credentials の方がより直接的でクリーンである(直接 TGT と NT hash を取得)。RBCD は別途制御下のマシンアカウントが必要で、特定サービスに落とす。
**Q3**: 書き込み後に PKINIT が「適切な KDC 証明書がない」と報告する?
**A3**: ドメインが DC に PKINIT 用のドメインコントローラ証明書を発行していないことを示す。PKINIT が利用不可なら shadow credentials 認証は失敗する。RBCD(純粋な Kerberos 委任で PKINIT 不要)へ転換するか、書き込み権限を直接他の用途に使う。
**Q4**: 対象の KeyCredentialLink に既に内容があり、壊すのが怖い場合は?
**A4**: 上書きせず追記する。操作前にツールで元の値を list してバックアップし、使い終わったら自分が追加した項目を remove する。相手の既存値を消さない。消すと障害アラートを引き起こす。
**Q5**: 高価値アカウントへの書き込み権限が何もない場合は?
**A5**: 書き込み権限の取得元へ戻る。ACL 攻撃チェーン(BloodHound で GenericWrite/WriteDacl の経路を探す)、または先に ESC1/relay で ACL を変更できる身元を取得し、その後 shadow credentials を行う。

### 脆弱テンプレートが山ほどあるが、どれから打つか分からない場合
**Q1**: Certipy が ESC1/ESC2/ESC3/ESC4 を一度に複数報告した。どんな順序で攻める?
**A1**: 順序の判定基準:①前提権限が既に満たされているか(現在の身元で enroll できるものを優先)。②直接到達度(ESC1 は一段階で管理者証明書 > ESC3 は二段階 > ESC4 は設定変更が必要)。③痕跡とリスク(CA/テンプレート設定を変更しないものを優先)。④追加トリガーの要否(relay 類は coerce が必要なので後回し)。総合して「今の自分が一段階で突破でき、変更が最小」のものを選ぶ。
**Q2**: あるテンプレートが複数の ESC に該当する場合は?
**A2**: 該当が多いほど設定が緩く、通常は攻めやすい。しかしハニーポットの囮の可能性もある。実環境では「業務としては正常だが、たまたま設定を怠った」テンプレートを優先し、明らかに異常なほど開いたテンプレートは避ける。
**Q3**: 現在の身元がテンプレートに enroll 権限を持つかをどう知る?
**A3**: Certipy find がテンプレート ACL の enrollment principals を解析し、自分の所属グループと照合して "Enrollee" と注記する。またはテンプレートの `msPKI-Enrollment` 関連 ACE に Authenticated Users / Domain Users / 自分の所属グループが含まれるかを確認する。
**Q4**: 全テンプレートで enroll 権限がない場合は?
**A4**: 転換する。先に enroll 権限を持つアカウントを横展開で取得する(ドメイン内の多くのユーザーテンプレートは Domain Users に開かれている。まずこれを確認)。またはテンプレート enroll 権限に依存しない ESC8/ESC11 relay へ進む。
**Q5**: ある ESC を打って管理者を取得した。残りも管理する必要があるか?
**A5**: DA/EA を取得したら残りの ESC を逐一打つ必要はないが、永続化とレポートのために記録する価値はある。レッドチームとして「これが塞がれたらあれがある」を網羅し、レポートで複数経路を示して深さを表現する。

### 対象テンプレートが Manager Approval を要求する場合の回避
**Q1**: 狙いの脆弱テンプレートに `CT_FLAG_PEND_ALL_REQUESTS`(手動承認が必要)が設定されていて、申請後ずっと pending になる。どうする?
**A1**: enroll 権限だけでは承認を通過できない。CA 側の Manage Certificates(Issue)権限を別途持つかを判断する。あれば自分で承認する(ESC7 の手)。なければこのテンプレートは通らない。無駄に待たない。
**Q2**: 承認不要の同等テンプレートを探せるか?
**A2**: 優先する。同じ CA には通常複数のクライアント認証テンプレートがある。PEND_ALL_REQUESTS が開いていないものを探す。承認要件はテンプレート単位の設定であり、テンプレートを変えれば回避できる。
**Q3**: ESC4(テンプレート書き込み権限)を持つ場合は?
**A3**: `msPKI-Enrollment-Flag` の PEND_ALL_REQUESTS ビットを直接オフにし、申請が自動署名になるようにする。取得後に復元する。ESC4 は承認、SAN、EKU の複数の制限をまとめて解決できる。
**Q4**: 保留リクエストは管理者に見られて露見しないか?
**A4**: 露見する。pending リクエストは CA 管理コンソールに表示され、手動レビューを誘発しうる。自分で承認できないなら、pending を積み重ねると意図が露見する。そのテンプレートを申請しないか、自動署名できる経路へ進む。
**Q5**: 使えるテンプレートがすべて承認必須の場合は?
**A5**: ESC6(CA 全体の SAN。開いていれば任意の自動署名テンプレートが使える)、ESC7(Issue 権限を取得して自己承認)、または relay/非証明書経路へ完全に転換する。承認の壁はテンプレート単位の防御であり、CA 単位または非テンプレート経路へ直交ジャンプすればよい。

### テンプレートが承認署名(Authorized Signature)を要求する場合の判断
**Q1**: テンプレートに `msPKI-RA-Signature >= 1` が設定され、申請に特定の Application Policy を持つ署名が必要だ。これに遮られるか?
**A1**: 申請前に、指定の Application Policy(例: Certificate Request Agent)を満たす証明書を先に持つ必要がある。その代理証明書を先に取得できれば(ESC3 または別の脆弱テンプレートから)、署名要件を満たして申請を続行できる。
**Q2**: ポリシーを満たす署名証明書を持っていない場合は?
**A2**: その Application Policy を発行するテンプレートを探して enroll する。連鎖としては、先に脆弱な代理テンプレートを攻めて署名証明書を取得し、それで対象テンプレートに署名申請する。これは ESC3 の組み合わせ形である。
**Q3**: 署名要件 + ESC4 を持つ場合は?
**A3**: ESC4 で `msPKI-RA-Signature` を直接 0 に変更し、署名要件を外す。書き込み権限はあらゆるテンプレート単位の制約に勝る。
**Q4**: このチェーンが複雑すぎて署名を揃えたくない場合は?
**A4**: 承認署名を要求しない別テンプレート、または CA 単位(ESC6/7)、relay 単位(ESC8/11)へ転換する。承認署名は強力なテンプレート防御であり、より省力な迂回路があるなら無理に揃えない。

### Schannel/LDAP のみで証明書からドメイン制御権を取りたい場合
**Q1**: PKINIT 環境が不十分だが、高権限の証明書を持っており、Kerberos を経由せず直接 AD を操作したい。どうする?
**A1**: Schannel を使う。証明書は LDAPS クライアント認証に使える。`certipy auth -pfx x.pfx -ldap-shell` または PassTheCert で証明書から直接 LDAP へ接続する。LDAP セッションを取得後、RBCD、shadow credentials、DACL 変更、コンピュータ追加などを行う。
**Q2**: PassTheCert で接続後、最も強力なことは?
**A2**: 証明書の身元が DC マシンアカウントまたは高 ACL アカウントなら、自分のアカウントに DC への RBCD を追加するか、domain オブジェクトの DACL を直接変更して自分に DCSync 権限を付与する(DS-Replication-Get-Changes を追加)。その後 secretsdump で hash を抜く。
**Q3**: LDAPS が channel binding を要求して証明書認証が拒否される?
**A3**: 標準の 636/LDAPS と StartTLS を試す。channel binding が強制され実装が一致しないなら、PKINIT が使える場合はそちらへ戻す。証明書認証の二つの経路(Kerberos PKINIT / Schannel LDAP)は相補的であり、片方が塞がれたらもう片方を試す。
**Q4**: 両方とも通らない場合は?
**A4**: 非証明書の次元へ転換する。その証明書身元がアカウントに対応するなら、U2U で NT hash を解いて SMB/WMI/パスワード再利用へ進むか、証明書価値を永続化として残し、別経路で権限昇格を先に探す。

### CA ホスト自体を制圧した後にどう搾り取るか
**Q1**: 別経路で CA サーバーのローカル管理者/SYSTEM を取得した。どんな究極能力が得られる?
**A1**: CA ホスト = 証明書の玉座である。CA の秘密鍵と証明書をエクスポートし(`certipy ca -backup -ca name` または mimikatz の `crypto::certificates /export`)、それで任意身元・任意 EKU の証明書をオフライン署名する(ゴールデン証明書)。オンライン署名を完全に迂回し、リクエストログがなく、脆弱テンプレートも不要。
**Q2**: 秘密鍵のエクスポートが拒否された?
**A2**: 秘密鍵はエクスポート不可とマークされているか HSM に格納されている可能性がある。mimikatz には CryptoAPI に patch してエクスポート不可秘密鍵をエクスポート可能にするテクニックがある(`crypto::capi`/`crypto::cng`)。HSM 保護の場合は本当にエクスポートできず、そのマシン上で「借りて」オンライン署名するしかない。
**Q3**: ゴールデン証明書はどう使う?
**A3**: ForgeCert/Certipy forge で CA 秘密鍵から administrator の証明書に署名し、PKINIT する。署名が正当で信頼された CA に連鎖するため、KDC は完全に受け入れる。これは最も隠密なドメイン永続化のひとつであり、パスワードリセットも無効である。
**Q4**: ゴールデン証明書はどう対抗されるか?
**A4**: 唯一の強力な対抗は CA ルート/中間証明書の失効または PKI 再構築であり、コストが非常に大きいためブルーチームは通常行わない。ただし新しい SID 強マッピング要件の導入後は、偽造証明書にも正しい SID を含める必要がある。forge 時に対象 objectSid を加えればよい。
**Q5**: CA を取得したが、一時的に一度だけ使いたく、バックドアを残したくない場合は?
**A5**: その場合、オンラインで既存テンプレートを使って一枚署名して去る。秘密鍵の backup はしない(バックアップ操作自体がログに残る)。レッドチームは交戦規則に従い、最高危険度のバックドアを残せるなら控え、ゴールデン証明書は「到達可能な能力」の証明としてレポートに書く。

### ESC9/ESC10 の弱証明書マッピングの利用
**Q1**: Certipy があるテンプレートに ESC9(no security extension)または環境に ESC10(弱マッピングレジストリ)を提示した。この二つはどう使う?
**A1**: ESC9 は、テンプレートに `CT_FLAG_NO_SECURITY_EXTENSION` が設定され、証明書に SID 拡張が含まれないため、KDC が UPN ベースの弱マッピングへフォールバックする。あるアカウントの UPN を変更できる権限と組み合わせ、制御下アカウントの UPN を対象(例: administrator)に変更して証明書を申請し、認証時に対象へマッピングされる。ESC10 は CA 側のレジストリがマッピングを降格(StrongCertificateBindingEnforcement=0、または CertificateMappingMethods に弱ビットを含む)して同種の弱マッピングを起こす。
**Q2**: ESC9 を利用する具体的なチェーンは?
**A2**: あるアカウント(自分が制御するマシンアカウントや GenericWrite を持つユーザー)の userPrincipalName を `administrator` に変更し(@domain を外すか対象の sAMAccountName を使う)、ESC9 テンプレートで証明書を申請し、PKINIT/Schannel 認証が本物の administrator へ弱マッピングされる。その後 UPN を戻して衝突を避ける。
**Q3**: UPN 変更が拒否された、または衝突した?
**A3**: UPN は全域で一意である必要があり、対象 UPN が既に占有されていれば失敗する。ドメインサフィックスなしの形式(純粋な sAMAccountName)で一意性を迂回するか、現在誰も使っていない UPN の対象へ変更する。前提としてそのアカウントへの書き込み属性権限が必要。
**Q4**: この二つと 2022 パッチの関係は?
**A4**: ESC9/ESC10 はまさに「強マッピングを迂回する」手法であり、強マッピングを完全には適用していない設定の隙間を利用する。環境が強マッピングを厳格に強制している場合(enforcement=2 かつ全テンプレートが SID 拡張付き)、この二支流は無効になる。
**Q5**: 無効になったらどこへ転換する?
**A5**: ESC1(SID 付きの直接 SAN)、ESC6/7(CA 単位)、relay 類へ転換する。ESC9/10 は特定の設定の隙間であり、通らなければ主流の脆弱テンプレート経路へ戻る。

### ESC11(ICPR RPC relay)をいつ投入するか
**Q1**: CA の HTTP 登録エンドポイントが開いていないか EPA があり、ESC8 が使えない。ESC11 はどう助ける?
**A1**: ESC11 は CA の MS-ICPR RPC インターフェース(証明書登録の RPC 経路)へ relay する。前提は、その RPC インターフェースの `IF_ENFORCEENCRYPTICERTREQUEST` が未有効(つまり暗号化/パケット整合性を強制していない)であること。このとき coerce で得た NTLM 認証を RPC へ relay して証明書を申請し、HTTP 側の制限を迂回できる。
**Q2**: どのツールを使う?
**A2**: ESC11 パッチ対応の ntlmrelayx(-icpr/rpc-mode 付きブランチ)または certipy 関連モジュール。フローは ESC8 と同じで、高価値マシンを coerce → CA RPC へ relay → マシン証明書を取得 → PKINIT。
**Q3**: RPC が暗号化を強制している場合は?
**A3**: その場合 ESC11 の前提が成立しない。ESC8 に戻る(HTTP エンドポイントのどれかがまだ開いていて EPA がない場合)か、relay を完全に諦めてテンプレート単位/CA 単位へ進む。
**Q4**: ESC8 と ESC11 のどちらへ進むかを素早く判断するには?
**A4**: 判定基準:HTTP エンドポイントが開いていて EPA がなければ ESC8 の方が成熟している。HTTP が閉じているか EPA があるが RPC が暗号化非強制なら ESC11。Certipy find の CA セクションが "Enforce Encryption for Requests" と Web enrollment 状態を注記するので、それで二択を決める。

### 攻撃前に「権限昇格か横展開/永続化か」を明確にする
**Q1**: ADCS 攻撃面を前にして、乱打しないためにどう目標を定める?
**A1**: まず現在の要望を明確にする。ドメイン管理者への権限昇格が目的なら、高権限身元の証明書を発行できる ESC(1/3/4/6/7/8)を探す。特定マシンへの横展開が目的なら、証明書身元がマシンアカウントに対応すれば PKINIT でそのマシンになれる。永続化が目的なら、自分/マシンに長期証明書またはゴールデン証明書を申請する。目的が異なれば、選ぶ ESC と対象 SAN も異なる。
**Q2**: DA は必要なく、特定のサーバーだけを取りたい場合は?
**A2**: その場合、そのマシンアカウント(host$)の証明書を申請するか RBCD を進め、やみくもに administrator を打たない。最小十分の対象を選び、動きを減らす。
**Q3**: 長期潜伏が目的の場合は?
**A3**: 低アラートの操作を優先する。通常ユーザーテンプレートで自分に長期証明書を申請する(ほぼ異常なし)。高リスクの CA 設定変更やゴールデン証明書は必要でない限り避ける。高リスク能力は「到達可能」として記録し、実際には展開しない。
**Q4**: 打ち間違えた(不要な高権限を取って逆にアラートを誘発した)場合は?
**A4**: 経路選択を振り返る。証明書攻撃の多くの手順は CA ログ(申請者、テンプレート、SAN)に書かれる。高リスク対象を打つほど threat hunting に当たりやすい。要望に合った最小経路へ転換し、不要な保留/発行済み証明書の痕跡を清掃する。

### 証明書攻撃の痕跡と回避
**Q1**: 証明書経路を進めたいが、ブルーチームがログから検知するのが心配だ。どの動作が最も音が大きい?
**A1**: 最も音が大きいのは、証明書リクエストイベント(Event 4886/4887。申請者とテンプレートを含む)、SAN と申請者 sAMAccountName の不一致(古典的な ESC1 の指紋)、短時間の大量または異常テンプレートの enroll、CA 設定変更(EDITF/officer/テンプレート公開)、coerce がトリガーする認証異常である。
**Q2**: ESC1 の SAN 不一致アラートをどう下げる?
**A2**: これは強い指紋で完全には消しにくい。対象 SID マッピング方式を選ぶ、申請頻度を制御する、合理的に見えるテンプレートを使う。ただし成熟したブルーチームは「申請者≠SAN 主体」を専門に監視していると認識すること。検知リスクを評価してから、この支流を使うか、より隠密な relay/shadow creds を使うかを決める。
**Q3**: relay 類は何を残す?
**A3**: coerce は強制されたマシン上に RPC 呼び出しと異常ホストへの認証記録を残す。relay が CA に落ちるとマシン証明書リクエストがひとつ残る。ブルーチームが「あるマシンが突然自分の証明書を申請 + その前に coerce」を関連付ければ特定される。できるだけ窓を短くし、使い終わったら即座に去る。
**Q4**: 事後清掃したい場合は?
**A4**: CA ログと Windows イベントログの清掃には CA ホスト管理者権限が必要で、ログ清掃自体が高リスクである(4104/1102)。レッドチームは通常強引に消さず、控えめな経路選択と最小動作で命中率を下げ、清掃は確信がある場合に残す。
**Q5**: ブルーチームに睨まれて対応が始まった場合は?
**A5**: 即座に永続化の足場を切り替え、露見したばかりの証明書だけに依存しない。その証明書が失効されるかを見極め、直交する復帰経路(別の身元/別マシンの足場)を準備し、単一点を抜かれて即退場にならないようにする。

### ドメインに脆弱テンプレートはないが CA はある。まだ手はあるか
**Q1**: Certipy find が脆弱テンプレートを何も報告せず、CA にも EDITF の穴がない。この経路は死んでいるか?
**A1**: 必ずしもそうではない。テンプレート設定に依存しない支流がまだある。ESC7(CA 管理権限アカウントを取得できる場合)、ESC8/11(登録エンドポイントが relay できる場合)、CA ホスト制圧後のゴールデン証明書、shadow credentials(PKINIT が使えれば脆弱テンプレート不要)。まずこれらの前提をひとつずつ確認する。
**Q2**: これらの前提もすべて不成立の場合は?
**A2**: その場合 ADCS の次元は当面解なしとなる。素直に直交へ転換する。BloodHound に戻って ACL/委任経路、Kerberoast、パスワードスプレー、既存認証情報の横展開、脆弱性面(未パッチの EternalBlue/Zerologon/PrintNightmare など)を探す。
**Q3**: 偵察不足でテンプレートを見落とした可能性は?
**A3**: 別の身元で再び find する(ユーザーごとにテンプレート ACL の可視性が異なる)。または Windows 上で直接 `certutil -template` を列挙する方が網羅的な場合がある。脆弱テンプレートが特定グループに開かれている場合、そのグループメンバーになって初めて現れることがある。
**Q4**: 証明書経路への継続投入に価値はあるか?
**A4**: 判定基準:既に速い非証明書の権限昇格経路(例: 既存の Kerberoast 弱いパスワード)があるなら先にそれを進める。証明書経路の強みは隠密な永続性だが、今通らないならサンクコストにせず、ドメインコントローラを取得した後に ADCS を永続化として改めて補う。

### 証明書身元を取得した後に DCSync へ着地する
**Q1**: PKINIT で DC マシンアカウントまたは DA になった。次の DCSync を最も安定して行うには?
**A1**: TGT を取得したら `secretsdump -k -no-pass DC` または mimikatz の `lsadump::dcsync /user:krbtgt`。DC マシンアカウントはデフォルトで複製権限を持つため、DCSync に十分である。まず krbtgt を取ってゴールデンチケットを最終永続化として作り、その後対象アカウントの hash を取る。
**Q2**: DCSync が権限不足と出た?
**A2**: 証明書身元が Replicating Directory Changes (All) 権限を本当に持つかを確認する。一般ユーザー証明書では無理である。DA、DC マシンアカウント、または明示的に複製権を付与されたオブジェクトが必要。身元が足りなければ、正しい relay/申請対象を選び直す。
**Q3**: 単一アカウントの hash だけが欲しく、騒がせたくない場合は?
**A3**: DCSync で単一 /user を指定する方が全量ダンプより静かで、4662 イベントも少ない。krbtgt が要るなら krbtgt だけを単独で引き、ドメイン全体を dump しない。
**Q4**: DCSync が監視されていて(4662 複製権限アラート)遮断された?
**A4**: 転換する。複製プロトコルを使わず、DC 上でローカル dump する(DC 上のコード実行が必要)、または ntds.dit + system hive でオフライン抽出(ボリュームシャドウコピー)、または取得した高権限で DPAPI/LSASS のアクティブ認証情報を取る。DCSync は hash 取得のひとつに過ぎず、監視されたプロトコルに無理に当たらない。

### 証明書 EKU が「何に使えるか」を決める。間違った刃物を使わない
**Q1**: 証明書を取得したが認証に失敗する。EKU が違う疑いがある。どう確認する?
**A1**: 証明書の Extended Key Usage を見る。ドメイン認証には Client Authentication(1.3.6.1.5.5.7.3.2)、Smart Card Logon(1.3.6.1.4.1.311.20.2.2)、PKINIT Client Auth(1.3.6.1.5.2.3.4)、Any Purpose のいずれかが必要。Server Authentication、Code Signing、EFS のみの証明書はログオンに使えない。
**Q2**: テンプレート EKU が Server Authentication なら何ができる?
**A2**: PKINIT ログオンはできないが、中間者/偽造 TLS サーバー(偽 LDAPS、内部 HTTPS サービスなど)、またはサーバー証明書の信頼に依存する攻撃に使える。経路選択時にこれを認証に使わない。
**Q3**: EKU が Any Purpose または空の場合は?
**A3**: Any Purpose(ESC2)はクライアント認証を含むため直接使える。EKU が完全に空の場合も、多くの実装では Any Purpose と同等で認証できる。この種のテンプレートは価値が高く、優先する。
**Q4**: 非認証 EKU のテンプレートしかない場合、証明書経路は無駄か?
**A4**: 認証による権限昇格という点では刃物が違う。Client Auth を含むテンプレートを探す。または ESC4 の書き込み権限があるならテンプレートに Client Authentication EKU を直接追加する。EKU が違うならテンプレートを変えるか変更するのであって、間違った刃物を無理に使わない。

### セッション/認証情報形態の変換:証明書 ↔ チケット ↔ hash
**Q1**: 手元が証明書だが、現在のツール/横展開手法が求めるのは NT hash か TGT だ。どう変換する?
**A1**: 証明書 → TGT は PKINIT(certipy auth)。TGT → NT hash は U2U で PAC 内の NTLM 補足認証情報を解く(certipy auth が自動で hash を出す)。hash があれば pass-the-hash で横展開でき、TGT があれば pass-the-ticket ができる。三形態を必要に応じて相互変換し、単一形態に縛られない。
**Q2**: hash を取得後、平文へ戻したい場合は?
**A2**: hash は一般に不可逆だが、pass-the-hash でそのまま使うか、弱いパスワードならオフラインでブルートフォースするか、hash で TGT をリクエストして運用する。多くの横展開は平文を必要とせず、PtH/PtT で十分である。
**Q3**: チケットしかないが、ツールが求める ccache/kirbi 形式が一致しない?
**A3**: impacket の ticketConverter で kirbi(Windows/Rubeus)と ccache(Linux/impacket)を変換する。クロスプラットフォーム運用では形式変換がよくある詰まりどころなので、変換ツールを準備しておく。
**Q4**: 何も変換できず、認証が失敗し続ける場合は?
**A4**: 最も根本的な判定基準へ戻る。対象アカウントが有効か、証明書が期限切れ/失効していないか、クロックが同期しているか(Kerberos は時刻に敏感で、5 分超のずれは即失敗)。先にこれらの基礎項目を排除してから、高度なマッピング問題を疑う。

### マシンアカウント割当量と「自作マシンアカウント」の証明書への組み合わせ
**Q1**: 多くの証明書/RBCD チェーンは制御下のマシンアカウントを要求する。一般ユーザーが作れるか?
**A1**: `ms-DS-MachineAccountQuota` を見る。デフォルト 10 であり、一般ドメインユーザーは最大 10 台のコンピュータアカウントを追加できる。impacket の addcomputer か PowerMad で作り、その認証情報を取得して RBCD、shadow credentials、または relay/証明書チェーン内の「制御下身元」として使う。
**Q2**: 割当量が 0 に設定されている場合は?
**A2**: マシンアカウントを作れず、チェーンが断たれる。転換する。既存の制御可能なマシンアカウント(制圧済みホストの host$)を探すか、コンピュータオブジェクトの CreateChild 権限を持つ身元を探すか、マシンアカウント不要の支流(純粋な ESC1、ESC8 で直接 DC へ relay)へ切り替える。
**Q3**: マシンアカウントを作ったが RBCD 設定に失敗する?
**A3**: msDS-AllowedToActOnBehalfOfOtherIdentity の設定には対象マシンオブジェクトへの書き込み権限が必要である。マシンアカウントを作っただけで対象 DC への書き込み権限がなければ、DC への RBCD は成立しない。このとき shadow credentials(対象 KeyCredentialLink の変更。同じく書き込み権限が必要)または証明書直接申請の方が適する。
**Q4**: この一連がすべて通らない場合は?
**A4**: 対象オブジェクトへの書き込み権限という中核前提が欠けていることを示す。権限取得へ戻る。BloodHound で誰が対象を書けるかを探すか、先に他の ESC で権限昇格して書ける身元を取得し、その後マシンアカウントチェーンを組み立て直す。

### 「真の脆弱性」かハニーポット/囮テンプレートかを判断する
**Q1**: ドメインに極端に開いたテンプレート(Domain Users が enroll 可能 + 自己記入 SAN + クライアント認証 + 承認なし)がある。順調すぎて逆に疑わしい。どう判断する?
**A1**: 現代のブルーチームはこのような「完璧すぎる」ESC1 を狙った ADCS ハニーポットテンプレートを設置する。警戒シグナルは、テンプレート名が怪しい、作成時刻が新しい、正常な業務対応がない、Certipy 以外の使用履歴がない。判定基準は「打たない」ことではなく、監視をトリガーする確率を評価すること。
**Q2**: どう低リスクで検証する?
**A2**: まず低感度の対象(自分自身のアカウント)の証明書を申請して反応を観察し(アカウント無効化、セッション切断、ブルーチームの動き)、いきなり administrator を申請しない。ハニーポットなら DA 申請は即座に高優先度アラートを誘発する。
**Q3**: ハニーポットと確認した後は?
**A3**: それを避け、別の証明書経路か非証明書経路へ転換する。同時に、これはブルーチームが ADCS を監視しているというインテリジェンスであり、以降の証明書操作はすべてより慎重かつ最小化する。
**Q4**: 真偽を判断できないが時間が切迫している場合は?
**A4**: 交戦目標を秤にかける。競技/評価で得点が要るなら素早く利用し、露見リスクを受け入れる。実レッドチームで隠密重視なら迂回する。その判断をレポートに記録し、なぜそのテンプレートを選ぶ/選ばないかを説明する。

### クロスドメイン/クロスフォレストでの証明書攻撃の境界
**Q1**: 子ドメインで DA を取得し、証明書経路で親ドメイン/フォレストルートへ攻め込みたい。証明書はドメインを跨げるか?
**A1**: 企業 CA は通常 configuration パーティションに公開され、フォレスト全体から見える。ひとつの CA が複数ドメインにサービスできる。脆弱テンプレートがフォレスト内の他ドメインアカウントの証明書申請を許可する場合(SAN/SID が親ドメインアカウントを指す)、クロスドメインできる。鍵はテンプレート ACL と、CA がクロスドメイン SAN を受け入れるか。
**Q2**: フォレストルートの administrator 証明書を直接申請したい場合は?
**A2**: その CA がクロスドメイン身元を信頼して処理し、かつ対象ドメインの SID を埋め込める必要がある(強マッピング下)。子ドメイン DA は通常、SID History/信頼チケットでフォレストルートを打つのに既に十分であり、証明書は補助手段のひとつである。
**Q3**: クロスフォレスト(外部/フォレスト信頼)は?
**A3**: 証明書の信頼は明示的な PKI クロスフォレスト信頼を設定しない限り自動では跨らない。多くの場合クロスフォレストでは証明書経路は打てない。クロスフォレストの古典的手法(信頼アカウント、外部信頼列挙、SID filtering 迂回)へ転換する。
**Q4**: クロスドメイン証明書申請が拒否された?
**A4**: フォレスト内の成熟した権限昇格経路へ転換する。子ドメイン DA → クロスドメイン参照チケットの偽造(child の krbtgt + 対象 SID を利用)でフォレストルートを打つか、SID History 注入。証明書のクロスドメインが制限される場合、Kerberos 信頼経路の方が汎用的である。

### CA サーバーオブジェクト/PKI コンテナへの書き込み権限がある場合に ESC5 へ進む
**Q1**: BloodHound/Certipy が、自分(または制御下グループ)が CA のコンピュータオブジェクト、`pKIEnrollmentService` オブジェクト、`NTAuthCertificates`、`Public Key Services` コンテナへの書き込み権限を持つと提示した。これは ESC5 だ。どう換金する?
**A1**: ESC5 は PKI 制御面の ACL 面であり、単一テンプレートより範囲が広い。分岐判断:①CA ホストのコンピュータオブジェクトに書ける → RBCD または shadow credentials で CA ホスト SYSTEM を取得し、秘密鍵をエクスポートしてゴールデン証明書を作る。②`NTAuthCertificates` に書ける → 自己署名の悪意ある CA 証明書を信頼済み NTAuth に注入し、偽造証明書を全域で信頼させる。③`pKIEnrollmentService` に書ける → CA が公開するテンプレートリストを改竄する。判定基準:PKI の重要オブジェクトへの Write/GenericAll。
**Q2**: 三分岐のうちどれを優先する?
**A2**: 「CA ホスト制御へ直結できる」ものを優先する(CA コンピュータオブジェクトへの書き込み)。CA ホストを取ればすべてが可能になる(オンライン署名+オフライン偽造)。NTAuthCertificates への書き込みはより隠密だが、CA 証明書の生成と注入ができる必要があり、チェーンが長い。
**Q3**: 悪意ある CA を NTAuth に注入しても証明書が信頼されない?
**A3**: NTAuth の更新は各 DC への複製が必要で、DC にはローカルキャッシュがある(certutil -enterprise NTAuth)。伝播に遅延がある。また偽造証明書のチェーンが正しく、SID 強拡張付きである必要もある。複製完了とチェーン閉合を確認する。
**Q4**: ESC5 の書き込み権限が周辺的すぎて完全なチェーンを組めない場合は?
**A4**: BloodHound に戻して全体の経路計画に組み込む。ESC5 はしばしば長い ACL チェーンの一環である。PKI 意味論を使いこなせないなら、汎用の視点へ戻る。この書き込み権限は他にどんな高価値オブジェクトを書けるか。証明書に固執せず、RBCD/DCSync 認可など他の ACL 換金へ転換する。

### 証明書の issuance policy が特権グループに紐づく場合に ESC13 へ進む
**Q1**: Certipy があるテンプレートに issuance policy(certificate-issuance policy)OID を注記し、その OID が `msDS-OIDToGroupLink` で特権 AD グループへリンクされている。これは ESC13 だ。どう使う?
**A1**: ESC13 の核心は、ある issuance policy OID が OIDToGroupLink でグループ(例: 何らかの高権限グループ)へバインドされている場合、その policy 付き証明書を保持するアカウントは、認証後にそのトークンにそのグループメンバーシップを「獲得」する点にある。したがって、この特権 policy 付きテンプレートを enroll できる限り、証明書を取って認証すれば、暗黙的にそのグループメンバーへ昇格する。判定基準:テンプレートの `msPKI-Certificate-Policy` が指す OID が AD に group link を持ち、そのグループが特権グループであること。
**Q2**: どう着地して利用する?
**A2**: 現在の身元でそのテンプレートを enroll して証明書を取得し(SAN 自己記入は不要で、主体は自分自身のまま)、その後 PKINIT/Schannel で認証する。KDC/DC が OIDToGroupLink に基づいてその特権グループを PAC に加える。管理者にならなくても、グループメンバーシップによりそのグループがアクセスできるリソースへアクセスできる。
**Q3**: 認証後に期待したグループがトークンに現れない?
**A3**: OIDToGroupLink が実際に有効か(DC サポートが必要で、グループ種別/範囲が合法であること。通常は Universal グループ)、テンプレートの policy OID がリンク OID と完全一致するか、自分が本当にそのテンプレートの enroll 権限を持つかを確認する。どれか不一致ならグループは注入されない。
**Q4**: ESC13 が通らない場合はどこへ転換する?
**A4**: 他のテンプレート単位 ESC(1/2/3/9)、またはその特権グループの通常の乗っ取り経路(ACL/グループメンバー書き込み)へ転換する。ESC13 は特定の OID-グループバインドに依存する新しい稀な設定であり、通らなければ主流へ戻る。

### altSecurityIdentities の弱明示的マッピングがある場合に ESC14 へ進む
**Q1**: あるアカウントの `altSecurityIdentities` 属性に書き込める(または環境に弱明示的マッピングが存在する)ことを発見した。これは ESC14 だ。ESC9/10 の暗黙の弱マッピングとどう違い、どう使う?
**A1**: ESC14 は「明示的な証明書マッピング」を攻める。altSecurityIdentities 属性は証明書をあるアカウントへ明示的にバインドできる。対象(例: administrator)のこの属性に書き込めるなら、自分が制御/署名できる証明書の識別子(Issuer+Subject など、または Subject のみ/Issuer のみといった弱形式)を書き込み、対応する証明書で認証して対象へマッピングされる。判定基準:対象 altSecurityIdentities への書き込み権限、または環境に既に弱形式(X509IssuerSubject/X509SubjectOnly など偽造しやすい)のマッピングが存在すること。
**Q2**: 弱形式とは具体的に何で、なぜ危険か?
**A2**: 強形式は X509IssuerSerialNumber、X509SKI、X509SHA1PublicKey(一意の証明書にバインド)。弱形式は X509SubjectOnly、X509IssuerSubject、X509RFC822(メール)などで、「任意の Subject/Issuer が一致する証明書」で満たせる。攻撃者は Subject が一致する証明書を一枚用意するだけでなりすませる。
**Q3**: 対象への書き込み権限はないが、既存の弱マッピングだけ発見した場合は?
**A3**: その弱マッピング条件を満たす証明書を何とか取得する(Subject/Issuer が一致すればよい。Subject をカスタムできるテンプレートから発行できる可能性がある)。それで対象として認証する。前提は弱マッピングの一致条件を満たせること。
**Q4**: ESC14 の前提(属性書き込みまたは既存の弱マッピング)が不成立の場合は?
**A4**: 暗黙マッピング経路の ESC9/10(UPN 変更)、または直接 shadow credentials(KeyCredentialLink 変更。対象属性の書き込みだが意味論がより直接的)へ戻る。いずれも「対象のある属性を変更してなりすます」一族であり、前提が最も満たしやすいものを選ぶ。

### v1 テンプレートに Application Policies を注入できる場合に ESC15/EKUwu へ進む
**Q1**: 対象が schema version 1 のテンプレート(例: デフォルト WebServer)で、enroll 権限はあるが EKU がサーバー認証でログオンできない。まだ手はあるか?
**A1**: ある。ESC15/EKUwu(CVE-2024-49019)。v1 テンプレートは CSR 処理時に、リクエストに含まれる Application Policies を発行証明書へそのまま持ち込む。したがって CSR に Client Authentication、さらには Certificate Request Agent の application policy を注入し、本来サーバー認証のみの証明書にクライアント認証/代理能力を持たせられる。判定基準:テンプレートの schemaVersion=1 かつカスタム許可(WebServer など一部の v1 テンプレートはドメインユーザーに開かれていることが多い)。
**Q2**: どう攻める?
**A2**: -application-policies 対応の Certipy(新版)でその v1 テンプレートに申請し、Client Authentication ポリシーを注入してログオン可能な証明書を取得する。テンプレートが同時に SAN 自己記入を許可するなら、注入と組み合わせて ESC1 のように対象 UPN になりすませる。さらに Certificate Request Agent ポリシーを注入すれば ESC3 代理チェーンへ退化させられる。
**Q3**: 注入した application policy が証明書に入らない、または認証が失敗する?
**A3**: CA が対応パッチを当てていないか(パッチ後 CA はリクエスト側 application policy を無視する)、注入したのが application policy 拡張であって通常の EKU 拡張でないか(v1 ロジックが受け取るのは前者)、強証明書マッピングが SID を要求していないか(一括注入が必要)を確認する。
**Q4**: CA にパッチ済み / 制御できる v1 テンプレートがない場合は?
**A4**: 他のテンプレート単位 ESC または CA 単位経路へ転換する。ESC15 は新しい v1 処理の欠陥であり、パッチ後は無効になる。「v1 テンプレートに出会ったら一手多く試す」補助手段と位置づけ、主経路にしない。

### Certipy が EDR に遮断された、または環境に Python がない場合の転換
**Q1**: 制御下の Windows で ADCS を攻めたいが、Certipy/impacket をアップロードできないか、EDR に即殺される。どうする?
**A1**: 純粋なネイティブ手法へ転換し、システム標準の certutil/certreq/PowerShell PKI モジュールを使い、サードパーティバイナリを落とさない。列挙は `certutil -config - -ping`、`certutil -template`、`Get-CertificateTemplate`(PSPKI モジュール)。申請は INF ファイルを構築して `certreq -new` で CSR を生成し、`certreq -submit -config CA テンプレート` で提出する。これらは正当な管理ツールであり、EDR の命中率がはるかに低い。
**Q2**: ESC1 の自己記入 SAN をネイティブでどう埋め込む?
**A2**: certreq の INF/CSR で `[Extensions]` セクションに `2.5.29.17`(SubjectAltName)拡張を書くか、提出時に `-attrib "SAN:upn=administrator@dom"`(CA が属性 SAN を許可する場合、つまり ESC6 の場面)を使う。証明書取得後、Rubeus の `asktgt /certificate:` で PKINIT する。全行程ネイティブ + 単一 Rubeus。
**Q3**: Rubeus まで遮断される場合は?
**A3**: PowerShell で直接 Windows API を呼ぶか、certutil でエクスポートした pfx を `certutil -MergePFX` するか、システムの klist/標準機構を使う。または pfx を自分の Linux 機へ持ち出して impacket/Certipy で認証し、「申請」と「認証」を異なる環境へ分離して単機 EDR を回避する。
**Q4**: ネイティブツールもアプリケーションホワイトリスト/AMSI に塞がれた?
**A4**: 実行方式の次元へ転換する。防御が弱い別の制御下ホストで証明書操作を行うか、CA 通信をトンネル経由で Linux 攻撃機へプロキシし、純粋にリモートで打つ(証明書攻撃の大半はネットワークプロトコルであり、対象機ローカルで実行する必要はない)。ツール遮断は「実行着地点」の問題であり、着地点を変えればよい。EDR と死闘しない。

### 制圧済みホストから既存の証明書と秘密鍵を窃取する(THEFT 類)
**Q1**: ホストを制圧した。新しい証明書を申請せず、ユーザー/マシンが既に持つ証明書を直接盗むには?
**A1**: THEFT 経路。CA 発行ログをトリガーしない。入手元:①ユーザー/マシン証明書ストア(`certutil -store My`、mimikatz の `crypto::certificates /export`)から秘密鍵付き pfx をエクスポート。②DPAPI 保護の秘密鍵(`%APPDATA%\Microsoft\Crypto` と masterkey。SharpDPAPI/mimikatz で解く)。③マシンアカウント証明書は SYSTEM コンテキストでエクスポート。クライアント認証できる証明書を盗めば、その主体になりすまして PKINIT できる。
**Q2**: 秘密鍵がエクスポート不可とマークされている?
**A2**: mimikatz の `crypto::capi` / `crypto::cng` で CryptoAPI/CNG に patch し、エクスポート不可秘密鍵をエクスポート可能にしてから export する。証明書が本機にあり、十分な権限(ユーザー級証明書はユーザーコンテキスト、マシン証明書は SYSTEM)が必要。
**Q3**: 証明書はあるが DPAPI masterkey が解けない?
**A3**: ユーザー DPAPI masterkey にはユーザーパスワード/hash または domain backup key が必要。転換する。DCSync で取得した domain DPAPI backup key で任意ユーザーの masterkey を解くか、ユーザーのアクティブセッション内でそのコンテキストでエクスポートして復号を回避する。
**Q4**: このマシンに価値ある証明書がまったくない場合は?
**A4**: 別のホスト(管理者がログオンしたことがある、または証明書認証アプリを展開しているマシン)へ転換するか、THEFT を諦めて能動申請(ESC1 など)へ切り替える。THEFT は「対象機にたまたま高価な証明書がある」ことに依存する。なければマシンを変えるか経路を変える。
**Q5**: 盗んだ証明書がもうすぐ期限切れの場合?
**A5**: 有効期間内に即座に PKINIT で TGT 交換/NT hash 解読し、短命の証明書をより持続的な認証情報形態へ変換する(hash は PtH 可能、TGT は更新可能)。または取得した権限で別の長期証明書を申請する。証明書自体の期限切れは、既に交換済みの hash には影響しない。

### 仕上げ:証明書攻撃チェーンの清掃と納品
**Q1**: 証明書経路でドメインコントローラを取得した。交戦の仕上げで何を処理すべきか?
**A1**: 自分が作った証拠を点検する。申請した全証明書(request id/シリアル番号を記録)、一時的に変更したテンプレート設定(復元済みか)、追加した CA officer ロール、作ったマシンアカウント、書き込んだ KeyCredentialLink/RBCD 属性。ひとつずつ復元するか、レポートに載せて防御側に失効/削除を依頼する。
**Q2**: 何を必ず復元し、何をブルーチームに残す?
**A2**: 破壊的/永続的なもの(変更したテンプレート、追加した officer、作ったマシンアカウント、shadow credential 項目)は復元して穴を残さない。発行した証明書は一覧にして失効を依頼する。レッドチームの納品は、防御側が自分が開けた全ての扉を完全に閉じられるようにする。
**Q3**: レポートで証明書経路をどう書けば価値があるか?
**A3**: 具体的にどの ESC か、前提設定のどこが誤っているか(例: あるテンプレートが自己記入 SAN とクライアント認証 EKU を同時に開き、Domain Users に公開)、修復提案(テンプレート ACL の締め付け/自己記入 SAN の無効化/強マッピングパッチ適用/承認の有効化/CA Web エンドポイントの閉鎖または EPA)を書く。攻撃可能の証明だけでなく、実行可能な修復を示す。
**Q4**: 顧客が「ESC 全種をどう防ぐか」と尋ねたら?
**A4**: 多層防御の提案をする。定期的に Certipy/PSPKIAudit で全 ESC を自己点検、テンプレート権限と EKU の最小化、Manager Approval の有効化、強証明書マッピングの強制(KB5014754 enforcement)、CA Web/RPC エンドポイントへの EPA または閉鎖、4886/4887 と SAN 不一致の監視、MachineAccountQuota の制限、CA 秘密鍵の保護(HSM)。これは経路選択ツリー全体を根本から絞る。
