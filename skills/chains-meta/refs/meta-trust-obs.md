# メタ意思決定 · 観測を真とするか偽とするか:ツール/環境が私を騙しているか

### WAF が 200 を返したが内容が差し替えられた。これは突破できたのか
**Q1**: 私の送った payload リクエストが 200 を返すが、ページに期待する実行結果がなく、正常な業務 HTML だけがある。成功したがエコーがないのか、WAF/ゲートウェイに遮られてページを差し替えられたのか。
**A1**: 先にステータスコードを信じない。「陰性対照 + 陽性対照」をする:100% 合法なリクエストを送ってベースラインのレスポンス長/ヘッダーを見る、それから 100% 悪意だが構文が明らかに非合法なリクエストを送る。悪意リクエストと payload リクエストの返す body 長、Server ヘッダー、レスポンス時間がほぼ完全に同一で、合法リクエストが違うなら、WAF が中間で横取りし 200 を偽造した。
**Q2**: アプリケーション自身がエラーを飲み込んだのではなく WAF であることをさらに確認するには。
**A2**: レスポンスチェーンの特徴を見る。増えた中間層 header(特定のクラウド WAF が X-Cache/カスタム request-id を付けるなど)、TLS フィンガープリント変化、TTL 跳変、またはレスポンス時間が異常に短い(WAF が直接返し、バックエンドへ届いていない)。同じ payload を清浄な出口 IP に替えて再打し、IP を替えると挙動が変わるなら、境界装置であることがほぼ確定。
**Q3**: WAF 遮断と確認した。次のステップは。
**A3**: 同じインジェクション点で考えなしに変形しない。まず WAF の「トリガー境界」を測る:二分法で payload を削り、どの token が遮断をトリガーするか、キーワードか、特殊文字か、長さかを探す。トリガー点を特定してから、的を絞ってエンコーディング/チャンク分割/大文字小文字/コメントで迂回する。
**Q4**: このインジェクション点が WAF に固く溶接され、迂回できない(遮断されて方向転換)。どうするか。
**A4**: 直交次元へ方向転換。payload でなく攻撃面を替える。同じ脆弱性には往々にして複数の入口がある:HTTP メソッドを替える、パラメータ位置を替える(query→body→header→cookie→JSON)、内容型を替える(form→multipart→json、多くの WAF は一種しか解析しない)、または同源の別の WAF 未カバー API(内部 API、旧バージョンパス、バックアップドメイン)を探す。WAF ルールは通常 Web フロントエンドに掛かっており、バックエンドポートへ直連または隣接サイトは完全に迂回できるかもしれない。
**Q5**: 判定基準のまとめ、いつ「ここは確かに打てない」と認定すべきか。
**A5**: 陽性/陰性対照が、全変形が同一の偽造レスポンスに収束することを証明し、かつ IP 替え/入口替え/エンコーディング替えの三つの直交次元が全て無効な時、「WAF 強防御」ラベルを記録し、アセット測量へ方向転換して防御の弱い傍路アセットを探す。この一点で消耗し続けない。

### リバースシェルが接続できた。しかしハニーポットではないか
**Q1**: 私のリバースシェルが秒で戻ってきて、コマンドが全て実行でき、エコーも清浄。順調すぎて逆に不安になる。ハニーポットが私に付き合って演じているのではないか。
**A1**: 実際の本番ホストは往々にして「汚い」。雑然とした履歴プロセス、実在の業務負荷、不規則なユーザーディレクトリがある。ハニーポットは往々にして過度に清浄、または過度に魅力的。まず無害な環境偵察をする:uptime、プロセスツリー、/etc/passwd の実ユーザー数、bash_history、cron、ネットワーク接続。「本番 DB サーバー」のプロセスリストが空で、実在の業務接続がなく、home ディレクトリにおとりファイルが一つだけなら、高度に疑わしい。
**Q2**: 低コストの真偽判別動作には他に何があるか。
**A2**: レスポンスの一致性とリソースの真実性を見る。ハニーポットは往々にしてコンテナ/エミュレータを使い、cat /proc/cpuinfo、free、mount、dmesg が露呈する(異常な仮想化識別、モックされた /proc)。実際のカーネル対話を要する操作(/proc/self/status を読む、ulimit、uname -a とディストリビューションファイルの対比)を実行し、データが自己整合するかを見る。故意に存在しないコマンドを実行し、エラーが実際の shell のエラー形式かを観察する。
**Q3**: ハニーポットを疑うが確信がない。どう行動するか。
**A3**: 「低ノイズ、否認可能」モードに切り替える。急いでツールをアップロードせず、mimikatz を走らせず、横展開しない。全操作が録画されていると仮定する:読み取り専用偵察だけを行い、独自の TTP を足場確保しない。同時にこの「アセット」の攻撃チェーン上の価値を評価する。それが孤立し、実在のセグメントへ通じないなら、ハニーポットの可能性はより高い。
**Q4**: ハニーポットとほぼ確認した(おびき出された)。どこへ方向転換するか。
**A4**: 即直交方向転換。この経路を放棄し、一つ前のジャンプへ戻って、私が「どう」ここへ導かれたかを再評価する。おびき出しには往々にして餌がある:目立ちすぎる認証情報、開放的すぎるポート、完璧すぎる脆弱性。餌を遡って発見したら、逆に除外する:実際の入口は通常もっと秘匿で、もっと「打ちにくい」。リソースを「見た目平凡だが確かに業務中核」のアセットへ転じる。
**Q5**: 次回またハニーポットを踏まないためには。
**A5**: 「順調すぎる=疑わしい」のメタ判定基準を建てる。「ゼロコストで高価値対象を取る」状況は全て、真実性の交差検証(業務トラフィック、実ユーザー活動、他のアセットとの到達可能性)を通ってから深入りする。信頼は多源裏付けに頼り、単点の順調に頼らない。

### コマンド実行のエコーが空:エコーなしなのかフィルタリングされたのか
**Q1**: 疑似 RCE 点でコマンドを打つと、ページに何のエコーもない。コマンドが実行されていないのか、実行されたが結果がページに戻らないのか。
**A1**: 「エコーの有無」で成否を判断せず、「観測可能な副作用の有無」で判断する。エコーは多くの観測チャネルの一つに過ぎない。先に時間プローブをする:sleep/遅延コマンドを実行し、レスポンス時間が安定して伸びるなら、コマンドは確かに実行されており、エコーチャネルが通じないだけ。これは「エコー盲」と「実行盲」を分ける第一刀。
**Q2**: 時間プローブも明らかでない場合は。
**A2**: 帯域外(OOB)チャネルに替える。対象に、私が観測できる接続を能動的に発起させる:DNS クエリ、私のサーバーへの HTTP コールバック。DNS 帯域外の突破力が最も強い(多くの環境で DNS の外向き通信は制限されない)。私の DNS ログが対象からの解析リクエストを受信すれば、実行は 100% 確定。エコーの有無は根本的に重要でない。
**Q3**: OOB も戻ってこない。実行されていないのか、外向き通信しないのか。
**A3**: これは重要な分岐で、区別しなければならない。ファイルシステムの副作用でローカル検証をする:コマンドに Web アクセス可能なディレクトリへファイルを書かせ、HTTP でそのファイルへアクセスする。ファイルが現れれば、コマンド実行は成功だが対象は完全に外向き通信しない(純内部ネットワーク)。ファイルも現れなければ、初めてコマンドがそもそも実行されていない方向へ傾く。
**Q4**: 実行成功だがエコーもなく外向き通信もしないと確認した。どこへ方向転換するか。
**A4**: 「盲状態利用」の打法へ方向転換。全盲なら、エコーを自分が読める場所へリダイレクトする:コマンド結果を Web ディレクトリへ書いて読む、データベースの私が照会できるフィールドへ書く、レスポンス時間で一バイトずつ盲帯する(遅いが信頼できる)。同時に一つのことを優先する。shell を盲状態から対話状態に昇格する方法を考える(メモリ型、正向接続で内部ネットワークポートをリスニングしてから到達方法を考える)。盲状態を徹底的に脱する。
**Q5**: 副作用検証もできないなら(判定基準)。
**A5**: 時間プローブ、OOB、ファイル副作用の三チャネルが全て陰性の時だけ、「この点は実行不能」と判定できる。脆弱性点自体が誤判定か(誤検知判定チェーン参照)を疑うのに戻る。各種のコマンドエンコーディングを無限に足し続けない。

### curl タイムアウト:対象が死んだのか私が外向き通信できないのか
**Q1**: 対象へのリクエストが直接タイムアウト。対象が落ちた/ファイアウォールがパケット破棄したのか、私のこの出口チェーンに問題があるのか。
**A1**: タイムアウトは最も人を騙す観測。先に「私のこの端」を除外する。同一時刻に既知の安定した外部サイト(公共 IP、大サイト)へリクエストし、それも遅い/タイムアウトなら、問題は私のローカルか出口プロキシで、対象と無関係。自分のネットワークの責任を対象に押し付けて「対象オフライン」と誤判定しない。
**Q2**: 私の外向き通信は正常。では対象の問題か。
**A2**: 対象側の故障型を細分する。TCP 層プローブ:直接 nc/telnet で対象ポートへ。TCP ハンドシェイクが成功するがアプリケーション層がタイムアウトなら、アプリケーションの hang か WAF の静黙破棄。TCP がそもそも接続できないなら(RST は拒否、無応答は破棄)、ファイアウォールの drop かホストオフライン。RST と静黙破棄は意味が全く異なる。RST はホストが生きていて拒否していることを示す。
**Q3**: 「ACL が定向で私をブロックした」と「対象が誰にもタイムアウト」をどう区別するか。
**A3**: 出口を替えて検証する。対象に一度も接触したことのない清浄な IP(別の C セグメント/クラウドベンダー/プロキシ)で再打つ。新しい IP が通じ、旧 IP がタイムアウトなら、私の IP がブラックリストされた(ブロックをトリガーした)。新旧ともタイムアウトなら、対象の普遍的な問題。
**Q4**: 私の IP がブロックされた(遮断された)と確認した。どこへ方向転換するか。
**A4**: 直交方向転換、出口インフラとリズムへ。第一に、出口 IP プールをローテーションし、リクエストレート/並行数を下げる(ブロックは往々にして頻度トリガー)。第二に、どの動作がブロックをトリガーしたかを反省する(高頻度スキャン?特徴 payload?)。その類の高ノイズ動作を低速、擬人、分散に変える。第三に、IP 級でなくアカウント級ブロックなら、身分認証情報を替える。中核は同じ「マークされた」身分で壁に突き続けないこと。
**Q5**: 判定基準:いつ対象が本当に到達不能で、私の問題でないと認定するか。
**A5**: 「複数の清浄出口 + 直接 TCP プローブ + 既知外部対照」の三者が一致して対象の無応答を指す時だけ、対象到達不能と登録し、他のアセットを打つか、時間窓を替えて再試行する(一時的な保守かもしれない)。

### nmap 全ポート open:本当に開放なのかファイアウォールが演じているのか
**Q1**: 一台のホストをスキャンしたら、ほぼ全ポートが open と表示。これは正常でない。本当に全開なのか、装置がスキャナを騙しているのか。
**A1**: 大面積 open はほぼ確実に欺瞞。実際のホストが数百ポート全開なのは稀。これは通常、ファイアウォールの「tarpit/SYN プロキシ」かハニーポットで、全ての SYN に SYN-ACK を返す。ポート状態表を信じず、アプリケーション層検証に行く:ランダムに open ポートを数個選び、実際にプロトコルハンドシェイクをする(HTTP GET、SSH banner 取得)。各ポートが同じものを返すか、実 banner を返さないなら、偽装。
**Q2**: 真 open と偽 open をどう体系的に見分けるか。
**A2**: banner の多様性と挙動の一致性を対比する。実際のホストはポートごとに別のサービスが走り、banner が異なり、応答タイミングが異なる。欺瞞装置は往々にして全ポートの挙動が高度に酷似(同じ TTL、同じ window、同じ遅延、同じか空の banner)。絶対に開き得ない高位ポート(ランダムな 65000+)を一つ選び、それも open なら、全ポート欺瞞がほぼ実锤。
**Q3**: ポート表が汚染されたと確認した。実際の開放ポートをどう得るか。
**A3**: 能動スキャンを信じず、受動/アプリケーション層情報から逆算する。このホストがトラフィックで実際に通信するポート、DNS/証明書/HTTP が露出するサービスの手がかり、既に取ったホストの側から見て本当にリスニングするポートを見る。能動スキャンが汚染されたなら、情報源を替える。
**Q4**: スキャンが tarpit に引きずられ、結果が全く信頼できない(遮断された)。どこへ方向転換するか。
**A4**: 直交方向転換、スキャン技術と視点へ。第一に、スキャン方式を替える:tarpit は SYN スキャンを狙う。ACK スキャンを試すか、少数の推測ポートに直接完全なアプリケーションハンドシェイクをする。第二に、視点を替える:既に内部ネットワークの足場があるなら、内部からこのホストを見る方が外からファイアウォール越しにスキャンするよりはるかに正確。ファイアウォール欺瞞は通常外にしか効かない。第三に、スキャンをさらに拡大せず、「対象化検証」に転じ、高価値ポートを数個だけ検証する。
**Q5**: 判定基準のまとめ。
**A5**: ポート状態と「アプリケーション層が本当にセッションを確立できるか」が一致しない時、永遠にアプリケーション層を基準とする。スキャナの open は「SYN-ACK を受けた」だけで、「サービスがある」と等しくない。ポートスキャン結果を結論でなく手がかりに降格する。

### sqlmap が注入不可能と言う。信じるべきか
**Q1**: sqlmap が特定のパラメータを回し終えて not injectable と報告した。この点を放棄すべきか。
**A1**: ツールの陰性結論は最も信じられない。sqlmap の判定基準はその内蔵の一組の payload と検知ロジックで、点自体の安全を意味しない。先に sqlmap がこの点を本当に「はっきり見た」かを確認する:正しい --data、--cookie、認証状態、CSRF token、非デフォルト注入位置が必要か。多くの「注入不可能」は実は sqlmap のリクエストが注入可能なコード経路に全く到達していない(セッション失効、パラメータを正しく付けていない)。
**Q2**: パラメータを全て正しく付けても negative を返す場合は。
**A2**: 手作業の最小検証に戻る。最も素朴なプローブを使う:一つの引用符でエラー/状態変化があるか、一対の論理真偽(和 と 或)でレスポンスに安定した差異があるか。ツールが派手な payload を一山走らせて失敗しても、最も基本的なブール盲インジェクションが存在しないことを意味しない。手作業はツールが見られない微細な差分(長さ 1 バイト差、並び順変化、特定のレコードの出現/消滅)を見られる。
**Q3**: 手作業でも明らかな差異が見えない。本当に穴がないのか。
**A3**: 注入型の仮定を替える。sqlmap はデフォルトで数類のよくある注入に重点を置くが、対象は二次注入(payload を保存し、別の機能でトリガー)、または非 SQL の注入(NoSQL、ORM 層、テンプレート)かもしれない。観測チャネルも間違っているかもしれない。この点は時間次元または別のページでしか現れないかもしれない。一つの検知発想で全ての可能性を否定しない。
**Q4**: このパラメータは確かに注入できない(遮断された)と確認した。どこへ方向転換するか。
**A4**: 直交方向転換、他のパラメータと他のデータ流入点へ。一つのアプリケーションに数十のパラメータがあり、sqlmap の一つの negative は一つを否定しただけ。優先して「直接 SQL に入る」高確率点を測る:検索、ソート(order by は往々にして拼接)、フィルタリング、エクスポート、レポート、ID 類パラメータ。同時に攻撃類を替える。注入全体が打てないなら、このアプリケーションのアップロード、SSRF、権限外アクセス、デシリアライズを見る。
**Q5**: メタ判定基準:自動化ツールの「見つからない」をどう見るか。
**A5**: ツールの陽性結論(見つけた)は通常信じられる。陰性結論(見つからない)は「この一組のルールで今回はトリガーしなかった」だけで、決して「存在しない」と等しくない。ツールの negative に、あなたが別の理由で疑う攻撃面を閉じさせない。

### アップロード成功だがアクセス 404:パスマッピングの錯覚
**Q1**: ファイルアップロード API が私に「アップロード成功」を返し、ファイル名/パスも与えた。しかしアクセスすると 404。本当にアップロードされていないのか、パスが合わないのか。
**A1**: 「アップロード成功」はアプリケーションの言い分で、ファイルが Web アクセス可能ディレクトリに落ちたとは限らない。先にパスマッピングを疑う:API が返すパスは内部ストレージパスで、URL パスではないかもしれない。またはオブジェクトストレージ/CDN があり、実際のアクセス先は別のドメインと署名 URL。サーバー内部パスを持って HTTP アクセスして失敗と判定しない。
**Q2**: ファイルの実際のアクセス可能位置をどう見つけるか。
**A2**: 多源交差で特定する。アップロード成功レスポンスの全フィールドを見る(実際の url、bucket、hash 命名規則が隠れていることが多い);ページのアップロード後の表示ロジックを見る(フロントエンドがこのファイルをどう参照するか、それこそ真の URL);正常にアップロードした合法ファイル(アバター画像など)のアクセスパスを対比し、命名/ディレクトリ規則を逆算する。既知の正常サンプルで較正し、私の悪意ファイルに当てはめる。
**Q3**: パスを見つけてもまだ 404、または元の内容を返して解析しない。どうするか。
**A3**: 二種の失敗を区別する:ファイルが存在しない(404)vs ファイルはあるが私の望む方式で実行されない(ダウンロードできるがスクリプトとして解析されない)。ダウンロードできるならアップロード成功で、実行環境が合わないだけ。問題は「アップロード」から「どうそれを実行可能コードとして解析させるか」(ディレクトリ解析、内容型、二次レンダリング点)へ変わる。観測を「チェーンのどの環で詰まったか」まで精密にする。
**Q4**: ファイルが確かにどの制御可能な到達可能位置にも落ちない(遮断された)と確認した。どこへ方向転換するか。
**A4**: 直交方向転換、「アップロードの他の危害面」を利用する。getshell に執着しない。アップロード点は webshell を足場確保できなくても、XXE/SVG/XSS(レンダリング型)、パス横断で任意ファイル上書き、SSRF(リモート取得型アップロード)、デシリアライズ(一部の形式解析)、サービス拒否があり得る。同時に第二のアップロード/ファイル書き込み入口(ログ、キャッシュ、エクスポート)を探す。そのストレージポリシーが違うかもしれない。
**Q5**: 判定基準:いつアップロードが打てないと判定するか。
**A5**: 「ファイルが確かにサーバーに存在する(間接証拠あり)が、全到達可能パスで解析をトリガーできず、他の危害面もない」時だけ、この点を降格する。ファイルの実際の位置を特定していない限り、404 だけで失敗と判定できない。404 の最もよくある原因は私が場所を間違えたこと。

### 時間盲インジェクションの遅延が不安定:真の遅延かネットワークの揺れか
**Q1**: 時間盲インジェクションで sleep を注入すると、レスポンスが時に遅く時に速く、データがぐちゃぐちゃに出る。遅延がネットワークの揺れに飲み込まれたのか、そもそも注入されていないのか。
**A1**: 単回の遅延は信じられない。必ず統計化する。一回のレスポンス時間で結論を下さない。同じ真値プローブを複数回連続で送り中央値を取る。sleep なしのベースライン中央値と対比する。ネットワークの揺れはランダムノイズ、真の遅延は安定したオフセット。sleep ありの中央値がベースラインより安定して sleep 時長分ほど高いなら、注入は本当で、繰り返しサンプリングでノイズを除く必要があるだけ。
**Q2**: 揺れが大きすぎて中央値でも分離できない場合は。
**A2**: 信号雑音比を大きくする。sleep 時長を揺れ幅よりはるかに大きくする(揺れ ±1s なら sleep 5~8s を使う)、真の信号をノイズより明らかに高くする。同時に並行数を 1 に下げ、直列で送り、自分で対象やリンクを打ち揺らさない。必要なら各プローブをリトライして最小値を取る(真の遅延は加算の下限、ネットワークは遅くなるだけで速くならないので、「最小観測値」が実際の処理時間に近い)。
**Q3**: sleep を長くしたら対象レスポンスがレート制限または防御をトリガーした場合は。
**A3**: よりプローブ数を省くエンコーディング戦略に替える。時間盲インジェクションは bit ごとに送信し、極めて遅く脆い。二分/ビット演算で一度に複数 bit に迫り、総リクエスト数を減らす。あるいは時間チャネルをきっぱり諦め、ブール差分、エラーエコー、OOB というより速く安定したチャネルを探しに戻る。時間チャネルは最後の手段。
**Q4**: 時間チャネルが徹底的に使えない(リンクが揺れすぎ/レート制限、遮断された)。どこへ方向転換するか。
**A4**: 直交方向転換、非時間の観測次元へ。注入の存在を確認したなら(時間上でかすかに見えるだけでも)、観測の昇格を考える:エラーを構築してデータをエラー情報に入れられるか(エラー注入)、データを私の DNS/HTTP へ帯域外できるか(OOB 注入)、ブール型のページ差異を探せるか。「遅いチャネル」を「帯域のより高いチャネル」に替えるのがここの中核方向転換。
**Q5**: 判定基準:時間遅延が注入であり偶然でないことをどう確認するか。
**A5**: 陰陽対照をする。「真なら sleep」「偽なら sleep しない」の二つの論理が逆の payload を注入し、各複数回サンプリングする。真の論理が安定して遅く、偽の論理が安定して速く、かつ再現できる時だけ、時間チャネルが有効で、その抽出データを信じる。

### DNS 帯域外が戻ってこない:対象が外向き通信しないのかリゾルバがキャッシュしているのか
**Q1**: OOB DNS payload を打ったが、私の権威 DNS サーバーが対象の解析リクエストを受信しない。対象が外向き通信しないのか、中間のキャッシュ/リゾルバが飲み込んだのか。
**A1**: 急いで「外向き通信しない」と判定しない。DNS 帯域外チェーンは長く、どの環も観測を食い得る。先に自分側を除外する:私の権威 DNS が本当にパケットを受信しているか(自分のマシンでサブドメインを dig し、ログが記録できるか確認)。ドメイン委任が正しいか。多くの「戻ってこない」は実は私の受信端の設定ができていない。
**Q2**: 受信端が正常と確認したが、まだデータがない。中間段階をどう切り分けるか。
**A2**: 要点:各プローブにユニークなサブドメイン(ランダムプレフィックス)を使い、キャッシュを徹底的に迂回する。固定ドメインを使うと、対象の再帰リゾルバが結果をキャッシュして私の権威サーバーに再問いしない。私は二度と受信できない。ユニークサブドメインは「キャッシュ命中」と「本当に発出されていない」を区別できる。ユニークサブドメインに替えて受信できたなら、以前はキャッシュの錯覚。まだないなら、さらに進む。
**Q3**: ユニークサブドメインでも受信できない。対象側が外向き通信しないことをどう確認するか。
**A3**: 階層化して外向き通信能力を検証する。対象は DNS は外向き通信しないが HTTP は外向き通信するかもしれず、逆もあり得る。並行して複数の OOB チャネルを測る:DNS、HTTP、HTTPS、ICMP、さらには別のポート。どのチャネルが戻るかでそれを使う。全チャネルが戻らないなら、「ファイル副作用のローカル検証」(エコーチェーン参照)と合わせ、コマンドが確かに実行されたが環境が純内部ネットワークと確認する。
**Q4**: 対象が完全に外向き通信しない(遮断された)と確認した。どこへ方向転換するか。
**A4**: 直交方向転換、純内部ネットワーク作戦のパラダイムへ。一切の帯域外依存の発想を放棄する:エコーをローカルの読める位置へリダイレクト、結果を対象自身の照会できる場所へ書く、レスポンス内容/時間で帯域内伝送する。戦略的に、「この外向き通信しないホストを踏み台に、外向き通信できる隣人を探す」へ転じる。内部ネットワークには必ず外向き通信できるアセットがある。それを取ってチャネルを建てる。
**Q5**: 判定基準:「キャッシュ欺瞞」「受信端故障」「真の外向き通信なし」をどう区別するか。
**A5**: 三ステップで固定する:先に受信端を自測(私側の故障除外)→ ユニークサブドメインに替える(キャッシュ除外)→ 多チャネル並測(部分外向き通信 vs 完全外向き通信なしの区別)。三ステップを終えても全陰性なら、「対象が外向き通信しない」と登録する。どのステップを飛ばしても「私が設定を間違えた」を「対象が封じた」と誤判定し得る。

### 権限昇格 exp が成功を報告するが whoami はまだ一般ユーザー
**Q1**: 権限昇格 exp を走らせ、出力が「[+] success」の山。しかしその後 id/whoami は私がまだ元の一般ユーザーと表示。結局上がったのか。
**A1**: exp 自身が印刷する "success" は、それがフローを実行し終えたことであり、私が特権文脈を得たことと等しくない。最もよくある落とし穴:権限昇格がサブプロセス/新 shell で成功したが、私の現在の shell が継承していない。まず exp が root shell を spawn してそれが既に退出していないか、私がそれの開いたポートへ接続/書いたファイルを読む必要があるかを確認する。exp の自己申告でなく、id の出力を信じる。
**Q2**: 現在の文脈の権限が変わっていないと確認した。exp は結局成ったのか。
**A2**: 特権 shell でなく特権の副作用を探す。exp が本当に成功すると通常痕跡を残す:suid ファイルを作成したか、/etc/passwd や sudoers を書いたか、新しいユーザーを生成したか、特定のポートで root リスニングを起動したか。これらの副作用が本当に起きたかを検証する。副作用が一つもなければ、exp はおそらく本当に利用成功しておらず、フローを走り終えただけ。
**Q3**: 副作用もない。exp が当たらなかったのか環境が合わないのか。
**A3**: 根因検証に戻る。権限昇格 exp は精密なカーネル/コンポーネントバージョン、アーキテクチャ、緩和措置(KASLR/SMEP/SMAP)に極度に依存する。対象の実際のバージョン(banner を信じず実際のファイルを読む)、アーキテクチャ、脆弱性がパッチ済みかを照合する。多くの「success だが上がっていない」は、exp が緩和あり/パッチ済みの環境で空回りしたもの。実際の環境フィンガープリントで較正し、exp の楽観出力を信じない。
**Q4**: この exp がこの環境で無効と確認した(遮断された)。どこへ方向転換するか。
**A4**: 直交方向転換、他の権限昇格次元へ。単一のカーネル exp に執着しない。権限昇格面は非常に広い:設定ミスの suid バイナリ、書き込み可能なサービス/計画タスク、sudo ルール、能力(capabilities)、認証情報再利用(他のプロセス/ファイルのパスワード)、コンテナエスケープ。先に一度の体系的なローカル列挙を行い、実際の設定に経路を露出させる。カーネル exp のバージョンを替えて運試しし続けない。カーネル exp はリスクが高い(落ちやすい)、設定類の権限昇格はより安定。
**Q5**: 判定基準:権限昇格が本当に成功したとどう確認するか。
**A5**: 唯一の判定基準は「私が制御可能な文脈で、特権身分としてコマンドを実行し、特権でしか読めないもの(特定の root-only ファイルなど)を安定して読める」こと。exp の印刷、戻り値、一瞬の root プロンプトは数えない。継続的に再現できる特権操作だけが数える。

### mimikatz が認証情報を一山掴んだ。おとりではないか
**Q1**: 一台のマシンで認証情報/hash を一群 dump した。数も多い。これらは本当に使える認証情報か、ハニーポットが仕込んだおとり(canary)か。
**A1**: 認証情報の価値は「使える」ことにあり、「掴めた」ことにはない。取れたからと興奮して横展開しない。先に低リスクで一部を検証する:おとり認証情報には往々にして canary 特徴がある。アカウント名が整いすぎ(admin/backup の類)、パスワードが古典的すぎる、またはこのアカウントが実環境で決してログインしない。最も秘匿な方式(オフライン検証、読み取り専用照会)で先に一、二個を探る。全部を一度にスプレーに使わない。
**Q2**: 「使う」前に真偽をどう判断するか。
**A2**: 認証情報の文脈の自己整合性を見る。実認証情報のアカウントはディレクトリに正常な属性を持つ:合理的な最終ログイン時間、所属グループ、説明、logon カウント。おとりアカウントは往々にして属性が異常(一度もログインしていないのに高権限、作成時間が他のアカウントと不連続、説明が空白か酷似)。このマシン自身の信頼度(ハニーポットチェーン参照)と総合判断する。汚いマシン上の汚い認証情報ほどむしろ本物かもしれない。
**Q3**: オフラインで真偽を判定できない。実測しなければならない。リスクをどう最小にするか。
**A3**: 単点、低頻度、否認可能に試す。中等度の権限で、最もおとりらしくない認証情報を一つ選び、低敏感の対象に単回認証し、告警挙動をトリガーするか観察する(アカウントが瞬間禁止、ハニーポット式の偽成功、異常リダイレクト)。canary 認証情報は一度使われると往々にして即告警さらにはロックする。「使った後の周辺挙動の突然変異」自体がそれがおとりである信号。
**Q4**: この一群の認証情報がおとり/全て canary(おびき出された)と確認した。どこへ方向転換するか。
**A4**: 直交方向転換、認証情報の他の出所へ。この一群にはもう触れない。実認証情報はもっと目立たない場所に隠れている:プロセスメモリ、設定ファイル、スクリプトのハードコード、ブラウザ/ソフト保存、チケットキャッシュ、計画タスク内のサービスアカウント。おとりは通常最も dump しやすい場所に置かれる。本物は往々にして一歩多く歩く必要がある。同時に警戒:一群の認証情報を簡単に dump できるこのマシン自体が罠かもしれない。再評価する。
**Q5**: 判定基準:認証情報の信頼度をどう階層化するか。
**A5**: 「信頼度の階層化」を建てる:アカウント属性が自己整合 + 出所が秘匿 + 業務ロールと一致 = 高信頼;明るみに置かれ、属性異常、権限とロール不整合 = 疑似おとり。永遠に最も高信頼、最低敏感の組み合わせから試し始め、canary トリガーの爆発半径を最小に抑える。

### 対象 banner の報告するバージョンは信じられるか
**Q1**: 特定のサービスの banner を掴み、既知の穴のあるバージョン番号が書いてある。直接対応 exp を上げるか。
**A1**: banner は最も偽造/誤導されやすい観測。管理者が故意に変えた偽バージョン(ハニーポットがあなたに特定 exp を上げさせる)、リバースプロキシ/WAF の偽造、またはパッチがコードだけ直してバージョン番号を変えていない(banner は古いが実は修正済み)の可能性。banner バージョンを免死金牌にせず、「要検証の仮説」として扱う。「事実」ではない。
**Q2**: banner だけを信じず実際のバージョンをどう検証するか。
**A2**: 挙動フィンガープリントで交差する。バージョンが違えばプロトコル詳細、エラーレスポンス、特性サポート、デフォルトページ、時間挙動に差異がある。バージョンを区別できるプローブを数個送る(特定の特性は X 版にしかない、特定のエラーは Y 版しかそう返さない)、挙動で実際のバージョン区間を組み上げる。挙動は騙せない、banner は騙せる。
**Q3**: banner バージョンには穴があるが、挙動はパッチ済みのようだ。どうするか。
**A3**: 優先して「無損検証」をしてから本当に打つか決める。多くの脆弱性には非破壊の存在性検知(観測可能だが無害な差異をトリガーする)がある。それで脆弱性が本当に存在するかを先に確認する。直接破壊的 exp を送らない。無損検知で修正済みと示されたら、サービスを落とし、自分を露呈し得る exp 試行を無駄にしない。
**Q4**: バージョンが偽造/脆弱性が修正済み(誤導された)と確認した。どこへ方向転換するか。
**A4**: 直交方向転換、他のフィンガープリント面と他のコンポーネントへ。一つのサービスのバージョンが偽装されても、マシン全体に穴がないとは限らない。転じて見る:そのサービスの設定類問題(弱いパスワード、デフォルト認証情報、危険機能)、同一ホストの他のサービス、依存コンポーネント(ミドルウェア、ライブラリ)のバージョン。同時にこの観測を逆利用する。相手がわざわざバージョンを偽装するのは、このマシンが重点防御か罠かもしれない。それへの信頼度を調整する。
**Q5**: 判定基準:いつ banner を信じられるか。
**A5**: banner バージョンと「挙動フィンガープリント」と「実際の脆弱性の無損検証」の三者が一致した時だけ、それに基づいて exp を上げる。どれか一つでも合わなければ、挙動と実測を基準とする。プローブを数個多く使って確認する方が、偽バージョンに実 exp を撃つよりまし。

### スキャナが高危険の脆弱性を報告した。本当か誤検知か
**Q1**: 脆弱性スキャンツールが「深刻」な脆弱性を一条報告した。直接レポートに書く/直接利用すべきか。
**A1**: 自動化スキャナの高危険報告には可観の割合で誤検知がある。特にバージョンマッチまたは受動特徴に基づくもの。先に報告根拠を分ける:「実際に payload を送って証拠を取った」(PoC 型、比較的信頼できる)か「バージョン番号/フィンガープリントを見て推測」(推測型、高誤検知)。推測型は手作業再現して初めて数える。
**Q2**: 誤検知かどうかをどう素早く判断するか。
**A2**: 手作業で再送し、「争いの余地のない証拠」を要求する。真の脆弱性は、偶然ではあり得ない観測可能な結果を生むはず:私が指定した計算を実行した、私が指定したランダム文字列を帯域外した、読むべきでない確定内容を読んだ。私が「レスポンスに特定のキーワードを含む」という弱い証拠しか見られないなら、誤検知か低危険の誇大の可能性が高い。証拠が「確定的で唯一」であるほど誤検知でない。
**Q3**: 手作業で再現できない。誤検知か私の姿勢が合わないのか。
**A3**: 「スキャナ誤検知」と「特定前置条件が必要」を区別する。真の脆弱性で、認証状態、特定設定、特定入力エンコーディングが必要なものもある。スキャナと私の手作業がどちらも前置不足で失敗するかもしれない。その脆弱性のトリガー前提を照合して一つずつ満たしてから判定する。前提が全て満たされても再現できないなら、誤検知に傾く。
**Q4**: 誤検知(この道は空)と確認した。どこへ方向転換するか。
**A4**: 直交方向転換、「スキャナが漏らしやすく人が見つけやすい」類へ。スキャナは既知 CVE に強く、ロジック脆弱性、権限外アクセス、業務チェーン濫用、組み合わせ利用に弱い。精力を「スキャナの与えたリストの検証」から「手作業の業務ロジック監査」へ転じる。同時にツールの信頼度を較正する。このスキャナが既にいくつか誤検知を出したなら、その他の報告も割引すべき。そのリストに引っ張られない。
**Q5**: 判定基準:スキャン結果にどう信頼級を付けるか。
**A5**: PoC 型 + 唯一性証拠 = 信頼して直接使う;推測型 = 一律手作業再現してから採信;誤検知を出したことのあるスキャン源 = 全面降格して手作業再確認。手作業確認を経ていないスキャン高危険項を利用やレポートに入れさせない。

### RCE で打ち込んだが、これはコンテナ/サンドボックスか
**Q1**: コマンド実行を得たが、環境が変に見える。これは実ホストか、コンテナ/サンドボックス/制限環境か。
**A1**: 先に環境定性をしてから路線を計画する。さもなければ戦術を間違える。コンテナの素早い判定:/.dockerenv を見る、cgroup のコンテナ識別、プロセス 1 が業務プロセスか(コンテナの PID 1 はしばしばアプリであり init でない)、mount の overlay、極めて少ないプロセス数、制限された /proc。サンドボックスの判定:コマンドが大量に制限されているか、ネットワークが極度に隔離されているか、ファイルシステムが読み取り専用か。
**Q2**: コンテナと確認した。これは何を変えるか。
**A2**: 目標と期待を変える。コンテナ内の root ≠ ホストの root で、横展開のロジックも異なる。伝統的なホスト発想でローカル権限昇格を探さず、評価する:コンテナが特権モードか、ホストの敏感ディレクトリ/docker.sock をマウントしたか、能力が過大か、ホストネットワークにアクセスできるか。コンテナエスケープはカーネル権限昇格と直交する一整套の技術。発想を切り替える。
**Q3**: 厳格なサンドボックスで、大部分のコマンドが遮られる場合は。
**A3**: 先にサンドボックスの境界を測り、硬突しない。体系的にプローブする:どのシステムコール/コマンドが禁止か、ファイルシステムのどこが書き込み可能か、ネットワークがどこへ行けるか。境界情報で縫い目を探す。サンドボックスは通常、業務機能のために特定の出口(ある許可されたネットワーク宛先、ある書き込み可能ディレクトリ、あるホワイトリストバイナリ)を残している。業務が必要とする通路に沿って歩く。禁止された壁に突かない。
**Q4**: 脱出不能なコンテナ/サンドボックスに閉じ込められた(遮断された)と確認した。どこへ方向転換するか。
**A4**: 直交方向転換、「制限環境内で取れる価値」と「縦でなく横」へ。ホストに逃げられなくても、コンテナ内には:環境変数のキー、マウントされた設定、到達可能な内部ネットワークサービス、サービスアカウントの token(特にオーケストレーション環境)があるかもしれない。これらの認証情報で他のコンテナ/サービスへ横展開する方が、エスケープに執着するより速く目標に届くかもしれない。逃げられなければ迂回する。
**Q5**: 判定基準:自分がどんな環境にいるかをどう確認するか。
**A5**: 複数の独立信号で交差する(PID 1、cgroup、mount、プロセス数、/proc の完全性)。単一の標識に頼らない。環境定性の誤りは後続の全ての意思決定の誤りを招く。この一歩はプローブを数個多く使って確認する価値がある。それから権限昇格かエスケープか横展開かを決める。

### 認証情報スプレーが全て成功:天から餡餅か全通ハニーポットか
**Q1**: 一群のアカウントでパスワードスプレーをすると、ほぼ各アカウントが「認証成功」。これは運が爆発したのか、詐欺か。
**A1**: 大面積成功 = 強い欺瞞信号。実環境で一噴き全的中はあり得ない。極めて可能性が高いのは:ハニーポット/欺瞞認証サービスがどんな認証情報にも成功を返す、または「全通」の偽認証エンドポイント。これらの「成功」で横展開せず、先に認証エンドポイント自体を疑う。一組の絶対に誤った認証情報(ランダムな乱雑アカウントパスワード)で認証し、それも「成功」するなら、偽エンドポイントが実锤。
**Q2**: エンドポイントが任意の認証情報に成功を返すと確認した。これらのアカウントはまだ救えるか。
**A2**: 「認証レスポンス」と「実際の認可」を分離する。偽成功エンドポイントは成功状態を返しただけで、これらの認証情報が他所で使えることを意味しない。そのうちの「成功」アカウントを一つ、実際の、独立したサービス(別の認証システム、実業務 API)で検証する。実システムで足場確保できて初めて真の認証情報。既知で確実に存在しないアカウントを対照に使い、真偽成功の境界をはっきりさせる。
**Q3**: 欺瞞認証の罠なら、私は既に一ラウンド噴いた。露呈リスクがあるか。
**A3**: 記録済みと仮定し影響を評価する。欺瞞認証サービスの目的は攻撃者を記録すること。即そのエンドポイントへのさらなる操作を止め、私がどのアカウント辞書、どのソース IP、どのツール特徴を露呈したかを評価する。以降、実エンドポイントにはより秘匿な方式(低頻度、出口替え、露呈したばかりの辞書を避ける)に替える。
**Q4**: これがおびき出しエンドポイント(おびき出された)と確認した。どこへ方向転換するか。
**A4**: 直交方向転換、実際の認証入口へ。欺瞞エンドポイントは往々にして故意に目立つ位置に露出される。転じて実際の業務認証入口を探す(もっと秘匿で、正常な失敗フィードバックがあるかもしれない)。実エンドポイントの判定標識はまさに「それが誤った認証情報を正しく拒否し、正しくロックし、実際のエラーコード差異がある」こと。あなたを拒否するものこそ本物。
**Q5**: 判定基準:偽認証成功をどう識別するか。
**A5**: 中核テスト。絶対に正しくあり得ない認証情報を一つ食わせる。真エンドポイントは必ず拒否し、偽エンドポイントは通す。「誤った入力にも成功を返す」サービスは一律欺瞞と判定し、その全「成功」結果を破棄し、横展開に入れない。

### 内部ネットワーク一スキャンで膨大なホストを発見。真のセグメントか欺瞞ネットワークか
**Q1**: 内部ネットワークでスキャンすると、数百から千台のホストが密集。これは大きなセグメントか、欺瞞/canary ネットワークが配置されたのか。
**A1**: ホスト密度と真実性を交差検証する。欺瞞ネットワーク(大量の偽ホスト/deception など)は一つのセグメントを異常に「満たす」。実際の内部ネットワークは通常、空洞があり、規則的な割り当てがあり、ホスト挙動がそれぞれ異なる。先にこれらのホストの「実在感」を見る:実在の開放サービスがあるか、banner が酷似か、ARP/MAC が疑わしいほど連続か、同一仮想化由来か。大量の挙動が高度に一致する「ホスト」は欺瞞の信号。
**Q2**: 真ホストと deception の偽ホストをどう区別するか。
**A2**: 対話の深さを見る。偽ホストは往々にしてスキャン層でしか「存在」せず、深入り対話すると露呈する:サービスが実際のプロトコルを受け付けない、ファイル/認証情報がおとり、互いに実在の業務通信がない。数台を「深入り」する。真ホストには実在の業務トラフィックと相互関係があり、偽ホストは孤島。同時に警戒:大量の偽ホストへ能動接続すること自体が deception 告警をトリガーする。
**Q3**: 逐台検証できない。どう低リスクで前進するか。
**A3**: 受動情報から優先して真対象を固定する。広撒きで全ホストへ接続しない(canary をトリガーする)。受動トラフィック、DNS レコード、ARP 表、既に取ったホストの接続履歴から、どのホストが人が実際に使っているか(ログインあり、業務接続あり)を逆算する。実価値のホストは実通信に現れる。偽ホストは現れない。スキャン結果でなく、真のトラフィックに従って歩く。
**Q4**: これが欺瞞ネットワーク(おびき出された)と確認した。どこへ方向転換するか。
**A4**: 直交方向転換、「ノイズ削減 + 実業務への追従」へ。全セグメントスキャンという高ノイズ動作を放棄する(それはまさに deception に餌をやる)。極低ノイズの定向偵察へ:信頼できる出所(実業務トラフィック、実認証情報でログインできるマシン)から確認されたアセットだけに触れる。戦略的に、私がどうこのセグメントへ入ったかを再検討する。deception セグメントは往々にして防御者が故意に攻撃者を導く隔離区。
**Q5**: 判定基準:一台のホストを「実在で信頼できる」とどうマークするか。
**A5**: 「実使用の証拠」が必要:実ユーザーのログイン痕跡、他のアセットとの実業務通信、自己整合するサービスとデータ。「スキャンで生きていると分かった」だけでは決して信頼に足らない。疑似欺瞞ネットワーク内で、信頼は業務の真実性による裏書が必要。

### 私の見るレスポンスは CDN キャッシュの他人のものか
**Q1**: ある API を測ると、レスポンス内容が少し噛み合わない。他人のデータのようだ、または私の payload が効いていない。私の見るのは CDN/キャッシュの旧レスポンスか。
**A1**: 中間キャッシュがあると、観測は深刻に歪む。先にチェーンにキャッシュ層があるか確認する(レスポンスヘッダーの Age/X-Cache/CF-Cache-Status、CDN 特徴)。キャッシュ命中があるなら、私の見るのはキャッシュ内の、他人が数分前に見たレスポンスかもしれず、今回のリクエストと全く無関係。キャッシュレスポンスに基づくどの脆弱性判断も信頼できない。
**Q2**: キャッシュを迂回して私のリクエストの実レスポンスを見るには。
**A2**: 強制キャッシュ穿透。ランダム query パラメータ/cache-buster を足す、キャッシュを迂回するヘッダーを付ける、キャッシュされないメソッドを使う(キャッシュは通常 GET しかキャッシュしない)。各リクエストをキャッシュの目から見て「新しいリクエスト」にし、実際のバックエンドへ打つ。cache-buster 追加前後のレスポンス変化を対比し、変化すれば以前は確かにキャッシュを食っていた。
**Q3**: 逆に、キャッシュ投毒/キャッシュ欺瞞が存在すると疑うなら、この歪みをどう利用するか。
**A3**: 「キャッシュがレスポンスを串刺しにする」を、干渉から攻撃面に変える。キャッシュキーの処理が不当な時、私の payload がキャッシュされて他のユーザーへ返される(キャッシュ投毒)、または本来プライベートな内容がキャッシュされて私が読める(キャッシュ欺瞞)。キャッシュがデータを串刺しにする異常を観測したら、それこそこの類の脆弱性の手がかり。「レスポンスがなぜ串刺しになるか」を深掘りする。
**Q4**: キャッシュ層がバックエンド挙動の安定観測を根本的に不可能にする(遮断された)。どこへ方向転換するか。
**A4**: 直交方向転換、キャッシュを迂回する経路へ。CDN を通らないオリジンサーバー直連アドレス(オリジンサーバー IP、内部ドメイン、非キャッシュの API サブドメイン)を探す。オリジンサーバー直連は清浄で安定した観測を得られ、同時に CDN 層の WAF を迂回できるかもしれない。オリジンサーバーを取れないなら、テストをキャッシュがカバーしない動的/認証 API に集中する。
**Q5**: 判定基準:レスポンスの信頼度をどう判断するか。
**A5**: どのレスポンスもまずそれがキャッシュ命中か(Age/X-Cache)を見る。キャッシュ命中のレスポンスは「私の今回のリクエストが何をしたか」への証明力がない。バックエンドへ打った(キャッシュ MISS または穿透済み)と確認したレスポンスだけが、脆弱性挙動の判断に使える。

### payload がページにエコーされた。実行されたのかただの反射か
**Q1**: 私の payload がそのままレスポンスページに現れた。それが実行された(SSTI/コード実行)のか、ただ文字列として反射されたのか。
**A1**: 「現れる」≠「実行」。そのまま現れるのは最尤で反射(潜在 XSS/情報エコー)であり、サーバー側実行ではない。判定基準は:payload に「演算」をさせ、固定文字列をエコーさせない。評価される式(特定のテンプレート/式構文の加算など)を送り、レスポンスが式の原文でなく演算結果を返せば、サーバー側実行。式をそのまま返せば、ただの反射。
**Q2**: 演算プローブも原文を返す。実行を徹底的に排除できるか。
**A2**: 一つの構文で全てのエンジンを否定しない。原文を返すのは「このエンジンのこの構文が評価されなかった」ことだけを意味する。対象は別のテンプレート/式エンジンで、構文が違うかもしれない。異なるエンジンをカバーするプローブ一組で個別に試す。同時に実行位置を区別する。この反射点は実行しないが、同じデータが別の機能(メールテンプレート、エクスポート、二次レンダリング)へ流れて初めて評価されるかもしれない。
**Q3**: 純反射で実行しないと確認した。この観測は無価値か。
**A3**: 反射自体が別の類の攻撃面。方向を替えれば役立つ。そのまま反射 = クライアント注入(XSS)、またはレスポンス分割、またはキャッシュ投毒の潜在点。「RCE でない」からといって捨てない。この反射点を評価する:反射位置(HTML/JS/属性/JSON)、エンコーディングの有無、スクリプト実行をトリガーできるか。観測された現象は、脆弱性の類を替えればまさに命中するかもしれない。
**Q4**: 反射もエンコード/エスケープされて徹底的に無害(遮断された)なら、どこへ方向転換するか。
**A4**: 直交方向転換、他のデータ集約点へ。一つの入力点が安全処理されても、同じデータが他所でも安全とは限らない。このパラメータのデータフローを追跡する:それが保存されて他所で表示されるか(ストレージ型)、ログ/管理画面/PDF/メールに入るか(二次トリガー)、SQL/コマンド/テンプレートなど他の sink へ流れるか。sink を替え集約点を替える。この一つの反射点に執着しない。
**Q5**: 判定基準:反射と実行を一目でどう見分けるか。
**A5**: サーバー側実行を測るのに「マーク文字列」でなく「評価可能プローブ」を永遠に使う:実行された時だけ変化し、反射されたらそのままの入力を送る。結果が変われば=実行、変わらなければ=反射。この判定基準は、XSS を RCE と見なす古典的誤判定を一瞬で避けられる。

### ツール出力が異常:対象がおかしいのか自分の環境が壊れたのか
**Q1**: 私のツールが一山の奇妙な結果を出し、期待と全く合わない。対象が仕掛けているのか、私のローカル環境/プロキシが問題なのか。
**A1**: 排錯の第一原則。先に自分のツールチェーンが良いことを証明する。同じツールで既知の、挙動の確定した対照対象(自分で建てた的や公共の安定サービス)を打つ。対照対象の結果も異常なら、問題は 100% 私側(プロキシ設定、DNS、証明書、ツールバージョン、中間者)で、対象と無関係。自分の壊れたツールを対象の挙動として分析しない。
**Q2**: 対照対象は正常で、この対象だけ異常。何を意味するか。
**A2**: それで初めて対象を疑う価値がある。しかしさらに隔離する:対象アプリケーションがおかしいのか、対象と私の間のチェーンがおかしいのか(WAF/プロキシ/CDN の書き換え)。ツールを迂回して直接手作業で生リクエストを送る(裸 socket/curl)し、ツールの挙動と対比する。手作業が正常でツールが異常なら、ツールのこの対象への解析/対話方式に問題がある。手作業も異常なら、対象かチェーン。
**Q3**: 私のプロキシ/中間層がトラフィックを書き換えていると疑う。どう確認するか。
**A3**: 「プロキシ経由」と「プロキシ非経由」の生バイトを対比する。パケットキャプチャで実際に送受信した生データを見る。私が送ったと思うものと合うか。一山のプロキシ/ツールカプセル化を経ると、リクエストは往々にして密かに書き換えられる(自動でヘッダー追加、エンコーディング、並べ替え)。私が思う payload が実際に送られたものでないかもしれない。観測の歪みは往々にして私自身のツールスタック由来。
**Q4**: ローカルツールチェーンの問題(自分が自分を騙している)と確認した。どこへ方向転換するか。
**A4**: 直交方向転換、より低層で、より制御可能なツールへ。高度にカプセル化された自動化ツールを捨て、各バイトを見て制御できる層へ下げる(手作業で生リクエスト構築)。最も素朴な方式で一度再現し、信頼できるベースラインを建て、徐々に自動化を戻す。中核の方向転換は「私と対象の間の抽象層を減らす」こと。抽象層が少ないほど観測は信頼できる。
**Q5**: 判定基準:異常を誰に帰属させるか。
**A5**: 厳格に階層排除する。対照対象(私側かどうかの特定)→ 手作業裸リクエスト(ツールかどうかの特定)→ 生バイト取得(チェーン書き換えかどうかの特定)。この三歩を歩き終えない限り、異常を対象に押し付けない。多くの場合、私を騙すのは対象でなく、私自身の環境。

### 対象の挙動が突然変わった:ブロックされたのか WAF が学習したのか
**Q1**: 前はうまく打てていたのに、突然全リクエストの挙動が変わった(遮断、リダイレクト、タイムアウト)。私がブロックされたのか、WAF が私の特徴を学習したのか。
**A1**: 先に変化の種別を定性する。観察は「全量遮断」か「攻撃リクエストだけ遮断」か:純合法リクエストを送り、それも通らないなら IP/セッション級ブロック。合法リクエストが正常で payload リクエストだけ遮断なら、特徴級遮断(WAF がルール追加または私のパターンを学習)。両者の方向転換は全く異なる。
**Q2**: IP/セッション級ブロックなら、境界をどう確認するか。
**A2**: 清浄な出口 + 全新セッションに替えて即リトライする。新しい身分が完全に正常なら、旧身分への定向ブロックが確定。同時にブロックトリガーの時点を記録し、その前後に私が何の高ノイズ動作(高頻度スキャン、特徴 payload、異常 UA)をしたかを遡り、トリガー条件を特定する。IP を替えたらまた秒封されないように。
**Q3**: 特徴級遮断(WAF 学習)なら、どう対応するか。
**A3**: 私の現在の payload パターンがブラックリスト入りしたと仮定する。同じ一組の変形を使わない。それらは学習された特徴を共有している。徹底的に別の利用パラダイム(別のエンコーディング族、別の注入位置、別の payload 構造)に替え、特徴分布を以前と完全に違わせる。WAF が学ぶのは「分布」。分布から飛び出して初めて効く。
**Q4**: IP 替え、特徴替えでもまだ遮断される(遮断された)。どこへ方向転換するか。
**A4**: 直交方向転換、時間次元と攻撃面次元へ。第一に、退避。極低頻度さらには一時停止し、自己適応防御に「クールダウン」の機会を与え、時を選んで再び来る。第二に、アセット替え。防御者がこのアセットでちょうど締めた。まだ「驚かされていない」他のアセットを打つ。第三に、プロトコル/入口替え。睨まれたのは往々にして特定の一つの Web パス。サービス、ポート、API バージョンを替えると防御のブラインド領域かもしれない。
**Q5**: 判定基準:ブロック vs 学習 vs 対象自身の変化をどう区別するか。
**A5**: 三プローブ。合法リクエスト(セッション級封かどうか)、清浄な新身分(IP 級封かどうか)、全新 payload パラダイム(特徴級学習かどうか)。三者の通/不通の組み合わせで、誰が変わっているか、どこへ方向転換するかを精密に特定できる。挙動変化を見たら「とりあえず IP を替える」と一括りにしない。

### webshell が接続できた。しかしコマンドは EDR に偽許可されておびき出されているか
**Q1**: 私の webshell は接続でき実行もできる。しかし EDR が「偽許可」しているのでは、つまり私に成功したと思わせて実は記録しおびき出しているのではと疑う。どう判断するか。
**A1**: 偽許可の特徴は「実行できるが異常に静か、または異常に順調」。通常 EDR に遮られるはずの敏感な動作(典型的な認証情報アクセス、疑わしいプロセス注入の良性等価物)を一つ測る。これさえ「順調に成功」して抵抗が全くないなら、逆に疑わしい。実際の EDR 環境が高危険動作に無反応であるはずがない。順調すぎるのは、演じている可能性。
**Q2**: EDR の実際の存在とポリシーをさらにどう探るか。
**A2**: 硬突でなく低リスクで防御を列挙する。まず読み取り専用偵察:EDR/AV プロセスがあるか、監視エージェントがあるか、異常なフックがあるか。無害な動作で境界を探る。どの操作が静黙に遮断されるか(実行しても効果なし)、どれが遅延するか(EDR 分析中)。偽許可は往々にして「コマンドは成功を返すが実際の副作用が起きない」と現れる。これは実実行と違う。副作用を検証する。
**Q3**: EDR があり、監視されているかもしれないと確認した。どう続けるか。
**A3**: 最小露呈、否認可能モードに切り替える。各動作が録画されていると仮定する。標識的なツール/TTP の足場確保を避け、システム標準で、正常な運用に見える手段(living-off-the-land)を優先する。「挙動検知をトリガーする動作」を、それぞれ無害なステップの連鎖に分解する。遅くとも、帰属可能な特徴を残さない。
**Q4**: このマシンがおびき出しホスト(honeypot + EDR 誘導)と確認した。どこへ方向転換するか。
**A4**: 直交方向転換。撤退して餌を遡る。おびき出しなら、操作を続けると防御側にデータを餌として与えるだけ。このマシンへ入った経路に戻り、私を引き込んだ餌(取りすぎた shell、開放的すぎる点)を識別する。実際の目標は通常、餌を迂回し、より秘匿な道を行く必要がある。リソースを「実業務があり、防御が正常(拒否し、告警する)」のアセットへ転じる。正常に防御するものこそ本物。
**Q5**: 判定基準:偽許可をどう識別するか。
**A5**: 中核判定基準は「実行成功の声明」と「実際の副作用」の一致。実実行には必ず実副作用がある(ファイルが本当に変わった、プロセスが本当に起きた、データが本当に動いた)。「成功を報告するが副作用が証拠なし」のものは全て、偽許可/おびき出しを疑う。それに基づいて前進しない。

### ポートノッキング後にサービスが現れる。真の開放かロードバランシングのラウンドロビンか
**Q1**: スキャンを繰り返すと、特定のポートが時に開き時に閉じ、または数回叩いてから「開く」。これはポートノッキング/オンデマンド開放か、ロードバランシングのバックエンドが開いているものと開いていないものがあるのか。
**A1**: 時に開き時に閉じる観測で急いで結論を下さない。先に「同一バックエンドの状態変化」か「複数のバックエンドが異なるインスタンスにラウンドロビンされた」かを分ける。各回のレスポンスのバックエンドフィンガープリント(banner 詳細、cookie、タイムスタンプ、証明書、エラーページ)を見る。開/閉が異なるバックエンドフィンガープリントに対応するなら、ロードバランシングが異なるインスタンスに振っている(あるのはそのサービスが走り、あるのは走っていない)のであり、ノッキングではない。
**Q2**: ロードバランシングの複数バックエンドと確認した。これは何を意味するか。
**A2**: 私が毎回違うマシンを打っている可能性があり、脆弱性状態とデータが不一致。これが深刻に誤導する。A バックエンドに注入したデータは、次のリクエストで B バックエンドに落ちて見つからないかもしれない。セッションを同一バックエンドに固定する方法(粘着 cookie、特定のバックエンド IP へ直連)を考えるか、「バックエンド不一致」を分析に組み込む(あるバックエンドに穴があり、あるのはパッチ不足)。
**Q3**: 確かにノッキング機構(特定シーケンス後にポートが開く)なら、どう利用するか。
**A3**: トリガー条件を再現する。「開く」前に私がちょうど何のシーケンス/ソース/時間をしたかを記録し、安定再現を試みる。ノッキングは通常、特定のポートシーケンスやソース特徴に依存する。安定トリガーできれば、それ自体が利用可能な秘匿チャネル。再現できなければ、ロードバランシング仮説に戻る。
**Q4**: バックエンド状態が乱れ、安定観測できない(遮断された)。どこへ方向転換するか。
**A4**: 直交方向転換、「単一バックエンドを固定」または「安定入口に替える」へ。特定の具体バックエンドの直連アドレスを何とか手に入れ、ロードバランシングを迂回し、一致して再現可能な観測を得る。取れないなら、明らかに同一インスタンスに当たる機能(状態あり、粘着セッションが必要な API)を打つか、このロードバランシング層を通らない別のアセットに替える。観測が不安定な時は、先に安定性を解決してから利用を論じる。
**Q5**: 判定基準:「時に開き時に閉じる」をどう解釈するか。
**A5**: バックエンドフィンガープリントの一致性で判断する:フィンガープリントが開閉に伴い変わる=複数バックエンドのラウンドロビン;フィンガープリントが変わらないが状態が変わる=真のノッキングかオンデマンドサービス。永遠に先に「私が結局誰と話しているか」を固定してから、その挙動を解釈する。観測が再現できない脆弱性の九割は、毎回打っているのが同じものでないことが原因。

### 私が取ったのは本番でなくテスト/ミラー環境ではないか
**Q1**: 対象に打ち込んだが、データがテストデータのようで、設定がプレリリース環境のようだ。非本番環境に打ち間違えたのではないか。
**A1**: 先に環境レベルを定性する。さもなければ努力が無駄になり得る。環境識別を探す:ドメイン/ホスト名の test/staging/dev、設定内の環境変数、データの真実性(テスト環境は往々にしてマスキング/作られた偽データ)、接続する下流がテストサービスか。テスト環境に本番向けのリソースを投入せず、テスト環境の「成果」を本番攻略と誤認しない。
**Q2**: データが実本番データか作られたものかをどう判断するか。
**A2**: データの真実性のテクスチャを見る。本番データは実分布。実名/メール形式が多様、タイムスタンプが長周期に連続、実業務の雑然さがある。テストデータは往々にして整然(test001、aaa@test.com)、量が少なく、時間が集中、または明らかにジェネレータ製。データの「汚さと真実さ」が本番判断の強い信号。
**Q3**: テスト環境と確認した。それにまだ価値はあるか。
**A3**: ある。直接捨てない。テスト環境は本番への踏み台とインテリジェンス源:それは往々にして本番とコードを共有(ホワイトボックスで脆弱性を監査できる)、認証情報を共有(テストパスワードが本番でも使えるかもしれない)、内部アーキテクチャと API ドキュメントを露出、防御が通常より弱い(ここで発想を先に通してから本番を打つ)。それを「本番の低防御コピー」としてインテリジェンスを絞り取る。
**Q4**: テスト環境が完全隔離で本番へ通じない(遮断された)なら、どこへ方向転換するか。
**A4**: 直交方向転換、「テスト環境の知識で本番を打つ」へ。ネットワークが隔離でも、私がここで学んだ脆弱性、コードロジック、認証情報規則、API 構造は、高確率で本番に適用できる。本番入口へ方向転換し、ここの戦果(同型の脆弱性、同型の弱点)を再利用する。同時に本番環境の実入口を探す。それは通常別のドメイン/セグメントで、防御がより強いがアーキテクチャが似ている。
**Q5**: 判定基準:自分が本番にいることをどう確認するか。
**A5**: 多信号交差:実の汚いデータ + 本番ドメイン/証明書 + 実ユーザーの活発さ + 実下流への接続。どれか一つが「テスト/プレリリース」を示せば、現在の成果を「非本番戦果」とマークし、本番への経路を再評価する。「打ち込んだ」興奮で「打ち込んだのが本番でない」という致命的な前提エラーを覆い隠さない。

### エラー情報の手がかりは、真の漏えいかハニーポットが仕込んだおとりか
**Q1**: 対象の返すエラー情報に誘惑的な内容(パス、バージョン、認証情報のようなものまで)が混ざる。これは真の漏えいか、故意に仕込まれたおとりか。
**A1**: 「親切」なエラーほど警戒する。本番システムは通常、詳細エラーを閉じる。攻撃者に異常に友好的で、ちょうど重要情報を漏らすエラーは、ハニーポットのおとりかもしれない。判定基準は自己整合性と代償:真の漏えいは往々にして無意図で、散発的で、システムの他の挙動と一致する。おとりは往々にして過度に完全で、過度に対口で、かつ「利用しやすすぎる」方向を指す。
**Q2**: エラー内の手がかりの真偽をどう検証するか。
**A2**: 独立交差検証する。単点で採信しない。エラーがパスは X と言えば、別の手段(ディレクトリプローブ、他の API の挙動)で X が実在し一致するかを裏付ける。エラーがバージョンを与えたら、挙動フィンガープリントで照合する。おとり情報は通常交差検証に耐えない。他の観測チャネルで合わないか、指すものに一触れると告警をトリガーする。
**Q3**: エラーの手がかりが「順調すぎる」利用経路を指す場合、どうするか。
**A3**: 「おとりコスト」の心構えで評価する。エラーに沿って進むと、次が高価値ゼロ抵抗の収穫なら、一度止まる:防御側はなぜエラーで私にこれを能動的に餌として与えるのか。高誘惑低抵抗の経路には、先に否認可能な軽探をし、異常(告警式レスポンス、アカウント瞬変)をトリガーするか観察してから深入りを決める。
**Q4**: エラーがハニーポットのおとり(誘導された)と確認した。どこへ方向転換するか。
**A4**: 直交方向転換、「実の無意図の漏えい」へ。真のインテリジェンスは、システムがうっかり露出した場所にある:不一致のレスポンス差異、タイミング傍路、キャッシュ/ログの残存、正常機能の境界挙動。これらは誰も私のために用意していないので、むしろ信頼できる。おとりの指す方向を放棄し、「防御者が私に見せるつもりはないが、確かに漏れている」情報を掘る。
**Q5**: 判定基準:エラー情報の信頼度をどう定めるか。
**A5**: 無意図で、散発的で、交差裏付け可能 = 比較的信頼できる;完全で、対口で、ゼロ抵抗の大収穫を指す = 疑似おとり。エラーの手がかりは一律、先に交差検証してから採信する。特に「好すぎる」時は、デフォルトでそれが鉤。

### システム時間/タイムスタンプが合わない。私を誤導しないか
**Q1**: 対象で見るシステム時間、ログタイムスタンプが変(未来の時間、タイムゾーン乱れ、私の期待と大きく違う)。これは私の判断を誤導しないか。
**A1**: 時間は多くの判断の暗黙の基準。先に較正する。対象の時間が私と一致するとデフォルトで思わない。対象の実際のタイムゾーンと現在時刻を素早く照合する(複数の出所:システム時計、ログ、ファイル mtime、プロトコルの時間フィールド)。それらが互いに矛盾するなら、時間が人為的に変えられたか環境異常。時間ベースの推論(どの認証情報が新しいか、どのセッションが有効か、イベントの前後)は全て疑問符を付ける。
**Q2**: 時間不一致は具体的にどの意思決定を陥れるか。
**A2**: 時間に敏感な攻撃を陥れる:Kerberos 系プロトコルは時計偏差に敏感(偏差が大きいと直接認証失敗、認証情報無効と誤判定しない)、証明書/チケットの有効期限判断、ログタイミング関連(イベント因果の判断、防御者が応答済みかの判断)。「認証が不可解に失敗」したら、先に時計偏差かどうかを切り分ける。認証情報が間違いと先に疑わない。
**Q3**: 時間が故意に改ざんされて誤導に使われたと疑う場合、どうするか。
**A3**: 対象の自己申告時間に依存しない錨点を使う。私自身の信頼できる時間を基準に、私の各動作の実時刻を記録する。外部の信頼できる時間源で交差する。対象イベントを分析する時、対象の自己申告タイムスタンプを完全に信じるのでなく、相対順序と私側のタイムラインを優先する。それは隠蔽や誤導のために変えられているかもしれない。
**Q4**: 時間の乱れで時間敏感攻撃が全て失敗する(遮断された)なら、どこへ方向転換するか。
**A4**: 直交方向転換、時計同期または非時間敏感な手段へ。Kerberos 類の偏差問題なら、私のリクエスト時間を対象の時計に合わせる(認証情報ポリシーを変えるのでなく)。合わせられないなら、時計を食わない攻撃面(チケット時効に依存しない経路)へ。中核の方向転換:「認証情報/脆弱性の失敗に見える」問題を、まず「時間基準」という隠れた変数に帰因して切り分ける。
**Q5**: 判定基準:いつ時間が私を騙していると疑うべきか。
**A5**: 「認証情報/チケットが不可解に失効」「ログタイミングが筋が通らない」「証明書状態が矛盾」という現象が出た時、時計偏差を第一容疑にし、先に時間を較正してから再判定する。時間は最も見落とされやすく、最も静かに判断を誤導できる観測次元。

### dump したデータは真のライブラリかマスキング/偽データか
**Q1**: データベースからデータをエクスポートしたが、マスキングされたか作られたもののように見える。これは実データか、偽に差し替えられたのか。
**A1**: データを得たら先に真偽を検証してから価値を論じる。データの真実性のテクスチャを見る:実ライブラリは実分布(電話番号/メール/身分情報の形式が実在し多様、金額に長尾、時間スパンが大きい)。マスキングデータは往々にして規則的な置換(統一マスク、形式化された偽値)。偽データは往々にしてジェネレータの痕跡(連続 ID、酷似パターン)。偽データの一群を戦果とせず、偽認証情報に基づいて横展開しない。
**Q2**: これが本番主ライブラリかをどう確認するか。
**A2**: データの「活性」を交差検証する。数レコードを選び実業務側で裏付ける。この「ユーザー」がフロントエンド機能で実在するか、この注文が照会できるか。真ライブラリのデータは業務内で生きている。偽/マスキングデータは業務内で往々にして合わない。同時にライブラリのメタ情報(表名、コメント、他のライブラリ、接続元)が本番らしいかを見る。
**Q3**: マスキング/テストデータと確認した。まだ使えるか。
**A3**: 構造と schema にはまだ価値がある。データ自体の価値は低い。データが偽でも、表構造、フィールド命名、関連関係は業務ロジックと他の打てる場所を明らかにする。しかもこのライブラリへ接続できることは、認証情報/注入が本当であることを示す。この通路で実際のライブラリ/インスタンス(同一インスタンスの他 schema、より「本番らしい」データベース接続)を探す。
**Q4**: 偽データにしかアクセスできず、真のライブラリに触れない(遮断された)なら、どこへ方向転換するか。
**A4**: 直交方向転換、実データの他の担体へ。実データは:主ライブラリ(私が今接続しているのは読み取り専用コピー/テストライブラリ)、バックアップ、キャッシュ、ログ、他のマイクロサービスのストレージにあるかもしれない。現在の足場で、実データ源を指す接続文字列/設定/認証情報を探す。データ層が隔離されたら、アプリケーション層へ。業務 API を通じて間接的に実データを読む。この偽ライブラリに執着しない。
**Q5**: 判定基準:データの真実性をどう判断するか。
**A5**: 分布が実在 + 業務で裏付け可能 + メタ情報が本番らしい = 真;規則的なマスク/ジェネレータ痕跡/業務で合わない = 偽またはマスキング。永遠に先にデータに真偽級を付けてから、それが戦果か、インテリジェンスか、それとも本物を探し続けるべきかを決める。

### 権限昇格後は完全な shell か制限 shell(rbash 等)か
**Q1**: shell を取ったが、多くのコマンドが使えず、cd も動かず、変数も変えられない。権限不足か、制限 shell が私を枠にはめているのか。
**A1**: 先に制限 shell(rbash の類)かどうかを定性する。「権限が低い」と誤判定しない。特徴:cd できない、/ 付きのパスを使えない、PATH/SHELL を変えられない、リダイレクト禁止、限られたホワイトリストコマンドしか使えない。これらなら、shell 環境が制限されているのであり、アカウント権限問題ではない。解法は全く異なる(制限 shell のエスケープであり、権限昇格ではない)。
**Q2**: 制限 shell と確認した。どう脱出するか。
**A2**: 許可されたプログラムの中で「子 shell を起せる」機能を探す。多くのホワイトリスト内の通常プログラム(エディタ、ページャ、言語インタプリタ、find/awk の類)には外部コマンド実行や spawn shell の能力がある。それらで制限環境から脱出する。中核の発想:制限されているのはこの shell であり、システム全体ではない。制限されていないプロセスを借りて脱出する。
**Q3**: 制限 shell を脱出した後、権限がまだ非常に低いと分かった。次は。
**A3**: それで初めて本当の権限昇格段階に入る。二つの問題を混ぜない。先に完全に使える対話環境(安定 PTY)を得てから、通常の権限昇格列挙をする。以前の制限 shell は実権限状況を覆い隠していた。脱出後は環境と権限の定性をやり直す。制限時の誤った観測で推論を続けない。
**Q4**: 制限 shell が脱出できず、コマンドが全て固着した(遮断された)。どこへ方向転換するか。
**A4**: 直交方向転換、「別の進入経路に替える」。この shell を硬脱出しない。同一アカウント/マシンに別のアクセス方式があるかもしれない:別のプロトコルでログインする(別のサービスの与えるのは完全 shell かもしれない)、認証情報で別の入口から入る、またはこの対話 shell を放棄し、非対話のコマンド実行チャネル(計画タスク、サービス、Web 層 RCE)に替える。制限されているのはこの入口の shell。入口を替えればこの制限がないかもしれない。
**Q5**: 判定基準:「制限 shell」と「権限が低い」をどう区別するか。
**A5**: 制限 shell = コマンド/パス/リダイレクトが構造的に禁止(能力が枠にはめられている);権限が低い = コマンドは走るが権限で拒否される(できるが権限がない)。無害な基礎操作を一つ測る(PATH を変える、cd で / へ、絶対パスでコマンド実行)。shell 構文層に拒否されれば制限、システム権限に拒否されれば権限が低い。定性が合って初めて戦術を間違えない。

### デシリアライズ payload がエラーもなくエコーもない:成功か飲み込まれたか
**Q1**: デシリアライズ payload を送った。対象はエラーも出さずエコーもない。利用成功(静黙実行)なのか、安全なデシリアライズに飲み込まれたのか。
**A1**: デシリアライズ利用は天然にエコーがないことが多い。「反応がない」で失敗と判定しない。エコーなし RCE と同じく、副作用/OOB で検証する:対象に一回の観測可能な帯域外(DNS/HTTP コールバック)を発起させるか、私が照会できる副作用を生む payload を構築する。帯域外を受信 = チェーン成功で実行。受信しなければさらに切り分ける。それがエコーすることを期待しない。
**Q2**: OOB が戻ってこない。チェーンが成らないのか外向き通信しないのか。
**A2**: 「gadget チェーンの問題」と「環境問題」を分離する。先にデシリアライズ入口自体が通じるかを確認する:「完全な利用チェーンを必要としないが、観測可能な差異をトリガーできる」プローブ(特定の例外やクラスロード挙動をトリガーする最小 payload)を送り、レスポンス/時間に変化があるかを見る。最も基本的なデシリアライズさえトリガーされないなら、入口/形式問題。トリガーされるがコマンド実行しないなら、gadget チェーンか環境(外向き通信しない)問題。
**Q3**: gadget チェーンと対象環境の不一致を疑う。どうするか。
**A3**: 依存が gadget を決める。デシリアライズの RCE 可否は、対象のクラスパスにどんな利用可能ライブラリがあるかで決まる。一本のチェーンで天下を打たない。先に対象の依存/バージョンを探る(エラー、挙動、既知フレームワーク特徴)、それに基づいて対応する gadget チェーンを選ぶ。適切な gadget がない時、デシリアライズは限定的な効果(DoS、SSRF、ファイル操作)しかできないかもしれない。期待を調整する。
**Q4**: このデシリアライズ点に使える RCE チェーンがない(遮断された)と確認した。どこへ方向転換するか。
**A4**: 直交方向転換、デシリアライズの非 RCE 危害と他の入口へ。RCE チェーンが通らなくても、デシリアライズは往々にして SSRF、任意ファイル読み書き、サービス拒否、内部ネットワークプローブを打てる。これらの迂回リターンを使う(SSRF で内部ネットワークを打つ、ファイル書き込みで webshell を足場確保)。同時に他のデシリアライズ入口(別の API/フィールド/プロトコル)を探す。そのクラスパスとフィルタリングが違うかもしれない。
**Q5**: 判定基準:デシリアライズ利用の成功をどう確認するか。
**A5**: 唯一信頼できる判定基準は観測可能な確定的副作用(指定の帯域外を受信、指定のファイル/挙動を生成)。「エラーがない」は静黙成功かもしれず静黙失敗かもしれず、情報量ゼロ。永遠に盲状態利用に独立した検証チャネルを配る。対象の沈黙で当てない。

### 「ドメインコントローラ」を一台スキャンした。真の DC か偽装か
**Q1**: 内部ネットワークでドメインコントローラらしきマシンを見つけた(対応ポート/サービスが開いている)。直接それを中核対象として猛攻するか。
**A1**: 高価値対象は最も罠に偽装されやすい。先にそれが真のドメインコントローラかを検証し、特徴ポートを見たからと突っ込まない。真の DC には一整套の自己整合するサービスとロール特徴があり、実在のディレクトリデータを担い、大量の実ホストに依存される。偽装の「DC」は往々にして誘人なポートを数個開いただけで、実在のディレクトリデータがなく、実クライアントが依存していない。多次元でロールを裏付ける。ポートだけを見ない。
**Q2**: 草を驚かせずにその実際のロールをどう検証するか。
**A2**: 攻撃的プローブでなく低ノイズの正常照会を使う。正常クライアントがする方式で対話し、返すデータが実ドメインにあるべきもの(実のドメイン情報、実のオブジェクト数と関係)かを見る。真のドメインコントローラの背後は生きた組織構造。ハニーポットの「ドメインコントローラ」のデータは往々にしてまばら、酷似、または明らかな偽造。データの「組織の実在感」を観測する。
**Q3**: 真のドメインコントローラと確認したが、明らかに重点監視されている。どう前進するか。
**A3**: 真の DC は必ず高監視区。最小動作、最高秘匿で前進する。最初から騒がしい攻撃(大規模チケットリクエスト、明らかな既知脆弱性プローブ)を走らせない。先に側面情報(一般メンバーマシンから、ディレクトリの正常な可読部分から)を収集し、DC の直接 API への接触をできるだけ減らす経路を計画する。中核対象には、偵察を厚く、動作を節約。
**Q4**: この「ドメインコントローラ」がハニーポット(おびき出された)と確認した。どこへ方向転換するか。
**A4**: 直交方向転換、実際のドメイン中核へ。偽 DC は往々にして目立つ、見つけやすい位置に置かれ、攻撃を誘う。転じて実メンバーマシンと実ドメイントラフィックを通じて、クライアントが本当に認証し、本当に依存しているあの/それらの DC を特定する。真の中核は実ホストに取り巻かれており、孤立してあなたが打つのを待つものではない。実の依存関係に従って歩く。「DC らしく見える」特徴に従わない。
**Q5**: 判定基準:一台のマシンが真のドメイン中核であることをどう確認するか。
**A5**: 実クライアントの依存 + 自己整合で豊富なディレクトリデータ + 完全なロールサービス = 真;孤立 + データがまばらで偽造 + 誘人なポートだけ開放 = 疑似罠。最高価値の対象には、真実性検証の基準も最高にすべき。それが防御側のおとりである可能性も最も高いから。

### 多層プロキシ下で、私の観測する IP/遅延が全て歪んでいる
**Q1**: 私のトラフィックが数層のプロキシ/踏み台を経て対象に届く。今、遅延、ソース IP、さらにはレスポンスまで信頼できないと感じる。どうするか。
**A1**: 先に意識する:プロキシを一層足すごとに、観測は一層歪む。遅延は累加増幅され(時間盲インジェクション全乱)、ソース IP は最後の一跳のもの(対象が見るのは私の思うものと違う)、一部のプロキシはトラフィックも書き換える。意思決定前に「歪み地図」を建てる:私のこのチェーンは何跳あるか、各跳がどうデータを改変し得るか。プロキシが導入する錯覚を対象の挙動としない。
**Q2**: プロキシが時間盲/タイミング判断を信頼できなくする。どう補救するか。
**A2**: 重要測定はできるだけプロキシチェーンを短縮または傍路する。時間敏感な操作は、可能なら対象により近く、より少ない跳の位置から発起する(既に取った内部ネットワークの踏み台から直接打つ。大きく一回りしない)。あるいはタイミングチャネルを放棄し、遅延に不敏感な観測(ブール差分、内容差異、OOB)に替える。中間層を減らすことが観測信頼度を回復する根本。
**Q3**: 特定の層のプロキシが私のリクエスト/レスポンスを書き換えていると疑う。どう特定するか。
**A3**: エンドツーエンドのバイト対比。チェーンの両端(私が送った、対象が実際に受けた。対象側から観察できれば)の生バイトを対比する。対象側で見られないなら、逐跳二分する:一層のプロキシを外して再打ち、挙動が変わるかを見て、どの跳が書き換えているかを特定する。プロキシの自動ヘッダー追加、エンコーディング変更、キャッシュ、リトライは全て観測を汚染する。
**Q4**: プロキシチェーン自体が不安定/深刻に歪み、簡素化できない(遮断された)なら、どこへ方向転換するか。
**A4**: 直交方向転換、「近場への足場確保」へ。長いチェーンで遠隔操作するより、対象の近くで安定した足場を一つ確立する(対象セグメント内の踏み台を一台取る)。以降の全観測をそこから発起する。チェーンが短く、歪みが小さく、より秘匿。中核の方向転換は私の「観測位置」を変えること。歪んだ遠隔チェーン上で混乱したデータを繰り返し解釈しない。
**Q5**: 判定基準:どの観測がプロキシ下で信頼できないか。
**A5**: 絶対時間/遅延、ソース IP、中間層に書き換えられ得る/キャッシュされ得る内容。多層プロキシ下ではデフォルトで信頼せず、近場で再測するかチャネルを替える必要がある。安定して信頼できるのは「確定的副作用類」の証拠(OOB のユニーク文字列、対象側で照会できる状態変化)。この類を優先依存する。

### ツールが「接続成功」を報告するが、半開/RST 偽装ではないか
**Q1**: 私のツールが特定のポートと「接続成功」と報告するが、後続で何もできない。本当に接続を確立したのか、ファイアウォールに偽レスポンスで騙されたのか。
**A1**: 「接続成功」はどの層の成功かを見る必要がある。ツールは SYN-ACK を受けただけで成功と報告するかもしれない(TCP 半開/SYN プロキシファイアウォールが全ポートに SYN-ACK を返す)。実サービスが根本的にない。判定基準は「アプリケーション層で意味のある対話」ができるか:接続後にそのサービスの実プロトコルリクエストを送り、プロトコルに合う応答があるかを見る。TCP が通る ≠ サービスがある。
**Q2**: TCP は接続するがアプリケーション層が無応答。何を意味するか。
**A2**: いくつかの可能性:ファイアウォールの SYN プロキシ(ハンドシェイクを騙し、バックエンドにサービスがない)、サービスはあるが特定のプロトコル/認証ハンドシェイクをして初めて応答する、またはサービスが hang。区別方法:同一ホストの既知で実在する開放ポートに同じアプリケーション層プローブを対照として行う。実ポートにはアプリケーション層応答があり、このポートにはないなら、この「成功」はファイアウォール偽装の空接続の可能性が高い。
**Q3**: ファイアウォールが接続状態を偽造していると疑う。さらにどう確認するか。
**A3**: TCP 挙動の詳細を見る。実サービスの接続とファイアウォールプロキシの接続は、TTL、window size、タイミング、後続の RST 挙動に往々にして差異がある。ファイアウォールは大量のポートに一致するハンドシェイク特徴を返す。実サービスはそれぞれ違う。数個の「成功」ポートを選びこれらの低層特徴を対比する。一致して疑わしいなら偽装された。
**Q4**: これらの「開放ポート」が全てファイアウォール偽造の空殻(遮断された)と確認した。どこへ方向転換するか。
**A4**: 直交方向転換、アプリケーション層検証駆動のスキャンへ、そして視点を替える。TCP 状態だけを見るスキャン結果を放棄し、「アプリケーション層ハンドシェイクを完成できる」ポートだけを信じる。戦略的に、外からファイアウォール越しに全て偽装なら、内部視点(既存足場があれば内部ネットワークから見る)か、プローブ技術を替える(SYN プロキシ偽装を穿透できる方式)。ファイアウォールが餌として与える偽の開放ポートをアセットリストにしない。
**Q5**: 判定基準:接続成功はどこまでで数えるか。
**A5**: TCP ハンドシェイク成功 = 最弱の証拠(偽造可能);そのサービスのアプリケーション層プロトコル対話を完成し、プロトコルに合うレスポンスを得る = 実サービス。永遠に「接続成功」をアプリケーション層検証まで押し下げる。伝送層の錯覚で私の対象リストを決めさせない。

### 対象が能動的に誘惑的な「漏えい」を餌として与える。真の機会か canary か
**Q1**: とても価値がありそうなものを見つけた。露出したキー、開放した API、ダウンロード可能なバックアップ。目立ちすぎる。真の機会か canary token/罠か。
**A1**: 価値と露出度は反比例するのが正常。価値があり露出もあるなら、デフォルトで疑う。本当に価値あるものは通常誰かに保護され、明るみに勝手に転がっていない。「高価値 + ゼロ障壁」の発見は、先に鉤と仮定する(canary token は一度使われると告警して攻撃者を特定)。興奮して即使わず、先に「それを使う」ことが罠のトリガーそのものかを評価する。
**Q2**: 使う前にそれが canary かをどう判断するか。
**A2**: その「自然性」と「孤立性」を見る。実の漏えいは通常、ある疏忽の副産物で、周囲に一致する文脈がある(それが位置するリポジトリ/ディレクトリ/システム全体が実在で稼働している)。canary は往々にして孤立して、作為的に置かれ、周囲の環境が空すぎるか完璧すぎる、かつそれが指すリソースが「専ら訪問を待つ」。それをトリガーしない方式(読み取り専用のメタ情報、オフライン分析)で先にその来歴を偵察する。
**Q3**: オフラインで判断できない。必ず「使って」初めて分かる。リスクをどう制御するか。
**A3**: 最小化、否認可能に試探する。疑似 canary 認証情報/token なら、最低敏感度の方式で単回検証し、「使えば既に露呈したかもしれない」と事前に置く。使用後の連鎖反応を観察する:即異常があるか(アカウント禁止、リダイレクト、挙動の突然変異)。canary の典型特徴は「一触れると反応がある」。
**Q4**: それが canary/おとり(誘導された)と確認した。どこへ方向転換するか。
**A4**: 直交方向転換、実の疏忽点へ。そして canary をインテリジェンスにする。防御側が canary を仕掛けたことは、ここに誰かが能動的に防御していることを示す。この区域への警戒を上げる。転じて本当に無意図の漏えいを探す。あの、そんなに目立たず、一歩多く歩く必要があり、防御側自身も露出に気づいていないもの。同時に canary の存在自体が防御側の注目点を漏らす。彼らが何の本物を守っているかを逆算する。
**Q5**: 判定基準:「機会」を発見したら、先に何を問うか。
**A5**: 先に「それがなぜこれほど簡単に私に取れるのか」を問う。答えが「防御の疏忽で文脈が自己整合」なら、慎重に前進できる。「これほど露出する合理的理由がない」なら、デフォルトで鉤とし、先に来歴を偵察してから触るかを決める。高誘惑の発見には、疑いがデフォルト態度。信頼は文脈で稼ぐ。

### 私の C2 コールバックデータは、リプレイや中間者改ざんされないか
**Q1**: 私の implant のコールバックデータ、または私が命令を下して受けた結果は、防御側に遮断、リプレイ、さらには改ざんされて私を誤導しないか。
**A1**: 通信チャネルが観測さらには操作される可能性を仮定する。特に高対抗環境で。C2 トラフィックに強暗号化と完全性/新鮮性保護がなければ、受けた「結果」はリプレイされた旧データか、防御側に偽造された偽エコー(私を誤判断に導く)かもしれない。先にチャネル自体が信頼できるかを確認する:エンドツーエンド暗号化か、リプレイ防止(nonce/シーケンス番号)か、完全性検証か。これらがなければ、どの受信データも「真かもしれない」だけ。
**Q2**: 自分がリプレイか偽造データを受けたかをどう察知するか。
**A2**: 新鮮性プローブを使う。各命令の送信時に、私側で生成した一回限りのランダムマークを付け、結果にこのマークを返すよう要求する。受けた「結果」が現在のマークを含まない、または旧マークを含むなら、リプレイ。同時に結果を自己整合検査する。同じ状態を二回照会して論理的に筋が通らない(時間逆流、状態が理由なく巻き戻る)なら、改ざんかリプレイを疑う。
**Q3**: 防御側が中間者で命令結果を改ざんしていると疑う。どうするか。
**A3**: 重大な結論を交差多チャネル検証する。重大意思決定に影響する観測(「特定の防御が閉じた」「特定の認証情報が有効」など)は、一条の C2 チャネルの報告だけを信じない。独立した、異なる経路を通るチャネルで同じ事実を再確認する。二条の独立チャネルが一致して初めて重大結論を採信する。特に高リスク行動を取る前に。
**Q4**: C2 チャネルが防御側に掌握/汚染された(捕まったチャネル)と確認した。どこへ方向転換するか。
**A4**: 直交方向転換、信頼チャネルの再建へ。汚染されたチャネルを放棄する(それが与えるものは全て信頼できず、私を逆に特定し得る)。バックアップの、別プロトコル/別インフラの秘匿チャネルへ切り替え、暗号化と完全性保護をアップグレードする。戦略的に、以前そのチャネルを経た全観測が誤導された可能性を仮定し、戻って重要判断を再検証する。汚染チャネルが餌として与える「事実」の上に意思決定を建て続けない。
**Q5**: 判定基準:C2 観測はいつ信頼できるか。
**A5**: エンドツーエンド暗号化 + リプレイ防止の新鮮性マーク + 完全性検証 + 重要結論の多チャネル裏付け。四者が揃って初めて重大意思決定に採信する。どれか一つでも欠ければ、C2 の報告は「事実」でなく「手がかり」として扱う。特に、それに基づいて不可逆の高リスク動作を軽率に取らない。

### 外向き通信テストが全通。本当の外向き通信かトランスペアレントプロキシのハイジャックか
**Q1**: 対象で外向き通信を測ると、どの外部アドレスも「通じ」、存在しないアドレスでさえ応答があるように見える。これはネットワークが本当に通じているのか、トランスペアレントプロキシ/ゲートウェイがハイジャックしているのか。
**A1**: 「全通」は「全不通」と同じく疑わしい。企業ゲートウェイには往々にしてトランスペアレントプロキシがある:それは全てのアウトバウンド接続を遮断し、自分が代わりに応答し、あなたに外網へ直連したと思わせる。判定基準は「絶対に応答が存在しないはずの」目的地(ランダムな不存在ドメイン、ブラックホール IP)を測ること。それも「通じ」るか内容(特に統一の遮断ページ/認証ページ)を返すなら、中間にプロキシが応答しており、私は根本的に本当の外向き通信をしていない。
**Q2**: トランスペアレントプロキシであり真の外向き通信でないことをどう確認するか。
**A2**: レスポンスの一致性と出所を見る。トランスペアレントプロキシは往々にして異なる外部対象に酷似特徴を返す(同じ証明書、同じエラーページ、同じ認証ポータルへのリダイレクト)。真の外向き通信では対象ごとに挙動が異なる。私が完全に制御する外部サーバーを数個訪問し、それらが本当に対象からの接続を受けたか(私のサーバー側でログを見る)を確認する。受けないなら、プロキシに遮られた。
**Q3**: トランスペアレントプロキシの存在を確認した。これは私の帯域外/C2 に何を意味するか。
**A3**: 私の帯域外データがプロキシに見られ、記録され、特定の内容を遮断される可能性を意味する。DNS 帯域外が内部 DNS に遮断され、HTTP がプロキシに監査されるかもしれない。「外向き通信できる」から自由に帯域外できると思わない。調整:プロキシが許可するプロトコル/ポートを通す、プロキシが深検しないチャネルを使う、C2 を正常なプロキシ経由の業務トラフィックに偽装する(ドメインフロント/合法クラウドサービス)。
**Q4**: トランスペアレントプロキシが全ての真の帯域外を切断する(遮断された)なら、どこへ方向転換するか。
**A4**: 直交方向転換、「プロキシ自体を利用する」または「純内部ネットワーク」へ。第一に、プロキシは必経の道。それが何を許可するかを研究する。それは必ず何らかの業務を外向き通信させている。許可された目的地/プロトコルに沿ってトンネルを建てる。第二に、徹底的に出られないなら、純内部ネットワークパラダイムに戻る(外向き通信しないチェーン参照):帯域外せず、内部ネットワークの踏み台を中心に作戦し、真に自由に外向き通信できるマシンを一台見つけてチャネルを建てる。
**Q5**: 判定基準:「本当に外向き通信した」ことをどう確認するか。
**A5**: 唯一信頼できる判定基準は「私自身が制御する外部サーバーが本当に対象からの接続を受けた」こと。対象側が「通じた」ように見えることではない。対象側の「接続できる」で結論を下す外向き通信判断は全てトランスペアレントプロキシに偽造され得る。外部の落点の実受信で錨を下ろす。対象の自己申告の通じを信じない。
