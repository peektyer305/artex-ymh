# メタ意思決定 · 費用対効果による並び替え:どれを先に攻めるか

### 偵察が終わった直後、多数の開放ポートを前にどれを先に攻めるか
**Q1**: ポートスキャンが戻ってきた。ホスト A は web(80/443)、SMB(445)、RDP(3389)、データベース(3306/1433)、多数の高位サービスを開いている。時間が限られている。どれを先に攻めるべきか。
**A1**: ポート番号順に攻めず、「利用の成熟度 × 権限利得 × 露出面」の三次元で並べる。まず「既知の高危険で一撃で決着できる」ものを一瞥する:445 は MS17-010/SMBGhost の類に対応、データベースの弱いパスワードは一歩で shell、この類を先に検証する。Web は面が大きいが深浅がまちまちで、第二ラウンドで細かく見る。RDP は通常「認証情報があって初めて役立つ」。認証情報がなければ先に飛ばす。
**Q2**: どのポートが「費用対効果が最も高い」かを、個別に噛まずにどう素早く判断するか。
**A2**: 「一回のプローブで反証/確認できる」動作でフィルタリングする:445 に MS17-010 検知スクリプトを一つ送る、データベースに空パスワード+弱いパスワード三連を送る、web はホームページのフィンガープリントを掴んでフレームワークバージョンを見る。10 分以内に各ポートに「赤/黄/緑」のラベルを付ける(赤=高確率で打てる、黄=深掘りが必要、緑=当分アイデアなし)。そして赤黄にだけ投入する。
**Q3**: いくつかのポートが全て「黄」で、明らかな赤点がない場合は。
**A3**: 「利用後の権限が最も高く、横展開価値が最大」のものを深入り方向として優先選定する。通常はシステム権限を直接与えられるサービス(データベース、ミドルウェア、履歴デシリアライズのあるコンポーネント)が純フロントエンド web より優先。同時に残りの黄点をフォールバックスタックとして記録し、捨てない。
**Q4**: 445 を狙って MS17-010 を半時間攻め、exploit がずっと不安定/ブルースクリーンになった。この道が塞がれた。どこへ方向転換するか。
**A4**: 直交次元を替える:「メモリ脆弱性利用」から「設定/認証情報」次元へ。同じ 445 で、匿名共有の列挙、null session、SMB signing 無効時の relay、共有内の敏感ファイルを試す。あるいは徹底的にポートを替えて web 面に戻る。不安定なメモリ exploit を無限にリトライしない。それは負の期待値。
**Q5**: これらの判断をどう記録して重複労働を避けるか。
**A5**: 「対象×サービス×状態×次のステップ」の小表を維持し、各組み合わせに tried/blocked/todo と記す。方向転換時にまず表を調べ、各投入が未探索または高信頼のマスに打たれることを保証する。感覚で打ち直さない。
**Q6**: 全ポートを探り尽くしても突破点がない。次のステップは。
**A6**: 単機の攻撃面がやり尽くされたことを示す。「情報の広さ」へ次元を変える:サブドメイン/隣接サイト/履歴アセットを補う、web 内のコメントと JS 内の API をひっくり返す、同一セグメントの他のホストを探す。単点が打てない時、広さ収集は往々にして無視された柔らかい対象を見つけられる。

### 高価値対象 vs 低い位置の果実の並べ方
**Q1**: 中核対象(ドメインコントローラ/中核業務システム)が一目で見えたが、防御が非常に厳しい。隣には明らかにパッチを当てていない境界マシンが数台。先に硬い骨を噛むか、先に柔らかい果実を摘むか。
**A1**: レッドチームの実戦では、スコアリングが明確に中核対象だけを認める場合を除き、先に柔らかい果実を摘む。なぜなら足場(foothold)は全ての前提で、境界マシンを取れば内部ネットワーク視点、認証情報、ルーティングを提供でき、逆に中核対象を「内部から」柔らかくする。中核対象への直接の硬攻は往々にして高ノイズ、低成功率。
**Q2**: しかし柔らかい果実を摘むのは価値のないマシンで時間を無駄にしないか。
**A2**: 「この柔らかい果実が再利用可能なアセットを産出できるか」が鍵:認証情報、ドメイン情報、内部ネットワーク接続性、チケット。境界マシンを取った後、ドメインユーザーの hash やキャッシュ認証情報を dump できれば、その「レバー価値」はそれ自体をはるかに超える。柔らかい果実は「中核アセットに近い、または認証情報が豊富な」ものを選ぶべきで、適当な一台ではない。
**Q3**: 一台のマシンの「レバー価値」をどう見積もるか。
**A3**: 三問:それはドメイン内か。それに高権限サービスアカウントが走っているか。それは私の届かないセグメントへ接続できるか。三つとも yes なら高レバーの踏み台で優先。三つとも no の孤立マシンは、打ちやすくても後回し。
**Q4**: 摘める柔らかい果実を全て摘んだのに、中核対象にまだ入れない。ここで塞がれた。どこへ方向転換するか。
**A4**: 「ネットワーク経路」次元から「身分経路」へ方向転換:ネットワークから突破することはもう考えず、それにログインできる身分を集める。その管理者は誰か、どのマシンにそのセッション/認証情報があるか、それへの権限を持つサービスアカウントはないか。中核対象は通常 exploit で突破されるのではなく、一つの正規の認証情報で正門から入られる。
**Q5**: 認証情報経路も通らない場合は。
**A5**: 「信頼関係」次元へ再方向転換:それは誰を信頼するか。ドメイン信頼、証明書テンプレート(ADCS)、SCCM/WSUS、バックアップシステム、監視 agent。これらの帯域外の管理チャネルは往々にして中核対象の真の弱点で、正面ポートよりはるかに打ちやすい。
**Q6**: いつ断固として中核対象を放棄して戦果を拡大すべきか。
**A6**: 中核対象の各試行がアラートリスクを上げて進展がなく、横展開の拡散がまだ新認証情報/新ホストを産出し続けられる時、拡散に転じる。戦果の広さがある程度積み上がると、往々にして「ついでに」中核への鍵を拾える。

### 一群の Web アプリケーション、先にどれを見るか
**Q1**: アセット測量で数十の web サイト/管理画面が出た。全部手テストはできない。先にどれを見るか。
**A1**: 「技術的負債の濃度」で並べ、ドメイン名のアルファベット順で並べない。優先度:自社開発の老朽システム > アップロード/ファイル/エクスポート系機能サイト > 管理画面ログインページ > 標準化 CMS の最新版 > 純静的サイト。自社開発の老朽システムはセキュリティ監査が欠け、ロジック脆弱性とインジェクション密度が最も高い。
**Q2**: 個別に手テストせずにどう素早くレベル分けするか。
**A2**: バッチでフィンガープリントを一回行い、フレームワーク+バージョンを取り、まず「既知の重大 CVE バージョン」のサイトを単独で抜き出す(某ミドルウェアのデシリアライズ、某フレームワークの RCE バージョンなど)。これらは確定リターンで先に打つ。残りはレスポンス特徴で分類:ログインボックスあり、エラーエコーあり、ファイル操作あり、それぞれまとめる。
**Q3**: 複数のサイトが同じテンプレート/同じ開発元に見える場合は。
**A3**: これは良い知らせ:一つを突破すれば一類を把握できる。その中で「権限が最も高い/データが最も敏感な」ものをサンプルとして選び深掘りし、脆弱性を確認したら同源の全サイトに横展開適用する。同源サイトは「一回の研究、バッチ収穫」の高費用対効果対象。
**Q4**: 選んだ重点サイトのスキャンが全緑、手テストも穴がない。遮断された。どこへ方向転換するか。
**A4**: 「アプリケーション脆弱性」次元から「アセット/設定」次元へ:そのバックアップファイル(.bak/.zip/.git)、露出した設定、隣接サイト、同一 IP の他のサービス、履歴バージョン(web アーカイブ)を探す。多くのサイト自体は非常に綺麗だが、漏えいしたソースやバックアップがそれを裸同然にする。
**Q5**: 一つのサイトに WAF が立っている場合、バイパスを続けるかサイトを替えるか。
**A5**: まず低コストで二、三種のバイパスを試す(エンコーディング、チャンク分割、大文字小文字、パラメータ汚染)。通らなければサイトを替える。このサイトが唯一の入口でない限り。数十のサイトを選べる時、WAF バイパスの時間コストは通常、WAF のないサイトに替えるより高い。WAF サイトはフォールバックとして残す。
**Q6**: 全サイトが突破できず、web 面がやり尽くされた。次の次元は。
**A6**: 非 web 面へ方向転換:同一アセットのメール、VPN、要塞ホスト、API ゲートウェイ、モバイル app を逆コンパイルして出た API。web は攻撃面の一層に過ぎない。身分入口(メール/VPN の弱いパスワード、フィッシング)は web 脆弱性より速く内部ネットワークに入れることが多い。

### 時間ボックス制約下での費用対効果の取捨
**Q1**: 競技/演習の残り時間が限られている。手元の三本の線は全て「見込みはあるが確信がない」。残り時間をどう配分するか。
**A1**: 「期待リターン = 成功確率 × 権限利得 ÷ 見込み所要時間」で各線を採点し、点数が最も高い一、二本にだけ投入する。均等に撒かない。時間ボックス内で分散投入 = 各本が完成しない。低確率高リターンの線は余裕がある時だけ触る。
**Q2**: 自欺せずに「成功確率」をどう見積もるか。
**A2**: あなたが既にどれだけ確定的な信号を得ているかを見る:明確なバージョン+公開 exp = 高;エラーエコー+インジェクション疑い = 中;純推測/エコー全くなし = 低。「打てるはず」という感覚と「利用可能な信号を既に見た」を厳密に分け、後者だけが高確率に値する。
**Q3**: 一本の線に既に多くの時間を投入したが結果が出ない。埋没コストで手放せない。どう意思決定するか。
**A3**: 埋没コストは意思決定に参加させない。「今から、さらに X 時間投入した期待リターン vs 線を替えた期待リターン」だけを問う。この線の残存不確実性が前の投入で下がっていないなら(まだ検証されていないあの仮説のまま)、負の期待値。すぐ替える。
**Q4**: もう時間がないのに足場がまだ一つもない。あの高リスク exploit に一か八かで賭けるべきか。
**A4**: 場合による:打たなければゼロなら、高リスク高リターンの賭けは臨界時には合理的。最低限もゼロなのだから。ただし打つ前に、それがあなたの唯一の対象を殺さない(ブルースクリーン/サービスダウン)ことを確認する。さもなければ賭けに負けたらフォールバックさえない。
**Q5**: 時間ボックス内で穴を一つ見つけたがエクスプロイトチェーンが長く、完全な武器化が間に合わない場合は。
**A5**: 「最短の使える経路」を評価する:半製品で部分成果(ファイル読み取り/低権限 shell)を先に足場確保できるか。一歩で root を追求しない。「証明できる最小成果」を先に取り、残り時間で増分的に権限昇格する。完璧なチェーンのために取れる点を逃さない。
**Q6**: 全ての線が低確率で、時間も足りない。理性的なやり方は。
**A6**: 「確実性が最も高い最低目標」へ方向転換:目標を「中核攻略」から「任意の証明可能な足場/情報漏えいを一つ取る」に格下げする。目標の高さを下げて確定産出と交換する。ゼロ産出よりはまし。同時に、打ち切れなかった高価値の線を「次回優先」リストに整理する。

### 既知 CVE の打法 vs 未知のロジック脆弱性
**Q1**: 対象のフィンガープリントが明確で、対応する N-day CVE が試せる。一方、その業務ロジック脆弱性を掘るのに時間をかけられる。どちらを先に歩くか。
**A1**: 先に N-day。既知 CVE は「確定リターン、低時間コスト」。既成 PoC があり、数分で反証または突破できる。ロジック脆弱性は「高不確実、高時間投入」で、N-day 失敗後の深水区として残す。先に低い位置、後に深掘りが通用のリズム。
**Q2**: N-day にネット上で PoC があるが打てない。PoC が偽か、環境が合わないか。
**A2**: 三ステップで判じる:①バージョンが本当に影響範囲内か確認(フィンガープリントは人を騙すことがある);②前置条件(某設定が有効/某ポートが到達可能/某権限)を確認;③ローカルで PoC を再現してスクリプト自身の問題を除外。三ステップ過ぎても通らないなら、対象がホットパッチを当てたか緩和がある可能性が高い。マークして方向転換する。
**Q3**: 全ての既知 CVE がパッチ済み(パッチが非常に揃っている)。今ロジック脆弱性に転じる。どう効率的に掘るか。
**A3**: ロジック脆弱性の掘削も並べる必要がある:優先「権限検証の欠如」(権限外アクセス/未認可アクセス API)、「パラメータ制御可能な危険操作」(ファイル、コマンド、SSRF)、「業務フローのバイパス」(支払い/検証/多段フローのステップ飛ばし)。機能点から「間違えたら結果が最も深刻な」ものを先にテストする。
**Q4**: ロジックの穴も掘れない。徹底的に遮断された。どの直交次元へ方向転換するか。
**A4**: 「対象自身のコード脆弱性」から「対象の依存と運用」へ:その第三者コンポーネント、その CI/CD、そのクラウド設定(ストレージバケット/メタデータサービス)、その運用者(フィッシング/認証情報漏えい)。対象プログラムが堅固でも、そのサプライチェーンと運用が堅固とは限らない。
**Q5**: ロジック脆弱性で無限に深掘りして抜け出せないのをどう避けるか。
**A5**: ロジック掘削に「仮説検証時間ボックス」を設ける:各脆弱性仮説に固定時間を与えて検証し、時間内に疑わしい信号(異常レスポンス/権限外アクセスの兆候)が出なければアーカイブして次の仮説へ。ロジック脆弱性は最も人を消耗させる。必ず時間ゲートで制約する。

### 一つの点に長く詰まりすぎた。いつ放棄して方向転換するか
**Q1**: 同じ疑わしい脆弱性点で既に長く揉んでいる。諦めたくないが進展もない。方向転換すべきかどう判断するか。
**A1**: 三本の硬い損切り線を設け、どれか一つに触れたら方向転換:①連続 N 回の試行が「新しい情報」を何も生んでいない(レスポンスが全て同じ);②以前試した発想を皮を替えて繰り返している;③アラート/ブロックリスクが上がっているのにリターンがゼロ。どれかを満たせば、現在の経路は負の期待値区間に入っている。
**Q2**: しかし私は「もう一回で成る」と「感じる」。この直感は信じられるか。
**A2**: 直感の出所を区別する。直感が「新しい疑わしい信号を見た」(新エラー、新差異)に基づくなら信じられる。もう一ラウンド投入する。直感が「これだけ投入したからもうすぐのはず」だけなら、それは埋没コストの誤謬で、信じられない。新しい信号に支えられない楽観は、一律に採用しない。
**Q3**: 方向転換を決めた。でたらめに転ばず、どこへ転ぶかをどう選ぶか。
**A3**: 最初の攻撃面地図に戻り、「まだ探索していない直交次元」を探す:ずっと脆弱性利用を攻めていたなら身分/認証情報へ;ずっとアプリケーション層を攻めていたならインフラ層へ;ずっとこのホストを攻めていたならその隣人へ。方向転換は「情報エントロピーが最も高い(最も知らない)」方向へ転ぶべき。そこが期待リターン最大。
**Q4**: 方向転換後の新方向もすぐ詰まった。私の全体の発想が間違っているのか。
**A4**: 「情報不足」であり「経路の誤り」ではない可能性がある。連続する二方向がすぐ固着したなら、通常は偵察の深さが足りないことを示す。一歩引いて深い情報収集をする(既存の足場/エコーを一バイトずつ絞り尽くす)。情報を補ってから優先度を並べ直す。経路を替えて試行錯誤し続けない。
**Q5**: 「詰まり—方向転換—また詰まり」が当てもなく乱転しないようにするには。
**A5**: 明示的な「仮説スタック」を維持する:各経路を「仮説 X が成立→動作 Y→期待結果 Z」と書く。方向転換は反証された仮説をポップし、新しい仮説をプッシュすること。スタックがあれば、繰り返しも欠落もない。乱転の本質は仮説を記録していないこと。
**Q6**: 思いつく方向を全て試して全て詰まった。最後の一手は。
**A6**: 強制「視点切り替え」:自分がこのシステムの開発者/運用者になったつもりで、それが普段どうアクセスされ、どうバックアップされ、どう障害切り分けされ、誰が鍵を持つかを考える。防御者/運用者の視点からは、攻撃者の思考ブラインド領域にある合法チャネル(管理 API、デバッグポート、デフォルト認証情報)が見えることが多い。

### 広さ優先か深さ優先か
**Q1**: 最初の足場を取った後、横に敷いて数台多く触る(広さ)か、この台で root まで深掘りする(深さ)か。
**A1**: 早期は「足りる」程度まで広さを優先:まず現在の権限で内部ネットワーク地図、到達可能ホスト、見える認証情報を素早く一回収める(低コスト、高情報利得)、それから誰を深掘りするかを決める。盲目的に第一台で権限昇格を深掘りすると、root まで上げてからこの台が死角で横展開価値がないと分かるかもしれない。
**Q2**: 「足りる広さ」はどれだけか。どう無限に敷かないか。
**A2**: 広さ収集は「次の高価値対象を識別できる」までで止め、深さに転じる。判定基準:ドメインコントローラがどこか、中核アセットがどこか、私の現在の認証情報で誰に触れるかを既に知っているか。三つの問いに答えられるなら、広さは足りた。中核へ通じる最短の道を深掘りすることに集中すべき。
**Q3**: 広さスキャンはうるさすぎて露呈しないか。
**A3**: する。だから広さは全ネットワーク大スキャンではない。「低ノイズの広さ」を使う:先にローカル既存情報(キャッシュ、設定、hosts、ブラウザ、チケット)を読む。これらはネットワークトラフィックがゼロ。能動プローブが必要な時は、狭い範囲、低速、重要ポートだけを探る。広さの情報の多くはローカルに隠れており、全てスキャンに頼る必要はない。
**Q4**: ずっと広さを敷いているのに、深掘りできる突破口が見つからない。この「平押し」に嵌った。どこへ方向転換するか。
**A4**: 「横の広さ」から「縦の深さ」へ賭ける:現在情報が最も豊富な一台を選び、高権限まで深掘りし、高権限でもう一度広さ収集をする。突破口がないのではなく、現在の権限が低すぎて見えないことがある。権限昇格後に視野が開く。これは深さが広さにフィードバックする。
**Q5**: 逆に、一台で長く深掘りして権限昇格できない。またどうするか。
**A5**: 深さから広さへ戻る:この台を置き、既存の認証情報で横展開する。別の台では設定が違うため簡単に権限昇格できることがよくある。それから新しい身分でこの台を処理する。同じ認証情報でもホストが違えば権限が天と地ほど違う。マシンを替えるのは権限昇格の高費用対効果の「バイパス」。

### 認証情報の再利用 vs 新しい脆弱性探しの継続
**Q1**: 一群の認証情報(hash/平文/チケット)を dump したばかり。先にこれらで横展開再利用するか、現在のホストで穴探しを続けるか。
**A1**: 即「認証情報再利用」を優先。一つの有効な認証情報のレバーはもう一つの穴を掘るよりはるかに高い:パスワード再利用、pass-the-hash、pass-the-ticket が一歩で複数マシンにログインするかもしれない。穴探しは線形リターン、認証情報の横展開は指数的拡散かもしれない。まず認証情報の価値を絞り尽くしてから穴探しに戻る。
**Q2**: 認証情報が山ほどある。どれを先に使い、どこを打つか。
**A2**: 「アカウント権限 × 再利用の広さ」で並べる。ローカル管理者/ドメインアカウント/サービスアカウントは一般ユーザーより優先。先に高権限アカウントで一回の全ネットワークスプレーを行う(ロックポリシーに注意)。それがどのマシンにログインできるかを見て、「この鍵が開けるドア」を素早く囲い、それから個別に入る。
**Q3**: パスワードスプレー/再利用がアカウントロックを引き起こすのが怖い。どう天秤にかけるか。
**A3**: まずロックポリシー(しきい値、時間窓)を把握してからスプレーする。一つのアカウントは窓内で少数の高信頼パスワードだけを試す。遅くともロックしない。ロックは露呈するだけでなく、合法アカウントをロックして応答を引き起こすかもしれない。ポリシーが不確かなら、「アカウントごとに一回、多アカウントの広さ」で「単アカウントの複数回」を代替する。
**Q4**: 認証情報を全て試しても新しいマシンにログインできない。再利用のこの道が遮断された。どこへ方向転換するか。
**A4**: 「横展開ログイン」から「認証情報の昇格/派生」へ:既存の認証情報でさらに多くの認証情報を要求する。Kerberoast のサービスチケットをオフラインで割る、DCSync(権限が足りれば)、これらのアカウントがアクセスできる共有/データベース内の二次認証情報をひっくり返す。この道の再利用は通らないが、認証情報は「認証情報を生む」。別の利用方法に替える。
**Q5**: 派生も駄目なら、認証情報は無用なのか。
**A5**: 必ずしもそうではない。低権限の認証情報にもまだ「情報価値」がある:それで認証後の情報収集(ドメイン列挙、ACL、グループ関係、GPO)を行い、高権限への ACL 設定ミスの経路(某一般アカウントが某高権限オブジェクトへの書き込み権限を持つなど)を探す。認証情報がマシンを打てなくても、内部ネットワークの権限トポロジを照らせる。

### 内部ネットワーク横展開:先にドメインコントローラを打つか先に足場を拡散するか
**Q1**: 内部ネットワークに入って一台のドメイン内マシンを取った。ドメインコントローラに直行するか、先に横展開で数台制御するか。
**A1**: 一歩でドメインコントローラを取れる経路(直接 DCSync 可能/既知のドメインコントローラ脆弱性)を握っている場合を除き、先に足場を拡散する。ドメインコントローラ直行は高ノイズ、監視をトリガーしやすく、失敗後は足場が一つしかないかもしれない。先に拡散するのは「抗打撃」と「認証情報蓄積」のためで、ドメインコントローラへの道を自然に浮かび上がらせる。
**Q2**: 自分が既に「一歩でドメインコントローラ」の札を持っているかをどう判断するか。
**A2**: 手元に以下があるか確認:ドメイン管理者/等価の認証情報、利用可能なドメイン級脆弱性(某認証バイパスなど)、ドメインコントローラへの高権限サービスアカウント、ADCS 証明書濫用経路、書き込み権限のある重要 ACL。どれか一つあれば直接取れる。なければ素直に蓄積する。
**Q3**: 拡散の過程で、ドメインコントローラへ通じる道を敷くために何を収集すべきか。
**A3**: 目標指向で収める:誰がドメイン管理者か、ドメイン管理者のセッションがどのマシンにあるか(特定して dump)、Kerberoast で割れる高権限サービスアカウントがないか、AS-REP で打てるアカウントがないか、ADCS テンプレート設定、ドメイン信頼。各マシンで「それは私をドメイン管理者に近づけるものを持っているか」を問う。
**Q4**: ドメイン管理者セッションのあるマシンを見つけたが打てない。ドメインコントローラへの道が塞がれた。どこへ方向転換するか。
**A4**: 「プロトコル/サービス」の直交次元を替える:このマシンの通常入口から打たず、ADCS(ESC シリーズ証明書濫用)、委任濫用(制約付き/非制約付き/RBCD)、GPO 濫用、ドメイン信頼のクロスドメイン攻撃へ転じる。ドメインコントローラへの道は「ドメイン管理者パスワードを取る」だけではない。身分システム自体の設定ミスがより秘匿な正門であることが多い。
**Q5**: 全ての横展開を終えてもドメインコントローラに届かない。徹底的に詰まった。
**A5**: 「データ即目標」の心構えへ方向転換:ドメインコントローラ自身が阻まれたなら、先に直接中核データアセット(ファイルサーバー、データベース、コードリポジトリ、メール)に届く。多くの実戦目標はドメインコントローラなしで達成できる。ドメインコントローラを必須経路にしない。それは手段であって目的ではない。

### 権限昇格 vs 横展開移動、どちらを先にやるか
**Q1**: 一台のマシンで低権限 shell を取った。先にローカルで system へ権限昇格するか、低権限のまま先に横展開するか。
**A1**: あなたの目的とこのマシンの役割を見る。現在の低権限で既に横展開に必要な動作(認証情報を読める、認証を発起できる)ができるなら、先に横展開して「戦いながら養う」。横展開により高い権限が必要(LSASS を読むのに system が必要など)なら、先に権限昇格する。デフォルト傾向:先に低権限で何を絞り出せるかを見て、足りなければ昇格する。
**Q2**: 権限昇格にも多くのルートがある。どれを先に試すか。
**A2**: 「自動化度と成功率」で並べる:まず権限昇格情報収集スクリプトを一回回して全疑わしい点を列挙し、次に「設定類」(サービス権限の設定ミス、計画タスク、AlwaysInstallElevated、書き込み可能なサービスのパス、sudo の設定ミス)を優先。これらは確定性が高く、exploit 不要。カーネル exploit 権限昇格は最後。落ちやすく、バージョン依存だから。
**Q3**: 権限昇格の試行がプロセスを落として shell を失うかもしれない。どうリスクを天秤にかけるか。
**A3**: 権限昇格前に「再侵入能力」を確保する:低権限のコールバックを一つ永続化するか、足場を再取得できることを確認する。そうすればカーネル exploit が落としても、これまでの成果が無駄にならない。フォールバック能力がない時は、無損の設定類権限昇格を優先選定し、カーネル exploit はバックアップがある時に残す。
**Q4**: ローカル権限昇格の各種の手を全て試して昇格できない。低権限に詰まった。どこへ方向転換するか。
**A4**: 「本機の権限昇格」から「マシンを替えた権限昇格」へ:低権限の認証情報で別のマシンへ横展開する。そのマシンの設定には、このマシンにない権限昇格点があるかもしれない。権限昇格の本質は設定ミス探しで、マシンごとに設定ミスが違う。マシンを替える方が本機に執着するより速く system に至ることが多い。これは権限昇格問題を横展開問題に変換する。
**Q5**: 全てのマシンで権限昇格できないなら。
**A5**: 「ドメイン層の権限昇格」へ方向転換:個人マシンで上がらなくても、ドメイン内の ACL/委任/ADCS 設定ミスが、低権限ユーザーから直接ドメイン級権限を取らせ、逆に単機権限を上書きするかもしれない。縦(単機)の権限昇格が壁に当たったら、身分システム層へ横展開すると意外な通路があることが多い。

### 複数台を getshell 済み。先にどれを深く掘るか
**Q1**: 数台のマシンを同時に制御している。精力が限られる。どの台を先に深く掘るか。
**A1**: 「先に取った」順ではなく「戦略的位置」で並べる。優先して深掘り:①新セグメントへ通じるデュアル NIC/踏み台マシン;②認証情報/セッションが最も豊富なマシン(運用踏み台、端末サーバー);③中核アセットに最も近いもの。先に取ったマシンが最も価値があるとは限らない。順序に縛られない。
**Q2**: 各マシンの「戦略的位置」をどう素早く評価するか。
**A2**: 各マシンで軽量な三つのことをする:ネットワークカードとルーティングを見る(新セグメントの有無)、ログインユーザーとセッションを見る(高権限/多ユーザーの有無)、それが接続するサービスを見る(中核へ向かう認証情報/マウントの有無)。三分で人物像を描き、各台に「踏み台価値/認証情報価値/データ価値」の三点を付ける。
**Q3**: データ価値が高いが戦略的位置が悪い台と、その逆の台がある。どちらを先にするか。
**A3**: 早期は戦略的位置を優先(それはより多くのマシンと認証情報をもたらす「乗法」)。中後期、地図が既に明らかでデータを取るだけの段階ではデータ価値を優先(それは「目標」そのもの)。段階によって重みが違う:拡張期はレバーを見て、収穫期は目標を見る。
**Q4**: 重点的に深掘りしていた台が突然オフライン/駆除された。不意を突かれた。どうするか。
**A4**: これはまさに「単点に集中投資しない」教訓。即バックアップ足場に切り替える。方向転換の前提は、複数台に永続化冗長をしておいたこと。なければ、まず残りの制御中マシンで緊急に足場と永続化を建て直し、オフラインが偶発か応答かを評価する(応答なら、全面低ノイズモードへ)。
**Q5**: 深掘り前に「集中投資即制御不能」のリスクをどう下げるか。
**A5**: どの台を深掘りする前にも、複数の制御済みマシンに互いに依存しない永続化(別ユーザー、別メカニズム、別コールバックチャネル)を敷き、足場を冗長化する。冗長があって初めて集中深掘りできる。これは深い投入の前提条件で、選択肢ではない。

### WAF に遮られたらどこへ方向転換するか
**Q1**: web payload を送るとすぐ WAF に遮られる/遮断ページが返る。バイパスを続けるか、発想を替えるか。
**A1**: まず「低コスト三連バイパス」で WAF の強度を検証する:エンコーディング変形、大文字小文字/コメント難読化、チャンク分割/パラメータ汚染。三連の一つが payload を部分的に通した(エラーが変わった)なら、バイパス可能で投入価値がある。全て即遮断されレスポンスが完全に一致するなら、WAF ルールが硬く、バイパスの費用対効果が低い。次元を替えることを考える。
**Q2**: WAF が何を遮断しているか(特徴か挙動か)をどう判断するか。
**A2**: 対照実験をする:純粋に正常なリクエスト(通る)、明らかな悪意特徴リクエスト(遮断)、構造が怪しいが特徴のないリクエスト(観察)。これで「キーワード特徴マッチング」(エンコーディングでバイパス可)か「意味論/挙動分析」(文字を変えるのでなくロジックを変える必要)かを判断する。バイパス前に何をバイパスするかを知る。
**Q3**: 特徴がバイパスできない。この脆弱性点は廃棄か。
**A3**: そうではない。「入口の次元」へ方向転換:同じ脆弱性にも WAF がカバーしない入口があるかもしれない。別の API パス、別のパラメータ位置(header/cookie/json body vs url)、別のサブドメイン、またはオリジンサーバー直連(CDN/WAF を迂回して実 IP を探す)。WAF は往々にして正面のドアしか守らず、側面ドアと裏口は管轄していない。
**Q4**: オリジンサーバー探し/CDN 迂回も駄目。WAF のこの道が徹底的に塞がれた。どこへ方向転換するか。
**A4**: 「web インジェクション」次元全体から撤退し、「非インジェクション類」攻撃面へ:認証ロジック(弱いパスワード、権限外アクセス、token 欠陥)、ファイル系機能、SSRF、および全く非 web の入口(他のポートサービス、フィッシング)。WAF は payload の特徴を遮れるが、業務ロジック欠陥と弱いパスワードは遮れない。
**Q5**: この WAF サイトが唯一の入口で、打たざるを得ない場合は。
**A5**: それなら速攻目標ではなく研究プロジェクトとして扱う:レートを下げて IP バンされないようにし、制御可能なローカル環境でこの類の WAF を模してバイパスを研究する。あるいは WAF 自体/その管理面を攻める。ただし先に「本当に唯一か」を確認する。多くの場合、いわゆる唯一の入口は傍路を見つけていないだけ。

### ポートが全てファイアウォールにフィルタリングされたらどう転換するか
**Q1**: 対象が極少数のポートしか開いていない(443 だけなど)、または大量のポートが filtered。通常の攻撃面が極めて狭い。どうするか。
**A1**: まず「ファイアウォール前置」を仮定し、「ポート閉鎖」と「フィルタリング」を区別する。狭い攻撃面の下で、唯一の開放ポートを極限まで絞る。443 の背後には複数の仮想ホスト、複数の web アプリケーション、API、VPN ポータルがあるかもしれない。狭い ≠ ない。唯一の入口の各層を深掘りする。
**Q2**: 唯一の開放ポートにも穴を掘れない。この対象は打てないのか。
**A2**: 「出方向」の発想へ方向転換:外から打てなくても、内から出られないとは限らない。何らかの方法で対象に能動的にあなたへ接続させられれば(SSRF、メール、サプライチェーン、水飲み場)、インバウンドファイアウォールを迂回できる。インバウンドが厳しい対象はアウトバウンドが緩いことが多い。攻撃ベクトルを「私がそれに接続する」から「それが私に接続する」に変える。
**Q3**: 対象に「能動的に私へ接続させる」トリガー点をどう探すか。
**A3**: 「対象が外部入力を処理してリクエストを発起する」機能を全て探す:URL プレビュー、画像取得、webhook、メール、リモートリソースのインポート、更新チェック、ログ/監視レポート。これらは SSRF/コールバックの温床。狭い攻撃面では、コールバックベクトルが往々にして唯一の突破口。
**Q4**: 出方向も固く塞がれ、内外とも通らない。この対象線が徹底的に塞がった。どこへ方向転換するか。
**A4**: 「人とサプライチェーン」次元へ:対象マシンがいくら固く封じられていても、それを操作する人とそれに供給する上流は封じられていない。フィッシングで運用認証情報を取り、それが信頼する管理システム/更新源を打ち、「信頼された側」から入る。技術的境界の果てで、信頼関係が新しい攻撃面になる。
**Q5**: 純技術演習でソーシャルエンジニアリング禁止なら。
**A5**: それなら「同一環境の他のアセット」へ方向転換:厳重に守られているのは往々にして一台だけで、そのセグメント/クラウドアカウント/管理平面には必ず防御の弱い隣人がいる。隣人を取ってから内部ネットワーク側からこの台を見る。インバウンドファイアウォールは内部ネットワークトラフィックには通常形骸化している。硬い対象を迂回し、その柔らかい隣人から迂回する。

### 見かけ上攻略不可能な対象を前に、バイパスするか判断する
**Q1**: 一つの対象がパッチ全、設定厳、明らかな脆弱性なし。硬く噛み続けるか、バイパスするか。
**A1**: まず「それは目的か手段か」を問う。それが本当の目標への一環に過ぎないなら、絶対に硬く噛まない。それをバイパスし、最終目標へ到達する別の経路を探す。それが唯一の最終目標そのものである時だけ、重兵投入に値する。手段目標と最終目標の区別が損切り前提。
**Q2**: 一つの対象が「硬く噛む価値がある」かをどう素早く判断するか。
**A2**: 投入産出を計算する:硬く噛む見込み時間/リスク vs バイパスして別経路を探す見込み時間/リスク。内部ネットワークに最終目標へ通じる道が五本あり、この台が最も硬い一本なら、理性ある選択は残り四本の最も柔らかいものを行くこと。目標は結果達成であり、各マシンの征服ではない。
**Q3**: 実は穴があるのに見つけていないだけではないか。早すぎる放棄をどう避けるか。
**A3**: 「攻撃ゲート」でなく「偵察ゲート」を与える:限定時間で徹底的な情報収集(全バージョン、全設定、全露出)を行う。ただし利用試行は無限にしない。徹底調査後、確かに疑わしい信号がなければ、それは真に硬い。安心してバイパスする。「試行の尽き」でなく「情報の尽き」で判定する。
**Q4**: バイパスを決めた後、それが持つはずの重要物を見逃さないようどう保証するか。
**A4**: バイパス ≠ 忘却。「このマシンは X(データ/認証情報/信頼)を持つかもしれない」と記録する。別の経路でより高い権限を得た後、内部/上流から戻ってそれを収める。その時は無防備に開くかもしれない。バイパスは「一時スキップして回収をマーク」であり、永久放棄ではない。
**Q5**: 一巡して全道がこの硬い対象に通じていると分かった場合は。
**A5**: それならそれは本当の咽喉で、投入価値がある。この時打法を転換:「外部脆弱性利用」から「内部/信頼利用」へ。あなたは既に内部ネットワークにいる。蓄えた認証情報、信頼関係、管理チャネルで、それが信頼する側から入る。それが防御する側から攻めない。位置が変われば、同一対象の軟硬も変わる。

### 情報不足の時、先に偵察を補うか先に試探するか
**Q1**: 対象への理解が少ない。黙々と情報収集を続けるか、直接試探的攻撃を始めるか。
**A1**: 「情報の限界価値」で決める。もう少し収集すれば攻撃成功率を大きく上げられる(まだバージョン/設定/攻撃面全景を取っていないなど)なら、先に偵察を補う。情報が既に一、二個の高信頼攻撃点を特定できるなら、過度に偵察せず直接試探する。試探自体も一種の情報収集。
**Q2**: 「偵察中毒」、無限収集して動かないのをどう防ぐか。
**A2**: 「偵察足りる」判定基準を設ける:少なくとも一つ「具体的で、実行可能で、明確な期待のある」攻撃動作を列挙できるか。できれば情報は足りており、動くべき。列挙できなければ、まだ重要な情報が欠けている。収集を続ける。偵察の唯一の目的は実行可能な動作を産出すること。収集のための収集ではない。
**Q3**: 逆に、試探的攻撃は情報不足で露呈/低効率にならないか。
**A3**: 「低コスト無害の試探」を先に行う:アラートをトリガーしないプローブ(正常リクエストに軽量テストを混ぜる)を送り、レスポンス差異を観察する。この類の試探は情報を補いつつ低リスク。「重型攻撃」は情報が足り、信頼度が高い時に残す。情報不足で重い手を打たない。
**Q4**: 長く偵察しても攻撃面が組み上がらない。情報収集も詰まった。どこへ方向転換するか。
**A4**: 「能動対話式偵察」へ方向転換:受動収集で図が組めない時、制御された能動対話で情報を引き出す。故意にエラーをトリガーしてスタック情報を見る、異常入力を送って挙動を見る、境界を測ってロジックを見る。情報は往々にして「収集」されるのではなく「対話で引き出される」。受動観察から能動刺激へ。
**Q5**: 能動偵察でも情報が乏しい。対象に本当に攻撃面がないのか。
**A5**: 「あなたが間違った層で探している」可能性が高い。偵察の層を転換する:アプリケーション層からインフラ層へ、技術層から組織層(従業員、サプライヤ、公開漏えい)へ、現在アセットから関連アセットへ。情報の乏しさは往々にして視野が狭すぎる。層を替えれば世界がぐっと広がる。

### 突破が連続失敗。戻って情報収集をやり直す
**Q1**: いくつかの突破の発想を試して全て失敗した。新しい打法を考え続けるか、戻って情報を収集し直すか。
**A1**: 三回以上連続失敗したら、情報収集に戻る。連続失敗は通常「手が足りない」のではなく「対象への理解に体系的偏りがある」。あなたは間違った地図に基づいて行動している。戻って地図を照合する:バージョンが正しいか、攻撃面が全か、フィルタリングに誤導されていないか。
**Q2**: 情報収集に戻って、重点的に何を再照合するか。
**A2**: 三類の高頻度誤判定を照合:①フィンガープリント/バージョンが偽装または時代遅れでないか;②私が到達可能だと思ったサービスが本当に到達可能か(ファイアウォール/セグメント);③私が対象だと思ったものが本当の対象か(CDN/プロキシ/ハニーポットの背後)。この三類の誤判定は全ての下流攻撃を必ず失敗させる。
**Q3**: 「情報が間違い」による失敗と「手が合わない」による失敗をどう区別するか。
**A3**: 失敗の一致性を見る。別々の発想が全て同じ段階で失敗する(全て接続できない、全て同じく遮断される)なら、情報/環境問題(手がいくらあっても無駄)。失敗点がそれぞれ違うなら、手の問題。同じ壁に何度もぶつかるなら、先に壁の位置を描き間違えていないか疑う。
**Q4**: 情報を収集し直して地図が確かに間違っていたと分かり、修正後も打てない。さらにどこへ方向転換するか。
**A4**: 「偵察境界の拡大」へ方向転換:現在のアセット範囲に突破口がないなら、境界を外へ広げる。関連ドメイン、隣接サイト、子会社アセット、サプライチェーン、履歴アセット、クラウドアセット、従業員のデジタル足跡。突破失敗は往々にして「突破の的を狭く選びすぎた」。より大きな的場に替える。
**Q5**: 境界を広げても門がない。何を反省すべきか。
**A5**: 「対象画像」そのものを反省する:高防御の一点を唯一の入口と見なしていないか。本当の入口は往々にして防御者のブラインド領域にある。シャドー IT、テスト環境、オフラインにし忘れた旧システム、第三者ホスティング。「主アセット」の執念から飛び出す。ブラインド領域こそ突破の高費用対効果区。

### 高対話(アラートを引き起こしやすい)vs 低対話、どちらを先に選ぶか
**Q1**: 二つの道がある。一つは動きが大きいが直接的(スキャン/ブルートフォース/exploit)、一つは秘匿だが遅い(受動収集/正規認証情報)。レッドチームの場面でどちらを先に行くか。
**A1**: 演習が検知スコアリングを計上するかを見る。ブルーチームがオンラインで検知点を計るなら、デフォルトで低対話優先。まずアラートをトリガーしない正規手段(既存認証情報、受動情報)で前進し、高対話動作は必要かつ露呈に値する時に残す。純攻防で秘匿を計らないなら、効率優先で高対話も構わない。
**Q2**: ある動作の「アラートコスト」をどう判断するか。
**A2**: 「正常挙動ベースラインから逸脱するか」で見積もる:正規認証情報で勤務時間に通常操作=低;大規模ポートスキャン、パスワードブルートフォース、メモリ注入、異常プロセス=高。各動作の前に「この動作はログでどう見えるか、攻撃に似ているか」を暗算する。似ているほど後回し。
**Q3**: 秘匿経路が遅すぎ、進捗が落ちるのが見える。高対話に転じて加速すべきか。
**A3**: 「露呈と速度の交換」が価値に合うかを天秤にかける。一回の高対話動作が決定的突破をもたらす(一発の exploit が直接重要システムを取るなど)なら、露呈は価値がある。単に少し時間を省くための定例動作なら、露呈で小さな得を交換しない。高対話動作は「チケット代に見合う」時にだけ使う。
**Q4**: ずっと低対話でいたのにブルーチームに発見されて足場を封じられた。秘匿路線も失陥した。どこへ方向転換するか。
**A4**: 「多点冗長 + より深い秘匿」へ:即バックアップ足場を発動する(前提は事前に敷いてあること)。さらに挙動をベースライン以下に抑える。コールバックチャネル、時間窓、より「正常な」アカウントを替える。発見されたのは現在の秘匿レベルが足りないのであり、秘匿戦略が間違いではない。もう一段ノイズを下げる。
**Q5**: 秘匿を極致までしても捕まるなら、逆に「速さで遅さを打つ」べきか。
**A5**: 臨界の場合はできる。秘匿が無意味になった(既に露呈/時間切迫)、「電撃戦」へ:秘匿を放棄し、最速最猛の手段で、駆除される前に最大戦果を取って証明する。秘匿は長く生きるため。長く生きられないと決まった時、速度と戦果が秘匿を圧倒する。

### 秘匿性 vs 速度の天秤
**Q1**: 各動作で「より秘匿だがより遅い」と「より速いがより騒がしい」を選ばなければならない。統一的な意思決定原則はあるか。
**A1**: 「現在段階 × 残り時間 × 既露呈度」の三因子を使う。初期未露呈かつ時間に余裕→秘匿で保命寄り;中期に突破が必要で時間中程度→動作価値に応じて高対話を時機で;末期または既露呈→速度が全てを圧倒。恒常の答えはない。段階とともに滑る重み。
**Q2**: 「既に露呈したか」をどう知り、重みを調整するか。
**A2**: 環境のフィードバックを観察する:足場が異常にオフラインでないか、アカウントがリセットされていないか、防御ポリシーが突然締まっていないか、ハニーポット兆候。これらの信号があれば露呈済みの可能性があり、重みは即速度へ滑る。信号がなくても絶対安全と仮定せず、定期的に「最小露呈テスト」で防御があなたを監視しているかを探る。
**Q3**: 秘匿と速度は二択でなく両立できるか。
**A3**: できる。「準備」で両立する:事前に遅くて秘匿な準備作業(情報収集、チャネル布設、認証情報蓄積)を十分にやる。手を打つ必要がある時に、速く正確に一撃できる。「速くて秘匿」な美しい操作の多くは、前期の秘匿蓄積に依存し、臨場の速遅の取捨ではない。
**Q4**: ひたすら速さを求めて早期露呈して遮られた。速度戦略が覆った。どう方向転換するか。
**A4**: 「秘匿再建 + 低速ペネトレーション」へ:秘匿モードに戻り、バックアップ足場で目立たず再建する。今回はリズムを落とし、各動作の露出面を計算してから動く。覆った教訓は「当時実は秘匿余量があったのに使わなかった」。方向転換は使わなかった余量を使うこと。
**Q5**: ひたすら秘匿を求めて進捗ゼロになったら、またどうするか。
**A5**: 「計算された露呈」へ方向転換:価値が最も高い一つの動作を選び、その露呈コストを受け入れ、この一撃に集中して突破を求める。秘匿過剰の問題は「決して手を出さない」。方向転換は「価値ある一回の手出しを精選する」こと。秘匿は手段であって目的ではない。ゼロ産出の秘匿は失敗に等しい。

### 複数の認証情報を見つけた。どれを先に使い、どこを打つか
**Q1**: 一度に複数組の異なる出所の認証情報(ローカルアカウント、ドメインアカウント、サービスアカウント、アプリケーション設定内のもの)を得た。どれを先に使うか。
**A1**: 「権限階層 × 適用範囲 × 再利用可能性」で並べる。ドメイン管理者/ドメインサービスアカウント > ローカル管理者 > アプリケーション/データベースアカウント > 一般ドメインユーザー。同時に認証情報の「新鮮度」と「出所」を見る。高権限マシンから dump した、設定ファイルに平文のものは往々にして再利用性が強い。先にレバーが最大の一つを試す。
**Q2**: 某認証情報がどのドアを開けられるか不確か。乱撒せずにどう効率よく試すか。
**A2**: 先に「検証」してから「使用」する:各認証情報に一度の目立たない有効性検証を行う(単点認証、スプレーしない)。生きていて権限が期待通りか確認する。有効な認証情報について横展開経路を計画する。真偽不明の認証情報の一群をあちこちぶつけず、まず「確かに使える」サブセットに仕分ける。
**Q3**: サービスアカウントの認証情報(SPN を持つ可能性)に特別な用法優先度はあるか。
**A3**: サービスアカウントはその「オフライン解析」と「委任濫用」価値を優先考慮する:Kerberoast できるならオフラインで平文を割り、平文を得れば再利用性が極めて強いことが多い;委任が設定されていれば、直接他人を詐称して重要サービスにアクセスできるかもしれない。サービスアカウントの価値は往々にしてログインではなく、Kerberos における特殊な地位にある。
**Q4**: 全ての認証情報を試し尽くし、再利用横展開が全てログインできない。認証情報路線が遮断された。どこへ方向転換するか。
**A4**: 「認証情報の間接価値」へ:マシンにログインできなくても、認証情報は①認証後情報収集(ドメイン列挙、ACL 分析で設定ミス探し)、②非ログイン型リソースへのアクセス(メール、共有、クラウド、コードリポジトリ、VPN ポータル)に使える。多くの認証情報の価値は SMB/RDP ログインではなく、それが読めるデータと照らす権限トポロジにある。
**Q5**: 認証情報の間接価値も絞り尽くしたら。
**A5**: 「新しい認証情報の製造」へ戻る:既存の任意の足場で再 dump(前回権限不足で漏れた可能性)、セッションを釣る、キーロガー/認証情報キャプチャを配置して管理者ログインを待つ。旧認証情報を使い切った時、新認証情報は「翻して探す」でなく「待ち伏せ」で得る。収穫から網張りへ。

### オフライン解析 vs オンラインブルートフォース、どう選ぶか
**Q1**: 某アカウントのパスワードが欲しい。オフラインで hash を割る(Kerberoast/dump した hash)ことも、オンラインでログイン API をブルートフォースすることもできる。どちらを先に行くか。
**A1**: hash があってオフラインで割れるなら、絶対にオンラインでブルートフォースしない。オフライン解析はアラートなし、ロックリスクなし、膨大な試行が可能。オンラインブルートフォースは騒がしく、ロックとブロックを引き起こしやすい。hash を取ってオフラインに転じられる経路(Kerberoast、AS-REP roast、dump SAM/NTDS/LSASS)を優先する。
**Q2**: オフラインで長く割っても割れない(強いパスワード)。オンラインに転じるべきか。
**A2**: 先にオンラインに転じず、先にオフラインを最適化する:より的を絞った辞書(対象組織の情報に基づきカスタマイズ)に替え、ルール変形を加え、計算力/GPU を上げる。オフラインで割れないのは通常「辞書が合わない」のであり「方法が合わない」のではない。オンラインブルートフォースは強いパスワードに対して同じく割れず、さらに露呈とロックが増える。良い代替ではない。
**Q3**: オンラインブルートフォース/スプレーが合理的な選択になるのはいつか。
**A3**: ①hash が全く取れずオフライン不能、かつ②対象のロックポリシーが緩いか探明でき、かつ③高信頼の少数候補パスワード(デフォルト/季節+年/企業慣用など)がある時。この時「パスワードスプレー」(多アカウント、各少数試行)を使い、「単アカウントへの暴力ブルートフォース」を使わない。ロックしきい値の下で、高信頼パスワードを低頻度で試す。
**Q4**: オフラインで割れず、オンラインはロックが怖い。パスワードのこの道が全体として遮断された。どこへ方向転換するか。
**A4**: 「パスワードを迂回する」次元へ:パスワードを割らず、pass-the-hash/pass-the-ticket で hash/チケットを直接使い認証する(平文は不要)。またはパスワードなしのチャネルを行く。Kerberos 委任濫用、証明書認証(ADCS)、token 窃取、セッションハイジャック。現代 AD では、パスワードを知らなくても身分を詐称できる。
**Q5**: hash/チケットも取れず迂回できないなら。
**A5**: 「より弱い別のアカウントから入る」へ方向転換:この強いパスワードのアカウントを割るのに執着しない。内部ネットワークには必ず弱いパスワードのアカウントか、設定が平文を漏らすアカウントがある。最も弱い一環から割り入り、それで横展開/権限昇格して、その強いアカウントが触れるリソースに届く。パスワード割りは柔らかいものを選んで割り、最も硬いものに執着しない。

### exploit 開発に投入するかを決める
**Q1**: 疑わしい脆弱性を見つけたが既成 exploit がない。自分で exploit を書くべきか。
**A1**: 高いハードルの意思決定。デフォルト傾向は「書かず、先に迂回」。自研 exploit は高時間、高不確実の投入。先に「exploit を書かない代替経路」を尽くす:別の脆弱性、別の入口、別の対象。①これが唯一の経路で ②対象価値が極めて高く ③あなたが実行可能性は十分と判断した時だけ、開発に投入する。
**Q2**: 一つの脆弱性が「武器化に値する」かをどう素早く評価するか。
**A2**: 三点を評価:脆弱性種の利用難度(情報漏えい/コマンドインジェクションは易、メモリ破壊は難)、利用プリミティブの強さ(実行フロー/読み書きを安定制御できるか)、および参考にできる公開の類似利用があるか。「利用できるか」自体を長時間研究しないと分からないなら、費用対効果は通常非常に低い。慎重に入る。
**Q3**: 投入を決めた後、この「深い穴」が全時間を飲み込まないようどう制御するか。
**A3**: 段階別にマイルストーンゲートを設ける:先に「脆弱性がトリガーできる」(クラッシュ/異常)を証明、次に「制御できる」(実行/データに影響)を証明、最後に「安定利用」。各段階に時間上限を設け、期限にマイルストーンに達しなければ損切りする。底なしの穴をゲート付きの階段に切り、いつでも体裁よく撤退できる。
**Q4**: exploit を半分書いたところで難しすぎ/不安定と分かり、穴が深くて這い出せない。どこへ方向転換するか。
**A4**: 「メモリ級の精密利用」から「ロジック級の荒い利用」へ:多くの対象は高難度 exploit を書かなくても、同一ソフトの設定欠陥、ロジック脆弱性、既知弱点の組み合わせに退けばよい。全く別の対象へ転じることもできる。この脆弱性が打てないからといって、他所に低い位置の果実がないとは限らない。沈んだ研究時間は撤退判断に参加させない。
**Q5**: この exploit が確かに唯一の経路で、しかも書けない場合は。
**A5**: 能力/時間の境界を認め、「目標を下げる」か「迂回」へ:別の層から部分目標を達成する(権限でなくデータを取る、本システムでなく隣接システムを取る)、または「より多くの時間/リソースが必要な長期項」とマークし、現在の制約下で取れるものを取る。噛めない exploit 一つで全体の行動をゼロにしない。

### 外向き通信が制限された。先に外向き通信を解決するか先にローカル権限昇格するか
**Q1**: shell を取ったが、対象の外向き通信が制限されている(コールバックが出られない)。先に外向き通信を何とかするか、先にローカルで権限昇格/収集するか。
**A1**: まず「現在の shell の能力内」で、外向き通信に依存しないことを済ませる:ローカル情報収集、ローカル権限昇格、認証情報読み取り、内部ネットワーク到達可能性確認。これらは外向き通信不要。ローカルの価値を絞り尽くしてから、「外部送信/コールバックが必須か」で外向き通信をわざわざ攻略するかを決める。
**Q2**: どの場合、外向き通信を優先解決しなければならないか。
**A2**: 後続動作が外部ツール/C2 に強く依存する時(大型ツールの転送が必要、対話型制御が必要、データの帯域外が必要)。数命令の実行だけなら、既存の半対話 shell で足りる。急いで全機能の外向き通信チャネルを建てる必要はない。「次のステップが外向き通信を本当に必要とするか」で優先度を決める。
**Q3**: 外向き通信がどこまで制限されているかを低コストでどう探るか。
**A3**: 層ごとに試す:外部 IP へ直連(別ポート)、DNS 経由で出る、HTTP(S) でプロキシ経由で出る、ICMP 経由。多くの環境は特定プロトコル/ポート/プロキシ経由だけを放行する。「どの縫い目が通じるか」を把握してから的を絞ってチャネルを建てる。「完全に外向き通信しない」と仮定してコールバックを放棄しない。
**Q4**: 各種の外向き通信プロトコルを全て試して全封。徹底的に外向き通信しない。どこへ方向転換するか。
**A4**: 「内部ネットワーク中継」次元へ:現在のマシンが直接外向き通信することを追求せず、それを内部ネットワークノードとして、既に外向き通信できる別のマシンで中継/ポートフォワード/socks プロキシして出す。外向き通信は「内部ネットワーク全体に出口が一つあればよい」問題で、各台が出られる必要はない。出口マシンを見つけて踏み台にする。
**Q5**: 内部ネットワーク全体が厳格に外向き通信しないなら。
**A5**: 「オフライン作業 + 秘匿帯域外」へ:リアルタイム C2 を放棄し、コールバックなしのローカル操作(命令は入力チャネルで下達、結果は区切ってエンコードし、許可されたチャネルで低速帯域外、DNS/合法業務チャネルなど)に替える。または成果を物理的/論理的に触れられる位置に足場確保する。極端な隔離環境では「リアルタイム制御」から「オフラインペネトレーション」の心構えに転じる。

### 見慣れない新技術スタックを打つか
**Q1**: 対象が私の見慣れない技術/フレームワーク/プロトコルを使っている。頭から研究するか、迂回するか。
**A1**: まず「素早い実行可能性偵察」をする:少し時間をかけてこの技術スタックの既知脆弱性類とよくある弱点を検索する(どんな技術にも典型弱点パターンがある)。成熟した攻撃面(某類のデフォルト設定、某類のインジェクション)があれば、投入して学ぶ価値がある。真っ白なら、迂回して見慣れた柔らかい対象を優先探す。
**Q2**: 見慣れない技術の攻撃切り口をどう素早く見つけるか。
**A2**: 「技術無関係の汎用弱点」で切り込む。スタック全体をゼロから学ぶのでなく:どんな技術にもデフォルト認証情報、未認可 API、インジェクション、SSRF、デシリアライズ、設定漏えいがあり得る。まずこれらの汎用視点で一回スキャンする。往々にしてその技術に精通しなくても汎用類脆弱性を見つけられる。
**Q3**: 投入して学ぶ価値があるかないかの線引きはどこか。
**A3**: 「この技術が対象へ通じる必須関門か」および「学ぶ時間 vs 迂回する時間」を見る。迂回しても別の道があるなら、学ばない。それが唯一の咽喉で価値が高いなら、学習投入は価値ある戦略投資。「好奇心駆動」と「目標駆動」の学習を区別する。
**Q4**: この見慣れない技術を研究投入したが短期突破できない。新技術に遮られた。どこへ方向転換するか。
**A4**: 「見慣れた隣接面」へ:見慣れない技術のシステムには、往々にしてあなたが見慣れたコンポーネント(下層 OS、依存データベース、前置プロキシ、認証層)がある。あなたが分かるその層を攻め、分からないその層を迂回する。見慣れない技術と正面から較量せず、その見慣れた弱点の側面から入る。
**Q5**: 環境全体が見慣れない技術スタックなら。
**A5**: 「人と設定」という技術横断の汎用次元へ:いくら見慣れない技術も人が設定し運用する。弱いパスワード、設定ミス、漏えいした認証情報、運用習慣は技術横断で汎用。技術が新しくても、人間性と運用の手抜かりは変わらない。技術無関係の層から手を下し、技術壁を回避する。

### CTF flag 指向 vs 実戦権限指向の優先度差異
**Q1**: これは CTF/旗取り式スコアリングか実戦式権限スコアリングかを意識すべき。両者の優先度は違うか。
**A1**: 違う。必ず先にスコアリングルールを把握してから並べる。flag 指向:「flag を最短で取る経路」を最適化し、無関係の権限昇格/横展開は全て無駄。flag のある場所に専念。権限/実戦指向:「権限の深さとカバーの広さ」を最適化し、永続化、横展開、秘匿が全て加点。スコアリングモデルを間違えると無関係な動作で時間を無駄にする。
**Q2**: flag 指向の下で優先度をどう並べるか。
**A2**: 逆算思考:flag が通常どこに隠れるか(高権限ディレクトリ、データベース、特定ユーザーのホームディレクトリ、設定)から必要な最低権限を逆算し、その権限を取るのに必要な動作だけをする。root が不要で読める flag なら権限昇格しない。横展開が不要で取れるなら拡散しない。全ては「flag に届く」という唯一目標に奉仕。
**Q3**: 実戦権限指向の下ではどう並べるか。
**A3**: 「権限価値 + カバー + 堅固さ」で並べる:先に重要権限(ドメインコントローラ/中核システム)、次に横展開でカバーを広げ、さらに永続化で堅固さを保つ。過程で秘匿に注意し検知点を減点されない。「どれだけ制御するか、どれだけ深く、どれだけ安定か」が全て点数。flag 指向のように一路突き抜けて他を顧みないのとは違う。
**Q4**: flag 指向の打法(直取)で実戦スコアリングが非常に低いと分かった。戦略が偏った。どこへ方向転換するか。
**A4**: 「広さと縦深を並重」へ:一路直突を止め、戻って横展開カバーと永続化を行い、「一点を取る」を「一片を制御する」に広げる。スコアリングモデルが戦略を決める。打法とスコアリングが合わないと分かったら、即スコアリング重みで動作優先度を並べ直す。間違った成功基準で続けない。
**Q5**: スコアリングルールが不明/両方必要な場合は。
**A5**: 「先に最低限確保、後に加点」戦略:先に最短経路で確定的成果(一つの flag/一つの足場)を取り最低限を確保し、残り時間でより高リスクの深さ/広さ動作に投入して加点を博す。ルール不明時、確実な最低限点が常に不確実な高点より優先。

### 内部ネットワーク複数セグメント、先にどのセグメントを打つか
**Q1**: 踏み台を得た後、内部ネットワークに複数のセグメントがある。先にどのセグメントを探り/打つか。
**A1**: 「セグメント命名/アドレス規則から価値を推測」で優先度を並べる。通常、サーバーセグメント、管理セグメント、DMZ、オフィス端末セグメントで価値と防御が違う。「現在の足場が直接ルーティングでき、かつ中核アセット(サーバー/DB/AD)を含む可能性のある」セグメントを優先探る。先に到達可能性を探り、到達不能なセグメントは先に置く。
**Q2**: 全ネットワークを驚かせずに各セグメントの価値をどう判断するか。
**A2**: 目立たずに探る:まず本機のルーティングテーブル、ARP キャッシュ、hosts、既存接続レコードから「受動的に」活発なセグメントと重要ホストを識別し、次に重点セグメントを狭い範囲で重要ポート(AD、DB、管理サービス)を探る。最初から全セグメント大スキャンをしない。それは騒がしく遅い。既存情報で能動スキャンの範囲を縮める。
**Q3**: ある高価値セグメントが現在の踏み台からルーティング不能。どうするか。
**A3**: 到達不能は「ネットワーク経路」問題。先に「そのセグメントへ行けるマシン」を二段踏み台として探す。マルチ NIC ホスト、踏み台マシン、そのセグメントへの接続レコードのあるマシン。多段 pivot で触れる。セグメント隔離は「二つのセグメントを跨ぐ」マシンを探して突破する。「現在位置から硬接」しない。
**Q4**: 重点攻めしたセグメントをスキャンすると全て低価値端末/突破口なし。セグメントを選び間違えた。どこへ方向転換するか。
**A4**: 「アドレスセグメントでなく、認証情報と信頼に従う」へ:現在のセグメントのマシンがどこへ接続しているか(その接続、マウント、認証情報がどのセグメントを指すか)を見る。それらの「接続先」セグメントこそ中核。アドレスセグメントの価値判断は間違うかもしれないが、トラフィックと信頼関係は騙さない。それに従って真の中核セグメントへ転じる。
**Q5**: 全到達可能セグメントが低価値で、中核セグメントが完全隔離で入れない。どこへ方向転換するか。
**A5**: 「隔離の合法突破点を探す」へ:厳格に隔離された中核セグメントには必ず合法の管理/業務チャネル(踏み台/要塞ホスト、特定サービス、データ同期)が出入りしている。これらの「承認された門」を探す。「壁越え」ではない。同時に中核セグメントの運用者/管理端末を考える。彼らのマシンは合法に中核セグメントへ入れる。彼らを取れば経由できる。

### ドメイン管理者を取得済み。次の目標の並べ方
**Q1**: ドメイン管理者権限を得た。次にどんな順序で動き、でたらめに掴まないか。
**A1**: ドメイン管理者は手段であって終点ではない。「堅固→目標→カバー」で並べる:①先に堅固さを確保(ドメイン級アクセスを永続化し、蹴られないように)、②スコアリング/タスクが要求する中核アセット(データ、特定システム)を直取、③必要に応じてカバー拡張。ドメイン管理者を取ったらすぐあちこち乱翻しない。先にこの高地を固定してから収穫を計画する。
**Q2**: ドメイン管理者を取った後、リセットされて蹴り出されないようどう素早く堅固にするか。
**A2**: 「単一認証情報に依存しない」永続化を建てる:ドメイン級永続手段(ゴールデンチケット素材、DCSync 能力、複数のバックドアアカウント/委任)を掌握すると同時に、全ての希望を、変更されるかもしれない一つのパスワードに押し付けない。ドメイン管理者パスワードはいつリセットされるか分からない。永続化は認証情報のローテーションに耐えられなければならない。
**Q3**: ドメイン管理者があれば、全対象が手の届くところにあり、でたらめに打てるか。
**A3**: そうではない。ドメイン管理者 ≠ 「全ネットワーク食べ放題」:独立ドメイン/フォレスト、非ドメインアセット(ネットワーク機器、Linux、クラウド、隔離システム)、追加保護のある特権システム(PAW、階層管理)はドメイン管理者にカバーされないかもしれない。ドメイン管理者を取った後、「まだ届かないもの」を再棚卸しし、これらを単独で計画する。ドメイン管理者を取れば万事解決と思わない。
**Q4**: ドメイン管理者を取ったのに、真の中核データが、ドメイン管理者も入れない隔離システムにあると分かった。詰まった。どこへ方向転換するか。
**A4**: 「人と管理チェーンから手を下す」へ:隔離システムがいくら独立していても、人が管理し、データの流入出がある。ドメイン管理者権限でその管理者を監視/特定する(彼のマシンはあなたが制御できる)、彼の隔離システムへのセッション/認証情報をハイジャックする。またはデータ同期/バックアップチェーンから間接的にデータを取る。ドメイン管理者の価値は「管理者の必経路に待ち伏せできる」こと。
**Q5**: タスクが実はドメイン管理者不要なのに、大きな力をかけて取った。これは偏りか。
**A5**: 対象データがより低い権限で取れるなら、確かに過度投入。教訓は「常に最終目標が必要とする最低権限に合わせる」。この時、即目標自体に戻り、手元の高権限で直接、素早く本当の目標を達成する。ドメイン管理者でできる見せびらかし動作に耽溺し続けない。

### 脆弱性がチェーン利用を要する。組み立て価値の判断
**Q1**: 単一脆弱性では対象を取れず、いくつかの中低危険を一本のエクスプロイトチェーンに繋ぐ必要がある。組み立てる価値があるか。
**A1**: 「チェーンの長さ × 各環の安定性 × 終点の価値」を見る。短いチェーン(2-3 環)で各環が安定し、終点が高価値なら、価値がある。長いチェーン(多環)で一部の環が脆い/苛酷な前置条件が必要なら、期待成功率が環ごとに掛け合わされて非常に低くなる。往々にしてより短い道を探す方がまし。
**Q2**: 一本のエクスプロイトチェーンの全体成功率をどう評価するか。
**A2**: 各環の成功確率を掛け合わせる。三環各 80% で約 50% しか残らない。五環各 80% で約 33% 残る。チェーンが長いほど、各環が見た目頼もしくても全体は脆い。評価時、各環で最も脆い「運/タイミング次第」の段階に特に警戒する。それがチェーン全体の急所。
**Q3**: 長いチェーンの組み立てを決める前に、失敗リスクをどう下げるか。
**A3**: 先に「逐環独立検証」してから直列にする:各環が隔離条件下で実行可能なことを個別に確認してから組み合わせる。チェーン全体を一度に組んでからテストしない。それだと失敗時にどの環で断たれたか分からない。逐環検証は弱い段階を特定でき、早期に「このチェーンは根本的に通らない」と気づいて適時損切りもできる。
**Q4**: チェーン組み立てがある環で固着して接続できない。チェーン全体が断たれた。どこへ方向転換するか。
**A4**: まず断たれたこの環が「等価の段階で代替」できるか(同じ中間状態に達する別の手段)を見る。できれば補って続ける。できなければ一歩引いて「本当にこの完全なチェーンが必要か」を問う。全く別の、より短い攻撃経路へ方向転換する。念入りに設計したチェーンを通すために些末な点に固執しない。チェーンは手段であって目的ではない。
**Q5**: 確かにより短い道がなく、長いチェーンも組めない場合は。
**A5**: 「チェーン終点の要求を下げる」へ:最終目標まで全チェーンを歩く必要はないかもしれない。チェーンの途中のある状態が既に価値ある部分成果(一部データを読む、ある認証情報を取る)を産出できる。チェーン上で「既に安定到達できる最遠点」の成果を懐に入れる。全行程を歩き切って粒なしに終わるよりまし。

### ソーシャルエンジニアリング/フィッシング vs 技術突破の費用対効果
**Q1**: 外部突破が非常に硬い。ソーシャルエンジニアリング/フィッシングへ転じることを考えている。どう天秤にかけるか(ソーシャルエンジニアリング許可の前提)。
**A1**: 「技術攻撃面が非常に硬いところまで収束し、人の攻撃面にまだ触れていない」時、ソーシャルエンジニアリングの費用対効果が往々にしてより高い。一通の成功したフィッシングが直接内部ネットワークの足場と本物の認証情報を与え、全ての外部防御を迂回するかもしれない。技術突破が長く壁に当たった後、人の次元は往々にして未利用の高リターン直交方向。
**Q2**: ソーシャルエンジニアリングにも多くの形式がある。どれを先に使うか。
**A2**: 「投入産出と秘匿」で並べる:先に人に接触しない「情報型ソーシャルエンジニアリング」(公開漏えい、従業員のデジタル足跡、パスワード漏えいライブラリ照合)。ゼロリスク高リターン。次に低接触フィッシング(メール)、最後に高接触(電話/物理)。後者はリスクとハードルが高い。受動情報ソーシャルエンジニアリングから能動接触へ昇格する。
**Q3**: ソーシャルエンジニアリングが「投入価値がある」か、時間を無駄におとりを作るだけかをどう判断するか。
**A3**: 対象組織の「人因露出面」を見る:従業員が膨大か、公開メールフォーマットがあるか、認証情報漏えい履歴があるか、セキュリティ意識のトレーニング程度。露出面が大きく、意識が弱い組織はソーシャルエンジニアリング命中率が高く、投入価値がある。逆に警戒が固く、従業員が少ない対象は、ソーシャルエンジニアリングの投入産出が技術脆弱性の掘り続けより劣るかもしれない。
**Q4**: フィッシングを送っても誰も引っ掛からない。ソーシャルエンジニアリングのこの線も黄色になった。どこへ方向転換するか。
**A4**: 「技術面 + ソーシャルエンジニアリングの情報副産物」へ戻る:誰もフィッシングをクリックしなくても、前期のソーシャルエンジニアリング収集の情報(従業員名、メール、組織構造、技術スタック)は技術突破に還元できる(パスワード辞書のカスタマイズ、重要人物の対外システム特定)。ソーシャルエンジニアリングの情報価値はフィッシングの成否から独立。それで技術攻撃を武装してもう一ラウンド打つ。
**Q5**: ルールが一切のソーシャルエンジニアリングを禁止するなら。
**A5**: それなら「ソーシャルエンジニアリング思考」を純技術アセットに使う:「内部者の視点」を模して、従業員/運用の利便性のために開いた弱防御の入口(セルフサービスポータル、VPN、メール、協働プラットフォームの弱いパスワード)を探す。人に接触しないが、「人に奉仕するシステム」を攻める。これらのシステムは人を便利にするため、技術防線の中で最も柔らかい部分であることが多い。

### パッチ全の新マシン vs 老朽マシン、先にどちらを打つか
**Q1**: 内部ネットワークに維持の良い新システムと年久しく失修の老朽システムがある。先にどちらを打つか。
**A1**: 先に老朽システムを打つ。老朽システム = 既知脆弱性が多く、パッチ欠落、弱い設定、忘れられている。それらは「確定的な足場」で、取る費用対効果が全パッチの新システムを噛むよりはるかに高い。老朽システムを踏み台と認証情報源にし、内部からそれらの新システムに届く。
**Q2**: 内部ネットワークで「老朽の柔らかい果実」をどう素早く識別するか。
**A2**: OS バージョン、サービスバージョン、最終ログイン/更新時間、命名(test/old/backup/臨時)を見る。サポート終了の旧システム、テスト残存、シャドー IT が重点。これらのシステムは往々にして誰も管理せず、パッチフロー外で、監視重点外でもある。一挙両得。
**Q3**: 老朽システムは打ちやすいが、横展開価値がない(孤島)のではないか。
**A3**: 評価すべき。一部の老朽システムは孤立した死角(打っても無用)、一部の老朽システムはまさに中核区に横たわり信頼されている(古いドメイン内サーバー、古い運用ツール)。「古くてドメイン内/古くて中核に信頼されている」を優先打ち、「古くて孤立」を避ける。古さは攻略しやすさ、重要経路上にあるかは価値。両方を見る。
**Q4**: 老朽システムを全て打ち終え、残りは全てパッチ全の新システムで噛めない。どこへ方向転換するか。
**A4**: 「脆弱性利用」から「身分と信頼」へ:新システムはパッチ全でも合法認証は受けなければならない。老朽システムから dump した認証情報、チケットで新システムにログインする。それがいくら新しくても有効なドメイン認証情報は防げない。新システムの弱点はコードではなく「それが信頼する身分」にあり、その身分はあなたが既に取った老朽システムに存在するかもしれない。
**Q5**: 新システムが認証情報再利用にも防御した(階層/MFA)なら。
**A5**: 「その依存と管理面を攻める」へ:いくら厳しい新システムも下層インフラ(仮想化、ストレージ、バックアップ、ネットワーク、認証サービス)と管理チャネルに依存する。その足下のインフラ、またはそれを管理するシステムを攻め、下方または側面からそれを取る。防御がアプリケーション層に集中するほど、インフラ層はブラインド領域である可能性が高い。

### 敏感データ点(DB/ファイルサーバー)の優先度
**Q1**: 内部ネットワークのデータベース、ファイルサーバー、コードリポジトリという「データ金鉱」と一般ホスト。それらにどんな優先度を与えるべきか。
**A1**: 最終目標がデータなら(多くの実戦/演習はそう)、データ金鉱は最終目標で、「それを中心に逆算計画」すべき。ただし必ずしも「最初に打つ」のではない。先に打つのは「私にデータ金鉱へ入る鍵を与える」マシン(管理者、アプリケーションサーバー)。データ点は目的地。経路計画はそれを錨にし、実行時はまずそれへの鍵を取る。
**Q2**: 複数のデータ点、先にどれを取るか。
**A2**: 「データ価値 × 到達可能性 × 防御強度」で並べる。スコアリング/タスクが明確に要求するデータが最優先;次に認証情報/キー類データ(取ればより多くのドアを開ける、乗法);さらに到達可能で防御が弱いもの。頭から防御最強の中核ライブラリに突っ込まず、先に能力を広げる「鍵型データ」を取る。
**Q3**: DLP/監査をトリガーせずにデータ点に接触するには。
**A3**: 先に「読み取り専用偵察」で価値を確認してから取る:ライブラリ/共有に確かに目標データがあるか、データ量、暗号化の有無を確認してから帯域外方式を決める。盲目的に大量のライブラリを引き抜かない。それは DLP と監査アラートをトリガーする。先に小範囲で価値を検証し、高価値データには目立たず、バッチで、必要最小限の方式で接触する。
**Q4**: データ点に届いたがデータが暗号化/追加キーが必要。取っても使えない。詰まった。どこへ方向転換するか。
**A4**: 「暗号を破るのでなくキーを探す」へ:暗号化データの価値はキーに閉じ込められており、キーは往々にしてすぐ傍にある。アプリケーションサーバーの設定、KMS、キー管理システム、開発者マシン、コードリポジトリ。キーを取りに方向転換し、暗号アルゴリズムを硬く破らない。データが暗号化された時、攻撃対象は「データ」から「キーの保管場所」に移る。
**Q5**: キーも取れない。暗号化データのこの線が徹底的に通らないなら。
**A5**: 「データの他の形態と位置」へ:同じデータが未暗号化の形態で他所に存在するかもしれない。バックアップ、キャッシュ、ログ、レポート、下流システム、平文エクスポート、メモリ中。データは一箇所で暗号化されても、その全てのコピーが暗号化されているとは限らない。暗号化された主ライブラリを迂回し、保護されていないその影のコピーを探す。

### いつスクリーンショット証拠/成果足場確保 vs 前進継続をするか
**Q1**: 価値ある成果(shell/認証情報/データ)を取ったばかり。すぐ証拠足場確保するか、勢いのまま深入りするか。
**A1**: まずごく短時間「既得成果を固定」してから前進する。レッドチームで「取ったが証明していない/保っていない」は取っていないに等しい。素早くスクリーンショット/重要証拠を記録し、足場の永続化を確保する。この数十秒の投入は、後続操作の失敗や駆除で成果が蒸発するのを防ぐ。固定してから安心して深入りする。
**Q2**: 証拠/永続化の動作自体が露呈を増やし、逆に悪くならないか。
**A2**: 天秤にかける:軽量証拠(スクリーンショット、記録)はほぼ追加露呈なしで、即やる価値がある。重永続化(ファイル足場確保、バックドア設置)には露呈コストがある。この足場の価値と駆除リスクを見る。高価値+高駆除リスク→冒険して固定する価値がある。低価値→軽く記録するだけ。小さな成果のために重い動作をして露呈を招かない。
**Q3**: 深入りが現在の成果を失うかもしれない(権限昇格クラッシュ、誤操作)。どうバランスするか。
**A3**: 「高価値の不可逆動作の前に先にアーカイブ」を守る:制御不能を引き起こし得る動作(カーネル exploit、アラートをトリガーし得る大動作)の前に、まず現在の成果の証拠とアクセスを固定する。そうすれば最悪の場合、証明済みの成果に戻れる。ゼロに戻らない。アーカイブは深入り冒険の命綱。
**Q4**: 前進だけに専念して適時証拠を取らなかった結果、足場が駆除され、成果に証拠がない。どう補救して方向転換するか。
**A4**: 「再建 + 即固定」へ:バックアップ足場か再攻撃で戻り、今回は一取ったら先に証拠を取る。再建できないなら、既存の間接証拠(ログ、記録、中間産物)を整理してなるべく裏付ける。教訓をルールに変える:以降、各マイルストーン成果は「先に証明、後に前進」。証拠を前進より前に置く。
**Q5**: 時間が迫り、証拠と前進のどちらかしか選べない。どちらを選ぶか。
**A5**: 証拠で既存成果の最低限を確保することを選ぶ。「もう一歩の成果価値が現在よりはるかに高く、かつ高確率で取れる」場合を除く。手にした確定成果 > 不確実なより大きな成果。演習スコアリングはあなたが証明できるものしか認めない。いくら遠く前進しても、証拠がなければゼロ。確実性が貪欲より優先。

### 複数 agent/複数線並行時のタスク割り当て
**Q1**: 複数の線を並行推進できる(または複数の実行ユニットがある)。無駄なく、衝突なくどう割り当てるか。
**A1**: 「直交性」で割り当てる:並行の線に、互いに依存せず干渉しない直交次元(一本は web、一本はネットワークサービス、一本は情報収集)を歩かせる。複数の線が同じ対象・同じ入口に集中し、互いに干渉してアラートを重複トリガーするのを避ける。並行の価値は異なる次元をカバーすること。同じ事を複数回やることではない。
**Q2**: 限られた精力/計算力の下、並行は何本が最適か。
**A2**: 並行数は多ければ多いほど良いわけではない。一本増えるごとに文脈切り替えと管理コストが増える。「現在の期待リターンが最も高い少数(2-3)」を選んで並行し、残りはキューに入れる。リソースを高期待の線に集中する方が、十本の低期待の線に撒くより速く成果が出る。
**Q3**: 並行の数本の線の間で互いに餌を与えられる情報を発見した。どう協働するか。
**A3**: 「共有インテリジェンスプール」を建てる:一本の線が得た認証情報、内部ネットワーク地図、フィンガープリントを即共有し、他の線が再利用する。並行の最大の見返りは「一本の線の副産物が別の線の突破口になる」こと。並行を情報孤島にしない。協働再利用こそ並行の乗数効果。
**Q4**: 並行の全ての線がそれぞれ詰まり、全面停滞。どこへ方向転換するか。
**A4**: 「集約して並べ直す」へ:並行を止め、各線が積んだ情報を一つに集めて一度の全体分析をする。単独で見ると各線は行き止まりでも、合わせると各線の断片情報が新しい経路を一本組み上げるかもしれない。全面停滞は往々にして道がないのではなく、道が線を跨ぐ情報の組み合わせに隠れている。並行実行から集中分析へ切り戻す。
**Q5**: 集約後も道がない。戦線を縮小すべきか。
**A5**: すべき。「集中兵力の単点突破」へ:低期待の多線並行を放棄し、全リソースを唯一の最も見込みのある線に押して深掘りする。並行は広さ探索期の戦略。広さ探索が「至る所壁」を証明したら、集中突破期に入り、最もあり得る一点に All in する。

### 全面固着。体系的に優先度を並べ直す
**Q1**: 既知の全ての発想を試し尽くし、徹底的に固着した。でたらめに当てずっぽうせず、どう体系的に優先度を並べ直すか。
**A1**: 一度の「ゼロリセット振り返り」をする:既知の全て(アセット、サービス、認証情報、失敗レコード、成功レコード)をリストし、この対象を引き継いだばかりのふりをして、攻撃面地図を描き直す。固着は往々にして旧発想に嵌っていることが原因。強制的な「新人の視点」が、ずっと無視された入口を露出させる。
**Q2**: 振り返りで重点的に何の無視されたものを見つけるか。
**A2**: 四類のブラインド領域を体系的にスキャンする:①「打てない」と判定したが実は徹底調査していない対象;②収集したが深く分析していない情報(ログ、設定、コメントの手がかり);③途中で放棄した経路(当時前置が欠け、今は条件が揃った可能性);④一度も触れていない直交次元(ずっと技術で身分に触れていない、ずっとこの層で下層に触れていない)。
**Q3**: 並べ直した後の優先度に客観的根拠を与えるには、また感覚に頼らないようにするには。
**A3**: 各候補動作に「期待リターン(成功率×価値÷コスト)」を再採点する。特に「前回情報不足で過小評価した」動作を再評価する。今は情報が増え、その成功率が変わったかもしれない。更新後の情報で再計算し、古い直感の並びを踏襲しない。情報が変われば優先度も変わるべき。
**Q4**: 振り返り並べ直し後も新しい道が見つからない。本当に行き詰まった。最後にどこへ方向転換するか。
**A4**: 「境界拡大 + 攻撃層の変更」へ:現在の対象範囲を飛び出し、外へ広げる(関連アセット、サプライチェーン、クラウド、第三者、人員);下へ広げる(インフラ、ハードウェア、ネットワーク機器);組織へ広げる(フロー、運用習慣、忘れられたアセット)。本当の行き詰まりは極めて稀。多くは攻撃面を小さく囲いすぎている。境界の外こそ出路。
**Q5**: 境界も極限まで広げても突破できない。どう締めるか。
**A5**: 「能力/時間問題か、対象が確かに極めて硬いか」を正直に評価する。前者なら、最も見込みがあるがやり切れなかった経路を「次段階の優先攻撃リスト」に整理して引き継ぐ。後者なら、達成済みの成果と「対象がなぜ攻略困難か」の分析(それ自体価値ある防御インテリジェンス)を整理して出力する。固着時、明晰な損切りとインテリジェンスの沈殿が、それ自体一つの専門的な産出。
