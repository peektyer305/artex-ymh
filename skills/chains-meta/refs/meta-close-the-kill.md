# メタ意思決定 · 急所に着いたらまず締めくくる:shell を取れる位置で無駄に発散しない

> tags: 締めくくり, 急所, 発散, getshell, shell, webshell, 管理画面, テンプレート管理, アップロードポイント, インジェクションポイント, 足場, セッション, remember, 黒板, thrash

### 「急所」の識別:あなたは既に shell/flag を直接取れる位置に立っている
**Q1**: 何が「急所」にあたるのか。自分が既に締めくくりに入るべき位置に達したことを、どうやって知るのか。
**A1**: 急所 = あなたが【コード実行/ファイル読み書き/flag 取得に直接変換できる】プリミティブを既に握っており、あと一歩のところまで来ている状態。典型的な信号:①管理画面に入り、テンプレート管理/カスタムPHP/プラグイン編集が見える;②拡張子を検証しないアップロードポイントを見つけた;③スタック(stacked)SQLインジェクションがある、または into outfile に書き込める;④任意ファイル読み取りがあり、flag パスを読める;⑤コマンドを実行できる経路が既にある。これらを見たら【横展開の探索を止め】、それを shell/flag に変換することに集中する。
**Q2**: 管理画面のテンプレート管理ページに着いたが、まだ MySQL や試していない別の API もある。先に全部一通り触るべきか。
**A2**: 触らない。ここが最も失敗しやすい場所である。run の振り返りで、モデル t30 は SeaCMS の「テンプレート管理」(getshell の急所)の上に立っていたのに、引き返して CAPTCHA を破り、ソースコードを読み直し、70 手にわたり発散して予算を使い果たしても締めくくらなかった。既に入れるドアは、先に入って shell を手に入れてから、他のことを考える。急所を握っている時、発散 = 自殺。
**Q3**: では、どの程度まで発散するのが合理的か。
**A3**: 【現在の急所が確実に突破し尽くされた】と確認した後でのみ発散する(例:テンプレートディレクトリが書き込み不可で、他に書き込みポイントがない)。それまでは、全ての動作が「この一つのプリミティブを shell/flag にする」ことに奉仕すべき。判定基準:あなたの次の動作は【shell 取得に近づいている】のか【より多くの情報を集めている】のか。急所を握っていながら情報を集めているのは、方向を外している。

### 締めくくりの前にまず「入場券」を黒板に書き込む
**Q1**: 使える管理画面のセッション/cookie を手に入れるのに多くの手数を費やした。次に何をすべきか。
**A1**: 【まず最初に:remember】。セッション cookie(PHPSESSID=...)、管理画面のパス、デフォルトパスワード、CAPTCHA のバイパス方法を、すぐに黒板へ remember する。なぜなら文脈は Ralph によって圧縮・リセットされ、ウィンドウ内の cookie は無くなる時は無くなる。黒板に落とさなければ、圧縮後に最初から再ログインし、CAPTCHA を破り直すことになり、これまでの成果が台無しになる。
**Q2**: なぜウィンドウ内の記録に頼ってはいけないのか。今手に入れたものはまだ目の前にある。
**A2**: 「目の前」は消えるものだから。黒板は圧縮をまたいで失われない唯一の記憶であり、recall は任意のラウンド数をまたいで取り出せる。run の振り返り:モデルは全行程 0 回の remember で、同じ backup.zip を 38 回も読み直し、CAPTCHA を 29 回も破り直した。どれも、既に手に入れていたものを再導出していただけ。手に入れたら保存する。これは規律であり、選択肢ではない。
**Q3**: 以前読んだファイルを読み直していることに気づいた。これは何を意味するか。
**A3**: 文脈を失い、古い情報を再導出していることを意味する(ガードレールは「最近 N 回の出力が以前と重複している」と述べる)。読み直すのはやめ、このファイルから得た【結論】を remember する(原文ではなく結論:「アップロードポイントは X にあり、Y をフィルタリングしており、Z でバイパスできる」)。そして結論に基づいて次のステップへ進む。同じ内容を読み直しても新しい情報は決して得られない。

### 締めくくりの動作順序
**Q1**: 急所を握り、入場券も保存済みと確認した。締めくくりは具体的にどう進めるか。
**A1**: ①この一つのプリミティブを固定し、「それを shell にする」最短パスを書き出す;②実行し、実際のエコーを見る;③失敗したら【このプリミティブ】が何に阻まれているか(権限/フィルタリング/パス)を診断し、プリミティブを替えるのではなく、このプリミティブ内の攻め方を替える;④実行を取得したら、すぐに flag を読めるか/webshell を落とせるかを検証する;⑤成功したら足場を remember し、次の区間へ進む。
**Q2**: 締めくくりの途中で小さな障害に行き詰まった(例えばアップロードを一度遮断された)。すぐ対象を替えるべきか。
**A2**: 替えない。一度の失敗は終点ではなく手がかりである。拡張子のブラックリストか。content-type 検証か。パスが書き込み不可か。それを診断し、【同じプリミティブ】の中でバイパス方法を替える(拡張子変更/MIME 変更/ディレクトリ変更/二次レンダリング位置)。このプリミティブの全ての妥当なバイパス方法を試しても行き止まりの場合にのみ、次のプリミティブを探しに戻る。
