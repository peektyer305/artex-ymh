# メタ意思決定 · 次元を変える:直交パスの列挙

### 単一点への執着:いつ「次元を変えるべき」と判定するか
**Q1**: 同じインジェクションポイント/同じ脆弱性に長く磨いており、payload の変種を数十個も試しても進展がない。磨き続けるか、替えるか。
**A1**: まず「執着」にしきい値を設ける。レッドチームで最も高くつくのは失敗ではなく、同一次元上で情報利得なしに繰り返すこと。判定基準:連続 N 回の試行(経験上 15~25 回)で得られるレスポンス/エラーが完全に同質で、新しいステータスコード/長さ/タイミングの差異がない。これはこの次元の情報がやり尽くされたことを示す。方向転換すべき。「もうすぐ成功する」という感覚で延命しない。
**Q2**: 「あと一歩」と「根本的にこの道は通じない」をどう区別するか。
**A2**: 「信号勾配」の有無を見る。各試行でまだ微細な差異(エラーが変わった、遅延が変わった、挙動が分岐した)を観測できるなら、あなたは情報勾配を登っており、続ける価値がある。全ての入力が同一の出力に写像されるなら、勾配はゼロで平原。横の列挙は無意味。
**Q3**: 次元を変える前に何を残すべきか。
**A3**: 「保留マーカー」を一条記す:この点はどこで行き詰まったか、何を試したか、どんな条件で戻る価値があるか(例:「特定の類の認証情報を得たら戻って認証状態を試す」)。直交の方向転換は放棄ではなく、スケジューリング。
**Q4**: この道が徹底的に失敗/遮断された。どの直交次元へ方向転換するか。
**A4**: 「同一対象の別の属性軸」へ方向転換。ずっとこのサービスの「脆弱性利用」軸を攻めていたなら、「認証情報/設定/信頼関係」軸に切り替える。ずっとアプリケーション層なら、ネットワーク/プロトコル層に切り替える。ずっと技術面なら、人/フロー面に切り替える。要訣:変えるのは次元(軸)であり、同じ軸上のパラメータ値ではない。
**Q5**: 次元を変えるのが「あちこち飛び回ってどこも深くない」にならないようにするには。
**A5**: 「軸×深さ」マトリクスを維持し、各直交軸に限られたプローブ予算だけを与え、乱れ飛ばずローテーションする。まず全軸を浅く一巡して信号ランキングを取り、予算を信号最強の軸に注いで深く攻める。広さで道を探り、深さで突破する。

### 直交次元リスト:まず「どんな軸があるか」を列挙してから選ぶ
**Q1**: 対象を前に、どう体系的に「総計どの直交パスがあるか」を知り、思いつくままに打つのではないか。
**A1**: まず軸リストを建ててから動く。常用の直交軸:①攻撃面軸(ネットワーク/アプリケーション/プロトコル/依存/人)②手段軸(脆弱性利用/認証情報/設定エラー/信頼濫用)③層軸(ネットワーク/伝送/アプリケーション/ビジネスロジック)④時間軸(即時ブルートフォース/持久待機)⑤チャネル軸(帯域内/帯域外)⑥データ状態軸(伝送中/静止)⑦身分軸(現在の文脈/他のユーザー/サービスアカウント)。対象を各軸に一回投影する。
**Q2**: 軸が多すぎて打ち切れない。どれを先に打つか。
**A2**: 「情報の入手しやすさ × ROI」で並べる。「低コストで高信号を得られる」軸を優先して先に偵察投影する。最初から最も重い脆弱性利用軸に全額賭けない。
**Q3**: 二つの道が「本当に直交」か(名前を変えただけで中身が同じでないか)をどう知るか。
**A3**: 判定基準:道 A の失敗原因が道 B の失敗も引き起こすなら、それらは直交しない(同じ失敗根因を共有)。真に直交する経路は、成功が異なる前提に依存し、異なる防御を迂回する。例:同一 WAF の背後でエンコーディングを替える ≠ 直交(どちらも同一 WAF に管轄される)。WAF を通らないプロトコルポートに替えることこそ直交。
**Q4**: これらの軸を一巡スキャンして全く信号がない場合は。
**A4**: 「軸リスト」自体の次元が足りないことを示す。「メタ次元」へ方向転換:対象の境界を再び疑う。範囲の線引きが間違っていないか。本当の入口は対象の上流(CI/サプライチェーン)、隣接サイト、または運用/管理面にあるかもしれない。対象の定義を広げること自体が一回の次元変更。
**Q5**: 軸を丸ごと見落とすのをどう防ぐか。
**A5**: リスト法で強制的に一巡する。直感は、あなたの不得手な軸を体系的に無視する(Web 偏重の人は常にプロトコル/横展開/帯域外を無視する)。リストはブラインド領域に対抗するツール。

### 攻撃面:縦の深掘り vs 横の展開
**Q1**: 疑わしい機能点を発見した。その場で深く掘る(縦)か、先にアプリケーション全体の機能点を一巡する(横)か。
**A1**: 早期は横寄り、後期は縦寄り。偵察段階では先に横で全ての入口/パラメータ/API を列挙してグラフにし、「攻撃面地図」を建てる。全景なしで深掘りすると、次善の点位に頭から突っ込み、より柔らかい対象を見逃しやすい。
**Q2**: 横に展開する時、どの点が戻って縦に深掘りする価値があるかをどうマークするか。
**A2**: 各点に「異常スコア」を付ける:エラー漏えい、非標準のレスポンス、テンプレート/シリアライズの痕跡の疑い、タイミング異常、権限の不一致。異常スコアが高いものは縦のキュー前列に並べる。
**Q3**: 縦に掘る途中で詰まった。掘り続けるか横に戻るか。
**A3**: 「この点の理論上の天井」を見る。突破しても同権限の情報漏えいに過ぎず、横のキューに RCE/認証バイパスの疑いのある点がまだあるなら、横に戻るべき。埋没コストでなく潜在的リターンで決める。
**Q4**: 横に敷き終え、縦にも掘り尽くして通らない。どこへ方向転換するか。
**A4**: 「アプリケーション内の攻撃面」という平面から直交して「アプリケーション外の攻撃面」へ跳ぶ:同一ホストの他のサービス、隣接サイト、ホスト/コンテナ、CI/CD、運用チャネル。あなたはずっと二次元平面で探しており、出口は第三の軸(インフラの縦深)にあるかもしれない。
**Q5**: 横の展開が無脳の全ポート全辞書スキャンにならないようにするには。
**A5**: 横は「仮説を持って敷く」。各拡張で「どの類のものを探しているか」(認証点?アップロード?デシリアライズ入口?)に答えるべき。目的のない広さは予算の浪費。

### 脆弱性利用 vs 認証情報取得:二本の直交する幹
**Q1**: 一つのサービスを攻めるにあたり、「そのコードの脆弱性を探す」か「その認証情報を仕入れる」か。
**A1**: これは最も混同されやすい二本の直交する幹であり、並行して評価すべき。脆弱性利用軸は対象に利用可能な欠陥があることに依存する。認証情報軸は、あなたが他所から拾う/ブルートフォースする/再利用するログイン認証情報に依存する。認証情報軸は往々にしてより安定し、より秘匿で、防御をより少なくトリガーする。最初から exploit だけを狙わない。
**Q2**: いつ認証情報軸を優先するか。
**A2**: 対象のパッチが比較的新しく、公衆ネットワークで強化済みだが、あなたが既に環境内に足場を持つ(設定、メモリ、履歴コマンド、バックアップをひっくり返せる)時、認証情報の再利用/スプレーの ROI は通常、硬い exploit よりはるかに高い。
**Q3**: 認証情報軸を具体的にどう展開するか。
**A3**: サブ軸:足場確保された認証情報(設定/ログ/メモリ/ブラウザ/認証情報マネージャ)、ネットワーク認証情報(パケットキャプチャ/中間者/プロトコルフォールバック)、ブルートフォーススプレー(ロックを防ぐ低頻度のアカウント横断 password spraying)、信頼認証情報(チケット/証明書/キー/セッショントークン)。サブ軸ごとに投影する。
**Q4**: 脆弱性利用軸が完全に死んだ(全てパッチ済み)。どう方向転換するか。
**A4**: 直交して認証情報軸と「設定/信頼」軸へ方向転換。パッチはコード欠陥を直せるが、弱いパスワード、過度の認可、再利用されたキー、誤った信頼関係は直せない。防御は脆弱性軸で強い ≠ 身分軸も強い。これこそ次元を変える価値。
**Q5**: 二本の軸がどちらも少し進展したが、どちらも不十分。どう組み合わせるか。
**A5**: 二軸に互いに餌をやらせる:小さな情報漏えい(脆弱性軸)→ユーザー名/パスを取得→認証情報軸のスプレーに餌を与える。弱い認証情報(認証情報軸)→管理画面へログイン→脆弱性軸のテスト可能面を広げる。直交軸の積は往々にして各自の単独より大きい。

### ネットワーク層 vs アプリケーション層:打てなければ沈む/浮上する
**Q1**: アプリケーション層(HTTP ビジネスロジック)を一通り試して突破できない。ネットワーク層を見るべきか。
**A1**: 見るべき。層軸は最も古典的な直交次元。アプリケーション層がフィルタリング/強化された時、伝送/ネットワーク層へ沈むと往々にして驚きがある:暗号化されていないプロトコル、内部ネットワークサービスの直連、管理ポート、プロトコル自体の認証欠陥。逆にネットワーク層が塞がれた時、ビジネスロジックの脆弱性へ浮上する。
**Q2**: ネットワーク層へ沈む価値があるかをどう素早く判断するか。
**A2**: 対象が「Web でないもの」を露出しているかを見る:データベース、キャッシュ、メッセージキュー、RPC、管理プロトコル、運用 agent。これらはしばしば Web の注意力に遮蔽され、防御がはるかに弱い。
**Q3**: ネットワーク層でポートは見えるが全て認証が必要な場合。
**A3**: 「プロトコル弱点/デフォルト設定」のサブ次元へ方向転換:デフォルト認証情報、匿名アクセス、未認可コマンド、プロトコルダウングレード、旧バージョンの認証欠陥。多くのインフラサービスの認証は「設定で作り込まれた」もので、デフォルトは往々にして開いている。
**Q4**: ネットワーク層とアプリケーション層がどちらも壁に当たった。どの直交面へ方向転換し続けるか。
**A4**: 「層間の信頼」面へ方向転換:アプリケーション層はどうバックエンドへ接続するのか。その内部接続は往々にして無防備(平文、パスワード不要、強い信頼)。南北向(外→内)が打てなければ、足場を一つ得て東西向(内→内)を打つ。それは全く別の信頼モデル。
**Q5**: 層の間を何度も行き来して時間を無駄にしないには。
**A5**: 沈む/浮上するたびに「その層固有の産物」(一つのポート、一段のプロトコルフィンガープリント、一つのエラー)を持ち帰る。手ぶらで往復するのは、その層で真剣に投影していない証拠。予算は産物のある層に残す方がよい。

### 技術面 vs 人/フロー面
**Q1**: システムが技術的に非常に硬く、パッチが揃い、設定が厳しい。人の次元を考えるべきか。
**A1**: 技術軸と人/フロー軸は天然に直交する。システムがいくら硬くても、それを操作する人、それをデプロイするフロー、それを保守する認証情報管理の習慣は別の平面。レッドチームは技術軸を尽くした後、「人は省力を好む」という法則で局面を破ることが多い(弱いパスワード、キーのハードコード、内部文書の漏えい、設定の外部流出)。
**Q2**: 認可の範囲内で、人の次元は具体的に何を指すか(必ずしもフィッシングを仕掛ける必要はない)。
**A2**: フィッシングだけではない。含まれるもの:公開情報に残る人員の痕跡(リポジトリのコミット、文書、チケット)、命名規則(アカウント/ホストの命名習慣)、フローの仮定(運用は内部ネットワークをデフォルトで信頼する、臨時のバックドアを消し忘れる、テストアカウントが残る)。これらは全て「人的要因」の技術的投影。
**Q3**: 「人の規則」を実行可能なプローブにどう変えるか。
**A3**: 習慣を辞書と仮説に変える:命名規則→アカウント/ホスト/パスの辞書を生成;省力→デフォルト認証情報/パスワード再利用をテスト;急ぎ仕事→残されたデバッグ API/テスト環境/バックアップファイルを探す。
**Q4**: 技術面と情報収集を両方やったのに、人の面にも手がかりがない。どこへ方向転換するか。
**A4**: 「時間/フローノード」の次元へ方向転換:リリース窓、運用操作の時間帯、一時開放のチャネル。防御強度は時間とともに揺らぎ、普段は閉じているチャネルもデプロイ/障害切り分けの際に短時間開くことがある。「空間に穴を探す」から「時間に窓を待つ」へ。
**Q5**: 人に過度に依存して技術の再確認を軽んじないようにするには。
**A5**: 人因から得た手がかり(例えば疑わしいパスワード)は必ず技術軸に戻って検証しループを閉じる。二軸は相補的な証拠チェーンであり、二者択一ではない。

### 正面ドアの認証 vs 側面ドアの未認可 API
**Q1**: ログインページが非常に硬い(ロック、CAPTCHA、MFA)。正面のブルートフォースは見込みがない。どう考えるか。
**A1**: 「正面ドア」だけを見ない。認証は一層だが、業務システムには往々にして大量の「側面ドア」がある。認証が掛かっていない API、内部 API、静的リソース、デバッグエンドポイント、旧バージョンのルート。直交する問いは「この錠をどう破るか」ではなく「この建物にはまだ錠の掛かっていないドアが何枚あるか」。
**Q2**: 側面ドアをどう列挙するか。
**A2**: 「ルート/API 空間」に沿って投影する:フロントエンド JS/API ドキュメント内の隠しエンドポイント、バージョン化されたパス(/v1 /v2 の旧バージョン)、内部/管理プレフィックス、直接オブジェクトアクセス(ID を変えて権限外アクセス)、認証と認可が分離している箇所(認証は通るが権限を検証しない)。
**Q3**: 未認可 API を見つけたが機能が非常にショボい。深掘りする価値があるか。
**A3**: それが「情報/身分のレバー」かを見る。ユーザー名を列挙できるショボい API は正面のスプレーに餌を与えられる。設定を読める API は認証情報軸に餌を与えられる。ショボい API の価値は往々にして他の軸を養うことにある。
**Q4**: 正面ドアも裏口も全て施錠された。どの直交次元へ方向転換するか。
**A4**: 「認証後の横展開仮定」へ方向転換:任意の正規セッションを手に入れられる口(セルフサービス機能、登録フロー、第三者ログインのコールバック)を探し、正規の身分で入り、「認証後の攻撃面」という新平面で権限外アクセス/ロジック脆弱性を探す。戦場を「入れるかどうか」から「入った後に何を濫用できるか」へ替える。
**Q5**: 側面ドアの列挙で迷子にならないようにするには。
**A5**: 「認証/認可マトリクス」で記録する:各 API→認証が必要か→認可を検証するか→返す敏感度。マトリクス内の「認証が必要だが認可を検証しない」と「そもそも認証不要」の二マスが、突破のスケジューリング表。

### データ伝送中 vs データ静止
**Q1**: 敏感データが手に入らない。伝送中のもの(in-transit)を遮るか、静止したもの(at-rest)を探すか。
**A1**: データ状態は一本の独立した直交軸。伝送中:パケットキャプチャ、中間者、プロトコルダウングレード。静止:ファイル、データベース、バックアップ、キャッシュ、ログ、メモリスナップショット。一本が打てなければもう一本に替える。同じデータでも状態が違えば防御強度は往々にして天と地ほど違う。
**Q2**: 伝送暗号化が非常に硬い(TLS 全サイト)。伝送状態にまだ見込みはあるか。
**A2**: 暗号を破るのではなく「端点状態」へ方向転換:データは暗号化に入る前/復号後に必ず平文。復号端のメモリ、一時ファイル、ログ、デバッグ出力を探す。暗号を迂回するより、暗号の両端へ迂回する方がよい。
**Q3**: 静止データも全て暗号化されている場合は。
**A3**: 「復号せざるを得ない場所」を探す:アプリケーションの実行時は必ずキーを保持しているか、復号を呼び出せる。プロセスメモリ、キー管理呼び出し、サービスアカウント権限へ方向転換。暗号化されたデータは問題を「キーを探す/復号する権限のある身分を探す」に変換している。それは身分軸の問題。
**Q4**: 伝送状態も静止状態も壁に当たった。どこへ方向転換するか。
**A4**: 「データライフサイクルの上流」へ方向転換:データはどこから来るか。それを生成するサービス、それを同期するパイプライン、それをバックアップするタスク、それをエクスポートするレポート。主ストレージは重兵に守られているが、データは「通る道の途中」(ETL、バックアップ、エクスポート、第三者同期)でしばしば丸裸。
**Q5**: 伝送を先に打つか静止を先に打つかをどう選ぶか。
**A5**: 足場を見る。足場がなく、ネットワーク経路上にいるなら→伝送状態を優先。既にホストの足場があるなら→静止状態/メモリ状態を優先。現在位置がどのデータ軸のコストが低いかを決める。

### 一つのサービスが打てない:ポートを替えサービスを替える
**Q1**: ホスト A で私が狙っているそのサービスが軟硬とも受け付けない。ホストには他にもポートが開いている。どうするか。
**A1**: サービスは直交する単位。同一ホストの各リスニングポートは独立した攻撃面で、防御水準はそれぞれ異なる。最も目立つ(往々にして最も硬い)サービスで消耗し尽くさず、各開放ポートを独立した対象として一度のフィンガープリントと既知欠陥の投影を行う。
**Q2**: どのサービスを先に打つか、どう並べるか。
**A2**: 「柔らかさ」で並べる:バージョンが古い、非主力業務の、運用/管理系の、自社開発の小さなツール類は、通常中核の対外サービスより柔らかい。マイナーなポート = マイナーな注目 = 忘れられたパッチ。
**Q3**: ポートは全てスキャンしたが多くが知らないもの。どうするか。
**A3**: 「プロトコルフィンガープリント/能動対話」の次元へ方向転換:プローブパケットを送ってレスポンスを見る、banner を掴む、特徴ライブラリと照合する。それが何のサービスかを識別すること自体が解錠点。未知のポートは行き止まりではなく、翻訳を待つ情報。
**Q4**: このホストの全サービスが打てない。どこへ方向転換するか。
**A4**: 「単一ホストのサービス軸」から直交して「ホスト間関係軸」へ跳ぶ:この硬いホストは誰に繋がっているか、誰を信頼するか、誰がその管理口へ接続できるか。硬い対象は往々にして一台の柔らかい隣人に管理されている(踏み台/要塞/運用マシン)。次元を変える = ホストの視点を変える。
**Q5**: 無関係なポートの一群に時間を無駄にしないようにするには。
**A5**: まず低コストのフィンガープリントで全ポートにラベルを貼り、「既知の攻撃履歴のあるサービスタイプ」にだけ深度予算を投入する。識別コストは低く、利用コストは高い。先に安く識別してから、どれに投入するかを決める。

### 現在のユーザー文脈 vs 他の身分
**Q1**: 低権限の shell/アカウントを手に入れた。できることは全てやった。次は。
**A1**: 身分は直交軸。「私という身分が何をできるか」の中だけで回らず、「このマシンには他にどんな身分が住んでいるか」を問う。他のログインユーザー、サービスアカウント、計画タスクの身分、より高い権限で実行されるプロセス。あなたの苦境は身分の制限であり、必ずしもホストの制限ではない。
**Q2**: 奪取できる他の身分をどう発見するか。
**A2**: 「身分の残存物」に沿って投影する:高権限プロセス、セッション/トークン、キャッシュされた認証情報、他のユーザーのホームディレクトリの残存、サービス設定内の実行アカウント、メモリ内のチケット/キー。それぞれが「別の身分への横展開」の一回の機会。
**Q3**: 権限昇格(縦の身分変更)がずっと失敗する場合は。
**A3**: 「身分を上げる」のではなく「身分を平行移動する」へ方向転換:必ずしも root/admin でなくてよい。対象データを読める、または次のマシンへ接続できる同格のサービスアカウントの方が、本機の権限昇格に執着するより有用なことがある。変えるのは身分の「能力の方向」であり「高さ」ではない。
**Q4**: 本機の全ての身分が対象に届かない。どの直交次元へ方向転換するか。
**A4**: 「遠隔身分」の次元へ方向転換:このマシンが保持する、他所で使える認証情報(ドメイン認証情報、API キー、SSH キー、クラウド認証情報)。本機の身分軸を尽くしたら、「本機で拾った身分で他所へログインする」横の身分軸へ跳ぶ。
**Q5**: 「私の手元にどんな身分があるか」をどう体系的に管理するか。
**A5**: 身分台帳を維持する:各身分→権限範囲→到達できるリソース/ホスト→出所。台帳はどの身分が対象への最短ジャンプかを示してくれる。現在の shell に執着しない。

### 能動的利用 vs 受動的待機
**Q1**: ずっと能動的に攻めている(payload を送る、スキャンする、ブルートフォースする)。「待つ」ことを考えるべきか。
**A1**: 時間/能動受動は直交軸。能動は防御をトリガーし、ノイズを残す。受動的待機(コールバックを待つ、認証情報の足場確保を待つ、計画タスクの発火を待つ、管理者の操作を待つ)は往々にして低ノイズかつ高品質。能動経路が全て硬い時、罠を敷いて相手が「送ってくる」のを待つのは別の次元。
**Q2**: 受動経路を具体的にどう敷くか。
**A2**: 認可内で「収集器」を敷く:トリガーされ得るチャネルを監視する、高権限プロセスが読む/実行できるおとりを置く、周期性タスクを待つ、運用ログインのタイミングを観察する。静的攻撃を「待ち伏せ」に変える。
**Q3**: どのくらい待てば合理的で、ただ待つだけにならないか。
**A3**: 受動は必ず能動と並行し、純粋な待機ではない。「受動チャネル+能動プローブ」の二線を設ける。受動はバックグラウンドの低コストプロセスとして動かし続け、能動線は前進を続ける。発火すれば即利得。
**Q4**: 能動が全て遮断され、受動も何も待てない。どこへ方向転換するか。
**A4**: 「イベントを製造する」次元へ方向転換:自然なイベントを待つより、認可範囲内で一つのイベントを誘発する(あるフローをトリガーする、運用の介入が必要な状況を作る)。「受動信号を待つ」を「能動的に受動信号を誘発する」へ昇格させる。これは時間軸と対話軸を組み合わせた次元変更。
**Q5**: 受動手段の最大のリスクは何か。
**A5**: 自分が敷いたものを忘れること→制御不能/痕跡を残す。各受動収集器は登録し、回収可能にする。レッドチームは布置物を綺麗に清掃できなければならない。

### 単一ホスト vs 横展開してから再び戻る
**Q1**: 対象ホスト T が正面から打てない。しかし私は既に同一セグメントのホスト A に入っている。A をどう使うか。
**A1**: 「攻撃位置」という次元を変える。公衆ネットワークから T を打つ(南北向)のと A から T を打つ(東西向)のは、二つの全く異なる信頼と防御のモデル。内部視点では T は A に対してパスワード不要/強い信頼/管理口を開けているかもしれない。位置そのものが一本の直交軸。
**Q2**: 内部の足場 A を得た。T を打ち返す前にまず何をするか。
**A2**: まず A で「T に向けた偵察」をする:A から見える T のポート(内部ネットワークの露出面は通常より大きい)、A に T へ接続した認証情報/キー/セッションがないか、A と T が同ドメイン/同信頼か。内部偵察は往々にして T の鍵を直接与える。
**Q3**: A が T に打てない(ネットワーク隔離)。どうするか。
**A3**: 「ハブ/マルチ NIC」の次元へ方向転換:二つのセグメントを跨ぐホストを踏み台として探す。または T が能動的に外向き接続する方向を探して逆利用する。隔離はネットワーク次元の壁。接続されたホストに替えることはネットワーク軸を替えること。
**Q4**: 数台横展開しても T に届かない。全体としてどこへ方向転換するか。
**A4**: 「制御面/管理面」の次元へ方向転換:T がいくら孤立していても、必ず何かに管理されている(ドメインコントローラ、構成管理、要塞ホスト、仮想化プラットフォーム、クラウドコンソール)。逐台の横展開を放棄し、直接「一片のホストを号令できる中枢」を探す。一点突破で全盤が下る。「逐点の横展開」から「制御中枢」へ跳ぶのは次元の昇格。
**Q5**: 横展開の際に迷わないためには。
**A5**: 「到達可能性グラフ」を描く:ノード = ホスト、辺 = 到達可能/ログイン可能。一台取るたびにグラフを更新する。対象 T から現在位置までの最短経路が一目瞭然になり、盲目的に跳ばない。

### 時間次元:即時ブルートフォース vs 持久待機
**Q1**: すぐに取りたいが、毎回の強攻がアラート/ロックをトリガーする。減速すべきか。
**A1**: 「速度」を調整可能な次元として扱う。高速強攻は防御が弱い時は効率的だが、ロック/レート制限/アラートに対抗する時、低速持久(低速スプレー、長周期の待機、ピーク回避操作)は直交する戦略。速く打てなければ遅く磨く。
**Q2**: 遅い次元を具体的にどう足場確保するか。
**A2**: しきい値以下に降頻する(アカウントロックしきい値、アラート頻度しきい値の下)、長い時間窓に分散する、通常業務の時間帯に紛れてノイズに隠す。「一度で打ち切る」を「細く長く流す」に分解する。
**Q3**: 遅くしても進展がない。時間次元に他に遊びはあるか。
**A3**: 「タイミングの次元」へ方向転換:速い遅いではなく「どの時点で打つか」。デプロイ窓、保守窓、当番交代、休暇。防御と応答能力は時間とともに起伏する。防御が最も弱い瞬間を選んで重要な動作をする。
**Q4**: 時間次元を全て試した(速い、遅い、タイミング選定)が駄目。どこへ方向転換するか。
**A4**: ボトルネックは時間軸にないことを示す。空間/手段軸へ戻る。対象にはあなたが攻めているその類の弱点がそもそもない。時間軸でパラメータ調整を続けず、攻撃面/手段リストに戻って別の直交する道を選び直す。「現在の軸は根本的に解がない」と識別すること自体が重要なメタ意思決定。
**Q5**: 低速待機が制御不能/期限超過にならないようにするには。
**A5**: 明確な時間ボックスと退出条件を設ける。待機には「期限に発火しなければ撤収する」規律が必要。さもなければ予算を無期限に占有する。

### 既知 CVE vs 設定エラー/弱いパスワード
**Q1**: 対象のバージョンを調べたが、公開の利用可能な exploit がない。解はないのか。
**A1**: 「CVE がない」を「穴がない」としない。既知の脆弱性は一つの軸。設定エラー/弱いパスワード/デフォルト値/過度の認可は完全に直交する別の軸で、後者は永遠にパッチを打ち切れない。パッチが全部 ≠ 設定が正しい。
**Q2**: 設定エラーをどう体系的に探すか。
**A2**: 「そのサービスのセキュリティベースライン」に沿って逐項逆検査する:デフォルト認証情報を変えたか。匿名/ゲストは開いているか。権限を最小化したか。デバッグ/管理 API を閉じたか。危険な機能を無効化したか。それぞれの「やっていない」が一つの穴。
**Q3**: 設定はかなり規範的で、弱いパスワードもブルートフォースで出なかった。どうするか。
**A3**: 「信頼/認可設計」の次元へ方向転換:各マシンの設定が正しくても、システム間の信頼関係は設計が広すぎることがある(誰がパスワード不要で誰に接続できるか、誰の権限が過大か)。単点の設定が正しい ≠ 全体の信頼設計が正しい。
**Q4**: CVE、設定、弱いパスワードの三つが全て空。どこへ方向転換するか。
**A4**: 「未知/ロジック脆弱性」の次元へ方向転換:ビジネスロジックの欠陥、競合、権限外アクセス。CVE がなく、スキャンで出ず、業務を理解して手掘りするしかない。「ライブラリ照会/スキャン」の自動化軸から、「業務を読み解いて手で打つ」分析軸に替える。
**Q5**: CVE 軸を先に行くか設定軸を先に行くかをどう決めるか。
**A5**: 先に設定/弱いパスワード(コストが低く、ノイズが制御でき、往々にして意外な効果がある)。CVE 利用(特にメモリ破壊類)はコストが高く、リスクが高く、サービスを落としやすい。後手として残す。先に低い位置の果実を摘む。

### 内容層 vs メタデータ/帯域外チャネル
**Q1**: インジェクションを疑うが、ページのエコーに何の結果も見えない。穴がないのか。
**A1**: エコーがない ≠ 脆弱性がない。エコー(内容層)は一つの観測次元に過ぎない。「帯域外/ブラインド攻撃」という直交する観測次元がある:時間遅延、DNS/HTTP 帯域外、エラー挙動の差異。盲インジェクション/OOB は、内容チャネルが口を閉じた時に切り替える次元。
**Q2**: 帯域外チャネルをどう建てるか。
**A2**: 対象に能動的に「外へ信号を送らせる」:一度の DNS クエリ、一度の外向き HTTP、一度の計測可能な遅延をトリガーする。観測点を「対象が私に返す内容」から「対象が第三者へ発する動作」へ移す。
**Q3**: 対象が完全に外向き通信せず、帯域外も死んだ場合は。
**A3**: 「純時間サイドチャネル」の次元へ方向転換:1 bit さえ出せなくても、レスポンス時間の差異で一位ずつ情報を推測できる(ブール盲/タイミング)。空間チャネル(内容、ネットワーク)が全封でも、時間チャネルは往々にしてまだ開いている。
**Q4**: 内容、帯域外、タイミングが全て通らない。インジェクション経路全体がどこへ方向転換するか。
**A4**: 「ストレージ/二次」の次元へ方向転換:入力は現在のリクエストでトリガーされず、少し後に別のコンポーネント/バックグラウンドタスクで処理されるかもしれない(二次インジェクション)。あるいは脆弱性の類を替える。このパラメータを放棄し、攻撃面地図に戻って次の直交入口を選ぶ。
**Q5**: 早めに帯域外次元へ上がるべきとどう判断するか。
**A5**: インジェクションが成立しそうだが「口がきけない」(エコーなし)なら、第一反応は帯域外/タイミングに上がること。内容層の payload を調整し続けない。口のきけない穴のデフォルト対応は観測次元を替えること。

### 制御チャネル:フォワード / リバース / 帯域外(外向き通信の遮断を含む)
**Q1**: コマンド実行できるようになったが、対話型 shell に接続できず、データも出て行かない。どうするか。
**A1**: 制御チャネルの方向は直交軸。梯子に沿って逐級降格して試す:フォワード(私が対象へ接続)がインバウンドファイアウォールに遮られた→リバース(対象が私へ接続)に替える→リバースがアウトバウンドポリシーに遮られた→帯域外に替える(直連 TCP→HTTP/HTTPS プロキシ→DNS→ICMP→認可済み業務のアウトバウンド→ドメインフロント/CDN)。コマンド実行があるのは出発点に過ぎない。「直連が通らない」だけで「外向き通信しない」と結論しない。アウトバウンドポリシーはほぼ常に業務用の縫い目を残している。
**Q2**: どの方向/サブチャネルを先に試すか。
**A2**: 先に「対象が元々許しているアウトバウンド」を試す:それは普段何でネットワークに繋がるか(更新、レポート、DNS 解決、外部依存へのアクセス)。制御/返信トラフィックをその合法チャネルに寄生させる。新たに穴を開けず、より通じやすく、より秘匿。
**Q3**: 通常チャネルが全て塞がれ、DNS だけが解析できる場合は。
**A3**: 「DNS/帯域外」の次元へ方向転換:ドメイン名解決リクエストは往々にして層層転送でき、帯域は極めて低いが重要な情報を伝え、制御を維持するのに十分。全ての直接チャネルが塞がれた時、DNS はしばしば最後の縫い目。
**Q4**: 完全に外向き通信しない(純内部ネットワーク孤島)場合、どう制御するか。
**A4**: 「帯域内/足場確保/中継」の次元へ方向転換:リアルタイム対話を放棄し、「タスク投下—結果足場確保—回収」の非同期モードに替える。共有ストレージ/半接続の中間ホストを経由してリレーする。「リアルタイムチャネル問題」を「ファイル/タスク交換問題」に次元を下げる。
**Q5**: 全てのリバース/トンネルが EDR/ファイアウォールに切断された。全体としてどの直交次元へ方向転換するか。
**A5**: 「担体」の次元を替える:独立した C2 チャネルを追求せず、命令/返信を対象が元々許しているプロトコルフィールド、DNS 名、HTTP ヘッダーにエンコードし、合法業務フローに寄生させる。「新しいチャネルを増やす」軸が塞がれた時、「認可済みチャネルの再利用」は全く別の一本の軸。
**Q6**: コマンド実行はあるが安定チャネルを取れない。先に何をすべきか。
**A6**: 急いで shell を弾かない:コールバックなしの「盲実行」で重要な情報収集を済ませ(結果は回収可能な場所に足場確保)、低コストのプローブで各プロトコル/ポート/方向の接続性を個別に測り、「外向き通信可否表」を描く。それからどのチャネルに投入するかを決める。盲目的に重チャネルを一つずつ試さない。

### 権限昇格の四つの直交面:カーネル/サービス/設定/認証情報再利用
**Q1**: 一台のマシンで権限昇格したい。どの直交方向から考えるか。
**A1**: 権限昇格は一本の軸ではなく四つの直交面:①カーネル/システム脆弱性面 ②高権限で実行されるサービス/プロセス面 ③誤ったファイル/サービス/権限設定面 ④再利用可能な高権限認証情報面。一つしかできない人が多い(多くはカーネル exp だけを探す)。四面をローテーションする。
**Q2**: カーネル exp 面を先に何を見るか。
**A2**: 精密なフィンガープリント(カーネル/システムバージョン、パッチレベル)→既知のローカル権限昇格にマッチ→安定性を評価(落ちるか)。カーネル exp は強いが脆い。使い捨て/復元可能な環境で優先し、本番では慎重に。
**Q3**: カーネル権限昇格が落ちた、または使える exp がない。どの面へ方向転換するか。
**A3**: 「設定/サービス」面へ方向転換:書き込み可能な高権限サービスパス、弱い権限の計画タスク、危険な SUID/サービスアカウント権限、ハイジャック可能なロードパス。設定類の権限昇格は安定し、静かで、サービスを落とさない。優先度は実はカーネル exp より高いことが多い。
**Q4**: 三つの技術面が全て通らない。最後の直交面は何か。
**A4**: 「認証情報再利用」面:本機のメモリ/ファイル/履歴にある高権限認証情報を直接「ログインして成る」。つまり「権限昇格して成る」のではなく。この道は全てのローカル脆弱性を迂回する。身分で脆弱性を代替するのは、前三面と完全に直交する発想。
**Q5**: 四面をどう優先度付けするか。
**A5**: 一般に 認証情報再利用 > 設定類 > サービス類 > カーネル exp(安定性↓、ノイズ↑、クラッシュリスク↑で並べる)。先に「鍵を拾う」「設定ミスを利用する」を探し、どうしてもなければ落ちるカーネル exp を上げる。

### Web 三状態:入力点 / 出力点 / ストレージ点
**Q1**: 一つの入力パラメータを狙ってインジェクションを打ったが成らない。Web 脆弱性はどの直交角度から切れるか。
**A1**: 一つのデータには三つの攻撃可能状態がある:システムに入る入力点、ユーザーに描画される出力点、データベースに落ちるストレージ点。同じ脆弱性類も状態が違えば現れ方が違う(反射 vs ストレージ vs DOM)。入力点のフィルタリングが厳しくても、出力点はエンコーディングをしていないかもしれない。
**Q2**: 入力点が厳しくフィルタリングされた。どこへ方向転換するか。
**A2**: 「出力点/文脈」の次元へ方向転換:データは他所で取り出されて描画される時に初めて問題になることがある。それが最終的にどんな文脈(HTML/JS/属性/URL/SQL)に落ちるかに注目する。フィルタリングは入口で起き、脆弱性は往々にして出口で起きる。
**Q3**: 入力も出力も綺麗。ストレージ状態をどう利用するか。
**A3**: 「保存されて初めて発火する」二次経路を探す:データは入庫時は無害で、別の機能/バックグラウンドタスク/管理面が取り出して使う時にトリガーされる。ストレージ状態の脆弱性は観測が遅れる。提出した瞬間に「穴がない」と結論しない。
**Q4**: 三状態を全て試してこのデータフローが駄目。どこへ方向転換するか。
**A4**: 「データフロー」そのものを替える:このデータチェーンを放棄し、攻撃面地図に戻って別の入口から別の sink への直交データフローを探す。一本のデータフローの三状態は一つの連結領域。データフローを替えることこそ次元を変えること。
**Q5**: 三状態を漏れなく体系的にカバーするには。
**A5**: 各制御可能入力に、その全 sink(どこで取り出されて使われるか)を注記し、「ソース→シンク」表を作る。表の各「ソースからシンク」は一本の独立したテスト経路。入口だけを測って全部測ったと思わない。

### 認証バイパス vs 認証後の機能濫用
**Q1**: 「入れない」ところで詰まり、ずっと認証バイパスを試している。他に大きな方向はあるか。
**A1**: ある。しかも往々にして無視される。「入れるかどうか」(認証)と「入った後に悪事をできるか」(認可/機能濫用)は二本の直交軸。多くのシステムは認証が非常に硬いが、認証後は権限外アクセスだらけ。まず最低権限の正規の身分を一つ手に入れる方法を考える。戦場が変わる。
**Q2**: 正規の身分を低コストで一つ手に入れるには。
**A2**: 「セルフサービスで身分を得る」入口を探す:オープン登録、トライアル、第三者ログイン、パスワード回復フロー。最低権限のアカウントでも、あなたを「外部攻撃者」から「内部の低権限ユーザー」に変え、テスト可能面が爆発的に広がる。
**Q3**: 低権限アカウントを得た。認証後にまず何を打つか。
**A3**: 「認可境界」を打つ:水平の権限外アクセス(同格の他人のデータへのアクセス)、垂直の権限外アクセス(管理機能への到達)、直接オブジェクト参照、隠された高権限 API。認証がうまくできているシステムは、認可が往々にして粗い。
**Q4**: 認証バイパスも認証後の権限外アクセスも試して突破できない。どこへ方向転換するか。
**A4**: 「信頼チェーンの上流」の次元へ方向転換:このアプリケーションは誰に身分を発行させているか(SSO/身分プロバイダ/ゲートウェイ)。上流の身分源を攻めるか、アプリケーションと身分源の間の信頼仮定を利用する。このアプリケーションの認証を正面から攻めるより直交している。
**Q5**: 認証に優先投入するか認可に優先投入するかをどう判断するか。
**A5**: 低コストで正規の身分を得られるなら、認可軸を優先(投入産出が高い)。身分を得るのも難しいなら、認証バイパス軸に多く投入する。最も硬い認証の壁で予算を消費し尽くさない。

### サプライチェーン/第三者コンポーネント vs 自社開発コード
**Q1**: 対象の自社開発コードはかなり厳密そうで、明らかな穴がない。他にどの直交軸があるか。
**A1**: 「第三者/サプライチェーン」軸へ方向転換。現代のシステムの 90% のコードは導入されたコンポーネント、フレームワーク、ライブラリ、イメージ。自社開発部分がいくら厳密でも、一つの時代遅れの第三者コンポーネントが門を開ける。業務コードだけを見ず、その「材料」を見る。
**Q2**: 第三者コンポーネントの弱点をどう探すか。
**A2**: まずコンポーネントとバージョンのフィンガープリント(フレームワーク特徴、エラー、静的リソースのハッシュ、依存リスト)を行い、そのバージョンの既知の脆弱性にマッチする。自社開発コードは 0day を掘る必要があるが、第三者コンポーネントには往々にして既成の 1day がある。
**Q3**: コンポーネントが全て新バージョンで、既知の穴がない。どこへ方向転換するか。
**A3**: 「サプライチェーンのさらに上流」へ方向転換:ビルドパイプライン、依存リポジトリ、イメージの出所、CI/CD 認証情報。実行時のコンポーネントを打てないなら、「この実行時を生産するパイプライン」を打てるかもしれない。「完成品を打つ」から「生産ラインを打つ」に替える。
**Q4**: サプライチェーンも自社開発も壁に当たった。まだ直交方向はあるか。
**A4**: 「統合/グルー層」へ方向転換:自社開発と第三者をつなぐ接着コード、設定、デシリアライズ、データフォーマット変換箇所は、双方が手薄な、誰も管理しない地帯。脆弱性は往々にして二つのコンポーネントの中ではなく、その接ぎ目にある。
**Q5**: 見知らぬシステムを前に、自社開発軸と第三者軸のどちらに先に投入するか。
**A5**: 先に第三者(フィンガープリント+既知脆弱性照会はコスト極低、命中すれば高リターン)。自社開発の深掘り(時間がかかり、業務理解が必要)は後続とする。先に他人の踏んだ穴を使い、それから自分で穴を掘る。

### 対象本体 vs 対象の依存/上流
**Q1**: 対象 X の本体が非常によく防御されている。それに執着するしかないのか。
**A1**: そうではない。対象は境界のあるシステムだが、それが依存するもの(それが接続するデータベース、それが呼ぶ API、それが信頼するサービス、その運用チャネル)は、あなたの認可範囲内では往々にして有効な経路でもある。X を打てなければ、X が離れられないものを打つ。
**Q2**: 対象の依存をどう列挙するか。
**A2**: X が能動的に外へ接続する方向を観察する:どのデータソースを照会するか、どの内部サービスを呼ぶか、どこから設定/更新を引くか、ログ/データを誰に送るか。各外向き接続が、より柔らかいかもしれない一本の直交経路。
**Q3**: 依存サービスにも届かない場合は。
**A3**: 「共有インフラ」の次元へ方向転換:X と他のシステムが同じ土台を共有していないか(同じデータベースインスタンス、同じ認証センター、同じクラスタ、同じ認証情報)。共有土台を攻略すれば、X 本体の全防御を迂回することに等しい。
**Q4**: 本体、依存、共有土台が全て壁に当たった。どこへ方向転換するか。
**A4**: 「X を信頼する下流」の次元へ方向転換:誰が X の出力を信頼するか、誰が X のデータを自動消費するか。他人の X への信頼を逆利用する(X の出力に影響できれば)、下流を汚染する。攻撃方向を「X に攻め入る」から「X を借りて他人を攻める」に反転する。
**Q5**: 依存がこれほど多い。どう発散しないか。
**A5**: 「最終目標のデータ/権限に通じる」依存だけに沿って歩く。依存からあなたが本当に欲しいものへ戻る経路を一本描く。依存の列挙は目標に奉仕すべきで、発散のための発散ではない。

### プロトコル次元:HTTP vs その他のプロトコル
**Q1**: ずっと HTTP 視点で攻めている。対象には非 HTTP ポートも一群開いている。重視すべきか。
**A1**: すべき。プロトコルはひどく無視されている一本の直交軸。レッドチームは長年 HTTP に経路依存を訓練されてきたが、SMB/LDAP/RPC/SNMP/データベース/メッセージキューなどのプロトコルには独自の認証モデルと歴史的脆弱性があり、防御は対外 Web より普遍的に弱い。
**Q2**: 見知らぬプロトコルポートを前にまず何をするか。
**A2**: まずプロトコルと実装を識別する(能動対話でレスポンスを見る、banner を掴む、フィンガープリントを照合する)、それからそのプロトコル+その実装の既知弱点とデフォルト設定を調べる。識別は見知らぬプロトコルを解錠する第一歩。「見たことがない」からといって飛ばさない。
**Q3**: プロトコルが認証を必要とし、既知の脆弱性もない場合は。
**A3**: 「プロトコル交差/認証情報共通」の次元へ方向転換:多くの環境で同じ一組の認証情報が複数のプロトコル間で共通。一つのプロトコルで得た認証情報が別のプロトコルのログインに直接使えるかもしれない。また、プロトコルがより弱い認証方式へのダウングレードをサポートするかも見る。
**Q4**: 各種プロトコルが全て打てない。どの直交次元へ方向転換するか。
**A4**: 「アプリケーション/人」の次元へ戻る:プロトコル層が全て硬い時、インフラの強化が行き届いていることを示す。弱点はむしろ上層のビジネスロジックか人的要因にある。プロトコル軸を尽くしたことは一つの信号:予算をアプリケーションロジックか認証情報/ソーシャルエンジニアリング面に戻す。
**Q5**: 一群のプロトコルポートに引きずられないようにするには。
**A5**: 先に「プロトコルの歴史的危険度 + 認証が必要か + バージョンの新旧」でポートを並べ、前列のものだけ深掘りする。プロトコル軸は非常に広い。優先度を持ち、平均的に力を入れない。

### 暗号化トラフィック:破解 vs サイドチャネル/ダウングレード/端点
**Q1**: 対象の通信が全暗号化で、私が掴んだパケットは全て暗号文。見込みはないのか。
**A1**: 正面から暗号を破りに行かない(ほぼ実行不能)。「暗号化の破解」は死んだ軸。直交軸は「暗号化の必要性を迂回する」こと:弱い暗号化/平文へダウングレード、暗号化前後の端点で平文を取る、メタデータ(パケットサイズ/タイミング/宛先)でトラフィック分析をする。
**Q2**: ダウングレードを誘導できるか。
**A2**: 交渉プロセスが弱いスイート/旧バージョン/平文へのフォールバックを許すかを見る。多くの実装は互換性のために弱い選択肢を残している。弱いものに交渉できれば強いものを破る必要がない。これは「相手に自ら弱い暗号化を使わせる」発想。
**Q3**: ダウングレードも塞がれた場合は。
**A3**: 「端点状態」の次元へ方向転換:データは送信端で暗号化する前、受信端で復号した後に必ず平文。線路上の暗号文を放棄し、キーを保持する端点(メモリ、ログ、一時ファイル)を攻める。暗号化が守るのは「路上」で、両端は平文。
**Q4**: 端点にも届かない。暗号化トラフィックからまだ何を絞り出せるか。
**A4**: 「トラフィック分析/メタデータ」の次元へ方向転換:内容が読めなくても、誰が誰と通信しているか、頻度、データ量、タイミングパターンから、トポロジ、身分、挙動、トリガー関係を推測できる。暗号文のメタデータは暗号化されていない。
**Q5**: いつ暗号化トラフィックのこの線をきっぱり放棄するか。
**A5**: 端点の足場がなく、ダウングレードできず、メタデータも実行可能なインテリジェンスを出せない時、暗号化トラフィック軸の ROI は極めて低い。保留にし、端点/身分/アプリケーションを攻める他の直交軸に戻るべき。

### 情報収集:アセットの広さ vs 単一アセットの深さ
**Q1**: 偵察段階で、アセットをできるだけ広く敷くべきか、一つを捕まえて力いっぱい掘るべきか。
**A1**: これは偵察の中の直交する取捨。広さ(アセット/サブドメイン/ポート/API の数)は攻撃面の大きさを決める。深さ(単一アセットのフィンガープリント/バージョン/設定詳細)は単点の利用可能性を決める。早期は広さ優先で全景を建て、柔らかい点を見つけたら深さに切り替える。
**Q2**: 広さの収集をどこまでやったら深さに転じるべきか。
**A2**: アセットリストに明らかな「柔らかい信号」(旧バージョン、非標準のサービス、テスト/一時アセットの疑い)が出たら、即そのアセットに深さを切り替える。広さを完成させるために時間窓を逃さない。
**Q3**: 深さのフィンガープリントが詰まった(より多くの詳細を取れない)場合は。
**A3**: 「認証状態/対話状態」の深さへ方向転換:多くの詳細はログイン後、または深い対話の後で初めて露出する。「歴史次元」へも方向転換:このアセットの過去の形態(履歴レコード、キャッシュ、旧バージョンの残存)が今は隠された情報を漏らすかもしれない。
**Q4**: 広さも深さもやったが入口を見つけられない。どこへ方向転換するか。
**A4**: 「関連の次元」へ方向転換:収集済みのアセットを関連分析する。命名規則、共有証明書/インフラ、アカウント再利用パターン。単一アセットに穴がなくても、アセット間の「関係」に入口が隠れていることが多い(一つのアセットの情報が別を解錠する)。
**Q5**: 偵察が無限に拡張して収まらないのをどう防ぐか。
**A5**: 偵察には「足りれば止める」判定基準を持つ:既存の攻撃面が次のステップの行動を支えるのに十分になったら、収集を止めて動く。情報収集は意思決定に奉仕するもので、目的そのものではない。

### スキャン無結果:スキャナを替える/辞書を替える/視点を替える
**Q1**: ツールでディレクトリ/脆弱性/ポートをスキャンしたが、何も出なかった。本当に何もないのか。
**A1**: 「スキャンで出ない」には三つの直交する原因がある:ツールの能力不足、辞書/ルールの不一致、視点の誤り(未認証 vs 認証状態)。payload だけを替えず、まずどの層の問題かを診断し、それから対応する直交軸を替える。
**Q2**: どれを先に疑うか。
**A2**: 先に「視点」を疑う。同じ対象でも、匿名スキャンと正規の身分を一つ持ってスキャンするのとでは、結果が天と地ほど違う。任意の低権限身分を得て再スキャンすると、往々にしてそれまで見えなかった API/ディレクトリ/機能が一片現れる。
**Q3**: 視点を替えても空。何を替えるか。
**A3**: 「辞書/ルールの的の絞り方」を替える:汎用辞書は特定の技術スタック/命名習慣には往々にして無効。識別済みの技術スタック、言語、フレームワーク、対象の命名規則に基づいて辞書をカスタマイズする。考えなしに大辞書をかけない。
**Q4**: ツール、辞書、視点を全て替えても結果ゼロ。どこへ方向転換するか。
**A4**: 「手作業/プロトコルネイティブ」の次元へ方向転換:自動化ツールには体系的ブラインド領域がある(非標準レスポンス、多段対話が必要、文脈依存のロジック)。手作業でプロトコルネイティブに対話し、ツールが見落とす微細な差異を観察する。あるいは攻撃面がそもそもここにない。上層に戻って直交軸を選び直す。
**Q5**: 「スキャナの空結果への迷信」をどう避けるか。
**A5**: スキャナはそれが知っているパターンしかカバーしないと常に覚える。空結果は「既知パターンが命中しなかった」ことだけを証明し、「脆弱性がない」ことを証明しない。空結果を「終了信号」でなく「次元変更信号」として扱う。

### Payload が WAF/フィルタリングに遮られた:エンコーディングを替えるか次元を替えるか
**Q1**: payload を送るとすぐ WAF に遮られる。変形バイパスを続けるか、発想を替えるか。
**A1**: まず二層を分ける。「エンコーディング/変形を替える」はまだ同じ軸の上(WAF とルールライブラリを競う)にあり、往々にして軍備競争に嵌る。本当の次元変更は payload をそもそも WAF を通さないか、WAF が検知しない別の類の攻撃に替えること。まずバイパス試行に上限を設ける。
**Q2**: 変形バイパスを試すべきか、どこまで試すか。
**A2**: 有限の数ラウンド(エンコーディング、大文字小文字、コメント、チャンク分割、パラメータ汚染)を素早く試す価値はある。ただし信号が全く変わらないなら、ルールが非常に硬いことを示す。適時に手を引く。予算全体をルールエンジンとの硬直に消費しない。
**Q3**: 「payload を WAF を通さない」にはどうするか。
**A3**: 「経路/入口」の次元へ方向転換:WAF は通常特定の入口(対外 Web など)しか遮らない。WAF を通らない経路を探す。内部 API、他のポート、他のプロトコル、オリジンサーバー直連、非標準入口。同じ脆弱性を、無防備の入口に替えて打ち込む。
**Q4**: 全入口に WAF がある。全体としてどの直交次元へ方向転換するか。
**A4**: 「脆弱性の類」の次元を替える:WAF はインジェクション類の特徴のマッチが得意だが、ビジネスロジック脆弱性、権限外アクセス、競合、認証欠陥にはほぼ無感覚。WAF が得意に遮るインジェクション類を放棄し、WAF が見えないロジック類脆弱性へ転じる。
**Q5**: 次元を替えるべきかバイパスを続けるべきかを早めに判断するには。
**A5**: 最初の数ラウンドの変形後、「遮断挙動が完全に一致し、放行の兆候が一切ない」なら、ルールライブラリのカバレッジが十分と判定し、すぐ入口か脆弱性の類を替える。終わりのないエンコーディング変種ループに入らない。

### 認証情報はあるがログインできない:認証の次元を替える
**Q1**: 有効そうな認証情報を一組仕入れたが、対象のログイン点が認めない。どうするか。
**A1**: 急いで認証情報が無効と判定しない。「ログインできない」は「間違ったドアにログインしている」かもしれない。同じ一組の認証情報でも、プロトコル/サービス/入口が違えば受け入れ度が違う。ここで認めなくても、同じ身分源を受け入れる別の入口/プロトコルを試す。
**Q2**: 先に何を替えるか。
**A2**: 先に「認証入口」を替える:同じ身分が Web、管理口、遠隔管理プロトコル、API、他の同ドメインサービスで使えるかもしれず、各入口のポリシー(MFA、ソース制限、ロック)は異なる。ポリシーが最も緩く、かつこの一組の認証情報を受け入れる入口を探す。
**Q3**: 各入口が全て MFA/追加因子を要求する場合は。
**A3**: 「非対話型認証」の次元へ方向転換:多くのシステムのサービス間認証、API トークン、キー、チケットは MFA を通らない。認証情報で非対話の認証情報(トークン/チケット/キー)を交換し、それでアクセスする。人機対話の第二因子を迂回する。
**Q4**: 認証情報が全入口で拒否された。どこへ方向転換するか。
**A4**: 「認証情報の形態変換」の次元へ方向転換:あなたの手元にあるのは平文ではなく hash/チケット/キーかもしれず、「入力」ではなく「パス」の方式で使う必要がある(pass-the-hash/ticket 系の発想)。あるいはそれは別の身分ドメインに属する。「この認証情報をどう使うか」の次元を替えるのであり、それを放棄するのではない。
**Q5**: 認証情報が本当に無効か、使い方が間違っているかをどう判断するか。
**A5**: エラーフィードバックの差異を見る:「アカウント不存在」「パスワード間違い」「ここではこのアカウントを許可しない」「追加検証が必要」は全く異なる信号。フィードバックの差異は、認証情報自体は有効だが用法/入口が間違っていることを教える。それなら認証の次元を替えるべきで、認証情報を捨てるべきではない。

### 対象に到達不能:ネットワーク経路の次元を替える
**Q1**: 対象ホスト/サービスが私の現在位置から全く ping/接続できない。ここまでか。
**A1**: 「到達不能」はネットワーク経路の次元の問題であり、対象が存在しないのではない。経路を替える:ソースアドレス/出口を替える、プロキシ/ハブを経由する、そこへ到達できる中間ホストを探す、またはそれが能動的に外向き接続する方向を利用する。到達可能性は「あなたがどこに立つか」に対して相対的。
**Q2**: まずフィルタリングされたのか本当にないのかをどう判断するか。
**A2**: 複数のプローブ方式で交差する(別のプロトコル、別のポート、別のソース)。「ホストが存在しない」「ホストはいるがポートがフィルタリングされた」「セグメント全体が隔離された」を区別する。診断がはっきりして初めて、どの経路次元を替えるべきか分かる。
**Q3**: ネットワーク隔離と確認した。どう迂回するか。
**A3**: 「踏み台/ハブ」の次元へ方向転換:あなたと対象の両方を同時に見られるホスト(マルチ NIC、セグメント跨ぎ、VPN ノード、要塞ホスト)を探し、それを中継として到達経路を建てる。到達不能は往々にして中継点が一つ欠けているだけ。
**Q4**: 中継できるホストが一つも見つからない。どの直交次元へ方向転換するか。
**A4**: 「逆方向到達」の次元へ方向転換:あなたは対象へ届かないが、対象はあなた、またはある公共点へ届くかもしれない。対象が能動的に発する接続(その外向き接続、コールバック、レポート)を利用し、「私がそれに接続する」を「それが私に接続する」に反転して、インバウンドの到達不能を迂回する。
**Q5**: 到達不能な対象で空回りするのをどう避けるか。
**A5**: 中継もなく、対象にも外向き接続行動がなく、しかもそれが重要経路上にないなら、保留にし、あなたが到達できる他のノードを攻める。横展開で「現在位置」を徐々に変えてから戻る。到達可能性はあなたの足場とともに変わる。

### 単一の脆弱性類を尽くした:類の列挙を替える
**Q1**: インジェクション類(SQLi/コマンドインジェクションなど)を頭から尾まで試したが全くない。次は。
**A1**: あなたは脆弱性類空間の一つの類しか尽くしていない。類を替えるのは最も直接的な直交列挙:インジェクション類→認証/セッション類→認可/権限外アクセス類→ロジック/業務類→デシリアライズ/ファイル類→設定/情報漏えい類。一類が空になったら次類へ跳ぶ。一類の中で繰り返さない。
**Q2**: 次にどの類を試すかをどう決めるか。
**A2**: 「対象の技術スタックとの一致度」で選ぶ:対象が何の言語/フレームワークかで、そのスタックの高発の脆弱性類を優先試行する(あるスタックはデシリアライズ高発、あるスタックはテンプレートインジェクション高発)。脆弱性類を技術スタックに一致させ、盲目的に巡らない。
**Q3**: よくある類を全て試したがまだない。まだ替えられる類はあるか。
**A3**: 「組み合わせ/チェーン」の次元へ方向転換:単一類に高危険の穴がなくても、二、三個の低危険の穴(情報漏えい+権限外アクセス+ロジック欠陥)を組み合わせるとチェーンになるかもしれない。「一つの大穴」を探すのをやめ、「繋げられる小穴」を探す。
**Q4**: 全ての脆弱性類を列挙し尽くして確かにない。どこへ方向転換するか。
**A4**: 「この対象本体の脆弱性を打つ」という大軸がほぼ尽きたことを示す。全く別の大次元へ跳ぶべき:認証情報/身分軸、サプライチェーン軸、人/フロー軸、あるいは対象を替える(依存/上流/隣接サイト)。脆弱性類の尽きは「攻撃面を替えるのであって脆弱性を替えるのではない」という信号。
**Q5**: 繰り返し列挙しないようどう記録するか。
**A5**: 「脆弱性類 × 入口点」のカバレッジ表を維持し、各マスに試したか、結果はどうかを記す。表は、あなたが焦りの中で試し済みの類に繰り返し戻るのを防ぎ、注意力を未カバーのマスへ追い込む。

### ブラックボックスで固着:ホワイトボックス/ソース/文書の次元へ転換
**Q1**: 純ブラックボックスで長く推測しても対象の内部ロジックが読み解けない。直交する情報源はあるか。
**A1**: ある。ブラックボックス(外部挙動だけを見る)は一つの情報次元。ホワイトボックス(ソース/バイナリ/文書/設定)は直交する別の次元。認可範囲内で、対象のオープンソースコンポーネントのソース、クライアントコード、API ドキュメント、エラー詳細を取れるなら、「推測」を「読む」に変える。
**Q2**: ブラックボックスの下でどうホワイトボックスに近づくか。
**A2**: まず「半ホワイトボックス」情報を絞り出す:フロントエンド JS、モバイル/クライアントの逆コンパイル、公開された同型のオープンソースコンポーネントのソース、漏えいした文書/設定、詳細エラー。これらは内部構造の一部を見せてくれ、ブラックボックスの推測空間を大幅に縮める。
**Q3**: ソース/クライアントを得た後、重点的に何を見るか。
**A3**: ブラックボックスでは見えないものを見る:隠し API とパラメータ、認証/認可の実装詳細、危険な関数呼び出し、ハードコードされた経路/キーの手がかり、入力検証の具体的ロジック。ソースは「どこに穴があり得るか」を直接指し示す。
**Q4**: ホワイトボックス情報が全く取れない(クローズドソース、漏えいなし)。どこへ方向転換するか。
**A4**: 「挙動差分」の次元へ方向転換:大量の制御された入力で出力の微細な差異を観察し、内部ロジックを逆算する(ブラックボックスリバース)。あるいは同類のオープンソース実装を攻め、その既知の問題でクローズドソース対象の類似欠陥を推測する。「得られるホワイトボックス」で「対象のホワイトボックス」を代替する。
**Q5**: ホワイトボックス情報はミスリードしないか。
**A5**: する。ソース/文書はオンラインの実際のデプロイバージョンと一致しないことがある。ホワイトボックスは仮説を与え、必ずブラックボックスに戻ってオンラインの実挙動を検証しなければならない。二つの次元は互いを検証し、一方だけを信じない。

### 静的防御が強い:実行時/メモリ/プロセスの次元へ転換
**Q1**: 対象ディスク上のもの(ファイル、バイナリ)が全て署名検証/読み取り専用保護で、静的に変更できない。どうするか。
**A1**: 「実行時」の次元を替える。静的防御が守るのは「足場確保されたもの」。プログラムが実行時にメモリ内の状態、ロードされたモジュール、プロセス間通信、一時データは往々にして無防備。ファイルは動かせなくても、メモリ/プロセスは往々にして動かせる。
**Q2**: 実行時の次元で具体的に何を攻めるか。
**A2**: プロセスメモリ内の平文データ/キー/セッション、ハイジャック可能な動的ロード(ライブラリ/パス/環境)、プロセス間通信チャネル、実行時に注入できる拡張点。静は死んでおり、実行時は生きている。生きている場所は縫い目が多い。
**Q3**: 実行時も EDR に監視されている(挙動監視)場合は。
**A3**: 「正規機能の濫用」の次元へ方向転換:注入せず、異常挙動をせず、対象自身が提供する、許可された機能(内蔵スクリプト、プラグイン、設定、通常の管理 API)で目的を達成する。EDR が見張るのは「異常」。あなたは「正常」なもので働く(living-off-the-land)。
**Q4**: 静的、実行時、EDR が全て硬い。どの直交次元へ方向転換するか。
**A4**: 「人/認証情報」の次元へ方向転換:端末防御が極致に達した時、最も柔らかいのは往々にしてその端末を使う人と彼が保持する認証情報。端末の技術的突破を放棄し、正規の認証情報を取得して「正常なユーザーとして」操作する。防御に区別させない。
**Q5**: 静的を攻めるか実行時を攻めるかをどう判断するか。
**A5**: 対象の価値が「保存されたもの」か「実行中のもの」かを見る。欲しいのが足場確保されたファイル/永続化→静的軸。欲しいのが実行中のキー/セッション/復号データ→実行時軸。対象の形態がどの軸を攻めるかを決める。

### ユーザー空間が制限された:カーネル空間か他のユーザー空間サービスへ転換
**Q1**: ユーザー空間でサンドボックス/権限に固く制限され、できることが極めて少ない。どう突破するか。
**A1**: 二つの直交方向:下へ(カーネル空間/システム層)隔離境界を突破するか、横へ(同層の他のユーザー空間サービス/プロセス)制限のより緩い実行体を探す。必ずしも下へカーネルを突く必要はない。隣の緩いサービスがより取りやすいかもしれない。
**Q2**: 先に横か、先に下か。
**A2**: 先に横(コストが低く、リスクが小さい):同一ホストに権限がより高く、制限がより緩いサービス/プロセスで、対話またはハイジャックできるものがあるか。その手を借りて働ければ、自分で境界を硬突破する必要がない。
**Q3**: 横に借りられるサービスがない。下へどう進むか。
**A3**: 「境界脆弱性」の次元へ方向転換:サンドボックス/コンテナ/権限隔離の実装欠陥、低権限に露出した高権限 API、共有カーネルのエスケープ面。下への突破は難しいがリターンが大きい。安定性を評価してから動く。
**Q4**: カーネル/境界も突けない。全体としてどの直交次元へ方向転換するか。
**A4**: 「別の実行環境への横展開」の次元へ方向転換:現在のこの制限された環境は行き止まり。それを踏み台として扱い、別の制限のより緩いホスト/コンテナ/環境へ到達する方法を考える。そこでもう一度展開する。死んだ環境で硬突破するより環境を替える方が実際的。
**Q5**: 制限された環境で、この意思決定をするためにまず何を収集すべきか。
**A5**: まず「制限の形状」を把握する:何を読めるか、何に接続できるか、どんな隣接プロセス/サービスがあるか、外向き接続を発起できるか。制限の境界を描き出せば、横/下/環境替えの三本の直交する道のどれが実行可能かがはっきりする。

### メタ層:「偽の経路」の識別、いつ方向全体を放棄するか
**Q1**: 一本の線に長く投入し、それが「ウサギの穴」(見た目は見込みがあるが実は行き止まりかおとり)ではないかと疑い始めた。どう判断するか。
**A1**: これは最上位の次元変更意思決定。判定基準:①持続投入しても情報利得がゼロに近づく ②各「進展」が、対象に近づかないさらなる投入を必要とするサブタスクを指す ③手がかりが過度に滑らか/作為的(ハニーポット誘導の疑い)。満たせば方向全体を疑うべきで、さらに加算しない。
**Q2**: 「難しいが本物」と「偽の経路」をどう区別するか。
**A2**: 「この道が通じたとしても、最終目標に本当に近づくか」を問う。本物の経路の各ステップはあなたと目標の距離を縮める。偽の経路はあなたを忙しくさせるが近づかない。「目標までの距離が単調に減少するか」で健康診断する。「やることがあるか」ではない。
**Q3**: ハニーポット/おとりを疑う場合は。
**A3**: 交差検証する:ハニーポットは往々にして細部が非自己整合(過度に開放的、データが非現実的、環境の他の部分とスタイルが合わない、実業務のノイズが欠如)。「環境の一貫性」の次元へ転換して精査する。全体環境と調和しない「柔らかい対象」は高度に警戒すべき。頭から突っ込んで自分を露出しない。
**Q4**: この方向全体が行き止まり/罠と確認した。どこへ方向転換するか。
**A4**: 最初の「直交軸リスト」に戻り、この方向を丸ごと取り消す(その全サブ経路とともに)。リストからその失敗根因と無関係な一本の軸を選んで再起動する。鍵は「全体を放棄」することであり、廃れた方向の中で変種を探し続けないこと。それこそウサギの穴があなたにさせること。
**Q5**: 制度として偽の経路に嵌るのをどう避けるか。
**A5**: 事前に「損切り契約」を設ける:各大方向は着手前に「どんな現象が出たらそれを放棄するか」を書く。事前の放棄条件があれば、その中で埋没コストに縛られた時も、事前の理性で自分を引き出せる。
**Q6**: 頻繁に疑うと、何も深く踏み込めなくならないか。
**A6**: 「マイルストーン」でバランスする:各道に「期限に必ず現れなければならない実際の進展」のチェックポイントを数個設ける。期限に進展があれば大胆に深く入る。期限に進展がなければ断固として次元を替える。盲目に執着もせず、神経質に乱れ替えもしない。チェックポイントのリズムで直交の方向転換を管理する。
