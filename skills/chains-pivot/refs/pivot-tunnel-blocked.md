# ネットワーク到達可能性 · 転送リンクが不安定または中間装置に遮断されたときのトラブルシューティングと方向転換

### まず層別に特定する:リンク問題かアプリケーションプロトコル問題か
**Q1**: トンネルは構築直後は使えたが、しばらくするとコマンドが落ち始め、返却が欠ける。まずどこから着手するか?
**A1**: 急いでツールを替えない。OSI の層に沿って下から上へ層別に排除する:まず L3 が通るか(到達可能か/パケットロスか)、次に L4 が安定して接続を確立できるか、次に TLS/プロトコルのハンドシェイクが完全か、最後にアプリケーション層。判定基準は「どの層が最初に異常を出すか」が責任層を決める。
**Q2**: L3 がジッターし、L4 も頻繁に half-open なら、中間装置と断定できるか?
**A2**: 直接結論を出せない。まず両端のローカルリソース問題(fd 枯渇、メモリ圧迫、ルーティングのジッター)を排除する。両端のローカルが安定し、単一ホップは到達可能なのに接続追跡テーブルが異常に落ちる場合にのみ、中間ボックスのセッション老化または状態機械の制限を疑う。
**Q3**: 層別に排除しても根本原因が見つからない場合は?
**A3**: この道は通じない。「受動観測次元」へ切り替える。自前のトンネルでのトラブルシューティングをやめ、トラフィック特徴(パケット長分布、時系列、再送パターン)を受動的に収集し、「リンクが誰に見抜かれたか」の観点から逆算する。プロトコル内で堂々巡りしない。
**Q4**: 判定基準で最も見落としやすいものは?
**A4**: 「対照群」である。既知の安定したベースラインチャネルが1本もないと、すべての異常が錯覚の可能性がある。まず同セグメントに最小限のベースライン接続を1本作り、それから対象トンネルと比較する。

### ランダムなパケットロスと選択的遮断の区別
**Q1**: コマンドが通るものと、直接固まるものがある。ランダムなパケットロスか、コンテンツがトリガーか?
**A1**: 最小の再現集合を使う:同じコマンドを N 回繰り返し、失敗率が均一ならリンク品質の問題。特定のコマンドが 100% 失敗し、他が 100% 成功するなら、コンテンツがトリガーで、中間装置がキーワード/特徴マッチングを行っている。
**Q2**: 特徴マッチングであることをさらに検証するには?
**A2**: 二分探索。失敗コマンドを半分に分けて測り、トリガーとなる文字/バイト列を特定する。判定基準は「最短トリガー列」である。これ以上短くできない断片が特徴ルールのヒット点である。
**Q3**: 特徴マッチングが平文層にある場合、どう回避するか?
**A3**: 上層にもう一層エンコード/暗号化をかければ特徴を隠せる。ただし性能低下と、新しいトラフィックフィンガープリントを生まないかを評価する。
**Q4**: 暗号化を加えても識別される場合は?
**A4**: 直交する次元へ切り替える。「コンテンツ層」で回避し続けるのではなく、担体プロトコル自体を変える(たとえばネイティブ TCP から合法業務プロトコルへの相乗りへ変える)。特徴マッチングの付け入る隙をなくす。

### 中間ボックスが SNI/平文キーワードフィルタリングを行うかの判定
**Q1**: TLS トンネルはハンドシェイクできるが、完了直後に切れる。SNI フィルタリングのようだ。どう確認するか?
**A1**: 対照テスト:同じ宛先 IP に対し、異なる SNI 値でハンドシェイクを発する。特定の SNI だけ全断で、他が正常なら、SNI のホワイト/ブラックリストが選別している。
**Q2**: SNI を替えても切られる場合は?
**A2**: 切断タイミングを観察する。ハンドシェイク終了直後に切れるか、データを数十バイト転送した後に切れるか。後者なら、識別しているのは証明書情報か ALPN であり、SNI ではない。
**Q3**: 全部替えても切れる場合は?
**A3**: 直交する次元へ切り替える。TLS という層を偽装の土台にするのをやめ、中間ボックスが通したがる既存の業務チャネルにトラフィックを落とす。船を借りて海に出る。
**Q4**: 方向転換後の判定基準は?
**A4**: 対象の担体プロトコルが、環境内に既存の通常業務トラフィックでなければならない。さもなければ「新規プロトコルの出現」自体が異常特徴になる。

### 外向き方向のポートホワイトリストの迅速な把握
**Q1**: 対象が少数のポートしか出網を許さない。どう最速で把握するか?
**A1**: 順序付きポートスキャン + 既知の一般的なサービスポート優先で、全ポートの盲スキャンをしない。判定基準は「どのポートが公衆/踏み台に届くか」をできるだけ早く得ることであり、完全な情報ではない。
**Q2**: 一般的なポートが全遮断で、個別の高位ポートだけ通る場合は?
**A2**: 通るポートを記録するが、それらが監査対象かを警戒する。高位ポートを故意に残し「ハニーポート」にしている環境がある。
**Q3**: 高位ポートまで遮断される場合は?
**A3**: アプリケーション層の出口へ方向転換する。L4 が厳重でも、環境内に HTTP プロキシやゲートウェイ強制の業務があれば、プロキシ経由で出られることが多い。焦点を「直結ポート」から「アプリケーション層ゲートウェイ」へ切り替える。
**Q4**: 外向き方向が完全に封鎖された場合は?
**A4**: 「内部から外部への能動的出網」を放棄し、直交する次元へ転換する:「すでに入ってきた合法トラフィック」(既存接続の反射利用、依存サービスのコールバック)から利用可能なチャネルを探す。

### TCP 長い接続が idle-timeout で切断される
**Q1**: トンネルが数分のアイドルで切れる。状態テーブルの期限切れのようだ。どう処理するか?
**A1**: アプリケーション層のハートビートを加え、間隔を中間装置の idle しきい値より小さくする。まず二分探索でしきい値を測り、ハートビートをしきい値の 1/2〜2/3 に設定する。
**Q2**: ハートビートを加えたら識別された場合は?
**A2**: ハートビートを業務パケットらしくする(ペイロード偽装、間隔にランダムなジッターを加える)。実在の業務パケットに寄生し、独立したハートビートをやめる。判定基準は「ハートビートに識別可能な周期的フィンガープリントがないこと」である。
**Q3**: ハートビートでも長い接続を維持できない場合は?
**A3**: 短い接続モデルへ切り替える。毎回の対話で新規接続を作るか、ステートレスな担体(ポーリング式チャネル)を使う。直交次元の切り替えで、対話速度を犠牲に安定性を取る。

### TLS フィンガープリントが識別されたときの方向転換
**Q1**: クライアント TLS フィンガープリントがブラックリスト入りした疑い。どう検証するか?
**A1**: 一般的なブラウザの TLS フィンガープリントに替えて同じ接続を発し、通ればフィンガープリント識別とほぼ確定できる。判定基準は「クライアントライブラリの切り替え = 結果の切り替え」である。
**Q2**: ライブラリ層での調整方向は?
**A2**: ClientHello をカスタマイズできるライブラリを使い、暗号スイート、拡張の順序、GREASE 値を主流ブラウザに揃える。要点は「全体の一致」で、1項目だけ変えるとかえって怪しい。
**Q3**: フィンガープリントを調整しても識別される場合は?
**A3**: 直交する次元へ方向転換する。裸の TLS トンネルを捨て、トラフィックを合法アプリケーションプロトコル(既存業務)に詰め、識別システムに既知の許可対象を見せる。

### HTTP プロキシ vs 直結の選択
**Q1**: 環境が HTTP プロキシを強制し、直結はすべて RST される。トンネルをどう設計するか?
**A1**: CONNECT チャネルを通し、コンプライアンス HTTPS 対象に偽装する。判定基準は、プロキシが任意のポート/ドメインへの CONNECT を許可するかで、制限されていれば許可リスト内のポートしか選べない。
**Q2**: プロキシが認証を要求する場合は?
**A2**: 環境内に既存の合法認証情報源(ブラウザキャッシュ、システムレベルのプロキシ設定)を優先して探し、闇雲に推測しない。なければ、NTLM/Kerberos の透過認証が使えるか評価する。
**Q3**: プロキシが少数のホワイトリストドメインしか許可しない場合は?
**A3**: 直交する次元へ転換する:「合法ドメイン/CDN を前置にする」考え方(概念的には:SNI と Host を許可ドメインにし、バックエンドを前置サービスが振り分ける)を採る。要点は、この手法の合法性とコンプライアンス境界を評価すること。
**Q4**: 前置の考え方も使えない場合は?
**A4**: 出網を完全に捨て、「内部横展開」へ方向転換する。現在のノードを終点とし、内部リソース(内部メール、内部アーティファクトリポジトリ)経由で迂回通信する。

### 単方向のみ到達可能 —— リバース接続が確立できない
**Q1**: 対象が能動的にコールバックできず、受動的に受け付けるしかない。トンネル設計をどう変えるか?
**A1**: 「対象が能動的に出る」から「こちらが能動的に入る」へ変え、バンド待ち受けまたはポーリングモデルを採る。判定基準は、対象側に長期駐留できる待ち受け点が存在するかである。
**Q2**: 待ち受けポートがすぐ閉じられる場合は?
**A2**: 寄生モードを採る。既存サービスのポート(たとえば Web サービス)に付着してトンネル入口を提供し、異常ポートの露出を減らす。
**Q3**: 待ち受けを完全に開けない場合は?
**A3**: ポーリング次元へ切り替える。対象側が周期的に公共の書き込み可能媒体から命令を取る(たとえば特定のオープンなストレージやメッセージチャネル)。「リアルタイム双方向」を完全に捨て「最終的到達可能」を取る。

### バンド vs リバース SOCKS の取捨選択
**Q1**: バンドを使うか、リバースを使うか?
**A1**: 境界方向を見る。現在のノードが能動的に出網できる → リバースの方が単純(能動的にコールバックする)。現在のノードが受動的にしか入れない → バンドで、外部から接続する。判定基準は「どちらの方向の接続が厳格な防御をピボットせずに済むか」である。
**Q2**: 両方できる場合、どう選ぶか?
**A2**: 安定性優先ならリバース(自己修復が簡単)、隠蔽性優先ならバンド(外向きの新規接続を生まない)。衝突する場合は、対象場面がどちらの検知に敏感かを見る。
**Q3**: 両方試しても不安定な場合は?
**A3**: アプリケーション層トンネル(HTTP セマンティクスベース)に方向転換し SOCKS を置き換える。性能を多少犠牲にして業務トラフィックとの同型性を得る。

### 多層踏み台下のレイテンシ膨張
**Q1**: 3〜4層の踏み台後、レイテンシが大きく操作がジッターする。どう最適化するか?
**A1**: まず各ホップのレイテンシを測り、最大のボトルネック区間を見つける。判定基準は「単一ホップのレイテンシが他より突出していないか」である。突出していればそのホップを最適化(プロトコル変更、ノード変更、経路変更)、均等に高ければトポロジ自体の問題。
**Q2**: 中間層で「統合」する方法はないか?
**A2**: 不要な暗号化/復号のラウンドを減らし、接続を再利用し、コマンドをバッチ化する。核心は round-trip 回数を減らすことで、単回の速度を上げることではない。
**Q3**: 限界まで最適化しても遅い場合は?
**A3**: 次元を変える:ファイルレベルの非同期配信に変える。たとえばスクリプトを前もって投げ、結果をバッチで回収する。リアルタイム対話にしない。遅いが制御可能。

### 内部 DNS 分離で解決が通らない
**Q1**: トンネルは通るが、ドメインが解決できず失敗する。DNS が出られないのか?
**A1**: 現在どの DNS を使っているかを明確にする。クライアントが内部 DNS を指したまま、その内部 DNS が外網へ再帰しないなら、それは正常。判定基準は「対象 IP に直接到達可能か」である。
**Q2**: 内部 DNS が一部のドメインしか解決しない。どう使うか?
**A2**: トンネル経由で解決リクエストを「送り出し」、結果を取って戻す。DNS リクエストをアプリケーショントラフィックとして既設のトンネルに流し、本機 DNS を直接出網させない。
**Q3**: DNS が強制遮断され、解決リクエストも出せない場合は?
**A3**: 次元を変える:IP で直接通信し、ドメインを捨てる。あるいは逆に、DNS 自体を隠蔽チャネルとしてデータを運ぶ(概念上)。ただし帯域が極小で、DNS 監査に発見されやすい。

### UDP チャネルが NAT/ファイアウォールに殺される
**Q1**: UDP トンネルが十数秒で無応答になる。誰に殺されたか?
**A1**: NAT テーブルの UDP セッション老化は通常 TCP よりはるかに短い。まず NAT/ファイアウォールの UDP タイムアウトを確認する。判定基準は「発信パケットは出る、受信パケットが来ない」→ 回程マッピングの失効の可能性が高い。
**Q2**: 保活で救えるか?
**A2**: 救えるが、保活間隔を最短の中間装置 UDP 老化時間より小さくする。エンドツーエンドで測定し、推測しない。
**Q3**: UDP が厳格に遮断される場合は?
**A3**: TCP 担体へ転換する。UDP トンネルは制限の多いネットワークではそもそも第一候補ではなく、レイテンシに敏感で UDP が許可されている場合のみ使う。これは戦術的な直交切り替えである。

### トンネル内 MTU 分割で大パケットが落ちる
**Q1**: 小さい対話は問題ないが、大ファイルを送ると切れる。MTU の可能性か?
**A1**: 段階的に大きくしたプローブパケットで PMTU を測る。判定基準は「あるサイズ以下は全通、以上は全断」である。
**Q2**: 中間ボックスが ICMP を禁じ PMTU 探索が失敗する場合は?
**A2**: トンネル端点で手動で MSS を安全値にクランプする。非効率でも、固まるよりはまし。
**Q3**: MSS をクランプしても不安定な場合は?
**A3**: 次元を変える:大オブジェクトは「分割 + レジューム」のアプリケーション層プロトコルに乗せ、L4 の一括転送に依存しない。パケットが落ちても継続できる。

### WebSocket / HTTP2 担体 vs ネイティブ TCP
**Q1**: 裸の TCP でなく WebSocket/HTTP2 を使うのはいつか?
**A1**: 環境が HTTP(S) しか許可しないとき。WebSocket は上下とも持続化でき、HTTP2 は多重化で接続数を節約する。どちらも「Web ページに見える」。
**Q2**: どちらを選ぶか?
**A2**: 長期の双方向対話が必要 → WebSocket。既存の Web 業務と混流したい → HTTP2 の方が自然。判定基準は「どちらが対象環境にすでに大量に存在するか」である。
**Q3**: どちらも使えない場合は?
**A3**: HTTP ポーリング(短い接続、プル式)へ退化する。遅いが汎用的で、最低限の保証になる。

### 暗号化トラフィックの特徴異常がトラフィック分析を誘発する
**Q1**: トンネルは TLS なのに、なぜ不審と判定されるか?
**A1**: TLS はコンテンツを暗号化するが、タイミング、パケット長、方向分布は暗号化しない。側チャネル分析はこれらの統計特徴からトンネルを識別できる。判定基準は「総トラフィックの正規化度合い」である。
**Q2**: 統計異常をどう下げるか?
**A2**: パディング、ジッターを加え、合法業務のノイズを混ぜる。核心は統計分布を周囲の業務トラフィックに揃えること。
**Q3**: 揃えるコストが高すぎる場合は?
**A3**: 次元を変える。隠蔽を追わず、「許可された時間ウィンドウ」内でのバースト使用に変える。空間次元ではなく時間次元で隠蔽する。

### トンネル同時接続数が中間ボックスにレート制限される
**Q1**: 開いたセッション数がある値を超えると新規接続が張れない。レート制限のようだ。どう対処するか?
**A1**: まず臨界値を測る。判定基準は「新規接続の失敗点」である。見つけたら同時接続上限を臨界値の 70% 以下に下げる。
**Q2**: 業務がより高い同時接続を要する場合は?
**A2**: 多重化(単一 TCP 上で複数の論理ストリーム)を使い、複数の TCP にしない。
**Q3**: 多重化が異常と識別される場合は?
**A3**: 次元を変える:多点分散。接続元を複数のソースノードに分散し、各ソースをしきい値内に収める。

### 出口 IP が一時的に遮断された後の縮退
**Q1**: 出口 IP が突然対象側に ban された。どう優雅に切り替えるか?
**A1**: まず遮断の次元を判定する:特定のソース IP が ban されたのか、特定の行動がトリガーした ban なのか。判定基準は「IP を変えると即座に回復するか」である。
**Q2**: 行動トリガーの ban なら、IP を変えても再 ban されるか?
**A2**: 問題は IP でなく行動にある。まずレート、フィンガープリントを直してから IP を変える。さもないと新 IP が秒で落ちる。
**Q3**: 短期でトリガー原因を特定できない場合は?
**A3**: 次元を変える。現在のリンクを一時停止して「冷却」を働かせ、同時に他の次元(他のプロトコル、他のノード)で進める。観察されている同じリンクで露出を続けない。

### 対象が少数のドメイン/CDN しか許可しないときの方向転換
**Q1**: 外向き方向が少数のドメイン(通常は大手 CDN)にしか行けない。トンネルはどこへ行くか?
**A1**: コンプライアンス担体を借りる。トラフィックを既に許可されたコンプライアンスサービスのチャネルに詰める(概念上の「借道」)。新しい出口を掘らない。判定基準は、選んだ担体が「表面上はそれ自身であり続ける」ことである。
**Q2**: 借道自体がコンプライアンスのレッドラインに触れないか?
**A2**: 認可範囲を見る。演習ではその手法が認可ホワイトリスト内かを明確にし、なければ別案に替える。
**Q3**: 完全に借道できない場合は?
**A3**: 次元を変える。出網せず、内部通信に転換し、内部横展開を「一時的到達可能」として使う。リアルタイム性は劣るがリスクは低い。

### 中継踏み台がダウンした後のリンク自己修復
**Q1**: 中間のある踏み台が落ち、トンネル全体が断。自己修復するにはどう設計するか?
**A1**: アーキテクチャから冗長を導入する。多踏み台の並列、クライアントの失敗再接続と経路切り替え能力。判定基準は「任意の1ホップが落ちても自動縮退できるか」である。
**Q2**: 冗長コストが高すぎる場合は?
**A2**: 段階化する。重要なリンクだけ冗長にし、使い捨てのタスクではしない。過剰設計しない。
**Q3**: 冗長ノードが全部落ちた場合は?
**A3**: 次元を変える。最も原始的な通信チャネル(オフライン配信、非同期取得)へ戻る。リアルタイムを追わず、情報が届くことだけを求める。

### トンネル端点のクラッシュ vs ネットワークジッターの区別
**Q1**: トンネルが突然途絶した。端点が落ちたか、ネットワーク事故かをどう素早く判定するか?
**A1**: 両端から同時に見る。片端が生きてデータを受信でき、他端のプロセスが消えている → クラッシュ。両端のプロセスがいるがデータが通らない → ネットワーク。判定基準は「プロセス状態 + ポート待ち受け状態」である。
**Q2**: 片端しか見えない場合は?
**A2**: 帯外チャネル(短信、別トンネル)で他端の状態を確認する。推測に頼らない。
**Q3**: 帯外チャネルがまったくない場合は?
**A3**: 次元を変える。設計上「ハートビート以外の生存プローブ」を持つ。たとえば公共の読み取り可能媒体に定期的にノード状態を公開し、いつでも遠隔確認できるようにする。

### 認証型プロキシ(アカウント/パスワード必須)の対処
**Q1**: 内部ネットワークが認証プロキシを走らせ、認証情報なしでは出られない。どうするか?
**A1**: 既存の認証情報源(システムレベルの設定、ブラウザの永続化、開発ツールの設定ファイル)を優先して探す。判定基準は「現在の身分で既に透過的にプロキシを使える実体」である。
**Q2**: 平文の認証情報が見つからないが透過認証を利用できる場合は?
**A2**: トンネルにシステムレベルの HTTP クライアントを使わせ、認証を OS 統合層に任せ、自分で認証を処理しない。
**Q3**: 透過認証もだめな場合は?
**A3**: 次元を変える。このプロキシを通らず、内部リソースで非同期に飛び出す(たとえば出網できるサービスに代わりに担わせる)。

### DPI がトンネルプロトコルを識別する
**Q1**: 中間ボックスが DPI で、プロトコルシグネチャで直接遮断する。どうするか?
**A1**: 担体プロトコルを変えるか、プロトコル難読化を行う。判定基準は「対象 DPI ルールベースの網羅度」で、汎用プロトコルはシグネチャが多く、独自プロトコルは少ない。
**Q2**: プロトコル変更のコストが高い場合は?
**A2**: 既存のコンプライアンスプロトコルを外殻にする(HTTP2/QUIC/gRPC など)。内部は独自にする。
**Q3**: DPI がアプリケーションのペイロードセマンティクスまで網羅する(signature より深い)場合は?
**A3**: 次元を変える。隠さず、「低頻度・断続・単点」の通信に変え、DPI に異常と判定させる十分なサンプルを与えない。

### ポートノッキング / 単一パケット認可環境
**Q1**: 対象ポートが対外的に沈黙し、先にノックしたときだけ開く。どう把握するか?
**A1**: 大半の環境はこの仕組みを使わない。ただし疑うなら「あるシーケンスの後にポートが開く」パターンがないか観察する。判定基準は、ブルートフォースではなく合法ユーザーの行動プロファイルによる。
**Q2**: ノックシーケンスを入手できない場合は?
**A2**: 闇雲に推測しない(間違えるとかえって記録される)。認可済みのマシンやユーザーを優先して探し、そのアクセス経路を引き継ぐ。
**Q3**: ノックシーケンスを完全に入手できない場合は?
**A3**: 次元を変える。この入口を捨て、旁路(ノック保護のない別サービス)を探す。

### クライアント NAT 種別の不一致(対称 NAT)
**Q1**: P2P トンネルのホールパンチングが失敗する。対称 NAT を疑う。どう確認するか?
**A1**: 外部サービスで、異なる宛先から見える公衆ポートが一致するかを見る。不一致 → 対称 NAT で、ホールパンチングは極めて難しい。
**Q2**: 強引にホールパンチングできるか?
**A2**: 確率が極めて低く、投入に見合わない。判定基準は投入対効果である。
**Q3**: ホールパンチングできない場合は?
**A3**: 次元を変える。中継サーバーを導入して relay し、直結性能を犠牲に接続性を得る。

### IPv6 専用セグメントまたはデュアルスタックの乱れ
**Q1**: クライアントに v4 と v6 があり、ある対象は v4 が通り v6 が通らない(または逆)。どう処理するか?
**A1**: 現在の解決がどちらのアドレスファミリを通ったかを明確にする。判定基準は getaddrinfo の返却結果である。デュアルスタックが常に兜底できると決めつけない。
**Q2**: デュアルスタックの乱れで間欠的な失敗が起きる場合は?
**A2**: 一方のファミリ(通常は安定側)に強制し、自動選択を切る。
**Q3**: 対象が v6 のみで直達できない場合は?
**A3**: 次元を変える。デュアルスタックの踏み台でプロトコル変換するか、アプリケーション層ゲートウェイでファミリを跨いで転送する。

### VLAN 分離/レイヤー2分離の方向転換
**Q1**: 同じ物理セグメントだがレイヤー2分離で ARP が通らない。どう跨ぐか?
**A1**: レイヤー2分離下では L3 が切り口になる。ゲートウェイ装置かルーティングノードを見つけ、ブリッジさせる。判定基準は「転送を引き受ける L3 転送装置があるか」である。
**Q2**: ゲートウェイ装置が転送を許さない場合は?
**A2**: 同じセグメントで信頼されているホスト(ホワイトリスト内)を探し、プロキシ踏み台にする。
**Q3**: 全ホストが厳格に分離されている場合は?
**A3**: 次元を変える。レイヤー2横展開を捨て、より上位の共有リソース(公共ストレージ、公共サービス)で間接的に到達する。IP 到達可能性に依存しない。

### 中間装置の TCP リセット(RST 注入)
**Q1**: 接続が常に同じ秒で RST される。RST 注入のようだ。どう確認するか?
**A1**: 両端でそれぞれパケットキャプチャし、RST がどちら側から出たかを見る。判定基準は「RST の TTL、シーケンス番号」が合法端と一致するか。不一致 → 中間注入。
**Q2**: 注入を確認したらどうするか?
**A2**: 暗号化で特徴ヒットを避ける(注入は平文マッチングに基づくことが多い)、または両端で不正 RST を無視する(制御された実験環境のみ)。
**Q3**: 暗号化後も注入される場合は?
**A3**: 次元を変える。担体をステートレスまたは擬似接続のプロトコル(合法担体上の UDP)にし、RST の付け入る隙をなくす。

### トンネルトラフィックの逆流(本機トラフィックの漏出)
**Q1**: トンネル構築後、本機の全トラフィックが誤ってトンネルを通る。逆に、重要なトラフィックが通らない。どうするか?
**A1**: ルーティングテーブルとポリシールーティングを確認する。判定基準は「トンネルを通るはずのトラフィックの次ホップがトンネル iface か」である。
**Q2**: ルーティングテーブルは正しいのに漏れる場合は?
**A2**: DNS 漏出か、一部アプリケーションがシステムプロキシを迂回している可能性がある。アプリケーション層を個別に監査する。
**Q3**: 漏出を完全に防げない場合は?
**A3**: 次元を変える。システムレベルのトンネルを使わず、重要なツール内だけにプロキシを注入する。汎用性を犠牲に制御性を得る。

### ICMP 出口のみ通る(ICMP tunnel)の取捨選択
**Q1**: ICMP 以外が全封鎖。ICMP トンネルはやる価値があるか?
**A1**: 対象ネットワークの ICMP セッション追跡の厳しさを評価する。判定基準は「ICMP echo に回程制限があるか」。回程が制限されると帯域が極小になる。
**Q2**: やる価値はあるが帯域が極小の場合は?
**A2**: 制御チャネル(命令送信、小状態の報告)専用にし、データプレーンは別の機会に回す。
**Q3**: ICMP もレート制限/監査される場合は?
**A3**: 次元を変える。ネットワークチャネルを完全に捨て、オフライン媒体か物理層チャネルに変える(コンプライアンス演習の範囲内のみで検討)。

### アプリケーション層ゲートウェイ(ALG)のパケット書き換えによるプロトコル錯乱
**Q1**: 特定のプロトコルが中間装置を通過するとパケットが不可解に変更される。ALG が手を加えているようだ。どうするか?
**A1**: パケットキャプチャで両端のペイロードを比較する。判定基準は「どのフィールドが変更されたか」。ポート、アドレスが書き換えられていれば → 典型的な ALG の挙動。
**Q2**: ALG を切れない(装置が自分の手にない)場合、どう回避するか?
**A2**: ペイロードを暗号化して ALG に読めなくし、書き換えさせない。またはポート/プロトコルを変えて ALG のトリガー条件を避ける。
**Q3**: 暗号化すると ALG が直接遮断する場合は?
**A3**: 次元を変える。ALG に狙われるプロトコルを捨て、環境で「最も平凡な」プロトコルを担体に選ぶ。

### ハニーポット/サンドボックス疑いのトンネル挙動
**Q1**: トンネルがあまりに順調で、コマンドがすべて即座に返る。かえって不審に思う。どう見分けるか?
**A1**: 応答の真実性を観察する:環境の「個性の痕跡」(ユーザー履歴、タイムゾーン、非標準設定)が妥当か。判定基準は「エントロピー」で、過度にきれいな環境はかえって怪しい。
**Q2**: 即断できないが疑いがある場合は?
**A2**: センシティブな操作を減らし、受動的な収集と軽量命令だけにし、手法をすべて露出しない。
**Q3**: ハニーポットの疑いが強い場合は?
**A3**: 次元を変える。現在の身分を即座に撤退し、別の独立したリンクへ切り替える。ハニーポットに自分のツールチェーン全体を観察させない。

### リンクコスト vs 隠蔽性のトレードオフ
**Q1**: 高隠蔽トンネルはコストが高く性能が悪い。いつ価値があるか?
**A1**: タスク段階を見る。下調べ段階では少し騒がしくてもよい(帯域優先)、重要な動作は必ず隠蔽する。判定基準は「発見される代償」である。
**Q2**: コストモデルはどう計算するか?
**A2**: 「リンク寿命」で測る。1回の動作が処分されずにどれだけ持つか。寿命が短ければ単純なリンクで素早く打って素早く引き、寿命が長ければ高隠蔽に投資する。
**Q3**: コストを判定しきれない場合は?
**A3**: 次元を変える。「階層リンク」を導入する:センシティブな操作は独立チャネル、通常の照会は共用チャネル。失われても互いに巻き込まない。

### 撤退と掃除:いつ現在のリンクを断固放棄するか
**Q1**: あるリンクが頻繁にジッターし、毎回修復しても短命。修復すべきか、捨てるべきか?
**A1**: 修復コスト vs 残存価値を計算する。判定基準は「直近3回の障害が収束するか」。収束しなければ捨てる。
**Q2**: 捨てた後、以前の動作が露出するのが心配な場合は?
**A2**: 撤退前に痕跡を掃除する(一時ファイル、プロセス、アカウント変更)。それからリンクを断つ。撤退は電源を抜くことではなく、秩序ある回収である。
**Q3**: 撤退後、入口を完全に失う場合は?
**A3**: 次元を変える。「リンク再構築」から「入口の再探索」へ移る。焼かれた同じ道で再開せず、偵察段階に戻って新しい面を探す。撤退は資源保護であり、失敗ではない。
