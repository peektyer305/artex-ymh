# ネットワーク到達可能性 · 単方向コマンドチャネルしかないときの内部ネットワークセグメントへの到達可能性の確立方法

### チャネル方向性の事前判定
**Q1**: コマンドを実行できるがエコーしか見えない入口を入手した。それが真の「単方向」なのか、「実は双方向だが測りきれていないだけ」なのか、どう判定するか?
**A1**: 急いでプロキシを導入しない。まず2つの方向を別々に測る:ホストA からこちらへ TCP/UDP/ICMP/DNS の外向き通信プローブを発し、成功と失敗の組み合わせを記録する。次にこちらからホストA の一般的なポートへ内向き通信のハンドシェイクを行う。「内向き通信表」と「外向き通信表」を分けて並べる。単方向/双方向/半開きの違いが、この後リバース・バンド・プルモードのどれを選ぶかを直接決める。
**Q2**: プローブがすべて不確定(こちらにも届かず、エラーも出ない)場合は?
**A2**: コマンドエコーがネットワーク動作に対して不透明であることを意味する。【外部観測次元】へ方向転換する:ホストA に、必ず外部の観測可能な点を通過する動作(たとえば制御下の権威ドメインへの DNS 解決)をトリガーさせ、権威側でクエリが来たかを見る。エコーへの依存を回避する。
**Q3**: 権威側でも見えない場合は、死んでいるのか?
**A3**: 必ずしもそうではない。ホストA に直接の外向き通信がなく、何らかのプロキシ/ゲートウェイを経由する必要がある可能性がある。このとき問題は「出られるか」から「誰を経由して出るか」に変わる。プロキシ設定(環境変数、システムレジストリ、PAC、DNS 分割)の識別へ方向転換する。
**Q4**: 双方向到達可能と確認できたが、レイテンシが高くジッターが大きい場合は?
**A4**: 「通る」ことは「対話を担える」ことを意味しない。チャネルの用途を層に分ける:短いコマンドは高レイテンシのチャネル、大流量は別途低レイテンシの経路を探す。1本の管ですべての場面をまかなわない。

### 外向き通信プロトコル探査の順序
**Q1**: 外向き通信を探る場合、どのプロトコルを最初に試すのが最も割に合うか?
**A1**: 一般的なヒューリスティックは、通常業務らしいものほど優先する:DNS → 大衆エンドポイントへの HTTPS → HTTP → 指定目的ポートの TCP → ICMP → 任意の UDP。背後にある判定基準は「低ノイズ、遮断確率が小さい、失敗しても目立たない」である。
**Q2**: 各プロトコルで何のシグナルを測るか?
**A2**: 3つある。接続を確立できるか(SYN-ACK)、アプリケーション層データを送れるか、返却内容が書き換えられているか(透過プロキシは UA を書き換え、TLS 遮断は証明書を差し替える)。1つでも欠けると「通ったが実は通っていない」と誤判定する。
**Q3**: すべて無反応の場合は?
**A3**: 【逆方向観測次元】へ方向転換する。ホストA に、必ず外部を経由する動作(権威 DNS クエリ、公衆時刻同期)を能動的に行わせ、外部で受信したかを見る。観測点をホストA に置かないことで、エコーの盲点を迂回する。
**Q4**: 探査自体がアラートを誘発するか?
**A4**: 誘発する。だから順序の前方ほど「無害」にする。いきなり全ポートの TCP スキャンをしない。判定基準は「1回の探査の最悪の結果」が「もう1回探査して省ける時間の価値」より小さいことである。

### 外向き通信ホワイトリストの形状の仮説
**Q1**: 厳格な外向き通信ホワイトリストがあると疑う場合、その形状をどう仮定するか?
**A1**: 典型的な形状:プロキシは【ドメイン分類】で許可し、ポートでは許可しない。まず FQDN 分類ホワイトリストと仮定し、それが IP セグメント/SNI 検査かどうかを検証する。
**Q2**: FQDN ホワイトリストと SNI 検査を低コストで区別するには?
**A2**: 「有名な分類ドメイン」と「新規登録ドメイン」をそれぞれ同ポートへ TLS ハンドシェイクし、さらに「SNI なしの IP 直結」と「偽 SNI 付き」の2群を対照する。差異から粒度を逆算できる。
**Q3**: SNI 検査と確認でき、ドメインフロンティングも無効な場合は?
**A3**: 【合法 SaaS 担体次元へ方向転換】する。トンネルトラフィックを「業務上必ず許可する」カテゴリ(ソースコードホスティング、コラボレーションプラットフォーム、クラウドストレージ API)に寄生させる。同じ層を掘り続けるのではなく、担体を切り替える。
**Q4**: DNS まで分割されている(内部 DNS が内部だけを解決)場合は?
**A4**: このマシンには名前解決の外向き通信がないことを意味し、内部プロキシを通す必要がある。プロキシ設定の識別へ考え方を変え、トンネルをプロキシに収める。迂回はしない。

### リバース接続失敗の損切り
**Q1**: 公衆の待ち受けへのリバース接続を試したが通らない。変形を続けるか、経路を変えるか?
**A1**: まず失敗原因を分類する:「TCP ハンドシェイクすら完了しない」(多くは遮断)か「ハンドシェイク完了直後に切断される」(多くはアプリケーション層検知)か。判定基準が不明なまま試し続けるのは予算の浪費である。
**Q2**: アプリケーション層検知なら、どの変形を試す価値があるか?
**A2**: ポート変更(80/443/53)、プロトコルカプセル化の変更(HTTP CONNECT、WebSocket、TLS)、TLS フィンガープリントの変更、宛先 ASN の変更。これらの変形が答えるのは「検知の粒度」であり、「通るかどうか」ではない。
**Q3**: 全変形が失敗した場合は?
**A3**: 【プルモードへ方向転換】する。ホストA に能動的な接続をさせず、「必ず届く」場所(SaaS ストレージ、許可リスト内のドメイン)を周期的に pull させる。方向を push から pull へ反転し、チャネル特徴を「長い接続」から「短いポーリング」に変える。
**Q4**: プルモードの帯域がプロキシを動かすのに足りない場合は?
**A4**: プルモードは「コントロールプレーン」(コマンド送信、小さい結果の取得)だけを担い、「データプレーン」は別経路を探す。たとえばすでに張った最初のホップ経由で第二層のトンネルを掘る。

### エコーコマンドから対話型シェルへの昇格
**Q1**: web shell の実行は「毎回1コマンド、出力はエコー」で、vim/ssh のような対話型ツールが使えない。昇格すべきか?
**A1**: 後続の動作が【必須で】対話を要する(パスワード入力、y/n 応答、進捗バー表示、環境変数の維持)場合のみ昇格する。非対話で代替できる(expect のワンショットスクリプト、コマンドを1行に連結)なら昇格しない。昇格自体が設置ファイルと追加チャネルをもたらす。
**Q2**: 昇格経路の優先順位は?
**A2**: 軽い順に:パイプ連結 → 環境変数注入 → 半対話 pty(python/script/socat) → 全対話リバースシェル(ウィンドウサイズ同期付き)。前段で足りるなら後段は使わない。
**Q3**: 対象に python/perl/script がなく、pty が起動できない場合は?
**A3**: 【「対話をローカルへ移す」次元へ方向転換】する。状態を持てるラッパー(Expect スクリプト、one-shot コマンドパック)でローカルに組み立て、各ステップを非対話コマンドとして投げる。遠隔で pty を無理に起動しない。
**Q4**: pty を起動したがウィンドウサイズ/シグナル処理で止まる場合は?
**A4**: シェルの安定性の問題であり、到達可能性の問題ではない。同じ管に「ハートビート/ウィンドウ同期」の制御フレームを追加するか、より安定した担体(SSH-over-トンネル)へ直接切り替える。

### 設置バイナリの取捨選択
**Q1**: ホストA にトンネルツールを置く場合、最初に何を決めるか?
**A1**: 「リンク方式」と「サイズ」を決める。静的リンクは依存を省くが大きい、動的リンクは小さいが対象の libc バージョンに制約される。まず対象のディストリビューションと libc バージョンを把握してから選ぶ。闇雲に最新の静的版を落とさない。
**Q2**: 転送方式はどう選ぶか?
**A2**: まずチャネル帯域を見る:小さいツールは base64 で直接貼る → curl/wget で取る → 分割再構成で取る。判定基準は「転送時間 + 被検知リスク」が最小であること。
**Q3**: 対象ディスクが読み取り専用または極端に逼迫している場合は?
**A3**: 【「非設置」次元へ方向転換】する。メモリ実行(インタープリタ経由のロード、fd からの直接 exec、ツールを一時ファイルシステムに入れる)を使う。あるいはシステム標準ツール(ssh、socat、nc、bash /dev/tcp)でトンネルを組み、自前のバイナリを置かない。
**Q4**: 設置したがアンチウイルスが即座に削除する場合は?
**A4**: 到達可能性だけでなく、ホストセキュリティ次元も重なっている。改名/パッキング/遅延実行で静的特徴を回避するか、「システム標準を使う」路線へ戻るか、先にホストセキュリティを処理してからネットワークに戻る。

### 設置ディレクトリの書き込み可能・実行可能の判定基準
**Q1**: バイナリを設置する場合、どのディレクトリを選ぶか?
**A1**: 3条件を同時に満たすこと:現在のユーザーが書き込み可能、noexec がマウントされていない、巡回監視に引っかかる確率が低い。まず `mount` で各パーティションのマウントオプションを見る。`ls -la` の権限だけを見ない。
**Q2**: よくある落とし穴は?
**A2**: /tmp、/var/tmp、/dev/shm は noexec にされることが多い。ユーザーのホームディレクトリは書き込み可能だが EDR に監視される。/var/log は書き込み権限があるが実行できない。判定基準は「書ける」と「実行できる」が別物であること。
**Q3**: 書き込み可能な全ディレクトリが noexec の場合は?
**A3**: 【「noexec を迂回する実行方式」次元へ方向転換】する。インタープリタでスクリプトを実行する(bash/python/perl)、ld.so で直接 ELF をロードする、ロジックを shared object にして既存プロセスにロードさせる。実行は必ずしも「ファイルを exec する」ことに頼らない。
**Q4**: インタープリタまで制限されている場合は?
**A4**: 「既存の実行ファイルの再利用」へ退く。システム標準の合法ツール(curl/socat/ssh/openssl)を組み合わせてトンネルを作り、自前のバイナリを導入しない。

### コマンドエコー欠落時の情報の持ち帰り
**Q1**: コマンドは実行されるがエコーがまったくない(盲コマンド)。どうチャネルを構築するか?
**A1**: 「持ち帰り」を先に解決してから「チャネル」を語る。結果を、自分が観測できる側チャネルにエンコードする:DNS クエリ名、HTTP リクエスト URI、タイミング差。判定基準は「側チャネルの帯域が、次の判断に必要な情報を伝えるのに足りるか」である。
**Q2**: 側チャネルの帯域が極めて小さい(たとえば毎回数十バイト)場合は?
