# ネットワーク到達可能性 · 外向き通信が制限されている(コールバック不能)ときの接続方向の決定

### まず「コールバック不能」が全面的遮断か選択的遮断かを判定する
**Q1**: リバースシェルが戻ってこない。外向き通信方向が丸ごと死んでいるのか?
**A1**: 急いで手法を変えない。まず層別に検証する:対象が外部ドメインを解決できるか(DNS 外向き通信)、公共 HTTP(S) ページを取得できるか、ping が出せるか。3つの次元のうち1つでも通れば「全面的断」ではなく「選択的断」である。判定基準:遮断の特徴が「プロトコル次元」か「宛先次元」かが、この後プロトコル偽装を使うか中継点を使うかを決める。
**Q2**: 対象は盲目的実行しかできず、対話型のエコーがない場合、どう判定するか?
**A2**: 副作用が最小のプローブを使う。対象に、一意な識別子を付けたリクエストを公衆の制御可能なエンドポイントへ発信させ(HTTP/DNS を1つずつ)、自分側でログを見る。受信できた = そのプロトコルは通っている。受信できなければ = プロトコルが遮断されているか、実行が設置されていないかのどちらかで、交差検証する。
**Q3**: DNS は通るが HTTP が通らない。何を意味するか?
**A3**: 強制プロキシかアプリケーション層ホワイトリストが存在する可能性が高い。DNS は通常内部の再帰サーバー経由で出ていき、HTTP は独立した egress ルールを通る。このときは「既存の DNS チャネルの活用」か「プロキシの探索」へ直交に切り替える。
**Q4**: この経路がまったく通らない(DNS すら出られない)場合、どこへ方向転換するか?
**A4**: 「内部から能動的に出る」方向を放棄し、「外部から内部へ」へ直交転換する。現在のホストが対外向けに公開できるサービスポート(たとえばすでに待ち受けている Web サービス)を探し、バンドシェルの入口として、外部から能動的に接続する。方向反転がこの種の遮断における中核の突破口である。
**Q5**: プローブ自体がアラートを誘発するのをどう避けるか?
**A5**: 低頻度で、通常トラフィックに擬態したプローブ(たとえば実在する公共ドメインへのアクセス)を使い、明らかな attacker.example を叩かない。頻度は通常業務の量以下に抑える。

### プロトコル次元の選定:TCP / UDP / ICMP のどれが最も有望か
**Q1**: TCP の高位ポートが全遮断と分かっている場合、UDP と ICMP のどちらを優先するか?
**A1**: 対象ネットワークのプロファイルを見る。企業の出口は通常 DNS(53/UDP)、NTP(123/UDP)を許可し、ICMP echo も運用監視のため許可することが多い。厳格な環境では逆の場合もある。判定基準:まず「業務に必須のプロトコル」のチャネルを測る。業務が欠かせないチャネルが遮断される確率が最も低い。
**Q2**: 3つとも一部は通る場合、どれでトンネルを組むか?
**A2**: 帯域(TCP > UDP > ICMP)、レイテンシ安定性(TCP が最も安定)、隠蔽性(業務との混在度)の3点を比較する。日常の運用では TCP で 443 を選ぶ。短い制御シグナリングでは UDP/ICMP の方が隠蔽しやすい。
**Q3**: ICMP は通るがレート制限されている。使う価値はあるか?
**A3**: 制御チャネル(短いコマンドの送信、ハートビート)専用にし、データプレーンは別に用意する。制御は ICMP、データは別の担体に乗せる混合方向にする。
**Q4**: 3つとも通らない場合は?
**A4**: 「アプリケーション層の担体」次元へ方向転換する。裸のプロトコル出網に依存せず、対象がアクセスを許可されているアプリケーションサービス(メールゲートウェイ、コードホスティング、クラウドオブジェクトストレージ、チャット API)をメッセージ中継として使う。方向は「プロトコルトンネル」から「アプリケーション中継」へ移る。
**Q5**: あるプロトコルがステートフル追跡されているかどうか、どう判定するか?
**A5**: 双方向パケットが対になって通過できるかを観察する。発信パケットが出て、戻りが落とされるなら、状態追跡か非対称ルーティングがある。このときは「戻りも内部から外へ発信させる」必要があり、外部からの戻りパケットを待ってはならない。

### HTTP(S) 外向き通信がトンネル担体として使えるか
**Q1**: 対象がインターネットの Web にアクセスできる。直接 HTTP トンネルを組むべきか?
**A1**: まず強制プロキシの有無を見る。IP 直結の公衆エンドポイントへ curl し、失敗するがドメインアクセスは成功するなら、プロキシか DNS 強制が存在する。判定基準:proxy 経由が必要かどうかが、トンネルクライアントの選定に直接影響する。
**Q2**: TLS 中間者プロキシがあり、自己署名 CA がクライアント信頼に注入されている場合、TLS トンネルはまだ構築できるか?
**A2**: できるが、ペイロードは解かれてしまう。二層暗号化(トンネル内にもう一層)にするか、コンプライアンス業務に偽装する(SNI と Host をホワイトリストドメインに揃える)かして、プロキシのコンテンツポリシーに引っかからないようにする。
**Q3**: 特定ドメインのホワイトリストのみ外向き通信が許可されている場合は?
**A3**: 「ドメインフロンティング」または「コンプライアンスドメインへの寄生」へ直交転換する。ホワイトリスト内の公共 CDN/クラウドサービスを踏み台ドメインとして使う。前提は、それらのサービスが実際に許可リストに存在すること。実現可能性を評価するときは、SNI 検証の厳しさを重点的に見る。
**Q4**: HTTP は出られるが、コンテンツ IDS のセンシティブルールにマッチする。特徴をどう下げるか?
**A4**: 3つの道がある。低頻度化(ハートビートを伸ばす)、擬態(通常の JSON/画像に埋め込む)、変形(独自エンコード+分割)。これは隠蔽性と帯域のトレードオフで、速度を求めないなら最も業務らしい形を選ぶ。
**Q5**: HTTP が完全に通らない場合、どこへ方向転換するか?
**A5**: 「DNS 担体」または「クラウドストレージのポーリング」へ方向転換する。DNS は通常最後まで遮断されず、クラウドオブジェクトストレージ(公開 bucket の読み書き)は低い障壁の代替案である。

### DNS トンネルの適用性とコスト評価
**Q1**: DNS が現在唯一のチャネル。何を担えるか?
**A1**: 小帯域の制御フローは問題なく担える(数十 bps〜数 kbps)。対話型シェルはかろうじて、ファイル転送は極めて遅い。判定基準:まず1回の操作に何バイト必要か、DNS クエリ文字列長以内に分割できるかを計算する。
**Q2**: 内部 DNS が少数の固定サフィックスしか再帰しない場合は?
**A2**: 利用可能な「内部で解決可能なドメイン」があるか判断する(たとえば運用上の都合ですべての .xxx サフィックスを転送する環境がある)。なければ、「ハートビートの漏出」用途だけに後退し、双方向トンネルは期待しない。
**Q3**: DNS over HTTPS(DoH)は通るか?
**A3**: HTTPS ホワイトリストが DoH プロバイダーを許可していれば、DoH は内部 DNS 検査を迂回する道になるが、特徴が明確で専用ポリシーで遮断されやすい。使うかどうかは、防御側の検知成熟度を見て評価する。
**Q4**: DNS トンネルが行動検知に識別された場合は?
**A4**: 「極低頻度ビーコン+外部トリガー」モデルへ方向転換する:内部のみ
