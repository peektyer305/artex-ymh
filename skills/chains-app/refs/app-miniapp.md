# Appクライアント · ミニプログラム/H5/モバイルAPI攻撃面

### APK/IPA/ミニプログラムパッケージを入手したら、まず静的棚卸しをするか、それとも直接パケットキャプチャするか
**Q1**: 対象Xが手元に来たばかりで、インストールパッケージ（またはストアのリンク）しかない場合、先に動的パケットキャプチャをすべきか、先に静的にパッケージを展開すべきか？
**A1**: 先に静的棚卸しを行う。コストが最も低く、リスク管理を刺激しない。パッケージを展開して方向を決める3つの要素を見る。①ネットワークドメイン/API一覧（文字列・リソース・設定の中から http、api、host、Base_URL を検索する）。②認証と暗号化の手がかり（sign、token、secret、AES、RSA、appKey のキーワード）。③プロテクト/パッカーとSDKの一覧。静的にまず「バックエンドがどう見えるか」を描き、それから問題を持って動的パケットキャプチャを行う。盲目的に取得するより効率が一桁高い。
**Q2**: 静的解析でドメインとAPIが非常に少なく、文字列がほぼ無い場合、隠されているのか本当に無いのかをどう判断するか？
**A2**: 高確率でプロテクト/文字列暗号化である。判定基準：DEX が異常に小さい、native so がロジックを担っている、文字列の大半が暗号文またはリフレクション呼び出しである。この時点で静的解析の利得は逓減するため、動的解析へ移る。
**Q3**: 静的段階で最も優先して抽出すべき「高価値の単点」は何か？
**A3**: ハードコードされた認証情報（サードパーティクラウドのAK/SK、プッシュ/SMS/地図のkey）、テスト/debug スイッチ、そしてAPI全体の命名規則（RESTful のパスプレフィックス、バージョン番号 /v1/ /api/）である。命名規則によって、その後未公開APIを列挙できるようになる。
**Q4**: この静的解析の道が完全に行き詰まった場合（全面プロテクト・可読情報なし）、どうするか？
**A4**: 直交する次元へ移る。すなわち「クライアントを読む」ことをやめ、「クライアントが話すこと」を見る。直接動的パケットキャプチャ/インストゥルメンテーションを行い、注意を「ファイルのリバースエンジニアリング」から「トラフィックと実行時のリバースエンジニアリング」へ切り替える。クライアントがどれほどプロテクトされていても、最終的にはネットワークリクエストを送る。トラフィックは回避できない露出面である。
**Q5**: 動的パケットキャプチャにも方向が必要だが、静的解析は動的解析にどのような「フック」を残すべきか？
**A5**: 残すのは、中核業務APIのドメイン、認証パラメータらしき名前、暗号化アルゴリズムの種別（対称/非対称）である。こうすれば動的解析で暗号文を取得したとき、すぐに対応づけでき、ゼロから推測せずに済む。

### HTTPS のパケットが取れないとき、まず何を疑うか
**Q1**: プロキシ証明書を導入し、ブラウザでは取得できるのに、対象Appのトラフィックがパケットキャプチャツールにまったく現れない、またはエラーになる場合、どう切り分けるか？
**A1**: 確率順に切り分ける。①App がシステムプロキシを認識していない（多くは OkHttp のカスタム実装で、システムプロキシを通らない）→ 透過プロキシ/VPNモードでのキャプチャが必要。②証明書固定 SSL Pinning → ハンドシェイクが直接失敗する。③App が独自の CA 検証または相互認証を内蔵している。まず現象を見る。完全にトラフィックが無い場合は「プロキシを通っていない」ことが多く、ハンドシェイクの alert/切断は Pinning であることが多い。
**Q2**: 透過プロキシ/VPN のパケットキャプチャモードに切り替えた後、TLS ハンドシェイクの時点で切断されるのは、何を意味するか？
**A2**: ほぼ SSL Pinning と確定する。この時、プロキシ層で無理に抗わず、実行時に移る。インストゥルメンテーションフレームワークで証明書検証関数を hook して無効化する。
**Q3**: 非HTTPSのトラフィックすら一切無く、App が「オフライン」のように見える場合は？
**A3**: 3つの点を疑う。native 層のネットワークスタックを強制使用している、プロキシを検知して即座に動作を止めている、または非HTTPプロトコルを使っている（独自TCP/QUIC/WebSocket over 443）。全ポートの pcap を1つ取得し、実際にどこへ接続し、どのプロトコルを使うかを見る。HTTP だけに注目しない。
**Q4**: この「ネットワーク層パケットキャプチャ」が全面的に塞がれた場合（プロキシ検知+Pinning+アンチデバッグの3点セットが揃っている）、どうするか？
**A4**: 直交する次元へ移る。「中間者」から「エンドポイント迂回」へ移る。中間で取得できないなら、クライアントプロセス内部で取得する。すなわち、暗号化関数の平文入口/出口を hook する（encrypt の前、decrypt の後に平文を取得する）、または送信前の buffer を直接読む。TLS 自体を迂回し、アプリケーションロジック層でデータを取得する。
**Q5**: エンドポイント迂回も設置が必要だが、具体的にどの層を hook するのが最も安定するか？
**A5**: 言語ランタイム内の高層 API を優先して hook する（OkHttp の Request/Response、システム HTTP クライアントなど）。低層の socket を hook するより得られるデータが構造化され、可読性が高い。取得できなければ、さらに下の暗号化・復号関数へ降りる。

### SSL Pinning 迂回にはどの手法を選ぶか
**Q1**: 証明書固定を確認した。迂回手段として、汎用スクリプト、手動での smali 改変によるリパッケージ、hook の3つの道があるが、まずどれを選ぶか？
**A1**: まず汎用 hook スクリプトを試す（一般的なネットワークライブラリとシステム検証点をカバーする）。コストが最も低く、5分で効果が出る。判定基準：スクリプト注入後にハンドシェイクが回復するか。これで大半の「標準的な書き方」の Pinning を回避できる。
**Q2**: 汎用スクリプトが無効で、ハンドシェイクが依然として切断される場合、Pinning はどこに書かれているのか？
**A2**: 非標準実装であることを示す。native so 内で証明書比較を行っている、自社開発の検証を使っている、または検証点が難読化されている可能性がある。汎用スクリプトは高層の Java/システム API しかカバーせず、native には届かない。方向転換：so 内の検証関数を特定する。
**Q3**: native 層の検証点を素早く特定するには？
**A3**: ネットワークハンドシェイクの前後で呼び出される so 関数を動的に trace する、または so 内で証明書/公開鍵フィンガープリントの定数を検索する（Pinning は必ず期待フィンガープリントを1つ内蔵している）。比較関数を見つけたら、その戻り値を常に真にするよう hook すればよい。
**Q4**: native hook すらアンチデバッグに遮られる場合（インストゥルメンテーションすると即クラッシュする）はどうするか？
**A4**: 直交する次元へ移る。「App に自分の証明書を信じさせる」ことをやめ、「App 自身の証明書経路を使う」に変える。App が自身の内蔵公開鍵を信じるなら、中間者にならない。エンドポイント迂回に戻り、直接平文を hook して Pinning を形骸化させる。認証の迂回 ≠ MITM が必須というわけではない。
**Q5**: リパッケージして smali を改変する道は、どのような場合に使う価値があるか？
**A5**: 対象に App レベルの署名検証が無く、かつ長期にわたって安定的に再現する必要がある場合（チームメイト/自動化用）にのみ行う。一度で済むが重く、署名検証に遭遇すると別の迂回タスクを連鎖的に引き起こすため、短期的な侵入には割に合わない。

### クライアントのリバースエンジニアリングが難しすぎる場合、API自体の攻撃に切り替える
**Q1**: プロテクトをアンパックできず、Pinning を迂回できず、時間だけが過ぎる。クライアントを諦めるべきか？
**A1**: 諦めるべきだ。再評価する。クライアントは「APIの呼び出し元」に過ぎず、本当の攻撃面はバックエンドAPIである。たとえ1つのAPIの完全なリクエスト（ドメイン+パス+1つの正規署名）でも取得できたなら、API fuzz の足がかりが得られる。精力を「クライアントを突破する」ことから「APIと直接対話する」ことに移す。
**Q2**: 取得できたAPIサンプルが1つしかない場合、どうやってAPI面全体に拡張するか？
**A2**: 3つの方向がある。①パスの規則に沿って同種のAPIを列挙する（/user/info → /user/list、/order/detail）。②ミニプログラム/H5版を調べ（往々にしてプロテクトが弱く、APIは同一である）、より完全なAPI一覧を取得する。③APIドキュメントの漏洩を探す（swagger、api-docs、テスト環境）。
**Q3**: 署名パラメータはどうするか。クライアントが無ければ sign を計算できないのでは？
**A3**: まず署名のカバー範囲を判断する。多くの sign は一部のパラメータのみに署名している、または改ざん防止のみでリプレイは防いでいない。テスト方法：署名でカバーされていないパラメータを1つ変更し、依然として成功するかを見る。または元のリクエストをそのままリプレイし、権限外アクセスの対象を変更する（id を他人のものに置き換える）。正規署名のリプレイは往々にして権限外アクセスを成立させられるため、sign を再計算する必要すらない。
**Q4**: すべてのAPIが強力な署名・強力なタイムスタンプを備え、クライアントの関与が必須の場合はどうするか？
**A4**: 直交する次元へ移る。「オフラインで署名を計算する」ことを「オンラインで署名を借りる」ことに変える。実際のクライアントを動かし、hook を通じてローカル署名サービスを公開する（署名対象データを渡し、署名を取り出す）。自分の fuzz ツールがそれを呼び出す。クライアント自身のアルゴリズムに自分のために働かせれば、アルゴリズムをリバースエンジニアリングする必要はない。
**Q5**: 正規サンプルすら1つも取得できない場合（すべての条件が失敗する）、最後の手段は？
**A5**: 最も外側の層まで退き、同じバックエンドの他の入口を探す。公式サイト/PC版/提携先の公開API/過去のAPP版である。それらはバックエンドを共有しているが、認証がより緩いことが多い。攻撃面は「バックエンド」であり、「この1つのApp」ではない。

### プロテクトのパッカーを識別し、アンパックするかを決める
**Q1**: APK を入手し、DEX 内がすべてパッカーのローダーである場合、まずアンパックの必要性をどう判断するか？
**A1**: まず自問する。アンパックする目的は文字列/APIを取得するためか、それともロジックを改変するためか。APIと暗号化アルゴリズムだけを得たいなら、動的 hook の方がアンパックよりはるかに速いことが多い。アンパックは重作業であり、完全な静的監査が必要な場合にのみ価値がある。まずパッカーのベンダーを識別し（特徴ディレクトリ、so の命名、ロードフロー）、成熟したアンパック手法が既にあるかを判断する。
**Q2**: 主流の商用パッカーで、既製のアンパック機がある場合、直接使うべきか？
**A2**: 使うべきだ。ただしバージョンの対抗に注意する。新版のパッカーにはアンパック対策があることが多い。判定基準：アンパックされた DEX が完全か（メソッド本体が抜き取られていないか、CodeItem が nop でないか）。抽出型パッカーはアンパックしても空のメソッドだけになることがあり、能動的な呼び出し/メモリダンプによる補完が必要である。
**Q3**: アンパックしたら重要メソッド本体が空であることが分かった場合（関数抽出/VMP）、どうするか？
**A3**: 高強度の保護であることを示し、静的復元のコストは極めて高い。単一の関数に固執しない。方向転換：実行時にのみこの関数の入出力を観察し（境界を hook する）、それをブラックボックスとして扱う。必要なのは挙動であり、ソースコードではない。
**Q4**: アンパックの道全体がアンパック対策で完全に塞がれた場合はどうするか？
**A4**: 直交する次元へ移る。「コードの復元」から「実行時状態の観測」へ移る。パッカーが保護するのは静的な形態であり、実行時のメモリは保護できない。パッカーも最終的にはメモリ内で平文DEX/鍵を復元しないと実行できない。メモリダンプ/実行時 trace に切り替え、最も脆弱な「実行の瞬間」に取得する。
**Q5**: アンパックに無限に時間を費やすのを避けるには？
**A5**: タイムボックスを設ける（例：1時間）。アンパックは手段であって目的ではない。時間超過時は hook またはAPI面に切り替える。レッドチームに必要なのは突破口であり、このパッカーを研究し尽くすことではない。

### ミニプログラムパッケージをどう入手し、どう復元するか
**Q1**: 対象が WeChat ミニアプリの場合、監査するためにそのコードをどう入手するか？
**A1**: ミニプログラムパッケージはデバイスローカルにキャッシュがある（暗号化された wxapkg）。手順：root 済みのアンドロイド/エミュレーターでミニプログラムを一度開いてダウンロードを発生させ、WeChat のデータディレクトリからパッケージを取得し、既製の展開ツールで wxml/wxss/js に復元する。ミニアプリは App より攻略しやすい。コードはほぼ平文の JS であり、プロテクトは非常に弱い。
**Q2**: 展開したパッケージが暗号化されている場合（.wxapkg が開けない）はどうするか？
**A2**: 新版パッケージは簡易な暗号化が施されているが、アルゴリズムは公開されており、既製の復号スクリプトがある（デバイス関連の復号パラメータが必要）。復号鍵を取得したらワンクリックで復元する。この手順は基本的にフロー化されており、詰まる場合はパッケージパスまたはバージョンが一致していないことが多い。
**Q3**: 復元後の大量の JS について、まず何を見るか？
**A3**: 3箇所に直行する。①request/API呼び出し（ミニアプリのネットワークリクエストドメインはバックエンド設定でホワイトリストになっているため、逆引きすれば全バックエンドドメインを取得できる）。②ハードコードされた appid/key/クラウド環境ID。③業務ロジックの判定（フロントエンドが行う認証/金額検証は、ほぼ必ず迂回できる）。ミニアプリはロジックを大量にフロントエンドに置いており、権限外アクセスとロジック脆弱性の多発地帯である。
**Q4**: ミニアプリがクラウド開発（serverless）を使い、APIが従来のHTTPではない場合はどうするか？
**A4**: クラウド開発の攻撃面へ移る。クラウド関数呼び出し、クラウドデータベースへの直接接続である。フロントエンドコード内からクラウド環境IDとデータベースコレクション名を見つけられる。ミニアプリのクラウドデータベースには過度に緩いセキュリティルールがあることが多い（フロントエンドが直接読み書きする）。直接クラウド呼び出しを構築し、テーブル全体への権限外アクセスによる読み書きを試みる。これは「HTTP APIを攻撃する」ことと完全に直交する1つの線である。
**Q5**: ミニアプリの実機デバッグ/パケットキャプチャが制限されている場合はどうするか？
**A5**: 方向転換する。ミニアプリの本質はH5+JSである。開発者ツールで復元後のソースコードをローカルで実行するか、取得済みのドメイン一覧で直接バックエンドAPIを攻撃し、ミニアプリクライアント自体を迂回する。

### ハードコードされた鍵を掘り出した後、その価値をどう判断するか
**Q1**: 静的解析で AccessKey/Secret らしき文字列を見つけた場合、それが使えるかどうかをどう判断するか？
**A1**: まず種別を分類し、それから有効性を検証する。どのクラウド/サービスに属するかを見る（オブジェクトストレージ、SMS、プッシュ、地図、IM）。サービスごとに危害は大きく異なる。有効性検証の方法：対応するクラウドの CLI/SDK でこの鍵のペアを使い、最小権限のプローブを行う（リソースの列挙）。判定基準：正常に呼び出せるか。無効なkeyは無価値だが、有効なオブジェクトストレージのkeyはストレージバケット全体を直接乗っ取れる可能性がある。
**Q2**: key は使えるが権限不足のエラーになる場合、まだ見込みはあるか？
**A2**: ある。それが実際に何をできるかを列挙する。多くの App は手間を省くために過大な権限を与えている。サービス/アクションを1つずつ境界を探る。読み取り専用であっても、全ユーザーのアップロードファイル/バックアップを読める可能性がある。1つのアクションが拒否されただけで捨てない。
**Q3**: 見つかったのがクラウド認証情報ではなく RSA/AES 鍵の場合、どう使うか？
**A3**: その価値は「トラフィックの復号/署名の偽造」にある。対称鍵はリクエストボディの暗号文を復号し、正規リクエストを偽造できる。RSA秘密鍵がクライアントにある場合（危険な誤設計）、サーバーの署名を偽造したり復号したりできる。まず通信における役割を確認し、それから展開に使うか偽造に使うかを決める。
**Q4**: ハードコードされたkeyがすべて無効/プレースホルダー/テスト値で、この道が途絶えた場合はどうするか？
**A4**: 直交する次元へ移る。「静かに既製のkeyを拾う」ことから「動的にメモリから生きたkeyを取得する」ことへ移る。多くの真の鍵は実行時にサーバーから配布されるかローカルで生成されるもので、静的解析には存在しない。実行時に切り替え、暗号化・復号関数が呼び出される際にパラメータを dump し、生きたまま鍵を取得する。
**Q5**: 大量の無効な文字列の検証に時間を浪費するのを避けるには？
**A5**: 優先順位を確立する。クラウドオブジェクトストレージ/SMS/決済系のkeyを優先して検証し、地図/統計系のkeyは低優先とする。「漏洩後の危害」でソートし、発見順でソートしない。

### モバイルAPIの署名メカニズムをどう分解するか
**Q1**: すべてのリクエストに sign パラメータがあり、どのパラメータを変更しても 403 になる場合、どう系統的に分解するか？
**A1**: 目標は「sign = f(どのデータ, どのアルゴリズム, どのkey)」を解明することである。方法：複数組のリクエストを取得して差分を取る。1つのパラメータだけを変更したときの sign の変化を比較し、どのフィールドが署名に関与するか、タイムスタンプ/nonce を含むかを推測する。同時に静的解析/hook で署名関数を特定する。まず「署名がどのフィールドをカバーするか」を解明する。往々にして署名が全フィールドに及んでいないことが分かる。
**Q2**: 差分から sign が一部の重要パラメータしかカバーしていないことが分かった場合、何を意味するか？
**A2**: カバーされていないパラメータは自由に変更しても署名が依然として有効であることを意味する。これが突破口である。例えば sign が業務パラメータに署名しているが userId/orderId に署名していない場合、権限外アクセスが直接成立する。まず「署名の盲点」を攻める方が、アルゴリズムのリバースエンジニアリングよりはるかに費用対効果が高い。
**Q3**: 署名が全パラメータをカバーしており、アルゴリズムを逆算するしかない場合、どう効率的に逆算するか？
**A3**: 逆コンパイルに固執しない。署名関数の入口を hook し、それが受け取った元の署名対象文字列と出力を表示する。一目で結合規則とアルゴリズムが分かる（MD5/HMAC の長さの特徴は非常に明瞭）。key も引数の中にある。実行時観測 >> 静的リバースエンジニアリング。
**Q4**: アルゴリズムが native/VMP 内にあり逆算できない場合はどうするか？
**A4**: 直交する次元へ移る。アルゴリズムを逆算せず、「署名オラクル」を作る。クライアントを継続実行させ、外部から呼び出せる署名APIを hook で作る。自分のツールが任意の payload を送り、正規の sign を受け取る。不可逆なブラックボックスを自分の署名サービスに変える。
**Q5**: 署名にサーバー配布の動的ソルト/ワンタイムトークンも含まれる場合はどうするか？
**A5**: 署名にセッション依存があることを示す。方向転換：まず通常のログインフローで現在のセッションのソルトを取得し、セッション有効期間内に一括でリプレイ/構築する。または署名オラクル方式を直接使う。それはセッション状態を内包しているため、手動でソルトを管理する必要がない。

### 権限外アクセス(IDOR)テストの進め方と判定基準
**Q1**: APIに userId/id パラメータがある場合、水平方向の権限外アクセスをテストしたい。どう始めるか？
**A1**: 2つのアカウントA、Bを用意する（または1つのアカウント+既知の他人のid）。AのセッションでBのリソースidをリクエストし、Bのデータが返るかを見る。判定基準は明確である。Aに属さないデータが返れば権限外アクセスが成立する。2つ目のアカウントが無い場合は、まず id を変更して返りの差異を探る（404 vs 403 vs 200でデータ付き）。
**Q2**: 平文idを直接変更したところ遮断された（権限なしが返る）場合、権限外アクセスは無いのか？
**A2**: そうとは限らない。id が間接参照/暗号化されているかを確認する。暗号化id、ユーザー名、電話番号など他の識別子に変更して試す。多くのシステムは主idにのみ検証を行い、傍路の識別子には検証していない。一括API、エクスポートAPI、旧版APIもテストする。検証の強度は往々にして一貫していない。
**Q3**: id が暗号化されている場合（例：暗号文文字列）、権限外アクセスをどうテストするか？
**A3**: まず他人の暗号化idを取得できるかを確認する（一覧API、共有リンク、メッセージプッシュには他人の暗号化idが漏れることが多い）。取得できれば直接置換できる。暗号化は隠蔽に過ぎず、認可の検証ではない。または署名/暗号化アルゴリズムを組み合わせて自分で暗号文を作る。
**Q4**: 全サイトの権限外アクセスが厳格に検証され、この道が行き詰まった場合はどうするか？
**A4**: 直交する次元へ移る。「水平方向の権限外アクセス」から「垂直方向の権限外アクセス/機能の権限外アクセス」へ移る。一般ユーザーが管理API（adminパス、バックエンドAPI）を呼び出し、自分のロールに本来現れるはずのない機能を呼び出す。フロントエンドで隠すこと ≠ バックエンドの認証である。多くの管理APIはフロントエンドでボタンを表示しないだけの「保護」に頼っている。
**Q5**: 垂直方向の権限外アクセスも無い場合、さらにどこへ移るか？
**A5**: 「権限外アクセスの読み書き非対称」へ移る。多くのAPIは読み取りの検証は厳しいが書き込み/削除の検証は緩い、またはその逆である。GET と POST/DELETE をそれぞれテストする。さらに「権限外アクセスのタイミング」へ移る。状態遷移API（注文の支払い待ち→支払い済み）は検証が欠けていることが多く、手順をスキップできる。

### SMS/認証コード系ロジック脆弱性の判断
**Q1**: ログイン/登録がSMS認証コード経由の場合、ロジック脆弱性を探すには、どの方向から切り込むか？
**A1**: 5つの定番方向を並行して調査する。①認証コードをブルートフォースできる（4桁でロックなし/頻度制限なし）。②認証コードがレスポンスにエコーバックされる（返却パケットに直接 code が含まれる）。③認証コードが電話番号に紐づいていない（Aの電話番号のコードでBを検証できる）。④SMS爆撃（頻度制限なし）。⑤万能コード/テストコード（000000、123456）。まずレスポンスパケットを見る。エコーバックは最も手早く決定的な一手である。
**Q2**: 認証コードが6桁で失敗回数ロックがある場合、ブルートフォースは望みがない。どうするか？
**A2**: 「紐づけ関係」と「再利用」の攻撃に切り替える。同じコードを複数回使えるか、検証成功後に無効化されるか、Aの検証状態をBの操作に使えるか。ロジック脆弱性は「コードを当てる」ことではなく、「コードと身元の紐づけ/ライフサイクル」が不十分な点にあることが多い。
**Q3**: 検証APIと業務APIが分離されていることが分かった場合（先にコードを検証してトークンに交換し、そのトークンで業務を行う）、何を攻められるか？
**A3**: 「トークン交換」の手順を攻める。コードを1回検証して得たトークンを複数回/複数人の操作に再利用できるか、権限外アクセスで他人のトークンに交換できるか、トークンは予測可能か。分離設計では「コード→認証情報」の変換箇所で検証が漏れることが多い。
**Q4**: すべてのSMSロジックが厳格で、この業務ラインを攻略できない場合はどうするか？
**A4**: 直交する次元へ移る。「認証コード自体」から「認証コードが保護する機能」へ移る。本来コードを検証すべきなのに漏れている入口を探す。パスワード変更、携帯電話の紐づけ変更、支払い確認など、コード検証不要の傍路API（旧API、H5API、内部API）が存在しないかを見る。同じ機微な操作には往々にして複数の入口があり、検証強度が異なる。
**Q5**: さらに深掘りしたい。認証コード以外の認証情報に見込みはあるか？
**A5**: ある。画像認証コード/スライダーの迂回（認識、デコード代行プラットフォーム、パラメータ再利用）をブルートフォースの前置きとして行い、さらにログイン/登録APIのユーザー列挙（エラープロンプトの違いでアカウントの存在を区別する）を後続のパスワードスプレーの布石とする。

### H5/WebView ハイブリッドアプリでどう脆弱性を探すか
**Q1**: App内に大量のH5ページ（WebView）が埋め込まれている場合、この攻撃面にどう切り込むか？
**A1**: まず WebView が読み込む URL と、それが公開する能力を特定する。重要な確認点：①制御可能な URL を読み込むか（外部リンク、パラメータで制御可能な url）→ XSS/フィッシングの可能性。② addJavascriptInterface がネイティブメソッドを JS に公開しているか（JSBridge）→ JS がネイティブ能力を呼び出せ、リスクは極めて大きい。③ file:// アクセスと setAllowUniversalAccessFromFileURLs を有効にしているか。
**Q2**: WebView が読み込む URL をパラメータや deeplink で制御できることが分かった場合、何ができるか？
**A2**: 自陣のページをその WebView に読み込ませ、注入されている JSBridge を呼び出すことを試みる。判定基準：WebView を任意のドメインへ遷移させられるか。可能なら、自分の JS がネイティブブリッジのあるコンテキストで実行され、公開された native メソッドを呼び出せる（ファイルを読む、トークンを取る、支払いを呼び出す）。
**Q3**: JSBridge にドメインホワイトリストがあり、自社ドメインの呼び出しのみ許可している場合はどうするか？
**A3**: ホワイトリストの迂回を探す。自社ドメイン配下のXSS（反射型/格納型XSSがあればホワイトリスト内で JS を実行できる）、サブドメインの乗っ取り、またはホワイトリスト検証に弱いマッチングを使っている（ドメインのサフィックス/包含判定は evil.com/self.com や self.com.evil.com で迂回できる）。ブリッジの安全性は「誰がホワイトリストドメインで JS を実行できるか」に強く依存する。
**Q4**: WebView が厳格に作られている場合（外部リンクを読み込まない、ブリッジなし、ホワイトリスト厳格）、この部分が行き詰まったらどうするか？
**A4**: 直交する次元へ移る。「クライアントのWebView」から「H5ページ自体に対応するバックエンド」へ移る。H5ページが呼び出すAPIは App とバックエンドを共有しているか独立のバックエンドを持つ。直接ブラウザでH5を開き、そのAPIを取得して攻撃する。H5の認証と暗号化は通常ネイティブAppよりはるかに弱く、同じバックエンドの弱点となる入口である。
**Q5**: 他にも WebView 関連の攻撃面はあるか？
**A5**: ある。ローカルHTML/リソースのパストラバーサル、WebViewキャッシュ内の機微データ、そして intent scheme / カスタムscheme で WebView を起動する際のパラメータ注入である。WebView を「App内のブラウザ」として捉えれば、ブラウザの脆弱性はほぼすべて存在しうる。

### deeplink/URL Scheme のハイジャックと悪用
**Q1**: App がカスタムschemeとdeeplinkを登録している場合、それが攻撃面かどうかをどう判断するか？
**A1**: まず登録している scheme/host/path を列挙する（マニフェストファイルにすべてある）。次にこれらの入口がパラメータを誰に渡すかを見る。重要な問題：外部から起動できるコンポーネントが信頼できないパラメータを処理しているか。すなわちURLジャンプ、WebViewの読み込み、アクションの実行である。任意のアプリ/ウェブページから起動可能 + パラメータが機微な操作に流入 = 攻撃面である。
**Q2**: ある deeplink がジャンプ先 url パラメータを1つ持てることが分かった場合、どう悪用するか？
**A2**: オープンリダイレクトと WebView 注入をテストする。自陣のページへジャンプさせる。対象 WebView が JSBridge またはログイン状態を伴うなら、トークンを釣り、ネイティブ能力を呼び出せる。判定基準：外部で構築したリンクが App に任意のアドレスを読み込ませ/ジャンプさせられるか。
**Q3**: deeplink がジャンプではなく機微なアクション（支払いを開く、紐づけ、認可など）をトリガーする場合、どう攻めるか？
**A3**: 「ワンクリックアクションのハイジャック」をテストする。ユーザーを誘導して1つのリンクをクリックさせるだけで機微な操作を完了させる（CSRF方式）。アクションに二次確認があるか、送信元を検証しているかを見る。モバイルのコンポーネント呼び出しは送信元検証が欠けていることが多く、外部から静かにトリガーできる。
**Q4**: scheme すべてに送信元/署名検証が施され、起動できない場合はどうするか？
**A4**: 直交する次元へ移る。「外部からの起動」から「コンポーネントの公開」自体へ移る。同じ App 内で公開された Activity/Service/Provider（exported=true）は、同じデバイスの他のアプリから直接呼び出せ、scheme 層を迂回する。ContentProvider の権限外アクセスによる読み書き、公開 Activity のパラメータ注入は、deeplink と直交する1つのローカル攻撃ラインである。
**Q5**: ローカルに他の悪意あるアプリの協力がない場合（リモートシナリオ）、deeplink にはまだどのような価値が残るか？
**A5**: 「ウェブページ→App」のクロスドメイン攻撃が残る。ウェブページ内のリンクだけで App の挙動をトリガーでき、WebView の信頼チェーンと組み合わせればリモートフィッシング/トークン窃取が可能である。これはモバイルでは珍しい「リモートから到達可能」な面であり、深掘りする価値がある。

### クライアントローカルストレージの機微データ
**Q1**: App がデバイスローカルにどのような機微なものを保存しているかを見たい。どこから探すか？
**A1**: ローカルストレージを系統的に調べる。SharedPreferences/plist、SQLiteデータベース、キャッシュファイル、SDカードディレクトリ、keystore/keychain である。キーワード token、password、secret、id を検索する。判定基準：認証情報が平文で保存されているか。多くの App は token、さらにはアカウントのパスワードまで平文でローカルに書いている。
**Q2**: ストレージが暗号化されている場合（データベース/ファイルが暗号文）、どうするか？
**A2**: 復号鍵の場所を探す。十中八九はクライアントにもある（ハードコード、またはデバイスidから派生、または keystore 内）。クライアントストレージ暗号化のパラドックスは「鍵もクライアントになければならない」ことであり、ほぼ常にローカルで復号できる。暗号化関数を特定し、hook するかkeyを抽出する。
**Q3**: ローカルのtoken/認証情報を取得した後、その価値をどう最大化するか？
**A3**: その権限と有効期間を検証する。長期tokenか短期tokenか。API呼び出しに直接使えるか（それでAPIを攻撃する）。デバイスをまたいで再利用できるか（サーバーがデバイスに紐づけていないことを示す）。長期token+デバイス非紐づけ=アカウントを持続的に乗っ取れる。
**Q4**: ローカルに機微データがまったく保存されていない場合（すべてメモリ上にあり、使い終われば消える）、どうするか？
**A4**: 直交する次元へ移る。「ディスクへ書き出すストレージ」から「実行時メモリ」へ移る。データがディスクに書き出されていないことは存在しないことを意味しない。それは必ずメモリ内に出現している。メモリダンプ/実行時 hook に切り替え、token が使われた瞬間に取得する。ストレージスキャンが空振りならメモリフォレンジックへ移る。
**Q5**: ストレージを読むにはデバイスへの物理アクセス/root 権限が必要だが、それがない場合はどうするか？
**A5**: 「バックアップ」と「ログ」という2つの緩い経路へ移る。App がデバッグバックアップを許可しているか（backup=true なら root なしでデータをエクスポートできる）、システムログ/クラッシュレポートに機微情報を出力しているか。この2つは root なしでデータを取得できることが多い。

### Root/脱獄検知が動的解析を阻む場合
**Q1**: root 端末上で App が起動直後に終了する/環境リスクをプロンプトする場合、どう続行するか？
**A1**: まず root 検知であることを確認する。迂回は階層化して行う。まず汎用の root 隠蔽手法を試す（su の隠蔽、denylist、一般的な検知点の hook）。判定基準：App が正常に起動できるか。多くの App は標準的な検知を使っている（suファイル、パッケージ名、プロパティの検査）。汎用手法で回避できる。
**Q2**: 汎用隠蔽が無効で、App が依然として検知する場合、検知はどこにあるのか？
**A2**: カスタム/native の検知点があることを示す。方向転換：App 起動時にどのファイルを読み、どのシステムプロパティを呼び、どのプロセスを fork したかを trace し、その検知ロジックを1つずつ特定して、的を絞って hook し「クリーン」を返させる。検知点が多くても有限集合であり、1つずつ潰せる。
**Q3**: 検知が native にあり、アンチデバッグと連動している場合（hook すると即クラッシュする）、どうするか？
**A3**: root のある環境で無理に抗わない。直交する次元へ移る。「root 不要の解析経路」に切り替える。非 root のパケットキャプチャ（VPNモード）、非 root の frida gadget 注入（リパッケージして内蔵）、または直接エミュレーター/クラウド実機で実行する（検知によってはエミュレーターに対してむしろ弱く、あるいは下層を改変できる）。元の戦場で無理に抗うのではなく、戦場を変える。
**Q4**: 非 root のパケットキャプチャすら Pinning に遮られ、エミュレーターも検知される場合はどうするか？
**A4**: 最も直交する一手に戻る。クライアント環境の動的解析を諦め、全力でAPI面へ移る。root 検知が保護するのは「クライアントの実行環境」であり、バックエンドAPIは保護できない。静的解析または1回のパケットキャプチャからAPIを取得済みなら、クライアントを迂回して直接APIを攻撃する。
**Q5**: root 検知の迂回にどれだけ力を注ぐべきかをどう判断するか？
**A5**: 目的を見る。API取得だけが目的なら、検知の迂回は割に合わないことが多い。直接VPNでパケットキャプチャするかAPIを攻撃する方が速い。中核ロジックを必ず実機で実行しなければならない場合にのみ、検知迂回への投資に価値がある。手段は目的に従う。

### Frida/インストゥルメンテーションがアンチ検知に遭った場合の打破方法
**Q1**: frida を注入するとすぐに App がクラッシュする、または検知され、動的 hook を続行できない場合、どうするか？
**A1**: まず anti-frida であることを確認する。特徴：注入直後にクラッシュする、frida のポート/プロセス/メモリ特徴を検知して終了する。まず対抗策を試す。frida の既定ポートを変更する、プロセス名を変更する、server 方式ではなく gadget 方式を使う、メモリ特徴を隠す。判定基準：安定して注入でき、クラッシュしないか。
**Q2**: ポート変更と名前変更後も検知される場合、それは何を検知しているのか？
**A2**: 一般的な検知点：メモリ内の frida 文字列のスキャン、maps 内の不審なライブラリの検査、特定スレッド/ファイルディスクリプタの検知、TracerPid である。方向転換：その検知関数を特定し（クラッシュ前の呼び出しスタックを trace する）、検知自体を hook して無効化する、またはより秘匿性の高い注入方式を使う（先に注入してから痕跡を消す）。
**Q3**: アンチデバッグ+アンチfrida+整合性検証の3点セットで、インストゥルメンテーションの道が極めて困難な場合はどうするか？
**A3**: 直交する次元へ移る。インストゥルメンテーションの担体を変える。frida から他のメカニズムへ変える。ptrace ベースのデバッガー、カーネル層の hook、あるいは思い切って静的 patch を使う（検知のジャンプを nop で潰してからリパッケージする。ただし署名検証への対処が必要）。インストゥルメンテーション技術ごとに検知のカバー範囲が異なるため、武器を変えて検知面を外す。
**Q4**: すべての実行時インストゥルメンテーションが塞がれた場合はどうするか？
**A4**: プロセス内インストゥルメンテーションを必要としない、純粋な静的解析+ネットワークの2つの道に退く。静的アルゴリズム復元（遅いが実行時検知をトリガーしない）、純粋なパッシブトラフィック解析（Pinning を突破できればネットワーク層で見る）。そしてAPI直接攻撃に戻る。そのプロセスに入らなければ、そのアンチインストゥルメンテーションは自分に届かない。
**Q5**: アンチ検知との無限のいたちごっこを避けるには？
**A5**: 境界を設ける。アンチ検知は軍拡競争であり、費用対効果は急落する。中核アセット（鍵、アルゴリズム）を取得したら即座に撤退し、成果を使ってバックエンドを攻撃する方向へ移る。この App のすべての保護を研究し尽くすのではない。レッドチームは成果を出すものであり、リバースエンジニアリングの教科書を作るものではない。

### ログイン状態/Token メカニズムの解析経路
**Q1**: 身元の偽造/ハイジャックのために App のセッションメカニズムを解明したい。まず何を見るか？
**A1**: ログインフローを取得し、それが発行する認証情報を見る。JWT、opaque token、cookie、それとも自社開発の署名か。重要な判定基準：token が自己完結的か（JWTは解ける）、それともサーバー保存か。JWT はまず展開して payload を見る（ロール、userId、有効期限）。改ざん可能な点があることが多い。
**Q2**: JWT の場合、攻撃点をどう探すか？
**A2**: 定番の4つの確認がある。①alg=none が受け入れられるか。②弱い鍵で HMAC をブルートフォースできるか。③kid 注入/jku が制御可能な宛先を指すか。④payload 内のロール/id を変更した後、サーバーが検証するか。1つのフィールドを変更してリプレイし、有効になるかを見る。JWT の信頼は往々にして置き場所を間違えている。
**Q3**: token がサーバー保存の opaque 文字列で、内容を変更できない場合、どう攻めるか？
**A3**: token の「ライフサイクルと紐づけ」の攻撃に切り替える。長期に失効しないか、ログアウト後に本当に失効するか、デバイス/IPに紐づいているか、予測可能/列挙可能か。1つの token を取得してどのくらい使え、どこで使えるかは、その内容より重要である。
**Q4**: セッションメカニズムが厳格に作られている場合（短期token+リフレッシュ+デバイス紐づけ）、ハイジャックの手掛かりがない場合はどうするか？
**A4**: 直交する次元へ移る。「tokenの偽造/改ざん」から「他人のtokenの合法的取得」へ移る。権限外アクセスAPI、ログ漏洩、WebViewでのフィッシング、ローカルストレージ読み取りなどを通じて他人の正規tokenを直接取得する。セッションメカニズムを破る必要はなく、有効な鍵を1つ盗むだけでよい。メカニズム解析が不調なら実物の窃取へ移る。
**Q5**: リフレッシュtokenメカニズム自体に攻撃可能な点はあるか？
**A5**: ある。refresh token は軽視されがちである。長期有効か、漏洩後に無限に延命できるか、リフレッシュAPIに権限外アクセスがあるか（Aの refresh でBの access を取る）。リフレッシュ経路の認証は主APIより緩いことが多い。

### API がレート制限/リスク管理で遮断された場合の続行方法
**Q1**: fuzz/ブルートフォースの途中で、API が 429 を返し始めるか直接 IP を遮断してきた場合、どうするか？
**A1**: まず遮断の次元を判断する。IP遮断、アカウント遮断、デバイスフィンガープリント遮断、それとも token 遮断か。それぞれテストして初めて分かる。判定基準：IP変更で回復=IP遮断。IP変更では回復しないがアカウント変更で回復=アカウント/デバイス遮断。原因に応じて対処し、盲目的に IP を変更しない。
**Q2**: IP遮断と確認できた場合、どう継続して作業するか？
**A2**: IPプール/プロキシローテーションを使い、リクエスト頻度をリスク管理の閾値以下に下げる（遅いことが速さである）。同時に免除経路がないかを見る。一部のAPI（H5、旧版、内部）は同じリスク管理ポリシーの対象外である可能性がある。
**Q3**: 遮断されたのがデバイスフィンガープリント/リスク管理パラメータの場合（IP変更が無効）、どうするか？
**A3**: リスク管理パラメータを特定する。リクエストに含まれる deviceId、フィンガープリント文字列、リスク管理SDKが生成する token である。これらはクライアントが生成することが多い。方向転換として、リスク管理パラメータの生成関数を hook し、「1台につき1フィンガープリント」の一括偽造を実現して、各リクエストが異なるデバイスから来たように見せる。
**Q4**: リスク管理が極めて強力な場合（行動分析、機械学習による遮断）、通常の迂回が効かない場合はどうするか？
**A4**: 直交する次元へ移る。「リスク管理に対抗する高頻度攻撃」から「低頻度の精密攻撃」へ移る。多くの高価値脆弱性（権限外アクセス、ロジック脆弱性、ハードコード漏洩）は高頻度リクエストをまったく必要としない。1回の正しい権限外アクセスリクエストで十分である。ブルートフォースの発想を捨て、単点のロジック脆弱性へ移れば、リスク管理は攻撃対象を失う。
**Q5**: リスク管理をトリガーする前にどう計画を立てるか？
**A5**: まずリスク管理の境界を偵察する（小規模な試行で閾値、遮断次元、回復時間を探る）。それから攻撃のペースを設計する。リスク管理を、まずルールを把握すべき相手として扱い、ぶつかってから反応するのではいけない。

### リクエストボディ全体が暗号化され、何を送っているか分からない場合
**Q1**: 取得したリクエスト body がまるごと暗号文で、パラメータがまったく見えない場合、どう手を付けるか？
**A1**: 目標は暗号化・復号の平文とアルゴリズムを得ることである。暗号文について当てずっぽうに推測しない。直接 hook する。App プロセス内で、暗号化関数呼び出し前の引数が平文であり、復号関数の戻り値が平文である。この2つの関数を特定する（encrypt/decrypt、AES/RSA 呼び出しを検索する、またはネットワーク送信関数から上へ遡る）。平文を得ればすべて解決する。
**Q2**: 暗号化関数を素早く特定するには？
**A2**: 2つの道がある。①暗号化APIの呼び出し点を静的に検索する（システム crypto ライブラリの呼び出しは必ず存在する）。②動的にネットワーク送信関数にブレークポイントを張り、暗号文が誰から渡ってきたかを見て、上へ遡って暗号化点に至る。動的遡行は通常、静的検索より速い。送信点が明確だからである。
**Q3**: アルゴリズムとkeyを取得した後、単に復号して見るだけでなく、どう攻撃に使うか？
**A3**: 自分用の暗号化・復号ツールチェーンを構築する。復号してリクエストを見る(パラメータを探す)→平文を改ざんする→同じアルゴリズムで再暗号化する→送信する。こうすれば暗号化APIに対して完全なパラメータ改ざん/権限外アクセス/インジェクションテストができ、暗号化は自分にとって透明になる。または暗号化・復号オラクル（hook でサービスを公開する）にして、自分での実装を避ける。
**Q4**: 暗号化が native/VMP にあり、key が動的生成で逆算できない場合はどうするか？
**A4**: 直交する次元へ移る。アルゴリズムを逆算せず、「暗号化・復号オラクル」を使う。encrypt/decrypt の2つの関数を hook して外部から呼び出せるようにし、自分の fuzz ツールは、平文→encrypt を呼んで暗号文を得る→送信、暗号文を受信→decrypt を呼んで結果を見る、という流れにする。クライアントを自分の暗号化・復号エンジンにし、アルゴリズム自体には一切触れない。
**Q5**: 暗号化の目的が単にパケットキャプチャ対策で、パラメータを変更すると署名が失敗する場合はどうするか？
**A5**: 暗号化と署名は別物であることに注意する。暗号化は「見えない」問題を解決し、署名は「改変できない」問題を解決する。復号してパラメータを見た後、独立した署名がまだあるなら、署名メカニズムの処理に戻る。2つのメカニズムは独立していることが多く、1つずつ分解する。

### 業務ロジック脆弱性（支払い/特典/ポイント）をどう系統的に探すか
**Q1**: チャージ/支払い/クーポンのような「金銭を搾取できる」ロジック脆弱性を探したい。どこから切り込むか？
**A1**: 「金額/数量/状態」の3種類のパラメータについて、クライアントとサーバーサイドの信頼境界に注目する。定番の手法：①金額の改ざん（支払金額の変更、単価を負/0にする、小数オーバーフロー）。②数量の改ざん（負数、極大数、範囲外）。③注文状態の跳び移り（支払いをスキップして直接支払い済みにする）。④特典の重ね掛け/再利用。判定基準：サーバーサイドが二次検証するのか、それともクライアントが渡した値を信じるのか。
**Q2**: 金額を直接変更してサーバーサイドに拒否された場合、見込みはないのか？
**A2**: そうではない。「最終結果」ではなく「計算過程」の攻撃に切り替える。総額ではなく単価を変更する、割引率を変更する、ポイント充当比率を変更する、数量を変更してサーバーに計算を間違わせる。サーバーは総額のみを検証し、計算に関与する中間パラメータを信頼していることが多い。計算チェーンの出力ではなく入力を攻撃する。
**Q3**: クーポン/ポイント系はどう探すか？
**A3**: 「並行性」と「タイミング」を攻める。同じクーポンを並行して複数回送信する（競合状態、レースコンディションで使い捨て検証を迂回する）、先に注文してクーポンをロックし、注文をキャンセルしたのにクーポンが消費済みのまま戻らない異常、返金後にポイントが回収されない、などである。並行性と状態の巻き戻しはロジック脆弱性の多発地帯であり、シングルスレッドでは検出できないため、並行して負荷をかける必要がある。
**Q4**: 支払いロジックが厳格な場合（サーバーサイド全検証、冪等性あり、並行ロックあり）、このラインを攻略できない場合はどうするか？
**A4**: 直交する次元へ移る。「取引パラメータの改ざん」から「支払いコールバック/認証情報の改ざん」へ移る。サードパーティ決済の非同期通知コールバックが署名検証を行うか、支払い結果の認証情報を偽造/リプレイできるか、注文と支払い伝票の紐づけを誤って組み合わせられるか（1件の少額決済の成功コールバックで1件の高額注文を消し込む）。コールバック経路は注文経路より検証が緩いことが多い。
**Q5**: さらに深掘りしたい。もっと秘匿性の高いロジック面はあるか？
**A5**: ある。返金ロジック（過剰返金、重複返金、他人アカウントへの返金）、業務横断の枠共有（1つの枠を複数箇所で消費する競合状態）、そしてテスト商品/内部価格APIの漏洩である。ロジック脆弱性の本質は「業務ルールの境界をサーバーサイドで担保していない」ことであり、金と状態の流れを辿れば必ず隙間がある。

### クライアントから隠し/内部APIを逆算する
**Q1**: 既知のAPIをすべて攻撃したが脆弱性がなく、未公開の内部APIがあると疑う場合、どう掘り出すか？
**A1**: 3つの出所がある。①クライアントコードに現れるが通常フローでは通らないAPI（debug、admin、ベータ機能）。②APIパスの規則からの外挿（/api/v1/user → /api/v1/admin、/internal/、/api/v2/ を試す）。③APIドキュメントの漏洩（swagger、api-docs、js 内のAPIマップ）。クライアント内で「言及されているが使われていない」APIが最も試す価値がある。
**Q2**: 外挿パスが大半 404 の場合、命中率をどう上げるか？
**A2**: 当て推量ではなく実際の命名習慣を使う。既知APIから命名スタイルを抽出し（アンダースコアかキャメルケースか、バージョン番号の形式、動詞の習慣）、同じスタイルで構築する。同時に 404（存在しない）と 403/401（存在するが権限がない）を区別する。後者は重要な手掛かりであり、API はあるが権限がないことを示すため、権限外アクセスへ移る。
**Q3**: 403 のAPIが一括して見つかった場合（存在するが拒否される）、どうするか？
**A3**: これはまさに内部APIのシグナルである。認証の攻撃に切り替える。より高い権限の token に変更する、内部識別ヘッダーを付与する（X-Internal、送信元IP偽装ヘッダー）、認証のない兄弟APIを試す。内部APIは「内網/内部クライアントしか呼ばない」と想定して認証が弱いことが多い。
**Q4**: パス外挿もドキュメント漏洩も結果が出ない場合はどうするか？
**A4**: 直交する次元へ移る。「APIを推測する」ことから「サーバーにAPIを語らせる」ことへ移る。情報漏洩の入口を探す。エラースタック、GraphQL の introspection（GraphQL なら1回の自省で全 schema とAPIを取得できる）、ヘルスチェック/actuator 系エンドポイント、そして異なるクライアント（PC、H5、提携先SDK）が公開するAPIの差集合である。別のクライアントに切り替えると、App に無いAPIが公開されるかもしれない。
**Q5**: これらの内部APIらしきものをどう優先順位付けするか？
**A5**: 危害の見込み順に並べる。admin/manage/internal/export/config の文字を含むものを優先する。データエクスポート、ユーザー管理、設定変更系を優先する。これらが認証なしなら重大な突破口となる。

### APIバージョンのロールバック/旧API攻撃
**Q1**: 現行版のAPIは認証/暗号化が厳格で、旧版はより緩いと疑う場合、どう検証するか？
**A1**: 旧APIはモバイルの定番の弱点である。旧Appとの互換性のため、バックエンドは旧版APIを残したまま下線できず、セキュリティ強化が追いついていないことが多い。方法：リクエストパス内のバージョン番号を下げる（/v3/ → /v2/ → /v1/）、またはバージョン番号を外し、旧APIが依然として有効か、認証がより緩いかを見る。
**Q2**: どのような旧バージョンがあるかをどう知るか？
**A2**: 複数の出所から組み立てる。過去のAPKバージョン（旧版パッケージをダウンロードし、当時のAPIを逆算する）、web archive 内の旧ドキュメント、そして直接バージョン番号を列挙する。旧版クライアントは往々にして平文、弱い署名、一部の新しい検証なしを使っている。旧クライアントの呼び出し方式で新バックエンドを攻撃する。
**Q3**: 旧APIがまだ有効だが認証も施されている場合はどうするか？
**A3**: 新旧APIの「能力の差集合と検証の差集合」を探す。同じ機能で新APIには権限外アクセス検証が追加されたが旧APIには無い、新APIにはパラメータ署名が追加されたが旧APIは token だけでよい、といった差である。旧APIを使って新APIではできない権限外アクセス/改ざんを行う。差異そのものが脆弱性である。
**Q4**: すべての旧APIが下線済み、または同様に厳格な場合はどうするか？
**A4**: 直交する次元へ移る。「バージョンのロールバック」から「クライアント種別の差異」へ移る。同じバックエンドサービスの異なるクライアント（アンドロイド/iOS/H5/ミニプログラム/PC/オープンプラットフォーム）では、APIの認証実装が一致しない可能性がある。「あるクライアントでは呼べるが別のクライアントでは遮断される」APIを探し、弱いクライアントの呼び出し方式で攻撃する。バージョンは1つの次元であり、クライアント種別は別の直交する次元である。
**Q5**: この種の攻撃をどう方法論として定着させるか？
**A5**: 「APIバージョン×クライアント種別」のマトリクスを構築し、同じ機能について全バージョン・全クライアントで認証強度をそれぞれ1回テストする。安全性は最も弱い組み合わせに依存し、防衛側がすべての組み合わせを強化しきることはほぼ不可能である。

### debug/テスト環境/ベータスイッチの漏洩
**Q1**: テスト環境と debug 入口を探したい。クライアントから何を掘り出せるか？
**A1**: 静的に debug/test/dev/beta/staging のキーワードを検索し、コメントアウトや条件で無効化されたテストドメインを検索し、隠されたデバッグメニューのスイッチを検索する。多くの App はテスト環境アドレス、デバッグスイッチ、mockデータをリリースパッケージに残している。判定基準：非本番のドメイン、または有効化できるデバッグ機能が存在するか。
**Q2**: テスト環境ドメインを見つけた場合、直接攻撃するか？
**A2**: 攻撃する。ただし先に評価する。テスト環境は①WAFなし/リスク管理なし、②弱いパスワード/既定アカウントを使う、③データはマスキングが不十分な実データ、④各種デバッグAPIが開いている、ということが多い。それは同じコードの「無防備版」である。ただしテスト環境のデータの実在性と認可の境界に注意し、無関係なシステムを攻撃しない。
**Q3**: クライアントに隠しデバッグスイッチがある場合（例えば logo を連打するとデバッグモードに入る）、何ができるか？
**A3**: 有効化すると、環境切り替え、APIログ、mockログイン、検証をスキップするバックドアが公開されることが多い。これらは開発者が残した利便性のバックドアであり、テストバックエンドへの直接切り替え、平文リクエストの閲覧、さらには認証なしのログインを可能にするかもしれない。このスイッチをトリガーする方法を考える（設定変更、スイッチ判定を真にする hook）。
**Q4**: テスト環境の漏洩もなく、デバッグスイッチもない場合はどうするか？
**A4**: 直交する次元へ移る。「非本番環境を探す」ことから「本番環境のデバッグ残留を探す」ことへ移る。本番APIが詳細なエラーを開いているか（stacktrace 漏洩）、actuator/監視エンドポイントがあるか、閉じられていないAPIドキュメントがあるか、ログに機微情報が出力されているか。本番環境の「デバッグの閉じ忘れ」と「テスト環境の存在」は、直交する2つの情報漏洩ラインである。
**Q5**: テスト環境に侵入できた場合、どう本番まで活用するか？
**A5**: 両者の関連を見る。データベース/キャッシュ/アカウント体系を共有しているか、テスト環境で取得した鍵/token が本番でも有効か、テスト環境の脆弱性（SSRF、コマンド実行など）が本番ネットワークへ横展開できるか。テスト環境は本番内網に侵入するための足がかりであることが多い。

### App レベルの署名検証がリパッケージを阻む場合
**Q1**: smali を改変してリパッケージしインストゥルメンテーションしようとしたが、App がインストール直後に署名が異なると検知して終了する場合、どうするか？
**A1**: 署名検証（App が自身の署名フィンガープリントを検証する）であることを確認する。迂回は2層に分かれる。①検証関数を見つけて patch する（ただし検証は native にある可能性、複数点にある可能性がある）。②パッケージを変更しない注入方式でリパッケージを避ける（システム層注入、gadget ではなく frida server など）。まずリパッケージが本当に必須かを判断する。多くの場合、実行時注入を使えばパッケージを変更する必要がなく、署名検証をトリガーしない。
**Q2**: パッケージ変更が必須の場合（gadget を内蔵して非 root 注入を行うなど）、署名検証をどう迂回するか？
**A2**: 検証点を特定する。getPackageInfo、signatures、証明書フィンガープリント定数の比較を検索する。検証ロジックの本質は「実際の署名==内蔵の期待値」であり、hook/patch して常に真にする。複数の検証点や native 検証がある可能性に注意し、trace で全体を押さえる。
**Q3**: 署名検証が native にあり、整合性検証と連動している場合（どのバイトを変更してもクラッシュする）、どうするか？
**A3**: 直交する次元へ移る。「パッケージ変更後に検証を欺く」ことから「パッケージを変更しない」ことへ移る。APKファイルを変更しない技術で同じ目的を達成する。ディスク上のファイルは一切変更せず、実行時のメモリ内でのみ注入/hook する。署名検証と整合性検証が検査するのはディスクファイルであり、実行時メモリ注入は検知できない。
**Q4**: 実行時注入もアンチデバッグに遮られ、リパッケージも署名検証を通過できないという両面塞がりの場合はどうするか？
**A4**: プロセス内に入らないルートに退く。重要アルゴリズムの純粋な静的復元（App を実行しない）+ API面の直接攻撃である。署名検証、整合性検証、アンチデバッグはすべて「クライアントの自己防衛」であり、いずれも「このクライアントを実行する」ことに対して作用する。アルゴリズムとAPIさえ取得すればクライアントを迂回でき、これらの防衛は自分にとってゼロになる。
**Q5**: リパッケージの道を進む価値があるかをどう判断するか？
**A5**: リパッケージは署名検証+整合性検証という2つの迂回タスクを連鎖的にトリガーし、重い投資である。「改造版を自動化/チームメイトに配布して長期使用する」必要がある場合にのみ価値がある。一時的な侵入では、パッケージを変更しない実行時方式を優先する。

### 実行時にメモリから鍵/平文を抽出する
**Q1**: 静的解析で key が見つからず、アルゴリズムが native にあって逆算できない。key はメモリ内にあると分かっているが、どう取得するか？
**A1**: 中核の考え方：key が「必ず平文で現れる」瞬間に取得する。鍵がどのように保護されていても、暗号化・復号の実行時には平文に戻して crypto 演算に渡さなければならない。方法：システム crypto API を hook し（ほぼすべての暗号化は最終的にシステムライブラリを呼ぶ）、それが呼び出される際に渡された key と data を dump する。システムライブラリはすべての暗号化の最終到達点であり、防ぎようがない。
**Q2**: それがシステム crypto ライブラリを呼ばず、自社開発アルゴリズムをメモリ内で実行している場合はどうするか？
**A2**: メモリ検索/dump へ移る。暗号化操作の前後でプロセスメモリを dump し、既知の暗号文/平文ペアで差分比較して key が存在するメモリ領域を特定する。または key らしきメモリ領域にアクセスブレークポイントを張り、誰がそれを使うかを見る。自社開発アルゴリズムも「データがメモリに入って読み書きされる」ことからは逃れられない。
**Q3**: アンチデバッグにより attach できず、ブレークポイントを張ると即クラッシュする場合はどうするか？
**A3**: 「オフラインメモリスナップショット」へ移る。プロセスのメモリダンプ（core dump、エミュレーターメモリスナップショット）を取得する方法を考え、オフラインスナップショット内で鍵の特徴（高エントロピー文字列、既知形式のkey）を静的に検索する。オフライン解析は実行時アンチデバッグをトリガーしない。「いつメモリを取るか」を変える。
**Q4**: メモリ内の key も難読化/断片化保存されている場合（使う時だけ組み立てる）、どうするか？
**A4**: 直交する次元へ移る。「key という静的オブジェクト」を探さず、「key が使われる関数」を探す。crypto 演算関数（key 変数ではない）のところで hook する。この瞬間、key は必ず組み立て済みで利用可能な形に復元されている。「保存された鍵を探す」ことから「使用中の鍵を取得する」ことへ移る。
**Q5**: メモリ内の key を取得した後、何に注意するか？
**A5**: それが長期keyかセッション一時keyかを確認する。セッションkeyは現在のセッションにのみ有効であり、必要なのはすべてのセッションkeyを導出できる主鍵またはアルゴリズムかもしれない。一時keyなら、その生成関数を hook し直すことが根本である。

### WebSocket/長接続/独自プロトコルをどう解析するか
**Q1**: App が WebSocket または独自TCP長接続で中核データを送信しており、HTTPパケットキャプチャツールでは見られない場合、どうするか？
**A1**: まずプロトコル種別を確認する。全トラフィックの pcap を取得してポートとハンドシェイク特徴を見る（WebSocket にはアップグレードハンドシェイクがあるが、独自TCPにはない）。WebSocket over TLS は WS 対応のパケットキャプチャツール、または上位 frame の hook で対応できる。独自バイナリプロトコルなら、クライアントの送受信関数を hook して平文を取得するしかない。判定基準：テキストフレームかバイナリか、さらに暗号化が重ねられているか。
**Q2**: WebSocket フレームの内容が依然として暗号文/protobuf で、構造を読み解けない場合はどうするか？
**A2**: protobuf なら proto 定義を探す（クライアントに .proto が含まれることが多い、またはコードからフィールド構造を復元できる）。あるいは protobuf デコードツールでフィールドを盲解する。さらに暗号化が重ねられているなら hook で暗号化・復号関数に戻る。独自プロトコルの要点は「符号化・復号」の層を押さえることであり、通常クライアントに明確なシリアライズ/デシリアライズ関数がある。
**Q3**: 長接続に対して改ざんテストを行いたい。見るだけでなく、どう行うか？
**A3**: 送受信関数で hook して「実行時中間者」を実現する。outgoing frame を遮断して内容を改変してから送信し、incoming frame を遮断して内容を改変してから App に渡す。これはネットワーク層の MITM より強力である。暗号化の内側、プロトコルの内側で操作するからである。これで権限外アクセス、インジェクション、ロジック迂回をテストする。
**Q4**: 長接続プロトコルのリバースエンジニアリングのコストが高すぎ、時間が足りない場合はどうするか？
**A4**: 直交する次元へ移る。「長接続を攻略する」ことから「そのHTTP兄弟APIを探す」ことへ移る。中核業務は長接続プッシュ以外にも、ログイン/注文/照会などの重要操作は往々にして依然としてHTTP APIを通る（長接続はメッセージ/リアルタイムプッシュに使われることが多い）。まずHTTP面を攻略し尽くし、長接続は最後に回す。最も難しいプロトコルに評価全体を妨げさせない。
**Q5**: 長接続自体に固有の攻撃面はあるか？
**A5**: ある。接続確立時の認証がハンドシェイクで1回だけか（その後は検証されず、接続のハイジャックがそのまま身元のハイジャックになる）、メッセージを権限外アクセスで他人に配信できるか、サーバープッシュを偽造できるか。長接続の「1回の認証で長期信頼する」モデルは、それ特有の弱点である。

### アカウントなし/未ログイン状態でどう局面を開くか
**Q1**: 対象Appが登録・ログインを必要とするが、手元に有効なアカウントがない場合、どう始めるか?
**A1**: まず未ログインで到達可能な攻撃面を列挙する。登録API、ログインAPI、パスワード再設定、ゲスト/未ログインでアクセス可能なAPI、そして静的リソースと公開APIである。多くのAPIは未ログイン状態で攻撃できる（情報漏洩、権限外アクセス、インジェクション）。アカウントは根本的に不要である。まず「匿名で到達可能な面」を把握する。
**Q2**: ログイン済みテスト用のアカウントが欲しいが、登録が制限されている場合（招待コード/実名/電話番号が必要）、どうするか？
**A2**: 登録の傍路を探す。H5版/ミニプログラム版の登録がより緩いか、旧版登録APIは一部の検証が不要か、サードパーティログイン（WeChat/Appleログイン）が電話番号登録を迂回できるか。同じアカウント体系には往々にして複数の登録入口があり、ハードルが異なる。
**Q3**: まったく登録できず、アカウントを1つも入手できない場合はどうするか？
**A3**: 直交する次元へ移る。「認証が必要な攻撃面」から「認証メカニズム自体」へ移る。ログイン/登録/再設定フローをハードルではなく攻撃対象として扱う。SMS認証コードのロジック脆弱性、パスワード再設定のロジック脆弱性、ユーザー列挙、OAuthのロジック脆弱性である。認証フローの突破はアカウントを取得できるだけでなく、それ自体が高危険度の脆弱性である。「アカウントで業務を攻撃する」ことから「認証を攻撃してアカウントを取る」ことへ移る。
**Q4**: 認証フローも厳格な場合はどうするか？
**A4**: 「横方向での身元借用」へ移る。サードパーティログインのロジック脆弱性（token の混用、紐づけハイジャック）、または他の合法的な経路からテスト認証情報を取得する。そして登録が開放されたテスト環境がないかを見る。常に認可の範囲内で操作する。
**Q5**: 低権限アカウントを1つ取得した後、次の判断は何か？
**A5**: 即座に権限外アクセスへ移る。このアカウントで水平方向の権限外アクセス(他人のデータを見る)と垂直方向の権限外アクセス(管理APIを呼ぶ)を試す。1つの一般アカウントはシステム全体をこじ開ける足がかりであり、認証付きでほぼすべてのAPIにアクセスできるようにして、権限外アクセスとロジック脆弱性を系統的にテストできる。

### 攻撃面の優先順位：クライアント vs API vs サーバーサイドコンポーネント
**Q1**: モバイルAppの対象に対し、クライアントのリバースエンジニアリング、APIテスト、サーバーサイドコンポーネントの3つがすべて攻撃できる場合、まずどこに投じるか？
**A1**: 「費用対効果」順に並べると、通常は API面 > サーバーサイドコンポーネント > 深度のあるクライアントのリバースエンジニアリングである。高危険度の脆弱性（権限外アクセス、ロジック脆弱性、インジェクション、未認可）は大半が API/サーバーサイドにあり、深度リバースエンジニアリング（アンパック、VMP迂回）は投資が大きく、成果は「アルゴリズムの取得」という中間生成物に過ぎないことが多いからである。戦略：軽量なリバースエンジニアリングで API と署名を取得する → 主力を API 攻撃に注ぐ → リバースエンジニアリングは API が必要とする場合にのみ必要に応じて深掘りする。
**Q2**: どのような場合に深度のあるクライアントのリバースエンジニアリングを優先すべきか？
**A2**: ①中核アセットがクライアントにある場合（ハードコードされた高価値の鍵、ローカルの機微データ）。②アルゴリズムを逆算しないと API とまったく対話できない場合（全暗号化・全署名かつオラクルが使えない）。③対象自体がクライアントの安全性評価である場合。そうでなければ、リバースエンジニアリングは手段であって目的ではない。
**Q3**: API を一通り攻撃したがすべて厳格な場合、サーバーサイドコンポーネントへ移るべきか？
**A3**: 移るべきである。「アプリケーション層APIのロジック」から「サーバーサイドのインフラストラクチャ」へ移る。API背後のミドルウェア、アップロード機能によるファイル解析/SSRF、APIがトリガーするサーバーサイドコンポーネント（エクスポートがある解析ライブラリを使う、画像処理があるコンポーネントを使う、など）である。App のAPIはサーバーサイドコンポーネントを攻撃する入口であり、ロジックを攻略できなければ技術的な脆弱性を攻撃する。
**Q4**: 3つすべてに投資したがうまくいかず、全体が行き詰まった場合はどうするか？
**A4**: 直交する次元へ移る。「この1つのApp」から飛び出し、「このバックエンドの他の露出面」へ移る。同じバックエンドサービスは通常、web版、オープンプラットフォーム、提携先連携、内部システムからも呼び出されている。攻撃面の境界は「このバックエンドシステム」であり、「このモバイルApp」ではない。アセットのマッピングで関連ドメイン/システムを洗い出し、最も弱い入口から入る。
**Q5**: この優先順位をどう動的に調整するか？
**A5**: 情報点を1つ突破するたびに並べ直す。ハードコードされたクラウドkeyを取得→クラウドアセットを優先する。権限外アクセスを1つ取得→権限外アクセス面を深掘りする。テスト環境を発見→テスト環境攻撃へ移る。レッドチームの優先順位はインテリジェンスに応じて随時更新されるもので、開始時に固定しない。常に「現在の既知情報の中で最も決定的な成果を得やすいライン」にリソースを集中する。

### サードパーティSDKが突破口になる場合
**Q1**: App が多数のサードパーティSDK（プッシュ、統計、決済、カスタマーサービス、地図）を統合している場合、これは攻撃面になるか？
**A1**: なる。しかも往々にして「防衛側の管理が届かない」弱点である。まず SDK の一覧とバージョンを洗い出す（静的解析でパッケージ名/クラス名/バージョンを抽出できる）。判定基準：既知の脆弱性バージョンがあるか、コンポーネントを公開しているか、独自の認証とAPIがあるか。SDK は他人が書いたコードが対象の中で動いているものであり、メインプログラムがどれほど安全でも SDK の穴は塞ぎきれない。
**Q2**: ある SDK に既知のCVEがあることが分かった場合、どう悪用するか？
**A2**: バージョンが一致することを確認した後、その脆弱性のトリガー経路が対象 App 内で到達可能かを見る（脆弱性のある機能を使っているか、入口が制御可能か）。一般的な SDK の脆弱性：デシリアライゼーション、任意ファイル読み書き、公開された service/provider、WebView 関連である。到達可能なら攻撃できる。
**Q3**: SDK 自身もバックエンドを呼び出している場合（カスタマーサービスSDK、IM SDK が独立サービスを持つなど）、どう攻めるか？
**A3**: SDK のバックエンドを独立した対象として扱う。それは独自の認証、独自のAPIを持ち、主業務とユーザー身元を共有することが多い。SDK バックエンドのセキュリティ水準はまちまちで、権限外アクセスによるメッセージの読み取り、権限外アクセスによるメッセージ送信、情報漏洩が存在しうる。SDK の独立トラフィックを取得して個別に解析する。
**Q4**: SDK がすべて最新版で、既知の穴がない場合はどうするか？
**A4**: 直交する次元へ移る。「SDKの脆弱性」から「SDKの設定ミス」へ移る。開発者が SDK を統合する際のミスこそが多発地帯である。秘匿すべき SDK の secret をハードコードする、SDK に過大な権限を与える、SDK のコールバック/ホワイトリストの設定を誤る、プッシュSDKが任意にプッシュされうる、などである。脆弱性は SDK のコードではなく統合方法にある。
**Q5**: SDK の部分をさらにどう広げられるか？
**A5**: 「サプライチェーン視点」へ広げる。同じ SDK が大量の App に使われており、1つの SDK の一般的な設定ミスのパターンを一括で再利用できる。そして SDK が報告するデータフロー（統計SDKが機微情報を持ち出す可能性があり、ハイジャックされうる）。サードパーティSDKは攻撃面の中で防衛側に最も軽視されやすい一環である。

### クライアントが行う検証を、サーバーサイドは信じるか
**Q1**: App がクライアントで大量の検証を行っていることに気づいた（金額、形式、権限判定）。これらはすべて迂回できるか？
**A1**: サーバーサイドも検証していると証明されるまで、既定ではすべて迂回可能とみなす。中核原則：クライアント検証はUXに過ぎず、セキュリティ境界ではない。方法：クライアントを迂回し（App の検証コードを経由せずに直接リクエストを構築する）、クライアントが遮断した不正な値を直接サーバーに送信し、サーバーが受け入れるかを見る。判定基準：サーバーサイドが独立して検証するか。
**Q2**: 「クライアントを迂回してサーバーサイドだけをテストする」ことをどう効率的に行うか？
**A2**: 直接API層でリクエストを構築する（取得した正規リクエストをテンプレートにする）。App の画面を一切経由しない。クライアントのすべてのフロントエンド検証(ボタンの無効化、形式制限、金額ロック)は、直接パケットを送信すればすべて無効になる。これはモバイル/フロントエンドセキュリティテストの基本であり、常にトラフィック層でテストし、UI層でテストしない。
**Q3**: どのクライアント検証を最優先で迂回テストすべきか？
**A3**: 優先順位：①金額/権限/身元に関わる検証（迂回=権限外アクセスまたは金銭搾取）。②形式/長さ検証（迂回=インジェクションの前置き）。③業務状態検証（迂回=ロジック脆弱性）。「クライアントができないと言う」場所はすべて、サーバーサイドで本当にできないのかを検証する価値がある。
**Q4**: 迂回後、サーバーサイドも確かにすべて検証していることが分かり、クライアント検証という方針が途絶えた場合はどうするか？
**A4**: 直交する次元へ移る。「クライアントは行いサーバーは行わない」ことから「クライアントとサーバーの理解の不一致」へ移る。両端の同じデータに対する解析/検証ルールに差異がある場合（クライアントはルールA、サーバーはルールBなど）、その間の差集合が脆弱性となる。パラメータ汚染、型混乱、エンコーディング差異、切り詰め差異である。「誰が検証しないか」ではなく、「両側の検証が異なる」ことが問題である。
**Q5**: この原則をどう検査アクションとして内面化するか？
**A5**: クライアントの制限の1つ1つについて、「クライアントを通さず、この不正な値を直接送信したら、サーバーはどうなるか」と問いかける。これを条件反射にする。モバイルとH5の大半の脆弱性の根源は「信頼すべきでないクライアントを信頼した」ことである。

### OAuth/サードパーティログインのロジック脆弱性
**Q1**: App が WeChat/Apple/サードパーティアカウントのログインに対応している場合、この部分でどう脆弱性を探すか？
**A1**: 認可コード/token の受け渡しと紐づけの段階に注目する。定番の点：①サードパーティが返す code/token をサーバーがユーザー情報と交換する際、紐づけ関係をハイジャックできるか。②redirect_uri の検証が厳格か（制御可能なら認可コードをハイジャックできる）。③サードパーティの openid/unionid が身元として信頼され、二次検証が欠けていないか。判定基準：1つのサードパーティ身元で別の業務アカウントにログイン/紐づけできるか。
**Q2**: 具体的にアカウントハイジャックをどうテストするか？
**A2**: 紐づけフローをテストする。ログイン状態でサードパーティアカウントを紐づける際、紐づけ先のアカウントidを改ざんできるか（攻撃者のサードパーティアカウントを被害者アカウントに紐づける、またはその逆）。そしてログイン時にサードパーティアカウントが未登録の場合に自動作成/既存アカウントへ自動関連付けするか、関連付けロジックには欠陥があることが多い。
**Q3**: redirect_uri と認可コードの検証がともに厳格な場合はどうするか？
**A3**: 「token の混用/端末横断」へ移る。1つのサードパーティの access token を他の使うべきでない場所で使えるか、異なる App がサードパーティの appid を共有する場合に token を App 横断で使えるか、id_token の署名と受信者(aud)が検証されるか。OAuth の信頼の誤配は「token が想定外の受信者に使われる」ことにあることが多い。
**Q4**: OAuth フロー全体が厳格な場合はどうするか？
**A4**: 直交する次元へ移る。「OAuthプロトコルのロジック」から「OAuthの後のセッション」へ移る。サードパーティログイン成功後、業務システム自身が発行するセッションtoken/紐づけロジックこそが弱点である。サードパーティは身元認証を正しく行ったが、業務システムがその身元を受け取る際に誤りうる（権限外アクセスによる紐づけ、セッション固定、身元の混同）。攻撃点はプロトコル自体から「業務システムが認証結果をどう消費するか」へ移る。
**Q5**: この種の脆弱性の危害をどう評価するか?
**A5**: 「ゼロインタラクションでのアカウント乗っ取り」または「一括乗っ取り」が可能かを見る。認可コード/紐づけハイジャック系が1回のクリック誘導で乗っ取り可能なら高危険度、openid の予測/列挙で他人のアカウントに一括ログイン可能なら極めて危険である。サードパーティログインの脆弱性は、往々にして一度の攻撃で完全なアカウント乗っ取りになる。

### モバイルAPIのインジェクション系脆弱性
**Q1**: APIの認証ロジックを攻略できない。従来型インジェクション（SQLi/コマンドインジェクションなど）を探したいが、モバイルAPIへどう切り込むか？
**A1**: モバイルAPIのインジェクション面は web と同じだが、パラメータが暗号化 body に隠れているため軽視されがちである。前提：まず復号して平文パラメータを見る。それから各パラメータに対して定番のテストを行う。SQLi(エラーベース/ブール/時間ブラインド)、NoSQLインジェクション、コマンドインジェクション、SSTI である。モバイルバックエンドも普通のバックエンドであり、パラメータが SQL/コマンド/テンプレートに入ればやはりインジェクションできる。判定基準：インジェクション特徴を持つ payload が異常/遅延/データ変化を引き起こすか。
**Q2**: パラメータが暗号化と署名を経ており、変更すると署名が失敗する場合、どうインジェクションをテストするか？
**A2**: 暗号化・復号/署名オラクルの能力を使う。復号→パラメータを変更して payload を注入→再暗号化→署名を再計算（またはオラクルを使う）→送信、という流れである。暗号化署名はインジェクションテストの手続きを1つ増やすだけで、インジェクション自体の存在を変えるものではない。多くの人が「パラメータを変更できない」からとインジェクションテストを諦め、まさにこの部分を見落とす。防衛側も「暗号化すればインジェクションはない」と思いがちである。
**Q3**: どのモバイルAPIパラメータにインジェクションが最もありうるか？
**A3**: 優先してテストするのは、検索/絞り込み/ソートパラメータ（SQL の orderby/where に直接入る）、エクスポート/レポートAPI、旧API（パラメータ化されていないことが多い）、そしてバックエンドコマンドに結合されるパラメータ（ファイル名、パス）である。モバイルの検索と一覧APIは SQLi の多発地帯である。
**Q4**: 従来型インジェクションがすべてパラメータ化/WAF に遮られる場合はどうするか？
**A4**: 直交する次元へ移る。「ユーザー入力のパラメータを注入する」ことから「信頼された header/メタデータを注入する」ことへ移る。モバイルAPIはデバイス情報、バージョン番号、送信元などを header に置き、サーバーが無防備にそれらを記録/照会することが多い（User-Agent、deviceId をログSQLに結合したり照会に使ったりする）。防衛側の注意は業務パラメータに集中しており、メタデータフィールドは盲点である。
**Q5**: インジェクションポイントを1つ見つけた後、どう戦果を拡大するか?
**A5**: インジェクション位置が何に到達できるかを評価する。データベースインジェクション→データベースの持ち出し/ファイル書き込み/権限昇格。コマンドインジェクション→サーバーへの直接RCE。SSTI→往々にして同じくRCEである。モバイルAPIのインジェクションは成立すれば、「Appの脆弱性」から「サーバー陥落」の入口へ格上げされ、全力で深部へ攻める。

### ファイルアップロードAPIへの攻撃
**Q1**: App にアバター/画像/添付ファイルのアップロード機能がある場合、このAPIをどう攻めるか？
**A1**: アップロードはモバイルで一般的な高危険度の面である。まず把握する。どこへアップロードするか（自社ストレージかクラウドOSSか）、サーバーがどう検証するか（種別、拡張子、内容）、アップロード後のファイルがどうアクセス・処理されるか。判定基準：想定外の種別をアップロードできるか、保存パスを制御できるか、アップロードしたファイルがサーバーに解析されるか。「アップロードする」ことと「悪用できる」ことの2段階に分ける。
**Q2**: webshell をアップロードしたいが種別検証がある場合はどうするか？
**A2**: 定番の迂回コンビネーション：拡張子/大文字小文字の変更、Content-Type の変更、画像ヘッダーを付けた多言語ファイル化、解析脆弱性の悪用（一部ミドルウェアの解析特性）、二重拡張子、パストラバーサルによる保存位置変更である。判定基準：まず検証がクライアントかサーバーかを見る（クライアント検証なら直接迂回できる）。サーバー検証なら迂回点を1つずつ試す。
**Q3**: アップロードは成功したがファイルが OSS にあり実行不可で、shell を送っても無駄な場合はどうするか?
**A3**: 他のアップロード危害の攻撃に切り替える。①パストラバーサルによる既存ファイルの上書き（設定/他人のファイルを上書き）。②XSS（html/svg をアップロードしてブラウザに解析させる）。③サーバー処理時の脆弱性（画像処理コンポーネントの解析脆弱性、リモート画像 url 経由の SSRF）。④他人がアップロードしたファイルへの権限外アクセス。アップロードの危害は webshell だけではない。
**Q4**: アップロード検証が極めて厳格で、ストレージも十分に隔離されており、この道が途絶えた場合はどうするか？
**A4**: 直交する次元へ移る。「アップロードするファイル内容」から「アップロードが引き起こすサーバー挙動」へ移る。例えばアップロード時に url を渡してサーバーに取得させる（SSRF）、アップロード後にトリガーされるトランスコード/プレビュー/ウイルススキャン（コンポーネント脆弱性がありうる）、またはアップロードAPI自体の権限外アクセス（他人のスペースへ送る）。攻撃点は「ファイル自体」から「サーバーがファイルを処理する過程」へ移る。
**Q5**: アップロード脆弱性の最終的な価値をどう判断するか?
**A5**: 順位付け：実行可能ディレクトリへの shell アップロード=RCE(最高)。パストラバーサルによる重要ファイルの上書き≈RCEまたは権限昇格。サーバーコンポーネント脆弱性のトリガー=RCE。格納型XSS/ファイルへの権限外アクセス読み取り=中危険度。まずコード実行に至るかを判断し、不可能なら次善策として情報漏洩/XSS を取る。

### GraphQL/新方式APIの攻撃面
**Q1**: パケットキャプチャでAPIが GraphQL（または同様の集約照会API）であることが分かった場合、REST の手法と何が異なるか?
**A1**: GraphQL 最大の贈り物は introspection（自省）である。まず自省照会で完全な schema を取得できるか試す。1回のリクエストですべての種別、フィールド、query、mutation が得られ、全APIドキュメントを手に入れたに等しい。判定基準：自省が有効か。有効なら対象がAPIマップを差し出したに等しく、機微な query/mutation を重点的に探す。
**Q2**: 自省が無効化されている場合はどうするか?
**A2**: フィールドブルートフォースとエラー情報の活用へ移る。GraphQL のエラーは「フィールドXが欲しいのでは」(did you mean) とプロンプトすることが多く、これに基づいて schema を徐々に推測できる。またはクライアントコードから実際に使う query を抽出する。自省が無効なことはAPIが無いことを意味せず、地図を自分で組み立てる必要があるだけである。
**Q3**: GraphQL 特有の脆弱性で重点的にテストすべきものは何か?
**A3**: ①権限外アクセス：GraphQL はフィールド単位の認証で誤ることが多く、あるフィールドに権限を付け忘れると機微データを照会できる。②ネスト照会DoS（深いネストでリソースを枯渇させる）。③一括照会によるレート制限迂回（1つのリクエストに複数の操作をまとめて頻度制限を迂回し、認証コードのブルートフォース/列挙に使える);④mutation の権限外アクセス（他人のデータを変更する）。フィールド単位の権限外アクセスは GraphQL の第一の問題である。
**Q4**: GraphQL の認証が厳格に作られている場合はどうするか?
**A4**: 直交する次元へ移る。GraphQL の「集約」特性を利用して、他のAPIにはできないことを行う。エイリアス/一括処理で1つのリクエスト内に大量の操作を発行して、リクエスト数ベースのレート制限を迂回し、GraphQL をレート制限迂回のツールとして使って他の脆弱性を攻撃する（ブルートフォース、列挙）。「GraphQL 自体を攻撃する」ことから「GraphQL の特性で別の面を攻撃する」ことへ移る。
**Q5**: GraphQL の対象に対する優先アクションをどう素早く判断するか?
**A5**: 開始時の三連：自省を試す(schema を取る)→schema を調べて機微な mutation（パスワード変更/ロール変更/送金系）と機微な query（ユーザー照会/設定照会）を探す→1つ選んでフィールド単位の権限外アクセスをテストする。GraphQL は攻撃面を構造的に公開しており、REST より系統的に整理しやすい。この特性を活用する。
