# Appクライアント · プロテクトのアンパックの判断

### APK を入手したらまずプロテクトか判定する
**Q1**: 手元にアンドロイドの APK がある。まだ解析を始めていない。最初に何を判定すべきか?
**A1**: まず「プロテクト/パッカーかどうか」を判定し、業務ロジックの逆コンパイルを急がない。判定基準:解包後、classes.dex 内の Application クラスが極小で、本物の業務クラスがほぼ存在せず、パッカーの Loader しかない。lib ディレクトリに libjiagu/libshell/libsecexe/libDexHelper の類の SO がある。assets 内に暗号化された dex blob がある(サイズ大、エントロピー高)。メイン dex に業務コードが見つからなければ、ほぼパッカー。パッカーの Loader を読むのに時間を浪費しない。

### どのプロテクトベンダーか識別する
**Q1**: パッカーがあると確認した。まずベンダーを識別すべきか?
**A1**: すべき。ベンダーがアンパックの打ち手を決める。判定基準は特徴による。SO 名、パッケージ名のプレフィックス、assets のファイル名、登録された native メソッド名。ベンダーごとにパッカーの dex 解放タイミング、アンチデバッグの強度、抽出の有無(メソッド本体を空にする)が大きく異なる。
**Q2**: 特徴が曖昧で、SO 名が変更されている場合はどうする?
**A2**: 挙動フィンガープリントに移る。Application.attachBaseContext 内で何を呼んだか、カスタム ClassLoader があるか、DexClassLoader で一時的に解放されたファイルを読み込むかを確認する。既製の識別ツール(apkid など)で先に一度走らせて事前情報を得て、その後人手で補正する。

### 全体パッカー vs 抽出パッカーの分岐判断
**Q1**: アンパック前にまず 1 つ判定しなければならない。これは全体プロテクトか関数抽出(dex を空にする)か。
**A1**: これが最も重要な分岐。全体パッカー:完全な dex がメモリ内のある時点で完全なので、メモリを dump すればよい。抽出パッカー:dex 構造はあるが、メソッドの code_item が空にされ、そのメソッドを実行するときに初めて native が回填する。判定基準:静的解析で dex 内のメソッド insns の長さが 0 か異常オフセットを指し、大量のメソッドの code_off が同じか 0。判定を誤ると dump しても全部空メソッドになる。
**Q2**: 抽出パッカーだとどう素早く検証する?
**A2**: dex 解析ツールで code_item を集計する。圧倒的多数のメソッド本体が空だがクラス構造が完全なら、抽出。このとき全体 dump は無効で、「能動的呼び出し+ランタイム回填後に取得」(fart 系の方式)に移る必要がある。

### アンパックツール選択の優先順位
**Q1**: 未知のパッカーに対し、アンパックツールをどう選び、どの順で試す?
**A1**: 「粗から細へ、汎用から専用へ」に従う。まず汎用のワンクリック(frida-dexdump / drizzleDumper など)で全体パッカーに素早く対処する。ダメなら hook タイミング型(メモリ dump)に移る。さらにダメならカスタム(fart/BlackDex 系の能動的呼び出しで抽出をアンパック)。原則:まず 5 分で最も省力なものを試し、いきなりカスタム ROM をコンパイルしない。
**Q2**: ワンクリックツールで大量の dex を dump したが逆コンパイルがエラーになる場合はどうする?
**A2**: 正常だ。dump にはよく汚いデータが混じる。フィルタリングに移る。サイズと有効クラス数で並べ替え、パッカー自身の小さな dex を捨て、大きな dex は baksmali で逆コンパイル可能性を検証してから、統合・修復する。

### frida-dexdump で出ないときの切り替え
**Q1**: frida を attach したのに dexdump で dex が 1 つも取得できない。どういうことか?
**A1**: まず 3 つの可能性に分ける。1 つ目は frida がアンチデバッグ/アンチ注入に潰された(プロセスが即終了または gadget を検知)。2 つ目は dex が平文で完全にメモリに常駐したことがない(抽出パッカー)。3 つ目はタイミングが悪く、dex 解放後に消去された。判定基準:frida が安定して attach できているか、プロセスが生存しているかを見る。
**Q2**: アンチ frida に潰されたと確認した。どこへ移る?
**A2**: 対抗の次元に移る。frida-gadget 注入(パッケージを変えて再導入)、magisk の隠蔽、アンチデバッグ点の patch、または frida 以外のアンパック方式(xposed/lsposed ベースの fart、魔改造 ART など)に変える。frida そのものに固執しない。

### dex を取得する最適なタイミング
**Q1**: 全体パッカーの dex はある瞬間だけ平文。hook はどこに張るべきか?
**A1**: 定番のタイミングは dex 読み込み入口。DexFile 構築、DexClassLoader、または ART の OpenMemory/DefineClass/LoadMethod。これらの点でメモリ内の dex ヘッダー(魔数 dex\n035)を dump するのが最も安定。判定基準:hook 命中時に begin ポインタを読んで完全な dex_file 構造を得る。
**Q2**: hook できたが、dump した dex はヘッダーが合っているのに内容が切れている?
**A2**: 読んだ size が間違っているか、dex が分断されている。方向転換:dex header 内の file_size フィールドに従って読み直すか、プロセスメモリ内のすべての dex 魔数セグメントを走査して全量 dump し、1 つずつ検証する。

### アンチデバッグでプロセスが即終了する
**Q1**: attach するかデバッグを開くとすぐ App がクラッシュする。アンチデバッグが強固だ。どう突破する?
**A1**: まずアンチデバッグ点を特定する。よくあるのは ptrace 自己アタッチ、TracerPid の検知、/proc/self/status の検知、frida ポート 27042 の検知、gadget so 名の検知。strace またはキーシステム呼び出しの hook で、どの検知で止まるかを見る。
**Q2**: 検知点が多すぎて 1 つずつ patch するのは遅すぎる?
**A2**: 次元を下げる方向に移る。環境を直接替える。root + magisk 隠蔽 + カスタムのアンパック ROM を使うか、実機 vs エミュレータを切り替える(エミュレータだけを検知するパッカーがある)。「単点検知との対抗」を「それが検知できない実行基盤への交換」に変える。

### dump 後の dex 修復(header/検証)
**Q1**: dump した dex が baksmali で checksum/signature エラーとなり、逆コンパイルできない?
**A1**: これはよくある。dump したメモリ dex ヘッダー内の checksum、signature、file_size、map_off がパッカーに変更されているか実際と一致しない可能性。修復スクリプトで checksum(adler32)と SHA1 signature を再計算し、file_size を修正する。大半のツールは逆コンパイル時にこの数項目しか検証しないので、直せばよい。
**Q2**: 直してもなお構造エラーが出る?
**A2**: セグメントのずれの特定に移る。010 editor で dex 形式と照らし合わせ、map_list の各セグメントの offset を手作業で検証するか、より寛容なパーサ(jadx は baksmali より寛容なことがある)に替える。ダメなら string/method 表だけを抽出して静的解析の手がかりにし、完全な逆コンパイルを諦める。

### 抽出パッカー:メソッド本体が空、どうコードを取り戻すか
**Q1**: 抽出パッカーと確認し、dex 構造は全部あるがメソッドがすべて空。どう code_item を取り戻す?
**A1**: 核心の発想は「能動的呼び出しで回填をトリガーする」。各メソッドを ART に 1 回ずつインタープリタ実行させると、パッカーは実行前に code_item を埋め戻す。埋め戻した後、実行前にそのメソッドを dump する。これが fart の原理で、魔改造した ART が ArtMethod の呼び出し点でメソッド本体をエクスポートし、その後オフラインで dex に再統合する。
**Q2**: 能動的呼び出しのトリガーが不十分で、一部のメソッドが一向に回填されない?
**A2**: 走査戦略に移る。リフレクションで全クラスの全メソッドを列挙して能動的に invoke する(クラッシュの catch に注意)。ニッチなメソッドをカバーする。または特定の業務クラスを手動でトリガーする。なお漏れがあれば部分的なアンパックを受け入れ、対象関数に対して点対点で補完する。

### キー関数が 1 つ必要なだけ、全体をアンパックする価値はあるか
**Q1**: ある署名アルゴリズム/暗号化関数だけを見たい。App 全体をきれいにアンパックする必要があるか?
**A1**: 価値がない。全体のアンパックはコストが高い。正確な打撃に移る。対象関数の引数と戻り値を直接 hook する(動的観測)か、その関数を含むクラスだけをアンパックする。レッドチームは対象志向で、入出力のマッピングを得られれば十分。「ソースの完全復元」を追求しない。
**Q2**: 対象関数が native レイヤ(SO)内にあり、dex のアンパックは無意味?
**A2**: native のリバースエンジニアリング次元に移る。IDA/Ghidra で SO を静的解析するか、frida でその native 関数を hook してパラメータを見る。JNI 登録の動的関数なら、先に RegisterNatives を hook して本物の関数アドレスを得てから解析する。

### SO のプロテクト(パッカー化された native ライブラリ)の判断
**Q1**: dex のアンパックは終えたが、キーロジックが SO にあり、SO もパッカー化されている(ollvm/自己復号など)。どう判定する?
**A1**: 判定基準:IDA で SO を開くと大量の制御フロー平坦化(ディスパッチャ+状態変数)、文字列暗号化、または .init_array 内に自己復号コード(セグメントがランタイムになって初めて平文)が見える。entry 付近に mprotect + ループ XOR が見えれば、ほぼランタイム復号パッカーだ。
**Q2**: 静的に見るとジャンクコードだらけで読めない?
**A2**: 動的な SO の dump に移る。それを実行させて自己復号させた後、メモリから復号済みの .text セグメントを dump し、IDA で静的解析する。ollvm の平坦化はシンボリック実行/平坦化除去スクリプト(D-810 / deflat など)で復元する。

### 逆コンパイルツールの選定(jadx vs 逆アセンブル)
**Q1**: dex はあるが、jadx で逆コンパイルするとエラーと // ERROR が大量に出る。信じるべきか?
**A1**: jadx は最善を尽くす逆コンパイルで、複雑/難読化に当たると誤り、場合によっては誤誘導する。判定基準:キーロジックの箇所に goto、種別の喪失、明らかに非論理的なコードが現れたとき、java ビューを信じない。
**Q2**: では何を見る?
**A2**: smali レイヤに移る。baksmali が出す smali を直接見る。それは dex の忠実な逆アセンブルで、jadx のように「推測を誤る」ことがない。レッドチームはキー制御フローの照合を一律 smali 基準にし、java は読みの補助に留める。

### 難読化(ProGuard/R8/DexGuard)下での特定
**Q1**: アンパックは成功したが、クラス名もメソッド名も全部 a.b.c で、業務ロジックが見つからない。どうする?
**A1**: 名前の難読化はロジックに影響しない。名前を読むのではなく「アンカー特定」に頼る。文字列定数(URL、エラーメッセージ、SP key)、システム API 呼び出し(Cipher/MessageDigest/OkHttp)、リソース id からそれを参照するコードを逆引きし、つるを辿る。
**Q2**: 文字列も暗号化されている(DexGuard の文字列暗号化)?
**A2**: 動的解析に移る。復号関数(通常 1 つの統一された static String decrypt(...))を hook して文字列を一括復元する。またはランタイムに対象 API(Cipher.doFinal など)を hook して平文データフローを直接観測し、静的復元を回避する。

### メモリ内に完全な dex が現れたかの判断
**Q1**: 「メモリ dump」に賭けるべきか「能動的呼び出し」に賭けるべきかをどう知る?
**A1**: 素早い探査を行う。libart の DefineClass/OpenMemory を hook し、毎回の読み込みの dex サイズとメソッド数を表示する。ある時点でメソッド数が完全で code が空でない大きな dex が読み込まれたなら、全体パッカーなので、メモリを直接 dump すればよい。読み込まれた dex のメソッド本体が空なら、抽出。データで語り、推測しない。
**Q2**: 探査で dex が複数回、セグメントごとに読み込まれる(マルチ dex / 動的読み込みプラグイン)と分かった?
**A2**: セグメントごとの収集に移る。毎回の DexClassLoader 読み込みを dump し、最後に統合する。プラグイン化フレームワーク(ホットフィックスなど)はランタイムに追加の dex を配信し、対応機能をトリガーして初めて読み込む点に注意。

### パッカーが root/環境を検知してデグレード実行する
**Q1**: App が root を検知して、クラッシュはしないがキー機能が使えなくなり、アンパックのタイミングをトリガーできない?
**A1**: キー機能が動かなければ、抽出パッカーは回填しない。まず root 検知を通す。magisk denylist / zygisk 隠蔽、root 検知点(su パス、magisk パッケージ名、ro.debuggable の検知)の hook。判定基準:機能が正常に戻る。
**Q2**: 隠してもなお検知される(SafetyNet/Play Integrity の強検証)?
**A2**: root なしの経路に移る。VirtualApp/デュアル起動フレームワークでアプリケーションレイヤでアンパックするか、frida-gadget で root なし注入するか、実機の物理環境に直接替える。「検知の回避」を「生まれつき適合する基盤への交換」に変える。

### パッカー化後のリソース/マニフェスト情報はまだ信頼できるか
**Q1**: プロテクト後、AndroidManifest とリソースはまだ正確か。先に静的情報収集できるか?
**A1**: できる。しかも先に行うべき。プロテクトは通常 Manifest とリソースを変更しない(変更すると App が動かない)。Manifest からパッケージ名、コンポーネント、権限、exported コンポーネント、ディープリンク、network_security_config を得る。これらは攻撃面の手がかりで、パッカーの影響を受けない。判定基準:aapt/apktool で Manifest を正常に解ける。
**Q2**: apktool の解包がリソース段階でエラーになる?
**A2**: Manifest だけを解く方向に移る。AXML 解析専用ツールでバイナリ Manifest を単独抽出する。リソースのエラーはリソースのプロテクト(一部のパッカーが resources.arsc を暗号化するなど)が原因のことが多いが、コンポーネントリストの取得には影響しない。リソースに詰まらない。

### アンパック生成物の検証で正しさを確認する
**Q1**: アンパックが「成功」した。正しく完全にアンパックできたかをどう確認する?
**A1**: 3 つの検証。1 つ目、対象のキークラス/メソッド本体が空でなくロジックが合理的か。2 つ目、メソッド総数が元の App の規模に近いか(少なすぎるなら漏れ)。3 つ目、再パッケージ化して実行できるか(動けば dex 構造が OK)。dex が出たから終わり、と思わない。
**Q2**: 検証でメソッド数が明らかに少ないと分かった?
**A2**: 補完アンパックに移る。まだ取得していない dex がある(マルチ dex/遅延読み込み/プラグイン)。読み込み hook に戻ってより多くの機能経路をトリガーするか、欠落クラスに対して点対点で能動的呼び出しして回填する。

### 対象がキャプチャ/プロトコル確認だけならアンパックは必要か
**Q1**: 対象は実はサーバーとの通信を理解すること。アンパックはまだ必要か?
**A1**: まずアンパックしない。キャプチャのコストはアンパックよりはるかに低い。先にプロキシで HTTPS をキャプチャする。判定基準:平文リクエストが見えれば API テストを始めるのに十分。アンパックはクライアントのアルゴリズム(署名/暗号化)を見るためで、目的そのものではない。
**Q2**: キャプチャで SSL Pinning を発見し、取得できない?
**A2**: pinning 回避に移る。frida で TrustManager/OkHttp の CertificatePinner を hook するか、objection のワンクリック、またはパッケージを変えて pinning を無効化する。pinning も native/プロテクト内にあるなら、初めてアンパックを検討して pinning ロジックを特定する。

### キャプチャで署名パラメータ(sign/token)が見えて初めてアンパックが必要になる
**Q1**: キャプチャは成功したが、リクエストに計算できない sign フィールドがあり、リプレイが失敗する。今どうする?
**A1**: これこそがアンパックの本当の動機で、sign アルゴリズムを復元したいからだ。しかしより省力な道がまだある。sign を生成する関数(MessageDigest/Mac/独自の呼び出し点を探す)を先に hook し、入力の連結規則を観測して、ブラックボックスでアルゴリズムを復元する。完全なアンパックは不要。
**Q2**: sign アルゴリズムがプロテクトされた SO 内にあり、java レイヤを hook できない?
**A2**: native hook に移る。frida でその SO のエクスポート/JNI 関数を hook するか、直接 RPC で呼び出す。暗号化関数をブラックボックス オラクルとしてリモート呼び出しすれば、アルゴリズムを復元せずとも sign を大量計算できる。

### アンパックを諦める損切り点
**Q1**: アンパックに長く取り組んだが進展がない。いつこの道を諦めるべきか?
**A1**: 損切りを設定する。ベンダーのパッカーが最新の商業用強パッカー + 抽出 + native 難読化 + 強アンチデバッグで、しかも対象がただのあるデータなら、投入と産出が深刻に不均衡になった時点で切り替える。判定基準:核心の対象を迂回路で達成できるか。
**Q2**: どの迂回路に移る?
**A2**: 攻撃面の直交する次元に移る。サーバー側 API の権限外アクセス/ロジック脆弱性(クライアントがどれだけ硬くてもサーバー側は脆いことがある)、キャプチャによるパラメータ改ざん、コンポーネントの露出(exported activity/service/provider)、ディープリンク、WebView の脆弱性、バックアップによるデータ抽出。クライアントのプロテクトはサーバー側の不始末を防げない。

### exported コンポーネント、プロテクトを迂回する近道
**Q1**: プロテクトが硬く、アンパックが面倒。パッカーに触れずに攻められる点はないか?
**A1**: ある。exported コンポーネントを調べる。Manifest 内で exported=true の Activity/Service/Provider/Receiver は外部から直接呼び出せる攻撃面で、プロテクトと無関係。判定基準:認証のない exported ContentProvider(任意ファイル読み取りの可能性)、intent で起動できる内部ページを見つける。
**Q2**: コンポーネントがすべて permission 保護を設定している?
**A2**: permission 解析に移る。signature 級か normal 級かを見る(normal 級は悪意ある App が申請できる)。またはコンポーネント内部のロジックが intent パラメータを信頼している(パストラバーサル、内部 provider への SQL インジェクション)。コンポーネントの門番ではなくデータフローから穴を探す。

### WebView/H5 ハイブリッドアプリの判断
**Q1**: App の大量のページが WebView。プロテクトをアンパックする価値はまだあるか?
**A1**: 必ずしもない。ハイブリッドアプリのコアロジックは H5/JS 内にあることが多い。判定基準:機能ページが WebView。JS レイヤに移る。H5 リクエストをキャプチャ、addJavascriptInterface が公開する native API を見る(RCE の可能性)、WebView が file アクセスを開いているか、制御可能な URL を読み込むかを見る。これらはアンパック不要。
**Q2**: JS も圧縮・難読化されている?
**A2**: ランタイムに移る。WebView のリモートデバッグを有効にする(chrome://inspect。debuggable なら、または setWebContentsDebuggingEnabled を hook して強制有効化)。devtools 内で直接ブレークポイントを張って平文 JS ロジックを見る。静的復元より速い。

### プロテクトされた App のローカルデータ/ストレージ抽出
**Q1**: パッカーと戦いたくない。デバイスから直接そのデータを取得できるか?
**A1**: できる。root 下で /data/data/パッケージ名/ を直接読み、SP、db、キャッシュ、token を取得する。プロテクトはコードを守るが、ランタイムに設置されたデータは守らない。判定基準:データベース/SP 内に平文の認証情報、キャッシュされたレスポンスがある。
**Q2**: データベース/SP が暗号化されている(SQLCipher、暗号化 SP など)?
**A2**: 鍵の取得に移る。鍵は通常ランタイムに生成されるか native から取られる。データベースを開く関数(SQLiteDatabase.openOrCreate または SQLCipher の key が渡る点)を hook して平文 key を得る。またはデータを読む上位 API を直接 hook して復号後のオブジェクトを得て、ストレージ暗号化を回避する。

### マルチ dex / 動的読み込みによるアンパック漏れ
**Q1**: アンパック後、ある機能のクラスがどうしても見つからない。アンパック漏れか?
**A1**: 動的読み込みの可能性が高い。ホットフィックス、プラグイン化、または初回使用時にネットワーク/assets から復号して読み込まれる dex。判定基準:静的パッケージ内にないが、機能は使える。この種の dex はプロテクト時にメイン dex に含まれていないことがある。
**Q2**: こうした遅延読み込みの dex をどう取得する?
**A2**: トリガー式 dump に移る。App 内で手動でその機能まで進んで読み込みをトリガーし、同時に DexClassLoader/InMemoryDexClassLoader の構築を hook して dex をディスクへ書き出す。ネットワーク配信のものは、復号後・読み込み前のステップで平文を dump することもできる。

### java レイヤか native レイヤで手を付けるかの判断
**Q1**: ある機能のキーロジックについて、java か native かをどう素早く判断する?
**A1**: まず java レイヤのアンカーが native に直結しているかを見る。対象 java メソッドが native 宣言か、すぐに System.loadLibrary のライブラリ関数を呼ぶか。判定基準:java 内が native 宣言 1 行だけなら、ロジックは必ず SO にある。逆にロジックが dex にあれば、アンパックで解決する。
**Q2**: 区別できず、両方にある?
**A2**: データフロー追跡に移る。java の入口を hook してパラメータを表示し、データを誰に渡すかを見る。native 境界(JNI 呼び出し)まで追ったら SO 解析に移り、境界を越えなければ dex 内で続ける。データの流れで戦場を決め、感覚に頼らない。

### パッカーのアンチ hook(frida/xposed の検知)
**Q1**: frida は attach できるが、キー関数を hook すると App の挙動が変わる/クラッシュする。アンチ hook をどう突破する?
**A1**: パッカーが関数入口の命令を検証する、メモリ内の frida 特徴を走査する、または inline hook のジャンプを検知する可能性。判定基準:hook 前は正常、hook 後は異常。まずどの種別を検知しているか(チェックサム/メモリ走査)を特定する。
**Q2**: 検知が強すぎて hook できない?
**A2**: ハードウェア/非侵襲の観測に移る。inline hook ではなく stalker で命令レベル trace を行うか、gdb のハードウェアブレークポイント、または魔改造した ART で下層からエクスポートする(fart は対象プロセスの可視特徴を変えない)。「検知される hook」を「対象に見えない観測手段」に替える。

### ワンクリックアンパックツールが複数 dex を出す場合の統合
**Q1**: アンパックで十数個の dex 断片が出た。逆コンパイルには統合が必要。どう処理する?
**A1**: まず分類する。パッカー自身の dex(小さく、クラスが loader)は捨てる。業務 dex は残す。ツールで有効な dex を jar に統合する(dex2jar)か、直接複数 dex を一緒に jadx に渡す。判定基準:統合後、対象クラスがすべてあり、参照を解決できる。
**Q2**: 統合後にクラス衝突/重複定義?
**A2**: 重複除去に移る。同名クラスは code が空でなくメソッドが完全な方を残す(抽出パッカーで回填後の版は元の空の版より良い)。スクリプトでメソッド本体が空かどうかで優れた方を選んで統合し、単純に上書きしない。

### プロテクト強度と対象価値の費用対効果の判断
**Q1**: 時間が限られている。強プロテクトの App に対し、どう優先順位を付ける?
**A1**: 「費用対効果マトリクス」で判断する。対象価値が高く+迂回路(サーバー側/コンポーネント/キャプチャ)がある → 先に迂回路を進む。対象価値が高く+クライアントのアルゴリズムが必須 → アンパックに投入するが点対点だけ行う。対象価値が低い → 直接飛ばす。パッカーに正面から当たって時間予算を使い切らない。
**Q2**: チーム/大会で他の人もこの App で詰まっている?
**A2**: 情報共有と分業に移る。パッカーが同じならアンパック方式を再利用でき、1 人がパッカーを攻め、残りがサーバー側を並行して攻める。情報を共有して車輪の再発明を避ける。レッドチームでは「人を替えて次元を替える」こと自体が有効な切り替えだ。

### アンパック環境:エミュレータ vs 実機 vs カスタム ROM
**Q1**: アンパックが何度も失敗する。環境の選択を誤ったか?
**A1**: 環境は見落とされがちな変数。判定基準:パッカーがエミュレータを検知するなら実機、ART の魔改造が必要ならカスタム AOSP ROM(アンパック専用 ROM など)、root なしにしたいなら VirtualApp。まず現在のパッカーが最も嫌う環境を確認してから選ぶ。
**Q2**: 手元に環境が 1 種類しかない?
**A2**: アプリケーションレイヤの方式に移る。root もカスタム ROM もないときは、frida-gadget の再パッケージ化+アプリケーションレイヤのアンパック(BlackDex の類は root なし/対象プロセス内でアンパックできる)で、環境への依存を最小にする。

### iOS クライアント:アンパックではなく復号
**Q1**: 対象が iOS App(ipa)。ここでの「アンパック」は何を指す?
**A1**: iOS の「パッカー」は App Store の FairPlay DRM 暗号化(Mach-O __TEXT 暗号化)で、「復号」(decrypt)して初めて静的解析できる。判定基準:otool -l で cryptid=1 なら暗号化されている。ツール:frida-ios-dump、dumpdecrypted。
**Q2**: 復号後もなお解析が難しい(自社 VMP などのサードパーティプロテクトがさらにある)?
**A2**: 動的解析に移る。iOS では frida で Objective-C/Swift メソッドを hook して挙動を観測するか、cycript/lldb でランタイム解析する。OC の runtime 特性により、動的観測は静的解析での復号後の逆解析より効率的なことが多い。

### 文字列/リソースが単独で暗号化されているかの判断
**Q1**: アンパック後コードは読めるが、キー定数(URL、鍵)が文字化けしているかランタイムに組み立てられる。どうする?
**A1**: 文字列暗号化/リソース保護があり、dex のプロテクトとは独立している。判定基準:コード内がすべて decrypt("文字化け") または char 配列の連結。静的に無理に解かない。
**Q2**: どう効率よく復元する?
**A2**: 復号関数の hook で一括復元する方向に移る。その統一された decrypt 入口を特定し、frida で hook してすべての (暗号文→平文) 対を表示し、App 全体の文字列を一度に復元する。または対象箇所でランタイムに表示する。静的に 1 つずつ解くのは遅すぎる。

### プロテクトされた App のデバッグ属性と debuggable の強制有効化
**Q1**: プロテクトされた App を動的デバッグしたいが、debuggable=false でデバッガを検知する。どう始める?
**A1**: まずデバッグ可能にする。Manifest の debuggable=true に変えて再パッケージ化(署名/完全性検証が発動する可能性)、または ro.debuggable のグローバルデバッグ可能 ROM、または ApplicationInfo.flags を hook。判定基準:jdwp/frida で接続できる。
**Q2**: 再パッケージ化で署名検証(パッカーの自己検証)が発動してクラッシュする?
**A2**: 署名検証の回避に移る。PackageManager.getPackageInfo の署名戻り値を hook するか、パッカーの自己検証関数を hook するか、パッケージを変えない注入方式(frida attach、再パッケージ化ではない)を使う。「パッケージ変更が検証される」を「パッケージ変更なしの注入」に替え、完全性検知を避ける。

### アンパックが全工程で詰まったら、対象そのものに戻って再検討する
**Q1**: 様々なアンパック法を試し、迂回路も考えたが、なお進まない。最後の一手は何か?
**A1**: 根源の問いに戻る。自分は結局何が欲しいのか。「アンパック」という手段を置き、対象を達成するすべての経路を列挙し直す。判定基準:対象がデータ → データの設置点(ストレージ/ログ/メモリ)を探す。対象が API → キャプチャ+サーバー側。対象がアルゴリズム → hook のブラックボックス オラクルでリモート呼び出し。
**Q2**: 再検討しても本当にアンパックが不可欠だと分かった?
**A2**: ならば範囲を極限まで絞る。対象を含む 1 つのクラス/1 つのメソッドだけをアンパックし、最も急進的なランタイム dump(命中したら即取得)を使い、汚いデータは人手で直すことを受け入れる。レッドチームで最も忌むのは牛角に突き進むこと。手段は対象に奉仕する。対象が変わらないなら、あらゆる手段を尽くして替える。
