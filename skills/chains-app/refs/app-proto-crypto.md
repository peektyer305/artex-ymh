# Appクライアント · 通信プロトコルと暗号化の復元

### 未知の App を入手したら、先にトラフィックを見るか、先に静的解析するか
**Q1**: 対象が apk/ipa をくれた。その通信プロトコルを復元するには、第一段階としてパケットキャプチャでトラフィックを見るべきか、先に逆コンパイルすべきか?
**A1**: 先にパケットキャプチャで定性し、次に静的解析で位置を特定する。トラフィックは「事実」であり、すぐに教えてくれる。HTTP を通るか、TLS があるか、body は平文/base64/暗号文か、sign/ts/nonce のようなリスク管理フィールドがあるか。いきなり逆コンパイルの海に飛び込まない。数万のクラスの中で迷子になりやすい。判定基準：ログイン、一覧、注文の典型的なリクエストを 5~10 個取得し、リクエストボディの形態を見て、まず「これはどういう形態のプロトコルか」という仮説を形成し、それから問題を持ってリバースエンジニアリングする。
**Q2**: トラフィックは取得できたが、body が理解できない文字列の塊である。どう素早く定性するか?
**A2**: 3つを見る。長さが 16 バイトの整数倍か（対称ブロック暗号の疑い）、文字集合（純粋な base64/hex/それともバイナリ）、固定ヘッダーのマジックナンバーの有無。base64 は先に 1 層 decode して構造が出るかを見る。定長かつ高エントロピー→AES/SM4。先頭に 30 82 など→ASN.1/RSA/証明書。
**Q3**: 静的逆コンパイルはどの関数から切り込むのが最も時間を節約できるか?
**A3**: 通読せず、「キーワード駆動検索」を行う。sign/encrypt/AES/doFinal/getBytes/Cipher を検索し、リクエスト URL 内のパス文字列を検索し、Content-Type を検索する。文字列定数はリバースエンジニアリング界の道標であり、文字列の相互参照を辿って上へ遡り、リクエストを組み立てる層を見つける。
**Q4**: この「先にパケットキャプチャ」する道が失敗した。すなわちパケットがまったく取得できず、プロキシの中が真っ白な場合はどうするか?
**A4**: 「これは標準的な HTTP プロキシトラフィックではない」という仮説の次元へ移る。非 HTTP の独自 TCP、QUIC/UDP を通っている、またはプロキシ逃逸（システムプロキシを読まない）を行っている可能性がある。透過ゲートウェイでのキャプチャ（iptables リダイレクト / VPN モードのパケットキャプチャツール）に切り替え、リンク層で遮断する。アプリケーション層のプロキシ層で遮断しない。
**Q5**: 透過パケットキャプチャで TCP ストリームは見えるがすべてバイナリで、HTTP ではない場合は?
**A5**: 独自バイナリプロトコルであることを示す。「プロトコル構造の復元」サブタスクへ移る。先に TCP ストリームに従ってフレーム分割し、長さフィールドを探し（分割・粘着パケットの境界）、TLV 構造を推測する。同時に静的解析で socket/OutputStream/ByteBuffer を検索してパッキング関数を特定する。
**Q6**: 時間が迫っている場合、静的解析の深掘りを続けるべきか、動的 hook に切り替えるべきかをどう判断するか?
**A6**: 判定基準は「重要ロジックが可読か」である。逆コンパイル結果が明快な Java で、重要関数が一目で読めるなら、静的解析を続ける。コストが最も低い。難読化が激しい/so 内にある/ホワイトボックスの場合は、無理に読み解かず、動的 hook に切り替えて実行時に平文と鍵を直接取得し、時間を可読性と交換する。

### HTTPS パケットキャプチャが証明書固定(SSL Pinning)に遮られる場合
**Q1**: システム証明書を導入し、ブラウザでは取得できるのに、App が通信するとすぐエラーで切断される。典型的な Pinning である。どう突破するか?
**A1**: まず Pinning かどうかを確認する（SSL handshake / cert 検証失敗のエラーが出る。業務エラーではない）。突破方法はコスト順に並べる。まず汎用迂回スクリプト（Frida の universal unpinning）を試し、OkHttp/TrustManager/一般的なフレームワークをカバーする。駄目なら具体的な検証点を特定して単点 hook する。
**Q2**: 汎用スクリプトを実行しても切断される場合、検証が標準的な位置にないことを示すか?
**A2**: Pinning が非標準の層にあることを示す。native so 内で証明書比較を行っている、BoringSSL の独自検証を使っている、またはハンドシェイクではなくレスポンスを検証している可能性がある。so 層へ移り、SSL_CTX_set_custom_verify / SSL_get_verify_result のような低層関数を hook するか、検証の戻り値を直接 patch する。
**Q3**: so 層も hook したが駄目で、相互認証(mTLS)を疑う場合は?
**A3**: これは重要な方向転換だ。サーバーがクライアント証明書を要求する場合、サーバー証明書検証の迂回だけでは無意味で、クライアント証明書が欠けている。「クライアント証明書/秘密鍵の抽出」の次元へ移る。apk のリソース、assets、暗号化された p12/bks から探すか、実行時に KeyStore/PrivateKey を hook して鍵素材を取得する。
**Q4**: クライアント証明書が暗号化保存された p12 で、パスワードが分からない場合は?
**A4**: パスワードのブルートフォースはせず、ロードポイントを hook する。App 自身は必ず平文パスワードで load する。KeyStore.load(InputStream, char[]) を hook して 2 番目の引数を直接読むか、SSLContext を生成する場所を hook して初期化済みのオブジェクトを取得する。
**Q5**: 対象が iOS で、Frida 環境を整えられない場合は?
**A5**: プラットフォーム直交の次元へ移る。iOS では脱獄 + SSL Kill Switch 系ツールを優先するか、objection の pinning bypass を使う。どうしても脱獄しないなら MITM + プロファイル信頼 + バイナリ層 hook を使う。iOS の pinning は NSURLSession delegate の didReceiveChallenge にあることが多く、このコールバックを特定する。
**Q6**: すべての迂回が失敗し、時間が足りない場合、他に退路はあるか?
**A6**: 「経路を復号せず、エンドポイントでのみ平文を取る」という直交する考え方に退く。伝送層で平文を見ることをやめ、App 内部の暗号化関数の入口（引数が平文）を hook するか、レスポンス復号関数の出口を hook する。必要なのは平文の意味であり、必ずしもネットワーク層で取る必要はない。

### トラフィックは取得できたが body 全体が暗号化され、暗号化入口を見つけられない場合
**Q1**: リクエストボディがひとまとまりの暗号文である。パラメータを変更してリプレイするには、まず組み立て+暗号化のコードを見つける必要がある。どこから手を付けるか?
**A1**: 「平文キーワード逆引き」を使う。ある平文パラメータ値（自分が入力した電話番号/ユーザー名など）を知っている場合、実行時に一般的なエンコード/暗号化入口（getBytes、String→byte、Cipher.doFinal、Base64.encode）を hook し、スタック内でこの平文が現れる呼び出しを検索する。呼び出しスタックを辿ればパッキング関数を特定できる。
**Q2**: doFinal を hook したがトリガーが多すぎ、ノイズが大きくてどれが対象か区別できない場合は?
**A2**: フィルタを追加する。データ長、呼び出し前後の URL、スレッド、自分の目印平文を含むかでフィルタする。または逆方向にネットワーク送信点から hook し（OkHttp Interceptor / write(byte[])）、暗号文を取得して、どの doFinal が産出したかを暗号文で逆引きする。
**Q3**: 暗号化関数を特定したが、それが多数の独自変換を呼んでいて、1行ずつ逆算するのが面倒である。どう速くするか?
**A3**: アルゴリズムを逆算せず、「関数レベル RPC」を行う。この関数を直接 hook して能動呼び出しAPIとして公開し、平文を入力すれば暗号文が得られ、暗号文を入力すれば平文が得られる。App を暗号化・復号のブラックボックス oracle として使い、アルゴリズムの詳細を迂回する。
**Q4**: この「暗号化入口を探す」ことが完全に行き詰まり、どうしても特定できない場合は?
**A4**: 「レスポンス側」という直交する入口へ移る。リクエスト暗号化関数が探しにくいとき、レスポンス復号関数の方が往々にして取得しやすい。復号後すぐに JSON 解析され、setText で表示されるからである。JSON 解析入口（fromJson/JSONObject 構築）や UI レンダリング点を hook し、復号関数を逆引きし、対称性に沿ってリクエスト暗号化を推測する。
**Q5**: レスポンス側に替えても駄目で、暗号化が native にあると疑う場合は?
**A5**: so 層へ移る。hook で JNI 境界を記録し（RegisterNatives で native 関数のアドレスを取得）、native へ出入りする byte[] を表示する。so 内部の計算はひとまず無視し、まず平文・暗号文の JNI 境界での形態を確認して、ブラックボックスの境界を native 入口まで縮める。
**Q6**: 脆弱性を素早く検証したいだけで、暗号化を完全に復元したくない場合、近道はあるか?
**A6**: ある。目標が「特定の暗号化リクエストを送ってあるAPIを攻撃する」だけなら、App 自身を暗号化器として使う。hook を通じて App に自分が制御する平文で通常の送信フローを一度通らせ、それが産出する正規の暗号文メッセージを取得し、直接リプレイ/改変に使う。アルゴリズムは完全に復元しない。

### どの暗号化アルゴリズムが使われているかを判断する
**Q1**: 暗号化関数を取得したがコメントがない。AES か DES か中国国家暗号（国密）か自社開発かをどう判断するか?
**A1**: 特徴定数を見る。AES には S-box / Rijndael 定数表、SHA-256 には K 定数、MD5 にはマジックナンバー 0x67452301、SM4 には固定の CK/FK がある。逆コンパイルでこれらの定数表を検索すればアルゴリズムを即座に判定できる。ブロック長 16→AES/SM4、8→DES/3DES。
**Q2**: 標準の Cipher.getInstance を呼んでいるのを見つけた。モードとパディングをどう確認するか?
**A2**: getInstance の文字列引数を直接読む。「AES/CBC/PKCS5Padding」のようなものは一目瞭然である。重点は IV の出所を押さえること。固定か、ランダムで毎回暗号文の先頭に付加されるか、それとも key から派生するか。IV の扱いを誤るとリプレイ/構築がすべて失敗する。
**Q3**: getInstance のアルゴリズム名が実行時に組み立てられる文字列で、静的解析では見えない場合は?
**A3**: 動的解析へ移る。Cipher.getInstance を hook して実際の transformation 文字列を表示し、init を hook して key と IV の byte[] を表示する。実行時はすべて明らかになる。静的解析の文字列結合と格闘しない。
**Q4**: 「標準アルゴリズム」と判定したが、自分で実装して再現してもどうしても合わない。どこが間違っているか?
**A4**: 一般的な落とし穴を調査する。文字エンコーディング（UTF-8 vs GBK）、key は直接使うか先に hash/切り詰めるか、IV は前置か、先に gzip してから暗号化するか、base64 は標準か URL-safe か、末尾に改行があるか。変数を 1 つずつ固定し、App で実測した一組の平文・暗号文を「正解」として突き合わせる。
**Q5**: 再現がどうしても合わず、標準アルゴリズムではなく改変されていると疑う場合は?
**A5**: 「改変の検証」の次元へ移る。多くの App は S-box を改変し、ラウンド数を変え、標準アルゴリズムの前後に XOR/バイト置換を追加する。標準ライブラリを仮定するのをやめ、逆コンパイルに戻ってラウンド関数の定数を 1 つずつ比較するか、再現を諦めて前述の RPC ブラックボックス呼び出しに切り替える。
**Q6**: 国密の SM2/SM4 と判断したが、ツールチェーンに不慣れな場合は?
**A6**: 国密専用ツール/ライブラリへ移る（gmssl / bouncycastle の国密拡張）。SM4 の用法は AES に類比でき、SM2 は非対称で ECC に類比できる（C1C2C3 vs C1C3C2 の暗号文の並び順に注意。これは最も踏みがちな落とし穴である）。

### ハードコードされた鍵の特定
**Q1**: AES と確認できた。次に key を探す必要があり、ハードコードを疑う。どこを探すか?
**A1**: Cipher.init の 2 番目の引数を遡って追う。key の一般的な隠れ場所：文字列定数、strings.xml/リソースファイル、assets、結合されて作られたもの、native getKey() から取得したもの。まず逆コンパイルで SecretKeySpec の構築に対する相互参照を行えば、90% は出所まで追える。
**Q2**: key が複数の文字列の結合 + 変換で作られており、静的解析で追うのが大変な場合は?
**A2**: 手計算せず、動的に SecretKeySpec コンストラクタを hook して最終的な key の byte[] を直接表示する。どう結合し、どう変換していても、鍵オブジェクトを構築する瞬間は必ず完全な平文 key である。
**Q3**: 表示された key が実行ごとに異なる場合は?
**A3**: 動的鍵であり、ハードコードではないことを示す。「鍵の出所」の解析へ移る。デバイスフィンガープリント派生、サーバー配布、または都度鍵の鍵交換の可能性がある。この時、単一のハードコード key を探すのは誤った方向であり、鍵生成/交換ロジックを復元する必要がある（鍵交換の項目を参照）。
**Q4**: key が so 内にあり、native getKey が返し、静的 IDA も難読化されている場合は?
**A4**: 動的解析へ移る。その native 関数の戻り値を hook するか、JNI 境界を hook して返された jbyteArray を取得する。so の難読化がどれほど強力でも、key を上位の Java の Cipher に必ず渡すため、JNI の受け渡し箇所で遮断するのが最も楽である。
**Q5**: この「ハードコード key を探す」ことが完全に通じない場合（ホワイトボックス暗号で、独立した key が根本的に存在しない）は?
**A5**: 重要な方向転換だ。ホワイトボックス(WBC)に遭遇した場合、key はテーブル参照演算に溶け込んでおり、抽出可能な key は存在しない。key 探しをやめ、ホワイトボックス暗号化・復号関数全体をブラックボックス RPC 呼び出しとして使うか、ホワイトボックステーブルを抽出してテーブル参照ロジックを逆算する（コストが高いため RPC を優先）。
**Q6**: key を見つけたが「そのうちの 1 層」に過ぎず、復号してもまだ文字化けする場合は?
**A6**: 多層の暗号化/エンコードのネストであることを示す。「層ごとに玉ねぎを剥く」戦略へ移る。1 層復号するたびに形態を再判定する（また base64 の層か、gzip マジックナンバー 1f8b か、また暗号文の塊か）。1 層ずつ剥き、一発で到達しようと期待しない。

### Frida が attach できない / アンチデバッグに遭う場合
**Q1**: 動的 hook をしたいが、Frida が attach すると対象が即クラッシュする、または検知される場合はどうするか?
**A1**: まず何を検知しているかを特定する。一般的なもの：frida-server のポート/プロセス名の検知、/proc/self/maps 内の frida の検知、TracerPid の検知、ptrace 自己アタッチ。原因に応じて対処する。frida-server の名前とポートを変更する、gadget 注入方式を使う、検知関数の戻り値を hook で無効化する。
**Q2**: 非標準ポートに変えても殺される場合、maps スキャンを疑うか?
**A2**: maps 読み取り/文字列比較を hook し、「frida」/「gum」を含む行をフィルタで除去する。またはポートを使わない注入方式（gadget を apk に組み込んでリパッケージする）でネットワーク特徴スキャンを回避する。
**Q3**: アンチデバッグが非常に頑固で、ずっとクラッシュし、検知点の hook がもぐら叩きのようになる場合は?
**A3**: 「より低層のランタイム」の次元へ移る。改造カーネル/LSPosed/Zygisk 系フレームワークでシステム層から隠すか、エミュレーター/unidbg で対象 so を取り出して管理された環境で実行し、App のアンチデバッグ自己検査環境から完全に離脱する。
**Q4**: root 検知が原因で App が起動せず、hook の機会すらない場合は?
**A4**: 先に root 検知を通過してから hook を考える。File.exists を hook して su/magisk パスを遮断する、一般的な RootBeer 系ライブラリが false を返すよう hook する、Zygisk-denylist/マスク隠蔽を使う。起動すらできないとき、root 隠蔽の優先度は何よりも高い。
**Q5**: いっそデバイスに接続できず/環境が毎日壊れ、時間がすべて環境に費やされる場合は?
**A5**: 戦略的な方向転換として「静的優先」を行う。動的環境のコストが制御不能なら、純粋な静的リバースエンジニアリング + unidbg による環境補完と重要関数の模擬実行に退く。環境の泥沼に無限に投資せず、静的で解決できるものを先に解決する。
**Q6**: 対象が整合性検証を行っており、リパッケージして gadget を注入すると起動エラーになる場合は?
**A6**: 注入方式を変える。リパッケージをやめ、実行時注入（ptrace による gadget 注入 / LSPosed モジュール）に切り替え、apk 本体を変更せずに署名検証と整合性検証を迂回する。検証対象はファイルであり、ファイルを変更しなければよい。

### パケットが取れない場合（HTTP プロトコルではない）
**Q1**: プロキシも透過ゲートウェイも設定済みなのに、業務トラフィックが取得できない。しかし App は確かに通信している。どういうことか?
**A1**: 非 HTTP 伝送を使っていると仮定する。まずデバイス上で接続を見る。netstat/ss で App がどの TCP/UDP 接続を確立し、どのポートに接続したかを見る。443 以外の不審なポート、UDP 接続は、独自プロトコルまたは QUIC を示唆する。
**Q2**: 非 443 の TCP ポートに接続し、継続的な長接続であるのが見えた場合は?
**A2**: 長接続 + 独自ポート → 自社構築の長接続である可能性が高い（IM/プッシュ/RPC）。「バイナリプロトコル復元」へ移る。このストリームの生バイトを取得し、フレーム分割を解析する。同時に静的解析で Socket/Netty/mars/自社開発ネットワークライブラリを検索してコーデックを特定する。
**Q3**: UDP で、QUIC または自社開発 UDP プロトコルを疑う場合は?
**A3**: QUIC 自体が暗号化されており、取得しても暗号文である。リンク層で無理に抗わない。エンドポイント hook へ移る。App のネットワーク送信関数（sendto / ネットワークライブラリの write）を hook し、暗号化前/復号後に平文を取る。QUIC の暗号化は自分にとって透明になる。
**Q4**: 静的解析でネットワークライブラリが自社開発であり、標準の send が見つからない場合は?
**A4**: 「データ出所追跡」法へ移る。知っている平文フィールド（ユーザー名）から出発してエンコード入口を hook し、呼び出しスタックを下へ辿って最終的なバイト書き出し点へ至る。途中が何という名前でも、終点は必ず何らかの write(byte[]) である。
**Q5**: これが完全に解けず、確立した接続すら特定できない場合（多プロセス/native 直結の可能性）は?
**A5**: システムコール層へ移る。strace/ltrace または eBPF で syscall 層の connect/sendto/write を取得し、アプリケーション層のすべてのラッピングを迂回する。システムコールは最後に観測できる境界であり、App は逃れられない。
**Q6**: バイナリストリームを取得したが完全に構造が無い場合、どう始めるか?
**A6**: 差分解析を行う。同じ操作を複数回送ってバイトの差異を比較する（どのバイトが変わり、どのバイトが変わらないか）。変わるのは往々にしてシーケンス番号/タイムスタンプ/乱数で、変わらないのはプロトコルヘッダー/マジックナンバー/コマンド語である。挙動の差分でフィールドの意味を逆算する。

### .proto ファイル無しの protobuf 復元
**Q1**: 取得した body が protobuf バイナリだが、.proto 定義がない。フィールドをどう読み解くか?
**A1**: まず protobuf の自己記述性を利用して強引に解く。protoc --decode_raw またはオンラインの raw decoder で、field number + wire type + value の骨格を解ける。この段階では .proto は不要で、まず構造の輪郭を得る。
**Q2**: raw decode で番号と型しか得られず、フィールドの意味が分からない場合は?
**A2**: 既知の意味と突き合わせる。リクエストに電話番号/金額があると分かっていれば、raw 結果の中で値によって対応づける（電話番号は string、金額は int）。各 field number に名前を付け、意味づけされた .proto を徐々に再構築する。
**Q3**: 1 つずつ推測するのではなく、一括で信頼性高く復元したい場合は?
**A3**: App から既製の descriptor を抽出する。多くの App はパッケージング時に protobuf の FileDescriptor（リフレクション登録用）を含んでおり、逆コンパイルで生成された protobuf クラスまたは .proto の descriptor バイトを検索すれば、完全な定義を直接復元できる。
**Q4**: フィールドに message がネストし、さらに暗号化された bytes が 1 層ネストしている場合は?
**A4**: protobuf 内の bytes フィールドは、また暗号文の塊かネストした message である可能性が高い。「層ごとの形態判定」へ移る。各 bytes フィールドを個別に判定する（ネストした pb か、暗号文か、生バイナリか）。ネストした pb なら decode_raw を再帰的に続ける。
**Q5**: decode_raw が直接失敗し、正当な protobuf ではないと報告される場合は?
**A5**: 仮説の修正へ移る。外側にもう 1 層（暗号化/圧縮/独自ヘッダー）がある可能性がある。先にヘッダーを剥がす/復号する/gunzip してから decode する。またはそもそも protobuf ではなく thrift/flatbuffers/独自 TLV であり、形態判定に戻って定性し直す。
**Q6**: フィールドを変更してリプレイしたいが、protobuf を手作業で構築するのがつらい場合は?
**A6**: 復元した .proto からコーデックコードを生成するか、App を直接変更する。シリアライズ前の message オブジェクトを hook してフィールドを変更し、App 自身にシリアライズ+暗号化+署名をさせる。自分は意味だけを変更し、バイトには触れない。

### リクエスト署名 sign 検証の迂回 / 再現
**Q1**: リクエストパラメータを変更してリプレイしたところ、サーバーが署名エラーを返す。sign フィールドがある。署名をどう再現するか?
**A1**: まず署名アルゴリズムを復元する。sign は通常、パラメータのソート結合 + ソルト/key + hash（MD5/HMAC/SM3）である。sign を計算する関数を hook し、その入力文字列と出力を表示すれば、「結合規則 + ソルト」という 2 つの鍵が分かる。
**Q2**: sign 関数を見つけ、入力文字列の規則は解明したが、ソルトはどこから来るか?
**A2**: ソルト(salt/appsecret)は key と同様に定数/native/リソースに隠れていることが多く、方法は鍵の特定と同じである。最終的に hash へ渡される完全な文字列を hook するのが最も速い。ソルトは必ずその文字列内に平文で現れる。
**Q3**: パラメータのソート規則が複雑で（署名に参加しないフィールドがある、ネストがある）、再現がどうしても合わない場合は?
**A3**: 精密に突き合わせる。App が実際に計算する際の原文文字列を表示し、自分で組み立てたものと 1 文字ずつ diff する。どのフィールドが計算に入っていないか、順序がどこで違うか、URL エンコーディングの差異があるかがすぐ分かる。App の原文文字列を唯一の真実とする。
**Q4**: 再現したくない。sign を計算せずに済ませられないか?
**A4**: 「刀を借りる」考え方へ移る。sign 関数を hook して署名 oracle として公開し、パラメータを渡せば sign を返す。または App に署名させる。hook で自分のパラメータを通常のリクエストフローへ注入し、App 自身が署名して送信する。アルゴリズム全体の再現を省ける。
**Q5**: この道が失敗する。すなわち sign がサーバー側で body の完全な暗号化も検証し、パラメータだけを変更してもどうやっても通らない場合は?
**A5**: 署名が暗号化 body 全体をカバーしていることを示す。「暗号化前に手を付ける」方向へ移る。暗号文/署名層で抗わず、平文層へ戻る。App が暗号化+署名する前に hook で平文パラメータオブジェクトを変更すれば、後続の暗号化と署名はすべて App が自動で行い、自然に正規になる。これは暗号化+署名の二重保護 API を攻める定番手法である。
**Q6**: さらに未認可/権限外アクセスのテストをしたいが、各リクエストに正規署名が必要で遅すぎる場合は?
**A6**: App を「署名プロキシサービス」にする。常駐 hook + 1 つのローカル HTTP API を用意し、自分の fuzz/権限外アクセススクリプトが平文を送り、App 側が自動で暗号化署名してから転送する。これで通常の Web テストツールでこの暗号化APIを攻撃できる。

### タイムスタンプ + nonce のリプレイ対策
**Q1**: 暗号化と署名を再現し、単一リクエストは通るが、少し時間が経ってから再送すると無効になる。どういうことか?
**A1**: 高確率で ts（タイムスタンプ）のウィンドウ超過 + nonce のリプレイ対策である。まず確認する。リクエストに timestamp、ランダムな nonce フィールドがあり、それらが署名に参加しているか。サーバーは ts が数分のウィンドウ内であること、nonce が再利用されないことを検証する。
**Q2**: ts があると確認できた。リプレイを継続的に有効にするには?
**A2**: 古いパケットをリプレイせず、「リアルタイム再署名」を行う。各リクエスト送信前に現在時刻で ts を生成し、新しい nonce を生成し、署名を再計算する。つまり静的リプレイを動的構築へ格上げする。
**Q3**: nonce にサーバー配布のチャレンジ値(challenge)があり、クライアントのランダムではない場合は?
**A3**: 「先に challenge を取得してから応答する」2 段階フローへ移る。まずリクエストしてサーバーの nonce/challenge を取得し、それで応答を構築する。リバースエンジニアリングで復元すべきは「challenge→response」の計算関係であり、固定値を探すのではない。
**Q4**: タイムスタンプにクライアントの時計同期/サーバー時刻オフセット補正も含まれる場合は?
**A4**: 時刻を取得する箇所を hook し、ローカル時刻を使うのか、サーバー配布の基準時刻を使うのかを見る。サーバー基準なら、まず時刻同期APIを 1 回取得して offset を得て、リクエスト構築時に「サーバー時刻」を使う。ローカル時刻を使わない。
**Q5**: すべて合っているのに失敗し、リプレイ対策メカニズムを根本的に迂回できない場合は?
**A5**: 「リプレイせず、生体を通す」という直交する次元へ移る。オフライン構築をやめ、App を直接リアルタイムプロキシにする（hook で平文を注入する）。各リクエストを App が現場で生成する正規リクエストにし、ts/nonce/署名をすべて App がリアルタイムで生成させる。リプレイ対策は自分に無効になる。
**Q6**: API を一括で実行したいが、nonce に頻度制限/一回限りがある場合は?
**A6**: これが迂回可能な点ではなく防護であると評価する場合、テスト戦略を調整する。並行性を下げる、nonce を直列で取得する、またはロジック脆弱性に集中する（少数の正規リクエストで権限外アクセス/パラメータ改ざんを検証する）。高頻度 fuzz はしない。「これは設計上の制限である」と認識して、ここで空費しない。

### パッカー適用 App のアンパック
**Q1**: 逆コンパイルして開くとクラスがほとんど無い、またはクラス名がすべてパッカーの loader である。パッキングされている。どうアンパックするか?
**A1**: まずパッカーの種別を識別する（パッケージ名/特徴 so を見る。一般的な数社の商用パッカーにはフィンガープリントがある）。アンパックは世代ごとに行う。第 1 世代パッカーは dex 全体がメモリにあり、メモリダンプ系ツールで実行時に dex を引き出す。高世代の抽出型パッカー（メソッド単位の抽出）は、能動呼び出し/dex 補完を行うアンパック機が必要である。
**Q2**: dump した dex のメソッド本体が空の場合（CodeItem が抽出されている）は?
**A2**: これは関数抽出型パッカーである。「能動呼び出しアンパック」へ移る。FART/北斗 系フレームワークで全メソッドを走査して復号・復元をトリガーし、メソッド実行前に CodeItem を dump して再充填し、完全な dex を再構成する。
**Q3**: いくつかの重要な暗号化関数だけに関心があり、App 全体をアンパックしたくない場合は?
**A3**: 精密攻撃を行う。対象クラス/メソッドを特定し、それが呼び出されてコードがメモリへ復元された瞬間に hook で単点 dump する。あるいはアンパックせず、その入出力を直接 hook して平文を取る。アンパックは手段であって目的ではない。
**Q4**: アンパック後の dex が逆コンパイルでやはりエラーになる/構造が破損している場合は?
**A4**: dex ヘッダーと参照を修復する（アンパック機付属の修復または専用ツールを使う）、または別の逆コンパイラに変えてクロス検証する。破損は dump のタイミングが悪いことが多く、より遅い dump 点に変えてやり直す。
**Q5**: 重要ロジックが dex 内にまったく無く、すべて so に移されている場合は?
**A5**: so 層へ移る。パッカーが中核ロジックを native 化しており、dex のアンパックは無駄である。so のリバースエンジニアリング（IDA/Ghidra）か、JNI 境界の hook / unidbg 模擬実行に変える。戦場は Java 層から native 層へ移る。
**Q6**: アンパック環境がいつも崩れる場合（パッカーに強力なアンチデバッグがある）は?
**A6**: 「環境隔離」の次元へ移る。カスタム ROM / 特定のアンドロイドバージョン / エミュレーターでパッカーの環境自己検査を回避するか、クラウド実機を使う。パッカーのアンチデバッグは特定の検知面に紐づいていることが多く、環境を変える方が検知点に無理に抗うより速い。

### so 層 native 暗号化のリバースエンジニアリング
**Q1**: 暗号化がすべて libxxx.so 内にあり、IDA で開くと大量のアセンブリである。どこから切り込むか?
**A1**: まず入口を特定する。JNI_OnLoad 内の RegisterNatives を見て、native メソッドと so 内アドレスの対応を取得し、対象 native 関数へ直接ジャンプする。so 全体を当てもなく歩き回らない。
**Q2**: 関数は見つかったが長すぎて、アセンブリを 1 命令ずつ読みたくない場合は?
**A2**: 先に動的観察してから、精読するか決める。この native 関数の入出力（平文 byte[] と暗号文）を hook し、入力と出力の関係が安定していれば、そのままブラックボックス RPC として使い、so 内部を読む必要はない。
**Q3**: アルゴリズムの復元が必須で（オフライン一括計算が必要など）、so がさらに OLLVM で難読化されている場合（制御フロー平坦化）は?
**A3**: 逆難読化へ移る。シンボリック実行/平坦化解除スクリプト（IDA/Miasm/Triton ベース）で元の制御フローを復元するか、unicorn/unidbg でこのコードを直接模擬実行し、ブラックボックスとして入力を与えて出力を取る。静的に難読化を読む苦痛を迂回する。
**Q4**: so 内にさらに native アンチデバッグがある場合（ptrace 自己アタッチ、検知）は?
**A4**: native アンチデバッグを hook/patch で潰す。ptrace を hook して成功を返させ、検知分岐を patch する。または unidbg で純粋な模擬環境で実行する。そこには実際の ptrace 環境が無いため、アンチデバッグロジックは自然に無効化される。
**Q5**: unidbg の環境補完が途中まで進み、大量の JNI/システムコールが欠けて補完できない場合は?
**A5**: トレードオフの方向転換を行う。環境補完のコストが利益を上回るなら、「実機 hook のブラックボックス呼び出し」に退く。App から独立した再現を追求せず、「App の存在が必須」の RPC 方式を受け入れる。unidbg は関数が純粋で依存が少ない場面に向いており、依存が爆発したら早めに損切りする。
**Q6**: so がパッキングされている場合（so も保護/暗号化セクション）は?
**A6**: so のアンパックへ移る。多くの so 保護は実行時にコードセクションを復号する方式である。so ロード後、関数実行時にメモリから復号済み so を dump して静的解析するか、復号済みメモリ内で直接 hook する。

### ホワイトボックス暗号(WBC)の識別と対処
**Q1**: 暗号化関数を探すと独立した key がなく、巨大なテーブル参照とビット演算の山がある。ホワイトボックスを疑う。どう確認するか?
**A1**: ホワイトボックスの特徴：超大な静的テーブル（数十 KB〜MB のルックアップテーブル）、密集したバイト置換+XOR、識別可能な独立 key 変数が無い、アルゴリズム構造は AES に似ているがテーブル内に押し込まれている。「大テーブル + テーブル参照パイプライン」が見えればほぼホワイトボックスと判定できる。
**Q2**: ホワイトボックスと確認した後、key を抽出したいか?
**A2**: 通常は抽出しない。ホワイトボックスの設計目的は key を平文で存在させないことであり、抽出には DFA/BGE などの専門的なホワイトボックス攻撃が必要で、コストが極めて高い。レッドチーム実戦の優先順位：まずホワイトボックス関数をブラックボックス RPC として使い、「暗号化・復号できる」ことを満たせばよい。
**Q3**: しかしオフラインで、デバイスから離れて一括で暗号化・復号したい場合は?
**A3**: ホワイトボックス実装全体を抽出して持ち去る。テーブル参照データ + 演算ロジックを完全に dump し、unidbg/unicorn で模擬実行するか独立プログラムに移植する。持ち去るのは「テーブル付きの暗号化マシン」であり、key ではない。
**Q4**: ホワイトボックスが so 内にあり、アンチデバッグ/整合性検証と固く結びつき、触れると即クラッシュする場合は?
**A4**: 「その場で利用する」戦略へ移る。持ち去らず、実機上でホワイトボックス関数をローカルサービスとして公開し（hook + ローカルAPI）、ネイティブ環境内で正常に動かしたまま、自分はリモートから呼び出す。移設が引き起こすすべての環境依存を迂回する。
**Q5**: 本当にホワイトボックスを破って key を取りたい場合（大量の認証情報を偽造する必要があるなど）、価値はあるか?
**A5**: ROI を判断する。ホワイトボックスの差分故障解析は確かに key を出せるが、専門的な暗号解析の投入が必要である。対象の価値が極めて高く、かつオフラインでの大規模偽造が必須でない限り、この道はレッドチームの時間軸では通常割に合わない。RPC/ブラックボックス方式に戻る。
**Q6**: ホワイトボックス + 動的鍵交換が重なっている場合（テーブルも配布される）は?
**A6**: 「交換フローの復元」の次元へ移る。テーブル/パラメータがサーバー配布であることは、鍵/パラメータ配布プロトコルが 1 層あることを示す。まず配布プロトコルを復元して現在のセッションのテーブルを取得し、それからテーブルを使う。戦場は「テーブルを破る」ことから「配布を取得する」ことへ変わる。

### 鍵交換 / 都度鍵(DH/ECDH/配布)
**Q1**: hook した key が毎回変わり、動的鍵と確認できた。どう復元するか?
**A1**: まず「交換」か「配布」かを切り分ける。ハンドシェイクリクエストがあるかを見る。クライアントが公開鍵/乱数を送り、サーバーが公開鍵/暗号化されたセッション鍵を返す→交換（DH/ECDH/RSA ラッピング）。あるAPIが暗号文 key を直接配布する→サーバー配布。ハンドシェイクメッセージを取得して定性する。
**Q2**: ECDH 交換で、セッション鍵を復元したい場合は?
**A2**: クライアントに完全な制御権があるなら、DH を破る必要はない。交換完了後に生成されるセッション key（KDF 出力/SecretKeySpec 構築の箇所）を hook し、今回のセッションの対称 key を直接取得して、後続のセッショントラフィック全体の復号に使う。
**Q3**: 以前に取得したトラフィックをオフラインで復号したい場合（事後のフォレンジック方式）は?
**A3**: 当時のセッション鍵または秘密鍵が必要である。クライアントの秘密鍵が固定なら（RSA ラッピングの場面）、秘密鍵を抽出すれば過去のトラフィックを解ける。ECDH の一時鍵なら、当時の中間値が無ければ解けず、リアルタイム hook が必須である。はっきり判断してから「事後に解けるか」を決める。
**Q4**: サーバー配布の key 自体がさらに上位の鍵で暗号化されている場合（鍵チェーン）は?
**A4**: 鍵チェーンを上へ剥いていく。「配布 key の暗号文」を解く上位 key（ハードコードされたルート鍵またはデバイス派生であることが多い）を探し、セッション key を復号する。層が入れ子のときは、各層で「復号関数の出口を hook」して次の層の平文を取るのが最も楽である。
**Q5**: 交換にサーバー乱数が混ざっており、中間者として改ざんしたいが通らない場合は?
**A5**: 方向転換：目標が MITM ではなく復号/構築なら、中間者にならない。自分はクライアントにおいて「正規の一端」であり、クライアントで hook したセッション鍵を直接使って操作すればよい。交換に介入する必要はない。MITM は「自分が通信当事者ではない」問題を解決するときにのみ使う手段である。
**Q6**: 交換全体が native 内にあり、しかもホワイトボックスで、リアルタイム hook でもきれいな対称 key が取れない場合は?
**A6**: 最終使用点へ退く。交換がどれほど複雑でも、業務データは必ず何らかの key で一度 Cipher.doFinal/native 暗号化関数を通る。「実際に業務データを暗号化・復号するその 1 回の呼び出し」でパラメータを hook するのが、鍵交換のすべての複雑さの最終収束点である。

### ハイブリッドアプリ / ミニプログラム / H5 のパケットキャプチャ
**Q1**: 対象がミニプログラムまたは App 内の H5 ページである。通常のパケットキャプチャで見えるのは WebView トラフィックで、しかも暗号化がある。どうするか?
**A1**: 層を切り分ける。H5/ミニプログラムの暗号化ロジックは JS 内にあり、native にはない。まずパケットキャプチャでリクエスト形態を見て、それから JS ソースコードを取得する。ミニプログラムには wxapkg パッケージがあり、展開してソースコードを取得できる。H5 はリモートの js を直接見る。戦場はバイナリのリバースエンジニアリングから JS のリバースエンジニアリングへ変わる。
**Q2**: ミニプログラムパッケージを展開した JS が圧縮/難読化されている場合は?
**A2**: JS の逆難読化（AST 復元、変数リネーム）+ フォーマットを行い、encrypt/sign/CryptoJS キーワードを検索する。JS のリバースエンジニアリングは native よりはるかに扱いやすく、ブラウザ/node で直接デバッグ実行して検証できる。
**Q3**: 暗号化関数が JS 内にあるが、ミニプログラムのランタイム環境(wx.xxx)に依存しており、切り出して単独で動かせない場合は?
**A3**: 環境を補完するか、その場で呼び出す。wx などのグローバルオブジェクトの mock を揃えて node で実行するか、ミニプログラム開発者ツール/デバッグ環境で直接ブレークポイント hook し、ネイティブ環境で計算させて自分は値を取る。native の RPC の考え方に類比できる。
**Q4**: WebView 内の H5 で、JS がさらに native の JSBridge を呼んで暗号化している場合は?
**A4**: JSBridge 境界へ移る。WebView の addJavascriptInterface / JS が native を呼ぶブリッジメソッドを hook し、このブリッジ層で平文・暗号文を取る。JSBridge は H5 と native の受け渡し点であり、暗号化はそれを跨ぐときに起こることが多い。
**Q5**: WebView トラフィックがまったく取得できない場合（独自 WebView/カーネル）は?
**A5**: JS 層の hook へ移る。JS エンジン内の XMLHttpRequest/fetch/リクエスト送信関数を直接 hook するか、JS を注入してリクエスト前の平文を表示する。リンク層を迂回し、JS ランタイムでデータを取る。
**Q6**: 暗号化 key が JS 内にあるが、それもサーバー配布/動的である場合は?
**A6**: native と同じ考え方で使用点に収束する。JS の暗号化呼び出し（CryptoJS.AES.encrypt など）を hook して key と平文を表示する。key がどう来ようと、呼び出しの瞬間は明らかである。JS ではブレークポイントにコンパイルすら不要で、より便利である。

### デバイスフィンガープリント / リスク管理遮断
**Q1**: 暗号化署名をすべて正しく再現したのに、リクエストがリスク管理に遮られる（リスク管理コード/スライダーが返る）場合はどうするか?
**A1**: まず遮断原因を定性する。デバイスフィンガープリントフィールドの欠落、環境の識別（root/frida/エミュレーター）、挙動異常（頻度/正常な前置きリクエストなし）。遮断されたリクエストに、正常なリクエストが持つ header/フィールドのどれが欠けているかを見る。リスク管理は往々にして大量の環境収集フィールドに依存する。
**Q2**: リクエストヘッダーに device-id / リスク管理 token フィールドがあり、暗号化されたデバイスフィンガープリントであることが分かった場合は?
**A2**: 「フィンガープリント生成の復元」へ移る。このフィールドを生成する関数を hook する。それは IMEI/mac/センサー/システムプロパティなどを収集してフィンガープリントを組み立て、暗号化している。必要なのは「正常に見える」フィンガープリントを生成させることであり、App が今生成したものを直接使えばよい（hook で値を取る）。自分で作らない。
**Q3**: 環境自体がリスク判定され（hook/root を検知）、フィンガープリントにリスクマークが付く場合は?
**A3**: 環境隠蔽の次元へ戻る。まず root/frida をきれいに隠し（Zygisk 隠蔽、特徴除去）、App に「きれいな環境」を収集させてからフィンガープリントを生成させる。フィンガープリントは環境のスナップショットであり、環境が汚れればフィンガープリントも汚れる。順序は先に環境をきれいにし、後でフィンガープリントを取る。
**Q4**: リスク管理が実際の人の行動シーケンス（先に閲覧してから注文）を要求し、純粋なAPI攻撃ではリスク管理をトリガーする場合は?
**A4**: 「行動チェーンの補完」へ移る。対象APIだけを送らず、正常な業務の前置きリクエスト（初期化、イベント計測、一覧）を補い、合理的なタイミングを模擬する。リスク管理が見るのは行動グラフであり、単点のリクエストではない。
**Q5**: どうしてもリスク管理を通過できず、このプロトコル再現ルートを続ける価値はあるか?
**A5**: 直交する方向転換の判断を行う。リスク管理が難物なら、「生体 App プロキシ」への変更を評価する。実機上の正常な App にリクエストを送らせる（hook で payload を注入する）。自分の攻撃は正規環境と正規挙動の中に隠れ、リスク管理はほぼ識別できない。これは強力なリスク管理に対抗する最も安定した汎用の退路である。
**Q6**: 目標は実は水増しではなく脆弱性探しであり、リスク管理は邪魔なだけの場合は?
**A6**: 目標を正しく置く。リスク管理は主に一括処理/自動化を防ぐもので、ロジック脆弱性の検証には少数の正規リクエストしか必要ない。「App プロキシ + 手動/低頻度」方式で、精緻に構築したいくつかのリクエストを送って権限外アクセス/パラメータ脆弱性を検証し、リスク管理をトリガーする高頻度挙動を完全に避ける。

### リクエストは通るがサーバーがパラメータを二次検証する場合
**Q1**: 金額/ID を変更してリプレイし、署名も暗号化も正規なのに、サーバーがエラーを返すか反映しない。なぜか?
**A1**: サーバーが業務側の二次検証を行っている（金額が商品と一致しない、ID が現在のユーザーに属さない、状態機械が許可しない）。暗号化の再現を疑わない。これはロジック層である。まずエラーコードの意味を見て、「技術的な拒否（署名/形式）」と「業務的な拒否（ロジック検証）」を区別する。
**Q2**: 暗号化の再現に問題がなく、問題が業務ロジックにあることをどう確認するか?
**A2**: 変数を制御する。まず何も変更せずそのままリプレイする。成功すれば暗号化経路は OK であり、失敗の原因は自分が変更したパラメータがトリガーした業務検証にある。この 1 手で「暗号化を間違えた」と「サーバーがこれの変更を許さない」を切り分ける。
**Q3**: 権限外アクセス系の業務検証と確認できた。変更可能な点をどう探すか?
**A3**: Web ロジック脆弱性の考え方へ移る。サーバーが帰属を検証していないパラメータを列挙し（他人の order_id を変更する、数量を変更する、状態を変更する）、水平/垂直の権限外アクセステストを行う。暗号化は外殻に過ぎず、中身は標準的な Web の権限外アクセス/ロジック脆弱性の戦場である。
**Q4**: パラメータを 1 つ変更するたびに再暗号化・再署名が必要で、テスト効率が極めて低い場合は?
**A4**: 「暗号化プロキシ」を使う。App をローカルの暗号化・復号/署名プロキシサービスにし、Burp/スクリプトが平文を送り、プロキシ層が自動で暗号化署名して転送し、レスポンスを平文に復号して返す。これで成熟した Web テストツールで暗号化APIをスムーズに fuzz できる。
**Q5**: 二次検証に、サーバーが計算したハッシュ/token のフィールドがあり、主パラメータを変更すると一致しなくなる場合は?
**A5**: この関連フィールドの出所を追う。クライアントが計算するのか（なら一緒に再計算する）、それとも 1 つ前のAPIが返すのか（なら先に前段階を進めて一致する値を取る）。「複数段階の業務フロー」の復元へ移り、依存のあるフィールドを呼び出しチェーンの順序で揃える。
**Q6**: 色々やった結果、サーバーが確かに検証を厳密に行い、単一APIを攻略できない場合は?
**A6**: 攻撃面を移す。別のAPIに変える。同じ App には数十から百以上のAPIがあり、防護強度は不均一で、旧API/内部API/新規公開APIに弱点があることが多い。復元済みの暗号化能力でAPIを広くスキャンし、1 つの硬い点に固執しない。

### 難読化が激しい場合(OLLVM / 制御フロー平坦化) 読み解けない
**Q1**: 逆コンパイルまたは IDA で制御フロー平坦化、偽分岐が大量に出て、人間には到底読み進められない場合はどうするか?
**A1**: まず無理に読まない。「アルゴリズムを読み解く」必要があるかを評価する。入出力だけが必要なら、直接動的 hook/模擬実行でブラックボックスとして値を取る。難読化がどれほど強力でもブラックボックスの挙動には影響しない。ソースコードを読むのはコストが最も高い道であり、読まずに済むなら読まない。
**Q2**: ロジックの復元が確かに必須の場合（オフライン一括/App を持ち込めない）、平坦化にどう対処するか?
**A2**: 逆難読化ツールチェーンを使う。シンボリック実行（Triton/Miasm/angr）で実際の制御フローを復元し、ディスパッチャ（dispatcher）を除去するか、IDA プラグインで平坦化を解除する。難読化後の CFG を可読な元のロジックへ復元してから解析する。
**Q3**: 文字列も暗号化されており（動的復号）、相互参照で道標が見つからない場合は?
**A3**: 動的な文字列取得へ移る。文字列復号関数を hook して復号後の全文字列を一括 dump するか、実行時にメモリ内の復号済み文字列テーブルを dump する。平文文字列があれば、相互参照の道標が戻ってくる。
**Q4**: OLLVM にさらに仮想化（VMP 系）保護が重なっている場合は?
**A4**: 仮想化は最も硬く、VM インタプリタの逆算コストは極めて高い。戦略的な方向転換を行う。断固としてブラックボックスで進む。unidbg/実機 hook で仮想化された関数を正常に実行させ、自分は入出力だけを取る。VM の逆算は、やむを得ない場合（完全復元が必須かつ実行不能）にのみ行う。
**Q5**: angr/シンボリック実行が経路爆発して解けない場合は?
**A5**: 範囲を縮小し、実行式の模擬に切り替える。重要で小さい関数にだけシンボリック実行を行い、広範囲は unicorn の具体値模擬（concrete execution）で実入力を使って 1 回実行して結果を得る。経路爆発を避ける。具体+シンボルの混合は純粋なシンボリックより実用的である。
**Q6**: 時間予算が尽きかけているのに、まだ読み解けていない場合は?
**A6**: 早めに損切りしてブラックボックスへ移る。「読み解く」道は割に合わないと認め、hook ブラックボックス RPC に戻って実戦ニーズを満たす。レッドチームの目標は攻撃チェーンを繋ぐことであり、リバースエンジニアリングの論文を発表することではない。使えればよい。

### 平文を hook できるが特定のタイミングのみ / 不安定
**Q1**: hook は効いている。たまに平文を表示できるが、大半は取れないか漏れる。どういうことか?
**A1**: トリガー条件を調査する。多プロセスか（間違ったプロセスを hook した）、複数のオーバーロード関数のうち 1 つしか hook していないか、タイミングが早すぎて関数がまだロードされていないか。まず hook したのが、実際に業務を実行するプロセスとメソッドかを確認する。
**Q2**: 多プロセスと確認し、業務が子プロセス/native プロセスにある場合は?
**A2**: 多プロセス注入へ移る。hook フレームワークに spawn 時に全プロセスまたは指定対象プロセスへ注入させ、プロセス名でフィルタする。App はネットワーク/暗号化を独立プロセスに置くことが多く、メインプロセスを hook しても当然取れない。
**Q3**: 関数に複数のオーバーロードがあり / ジェネリクス消去で hook が不完全な場合は?
**A3**: すべてのオーバーロードを列挙して hook するか、より低層の収束点（全オーバーロードが最終的に呼ぶ基礎関数）を hook する。呼び出しチェーンの下流で唯一必ず通る道を探す方が、上流で複数の分岐を追うより安定する。
**Q4**: タイミングの問題で、関数が hook スクリプトのロード前に実行される場合は?
**A4**: attach モードではなく spawn モード（起動を停止し、注入完了後に続行）に切り替え、hook が対象コードより先に実行されることを保証する。attach は一歩遅れて早期呼び出しを逃す。
**Q5**: hook 自体が App の挙動を変える/クラッシュさせる場合（観測者効果）は?
**A5**: 侵入を減らす。hook 内で重い処理をしない（大量ログ/ブロッキングを避ける）、読み取りのみで変更しない。またはより軽い観測方式（メモリブレークポイント/サンプリング）に変える。App が hook の副作用を検知するなら、アンチデバッグ隠蔽の次元へ戻る。
**Q6**: 長く試しても hook がどうしても不安定な場合、他にデータ取得の方法はあるか?
**A6**: 直交する観測手段へ移る。メモリスキャン（暗号文送信前にメモリを走査して平文の残存を探す）、core dump 後のオフライン解析、eBPF による syscall 層の観測に切り替える。hook は唯一の実行時観測手段ではない。観測面を変える。

### リクエストとレスポンスがともに暗号化され、両方を復元する必要がある場合
**Q1**: リクエスト body も暗号化され、レスポンス body も暗号化される。両方を復元する必要がある。どちらを先にやるか?
**A1**: 先にレスポンス復号を行う。復号後のデータはすぐに JSON 解析/表示されるため、より特定しやすい（UI や JSON 入口を hook して逆引きする）。しかもリクエスト暗号化とレスポンス復号は同じ key/アルゴリズムを使うことが多く、片方を解けばもう片方はほぼただである。
**Q2**: レスポンスを解いたらリクエストとアルゴリズムが異なることが分かった場合（非対称）は?
**A2**: 別々に処理する。多くの App はリクエストに 1 つの方式（非対称の key ラッピングを含む可能性）、レスポンスに対称方式を使う。両方向の Cipher 呼び出しを別々に hook し、それぞれのアルゴリズム/key/IV を記録する。両側が必ず対称だと仮定しない。
**Q3**: 完全な中間層の復元をしたい場合（レスポンスを読み、リクエストを変更できる）は?
**A3**: 双方向の暗号化・復号プロキシを構築する。リクエスト方向は平文→暗号化→送信、レスポンス方向は暗号文→復号→自分へ、という流れである。App の hook 能力または再現したアルゴリズムでこのプロキシを実装すれば、「平文視点」の対象 App が得られる。
**Q4**: レスポンス復号が詰まる場合（レスポンスは先に復号してから署名検証し、検証が通らなければ自身が破棄する）は?
**A4**: より下流の hook へ移る。署名検証を通過した後、実際に業務データを解析する箇所で hook する。または署名検証関数を hook して常に真にし、フローを復号後の平文まで進める。データフローに沿って「すでに平文である」瞬間を探す。
**Q5**: 両方を復元したが、脆弱性を素早く検証したいだけで、完全なプロキシを構築したくない場合は?
**A5**: 必要に応じて簡略化する。単一の脆弱性を検証するなら、レスポンスを手動で 1 回復号して結果を見て、リクエストを手動で 1 回暗号化して送ればよい。エンジニアリング化は不要である。エンジニアリング化したプロキシは大量テスト用であり、小規模な検証に過度に投資しない。
**Q6**: レスポンス内にさらに暗号化フィールドがネストしている場合（全体を復号した後、あるフィールドがまた暗号文）は?
**A6**: 層ごとに剥く。全体を復号して JSON を得た後、不審なフィールドを個別に形態判定してから復号する。多層暗号化は機微フィールド（パスワード/支払い）に多く、外層のセッション暗号化 + 内層のフィールド暗号化を層ごとに処理する。

### 判断:純粋な静的リバースエンジニアリング vs 動的 hook vs RPC/unidbg
**Q1**: 暗号化復元タスクに直面し、3 つの道（静的アルゴリズム逆算 / 動的 hook による値取得 / unidbg 模擬）のどれを選ぶべきか?
**A1**: 「目標 + 可読性 + オフライン要否」の 3 次元で判断する。入出力だけでよく App を持ち込めるなら、動的 hook RPC（最速）。オフライン一括が必須で関数が純粋なら、unidbg。アルゴリズムを完全に理解する必要があるなら（レポート作成/実行不能）、静的逆算。既定では hook から始めるのがコスト最低である。
**Q2**: 最初にどの道を行くかをどう素早く判断し、選び間違えて時間を無駄にしないか?
**A2**: まず 10 分かけて偵察する。逆コンパイルで重要関数の可読性（明快な Java? 難読化? native?）、アンチデバッグの有無（hook できるか）、要件（デバイスから離れるか）を見る。偵察結果を 3 つの道の 1 つへ直接対応づける。盲目的に選ばない。
**Q3**: hook を選んだが、要件は実はオフラインの大規模一括であり、hook は App を持ち込むため遅すぎる場合は?
**A3**: 早めに unidbg へ切り替える。重要 so 関数を unidbg 模擬に取り込み、最小環境を補完して、デバイスから離れた高速な暗号化・復号を得る。判定基準は「App から離れる必要があり、かつ高スループットか」である。満たすなら環境補完のコストを払う価値がある。
**Q4**: unidbg を選んだが、環境依存が爆発して補完できない場合は?
**A4**: hook RPC に戻す。この関数は依存が重すぎて模擬に向かないと認め、実機 hook のブラックボックス呼び出しに退き、「App を持ち込む」代償を受け入れる。3 つの道は行き来できなければならず、この道のコストが制御不能になったら切り替える。サンクコストに縛られない。
**Q5**: 3 つの道をすべて試したがどれも苦しい場合、方向が間違っているのか?
**A5**: 攻撃目標自体を振り返る。もしかするとこの暗号化を復元する必要がそもそもない。目標を見直す。あるAPIを攻撃したいだけなら、前述の「App を暗号化器/プロキシにする」方法で数分で片付く可能性があり、アルゴリズム復元より洗練されている。まず「自分はいったい何が欲しいのか」を問い、リバースエンジニアリングのためのリバースエンジニアリングを避ける。
**Q6**: チーム協働で、復元成果を再利用可能にするには?
**A6**: API化された暗号化・復号能力（ローカルサービス/ライブラリ）を成果として出す。使い捨てスクリプトではない。どの道を行っても、最終的に「平文を入れれば暗号文が出る」安定したAPIにラップし、後続の全攻撃（fuzz/権限外アクセス/リプレイ）で再利用する。

### プロキシ逃逸（一部のトラフィックがシステムプロキシを通らない）
**Q1**: システムプロキシを設定し、ログインは取得できるが、重要APIは取得できない。プロキシを迂回しているようだ?
**A1**: これはプロキシ逃逸である（App がシステムプロキシを能動的に読まず、socket へ直接接続する）。まず確認する。取得できるものとできないものが、異なるドメイン/異なるネットワークライブラリか。重要APIが自ら new Socket で直接接続すれば、システムプロキシ設定を迂回する。
**Q2**: 直接接続と確認できた。この部分のトラフィックをどう取り戻すか?
**A2**: 透過プロキシ/VPN モードでネットワーク層で強制リダイレクトする（iptables REDIRECT / tun パケットキャプチャ）。App が能動的にプロキシを通ることに依存しない。リンク層のハイジャックはプロキシ逃逸に免疫がある。ハイジャックするのがデータパケットであり、プロキシ設定ではないからである。
**Q3**: 透過プロキシでも取得できない場合（さらに TLS Pinning を行っているか直接 TCP である）は?
**A3**: 2 種類に分ける。HTTPS+Pinning なら、前述の unpinning を重ねる。独自 TCP なら、バイナリプロトコル + エンドポイント hook に戻る。プロキシ逃逸は Pinning/独自プロトコルと重なって現れることが多く、層ごとに解決する。
**Q4**: さらに DNS-over-HTTPS / 独自 DNS を使って自分の名前解決ハイジャックを迂回している場合は?
**A4**: エンドポイント hook へ移る。DoH/独自 DNS でリンクハイジャックが無効になるときは、App 内でネットワーク送信関数を直接 hook して平文を取るか、その DNS 名前解決/接続関数を hook する。App 内部のあらゆる迂回は「App 内での hook」には無効である。
**Q5**: リンクと hook を両方試しても漏れる場合、どのトラフィックが漏れているかをどう系統的に調査するか?
**A5**: syscall/eBPF の全量観測へ移る。システムコール層ですべての connect/write を記録し、取得できたものと比較して、どの接続が漏れ、どこへ接続したかを精密に特定する。最も低層の観測面でトラフィック監査を行い、死角を残さない。
**Q6**: App のすべてのアウトバウンドトラフィックを徹底的に把握したい。最終手段はあるか?
**A6**: 究極の最終手段は「App とカーネルの間」で取得することである。tun モードによる全量掌握 + 暗号化前平文の hook を重ねる。リンク層が全パケットの取得を保証し（たとえ暗号文でも）、hook 層が平文の意味の取得を保証する。組み合わせれば漏れがない。

### iOS App リバースエンジニアリングの差別化判断
**Q1**: 対象がアンドロイドから iOS 版に変わった。同じく暗号化を復元する。考え方をどう調整するか?
**A1**: 中核の方法論は同じである（パケットキャプチャ定性→暗号化特定→hook で値取得）。ただしツールチェーンと環境が異なる。iOS は Mach-O/Objective-C/Swift で、サンドボックスと署名制限がある。まず脱獄するかしないかを決める。それが後続のすべての手段を決める。
**Q2**: 脱獄デバイスがある場合、どう素早く始めるか?
**A2**: 脱獄下ではアンドロイドと似ている。Frida/objection で hook し、class-dump/Hopper/IDA で OC メソッドを見、SSL Kill Switch で pinning を破る。OC のメソッド名は通常難読化されておらず、アンドロイドより読みやすい。メソッド名を辿って encrypt/sign を探す。
**Q3**: 脱獄デバイスを入手できず、通常のデバイスしかない場合は?
**A3**: 脱獄不要のルートへ移る。再署名で Frida gadget を注入する（objection patchipa / 手動 dylib 注入を使う）か、脱獄不要のパケットキャプチャ + プロファイルを使う。能力は制限されるが、大部分の hook ニーズをカバーできる。
**Q4**: 暗号化が Swift 内にあり、シンボルが strip され、名前修飾(mangling)で読みにくい場合は?
**A4**: Swift は OC より逆算が難しい。まずシンボルを demangle し、重点はやはり動的 hook へ移る（メソッドを hook できればよく、Swift 実装を読み解く必要はない）。Swift の静的逆算はコストが高く、実行時の値取得に依存する。
**Q5**: iOS 特有の保護（脱獄検知、プロテクト）で hook 環境が立ち上がらない場合は?
**A5**: 脱獄隠蔽 + 環境処理へ移る。脱獄隠蔽ツールで検知を通過するか、よりきれいな脱獄方式に変える。プロテクトが強すぎるなら、「パケットキャプチャのみ + 重要関数のエンドポイント hook」に退き、全量制御を追求しない。
**Q6**: 重要ロジックがやはり native（C/C++ 静的ライブラリ）に移されている場合は?
**A6**: アンドロイドの so と同様に処理する。Mach-O 内の native 関数を逆算するか hook する。戦場は OC/Swift 層から native 層へ移り、方法論はアンドロイド so のあの一連を完全に再利用する。

### JSON フィールドを base64 で解いても文字化けする場合
**Q1**: レスポンスが JSON で、あるフィールドを base64 decode したら平文を期待していたのに、結果は文字化けの山である。どこが間違っているか?
**A1**: base64 の中にもう 1 層あることを示す。文字化けの形態を判定する。高エントロピー→やはり暗号文（さらに復号が必要）。先頭 1f8b→gzip。先頭 78 9c→zlib。また base64 らしい→もう 1 層 decode する。base64 はエンコーディングに過ぎず、終点ではない。
**Q2**: 中身が gzip と判断した。解凍すれば平文になるか?
**A2**: gunzip を試す。構造化データ（JSON/テキスト）が出れば終点である。やはり高エントロピーなら、「先に暗号化してから圧縮」または「先に圧縮してから暗号化」であり、形態に従って剥き続ける。剥く順序は暗号化時と逆であることを覚えておく。
**Q3**: 中身が暗号文だが、この層をどの key/アルゴリズムで解くか分からない場合は?
**A3**: hook へ戻る。この層の解き方を推測するより、このフィールドを処理する復号関数を hook して、どう解き、どの key を使うかを直接見る。フィールド単位のネスト暗号化の最速の破り方は、その処理コードを実行時に観察することである。
**Q4**: base64 decode が直接エラーになる場合（正規の base64 ではない）は?
**A4**: バリアントを確認する。URL-safe base64（- _ が + / を置換）、パディングなし、またはそもそも base64 ではなく base62/base58/hex/独自アルファベット表。対応するデコーダに変えるか、App 内のエンコード関数を見てアルファベット表を確認する。
**Q5**: 何層か剥いても文字化けし、判定チェーンのどこかが間違っていると疑う場合は?
**A5**: 「hook を正とする」検証へ移る。層を盲目的に推測せず、App 内でこのフィールドが暗号文から平文になる完全な処理チェーンを hook し、各層の中間値を表示して、実際のエンコーディング/暗号化の順序をはっきり見てから、それに従って実装する。
**Q6**: この種のネストフィールドを一括処理したい場合は?
**A6**: 安定した剥離パイプライン（decode→decrypt→decompress の固定順序）を復元して関数にラップするか、App の復号関数を直接再利用して RPC にする。構造を 1 回解明すれば、後続は一括で適用できる。

### WebSocket / 長接続プロトコルのリバースエンジニアリング
**Q1**: App が WebSocket 長接続でメッセージをプッシュし、フレーム内容が暗号化されている。どう復元するか?
**A1**: まず WS ハンドシェイクとフレームを取得する。標準 WS（Upgrade ハンドシェイクがある）か自社開発の長接続かを確認する。標準 WS はパケットキャプチャツールでフレーム分解でき、各フレームの payload 形態（テキスト/バイナリ/暗号化）を見る。定性後に暗号化を特定する。
**Q2**: WS フレームが暗号化されたバイナリで、中にさらにサブプロトコル（コマンド語+body）がある可能性がある場合は?
**A2**: 2 層に分解する。WS は伝送層であり、中の暗号化 payload こそが業務プロトコルである。先に単一フレームを復号し、それから業務プロトコル構造（コマンド語、シーケンス番号、body は protobuf/JSON であることが多い）を解析する。WS フレーム構造と業務プロトコルを混同しない。
**Q3**: WS が wss(TLS)を通り、しかも pinning があるため、フレームを取得できない場合は?
**A3**: unpinning を重ねるか、エンドポイント hook へ移る。WebSocket の send/onMessage コールバックを hook し、暗号化前/復号後に平文フレームを取る。長接続フレームワークの送受信コールバックは最良の hook 点である。
**Q4**: 自社開発の長接続（非標準 WS）で、パケットキャプチャツールがフレーム分解できない場合は?
**A4**: 独自バイナリプロトコル復元へ移る。TCP ストリームに従って長さフィールドを探してフレーム分割し、粘着/分割パケットを処理し、各フレームの構造を判定する。同時に長接続ライブラリのコーデックを hook してパッキング関数を特定する。
**Q5**: 長接続にハートビート/暗号化ハンドシェイクがあり、単一フレームのリプレイが無意味な場合は?
**A5**: 「接続内での注入」の考え方へ移る。長接続には状態（シーケンス番号、セッション鍵）があり、オフラインでの単一フレームのリプレイは無意味である。確立済みの接続を hook し、その送信関数内で自分のフレームを注入し、セッション状態と暗号化を再利用する。
**Q6**: 能動的にメッセージを構築してサーバーを攻撃したい場合（プッシュ偽造/権限外アクセス命令など）は?
**A6**: 生体接続を使う。App に接続を確立させた後、hook でこの認証済み接続上から自分が構築した業務フレームを送る。借りるのは App が完了済みのハンドシェイク+認証+暗号化コンテキストであり、自分でゼロから接続を確立するのはほぼ不可能である。

### バイナリ独自プロトコル:分割・粘着パケットと TLV
**Q1**: 取得した TCP ストリームがすべてバイナリで、1 つずつのメッセージに分解する必要がある。メッセージ境界をどう探すか?
**A1**: 長さフィールドを探す。多くの独自プロトコルは「長さプレフィックス」方式で、先頭 2/4 バイトが本メッセージの長さである。複数メッセージを比較し、先頭のどのバイトの値が後続内容の長さとちょうど等しいかを見る。それが長さフィールドである。長さフィールドの特定=分割・粘着パケットの解決である。
**Q2**: 長さフィールドを見つけた後、メッセージ内部構造をどう分解するか?
**A2**: 一般的には TLV（Type-Length-Value）または固定ヘッダー+body である。差分を行う。異なる操作をいくつか送り、どのバイトが固定か（マジックナンバー/バージョン/コマンド語）、どのバイトが変化するか（シーケンス番号/タイムスタンプ/payload）を見る。固定のものがプロトコルの骨格で、変化するものは意味に従って推測する。
**Q3**: コマンド語(cmd)がどの操作に対応するか対応づけられない場合は?
**A3**: 挙動を関連づける。各操作を 1 回ずつ取得し、その cmd 値を記録して、cmd→機能の対応表を作る。同時に静的解析で switch/case または cmd 定数定義を検索する。逆コンパイル内の cmd 分配ロジックが完全なコマンド表を直接与えてくれる。
**Q4**: body が暗号化されており、フレーム分割しても内容を読み解けない場合は?
**A4**: 層を分ける。先にプロトコルフレームワーク（フレーム分割+ヘッダー）を解決し、body の復号は別のサブタスクとして暗号化復元フロー（暗号化・復号関数の hook）へ移る。フレームワーク層と暗号化層を分けて攻め、ごった煮にしない。
**Q5**: 長さフィールドが見つからない場合（定長メッセージ? またはエスケープ/区切り文字がある?）は?
**A5**: フレーム分割の仮説を変える。定長メッセージ（N バイトごとに 1 つ）、区切り文字（特定バイト列で区切る）、またはエスケープ機構がある可能性がある。仮説を 1 つずつ検証するか、静的解析でコーデックがどうフレームを切るかを直接見る。バイトを当て推量しない。
**Q6**: ビッグエンディアン/リトルエンディアン / アラインメントを間違えて解析がすべて乱れる場合は?
**A6**: バイト順序を校正する。長さと数値フィールドでビッグエンディアンとリトルエンディアンを試し、解いた結果が合理的な方（長さが実際の内容長と等しい）が正しい。独自プロトコルでは大小端の両方が一般的であり、「長さフィールドの自己整合」を検証のアンカーにする。

### アカウント乗っ取り:ログイン / token リフレッシュロジックの特定
**Q1**: アカウント乗っ取りやセッション操作をしたい。ログインと token メカニズムを理解する必要がある。どこから切り込むか?
**A1**: ログイン全フローを取得する。アカウント・パスワードがどう暗号化されて送られるか、サーバーが何を返すか（token/refresh_token/session）、後続リクエストがどう token を付けるか。まず「ログイン→token 取得→token 付きアクセス→token 期限切れ→リフレッシュ」というチェーンを描く。
**Q2**: パスワードが暗号化されて送られる。それがパスワードをどう処理するかを見たい場合は?
**A2**: パスワード入力から送信までの処理を hook する。RSA によるパスワード暗号化 + 伝送層での再暗号化であることが多い。パスワード暗号化関数を特定し、リプレイ可能か（固定暗号化）、ランダム付きか（毎回異なる）を理解する。これがログインパケットをオフライン構築できるかを決める。
**Q3**: token リフレッシュメカニズムを利用したい場合（refresh_token が失効しないなど）は?
**A3**: リフレッシュAPIを解析する。refresh_token の有効期間、一回限りか、リフレッシュ時に何を検証するか。レッドチームの関心点：token が漏洩した後どのくらい延命できるか、二次検証を迂回してリフレッシュできるか。token ライフサイクルのロジック脆弱性解析へ移る。
**Q4**: ログインに SMS/画像認証コードがあり、完全なログインを構築できない場合は?
**A4**: 方向転換：アカウント乗っ取りは必ずしもログインを経由しなくてよい。パスワードレスロジック（token 直接注入、デバイス信頼、権限外アクセスによる電話番号紐づけ変更）があるか、既存 token で操作できるかを見る。認証コードが塞ぐのはログイン入口であり、業務APIを塞ぐとは限らない。
**Q5**: 暗号化ログインパケットを再現できない場合（デバイスフィンガープリント/リスク管理付き）、この道は途絶えるか?
**A5**: 「生体+ロジック」の次元へ移る。App プロキシで正規ログインを送って token を取り、token 取得後の権限外アクセス/紐づけ変更/情報漏洩を研究する。攻撃の重心を「ログインの偽造」から「正規ログイン後のロジック脆弱性」へ移し、ログイン箇所の強力な暗号化・強力なリスク管理を避ける。
**Q6**: アカウントを一括検証したい（クレデンシャルスタッフィング系）が、各リクエストの暗号化コストが大きい場合は?
**A6**: 必要性と手段を評価する。一括が確かに必要なら、復元済みの暗号化能力で暗号化プロキシを作って一括送信する。しかし一括ログインは必ずリスク管理をトリガーすると意識すべきである。レッドチームの価値は通常「一括」ではなく「単一アカウントの深い乗っ取り」にあり、目標に応じて調整する。

### 環境構築が行き詰まる場合(デバイス/root/バージョン不一致)
**Q1**: リバースエンジニアリングを始める前に環境が崩れる。root がきれいでない、frida バージョンが合わない、デバイスアーキテクチャが一致しない。どう打開するか?
**A1**: まず応急処置し、構築しながら試行錯誤しない。環境依存の一覧を出す。アンドロイドバージョン、アーキテクチャ（arm64/arm）、frida-server バージョンは client と一致させる、root 方式（magisk）、対象 App の最低バージョン要件。一度に揃え、あれこれ試さない。
**Q2**: frida attach がバージョン不一致 / プロトコルエラーを報告する場合は?
**A2**: frida-server とホストの frida ツールのバージョン番号を厳密に揃える（必ず一致）。アーキテクチャはデバイス CPU と一致させる。これは最も一般的な落とし穴で、バージョン番号が少しでも違えば接続できない。まずこの基礎を固める。
**Q3**: 適切な物理デバイスが無い / 実機を root できない場合は?
**A3**: エミュレーター/クラウド実機へ移る。root と arm 変換をサポートするエミュレーター、またはクラウド実機サービスを使う。App がエミュレーターを検知する可能性に注意し、エミュレーター検知対策を組み合わせる。デバイスは唯一解ではなく、仮想環境+アンチ検知で十分なことが多い。
**Q4**: App がエミュレーターを検知して起動しない場合は?
**A4**: エミュレーター検知対策へ移る。検知点（getprop 内のエミュレーター特徴、センサー欠落、特定ファイル）を hook するか、より本物に近いエミュレーター/実機を使う。エミュレーターのコストが高すぎるなら物理デバイスのルートに戻る。二刀流で、使いやすい方を使う。
**Q5**: 環境問題が大量の時間を繰り返し消耗し、進行を大きく遅らせる場合は?
**A5**: 戦略的に静的/オフラインへ移る。動的環境が底なし沼なら、静的でできること（so を取り出して unidbg、純粋な逆コンパイルでロジックを読む）を先に済ませ、脆弱な動的環境への依存を減らす。環境は手段であり、環境構築をメインタスクにしない。
**Q6**: 複数の対象 App をテストする必要があり、それぞれ環境を再構築する場合は?
**A6**: 標準化した環境を蓄積する。再利用可能な root+frida+パケットキャプチャのイメージ/スクリプト一式を固め、新対象にはそのまま適用する。環境構築を「毎回の落とし穴踏み」から「ワンクリックで準備完了」に変える。これはレッドチームのエンジニアリング化の基礎投資である。

### 差分解析法による未知プロトコルのリバースエンジニアリング
**Q1**: 完全に未知の暗号化プロトコルに直面し、手掛かりがない。コードを読まない汎用の出発方法はあるか?
**A1**: 差分解析（ブラックボックス）である。同じ操作を複数回送り、メッセージを比較する。不変部分（プロトコルヘッダー/固定フィールド）と変化部分（シーケンス番号/時刻/乱数/業務値）を洗い出す。さらに単一の入力（ユーザー名を 1 文字変更）を変え、メッセージのどこが変わるかを見て、「入力フィールド↔メッセージ位置」の対応を構築する。
**Q2**: 暗号化メッセージの差分で、1 バイトの平文を変えると暗号文が全部変わる（雪崩効果）ため、差分で対応が見えない場合は?
**A2**: 雪崩効果はブロック暗号/ストリーム暗号の全体暗号化であることを示し、フィールド単位の差分は暗号文上で無効になる。「暗号化前」の差分へ移る。hook で平文を取ってから差分するか、暗号文層の差分を直接やめて暗号化復元へ移る（平文を得ればすべて楽になる）。
**Q3**: あるフィールドがタイムスタンプか乱数かを確認したい場合は?
**A3**: 時間次元の差分を行う。異なる時間間隔で同じリクエストを送り、どのフィールドが時間に従って単調に変わるかを見る。単調に変わる→タイムスタンプ。毎回変わるが規則なし→乱数/nonce。完全に不変→固定設定。「時間を制御する」という変数で判定する。
**Q4**: 差分でフィールド位置は特定できるが、フィールドのエンコーディング（int? 可変長?）が分からない場合は?
**A4**: 既知の数値を変えて観察する。ある数値パラメータを 1 から 255、さらに 256 に変え、メッセージの対応バイトがどう変わるかを見て、定長 int（256 で次のバイトへ繰り上がる）か varint かを導く。境界値でエンコーディング方式を探る。
**Q5**: 純粋なブラックボックス差分が限界に達し、これ以上の意味を推測できない場合は?
**A5**: ホワイトボックスによる補完へ移る。差分が構造の仮説を与え、その仮説を逆コンパイル/hook に持ち帰って検証・補完する。ブラックボックス差分とホワイトボックス逆算は相補的である。差分は素早く出発して位置を特定し、ホワイトボックスは意味を精密に確定する。両者を組み合わせる。
**Q6**: 差分を自動化したい場合は?
**A6**: スクリプト化した収集+比較を行う。バリアントリクエストを自動送信し、メッセージを自動 diff し、変化位置を自動注記する。フィールドの多い複雑なプロトコルでは、自動差分は手動の目視よりはるかに速く、微細な変化フィールドも見落としにくい。

### 整合性検証 / 改ざん防止(リパッケージが拒否される)
**Q1**: リパッケージしてコードを注入した後、App が起動時にエラーになるかクラッシュする。整合性検証である。どうするか?
**A1**: まず検証種別を特定する。署名検証（APK 署名の照合）、ファイルハッシュ検証（dex/so の整合性検証）、それとも CRC。エラーのタイミングと内容を見る。対策：ファイルを変更しなくて済むなら変更しない。実行時注入（リパッケージ不要）を優先し、あらゆるファイル検証を迂回する。
**Q2**: ファイル変更が必須の場合（あるロジックを patch するなど）、署名検証をどう通過するか?
**A2**: 署名検証点を hook する。PackageManager.getPackageInfo / getPackageInfo が返す署名を hook し、元の署名値を返させる。または自己検証関数を見つけて直接通過に patch する。「読み取った署名」を正規の値に偽造する。
**Q3**: 検証が native 内にあり、しかも so 自身を検証している場合は?
**A3**: native の patch/hook へ移る。native 検証関数の戻り値を hook するか、検証前にメモリ内の比較基準を実際の値に変更する。so の自己検証は通常、自身のファイルを読んでハッシュを計算して比較するため、ハッシュ比較結果を hook で潰せばよい。
**Q4**: サーバーが関与する整合性検証がある場合（検証結果をサーバーへ報告する）は?
**A4**: これは難物である。「クライアントを改ざんしない」ルートへ移る。App の変更をやめ、純粋な hook（実行時注入でファイル不変更）+ パケットキャプチャ解析に切り替える。サーバーが整合性を検証する場合、ローカル改ざんは必ず露見するため、改ざんせず、観測と既存能力の利用だけを行う。
**Q5**: 実行時注入すら検知される場合（hook フレームワークを検知）は?
**A5**: アンチデバッグ/アンチ hook 隠蔽の次元へ戻る。まず注入フレームワークをきれいに隠して（frida/xposed の特徴を隠す）から注入を考える。hook 検知とデバッグ検知は同種の対抗であり、同じ隠蔽手段で対処する。
**Q6**: すべてのローカル手段が防がれた場合、さらにどう進めるか?
**A6**: 純粋なネットワーク側 + 生体へ移る。クライアントバイナリに一切触れず、パケットキャプチャ + きれいな App を暗号化プロキシとしてリクエストを送る方法で、攻撃面をサーバーAPIのロジック脆弱性に絞る。クライアントがどれほど防いでも、サーバーAPIはリクエストを処理しなければならず、そこが最終戦場である。

### 国密アルゴリズム(SM2/SM3/SM4)特化
**Q1**: 対象が国密（SM 系列）を使っていると識別した。通常の AES/RSA 処理と比べて何が異なり、何に注意すべきか?
**A1**: 方法論は同じで、落とし穴は細部にある。SM4 は AES に類比する（ブロック 16 バイト、ECB/CBC と IV に注意）。SM3 は SHA-256 に類比してハッシュ/HMAC に使う。SM2 は ECC に類比して非対称に使う。まず具体的にどれを使うかを確認し、まとめて「国密」と扱わない。
**Q2**: SM2 暗号化の再現で、暗号文形式がどうしても合わない場合は?
**A2**: 最大の落とし穴は暗号文の並び順である。SM2 暗号文には C1（楕円曲線上の点）、C2（暗号文）、C3（ハッシュ）があり、標準は C1C3C2 だが、多くの実装は C1C2C3 を使い、さらに 04 プレフィックスの有無の違いもある。並び順の組み合わせを 1 つずつ試し、App の実測暗号文と突き合わせる。
**Q3**: SM4 の再現が合わない場合は?
**A3**: AES と同様に調査する。モード（ECB/CBC）、IV、パディング（PKCS7）、key 長（16 バイト）。国密ライブラリ間の実装差異も細部の違いを生むため、App の一組の実測平文・暗号文を正解として項目ごとに突き合わせる。
**Q4**: ツール/ライブラリの国密サポートが悪く、再現が困難な場合は?
**A4**: 成熟した国密ライブラリへ移る（gmssl、bouncycastle の国密拡張、各言語の sm-crypto）。国密非対応の標準ライブラリで無理に合わせない。ライブラリを正しく選べば、大量の暗号文形式の落とし穴を省ける。
**Q5**: 国密アルゴリズムが native にあり、しかも改変されていて、再現の見込みがない場合は?
**A5**: 汎用の退路であるブラックボックス RPC に戻る。国密かどうか、改変があるかどうかに関係なく、その暗号化・復号関数を hook してブラックボックスとして使う。アルゴリズムが何かはブラックボックス呼び出しには無関係であり、これはあらゆる「再現困難」場面の統一出口である。
**Q6**: SM2 署名を偽造したい場合（秘密鍵を取る）は?
**A6**: 秘密鍵特定と同じ考え方である。クライアントの署名は必ず秘密鍵を使うため、秘密鍵または署名関数を hook して署名 oracle として使う。SM2 を本当に破って秘密鍵を取るのは暗号解析では非現実的であり、「クライアントが秘密鍵を保持している」という事実を頼りに hook するのが実戦経路である。

### 目標は脆弱性攻撃:正規の暗号化メッセージを構築して初めて到達できる
**Q1**: 脆弱性らしきAPI（未認可/インジェクションなど）を発見したが、それが暗号化メッセージを要求し、正しく構築しないと脆弱性ポイントへ到達できない場合はどうするか?
**A1**: まず「暗号化の外殻」と「脆弱性ペイロード」を分ける。必要なのは、任意の平文ペイロードを暗号化して正規メッセージにする能力である。App を暗号化器として使う（hook で自分の payload を注入し、App に暗号化させて送信させる）のを優先し、ゼロからのアルゴリズム再現はしない。
**Q2**: 脆弱性がインジェクション系（SQLi/コマンドインジェクション）で、payload に特殊文字がある。暗号化後、正常に到達できるか?
**A2**: できる。暗号化は透過チャネルであり、payload の平文にどのような特殊文字が含まれていても、復号後にサーバーが受け取るのはその文字そのものである。重要なのは payload が暗号化されるフィールドに入ることを保証することである。暗号化プロキシで、平文APIを攻撃するようにこのフィールドを攻撃する。
**Q3**: 自動化ツール（sqlmap/burp）でこの暗号化APIを攻撃したい場合は?
**A3**: 暗号化プロキシ中間層を構築する。ツールが平文を送り→プロキシが暗号化署名→転送→レスポンス復号→ツールへ返す。こうして暗号化APIを「次元を下げて」普通の平文APIにし、すべての Web 自動化ツールを直接使えるようにする。これは暗号化APIの脆弱性を攻める中核のエンジニアリング手段である。
**Q4**: 暗号化に署名が付いており、payload が変わると署名を再計算しなければならない。プロキシでどう処理するか?
**A4**: プロキシに署名ロジックを統合する。毎回の転送前に、hook で得た署名能力で現在の（payload を含む）平文に再署名する。つまりプロキシは暗号化だけでなく、完全な「暗号化+署名」の組み立てフローを再現し、各バリアント payload がすべて正規メッセージになることを保証する。
**Q5**: 暗号化メッセージは到達できるが、脆弱性の悪用が失敗する。脆弱性が存在しないのか、構築に問題があるのか?
**A5**: 変数を制御して確認する。まず既知の正規な通常リクエストを送って経路が通ることを確認し、次に明確なプローブ payload（エラーベース注入のプローブなど）を送る。通常リクエストが通り、プローブに反応がなければ、脆弱性が存在しないかフィルタされている可能性がある。通常リクエストすら通らないなら、暗号化構築の問題である。層ごとに切り分ける。
**Q6**: 暗号化APIを攻略できない場合、考え方を変えるべきか?
**A6**: 攻撃面 + 情報の次元へ移る。このAPIが硬いなら、他のAPIに変える。または先に情報収集を行う（復元したプロトコルに内部APIパス、パラメータ、バージョンが露呈している可能性がある）。プロトコル復元の成果を使って、より軟らかい単点を探す指針とする。プロトコル復元自体が 1 回の深い情報収集であり、1 つの穴だけを見つめない。
