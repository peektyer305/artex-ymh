# Appクライアント · APKリバースエンジニアリングでAPIと鍵を抽出

### APK を入手したら、まず何をするか
**Q1**: 手元に未知の APK があり、対象はバックエンド API と鍵の抽出。最初にすべきことは何か。いきなり jadx に飛びつかずに?
**A1**: まず情報偵察をしてから分解に取りかかる。最初のアクションは APK の展開(unzip でよい、APK の本質は zip)と、ディレクトリ構造の一括走査。`AndroidManifest.xml` でパッケージ名/権限/コンポーネント/exported を、`assets/` と `res/raw/` で平文設定の有無を、`lib/` で native so の有無を、`META-INF/` で署名を見る。判定基準:この手順で 5 分以内に「純粋な Java/Kotlin アプリ」か「コアロジックが native/プロテクトのパッカー内」かを判断でき、その後の逆コンパイル方針かアンパック/frida 方針かを決められる。いきなり jadx を開いて無心でコードを読み進めない。
**Q2**: ディレクトリを走査し終えるとクラス名がすべて a/b/c/一文字で、jadx では文字化けだらけ。次の手順をどう判断するか?
**A2**: これは難読化(ProGuard/R8/DexGuard)の兆候だが、難読化 ≠ プロテクト。まず区別する:`classes.dex` が正常に逆コンパイルできてロジックが出る(名前が醜いだけ)なら、それは通常の難読化で、API の URL や鍵の文字列は通常残っているので、そのまま文字列検索に進む。dex 内に業務クラスがまったくなく、パッカー SDK(各プロテクトベンダーの Application クラスなど)しかないなら、それはプロテクトなので、まずアンパックが必要。判定基準:グローバルに `http`、`api`、パッケージ名のキーワードを検索し、業務文字列がヒットすればパッカーはないと分かる。

### 難読化 vs プロテクト vs 無保護、三叉路の選び方
**Q1**: この APK が「無保護/難読化のみ/プロテクト済み」のどれに該当するかを素早く判定し、方針を誤らないようにするには?
**A1**: 3 つのシグナルを見る。(1) `classes.dex` の数とサイズ。プロテクトのパッカーは往々にしてメイン dex が極小で、本物の dex は assets 内に暗号化されて隠される。(2) `AndroidManifest` の `application:name` が指すクラスがプロテクトベンダーの SDK かどうか(このクラス名を検索する)。(3) `lib/` 配下にプロテクトの特徴 so があるか(ベンダープレフィックス付きの命名)。どれか 1 つでも該当すればプロテクトとして扱い、そうでなければ難読化/無保護として扱う。判定基準:これは「どれだけコストを投じるか」を決めるトリアージで、プロテクトはアンパックが必要(重い)、難読化は検索+リネームのみ(軽い)。
**Q2**: プロテクトと判定したが、時間が限られている。必ずアンパックが必要か?
**A2**: 必ずしもそうではない。まず「欲しいものがパッカーの外にあるか」を問う。API の URL、H5 ページのアドレス、サードパーティ SDK の appid などは、`assets/`、`res/`、`AndroidManifest` の `meta-data`、さらには H5 リソース内に平文で置かれていることが多く、アンパックなしで取得できる。保護された dex 内にコアな署名アルゴリズムや秘密鍵がある場合にのみアンパックする価値がある。方向転換:まず「アンパックせずに取れる情報」を搾り尽くしてから、アンパックという重作業に進むか決める。

### jadx が開けない・クラッシュする場合
**Q1**: jadx-gui がこの APK の読み込みで直接クラッシュまたはフリーズする。このパッケージはリバースエンジニアリング不能なのか?
**A1**: いいや。jadx のクラッシュのよくある原因は、dex が大きすぎる、逆コンパイル対策の不正なバイトコードがある、またはマルチ dex。まず手段を下げる:コマンドライン `jadx --no-debug-info --show-bad-code` でエラー耐性を持たせて実行する。それでもダメなら `d2j-dex2jar` で jar に変換して別のデコンパイラ(procyon/CFR/Fernflower)でクロスチェックする。さらにダメなら smali レイヤに退き、`apktool d` で smali を出して直接アセンブリを読む。判定基準:デコンパイラは道具に過ぎず、1 つがダメなら別のに替える。smali は必ず読める。
**Q2**: smali は低レベルすぎて読むのが遅い。手抜きの方法はあるか?
**A2**: ある。smali を通読せず、「手がかりによる特定」を行う。まず grep で smali ディレクトリ内の文字列定数(URL、鍵の形式、`AES`/`RSA`/`HmacSHA256` などの暗号化アルゴリズム名)を検索し、具体的な smali ファイルとメソッドを特定して、その数個のメソッドだけを精読する。方向転換:「コードを通読」から「文字列駆動の狙い撃ちリーディング」に切り替える。効率が 1 桁上がる。

### 平文の鍵/API の第一波の回収
**Q1**: 平文の API と鍵を一気に回収したい。最も省力な検索の打ち方は?
**A1**: 逆コンパイル生成物(または apk の展開ディレクトリに直接)に対してグローバル文字列検索を行い、キーワードを数カテゴリに分けて打つ。プロトコル系 `http://`/`https://`/`ws://`、API 系 `/api/`/`/v1/`/`endpoint`/`base_url`、鍵系 `secret`/`appkey`/`app_secret`/`token`/`ak`/`sk`/`private_key`/`-----BEGIN`、設定系 `password`/`pwd`/`config`。同時に高エントロピー文字列(長い base64/hex)を走査する。判定基準:この一撃で 60% 以上の手軽に得られる成果にヒットする。特にサードパーティのクラウド SDK の AK/SK がそうだ。
**Q2**: 鍵らしきものが大量にヒットした。どれが本当に有用かをどう見分ける?
**A2**: 「検証可能性」で並べ替える。クラウドベンダーの AK/SK は固定プレフィックス形式(識別可能)、プッシュ/統計/地図 SDK の key は用途が明確なので、これらを優先する。不明な文字列は、コード内で誰に呼び出されているかを見る。HTTP ヘッダーや署名関数に埋め込まれているものだけに価値があり、単なるローカルキャッシュの key として使われているものは無価値。方向転換:「何を検索できたか」から「この鍵がどの呼び出しチェーン上にあり、何を得られるか」に切り替える。下流の用途がない鍵はノイズだ。

### assets/res 内の隠し設定
**Q1**: コード内で API が見つからない。API アドレスが動的に配信されているのか?結論を急がず、まだ見ていない静的な場所はどこか?
**A1**: `assets/` と `res/raw/` を調べる。多くの App がここに設定を置く。json/xml/properties の設定ファイル、埋め込み H5(index.html + js、中は API だらけ)、React Native の `index.android.bundle`、Flutter のリソース、ミニプログラムカーネルのパッケージ。さらに `res/values/strings.xml` には `base_url` がよくある。判定基準:assets は「コード外の第二の倉庫」で、リバースエンジニアリング初心者が最も見落としやすい。先に assets 全体を grep してから、API が動的かどうかを語る。
**Q2**: assets 内に `.bundle` や暗号化された設定ファイルを発見したが開けない場合どうする?
**A2**: 分類して処理する。JS bundle(RN)は美化(prettier)してから通常の JS として読める。API はすべて中にある。暗号化された設定はコード内で「誰が復号したか」を探す。ファイル名の文字列を検索し、読み取り+復号コードを特定して、アルゴリズムと鍵を得る。方向転換:暗号化されたリソースに当たったら無理に解かず、「復号側のロジック」へ移る。鍵は必ずクライアント側にある(ホワイトボックス)。呼び出しチェーンを辿れば掘り出せる。

### native so に隠されたコアロジック
**Q1**: Java レイヤには `nativeSign()` のような native メソッド宣言しか見えず、本当の署名/鍵は so 内にある。どう切り込むか?
**A1**: すぐに IDA で so をがっつり読もうとしない。コストをレイヤ分けして判断する。(1) まず Java レイヤの呼び出しを見る。native メソッドの引数・戻り値をどう使っているかで、その「機能的な意味」(署名か?暗号化・復号か?)を推測できる。(2) `frida` でこの native メソッドを hook し、ランタイムの引数と戻り値を直接見る。多くの場合、ブラックボックス hook で結果を得られれば十分で、アセンブリを読む必要はない。(3) オフラインでアルゴリズムを再現する必要があるときだけ、IDA/Ghidra による静的解析で so を読む。判定基準:hook で結果を得る << アルゴリズムを逆解析。ブラックボックスで解決できるならホワイトボックスにしない。
**Q2**: so 内のアルゴリズムを必ずリバースエンジニアリングしなければならないが、IDA で開くとシンボルが剥がされ、OLLVM 難読化(制御フロー平坦化)もある。どう進める?
**A2**: 通読ではなく、まずアンカーを探す。アンカーの出どころ:エクスポート関数名(JNI メソッド名 `Java_パッケージ名_クラス_メソッド`)、文字列参照(アルゴリズム定数、エラーメッセージ)、インポート関数(`AES`/`memcpy`/システム暗号化 API を呼んでいる)。アンカーからキー関数を特定したら、OLLVM の平坦化に対しては、静的解析で無理に追うのではなく、frida trace/unicorn によるシミュレーション実行で「一度走らせてデータフローを見る」ことを優先する。方向転換:静的解析が難読化で塞がれたら、動的解析(frida/シミュレーション実行)に移り、ランタイムの実データからアルゴリズムを逆算する。

### 動的に配信される API アドレス
**Q1**: 静的解析でくまなく調べても「設定センター」のアドレスが 1 つ見つかるだけで、実際の業務 API は起動後に取得される。全量の API をどう得るか?
**A1**: 静的から動的に切り替える。パケットキャプチャだ。実際の API は実行時にすべてネットワークトラフィックに露出する。プロキシ(Burp/mitmproxy)を立てて App を動かし、一通り操作すれば、すべての API が自動的に網にかかる。判定基準:コード内で動的ロジックを推測するより、App 自身に API を「語らせる」。これはリバースエンジニアリングの次元からトラフィックの次元への切り替えだ。
**Q2**: プロキシを設定したのに App のトラフィックがまったくプロキシを通らない、または直接ネットワークエラーを返す。どうする?
**A2**: 可能性を 1 つずつ排除する。(1) App が SSL Pinning(証明書バインディング)を使っている。最も多い。バイパスが必要(後述)。(2) App がシステムプロキシを読まず、独自のネットワークスタックを通る。VPN モードでのパケットキャプチャ(透過プロキシ/tun など)か、frida によるネットワークライブラリの hook が必要。(3) App がプロキシを検知して直接接続拒否する。プロキシの特徴を隠す必要がある。方向転換:パケットが取れないのはトラフィックがないことを意味しない。VPN/tun レイヤでのキャプチャかネットワークライブラリの hook という 2 つの直交する手段に移る。

### SSL Pinning がパケットキャプチャを遮る
**Q1**: キャプチャ時に App が証明書エラー・接続中断を返す。SSL Pinning と判断する。どう回避する?
**A1**: コストの低い順に。(1) まず汎用 frida スクリプト(コミュニティの universal unpinning スクリプトなど)を試す。OkHttp/TrustManager/ネイティブなどの主要実装をカバーし、大半の App は一発で通る。(2) ダメなら objection の `android sslpinning disable` を使う。(3) さらにダメなら、それは独自の pinning か native レイヤでの検証なので、検証関数を手動で特定して hook する必要がある。判定基準:まず汎用スクリプトを試す。90% の商用 App は通る。
**Q2**: 汎用スクリプトを全部試してもなお pin され、証明書検証が native so 内にあり、frida でも hook しにくい。どう切り替える?
**A2**: 発想を変え、証明書と格闘しない。(1) 一部の App には「テスト環境/debug スイッチ」があり、pinning を無効化する設定ビットがないかをリバースエンジニアリングで探す。(2) キャプチャではなく直接コードを読む。対象が「どの API があるかを知ること」なら、逆コンパイル内の API 定義(Retrofit アノテーション、URL 定数)自体が API リストであり、必ずしもキャプチャでトラフィックを見る必要はない。(3) flutter などでは pinning が BoringSSL 内にあるため、so の特定関数オフセットを patch する必要がある。方向転換:キャプチャが pin で塞がれたら、静的に API 定義を読む方向に戻るか、native の検証点を直接 patch/hook する。

### Retrofit/OkHttp の API リストの静的抽出
**Q1**: キャプチャせず、純粋に静的解析で「完全な API リスト」を得たい。この App は Retrofit を使っている。どう効率よく抽出する?
**A1**: Retrofit の API はすべてアノテーション付きの interface。アノテーションのキーワードを検索する:`@GET`/`@POST`/`@PUT`/`@DELETE`/`@Path`/`@Query`/`@Body`/`@Headers`、そして `@Url`。これらの interface を特定したら、各メソッドのパス+パラメータが 1 つの完全な API シグネチャになり、base_url と組み合わせて完全な URL を組み立てる。判定基準:Retrofit のアノテーションが API リストを構造化し、キャプチャより網羅的になる(クリックされていない API も含む)。
**Q2**: 難読化後もアノテーションは残るか?アノテーションも R8 の最適化で消えた場合はどうする?
**A2**: ランタイムのリフレクションで使われるアノテーションは通常 keep され、高い確率で残っている。実際に削除されたなら、次善策としてパス文字列(`/api/`、`/v` で始まる定数)を検索するか、OkHttp の `Request.Builder`/`.url(`/`.addHeader(` の構築点を検索し、URL を組み立てている箇所を追う。方向転換:アノテーションが消えたら、「URL 文字列定数」と「リクエスト構築コード」という 2 つの直交する入り口から API を逆算する。

### WebView / H5 ハイブリッドアプリ
**Q1**: この App の機能の大半は WebView が H5 を読み込むもので、ネイティブコードはごく薄い。API はどこで探すべきか?
**A1**: API は H5 の JS 内にあり、ネイティブにはない。WebView が読み込む URL を探し(`loadUrl`/`WebView` を検索)、2 つに分ける。(1) リモート H5 の読み込み。直接キャプチャするか、その H5 サイトにアクセスして Web 対象として攻める。(2) 内蔵オフライン H5。assets 内にあるので、取り出して JS を読む。同時に JS Bridge(`addJavascriptInterface`/`@JavascriptInterface`)に注目する。ネイティブが JS に公開するメソッドは、しばしば機微な能力(ファイル読み取り、token 取得)だ。判定基準:ハイブリッドアプリの攻撃面の重心は Web/JS にあり、ネイティブのリバースエンジニアリングにはない。
**Q2**: H5 の JS も圧縮/難読化されているか、API が暗号化を通る。どうする?
**A2**: JS の難読化はネイティブよりはるかに弱い。まず prettier で整形し、Chrome DevTools(`chrome://inspect` で WebView をリモートデバッグ)でブレークポイントを張って動的に調べる。ランタイムの変数が一目で分かる。JS Bridge は追加の突破口だ。ネイティブが JS に危険なメソッドを公開していれば、ローカルファイル読み取り/権限外アクセスになり得る。方向転換:H5 のリバースエンジニアリングは、静的解析で難読化 JS を読むよりブラウザデバッグ(動的)を優先し、JS Bridge の権限外アクセスの面を個別に評価する。

### Flutter アプリの特別な扱い
**Q1**: 逆コンパイルすると Flutter アプリと分かり、jadx には業務ロジックがほぼなく、すべて `libapp.so` 内にある。どうする?
**A1**: Flutter の特殊性を認識する。業務ロジックは `libapp.so`(Dart AOT)にコンパイルされ、標準の IDA には Dart 構造の認識がなく、SSL も自前の BoringSSL を通るためシステム証明書を認めない。戦略の優先順位:(1) キャプチャは flutter 専用の pinning バイパス(reFlutter の再パッケージ化、または BoringSSL の `ssl_verify_peer_cert` の hook)。(2) 静的解析では `reFlutter`/`Doldrums`/`blutter` で Dart クラス構造を復元する。判定基準:Flutter は通常の so を逆解析する発想ではなく、Dart 専用のツールチェーンを使う。
**Q2**: reFlutter で再パッケージ化した後、インストールできない(署名衝突)か起動しない。どう切り替える?
**A2**: 再パッケージ化の失敗は、多くの場合署名検証か完全性検証が原因。方向転換:(1) 再パッケージ化せず、対象プロセスの BoringSSL 関数オフセットを直接 frida hook する(先に so 内でオフセットを特定する必要がある)。(2) API だけ欲しくてアルゴリズムが不要なら、pinning のない旧バージョンやデグレード環境で App を動かす。(3) tun レイヤのキャプチャと証明書注入を組み合わせる。方向転換の核心:Flutter のキャプチャが詰まったら、「再パッケージ化」から「ランタイムでの so オフセット hook」に切り替える。

### プロテクトのパッカーのアンパック判断
**Q1**: 主流のプロテクトのパッカーと確認し、本物の dex が暗号化されている。アンパックすべきか?どの方式を使う?
**A1**: まず「アンパックする価値があるか」を確認する(前述のトリアージ)。価値があれば、方式を環境に応じて選ぶ。(1) root/frida 環境があるなら、frida-dexdump または FRIDA-DEXDump によるメモリのアンパック。汎用性が高い。(2) カスタム rom/hook フレームワークがあるなら、Xposed 系のアンパックプラグイン(各種 dump ツールなど)。(3) 全体プロテクトはメモリ dump でよいが、関数抽出型(vmp/抽出)のプロテクトはより難しく、能動的な呼び出しによる復元が必要。判定基準:まず「全体プロテクト」(メモリ全体を dump すればよい)か「関数抽出/vmp」(メソッドごとに復元が必要)かを区別する。両者の難易度は大きく異なる。
**Q2**: アンパック後に dump した dex を開くと、メソッド本体がすべて nop で、ロジックが抜き取られている。これは何を意味し、どうするか?
**A2**: これは「関数抽出型/vmp のプロテクト」。メモリ dump ではパッカーしか得られず、本当の命令は実行時に回填されるか native でインタープリタ実行される。対処:(1) 「能動的呼び出し」型のアンパックを使う(各メソッドを走査してトリガーし、回填されてから dump する)。(2) vmp 型は静的にほぼ手が出ないので、純粋な動的解析に切り替える。frida でキーとなる native メソッドを hook して入出力を得て、ブラックボックスで再現する。方向転換:抽出/vmp が静的解析を遮るときは、ブラックボックスの動的解析に徹底的に切り替え、「完全なコードの復元」という執念を捨てて、対象データの取得だけを目指す。

### frida が接続できない / アンチデバッグに検知される
**Q1**: frida で動的解析したいが、App が起動するや否やクラッシュする。アンチデバッグ/アンチ frida を疑う。どう特定して回避する?
**A1**: まずクラッシュが frida 検知によるものか確認する。frida を起動しないときは App が正常で、attach した途端に落ちるなら、ほぼ確定。よくある検知点:プロセス内の `frida`/`gum-js-loop` スレッド名の走査、ポート 27042 の走査、`/proc/self/maps` 内の frida so の検知、ptrace によるアンチデバッグ。対処:(1) attach ではなく spawn モードを使い、早期に注入する。(2) frida-server のデフォルトポートと特徴名を変える。(3) magisk の隠蔽(denylist)+ アンチアンチデバッグスクリプトで検知関数を hook して無効化する。判定基準:まず「attach したときだけ落ちる」を見て検知と確認し、それから狙って隠蔽する。
**Q2**: 特徴をすべて隠してもなお検知される(検知ロジックが native/カーネルモードにある)。frida 方針が通らない。どう切り替える?
**A2**: frida に固執しない。直交する方式:(1) 動的フレームワークを替える。Xposed/LSPosed 系(hook レイヤが異なり、検知点も異なる)または ptrace 系デバッガを使う。(2) 静的解析に替える。ブラックボックスが封じられたなら、IDA に戻って静的にアルゴリズムを逆解析する(大変だが確実)。(3) シミュレーション実行(unicorn/qiling)でクリーンな環境で対象関数を動かす。本物の App プロセスに触れなければ、すべてのランタイム検知を回避できる。方向転換:ランタイム検知が厳しすぎるときは、「App を動かさない」静的解析/シミュレーション実行の次元に退く。

### API を取得した後、どうサーバー側を攻めるか
**Q1**: すでに API の URL を一通り抽出した。次はクライアントのロジックをさらに逆解析するか、サーバー側を攻めるか。どう判断する?
**A1**: サーバー側へ移る。クライアントのリバースエンジニアリングの最終的な価値はサーバー側にある。API を得たらすぐに行う:(1) App を離れて curl/repeater で API に直接リクエストし、認証が必要か、パラメータ検証が緩いかを確認する。(2) 認証のない API を探す(多くの内部/テスト API は無防備)。(3) 一般的な Web 脆弱性(未認可、権限外アクセスの IDOR、インジェクション)を試す。判定基準:クライアントは「API 発見ツール」に過ぎず、本当の成果はサーバー側 API の認証とロジックの脆弱性にある。
**Q2**: API がすべて署名パラメータ(sign/token)を要求し、App を離れた直接リクエストはすべて拒否される。どうする?
**A2**: これは「API 署名/リプレイ対策」。回避には 2 つの道がある。(1) 署名アルゴリズムを逆解析して(前述の native/so のリバースエンジニアリングはこのため)、オフラインで署名を生成する。(2) アルゴリズムを逆解析せず、frida で App 内の署名関数を能動的に呼び出して「署名オラクル」にする。`sign()` メソッドを hook し、自分でパラメータを与えて App に署名を計算させる。方向転換:署名が壁になるときは、アルゴリズムを無理に逆解析するより「App を署名マシンにする」(frida の能動的呼び出し)を優先する。省力で正確だ。

### ハードコードされた鍵の実際の悪用価値の評価
**Q1**: App からクラウドストレージ/SMS/プッシュの AK/SK を掘り出した。喜ぶ前に、その実際の破壊力をどう評価する?
**A1**: 3 点を評価する。(1) 権限の範囲。特定の bucket のみ読み取りか、それともアカウントレベルの全権限か。クラウド SDK の key は権限差が極めて大きい。(2) App を離れて使えるか。対応するクラウド SDK/API でこの key の組を直接呼び出し、通って初めて本物とみなせる。(3) 影響範囲。SMS の key は SMS を送信でき(不正利益/フィッシング)、ストレージの key は他人のファイルの読み書き/削除ができる(データ漏えい/改ざん)、プッシュの key は一斉送信できる。判定基準:鍵の価値 = 権限 × 悪用可能性。取得したら、無害な読み取り専用 API を 1 つ呼んで有効性を検証してみる。
**Q2**: この key を呼んでみると権限不足または失効と返る。無駄だったのか?
**A2**: 必ずしもそうではない。失効/権限低下した key にも情報価値がある。(1) バックエンドがどのクラウド、どのサービスを使っているかが露呈し、インフラを描ける。(2) 同じ App 内には多くの場合複数セットの key(テスト/本番、複数環境)があり、引き続き調べる。(3) key の命名とコメントが内部の命名規則や運用習慣を漏らすことがある。方向転換:単一の key が失効したときは、それを「直接の認証情報」ではなく「インフラ情報」として扱い、同種の key を横方向に探す。

### 複数環境/テスト API の発掘
**Q1**: 本番 API はすべて厳密な認証がある。突破口を探したい。正面から無理に攻める以外に、どの角度があるか?
**A1**: 「テスト/ステージング/内部環境」を探す。App コードにはよく残っている:テストドメイン(`test.`/`dev.`/`uat.`/`pre.` プレフィックス)、debug スイッチ、イントラネットアドレス、コメントアウトされた旧 API。これらの環境は往々にして認証が緩く、デバッグ API があり、イントラネットにまで繋がっている。判定基準:開発者は本番環境には鍵をかけるが、テスト環境には鍵をかけ忘れることが多い。そしてテスト環境の URL はクライアント内にはっきり書かれている。
**Q2**: テストドメインを見つけたが外部からアクセスできない(名前解決できないか接続拒否)。手がかりは途切れたか?
**A2**: 途切れていない。むしろ良いシグナルで、イントラネットのアセットであることを示す。このドメイン/IP を記録する。それは「外から内へ」の対象の 1 つだ。(1) 後で VPN/イントラネットの足がかりを得られたら、これは横展開の対象になる。(2) 対外的な境界露出がないか試す(テスト環境がパブリックネットワークに繋がっているのに DNS を作っていないことがある)。(3) サブドメイン/類似ドメインの列挙で、同じグループの未防御アセットがよく掘り出せる。方向転換:イントラネットのテストドメインにアクセスできないときは、それをイントラネット横展開の対象として記録し、同源アセットの列挙を行う。

### サードパーティ SDK がもたらす連鎖的な攻撃面
**Q1**: リバースエンジニアリング中に App が多数のサードパーティ SDK を統合しているのを見つけた。業務 API のほかに、これらの SDK 自体は攻撃面になるか?
**A1**: なり得るし、しかも無視されがち。注目する:(1) SDK 自身の key/設定(計測、地図、決済、カスタマーサポートの SDK はそれぞれ key を持つ)。(2) 既知の CVE がある旧バージョン SDK(古い画像ライブラリ、ネットワークライブラリ、H5 コンテナには RCE/任意読み取りがある)。(3) SDK が公開する exported コンポーネントや deeplink。判定基準:App の自社コードは厳格でも、組み込まれたサードパーティ SDK は玉石混交で、「サプライチェーン側」の弱点になる。
**Q2**: ある SDK バージョンに既知の脆弱性があるかをどう素早く判断する?
**A2**: バージョン番号を特定し(SDK のパッケージ名パス、`BuildConfig`、リソース内の version 文字列)、公開の脆弱性データベース/その SDK のセキュリティアドバイザリを調べる。既知の CVE にヒットすれば、既製の PoC を再利用できる。方向転換:自社ロジックが読めないときは、「コンポーネント/依存関係のバージョン」の次元に移り、公開脆弱性でサードパーティ SDK を攻める。自社コードを逆解析するより省力なことが多い。

### exported コンポーネントとローカル攻撃面
**Q1**: 対象は API の抽出だけでなく、App 自体のローカル脆弱性も探したい。どこから切り込む?
**A1**: `AndroidManifest.xml` のコンポーネント権限から入る。`exported=true`(または intent-filter による暗黙的エクスポート)の Activity/Service/Provider/Receiver をすべて列挙する。特に `ContentProvider`(任意ファイル読み取りの可能性)、`WebView を担う Activity`(deeplink で開かれて任意 URL を読み込む可能性)。判定基準:exported コンポーネントは他の App(または攻撃者)が直接到達できる入り口で、ローカル権限昇格/データ漏えいの定番の面だ。
**Q2**: exported なコンポーネントを見つけたが、どう呼び出しを構成してトリガーすればいいか分からず詰まっている。どうする?
**A2**: `adb` で intent を直接構成してトリガーする(`am start`/`am startservice`/`content query`)。パラメータを試行する。deeplink 型は `am start -d "scheme://..."` で攻める。どの extra を受け取るか、その extra をどう使うか(ファイルパスとして、URL として、SQL 連結として使っていないか)を見る。方向転換:静的解析でコンポーネントのロジックが読めないときは、adb で動的に呼び出しを構成して実測し、入力をブラックボックス fuzz する。

### deeplink / URL scheme の悪用
**Q1**: App がカスタム URL scheme を登録している。これは遷移以外にどう使える?
**A1**: deeplink は「外部から制御可能に App を駆動する」経路だ。パラメータがどう処理されるかを重点的に見る。(1) パラメータを直接 WebView に渡していないか(→ 任意 URL/XSS/ローカルファイルのオープン)。(2) API パラメータとして透過的に渡していないか(→ 権限外アクセス/リダイレクト)。(3) 機微な操作(送金、認可、友達追加)を二次確認なしでトリガーしていないか(→ ワンクリックフィッシング)。判定基準:ウェブページ内の 1 つのリンクで静かにトリガーできる機微な能力は、高価値な deeplink 脆弱性だ。
**Q2**: deeplink のパラメータで WebView の URL を制御できそうだが、ドメインのホワイトリスト検証があり回避できない。どうする?
**A2**: ホワイトリスト検証のロジック自体を攻める。よくある欠陥:部分文字列マッチ(`indexOf("target.com")` は `target.com.evil.com` で回避できる)、host のみ検証して scheme を検証しない、大文字小文字/エンコードの回避、`@` による難読化。検証関数を逆解析し、その実装上の欠陥に対して構成する。方向転換:ホワイトリストが壁になるときは、無理に突破せず「検証ロジックの実装上の不備」を審査する。URL 解析系の検証にはほぼ必ず回避の角度がある。

### ローカルストレージの機微データ
**Q1**: API と鍵のほかに、App がローカルに保存している掘る価値のあるものは何か。どこで探す?
**A1**: ランタイムに設置された機微データを探す。`/data/data/パッケージ名/` 配下の `shared_prefs`(token/ユーザー情報/スイッチが平文で保存されることが多い)、`databases`(sqlite、チャット/キャッシュ/認証情報を保存しうる)、`files`、キャッシュディレクトリ。アクセスには root または `run-as`(debuggable アプリ)が必要。判定基準:コード内にあるのは「ロジック」、ローカルストレージにあるのは「実際に実行された後の認証情報とデータ」で、直接再利用できるログイン状態の token を含むことが多い。
**Q2**: App がローカルデータを暗号化して保存している(sp/db がすべて暗号文)。どうする?
**A2**: 鍵はクライアントにある(ホワイトボックス)。(1) ローカル暗号化の key とアルゴリズムを逆解析する(よくあるのは SQLCipher、自社 AES)。多くは key もハードコードしているか、予測可能な因子(デバイス番号+ソルト)から派生している。(2) より省力なのは、frida でデータが「復号された後/書き込まれる前」の瞬間を hook し、平文を直接得ること。暗号化アルゴリズムには触れない。方向転換:ローカルデータが暗号化されているときは、暗号化アルゴリズムを逆解析するより、平文が通過するメモリ上の地点を優先して hook する。

### ログイン状態の token の取得と再利用
**Q1**: 被害者のログイン状態で API を直接呼びたい。App 側から再利用可能な token をどう得るか?
**A1**: いくつかの出どころがある。(1) キャプチャでログイン後のリクエストヘッダー/cookie 内の token を見る(最も直接的)。(2) ローカルの `shared_prefs`/db に保存された永続化 token。(3) frida で token の生成/読み取り関数を hook する。取得後、App を離れて token で直接リクエストし、サーバー側が token だけを認めてデバイスフィンガープリントを認めないかを検証する。判定基準:token にバインディング(デバイス/IP)がなければ異地で再利用でき、権限外アクセス/セッションハイジャックの面が成立する。
**Q2**: token の再利用でサーバー側が「デバイス不一致/再ログインが必要」と返す。デバイスバインディングがある。どうする?
**A2**: バインディング因子を分析する。リクエスト内に token のほかに何が含まれるか(デバイスフィンガープリント、タイムスタンプ署名、did)。これらの因子もクライアントで生成されるので、同じく逆解析/hook 可能。デバイスフィンガープリントを一緒に複製するか、frida でこれらの因子を生成する関数を能動的に呼び出す。方向転換:token にデバイスバインディングがあるときは、「バインディング因子の生成ロジック」もリバースエンジニアリングの範囲に含めるか、App をオラクルとしてその場で計算させる。

### リクエストボディが暗号化された API
**Q1**: キャプチャでリクエストボディもレスポンスボディも暗号文。API はあるが、何を送るか分からない。どう突破する?
**A1**: まず暗号化の位置と種別を判断する。body 全体の暗号化か、フィールド単位か。暗号化・復号の地点を特定する。(1) キャプチャツールで暗号文の形式を見て(base64?)、コードに戻って関連する呼び出しを検索する。(2) 最も速いのは、frida でネットワークライブラリの send/receive の前後、または暗号化関数を hook し、「暗号化前/復号後」の平文を直接得ること。判定基準:クライアントが暗号化できるなら必ずローカルで復号できる。平文は必ずメモリ上に現れる。その瞬間を hook する。
**Q2**: 暗号化関数を hook できたが、App を離れて自分で暗号化リクエストを構成して fuzz/リプレイしたい。どうする?
**A2**: 2 つの実現方法がある。(1) アルゴリズムと key を逆解析し、自分のスクリプトで暗号化・復号を実装して、完全に App から離れる。(2) frida RPC で App の暗号化・復号関数をリモート呼び出し可能なサービスとして公開し、自分のスクリプトから App を呼んで暗号化・復号させる(App を暗号化マシンにする)。後者の方がはるかに速く、アルゴリズムが複雑でも問題ない。方向転換:リクエスト暗号化がリプレイを塞ぐとき、App を「暗号化・復号 RPC サービス」として包むのが最も実戦的な回避法だ。

### バージョン差 — 旧バージョン APK の価値
**Q1**: 最新版 App はプロテクトが厳しく、pinning が強力で、アンチデバッグが揃っており、リバースエンジニアリングが一歩も進まない。ほかに手はあるか?
**A1**: 旧バージョンの APK を探す。旧バージョンは往々にして:プロテクトがないか弱い、pinning がない、debug が無効化されていない、API と鍵が平文。サードパーティの APK サイト/履歴バックアップ/自分の旧デバイスから履歴バージョンを入手する。旧バージョンで API リスト、アルゴリズム、鍵を抽出すれば、高い確率で新版のバックエンドもこれらの API にまだ対応している。判定基準:セキュリティプロテクトは段階的に加えられるもので、履歴バージョンは「同じバックエンドの低防御ミラー」だ。
**Q2**: 旧バージョンで抽出した API/鍵を、新版のサーバー側はまだ認めるか?旧バージョンで掘る価値があるかをどう判断する?
**A2**: 旧 API を直接新しいバックエンドに当てて検証する。バックエンドは旧クライアントとの互換性のために旧 API をめったに廃止せず、署名アルゴリズムも長年変わらない。鍵がサーバー側設定の類なら、新旧共用の確率が高い。方向転換:新版のリバースエンジニアリングが詰まったら、「バージョンの時間軸」の次元に退き、防御が最も弱い履歴バージョンで逆解析して、その結果を現在のバックエンドに当てる。

### 逆コンパイル生成物の信頼性が疑わしい場合
**Q1**: 逆コンパイルしたコードのロジックが怪しい(dex2jar が間違う可能性)。それに従ってアルゴリズムを再現しても必ず一致しない。どう切り分ける?
**A1**: 単一のデコンパイラを信じない。dex2jar/jadx は複雑なバイトコードで誤った Java 逆コンパイルを生み出す(特に try-catch、ジェネリクス、lambda)。クロス検証:同じメソッドを jadx、CFR、smali の 3 つで照合し、smali(バイトコードに最も近く、ほぼ間違わない)を基準にする。判定基準:アルゴリズムの再現が一致しないときは、まず自分のロジックの誤りではなくデコンパイラの翻訳ミスを疑う。
**Q2**: smali を基準にしても再現が合わない。どこに問題がありうるか?
**A2**: ブラックボックス検証に移る。静的にこだわるより、frida で対象関数を hook し、既知の入力を与えて実際の出力を得て、この「入出力の対」で逆に自分の実装を検証/較正する。ランタイムの真値が唯一の審判だ。方向転換:静的再現が何度やっても合わないときは、動的解析で真値を取得してテストケースとし、正しい実装に近づける。

### 時間予算と諦めの判断
**Q1**: 強プロテクト+vmp+native 署名の App の逆解析に長く時間を費やしている。続行すべきか、損切りして切り替えるべきか、どう判断する?
**A1**: 対象そのものに立ち返り「自分は結局何が欲しいのか」を問う。最終目的がサーバー側を攻めることで、API リストがすでにキャプチャ/旧バージョンで得られているなら、vmp 内のアルゴリズムは「オフラインで署名を大量に構成する必要がある」ときだけ必要だ。frida を署名オラクルとして使って要件を満たせるなら、vmp を逆解析する必要はない。判定基準:逆解析の深さは攻撃対象に奉仕すべきで、逆解析のための逆解析ではない。より軽い手段で同じ効果を達成できるなら損切りする。
**Q2**: 確かにオフラインで大量の署名が必要で、frida オラクルのスループットが足りず、vmp も逆解析できない。どうする?
**A2**: エンジニアリング化したブラックボックスに移る。(1) 複数の App インスタンス/複数デバイスで frida オラクルを並列実行してスループットを上げる。(2) unicorn/qiling で署名用の so を単独で取り出してシミュレーション実行し、vmp のランタイム保護を回避しつつアルゴリズムを理解する必要もなくす。(3) 極端な場合はクラウド実機ファームで大量処理する。方向転換:アルゴリズムが逆解析できず量産が必要なときは、「アルゴリズムの理解」から「ブラックボックスのスケール化呼び出し」(マルチインスタンス オラクル/so シミュレーション実行)に移る。

### ソースなし App(インストール済みアプリのみで、apk が入手できない)
**Q1**: 対象 App がデバイスにインストールされているが、ストアで入手できず、apk ファイルもない。リバースエンジニアリング可能なパッケージをどう得る?
**A1**: デバイスから抽出する。`adb shell pm path パッケージ名` で apk のデバイス上のパスを取得し、`adb pull` で取り出す。分割アプリ(split apk)は base とすべての split を一緒に取り出す。root なしでも通常のアプリに対して可能。判定基準:インストールされている限り、必ず `/data/app/` または `pm path` からインストールパッケージを取り出せる。
**Q2**: 取り出したのはデバイスから抽出したもので、システムにより最適化済み(oat/vdex など)かもしれず、分割パッケージが不完全で逆解析がエラーになるかもしれない。どうする?
**A2**: 分割パッケージが不完全だと逆コンパイルでクラスが欠ける。必ず `base.apk` + すべての `split_*.apk` を揃え、apks に統合するか jadx に一緒に読み込ませる。vdex/odex の最適化生成物に当たったら、`vdexExtractor`/`baksmali deodex` で dex を復元する。方向転換:デバイス抽出のパッケージで問題が出たら、まず「分割パッケージを揃えたか」と「deodex 復元」を確認してから、通常のリバースエンジニアリングのフローに入る。

### リクエスト署名のリプレイとリプレイ対策
**Q1**: API を呼べるようになったが、タイムスタンプ+nonce+署名でリプレイ対策がなされ、旧パケットのリプレイは直接拒否される。どう突破して大量テストする?
**A1**: 署名ロジックがクライアントで制御可能なら、リプレイ対策は有名無実になる。毎回のリクエスト前に frida オラクルまたはローカルで再現したアルゴリズムで、「現在のタイムスタンプ+新しい nonce」から正当な署名をリアルタイム生成すれば、無限に新規リクエストを送れる。判定基準:リプレイ対策はサーバー側の時間窓と nonce の一意性の検証に依存するが、正当な署名をリアルタイム生成できる限り、常に時間窓内で nonce も常に新しい。
**Q2**: サーバー側の nonce がさらにグローバル一意かつサーバー側記録を要求するか、時間窓が極端に短く、大量処理時に偶発的に失敗する。どうする?
**A2**: エンジニアリングで処理する。クライアントが毎回ランダムな nonce を生成するので衝突確率は極めて低く、失敗時は再試行すればよい。時間窓が短ければ、署名生成からリクエスト送信までの経路を低遅延にする(ローカルでアルゴリズムを再現し、frida の往復を避ける)。サーバー側が同じアカウントに頻度制限をかけるなら、複数アカウントのローテーションに移る。方向転換:リプレイ対策のエンジニアリング上の細部が量産を塞ぐときは、「ローカルのリアルタイム署名+複数アカウント/複数 nonce のローテーション」で解決し、検証の回避にこだわらない。

### 難読化された文字列/鍵のランタイム復元
**Q1**: コード内の鍵は平文ではなく、多数の XOR/復号関数がランタイムに組み立てるもので、静的に検索できない。どう真値を得る?
**A1**: 各復号呼び出しを静的に復元しない(大変で間違えやすい)。ランタイムに復号されて真値になるなら、直接動的に取得する。frida でその「文字列復号関数」を hook し、すべての入力と出力を表示すれば、1 回の実行で App 全体の隠し文字列(鍵、URL、アルゴリズムパラメータ)を全部 dump できる。判定基準:文字列暗号化は静的走査だけを防ぐもので、ランタイムに復号の出口を hook するこの手は防げない。
**Q2**: 復号関数がインライン化/分散されて多くの場所にあり、統一された出口がなく hook できない。どうする?
**A2**: hook の階層を変える。より低レイヤの汎用ポイントを hook する。`String` の構築、`new byte[]`→`String`、あるいは暗号化・復号 API(`Cipher.doFinal`)の戻り値など。復号された平文はすべてこれらの低レイヤを通過するので、広く網を張れば必ず収穫がある。または frida のメモリ検索で、少し動かしてからヒープ内の特徴を探す。方向転換:集中した復号の出口がないときは、hook 点を言語/システムの低レイヤの共通 API に沈めるか、メモリスキャンに移る。

### App のリバースエンジニアリングからイントラネット入り口への接続
**Q1**: App のリバースエンジニアリングの成果(API、イントラネットドメイン、認証情報)を「イントラネットに侵入する」完全なチェーンにどう結びつけるか。断片的な情報にしないために?
**A1**: アセットと認証情報を集約・整理する。(1) すべてのイントラネット/テストドメイン → イントラネット対象リスト。(2) すべてのハードコードされた認証情報(db のアカウント・パスワード、クラウド key、api token)→ 認証情報庫。適用システムを注記する。(3) RCE/任意読み取りのある API → 直接の足がかり候補。これらを「どの認証情報がどの扉を開くか」にマッピングする。判定基準:App は「外側の情報の鉱脈」で、リバースエンジニアリングの終着点は「イントラネットに通じる認証情報-アセットマップ」を生み出すことだ。
**Q2**: 手元に認証情報と API が多数あるが、すべて断片的で、どれが本当に突破口を開けるか分からない。どれから先に攻める?
**A2**: 「直接到達度」で並べ替えて攻める。まず認証なし/弱い認証で危険な機能を持つ API を攻める(直接 RCE/ファイル読み取りの可能性)。次にハードコードされた db/サービスのアカウント・パスワードで直接接続できるか試す(データベース、管理画面、クラウドコンソール)。最後に横展開の布石が必要なもの。どれか 1 つ当たれば足がかりができ、その足がかりからイントラネットドメインを見返す。方向転換:情報過多のときは、「この認証情報/API が一歩で実行または読み取り能力を得られるか」で並べ替え、全面展開ではなく単点突破する。

### 署名検証 / 完全性検証が再パッケージ化を阻む
**Q1**: apktool で再パッケージ化して計装したい(コード変更、pinning 無効化、ログ追加)が、変更後にインストールすると App が直接クラッシュするか改ざんを警告される。どうする?
**A1**: これは署名検証(APK signature/completeness check)が働いている。まず検証点を特定する。App は起動初期に自身の署名(`getPackageInfo`/`signatures`)を読み、内蔵値と照合する。対処:(1) frida で署名取得関数を hook し、元の署名を返させる(動的回避、パッケージを変更しない)。(2) 内蔵の期待署名値を逆解析し、再パッケージ化後に照合ロジックを patch して無効化する。判定基準:再パッケージ化が阻まれたときは、hook による署名検証の回避を優先し、完全性検証との正面衝突を避ける。
**Q2**: 検証が native レイヤにあり、冗長な検証が複数箇所にあって、1 つ通しても別の場所でクラッシュする。どう切り替える?
**A2**: 再パッケージ化の道を諦め、「パッケージを変更しない」動的注入に移る。frida/LSPosed でランタイムに対象ロジックを直接 hook し、APK ファイルにはまったく触れない。すると署名検証も完全性検証も発動しない。方向転換:多重の完全性検証が再パッケージ化を封じたときは、「パッケージ変更」から「ランタイム hook」に完全に切り替え、すべての静的改ざん検知を回避する。

### root/環境検知が動的解析を阻む
**Q1**: デバイスは root 済みで、frida/キャプチャを動かしたいが、App が root 環境を検知して直接終了するか機能を制限する。どうする?
**A1**: root 検知のよくある手段:`su` ファイルの確認、`which su`、magisk のパッケージ名/パスの検知、`ro.debuggable`/`ro.secure` の検知、マウントポイントの異常。対処の優先順位:(1) magisk の denylist/隠蔽モジュール(Shamiko など)で対象パッケージに root を隠す。(2) frida で root 検知関数を hook して無効化する(`su`/`superuser`/`magisk` の文字列で特定)。(3) 疑わしいデバッグ属性を無効化する。判定基準:まず magisk の隠蔽という「システムレベルの方式」を使い、大半の検知をカバーする。
**Q2**: root を隠してもなお検知される(SafetyNet/Play Integrity または自社の強力な検知を使っている)。動的環境を構築できない。どう切り替える?
**A2**: レーンを替える。(1) root していない実機+非侵襲の手段を使う。ベンダーの debuggable バージョンや、キャプチャのみ(プロセス注入ではなくネットワークレイヤの pinning 回避を併用)。(2) 制御可能なカスタムエミュレータ/rom を使う。(3) いっそ純粋な静的リバースエンジニアリングに切り替え、動的環境に入らない。方向転換:強い環境検知が動的解析を封じたときは、「root なし実機でのキャプチャ」または「純粋な静的解析」という、検知を発動させない 2 つの次元に退く。

### ミニプログラム/RN/Cordova のようなクロスプラットフォームコンテナの API 抽出
**Q1**: リバースエンジニアリングで、App のコアがクロスプラットフォームコンテナ(ミニプログラムカーネル/RN/Cordova)で、ネイティブはただのパッカー、API ロジックはパッケージされたスクリプト内にあると分かった。どう抽出する?
**A1**: 「ロジックは dex ではなくスクリプトパッケージ内にある」と認識する。スクリプトリソースを特定する。RN なら `index.android.bundle`、Cordova なら `assets/www/`、ミニプログラムなら対応するパッケージファイルを探す。スクリプトを dump し、整形/解包すれば、中には完全な API 呼び出し、パラメータ組み立て、さらには鍵がある。判定基準:クロスプラットフォームコンテナは業務ロジックをネイティブから JS/スクリプトレイヤに移しており、リバースエンジニアリングの重心もスクリプトリソースに移る。
**Q2**: スクリプトパッケージが暗号化されているか、独自のパッケージ形式で解けない。どうする?
**A2**: 2 つの道がある。(1) 動的。コンテナがスクリプトをメモリに読み込んだ後、メモリを hook して平文スクリプトを得る(暗号化パッケージはランタイムに必ず復号される)。またはコンテナの JS エンジンを直接リモートデバッグする(RN の debug チャネルなど)。(2) ローダーのコードを探し、解包/復号ロジックを逆解析する。方向転換:スクリプトパッケージが静的に解けないときは、「コンテナのランタイム」に移り、スクリプトがエンジンに実行される前のメモリで平文を截る。

### 非 HTTP プロトコル / protobuf バイナリ API
**Q1**: キャプチャでトラフィックが JSON ではなくバイナリ(protobuf/独自 TLV)と分かった。フィールドが読めない。API をどう解析する?
**A1**: まず protobuf かどうかを識別する(特徴:フィールド番号+wire type のコンパクトな符号化)。構造を得る道は 2 つある。(1) リバースエンジニアリングで `.proto` が生成したクラスを探す。protobuf ランタイム(`GeneratedMessage`/`parseFrom`/フィールド番号)を検索し、逆コンパイルした message クラスからフィールド定義を直接得る。(2) protobuf のブラインド解析ツール(protobuf-inspector など)でバイナリをフィールド番号+値の木に分解し、意味と突き合わせて推測する。判定基準:protobuf API の「schema」はクライアントのクラス内にあり、推測不要で、message 定義を逆解析すれば構造化できる。
**Q2**: 完全に独自のバイナリプロトコル(自社 TLV/長接続)で、既製のパーサがない。どうする?
**A2**: 「符号化・復号化の地点」に戻ってブラックボックスを行う。frida でシリアライズ(パッケージ送信前)とデシリアライズ(受信後解析前)の関数を hook し、「構造化オブジェクト ↔ バイナリ」の対応関係を得る。プロトコル形式を理解しなくても読み書きできる。App を離れて構成するなら、App の符号化・復号化関数を RPC サービスとして使う。方向転換:独自バイナリプロトコルが読めないときは、形式を逆解析せず符号化・復号化の両端を hook し、バイト状態ではなくオブジェクト状態を得る。

### クライアント証明書 / mTLS 双方向認証
**Q1**: キャプチャ時にハンドシェイクで失敗し、サーバー側がクライアント証明書(mTLS)を要求することが分かった。通常のプロキシを挟めない。どう突破する?
**A1**: クライアント証明書は必ず App 内にパッケージされている(ホワイトボックス)。それを特定する。`assets`/`res/raw` 内の `.p12`/`.pfx`/`.bks`/`.jks` 証明書ファイルと、コード内で KeyStore を読み込む箇所(`KeyStore`/`SSLContext`/`.p12`/`loadKeyStore` を検索)を探す。証明書ファイルとその読み込みパスワード(パスワードは近くにハードコードされていることが多い)を得て、クライアント証明書をキャプチャプロキシにインポートすれば、双方向ハンドシェイクのキャプチャができる。判定基準:mTLS の秘密鍵はクライアントにあり、証明書+パスワードを逆解析できればクライアントになりすませる。
**Q2**: 証明書が native レイヤにあり、ハードウェアキーストア(エクスポート不可)を使っていて、ファイルが取得できない。どうする?
**A2**: 「証明書のエクスポート」という執念を捨てる。(1) frida で `SSLContext`/`TrustManager`/`KeyManager` の初期化を hook するか、暗号化の送受信点を直接 hook して、アプリケーションレイヤで平文を得て、ハンドシェイクに触れない。(2) mitmproxy の上流証明書透過+frida でクライアント証明書検証と KeyManager をまとめて乗っ取る。方向転換:mTLS の秘密鍵がエクスポート不可のときは、「プロキシ側でハンドシェイクを再現する」から「App プロセス内で平文の送受信を hook する」に切り替え、TLS レイヤ全体を飛ばす。
