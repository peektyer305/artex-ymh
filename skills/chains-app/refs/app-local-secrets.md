# Appクライアント · クライアントのローカルストレージとハードコードの悪用

### APK/IPA を入手したら、まず偵察方針を分岐させる
**Q1**: 手元にインストールパッケージ(APK か IPA)を入手したばかり。限られた時間をまずどの道に使うべきか?
**A1**: まず「ゼロコストの静的振り分け」を行い、Frida を急がない。判定基準は投入産出比。①まずパッケージサイズとフレームワーク種別(ネイティブ Java/Kotlin、Flutter、React Native、Unity、Cordova/Ionic、Electron)を見る。フレームワークが以降のツールチェーンをまったく変える。②`strings`/`grep` で一巡して、むき出しの http(s) エンドポイント、AK/SK プレフィックス、`-----BEGIN`、`token=`、`Authorization` がないかを見る。③manifest/Info.plist でエクスポートコンポーネント、URL scheme、ネットワークセキュリティ設定を探す。3 分以内に、これが「鍵がそのまま assets に置かれている」軟対象か「プロテクト+pinning+アンチデバッグ」の硬対象かを判断できる。
**Q2**: 静的解析で一目では平文鍵が見えない。すぐ動的 hook に移るべきか?
**A2**: いや。まずパッケージがプロテクト/パッカー化されているか確認する(アンパックチェーン参照)。静的解析で結果がないのは 2 つの可能性。本当にないか、パッカーに隠されているか。まず `apktool`/`jadx` で逆コンパイルし、Application の入口が SDK パッカーの代理クラスか(`com.*.StubApp`、`ProxyApplication` のようなクラス名)、DEX 数が異常に少ないか、メソッド本体が native かを確認する。プロテクトを確認してから、アンパックか直接動的解析かを決める。やみくもに Frida を導入して時間を無駄にしない。
**Q3**: フレームワークが Flutter/Unity で、jadx がロジックを開けない場合はどうする?
**A3**: これは最もよくある「詰まったように見える」点。Flutter のロジックは `libapp.so`(AOT スナップショット、blutter/reFlutter が必要)、Unity は `libil2cpp.so`+`global-metadata.dat`(Il2CppDumper でシンボルを復元)。方向転換の次元:「Java レイヤを読む」から「native レイヤのシンボル復元を読む」に切り替える。またはいっそロジックの逆解析を諦め、ネットワークレイヤに移って挙動を観測する(その鍵は最終的に必ず送出される)。
**Q4**: この静的経路が全体的に失敗した。パッケージがプロテクト、native、文字列が全暗号化。どの直交する次元に移るべきか?
**A4**: 「ランタイム/ネットワーク境界」の次元に移る。クライアントがどれだけ隠しても、鍵は使用の瞬間に必ず平文でメモリとネットワークリクエストに現れる。バイトコードをがっつり読むのを諦め、①計装してランタイムメモリを取得、②キャプチャで実際に何を送るかを見る(pinning でも回避できる)、③設置されたローカルファイルを取得する(実行後の SharedPreferences/サンドボックスには平文がキャッシュされていることが多い)に変える。
**Q5**: 時間がない。1 つだけ選ぶなら、優先順位をどう付ける?
**A5**: 軟対象は静的 grep を優先(30 秒で成果が出る可能性)。硬対象は「実行後に設置ファイルを取得+キャプチャ」を優先。動的観測は逆解析・アンパックより速いからだ。逆解析・アンパックは最後の手段で、情報が最も網羅的だが最も時間がかかる。
**Q6**: 「この App を攻め続ける価値があるか」を判断する損切り線はどこか?
**A6**: 対象がサーバー側権限の取得なら、クライアントは入口に過ぎない。クライアントが使えるサーバー側の認証情報/エンドポイント/暗号化プロトコルをすでに渡してきたら、すぐサーバー側に移る。クライアントに何もなくプロテクトが極めて硬いなら、より割の合う入口(Web、API ゲートウェイ)があるか評価し、1 つのパッカー化 App に最後まで粘らない。

### 逆コンパイルツールチェーンの選定と失敗時の後退
**Q1**: Android パッケージを逆コンパイルする。jadx、apktool、ghidra のどれを先に使うべきか?
**A1**: 目的で選ぶ。Java レイヤのロジックを見る/文字列を検索するなら `jadx`(Java へ逆コンパイル、可読性が最高)。リソースを変更、smali を見る、再パッケージ化するなら `apktool`。native の `.so` 解析は `ghidra`/`IDA`。iOS は `class-dump`/`Hopper`/`ghidra` + 復号(frida-ios-dump)。デフォルトは jadx-gui から始め、グローバル検索が最も速い。
**Q2**: jadx が逆コンパイル不完全のエラー、大量の `// decompilation failed` を返す?
**A2**: 単一ツールに詰まらない。smali(`apktool d`)にダウングレードして生のバイトコードを読む。逆コンパイルが失敗しても smali は必ずある。または CFR/Procyon など他のデコンパイラに替えてクロス検証する。キーロジックは smali を命令ごとに読む。遅いが漏れない。
**Q3**: グローバル検索のキーワードはどの語根から入る?
**A3**: 鍵系:`secret`、`password`、`passwd`、`pwd`、`key`、`token`、`apikey`、`appkey`、`appsecret`、`aes`、`des`、`iv`、`salt`、`sign`。クラウドベンダーのプレフィックス:`AKIA`(AWS)、`LTAI`(アリババクラウド)、`AKID`(テンセントクラウド)。エンドポイント系:`http://`、`https://`、`.com/api`、`internal`、`test`、`dev`、`staging`。認証情報形式:Base64 の長い文字列、`eyJ`(JWT ヘッダー)、`-----BEGIN`。
**Q4**: 数百個の `key` がヒットし、ノイズが大きすぎる。どう絞る?
**A4**: 制約を加えて SN 比を下げる。①正規表現で固定長の十六進/Base64(32/16 桁で整う AES key など)を一致させる。②代入のコンテキストが `static final`(ハードコード定数)かを見る。③サードパーティライブラリのパス(`okhttp`、`gson`、`androidx`)を除外し、アプリ自身のパッケージ名だけを見る。④「暗号化関数/ネットワーク関数と同じクラスにある」定数を優先する。
**Q5**: ツールチェーンを全部使ってもロジックが読めない。この静的リバースエンジニアリングの道が失敗した。どこへ移る?
**A5**: 「静的リーディングの代わりに動的計装」に移る。アルゴリズムを理解しなくてよい。暗号化関数の入口を直接 hook して平文引数を表示し、ネットワーク関数を hook して平文リクエストボディを表示する。逆解析の目的は鍵/プロトコルを得ることで、動的解析は直接結果を出し、コードを読む知的コストを回避する。

### ハードコード鍵の検索:最も見落としやすい隠し場所
**Q1**: smali を grep しても鍵が見つからない。ハードコードがないということか?
**A1**: その結論は出せない。ハードコードにはコード以外の隠し場所が多く、見落とされがち。`assets/` 配下の config.json/*.properties/*.xml/証明書ファイル、`res/raw/`、`res/values/strings.xml`(`google_api_key`、`facebook_app_id` がよくある)、`AndroidManifest.xml` の `<meta-data>`、`resources.arsc`、Native `.so` の `.rodata` セグメント、さらには画像/フォント末尾のステガノグラフィ。1 つずつカバーする。
**Q2**: strings.xml と meta-data からは通常何を掘り出せる?
**A2**: サードパーティ SDK の公開だが機微な認証情報。地図 key、プッシュ appkey、統計 SDK の secret、`google_maps_key`、Firebase 設定(`google-services.json` はよく assets に直接入り、中に project id、api key、database url がある)。これらはサードパーティのクラウドバックエンドへ横展開できる。
**Q3**: 鍵が連結/XOR/Base64 エンコード後に保存され、grep で平文が見つからない?
**A3**: これは普通だ。コード内の「ある定数に変換を施して暗号化関数に渡す」パターンを見る。定数そのものが暗号文。手段:①エンコードされた定数を抜き出し、ローカルで復号ロジックを再現する。②または復号せず、変換関数の戻り値を直接動的に hook する。判定基準:変換が純粋にクライアントで再現可能なら、鍵は公開と同じだ。
**Q4**: `.so` 内の鍵はどう探す?
**A4**: まず `strings libxxx.so` で `.rodata` を走査する。見つからなければ ghidra で JNI エクスポート関数(`Java_com_xxx`)を特定し、それが参照する定数データを遡る。native は key をバイト配列に分割して分散初期化することが多い(anti-strings)。このとき静的解析は非常に苦しい。動的にその JNI 関数の戻り値を hook する方が速い。
**Q5**: すべての静的な隠し場所を探してもない。この「ハードコード」という仮定自体が間違っているかもしれない。どう移る?
**A5**: 「鍵はパッケージ内になく、ランタイムに配信/派生される」という仮定に移る。初回起動時にサーバー側から取得(初期化リクエストをキャプチャ)、デバイスフィンガープリントから派生(派生関数を hook)、リモート設定に存在、の可能性。このときの直交する切り替えは、「鍵を取得するあのネットワーク通信」か「鍵を派生するあの関数」を取得することで、パッケージ内を掘り続けない。
**Q6**: 旧バージョンに、新版で削除された鍵が隠れていることはないか?
**A6**: ある。「バージョン履歴の比較」の次元に移る。サードパーティ APK サイト/アプリストアのキャッシュから複数の履歴バージョンを取得し、strings と config を diff する。開発者はあるバージョンでハードコードを「修正」(平文を削除)することが多いが、旧版は依然ダウンロードでき、古い key はサーバー側がローテーションしていなければ今も有効。

### プロテクトのアンパックの判断とタイミング
**Q1**: プロテクトパッケージ(よくある商用プロテクトのパッカー)と確認した。アンパックすべきか?
**A1**: まずアンパックの必要性を問う。対象(エンドポイント、鍵、プロトコル)が動的 hook で得られるなら、アンパックしない。アンパックはコストが高く失敗しやすい。アンパックは「完全な業務ロジックを通読する/隠し分岐を探す/静的監査する」必要があるときだけ価値がある。判定基準:対象が「点的に鍵を取る」なら動的、「面的にコードを審査する」ならアンパック。
**Q2**: アンパックすると決めた。方法はどう選ぶ?
**A2**: 「ランタイムのメモリ dump」系の汎用アンパックを優先し、特定のパッカー版に狙いを定めない。Frida-DEXDump の類のツールで、App がメイン画面まで進んだ後、メモリから復号済み DEX を抜き出す。これはパッカーの復号アルゴリズムを逆解析するより 1 桁速い。ディスクへ書き出した後、baksmali で復元する。
**Q3**: DEXDump で抜き出した DEX が不完全/一部のクラスがランタイムに復号される?
**A3**: これは抽出パッカー(メソッド級抽出)の特徴で、DEX 構造はあるがメソッド本体がランタイムに埋められる。方向転換:「能動的呼び出し」または命令レベル dump(fart、youpk のような ART ベースの能動的呼び出し+ログの方式)を使い、全メソッドを走査してトリガーし、埋め込み完了後に dump する。または「キークラスだけ dump できた」で十分と割り切る。
**Q4**: アンパック環境がアンチデバッグ/アンチ Frida で、App が起動するとすぐクラッシュする?
**A4**: 先に検知を解決してからアンパックする(アンチデバッグ回避チェーン参照)。切り替えの選択:非注入方式(ART hook ベースの LSPosed 環境、または ROM/エミュレータの変更)、または unidbg で局所ロジックを純粋にシミュレーション実行して、App を本当には動かさない。
**Q5**: アンパックの道全体が何度も失敗する(パッカーが新しすぎ、環境対抗が強い)。どの直交する次元に移る?
**A5**: 「完全なコードを得る」という執念を完全に捨て、「ブラックボックスの挙動観測」に移る。欲しいのはコードではなく、その対外挙動。キャプチャでプロトコルを見る、単点関数を hook して鍵を得る、読み書きするローカルファイルを観察する。プロテクトが守るのはコードの可読性で、ランタイムの実際の挙動は守れない。可読性の次元から挙動の次元へ移る。

### SSL Pinning 回避のレイヤ別判断
**Q1**: キャプチャ時に App が証明書エラーで接続できない。pinning と判断するか?
**A1**: まずシステムがユーザー CA を信頼しない(Android 7+ のデフォルト)か、アプリケーションレイヤの pinning かを区別する。判定基準:システム級 CA(または magisk モジュールでユーザー CA を信頼)を導入してキャプチャできれば、単なる信頼問題。導入してもキャプチャできなければ、アプリケーションレイヤの pinning。いきなり pinning と仮定せず、まず networkSecurityConfig の信頼設定を除外する。
**Q2**: アプリケーションレイヤの pinning と確認した。まずどの回避を試す?
**A2**: コストの低い順に。①まず汎用 Frida スクリプト(frida-multiple-unpinning/objection の `android sslpinning disable`)を使う。OkHttp、TrustManager、ネイティブ SSLContext などの主要実装をカバーし、ワンクリック成功率が高い。②ダメなら具体的な pinning 実装(OkHttp CertificatePinner か、自前実装の X509TrustManager か、native BoringSSL か)を見て、狙って hook する。
**Q3**: 汎用スクリプトが無効。pinning が native レイヤ(Flutter/自社 .so など)にある?
**A3**: Flutter はシステムプロキシを通らず、pinning が BoringSSL にあり、汎用 Java hook が無効。方向転換:①native の `ssl_verify`/`SSL_CTX_set_custom_verify` を hook する(reFlutter または libflutter.so の patch)。②または iptables/proxy でトラフィック転送を強制 + so 内の検証戻り値を変更する。これは「Java レイヤ hook」から「native レイヤ patch」への直交する切り替えだ。
**Q4**: 双方向認証(クライアントも証明書を持つ mTLS)。サーバー側がクライアント証明書を要求する場合はどうする?
**A4**: パッケージからクライアント証明書を探す。`.p12`/`.pfx`/`.bks` はよく assets にハードコードされ、パスワードもコード内にハードコードされている。抽出してキャプチャツールにクライアント証明書としてインポートすれば、双方向ハンドシェイクを完了できる。これは「pinning 回避」問題を「ハードコード証明書の抽出」問題に変換する。
**Q5**: すべての hook/patch が失敗し、平文トラフィックをキャプチャできない。どこへ移る?
**A5**: 「ネットワーク経路上で復号する」ことを諦め、「アプリ内部で平文を取る」に移る。トラフィックは暗号化の前後に必ずメモリ/関数引数内で平文になる。暗号化関数(`doFinal`、`SSL_write` など)を hook して暗号化前の平文リクエストボディを得るか、業務レイヤのネットワークラップ関数(`Retrofit`/`OkHttp` の Request 構築)を直接 hook する。こうすれば TLS レイヤにまったく触れず、pinning がどれだけ強くても防げない。

### Root/ジェイルブレイク検知で App が起動を拒否する
**Q1**: 対象 App が自分の root 済みテスト機で直接クラッシュ/環境異常を表示する。どう特定する?
**A1**: まず root 検知か別のもの(署名/完全性)かを判定する。root 検知はよく以下を調べる。`su` バイナリのパス、`Superuser.apk`、`test-keys`、`ro.debuggable`、magisk の特徴、`/system` の書き込み可。まず logcat を取得して終了前のログを見るか、`System.exit`/`Process.killProcess` を hook して呼び出しスタックを遡り、検知点を特定する。
**Q2**: 検知関数を特定した。最も省力な回避は?
**A2**: 1 つずつ hook するのではなく、環境側の隠蔽を優先する。Magisk Hide/Zygisk + Shamiko/DenyList で root を隠し、LSPosed の HideMyApplist で疑わしいパッケージを隠す。環境レイヤで 1 回解決すれば多くの App を通せる。判定基準:汎用隠蔽で通るなら、狙った hook を書かない。
**Q3**: 環境隠蔽後もなお検知される(App の自己チェックが厄介)?
**A3**: 関数レベル hook に移る。objection の `android root disable` または Frida で具体的な検知メソッドを hook し、「root されていない」と返させる。検知が native にあるなら、`fopen`/`access`/`stat` の機微パスへの呼び出しを hook して失敗を返す。点ごとに排除する。
**Q4**: root 検知を完全に回避できず、しかも動的解析が必須。どこへ移る?
**A4**: 「root なし動的解析」の次元に移る。①frida-gadget の再パッケージ化注入(root 不要のデバイスで、gadget を App に組み込む)。②または unidbg で対象 .so 内のアルゴリズムをシミュレーション実行する(完全な App をそもそも起動しない)。③または非 root 実機 + root なしコンテナフレームワークに替える。検知回避の直交する解は「検知できる root 環境を与えない」ことだ。
**Q5**: 再パッケージ化注入まで署名検証に阻まれる(完全性チェーン参照)。動的解析が完全に阻まれた場合はどうする?
**A5**: 純粋な静的解析+局所シミュレーションに後退する。unidbg/qiling でキーアルゴリズム関数を単独で抜き出し、x86 上で動かし、入力を与えて出力を得る。実際の実行環境にまったく依存しない。これは「マシン全体の動的解析」から「関数級のシミュレーション」への次元削減だ。

### Frida hook の対象関数の選択
**Q1**: hook で鍵/平文を得たいが、どの関数を hook すればよいか分からない。どう特定する?
**A1**: やみくもに hook しない。まず範囲を狭める。①静的解析で jadx から暗号化/署名関連クラスを探し、`doFinal`、`getSignature`、`sign`、`encrypt` を特定する。②または objection/frida-trace のワイルドカードで一括 trace(`javax.crypto.Cipher.*`、`java.security.*`)し、まずどれが呼ばれるかを観測する。③ネットワークリクエストの特徴(ある暗号化ヘッダー)から、それを構成する関数を逆算する。
**Q2**: すべての暗号化呼び出しを一網打尽にしたい。どうする?
**A2**: 加解密の収束点を hook する。`javax.crypto.Cipher` の `init`(key/iv を得る)と `doFinal`(平文/暗号文の対を得る)、`Mac`(HMAC 署名)、`MessageDigest`。`Cipher.init` を一気に hook すれば、すべての AES/DES の key と iv を截獲でき、業務がどこで呼んでも構わない。
**Q3**: hook したが、関数が無数に呼ばれ、出力が画面を埋めてどれが対象か分からない?
**A3**: フィルタ条件を加える。呼び出しスタックで(`Thread.currentThread().getStackTrace()` を表示)、業務パッケージ名がトリガーしたものだけを残す。パラメータの特徴(暗号文の長さ/平文に対象キーワードを含む)でフィルタする。または対象操作(ログインをクリックなど)の前後のタイムスタンプ窓内の呼び出しを記録する。
**Q4**: 対象ロジックが native にあり、Java hook で得られない?
**A4**: native hook に移る。`Interceptor.attach` をエクスポートシンボル(`Module.getExportByName`)に張るか、未エクスポート関数はベース+オフセットで hook する。よく hook する native の収束点:`SSL_write`/`SSL_read`(TLS 平文を得る)、`memcpy`/`strcpy`(コピー中の鍵を得る)。
**Q5**: App にアンチ Frida があり、注入するとすぐクラッシュし、hook の道が通らない。どこへ移る?
**A5**: アンチデバッグチェーンを参照。まず検知を通す。どうしても通らないなら、直交する切り替えとして「オフラインシミュレーション」へ。unidbg で対象 .so を読み込み、自分で JNI 環境を実装して対象関数を呼び、アンチ Frida の干渉がないクリーンな環境で結果を得る。アンチ Frida が守るのは「実機への注入」で、「関数が別の場所へ移されて実行されること」は守れない。

### SharedPreferences / plist / サンドボックスファイルの抽出
**Q1**: App を動かした後、ローカルにどんな機微データを保存したかを見たい。まずどこを見る?
**A1**: 「平文の確率」順にサンドボックスを調べる。Android は `/data/data/<pkg>/shared_prefs/*.xml`(ログイン token、ユーザー情報が平文のことが多い)、`/databases/*.db`、`files/`、`cache/`。iOS は `Library/Preferences/*.plist`、`Documents/`、`Library/Caches/`。開発者は省力のため token/パスワード/ユーザー情報を平文で SharedPreferences に詰め込むことが多い。
**Q2**: shared_prefs 内の値が暗号化されている(文字化け)場合はどうする?
**A2**: 暗号化は key があることを示し、key は高い確率でクライアントにもある。「復号 key を探す」に移る。ハードコード、Keystore、デバイス派生の可能性。判定基準:`EncryptedSharedPreferences` を使っていれば key は AndroidKeystore にある(Keystore チェーン参照)。自社暗号化なら key はハードコードのことが多く、その復号関数を hook して平文を直接得る方が key を探すより速い。
**Q3**: root なしで /data/data を取得できない場合はどうする?
**A3**: root なし抽出に移る。①`adb backup`(App の allowBackup=true なら。バックアップチェーン参照)。②debuggable な App は `run-as <pkg>` でプライベートディレクトリにアクセス。③iOS はバックアップ抽出またはジェイルブレイク済みデバイス。またはいっそ再パッケージ化して debuggable/allowBackup を設定してからインストールする。
**Q4**: 「どのファイルが対象データを保存しているか」を探したいが、ファイルが多すぎる?
**A4**: 挙動トリガーで特定する。サンドボックスを空にする → 対象操作(ログイン/決済)を実行 → サンドボックスの変化を diff し、新規/変更されたファイルが対象。またはファイル書き込み(`FileOutputStream`、`SharedPreferences.Editor.putString`)を hook してキー値とパスを表示する。
**Q5**: ローカルストレージが全暗号化で、key がハードウェア Keystore にあり取得できない。この「ローカルファイルを抜く」道が失敗した。どこへ移る?
**A5**: 「ランタイムメモリ」の次元に移る。データは表示/使用時に必ず復号されてメモリに入る。読み取り関数を hook して復号後の戻り値を得るか、プロセスメモリを直接 dump して平文を検索する。ローカルファイル暗号化は「App 自身が復号して使う」瞬間を防げない。使用点で遮断する。

### Keystore / Keychain 内データの取得
**Q1**: 機微データが Android Keystore / iOS Keychain で保護されている。key を直接エクスポートできるか?
**A1**: 通常直接エクスポートできない(ハードウェア級 key は TEE/SE から出ない)。しかしデータを得られないわけではない。発想を変える。欲しいのは key そのものではなく「key で復号した後の平文」。App はこの key を使う権限があり、App を hook して自分に代わって復号させればよい。
**Q2**: 具体的にどう App に自分に代わって復号させる?
**A2**: Keystore 関連の呼び出しを hook する。Android は `Cipher.doFinal` を hook する(このとき key はすでに Keystore から読み込まれており、平文出力を得られる)、または `KeyStore.getKey` 後の使用点を hook する。iOS は `SecItemCopyMatching` を hook する(Keychain 内のエントリを直接返す)。判定基準:App が実行中でロック解除済みなら、その復号能力は自分のものだ。
**Q3**: iOS Keychain 内の項目を一括エクスポートしたい?
**A3**: ジェイルブレイクデバイスでは keychain-dumper、または objection の `ios keychain dump` を使う。`kSecAttrAccessible` 属性がアクセス可能性を決める(ロック画面状態、本デバイス限定など)点に注意。これで全 App が保存する認証情報を直接得られる。
**Q4**: key に生体認証/ユーザー認証が必須と設定されている(setUserAuthenticationRequired)。hook 時に指紋を要求される?
**A4**: 認証ゲートの回避に移る。生体認証コールバック(`BiometricPrompt` の `onAuthenticationSucceeded`)を hook して成功経路を直接トリガーするか、認証検証関数を hook して true を返す。「認証通過」の分岐を無条件で通し、以降の復号を正常実行させる。
**Q5**: ハードウェア key、強認証、native 復号が揃い、平文を得られない。どの直交する次元に移る?
**A5**: クライアント側を諦め、サーバー側の信頼境界に移る。Keystore が守るのは「このデバイスローカルのデータ」だが、App はそれで復号した後、結局サーバー側と通信する。復号後にサーバー側へ送られる平文を取得する方向に移るか、サーバー側 API を直接攻める(クライアントの暗号化がどれだけ強くても、サーバー側のロジック脆弱性とは無関係)。

### ハードコードされたクラウド認証情報(AK/SK)の実用化
**Q1**: パッケージからクラウドベンダーの AK/SK らしき組を掘り出した(ベンダーごとに固定プレフィックス)。次は?
**A1**: まず検証してから利用を語る。権限を直接推測せず、公式 CLI/SDK の最小動作で検証する。現在の身元の照会、リソースの列挙など。判定基準:身元情報が返れば認証情報が有効で、返るアカウント/ARN から、それがサブアカウントかメインアカウントか、およそどのサービスかも分かる。
**Q2**: 認証情報が有効。何ができるかをどう把握する?
**A2**: やみくもに試さず、権限を列挙する。まず読み取り専用+列挙系の動作(list buckets、describe instances)を試してサービス境界を画定し、サービスごとに権限を探る。対応するクラウドベンダーの権限列挙スクリプトでツール化する。原則:まず権限マップを調査し、その後高価値リソース(オブジェクトストレージ、クラウドホスト、鍵管理、データベース)を狙って利用する。
**Q3**: 認証情報の権限が非常に狭い(ある bucket にしかアクセスできない)。どうする?
**A3**: 狭い権限から権限昇格/横展開の手がかりを探す。①この bucket 内に他の設定ファイル/より高い権限の認証情報があるかもしれない。②`iam` 関連の動作(PassRole、AttachPolicy)ができて権限昇格できるか確認する。③オブジェクトストレージ内のオブジェクトにサーバー側ソース、バックアップ、他のシステム認証情報が含まれるかもしれない。狭い権限は踏み台であって終点ではない。
**Q4**: AK/SK が失効済みか風控を発動して無効化された。この認証情報は死んだ。どこへ移る?
**A4**: 他の認証情報源に移り、死んだ認証情報に粘らない。①同じパッケージ内の他の SDK 認証情報(プッシュ/SMS/ストレージで各 1 セット)。②STS 一時認証情報の取得 API(クライアントには STS を交換するロジックがよくあり、hook して新鮮な一時認証情報を得る)。③サーバー側が認証情報を配信する API(キャプチャ)。直交する切り替えとして「認証情報の生きた源流」へ向かい、死水にこだわらない。
**Q5**: オブジェクトストレージの bucket アクセス権しかない。成果を広げられるか?
**A5**: できる。オブジェクトストレージは横展開のハブになることが多い。中の `.env`/config/バックアップ/ログを探して、より多くの認証情報を掘る。bucket がウェブサイトのソースとしてマウントされていれば、webshell を書き込める可能性。内部システムが信頼できるデータソースとして扱っていれば、毒を仕込める。「ストレージアクセス」を「コード実行/認証情報の拡散」に昇格する。

### ハードコードされた token/JWT の権限探査とリプレイ
**Q1**: ハードコードされた長期 token(API key か JWT)を掘り出した。価値があるかをどう判断する?
**A1**: まず解析してからリプレイする。JWT は直接 base64 で header/payload を解いて見る。発行者、有効期限(`exp`。長期または無期限が最も危険)、権限 scope、ロール claim、ユーザー/テナント識別子。API key はどのリクエストヘッダーで使うか、どのエンドポイントに付けるかを見る。判定基準:payload 内のロール/scope が権限の上限を直接教える。
**Q2**: この token で実際にどの API を呼べるかを知りたい?
**A2**: キャプチャで見えた API 構造で横方向に探査する。token を持って既知のエンドポイントを走査し、401/403(権限なし)vs 200(権限あり)を観察する。重点的に試す:管理系エンドポイント、他のユーザーのリソース(ID を変えて権限外アクセス)、内部/デバッグエンドポイント。token の本当の権限はサーバー側が実際に許可する集合で、探査で得られる。
**Q3**: JWT を改ざんして権限昇格したい(role=admin に変える)が署名がある?
**A3**: 定番の JWT 弱点を試す。①`alg:none` が受け入れられるか。②署名鍵が弱い/クライアントにハードコードされているか(クライアントが発行できれば、任意の claim を偽造できる)。③RS256→HS256 の混同(公開鍵を HMAC 鍵として使う)。判定基準:クライアントに発行/検証ロジックがあるとき、鍵は高い確率でクライアントでも得られる。
**Q4**: token が失効か失効処理され、リプレイが失敗する。どこへ移る?
**A4**: 「新しい token を取得するフロー」に移る。ログイン/リフレッシュ API をキャプチャして、どう token を交換するかを見る。ハードコードされているのが「ユーザー token を交換できる上流の認証情報」(client_secret、refresh_token など)なら、単一の失効済み access_token よりはるかに価値が高い。それで OAuth フローを通って新鮮な token を交換する。直交する切り替えとして「発行機構」へ向かい、「ある失効済みの証」にこだわらない。
**Q5**: token は有効だが権限がただの一般ユーザーで、これ以上搾り出せない?
**A5**: 「権限外アクセス/横展開」の次元に移る。token の身元は変わらないが、サーバー側に IDOR、権限外アクセスの API、マルチテナント分離の欠陥があるかもしれない。この正当な低権限 token で認証し、サーバー側の認可ロジックの脆弱性を攻める。クライアントがくれるのは「入場券」で、サーバー側の認可欠陥こそが「権限昇格の扉」だ。

### 再パッケージ化/完全性検証の回避
**Q1**: コード変更/gadget 注入後に再パッケージ化したいが、App に署名検証があるのを懸念している。まずどう判断する?
**A1**: まず低コストで試す。apktool で解包 → 無関係なリソースを適当に変更 → 再署名してインストール → 実行。正常に動けば、高い確率で署名の自己検証はない。クラッシュ/「非公式バージョン」と表示されれば、完全性検証(署名照合/DEX CRC/ファイルハッシュ)がある。まず検証の有無を把握してから、精密な回避をするか決める。
**Q2**: 署名検証があると確認した。通常何を検証し、どう回避する?
**A2**: よくある検証点:`PackageManager.getPackageInfo` で自身の署名を取得してハードコード値と照合、APK ファイルの CRC 検証、classes.dex のハッシュ検証。回避法:`getPackageInfo`/`getPackageSignatures` を hook して元の署名を返す。または検証関数を見つけて直接 patch して常に通過させる。静的変更はランタイム hook より安定(変更後はクリーン)。
**Q3**: 検証が native レイヤにあり、照合ロジックが複雑?
**A3**: 「再パッケージ化しない」方針に移る。パッケージ変更が検証を発動させるなら、パッケージを変更しない。root なし注入以外の方式、LSPosed モジュール(APK ファイルを変えずに hook)、または Frida で実行中プロセスに直接 attach。検証するのは「ファイルが変更されたこと」で、ファイルを変えなければ検知できない。
**Q4**: キャプチャ/hook したいだけで、必ずしもパッケージ変更は不要。再パッケージ化に粘る必要はあるか?
**A4**: ない。自分の目的を反問する。目的が動的解析なら、attach 式の Frida/LSPosed で APK ファイルにまったく触れず、完全性検証の話題全体を直接回避する。「変更後の版を被害者に配布する必要がある」か「持続化注入が必須」のときだけ、再パッケージ化が不可欠になる。
**Q5**: 再パッケージ化が必須(フィッシング用/gadget の持続化が必要)だが、検証を回避できない。どこへ移る?
**A5**: 「検証の前に乗っ取る」または「サーバー側から手を付ける」に移る。①root なしコンテナで元のパッケージを変更せずに実行し注入する。②検証がサーバー側配信の期待ハッシュに依存するなら、その配信チャネルを攻める。③または検証に TOCTOU 窓があるか分析する。直交する切り替え:「ローカル検証を騙す」から「検証が依存する外部入力を制御する」へ移る。

### クライアントのローカル認証/業務検証の回避
**Q1**: App のある機能(VIP、解錠、承認通過)がクライアントのローカル判定に見える。回避できるか?
**A1**: まず判断がどちらの端にあるか確認する。判定基準:ネットワーク断/ローカルデータ変更後に機能状態が変わるか。ローカルで `isVip=true`(SharedPreferences を変更するか getter を hook)が効くなら、クライアント認証で、これは設計欠陥なので直接回避できる。ローカル変更が無効で、毎回サーバー側に問い合わせるなら、ローカルでは回避できない。
**Q2**: クライアントのローカル判定と確認した。最も直接的な回避は?
**A2**: 3 つある。①ローカルストレージのフラグビットを変更する。②判定結果を返す関数を hook して恒真にする(`isVip()`→true、`checkLicense()`→pass)。③smali 内の条件ジャンプを patch する(if-eqz のロジックを反転/削除)。どれを選ぶかは、一回限りの検証(hook)か持続化(patch 再パッケージ化)かによる。
**Q3**: キー検証はサーバー側にリクエストするが、レスポンスは「クライアントが解析」する。隙はあるか?
**A3**: ある。「サーバー側レスポンスの改ざん」の次元に移る。サーバー側が `{vip:false}` を返すが、クライアントが解析して効く場合、キャプチャツールでレスポンスを `{vip:true}` に変えるか、解析関数を hook する。判定基準:「最終判断がクライアントで行われる」限り、サーバー側が何を言っても中間者に書き換えられる。
**Q4**: 回避したと思ったが、機能は実はサーバー側制御(変えても無駄)。どう素早く反証する?
**A4**: 対照実験を行う。ローカルで全部回避(フラグビット+hook+レスポンス変更)した後、機能に本当のサーバー側副作用(実際の注文、実際のリモートデバイス解錠)を発生させる。画面表示が変わっただけでサーバー側が認めない(注文失敗/デバイスが動かない)なら、本当の gate はサーバー側にあり、ローカル回避は「自欺」だ。早めに損切りし、偽の勝利に時間を無駄にしない。
**Q5**: コア検証がサーバー側にあり、クライアント回避が無効と確認した。どこへ移る?
**A5**: サーバー側の認可攻撃面に移る。クライアントとサーバー側の通信の認証リクエストをキャプチャし、サーバー側の権限外アクセス(IDOR)、パラメータ改ざん、決済/注文ロジックの脆弱性、競合状態を攻める。クライアントは UI に過ぎず、本当の権限判断はサーバー側にある。戦場をデバイスから API に移す。

### WebView / ハイブリッドアプリのローカル攻撃面
**Q1**: App が WebView を大量に使う。ローカルストレージとハードコードの攻撃面はどう異なる?
**A1**: WebView は web 側のローカルストレージを導入する。`/data/data/<pkg>/app_webview/` 配下の Cookies、Local Storage、IndexedDB(SQLite ファイルで、session/token が平文で保存されることが多い)。さらに JS Bridge(`addJavascriptInterface` で登録されたネイティブ API)を見る。それはよくファイル読み取り、デバイス情報取得、ネイティブ機能呼び出しを公開し、web→native の橋だ。
**Q2**: JS Bridge を悪用したい。どう手を付ける?
**A2**: 登録された API 名とメソッドをリバースエンジニアリングで探す(jadx で `addJavascriptInterface`、`@JavascriptInterface` を検索)。WebView が読み込む URL が制御可能(平文 http、中間者可能、XSS あり)なら、web 側から橋メソッドを呼んでローカルファイルを読む/token を得る。判定基準:橋メソッドの権限 × 読み込み内容の制御可能性 = 攻撃価値。
**Q3**: WebView が読み込むのが https で内容も制御できず、橋を使えない?
**A3**: 「ローカル web ストレージの直接取得」に移る。橋を通さず、app_webview ディレクトリ配下の Local Storage/Cookies ファイルを直接抜く。中の session token は web 側へ直接リプレイできることが多い。または WebView が `setAllowFileAccess`/`setAllowUniversalAccessFromFileURLs` を有効にして file:// の権限外ローカルファイル読み取りが起きるかを見る。
**Q4**: これが Cordova/Ionic の類の純ハイブリッド App?
**A4**: ならば業務ロジック全体が `assets/www/` 配下の JS 内にあり、ほぼむき出し。JS ソースを直接読んでハードコード鍵、API エンドポイント、認証ロジックを探す。Java を逆解析するよりはるかに簡単。「フロントエンドのソース監査として扱う」方向に移る。
**Q5**: WebView のローカルストレージが暗号化、橋に権限検証、内容が全部 https で、web 側の道が通らない。どこへ移る?
**A5**: native 本体に戻る。Hybrid は外殻に過ぎず、コアの暗号化/認証情報は原生レイヤにあるかもしれない。前述の原生 hook/サンドボックス/Keystore の方針に移る。またはサーバー側へ移る。WebView が読み込むバックエンド API 自体も攻撃面だ。

### エクスポートコンポーネント / ディープリンク / URL scheme の悪用
**Q1**: manifest に exported の Activity/Service/Provider を見た。ローカルストレージの悪用とどう関係する?
**A1**: エクスポートコンポーネントは「ローカル機微データを読む正当なチャネル」になり得る。exported の ContentProvider を重点的に見る。それが App のプライベートデータ(データベース/ファイル)を外部に提供し権限検証がないなら、任意の他の App(自分の悪意ある App)が直接照会して token/ユーザーデータを得て、サンドボックス分離を回避できる。
**Q2**: エクスポートコンポーネントから何を搾り出せるかをどう判断する?
**A2**: 種別ごとに見る。エクスポート Activity が Intent extra を受け入れて読み込み内容を制御するか(URL/パラメータ注入の可能性)。エクスポート Provider の `authority` と query が返す表(content:// で直接照会)。エクスポート Service/Receiver が信頼できない Intent を処理して機微操作をするか。判定基準:exported=true + permission なし + 外部入力を処理 = 悪用可能。
**Q3**: URL scheme/ディープリンクはどう悪用する?
**A3**: 登録された scheme(manifest の `<data android:scheme>`)と処理ロジックをリバースエンジニアリングで探す。ディープリンクのパラメータが、任意 URL を WebView に読み込む(→XSS/token 取得)、ファイルパスを連結する(→パストラバーサルでローカルファイル読み取り)、認証不要の操作をトリガーする、のいずれかに使われるなら、悪意あるリンクを構成して被害者にクリックさせられる。
**Q4**: コンポーネントがすべて権限保護/signature 級 permission を付けていて、直接呼べない?
**A4**: 「デグレード/間接トリガー」に移る。①無保護だが保護コンポーネントへ転送できる中間コンポーネントがないか探す。②`grantUriPermission`/`FLAG_GRANT_READ` の一時認可を誘導できるか。③signature permission だが App の署名検証が弱いときは再パッケージ化と組み合わせる。またはコンポーネントの道を直接諦め、他のローカルストレージ次元に移る。
**Q5**: コンポーネント攻撃面が全体として成果なし。どこへ移る?
**A5**: 「能動的データ読み取り」から「受動的データ捕捉」に移る。コンポーネントは「自分が App を突く」もの。突けないなら、hook/サンドボックス/キャプチャなど「App が自ら露出する」方針に移る。IPC 攻撃面が枯渇してもローカルデータが得られないわけではない。ストレージの直接読み取りかランタイム遮断に替える。

### ログ/クリップボード/一時ファイルの機微情報漏えい
**Q1**: 主経路が詰まった。ついでに拾える低コストのローカル情報源はないか?
**A1**: ある。まず漏えいしやすい 3 箇所を走査する。①logcat(`adb logcat` でパッケージ名をフィルタ。開発者は token/リクエストボディ/パスワードをログに出力することが多い)。②クリップボード(決済/ログイン場面で App がクリップボードに機微文字列を書く)。③一時ファイル/キャッシュ(`cache/`、`/sdcard/Android/data/<pkg>/` の外部ストレージ内の平文キャッシュ、クラッシュログ、エクスポートファイル)。
**Q2**: logcat からどう効率よく拾う?
**A2**: キー操作(ログイン/決済/更新)をトリガーしながら `adb logcat | grep -iE 'token|auth|passwd|http|secret'`。旧バージョンの App や debug ログを無効化していないものは、完全なリクエスト/レスポンスを直接出力する。判定基準:release パッケージに Log.d の平文出力がなおあれば、低級な漏えいで、タダ同然に拾える。
**Q3**: App が外部ストレージ(SD カード)に何かを保存している?
**A3**: 外部ストレージはサンドボックス保護がなく、ストレージ権限を持つ任意の App が読める。`/sdcard/Android/data/<pkg>/` とルート下の App が作ったフォルダを調べる。キャッシュされた画像/ドキュメント、エクスポートされたレポート、平文データベース、ダウンロードされた設定。この種のデータは root なしで得られる。
**Q4**: これらのついでの点がすべて空(ログがクリーン、外部ストレージに平文なし)。何を意味し、どこへ移る?
**A4**: 対象 App の衛生管理が良いことを示し、拾い拾いは無効。本線に戻る。これは低コストの迂回路に過ぎず、空なら粘らず、ハードコードの逆解析かランタイム hook の主経路に戻る。拾い拾いを主攻にしない。
**Q5**: クリップボード/ログの漏えいで断片的な認証情報を得たが不完全?
**A5**: 「断片のパズル組み」に移る。ログの断片(token の前半など)を他の源(キャプチャ、メモリ dump)と交差させ、完全な認証情報を組み立てる。または漏えいした断片情報(ユーザー ID、リクエスト構造)でサーバー側探査を補助する。断片そのものは手がかりであって終点ではない。

### adb backup / iTunes バックアップ抽出
**Q1**: root なし/ジェイルブレイクなしで、App のプライベートデータを得たい。バックアップ抽出は可能か?
**A1**: 2 つのスイッチを見る。Android は manifest の `android:allowBackup`。true(多くの App が閉じ忘れている)なら、`adb backup -f x.ab <pkg>` でプライベートディレクトリをエクスポートでき、解包(abe/android-backup-extractor)後、shared_prefs/databases を調べて平文認証情報を得る。iOS は iTunes/愛思助手で無暗号化バックアップを作ってからサンドボックスを抽出する。
**Q2**: allowBackup=true だが、バックアップに一部のファイルがない?
**A2**: `fullBackupContent`/backup rules で機微ファイルを除外していないか確認する(開発者が意図的に一部を除外)。除外されたものこそ、彼らが機微と考えるもの。他の方式(run-as、root、hook)でその数個のファイルを専用に取得する方向に移る。除外ルールが逆に道を示してくれる。
**Q3**: allowBackup=false でバックアップの道が塞がれた。どこへ移る?
**A3**: 他の root なし抽出に移る。①App が debuggable=true なら、`run-as <pkg>` でプライベートディレクトリに直接入る。②再パッケージ化して allowBackup を true に変えるか debuggable を加えて再インストール(署名検証を通す必要)。③一歩引いて root/ジェイルブレイクデバイスに移る。バックアップは root なし抽出の 1 つに過ぎず、唯一ではない。
**Q4**: iOS のバックアップが暗号化されており、平文を抽出できない?
**A4**: 暗号化バックアップはパスワードが必要。パスワードが分からなければ、ジェイルブレイク後にサンドボックスを直接読む(frida-ios-dump + Documents/Library の直接コピー)、または Keychain dump に移る。暗号化バックアップが阻むのは「バックアップファイルの解析」で、「デバイス上で直接読むこと」は阻めない。
**Q5**: すべての root なし抽出の道が失敗(allowBackup 無効、非 debuggable、root 不可)。どの直交する次元に移る?
**A5**: 「静的にローカルファイルの設置状態を取る」ことを諦め、「ランタイムにデータを取る」に移る。root なしの frida-gadget 再パッケージ化注入を使う(ファイルを読めなくても、メモリ/関数を hook して同じデータを得られる)。ローカルファイルは読めないが、App がランタイムにこれらのデータをメモリへ読み込む瞬間はなお遮断できる。

### クライアント暗号化アルゴリズムの逆解析(自社暗号化プロトコル)
**Q1**: キャプチャでリクエストボディが暗号化されている。平文を復元/リクエストを偽造したい。どこから切り込む?
**A1**: 対象はアルゴリズム+鍵+IV の取得。まず暗号化の収束点を特定する。`Cipher.init`(key/iv/モードを得る)と `doFinal`(平文・暗号文の対を得る)を hook するのが最速で、アルゴリズムを読まず直接鍵パラメータを得られる。標準アルゴリズム(AES-CBC など)なら、key/iv があれば任意のデータを自分で加解密できる。
**Q2**: 暗号化が自社製(非標準 Cipher、ビット演算の山)?
**A2**: バイトコード/native の精読かシミュレーションに移る。暗号化関数を unidbg/frida の能動的呼び出しでブラックボックスとして使う。既知の平文を与えて出力を見て、変換を推測する。純粋にクライアントで再現可能(サーバー側のランダム因子なし)なら、オフラインで加解密を複製でき、任意のリクエストを偽造/改ざんできる。判定基準:アルゴリズムがクライアントで得られる定数だけに依存するか。
**Q3**: 鍵が毎回のリクエストで異なる(パケットごとに鍵)。どうする?
**A3**: 鍵の生成源を探す。通常クライアントがローカルでランダム key を生成し、それを「固定の上位鍵」(ハードコード/非対称公開鍵のことが多い)で暗号化してパケットに付けてサーバー側へ送る。その固定の上位鍵/秘密鍵ロジックを抜き出せば、各パケットのセッション鍵を復号できる。方向転換として「単一パケットの鍵」ではなく「鍵ネゴシエーションのフロー」へ移る。
**Q4**: 暗号化にサーバー側配信のランダムソルト/タイムスタンプが混ざり、オフラインで複製できない?
**A4**: オンライン中継に移る。完全なオフライン複製を追求せず、必要なときに毎回 App を hook して自分に代わって暗号化させる(送りたい payload をその暗号化関数に与え、その出力を得る)。これを「App を暗号化オラクルとして使う」といい、自分でアルゴリズムを複製する難題を回避する。
**Q5**: アルゴリズムが極めて複雑+強アンチデバッグ+native 難読化で、逆解析が完全に詰まった。どの直交する次元に移る?
**A5**: プロトコル復号を諦め、「より高レイヤの攻撃面」に移る。暗号化は伝送だけを守るが、平文データは UI/メモリ/暗号化前の関数引数に存在する。業務レイヤを hook して平文を得るか、サーバー側の他の非暗号化 API/ロジック脆弱性を直接攻める。伝送暗号化が強いことはシステム全体が安全であることを意味しない。それを回避して弱点を探す。

### メモリ dump によるランタイム鍵の抽出
**Q1**: 鍵がパッケージ内で暗号化/派生され、静的に取得できないが、ランタイムでは確実に平文。どうメモリから拾う?
**A1**: ランタイムにプロセスメモリを dump して特徴を検索する。手段:Frida の `Memory.scan`/ranges を列挙してから dump、または objection の `memory dump all`、または GDB/fridump。検索のアンカー:既知の形式(32 桁 hex key、`eyJ` JWT、Base64 の長い文字列)、既知の前後缀、または先に hook しておおよそのアドレスを特定してから精読する。
**Q2**: メモリが大きすぎて検索できない/ノイズが多い?
**A2**: 時空の範囲を狭める。暗号化操作をトリガーした瞬間(暗号化関数の入口を hook したとき)に dump すると、key がメモリに読み込まれたばかりで最も命中しやすい。またはプロセス全体ではなく App 自身の so/heap の読み書き可セグメントだけを走査する。hook で key があるオブジェクトの参照を特定し、つるを辿ってメモリを読む。
**Q3**: 鍵が使い終わるとすぐゼロクリアされ(メモリ衛生が良い)、dump で取得できない?
**A3**: 「事後 dump」ではなく「使用瞬間の遮断」に移る。鍵を使う関数(`Cipher.init` の key パラメータ)を直接 hook し、ゼロクリアされる直前の瞬間に得る。メモリ衛生が防ぐのは「残留」で、「使っているその瞬間」は防げない。
**Q4**: native で、鍵が SO のプライベートヒープ内にあり、Frida で列挙できない?
**A4**: native の確保/使用点を hook する。`Interceptor` を復号関数に張り、その引数レジスタ/スタック上の key ポインタを読む。または unidbg で鍵生成箇所までシミュレーション実行してシミュレーションメモリを直接読む。native 級の正確な遮断に移る。
**Q5**: メモリ dump の道全体が失敗(強対抗、ゼロクリア、native 隠蔽)。どこへ移る?
**A5**: 「鍵を必要としない」方針に移る。key を得られないなら、「App をオラクルにする」。実行中の App に鍵が必要な操作(暗号化/署名)を自分に代わって完了させ、自分はその入出力だけを使う。「鍵を必ず保持する」という前提を回避する。

### バージョン履歴/複数バージョン比較で旧認証情報を回収
**Q1**: 現行バージョンの鍵がすべてローテーション/プロテクト済み。ほかに手はあるか?
**A1**: 時間次元に移って旧バージョンを掘る。サードパーティ APK アーカイブサイト、アプリストアの履歴、CDN キャッシュから複数の履歴バージョンを取得する。旧バージョンにはよくある:プロテクトされていない裸のパッケージ、既に「修正」で削除されたがサーバー側がローテーションしていないハードコード鍵、より弱い暗号化、露出したデバッグエンドポイント。新旧の strings/config を diff して差異点を探す。
**Q2**: どう効率よく複数バージョンを比較する?
**A2**: 一括逆コンパイルして diff する。assets/config、strings.xml、smali 内の定数、エンドポイントリストを比較する。重点的に「新版が何を削除または暗号化したか」を見る。削除されたものは機微項目であることが多く、それが旧版では平文で、しかもサーバー側の認証情報はローテーションしていないことがある。
**Q3**: 旧版のハードコード鍵を見つけたが、とうに失効しているのではと懸念?
**A3**: 直接検証する(認証情報の検証ロジック参照)。開発者はコード内のハードコードをローテーションするが、サーバー側で旧認証情報を失効させるのを忘れることが多い(特にサードパーティ SDK key、クラウド AK)。判定基準:検証成功 = サーバー側がローテーションしていない = 旧版の考古学が有効。これは極めて費用対効果の高い迂回路だ。
**Q4**: 旧バージョンを入手できない(全ネットで最新版のみ)?
**A4**: 「パッケージ内の履歴残留」に移る。最新パッケージにも履歴の遺物があるかもしれない。コメントアウトされた旧エンドポイント、`.bak` リソース、混入したテスト証明書、git 漏えいの痕跡。またはアプリの Web/API 版に移って旧 API を探す。
**Q5**: バージョン考古学で成果なし。どこへ移る?
**A5**: ランタイムの本線に戻る。考古学は低コストの迂回路で、空なら動的 hook/メモリ/キャプチャに移る。時間次元が枯渇したら、空間次元(現在の実行状態)に戻って続ける。

### デスクトップクライアント(Electron/asar)のローカルストレージとハードコード
**Q1**: 対象が PC 側の Electron アプリ。ローカルストレージ/ハードコードをどう掘る?
**A1**: Electron はほぼ「パッカー付きのウェブページ」で、掘りやすい。核心は `resources/app.asar`。`asar extract` で解包すると JS/HTML ソースを直接得られ、中のハードコードされた API エンドポイント、鍵、認証ロジックはほぼむき出し。ローカルデータは `%AppData%/<app>/` 配下(Local Storage、IndexedDB、Cookies、config.json)。
**Q2**: asar 内の鍵が簡単に難読化/分割されている?
**A2**: フロントエンド級の難読化は弱い。美化(beautify)してから読むか、Electron 内で直接 DevTools を開く(無効化していないものが多い)てランタイムに変数を読む。または main.js を変更してコード注入で表示する。Electron の「逆解析」の難易度はウェブページを読むのに近く、モバイル側のあの重いツールを使わない。
**Q3**: app.asar が暗号化/bytecode で .jsc にコンパイルされている?
**A3**: ランタイムに移る。①`--inspect` でデバッガを接続。②main プロセスを置換/patch してコード注入。③メモリから dump(V8 ヒープスナップショット)して平文を得る。bytenode コンパイルは静的解析を阻むが、ランタイムの V8 内はなお平文の関数だ。
**Q4**: Electron ではなく .NET/C++ のネイティブデスクトップクライアント?
**A4**: ツールチェーンを替える。.NET は dnSpy/ILSpy で逆コンパイルする(よくデータベースに直接接続し、接続文字列+パスワードが設定やコードにハードコードされており、極めて価値が高い)。C++ は IDA/ghidra。ローカルデータはインストールディレクトリ、`%AppData%`、レジストリ(HKCU 配下に認証情報がよく保存)、Windows 資格情報マネージャーを見る。
**Q5**: デスクトップクライアントのハードコードがデータベース/内部サービスを指す。これは終点か?
**A5**: いや、踏み台の起点だ。デスクトップ側(特に C/S アーキテクチャの ERP/OA)はよくデータベース直結文字列をハードコードする。直接 DB に接続する = コアデータの取得 + データベース経由の権限昇格(ストアドプロシージャでのコマンド実行など)でイントラネットへ横展開できる。方向転換として「データベース/イントラネット横展開」の次元へ。クライアントはあなたをサーバー側の裏庭に送り込んだに過ぎない。

### アンチデバッグ/アンチ Frida 対抗
**Q1**: Frida/デバッガを導入すると App がクラッシュするか挙動が異常。対抗点をどう特定する?
**A1**: まず検知種別を識別する。アンチデバッグ(`ptrace` 自己アタッチ、`TracerPid` チェック)、アンチ Frida(ポート 27042 の走査、メモリ内の `frida`/`gum` 文字列の走査、`frida-agent` スレッド/maps の検知)、アンチ Xposed/root。クラッシュ前の呼び出しスタックを取得するか、よくある検知 API を hook して特定する。
**Q2**: アンチ Frida は具体的にどう回避する?
**A2**: 検知手段に応じて対処する。frida-server のデフォルトポート/プロセス名を変える。Gadget モード(改名、非標準ポート)でポート走査を回避。`open`/`read` を hook して `/proc/self/maps`、`/proc/net/tcp` の読み取りをフィルタして frida の痕跡を除去。または魔改造版で文字列走査に対抗する。
**Q3**: アンチ ptrace のアンチデバッグはどう処理する?
**A3**: `ptrace` を hook して `PTRACE_TRACEME` を成功返却させ、TracerPid を検知する読み取りを 0 返却にする。または ptrace に依存しない計装方式を使う。native のアンチデバッグは IDA で検知分岐を patch する。
**Q4**: 対抗が極めて硬い(多重検知、時間検知、自己検証)。hook の猫鼠ゲームで勝てない。どこへ移る?
**A4**: 戦場を替え、「対抗のある実機プロセス内」で遊ばない。①unidbg/qiling で対象関数をシミュレーション実行する。クリーンな環境でアンチデバッグが一切発動しない。②静的に硬 patch して再パッケージ化(完全性検証を通す必要)。③物理的迂回路。直接キャプチャ+設置ファイルを読み、そもそもプロセスに注入しない。アンチデバッグは「プロセス内の動的解析」を守るので、プロセスの外へ回る。
**Q5**: シミュレーションも環境不足/複雑な依存で動かない。完全に詰まった。最後にどこへ移る?
**A5**: 純粋なブラックボックスに後退する。入出力だけを観測(ネットワークリクエスト/レスポンス、UI 挙動、ファイル変化)し、挙動差分でロジックを推測する。内部の鍵/アルゴリズムを得るのを諦め、サーバー側 API レイヤで脆弱性を探す方向に変える。対抗がどれだけ強くても、対外通信の観測可能性は変えられない。

### サードパーティ SDK のハードコード認証情報の横展開価値
**Q1**: パッケージからサードパーティ SDK の key が大量に掘り出された(プッシュ、統計、地図、IM、カスタマーサポート)。これらは価値があるか?
**A1**: ランク付けして見る。多数は「設計上クライアントに置くべき」公開 key(地図の JS key など)で、価値は限定的。しかし一部は secret 級(管理 API を呼べる、全員プッシュを送れる、ユーザーリストを読める)。判定基準:その key がクライアント SDK だけでなく「管理面/サーバー側」API を呼べるか。SDK ドキュメントで client key と server secret を区別する。
**Q2**: どのサードパーティ key が最も高危険に誤配置されやすい?
**A2**: プッシュ SDK の MasterSecret/AppSecret(一斉プッシュでフィッシング/DoS)、IM SDK の管理鍵(任意のセッションを読み書き、ユーザー情報を得る)、SMS/メール SDK の認証情報(任意の SMS を送れ、消費+フィッシング)、オブジェクトストレージ SDK の完全な AK/SK(クラウド認証情報チェーン参照)、地図 web サービス key(不正利用され得る)。
**Q3**: IM/プッシュの管理鍵を見つけた。どう昇格して悪用する?
**A3**: それでサーバー側管理 API を呼ぶ。ユーザー列挙、メッセージ読み取り、メッセージ送信。これで大量のユーザーデータを直接得るか、狙ったソーシャルエンジニアリングができるかもしれない。方向転換として「サードパーティの管理画面=もう一つのサーバー側攻撃面」。ハードコードはただの鍵だ。
**Q4**: これらの key がすべて純粋なクライアント公開 key で、管理権限を搾り出せない?
**A4**: それらの「間接価値」に移る。①露出した project/app id で対象の技術スタックと他のアセットを把握できる。②一部 SDK のデバッグ/設定 API が権限外アクセスになり得る。③Firebase の類の config が未認可アクセス可能なデータベースに繋がっているかもしれない(バックエンド設定チェーン参照)。公開 key もアセット偵察の手がかりだ。
**Q5**: サードパーティ SDK 方向がすべて低価値の公開 key。どこへ移る?
**A5**: 対象アプリ自身の認証情報に戻る。サードパーティ key は枝葉に過ぎず、主対象のサーバー側認証情報/エンドポイントこそが核心。自社 API の認証、自社暗号化、自社エンドポイントを掘る方向に移る。サードパーティの公開 key に過剰に投入しない。

### バックエンド設定の漏えい(Firebase / クラウド関数 / 内部エンドポイント)
**Q1**: パッケージを grep して URL が大量に出た。その中から高価値のバックエンドをどう見つける?
**A1**: これらのエンドポイントを分類する。本番 API、テスト/ステージング(`test.`/`dev.`/`uat.`。認証が弱いことが多い)、内部サービス(`internal`/イントラネットドメイン/IP。露出するだけで高危険)、クラウドホスティング(`*.firebaseio.com`、`*.cloudfunctions.net`、オブジェクトストレージのドメイン)、サードパーティコールバック。テスト環境と内部エンドポイントを優先する。
**Q2**: Firebase 設定(project id + api key + database url)を掘り出した。どう悪用する?
**A2**: 未認可アクセスを試す。Realtime Database は直接 `https://<project>.firebaseio.com/.json` でルールが `true`(公開読み書き可)かを見る。Firestore/Storage も同様に匿名読み書きを試す。Firebase Auth の api key は匿名登録/列挙を試せる。判定基準:多くの Firebase はルールが `allow read: if true` と設定されており、全データベースがむき出しになる。
**Q3**: 内部/イントラネットのドメインや IP エンドポイントを掘り出したが、現在は到達できない?
**A3**: 「イントラネット横展開の対象」として記録する。これらはアセット偵察の金鉱だ。他の経路(SSRF、VPN、イントラネット侵入済み)で到達できるようになれば、これらの内部 API は認証なし/弱認証のことが多い。方向転換として「外部情報をイントラネット段階へ供給する」。クライアントのハードコードがあなたにイントラネット地図を描いてくれた。
**Q4**: エンドポイントがすべて本番環境+強認証で、直接攻められない?
**A4**: 「弱認証の同源アセットを探す」に移る。テスト/ステージングエンドポイント(本番と DB を共有するが認証が弱いことが多い)、旧 API バージョン(`/v1/` が廃止されていないが新版の検証がない)、ドキュメント/ヘルスチェック/actuator の類の露出エンドポイント。または掘り出した認証情報をこれらのエンドポイントに付けて認証する。
**Q5**: すべてのエンドポイント方向が硬く、バックエンド設定を搾り尽くしても成果なし。どこへ移る?
**A5**: クライアント-サーバー側通信のランタイム観測に戻る。静的エンドポイントリストは不完全で、キャプチャでは静的解析にない実際の呼び出しエンドポイントとパラメータ構造が見える。動的キャプチャに移って攻撃面を補完し、実際のトラフィックに対してロジック脆弱性を探す。

### クライアントからサーバー側への信頼境界の突破
**Q1**: クライアントのローカルで得られるものは得た(エンドポイント、認証情報、アルゴリズム)。次に戦略上どう進む?
**A1**: クライアントは「信頼境界の鍵の保管場所」に過ぎず、本当の対象はサーバー側にあると明確にする。クライアントの生成物をサーバー側攻撃の弾薬に変換する。逆解析した暗号化アルゴリズムで正当なリクエストを偽造、ハードコード認証情報で認証、露出したエンドポイントで面を広げる。「デバイスの解析」から正式に「サーバー側を攻める」へ移る。
**Q2**: クライアントに「公式 App しか呼べない」暗号化/署名保護の API が多数ある。どう使う?
**A2**: クライアントの暗号化/署名の本質は「リクエストが正当な App から来たことの証明」だが、アルゴリズム/鍵を逆解析済みなら = 自分も正当なリクエストを生成できる。それで任意の payload を構成してサーバー側 API を呼び、サーバー側は自分を正当なクライアントとみなす。その権限外アクセス、インジェクション、ロジック脆弱性を攻める。クライアント保護はむしろ「信頼された身元」をあなたに与えた。
**Q3**: サーバー側がクライアントから来るデータを盲信するかをどう判断する?
**A3**: クライアントが本来検証すべきものを変えて、サーバー側が受け入れるかを測る。価格、数量、ユーザー ID、権限フラグを変える。クライアントがローカルで価格を計算して直接サーバー側に送り、サーバー側が再確認しなければ、改ざんが即効く。判定基準:「クライアントが計算/検証、サーバー側がそのまま全部受け取る」= 信頼境界の欠陥。
**Q4**: サーバー側検証が厳しく、偽造リクエストがすべて拒否される(署名/タイムスタンプ/リプレイ対策が揃っている)?
**A4**: 「本物の App が生成した正当なリクエストを変異させる」に移る。自分で偽造せず、本物のリクエストを取得して有効期間内に最小限の改ざんをしてリプレイする(業務パラメータを 1 つ変え、正当な署名構造を保つ)。または App を署名オラクルとして、改変後のデータを代わりに署名させる。リプレイ対策はランダムな偽造を防ぐが、「正当なリクエストの微調整」は必ずしも防がない。
**Q5**: サーバー側全体が堅固で、クライアントからサーバー側への突破の道が失敗した。どこへ移る?
**A5**: 他の信頼境界に移る。①その会社の他の App/Web へ横展開(バックエンド/SSO を共有することが多く、1 箇所の認証情報で通る)。②サプライチェーン(サードパーティ SDK の管理画面、CI/CD)。③ソーシャルエンジニアリング/内部人員。単一の App→サーバー側が突破できないなら、攻撃面を替え、1 つの入口だけを見ない。

### ハードコードされた非対称秘密鍵/証明書の悪用
**Q1**: パッケージ内に `-----BEGIN PRIVATE KEY-----` や `.p12`/`.jks` を発見。これは対称鍵より価値があるか?
**A1**: 通常より価値が高く、用途も異なる。それが何の秘密鍵かを判断する。①TLS クライアント証明書の秘密鍵(mTLS、サーバー側接続用)。②署名秘密鍵(リクエスト/JWT/更新パッケージに署名)。③業務データ加解密の秘密鍵。用途により悪用経路が異なるので、まずコード内でどの API に渡されるかを見る。
**Q2**: JWT/リクエスト署名用の秘密鍵。何ができる?
**A2**: 任意の正当な署名付き token/リクエストを偽造できる。JWT 発行秘密鍵なら、任意のユーザー/管理者の身元を偽造する。リクエスト署名秘密鍵なら、任意の API 呼び出しを偽造してサーバー側の署名検証を通す。これは「正当な身元でやりたい放題」級の脆弱性だ。
**Q3**: `.jks`/`.p12`/`.bks` にパスワードがあり開けない?
**A3**: パスワードは高い確率でクライアントにもある。コード内にハードコード、同じディレクトリの config、または固定文字列から派生。keystore 読み込み箇所のパスワードパラメータを grep するか、`KeyStore.load` を hook してパスワードを得る。判定基準:クライアントがこの証明書を使うなら、必ずパスワードを得られる。あなたも得られる。
**Q4**: 秘密鍵の用途がソフトウェア更新パッケージの署名。どう悪用する?
**A4**: 高危険だ。悪意ある更新を発行できる。App がこの公開鍵で更新パッケージを検証するなら、秘密鍵で悪意あるパッケージに署名 → 署名検証通過 → ユーザーへ配信 = サプライチェーン毒入れ/RCE。「更新機構」攻撃に移る。前提は更新配信チャネルを乗っ取れること(中間者/DNS/サーバー側)。
**Q5**: 秘密鍵を抽出したが、サーバー側が証明書を交換済み/他の因子をバインドしており、秘密鍵単独では無用。どこへ移る?
**A5**: 組み合わせ利用に移る。秘密鍵を他のハードコード因子(デバイスフィンガープリントアルゴリズム、タイムスタンプ署名)と組み合わせて完全な認証情報を揃える。または秘密鍵は交換されたが署名機構を明かしたので、新機構を理解して攻めるのに役立つ。または本物の App を署名オラクルとして使う方針に後退する。

### ハードコード認証情報の権限/機密ランク判定と損切り
**Q1**: 認証情報らしきものを 5 つ掘り出した。時間が限られている。どれを先に深掘りする?
**A1**: 「機密ランク × 到達可能性」で並べ替え、均等に力を入れない。機密ランク:サーバー側管理権/データベース/クラウドマスターを得られるもの > 単一ユーザー token > 公開 client key。到達可能性:検証成功で権限が大きいものを優先。まず 10 分かけて各々を検証+権限境界を探り、価値マップを描いてから、最高価値のものに全力投入する。
**Q2**: ある認証情報の「権限の天井」をどう素早く判断する?
**A2**: 最小探査。クラウド認証情報は身元を照会(メインアカウントか制限付きサブアカウントか)、token は scope/role を解析、API key は管理動作を 1 つ試して許可されるかを見る。判定基準は「最悪の場合どれだけの破壊を起こせるか」で、それに基づいて投入を決める。読み取り専用の client key 1 つに数時間かけない。
**Q3**: 高価値認証情報の探査時に対象のアラート/風控を発動した場合はどうする?
**A3**: 即座に減速して隠密戦略に変える。出口 IP を替え、通常のクライアント UA/リクエスト特徴を模擬し、頻度を下げ、明らかに危険な動作(一括列挙、削除・変更)を避ける。判定基準:レッドチームが欲しいのは「悪用可能の証明」で「ブルーチームを叩き起こすこと」ではない。必要なら先に証拠(スクリーンショット/最小 PoC)を固定してから手を止める。
**Q4**: 掘り出した認証情報をすべて検証したら全失効/全低価値公開 key で、この方向が枯渇した。どこへ移る?
**A4**: 死んだ認証情報に粘らない。直交する次元に移る。①ランタイムに「生きた」認証情報を取得する(App ログイン後に得る session/一時 token はハードコードより有効)。②エンドポイント/プロトコルの逆解析に移ってサーバー側脆弱性を探す。③他の攻撃面(Web、他の App)に移る。ハードコード枯渇 = 「ランタイム認証情報」か「サーバー側ロジック」へ移る。
**Q5**: 「新たな認証情報を掘り続けるが 1 つも前進しない」死循環に陥るのをどう避ける?
**A5**: 判定基準で損切りする。連続 N 個の認証情報が「サーバー側の実際の権限昇格」に転化できないなら、この App のハードコード方向はもう頭打ちで、レーン全体を替える(対象/攻撃面を替える)べきで、同じ次元で 6、7 個目の認証情報を掘り続けない。限界利益がゼロになったことを認識し、果断に切り替える。

### 派生鍵/デバイスバインド認証情報の処理
**Q1**: 鍵がハードコード定数ではなく、ランタイムにデバイス情報(IMEI/androidId/パッケージ名/時刻)から派生される。どうする?
**A1**: 派生関数を探し、入力の制御可能性を判断する。派生がクライアントで取得できる安定入力(パッケージ名、固定ソルト、デバイス ID)だけに依存するなら、再現できる。派生ロジックを抜き出し、任意の環境で同じ key を計算する。判定基準:派生の全入力が自分で取得して固定できるか。
**Q2**: 派生ロジックは複雑だが純ローカルで、複製コストが高い?
**A2**: 複製せず、派生関数の戻り値を直接 hook する。key を算出したその瞬間に截獲すればよい。または unidbg で派生関数をシミュレーション呼び出しし、入力を与えて出力を得る。ランタイム遮断は常に静的複製より省力だ。
**Q3**: 派生にサーバー側配信のランダム因子が混ざる(毎回異なる)?
**A3**: 「配信の取得+オラクル化」に移る。サーバー側がランダム因子を配信するあの通信をキャプチャする。または必要なときに毎回 App に自分に代わって派生させる。オフライン固定 key の発想を捨て、「毎回の有効な key をオンラインで取得」に移る。
**Q4**: 認証情報がデバイスと強バインド(デバイスを替えると失効、サーバー側がデバイスフィンガープリントを検証)で、自分の環境で使えない?
**A4**: デバイスフィンガープリントの偽造に移る。それがどのフィンガープリントをレポートするかを逆解析し(収集関数を hook)、自分の環境で対象デバイスのフィンガープリント値と一致するように偽造してレポートする。または対象の実機/そのミラー環境で直接操作する。「デバイスバインド」を「デバイス偽装」問題に変える。
**Q5**: 派生+デバイスバインド+サーバー側強検証が揃い、オフライン利用が完全に不可能。どこへ移る?
**A5**: 「正当な環境内で操作する」に移る。認証情報を運び出してオフラインで使うのを追求せず、すべての検証を通過済みの本物の App 実行状態内で、業務関数を hook して直接目的の操作を実行する。鍵を運び出せないなら、門の内側で手を動かす。「認証情報の抽出」を諦め「認可済みセッションの乗っ取り」に変える。

### ローカル SQLite / 構造化データベースの解析
**Q1**: サンドボックス内に `.db` ファイルが複数ある。どれが機微データを隠すかをどう素早く判断する?
**A1**: 取り出して sqlite ツールで直接開き、まず `.tables` でテーブル名を見る。`user`、`account`、`token`、`session`、`message`、`config`、`kv` の類の高価値なものを優先。列名で `password`、`token`、`secret`、`cookie`、`phone`、`idcard` を探す。多くの App がチャット記録、アカウント、キャッシュされた API レスポンスを平文で SQLite に保存する。
**Q2**: データベースファイル自体が暗号化されている(SQLCipher、直接開けない)?
**A2**: SQLCipher は鍵が必要で、鍵はクライアントにある。「SQLCipher の鍵を探す」に移る。`SQLiteDatabase.openOrCreateDatabase`/`net.sqlcipher` の `openDatabase` を hook して渡される password パラメータを得るか、native の `sqlite3_key` を hook する。key を得た後、ローカルで SQLCipher ツールで解く。判定基準:App がデータベースを読める = key が得られる。
**Q3**: ある業務データがどのテーブルに保存されるかを知りたい?
**A3**: 挙動トリガーで特定する。操作前後でデータベースを dump して diff し、新規行のあるテーブルが対象。または SQL 実行(`execSQL`/`rawQuery`)を hook して全ステートメントを表示し、insert/update がどのテーブルに入るかを見る。
**Q4**: データベース内のフィールド値が二次暗号化(データベースは暗号化されていないが単一フィールドが暗号文)?
**A4**: フィールド級の復号に移る。そのフィールドを読んだ後に復号するコードを探し、復号関数を hook して平文を得る。フィールド暗号化の key も同じくクライアントにある。これは前述の「クライアント暗号化アルゴリズム」問題に退化する。
**Q5**: データベース全暗号化+フィールド暗号化+key がハードウェア保護で、崩せない。どこへ移る?
**A5**: UI/メモリ表示レイヤに移る。データは最終的にユーザーへ表示されるので、表示前の getter を hook するか、レンダリングレイヤのメモリから直接平文を拾う。データベースがどう暗号化しても「App 自身が復号してレンダリングする」ことは防げない。

### React Native アプリの bundle とローカルストレージ
**Q1**: React Native アプリと判断した後、ハードコードとロジックはどこで探す?
**A1**: 核心は `assets/index.android.bundle`(パッケージ後の JS)。それは平文または単なる minify のことが多く、直接 grep してエンドポイント、apikey、token、認証ロジックを探す。圧縮後のフロントエンド JS を読むのと同じ。ローカルストレージは AsyncStorage を使い、`/data/data/<pkg>/databases/RKStorage`(SQLite)か files に設置され、token が平文で保存されることが多い。
**Q2**: bundle が Hermes バイトコード(開けないバイナリ)?
**A2**: Hermes の逆コンパイルに移る。hermes-dec/hbctool で `.hbc` を逆アセンブルして可読な疑似コード/文字列に戻す。文字列定数(エンドポイント、key)は直接 strings で抽出できることが多く、ロジックは Hermes アセンブリを読む必要がある。
**Q3**: RN の JS ロジックを動的に hook したい?
**A3**: RN は JS Bridge でネイティブと通信するので、ネイティブ橋渡しレイヤ(`ReactContextBaseJavaModule` のメソッド)を hook して言語間で渡るデータを見るか、Metro/リモートデバッグを有効にする(dev 版)。release 版は Frida で低レイヤのネットワーク/暗号化関数を hook する方向に移る。
**Q4**: bundle が暗号化/分割され、Hermes も読めない。どこへ移る?
**A4**: 「フレームワーク非依存」のランタイムレイヤに戻る。JS がどうパッケージされても、最終的なネットワークリクエストはネイティブ OkHttp/native を通り、暗号化は標準ライブラリを通る。`Cipher`/ネットワーク収束点を hook して平文を得る方向に移り、AsyncStorage の SQLite 設置ファイルも取得する。JS レイヤを回避してネイティブ境界で直接遮断する。
**Q5**: AsyncStorage の設置ファイルも暗号化されている?
**A5**: AsyncStorage の読み取り API の戻り値(`getItem` の結果)を hook する方向に移り、JS/橋渡しレイヤで復号後の平文を得る。またはメモリ dump。設置の暗号化は、読み取り時の復号の瞬間を防げない。

### クライアントのハードコードをイントラネット/横展開の踏み台にする
**Q1**: クライアントのリバースエンジニアリングで出た情報は、この業務バックエンドを攻める以外に、イントラネット横展開にどう役立つ?
**A1**: クライアントを「情報源」として見る。ハードコード内にはイントラネットドメイン/IP/ポート、内部サービス名、運用管理画面のアドレス、データベース接続文字列、内部 API のパス、従業員/テストアカウントがよくある。これらはイントラネットアセット偵察の一次情報で、現在到達できなくても、イントラネットに入れば即座に使える。体系的に抽出してアーカイブする。
**Q2**: ハードコードされた内部サービスの認証情報(内部メッセージキュー、キャッシュ、データベースアカウントなど)を掘り出したが、現在外側から接続できない?
**A2**: 「イントラネット設置後の即用弾薬」として標示する。判定基準:これらの内部サービスは通常外側に露出しないが、イントラネット内では強認証がない。イントラネットの足がかり(VPN、SSRF、境界マシン)を得たら、これらの認証情報で直接横展開できる。今接続できないからといって捨てない。
**Q3**: クライアントが運用/管理画面のアドレスをハードコードしている。直接攻められるか?
**A3**: まず到達可能性と認証強度を探る。多くの管理画面は手軽さのために到達可能なアドレスに置かれ、弱パスワード/デフォルトパスワード。クライアントが管理画面アカウント(テスト/デモアカウント)までハードコードしていれば直接試す。管理画面に入れれば = 大範囲の制御。
**Q4**: すべてのハードコードされた内部アセットが現在到達不能で、このイントラネット踏み台の道が一時的に断たれた。どこへ移る?
**A4**: 「先に足がかりを得てから、これらの情報を使う」に移る。イントラネット情報を保存し、「どうイントラネットに入るか」の直交する問題に戻る。業務バックエンドの RCE、SSRF、VPN 認証情報、フィッシング。情報は古くならず、先に到達可能性を解決する。
**Q5**: ハードコードされたアカウントがテストアカウントで、権限が低く、横展開価値が限定的?
**A5**: 低権限アカウントも「イントラネットの身元」だ。それで内部システムを認証した後、権限外アクセスを探す、見える内部ドキュメント/wiki/コードリポジトリ(より多くの認証情報がよくある)を探す、内部情報収集を行う。低権限アカウントはイントラネット情報収集の正当な入口で、終点ではない。

### クライアントのデバッグバックドア / 隠し設定スイッチ
**Q1**: App に開発者が残したデバッグバックドアや隠し機能がある疑いがある。どう探す?
**A1**: 特徴を検索する。`debug`、`isTest`、`developer`、`backdoor`、`admin`、`gm`(ゲーム管理画面)、`switchEnv`、`bypass` などのフラグビット。隠しジェスチャー/連打トリガーのロジックを検索。BuildConfig.DEBUG 分岐内で条件付きで無効化された機能を見る。開発者は「内部ビルドだけ有効」の危険な機能を残すことが多く、スイッチはクライアントで反転できる。
**Q2**: `if(DEBUG)` で保護されたデバッグ機能を見つけた。どう有効化する?
**A2**: スイッチを反転する。BuildConfig.DEBUG/isTest を hook して true を返すか、ローカル設定を変更するか、条件ジャンプを patch する。有効化後、環境切り替え(テストバックエンドへ切替)、ログ詳細、認証スキップ、内部メニュー、モックデータが解除されるかもしれない。判定基準:これらの機能は設計時に「内部の人間だけがトリガーできる」と仮定されている。反転すれば自分が内部の人間になる。
**Q3**: 「環境切り替え」バックドアで dev/test バックエンドへ切り替えられる?
**A3**: 高価値だ。テスト環境へ切り替えると、認証/風控が弱いことが多く、データは本番と共有か実データを含む可能性。切り替えてテストバックエンドを攻める方が、本番に正面から当たるよりはるかに容易なことが多い。これは「本番を攻める」から「防御がより弱い同源環境を攻める」への直交する切り替えだ。
**Q4**: デバッグバックドアがサーバー側の二次検証に阻まれる(クライアントでは有効だがサーバー側が認めない)?
**A4**: 「バックドアが明かす攻撃面」に移り、バックドアそのものではない。バックドアコードは内部 API のパス、パラメータ形式、特殊 header を漏らす。機能がサーバー側に阻まれても、これらの情報はサーバー側への攻撃を直接構成するのに使える。バックドアは地図であり、必ずしも扉ではない。
**Q5**: くまなく探してもデバッグバックドアがない。この道は空。どこへ移る?
**A5**: 本線のハードコード/ランタイム経路に戻る。バックドアは運任せの迂回路で、なければそれまで。体系的な認証情報の発掘とサーバー側突破に戻り、「必ずバックドアがある」に固執しない。

### iOS 対象:復号とサンドボックスフォレンジックの特殊経路
**Q1**: 対象が IPA(iOS)。Android と比べて最初の一歩はどう異なる?
**A1**: iOS の App Store パッケージは FairPlay 暗号化(実行セグメントが暗号文)で、静的に直接逆アセンブルすると暗号文が見える。まず「復号」して DRM を外す必要がある。判定基準:まずパッケージの出どころを確認する。ジェイルブレイクデバイスでの復号(frida-ios-dump/dumpdecrypted でランタイムに復号済み Mach-O を dump)が主経路。復号済みバイナリを得てから class-dump/Hopper/ghidra で解析する。企業署名/開発パッケージは暗号化されていないことがあり、直接解析できる。
**Q2**: ジェイルブレイクデバイスがない場合、どう復号/解析する?
**A2**: 代替手段に移る。①ジェイルブレイク済み環境かクラウド実機で復号してから復号済み IPA を得る。②静的文字列/リソース解析だけを行う(`Payload/App.app` 内の plist、bundle リソース、embedded provisioning、`.storyboard` にハードコードの手がかりがよくあり、この部分は暗号化されていない)。③frida-gadget をジェイルブレイクなしで再署名注入する(再署名と sideload が必要)。判定基準:復号済みバイナリを得られて初めて完全な逆解析を語れる。そうでなければ先に平文リソースを搾る。
**Q3**: iOS のローカル機微データはどこに隠れるか。Android との対応関係は?
**A3**: サンドボックスの `Documents/`、`Library/Preferences/*.plist`(SharedPreferences に対応、平文のことが多い)、`Library/Caches`、ローカルの `.sqlite`(Core Data)、`Library/Cookies`。認証情報は Keychain(Keystore に対応、ただし keychain-dumper で丸ごとエクスポート可能)。iOS の Keychain は Android Keystore より丸ごと dump しやすいことが多い。
**Q4**: App にジェイルブレイク検知があり、復号/解析環境で起動するとすぐクラッシュする?
**A4**: ジェイルブレイク隠蔽に移る。Liberty/Shadow/A-Bypass の類でジェイルブレイク特徴を隠すか、検知関数(`fork`/`stat` による `/Applications/Cydia.app`、`/bin/bash` などのパスの検知)を hook する。原理は Android の root 検知回避と同じ。先に環境を浄化してから作業する。
**Q5**: iOS 対象のジェイルブレイク検知が極めて硬く、使えるジェイルブレイクデバイスもない。この iOS リバースエンジニアリングの道が通らない。どこへ移る?
**A5**: 「プラットフォーム非依存」のサーバー側境界に移る。同一業務の iOS/Android/Web は通常バックエンドを共有する。より扱いやすい Android 版のリバースエンジニアリングに移るか、Web 側を直接キャプチャし、エンドポイントとプロトコルを得る。その後、サーバー側の脆弱性はクライアントのプラットフォームと無関係。厄介な iOS クライアントを避け、同源の軟対象からサーバー側に入る。

### キャプチャで暗号化トラフィックを見たが、対象はリクエストの偽造/改ざん
**Q1**: 暗号化リクエストをキャプチャできるようになったが、欲しいのはパラメータを変えてリプレイすること。見るだけではない。どう進める?
**A1**: まず暗号化の境界を特定する。リクエストが全体暗号化か、署名のみ(平文+sign フィールド)か。平文+署名なら、署名アルゴリズムを再現するだけでパラメータを変えられる。全体暗号化なら、加解密能力を得る必要がある。先に種別を判断してから戦略を決め、いきなり最も難しい全体暗号化に取りかからない。
**Q2**: 「パラメータ平文 + sign フィールド」型。署名アルゴリズムをどう再現する?
**A2**: sign を生成する関数(`パラメータ整列+連結+固定 salt+MD5/HMAC` が多い)を hook してアルゴリズムと salt を得る。再現後、任意にパラメータを変えて sign を再計算して提出できる。判定基準:salt/鍵がクライアントで得られる = 署名を偽造できる = サーバー側の署名検証が有名無実。
**Q3**: アルゴリズムを再現したくない。より速い道はないか?
**A3**: 「App を署名/暗号化オラクルにする」。中間レイヤを立て、送りたい改変後の payload を hook 済みの App の暗号化/署名関数に与え、その出力を得てから提出する。アルゴリズムが複雑すぎ、リクエストが少量で済む場面に適する。自動化を犠牲に省力さを得る。
**Q4**: 署名にサーバー側配信のセッション因子やタイムスタンプが混ざり、オフラインの改変が署名検証を通らない?
**A4**: 「有効期間内のリアルタイム中継」に移る。mitmproxy スクリプトで App を常駐させてリアルタイム署名するか、hook 後の App に時間窓内で即時生成させる。タイムスタンプ/セッション因子は「オフライン大量偽造」を防ぐが、「リアルタイムに App の手を借りて署名すること」は防げない。
**Q5**: 暗号化+署名+リプレイ対策+デバイスバインドがすべてあり、リクエスト偽造の道が完全に通らない。どこへ移る?
**A5**: 「偽造せず、本物のリクエストをリプレイしてロジック脆弱性を探す」に移る。App の通常操作で本物の正当なリクエストを生成し、その中に権限外アクセス(ID を変えてサーバー側が許可)、競合状態、数量/価格の未再確認を探す。またはサーバー側の他の弱防御 API に移る。偽造対策は「正当なリクエスト自体が露呈するサーバー側のロジック欠陥」を防げない。
