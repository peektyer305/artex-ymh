# Appクライアント · Frida/hook 動的解析の意思決定

### 未知の APK/IPA を入手したらまず何をするか
**Q1**: 手元に未知のクライアントのインストールパッケージがある。対象はそれとバックエンドの通信の解析/ある検証の突破。hook を急がず、まず何をすべきか?
**A1**: まず静的偵察でマップを作り、それから hook 対象を決める。順序:解包してディレクトリ構造、`AndroidManifest.xml`(権限、Activity/Service、`android:debuggable`、`networkSecurityConfig`)、言語スタック(Java/Kotlin/Flutter/RN/Unity/ネイティブ so)の特定。判定基準:`lib/` 配下がすべて `libflutter.so`/`libil2cpp.so` なら、業務ロジックは Java レイヤになく、以降の hook 戦略は次元を丸ごと替える必要がある。いきなり `frida-trace` から始めず、まずロジックがどのレイヤにあるかを知る。
**Q2**: ロジックが主に Java レイヤか native レイヤかをどう素早く判断する?
**A2**: 逆コンパイル(jadx/apktool)後、Java コードの密度と `System.loadLibrary` の数を確認する。キー関数の本体が `native` 宣言で、Java レイヤがただのパッカー、または大量の JNI 呼び出しがあるなら、ロジックは so 内に沈んでいる。このとき Java hook では引数と戻り値の境界しか見えず、内部には native hook(`Interceptor.attach` + モジュールベース+オフセット)が必要。
**Q3**: 静的解析で暗号化アルゴリズムが分からない場合はどうする?
**A3**: 動的解析に移る。まず広域 hook で網を張る。`javax.crypto.Cipher`、`Mac`、`MessageDigest`、`java.util.Base64` を hook し、毎回の呼び出しのアルゴリズム名、key、iv、平文/暗号文を dump する。ランタイムに何を使っているかを語らせ、逆解析で粘らない。
**Q4**: 環境準備の落とし穴?
**A4**: frida-server のバージョンはホスト側の frida バージョンと厳密に一致させ、アーキテクチャ(arm64/arm)も合わせる。root/ジェイルブレイク環境、SELinux、frida-server のポート(デフォルト 27042)。判定基準:`frida-ps -U` でプロセスを列挙できれば経路が通っている。

### App が root/ジェイルブレイクを直接検知して終了する
**Q1**: App を起動するとすぐ「リスク環境を検知」と表示してクラッシュし、メイン画面にすら入れない。どう突破する?
**A1**: これは root/ジェイルブレイク検知。まず検知点を特定する。よくある指標関数を hook する。`Runtime.exec`(su を探す)、`File.exists`(/system/xbin/su、Magisk パスを確認)、`getprop`(ro.debuggable、ro.secure)、`PackageManager` で既知の root 管理ツールのパッケージ名を確認。判定基準:どの関数が戻った直後に終了分岐に入ったか、そこが検知点だ。
**Q2**: 1 点を hook して回避したら、別の検知がまた表示される?
**A2**: 検知は通常多重で冗長。1 つずつ hook せず、成熟した検知除去方式に変える。Magisk Hide/Zygisk + DenyList、または frida スクリプトで一類の検知をまとめて stub 化する。同時に `System.exit`/`Process.killProcess` を hook して保険をかける。検知が発動しても、その自殺動作を遮る。
**Q3**: 方式を替えてもなお検知され、しかも native レイヤでの確認と分かった?
**A3**: native の次元に移る。検知ロジックが so 内で直接 `fopen("/system/bin/su")` するか `/proc/mounts` を読む。`libc` の `fopen`/`open`/`stat`/`access` を hook し、機微なパスに ENOENT を返す。これは低レイヤ検知を回避する直交する打ち方だ。
**Q4**: frida まで検知される(アンチデバッグ)?
**A4**: あの「App が frida 注入を検知する」の条を参照。これは別の直交する問題なので、まず root 検知とアンチ frida を分けて処理し、混ぜて調整しない。

### App が frida 注入を検知して直接クラッシュする
**Q1**: frida を attach すると App が即クラッシュ、または数秒後にクラッシュする。アンチ frida を疑う。どう確認して回避する?
**A1**: まず frida 検知かどうかを確認する。attach ではなく spawn モードを使い、起動時か起動後かを確認する。よくある検知:`/proc/self/maps` を走査して `frida`/`gum-js-loop`/`gadget` の字句を探す、ポート 27042 を走査、`frida-server` のプロセス名を検知、スレッド名 `gmain`/`gdbus` を検知。判定基準:非デフォルトポート `frida-server -l 0.0.0.0:PORT` に変えて落ちなくなれば、それはポート検知だ。
**Q2**: ポートを変えても落ちる。maps 文字列の走査か?
**A2**: 魔改造版 frida(メモリ内の特徴文字列を変える、pipe 名を変える)を使うか、server モードではなく `frida-gadget` を再パッケージ化して注入する。判定基準:gadget はプロセス内に内蔵され、独立した server プロセスやデフォルトポートの特徴がない。
**Q3**: spawn のタイミングが早すぎて hook できず、attach は検知される。どうバランスを取る?
**A3**: `spawn` + `gating`/`-f` で一時停止させ、スクリプトを注入してから resume する。検知コードの実行前に検知関数を hook する。核心は検知より先に hook を完了すること。`pthread_create` を hook して検知スレッドの作成を事前に遮断できる。
**Q4**: 全部試してもアンチデバッグを回避できない場合はどうする?
**A4**: 注入しない直交する経路に移る。中間者キャプチャ(SSL pinning の条を参照)でネットワーク側からデータを取るか、静的計装の再パッケージ化(smali で検知を patch)してから frida に戻るか、objection の patchapk に替える。同じ注入の次元で粘らない。

### HTTPS トラフィックがキャプチャできない(証明書固定)
**Q1**: システムプロキシを設定し、CA 証明書を導入し、ブラウザではキャプチャできるが App の HTTPS はキャプチャできない。高い確率で SSL Pinning。どう特定する?
**A1**: まず代理が通っていないのではなく pinning かを確認する。エラーを見る。App 内でネットワーク失敗だがキャプチャツールにリクエストがない場合、トラフィックがプロキシを通っていないか握手が拒否されている。判定基準:`SSLContext`/`TrustManager`/`X509TrustManager.checkServerTrusted` を hook し、独自実装が例外を投げていないかを見る。
**Q2**: pinning と確認した。どう回避する?
**A2**: レイヤごとに試す。OkHttp は `CertificatePinner` を使うので、その `check` メソッドを hook して直接返す。汎用方式では objection の `android sslpinning disable` や、成熟した universal unpinning の frida スクリプト(TrustManager、OkHttp、Conscrypt、WebView の複数をカバー)を使う。判定基準:スクリプト読み込み後、プロキシで平文リクエストが見える。
**Q3**: 汎用スクリプトが効かない。pinning が native レイヤ(BoringSSL/自社)にある?
**A3**: native に移る。Flutter/自社ネットワークスタックは `libssl.so`/`boringssl` 内で `ssl_verify` を行う。`SSL_get_verify_result` を hook して 0 を返すか、`ssl_crypto_x509_session_verify_cert_chain` を hook する。Flutter はさらにシステムプロキシを通らないので、透過プロキシ(iptables リダイレクト)+ `BoringSSL` の hook が必要。
**Q4**: 証明書検証を回避したが App が自分のプロキシを通らない?
**A4**: これは直交する問題、代理感知だ。App がシステムプロキシを読まないようハードコードしている可能性がある(Flutter/一部の SDK)。VPN モードのキャプチャ(tun2socks/ProxyDroid など)に替えるか、iptables `REDIRECT` で透過プロキシポートへ流し、トラフィックを自分のキャプチャツールに強制的に落とす。
**Q5**: それでも失敗。双方向証明書(mTLS)?
**A5**: クライアントも証明書を持つ。App からクライアント証明書と秘密鍵を dump する(`KeyStore.load`/`PrivateKey` を hook するか、`.p12`/`.bks` ファイル+パスワードを探す)。それをキャプチャツールにインポートしてクライアント認証する。

### キー関数が見つからない、どこを hook すべきか
**Q1**: ある VIP 判定/署名生成を突破したいが、コードの難読化が激しく、どのメソッドを hook すればよいか分からない。どう素早く特定する?
**A1**: 「観測可能なアンカー」から逆算する。UI にヒント文字があるか。文字列リソースを検索してそれを参照するクラスを見つける。ネットワークリクエストがあるか。リクエストのパラメータ名からそれを生成するメソッドを逆引きする。判定基準:まず自分がトリガーできる挙動を 1 つ特定し、呼び出しチェーンを辿って探す。
**Q2**: 文字列が暗号化されて検索できない?
**A2**: ランタイムのスタックバックトレースを使う。必ず通る低レイヤ関数(暗号化、`toString`、`StringBuilder` など)を hook し、`Thread.currentThread().getStackTrace()` を表示する。呼び出しスタックからどの業務クラスが呼んだかを見る。ランタイムに呼び出し関係を露呈させる。
**Q3**: クラス名もメソッド名もすべて a/b/c に難読化されている。どう特定する?
**A3**: `frida-trace` または objection の `android hooking search classes/methods` でキーワードで網を張り、トリガー操作と合わせて、クリック時にどのメソッドが呼ばれるかを見る。または `ClassLoader.loadClass` を hook して何が動的に読み込まれたかを見る。メソッドシグネチャの特徴(引数の種別、戻り値の種別)で絞ることもできる。
**Q4**: 網を張った hook が多すぎて、ノイズがシグナルを覆う?
**A3**: 時間窓を狭める。トリガー操作の直前に trace を始め、操作後にすぐ止めて、この区間の呼び出しだけを見る。または差分を使う。操作 A を行って一組の呼び出しを記録し、操作 B を行ってもう一組を記録して、差集合を取る。
**Q5**: まったく特定できない。メソッドが native または動的生成?
**A5**: 次元を替える。DEX の動的読み込み/ホットフィックス/パッカー化の可能性があり、クラスが元の APK 内にそもそもない。`DexClassLoader`/`InMemoryDexClassLoader` を hook してランタイム DEX を dump するか、アンパックツール(FRIDA-DEXDump)でメモリから本物の DEX を回収して静的解析する。

### プロテクトのパッカーでコードが見えない
**Q1**: jadx で開くとパッカーの Application と数個のクラスしかなく、本物の業務コードが全部消えている。パッカー化されている。どうする?
**A1**: まずパッカーベンダーを識別する(360、Tencent 楽固、愛加密、梆梆などは特徴的な so 名とディレクトリを持つ)。判定基準:`lib/` 配下の特徴 so、`assets/` 内の暗号化 dex。パッカーによってアンパック法は異なるが、汎用の発想はメモリ dump だ。パッカーは最終的に本物の DEX を復号してメモリに読み込む。
**Q2**: 具体的にどうメモリからアンパックする?
**A2**: DEX の読み込み点を hook する。ART 上で `OpenMemory`/`DefineClass`/`DexFile` 関連を hook するか、既製のアンパック frida スクリプト(FRIDA-DEXDump)でプロセスメモリ内の dex magic(`dex\n035`)を走査して丸ごと dump する。判定基準:dump した DEX が jadx で開けて本物のロジックが見える。
**Q3**: 第一世代のパッカーはアンパックしやすいが、関数抽出(第二世代パッカー)に出会うと dump してもメソッド本体が空?
**A3**: 第二世代パッカーはメソッド本体をランタイムになって初めて回填する(instruction 抽出)。各メソッドを能動的に呼び出して回填をトリガーするか、インタープリタの実行入口(`ExecuteSwitchImpl`/`artInterpreterToInterpreterBridge`)を hook してメソッドごとに CodeItem を dump してから回填補完する必要がある。これはより重い直交する打ち方だ。
**Q4**: VMP パッカー(命令仮想化)はまったく dump できない?
**A4**: 戦略を替える。コード復元を諦め、挙動観測に変える。静的に復元できないなら、システム API を呼ぶ境界(crypto、ネットワーク、ファイル)で hook し、入出力からブラックボックスでロジックを推測する。レッドチームの対象は通常データ取得/検証回避で、必ずしもコードを理解する必要はない。

### hook できたがメソッドにオーバーロードがあり呼べない
**Q1**: hook を書いたが、frida がメソッドに複数のオーバーロード(overload)があるとエラーを返す。どう処理する?
**A1**: オーバーロードのシグネチャを明示的に指定する必要がある。`.overload('java.lang.String', 'int').implementation = ...`。判定基準:まず `.overloads` で全オーバーロードを表示するか、`.overload('...')` が不確かなときは `Java.enumerateMethods` で完全なシグネチャを見る。パラメータの種別は完全修飾名を書く。
**Q2**: 具体的にどのオーバーロードが呼ばれているか分からない?
**A2**: `.overloads.forEach` で全オーバーロードを hook し、それぞれが自分のシグネチャとパラメータを表示する。ランタイムでどれが発動したかを見る。特定後、対象のものだけを正確に hook する。
**Q3**: hook できたが implementation 内で `this.method()` による元メソッド呼び出しがエラーになる?
**A3**: overload コンテキストで元実装を呼ぶには `this.methodName.overload(...).call(this, args)` か直接 `this.methodName.apply(this, arguments)` を使う。this のバインドを保つこと。戻り値の種別も一致させる必要があり、基本型で undefined を返さない。
**Q4**: 内部クラス/匿名クラスのメソッドが hook できない?
**A4**: 内部クラスは `$` で連結する。`Outer$Inner`、匿名クラスは `Outer$1`。`Java.enumerateLoadedClasses` または `enumerateMethods` で実際のクラス名を確認してから hook する。

### タイミングが早すぎてクラスがまだ読み込まれていない
**Q1**: spawn モードで注入し、hook 対象クラスで ClassNotFoundException。クラスがまだ読み込まれていない。どうする?
**A1**: クラスはランタイムになって初めて読み込まれる。スクリプトの最上位で直接 `Java.use` せず、`Java.perform` 内に包み、クラス読み込み後まで遅延させる。判定基準:起動直後にエラーが出るなら、クラスがまだ ClassLoader に読み込まれていないことを示す。
**Q2**: どうクラス読み込みを待ってから hook する?
**A2**: `ClassLoader.loadClass` を hook し、対象クラス名が読み込まれたときに自分の hook を実行する。動的読み込みの DEX なら、`Java.enumerateClassLoaders` で対象クラスを担う ClassLoader を探し、`Java.classFactory.loader = その loader` で切り替えてから `Java.use` する。
**Q3**: 複数 ClassLoader 環境(プラグイン化/ホットフィックス)で `Java.use` がクラスを見つけられない?
**A3**: デフォルトの factory はデフォルト loader だけを検索する。全 classloader を走査して対象クラスを load できるものを見つけ、対応する `Java.ClassFactory` インスタンスを作って use する。これはプラグイン化 App のよくある落とし穴だ。
**Q4**: それでも読み込みタイミングを掴めない?
**A4**: 受動的な観測に移る。能動的に探さず、対象メソッドがあるクラスが必ず通る親クラス/インターフェースのメソッドを hook するか、いっそ `DexFile.defineClass` を hook して全量記録し、クラス読み込みイベントを自ら浮かび上がらせる。

### パラメータ/戻り値を変更しても効かない
**Q1**: hook 内で戻り値を変えて検証を回避したいが、App の挙動が変わらない。どういうことか?
**A1**: まず hook が本当に命中しているか確認する。implementation 内にログを加える。表示されなければ hook 点が間違い(オーバーロード間違い、クラス間違い、そもそもこのメソッドを通らない)。表示されても値の変更が効かないなら、検証結果がキャッシュされているか二次検証がある可能性。判定基準:ログはすべての切り分けの出発点だ。
**Q2**: 命中は確認したが、戻り値を変えても App が認めない?
**A2**: 変更が遅すぎた可能性がある。本当の判断は別の中間変数を使うか、結果が native レイヤで確定している。上流へ hook するか、この値を本当に消費する場所を探す。完全性の自己検証(署名検証の条を参照)があり、hook を検知してデグレードロジックに進んだ可能性もある。
**Q3**: 基本型の戻り値を変えてエラーになる?
**A3**: 種別を厳密に一致させる。`boolean` は `1` ではなく `true` を返す。`long` は JS の number を使わず(2^53 を超えると精度が失われる)、`.valueOf` か Frida の Int64/UInt64 を使う。オブジェクトを返すときは構築を正しくする。
**Q4**: パラメータが複雑なオブジェクトで変更できない?
**A4**: オブジェクトはそのメソッド/フィールドで変更するか、新しいインスタンスを構築して置換する。フィールドの変更は `obj._fieldName.value = ...`(プライベートフィールドは下線を付けるかリフレクションを使う)。配列、ByteArray は `Java.array` で処理する。
**Q5**: 全部正しいのに効かない。ロジックがこのレイヤにないことを疑う?
**A5**: native に移る。Java レイヤのこのメソッドは単なる転送で、本当の判断は JNI にある可能性。`Interceptor.attach` で対応する native エクスポート関数を hook し、native の戻り値を変える(`retval.replace()`)。

### 境界しか hook できず内部が見えない
**Q1**: キーロジックが native 関数で、Java hook では JNI 境界の引数と戻り値しか見えない。内部を見たい場合はどうする?
**A1**: native hook に移る。まず特定する。`Module.getBaseAddress('libxxx.so')` + 関数オフセット(エクスポート関数は `Module.findExportByName`、非エクスポートは IDA/Ghidra でオフセットを計算)。`Interceptor.attach` の `onEnter`/`onLeave` でレジスタとメモリを読む。
**Q2**: 関数がエクスポートされておらず、オフセットアドレスしかない。どう attach する?
**A2**: `base.add(0xOFFSET)` で絶対アドレスを得てから attach する。Thumb モードのアドレスは `|1`(arm32)に注意。判定基準:offset は静的解析(IDA)から、base はランタイムから取得し、両者を加算する。PIE では毎回 base が変わるので、必ずランタイムに取得する。
**Q3**: パラメータがポインタ/構造体で読めない?
**A3**: `args[n]` でレジスタ値を取り、`Memory.read*` でメモリを読む。`ptr.readCString()`、`readByteArray(len)`、`readPointer()`。構造体はオフセットに従ってフィールドごとに読む。ARM64 の引数は x0-x7。データフローを見たいなら `hexdump(args[0])`。
**Q4**: so にアンチデバッグ/自身の完全性検証があり、attach すると落ちる?
**A4**: so が `.text` セグメントの CRC を検証して inline hook を検知する可能性。`Stalker` による命令レベル trace(メモリを変えない)に替えるか、先にその完全性検証関数を hook するか、ハードウェアブレークポイント(`Process.setExceptionHandler`)で inline patch の代わりにする。

### 暗号化パラメータ、アルゴリズムを逆解析できない
**Q1**: リクエスト内に生成方法が分からない sign/token パラメータがある。偽造したいが、アルゴリズムの逆解析が遅すぎる。近道はあるか?
**A1**: レッドチームはアルゴリズムを逆解析する必要はなく、RPC のブラックボックス呼び出しでよい。frida で App 内の署名関数をリモート呼び出し可能な API(`rpc.exports`)として公開し、パラメータを渡すと署名を返す。判定基準:payload を入力して正しい sign を安定して得られれば、署名能力を所有したのと同じで、アルゴリズムの理解は不要。
**Q2**: 署名関数が App の内部状態(デバイスフィンガープリント、session)に依存する?
**A2**: App を実行状態に保って RPC を行い、本物のコンテキストを持ったまま計算させる。または先に hook してこれらの依存を dump して固定化する。判定基準:RPC が返す sign をサーバー側へのリクエストに使って検証を通る。
**Q3**: 大量に呼びたいが App の単一インスタンスは遅い?
**A3**: スケール化に移る。複数の App インスタンス+frida のプール化、またはキー so を取り出して unidbg で純粋なシミュレーション環境で大量実行する(実機から離脱)。unidbg は移植可能な純計算 so に適する。
**Q4**: unidbg が動かない(システム呼び出しへの依存が多すぎる)?
**A4**: 環境を補完するか、実機 RPC に戻る。unidbg は JNI/syscall 環境の補完が必要で、依存が重いとコストが高い。判定基準:so が Android framework に大量に依存するなら、実機の frida RPC を素直に使う方が速い。

### 内部関数を能動的に呼びたい
**Q1**: 内部メソッド(復号、招待コード生成など)を特定した。UI を通さず、それを直接呼び出して結果を得たい。どうする?
**A1**: 能動的呼び出し。静的メソッドは直接 `Java.use('Cls').method(args)` を `Java.perform` 内に包む。インスタンスメソッドはインスタンスが 1 つ必要。判定基準:静的で副作用の依存がないものが最も呼びやすい。
**Q2**: インスタンスメソッドで、既存のインスタンスがない?
**A2**: 2 つの道がある。`Java.choose('Cls', {onMatch})` でヒープから既存の生きたインスタンスを 1 つ掴んで呼ぶ(本物の状態付き)。または `Java.use('Cls').$new(...)` で自分で new する(構築パラメータを正しくする必要がある)。判定基準:内部状態に依存するなら choose、状態を持たないなら $new。
**Q3**: `Java.choose` がヒープ内でインスタンスを見つけられない?
**A3**: インスタンスがまだ生成されていないか、すでに回収された可能性。まず UI でトリガーして生成させるか、コンストラクタを hook してインスタンスをグローバル変数に保存し、後で使う。native 側のオブジェクトは hook でポインタをキャッシュする。
**Q4**: 呼び出しが例外/クラッシュを投げる?
**A4**: 大半は JNI/スレッドコンテキストの問題。能動的呼び出しは `Java.perform` 内で正しいスレッドで行う。UI に関わるメソッドはメインスレッドに attach する(`Java.scheduleOnMainThread`)。パラメータの種別不一致でも落ちるので、シグネチャを 1 つずつ照合する。

### WebView / ハイブリッド App、ロジックが JS 内にある
**Q1**: App の画面が WebView で表示する H5 で、業務ロジックが JS 内にある。frida で Java を hook しても何も見えない。どう解析する?
**A1**: 戦場を Web レイヤに移す。WebView のリモートデバッグを有効にする。`WebView.setWebContentsDebuggingEnabled(true)` を hook して強制有効化し、Chrome の `chrome://inspect` で接続して、直接ブレークポイントを張って JS を見る。判定基準:devtools でページの DOM とスクリプトが見えれば成功。
**Q2**: App が debugging を無効化し検知もする?
**A2**: スイッチを強制 hook で有効化し(上記)、検知点も hook する。または `WebView.loadUrl`/`evaluateJavascript` を hook して読み込む URL と注入スクリプトを見る。JS とネイティブの橋渡しは `addJavascriptInterface` を見る。hook すると JS に公開されたネイティブメソッドが見える。
**Q3**: キーロジックがネイティブと JS の橋渡し呼び出し内にある?
**A3**: `@JavascriptInterface` アノテーション付きのメソッド(JS がネイティブを呼ぶ入口)と `evaluateJavascript`/`WebMessage`(ネイティブが JS を呼ぶ)を hook する。この 2 方向で hybrid 通信のすべてをカバーする。
**Q4**: H5 が暗号化/パッカー化された JS?
**A4**: フロントエンドのリバースエンジニアリング次元に移る。devtools でランタイムに難読化解除、XHR ブレークポイントを張ってリクエスト生成を取得、または直接 console でそれが公開するグローバル関数を呼んで RPC する。純粋な Web リバースエンジニアリングと同じ方法だ。

### Flutter App、通常の hook がすべて無効
**Q1**: 対象が Flutter 製で、Java hook では業務を取得できず、プロキシでもパケットを取得できない。通常の定石が全滅。どう手を付ける?
**A1**: Flutter の特性を認識する。業務ロジックは `libapp.so`(Dart AOT)にコンパイルされ、システム proxy を通らず、自前の BoringSSL で TLS を行う。だから 2 つの本線がある。キャプチャは透過プロキシ + BoringSSL の hook、ロジック解析は native so を読む。判定基準:プロキシにトラフィックがなくデバイスは正常に接続している場合、Flutter がシステムプロキシを読んでいない。
**Q2**: どう Flutter の HTTPS をキャプチャする?
**A2**: iptables/tun でトラフィックを透過的にキャプチャツールへリダイレクトし、`libflutter.so` 内の `ssl_verify_result`(reFlutter またはコミュニティスクリプトでオフセットを特定)を hook して証明書検証を無効化する。reFlutter ツールは再パッケージ化してトラフィックをプロキシに流し dump もできる。
**Q3**: `libapp.so` 内の Dart ロジックを解析したい?
**A3**: Dart AOT 専用ツール(reFlutter、Doldrums、blutter など)で Dart snapshot を解析し、クラス名・メソッド名の構造を復元する。純粋な IDA で Dart runtime を見るのは非常に苦しく、専用ツールならシンボルを復元できる。
**Q4**: バージョンが新しすぎてツールが非対応?
**A4**: ブラックボックスに移る。復元を諦め、直接透過プロキシでネットワーク挙動を見るか、`libflutter` の HTTP レイヤ関数を hook して平文リクエストを dump する。レッドチームはデータが欲しいので、必ずしも全コードを復元する必要はない。

### frida のスクリプト読み込みが無応答/フリーズ
**Q1**: スクリプト注入後、App がフリーズするか frida が無出力。スクリプトの問題か環境の問題かをどう切り分ける?
**A1**: 二分法。まず空スクリプトか `console.log('ok')` だけを注入する。正常なら環境は通っており、スクリプトのロジック問題。空スクリプトでも固まるなら、環境/注入の問題。判定基準:空スクリプトが出力できるか。
**Q2**: 空スクリプトは正常、hook を加えると固まる?
**A2**: よくある死因:高頻度関数(`StringBuilder.toString` など)を hook して IO ストームを起こす、implementation 内で同期ブロックする、無限ループ、メインスレッドで重い処理をする。hook 範囲を狭め、高頻度 hook を外し、console.log を減量するか非同期にする。
**Q3**: attach は成功したが対象メソッドがまったく発動しない?
**A3**: このコード経路を通っていない、クラス名/オーバーロードが間違い、またはインライン最適化された可能性。ログを加えて hook が attach 成功したか(attach 時に 1 回表示)、さらにメソッドが本当に呼ばれたかを確認する(別の必ず通るメソッドで hook 機構自体に問題がないか検証)。
**Q4**: 偶発的で、良かったり悪かったり?
**A4**: 競合状態だ。spawn 注入のタイミングとクラス読み込みが競合する。一時停止注入(`-f` + スクリプト内で遅延/クラス読み込み待ち)に変える。または frida-server が不安定なので、server を再起動するか安定版に替える。

### データがメモリ内で平文だが、正確に取得したい
**Q1**: 機微データ(鍵、平文)がどこかの時点でメモリ内にあると分かっているが、どの関数が処理するか分からない。取得したい。どうする?
**A1**: 2 つの道がある。データの特徴(固定プレフィックス/長さなど)が分かれば `Memory.scan` でメモリを走査して一致させる。具体値が分からなければ、データが必ず通る処理関数を hook する。判定基準:平文サンプルや特徴パターンがあれば直接 scan してアドレスを特定し、メモリブレークポイントを張って誰がアクセスするかを見る。
**Q2**: アドレスを特定後、誰が読み書きするかを知りたい?
**A2**: `MemoryAccessMonitor` またはハードウェアブレークポイントでそのアドレスの読み書きを監視し、発動時に呼び出しスタックを表示して、アクセスするコードを特定する。これは「データからコードを逆算する」打ち方だ。
**Q3**: データが使い終わるとすぐゼロクリアされて取得できない?
**A3**: タイミングを先取る。ゼロクリア関数(`memset`/Arrays.fill)の直前で取得するか、その生成関数を hook して生成の瞬間に dump する。メモリに入ってから走査せず、源流で直接遮る。
**Q4**: メモリ内が暗号化されており、平文を走査できない?
**A4**: 復号の境界に移る。メモリ内も暗号文なら、復号は使用の最後の瞬間に起きる。crypto の復号関数を hook し、`onLeave` で復号後の平文出力を取得する。

### アンチデバッグで attach 後プロセスが kill される
**Q1**: attach して数秒後にプロセスが自ら死ぬ。ログはアンチデバッグによる切断を示す。デバッグセッションをどう維持する?
**A1**: アンチデバッグ機構を特定する。よくあるもの:`ptrace(PTRACE_TRACEME)` による自己保護、`/proc/self/status` の TracerPid の検知、frida 特徴スレッドの定期検知。判定基準:TracerPid が 0 以外なら終了が発動する。`ptrace` を hook して成功を返すが実際には呼ばない、`fopen("/proc/self/status")` を hook して TracerPid を 0 に改ざんする。
**Q2**: 独立したウォッチドッグスレッドが定期検知する?
**A2**: `pthread_create` を hook し、ウォッチドッグスレッドの入口関数を識別して、その作成を遮断するか関数本体を空回りさせる。または検知関数を見つけて直接 `Interceptor.replace` で空実装にする。
**Q3**: native レイヤの `ptrace` 検知が so 初期化(JNI_OnLoad)で実行され、hook が間に合わない?
**A3**: so 読み込み前に hook する。`dlopen`/`android_dlopen_ext` を hook し、対象 so の読み込み完了後、`JNI_OnLoad` 実行前に自分の hook を差し込む。または `linker` の `call_constructors` を hook する。タイミングが肝心だ。
**Q4**: 全部回避できない。アンチデバッグが頑固すぎる?
**A4**: attach に依存しない経路に移る。アンチデバッグの smali/マシンコードを静的に patch してから再パッケージ化するか、エミュレータ/unidbg で実機のアンチデバッグ環境から離脱するか、ネットワーク側から MITM でデータを取る。次元を変えて正面から当たらない。

### App の操作を大量自動化したい(API の不正利用)
**Q1**: 署名ロジックを解析し終えた。API を大量に回す/自動化したいが、毎回手動では遅すぎる。どうスケール化する?
**A1**: 2 レイヤに分ける。署名能力は frida RPC で公開し(前述の条)、大量リクエストは外部スクリプト(Python)で組織する。App は署名計算だけを担い、リクエストはスクリプトが送る。判定基準:UICI を離れ、純粋な HTTP + RPC 署名で 1 回通す。
**Q2**: デバイスフィンガープリント/風控が単一デバイスにバインドしている?
**A2**: フィンガープリント収集点(IMEI、Android ID、MAC、デバイス機種)を hook して 1 セットに統一して偽造するか、複数セットのフィンガープリントを多重起動する。風控の次元は、それが何を収集するかを具体的に分析し、項目ごとに制御可能にする。
**Q3**: サーバー側に頻度制限/挙動風控がある?
**A3**: これは業務風控対抗の次元に移る。リクエストのリズムを擬人化し、IP をローテーション(プロキシプール)、デバイスフィンガープリントと token をローテーションする。同じフィンガープリントで高頻度に打たない。
**Q4**: RPC 並列時に App が落ちる/アカウントが混ざる?
**A4**: 単一 App インスタンスはスレッド安全でなく、アカウントが混ざりやすい。複数インスタンスの分離(インスタンスごとに 1 セットのコンテキスト)に変えるか、RPC 呼び出しを直列化してロックする。または so を取り出して unidbg でステートレスに並列署名計算する。

### キャプチャで暗号化 body を見たが、改変してリプレイしたい
**Q1**: リクエストを取得したが body が暗号化。パラメータを改ざんしてリプレイし、権限外アクセス/価格変更をテストしたいが、暗号化を変えられない。どうする?
**A1**: ネットワークレイヤで変えず、暗号化前に変える。暗号化関数の `onEnter` を hook して平文 payload を得て、ここでパラメータを改ざんし、App に自分の改変後の平文で再暗号化させて送信する。判定基準:取得した暗号文が変わり、サーバー側が受け入れること=改変成功。
**Q2**: レスポンスを変えたい(サーバー側が返す「権限なし」を「権限あり」に変えるなど)?
**A2**: 復号関数の `onLeave` を hook し、復号後の平文レスポンスを得て、改ざんして業務ロジックに返す。これはクライアント側の権限外アクセステストの定番ポイント。ただしこれはローカル表示にだけ影響し、本当の権限外アクセスはサーバー側で見る必要がある。
**Q3**: 暗号化にタイムスタンプ/nonce のリプレイ対策が付き、リプレイが失敗する?
**A3**: 旧パケットのリプレイではなく、RPC でリアルタイムに再署名する。毎回のリクエストで sign+タイムスタンプをその場で計算する。リプレイ対策は署名能力の所有を要求する(RPC の条を参照)ので、単純なリプレイではない。
**Q4**: 平文を変えたが、body の完全性 HMAC 検証が合わない?
**A4**: HMAC もクライアントで計算される。その入力を hook して改変後の body を使い、一致する新しい HMAC を計算させる。鍵/アルゴリズムがクライアントにある限り、すべての検証は追って再計算できる。

### 署名/完全性検証が改ざんを検知する
**Q1**: 再パッケージ化(smali を patch)後、App が起動時に「アプリが改ざんされた」と出て終了する。署名検証が発動した。どう通す?
**A1**: 検証点を特定する。App が自身の署名(`PackageManager.getPackageInfo` で signatures を取得してハッシュ照合)を検証する。`getPackageInfo`/`GET_SIGNATURES` を hook して元の署名情報を返す。判定基準:hook 後、改ざんの警告が出なくなる。
**Q2**: 検証が native レイヤで APK ファイルを読んで hash を計算する?
**A2**: native に移る。so 内で APK を `fopen` して自ら CRC/hash を計算し照合する。ファイル読み取りを hook して元の内容を返すか、照合関数を hook して等しいと返す。またはいっそ再パッケージ化せず、frida のランタイム patch に変える(ファイルを変えなければファイル完全性検証は発動しない)。
**Q3**: SafetyNet/Play Integrity のリモート証明がある?
**A3**: これはサーバー側の検証で、ローカル hook は対症療法に過ぎない。方向転換:attestation を通せる環境を使う(ハードウェア級で回避困難)、または検証ロジック自体を攻める(サーバー側がこの attestation 結果をどう使うか)、または機能のデグレードを受け入れる。ハードウェア証明は直交する強い防御だ。
**Q4**: 多重検証(署名+CRC+SafetyNet)が重なっている?
**A4**: 検証を発動させない経路を優先する。再パッケージ化ではなく純粋な frida のランタイム注入で、ファイル完全性と署名検証を根本から回避する。ファイルを変えずに済むなら変えないのが、すべての静的完全性検証を回避する上策だ。

### iOS ジェイルブレイク環境下の hook の違い
**Q1**: 対象が iOS App で、ジェイルブレイク機で解析する。Android とどう意思決定が異なり、まず何をする?
**A1**: iOS のロジックは主に Objective-C/Swift の Mach-O 内にある。まず復号する(App Store のパッケージは暗号化されている)。frida-ios-dump/dumpdecrypted でアンパックして平文の実行ファイルを得る。判定基準:class-dump でクラスとメソッドを列挙できればアンパック成功を示す。
**Q2**: OC メソッドはどう hook する?
**A2**: frida の `ObjC.classes['ClassName']['- methodName:'].implementation` で hook するか、`ObjC.chooseSync` でインスタンスを取得する。OC ランタイムはリフレクション可能で、Android より hook しやすい。`frida-trace -m '-[Class method]'` で網を張る。
**Q3**: Swift メソッド(OC runtime なし)が hook できない?
**A3**: 純 Swift で OC 橋渡しのないメソッドは、シンボル/オフセットで native hook(`Interceptor.attach` + `Module.findExportByName`)する。またはそれが呼ぶ OC/Foundation の境界を hook する。Swift の名前は mangled なので、demangler で復元する。
**Q4**: SSL pinning / ジェイルブレイク検知?
**A4**: Android と同じ発想だがツールが異なる。ジェイルブレイク検知は `fork`/`stat`(/Applications/Cydia.app を確認)/`dyld` で注入ライブラリを確認、pinning は SSL Kill Switch または frida unpinning。検知の原理は通じ、API を iOS のものに替えるだけだ。
**Q5**: ジェイルブレイクしていない機体はどうする?
**A5**: 再署名注入に移る。frida-gadget で再署名してパッケージ化する(開発者証明書が必要)か、objection の patchipa を使う。ジェイルブレイクなしでは gadget 内蔵方式を使い、利便性を犠牲に実現可能性を得る。

### hook 位置は正しいがインライン/最適化で消えた
**Q1**: 小さな関数を hook したいがまったく発動しない。コンパイラにインライン化された疑い。どう確認して対処する?
**A1**: native の小さな関数はよく inline 化され、呼び出し点が直接展開され、attach できる独立した関数入口がない。判定基準:IDA 内でその関数への call が見えない、または関数が小さい。対処:その呼び出し元(caller)を展開処理の位置で hook するか、Stalker の命令レベル trace で対応する命令セグメントを見つける。
**Q2**: Java レイヤのメソッドが ART に最適化され(AOT でマシンコードにコンパイル)、hook が不安定?
**A2**: frida の Java hook はインタープリタ/JIT 入口に依存し、AOT メソッドは回避される可能性。`frida --runtime` 関連の設定を使うか、逆最適化を強制する。objection/frida の新版は AOT に対処している。より上層の最適化されていない入口を hook することもできる。
**Q3**: hook したいが関数に安定した入口アドレスがない?
**A3**: Stalker でモジュール/スレッド全体の命令追跡を行い、対象コードセグメントの実行を特定し、命令レベルでレジスタ変化を観測する。Stalker は関数境界を必要とせず、インライン/難読化で明確な入口がないコードに適する。
**Q4**: Stalker が遅すぎてデータに埋もれる?
**A4**: 範囲を限定する。特定スレッドだけ follow、トリガー操作の時間窓内だけ追跡、`Stalker.exclude` で無関係なモジュールを除外。または先にモジュールを大まかに特定してから局所的に精密追跡する。

### マルチプロセス App、間違ったプロセスに注入した
**Q1**: hook が反応しない。App がマルチプロセス(:push、:remote などの独立プロセス)で、注入したのはメインプロセスだがロジックが子プロセスにある。どうする?
**A1**: まずプロセスを列挙する。`frida-ps -Ua` でその App の全プロセスを見る。判定基準:対象機能のあるプロセスはメインプロセスとは限らない(プッシュ、決済は独立プロセスのことが多い)。対象クラスを担うプロセスを見つけてから attach する。
**Q2**: 子プロセスが動的に fork されたもので、まだ起動していない。どう attach する?
**A2**: frida の child gating(`enable_child_gating`)で、子プロセスの fork/spawn 時に一時停止して注入する。または `Process.fork`/`Runtime.exec` を hook して子プロセス生成を捕捉する。こうして生まれたばかりの子プロセスを掴める。
**Q3**: ロジックがどのプロセスにあるか確信がない?
**A3**: 各プロセスに探針スクリプト(`Java.enumerateLoadedClasses` で対象クラス名を grep)を注入する。どのプロセスで対象クラスを列挙できるか、ロジックはそこにある。プロセスリストで 1 つずつ切り分ける。
**Q4**: プロセス間通信(AIDL/Binder)こそがキー?
**A4**: IPC の次元に移る。Binder トランザクション(`transact`/`onTransact`)を hook してプロセス間で渡るデータを見るか、`Messenger`/`ContentProvider` の境界を hook する。ロジックはマルチプロセスの協働に分散しうるので、IPC データフローを取得するのが最も直接的だ。

### 時間/環境依存で挙動が再現できない
**Q1**: あるバグ/機能が特定条件でのみ発動する(特定時刻、特定地域、特定バージョン)。安定して再現して解析したい。どうする?
**A1**: 環境収集点を hook して統一して偽造する。時間依存は `System.currentTimeMillis`/`Date` を hook。地域は `Locale`/`TelephonyManager` の国コードを hook。バージョン判定はバージョン読み取り関数を hook。環境変数を自分が制御可能な定数に変える。
**Q2**: サーバー側が配信するスイッチ(feature flag)に依存する?
**A2**: 設定解析箇所を hook し、サーバー側が返すスイッチフィールドを望む値に変える。その flag を読むメソッドを見つけ、戻り値のときに改ざんする。こうしてグレーリリース中の機能をローカルで強制有効化する。
**Q3**: A/B グループに依存し、自分のデバイスが実験グループに入っていない?
**A3**: グループ判定ロジックまたはグループ ID 生成(よくデバイス ID のハッシュに基づく)を hook し、対象グループの値に偽造する。または「実験グループかどうか」の判定関数を直接 hook して true を返す。
**Q4**: すべてサーバー側制御で、クライアント hook が無効?
**A4**: サーバー側の視点に移る。クライアントを変えられないなら、対象パラメータ付きのリクエストを直接構成してサーバー側 API を攻め、クライアントのグレーリリースを回避する。グレーリリースは往々にしてクライアントの表示制御に過ぎず、API 自体は直結できる。

### frida で App の二重プロセス守護・相互起動を検知
**Q1**: App に守護プロセスがあり、メインプロセスを kill するか注入で異常になると、守護プロセスがすぐそれを再起動し、状態が全部失われる。どう安定して解析する?
**A1**: まず守護機構を識別する。二重プロセスの相互監視、`JobScheduler`/`AlarmManager` による定期起動、native `fork` による守護。判定基準:プロセスを殺すと即座に復活する。対処:2 つのプロセスを同時に凍結/注入するか、先に起動ロジックを hook して無効化する。
**Q2**: 守護プロセスもデバッグを検知し、連動して終了する?
**A2**: child gating で親子プロセスを同時に引き継ぎ、検知除去スクリプトを統一的に注入する。2 つのプロセスを 1 つの全体として処理し、1 つだけを見ない。
**Q3**: 起動が速すぎてタイミングを掴めない?
**A3**: まず守護/起動のトリガー点(`AlarmManager.set`、`startService`、native fork)を hook して守護を無効化し、復活チェーンを断ってから、ゆっくりメインプロセスを解析する。先に守護を解体してから解析する。
**Q4**: 守護がシステム級(アカウント同期、アクセシビリティ)で無効化しにくい?
**A4**: 環境分離に移る。制御されたエミュレータ内でネットワーク断/特定コンポーネントの凍結、または Xposed/LSPosed のモジュールレベルで引き継ぎ、フレームワークレイヤから起動挙動を抑える。プロセス内で対抗しない。

### 取得したデータがクライアントかサーバー側の脆弱性かの判断
**Q1**: hook で、クライアントに「VIP かどうか」のローカル判定があり変更できると分かった。ローカルを変えると解除される。これは脆弱性か、次にどう判断する?
**A1**: キーの判定基準:クライアント変更後、機能が実際に効き、サーバー側が認めるか。ローカル hook で UI は解除されるが、制限データのリクエストをサーバー側がなお拒否する場合、純粋なクライアント表示の回避で価値は低い。サーバー側も許可するなら本当の権限外アクセスで価値が高い。実際のリクエストを送ってサーバー側の態度を検証する必要がある。
**Q2**: 「クライアントの偽解除」と「サーバー側の本当の脆弱性」をどう区別する?
**A2**: 対照実験を行う。hook で解除後、制限操作をトリガーし、キャプチャでサーバー側のレスポンスを見る。サーバー側が本当の制限データを返す場合、サーバー側がクライアントを信頼した(脆弱性)。サーバー側が拒否を返す場合、単なるローカル回避。常にサーバー側のレスポンスを基準にする。
**Q3**: サーバー側もクライアントが送る「vip=true」を信頼していると分かった?
**A3**: サーバー側の権限外アクセステストに移る。これはサーバー側が認可判断をクライアントに委ねたことを示し、定番のクライアント信頼脆弱性。リクエストを直接構成してこのフィールドを変え、各 API のサーバー側認証がどれもこれほど緩いかを大量テストする。
**Q4**: 成果を広げたい?
**A4**: この信頼欠陥から横方向に列挙する。クライアントがほかにどの「本来サーバー側が判断すべき」フィールド(価格、ユーザー ID、権限ビット)を送るか。サーバー側が検証するかを 1 つずつ測る。クライアントのリバースエンジニアリングの価値は、サーバー側 API とパラメータを露呈させ、サーバー側の深掘りに供することにある。

### 鍵がハードコードされているが平文を取得できない
**Q1**: 暗号化鍵が App 内にハードコードされている疑いがあるが、静的に検索できず、文字列がランタイムに組み立てられる。どう本物の key を得る?
**A1**: 組み立てロジックを静的に逆解析せず、使用点で動的に取得する。`SecretKeySpec` のコンストラクタ、`Cipher.init` を hook し、鍵がパラメータとして渡るときに直接 dump する。判定基準:key のバイト配列を hook できれば平文鍵を取得したことになる。
**Q2**: key が native レイヤで生成され、Java に入らない?
**A2**: native に移る。native の crypto ライブラリ(`libcrypto`/自社)の key 設定関数(`AES_set_encrypt_key`、`EVP_EncryptInit` など)を hook し、パラメータから key を読む。または暗号化関数の入口で鍵バッファを dump する。
**Q3**: key がホワイトボックス暗号(ホワイトボックス AES)で、独立した key がない?
**A3**: ホワイトボックスは key をルックアップテーブルに溶け込ませ、抽出可能な key がない。ブラックボックスに移る。key の抽出を諦め、その加解密関数を直接 RPC 呼び出ししてオラクルとして使う。加解密能力があれば十分で、key を所有する必要はない。
**Q4**: key がハードウェア keystore(TEE)にある?
**A4**: TEE 内の key はエクスポートできない。同じく RPC/オラクルの発想に移る。App に keystore 内の key で自分に代わって加解密させる。または業務が本当にこの key の機密性に依存するかを分析し、key そのものではなくその使用ロジックを攻める。

### リバースエンジニアリングで独自プロトコル(非 HTTP)を発見
**Q1**: キャプチャで App とバックエンドが HTTP を通らず、TCP 上の独自バイナリプロトコルと分かった。キャプチャツールで復号できない。どう解析する?
**A1**: socket の境界から hook する。`SocketOutputStream.write`/`InputStream.read`(Java)または `send`/`recv`(native)を hook し、送受信の生バイトを dump する。判定基準:平文のバイトストリームを得てからプロトコル構造(長さヘッダー、種別、payload)を解析する。
**Q2**: payload がさらに暗号化/シリアライズ(protobuf など)されている?
**A2**: 上流へ hook する。シリアライズ/暗号化の前の業務オブジェクトレイヤで取得する。protobuf の `toByteArray` 前のオブジェクト、または暗号化前の平文を hook する。socket レイヤは最外層で、本当に読めるデータは業務レイヤにある。
**Q3**: プロトコルにハンドシェイク/ハートビートがあり、オフラインのリプレイが難しい?
**A3**: RPC で App 内の生きた接続を維持し、その接続を借りて自分が構成したパケットを送る。またはプロトコルを復元してからスクリプトで完全なハンドシェイクを実装する。独自プロトコルは RPC で借りるのが最も省力なことが多い。
**Q4**: バイナリ形式をまったく解けない?
**A4**: 差分解析に移る。他の条件を固定し、操作を 1 つだけ変えて、バイトストリームの差異を比較し、フィールドごとに意味を推測する。シリアライズ点を hook してフィールド名からバイトへのマッピングを見るのと併用する。ブラックボックス差分はプロトコル形式を無理に逆解析するより速い。

### frida か Xposed/LSPosed か
**Q1**: 解析タスクで、いつ frida を使い、いつ Xposed/LSPosed に移るか。どう選ぶ?
**A1**: 判定基準は場面を見る。素早い反復デバッグ、native hook、一時的な探索は frida(スクリプト変更が即時反映、再起動不要)。持続化、起動時自動実行、フレームワーク級の安定した引き継ぎ、長期の常駐は Xposed/LSPosed。レッドチームの偵察段階は frida、利用の固定化/長期駐留は Xposed。
**Q2**: frida の検知が厳しすぎる。より隠密なものに替えたい?
**A2**: LSPosed(Zygisk ベース、プロセス内 hook、独立 server/ポートの特徴なし)に移ると比較的隠密。または Xposed モジュール。あるいは frida を魔改造して特徴を除去する。選定自体が一種の検知回避の方向転換だ。
**Q3**: 両方とも検知される?
**A3**: 静的計装に移る。smali/dex を直接変更して再パッケージ化して hook 効果を実現し、ランタイムに注入フレームワークの特徴を一切残さない。柔軟性を犠牲にランタイム特徴ゼロを得る。または VirtualApp/サンドボックスコンテナで対象 App を読み込み、制御環境で hook する。
**Q4**: 柔軟性と隠密性を両立したい?
**A4**: frida-gadget をライブラリ形式で App に再パッケージ化し、独立プロセスを持たない。またはカスタム hook フレームワークを使う。検知強度に応じて「柔軟-隠密」の軸上で点を選ぶ。万能解はなく、対抗の激しさに応じて調整する。

### App のキー操作に人機検証/スライダーが必要
**Q1**: 自動化時にスライダー/行動認証コードに当たり、hook でも通らない。人機検証で詰まっている。どう切り替える?
**A1**: まず認証コードの統合方法を分析する。SDK(极驗/Tencent 防水墙の類)か自社か。判定基準として、リクエスト内の検証 token がどこから来るかを見る。標準 SDK なら、その結果コールバックを hook して直接「検証通過」を返し、サーバー側がこの token だけを認めるかを見る。
**Q2**: hook でコールバックを通したが、サーバー側が token の有効性を二次検証する?
**A2**: 検証がサーバー側に強くバインドされ、ローカル hook が無効であることを示す。方向転換:検証 SDK のリクエスト生成を RPC で再利用できるか分析する(App に本物の検証を 1 回通させて token を得る)、または自動化のその操作への依存を下げる。
**Q3**: 認証コードを完全に回避できない?
**A3**: 攻撃面を替える。検証が必要なその API を回避し、検証不要の同機能 API を探す(他端/旧バージョンの API に検証がないことがある)。または検証がキー操作にだけあるなら、自動化の対象を検証不要の箇所に変える。
**Q4**: 分析したいだけで、量を回すのではない?
**A4**: ならば回避は不要。手動で検証を通してから frida で後続ロジックを観測すればよい。対象を区別する。分析は手動でコードを通す+hook 観測。大量処理で初めて検証回避が必要。分析問題を対抗問題にしない。

### バージョン更新後にオフセットが全部無効になる
**Q1**: 以前書いた native hook スクリプト(so オフセット基準)が、App 更新後にすべて無効になった。更新ごとにオフセットを再計算するのは大変だ。どうする?
**A1**: ハードコードのオフセットを動的特徴の特定で置き換える。バイトコードパターン(pattern)で `Memory.scan` を使い関数特徴を検索するか、エクスポートシンボルで、または文字列参照のクロス参照で関数入口を特定する。判定基準:バージョンを替えてもスクリプト変更なしで特定できること=特徴一致成功。
**Q2**: 関数にシンボルがなく、特徴もバージョンで変わる?
**A2**: 相対的な特定を使う。安定したアンカー(定数文字列、システム呼び出し、安定したエクスポート関数)から出発し、呼び出し関係や相対オフセットで対象を導く。アンカーが安定するほど、スクリプトは更新に強い。
**Q3**: オフセット依存から完全に脱却したい?
**A3**: シンボル/安定 API のあるレイヤへできるだけ上に移す。Java レイヤのメソッド名は native オフセットより安定。システム API(libc、JNI)は業務 so より安定。安定レイヤで hook すれば業務更新に耐えられる。
**Q4**: 変わりやすい native 関数を必ず hook しなければならない?
**A4**: 自動化した特定に移る。静的解析(IDA/Ghidra スクリプトで特徴から関数を探す)から自動的にオフセットを生成して frida に渡すスクリプトを書く。「毎回手計算」を「毎回自動計算」に変える。バージョン反復へのエンジニアリング対抗だ。

### 本番環境しかなく、乱暴にテストできない
**Q1**: 対象 App が本番環境しかなく、直接の自動化/パッケージ変更で風控のアカウント停止や実データへの影響が怖い。どう慎重に進める?
**A1**: まず読み取り専用の観測を行ってから手を付ける。第 1 段階は純粋な hook 観測(パラメータを読み、ロジックを見る)で異常リクエストを送らず、理解を構築する。判定基準:観測段階で異常トラフィックを一切発生させず、ゼロリスクで機構を把握する。
**Q2**: リクエストを送って脆弱性を検証しなければならない?
**A2**: テストアカウント、少額、ロールバック可能な操作で先に検証し、メインアカウントで高危険操作を打たない。影響範囲を制御する。先に脆弱性の存在を証明し(単発の小サンプル)、それから拡大するかを評価する。レッドチームも付随的損害を制御する必要がある。
**Q3**: hook 挙動そのものが風控にマークされるのを懸念する?
**A3**: 擬人化+低頻度+分離環境。独立デバイス/アカウントを使い、通常の使用リズムを模擬し、マシン特徴の露呈を避ける。風控対抗は始終付きまとう制約で、最後に考え始めるものではない。
**Q4**: 環境が本当に機微すぎる?
**A4**: オフライン/ミラー環境に移る。キー so を取り出して unidbg でオフライン実行するか、ローカル mock サーバーを立ててプロトコルを再現するか、テスト環境を申請する。破壊的検証を本番に影響しないサンドボックスに移す。

### 解析が行き詰まったときの体系的な切り替え方
**Q1**: あるクライアント解析が長く詰まり、hook すべきものは hook したのに欲しいものを得られない。どう体系的にどこへ切り替えるか判断し、やみくもに試さない?
**A1**: 「ロジックがどのレイヤにあるか」の座標系に戻って確認する。Java レイヤ → native so → Dart/Unity/JS → サーバー側。今どのレイヤで詰まっているか、隣接レイヤへ探す。判定基準:Java 境界でデータが native に入って出てこないなら、答えは native にある。native も転送なら、答えはサーバー側にある。レイヤごとに除外する。
**Q2**: レイヤをすべて切り分けてもなお詰まる?
**A2**: 観測次元を替える。「コードロジックの変更」から「データフローの観測」(crypto/socket/ファイル IO の 3 大境界を hook)、「静的復元」から「動的ブラックボックス RPC」、「クライアント」から「サーバー側 API への直結」。3 組の直交する次元のどれかは必ず突破できる。
**Q3**: 方向が最初から間違っていた疑い?
**A3**: 対象の本質を再点検する。欲しいのはデータか?→ データ境界を取得するだけで、コードを理解する必要はない。欲しいのは検証回避か?→ 検証点を探すだけで、アルゴリズムを理解する必要はない。欲しいのは署名能力か?→ RPC で、アルゴリズムを逆解析する必要はない。多くの行き詰まりは「レッドチームの対象」を「完全なリバースエンジニアリング対象」と取り違えたことに由来する。
**Q4**: 時間コストが高すぎる。損切りすべきか?
**A4**: この道の限界利益を評価する。対象が他の攻撃面(Web 側、ミニプログラム、公開 API、旧バージョン App)からより省力で達成できるなら、攻撃面を替える。クライアントのリバースエンジニアリングは手段であって目的ではない。対象への最短の道を進む。
**Q5**: 完全に発想が尽きた?
**A5**: 偵察に戻る。情報収集をもう一度やり直す。初回に見落とした手がかり(未解析の so、隠し Activity、デバッグ API、コメント内のテストアドレス、他のエンドポイント)がよくある。詰まったとき、補足の偵察はその場で hook を増やすより効果的なことが多い。
