# Appクライアント · C/Sアーキテクチャのパケットキャプチャとプロトコル解析

### 冒頭の三問:まずキャプチャか、まずリバースエンジニアリングか、まず権限リストか
**Q1**: 未知の App(Android/iOS/PC リッチクライアント)を入手し API を攻めたいが時間が限られている。どこから切り込むべきか?
**A1**: 3 つの道を並行してコストを判断する。(a) まず透過プロキシで一巡キャプチャし、トラフィックが HTTP を通るかを確認する。20 分で結論が出る。(b) apk/ipa を取得し、静的解析で AndroidManifest / Info.plist、usesCleartextTraffic、network_security_config、pin 宣言の有無を確認する。10 分で結論が出る。(c) 公開された API ドキュメントや web 版の同源 API があるかを確認する。3 つを同時に進め、先に手がかりが出た方に従う。
**Q2**: 3 つとも思わしくない。どれを続けて粘る?
**A2**: 優先して【フィンガープリント】を埋める。APK を apktool + jadx で開き、キーワード okhttp/retrofit/pinner/certificate/x509/protobuf/grpc/websocket/xxtea/aes を検索し、15 分以内にそのネットワークスタックが何かを特定する。プロトコルスタックが決まって初めて、以降のすべてのツール選択に根拠ができる。
**Q3**: 静的解析がすべてパッカー(360/愛加密/娜迦/梆梆)で、ソースがまったく見えない。どうする?
**A3**: ランタイムに移る。実機にインストールし、まず一巡動かして logcat を取得し、クラッシュ/ログの漏えいを見る。同時に frida-ps / objection でランタイムのプロセスを探り、attach できるかどうかが以降のすべての hook 戦略を決める。
**Q4**: 静的も動的も遮られ、attach すら許可されない?
**A4**: 直交する切り替え。クライアントを攻めず、サーバー側を攻める。たとえ 1 つでも取得できたリクエストから、ドメイン/API パスを抽出し、web 面/H5 版/ミニプログラム版に対して直接 API 列挙を行う。これらは通常バックエンドを共有し、pin がより弱い。
**Q5**: 判定基準は何か。いつ App 側を諦めてサーバー側を攻めるのか?
**A5**: 判定基準:2〜4 時間以内に平文トラフィックをプロキシ内に出現させられず + 静的解析が高度に難読化 + ジェイルブレイクしていない iOS。このとき、クライアントに粘る限界利益は急激に下がるので、直接バックエンドを攻める方が割に合う。

### HTTPS 証明書導入後、App が起動するとすぐ接続が切れる
**Q1**: プロキシと CA 証明書を導入済みで、ブラウザではキャプチャできるが、App を開くとすぐ「ネットワーク異常」。最初に何と判断すべきか?
**A1**: 3 つの可能性を同時に切り分ける。(1) App に SSL Pinning がある。(2) App が SNI を通るか、非 HTTP プロトコルを通っていてプロキシをまったく経由していない。(3) システムレベルのユーザー CA が Android 7+ では App に信頼されない(システム CA に導入するか network_security_config を変更する必要がある)。mitmproxy の tls_passthrough で、ハンドシェイクがクライアント側から能動的に RST されていないか観察する。
**Q2**: ハンドシェイクは完了したが直後に close_notify。誰が閉じている?
**A2**: 高い確率でクライアントの pin 検証失敗による能動的な切断。logcat に SSLHandshakeException / certificate pinning failure / trust anchor の類のログがないか確認する。この種のスタックは pin 命中の鉄の証拠だ。
**Q3**: ハンドシェイクがプロキシにまったく届いていない。これは何を意味する?
**A3**: App が独自の TCP/UDP チャネルを通っているか、SNI over TLS 以外のプロトコル(QUIC/自社プロトコルなど)を使っていることを意味する。方向転換として tcpdump を取得し、実際のポートとプロトコルの特徴を確認する。
**Q4**: pin と確認したが、apk を変更して再パッケージ化したくない。より速い道はないか?
**A4**: 優先して objection --gadget xxx explore + android sslpinning disable を一気に使う。よくある okhttp / trustmanager / conscrypt をまとめて通す。成功率は 60% 以上。通らなければカスタム frida スクリプトに移る。
**Q5**: objection の一括対処が成功せず、スタックにそれが hook する類のクラスがない。どうする?
**A5**: 【native レイヤ】に移る。pin 検証が so 内に沈められている(SSL_CTX_set_verify / SSL_get_verify_result)。frida の Interceptor.attach + Module.findExportByName で boringssl の SSL_verify 関数を探し、直接 1 を返させる。
**Q6**: この道が塞がれている(so がパッカー化、エクスポートシンボルが剥がされている)場合は?
**A6**: 直交する切り替え。pin を回避せず、【サーバー側証明書チェーンを差し替える】。App が pin しているのがリーフ証明書ではなくルート CA や中間 CA の公開鍵なら、システム CA で同じ CN の証明書を発行できる。あるいは直接【プロトコル経路をダウングレード】する。App に HTTP fallback がないか確認する(HTTPS の失敗が繰り返されると HTTP に戻る App がある)。

### SSL Pinning の具体的な種別の判断
**Q1**: すでに pin があると確認した。どの回避方式を使うか決める前に、pin がどのレイヤに張られているかを知る必要がある。どう素早く判断する?
**A1**: 4 レイヤに分けて切り分ける。(a) Java レイヤの X509TrustManager の自前実装。(b) OkHttp の CertificatePinner。(c) Conscrypt/TrustManagerImpl レイヤに hook を張る。(d) Native so 内の BoringSSL/OpenSSL の SSL_CTX_set_verify または自前の検証。frida でレイヤごとにログを出し、どのレイヤが checkServerTrusted / verify に入ったか、そこが主戦場だ。
**Q2**: 4 レイヤすべてに hook でログを張ったのに、1 つも入らずリクエストが切れる?
**A2**: pin がより早い段階にあることを意味する。【証明書チェーン解析前】の生の DER バイト比較、あるいは SPKI ハッシュを比較している可能性がある。方向転換として read/recv または SSL_read を hook し、ハンドシェイク段階の生バイトを見て、比較ロジックを特定する。
**Q3**: クライアントが証明書を検証しておらず、【サーバー側が返す業務フィールドの署名】を検証している。pin はただの目くらましか?
**A3**: 業務レイヤの逆解析に移る。verifySign / checkResponse / RSA.verify を検索する。このとき TLS レイヤを回避するだけでは不十分で、業務レスポンスも一緒に署名を偽造する必要がある。

### 双方向 TLS(mTLS)のクライアント証明書はどこから来るか
**Q1**: ハンドシェイクを取得し、サーバー側が Certificate を要求し、クライアントも素直に提示したことを確認した。まず何をする?
**A1**: クライアント証明書と秘密鍵を抽出する。3 つの可能性のある隠し場所がある。(1) apk/ipa の assets 内の .p12/.pfx/.bks/.jks ファイル。(2) so 内にハードコードされた DER バイト。(3) ランタイムにサーバー側から配信されて keystore に保存されたもの。まず grep -r "BEGIN CERTIFICATE" と、特徴バイト 30 82(DER ヘッダー)を grep する。
**Q2**: p12 を見つけたがパスワードが必要?
**A2**: KeyStore.load の char[] password パラメータを hook して直接表示する。または PKCS12 関連の呼び出しを hook して password を遮断する。iOS では SecPKCS12Import を hook する。
**Q3**: 証明書がランタイムに動的に申請されるもの(デバイスフィンガープリントと引き換えに証明書を得る)か?
**A3**: セッションの再利用に移る。SSLContext.init を hook して、初期化済みの KeyManager を取得し、メモリ内の PrivateKey.getEncoded() をエクスポートする。または SSLContext 全体を dump して自分のプロキシで再利用する。
**Q4**: 証明書が TEE / SE / Keychain 内にあり、秘密鍵がエクスポート不可で、署名操作はデバイス内でしかできない?
**A4**: 直交する切り替え。秘密鍵を再利用せず、【デバイスを署名オラクルにする】。App プロセスを生かしたまま、App に TLS ハンドシェイクやデータ署名を完了させ、自分はそれが何を送るかだけを操作する(frida rpc / 中間者による業務関数の引数の乗っ取り)。

### 平文は取れたが body が暗号文
**Q1**: TLS を回避し、リクエストもプロキシに入ったが、body が読めない base64/hex の塊。どう暗号化種別を判断する?
**A1**: 長さとエントロピーを見る。(a) 長さが 16 の倍数 → 高い確率で AES-CBC/ECB。(b) 長さは不定だが固定の先頭 12/16 バイトがある → nonce 付き GCM/CCM。(c) 先頭に 128/256 バイトの定長ブロックがある → RSA/ECDH で包んだ session key。(d) 高エントロピーで完全にランダム → すでに最終暗号文なので、鍵の出どころを探す必要がある。
**Q2**: 鍵がハードコードされて見つからない。ランタイムにネゴシエーションされたものか?
**A2**: 暗号化関数の入口を hook する。SecretKeySpec/Cipher.init/Cipher.doFinal(Java)、CCCryptorCreate(iOS)、EVP_EncryptInit_ex(native)を検索し、key と iv を出力する。key を取得できれば、すべてをオフラインで復号できる。
**Q3**: 暗号化が so に沈められ、関数名が剥がされ、VMP 保護がある?
**A3**: 【逆解析せず、データフローだけを観察する】に移る。ネットワークの出口(SSL_write / send)と暗号化関数の出口のバイトを hook し、同時に平文の入口(App 内で業務レイヤが encrypt を呼ぶ前の String 引数)を hook する。平文から暗号文への経路はコードを理解する必要がなく、両端のバイトを突き合わせれば加解密の結果を知ったのと同じになる。
**Q4**: 平文の入口も取れない(protobuf シリアライズ後すぐに暗号化されるなど)?
**A4**: 直交する切り替え。App を【加解密オラクル】にする。frida rpc を書き、任意の入力を与えて暗号化結果/復号結果を返させ、自分は外部で攻撃 payload を構成する。アルゴリズムを知る必要はない。
**Q5**: 判定基準は、いつ暗号化に粘るのをやめるか?
**A5**: 2〜3 時間 key を特定できず、しかも App が継続的に hook してオラクルとして使えるなら、直接オラクルモードに切り替えて前進する。省いた時間で業務ロジックを攻める。

### リクエスト署名フィールド(sign/token)の逆方向特定
**Q1**: リクエスト内に sign=xxx や X-Signature ヘッダーがあり、リプレイ時に 1 バイト変えるだけで 400 になる。どう署名生成点を特定する?
**A1**: 3 つの入口に同時に罠を張る。(1) java.security.MessageDigest.update/digest を hook して MD5/SHA の入力を出す。(2) javax.crypto.Mac.doFinal を hook して HMAC の入力を取得する。(3) frida で "sign" / "signature" の文字列参照を検索する。署名生成前には必ず update が 1 回あり、update の入力を呼び出し順に並べれば署名原文になる。
**Q2**: update が大量に出るが、どれがそれか分からない?
**A2**: 【バックトラック法】を使う。まず sign の値を取り、hook 内で「どの digest の戻り値がこの sign と等しいか」を絞り込む。その回の入力が署名原文だ。
**Q3**: 署名が標準ライブラリを通らず、自前の xxtea / murmur / crc の亜種か?
**A3**: 文字列定数から逆算する。magic 数(xxtea の 0x9E3779B9 など)、salt 文字列、ユーザー情報と連結される固定の前後缀を検索する。native レイヤなら .rodata を検索する。
**Q4**: 署名原文の一部がデバイスフィンガープリント/タイムスタンプ/nonce で、オフラインの再計算がいつも数桁ずれる?
**A4**: フィールドごとに揃える。スクリプトを書いて列挙する。タイムスタンプの精度は秒かミリ秒か。nonce は UUID か。deviceId は IMEI か androidId か自前 UUID か。フィールド順はパラメータ名の辞書順か API 固定順か。1 回でもずれたらこの 4 点を確認する。
**Q5**: 全部揃えてもなおずれる。これは何を意味する?
**A5**: 【隠しフィールド】が存在する。署名原文に、リクエスト内に現れないもの(app バージョン、チャネル番号、前回のレスポンスの token)が混入している。方向転換として署名関数の呼び出しスタック周辺のすべての String 変数を dump すれば、必ず見つかる。
**Q6**: 署名ロジックが so 内にあり、VMP で、引数が取得できない?
**A6**: オラクルモードに移る。署名関数を hook し、任意の原文を与えて任意の署名を得て、自分は外部で構成する。

### 独自バイナリプロトコルのゼロからの逆解析
**Q1**: tcpdump で TCP トラフィックを取得したが、HTTP ではなく独自バイナリ。最初の一手はどう切る?
**A1**: 【長さプレフィックス】と【magic】を探す。先頭 4 バイトが残りの長さと等しいか(ビッグ/リトルエンディアン両方試す)、先頭 2/4 バイトが固定の magic か(0xDEADBEEF、0xAABBCCDD など)を見る。フレーム境界を見つけて初めて他を語れる。
**Q2**: 長さプレフィックスが合わない。1 つの TCP メッセージに複数フレームが詰め込まれている?
**A2**: 複数の接続の先頭バイト分布を観察する。通常ヘッダー構造は一致する。統計法を使う。各メッセージの先頭 N バイトを頻度分析し、固定値の位置が magic/type、変化するが相関する位置が length/seq。
**Q3**: プロトコル内のフィールドが TLV 構造だが tag 番号が分からない?
**A3**: App のリバースエンジニアリングと組み合わせる。native レイヤで write/send 前の buffer 構築関数を hook する。通常 pack_uint32 / write_varint の類の補助関数があり、その中で tag と value を分けて書き込む。それらを hook すれば tag の意味を再構築できる。
**Q4**: プロトコル全体が暗号化され、ハンドシェイク前の数パケットが DH/ECDH 交換か?
**A4**: クライアントの EC_POINT_mul / X25519 / DH_compute_key を hook し、shared secret を得れば以降のすべてのフレームを復号できる。ECDH 曲線は native 内で P256/curve25519 を検索して確認する。
**Q5**: プロトコルは独自に見えるが、実は標準プロトコル(MQTT/AMQP/RTMP/自社で protobuf を被せたもの)か?
**A5**: 先頭 3 バイトと第 5〜10 バイトを標準プロトコルの magic と一巡比較する。数日節約できる。protobuf シリアライズの特徴は tag<<3|wiretype で、先頭バイトはよく 0x08/0x10/0x1A。
**Q6**: まったく見当がつかず、動的解析も使えない?
**A6**: 直交する切り替え。【サーバー側の挙動】を観察する。異なるリクエストが異なるレスポンスサイズ、異なる遅延を引き起こすことから、プロトコル構造を推測できる。または、そのベンダーが類似 SDK をオープンソース化していないか、GitHub に古いバージョンのコードが漏れていないかを調べる。

### protobuf で proto ファイルなしのフィールド復元
**Q1**: protobuf と確認したが、.proto ファイルがない。どうフィールドを復元する?
**A1**: protoc --decode_raw または blackboxprotobuf で、まずバイトを field number + wiretype + value の三つ組の木に分解する。このときフィールドの【種別】と【入れ子構造】が出る。あとはフィールド名だけだ。
**Q2**: フィールド名は以降の fuzz に影響するか?
**A2**: 構成には影響せず、可読性にだけ影響する。攻撃時は field number で構成できる。フィールド名は業務の意味を推測するときにだけ有用だ。
**Q3**: フィールドの意味を知りたい?
**A3**: App 側から逆に調べる。jadx で protobuf が生成したクラス(GeneratedMessageLite や protobuf 関連の基底クラスを持つ)を検索すると、クラス内のフィールド名が field number にマッピングされており、直接読める。または protobuf クラスの getXxx() メソッドを hook して戻り値を見る。
**Q4**: クライアントも純バイナリで生成クラスがなく、nanopb か C++ の直接の符号化・復号化か?
**A4**: 相関性の観察に移る。リクエストを 1 回送り、パラメータを 1 つ変えて(ログインでユーザー名の長さを変えるなど)、protobuf 内のどのフィールドが変わるかを見て、1 対 1 に対応させる。
**Q5**: フィールドの変化が複雑すぎて対応が見えない?
**A5**: 差分キャプチャ+変数の固定化を使う。毎回 1 つの変数だけを変え、連続して 10 組のサンプルを取得し、フィールド単位の diff を行う。そのフィールドだけが変わっているものが対象だ。

### gRPC / HTTP2 のキャプチャ
**Q1**: 取得したのが HTTP/2 で、body がバイナリかつ :path が /svc/method 形式。gRPC と判定する。どう復号する?
**A1**: mitmproxy は HTTP/2 をサポートする。payload の先頭 5 バイトは gRPC フレームヘッダー(1 バイトの圧縮フラグ+4 バイトの長さ)で、その後が protobuf。protobuf のフローに従って復号する。
**Q2**: gRPC over TLS でクライアント証明書付き?
**A2**: mTLS のあのチェーンの解法に進み、クライアント証明書を取り出して再利用する。
**Q3**: gRPC-Web または Connect プロトコル亜種を使っている?
**A3**: 特徴は content-type: application/grpc-web または application/connect+proto。対応する proxy(Envoy や grpcurl など)で転送する。通常の mitmproxy ではきれいに截れないことがある。

### WebSocket 長接続のキャプチャとリプレイ
**Q1**: App の主要業務が WebSocket を通り、キャプチャでは upgrade 後しか見えず、平文がない?
**A1**: mitmproxy の websocket モード、または Charles/Burp の WS パネルを使うと、各フレームのテキスト/バイナリを表示できる。TLS を回避すれば WS フレームが直接見える。
**Q2**: WS 内のメッセージも暗号化/独自カプセル化されている?
**A2**: 【body 暗号文】のあのチェーンに進み、まず WS の onMessage / send 前後の加解密関数を特定する。
**Q3**: WS にハートビートがあり、サーバー側が無効なクライアントを切断する。リプレイはどうする?
**A3**: オフラインでのリプレイはできず、【本物の接続を維持する】必要がある。スクリプトを書く。まず App に接続を張らせ、sessionid / cookie を取得し、自分で wscat / websockets ライブラリで接続を引き継ぐ。または App をオンラインに保ち、frida で指定メッセージを注入する。
**Q4**: WS にシーケンス番号があり、サーバー側が厳密にインクリメントする?
**A4**: クライアントの send 関数を hook して現在の seq を得て、自分が引き継ぐときはこの seq から続ける。またはいっそ全工程を frida rpc で App に送らせる。

### QUIC / HTTP3 がキャプチャできない
**Q1**: プロキシに何もなく、tcpdump で大量の UDP:443 を確認。QUIC と判定する。どうする?
**A1**: 3 つの道がある。(1) 強制ダウングレード。iptables/ファイアウォールで UDP:443 を drop すると、App は通常 HTTP/2 over TCP に戻る。(2) QUIC をサポートする mitm(mitmproxy の新版や専用 QUIC proxy)を使う。(3) SSLKEYLOGFILE 環境変数でセッション鍵をエクスポートして Wireshark で復号する。
**Q2**: App が戻らず、QUIC のみで動き、pin 付き?
**A2**: クライアントの QUIC ライブラリ(よくあるのは cronet / quiche)の hook に移り、アプリケーションレイヤで平文を得て、ネットワークレイヤで復号しない。
**Q3**: クライアントが cronet を so に静的コンパイルしている?
**A3**: cronet の高レイヤ API(UrlRequest.write / onResponseStarted)を直接 hook する。このレイヤではバイトはまだ平文だ。

### エミュレータ識別によりデバッグできない
**Q1**: App がエミュレータに入るとすぐ終了し、「エミュレータ非対応」と表示する。どうする?
**A1**: 何を検知しているかを判断する。build.prop 内の ro.product.model / ro.hardware / ro.kernel.qemu、/dev 配下の qemu 関連デバイス、CPU 情報内の Goldfish/Ranchu、センサー数、Bluetooth、SIM カード。magisk + build.prop の変更、または frida で Build クラスの静的フィールドを hook する。
**Q2**: 変更してもなお終了する。native レイヤの検知があることを示す?
**A2**: __system_property_get を hook し、qemu 関連の key の戻り値をすべて改ざんする。またはいっそ実機+root に移り、一挙に解決する。
**Q3**: 実機も「異常環境」と識別される?
**A3**: 高い確率で magisk/root/frida を検知している。hidden 方式に移る。Magisk DenyList、Zygisk、shamiko。frida は attach ではなく frida-gadget の静的注入を使う。
**Q4**: すべて識別される。素早く検証したくて、粘りたくない?
**A4**: 直交する切り替え。クライアント環境を修正せず、【本物のクリーンなデバイスを 1 台用意】して実機操作を行い、tcpdump/pcap でネットワークレイヤで取得する。クライアントプロセスには触れない。pin は依然として処理が必要だが、検知の関門は直接回避できる。

### Root/ジェイルブレイク検知で App が起動を拒否
**Q1**: App が root を検知して直接クラッシュする。3 分以内の特定はどうする?
**A1**: よくある検知点を hook する。File.exists で /system/xbin/su を判定、Runtime.exec("su")、getprop で ro.build.tags が test-keys か、PackageManager で Magisk/Xposed のパッケージ名を確認。iOS も同様:stat /Applications/Cydia.app、fork() != -1、dyld 内で substrate/substitute を検索。
**Q2**: 検知点が多すぎて、1 つずつ hook するのは遅すぎる?
**A2**: 既製品を使う。RootBeer / anti-detect の frida スクリプト、objection の android root disable、iOS では A-Bypass / Shadow のジェイルブレイク検知回避プラグイン。8 割の App は直接通る。
**Q3**: 既製品が通らない。自社 SDK レイヤの検知(楽固/易盾など)があることを示す?
**A3**: 文字列を取得してその SDK の検知関数を特定する。一般に checkEnv / isSafe / getSecInfo という名前で、bool またはエラーコードを返す。hook して「安全」を強制返却する。
**Q4**: その関数が VMP 内にあり、hook できない?
**A4**: 【後続の消費点を乗っ取る】に移る。どう検知するかは問わず、最後は必ず結果に基づいて「終了するか」を決める。その System.exit / abort / ポップアップの呼び出し点を探し、上流の条件を短絡させる。
**Q5**: 検知+終了がすべて native にあり強く連動している。ほかに道はあるか?
**A5**: 直交する切り替え。root を使わず、【root なし方式】を使う。iOS は sideload + TrollStore、Android は VirtualApp/太極 陽/Xposed の root なし方式で App を制御されたコンテナ内で動かす。

### Frida が検知される/殺される
**Q1**: attach すると App がすぐ終了するか、そもそも attach できない?
**A1**: よくある検知:/proc/self/maps 内で frida/gum/gadget を検索、ポート 27042 の走査、D-Bus の検知、スレッド名の検知。frida-gadget でポートを変更+プロセス/スレッド名を変更+関連 syscall を hook する(openat で /proc/self/maps へのリクエストを遮断し、フィルタ済み内容を返す)。
**Q2**: 上記の一般的な回避がすべて対策されている?
**A2**: hook エンジンを替える。Xposed / LSPosed(zygote ベースで、gadget を注入しない)を使うか、stalker + ハードウェアブレークポイントという非侵襲の方式を使う。
**Q3**: より軽量にしたい?
**A3**: unicorn/qiling でオフラインシミュレーションに移り、so 内の暗号化関数を取り出して自分のプロセスで動かす。App プロセスに触れる必要はない。「ある関数を復号したいだけ」という場面に適する。
**Q4**: 対象関数が JNIEnv / 外部状態に依存し、シミュレーションが動かない?
**A4**: 直交する切り替え。App 全体をリバースエンジニアリングして純粋なアルゴリズム実装を探し、Python/JS 版に書き直す。または規約外のデバイスを 1 台オラクルとして使い、adb + socket で計算させる。

### ハードコードされた key が見つからない、すべてランタイムの組み合わせ依存
**Q1**: 静的に文字列をくまなく検索したが key らしきものがない。確実にランタイムで組み立てられる?
**A1**: 3 つの組み立て方を切り分ける。(1) ユーザー情報+定数 salt を連結してハッシュ。(2) サーバー側の初回レスポンスで配信。(3) native 内のバイト配列から復号。それぞれ、Cipher.init の key パラメータを hook、onResponse 内のフィールド解析を hook、so 読み込み時の復号関数を hook する。
**Q2**: key がサーバー側から配信されるなら、初回リクエストはどう暗号化する?
**A2**: 必ず【ブートストラッププロトコル】がある。通常、最初のリクエストは固定 key(ハードコード/RSA で暗号化された一時 key)でハンドシェイクを完了し、その後 session key に切り替える。そのブートストラップパケットの暗号化関数を探す。そこが死点で必ず解ける。
**Q3**: 起動のたびに key が異なり、オフライン再現が困難?
**A3**: オフラインを諦め、【リアルタイムプロキシ】モードに進む。mitmproxy addon が中間で key を取得したらその場で復号し、オフラインでのリプレイ可能性は追求しない。
**Q4**: オフラインでも復号したい?
**A4**: key をディスクへ書き出す。Cipher.init を hook したとき key + リクエスト id を sqlite に保存し、以降のオフライン解析ではリクエスト id から key を逆引きする。

### iOS でジェイルブレイクなし環境のキャプチャ方法
**Q1**: 対象は iOS App で、ジェイルブレイクしたデバイスがなく、購入予算も足りない。どうする?
**A1**: 3 つの道がある。(1) sideloadly / AltStore で SSKS(SSL Kill Switch)dylib 付きのバージョンを再署名し、pin を無効化してから通常デバイスにインストールする。(2) TrollStore(特定の iOS バージョン)を使う。ほぼジェイルブレイクと同等。(3) 保証切れの古い iPhone を 1 台見つけて直接ジェイルブレイクする。
**Q2**: 対象 App に再署名対策の検知がある(署名や embedded.mobileprovision を検証)?
**A2**: 検知点の hook に移る。コード署名検証は一般に SecCodeCopySelf を通るか、直接 __TEXT セグメントのハッシュを読む。dylib レイヤで hook して無効化する。
**Q3**: iOS の条件がまったく整わない?
**A3**: 直交する切り替え。Android 版は通常 iOS とバックエンド API を共有するので、Android をキャプチャすればプロトコルを取得したのと同じ。純粋な iOS 独占機能でない限り。

### クライアントのリプレイ対策(timestamp+nonce+sign)がリプレイを阻む
**Q1**: 取得したリクエストを 5 秒後にリプレイすると「リクエスト期限切れ」や「nonce 重複」を返す?
**A1**: 3 つのフィールドが抵抗因子だ。timestamp(有効期間は通常数秒〜数分)、nonce(単調増加またはランダムで重複除去)、sign(前 2 つのハッシュ)。リプレイするには【再署名】できる必要があり、再署名には key が必要。あの「署名フィールド特定」のチェーンに戻る。
**Q2**: 署名アルゴリズムを得て再署名できるようになったが、サーバー側がなお拒否する?
**A2**: nonce のポリシーを確認する。サーバー側が nonce 集合を保存して重複除去しているなら、同じ nonce は 1 回しか使えない。毎回のリプレイで新しい nonce に変える必要がある。クライアントの単調 seq なら、サーバー側が記録する最新 seq を予測する必要がある。
**Q3**: nonce がユーザーセッション関連の UUID で、推測できない?
**A3**: 【セッション内構成】に移る。オフラインのリプレイではなく、現在の App のセッションを引き継ぐ。hook または mitm で【現在送信中の】リクエスト内容を変更し、timestamp/nonce は App 自身が生成した正当な値を使う。

### JSBridge / WebView ハイブリッドアプリのキャプチャ
**Q1**: 対象 App の主要業務が WebView 内で動く H5 で、Native はただのパッカー。どうキャプチャする?
**A1**: WebView にプロキシ設定があればシステムプロキシを通る(容易)。pin は通常 WebViewClient.onReceivedSslError 内で proceed するので回避しやすい。本当の作業は JSBridge にある。native と JS が通信する API が攻撃面だ。
**Q2**: どう JSBridge のメソッドを列挙する?
**A2**: addJavascriptInterface を検索し、登録されたオブジェクト名とメソッドを列挙する。iOS では WKUserContentController.add を検索する。列挙後、JS console から直接呼び出す。権限は往々にして予想を超える。
**Q3**: WebView が独自の URL 遮断プロトコル(xxbridge://... など)を使っている?
**A3**: shouldInterceptRequest / shouldOverrideUrlLoading を hook してすべての URL を表示し、プロトコル形式を逆算する。
**Q4**: JSBridge に token 検証が加わり、信頼された H5 だけが呼べる?
**A4**: 【信頼された H5 ドメインを乗っ取る】に移る。中間者としてそのドメインが返す JS を差し替え、自分の payload を埋め込む。または WebView が file:// でローカルリソースを読み込むのを許す脆弱性を利用する。

### キャプチャ環境は正常だが業務機能が異常
**Q1**: キャプチャはすべて順調だが、ログイン/決済の類のキー API がキャプチャ環境下では通らない。キャプチャしなければ通る?
**A1**: 高い確率で【風控レポート】が発動している。App は異常環境下で意図的に機能を失敗させ、使える返却サンプルを与えない。追加のリクエストが風控 API(よくある数社のクラウドベンダーの風控 SDK ドメイン)に送られていないか確認する。
**Q2**: 風控のレポート点を見つけた。無効化したい?
**A2**: 3 つの打ち方がある。(1) レポートリクエストを hook し、常に「環境正常」を返させる。(2) レポート結果の処理を hook し、業務レイヤが常に safe を得るようにする。(3) いっそレポートのネットワークを断つ。iptables でそのドメインを遮断すると、ある種の App はネットワーク断時に「信頼」にフォールバックする。
**Q3**: サーバー側が端末上のシグナルを信頼せず、独自の二次判断(デバイスフィンガープリントの逆引き)をする?
**A3**: 【デバイスフィンガープリントの偽造】に移る。IMEI/androidId/mac/画面解像度/タイムゾーンを統一して偽造し、サーバー側に同一の通常デバイスと思わせる。
**Q4**: 風控を打ち崩せない。素早く業務サンプルを得たい?
**A4**: 直交する切り替え。実機に替え、キャプチャせず【物理レイヤの記録】を使う。スマホの画面録画 + adb logcat + Charles は http の観察側としてのみ(TLS を復号しない)。動くサンプルを得てからオフラインで解析する。

### 短接続 vs 長接続の混在
**Q1**: App が HTTP 短接続(ログイン、照会)と長接続(プッシュ、チャット)を同時に使っている。全部キャプチャしたい?
**A1**: HTTP は標準プロキシを通る。長接続は一般に socket または WS で、任意の TCP をサポートするキャプチャツールが必要。mitmproxy の tcp mode + wireshark の 2 つのツールを使う。
**Q2**: 長接続が独自 TLS 上のプライベートプロトコルか?
**A2**: あの「独自バイナリプロトコル」のチェーンに進む。TLS を回避した後、アプリケーションレイヤのバイトストリーム解析に入る。
**Q3**: 短接続と長接続の両端のフィールドに関連がある(短接続で配信された token が長接続の認証で使われる)?
**A3**: キャプチャの順序が重要だ。まず短接続のレスポンスを記録し、次に長接続の最初のハンドシェイクパケット内に同じ token が含まれるかを見て、マッピング関係を構築する。以降は短接続の token で長接続をこじ開ける。

### クライアントが大量の業務をローカルに置き、サーバー側 API がごく薄い
**Q1**: キャプチャで、キー業務(価格計算、クーポン判定など)がクライアントで完結し、サーバー側 API が検証しないことが分かった?
**A1**: 天与の好機だ。ローカルを直接改ざんするか、リクエストを改ざんする。どのフィールドが「クライアントが自分のために計算したもの」で、どれが「サーバー側に送り返すもの」かを判断する。前者はローカルを変更すればよく、後者はサーバー側が信じるか次第。
**Q2**: サーバー側が自分のデータだけを信じ、クライアントのレポートを無視する?
**A2**: ならばクライアントのローカル改ざんは自分の UI を騙せるだけ。サーバー側が【ローカルデータを読み取った後に検証せず使う】API を探す方向に移る。通常は決済/注文/ポイント交換などの業務にある。
**Q3**: サーバー側が厳密に検証し、クライアント側もローカルで二次検証する?
**A3**: 業務ロジックの脆弱性に移る。競合状態、金額の負数、クーポンの二次使用、注文状態の権限外アクセス。この種はキャプチャとの関係がむしろ薄い。

### ハートビート/keepalive 構造の逆解析
**Q1**: 長接続が数秒ごとに小さなパケットを送る。内容は固定か極めて簡素に見える。解析する必要はあるか?
**A1**: ある。ハートビート内には時間同期、セッション token、位置やデバイス情報が含まれることが多く、プロトコルヘッダー構造を研究する天然のサンプルだ。ハートビートを 20 個取得して diff し、変化する位置が【動的フィールド】、固定位置が【プロトコルの骨格】。
**Q2**: ハートビートが完全に固定バイトで、情報を提供できない?
**A2**: ならばそれは単なるキープアライブの役割。あの【ハートビート直後の最初の業務パケット】を見る方向に移る。通常、ハンドシェイク/補完パケットがハートビート確立後にトリガーされる。
**Q3**: ハートビート周期そのものがキャプチャ対策のシグナル(周期のドリフトで環境を検知)か?
**A3**: ネットワークのタイミングを厳密に保つ方向に移る。プロキシで人為的な遅延を入れないか、透過プロキシ(proxy ではなくルート書き換え)を使って観測可能な差異を減らす。

### TLS フィンガープリント(JA3/JA4)によるクライアント環境の識別
**Q1**: サーバー側が JA3 に基づいて mitmproxy/curl を拒否し、本物の App の TLS スタックだけを信頼する?
**A1**: 特徴:本物の App は通るが、自分で curl/burp を通したハンドシェイクは 403。判定基準は、レスポンスの差異が【リプレイ側】が異なるときだけ現れることだ。
**Q2**: どう回避する?
**A2**: curl-impersonate / mitmproxy の tls_start hook、またはフィンガープリント偽造専用のライブラリ(utls など)を使い、client hello 内の cipher_suites / extensions / groups の順序を実機と一致するように調整する。
**Q3**: サーバー側が HTTP/2 の SETTINGS フレーム、window_size までフィンガープリントに含めている?
**A3**: 【物理デバイスの中継】に移る。実機上にプロキシ App(Termux + mitmproxy または自前 socks)を配備し、外部マシンのリクエストをこの実機経由で出網させる。フィンガープリントが自然に一致する。

### リバースエンジニアリングが完全に行き詰まったら、サーバー側 API 攻撃へ
**Q1**: クライアント保護が厳しすぎて、1 週間かけても pin/暗号化/風控の 3 層を崩せない。諦めるべきか?
**A1**: 判定基準:攻撃対象が「サーバー側データ/権限へのアクセス」で、クライアントは入り口に過ぎないなら、それが動かないときはサーバー側を攻める方向に移る。サーバー側は通常、チーム内でより脆弱な一環だからだ。
**Q2**: サーバー側攻撃に移るが、手元に API ドキュメントがない。どう始める?
**A2**: 他の情報源から。(1) H5/ミニプログラム/Web 版には通常 open api がある。(2) 取得したたとえ 1 つの平文リクエストでも API 列挙のシードにできる。(3) Github/検索エンジンでドメイン + swagger/openapi/actuator/druid を検索する。
**Q3**: サーバー側も厳重に防御している(WAF + 強い認証)?
**A3**: 【サブドメイン/エッジサービス】に移る。メインドメインは厳重でも、サブドメインのテスト/管理/内部/ドキュメントサイトは往々にして無防備。再帰的なサブドメイン列挙+ポートスキャンを行う。
**Q4**: 判定基準は、いつこの App 対象を完全に諦めるか?
**A4**: クライアントが動かず + サーバー側のすべての露出面に隙がなく + ソーシャルエンジニアリング/サプライチェーンの入り口もない。このときはレッドチームのルールに従って記録し、証拠を保存し、悪用不能という結論を書き、コンプライアンス外の対象を無理に攻めない。

### キャプチャ時に App がプロキシ設定を能動的に検知する
**Q1**: システムプロキシを有効にすると App が「ネットワーク異常」を返し、無効にすると使える?
**A1**: App が ProxySelector / System.getProperty("http.proxyHost") または NetworkInfo で検知している。回避法:システムプロキシではなく【透過プロキシ】を使う。iptables で mitmproxy の transparent ポートへ redirect し、App にはまったく感知されない。
**Q2**: 透過プロキシでも通らない。より深い検知(ネットワークカードの異常/接続元 IP など)をしている?
**A2**: 【ゲートウェイ級のキャプチャ】に移る。スマホを自分が制御する WiFi に接続し、ゲートウェイ(OpenWrt + tcpdump / mitmproxy)でキャプチャする。App はどの角度から見ても正常に出網している。
**Q3**: すべてダメ。App に証明書の pin がある?
**A3**: pin 回避チェーンに戻る。キャプチャツールのレイヤはすでに透過的で、残るのは pin との正面からの対抗だ。

### 暗号化関数の Native レイヤにおける具体的なアドレスの特定
**Q1**: 暗号化が so 内にあることは分かったが、関数名が剥がされ/静的解析に時間がかかる。どう速くする?
**A1**: 挙動で特定する。libc の send/write を hook し、暗号文の呼び出しスタック(Thread.backtrace)を取得する。スタック内の最上層の so アドレスが暗号化関数の近傍だ。シンボル表へオフセットする(stripped でも一定の範囲はある)。
**Q2**: スタック上はすべて libc/libart で、業務 so が見えない?
**A2**: 中間に非同期(スレッド/handler)の分割があることを示す。Java レイヤで暗号化をトリガーできる最上層の呼び出し(request 構築など)を hook する方式に変え、JNI 呼び出しを順に下へ追う。
**Q3**: JNI レイヤが動的登録(RegisterNatives)を使っていて、関数名の対応が見えない?
**A3**: RegisterNatives そのものを hook し、(name, signature, fnPtr) の三つ組を表示する。java メソッド名から native アドレスへの完全なマッピング表を直接得られる。

### データ取得後のスマートな Fuzz の構成
**Q1**: 任意の加解密ができるようになった。サーバー側 API を fuzz したい。どのパラメータから手を付ける?
**A1**: 優先順位:(1) 数値型(id、amount、offset、limit)。境界、負数、極大。(2) 文字列。SQLi/SSTI/XXE の特徴。(3) 状態フィールド(status、role、type)。権限外アクセス。(4) ドキュメントに現れないがクライアントがたまに付ける隠しフィールド(debug=1、mock=true)。
**Q2**: サーバー側が毎回拒否する。署名が壊れたのか、fuzz payload が WAF を発動したのか分からない?
**A2**: 基準を固定する。まず既知の正当なリクエストを 1 回送り、署名と経路が正常と確認する。それから単独で 1 つのフィールドを変え、レスポンスに差異があればそれがこのフィールドの意味的なフィードバック。制御変数法だ。
**Q3**: fuzz 中に SQL エラーらしきものを発動したが不完全?
**A3**: 専用対応に移る。sqlmap を使うか自前のブラインドインジェクションを書き、そのパラメータを狙う。署名部分を自動再計算可能なミドルウェア(mitmproxy addon)にして、sqlmap の各リクエストを自動再署名する。
**Q4**: サーバー側のレート制限が厳しく、fuzz を始めるとすぐ 429?
**A4**: 直交する切り替え。レートを下げる+複数アカウント/複数 IP のローテーション。または汎用 fuzz を諦め、ドキュメント/API を精読して定点で脆弱性を掘る。

### クライアントにホットアップデート/リモート設定がある
**Q1**: キャプチャで、起動後に大きな zip/js/lua が配信されるのを確認。ホットアップデートの可能性がある?
**A1**: 保存する。中には新しい API、テスト機能、隠し設定、デバッグスイッチが含まれる可能性がある。ホットアップデートパッケージの復号 key も通常クライアントにある。
**Q2**: ホットアップデートパッケージの署名検証が厳しく、改ざんするとクライアントが読み込みを拒否する?
**A2**: 目的が【読む】ことなら十分で、改ざんは不要。毒を仕込むなら、検証関数を hook して true を返す方向に移る。
**Q3**: ホットアップデートのトリガー条件が特定ユーザー/AB test?
**A3**: クライアントがレポートする user_group / abtest_id / version パラメータを変更する方向に移り、サーバー側に実験グループの設定を配信させる。

### 複数デバイス/複数アカウント関連のセッション分離の解析
**Q1**: アカウント A のセッションを取得した。アカウント B に使いたいが、サーバー側が deviceId を厳密にバインドしている?
**A1**: サーバー側がデバイス-アカウントのバインディング検証をしていることを示す。deviceId を変えるには pushToken、androidId などの一連のフィンガープリントを連動して変える必要があり、1 つだけ変えても不十分。
**Q2**: アカウント B のセッションサンプルを取得して比較する。差異のあるフィールドは何か?
**A2**: 全フィールドを diff して分類する。【本当のセッション認証情報】(token)、【デバイス次元】(deviceId, uuid)、【業務次元】(uid, roleId)。アカウントを跨いだアクセスには最初の 2 種を丸ごと置換するだけでよい。
**Q3**: サーバー側がアカウント A のリクエストで送られてきた deviceId と履歴のバインドを能動的に照合し、なりすましでアラートが発動する?
**A3**: 【アカウント B の本当のデバイス情報の取得】に移る。対象がデータ取得で B を攻めることではないなら、無理になりすまさず、【垂直の権限外アクセス】(アカウント A で B のリソース id にアクセスする)を探す。

### 暗号文に見えて実際は圧縮の取得物
**Q1**: body が高エントロピーで暗号化と思ったが、gzip/zstd のヘッダーもない?
**A1**: 急いで暗号化と決めつけない。先頭 2 バイトを見る。0x1F8B は gzip、0x789C/0x78DA は zlib、0x28B52FFD は zstd、0x04224D18 は lz4。一部の App は magic を剥がして raw deflate を直接送る。直接 inflate(-15) で解いてみる。
**Q2**: 展開後は平文?
**A2**: ならば暗号化ではまったくなく、単なる圧縮。攻撃者にはおいしい。直接解析すればよい。
**Q3**: 展開後もまだバイナリ?
**A3**: それは「圧縮後暗号化」か「暗号化後圧縮」。暗号化チェーンに従って進む。

### Frida か Xposed か静的 patch かの選択
**Q1**: 持続化する回避を 1 回作りたい。frida / xposed / apk の静的変更、どれを選ぶ?
**A1**: 場面が決める。(a) 短期デバッグ/複数回の試行 → frida。素早く反復できる。(b) 長期使用+複数回の起動 → xposed/lsposed。持続的で安定。(c) 他人と共有/root を入れたくない → apk を静的に patch して再パッケージ化。
**Q2**: 対象は 1 回だけ動かしてデータを取ればよい。frida を選ぶが App にアンチ frida がある?
**A2**: frida-gadget の静的注入に移る(frida runtime を apk にパッケージする)。ランタイム検知を回避する。
**Q3**: 本番で某機能を長期的に使えるようにしたい?
**A3**: 静的に smali を patch するのが最も安定だが、署名検証を通す必要がある。再署名後は署名検知を回避する(PackageManager.getPackageInfo の signatures フィールドを hook して元の署名を返す)。

### データ関連解析、1 回の操作の背後にあるリクエスト数
**Q1**: 機能を 1 回クリックすると App が複数のリクエストを送る。どれが「キーとなるもの」か?
**A1**: レスポンスボディのサイズ、ステータスコード、パスのキーワードで並べ替える。実際に仕事をする API は一般に業務動詞(order/create/submit/pay/confirm)を持ち、補助 API はログ/レポート動詞(report/track/log/stat)を持つ。
**Q2**: キー API が前の数個の戻り値に依存する(preOrder → order など)?
**A2**: 依存チェーンを構築する。手動で 1 回実行し、各リクエストの入出力関係を記録し、どのフィールドが「前のレスポンスから持ち越されたもの」かを標示する。これが完全な業務フローで、リプレイ時は順序どおりに行う必要がある。
**Q3**: 前置ステップを飛ばして最後のステップを直接呼びたい?
**A3**: 試す。サーバー側が各ステップで状態を書く(sessionStorage/redis)なら、前置が欠けるとエラーになる。単にクライアント自身の案内なら直接飛ばす。判定基準:レスポンスのエラー情報に「前のステップ未完了」の類の意味があるか。

### キャプチャ環境は正常だが、ある種のリクエストだけ通らない
**Q1**: 大半のリクエストは通るが、あるドメイン/API だけ通らない?
**A1**: その API は以下かもしれない。(1) 独立ドメインの pin を通っている。(2) 異なる暗号化チャネルを使っている(決済が独立 SDK を通るなど)。(3) 特定の IP セグメント/CDN の使用を強制している。それぞれ nslookup + tcpdump で特定する。
**Q2**: 独立 SDK(決済/風控など)自身のチャネルか?
**A2**: それを個別に回避する。決済 SDK は通常独自の pin と暗号化を持つ。hook 対象はその SDK のクラスで、ホスト App ではない。
**Q3**: この API が極めて重要で回避できず、時間もない?
**A3**: 直交する切り替え。この API を攻めず、その【上流/下流】を調べる。決済には必ず注文前の API、注文後の API があり、前後両端は往々にして認証が弱く、そこから横切できる。

### あるフィールドが【タイムスタンプ】か【インクリメント id】か【ランダム nonce】かの判断
**Q1**: リクエスト内に 13/10 桁の数字フィールドがある。何か分からない?
**A1**: 長さで判定する。10 桁は秒単位の timestamp、13 桁はミリ秒。複数回サンプリングして差を見る。差が 2 回のリクエストの実際の間隔と等しければタイムスタンプ。差が極小で常に増加していれば seq。差がばらばらならランダム nonce。
**Q2**: 長さが 10 でも 13 でもなく、16 桁?
**A2**: timestamp+ランダム接尾辞、ナノ秒単位の timestamp、またはスノーフレークアルゴリズムの id の可能性。上位桁が時間に従って動くかを見る。
**Q3**: フィールドが十六進法または base64 の短い文字列?
**A3**: 高い確率で uuid 亜種かクライアントの request id で、通常はログ追跡にだけ使われ、認証には関与しない。
**Q4**: 認証に影響するか確信がない?
**A4**: 二分テストをする。そのフィールドを空にして 1 回送るか、1 バイト変えて 1 回送り、レスポンスを見る。(a) 直接成功 → サーバー側はこのフィールドを検証しない。(b) 署名エラー → 署名に関与するが認証には関与しない可能性。(c) 「期限切れ/重複」→ リプレイ対策に関与する。これに基づいて偽造に力を入れるか決める。
