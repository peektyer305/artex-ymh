# 脆弱性における複数トラフィックのエビデンス

脆弱性詳細の「関連トラフィック」は、ページをまたぐ複数選択、用途と説明、並び替え、およびバインド解除に対応する。トラフィックページでもレコードを複数選択でき、一度に 1 つの既存脆弱性へ関連付けられる。タスクから継承した脆弱性エビデンスは読み取り専用であり、変更にはソースタスクへ移動する必要がある。

システム設定の「Agent 自動バインドトラフィック」はデフォルトで無効であり、読み取りと変更の API は `/api/settings` の `agent_traffic_binding` である。有効にすると、リクエスト/レスポンスの参照、ツール呼び出し、およびプロンプトによるトークン消費が増える。次のターンの Agent が新しい設定を使用する。無効時は自動バインドのパラメータと追加バインドツールを非表示にし、自動バインドのガイドを注入せず、実行中のセッションが新たに送信する自動バインドを拒否する。手動バインド、トラフィックキャプチャ、保存済みエビデンスの読み取りとエクスポートには影響しない。

有効にすると、デフォルトの流れは「ファインディングの登録 → レポート Agent の自動起動 → トラフィックの確認とバインド → 最新のエビデンスバージョンに基づくレポート作成」となる。報告者は `evidence` に検証コマンド、重要な出力、既存の実トラフィック ID と用途を残す。レポート Agent は脆弱性詳細と実行記録を踏まえ、`traffic_search` / `traffic_get` で確認したうえで `bind_finding_traffic` を呼び出し、最新の `version` を読み取ってレポートを保存する。スイッチが無効な場合、レポート Agent は生トラフィックの検索/読み取りツールを追加で受け取らず、自動バインドも行わない。手動でバインドされたスナップショットは引き続き読み取り、レポートを生成できる。

既存の呼び出し元との互換性：`report_finding` の `traffic_refs` / `evidence_hint_id` による明示的な即時バインドは引き続き可能である。バインドは任意であり、TCP など非 HTTP の脆弱性、未収集、または該当レコードが見つからない場合は、参照を省略しても通常どおり報告とレポート作成ができる。コマンド出力やログなど他の検証可能なエビデンスを残し、未バインドの理由を説明することが推奨され、必須フィールドは追加されない。送信する ID はすべて有効で、本文が完全である必要がある。いずれか 1 件でも失敗すると今回のバインド操作はロールバックされる。報告と同時に明示的にバインドして失敗した場合は、報告全体がロールバックされる。同じスナップショットを重複して追加してもバインドは増えず、説明も上書きされない。

## Agent の採番とレポートバージョン

`report_finding` に任意パラメータを追加した。配列の順序が初期のエビデンス順序となる：

```json
{
  "traffic_refs": [
    {"traffic_id": "実トラフィックID", "role": "baseline", "note": "正常アカウントのリクエスト"},
    {"traffic_id": "別の実トラフィックID", "role": "proof", "note": "再現リクエスト"}
  ]
}
```

用途は `baseline`（正常系の対照）、`proof`（脆弱性の証明）、`verification`（補足検証）、`supporting`（補助エビデンス、デフォルト）である。まず `traffic_search` / `traffic_get` で実レコードを確認する。ドメインと時刻は候補の絞り込みにのみ用い、タスクの帰属は推定しない。

プロンプトは [CyberStrikeAI の脆弱性報告ツールガイド](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go) を参考にし、本プロジェクトの任意バインドの取り決めに合わせて、パッケージがない理由の必須チェックは導入しない。ID を推測してはならず、パッケージを補うためだけに重複した探索を行うべきでもない。

戻り値の 1 行目は引き続き `finding recorded: <探索节点 ID>` である。続く JSON には、独立した脆弱性レコード `finding_id`、探索ノード `finding_node_id`、およびバインドの要約が含まれる。

- `get_finding_traffic(finding_id)` は**独立した脆弱性レコード ID** を使用し、順序付きの一覧と `version` を返す。`binding_id`、`side=request|response`、`offset`、`length` を渡すと分割して読み取れ、1 回の読み取りは最大 8192 バイトである。
- `update_finding_report` の `finding_id` は**引き続き探索ノード ID** を使用する。新設の `evidence_version` には実際に読み取ったバージョンを指定する。生成中にエビデンスが変化した場合、旧バージョンの書き込みは拒否され、再読み取りと再生成が必要になる。
- 旧来のレポート呼び出しでバージョンを渡さない場合、既存のトラフィックエビデンスを上書きしたとは主張しない。バインド、説明、用途、または順序が変化すると、既存のレポートは更新待ちとして表示される。

自動バインドを有効にすると、`add_hint` / `add_task_hint` は単一のヒント、または一括指定した `hints` の各要素に `traffic_refs` を保存できる。Planner が代理で報告する場合は `evidence_hint_id` を渡し、本タスクに対応するヒント内の参照を明示的に選択できる。継承したヒントは参照できない。システムはドメイン、時刻、閲覧履歴からバインドを推測しない。送信に失敗しても、部分的な脆弱性は生成されず、レポートも事前に起動されない。

既存の脆弱性でバインド漏れがある場合は `bind_finding_traffic(finding_id, traffic_refs)` で追加バインドでき、重複登録は不要である。`list_findings` / `list_task_findings` / `node_detail` / `get_task_node_detail` は明確な `finding_id` と `finding_node_id` を返す。旧来の `id` は探索ノードの意味を保つ。

起動時は旧ツールの schema に任意属性を追加するだけで、元のデフォルトトラフィックツールのバインドはレポート Agent まで拡張される。追加バインドツールはデフォルトでレポート Agent に渡される。カスタムのバインド一覧、プロンプト、説明、および有効状態は保持される。ガイドは最終的なツール組み立て後に一括して加えられる。報告役は既存エビデンスの引き継ぎを、レポート Agent は確認、バインド、レポート作成を担う。プラットフォームのチャットにタスクのコンテキストがない場合は、構造化されたヒントでタスク Agent に引き継ぐべきであり、直接報告してはならない。タスクの完了を判定する前に既存エビデンスを引き継ぐ。パッケージがない場合は待機を強制しない。失敗した `report_finding` はレポート Agent を起動しない。

## API

ベースパス：`/api/exploration/findings/{finding_id}/traffic`。独立した脆弱性 ID を使用する。認証は既存の仕組みを踏襲し、`context_task` はタスクの可視性と継承時の読み取り専用を検証する。

| メソッド / 相対パス | リクエスト / レスポンス |
| --- | --- |
| `GET` | 順序付き要約、エビデンスバージョン、レポートが採用したバージョン |
| `POST` | `{"traffic_refs":[...]}` を一括追加 |
| `PATCH /{binding_id}` | `{"version":1,"role":"proof","note":"説明"}` |
| `DELETE /{binding_id}` | `{"version":1}` |
| `PUT /order` | `{"version":1,"binding_ids":["2","1"]}`。完全なリストである必要がある |
| `GET /{binding_id}` | スナップショットのメタデータと、サイズ上限付きの本文プレビュー |
| `GET /{binding_id}/body` | `side`、`offset`、`length`。`download=1` で完全な元バイト列をダウンロード |

バージョン/並び順の集合が競合した場合、およびアーカイブ中の書き込みは `409` を返す。継承時の書き込みは `403`、存在しない、または当該脆弱性に属さないバインドは `404`、トラフィック/添付ファイルの読み取りと検証の失敗は明示的なエラーを返す。

## ストレージとマイグレーション

起動時に PostgreSQL へ冪等なマイグレーションを実行する。`traffic_evidence_snapshots`、`finding_traffic_bindings`、および `findings.evidence_version` / `report_evidence_version`（デフォルト 0）を追加する。過去の文章から追加バインドを推測することはない。

スナップショットには元のトラフィック ID、取得時刻、URL、メソッド、ステータス、リクエスト/レスポンスヘッダ、本文長、および SHA-256 を保存する。本文はハッシュごとに `<data>/evidence/blobs/<先頭2桁>/<hash>.bin` へ格納され、クリーンアップ対象となる `data/traffic` とは独立している。複数の脆弱性が同じスナップショット/本文を共有できる。スナップショットには内容更新の API がなく、検証が一致しない場合は読み取りとエクスポートが失敗する。

元トラフィックの書き込みロックの下で、大きな本文の blob や旧ディレクトリのレコードを含む完全な本文を読み取る。まずファイルを永続化して検証し、その後、単一の PostgreSQL トランザクションで探索ノード、意図の関係、脆弱性、スナップショット、およびバインドを書き込む。コミット後にのみプランナーへ通知する。失敗時には参照のないファイルが残る可能性があるが、部分的な業務レコードは生成されない。

PostgreSQL の advisory lock `7337741004` がエビデンスファイルと SQL の参照を調整する。タスクの行ロックは、アーカイブがキューに入った後のエビデンス変更を禁止する。復元では本文のインストールからメタデータのコミットまで、全行程でエビデンスロックを保持する。脆弱性を削除するとバインドもカスケード削除される。

クリーナーは 1 時間ごとに実行され、参照がなく進行中の操作もない内容のみを、少なくとも 24 時間の遅延を置いて回収する。通常のトラフィックのクリーンアップはエビデンスディレクトリに触れない。ホットデータをバックアップする際は、PostgreSQL と `data/evidence` を同時にバックアップする。

## エクスポートとアーカイブ

Markdown には順序付きのエビデンス一覧とバージョンを含む。JSON にはメタデータを含む。CSV には件数とバインド ID を追加する。`md-zip` は脆弱性の Markdown を保持し、次を提供する：

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

Markdown は相対リンクでメッセージを参照する。ダウンロードを送信する前に、添付ファイルのコピー、ハッシュ検証、圧縮、ディスク同期、および全 ZIP エントリの CRC 読み取り検証を完了させる。欠落や破損があるとダウンロード全体が失敗する。完全な添付ファイルはバイナリの元バイト列を保持する。

アーカイブ v3 は脆弱性のバインド関係に従ってスナップショットと本文を収集し、元のトラフィックやドメインに依存しない。パッケージの検証が完了してからホットデータを削除する。共有されるエビデンスは引き続き保持される。復元ではまずインストールする本文を検証し、次にトランザクションでメタデータとバインドを復元する。失敗時の再試行に対応する。v1/v2 も引き続き復元でき、欠けている新規フィールドは明示的に 0 で補う。

## 検証と境界

テストパッケージごとに独立した新規の PostgreSQL テストデータベースを用意し、`ARTEX_PG_DSN` で指定する。残存したタスク/モデルのフィクスチャがバックグラウンド実行を誘発するのを避ける。関連パッケージのテストをすべて実行し、設定不足によるスキップがないことを確認する：

```sh
# 各パッケージの実行前に、対応する独立したテスト用 DB を ARTEX_PG_DSN に設定する。明示的な設定の失敗はエラーとして扱うこと。
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

フロントエンドの検証には `npx tsc --noEmit`、影響を受けるファイルの Biome チェック、Webpack ビルド、および `NEXT_EXPORT=1` による静的エクスポートを含める。独立したキャッシュディレクトリを使用し、稼働中の開発サービスを上書きしないようにする。

ローカルでのエンドツーエンド受け入れでは、独立したポート、制御された HTTP / ドメイン HTTPS のターゲット、および一時データディレクトリを使用し、2 つのバインド入口、ページをまたぐ選択、並び替え/説明、エラー表示、継承時の読み取り専用、ダウンロード、さらに元トラフィック削除後のエクスポート、アーカイブ、ホット本文の回収、復元とハッシュ検証までを対象とする。

初版ではグローバルなエビデンス調整ロックを採用する。大量のバインド/エクスポートや低速な添付ファイルのダウンロード中は、他のエビデンス操作が待機する可能性がある。キャプチャ記録や完全な本文がない場合、エビデンスを捏造することはできない。本機能はキャプチャのスイッチを変更せず、HTTPS で IP に直接アクセスする際の証明書問題も扱わない。
