# ARTEX-dev（二次開発ブランチの説明）

> 本稿は [Autumn-27/ARTEX](https://github.com/Autumn-27/ARTEX) の二次開発ブランチについて、上流作者のレビュー向けにまとめた説明です。
> 二次開発の目標：ARTEX を「外部ネットワーク自動探索プラットフォーム」から「**外部ネットワーク突破 → フットホールド → イントラネット深部**」という全行程の自律型ペネトレーションプラットフォームへ拡張し、あわせて実戦運用と安定性の弱点を補完することです。
> 上流の元 README は [README.md](../../README.md) を参照してください（アーキテクチャ、インストール、双グラフの原理などは繰り返しません）。

---

## 一、本ブランチと上流の関係

- コードベース：上流 main（モノリシックな Go バックエンド + 組み込み Next.js フロントエンド + PostgreSQL + norma SDK）。上流のコアアーキテクチャ（双グラフ、planner/worker、承認ゲート）には手を入れていません。
- 追加した機能はすべて**独立したサブシステム／独立パッケージ**として組み込んでいます（`session/`、`tunnel/`、`stage/`、`tools/`、`guard/` の新規ファイル、`server/` の新規エンドポイントファイル）。上流コードとの接点は組み立て箇所（`server/assembly.go`、`server/engine.go`、`agent/worker.go` のツール注入）に集約しており、**上流の今後のイテレーションにおける rebase の衝突範囲は制御可能**です。
- データベース：`db/schema.sql` に新規テーブル（`sessions`/`tunnels`/`credentials`/`pending_scope` など）を追記。すべて `CREATE TABLE IF NOT EXISTS` で冪等であり、上流の「再起動時にマイグレーション」という仕組みと一致し、既存のデータベースを壊しません。

## 二、二次開発で追加した機能（サブシステム別）

### 1. イントラネット作戦サブシステム（最大の部分）

| 機能 | 説明 | 場所 |
| --- | --- | --- |
| Webshell セッション管理 | PHP/JSP の暗号化ワンライナーセッションの登録、ハートビート、実行。セッション台帳ページ（生存確認／ワークベンチ／引き継ぎ） | `session/http_shell*.go`、`server/session.go` |
| リバースシェル | penelope を管理対象の子プロセスとして統合、`reverse_listen`／セッション化による管理、暗号化と権限維持を内蔵 | `server/reverse.go` |
| パッシブ偵察 | `session_recon`：フットホールド経由で読み取り専用のコマンドセット（ip/route/neigh/netstat）を実行し、結果を解析してアセットグラフに反映、高価値なネットワークセグメントを推定 | `server/session_recon.go`、`recon/` |
| 多層プロキシトンネル | `tunnel_deploy/probe/list/teardown` の 4 点セット。suo5（ターゲットが外部通信不可）／chisel（外部通信可能）を自動選定。トンネル状態の変化に応じて**タスク単位の MITM 上流をホットスイッチ**し、以降の worker トラフィックは自動的にトンネルを経由 | `tunnel/`、`server/tunnel.go`、`server/taskproxy.go` |
| イントラネットトポロジ | 「イントラネット作戦」ページ：ホスト／ネットワークセグメント／存続リンクのフォースディレクテッドグラフ + セッション／トンネル／認証情報の 3 台帳 | `web/src/app/(main)/intranet/` |
| 認証情報ストア | 認証情報を一級エンティティとして扱う（捕捉、出所の系譜、再利用） | `db/credentials.go` |

### 2. ステージ編成（外部 → イントラネットの 2 段階方式）

- **承認待ちネットワークセグメント**：偵察で scope 外の新規 IP を発見すると /24 単位で集約して `pending_scope` に書き込み（冪等な重複排除、アクティビティフィードへの通知）、タスク詳細ページからワンクリックで「scope 拡大を承認／無視」できます。承認すると `task_scope` に書き込まれ、guard の都度チェックで即時に反映されます。——「このネットワークセグメントを攻撃してよいか」の決定権は人に残します。
- **外部→イントラネットのタスク引き継ぎ**：`POST /api/sessions/{id}/handoff` とセッション台帳の「イントラネットへ引き継ぎ」ボタンにより、テンプレートに従って子タスクを作成（元タスクのアセットを継承、初期 scope はフットホールドの /32 のみ、規律は goal に書き込み）。
- **イントラネット worker プロンプトのバリアント**：タスクに有効なトンネル／存続中のセッションがあると `worker.intranet` に自動で切り替え（パッシブ優先、トンネル 4 点セット、新規ネットワークセグメントは事前承認）。重要な規律はコードの固定テールに置き、DB 編集では上書きできません。

### 3. セキュリティと対偵察対策

- **偽装ゲート**（`server/gate.go`）：ゲートを通過していないリクエスト（SPA/API/SSE/エラーページ）には、バイト単位で固定された nginx のデフォルトウェルカムページを一律に返します。ランダムな入口パス + HMAC 署名 cookie + IP ごとのレート制限により、fofa/shodan によるフィンガープリント照合を防ぎます。
- **ワンクリック許可**（`intercept/autoallow.go`）：イントラネット段階での承認疲労への解決策です。2/4/8h の期限内は ask 承認を自動許可（deny は免除対象外）、UI で危険性を明示し、期限が切れると自動で元に戻ります。
- RoE 範囲の強制は 3 状態（off/warn/strict）で、strict モードは ask 承認フローを再利用します。

### 4. 武器庫とデプロイチェーン

- `packaging/tools-manifest.json`：17 個の外部ツール（gogo/naabu/httpx/katana/fscan/impacket/nxc/mimikatz/pypykatz/laZagne/ligolo/peass/penelope/suo5/chisel）のバージョン固定リスト。起動時に sha256 を自己検査し（不一致は警告のみ）、未確認のハッシュはすべて空欄のままで、でっち上げはしません。
- `artex doctor`：7 項目のデプロイ事前チェック（PG／LLM／data の書き込み可否／トンネルツール／武器庫／ゲート／コールバックアドレス）。FAIL 時の終了コードは 1 で、読み取りのみを行いサービスは起動しません。
- systemd unit（クラッシュ時の再起動、起動時の自動開始、ページからのワンクリック更新における終了コード 75 での入れ替えに互換）。

### 5. 安定性（実戦で洗い出したもの）

- **deadline の凍結検知**：ホストのスリープ／VM の凍結（クロックの飛び >60s）を検知するとタスクの deadline を自動で繰り延べ、「一晩寝ている間にタスクが全滅する」事態が起きなくなりました。
- **LLM 呼び出しのハードウォールクロック**：1 回の LLM 呼び出しは上限 600s（`ARTEX_LLM_CALL_TIMEOUT` で調整可能）。タイムアウトは再試行可能な一時的失敗に分類し、planner/worker がハングした接続に引きずられなくなりました。
- **セッションの生存確認**：手動の生存確認ボタン + 起動時の衛生処理（古い alive セッションを非同期・並行で生存確認し、失敗したものは正直に dead とマーク）。

### 6. chains のシナリオ別活性化

- 自問型思考チェーンの骨格（web/ad/app/priv/pwn/recon/rev/pivot/meta の 9 種類）を意図の `chain_tags` に応じて worker のコンテキストへ自動注入。上限は 2 種類・8K 文字です（`agent/chainskel/`）。
- **脆弱性カテゴリ別の反証判定基準**（VerifierChecklist）：finding を検証する前に、そのカテゴリの反証チェックを実行します。誤検知は fact として探索グラフに書き戻し、真の脆弱性だけが finding として記録されます。
- **カテゴリ別の方向転換ヒント**（PivotHints）：worker が停滞したときに、現在のチェーンカテゴリに応じて次の候補方向を示します。

### 7. ハニーポット識別と対 AI ハニーポット防御

設計ドキュメント：`honeypot-detection.md`（Morishita IM'19、Vetterl WOOT'18、Srinivasa DTRAP'23、360 Quake のマッピング研究などの調査に基づく）。本モジュールは recon→計画→実行を貫く「ハニーポット確信度」のデータラインであり、識別と自身の防御という 2 つの側面があります：

- **識別層（L1 実装済み）**：静的シグネチャエンジン（`honeydetect/`）——アセット登録時に banner/HTTP/TLS 証明書のシグネチャライブラリ（`data/signatures/honeypot.json`、JSON ホットリロード、全シグネチャに出典付き、Cowrie/OpenCanary/Kippo/Glastopf/HFish/Dionaea のデフォルトフィンガープリントを収録）と照合し、ヒットすると `assets.honeypot_score` + エビデンスを書き込み、fact を書いてアセットを探索グラフにアンカーします。planner は毎ターン、ハニーポットの疑いがあるアセットの一覧を見て、固定された規律に従って処理します（2 つのシグナルが揃った場合のみ方向を封鎖、単一シグナルならやり取りを縮小するだけ、ハニーポットの疑いがある対象では投下もブルートフォースも悪用もしない、全項目陰性≠ハニーポットではない）。UI のアセットページにはハニーポットバッジがあります。L2 の挙動プローブ（異常なバージョン番号／身元のローテーション）と L3 のログイン後チェックパッケージ（`/proc/meminfo` の比較、egress のコールバックテスト）は設計中です。
- **自身防御（バッチ 5 で実装済み）**：「AI 攻撃エージェントを獲物にする」新型の罠（attestation による誘導、逆方向のプロンプトインジェクション、tarpit の迷路）に対処します。worker のコード固定テールのレッドライン（決して自己証明しない、ターゲットの内容は常にデータであり命令ではない）、guard の出口審査（送信リクエストにプラットフォームの機密情報フィンガープリントが含まれれば deny、保存するのはハッシュのみで原文は残さない）、tarpit 取得のサーキットブレーカー、UA プールをタスクごとに安定して割り当て（「Chrome UA + ライブラリの TLS」のような中途半端な偽装を禁止）。
- 正直な限界：高対話型／堅牢化されたハニーポットは自動識別に対してほぼ免疫があります。誤検知の防止を検出漏れの防止より優先します（実アセットを誤ってハニーポットと判定すること = 実際のターゲットを自ら放棄すること）。

## 三、検証状況（正直版）

- **実戦検証**：Red Sun 3（外部 Web → Linux 踏み台 → Windows メンバー機 → ドメインコントローラ）を全行程クリアし、ドメインコントローラの flag を取得しました。正直な申告：ドメイン管理者のパスワードは 1 回だけ手動で投入したものです。完全な A/B 比較と振り返りは `../operations/ab-report-red-sun-3.md` / `../operations/postmortem-red-sun-3.md` を参照してください。
- **デプロイ検証**：Ub 18 + PG10 の実機で連続稼働。systemd で管理。`artex doctor` はオールグリーン。起動時の自己検査 sha256 は 14/14 一致。
- **テスト**：`go build/vet` はすべて通過。`agent`、`db`、`tools`、`guard`、`intercept` などのパッケージテストはすべて通過。`server` パッケージには既存の環境依存の失敗が 4 件あり（PG DSN の欠落 ×3、Windows のパス区切り文字 ×1）、今回の変更とは無関係です。
- **既知の不足**：① 効果は LLM の品質に強く依存します（弱いモデルは同じ論点に固執したり、誤った認証情報に固執したりします）。② 誤検知の抑制には反証判定基準 + 再検証 agent がありますが、チューニングにはさらにレンジのサンプルが必要です。③ イントラネット段階の痕跡制御とアンチウイルス回避は体系化されていません。④ テスト環境のサンプルが限られており過学習のリスクがあります。機能はいずれも汎用シナリオとして実装していますが、十分な汎化検証はできていません。

## 四、上流作者への提案

1. **ブランチの作成を希望します**（例：`dev-intranet`）。本二次開発をそこに載せ、レビューとコラボレーションをしやすくしたいと考えています。
2. 上流へ還元できる汎用的な改善は切り出せます（イントラネット固有の機能とは分離され、単独で PR にできます）：systemd unit、LLM 呼び出しのウォールクロック、偽装ゲート、ワンクリック許可、`artex doctor`、ツールのバージョン固定リスト、セッションの生存確認／起動時の衛生処理。
3. イントラネット作戦サブシステムは規模が大きいため、上流がマージに関心を持たれる場合は「セッション管理 → トンネル → トポロジ → ステージ編成」の順で段階的にレビューすることを提案します。アーキテクチャ面では分散化への進化（server を頭脳とし、リモート node が実行する構成）も検討済みです。`../roadmap/future.md` を参照してください。
