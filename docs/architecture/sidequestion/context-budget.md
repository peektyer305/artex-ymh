# サイドクエスチョンの長い会話とコンテキスト予算

2026-09-11 修正。元の実装はリクエスト JSON の文字数をそのまま token とみなし、さらにメインタスクの 32K 出力予約を継承していたため、HTML、JS、ツール結果が多いと正常なサイドクエスチョンが早期に拒否されていた。

## オープンソース実装の照合

- [Grok CLI のサイドクエスチョンコンテキスト](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/agent/agent.ts#L739)：直近のユーザー・アシスタントのテキストから断片を抜き出し、文字予算は約 2000、1 件あたり最大 400 文字を切り出す。この経路では継続的なサイドクエスチョン Q&A 履歴を保持しない。
- [Grok CLI の独立リクエスト](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/utils/side-question.ts)：独立したキャンセルシグナル。モデルが対応している場合の出力上限は 2048 tokens。ツールは提供しない。
- [Grok CLI のメインセッション圧縮](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/agent/compaction.ts)：token を推定し、直近の内容を保持し、新しい内容を古い要約へ更新し、ターンをまたぐ切り詰めを処理する。
- [OpenCode のセッション圧縮](https://github.com/anomalyco/opencode/blob/b3f1a96c6dd7adeb28b36dd11add1998fc84d67b/packages/core/src/session/compaction.ts)：リクエスト全体の推定、出力／バッファの予約、直近内容＋ローリング要約、ツールなしの要約リクエスト。この実装ではデフォルトの直近予算が 8000、要約の出力上限が 4096 tokens。
- [OpenCode のオーバーフロー復旧](https://github.com/anomalyco/opencode/blob/b3f1a96c6dd7adeb28b36dd11add1998fc84d67b/packages/core/src/session/runner/llm.ts)：アシスタントの出力がまだ始まっていない場合にのみオーバーフロー復旧を試み、復旧後の呼び出しは同じオーバーフロー復旧経路に入らない。

ARTEX は独立した出力予算、直近の内容とローリング要約、限定的な復旧という方針を取り入れる。norma v0.3.6 の構造化メッセージとツールのペアリングを維持し、Grok のテキスト抜粋はそのまま踏襲しない。OpenCode のメインセッション圧縮イベントは ARTEX のメイン transcript へ書き込まない。

## リクエスト予算と実行

- メッセージは norma のコンテンツブロック単位の UTF-8 バイト推定と 4/3 の余裕を踏襲する。システムプロンプト、ツール schema、メッセージのラッピングに伴うオーバーヘッドを追加で計上する。推定はモデルの正確な token 数ではない。
- サイドクエスチョンの出力はデフォルトで最大 8192 tokens で、メイン設定に既に設定された出力上限も超えない。サービス環境変数 `ARTEX_BTW_MAX_OUTPUT_TOKENS` で 256–32768 の上限を設定できる。製品のデフォルトモデルやメインタスクのパラメータは変更しない。
- 入力予算はコンテキストウィンドウから出力上限と安全余裕を差し引いたもの。未知のウィンドウではプラットフォームのデフォルト 200K を使う。安全余裕はウィンドウの 5%、最小 128、最大 8192 tokens。
- 成功した Q&A は昇順の連番ごとに 1 バッチあたり最大 20 組を読み込む。原文は最大 20 組保持し、その token 予算は入力予算の 1/4 まで、かつ 16K を超えない。
- 超過した Q&A はローリング要約へ更新する。要約は履歴の出所とコンテキスト時刻を持つ。過去のアシスタント回答は新しいツールエビデンスと同義ではなく、矛盾する場合は最新のメインスナップショットを優先する。
- メインコンテキストが依然として長すぎる場合は、コピー内の古いメッセージのみを要約し、直近は最大 8K tokens 保持する。切り詰め位置がツール呼び出しと結果を分断することはない。大きすぎる単一の組は全体が要約に入る。
- 要約の入力は実際の残りウィンドウに応じて UTF-8 安全に分割し、出力上限は 2048 tokens。空の要約、切り詰め、ツール呼び出し、要約予算の超過はいずれもキャッシュに書き込まない。1 回のサイドクエスチョンで要約呼び出しは最大 12 回で、同じ 120 秒のタイムアウト制限を受ける。上限に達すると明示的に失敗し、無限ループにはならない。
- モデルが最初にコンテキスト超過を返し、まだテキストもツール呼び出しも出力していない場合は、さらに縮小して最大 1 回まで再試行する。推定サイズが減少していなければ、ただちに復旧を停止する。その他のモデルエラーや部分的なストリーミング出力ではこの復旧を発動しない。
- 取得したすべての使用量は、要約、失敗した試行、キャンセル時の使用量も含めて同じサイドクエスチョンリクエストへ累積する。Provider が使用量を返さない場合はゼロを記録するしかなく、推定値を実際の使用量に見せかけてはならない。

## 永続化と UI

`side_question_sessions.memory` は過去の Q&A 要約、対象となる ordinal、スナップショットの同一性ごとにキャッシュしたメインコンテキスト要約を保存する。`side_question_requests.context_info` は準備段階、実際に再生した組数、要約の使用状況、予算の推定を保存する。

要約は元のリクエストがまだ実行中で、クリア時のバージョンが一致する場合にのみ保存する。クリアではキャッシュも同時に消去し、遅延した書き込みが消去済みのデータを復元することはない。新しいスナップショットは古いスナップショットの要約を再利用しない。要約フィールドは v3 タスクのアーカイブとともに保存する。古い v3 で欠けているフィールドを復元するときは空オブジェクトを補い、v1/v2 は引き続き互換とする。

POST はいったんリクエストを受け付けて返し、準備と圧縮はバックグラウンドで実行するため、受け付けロックやデータベーストランザクションを保持しない。SSE／履歴は準備、Q&A 整理、コピー圧縮、回答の各段階を表示する。圧縮の失敗はそのサイドクエスチョンリクエストの失敗終状態として保存する。フロントエンドはエラーを保持し、今回失敗した質問の下書きを復元する。入力欄を覆うフローティング通知は使わない。履歴のポーリングで送信エラーが消えることはもうない。
