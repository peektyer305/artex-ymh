# テスト原則（過学習の防止）

> 本プロジェクトにおけるすべてのテスト活動の最上位の原則です。**テストはコードが動作するかどうかを検証するためのものであり、テスト対象に合わせるためのものではありません。**
> このプラットフォームが特定のシナリオや特定のサイトでしか動作しないのであれば、意味がありません。

## 3 つの鉄則

1. **コードは汎用バグのためにのみ変更し、特定の対象のために変更しない。**
   テストで露呈した問題は、修正前に必ず「この変更は任意の対象に対して成立するか？」と自問してください——「はい」と答えられなければコードには入れません。対象固有の情報（IP、ドメイン、認証情報、ページ構造、特定 CMS への攻撃手法）は常にインテリジェンスとコーパスに属し、ロジックには属しません。

2. **対象を追いかけない。**
   ある対象を突破できないとき、既定の仮定は「プラットフォームの汎用能力が不足している」であり、「この対象向けに何かを書く必要がある」ではありません。許される唯一の「適応」は、追加の武器庫ツール、シグネチャライブラリ（出典付きの公開フィンガープリント）、プロンプト内の汎用規律です。演習環境の特徴をコード、プロンプト、シグネチャに書き込むことは禁止します。

3. **演習環境は入れ替えて実行する。**
   単一の演習環境では汎用性を検証できません。テストマトリクスは、Web のみの入口、Linux 単一ホスト、Windows 単一ホスト、多層の内部ネットワーク／ドメイン環境、純粋な CTF ロジック問題、実企業に近い総合環境といった異なる構造を、できるだけ幅広くカバーすべきです。環境を入れ替えるたびに、まず「どの汎用能力が失われたか」を観察してください。それこそが最も価値のある入力です。

## 検証と報告の規律

- 「テスト通過」という結論には必ず、対象の種類、何を人手で介入したか（認証情報の投入／wp の投入／手動での許可）を明記し、「全自動で突破」と粉飾してはいけません;
- 振り返りの成果物は 2 種類に明確に分けてマークします：**汎用メカニズムの修正**（コードに入れる）と**対象固有の事情の記録**（振り返りドキュメントに入れ、コードには入れない）;
- 追加したコードに具体的な環境の特徴（内部ネットワークのセグメント、ドメイン、認証情報、特定対象のフィンガープリント）が現れた時点で過学習事故とみなし、必ず除去します——この原則の遵守状況は 1 回の grep でいつでも監査できます（演習環境の特徴文字列は本番コードではヒットゼロであるべきです）。

## 判断基準

ある機能が汎用的かどうかは、「それが红日靶场 3 で動作するか」ではなく、「これまで見たことのない環境に変えたとき、その挙動がなお妥当か」で判断します。
