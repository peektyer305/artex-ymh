# 紅日演習環境 3 タスクポストモーテム（タスク #1、2026-09-13）

> タスク：紅日演習環境 3 の多層内部ネットワーク（Web 入口 → Linux 踏み台 → Windows メンバー機 → ドメインコントローラ。flag はドメインコントローラの `C:\Users\Administrator\Documents\flag.txt`）。06:26–09:24 に実行（約 3 時間、14,992 件のイベント、49 個の worker 意図、79 ラウンドのプランニング）。ユーザーが自ら一時停止した。
> データソース：タスクの全 activity（14,992 件）、mainagent のチャット（41 件のユーザーメッセージ）、86 件のインターセプト履歴、サーバー側ログ。4 つの観点（タイムライン/予算パターン/技術的失敗/システム層）による独立分析を相互検証。

## 一、一言でいう結論

**これは「突破できない」失敗ではなく、「最後の一撃の直前に中止させられた」失敗である**。マシンアカウントの PTH でドメインコントローラの 445 を攻撃した件は 09:22 にすでに成功し、DCSync も進行中だったが、2 分後にタスクが一時停止された。本当の問題は突破できなかったことではなく、**本来 1 時間で走り切れるはずの道を 3 時間かけ、決着を担う意図がスケジューリングキューの中で死に、走り切った部分の 3 分の 1 が人手の投入に依存していたこと**である。

## 三、根本原因のランキング（すべてエビデンスあり、「結末への影響」順）

### R1. プラットフォームの session サブシステムが強化された PHP 上で全体として退行。最も深刻
`register_session` は eval 型のワンライナー WebShell しか認識せず、「コマンド実行型 WebShell」のプローブプロトコルと一致しない（「PHP のコード実行型ワンライナーではない」と繰り返し報告され、5 個の worker が同じ WebShell に対して登録を繰り返してもすべて失敗し、`lang:auto` は JSP と誤判定すらした）。結果：**登録に成功した session はすべて「ファイル読み書きのみ」に退行し、session_exec は全滅** → すべての worker がプラットフォームのセッションチャネルを使わなくなり、生 curl で自作のコマンド WebShell を叩く方式に切り替えた（290 回以上の手動リクエストループ）。セッション台帳/承認/証跡の体系は丸ごと迂回された。**これがフェーズ 1 の建設成果を無にした穴である。**

### R2. 決着を担う意図がスケジューリング段階で死んだ
意図 #207（マシンアカウントで DC を直接攻撃、当時すでに PTH の実現性は証明済み）は作成後**一度も引き取られなかった**：frontier には 36 件の open 意図が滞留し、P0 には引き取りタイムアウトの報告が無く、mainagent には `kill_work`/`cancel_intent` ツールが無いため steer/hint で指令を偽装するしかなかった。09:22 に PTH が通った後、DCSync は 2 分動いたところで一時停止された。**この一撃が 30 分早く実行されていれば、結末はおそらく違っていた**。

### R3. 攻撃機のツールチェーン欠損 + セルフチェック/報告の欠如 → 1 時間の手書き実装と誤った fact
攻撃機には pip/gcc/impacket が無く、apt はロック衝突。impacket は最終的に**ユーザーが手作業で持ち込んだ**。それ以前、worker は自作の SMB/TDS プロトコルクライアントを作らざるを得ず、「SMB 445 が塞がれている」など**4 件以上の誤った陰性 fact をブラックボードに書き込み、planner は誤った fact の上で数ラウンド空回りした**。最終的に impacket による再確認で 1 件ずつ覆された。worker 環境の依存不足にはセルフチェック/報告の仕組みが一切無く。ユーザーは 2 時間早く投入できたはずだった。

### R4. 予算の燃焼パターン（ユーザーの言う「一点への固執」は部分的に妥当）
- i69：glibc のバージョン不一致に対するブラインド悪用で、`malloc(): memory corruption` という同一のクラッシュシグネチャが十数ラウンド連続しても再試行し、**169 拍を焼き切った**。
- i104：すでにクローズした結論の再確認（300 イベント）。
- 同一の webshell を 5 個の worker が重複登録し、MySQL クライアントは 2 回書き、.so は 4 回ビルドし、SOCKS チャネルは 4 回再構築した。
- **chains meta の「同質なレスポンスが 15~25 回続いたら方向転換」ルールを worker のループに接続していれば、約 250-350 回の呼び出し、45-60 分（実時間の 20%）を節約できたはずである。しかしそれはプロンプトの中にしか無く、コードには入っていない。**

### R5. 共有インフラの相互汚染
複数の worker が同一の WebShell ファイル、同一の `/tmp` コマンドファイル、パスをハードコードした .so、同一の helper ポートを共用。出力の混線（センチネルが「WebShell が失効した」と誤検知）、ファイルの相互上書き、並列実行による Apache のタイムアウト多発を招いた。worker は「他者による干渉」を「自身の失敗」と誤判定して再試行した。

### R6. guard の巻き添えと「訓練による回避」
86 件のインターセプトはすべてルールによる自動裁定で、ユーザーの関与は 0 回（承認リクエストがそもそも届いていなかった）。巻き添えには、`ls` が削除と判定された件、PwnKit に必須の `rm -rf GCONV_PATH=.` がブロックされた件、**最終レポートが本文に psexec/wmiexec を含むために「横方向実行」ルールでブロックされ保存できなかった**件が含まれる。worker はすでに「回避の言い回し」を書くようになっている。guard が逆方向に訓練してしまっている。

### R7. chains の 4 層知識体系は実戦でゼロ使用
`use_skill` の呼び出しは 0 回。`chain_tags` は 11 回の add_intent でタグとして現れただけであり、chains の判定基準を参照した worker は皆無だった。**最も心血を注いで構築した知識層が、実戦では形骸化していた**。L3 は planner のタグ付け（ほとんど付かない）+ キーワードへのフォールバック（カバレッジが狭い）に依存し、L4 はモデルの自発的な呼び出し（決して自発的には呼ばれない）に依存している。

### R8. RoE のノイズと scope の矛盾
110 回の RoE 警告はすべて warn で許可され、ブロックはゼロ。ファイル名を「範囲外のターゲット」と判定するノイズが大量に発生し、scope には 192.168.111.0/24 が登録されている一方で実際の標的は 192.168.93.0/24。システムはログを流すだけで、この自己矛盾を指摘しない。

## 四、ユーザーの 2 つの仮説への裁定

- **「一点への固執」：成立。予算の約 20% を占める**（R4）。ただし主因ではない。主因は R1/R2/R3 の構造的問題であり、固執をすべて省いたとしても、同じスケジューリングのボトルネックに 45 分早く到達するだけである。
- **「ホストにツールが無い」：部分的に成立するが、位置が逆である**。**標的機にはツールが揃っている**（curl/wget/python/nc がすべてある）。ツールが欠けているのは**攻撃機**（pip/gcc/impacket が無い）である（R3）。ツールの欠如自体は恐るるに足らない。恐ろしいのは、欠如時にセルフチェック/報告が無く、agent に手書き実装を強いて誤った fact を生ませることである。

## 五、システム的な問題 vs 演習環境固有（過学習の防止）

| システム的（どの標的に変えても再発する） | 演習環境固有（これに基づいて設計を変えるべきではない） |
|---|---|
| session がコマンド WebShell を識別せず、disable_functions 回避の内蔵経路が無い（R1） | impacket を人手で持ち込む必要がある（この攻撃機の環境問題であり、pypi には実際に到達可能） |
| 意図のスケジューリング：frontier に上限が無く、P0 に引き取りタイムアウトが無く、mainagent に kill/cancel が無い（R2） | 標的機の PHP が意図的に強化されている（exec 系をすべて禁止 + sendmail 無し） |
| 環境の依存不足に対するセルフチェック/報告が無い。自作ツールの陰性結論がそのまま confirmed fact に昇格する（R3） | メンバー機のパスワードは公式 WP 由来（純粋な自律経路はこの演習環境には客観的に存在しない） |
| worker のループに同質レスポンスの停滞検出が無い（R4） | 踏み台ホストは外部ネットワークに出られず、リバーストンネルは原理的に不可能 |
| フットホールド/成果物に per-worker の名前空間が無い（R5） | 出題方式に起因する 111/93 の 2 セグメント間の scope 矛盾 |
| guard の文字列ルールによる巻き添え + 無人時の承認はデフォルト拒否（R6） | |
| chains に実際の呼び出し入口が無い（R7） | |
| RoE 抽出器のノイズ + scope/goal の一貫性が検証されない（R8） | |

## 六、修正計画（すべてシステム的で、紅日 3 に固有のものは無い）

**P0（今週必須）**
1. **session がコマンド実行型 WebShell をサポート + LD_PRELOAD 回避を内蔵**：プローブで eval 型 WebShell とコマンド型 WebShell を区別する。exec の全禁止を検出したら「プリコンパイル済み freestanding .so を投入 + putenv/mail() で発火」という経路を自動で通す（worker が手書きで実現可能なことはすでに証明済みなので、プラットフォームとして固定化する）。lang:auto の誤判定を修正する。プローブ失敗時の文言で「検出・削除された」と軽々しく言わない。
2. **chains L1 の実装：worker ループ内での停滞検出**。ローリングウィンドウでレスポンスシグネチャの類似度を統計し、閾値を超えたら「行き詰まりの要約 + 方向転換の要求」を強制する。Settlement に Q リストのセルフチェックを紐付ける。
3. **スケジューリング：P0 意図の引き取りタイムアウト（例：5 分）を mainagent に報告し、指名配布を許可する。frontier にハード上限（open ≤8）。mainagent に `kill_work`/`cancel_intent` を追加**。
4. **fact の完全性：worker が生成する結論（SUCCESS/FAILURE の判定）は、成果物を grep で再確認しない限り fact に書けない。自作ツールの陰性結論は inferred とし、成熟したツールで再確認して初めて confirmed への昇格を許可する**。

**P1（来週）**
5. 攻撃機のベースラインイメージ：pip/impacket の全 scripts/gcc/wordlists/proxychains をプリインストールし、`artex doctor` で検査する。起動時に依存関係をセルフチェックし、不足を mainagent に報告する。
6. トンネルに「フォワードモード」を追加：webshell 経由の管理されたフォワード SOCKS helper（台帳化し、worker の終了では殺さない）で、「標的が外部ネットワークに出られない」シナリオをカバーする。今回の手動 helper のプラットフォーム化である。
7. guard の意味解析化：heredoc とレポート本文をスキップする。レポート/ドキュメント系の Write をホワイトリスト化する。承認リクエストを mainagent のセッションに配信する。リスクレベル別のデフォルト動作（ドキュメント系はデフォルト allow + 監査）。
8. per-worker 名前空間の規約化（WebShell ファイル/コマンドファイル/helper ポート/.so パスを worker ごとに分離）+ per-session の実行ロック。
9. RoE：抽出器はネットワーク標的（IP/ドメイン/URL）のみを認識し、ファイル名を除外する。タスク初期化時に scope↔goal の一貫性を検査し、scope を自動補完する。

## 七、記録に値する明るい面（問題ばかりではない）

- MySQL プロトコルクライアントの手書き実装、as/ld による freestanding .so の手書き実装、LD_PRELOAD+mail() による回避、PwnKit による権限昇格、impacket の SOCKS グローバルパッチ、オフラインでのマシンアカウント解読。**agent の技術的な上限は確かに存在し、複数の操作は人間の専門家級である**。
- 検証パイプラインは全行程で 7 件のファインディングをすべて裁定した（1 件の誤検知を false_positive と判定したことを含む）。
- planner が 2 回自発的に軌道修正した（EFSRPC stub の手書き実装を止めさせ、pip のインストールを止めさせた）。
- ユーザーがパスワードを提供してから 15 分で命中。ヒューマン・イン・ザ・ループの協調機構そのものは有効である。
