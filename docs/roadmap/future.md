## 1. 動機と目標形態

目標：現在の「server 1 台で何もかも動かす」形態を、**server（頭脳）+ 複数の node（手足）** へ進化させることです：

- server：Web UI、LLM 呼び出し（llmpool）、planner、承認フロー、探索グラフ／アセットグラフ（PG）、スケジューラ。
- node：具体的なツール呼び出し（bash／HTTP／スキャン／デリバリ）だけを実行し、outbound で server へ回線接続して仕事を受け取る。インターネット側からの inbound は不要。
- 参考形態：市販のクラウドサンドボックスを実行ノードに使う製品（server がタスクを配信し、サンドボックスが実行後に回収される）。ただし本質的な違いを見る必要があります——**それらの製品はステートレスな使い捨てのツール実行を行うのに対し、ARTEX が行うのは継続的な運用です**：セッション、トンネル、リスナーはいずれも長期的に状態を持つアセットであり、スケジューリングモデルが根本的に異なります（§5 参照）。

## 2. 現状：実行面と server 本体の結合点一覧

現在の worker は独立したプロセスではありません：`Engine.Run` が server プロセス内でタスクごとに 1 個の planner + N 個の worker goroutine を起動し（`server/engine.go:823-830`）、`worker.Execute` は直接の Go 呼び出しです（`server/engine.go:1118-1120`）。したがって「worker を node へ移す」ことは agent loop 全体をプロセス外へ出すことを意味し、以下の結び付きが一つずつ破綻します：

| # | 結合点 | エビデンス | 性質 |
|---|--------|------|------|
| 1 | セッション登録表は純粋なインメモリ map で、worker が受け取った session_id は server 側が表を引いて解決する | `session/session.go:104-109`、`server/session.go:540-549` | メモリ状態 |
| 2 | reverse listener（penelope）は server の被管理サブプロセスで、MCP はループバックに束縛され、セッションはそのプロセスのメモリ上にあり再起動では復元できない | `server/reverse.go:276-286, 257-266, 80-88` | 本体プロセス |
| 3 | トンネルマネージャは server 本体のプロセス台帳で、ポートプールは本体の `net.Listen` 試行バインドに依存する | `tunnel/deploy.go:41-57, 137-144` | 本体プロセス+ポート |
| 4 | socks/MITM アドレスは `127.0.0.1` にハードコードされ、消費チェーン worker→タスク MITM→socks はすべて loopback 前提 | `server/tunnel.go:348`、`server/taskproxy.go:83`、`agent/worker.go:209-216` | ハードコードされたアドレッシング |
| 5 | トラフィック記録の MITM は server プロセス内にあり、CA 秘密鍵は server のディスク上、HTTPS の再署名も server で行われる。記録はローカルのファイルツリー+SQLite に書き込まれ、PG を通らない | `server/taskproxy.go:132-167`、`traffic/traffic.go:141-190`、`agent/worker.go:242-249` | 本体プロセス+ファイル |
| 6 | 承認のブロックと起床は純粋なインメモリ channel（`map[int64]chan bool`）で、リモートで待機するプリミティブが一切ない | `intercept/intercept.go:86-116, 610, 641-679` | メモリ上のプリミティブ |
| 7 | ファイル面は worker と server が同一ファイルシステムにある前提：runDir ワークスペース、stage の PutFile がローカルパスを直接読む、transcript の再開がローカルファイルを読む、chat uploads | `agent/worker.go:323-330, 516`、`server/stage.go:195-228`、`server/server.go:444`、`server/chatupload.go:42-44` | 共有ファイルシステム前提 |
| 8 | ツールバイナリと「kali ツールチェーン」＝ server ホスト機のローカルなコマンド環境 | `server/tunnel.go:35-46`、`server/reverse.go:216-224` | 本体環境 |
| 9 | engine↔worker の制御面（pause/kill/steer/deadline）はプロセス内の `context.CancelCause` と channel に基づく | `server/engine.go:167-171, 410-435` | プロセス内プリミティブ |

**有利な面（元々共有でき、ほぼゼロ改修）**：探索グラフ／アセット／意図／ファクト／ファインディング、sessions/tunnels 台帳、intercept ルールと pending 記録、settings、LLM profiles はすべて PG にあります。意図の取り合いには既に CAS があり（`ClaimIntent`、`server/engine.go:1333-1341`）、複数ノードが競合しても二重にはなりません。**これが ARTEX を他の多くより分散化に向かわせる根本的な理由です：唯一の事実源がすでにプロセスメモリではなく外部 PG だからです。**

**2 本のきれいな抽象の継ぎ目（改修の重要な取っ掛かり）**：

- すべてのツールが `actool.CoreTool.Call(ctx, json.RawMessage, ...)` という単一の JSON 入出力形状に収束している——天然の RPC 境界です。
- worker は `llm.Provider` インターフェースしか受け取らず（`agent/worker.go:165`）、key は server のメモリ上で組み立てられます（`server/llmpool.go:60-130`）——「LLM key が server の外へ出ない」はインターフェース層で天然に成立しており、欠けているのは server 側の LLM プロキシのエンドポイントだけです。

## 3. 目標アーキテクチャ

```
┌─ server ─────────────────────────────────────────────────────────────────┐
│ Web UI │ planner │ llmpool（鍵はプロセス外に出さない） │ guard/承認 │ PG │
│ スケジューラ：意図の割当配信、node 台帳、親和経路、承認の失効            │
└──────────────────────────────────────────────────────────────────────────┘

   ▲ mTLS：ツール呼び出し＋結果の返却 / 承認 long-poll / 制御面

  ┌─ node-1 ─────────────────────────────┐   ┌─ node-2 ───────────────────────┐
  │ agent loop                           │   │ agent loop                     │
  │ bash / HTTP / 走査                   │   │ 武器庫（manifest）             │
  │ セッション / トンネル（親和）        │   │ 固定版配布＋検証               │
  └──────────────────────────────────────┘   └────────────────────────────────┘
```

責務分割の原則：**頭脳は server に、手足は node に**。node が受け取るのは単発のツール呼び出し（1 本の bash、1 回の HTTP、1 回のデリバリ）であり、LLM コンテキストの全体像を返送しません。LLM key、承認の判断、探索グラフへの書き込み権限はすべて server の外へ出しません。

## 4. ノードプロトコルの設計要点

- **伝送と認証（セキュリティの基線であり、削れない部分）**：TLS 1.3 + mTLS の相互認証。server が自己署名 CA を発行し（`jwt.key`/`gate.key` と同じディスク書き込みの流儀、`server/auth.go:46`）、node はワンタイムの登録トークンでクライアント証明書を取得します。証明書のフィンガープリントは UI の「承認待ちノード」に現れ、手動で承認されて初めて有効になります（TOFU）。失効はフィンガープリントの削除です。ノードの待ち受けポートは Web ゲートから独立し、偽装ページを付けません——mTLS 自体がより強力な隠蔽です（クライアント証明書がなければハンドシェイクすら通らず、マッピングスキャンが見るのはブラックボックスのポートだけです）。候補の代替：WireGuard（カーネルレベルだがサンドボックスノードの鍵配布が煩雑）、chisel の逆接続（静的パスワードでは粒度が粗すぎるため一択で却下）。
- **ツール呼び出し面**：`actool.CoreTool` の JSON 境界を再利用して RPC を構成します。domain tools（`insert_assets/record_fact/add_intent` など 30 数個、現在は `*db.*Store` の具象型を保持、`agent/tools.go:76-82`）は**server に残して**プラットフォームサービスとし、node からリモート呼び出しします。実行系ツール（Bash/Read/Write/WebFetch）は node 上でローカルに実行します。
- **制御面（隠れた本命で、ツール RPC より作業量が多い）**：意図の取り合い（PG の CAS を再利用）、ハートビート、キャンセル（プロセス内の `CancelCause` を置き換え）、軌道修正の配信（steer）、deadline の締めくくり。明示的な実行プロトコル一式が必要です。
- **承認フロー**：pending 記録はすでに PG にあります（データの置き場所は正しい）。メモリ上の channel によるブロックを、node から server への long-poll／WS 待機に置き換えます。fail-closed の意味論、ctx キャンセルの伝播、タイムアウトとの競合（`intercept/intercept.go:644-679`）は項目ごとに再検証が必要です。guard hook は意図とともに node 側へ配信して実行し、ルール／RoE はリモートから読みます——**承認を下位へ降ろさなければ形骸化するため、これが M1 の厳格な前提条件です**。
- **結果の信頼できる記帳**：node が返す各結果にはノードの識別子を付け、DB へ `node_id` を記録します。あるノードが掌握された場合、`node_id` でそのノードの産出物だけを正確に「疑わしい」と印付けでき、DB 全体を不信にせずに済みます。

## 5. スケジューリングとノードアフィニティ（「ステートレスサンドボックス」方式との本質的な違い）

セッション駆動、トンネルプロセス、socks 入口、reverse listener はいずれも**作成されたノードに属し、そのノードと運命を共にする**ステートフルなアセットです。スケジューラは必ず次のようにします：

1. セッション／トンネル／リスナーに `node_id` を登録する。
2. これらのアセットに依存する後続の意図（トンネル経由で内部ネットワークを攻撃する、session_exec）は**アフィニティルーティングで元のノードへ戻す**——そうでなければ socks アドレスにはそもそも到達できません。
3. ノードの切断：その上にあるステートフルなアセットは正直に dead とマークする（既存の死活監視の仕組みを再利用し、`server/session.go:95-103` の起動時の衛生処理はそのまま改修できます）。
4. ステートレスなツール呼び出し（スキャン、HTTP プローブ）だけが、任意の空きノードへ自由にラウンドロビンできます。

## 6. ファイル面の方針

ワークスペース、stage の配信、transcript の再開、武器庫のバイナリは、現在すべて同一ファイルシステムを前提としています。方針：

- **武器庫の配布**：node のプロビジョニング時に `packaging/tools-manifest.json`（フェーズ 6 で作成済み、17 件のバージョン固定+sha256）に従って配布し検証します——これは既製のインフラであり、分散化はむしろその主要な受益シナリオです。
- **ワークスペース／成果物**：node のローカルワークスペース + 成果物を必要に応じて server へ返送します（大きいファイルは stage と同じランダムトークンのチャネルを使う）。transcript の再開は server 側での保存・取得に改めます（現在はすでにファイルなので、PG の bytea に移すか server のファイル API にするかで、改修範囲は抑えられます）。
- **stage の PutFile がローカルパスを読む**という前提は、「node がアップロード→server が一時保存→ターゲットが取得」の三段式に改める必要があります。

| フェーズ | 内容 | 主要な前提条件 | 工数 |
|------|------|----------|--------|
| M0 | 詳細設計ドキュメント（プロトコルのフィールド、アフィニティ表の構造、guard の下位配信設計、移行時の互換性） | — | 小（純粋な設計） |

## 8. リスクと未解決の課題

- **トラフィック記録**：HTTPS 再署名の CA は server にあります。node が server の MITM へ直接接続する（ネットワーク到達性+CA 配布が必要）のか、記録を node へ下ろしてから返送する（新しいパイプライン）のか。後者を推しますが、`traffic/` のディスク書き込み前提に手を入れることになります。
- **reverse の出口を下位へ下ろすか？** 最も楽なのは session_exec/reverse を常に server に残すこと（RPC 呼び出し）で、ターゲット側のコマンド出口は依然として server にあります。出口を node へ下ろすなら、Registry／ロック／penelope のシングルトンをすべて再設計する必要があります。M1〜M2 では下ろさず、M3 で再検討することを推奨します。
- **複数ノードが同一ターゲットを奪い合う**ノイズとブロックのリスク：タスク単位の同時実行上限ポリシーが必要です（現在は workers=6 のグローバルなスロットリングがあるが、分散化後は「ターゲットごと」の次元でもう一段制限する）。
- **node が掌握されたときの爆発半径**：設計上 node は LLM key を持たず、PG の DSN も持たず（server API 経由のみ）、武器庫もタスクごとに最小配布とします。しかし node は自分が実行するターゲットと戦利品の一部を必然的に見ることができ、単一ノードの掌握 ≈ そのノードが関与したタスクのコンテキスト漏えいです。これは分散化固有のトレードオフであり、§4 の `node_id` 記帳で事後の影響を抑えるしかありません。
- **デコイ役（任意の能力、M2 以降に評価）**：node は独立した出口上で「デコイ」に指名され得ます——ターゲットへ偽の攻撃トラフィック（偽スキャン／偽ブルートフォース／偽エクスプロイト）を流し、防御側の帰属を薄め、研判コストを押し上げます。ただし境界に注意：ノイズの形態は攻撃らしくあるべきで、閲覧らしくあってはなりません（後者は防御側の研判キューに入りません）。HW の一刀両断の IP ブロックは本物の node を巻き込む可能性があります。デコイと実 node のフィンガープリントの関連は逆に露見を招きます。単体版ではこの能力を実装しません。詳細は ../architecture/honeypot-detection.md の二-C 節を参照。

## 9. 結論

**可能であり、土台は多くの同類より良い**：状態はすでに集中化され（PG）、ツール面には JSON の抽象の継ぎ目があり、LLM key の境界はインターフェース層で成立し、武器庫のバージョン固定リストも準備済みです。しかしこれは「API をいくつか足す」改修ではありません——本当の本命は **engine↔worker 制御面プロトコル** と **トンネル／トラフィック／ファイルの三面にハードコードされた loopback 前提** にあり、M1 の 1 マイルストーンだけでフェーズ 1〜6 のどの単期よりも改修量が大きくなると見積もられます。現在のプラットフォーム（単体版）でレンジ検証と機能の安定を終えてから M0 を始めることを推奨します。
