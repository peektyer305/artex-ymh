# chains-web L3 意思決定チェーン(場面→判定基準→方向転換;chains コーパスから蒸留,完全な Q&A は skills/chains-web/refs/ を参照)
- 場面:インジェクションが疑われるパラメータ|判定基準:再現可能な真偽の分岐を見る。エラーは文法が変わっただけ、分岐こそ式が実行ロジックに入った証拠|方向転換:分岐なしなら時間ベースブラインド/OOB に切替、さらに注入位置を変える(body/header/cookie/JSON)
- 場面:インジェクション成立時にチャネルを選ぶ|判定基準:UNION>エラーベース>ブール>時間で情報量が最大かつ安定するものを取る。外向き通信が可能なら DNS 外帯が数桁速い|方向転換:読み書きが制限されたら認証情報の収穫へ(バックエンド hash/鍵)。クラウド RDS で OS 面がなければデータ+クラウド ID へ
- 場面:payload が WAF にブロックされる|判定基準:200 は突破を意味しない。WAF は 200 を偽装する。まず良性/悪性の対照を取ってからレスポンスを信じる。ブロックされた token を二分探索で特定し、一度に変える変数は一つだけ|方向転換:エンコーディング/位置/Content-Type を変える。クラウド WAF はオリジン IP を突き止めて直結
- 場面:アップロードポイントを発見|判定基準:まず良性ファイルを上げて三つを見る。パスのエコー、リネーム方針、直接アクセス可否。その後に webshell を考える|方向転換:ランダム名でエコーなしなら「アップロードのプリミティブ化」へ(XXE/ストアド XSS/phar/LFI の組合せ)
- 場面:アップロードのホワイトリストが画像のみ許可|判定基準:ファイル配置 ≠ 実行。アクセスしてソースが返るなら未解析。バリデーションとミドルウェアの拡張子判定アルゴリズムの不一致に隙がある|方向転換:解析の脆弱性/.htaccess へ。ディスク配置が根絶されたらメモリ馬へ(先に一度実行が必要)
- 場面:シリアライズデータが疑わしい|判定基準:エンコーディングを剥がしてマジックナンバーを見る。rO0=Java、O:数字=PHP、\x80\x03=pickle。URLDNS でまず「実際にデシリアライズされ、外向き通信する」ことを検証|方向転換:gadget がなければ SSRF/情報ポイントへ。ホワイトリスト filter なら二重デシリアライズか面を変える
- 場面:URL パラメータを処理し SSRF が疑われる|判定基準:まずコールバックの送信元 IP が対象サーバーの出口であることを検証(CDN/ブラウザの偽 SSRF を防ぐ)。次に内部ネットワークへ到達できるか試す。クラウド上ならまずメタデータ IMDS を打つ|方向転換:ホワイトリストなら 302/DNS 再バインド/名前解決の差異へ。ブラインドなら「状態変更」する内部ネットワークサービスへ
- 場面:入力がエコーされ SSTI が疑われる|判定基準:唯一の判定基準は {{7*7}} が 49 をエコーすること。curl の生出力で 49 が出れば SSTI、JS 実行が必須で出るなら CSTI。まずエンジンをフィンガープリントしてからチェーンへ|方向転換:サンドボックスで固められたら SECRET_KEY/設定の読み取りに降格。session の偽造は中途半端な RCE より価値が高いことが多い
- 場面:XML 入口で XXE が疑われる|判定基準:良性の外部エンティティを帯外アドレスに向ける。コールバック = パーサー生存 + 外向き通信。ブラインド XXE はまず DNS で疎通確認、次にパラメータエンティティで外帯|方向転換:DOCTYPE が禁止なら XInclude/ローカル DTD の error-based へ。全て禁止なら検証不要な SSRF に降格
- 場面:コマンドインジェクションが疑われる|判定基準:sleep の遅延は設定と線形に対応すること(3s→3s、7s→7s)でジッタによる誤検知を除外。帯外は時間ベースブラインドより優先|方向転換:区切り文字が全滅なら argument injection へ(tar/find/curl の危険なオプション)。配列形式の execve なら引用符ゲームを諦める
- 場面:ID 付きリクエストで IDOR が疑われる|判定基準:二アカウント対照。B セッションが A の埋め込んだ一意マーカー付きのプライベートリソースを読めて初めて権限外アクセス。公開データの誤検知を除外。読み書きをそれぞれ検証|方向転換:403 ならパラメータの渡し方/メソッド/オブジェクト型を変える。バルク/エクスポート API は認可の断層になりがち
- 場面:JWT/認証への攻撃|判定基準:まず alg=none、RS→HS 混同、kid/jku の四点セットを試す。署名が固いならライフサイクルへ(exp 未検証、ログアウトしても無効化されない、refresh がローテーションしない)|方向転換:偽造が動かなければ窃取・漏えいへ(JS/git/ログ)。認証が強いなら正規 ID の下での権限外アクセスへ
- 場面:CMS を特定できた|判定基準:ブランド+正確なバージョンがあって初めて nday に対応付けられる。優先順位:未認証 RCE>未認証の読み書き>認証後 RCE。バージョンが新しければプラグイン/テーマへ(更新遅れの重災害地帯)|方向転換:既知の脆弱性が全滅なら二次開発の継ぎ目、設定漏えい(.git/バックアップ)、ロジックの脆弱性へ
- 場面:脆弱性で shell を足場にする前|判定基準:まず三つの枠を埋める。DB タイプ、現在のユーザー権限、DB と Web が同一ホストか。まず既知のシステムファイルを読んで FILE 権限を検証してから書き込みを考える|方向転換:書き込めないなら設定を読んで認証情報を集め横展開へ。足場が検知・削除されたらメモリ馬へ
- 場面:一点を長く攻めても落ちない|判定基準:同質のレスポンスが連続 15~25 回(新たなステータスコード/長さ/タイミングの差異なし)なら情報は搾り尽くされている。即座に方向転換。シグナルの勾配があれば続行|方向転換:攻撃面マトリクスに従って次元を変える。パラメータ/脆弱性の種類/入口/アセットを変え、記録して保留し一点に固執しない
