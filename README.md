# ARTEX-ymh

AI 自律型ペネトレーションテスト基盤 · 二次開発版（Go バックエンド + Next.js フロントエンド + PostgreSQL）

> 本プロジェクトは [Autumn-27/ARTEX](https://github.com/Autumn-27/ARTEX) の二次開発ブランチです。アップストリームの v0.3.10 をベースに、アップストリームの更新を継続的に取り込み（v0.3.12 まで追従し、0.3.11/0.3.12 の修正を選択的に取り込み済み）、アップストリームの **AGPL-3.0** ライセンス（`LICENSE` 参照）に従います。
> 二次開発の方針：アップストリームの「外部ネットワーク自動探索基盤」を、「**外部ネットワーク突破 → フットホールド → 内部ネットワーク深部**」という全行程の自律型ペネトレーションテスト基盤へ拡張し、実戦的なセキュリティと安定性の不足を補います。

## アップストリームとの主な違い

| サブシステム | 内容 |
| --- | --- |
| **内部ネットワーク作戦** | WebShell 暗号化セッション管理（PHP/JSP）、リバースシェル（penelope 管理下）、フットホールドのパッシブ偵察（`session_recon`）、多層プロキシトンネル（suo5/chisel の自動選定、タスク単位の MITM ホットスイッチ）、内部ネットワークトポロジ図（タスクで絞り込み）、認証情報ストア |
| **ステージ編成** | 未承認セグメントの承認（偵察で scope 外のセグメントを検出 → 人手で承認して scope を拡張）、外部 → 内部ネットワークのタスク移管（handoff テンプレートでサブタスクを作成）、内部ネットワーク worker プロンプトのバリアント（フットホールドがあれば自動で切り替え） |
| **セキュリティと対偵察対策** | 偽装ゲート（ゲートを通過しないアクセスは一律でバイト単位に固定された nginx ウェルカムページを返し、入口パスはランダム化）、ワンクリック許可（2/4/8h の期限付き承認免除、deny は免除なし）、RoE 範囲の強制 3 状態（off/warn/strict） |
| **ハニーポット識別と対 AI ハニーポット防御** | 静的シグネチャ識別レイヤー（`honeydetect/`、組み込みシグネチャライブラリが Cowrie/OpenCanary/Kippo/Glastopf/HFish/Dionaea をカバー）、アセットのハニーポットスコアリングと UI バッジ、planner の対応規律。さらに「AI 攻撃エージェントを獲物とする」新型トラップへの対策：worker のレッドライン（決して自証しない）、外向きの機密情報インターセプト、tarpit 取得のサーキットブレーカー、UA プール。設計は `HONEYPOT-DETECTION-DESIGN.md` を参照 |
| **chains のシナリオ化** | 9 種類の自問型思考チェーン骨格を意図に応じて自動注入、脆弱性カテゴリ別の反証判定基準（誤検知は fact として記録し、真の脆弱性のみグラフに反映）、カテゴリ別の方向転換プロンプト |
| **武器庫とデプロイチェーン** | 17 項目の外部ツールのバージョン固定リスト（`packaging/tools-manifest.json`、起動時に sha256 を自己検査）、`artex doctor` によるデプロイ事前チェック、systemd unit |
| **安定性** | タスク deadline のフリーズ検知（ホストのスリープでタスクを消費しない）、LLM 呼び出しのハードウォールクロック、セッションの生存確認と起動時のクリーンアップ |

二次開発の詳細は `README-FORK.md`、分散化への進化の評価は `FUTURE.md` を参照してください。

## インストール

> **PostgreSQL** に依存します。探索には **LLM** の設定が必要です（OpenAI/Anthropic プロトコル互換、UI から設定可能）。

### 方式 1: ワンクリックインストールスクリプト

```bash
git clone https://github.com/r0th-m/artex-ymh.git
cd artex-ymh
./install.sh
```

スクリプトは Docker を検出し、必要なら自動インストールします。**① すべて Docker** か **② ローカルでビルドして実行**（`config.json` を生成し、フロントエンドを内蔵した単一バイナリをビルド）を選択できます。インストール後は `http://localhost:8787` を開きます。

### 方式 2: ソースから単一バイナリをビルド

> 前提条件：Go ≥ 1.26、Node ≥ 20（フロントエンドのビルドにはメモリ 4G 以上を推奨）。
> **旧ディストリビューションでの注意**:Node ≥ 18 の公式ビルドは glibc ≥ 2.28 を要求するため、Ubuntu 18.04（glibc 2.27）では動作しません——[unofficial-builds の glibc-217 ビルド](https://unofficial-builds.nodejs.org/download/release/)を使うか、より新しいシステムに移行してください。
> **中国国内のネットワーク**：GitHub のクローン、npm、Go モジュールにはプロキシ／ミラーが必要な場合があります。参考：`git config --global http.proxy socks5h://127.0.0.1:7890`、`npm config set registry https://registry.npmmirror.com`、`go env -w GOPROXY=https://goproxy.cn,direct`。

```bash
git clone https://github.com/r0th-m/artex-ymh.git
cd artex-ymh
# 1) フロントエンドの静的エクスポート
cd web && npm ci && npm run build:static && cd ..
# 2) 内蔵ディレクトリへコピー（クローン直後でディレクトリが無い場合は先に mkdir -p server/webui/dist）
cp -r web/out server/webui/dist
# 3) ビルド（-tags embedui を付けたときだけフロントエンドを内蔵）
CGO_ENABLED=0 go build -tags embedui -o artex ./cmd/artex
# 4) データベース接続を設定（必須。未設定だと起動しない）
cp config.example.json config.json   # database セクションを編集して記入
./start.sh
```

### 方式 3: systemd による常駐（Linux サーバー推奨）

```bash
sudo install -m644 packaging/artex.service /etc/systemd/system/artex.service
# unit を編集：User= / WorkingDirectory= / ExecStart= を自分のデプロイ用アカウントとインストール先に変更
sudo systemctl daemon-reload && sudo systemctl enable --now artex
journalctl -u artex -f
```

任意の環境変数（例：`ARTEX_CALLBACK_ADDR` のコールバックアドレス）は `/etc/artex.env` に記述します。

### 方式 4: Docker

リポジトリの `docker-compose.yml` は、**ソースから二次開発版のイメージをビルドする**ように設定済みです（`Dockerfile.source`：フロントエンドのビルド → Go のコンパイル → ツールのランタイムをすべて Docker 内で完結し、ホスト側に Go/Node は不要）：

```bash
git clone https://github.com/r0th-m/artex-ymh.git
cd artex-ymh
cp .env.example .env   # POSTGRES_PASSWORD を記入（# 文字は使わない）
docker compose up -d --build
```

⚠️ この compose のイメージを `autumn27/artex` に変更しないでください——それは**アップストリームのオリジナル**であり、二次開発のコードを含みません（2026-09 の実測で踏んだ落とし穴：アップストリームの compose をそのまま使ってデプロイすると、オリジナル版が入ります）。
⚠️ ビルドには apt/npm/Go モジュールのソースへのアクセスが必要です。中国国内のマシンでは、Docker にプロキシ（`~/.docker/config.json` の proxies セクション）またはミラーサイトを先に設定してください。

## 初回利用（重要）

二次開発版では**対偵察用の偽装ゲート**がデフォルトで有効です。ループバック以外で待ち受けている場合、`http://<IP>:8787` に直接アクセスすると nginx のウェルカムページが表示されます（正常な動作です）。

1. 起動ログに入口パスが `[gate] 偽装ゲートを有効にしました。入口パス: /g-xxxxxxxx` の形式で出力されます（`data/gate.path` にも書き込まれます）。
2. ブラウザで `http://<IP>:8787/g-xxxxxxxx` にアクセスし、ゲート口令を入力します（デフォルトは入口パスのランダム文字列と同じ）。
3. 初回は `/setup` で管理者パスワードを設定します。

## 外部ツール（武器庫）とデプロイ自己検査

ペネトレーション能力は一連の外部ツールに依存しており、すべて **`data/tools/`** に配置します：

| ツール | 用途 |
| --- | --- |
| suo5 / chisel / ligolo | トンネルと多層プロキシ（ターゲットが外部ネットワークに出られない／出られる／TUN で接続する場合） |
| gogo / naabu / httpx / katana / fscan | ポートスキャン、HTTP プローブ、クローリング、内部ネットワークの総合スキャン |
| impacket / nxc / mimikatz / pypykatz / laZagne | Windows プロトコルの攻略と認証情報の収集 |
| peass / penelope | 権限昇格の列挙 / リバースシェルハンドラ |

- **バージョン固定リスト**：`packaging/tools-manifest.json` にバージョン／プラットフォーム／sha256／相対パスを記録し、起動時に自己検査します（不一致は警告のみ、空欄は未固定を意味します）。
- **デプロイ事前チェック**：インストール後／アップグレード後に `./artex doctor` を実行します——PG、LLM プロファイル、data の書き込み可否、トンネルツール、武器庫、ゲート、コールバックアドレスを検査し、FAIL 時は終了コード 1 になります。
- ツールは「ツール」ページでカスタムツールとして登録（`kind=shell`）した後、agent が呼び出せるようになります。

## アップグレード

- **再起動でマイグレーション**:schema は起動のたびに冪等に再実行されるため、アップグレードではプログラムだけを入れ替えてデータには触れません（`./data` とデータベースのバックアップは今も良い習慣です）。
- ⚠️ **画面の「ワンクリック更新」は使わないでください**：**アップストリーム**のリリースソースを指しているため、二次開発版がアップストリームのオリジナルで上書きされます。二次開発版のアップグレードは `git pull` と再ビルド（方式 2）で行ってください。

## 設定

**データベース**（`config.json`、または環境変数 `ARTEX_PG_DSN` で上書き）：

```json
{
  "database": {
    "host": "127.0.0.1", "port": 5432,
    "user": "artex", "password": "yourpass",
    "dbname": "artex", "sslmode": "disable"
  }
}
```

**LLM**：画面の「LLM 設定」ページで入力します（推奨）。または `export ANTHROPIC_API_KEY=sk-...` / `OPENAI_API_KEY`。
**よく使うパラメータ**:`./start.sh -addr :8787 -proxy :8788`（`-addr` はフロントエンド + API、`-proxy` はトラフィック記録プロキシで、デフォルトはループバックのみにバインド）。
**同時実行数**：タスクごとの work agent 数は「システム設定」で設定します（デフォルト 3）。

## システム技術アーキテクチャ

ARTEX は **LLM マルチ agent 駆動の自律型ペネトレーションテストシステム**です：Go のモノリシックバックエンド（Next.js フロントエンドを内蔵）＋ PostgreSQL で構成され、agent の能力は [`norma`](https://github.com/Autumn-27/norma) SDK が提供します。中核は**デュアルグラフアーキテクチャ**です：

- **アセットグラフ（全体で共有）**：タスクをまたぐアセットの真実の値のライブラリで、ノードは root_domain/subdomain/ip/service/app/endpoint であり、企業に帰属します。ドメイン → サブドメイン → サービス → エンドポイントの親子関係はプログラムが計算し、agent は生の情報だけを送信します。
- **探索グラフ（タスクごとに独立）**：1 回のタスクの「思考と前進」の過程で、ノードは goal/intent/fact/finding/hint であり、spawns/derived_from/yields/proves のエッジで系譜チェーンを形成します。アンカー（`exploration_anchors`）を介してアセットグラフと接続し、アセットのテストカバレッジを支えます。
- **エンジンはイベント駆動の閉ループ**：グラフが変わると planner を起動 → planner が状況を読み取って意図を割り当て → worker が意図を 1 つ受け取り、実際のツールで実行し、新しいアセット／ファクト／ファインディングを 2 つのグラフに書き戻す → 再び起動。worker 間にはプロセスレベルの情報交換があり（`search_all_worker_traces`）、planner は起動をまたいで共有される todolist を保持し、多段攻撃チェーンを安定させます。

二次開発ではこれに加えて、セッション／トンネル／移管の内部ネットワーク作戦レイヤー、未承認セグメントの承認チェーン、ハニーポット信頼度のデータライン（識別＋防御）、chains のシナリオ化有効化を追加しています。詳細は各設計ドキュメントを参照してください。
